# dynamodb__events__lambda: a DynamoDB-Streams ESM's OnFailure SQS destination is written without authorizing the execution role — a role with no sqs:SendMessage is neither refused at create nor blocked at delivery (1 cause)

> _Note: this issue was identified against the code base at commit `e3f664225c71d6661c778bedbd316f93d7ff916d`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
CreateEventSourceMapping

## Description
One net-new root cause in this service group. The suite did not mark this check as owned by any open issue, so its replay key is new: the previously filed 20261103T062653Z-dynamodb-events-lambda-a-dynamodb-streams-esm-with.md is keyed to this check TIMING OUT with no verdict (Issue-Key '...|run#9|Timeout|time.sleep(4.0)'), i.e. nothing was ever delivered. The emulator's behaviour has since moved on: the failure record IS now produced, but the permission boundary around the destination is not enforced, which is a different defect and is what the check now fails on (AssertionError, not a timeout). Naming that issue for the fixer's benefit; it does not cover this behaviour.

Cause 1 of 1: the OnFailure destination of a DynamoDB-Streams event source mapping is written with no authorization check against the Lambda function's execution role, and CreateEventSourceMapping accepts the mapping without pre-flighting that role's access to the declared destination. Failing check: dynamodb__events__lambda.ddb-stream-esm-destination-missing-permission-rejected.

AWS: Smithy (lambda): CreateEventSourceMapping — POST /2015-03-31/event-source-mappings, success 202, input members DestinationConfig, MaximumRetryAttempts (@range -1..10000), BatchSize (@range 1..10000), StartingPosition; modeled errors include InvalidParameterValueException (client, httpError 400). AWS pre-flights the function execution role's access to the declared DestinationConfig.OnFailure destination and refuses the create with 400 InvalidParameterValueException whose message is the fixed text 'The function execution role does not have permissions to call SendMessage on SQS' (that sentence is entirely fixed — it carries no request- or state-derived values). Where the create is instead accepted, the destination write is still performed under the execution role, so a role without sqs:SendMessage on that queue produces NO delivery at all: the failure record never appears in the OnFailure queue. With sqs:SendMessage granted and MaximumRetryAttempts=0, a handler that raises yields exactly one record whose requestContext.condition is the fixed literal 'RetryAttemptsExhausted', whose requestContext.functionArn is the failing function's ARN (value from state) and which carries DDBStreamBatchInfo.streamArn equal to the table's stream ARN from the request (recorded behavior only for the failure-record document — the Smithy model does not describe it).
Emulator: with an execution role carrying only logs:* and dynamodb:GetRecords/GetShardIterator/DescribeStream/ListStreams and deliberately NO sqs:SendMessage, CreateEventSourceMapping is accepted (no 400 InvalidParameterValueException), and the poller then delivers the failure record to the OnFailure queue anyway. The check's negative leg reads a message off that queue and fails: AssertionError: unexpected failure-destination delivery despite missing sqs:SendMessage: {"version":"1.0",...,"requestContext":{...,"condition":"RetryAttemptsExhausted",...},"DDBStreamBatchInfo":{...}}. So the destination write is performed by the emulator itself rather than on behalf of the execution role, and no IAM evaluation gates it.
Why: a client relying on AWS's behaviour loses the permission boundary on poison-batch routing in both directions. A mis-scoped execution role is never reported at create time, and at runtime records are written to a queue the role is not allowed to send to — so an emulator run 'proves' a least-privilege configuration works that real AWS refuses or silently drops, and negative tests asserting that an unauthorized destination receives nothing pass on AWS and fail here. Anything auditing that failure data only reaches queues the role can write to is given the opposite answer.
Fix: the lambda crate's CreateEventSourceMapping validation (pre-flight the execution role against DestinationConfig.OnFailure and refuse with 400 InvalidParameterValueException and AWS's fixed message) and the event-source-mapping poller's failure-destination write path, which must evaluate the function's execution role against the target SQS queue (sqs:SendMessage on that queue's ARN) before emitting the record and emit nothing when the role does not allow it.
Traces: dynamodb__events__lambda.ddb-stream-esm-destination-missing-permission-rejected.

## Evidence
Cause 1 — Expected (AWS): CreateEventSourceMapping(FunctionName=<fn>, EventSourceArn=<table LatestStreamArn>, BatchSize=1, StartingPosition=TRIM_HORIZON, MaximumRetryAttempts=0, DestinationConfig={"OnFailure": {"Destination": <queue arn>}}) with an execution role holding the dynamodb stream-read grants but NO sqs:SendMessage is either refused with HTTP 400, Error.Code InvalidParameterValueException and Error.Message 'The function execution role does not have permissions to call SendMessage on SQS' (fixed text, no variable parts), or accepted and then NOTHING is ever delivered to that queue. Granting sqs:SendMessage on the queue yields exactly one record with requestContext.condition == 'RetryAttemptsExhausted' (fixed literal), requestContext.functionArn naming the failing function (from state) and DDBStreamBatchInfo.streamArn == the table's stream ARN (from the request).
Actual (emulator): the create is accepted (no refusal observed, so the check enters its no-delivery watch) and ReceiveMessage on the unauthorized OnFailure queue returns a complete failure record within seconds. ## Steps to Reproduce
1. CreateTable with StreamSpecification {StreamEnabled: true, StreamViewType: NEW_AND_OLD_IMAGES}; read LatestStreamArn from DescribeTable. CreateQueue and read its QueueArn.
2. Create an IAM role trusted by lambda.amazonaws.com with an inline policy granting logs:CreateLogGroup/CreateLogStream/PutLogEvents and dynamodb:GetRecords/GetShardIterator/DescribeStream/ListStreams, and deliberately NO sqs:SendMessage.
3. CreateFunction (python3.12) whose handler raises RuntimeError('boom'), using that role.
4. CreateEventSourceMapping(FunctionName=<fn>, EventSourceArn=<stream arn>, BatchSize=1, StartingPosition=TRIM_HORIZON, MaximumRetryAttempts=0, DestinationConfig={"OnFailure": {"Destination": <queue arn>}}).
5. If step 4 was accepted, PutItem into the table and poll ReceiveMessage on the queue for ~60 s.
6. Repeat 1–4 with sqs:SendMessage granted on the queue, PutItem, then poll ReceiveMessage.
On AWS: step 4 is refused with 400 InvalidParameterValueException 'The function execution role does not have permissions to call SendMessage on SQS', or accepted and step 5 yields no message at all; step 6 yields one record with requestContext.condition='RetryAttemptsExhausted', requestContext.functionArn and DDBStreamBatchInfo.streamArn.
On the emulator: step 4 is accepted and step 5 returns a full RetryAttemptsExhausted failure record on the queue the role has no sqs:SendMessage for.
