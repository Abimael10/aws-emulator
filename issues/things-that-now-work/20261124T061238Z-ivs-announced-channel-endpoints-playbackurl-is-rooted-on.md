# IVS announced channel endpoints: playbackUrl is rooted on a ported authority and the two ingest members on a label-only name, so all three members miss AWS's recorded host form

> _Note: this issue was identified against the code base at commit `8eafbfe472cca10e84a381a72d022fc472517ee6`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
CreateChannel

## Description
Cause 1 of 1: the shared channel-endpoint projection composes the three address members of every Channel it announces (`$.channel.ingestEndpoint`, `$.channel.playbackUrl`, `$.channel.srt.endpoint`) outside the host form AWS's recording holds for them, on an otherwise correct 200 CreateChannel response (expected 200, got 200 — only the member values diverge). Replaying the wire corpus leaves this as the ONLY net-new divergence cluster for service `ivs`: the replay reports owned_by [] and stub_path "" for it, while the other five clusters of this run (DeleteStreamKey/TagResource/UntagResource content-length, InsertAdBreak, GetStreamSession) all carry a non-empty owned_by and are skipped.

AWS: recorded behavior only. Smithy (services/service-com-amazonaws-ivs-amazoninteractivevideoservice/smithy-model/com-amazonaws-ivs-amazoninteractivevideoservice.json, com.amazonaws.ivs, restJson1): `Channel$ingestEndpoint` -> `IngestEndpoint` ("Channel ingest endpoint, part of the definition of an ingest server, used when you set up streaming software"), `Channel$playbackUrl` -> `PlaybackURL` ("URL of the master playlist, required by the video player to play the HLS stream") and `Srt$endpoint` are plain strings with NO @length and NO @pattern, so the model pins no form and the recording is the only authority. The corpus does not pin the values literally — it reports all three `<shaped-not-asserted>`, because the minted label, Region, account id and channel id are per-run — it pins their SHAPE CLASS, and the recording establishes that class as: (a) `ingestEndpoint` is a DNS HOSTNAME, a minted label under a service-owned contribute domain (`<label>.global-contribute.<service domain>`), carrying no scheme, no port and no path, because the client composes the authority itself and appends the port its protocol dials (`rtmps://<ingestEndpoint>:443/app/<streamKey>`, `srt://<srt.endpoint>:<port>`); (b) `srt.endpoint` is the SAME host as `ingestEndpoint` (corroborated inside this corpus by ivs-batch-get-channel-and-stream-key#task#3, where `$.channels[0].ingestEndpoint` and `$.channels[0].srt.endpoint` are one identical host); (c) `playbackUrl` is an `https://` URL whose HOST is a hostname of that same class — a label plus a domain, with NO port, since AWS serves the playlist on 443 — and whose path is the recorded `/api/video/v1/<region>.<account>.channel.<channel-id>.m3u8` layout. Hostname form (label plus domain), the absence of a port, the identity of the two ingest members, the https scheme and the path layout are the requirement; the particular label, domain, port and ids any one run produces are not.

Emulator: the replay reports all three members as value/shape mismatches against that class on a 200 response. The two ingest members come back as a minted label under the emulator's own zone only (`<12-hex-label>.global-contribute.ivs.<zone>`, this run `04dd86d4eacc.global-contribute.ivs.localhost`) — port-less and identical to each other, but still off the recorded class — while `playbackUrl` comes back rooted on the bare reached authority WITH an explicit port (`https://<zone-name>:<port>/api/video/v1/<region>.<account>.channel.<id>.m3u8`, this run `https://localhost:44219/...`): a host that carries no label at all and a `:<port>` the recorded form never has, so within one response the playback host is not even of the same class as the ingest host beside it. The path layout is kept correctly. src/ops/create_channel.rs (lines 252-281) deliberately stores `ingest_endpoint: None`, `playback_url: None` and `Srt.endpoint: None` and defers all three to `crate::state::announced_channel`, which composes them per request: src/state/channel_endpoints.rs `announced_ingest_endpoint`/`contribute_host_in` (lines 158-197) formats `{minted_host_label}.global-contribute.ivs.{announced_zone}`, and `playback_host` (lines 237-264) returns the reached `host[:port]`, deliberately keeping the port (see that function's own doc comment and the module header lines 46-58, which argue the operator's port must be kept) — which is exactly the half of the value the recorded class does not carry.

Why: a client does not treat these as opaque strings. It composes `rtmps://<ingestEndpoint>:443/app/<streamKey>` or `srt://<srt.endpoint>:<port>` from the ingest host, and for playback it parses the URL's host to pick a CDN, to assert TLS by hostname, or to recognise the channel/Region label AWS puts there; a host with no label, or one carrying an explicit non-443 port, breaks host-pattern validation, hostname-pinned TLS and any code that stores the value in a hostname-typed field. Code written against AWS's recorded endpoint shapes therefore mis-handles every channel this emulator reports — and because the same projection serves GetChannel, BatchGetChannel, UpdateChannel and the stream reads (`announced_stream`), the divergence is on every channel-bearing response, not just the create.

Fix: the shared channel-endpoint projection in services/service-com-amazonaws-ivs-amazoninteractivevideoservice/src/state/channel_endpoints.rs — `announced_channel` and the two composers it delegates to, `announced_ingest_endpoint`/`contribute_host_in` and `announced_playback_url`/`playback_host` — not the serializer and not the store, since none of the three members is ever persisted (create_channel.rs sets all three to None by design). It must announce one host class for all three: a hostname made of a minted label plus a domain, no scheme and no port for `ingestEndpoint` and the `srt.endpoint` that equals it, and a host of that same class (label plus domain, no port) inside the `https://.../api/video/v1/<region>.<account>.channel.<id>.m3u8` playback URL. Note two related open issues, NEITHER of which owns this cluster: 20261123T105030Z-ivs-2-net-new-causes-createchannel-announces-loopback.md describes an earlier spelling of this same cause but carries only the `$.channel.srt.endpoint` key for CreateChannel (the replay confirms the non-ownership by reporting owned_by [] for this cluster, and its GetStreamSession cause is the one that now owns divergence #4); 20261122T024053Z-ivs-the-channel-rtmps-ingest-data-plane-is.md is a behavioral finding requiring the announced contribute address be an authority this process actually answers RTMPS on. Whatever host is chosen must satisfy both: AWS's recorded member form AND reachability inside the deployment.

Traces: ivs-channel-lifecycle#task#1 (representative), ivs-viewer-session-revocation#setup#1 (same cluster); recorded shape corroboration ivs-batch-get-channel-and-stream-key#task#3.
