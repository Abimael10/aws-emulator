# glue: 2 net-new causes — CreateCrawler never accepts a crawler built on a freshly created Glue-assumable role (every crawler check exhausts its budget), and GetTable materializes empty StorageDescriptor.Parameters / SerdeInfo.Parameters maps the caller never sent

> _Note: this issue was identified against the code base at commit `96b6253dc6ea8319b5f1ad39858d0c023680de77`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
CreateCrawler

## Description
2 causes; both must be closed before submitting.

Related open issues, named for the fixer, none of which carries the replay keys listed here: 20261030T063753Z-glue-startcrawler-refuses-every-crawl-501-notimplemented-so.md (StartCrawler 501), 20261111T052620Z-glue-stopcrawler-stub.md (StopCrawler stub), 20261111T052620Z-glue-2-net-new-causes-startcrawler-on-a.md (StartCrawler/DeleteCrawler refusal messages) and Cause 3 of 20261029T185330Z-glue-9-net-new-root-causes-in-control.md (CreateCrawler skips the event-mode SQS permission check) all touch the crawler surface, but none of them describes a CreateCrawler that cannot create an ordinary S3-target crawler at all, which is what Cause 1 is.

Cause 1 of 2: CreateCrawler never accepts a crawler whose Role is a freshly created Glue-assumable IAM role, so the whole crawler group is unreachable.
AWS: Smithy: CreateCrawler takes required Name (NameString), Role and Targets (CrawlerTargets) and models exactly AlreadyExistsException, InvalidInputException, OperationTimeoutException and ResourceNumberLimitExceededException (all errorKind client, HTTP 400). Real Glue accepts a crawler whose Role is an IAM role trusting glue.amazonaws.com with the AWSGlueServiceRole managed policy attached and whose Targets are {"S3Targets": [{"Path": "s3://<bucket>/<prefix>/"}]}, answering 200 with an empty body; GetCrawler then reports Crawler.State "READY". The only refusal real Glue makes in that window is a TRANSIENT InvalidInputException/AccessDeniedException while the just-attached role trust propagates to Glue's AssumeRole probe, and it clears within seconds — which is why every one of these checks wraps CreateCrawler in a deadline-bounded retry that retries precisely those two codes.
Emulator: all five crawler checks end with "Check timed out after 60.0s" and produce no response payload at all. Two of them — glue.create-crawler-no-targets-fails and glue.reject-get-nonexistent-crawler — contain no other wait of any kind: their only cost that can span the budget is the CreateCrawler propagation-retry loop (90 s and 60 s deadlines respectively), whose retry predicate is exactly {InvalidInputException, AccessDeniedException}. Hypothesis: CreateCrawler keeps answering one of those two codes (or never answers) for a role and S3 target real Glue accepts, so the loop never converges and no crawler is ever created; the exhausted budget is the only thing the replay can observe. The downstream assertions those checks exist for are therefore never reached: the no-targets rejection (InvalidInputException with the fixed message "Targets are not defined"), the absent-crawler rejection (EntityNotFoundException with "Crawler entry with name <name> does not exist", where <name> is the requested crawler name from the request), the concurrent-start rejection (CrawlerRunningException with "Crawler with name <name> has already started"), the Schedule.State walk NOT_SCHEDULED -> SCHEDULED -> NOT_SCHEDULED driven by UpdateCrawlerSchedule/StopCrawlerSchedule, and BatchGetCrawlers' split of found crawlers vs CrawlersNotFound.
Why: a client cannot create a plain S3 crawler at all, so every crawler workflow — create, start, schedule, poll back to READY, metrics, ListCrawls, and every negative class above — is unreachable rather than merely wrong. Clients that use Glue's documented convergent create-then-retry pattern around IAM propagation spin until their own deadline and then fail, and a caller cannot distinguish a genuinely invalid crawler definition from the emulator's blanket refusal.
Fix: the CreateCrawler handler and the crawler state it writes (services/service-com-amazonaws-glue-awsglue/src/ops/create_crawler.rs and the crawler entry in the glue crate's state): accept a crawler whose Role is an existing role trusting glue.amazonaws.com with an ordinary S3 target, persist it with State READY, and keep the refusal set to the four modeled errors (InvalidInputException for an empty Targets map, never for a valid role).
Traces: glue.create-crawler-no-targets-fails, glue.reject-get-nonexistent-crawler, glue.crawler-create-start-poll-ready, glue.crawler-schedule-state-machine, glue.start-crawler-already-running-fails.

Cause 2 of 2: the catalog invents empty Parameters maps on StorageDescriptor and SerdeInfo that the caller never sent.
AWS: Smithy: StorageDescriptor$Parameters and SerDeInfo$Parameters both target ParametersMap and carry NO @default, so they are plain optional members; the same is true of StorageDescriptor$BucketColumns, StorageDescriptor$SkewedInfo, Table$PartitionKeys, Table$Owner and Table$LastAccessTime. Real Glue round-trips a table exactly as declared: an optional map or structure the caller omitted from TableInput is ABSENT from the GetTable response, while the documented scalar defaults are filled in (Table.Retention 0, Table.VersionId "0", Table.IsRegisteredWithLakeFormation false, StorageDescriptor.Compressed false, StorageDescriptor.NumberOfBuckets 0, StorageDescriptor.StoredAsSubDirectories false, StorageDescriptor.SortColumns []).
Emulator: for a CreateTable whose StorageDescriptor carried Columns/Location/InputFormat/OutputFormat/SerdeInfo and no Parameters, GetTable comes back with StorageDescriptor.Parameters PRESENT as an empty map; and for a SerdeInfo declared as {"SerializationLibrary": "<lib>"} alone, GetTable returns SerdeInfo as {"SerializationLibrary": "<lib>", "Parameters": {}}. The emulator materializes an empty ParametersMap instead of omitting the member. (Both checks show this on the plain API route, with no DDL/Athena involvement.)
Why: a client that diffs GetTable against the TableInput it submitted — the converge loop of CloudFormation/CDK/Terraform and of any catalog-sync tool — sees a permanent spurious drift on a table it just created, and re-applies forever. A client that tests for the PRESENCE of StorageDescriptor.Parameters or SerdeInfo.Parameters to decide whether serde/table properties were ever configured reads a false positive where AWS tells it nothing was set.
Fix: the table serialization used by GetTable and the table representation CreateTable stores (services/service-com-amazonaws-glue-awsglue/src/ops/get_table.rs and create_table.rs plus the table state in the glue crate): keep an optional, unsupplied map or structure absent on the wire rather than defaulting it to an empty collection, while continuing to fill the scalar catalog defaults listed above.
Traces: glue.glue-table-round-trips-the-cloudfront-log-schema-and-fills-catalog-defaults, glue.glue-tsd-external-table-schema-round-trips-with-catalog-defaults.
