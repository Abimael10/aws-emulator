# launchwizard deployment-pattern-version reads still diverge: pagination ignored and featureFlags capability state invented

> _Note: this issue was identified against the code base at commit `ff9b1a3de0df56cf19d04ad7446f3f4c83c2512c`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
ListDeploymentPatternVersions

## Description
Both launchwizard deployment-pattern-version reads answer HTTP 200 with a body that is not the one the recorded service returns for the same request. The shared fault is that the deployment-pattern-version projection is still served straight out of the emulator's seed: no paging layer bounds or continues the list, and the per-version capability block (featureFlags) is synthesised by the emulator rather than carrying the version's actual capability state. 2 causes.

NOTE on prior art: open issue 20261115T082538Z-launch-wizard-workload-catalog-is-seeded-with-invented-entries-list.md covers the workload/deployment-pattern CATALOG content on the 'launch-wizard' token and carries no replay key for task#5 or task#6. The issue that previously carried those two keys, 20261110T073938Z-launchwizard-deployment-pattern-version-responses-ignore-pagination-and-omit.md, is RESOLVED, and the replay reports both steps still diverging with no owning open issue (owned_by empty). The featureFlags member it asked for is now emitted, but with invented capability state (Cause 2), and the pagination defect it asked for is unchanged (Cause 1).

--- Cause 1 of 2: ListDeploymentPatternVersions ignores the paging inputs and never emits nextToken (fixture launch-wizard-workload-catalog-discovery, step task#5) ---
AWS: Smithy: ListDeploymentPatternVersions, POST /listDeploymentPatternVersions, success 200; input workloadName (required), deploymentPatternName (required), maxResults: MaxWorkloadResults @range 1..100, nextToken: NextToken @length 1..2048, filters: FilterList; output deploymentPatternVersions: DeploymentPatternVersionDataSummaryList plus nextToken: NextToken @length 1..2048; @paginated {inputToken: nextToken, outputToken: nextToken, pageSize: maxResults, items: deploymentPatternVersions}. The @paginated contract is the requirement: the service answers with ONE page of deploymentPatternVersions bounded by the request (not the whole collection), and whenever further results remain it also serializes nextToken, an opaque continuation value the client sends back as the next request's nextToken. The recording for this step shows exactly that paged shape — the response carries a nextToken (the corpus sanitizes the value to 'opaque-pagination-token' because the token's bytes are per-run) and does NOT carry the emulator's three seeded version entries. Fixed part of the requirement: one bounded page plus a nextToken while a further page exists, and the token resumes the listing. Variable: the page contents, the page size, and the token's literal bytes. Hypothesis: the recorded request narrows the first page (via maxResults and/or filters) so that the page carries no entry of its own while more results remain — legal, and the reason clients must loop on nextToken rather than on a non-empty page.
Emulator: 200, but $.deploymentPatternVersions holds three entries the recording's page does not contain — [0] deploymentPatternVersionName '1.0.27', [1] '1.0.1', [2] '1.0.0', all for workloadName 'SAP' / deploymentPatternName 'SapHanaHA', each with a synthesised 'Version <n> of this deployment pattern. ...' description and each now also carrying an emulator-authored featureFlags block (see Cause 2) — every one flagged 'extra (expected None, got ...)', and $.nextToken is absent ('missing (expected "opaque-pagination-token", got None)'). The paging inputs have no effect on the body: the entire seeded version list is emitted on every call as a single terminal page.
Why: a client that paginates correctly is wrong in both directions. With nextToken never emitted, an SDK paginator stops after the first response, so a client whose catalog genuinely exceeds one page silently truncates its view of the available versions; with maxResults/filters unapplied, a client that asked for a bounded page is handed the whole collection, so every assertion on page size, page boundary or continuation round-trip fails. Pagination-loop code validated against the emulator is never actually exercised, and the defect it exists to catch escapes to a real endpoint.
Fix: the ListDeploymentPatternVersions handler and its state query in the launchwizard crate — slice the version collection into a page using maxResults (and filters), mint an opaque nextToken whenever unserved entries remain, resume from a supplied nextToken on the next call, and have the serializer emit nextToken only while a further page exists.

--- Cause 2 of 2: GetDeploymentPatternVersion reports invented capability state in featureFlags (modifyDeployments ENABLED, a non-empty updateFromVersion) (fixture launch-wizard-workload-catalog-discovery, step task#6) ---
AWS: Smithy: GetDeploymentPatternVersion, POST /getDeploymentPatternVersion, success 200, output member deploymentPatternVersion: DeploymentPatternVersionDataSummary; errors ResourceNotFoundException (404), InternalServerException (500). The on-disk model's DeploymentPatternVersionDataSummary declares only deploymentPatternVersionName, description, documentationUrl, workloadName and deploymentPatternName — it does not declare featureFlags — so for this member: recorded behavior only. The recording shows featureFlags present and describing which optional deployment capabilities THIS version supports, one entry per capability with that capability's status (and an empty configuration/list where it has none): cloudFormationOutput {configuration: {fields: []}, status: 'DISABLED'}, modifyDeployments {status: 'DISABLED'}, postDeploymentSteps {status: 'DISABLED'}, updateFromVersion: []. The requirement is that each capability's status, and the upgrade-source list, reflect the version's real capability state; the particular 'DISABLED' values and the empty collections above are that version's state, not fixed text.
Emulator: 200, featureFlags now present but its contents are emulator-authored rather than the version's state: $.deploymentPatternVersion.featureFlags.modifyDeployments.status is 'ENABLED' where the recording has 'DISABLED' (value_mismatch), and featureFlags.updateFromVersion carries two extra entries ('1.0.1', '1.0.0' — i.e. every OTHER seeded version of the same pattern) where the recording has an empty list. The pattern of the extras in Cause 1 shows how the block is produced: modifyDeployments is hard-set ENABLED and updateFromVersion is derived mechanically as 'all sibling versions', so each listed version claims it can be upgraded from the others.
Why: featureFlags is how a client decides what it may do with a deployment pattern version. A capability advertised ENABLED that the version does not support leads a client to offer and attempt a modify-deployment flow the service refuses, and an upgrade-source list containing every sibling version leads it to offer upgrade paths that do not exist. Capability-gated client paths therefore take the wrong branch against the emulator and cannot be tested at all: the emulator says yes where the service says no.
Fix: the GetDeploymentPatternVersion handler/serializer and the deployment-pattern-version seed in the launchwizard crate — carry each version's real capability state on the seed (per-capability status plus its configuration, and the set of versions it can genuinely be updated from) and serialize that, instead of hard-coding modifyDeployments ENABLED and deriving updateFromVersion from the sibling version list. The same projection feeds the list operation, so it must be fixed once for both reads.
