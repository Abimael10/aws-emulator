# s3tables ValidationException constraint messages diverge: enum value set is not rendered in AWS's order, and a list-member length violation reports the indexed member path with a single bound instead of AWS's aggregate constraint-set form

> _Note: this issue was identified against the code base at commit `9eefc33eaece22bd4a7a53f7a36483a2f6e00b07`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
PutTableBucketStorageClass

## Description
Two net-new root causes in the s3tables framework-level constraint-violation MESSAGE rendering. Both refusals now carry the right HTTP status (400) and the right error code (`ValidationException`), so only the message text diverges — and for these framework validation errors the message is the sole discriminator of which member failed and why. Both causes must be closed before this issue is submitted.

These are distinct from, and not covered by, the open issues that named the same two paths for a DIFFERENT cause: 20261107T202917Z-s3tables-puttablebucketstorageclass-refuses-an-out-of-enum-storageclass.md and 20261114T194147Z-s3tables-untagresource-with-an-over-length-tag-key.md each recorded the refusal arriving as `BadRequestException`; in this replay the code is `ValidationException` on both paths and the checks now fail one assertion later, on the message. The generic-template faults recorded in 20261101T233620Z-s3tables-refusals-diverge-enum-pattern-violations-answer-validationexception.md (cause 5: the value is echoed, the pattern keeps its ^/$ anchors) are also not these: the emulator no longer echoes the value on either path here. The replay did not mark either check as owned by any open issue.

Cause 1 of 2: the enum value list in the enum-constraint sentence is not rendered in AWS's order.
AWS: PutTableBucketStorageClass with storageClassConfiguration.storageClass outside the modeled enum is refused HTTP 400, code `ValidationException`, message "1 validation error detected: Value at '<member path>' failed to satisfy constraint: Member must satisfy enum value set: [<enum values>]". Fixed text: "1 validation error detected: Value at '", "' failed to satisfy constraint: Member must satisfy enum value set: [", "]". Variable parts: the member path derived from the request's shape path (here `storageClassConfiguration.storageClass`) and the enum's value list, which AWS renders comma-space separated in ASCII-sorted order — for this member `[INTELLIGENT_TIERING, STANDARD]`. The offending value is not quoted. Smithy (services/service-com-amazonaws-s3tables-s3tablebuckets/smithy-model/com-amazonaws-s3tables-s3tablebuckets.json): PutTableBucketStorageClass input = tableBucketARN (@httpLabel @required @pattern ^(arn:aws[-a-z0-9]*:[a-z0-9]+:[-a-z0-9]*:[0-9]{12}:bucket/[a-z0-9_-]{3,63})$) + storageClassConfiguration (@required); StorageClassConfiguration.storageClass -> StorageClass (@enum, declaration order [STANDARD, INTELLIGENT_TIERING], @required); modeled errors BadRequestException(400), ConflictException(409), ForbiddenException(403), NotFoundException(404), TooManyRequestsException(429), InternalServerErrorException(500) — no ValidationException shape is bound anywhere in the service model, so the code is the framework's untyped validation refusal: recorded behavior only for the code and the ordering of the bracketed list.
Emulator: 400 `ValidationException` with the member path right but the list in model-declaration order — "1 validation error detected: Value at 'storageClassConfiguration.storageClass' failed to satisfy constraint: Member must satisfy enum value set: [STANDARD, INTELLIGENT_TIERING]".
Why: this sentence is the only machine-readable part of the refusal (the service models no ValidationException and no sub-code), so a client or SDK test that matches the refusal message, or surfaces the allowed-value list to a user, does not recognise the error and reports a different allowed-value list than AWS does for the same request.
Fix: the framework constraint-violation message formatter used by this service's request validation (the enum branch) — render the enum's values sorted, not in model-declaration order.
Traces: s3tables.put-table-bucket-storage-class-invalid-value-rejected, s3tables.put-table-bucket-storage-class-conflicting-active-tables-blocked.

Cause 2 of 2: a length violation on a LIST MEMBER is reported against the indexed member path with the single violated bound, instead of AWS's aggregate form on the list path.
AWS: UntagResource whose `tagKeys` list contains a key longer than the modeled 128-character maximum is refused HTTP 400, code `ValidationException`, message "1 validation error detected: Value at '<list member path>' failed to satisfy constraint: Member must satisfy constraint: [Member must have length less than or equal to <max>, Member must have length greater than or equal to <min>]". Fixed text: "1 validation error detected: Value at '", "' failed to satisfy constraint: Member must satisfy constraint: [Member must have length less than or equal to ", ", Member must have length greater than or equal to ", "]". Variable parts: the path of the LIST member as named in the request (here `tagKeys` — no element index and no `.member` suffix) and the two bounds taken from the model (128 and 1), reported as a set regardless of which bound was violated. The offending value is not quoted. The refused call has no effect: a tag already on the resource survives it, and untagging the well-formed key afterwards removes it. Smithy: UntagResourceRequest.tagKeys -> TagKeyList (@required, @httpQuery("tagKeys")); TagKeyList.member -> TagKey @length(min 1, max 128); http DELETE /tag/{resourceArn}, success 204.
Emulator: 400 `ValidationException` with "1 validation error detected: Value at 'tagKeys.1.member' failed to satisfy constraint: Member must have length less than or equal to 128" — it names the indexed element path `tagKeys.1.member` where AWS names the list `tagKeys`, and reports only the violated upper bound instead of the bracketed constraint set containing both bounds.
Why: the message is the only part of the refusal that identifies the offending member, so a client that parses it to point at a field receives a path that does not exist in AWS's vocabulary, and a client matching the exact sentence never matches. The indexed form also makes the message vary with the element's position where AWS's does not.
Fix: the same framework constraint-violation message formatter (the collection-member branch) — for a constraint declared on a list's member, report the LIST's request path and the member's full constraint set in brackets, rather than the indexed element path and the one violated bound.
Traces: s3tables.untag-resource-malformed-tag-key-rejected.
