# iot: 2 net-new causes — DeleteProvisioningTemplate deletes a template a registered CA still references for auto-registration, and CreateDomainConfiguration's nonexistent-certificate refusal names the validation certificate instead of the server certificate

> _Note: this issue was identified against the code base at commit `3b67cbc843a1c36f429f2495723307b26dcafbd5`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
DeleteProvisioningTemplate

## Description
Two independent net-new root causes under the suite heading '### iot'. They sit in different handlers and close independently. Causes are numbered; a fixer must close BOTH before submitting.

Cause 1 of 2: DeleteProvisioningTemplate SUCCEEDS while a registered CA certificate's registrationConfig still names the template for just-in-time provisioning (JITP).
  Failing check: iot.delete-provisioning-template-in-use-rejected.
  AWS: Smithy (services/service-com-amazonaws-iot-awsiotservice/smithy-model/com-amazonaws-iot-awsiotservice.json): DeleteProvisioningTemplate -> DELETE /provisioning-templates/{templateName}, templateName @httpLabel @required (len 1..36, pattern ^[0-9A-Za-z_-]+$), output {} with success code 200; modeled errors DeleteConflictException (httpError 409), ConflictingResourceUpdateException (409), InvalidRequestException (400), ResourceNotFoundException (404), ThrottlingException (400), UnauthorizedException (401). RegisterCACertificate -> POST /cacertificate carries registrationConfig (which holds templateName) and allowAutoRegistration. Recorded behavior: while a CA certificate registered with registrationConfig.templateName = <templateName> (allowAutoRegistration=true) still exists, DeleteProvisioningTemplate on that template is REFUSED with HTTP 409, error code DeleteConflictException and the message "The template <templateName> cannot be deleted as it is associated with one or more CAs for auto registration." — fixed text "The template " + " cannot be deleted as it is associated with one or more CAs for auto registration.", with the ONLY variable part being the templateName taken from the request. Nothing is removed: a following DescribeProvisioningTemplate still returns the template. Once the referencing CA certificate is removed (DeleteCACertificate), the same delete succeeds with HTTP 200 and an empty body, after which DescribeProvisioningTemplate answers 404 ResourceNotFoundException "Unable to find template named <templateName>" (fixed text "Unable to find template named " + the requested name).
  Emulator: the delete returns HTTP 200 with an empty JSON body and the template is gone, with no reference check at all. services/service-com-amazonaws-iot-awsiotservice/src/ops/delete_provisioning_template.rs removes the entry from `provisioning_templates` unconditionally and models only the not-found branch (ResourceNotFoundException when nothing was removed); no registered-CA registrationConfig is consulted, and DeleteConflictException is never constructed for this operation even though the model declares it.
  Why: this is the overly-permissive direction. A caller that relies on the refusal to protect a template wired into a CA's auto-registration path destroys it in the emulator and is refused 409 by AWS, so teardown ordering and guard logic that passes in test fails in production. Worse, the emulator is left in a state AWS cannot reach: a CA certificate with allowAutoRegistration=true whose registrationConfig names a template that no longer exists, so every subsequent JITP device enrolment through that CA has no template to apply, and the negative control (refusal, then success after the reference is released) is unverifiable.
  Fix: the DeleteProvisioningTemplate handler's pre-delete guard (services/service-com-amazonaws-iot-awsiotservice/src/ops/delete_provisioning_template.rs) — before removing anything, scan the registered CA certificates for any whose registrationConfig names the requested template and return the modeled DeleteConflictException (409) with AWS's wording, leaving the template in place; delete only when no CA references it.
  Traces: iot.delete-provisioning-template-in-use-rejected (the JITP template create, the CA registration with registrationConfig and the role setup all passed; the check dies on the first delete, which returned 200).

Cause 2 of 2: CreateDomainConfiguration's "certificate does not exist" refusal names the validationCertificateArn where AWS names the server certificate ARN, because the handler validates the two in the wrong order.
  Failing check: iot.negative-domain-configuration-invalid-certificate-blocked.
  AWS: Smithy: CreateDomainConfiguration -> POST /domainConfigurations/{domainConfigurationName} (success 200); input serverCertificateArns (ServerCertificateArns, list len 0..1), validationCertificateArn (AcmCertificateArn, len 1..2048, pattern ^arn:aws(-cn|-us-gov|-iso-b|-iso)?:acm:...:certificate/[a-zA-Z0-9/-]+$), domainName (len 1..253), serviceType (enum); modeled errors include InvalidRequestException (httpError 400) and CertificateValidationException (400). Recorded behavior: when BOTH serverCertificateArns=[A] and validationCertificateArn=B are supplied and NEITHER names a certificate the account holds in ACM, AWS refuses with HTTP 400, error code InvalidRequestException and the message "Certificate <A> does not exist." — the SERVER certificate ARN, i.e. AWS resolves serverCertificateArns first. Fixed text is "Certificate " + " does not exist."; the only variable part is the ARN value taken from the request's serverCertificateArns[0] (never a literal ARN from one run).
  Emulator: HTTP 400 and InvalidRequestException are correct, but the message is "Certificate <B> does not exist." — the same template filled with the validationCertificateArn from the request. In services/service-com-amazonaws-iot-awsiotservice/src/ops/create_domain_configuration.rs the existence lookup for validation_certificate_arn (and its trusted-CA test) runs BEFORE the loop over server_certificate_arns, so whenever a validation certificate is supplied its ARN is the one that reaches `crate::state::missing_acm_certificate_message` and the server certificate ARN is never reported.
  Why: a client reading the refusal to decide WHICH certificate ARN to fix (or asserting on the recorded message, as this check does) is pointed at the wrong input member: it re-imports or re-issues the validation certificate while the server certificate ARN that AWS actually rejected stays broken, so the create keeps failing for a reason the message never names. The status and code match, so the divergence is invisible except in the message text.
  Fix: the CreateDomainConfiguration handler's certificate-existence ordering (services/service-com-amazonaws-iot-awsiotservice/src/ops/create_domain_configuration.rs) — resolve the serverCertificateArns entries against the ACM store first and refuse naming the server certificate ARN, then resolve the validationCertificateArn (existence, then trusted-CA chain). Leave the message template itself alone; only the ARN it is filled with is wrong.
  Related open/fixed issues, neither of which covers this cause: 20261114T165150Z-iot-4-net-new-causes-createdomainconfiguration-accepts-a.md (open) is about a self-signed validation certificate being ACCEPTED, and 20261114T082236Z-iot-control-plane-gaps-9-causes-untrusted-domain.md (fixed) states the non-existent-ARN leg "is refused correctly" — it is refused with the right status and code, but names the wrong ARN, which this cause reports.
  Traces: iot.negative-domain-configuration-invalid-certificate-blocked (the InvalidRequestException code assertion passed; the check dies on the message assertion before the DescribeDomainConfiguration 404 leg, which is therefore unverified).
