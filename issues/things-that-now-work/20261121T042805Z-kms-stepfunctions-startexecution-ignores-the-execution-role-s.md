# kms__stepfunctions: StartExecution ignores the execution role's trust-policy Conditions (aws:SourceAccount / aws:SourceArn) and starts an execution under a role Step Functions can never assume

> _Note: this issue was identified against the code base at commit `2f215cd8a92428a081069d88561cad2cfdd06f78`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
StartExecution

## Description
Cause 1 of 1: the trust policy of a CMK-encrypted state machine's execution role is not evaluated at StartExecution, so a role whose `Condition` block can never match the starting machine is treated as assumable and the execution is started instead of refused.
Failing check ids: kms__stepfunctions.sfn-execution-role-trust-honors-source-account-and-source-arn, kms__stepfunctions.sfn-execution-role-trust-source-account-mismatch-blocks-cmk-execution.

AWS: Smithy models StartExecution{stateMachineArn (required, Arn, length 1-256), name, input, traceHeader} -> {executionArn (required), startDate (required)}, with KmsAccessDeniedException / KmsInvalidStateException / KmsThrottlingException / StateMachineDoesNotExist / StateMachineDeleting / ValidationException all client errors at HTTP 400 (model: services/service-com-amazonaws-sfn-awsstepfunctions/smithy-model/com-amazonaws-sfn-awsstepfunctions.json). The model says nothing about roleArn beyond it being an Arn, so the trust-evaluation rule is recorded behavior only: when the execution role's trust statement for Service `states.amazonaws.com` carries a Condition that the starting state machine does not satisfy — `StringEquals aws:SourceAccount` naming an account other than the caller's, or `ArnLike aws:SourceArn` naming a state machine other than the one being started — Step Functions cannot assume the role, and StartExecution on a CUSTOMER_MANAGED_KMS_KEY STANDARD machine is refused HTTP 400 with error code `KmsAccessDeniedException`. The message is the relayed STS failure; its fixed text is "com.amazonaws.sfn.invoker.sts.AssumeRoleFailedCacheableException: The principal states.amazonaws.com is not authorized to assume the provided role. (role: <role ARN>)" — every word is fixed except <role ARN>, which is the state machine's configured roleArn taken from emulator state. The refusal is permanent: unlike an IAM/KMS propagation window it never clears on retry, and that permanence is how a client tells the two apart. The matching positive legs succeed: a trust whose aws:SourceAccount equals the caller's account and whose aws:SourceArn ArnLike pattern matches the machine (a wildcard over the account's state machines, or the machine's exact ARN) lets a CMK-encrypted STANDARD execution reach SUCCEEDED and an EXPRESS StartSyncExecution return status SUCCEEDED.

Emulator: the Condition block is never consulted. StartExecution returns HTTP 200 with an executionArn for the un-assumable role in both grounding checks — the aws:SourceArn-mismatch twin (`...:stateMachine:no-such-machine`) and the foreign-aws:SourceAccount twin — so no KmsAccessDeniedException, no relayed AssumeRoleFailedCacheableException message, and the retry loop that waits for the permanent denial instead trips its "StartExecution unexpectedly started ... against the mismatched trust" / "StartExecution unexpectedly succeeded against the mismatched trust" guard. The positive legs of both checks now pass, so the divergence is confined to the negative path: trust Conditions are inert rather than mis-worded.

Why: aws:SourceAccount/aws:SourceArn on a service trust policy is AWS's standard confused-deputy guard. A client that hardens or audits an execution role this way is told the hardening works when it does not — the emulator starts executions under a role that real Step Functions could never assume, so a cross-account or cross-machine confused-deputy test passes against the emulator and fails in production. A client whose correct AWS retry loop retries the transient KMS code and stops on the permanent assume-role message never sees that message, and a caller that relies on a typed 400 to detect a broken role instead gets a running execution it must reconcile.

Fix: the role-assumption step of the StartExecution handler, ahead of the CMK data-key acquisition — evaluate the configured roleArn's trust policy, including the statement's Condition operators (StringEquals on aws:SourceAccount against the calling account, ArnLike on aws:SourceArn against the starting state machine's ARN), and when the assume fails, refuse the call with KmsAccessDeniedException whose message is the relayed AssumeRoleFailedCacheableException text above, creating no execution.
