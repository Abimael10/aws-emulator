# events: 4 net-new causes — PutTargets accepts an event-bus target with no RoleArn, cross-region bus forwarding reuses the origin EventId, and both InputTransformer rendering checks reach no verdict

> _Note: this issue was identified against the code base at commit `a601a0673e97812614567916cf1f1aa5edd20820`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
PutTargets

## Description
Four net-new root causes in EventBridge (suite service heading `events`). Each must be closed before submitting.

Cause 1 of 4: PutTargets accepts an event-bus target that carries no RoleArn, in this Region and cross-Region alike.
AWS: a Target whose Arn is an event bus must carry a RoleArn — EventBridge assumes that role to call events:PutEvents on the destination bus (Smithy, com-amazonaws-eventbridge-awsevents, Target$RoleArn: "The Amazon Resource Name (ARN) of the IAM role to be used for this target when the rule is triggered"). A PutTargets request that names a bus ARN without RoleArn is refused whole with HTTP 400 ValidationException and the message "RoleArn is required for target <bus arn>." — fixed text "RoleArn is required for target " + the offending Target's Arn + ".", the ARN being the value taken from the request. Because the request is refused whole, the valid SQS target submitted alongside it is NOT written either, so the rule still lists only the targets it had before. Smithy models ConcurrentModificationException, InternalException, LimitExceededException, ManagedRuleException and ResourceNotFoundException for PutTargets — ValidationException is unmodeled, so the status/code/message above are recorded behavior only.
Emulator: the call SUCCEEDS. PutTargets returns FailedEntryCount 0 and no error at all for a bus target with no RoleArn, for both a same-Region bus ARN and a bus ARN in a second Region (replay: AssertionError "the call succeeded; real AWS refuses it" raised from the check's _error() helper, which only reaches that line when no ClientError was thrown).
Why: a client gets a silently mis-configured rule. The bus target is stored with no role, so EventBridge can never assume anything to forward with; the forwarding simply never happens and the client has no refusal, no FailedEntries entry and no error code to react to at configuration time. Infrastructure tooling that relies on the refusal to catch a missing role ships a dead cross-bus route.
Fix: the events PutTargets target validation — the per-target check that a target Arn in the event-bus namespace requires RoleArn, and the whole-request ValidationException it must raise (message built from the offending target's Arn) before any target is persisted.
Traces: events.bus-target-without-role-arn-rejected-in-both-regions-and-the-rule-keeps-its-targets

Cause 2 of 4: an event forwarded to a bus in a second Region is delivered carrying the origin Region's EventId instead of a newly assigned one.
AWS: when a rule's target is an event bus in another Region, the forwarded event arrives on the destination bus as a fresh ingestion. Its envelope preserves source, detail-type, detail, resources, account and the ORIGIN Region in `region`, but `id` is a NEW event id assigned by the destination bus — it is never equal to the EventId that the origin PutEvents returned, and never equal to any id the origin returned. Recorded behavior only (the envelope `id` is not described by the Smithy model); the recording shows the delivered envelope with the nine keys account, detail, detail-type, id, region, resources, source, time, version and an `id` distinct from the origin's.
Emulator: the envelope delivered to the second Region's SQS target carries exactly the origin EventId (replay: AssertionError "the event delivered in the second region carries the origin region's EventId; cross-region forwarding assigns a new one"). Every other asserted envelope field matched, so the divergence is isolated to id assignment on the forwarding hop.
Why: the id is the only handle a consumer has to de-duplicate and to correlate. Reusing the origin id makes a forwarded event indistinguishable from the original, so a consumer reading both buses de-duplicates away a delivery it must process, and anything that treats ids as per-bus-unique collides.
Fix: the events cross-Region bus-target forwarding path — the forwarded PutEvents on the destination bus must mint a new event id rather than propagate the inbound one, while leaving `region` at the origin Region. (Open issue 20261124T132051Z-events-sqs-5-causes-puttargets-refusal-messages-for.md covers same-Region bus-to-bus forwarding not delivering at all; it does not carry this check's replay key and does not describe id reassignment.)
Traces: events.cross-region-bus-target-delivers-to-the-other-regions-rules-with-the-source-region-and-a-new-event-id

Cause 3 of 4: InputTransformer array-path rendering reaches no verdict — nothing the check waits for is ever delivered.
AWS: an InputTransformer InputPathsMap may bind array paths, and EventBridge renders them deterministically into the InputTemplate: a whole-array path splices the compact JSON array (`[10,20,30]` as a JSON value, and `"[10,20,30]"` when the placeholder sits inside a quoted string), an indexed path splices the element, an out-of-range index renders the empty string, a nested index splices the scalar, a `[*]` projection splices the projected array, an empty array renders `[]`, and a JSON null renders `null` (and the text `null` inside a quoted string). In a plain-text template the same values are spliced without JSON punctuation/quoting, e.g. `ids=[o1,o2] objs=[{id:o1,v:1},{id:o2}] second=20 empty=[]`. Recorded behavior only for the exact rendering (documented at the EventBridge target-input transformer reference); the rule, not one run's values, is the requirement.
Emulator: the check never reaches a verdict — it is cut off at the harness cap (replay: "Error: Check timed out after 60.0s"). Its own budgets are 120 s liveness and 90 s delivery, and none of the three awaited arrivals (the raw target, the JSON-template target and the plain-text-template target, all on one queue) is observed, so no rendered body exists to compare.
Why: a client that shapes target input with array paths receives nothing at all; the transformer is accepted by PutTargets and then moves no event, and the rendering contract it depends on is unobservable.
Fix: the events rule target dispatch for a target carrying an InputTransformer — the array/index/projection/null resolution of InputPathsMap against the event and the JSON vs plain-text template renderer, plus the SQS-target delivery it feeds.
Traces: events.input-transformer-array-paths-render-elements-slices-and-null-exactly

Cause 4 of 4: InputTransformer string escaping and the INVALID_JSON dead-letter path reach no verdict.
AWS: a JSON InputTemplate escapes every string it splices, so quotes, newlines, tabs, backslashes, non-ASCII and markup reach the target intact and the body parses back to the source values. A plain-text template splices them raw, so a value containing a quote or a newline renders a body that is not valid JSON; that delivery is not sent to the target but dead-lettered to the target's DeadLetterConfig queue, carrying the rendered unescaped body and message attributes ERROR_CODE="INVALID_JSON", ERROR_MESSAGE="Invalid input for target.", RULE_ARN=<the rule's ARN> and TARGET_ARN=<the target's ARN> — ERROR_CODE and ERROR_MESSAGE are fixed text, RULE_ARN/TARGET_ARN are values from the rule and target in state. The target's own queue must receive nothing for that event, and re-putting the same target Id with a JSON template restores delivery. Recorded behavior only (dead-letter attributes are not in the Smithy model).
Emulator: the check never reaches a verdict — it is cut off at the harness cap (replay: "Error: Check timed out after 60.0s"), with liveness and delivery budgets of 120 s each. Neither the escaped JSON-template delivery nor either dead letter is observed, so the escaping contract and the INVALID_JSON dead-letter classification are both unobservable.
Why: a client cannot tell a dropped delivery from a dead-lettered one and loses the diagnostic (ERROR_CODE/ERROR_MESSAGE/RULE_ARN/TARGET_ARN) that AWS uses to report a bad template; a JSON template that silently fails to escape would also corrupt every string payload.
Fix: the events InputTransformer renderer's string escaping for JSON templates, and the target-dispatch failure path that must classify an unparseable rendered body as INVALID_JSON and dead-letter it with the four message attributes instead of dropping or delivering it.
Traces: events.input-transformer-plain-text-template-does-not-escape-strings-and-dead-letters-invalid-json

## Steps to Reproduce
Cause 1: CreateEventBus twice in this Region (one as the rule's bus, one as the target bus) and once through a second Region's endpoint; create an SQS queue with an events.amazonaws.com SendMessage policy; PutRule on the custom bus with pattern {"source":[<src>]}; PutTargets with the queue target only (expect FailedEntryCount 0). Then PutTargets with Targets=[{Id:"q",Arn:<queue arn>},{Id:"bus",Arn:<same-region bus arn>}] and again with the second Region's bus ARN, each with NO RoleArn, and read Error.Code/Error.Message off the ClientError; then ListTargetsByRule and check it still lists only ["q"]. Finally repeat with a RoleArn (role trusting events.amazonaws.com, allowing events:PutEvents on both bus ARNs) and confirm acceptance and read-back.

Cause 2: CreateEventBus in a second Region; create an SQS queue there with an events.amazonaws.com policy; PutRule on that bus with {"source":[{"prefix":"sim2real.xregion."}]} and PutTargets the queue. In the home Region create a bus and a rule matching a unique source, and PutTargets the second Region's bus ARN with a forwarding RoleArn. PutEvents one entry on the home bus with Resources=[<an s3 arn>] and a detail marker, recording the returned EventId; drain the second Region's queue and compare the delivered envelope's `id` with that EventId.

Cause 3: create a custom bus, a rule on a unique source, and one SQS queue (events.amazonaws.com policy). PutTargets three targets on that queue: a raw one, one with InputPathsMap {items:$.detail.items, second:$.detail.items[1], beyond:$.detail.items[7], cell:$.detail.grid[1][0], grid:$.detail.grid, firstId:$.detail.objs[0].id, ids:$.detail.objs[*].id, objs:$.detail.objs, empty:$.detail.empty, nul:$.detail.nul, m:$.detail.m} and a JSON InputTemplate splicing all of them, and one with a quoted plain-text InputTemplate. PutEvents a detail of {items:[10,20,30], grid:[[1,2],[3,4]], objs:[{id:o1,v:1},{id:o2}], empty:[], nul:null, m:<marker>} and drain the queue for all three forms.

Cause 4: create a custom bus, a rule on a unique source, three queues (good, broken, dlq). PutTargets: a raw target and a JSON-template target on the good queue, plus two plain-text-template targets on the broken queue, each with DeadLetterConfig {Arn:<dlq arn>} and RetryPolicy {MaximumRetryAttempts:0}, one splicing a value containing a double quote and one a value containing a newline. PutEvents a detail carrying those tricky strings; drain the good queue (expect the escaped JSON body), drain the dlq (expect two dead letters with ERROR_CODE/ERROR_MESSAGE/RULE_ARN/TARGET_ARN) and poll the broken queue (expect nothing). Then PutTargets the same target Id with a JSON InputTemplate and confirm delivery resumes.
