# bcm-data-exports GetTable serves paraphrased column descriptions instead of the Data Exports dictionary text

> _Note: this issue was identified against the code base at commit `258c8ab75d10298fe334d15f451340286114620d`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
GetTable

## Description
GetTable answers HTTP 200 with the right table name, the right table properties and the right column SET, but the `Column.Description` strings in `Schema` are the emulator's own re-wording of the AWS Data Exports table dictionary rather than the text the dictionary publishes. Four independent causes, one per table catalog group; all four are wrong RESPONSE DATA on a read-only reporting operation, not a status or error divergence.

Shared fault: `Column.Description` is response data a client reads to decide what a column holds (Smithy: shape `Column`, member `Description` — "The description for a column."; `GetTable` doc — "This includes the list of columns in the table schema, their data types, and column descriptions"). The model constrains only the string (GenericString, len 0..1024, pattern ^[\S\s]*$) and does not carry the per-column text, so the requirement is RECORDED BEHAVIOR: the dictionary's published text for that column, carried over verbatim. The emulator's own catalog module states the same rule (services/service-com-amazonaws-bcmdataexports-awsbillingandcostmanagementdataexports/src/state/catalog.rs header: "every string below is the dictionary's PUBLISHED text for that column or property, carried over as published, rather than a shorter re-wording of it: a paraphrase is a different value on the wire"), so each cause below is that rule not being met for a group of columns. In several places the recorded text carries the dictionary's own quirks — a leading "he" instead of "The", "isolates" for "isolated", "a reservation of savings plan", no trailing "For example, ..." sentence — and the emulator serves a grammatically tidied or example-extended sentence instead. The published string is fixed text per column; nothing in it comes from the request or from state, so there is no template to fill and no per-run value involved.

Cause 1 of 4 — CARBON_EMISSIONS, column `model_version`.
AWS: recorded behavior only (model carries no column text). `GetTable` on the carbon emissions table publishes `model_version` as 'The version of the methodology the carbon footprint data was calculated with. For example, v2.0.0.'
Emulator: serves 'The version of the model that was used to generate the carbon footprint value.' — a different sentence that drops the methodology/version-example wording.
Why: a client that reads the catalog to label or document the column, or that diffs the published catalog against the dictionary to detect a schema revision, sees text that matches no AWS revision; the version example clients key documentation off is absent.
Fix: this service's state data — the carbon emissions column group in `crate::state::catalog` (`ColumnSpec` description for `model_version`). `GetTable`'s handler is correct: it copies `table.schema(&properties)` straight out of the catalog.
Traces: bcm-data-exports-catalog-get-table#task#1.

Cause 2 of 4 — COST_AND_USAGE_DASHBOARD (the curated view; its own columns plus the columns it carries over from the cost-and-usage group), 7 columns.
AWS: recorded behavior only. The dashboard dictionary publishes terser text than the cost and usage dictionary, including its own typos: `current_generation` = 'Describes the current generation of the resource.'; `unblended_cost` = 'he UnblendedCost is the UnblendedRate multiplied by the UsageAmount.' (the recorded text really does begin 'he'); `amortized_cost` = 'The amortized cost of the resource.'; `ri_sp_trueup` = 'The true-up fee for a reservation of savings plan.'; `ri_sp_upfront_fees` = 'Any upfront fee from your purchase of a reservation of savings plan.'; and for the carried-over columns `pricing_unit` = 'The pricing unit that AWS used for calculating your usage cost.' (no trailing example sentence) and `product_to_location` = 'Describes the location usage destination.'
Emulator: serves longer, grammatically normalized prose instead — `current_generation` 'Indicates whether the instance type is of the current generation of its instance family.', `unblended_cost` 'The unblended rate multiplied by the usage quantity.', `amortized_cost` 'The upfront and recurring costs of a Reservation or Savings Plan, distributed across the billing periods of the term that they apply to.', `ri_sp_trueup` 'The true-up charge for the Reservation or Savings Plan that this line item benefited from, for the billing period.', `ri_sp_upfront_fees` 'The upfront fees for the Reservation or Savings Plan that this line item benefited from, for the billing period.', `pricing_unit` with an extra ' For example, the pricing unit for Amazon EC2 instance usage is in hours.' appended, and `product_to_location` 'Describes the location where the usage is sent to.'
Why: the emulator substitutes the cost-and-usage dictionary's semantics for the dashboard dictionary's, so a client cannot tell the two dictionaries apart from the catalog and gets a different meaning for the view's aggregated measures; a client that compares published text to detect drift reports a false difference on every one of these columns.
Fix: this service's state data — the dashboard column group in `crate::state::catalog`, and (for `pricing_unit` / `product_to_location`, which the view reports out of the viewed group rather than copying) the cost-and-usage group those two are named out of.
Traces: bcm-data-exports-catalog-get-table#task#2.

Cause 3 of 4 — COST_AND_USAGE_REPORT, 48 columns (the `product_*`, `pricing_*`, `reservation_*`, `savings_plan_*`, `cost_category`, `discount`, `product`, `resource_tags`, `tags` columns listed in the cluster's key set).
AWS: recorded behavior only. Examples of the published text: `product_fee_description` = 'The description for the product fee.'; `product_location` = 'Describes the location that your resource resides in.'; `product_location_type` = 'Describes the location type of your task.'; `product_from_region_code` = 'Describes the source Region code for the AWS service.'; `product_to_location` = 'Describes the location usage destination.'; `product_to_location_type` = 'Describes the destination location of the service usage.'; `product_region_code` = the long Region paragraph ending '...and specifies where the AWS service is available.' and spelling the AZ clause 'multiple, isolates, and physically separate AZs'.
Emulator: serves a re-worded sentence for each — e.g. `product_fee_description` 'Describes the fee for the product.', `product_location` 'Describes the location of the Region that your resource resides in.', `product_location_type` 'Describes the location type of the Region that your resource resides in.', `product_from_region_code` 'Describes the Region code of the location where the usage originated from.', `product_to_location` 'Describes the location where the usage is sent to.', and for `product_region_code` the same paragraph with 'isolates' changed to 'isolated' and an extra ' For example, us-east-1.' appended.
Why: the largest and most-consumed table in the catalog publishes 48 wrong column descriptions, so any client generating a data dictionary, column mapping or schema hash from GetTable produces output that does not match AWS for the majority of the table. `product_to_location` is the same wrong string as in Cause 2 because the dashboard views this group's column, so fixing it here fixes both reports.
Fix: this service's state data — the cost-and-usage column group in `crate::state::catalog`.
Traces: bcm-data-exports-catalog-get-table#task#3.

Cause 4 of 4 — the FOCUS 1.2 schema: the per-version description REVISIONS are missing, so 6 columns are reported with the superseded FOCUS 1.0 text.
AWS: recorded behavior only. The FOCUS 1.2 schema publishes its own text for the columns the 1.2 specification re-words: `SkuId` = 'Provider-specified unique identifier that represents a specific SKU (e.g., a quantifiable good or service offering).'; `SkuPriceId` = 'A provider-specified unique identifier that represents a specific SKU Price associated with a resource or service used or purchased.'; `SkuPriceDetails` = 'A set of properties of a SKU Price ID which are meaningful and common to all instances of that SKU Price ID.'; `SkuMeter` = 'Describes the functionality being metered or measured by a particular SKU in a charge.'; `SubAccountType` = 'A provider-assigned name to identify the type of sub account.'; and the AWS extension column `x_Discounts` = 'A map column containing key-value pairs of any specific discounts that apply to this line item.'
Emulator: serves the unrevised/paraphrased text instead — `SkuId` 'The identifier assigned to a SKU by the provider.', `SkuPriceId` 'The identifier assigned to a SKU Price by the provider.', `SkuPriceDetails` 'Key-value pairs of the provider-specified details that define the SKU Price used to calculate the charge.', `SkuMeter` 'Provider-specified description of the functionality or capability that a SKU measures.', `SubAccountType` 'A provider-assigned name to identify the type of a sub account.' (an inserted 'a'), `x_Discounts` 'Key-value pairs for any discounts you are receiving.'
Why: the catalog is keyed per table AND per table version precisely so a client can tell FOCUS 1.0 from FOCUS 1.2 by the text each version publishes. Serving the superseded text for the re-worded columns makes the two versions indistinguishable, so a client that selects a table version by its published column semantics picks the wrong one.
Fix: this service's state data — the FOCUS 1.2 revised-description table in `crate::state::catalog` (the `ColumnGroup::Revised` revision list applied over the FOCUS 1.0 columns, plus the AWS-extension group entry for `x_Discounts`).
Traces: bcm-data-exports-catalog-get-table#task#7.

No existing open issue covers any of these: a keyword search for 'bcm-data-exports' returns no filed issues.
