# s3__sagemaker: 2 net-new causes — CreateTrainingJob's non-existent-input-bucket refusal drops the "Error message from S3" clause, and a job whose ContainerEntrypoint is python3 is never performed (positive control never Completed)

> _Note: this issue was identified against the code base at commit `c2e2977646e21c9b97875e6fc938d11020301ad9`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
CreateTrainingJob

## Description
Two net-new root causes on the SageMaker-training-over-S3 surface; a fixer must close BOTH before submitting. Neither failing check is marked OWNED or ALREADY FILED by the replay report, so neither replay key is carried by an open issue today.

Cause 1 of 2: CreateTrainingJob's synchronous refusal of an InputDataConfig S3Uri whose BUCKET does not exist omits the clause that reports what Amazon S3 itself answered, so "the bucket is not there" is worded identically to "the prefix is empty".
AWS: the operation models no error for a bad request (Smithy: CreateTrainingJob errors are ResourceInUse / ResourceLimitExceeded / ResourceNotFound only; InputDataConfig @length 1..20, S3DataSource$S3Uri carries only the @pattern), so the refusal class and its sentence are recorded behavior only. The recording shows 400 ValidationException with the message: fixed text `No S3 objects found under S3 URL "<S3Uri>" given in input data source. Please ensure that the bucket exists in the selected region (<region>), that objects exist under that S3 prefix, and that the role "<RoleArn>" has "s3:ListBucket" permissions on bucket "<bucket>".` followed by the fixed clause ` Error message from S3: ` and then S3's own answer for the condition — `The specified bucket does not exist` for a bucket that is absent. The variable parts are the request's S3Uri, the request's RoleArn, the bucket taken off that S3Uri and the region the request addressed; the trailing clause's own text is S3's answer, not a value of any one run.
Emulator: the emulator answers the right code (ValidationException) and the right leading sentence, but STOPS at `… permissions on bucket "<bucket>".` — the ` Error message from S3: The specified bucket does not exist` clause is absent. The emulator's own helper already supports the clause (state/admission.rs `no_s3_objects_found`, lines 130-145, takes `s3_error: Option<&str>` and appends " Error message from S3: {error}") and the doc there states the clause is emitted only when the listing was refused by AUTHORIZATION; the absence path loses it, because `state/s3_access.rs::location_holds_no_object` (lines 359-390) collapses S3's NoSuchBucket/NoSuchKey answer and an empty listing into one boolean, and `UnreadableLocation::NoObject` (state/s3_access.rs lines 116-121) carries no S3 answer for the caller to be told.
Why: a client cannot tell a mistyped/deleted bucket from an empty prefix. Both are the same code and nearly the same sentence, so the retry-vs-fix decision (create the bucket / fix the URI vs wait for data to land) is made on a message AWS words differently, and any client or test that matches on the documented sentence fails against the emulator.
Fix: CreateTrainingJob's input-data admission — the S3 location reading must carry WHICH answer S3 gave (bucket absent, key absent, empty listing) out to the refusal, and the refusal builder must then pass that answer as the `s3_error` clause for the absence conditions as well as the authorization one.
Traces: s3__sagemaker.sagemaker-training-job-invalid-s3-uri-error-negative

Cause 2 of 2: a training job whose AlgorithmSpecification.ContainerEntrypoint names `python3` is never performed at all, so the job never reaches Completed and produces no model artifact.
AWS: Smithy: AlgorithmSpecification$ContainerEntrypoint — "The entrypoint script for a Docker container used to run a training job. This script takes precedence over the default train processing instructions" — followed by ContainerArguments as its arguments. A SageMaker Deep Learning Container / built-in algorithm image is a Python environment, so ContainerEntrypoint ["python3"] + ContainerArguments ["-c", <script>] runs that script inside the container: it reads the channel data mounted at /opt/ml/input/data/<ChannelName>/, writes to /opt/ml/model, the job then reaches TrainingJobStatus=Completed and DescribeTrainingJob.ModelArtifacts.S3ModelArtifacts names the archive of /opt/ml/model under OutputDataConfig.S3OutputPath.
Emulator: the job never completes. DescribeTrainingJob reports a non-Completed status with FailureReason `This emulator performs a job's declared container program itself and provides no program named "python3", so the container's program was never started and the job performed no work.` — fixed text whose one variable part is the program name quoted from the request's ContainerEntrypoint (state/container_run.rs `program_not_performed`, lines 193-202, reached from `run_container_program` lines 271-286 whenever `performable_program` lines 252-259 does not find the name in the shell session's catalog). An entrypoint the catalog does name (/bin/sh) is performed, so recognition of the program name — not execution as such — is what fails.
Why: the standard "override the entrypoint with python3" training job — what the built-in algorithm images and every bring-your-own-script job use — never reaches Completed and never yields a model artifact, and the FailureReason describes the emulator's executor rather than anything about the job, so it is indistinguishable from a genuine AlgorithmError and not actionable. In this check it also makes the negative half unmeasurable: the positive control that is supposed to prove the no-S3-access role is what caused the refusal can never complete, so the IAM boundary has no control to be judged against.
Note: the open issue 20261116T100406Z-s3-sagemaker-2-net-new-causes-a-completed.md describes this same root cause as its Cause 2, but carries only s3__sagemaker.cli-sagemaker-invalid-s3-input-uri-negative as a replay key; the check listed here is a second, unclaimed exposure of it and the report does not mark it owned. Closing it must satisfy this check's replay too.
Fix: the CreateTrainingJob execution path — the in-process container-program executor behind ContainerEntrypoint/ContainerArguments must perform a python3 interpreter (with the channels materialised under /opt/ml/input/data/<ChannelName>/ and /opt/ml/model collected afterwards), and the terminal status and FailureReason it then records.
Traces: s3__sagemaker.cli-sagemaker-training-job-missing-s3-permission-negative
