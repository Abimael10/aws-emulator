# ivs: the channel RTMPS ingest data plane is unreachable — CreateChannel announces an ingestEndpoint host that is not one of the emulator's own hosts and no RTMP/RTMPS listener is served, so a channel never goes LIVE

> _Note: this issue was identified against the code base at commit `e78c42ae609a9de39ccf71b1c7802acc87efe3dc`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
CreateChannel

## Description
Cause 1 of 1: the contribute (ingest) address an IVS channel announces cannot be dialed on this emulator, and nothing ingests RTMPS, so every state a live IVS broadcast is supposed to produce is unreachable.

Failing checks for this cause: ivs.rtmps-ingest-live-stream-lifecycle, ivs.rtmps-ingest-native-protocol-round-trip.

AWS: Smithy (services/service-com-amazonaws-ivs-amazoninteractivevideoservice/smithy-model/com-amazonaws-ivs-amazoninteractivevideoservice.json): Channel$ingestEndpoint -> IngestEndpoint is documented "Channel ingest endpoint, part of the definition of an ingest server, used when you set up streaming software" (plain string, no @length/@pattern); StreamKey$value -> StreamKeyValue (@sensitive) is the secret the encoder authenticates the publish with; Stream$state -> StreamState is "The stream's state. Do not rely on the OFFLINE state ... instead, a \"NotBroadcasting\" error will indicate that the stream is not live" and Stream$playbackUrl is "URL of the master playlist, required by the video player to play the HLS stream". So on AWS an encoder that completes an RTMPS handshake to rtmps://<ingestEndpoint>:443/app/<streamKey> makes the channel live, and then: GetStream returns 200 with stream.state == "LIVE" and stream.channelArn equal to the channel's ARN; the channel's playbackUrl serves an HLS multivariant playlist (#EXTM3U) once segments are packaged (404 until then); InsertAdBreak on a LIVE channel with no ad configuration is refused 400 ValidationException with the message whose fixed text is "Request member: channelArn failed to satisfy the constraints: valid ad configuration is required to be associated with the channel requested for the ad break with ARN: " followed by the channelArn from the request (the ARN is the only variable part); StopStream on the live channel is accepted and the channel then answers GetStream 404 ChannelNotBroadcasting with the message "Channel: " + the request's channelArn + " is not currently online"; GetStreamSession for that streamId reports both startTime and endTime once the stream has ended; and after DeleteChannel, GetChannel answers 404 ResourceNotFoundException "Resource: " + the ARN + " not found". The endpoint member itself has no modelled form, so "recorded behavior only" applies to its spelling — but whatever spelling is chosen it has to be an address a client of this emulator can actually connect to, because the member exists to be dialed.

Emulator: both checks abort on the very first use of the announced ingest address, before any publish is attempted. CreateChannel's channel projection announces ingestEndpoint (and the identical srt.endpoint) as a minted label under a contribute domain in the loopback zone, e.g. a value of the form <12-hex-label>.global-contribute.localhost, carrying no port; the harness refuses to dial it: "simparity.published.PublishedUrlRejected: endpoint_url was given rtmps://<label>.global-contribute.localhost (published by the emulator or built by the check): its host is not one of the emulator's own hosts; a customer of the emulator needs rtmps://127.0.0.1:<port>/<resource path>, or rtmps://<own host>:<port>/<path> on a per-resource listener" (the hex label, the host and the port differ every run and are not the finding; the announced host not being an address this process answers on is). Even if the name resolved, nothing would answer: src/state/channel_endpoints.rs composes the value purely as a string (announced_ingest_endpoint, lines 124-133, zone from announced_zone/reached_authority) and src/lib.rs mounts only ops/scaffolded/service/state — the crate has no RTMP/RTMPS listener at all, and ffmpeg's publish therefore can never be ingested. Consequently none of the downstream facts is ever produced: GetStream never reports state LIVE, the playbackUrl never serves a playlist, the InsertAdBreak-on-unconfigured-channel refusal and StopStream legs are never exercised, and no StreamSession with startTime/endTime is ever recorded.

Why: a client that uses IVS the way AWS documents it — CreateChannel, read ingestEndpoint and the stream key, point an encoder at rtmps://<ingestEndpoint>:443/app/<streamKey>, then poll GetStream until LIVE and fetch playbackUrl — cannot get off the ground against this emulator. The announced contribute address is a host the client cannot resolve or reach (and it carries no port, so the client's own :443 lands nowhere), so ingest, live-stream monitoring, HLS playback, ad insertion and StopStream are all untestable. Code that works against AWS fails at the first contribution attempt here, and the live-path error semantics (ValidationException for a missing ad configuration, ChannelNotBroadcasting after StopStream) can never be observed.

Fix: the service's data plane and the announced-address projection together: (1) serve an RTMP/RTMPS contribution listener for channels — reachable at an authority this process actually answers on (the emulator's own host plus a port, or a per-resource listener), authenticating the publish by the stream key the channel minted at the /app/<streamKey> path; (2) have crate::state::channel_endpoints::announced_ingest_endpoint (and the srt.endpoint it fills) announce THAT reachable address rather than a name in a zone no resolver maps to this process; (3) on an accepted publish, write the stream state the reads already derive from — a Stream in LIVE with its streamId and startTime, a packaged HLS multivariant playlist at the announced playbackUrl path, and the unwind on StopStream/publisher exit (ChannelNotBroadcasting from GetStream, a StreamSession carrying startTime and endTime). Note the open issue 20261114T063329Z-ivs-createchannel-announces-loopback-host-port-endpoints-and.md: it is a WIRE-shape finding on these same members (it asks that the endpoint be a port-less DNS name rather than a loopback host:port) and it does NOT cover this cluster — it says nothing about reachability or about an ingest listener, and satisfying its form alone is what leaves the address undialable. Whatever spelling is chosen must satisfy both: AWS's member form AND an address this emulator answers RTMPS on.

Traces: ivs.rtmps-ingest-live-stream-lifecycle, ivs.rtmps-ingest-native-protocol-round-trip (both fail at ctx.endpoint_url(ingest_endpoint, scheme='rtmps', aws_port=443) on the value CreateChannel announced).
