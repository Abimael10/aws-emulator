# batch__cloudformation: 2 net-new causes — an AWS::Batch::JobQueue Priority above the schema maximum of 1000 deploys instead of failing validation, and a property-validation rollback of AWS::Batch::SchedulingPolicy emits no VALIDATION_ERROR operation event

> _Note: this issue was identified against the code base at commit `6df4780ed6263f6fd5cc79bc833a1ad99a020747`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
CreateStack

## Description
Two net-new root causes grounded in failing behavioral checks the suite lists under `### batch__cloudformation` and marks neither ALREADY FILED nor OWNED. Both concern CloudFormation's early (schema) property validation of AWS::Batch resource types: in one case it does not happen at all, in the other it happens but is not reported.

Related open issues exist for this service token but carry neither check's replay key and do not cover these two causes: 20261109T123922Z-batch-cloudformation-2-net-new-causes-cloudformation-created.md (CFN-created Batch resources are not registered in Batch's own state; Ref/GetAtt values) and 20261117T124549Z-batch-cloudformation-2-net-new-causes-a-valid.md (a valid JobQueue create rolls back; Priority-only UpdateStack rolls back). The same missing-VALIDATION_ERROR shape is filed for other resource types under other service tokens (e.g. 20261123T033806Z-cloudformation-redshift-..., 20261123T190802Z-bedrock-agent-cloudformation-..., 20261123T150355Z-cloudformation-ec2-iam-sagemaker-...); none of them covers AWS::Batch::SchedulingPolicy or this check.

=== Cause 1 of 2: an out-of-range AWS::Batch::JobQueue Priority is accepted and the stack reaches CREATE_COMPLETE ===
AWS: the AWS::Batch::JobQueue resource schema constrains Priority to a maximum of 1000 (recorded behavior only for the bound — the Batch Smithy model types JobQueueDetail.priority / CreateJobQueue.priority as a plain required Integer with no @range, so the 1000 ceiling is CloudFormation's resource schema, not the API model). CloudFormation evaluates that schema BEFORE creating any resource: a template whose JobQueue carries Priority 1001 fails early validation, the stack ends ROLLBACK_COMPLETE, and the stack-level CREATE_FAILED event's ResourceStatusReason is the fixed text "Validation failed with 1 error(s). Call DescribeEvents to retrieve the full list of issues with resource and property details, resolve each error, then retry the operation." (the only variable part is the error count). Because nothing was created, Batch afterwards knows neither the ServiceEnvironment nor the JobQueue named in that template: DescribeServiceEnvironments and DescribeJobQueues both answer with empty collections.
Emulator: the identical template with Priority 1001 is accepted — the stack reaches CREATE_COMPLETE ('stack with Priority 1001 ended CREATE_COMPLETE, expected ROLLBACK_COMPLETE'), so no stack-level CREATE_FAILED event and no validation reason exist, and the out-of-range queue (plus its scheduling policy and service environment) is left behind in Batch. The in-range control at Priority 1000 deploys and reads back correctly, so only the upper bound is unenforced.
Why: a client relies on CloudFormation to reject a malformed template atomically before touching the account. Here an invalid Priority silently becomes live infrastructure, a deployment pipeline that treats CREATE_COMPLETE as "template valid" ships a queue AWS would never create, and rollback-based cleanup never runs, so the stray Batch resources are left to the next deploy to collide with.
Fix: the template/property schema validation stage of CreateStack for AWS::Batch::JobQueue — enforce the resource schema's numeric bounds on Priority during pre-create validation, fail the stack with the fixed validation reason above, and roll back so no Batch resource survives.
Traces: batch__cloudformation.deploy-job-queue-rejects-priority-above-maximum.

=== Cause 2 of 2: a property-validation rollback records no VALIDATION_ERROR operation event, so DescribeEvents reports nothing about why the stack failed ===
AWS: FairsharePolicy.computeReservation is documented in the Batch Smithy model as "The minimum value is 0 and the maximum value is 99", and the AWS::Batch::SchedulingPolicy resource schema carries that same bound. A template with ComputeReservation 150 fails CloudFormation's property validation; besides rolling the stack back, CloudFormation records an operation event retrievable via DescribeEvents with EventType=VALIDATION_ERROR, ValidationName=PROPERTY_VALIDATION, ValidationStatus=FAILED, ValidationFailureMode=FAIL, ValidationStatusReason of the form "#/<property path>: <rejected value> is not less or equal to <schema maximum>" and ValidationPath of the form "/Resources/<LogicalId>/Properties/<property path>". The fixed text is "#/", ": ", " is not less or equal to " and the "/Resources/.../Properties/..." skeleton; the variable parts (property path FairsharePolicy/ComputeReservation, logical id, rejected value 150, bound 99) come from the request template and the resource schema. No policy with that name is listed by Batch afterwards.
Emulator: the stack does roll back (ROLLBACK_COMPLETE), but DescribeEvents returns no VALIDATION_ERROR OperationEvents at all — the collected validation rows are `[]` where AWS reports exactly one row ('validation rows [], expected [("SP", "PROPERTY_VALIDATION", "FAILED", "FAIL", "#/FairsharePolicy/ComputeReservation: 150 is not less or equal to 99", "/Resources/SP/Properties/FairsharePolicy/ComputeReservation")]'). The in-range control (ComputeReservation 50) deploys and reads back computeReservation 50, so the bound is being applied; only its reporting is missing.
Why: a client (and every CI log and `cdk deploy` diagnostic) learns WHICH property of WHICH resource was rejected and why solely from these validation events. With none emitted, a failed deployment is indistinguishable from any other rollback: no property path, no rejected value, no bound, so the template cannot be fixed from the API's answer.
Fix: the operation-event recording in the CloudFormation property-validation stage — when a resource property fails schema validation, emit the EventType=VALIDATION_ERROR / PROPERTY_VALIDATION operation event (status, failure mode, reason and path members populated as above) so DescribeEvents returns it for the rolled-back stack.
Traces: batch__cloudformation.deploy-scheduling-policy-rejects-out-of-range-compute-reservation.
