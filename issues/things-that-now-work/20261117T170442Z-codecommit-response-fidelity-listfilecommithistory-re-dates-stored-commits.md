# CodeCommit response fidelity: ListFileCommitHistory re-dates stored commits and TestRepositoryTriggers' branch-limit message is the Smithy doc string (2 causes)

## Description
TWO net-new codecommit causes from the wire replay, both on paths that answer with the correct HTTP status and the correct error code / response shape but fill a field with a value AWS never produces: one commit-metadata field that is regenerated per response instead of being read from the stored commit, and one error message that is the Smithy error shape's documentation sentence instead of AWS's wire text. A fixer must close BOTH causes before submitting.

=== Cause 1 of 2: ListFileCommitHistory reports a commit date that is not the date the same commit id reports elsewhere ===
AWS: Smithy com.amazonaws.codecommit#ListFileCommitHistory takes repositoryName (@required, @length 1..100, @pattern ^[\w\.-]+$), filePath (@required Path) and an optional commitSpecifier, and returns revisionDag (@required RevisionDag, a list of FileVersion). FileVersion carries commit (shape Commit) with commitId/treeId/parents/message/author/committer/additionalData; Commit.author and Commit.committer are UserInfo, whose `date` member is documented 'The date when the specified commit was commited, in timestamp format with GMT offset' (i.e. unix seconds followed by a GMT offset, e.g. '<seconds> +0000'). The model does not state the value, so recorded behavior supplies the rule: a commit's metadata is IMMUTABLE once the commit exists, so the author/committer date ListFileCommitHistory reports for commit <id> is byte-identical to the date every other operation reports for that same <id> (GetCommit, GetBranch's tip commit, GetDifferences), for the whole life of the repository. The recorded expectation for this step is bound to the date captured from the SAME commit earlier in the same run, which is exactly this invariant: one commit, one date.
Emulator: for the single FileVersion in revisionDag the emulator agrees on blobId, path, revisionChildren, commitId, treeId, parents, message, additionalData and on the author/committer name/email — but its author.date and committer.date carry a DIFFERENT timestamp from the one the same commit id reported earlier in the run, so the whole revisionDag[0] element fails to match. The format is right (unix seconds + ' +0000'); the value is not the stored commit's date. Hypothesis: the handler synthesises the Commit structure (and its UserInfo dates) at response time from the clock rather than reading the committer/author lines of the stored commit object.
Why: this is not a per-run clock difference — the expected value is a value captured from an earlier step of the SAME replay, so the two readings of ONE commit disagree inside a single run. A client that reads file history to show 'last changed at' and then calls GetCommit on the same id to show commit details renders two different times for the same commit; a client that caches or de-duplicates commits by (commitId, date) treats one commit as two, and a drift/consistency check that compares history metadata against GetCommit always reports a difference AWS never produces. Because the value moves, no caller can treat a commit's date as stable.
Fix: the ListFileCommitHistory handler's construction of FileVersion.commit in the codecommit service — populate the Commit/UserInfo fields (including author.date and committer.date) from the stored commit object the repository state holds, as the GetCommit path does, rather than generating a timestamp while serialising the response. The same Commit-mapping helper should be shared so every operation returning a Commit reports one date per commit id.

=== Cause 2 of 2: TestRepositoryTriggers' MaximumBranchesExceededException message is the error shape's documentation sentence ===
AWS: Smithy TestRepositoryTriggers takes repositoryName (@required) and triggers (@required RepositoryTriggersList) and models MaximumBranchesExceededException (errorKind client, httpError 400 [defaulted]) with a single `message` member; the shape's doc is only 'The number of branches for the trigger was exceeded.', so the model does not state the wire text and recorded behavior supplies it. A trigger whose branches list exceeds the per-trigger limit of 10 is refused with HTTP 400, error code MaximumBranchesExceededException, and the message 'A repository trigger cannot have more than 10 branches.' That message is entirely FIXED text apart from the limit itself (10, the service's per-trigger branch maximum); no trigger name, repository name, branch name or submitted count is interpolated into it.
Emulator: the same status (400) and the same error code, but the message 'The number of branches for the trigger was exceeded. The maximum number of branches for a trigger is 10.' — the first sentence is verbatim the MaximumBranchesExceededException documentation string in the on-disk Smithy model, with a second, emulator-authored sentence appended.
Why: for a modelled client error the message is part of the contract: a caller (or a test, or a CLI user) that matches or displays AWS's sentence never matches, and the emulator's wording states the rule as a past-tense observation rather than the constraint AWS words ('a repository trigger cannot have more than 10 branches'). It is also the same fault family already recorded for other codecommit refusal paths — open issue 20261109T190531Z-codecommit-validation-errors-carry-doc-string-or-sibling.md (causes 3 and 4) reports Smithy doc strings being returned as wire messages for CreateBranch/PutFile, and the trigger-message bundle 20261022T213415Z-codecommit-putcommentreaction-is-a-501-stub-cmk-disablement.md covers other templates — but neither carries this cluster's replay key (the replay reports owned_by empty for it) and neither names TestRepositoryTriggers' branch-limit refusal, so this cause is net-new and will not be closed by those fixes.
Fix: the triggers validation in the TestRepositoryTriggers handler (and the shared trigger-validation helper PutRepositoryTriggers uses, so both operations word the limit identically) — emit AWS's fixed sentence, built from the enforced branch limit, instead of the error shape's documentation text.
