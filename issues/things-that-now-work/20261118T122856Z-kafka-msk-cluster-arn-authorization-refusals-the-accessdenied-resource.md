# MSK cluster-ARN authorization refusals: the AccessDenied resource token is inverted (and carries an extra identity-policy clause), and DeleteCluster denies a non-cluster MSK ARN instead of refusing the parameter (3 causes)

> _Note: this issue was identified against the code base at commit `53a07ddf88f361ed2bd809df47996759a4dc983b`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
CreateChannel

## Description
THREE distinct net-new root causes on the kafka (MSK) pre-resolution authorization gate that every cluster-scoped operation now takes (crate::state::authorization). Each is its own rule and must be closed separately; all three must be closed before this issue is submitted. None of the three failing checks is marked ALREADY FILED or OWNED in the replay report.

Context a fixer needs: the FIXED issue 20261029T175822Z-kafka-msk-arn-handling-malformed-and-cross-region-arns.md (Causes 1 and 2) moved these two refusals onto AccessDeniedException, and that part now holds — the Error.Code is correct in Causes 1 and 2 below. What that filing never stated was the MESSAGE, which is where both checks now fail. This is therefore not a reopened refusal: AWS refuses these two calls too. Cause 3 is a precedence REGRESSION: the open issue 20261118T020526Z-kafka-msk-control-plane-refusals-createclusterv2-s-both-cluster.md (Cause 2) recorded that DeleteCluster on a configuration ARN still answered the correct 400 and asked for it to be LEFT alone; it no longer does.

Cause 1 of 3: a cluster-scoped action whose target IS an ARN but names no cluster is denied over the submitted ARN and with an identity-policy clause, where AWS denies it over the wildcard resource and stops there.
AWS: CreateChannel (Smithy: POST /v1/clusters/{ClusterArn}/channels, success 200; ClusterArn is an @httpLabel @required plain __string with no pattern; ChannelName and TopicConfigurationList @required; modeled errors BadRequestException 400, ConflictException 409, ForbiddenException 403, UnauthorizedException 401, NotFoundException 404, TooManyRequestsException 429, InternalServerErrorException 500, ServiceUnavailableException 503 — AccessDeniedException is NOT modeled, so it travels as an unmodeled 403). Recorded behavior only for the wording: a CreateChannel whose ClusterArn is a well-formed MSK ARN (partition/service/region/account all valid) whose resource segment is `cluster/<name>` WITHOUT the required `/<uuid>` suffix is refused with Error.Code AccessDeniedException and Error.Message exactly `User: <callerArn> is not authorized to perform: kafka:CreateChannel on resource: *`. Message anatomy: `User: ` + the caller principal ARN that signed the request (sts:GetCallerIdentity's Arn — a value from the request's credential, never a literal) + ` is not authorized to perform: ` + the fully qualified action `kafka:<ApiName>` of the operation + ` on resource: ` + the single fixed token `*`. The sentence ENDS there: AWS appends no ` because no identity-based policy allows the ... action` clause on this class. Hypothesis (neither the model nor the recording states it): a resource segment of the wrong arity resolves to no resource in the authorization context, so the decision is taken over the wildcard.
Emulator: the code is right, the message is not. It answers `User: arn:aws:iam::000000000000:user/emulator is not authorized to perform: kafka:CreateChannel on resource: arn:aws:kafka:us-west-2:000000000000:cluster/sim2real-bogus-da5bcc574afc because no identity-based policy allows the kafka:CreateChannel action` — the submitted ARN is interpolated where AWS prints `*`, and the trailing identity-policy clause is added. This is the `::service_common::arn::parse(value).is_some()` branch of `no_grant_for_cluster`.
Why: the message is part of the refusal contract. A client (or an error table, log scraper or exact-match assertion) keyed on AWS's sentence stops matching; worse, the emulator reflects caller input into a constant message, so one defect yields a different string per request and cannot be matched at all, and the added clause tells an operator to fix identity policy when AWS states no document at all was reached.
Fix: the cluster-scoped authorization refusal in services/service-com-amazonaws-kafka-kafka/src/state/authorization.rs (`no_grant_for_cluster`) — the branch taken when the target parses as an ARN but is not a cluster ARN must word the refusal over the wildcard resource with no policy clause.
Traces: kafka.channel-invalid-name-pattern-rejected. (The check's second half — a syntactically valid but nonexistent cluster ARN must answer NotFoundException with the fixed message `The requested resource doesn’t exist.` — was never reached and is unverified.)

Cause 2 of 3: the same gate, for a target that is NOT an ARN at all, denies over the wildcard where AWS denies over the submitted value.
AWS: DescribeClusterV2 (Smithy: GET /api/v2/clusters/{ClusterArn}, success 200; ClusterArn @httpLabel @required __string, no pattern; modeled errors BadRequestException 400, ForbiddenException 403, UnauthorizedException 401, NotFoundException 404, InternalServerErrorException 500; AccessDeniedException unmodeled, 403). Recorded behavior only for the wording: DescribeClusterV2 with ClusterArn that is not an ARN at all is refused Error.Code AccessDeniedException with Error.Message exactly `User: <callerArn> is not authorized to perform: kafka:DescribeClusterV2 on resource: <the submitted value, verbatim>` — same template as Cause 1, but the resource token is the request's own ClusterArn string rather than `*`, and again with NO trailing policy clause. So the two classes are the exact inverse of what the emulator does.
Emulator: `User: arn:aws:iam::000000000000:user/emulator is not authorized to perform: kafka:DescribeClusterV2 on resource: *` — the wildcard where AWS echoes the value. This is the non-ARN branch of the same `no_grant_for_cluster`, reached because DescribeClusterV2 is one of the actions a cluster policy can grant, so a non-ARN value is still decided here.
Why: same contract break as Cause 1, in the opposite direction; together they show the branch that picks the resource token is swapped, so a fixer who corrects only one half will flip the other check.
Fix: same function in services/service-com-amazonaws-kafka-kafka/src/state/authorization.rs — swap which branch names `ANY_RESOURCE` and which names the submitted value, and drop the identity-policy clause from both, keeping one shared sentence so the two cannot drift.
Traces: kafka.cluster-describe-malformed-arn-rejected.

Cause 3 of 3: DeleteCluster handed an MSK ARN that is not a cluster ARN is denied by the pre-resolution gate instead of being refused as the invalid parameter it is.
AWS: DeleteCluster (Smithy: DELETE /v1/clusters/{ClusterArn}, success 200; ClusterArn @httpLabel @required, CurrentVersion @httpQuery currentVersion; modeled errors BadRequestException 400, ForbiddenException 403, InternalServerErrorException 500, NotFoundException 404). Recorded behavior for the class: handed an MSK CONFIGURATION ARN as its ClusterArn, DeleteCluster answers HTTP 400 / Error.Code BadRequestException with Error.Message exactly `One or more of the parameters are not valid.` — the whole sentence is fixed text; the ARN, the account and the region never appear in it. (kafka:DeleteCluster is not one of the four actions an MSK cluster policy can grant, so there is no cluster-policy-only path to deny on.)
Emulator: HTTP 403 / AccessDeniedException with `User: arn:aws:iam::000000000000:user/emulator is not authorized to perform: kafka:DeleteCluster on resource: arn:aws:kafka:us-west-2:000000000000:configuration/<name>/<uuid>-1 because no identity-based policy allows the kafka:DeleteCluster action`. The `authorize_caller_operation` call at the TOP of services/service-com-amazonaws-kafka-kafka/src/ops/delete_cluster.rs runs before the handler's own `crate::state::is_cluster_arn` gate, so an ARN of another MSK resource type reaches `no_grant_for_cluster` and is denied, and the handler's correct `unreadable_cluster_reference` 400 is never reached.
Why: a client branches on the status and class — 403/AccessDenied means escalate to IAM, 400/BadRequest means fix the request. Pointed at a configuration ARN by mistake, a caller is told its principal lacks permissions it actually has, and least-privilege tooling retries or escalates instead of correcting the identifier. It also regressed a path a prior filing recorded as correct.
Fix: in delete_cluster.rs, let a value that is a parseable ARN but not an MSK CLUSTER ARN fall through the pre-resolution authorization gate to the operation's own parameter refusal (the shape gate / `unreadable_cluster_reference` 400), for the actions no cluster policy can grant. Do NOT unify this with the sibling readers: the open issue 20261118T020526Z (Cause 2) requires GetBootstrapBrokers / DescribeCluster / DescribeClusterV2 to answer 404 NotFoundException `The requested resource doesn’t exist.` on that same configuration ARN while DeleteCluster stays on its 400 — three recorded classes on one input, per operation.
Traces: kafka.configuration-arn-rejected-for-cluster-operations.
