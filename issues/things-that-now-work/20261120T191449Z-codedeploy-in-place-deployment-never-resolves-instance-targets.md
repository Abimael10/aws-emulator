# CodeDeploy in-place deployment never resolves instance targets, so a HOST_COUNT minimumHealthyHosts config's rolling concurrency is never observable (ListDeploymentTargets stays empty / deployment never reaches a sampleable rolling state)

> _Note: this issue was identified against the code base at commit `597db9eebaefdf1df0a6fca4ca797f56db8217fd`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
ListDeploymentTargets

## Description
Cause 1 of 1: a Server (EC2/on-premises) compute-platform deployment created against a deployment group selected only by ec2TagFilters never produces a deployment target, so every target-driven read on that deployment stalls: ListDeploymentTargets never returns the tagged hosts (it answers with an empty targetIds list or keeps answering DeploymentNotStartedException), BatchGetDeploymentTargets therefore has nothing to sample, and a caller that waits for the fleet to resolve before measuring rolling concurrency never gets past that wait — the check hangs until its budget expires rather than ever seeing a host go InProgress. Consequence: the concurrency contract of a custom deployment config with minimumHealthyHosts {type: HOST_COUNT, value: n} (at most hosts-n hosts out of service at once, and the deployment taking correspondingly longer than an unbounded AllAtOnce deployment over the same fleet) is not implemented in any observable way. Failing check ids for this cause: codedeploy.minimum-healthy-hosts-bounds-observed-concurrent-unavailability.

AWS: Smithy (codedeploy, CodeDeploy_20141006) — CreateDeploymentConfig accepts minimumHealthyHosts (MinimumHealthyHosts{type: HOST_COUNT|FLEET_PERCENT, value}); GetDeploymentConfig echoes it back on deploymentConfigInfo.minimumHealthyHosts. ListDeploymentTargets(deploymentId) returns output member targetIds (TargetIdList) — the set of targets CodeDeploy resolved for the deployment — and models DeploymentNotStartedException only for a deployment that has not started yet, i.e. it is a transient state, not a terminal one. BatchGetDeploymentTargets(deploymentId, targetIds) returns deploymentTargets, each with instanceTarget{targetId, status, lifecycleEvents}. For a Server-platform group whose ec2TagFilters (EC2TagFilter{Key,Value,Type=KEY_AND_VALUE}) match running tagged instances, AWS resolves each matching instance as an instanceTarget, drives it through the in-place lifecycle, reports it as InProgress while its hooks run, and bounds how many are InProgress at once by the group's deployment config: with HOST_COUNT value n over h resolved hosts at most h-n may be out of service simultaneously, while CodeDeployDefault.AllAtOnce bounds nothing and puts the whole fleet out of service at once. GetDeployment reports the matching per-status deploymentOverview counts plus createTime/completeTime. Recorded behavior for this check: two t3.micro hosts are launched and tagged at creation, two deployment groups over the same tag filter (one AllAtOnce, one with a custom HOST_COUNT=1 config) deploy the same revision whose BeforeInstall hook sleeps, and the per-target statuses are sampled with BatchGetDeploymentTargets while the deployment runs.

Emulator: the deployment is accepted but no target is ever resolved for it, so the caller's bounded wait for ListDeploymentTargets to report the tagged fleet never becomes satisfiable and the check is killed by the harness budget ('Check timed out after 60.0s') without a single sample of a host InProgress. No rolling behavior, no per-target InProgress window, and no minimumHealthyHosts-dependent difference in elapsed time between the bounded and the unbounded leg is observable at all. This is the same target-resolution gap already filed as open issue 20261120T163729Z-codedeploy-server-platform-deployments-never-resolve-ec2tagfilters-to.md (which records the Failed/NO_INSTANCES terminal outcome and does not carry this check or its replay key); the additional, distinct surface here is that minimumHealthyHosts concurrency bounding and the InProgress/overview sampling path have no implementation to exercise once targets do resolve.

Why: a client cannot test or rely on rolling deployments. Code that reads ListDeploymentTargets to discover the fleet a deployment is acting on blocks forever (the operation reports neither targets nor a terminal 'no targets' condition), and any logic that depends on a custom deployment config limiting simultaneous host unavailability — canary-style rollouts, safe redeploys of a two-host fleet, dashboards that read deploymentOverview's InProgress bucket — sees nothing happen.

Fix: the Server-platform deployment execution path's target resolution and rolling scheduler (the component behind CreateDeployment that materialises instanceTargets from the deployment group's ec2TagFilters and then advances them) must register the matching instances as targets so ListDeploymentTargets/BatchGetDeploymentTargets report them, and must schedule those targets according to the group's deployment config: at most (resolved hosts - minimumHealthyHosts.value) InProgress at one time for HOST_COUNT, unbounded for CodeDeployDefault.AllAtOnce, with GetDeployment's deploymentOverview buckets and createTime/completeTime reflecting that progression.

Traces: codedeploy.minimum-healthy-hosts-bounds-observed-concurrent-unavailability (times out in its wait for the deployment to resolve all tagged hosts as targets, before any concurrency or elapsed assertion is reached).

## Evidence
Expected (AWS): with two running EC2 instances tagged Key=<tag>,Value=<value>, a Server-platform application, a custom deployment config created by CreateDeploymentConfig(computePlatform='Server', minimumHealthyHosts={type:'HOST_COUNT', value:1}), and two deployment groups over ec2TagFilters=[{Key:<tag>,Value:<value>,Type:'KEY_AND_VALUE'}] (one using CodeDeployDefault.AllAtOnce, one using the custom config): ListDeploymentTargets(deploymentId) returns both instance ids shortly after each deployment starts; BatchGetDeploymentTargets reports each instanceTarget's status, with both hosts InProgress at the same instant under AllAtOnce and at most (2 - 1) = 1 host InProgress at any instant under the HOST_COUNT config; GetDeployment reports deploymentOverview buckets that partition the two hosts and a completeTime - createTime that is larger for the bounded leg than for the unbounded one.

Actual (emulator): no target is ever reported for either deployment — the bounded wait on ListDeploymentTargets for the deployment to resolve its 2 tagged hosts is never satisfied (the operation yields no targetIds, and/or keeps answering DeploymentNotStartedException, which AWS models only as a pre-start transient), so the check never reaches a single BatchGetDeploymentTargets sample and the replay ends with 'Check timed out after 60.0s'. No InProgress host, no deploymentOverview progression and no config-dependent elapsed difference is ever observable. The instance ids, tag value, deployment ids and the exact timeout number are per-run values and are not part of the requirement; the requirement is that a deployment whose group's ec2TagFilters match running tagged instances resolves those instances as targets and advances them under the bound its deployment config declares.

## Steps to Reproduce
1. Create an S3 bucket and put a Server-platform revision zip whose appspec.yml declares a files section and a BeforeInstall hook that sleeps ~45s.
2. Create a VPC/subnet and an instance profile allowing SSM + S3 read; ec2:RunInstances two t3.micro AL2023 instances with TagSpecifications Tags=[{Key:'sim2real-codedeploy-target', Value:'<unique>'}]; wait for both to be ready managed nodes.
3. codedeploy:CreateApplication(computePlatform='Server').
4. codedeploy:CreateDeploymentConfig(deploymentConfigName='<unique>', computePlatform='Server', minimumHealthyHosts={type:'HOST_COUNT', value:1}); confirm GetDeploymentConfig echoes it.
5. codedeploy:CreateDeploymentGroup twice over ec2TagFilters=[{Key:'sim2real-codedeploy-target', Value:'<unique>', Type:'KEY_AND_VALUE'}] — one with deploymentConfigName='CodeDeployDefault.AllAtOnce', one with the custom config.
6. codedeploy:CreateDeployment on each group with the S3 revision and fileExistsBehavior='OVERWRITE'.
7. Poll codedeploy:ListDeploymentTargets(deploymentId) for the two instance ids. Observe that it never returns them, so codedeploy:BatchGetDeploymentTargets can never be called to sample per-host InProgress counts and the HOST_COUNT concurrency bound (and the bounded-vs-unbounded elapsed difference from GetDeployment's createTime/completeTime) is never observable.
