# eks: 5 net-new root causes — admitted pods never run their containers, the CreateNodegroup and UpdateNodegroupConfig scalingConfig refusals are mis-worded, and the CA-rotation and node/pod data-plane lifecycles never reach a verdict

> _Note: this issue was identified against the code base at commit `3b9b0467f2eb3d7399c7e850c9f1cb96948fddb1`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
CreateNodegroup

## Description
Five independent defects in the eks emulator, found by behavioral replay. Each cause below is a separate defect and must be closed separately; its own failing check ids are listed with it.

Cause 1 of 5: a pod admitted by the served cluster Kubernetes API never runs its containers — it goes straight to phase Failed with an emulator-authored StartError.
AWS: recorded behavior only (the cluster's Kubernetes API server is not part of the EKS Smithy model; the model only describes Cluster.endpoint / Cluster.certificateAuthority on DescribeCluster). On a real EKS cluster with a registered managed-nodegroup node, a pod that is scheduled onto that node runs its image: status.phase moves Pending -> Running and, for a one-shot command, -> Succeeded, and each entry of status.containerStatuses reports state.terminated.reason "Completed" with exitCode 0 for a command that exits 0 (the fixed parts are the phase/reason tokens themselves; the container name and image come from the submitted PodSpec).
Emulator: the pod is scheduled (PodScheduled=True, Initialized=True) and then ends phase "Failed" with reason "StartError", message "This emulator does not run containers, so the pod's containers were never started", and containerStatuses[0].state.terminated = {reason: "StartError", exitCode: 128, message: same sentence}; ContainersReady/Ready are False with reason "ContainersNotReady".
Why: every client that verifies a workload actually ran — a Job/one-shot pod, a readiness gate, an init container, a smoke test that reads a pod's logs or exit code, or anything that waits for phase Running/Succeeded — sees a hard Failed with a reason no Kubernetes client knows. The emulator's own sentence is also surfaced to callers as if it were a cluster condition, so the failure is indistinguishable from a real image/start failure (which AWS would report as ImagePullBackOff/CrashLoopBackOff/RunContainerError, not "StartError" with exit 128).
Fix: the pod runtime/state of the served cluster Kubernetes API (the EKS cluster data-plane handler that admits pods and computes their status): an admitted pod must converge to Running and, for a terminating command, Succeeded with exitCode 0, instead of being terminated with a not-implemented reason.
Traces: eks.eks-managed-nodegroup-node-joins-and-runs-a-targeted-pod.

Cause 2 of 5: CreateNodegroup's internally-inconsistent-scalingConfig refusal carries an emulator-authored sentence.
AWS: Smithy: CreateNodegroup takes scalingConfig: NodegroupScalingConfig (minSize ZeroCapacity @range min 0, maxSize Capacity @range min 1, desiredSize ZeroCapacity @range min 0) and models InvalidParameterException (HTTP 400). A create whose desiredSize exceeds maxSize is refused 400 InvalidParameterException with the message "desiredSize can't be greater than maxSize" — that sentence is fixed text in its entirety, naming the two MEMBERS and interpolating no request values — and no nodegroup is created.
Emulator: the code is right (InvalidParameterException) but the message is "scalingConfig must satisfy minSize <= desiredSize <= maxSize, got minSize 1, desiredSize 5, maxSize 2", i.e. a framework-style sentence that states the whole invariant and echoes the three submitted values (the numbers shown are the values this run sent; the defect is the template, not the numbers).
Why: a client that branches on the refusal text (CDK/CloudFormation error surfacing, retry logic that distinguishes a desired-above-max mistake from a min/max mistake, or a test that asserts the documented sentence) does not match AWS's sentence and treats a well-classified refusal as an unknown error.
Fix: the validation of CreateNodegroup's scalingConfig in the CreateNodegroup handler (the message it builds for the desiredSize-above-maxSize case must be EKS's fixed sentence, and the min/max cases must keep their own AWS sentences).
Traces: eks.deploy-cfn-nodegroup-joins-cluster-and-scales.

Cause 3 of 5: UpdateNodegroupConfig's desiredSize-above-maxSize refusal is worded back-to-front.
AWS: Smithy: UpdateNodegroupConfig takes scalingConfig: NodegroupScalingConfig and models InvalidParameterException (HTTP 400). An update that raises desiredSize above the nodegroup's current maxSize is refused 400 InvalidParameterException with the message "desired capacity <desiredSize> can't be greater than max size <maxSize>". Fixed text: "desired capacity ", " can't be greater than max size "; variable parts: the desiredSize the request asked for, and the maxSize the nodegroup currently holds in state. The nodegroup's scalingConfig is left unchanged.
Emulator: the code is right but the message is "Maximum capacity <maxSize> can't be less than desired size <desiredSize>" — the two operands are swapped, the subject is the maximum rather than the requested desired capacity, and the wording ("Maximum capacity"/"desired size", "can't be less than") is not EKS's.
Why: a client that surfaces or matches the refusal text sees a different sentence, and the inverted phrasing misattributes the fault to the nodegroup's configured maximum rather than to the value the caller just sent, so operator-facing tooling points at the wrong field to fix.
Fix: the scalingConfig validation of the UpdateNodegroupConfig handler (the sentence it builds for desiredSize > current maxSize).
Traces: eks.deploy-nodegroup-scaling-config-enforced.

Cause 4 of 5: the certificate-authority rotation lifecycle never reaches a verdict — both end-to-end CA checks run out of budget without completing.
AWS: Smithy: CreateCertificateAuthority returns a CertificateAuthority (signingStatus NOT_USED) plus the Update that tracks trust distribution; "the successor CA can't be activated until its distributionStatus is COMPLETE", ActivateCertificateAuthority then makes it IN_USE and the outgoing CA NOT_USED, and DeleteCertificateAuthority refuses the signing CA with ResourceInUseException (409) and the fixed sentence "Cannot delete the active certificate authority. Activate a different CA first." Each of those transitions is observable to a poller within one polling interval.
Emulator: neither end-to-end rotation check reaches any of its assertions — both are cut off ("Check timed out after 60.0s") while polling the chain cluster CREATING -> ACTIVE, CA distributionStatus IN_PROGRESS -> COMPLETE, update InProgress -> Successful, signingStatus NOT_USED -> IN_USE. Hypothesis: every one of those moves is owed only after a stored due instant and is materialised lazily by the next read (services/service-com-amazonaws-eks-awswesleyfrontend/src/ops/create_certificate_authority.rs; CA_DISTRIBUTION_DELAY = UPDATE_COMPLETION_DELAY in services/service-com-amazonaws-eks-awswesleyfrontend/src/state/certificate_authority.rs and src/state.rs), so a caller's first probe after each call always observes the non-terminal status and pays a full polling interval per step; chained across the rotation, the sequence cannot settle inside a client's budget. The published statuses are therefore never observed to converge at all.
Why: a client that rotates a cluster CA cannot complete the documented workflow — it never sees distributionStatus COMPLETE, so it never gets to activate, and the whole rotation (including the protected-signer refusal) is unobservable. Related open issues describe the same class elsewhere (20261029T175608Z-eks-3-net-new-root-causes-startinsightsrefresh-response.md, 20261104T105252Z-eks-2-net-new-root-causes-the-metrics.md); neither carries these two checks.
Fix: the certificate-authority lifecycle clock in the EKS state slice (the due-instant/materialisation seam for CA distribution, the activation update and the cluster's UPDATING->ACTIVE return), so each transition is observable promptly rather than only after a long chain of lazily-materialised delays.
Traces: eks.e2e-certificate-authority-activation-to-teardown, eks.e2e-certificate-authority-issue-activate-disable-delete.

Cause 5 of 5: the node/pod data-plane scenarios never reach a verdict — a check that waits for a nodegroup's node to be Ready and a pod on it to run is cut off before its assertions.
AWS: recorded behavior only. On a real cluster a managed nodegroup's node registers and reports Ready, a pod scheduled on it reaches Running, and the EKS pod-identity agent injects the credential environment into the admitted pod — each within a poller's window; DeleteCluster on a cluster that still has a live nodegroup is then refused.
Emulator: both checks are cut off ("Check timed out after 60.0s") while polling the served Kubernetes API for node readiness / pod convergence, so neither the delete-with-live-node refusal nor the pod-identity credential scoping is ever exercised. Hypothesis: this is the same gap as Cause 1 — an admitted pod is terminated with StartError instead of ever reaching Running, so any wait for a running pod (or for a node with a running pod on it) cannot converge. These two checks are listed on the open issue 20261113T151622Z-eks-10-net-new-root-causes-in-the.md, but its causes (core/v1 nodes 404, Pod spec.containers omitted) no longer reproduce: those paths now answer, and the run gets as far as waiting for the workload.
Why: a client cannot verify that a managed nodegroup actually carries workloads, nor that pod-identity credentials are injected and scoped, because the wait never resolves — the scenario hangs instead of failing with a diagnosable status.
Fix: the pod runtime/state of the served cluster Kubernetes API (as in Cause 1) and the node-registration state that reports node conditions, so a node reports Ready and a scheduled pod converges.
Traces: eks.eks-delete-cluster-with-a-live-node-is-rejected, eks.eks-pod-identity-credentials-are-scoped-and-an-unallowed-bucket-is-denied.

Cause 2: CreateNodegroup(scalingConfig={minSize:1,maxSize:2,desiredSize:5}) -> InvalidParameterException, Message 'scalingConfig must satisfy minSize <= desiredSize <= maxSize, got minSize 1, desiredSize 5, maxSize 2'; expected Message 'desiredSize can't be greater than maxSize'. Cause 3: UpdateNodegroupConfig(scalingConfig={desiredSize:5}) on a nodegroup whose scalingConfig is (min 1, max 2, desired 1) -> InvalidParameterException, Message 'Maximum capacity 2 can't be less than desired size 5'; expected Message 'desired capacity 5 can't be greater than max size 2'. Causes 4 and 5: 'Check timed out after 60.0s' with no assertion reached — the checks were still polling DescribeCertificateAuthority/DescribeUpdate (cause 4) and the served Kubernetes API for node/pod readiness (cause 5).

## Steps to Reproduce
1. CreateCluster, wait for ACTIVE, CreateNodegroup with a valid scalingConfig, wait ACTIVE; through the cluster endpoint POST a pod pinned to that nodegroup's node with a busybox command that exits 0, then poll the pod -> observe phase 'Failed' with reason 'StartError' and the emulator sentence instead of 'Succeeded' (cause 1). 2. CreateNodegroup(clusterName=<cluster>, nodegroupName=<new>, nodeRole=<role>, subnets=[...], scalingConfig={minSize:1,maxSize:2,desiredSize:5}) -> read Error.Message (cause 2). 3. On a nodegroup whose scalingConfig is (1,2,1): UpdateNodegroupConfig(scalingConfig={desiredSize:5}) -> read Error.Message (cause 3). 4. CreateCertificateAuthority on an ACTIVE cluster, then poll DescribeCertificateAuthority for distributionStatus COMPLETE and DescribeUpdate for Successful, then ActivateCertificateAuthority and poll signingStatus IN_USE -> the chain does not converge inside a client budget (cause 4). 5. On a cluster with a live nodegroup, wait through the served Kubernetes API for the node to report Ready and a pod to run, then DeleteCluster / read the pod-identity-injected env -> the wait never resolves (cause 5).
