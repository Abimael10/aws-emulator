# sagemakertrainingsessionruntime: unknown training sessions accepted by ExecuteSamplingOperation, httpLabel pattern gate preempts the 404, and every not-found/validation message is emulator-authored

> _Note: this issue was identified against the code base at commit `74a62806d9bf98fd5d44f7f49a4e3b8f76e4fbff`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
ExecuteSamplingOperation

## Description
Ten behavioral checks of the SageMakerTrainingSessionRuntime (LegoRouterService) data plane fail on eight distinct root causes, all in the resource-resolution and request-validation paths of this one service. Related open issues name some of the same code (20261117T022256Z-sagemakertrainingsessionruntime-resource-resolution-path-diverges-unknown-session-accepted.md and 20261117T022256Z-sagemakertrainingsessionruntime-sampling-operations-never-produce-a-result-getsamplingoperationresult.md, both from the wire corpus); neither carries these behavioral check ids, and causes 2, 3, 4, 6 and 7 below are divergences those issues do not describe at all (zero-member union wording, the validation-path prefix, the "Value null" prefix, and the session-vs-operation 404 on both read paths, whose emulator text has drifted from what that issue recorded). Eight causes.

Cause 1 of 8: ExecuteSamplingOperation materialises a training session that was never created instead of refusing the submit.
AWS: ExecuteSamplingOperation is a data-plane call against a session the control plane already created. Smithy: ExecuteSamplingOperation (POST /v1/training-sessions/{trainingSessionName}/sampling-operations) models ResourceNotFoundException at httpError 404, documented "The specified training session or operation does not exist, or the operation does not belong to the specified training session." Recorded behavior: a structurally valid submit naming a session that does not exist is answered 404 ResourceNotFoundException with message "Session not found: <trainingSessionName>-<accountId>-<region>" — fixed text "Session not found: " plus the session identity composed from the request's trainingSessionName, the caller's account id and the signing region. Under concurrency every racer gets that same 404 independently; no racer sees a success and none sees ConflictException.
Emulator: answers HTTP 200 with a freshly minted operationId (e.g. content-length 51, body {"operationId": "sampling-..."}), and 8 concurrent racers against a never-created session all got ('success', None). src/ops/execute_sampling_operation.rs:180 uses store.session_for_submit(...), which creates the session record on first use and can only fail with ThrottlingException when the store is full; ResourceNotFoundException is never constructed on this path.
Why: a client that submits to a deleted or mistyped session gets a success and a resolvable operationId, so a missing session is never surfaced; every not-found branch (recreate-the-session, fail-the-job, alert) is dead code against the emulator, and tests that assert refusal of an unknown session pass wrongly.
Fix: ExecuteSamplingOperation's handler plus the session lookup it calls in the service state (session_for_submit) — a submit must resolve an existing session and return ResourceNotFoundException with AWS's "Session not found: " text when there is none, never create one.
Traces: sagemakertrainingsessionruntime.execute-sampling-operation-well-formed-session-not-found, sagemakertrainingsessionruntime.execute-sampling-then-get-result-session-not-found-consistent, sagemakertrainingsessionruntime.concurrent-execute-sampling-notfound-consistency.

Cause 2 of 8: the zero-member operationConfig refusal is worded by the emulator's union validator, not as AWS words it.
AWS: Smithy: SampleOperationConfig is a union of sample | computeLogprobs | loadWeightsForSampling, documented "Exactly one member must be set to specify the operation type"; ValidationException is modelled at httpError 400. Recorded behavior: an operationConfig with no member set is refused 400 ValidationException with message "operationConfig must contain exactly one of: sample, computeLogprobs, loadWeightsForSampling" — entirely fixed text naming the input member and the union's member names, with no per-request variable part.
Emulator: 400 ValidationException with message "union 'SampleOperationConfig' had no member set" — generic framework prose naming the Smithy shape rather than the request member, and not AWS's sentence.
Why: a client or test that matches on the refusal text for an empty operation config never matches; the message names an internal shape id that AWS never exposes.
Fix: the request-validation step that refuses union arity for ExecuteSamplingOperation's operationConfig (the deserialize→validate stage ahead of the handler, as execute_sampling_operation.rs:166-168 notes) must emit AWS's wording for the zero-member case.
Traces: sagemakertrainingsessionruntime.execute-sampling-operation-config-union-member-count.

Cause 3 of 8: constraint-violation paths inside operationConfig omit the union member segment.
AWS: Smithy: LoadWeightsForSamplingConfig.modelPackageArn is required; SampleConfig.prompt is required. Recorded behavior: the ValidationException message addresses the offending member by its full input path through the union member, i.e. "'operationConfig.loadWeightsForSampling.modelPackageArn'" and "'operationConfig.sample.prompt'" — the fixed scaffold is "<n> validation error detected: Value <value> at '<path>' failed to satisfy constraint: Member must not be null", with <path> built from the request's own member chain (operationConfig -> the set union member -> the member).
Emulator: drops the union member segment, producing "...Value null at 'operationConfig.modelPackageArn' failed to satisfy constraint: Member must not be null" and "...Value null at 'operationConfig.prompt' ...".
Why: the path is how a client locates which field of which operation variant it got wrong; 'operationConfig.modelPackageArn' names a member that does not exist on the union, so automated field-level error mapping points at nothing.
Fix: the constraint-path construction in the request-validation layer for union-typed members, so a violation inside a union member is reported under '<union member>.<member>'.
Traces: sagemakertrainingsessionruntime.execute-sampling-operation-load-weights-arn-format-unchecked, sagemakertrainingsessionruntime.execute-sampling-operation-prompt-required-rejected.

Cause 4 of 8: a missing non-scalar member is reported with the "Value null at" prefix where AWS writes "Value at".
AWS: recorded behavior: for the absent required structure-typed member SampleConfig.prompt (target ModelInput), the message reads "1 validation error detected: Value at 'operationConfig.sample.prompt' failed to satisfy constraint: Member must not be null" — no "null" token between "Value" and "at" for a structure-typed member, unlike the scalar case (loadWeightsForSampling.modelPackageArn, a String) which does render "Value null at".
Emulator: always renders "Value null at ...", so the prompt refusal reads "1 validation error detected: Value null at 'operationConfig.prompt' failed to satisfy constraint: Member must not be null".
Why: the refusal text is part of the error contract; a client matching AWS's exact validation sentence for a missing prompt sees a different string.
Fix: the message rendering in the request-validation layer — omit the value token when the violating member's target is not a scalar.
Traces: sagemakertrainingsessionruntime.execute-sampling-operation-prompt-required-rejected.

Cause 5 of 8: GetTrainingOperationResult and GetSamplingOperationResult enforce the modelled httpLabel @pattern where AWS resolves the resource and answers 404.
AWS: Smithy declares trainingSessionName and operationId as TrainingSessionName/OperationId (length 1..64, pattern ^[a-zA-Z0-9-]+$) bound as httpLabel on both read paths, but recorded behavior shows AWS does NOT refuse a label that violates the pattern on these reads: a request with trainingSessionName "bad name!" is answered 404 ResourceNotFoundException (message per causes 6 and 7, the offending label echoed verbatim). The same malformed name IS still refused 400 ValidationException by ExecuteSamplingOperation ("1 validation error detected: Value '<name>' at 'trainingSessionName' failed to satisfy constraint: Member must satisfy regular expression pattern: [a-zA-Z0-9-]+"), which the emulator gets right — so this is an asymmetry between the write and read surfaces, not a blanket drop of the pattern.
Emulator: both GET paths answer 400 ValidationException for the pattern-violating label and never reach resolution.
Why: a client that polls with an identifier containing an unexpected character sees a validation failure where AWS reports the resource does not exist, so give-up/create-on-miss logic takes the wrong branch and the call is not retryable the way AWS's 404 is.
Fix: the httpLabel constraint gate applied to GetTrainingOperationResult and GetSamplingOperationResult — the modelled pattern must not be enforced on these read paths; resolution must proceed to ResourceNotFoundException.
Traces: sagemakertrainingsessionruntime.get-endpoints-skip-session-name-pattern-validation.

Cause 6 of 8: GetTrainingOperationResult reports the SESSION as absent, in emulator prose, where AWS reports the operation.
AWS: recorded behavior: for an operationId that does not resolve on the training route, the 404 body is message "Operation not found: <operationId>" — fixed text "Operation not found: " plus the operationId taken verbatim from the request URI label; the session name is not part of the message and the session is not what is named, even when the session itself does not exist. Smithy: ResourceNotFoundException{message} required, httpError 404.
Emulator: 404 with "Training session <trainingSessionName> does not exist." — different fixed text and the wrong variable (the session label instead of the operationId).
Why: a poller cannot tell which resource is missing, and anything matching the refusal text for a missing training operation sees a different string for the same condition.
Fix: the ResourceNotFoundException message construction in GetTrainingOperationResult's handler (the session-miss branch must report the operation, as AWS does).
Traces: sagemakertrainingsessionruntime.training-vs-sampling-result-not-found-message-differs, sagemakertrainingsessionruntime.get-endpoints-skip-session-name-pattern-validation.

Cause 7 of 8: GetSamplingOperationResult likewise reports the session, not the sample request.
AWS: recorded behavior: the sampling read path answers 404 with message "Sample request not found: <operationId>" — fixed text "Sample request not found: " plus the request's operationId verbatim (including an operationId that violates the modelled pattern), and deliberately different wording from the training route's "Operation not found: ", so the two sibling lookups are distinguishable.
Emulator: answers 404 "Training session <trainingSessionName> does not exist." when the session is unknown (src/ops/get_sampling_operation_result.rs:171-183) and "Sampling operation <operationId> does not exist, or does not belong to training session <trainingSessionName>." when only the operation is unknown (lines 184-197) — neither is AWS's text, and the first names the wrong resource.
Why: both sibling read paths now return the identical session-centric sentence, so a client cannot distinguish a missing sampling request from a missing training operation, and the documented message contract is not met.
Fix: the ResourceNotFoundException message construction in GetSamplingOperationResult's handler, both the session-miss and operation-miss branches.
Traces: sagemakertrainingsessionruntime.get-sampling-operation-result-not-found-ignores-operation-id-pattern, sagemakertrainingsessionruntime.execute-sampling-then-get-result-session-not-found-consistent, sagemakertrainingsessionruntime.training-vs-sampling-result-not-found-message-differs.

Cause 8 of 8: SampleTrainingSessionWithResponseStream pattern-validates trainingSessionName instead of answering the session 404.
AWS: Smithy: the streaming surface (POST /training-sessions/{trainingSessionName}/sample-with-response-stream) binds trainingSessionName as httpLabel with the same pattern and models ResourceNotFoundException at 404. Recorded behavior: a streaming sample against a pattern-violating session name is answered 404 ResourceNotFoundException with "Session not found: <trainingSessionName>-<accountId>-<region>" — the label echoed verbatim into the session identity — so the identical malformed name diverges between the two surfaces (400 on ExecuteSamplingOperation, 404 here) by design.
Emulator: 400 ValidationException on the pattern, never reaching resolution.
Why: a streaming client sees a validation refusal rather than the not-found it must handle, and never reaches the error path AWS exposes on this surface.
Fix: the httpLabel constraint gate for SampleTrainingSessionWithResponseStream plus its session resolution, which must emit ResourceNotFoundException with AWS's "Session not found: " text. Note this operation is also an unimplemented scaffold stub (services/service-com-amazonaws-sagemakertrainingsessionruntime-legorouterservice/src/ops/sample_training_session_with_response_stream.rs), filed separately for the check that reaches the stub; this cause is the pattern gate that fires BEFORE the stub and must also be corrected.
Traces: sagemakertrainingsessionruntime.execute-sampling-vs-stream-same-malformed-session-diverge.
