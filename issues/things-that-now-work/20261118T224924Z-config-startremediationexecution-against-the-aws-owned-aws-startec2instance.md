# config: StartRemediationExecution against the AWS-owned AWS-StartEC2Instance document reports a SUCCEEDED remediation execution while the targeted EC2 instance is never started, so the remediation has no side effect and the DeleteRemediationConfiguration consequence is never reached

> _Note: this issue was identified against the code base at commit `53eda64883178af14e234ca05ac2be08d2ce631b`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
StartRemediationExecution

## Description
One net-new root cause on the AWS Config surface, reached by one check the suite lists under `### config`. The replay report marked this failure neither ALREADY FILED nor OWNED by an open issue, so no open issue carries its replay key.

=== Cause 1 of 1: a remediation execution whose target is the AWS-owned SSM Automation document AWS-StartEC2Instance reaches State SUCCEEDED in Config's own bookkeeping, but the document is never actually run and the targeted EC2 instance stays stopped ===
Failing check: config.e2e-remediation-auto-execution-consequence

AWS: Smithy (com.amazonaws.configservice#StarlingDoveService) models StartRemediationExecution(ConfigRuleName @required @length 1..128 @pattern \S, ResourceKeys @required @length 1..100) -> {FailureMessage, FailedItems}, errors InsufficientPermissionsException / InvalidParameterValueException / NoSuchRemediationConfigurationException (all client, HTTP 400), and documents it as "Runs an on-demand remediation for the specified Config rules against the last known remediation configuration. It runs an execution against the current state of your resources. Remediation execution is asynchronous." DescribeRemediationExecutionStatus(ConfigRuleName @required, ResourceKeys, Limit 0..100) -> RemediationExecutionStatuses projects the state of that real execution. The remediation configuration under test has TargetType=SSM_DOCUMENT and TargetId=AWS-StartEC2Instance, an AWS-managed Automation document that exists in every account/Region; recorded behavior: Config starts an SSM Automation execution of that document under the role supplied in the AutomationAssumeRole parameter, with InstanceId resolved from the ResourceValue RESOURCE_ID (the resource key's resourceId), and AWS-StartEC2Instance both calls ec2:StartInstances and waits for the instance, so when the execution settles and Config reports RemediationExecutionStatuses[0].State = SUCCEEDED the instance's State.Name is already "running". The requirement is the SIDE EFFECT paired with the terminal State — a SUCCEEDED state means the document ran and its effect landed. Execution ids, instance ids, step timestamps and generated rule/role names are per-run values and are not part of the requirement.

Emulator: the Config-facing surface answers plausibly and the whole setup leg passes — the instance is launched, stopped, discovered by ListDiscoveredResources, the rule reaches ConfigRuleState ACTIVE with a real evaluation result, PutRemediationConfigurations is accepted for TargetId=AWS-StartEC2Instance (so the refusal described in open issue 20261116T162529Z-config-putremediationconfigurations-refuses-the-aws-owned-ssm-automation.md no longer fires here), StartRemediationExecution answers 200 with FailedItems=[], and DescribeRemediationExecutionStatus progresses to State=SUCCEEDED (the check's `assert status["State"] == "SUCCEEDED"` passes). The consequence never happens: ec2:DescribeInstances for the remediated instance keeps reporting the instance NOT running after Config declared the remediation SUCCEEDED, and the check dies in the very next poll. The terminal State is therefore synthesized rather than derived from a real SSM Automation execution of the target document. Hypothesis: the StartRemediationExecution executor marks its own record terminal without ever calling SSM StartAutomationExecution for the rendered target, so no ec2:StartInstances ever happens. Caveat, stated plainly: this poll ended with the harness's own `TimeoutError: the polled condition: the run budget ended first; not graded` because the earlier convergence waits had consumed the run budget, so the duration of the wait is not graded; the graded, emulator-caused part is the pairing — a SUCCEEDED remediation execution for AWS-StartEC2Instance whose instance is not running.

Why: a client that remediates through Config is told the remediation SUCCEEDED while the resource was never changed. Nothing distinguishes a real fix from a fabricated success: the instance is still stopped, re-reading the rule's compliance still reports the original verdict, and the only way to notice is to look in SSM, where no execution of the document exists. Auto-remediation pipelines, compliance gates and runbooks that act on a SUCCEEDED RemediationExecutionStatuses record all read as working while having no effect; a SUCCEEDED record that corresponds to nothing is worse than a refusal, which a caller could handle. It also blocks the rest of the contract behind it: because the check cannot observe the consequence, DeleteRemediationConfiguration followed by DescribeRemediationConfigurations == [] and the post-delete StartRemediationExecution refusal (HTTP 400, Error.Code NoSuchRemediationConfigurationException, Error.Message `There is no applicable RemediationConfiguration setup for AWS Config rule ` + <ConfigRuleName from the request> — fixed text with the rule name as the only variable part) are never exercised against this flow.

Fix: Config's remediation execution path — the StartRemediationExecution handler and the asynchronous executor behind it must resolve the rule's stored remediation configuration, render its Parameters (StaticValue/ResourceValue, including AutomationAssumeRole and the RESOURCE_ID-derived InstanceId), actually invoke SSM StartAutomationExecution for an SSM_DOCUMENT TargetId — including AWS-owned `AWS-*` documents, whose steps must have their real effect (AWS-StartEC2Instance must drive the EC2 instance to `running` in EC2's state) — and derive the RemediationExecutionStatuses record's State and step timestamps from that execution's real status instead of synthesizing a terminal state. A remediation that cannot run its target must surface as a FAILED execution state or a modeled 400, never as SUCCEEDED.

Related but NOT covering: open issue 20261111T121325Z-config-2-net-new-behavioral-causes-startremediationexecution-never.md describes the same emulator predicate (StartRemediationExecution reports success without running the SSM document) as its Cause 1, but it carries only the replay keys of config.concurrent-start-remediation-execution-dedup, config.e2e-remediation-execution-resolves-noncompliant-resource and config.conformance-pack-deploy-compliance-summary — all three using CUSTOMER-created documents — and the replay report did not mark this check owned by it, which is why this check is recorded here; this one additionally requires the AWS-owned AWS-StartEC2Instance document to run and to mutate EC2 state. Open issue 20261116T162529Z-config-putremediationconfigurations-refuses-the-aws-owned-ssm-automation.md also lists this check id, but its cause is the PutRemediationConfigurations refusal, which no longer occurs: the check now progresses past that call and fails strictly later, at the side-effect observation. Fixing the executor once should clear all of these.
