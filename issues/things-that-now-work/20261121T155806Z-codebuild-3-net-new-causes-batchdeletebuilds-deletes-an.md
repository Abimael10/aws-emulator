# CodeBuild: 3 net-new causes — BatchDeleteBuilds deletes an IN_PROGRESS build, StartBuild ignores concurrentBuildLimit, and StopBuild stamps STOPPED on QUEUED while discarding the phases already run

> _Note: this issue was identified against the code base at commit `82319d48a946e26ab7d96dc7ca606472e537bd51`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
BatchDeleteBuilds

## Description
THREE net-new root causes in the codebuild crate (services/service-com-amazonaws-codebuild-codebuild-20161006). ALL THREE must be closed before this issue is resolved.

These are the only failing codebuild checks of this sweep that the suite report does not mark OWNED or ALREADY FILED. The related open issue 20261107T225801Z-codebuild-6-net-new-causes-builds-and-sandbox.md lists all three check ids, but its replay keys for them bind the OLD failure site, where every build FAULTed in PROVISIONING (batch-delete at `assert len(still_running) == 1 and not still_running[0]["buildComplete"]`, the concurrency check at `assert not live.get("buildComplete")`, the stop check at `_poll_until_phase` asserting the build did not complete first). On this checkout builds DO run: the occupying build now reaches its BUILD phase, the twin control now reaches SUCCEEDED with INSTALL/PRE_BUILD/BUILD/POST_BUILD all SUCCEEDED, and each of the three checks now fails further on, at the assertions described below. 20261109T181128Z-codebuild-buildspec-commands-are-not-run-through-a.md covers the SAME concurrency accounting but only on the RetryBuild seam (its Cause 3) and explicitly leaves the StartBuild seam to another issue; it carries no key for these assertions either.

Cause 1 of 3: BatchDeleteBuilds deletes a build that is still IN_PROGRESS instead of withholding it.
AWS: Smithy BatchDeleteBuilds(ids: BuildIds, required, length 1..100) -> {buildsDeleted: BuildIds, buildsNotDeleted: BuildsNotDeleted}; BuildNotDeleted{id ("The ID of the build that could not be successfully deleted"), statusCode ("Additional information about the build that could not be successfully deleted")}; the only modeled error is InvalidInputException (client, 400). Recorded behavior for the partition itself: a batch mixing one build that has reached a terminal state with one that is still running is accepted (HTTP 200) and PARTITIONED — only the terminal build's identifier appears in buildsDeleted, and the still-running build is returned in buildsNotDeleted as a BuildNotDeleted whose `id` is that build's full ARN plus a statusCode saying why it was withheld (recorded behavior only for the statusCode's text). The withheld build is deletable by the same call once it has reached a terminal state. Both lists are ARN-valued in practice despite the "IDs" doc wording.
Emulator: both builds are reported deleted. For a batch of [terminal build, build whose `sleep 90` command is demonstrably still running — the check re-reads BatchGetBuilds immediately before the delete and sees buildComplete false], buildsDeleted comes back with BOTH ARNs ('arn:aws:codebuild:<region>:<account>:build/<project>:<uuid-fast>' and '...:<uuid-slow>') and the running build is not withheld.
Why: a client that deletes a batch of build records destroys builds that are still executing, and the buildsNotDeleted contract it uses to learn which ids it must retry later comes back empty, so it never retries and never learns that a running build was swept away. In-progress protection is absent, not merely mis-reported.
Fix: the BatchDeleteBuilds handler in the codebuild crate — partition the requested ids on build state, delete only builds in a terminal state, and emit each non-terminal one as a BuildNotDeleted{id: the build ARN, statusCode: the reason} in buildsNotDeleted.
Traces: codebuild.batch-delete-builds-partial-failure-isolated.

Cause 2 of 3: StartBuild does not enforce the project's concurrentBuildLimit — it mints an extra build where AWS refuses, and that build is then visible to ListBuildsForProject.
AWS: Smithy StartBuild(projectName required) -> {build}; modeled errors AccountLimitExceededException, InvalidInputException, ResourceNotFoundException (all client, httpError 400); AccountLimitExceededException is documented "An Amazon Web Services service limit was exceeded for the calling Amazon Web Services account." With the project's concurrentBuildLimit already saturated by a build that is in its BUILD phase, AWS refuses with HTTP 400 AccountLimitExceededException and the message 'Concurrent build limit exceeded. This build project has a limit of <limit> concurrent build(s). Start the build again after other builds are complete, or edit project configuration.' — the fixed text is that sentence pair, and <limit> is the project's configured concurrentBuildLimit taken from project state (1 in this scenario). No build record is created, so ListBuildsForProject still reports exactly the pre-existing builds. The same call is accepted once the occupying build has finished.
Emulator: the second StartBuild returns HTTP 200 with a brand-new build (buildNumber 2, currentPhase 'QUEUED', buildStatus 'IN_PROGRESS', phases SUBMITTED SUCCEEDED + QUEUED) while the first build of a concurrentBuildLimit=1 project is provably in its BUILD phase. No error code and no message are produced at all, and the extra build enters the project's build list.
Why: the limit a project advertises is not enforced on its primary start path. A client that relies on the refusal to back off instead exceeds its own configured concurrency, and the build set it reconciles against gains a build AWS would never have created.
Fix: the StartBuild handler's precondition checks in the codebuild crate — count the project's non-terminal builds against the project's concurrentBuildLimit before minting a build, and refuse with AccountLimitExceededException (HTTP 400) carrying CodeBuild's wording, creating no build record on the refused path.
Traces: codebuild.codebuild-concurrent-build-limit-rejects-the-second-start-and-no-second-build-appears.

Cause 3 of 3: StopBuild attributes the stop to the QUEUED phase and the build's final phase timeline drops every phase that had already run.
AWS: Smithy StopBuild(id required) -> {build}; BuildPhase{phaseType, phaseStatus, startTime, endTime, durationInSeconds, contexts}; StatusType enum [SUCCEEDED, FAILED, FAULT, TIMED_OUT, IN_PROGRESS, STOPPED]; BuildPhaseType enum [SUBMITTED, QUEUED, PROVISIONING, DOWNLOAD_SOURCE, INSTALL, PRE_BUILD, BUILD, POST_BUILD, UPLOAD_ARTIFACTS, FINALIZING, COMPLETED]. Recorded behavior for the timeline: a StopBuild issued while the build reports currentPhase 'PRE_BUILD' marks EXACTLY ONE phase with phaseStatus STOPPED, and it is the phase that was in flight (PRE_BUILD); the phases that already finished keep phaseStatus SUCCEEDED (INSTALL here); the phases after the stopped one never reach SUCCEEDED; the stopped phase reports a durationInSeconds strictly smaller than the same phase of a twin build allowed to run it to completion; and the build settles buildStatus STOPPED with an endTime.
Emulator: the build is driven to currentPhase 'PRE_BUILD' (the check polls for it and sees it) and stopped there, yet the final record reports phases=[('SUBMITTED','SUCCEEDED'), ('QUEUED','STOPPED'), ('COMPLETED', None)] — the STOPPED status is stamped on QUEUED, which was not the running phase, and the PROVISIONING/DOWNLOAD_SOURCE/INSTALL/PRE_BUILD entries the build had already reported live are absent from the stopped build's phase list. buildStatus STOPPED and endTime are correct; a same-instant twin on the same project runs all four buildspec phases to SUCCEEDED, so this is specific to the stop path.
Why: the phase timeline is the only record of how far a stopped build got. A client reading it cannot tell which phase absorbed the stop, cannot see that INSTALL completed, and cannot compare the interrupted phase's durationInSeconds against a completed run — a build stopped deep in PRE_BUILD is indistinguishable from one stopped before it was ever provisioned.
Fix: the StopBuild transition in the codebuild build-execution component — stamp phaseStatus STOPPED on the phase that is currently in flight, preserve the phases already recorded with their SUCCEEDED statuses and their start/end/duration, close out the stopped phase with an endTime and durationInSeconds, and append COMPLETED without rewriting the earlier entries.
Traces: codebuild.stop-build-during-pre-build-stops-exactly-that-phase-and-leaves-the-rest-unrun.
