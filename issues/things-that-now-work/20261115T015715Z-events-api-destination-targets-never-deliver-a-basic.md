# events: API-destination targets never deliver — a BASIC connection's PUT/Authorization/bare-envelope contract and the 4xx-vs-5xx retry/dead-letter classification are both unobservable (2 causes)

> _Note: this issue was identified against the code base at commit `2f00469c6b1c115e8270b5c2778d03323e9ec131`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
PutTargets

## Description
Two net-new root causes of service `events`, grounded in two failing behavioral checks. Both sit on the same hop — an EventBridge rule target whose Arn is an `api-destination` — but they are two distinct contracts a fixer must close separately: the outbound HTTP request the emulator must actually make (Cause 1) and the retry/dead-letter classification of the endpoint's status code (Cause 2).

Note on related open issues: 20261029T092208Z-events-eventbridge-api-destination-targets-never-deliver-so-the.md, 20261107T042814Z-events-api-destination-dead-letter-attributes-and-the.md, 20261107T042814Z-events-lambda-sqs-an-api-destination-dead-letter.md and 20261027T200000Z-events-eventbridge-an-oauth-client-credentials-connection-never-fetches-a-token-so-its-api-destination-never-delivers.md describe adjacent api-destination defects (the OAUTH token fetch, invented dead-letter attributes). None of them carries the replay key of either check below, and the two checks below exercise the BASIC auth scheme and the 400-vs-500 differential, so they are filed here.

Cause 1 of 2: a BASIC connection's API destination never calls the endpoint, so the request's method, Authorization header, query string and body are never produced. Failing check: events.api-destination-basic-connection-sends-the-basic-authorization-header-with-the-destinations-method-and-the-bare-envelope.
AWS:      Smithy (eventbridge/awsevents): CreateApiDestination requires `ConnectionArn`, `InvocationEndpoint` (HttpsEndpoint) and `HttpMethod` (enum ApiDestinationHttpMethod); PutTargets accepts a target whose `Arn` is an `api-destination/<name>/<id>` ARN plus `RoleArn` and an optional `InputTransformer`. Model-described wire shape only for the control plane; the delivery itself is recorded behavior only. When an event matches a rule whose target is that destination, EventBridge issues ONE outbound HTTPS request to the destination's InvocationEndpoint using the destination's HttpMethod (PUT here, not POST), with no query string appended to the configured path, with an `Authorization: Basic base64("<Username>:<Password>")` header built from the connection's BasicAuthParameters, and with the matched event's bare envelope as the JSON body — exactly the keys `account, detail, detail-type, id, region, resources, source, time, version`, `id` the delivered event's id, `source` the publisher's source and `detail` the published detail. When the target carries an InputTransformer, the rendered template is sent as the body instead (here `{"order": <m>, "event": <id>}` with `<m>` = `$.detail.m` and `<id>` = `$.id`), and nothing else about the request changes.
Emulator: no request ever reaches the endpoint. PutRule/PutTargets on both rules are accepted (`FailedEntryCount == 0`) and PutEvents is accepted, but the capture endpoint receives neither the raw nor the transformed delivery; the check sits in its publish-and-poll loop until the harness cuts it — verdict mismatch, "Check timed out after 60.0s" (the check's own delivery budget is 180 s, so the replay shows absence of delivery, not a slow delivery).
Why:      a client that fans events out to an HTTP(S) API through an api-destination target gets nothing: no webhook is called, no Basic credential is presented, and the input transformer's rendering is never exercised. Because the hop is silent, the whole request contract above (method from the destination, no query string, Basic Authorization from the connection, bare envelope vs rendered template) is unverifiable.
Fix:      the EventBridge target-dispatch path for api-destination targets in the eventbridge crate — the outbound HTTP invoker that must resolve the target ARN to its destination, read the destination's HttpMethod/InvocationEndpoint, apply the referenced connection's AuthorizationType (BASIC -> the Authorization header) and serialize either the bare envelope or the InputTransformer rendering as the request body.
Traces:   events.api-destination-basic-connection-sends-the-basic-authorization-header-with-the-destinations-method-and-the-bare-envelope

Cause 2 of 2: an api-destination target's HTTP status code drives neither retry nor dead-letter classification — no event is ever dead-lettered with the status-bearing attributes. Failing check: events.api-destination-4xx-dead-letters-without-retry-while-5xx-is-retried-until-its-retry-attempts-are-used-up.
AWS:      recorded behavior only (the retry/dead-letter attributes are not in the Smithy model; PutTargets models `DeadLetterConfig.Arn` and `RetryPolicy.MaximumRetryAttempts`/`MaximumEventAgeInSeconds`, which this check sets to 1 and 900). For one event matched by a rule with two api-destination targets differing only in the status their endpoint returns: a 4xx response is NOT retried — the event is dead-lettered once, and the DLQ message attributes are exactly `ERROR_CODE=INVALID_PARAMETER`, `ERROR_MESSAGE="ApiDestination returned HTTP status 400 with payload: "` (fixed text with the status code taken from the endpoint's response and the payload appended verbatim), `RULE_ARN` the matched rule's ARN and `TARGET_ARN` the destination's ARN — with no retry attributes present. A 5xx response IS retried until MaximumRetryAttempts is used up (so the endpoint sees the event at least twice for MaximumRetryAttempts=1), and its dead letter carries `ERROR_CODE=UNKNOWN`, `ERROR_MESSAGE="ApiDestination returned HTTP status 500 with payload: "`, `EXHAUSTED_RETRY_CONDITION=MaximumRetryAttempts`, `RETRY_ATTEMPTS` the configured attempt count as a string, plus `RULE_ARN` and `TARGET_ARN`. The status code and the attempt count are values from the response and the target's RetryPolicy; the attribute names, the two ERROR_CODE values and the message's fixed text are the requirement.
Emulator: nothing is delivered and nothing is dead-lettered. CreateConnection(API_KEY), CreateApiDestination x2, the role, the bus, the rule and PutTargets (`FailedEntryCount == 0`) and every PutEvents are all accepted, but neither the /s400 nor the /s500 endpoint is ever called and the DLQ stays empty, so no event is ever dead-lettered by both targets. The check exhausts its run budget inside that loop and ends errored: `TimeoutError: an event dead-lettered by both targets: the run budget ended first; not graded` (its own delivery budget is 360 s).
Why:      a client relying on EventBridge's documented failure handling cannot tell a client-side (4xx, non-retryable) delivery failure from a server-side (5xx, retryable) one: no retry happens, no dead letter is produced, and the DLQ attributes it parses to route or alarm on failures never exist. Undeliverable events are silently lost instead of landing in the configured DeadLetterConfig queue.
Fix:      the api-destination invocation result handling in the EventBridge target-dispatch path — the status-code classification (4xx non-retryable vs 5xx retryable), the RetryPolicy attempt loop, and the dead-letter writer that stamps ERROR_CODE/ERROR_MESSAGE/EXHAUSTED_RETRY_CONDITION/RETRY_ATTEMPTS/RULE_ARN/TARGET_ARN onto the DLQ message.
Traces:   events.api-destination-4xx-dead-letters-without-retry-while-5xx-is-retried-until-its-retry-attempts-are-used-up
