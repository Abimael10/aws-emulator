# backup: 2 net-new causes — every backup job settles FAILED/AccessDenied because a role holding the AWS managed backup policy is read as granting nothing, and the resource-not-found job class is unreachable

> _Note: this issue was identified against the code base at commit `70791fed095f2893ec100d3b09cefba6c5cbd55a`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
StartBackupJob

## Description
Two distinct net-new root causes in the AWS Backup crate (services/service-com-amazonaws-backup-cryocontrollerusermanager). Both must be closed separately. None of the 12 failing checks below is marked ALREADY FILED or OWNED in the replay report. The nearest open issue, 20261029T175130Z-backup-aws-backup-vault-lock-and-tiering-refusals-use.md, covers the vault-lock refusal wording and the CALLER-side authorization of StartBackupJob (its explicit-deny half now passes in replay); it says nothing about the outcome a started job comes to under its IamRoleArn, which is what these two causes are about.

=== Cause 1 of 2: a backup job whose IamRoleArn names a role carrying the AWS managed backup policy is judged to withhold the resource-level backup action, so EVERY backup job settles FAILED with MessageCategory AccessDenied and no recovery point ===
AWS: Smithy: StartBackupJob.IamRoleArn is @required — "Specifies the IAM role ARN used to create the target recovery point"; DescribeBackupJob reports State (BackupJobState: CREATED|PENDING|RUNNING|ABORTED|ABORTING|COMPLETED|FAILED|EXPIRED|PARTIAL), StatusMessage and MessageCategory, whose doc reads "Example strings may include AccessDenied, SUCCESS, AGGREGATE_ALL, and INVALIDPARAMETERS". IAM authorization itself is not modeled, so for the decision this is recorded behavior only: a role whose trust policy trusts backup.amazonaws.com and which has had arn:aws:iam::aws:policy/service-role/AWSBackupServiceRolePolicyForBackup attached with AttachRolePolicy IS authorized for the per-resource-type creating action (dynamodb:CreateBackup for a DynamoDB table, elasticfilesystem:Backup for an EFS file system), so the on-demand job progresses CREATED -> RUNNING -> COMPLETED, carries no failure StatusMessage, and the vault gains the recovery point the job's RecoveryPointArn names.
Emulator: the job is stored already doomed and the clock settles it FAILED within half a second of StartBackupJob, PercentDone '0.0', BackupSizeInBytes 0, no recovery point stored, MessageCategory 'AccessDenied' and StatusMessage 'User: <IamRoleArn> is not authorized to perform: dynamodb:CreateBackup on resource: <ResourceArn> because no identity-based policy allows the dynamodb:CreateBackup action' (fixed text 'User: ', ' is not authorized to perform: ', ' on resource: ', ' because no identity-based policy allows the ', ' action'; the variable parts are the request's IamRoleArn, the per-resource-type action from state/job_outcome.rs BACKUP_ROLE_ACTIONS and the request's ResourceArn). The decision comes from state::job_outcome::withheld_backup_denial, which calls service_common::iam_role::role_withholds_action; that reader treats EVERY decision other than Allowed — including IAM's implicit deny, mapped to Decision::NotStated — as a withheld action, and the emulator's IAM holds no document for the AWS managed policy the role has attached, so SimulatePrincipalPolicy answers implicitDeny and the job is denied. This also contradicts the reader's own stated rule ("An attachment whose document this account does not hold is a grant nothing can read, so it is one of those non-answers as well").
Why: no backup can be taken at all against this emulator. Everything downstream of a COMPLETED job is unreachable for a client doing exactly what AWS's own documentation prescribes (create a service role, attach AWSBackupServiceRolePolicyForBackup, StartBackupJob): recovery points, restores, restore metadata, legal holds, lifecycle/vault-lock enforcement on a real recovery point, and copy jobs. A client sees an authorization failure for a correctly provisioned backup service role and has no way to make a backup succeed.
Fix: the role-permission half of a job's outcome — state/job_outcome.rs (withheld_backup_denial) and the shared reader it asks, services/common/src/iam_role.rs (role_withholds_action / role_withholds_action_through / role_action_decision_through): a managed policy attached to the role whose document this account's IAM does not hold, and the implicit deny IAM returns for it, must leave the job's outcome alone instead of denying it; alternatively the IAM store must hold the AWS managed policy documents it lets AttachRolePolicy attach, so AWSBackupServiceRolePolicyForBackup grants the per-resource-type action it publishes.
Traces: backup.backup-vault-lock-compliance-mode-server-enforced, backup.deploy-backup-vault-cfn-lock-enforced, backup.e2e-legal-hold-blocks-deletion-then-release, backup.e2e-plan-selection-backup-job-to-recovery-point, backup.e2e-restore-job-validation-flow, backup.ondemand-dynamodb-backup-restore-keeps-global-secondary-index, backup.recovery-point-restore-metadata-read-from-completed-dynamodb-backup, backup.start-backup-job-insufficient-role-permission-denied (its positive control), backup.vault-lock-min-retention-enforced, backup.delete-recovery-point-wrong-state-rejected (EFS resource type), backup.start-restore-job-invalid-metadata-rejected (cut off at the 60 s budget polling the never-completing prerequisite job).

=== Cause 2 of 2: a job started for a ResourceArn no service holds reports the role-denial class instead of AWS's resource-not-found class ===
AWS: recorded behavior only (the model documents neither class beyond the MessageCategory example strings above): a StartBackupJob naming a ResourceArn of the right shape for which the owning service holds no resource is accepted, and the job settles FAILED carrying StatusMessage 'Requested resource not found: ResourceArn: <the request's ResourceArn> not found' — fixed text 'Requested resource not found: ResourceArn: ' and ' not found' around the ResourceArn the request named — with MessageCategory 'RESOURCE_NOT_FOUND'; DescribeRecoveryPoint on the reserved RecoveryPointArn is then refused ResourceNotFoundException 'Cannot find recovery point'.
Emulator: that job settles FAILED with the Cause-1 authorization sentence and MessageCategory 'AccessDenied' instead. state/job_outcome.rs::withheld_backup asks the ROLE question first and returns on its answer, so the resource-existence question (protected_resource_answer) is never reached and the RESOURCE_NOT_FOUND class is unreachable for any resource type whose creating action appears in BACKUP_ROLE_ACTIONS.
Why: a client that branches on MessageCategory or on the StatusMessage — alerting on AccessDenied as a policy misconfiguration and on RESOURCE_NOT_FOUND as a stale selection/target — is told its backup role is broken when the protected resource simply does not exist, and the correct remediation is never surfaced.
Fix: the ordering and classification in state/job_outcome.rs::withheld_backup — the resource-existence answer must decide the job's class whenever the role question produces no genuine denial, so the two failure classes are distinguishable.
Traces: backup.start-backup-job-nonexistent-resource-job-fails.
