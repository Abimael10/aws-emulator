# lambda-core: a new connector's PENDING window has zero length, so the modelled ResourceConflictException state gates on UpdateNetworkConnector and DeleteNetworkConnector are unreachable

> _Note: this issue was identified against the code base at commit `94cb6f5119094356054cdb35f84935529834678c`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
UpdateNetworkConnector

## Description
One net-new root cause, grounded in both surviving failing behavioral checks of this service.

Cause 1 of 1 — a connector created by CreateNetworkConnector is never observably PENDING to any call that follows the create, so neither of the two state-gated refusals the model documents can ever be produced, and both mutations that AWS refuses on a freshly-created connector are instead accepted.

AWS: Smithy CreateNetworkConnector (POST /2026-04-04/network-connectors, success 202) documents "This operation is asynchronous. The network connector starts in PENDING state while ENIs are provisioned in your VPC … Use GetNetworkConnector to poll the connector state until it reaches ACTIVE", so PENDING is a state a client can read back through GetNetworkConnector, not only a value in the create's own 202 body. On top of that window two refusals are modelled:
  (a) UpdateNetworkConnector (PUT /2026-04-04/network-connectors/{Identifier}, success 202) — "The connector must be in ACTIVE state to accept updates"; its error ResourceConflictException (HTTP 409) is documented "The request could not be completed due to a conflict with the current state of the resource. For example, attempting to update a connector that is not in ACTIVE state." Recorded behavior: the refusal is ResourceConflictException / HTTP 409 with the message "Network connector <Id> is in state Pending and cannot be updated. Only ACTIVE connectors can be updated." Fixed text: "Network connector ", " is in state ", " and cannot be updated. Only ACTIVE connectors can be updated."; variable parts: <Id> is the connector's service-assigned NetworkConnectorId taken from the emulator's own state (never the identifier form the request happened to use), and "Pending" is the connector's current NetworkConnectorState spelled as a word (PENDING -> Pending). The refused update must leave the stored Configuration untouched (a subsequent GetNetworkConnector still reports the pre-update SecurityGroupIds/SubnetIds).
  (b) DeleteNetworkConnector (DELETE /2026-04-04/network-connectors/{Identifier}, success 202, idempotent) — "You can delete connectors in ACTIVE or FAILED states", with the same ResourceConflictException (HTTP 409) modelled. Recorded behavior: the refusal message is "Network connector is in PENDING state and cannot be deleted" — fixed text "Network connector is in " and " state and cannot be deleted", with the connector's current NetworkConnectorState as its wire value (PENDING) as the only variable part. The refused delete must not move the connector out of PENDING.
The positive controls AWS also provides: once the connector reaches ACTIVE, the same update is accepted 202 and converges to LastUpdateStatus=Successful with the new SecurityGroupIds, and the same delete is accepted 202 with State=DELETING.

Emulator: the PENDING -> ACTIVE transition is made due at the instant the create starts it — services/service-com-amazonaws-lambdacore-lambdacoreapiservice/src/state.rs defines `pub const fn settles_at(started: SystemTime) -> SystemTime { started }`, and create_network_connector.rs builds the connector's PendingTransition with `due: settles_at(now)`. Every later call resolves the record through `settled_mut`, which materialises any transition already due, so the FIRST call after the create already sees State=ACTIVE. The gates themselves are written and correct (update_network_connector.rs refuses with `update_requires_active(&connector.id, &connector.state)` when `connector.state != STATE_ACTIVE`; delete_network_connector.rs refuses with `delete_refused_in_state(&connector.state)` when the state is not one of ACTIVE/FAILED/DELETING) — they are simply dead code, because no state other than ACTIVE is ever reachable by a second call. Observed in replay: UpdateNetworkConnector issued immediately after a create whose own 202 reported State=PENDING was ACCEPTED (check network-connector-update-pending-conflict-then-active-success failed at its `_error(...)` helper with "the call unexpectedly SUCCEEDED; real AWS rejects it" instead of receiving ResourceConflictException), and across five fresh connectors no connector was still PENDING on the Get taken right after the mutation (check pending-connector-rejects-update-and-delete failed with "no connector stayed PENDING through both the Update and the Delete, so neither refusal could be observed against a PENDING connector").

Why: a client written against AWS gets two things wrong. First, it is told a mutation succeeded that AWS refuses with 409 — code that creates a connector and immediately reconfigures or tears it down appears to work against the emulator and then fails in production with ResourceConflictException, and emulator-side the configuration of a connector whose ENIs are notionally still being provisioned is mutated. Second, no client can exercise or test the PENDING arm of this service at all: the documented poll-until-ACTIVE loop never sees PENDING, retry/back-off logic keyed on ResourceConflictException is never triggered, and the two refusal messages the service owes (and their 409 status) are unreachable, so a 409-handling path can never be validated.

Fix: the connector lifecycle in this service's state layer — the `settles_at` policy in services/service-com-amazonaws-lambdacore-lambdacoreapiservice/src/state.rs and the PendingTransition the create handler installs — must give the PENDING -> ACTIVE provisioning a window of non-zero length, so that at least the next call addressed to the connector still observes PENDING and the already-written gates in the Update and Delete handlers fire with their modelled 409 and messages, while the window still stays short enough that the documented GetNetworkConnector poll loop converges to ACTIVE (the checks poll with 2 s–15 s intervals inside their budget) and the positive controls (update accepted and converging to LastUpdateStatus=Successful, delete accepted with State=DELETING) still pass. Note the tension with open issue 20261103T161149Z-lambda-core-lambda-microvms-vpc-egress-data-plane.md, which asks these transitions to settle so chained poll loops converge: both must hold — PENDING observable to the immediately-following call, and convergence to ACTIVE within a normal poll interval. Neither of the two open lambda-core network-connector issues (20261117T012253Z-lambda-core-network-connector-lifecycle-transitions-are-not.md, about version StateReason text and the version-scoped delete's State member, and 20261023T022015Z-lambda-core-admits-requests-aws-refuses-and-misclassifies.md, about identifier-shaped refusals) covers this state gate; replay reports both checks below as unowned.

Traces: lambda-core.network-connector-update-pending-conflict-then-active-success (the PENDING update was accepted) and lambda-core.pending-connector-rejects-update-and-delete (neither the PENDING update refusal nor the PENDING delete refusal could be observed across five fresh connectors).

## Steps to Reproduce
1. git_clone(), then run_behavioral_suite(); lambda-core.network-connector-update-pending-conflict-then-active-success and lambda-core.pending-connector-rejects-update-and-delete both fail as quoted in Evidence.
2. By hand against the running emulator: create a VPC, a subnet in an available AZ, a security group, and an IAM operator role trusting lambda.amazonaws.com.
3. CreateNetworkConnector with a VpcEgressConfiguration naming that subnet and group plus the operator role. Observe the 202 body reports State='PENDING'.
4. Immediately call GetNetworkConnector with the same Identifier — observe State='ACTIVE' on the very first read, although nothing was polled and no time was allowed to pass.
5. Immediately after the create, call UpdateNetworkConnector on that Identifier with a changed SecurityGroupIds list — observe HTTP 202 success. AWS answers HTTP 409 ResourceConflictException "Network connector <Id> is in state Pending and cannot be updated. Only ACTIVE connectors can be updated." and leaves the stored configuration unchanged.
6. Repeat from step 3 and, immediately after the create, call DeleteNetworkConnector on that Identifier — observe the 202 delete acknowledgement. AWS answers HTTP 409 ResourceConflictException "Network connector is in PENDING state and cannot be deleted" and leaves the connector in PENDING.
7. Positive controls that must keep working after the fix: once GetNetworkConnector reports ACTIVE, the same UpdateNetworkConnector is accepted 202 and GetNetworkConnector converges to LastUpdateStatus='Successful' with the new SecurityGroupIds, and the same DeleteNetworkConnector is accepted 202 with State='DELETING' and the connector later answers ResourceNotFoundException.
