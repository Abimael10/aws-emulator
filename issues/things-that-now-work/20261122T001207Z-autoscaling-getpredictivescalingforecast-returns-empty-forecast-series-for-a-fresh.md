# GetPredictiveScalingForecast returns empty forecast series for a fresh policy, and its unknown-policy ValidationError message drops AWS's trailing period (2 causes)

> _Note: this issue was identified against the code base at commit `a9288303feb8dead80b5d9b52ed92320ffa70966`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
GetPredictiveScalingForecast

## Description
Two net-new root causes in the autoscaling emulator's now-implemented `GetPredictiveScalingForecast` handler (services/service-com-amazonaws-autoscaling-autoscaling-2011-01-01/src/ops/get_predictive_scaling_forecast.rs). NOTE: the open issue `20261111T072954Z-autoscaling-getpredictivescalingforecast-stub.md` ("Implement autoscaling GetPredictiveScalingForecast: unimplemented scaffold stub") does NOT cover these: the operation no longer answers 501 — it answers 200 and an explicit ValidationError — and the replay report marks none of the three checks below as already filed or owned. These are fidelity defects in the implemented handler.

Cause 1 of 2: a freshly created PredictiveScaling policy is answered with EMPTY LoadForecast/CapacityForecast series instead of the hourly forecast grid.
AWS: Smithy model `GetPredictiveScalingForecast` output declares `LoadForecast` (LoadForecasts), `CapacityForecast` (CapacityForecast) and `UpdateTime` all **required**; `CapacityForecast` and `LoadForecast` each declare `Timestamps` (PredictiveScalingForecastTimestamps, "The timestamps for the data points, in UTC format") and `Values` (PredictiveScalingForecastValues, "The values of the data points") as **required**, and `LoadForecast` additionally `MetricSpecification`. The operation's own doc sentence — "A minimum of 24 hours of data is required to create the initial forecasts. However, having a full 14 days of historical data results in more accurate forecasts" — governs the QUALITY/accuracy of the forecast, not whether a grid is returned. Recorded behavior: for a policy created seconds earlier against a group with no CloudWatch history, AWS returns, for the requested StartTime..EndTime window, one LoadForecast entry per metric specification whose `Timestamps` is a strictly increasing hourly grid and whose `Values` is the same length as `Timestamps`, with unknown points filled with NaN, and a `CapacityForecast` on exactly the same timestamp grid whose NaN/non-NaN points coincide with the load series point for point. Status 200.
Emulator: answers 200 but with `LoadForecast[0].Timestamps == []`, `LoadForecast[0].Values == []` and `CapacityForecast.Timestamps == []`, `CapacityForecast.Values == []` (replay: "GetPredictiveScalingForecast returned an empty or length-mismatched LoadForecast/CapacityForecast series: load=[] cap=[]" and "LoadForecast Timestamps/Values must be non-empty and length-aligned, even immediately after policy creation with no CloudWatch history"). This is deliberate in the state module: `src/state/predictive_forecast.rs` documents (module header, bullet at lines 28-31) "Fewer than [MIN_HISTORY_PERIODS] hours observed … such a policy has NO forecast to report: its load and capacity series are reported empty rather than invented", implemented by `daily_profile` returning `None` when `history.len() < MIN_HISTORY_PERIODS` (lines 584-590), which collapses the whole series to empty.
Why: a client that reads the forecast grid — plotting it, sizing a warm pool from it, or zipping `Timestamps` with `Values` — sees no data points at all against the emulator where AWS hands back a full hourly grid of NaN placeholders. Any code that indexes the first/last point, computes a series length, or relies on load and capacity sharing one timestamp grid breaks on the emulator and works on AWS; a "no forecast yet" state becomes indistinguishable from "the window contains no hours".
Fix: the forecast computation in the operation's state component (`crate::state::predictive_forecast`, reached from the operation's handler): the hourly timestamp grid for the requested window must be produced independently of how much history exists, with NaN values where no forecast can be computed, and the capacity series emitted on that same grid with NaN at exactly the same points — rather than short-circuiting the whole series to empty when history is below the 24-period minimum.
Traces: autoscaling.predictive-scaling-forecast-load-capacity-consistency, autoscaling.predictive-scaling-forecast-timestamp-value-alignment (the same empty series also removes all content from the forecast assertions of autoscaling.predictive-scaling-policy-and-forecast).

Cause 2 of 2: the ValidationError refusal for a policy name that resolves to nothing omits the trailing period of AWS's sentence.
AWS: recorded behavior — GetPredictiveScalingForecast naming a policy that does not exist in the named group is refused with error code `ValidationError` and message `Policy <PolicyName> not found.` The fixed text is `Policy ` + ` not found.` (including the terminating full stop); the only variable part is `<PolicyName>`, taken verbatim from the request's `PolicyName` member. The model declares only `ResourceContentionFault` for this operation, so the refusal class itself is recorded behavior only; the code (`ValidationError`) and the status the recording carries are what the client sees.
Emulator: same code `ValidationError`, but the message is `Policy <PolicyName> not found` — the final period is missing (replay: expected message 'Policy sim2real-behav-as-nopol-… not found.', got 'Policy sim2real-behav-as-nopol-… not found'). Source: `src/state/policy_execution.rs` lines 235-237, `absent_policy_message` = `format!("Policy {policy_name} not found")`, which the handler uses for the absent-policy refusal.
Why: clients and test suites that match this refusal on its exact message text (log scrapers, error-mapping tables, assertions on the sentence) do not recognise the emulator's refusal as AWS's absent-policy refusal, so an error that should be understood as "no such policy" is treated as an unknown validation failure.
Fix: the absent-policy refusal message for this operation — the shared helper `absent_policy_message` in the service's policy state component. Note it is shared with the other policy-naming operations, so any sibling caller whose own recording shows different wording must keep its own sentence rather than being changed along with it.
Traces: autoscaling.predictive-scaling-policy-and-forecast.

## Evidence
Cause 1 — expected (AWS): GetPredictiveScalingForecast for a PredictiveScaling policy created moments earlier (ForecastOnly, one PredefinedMetricPairSpecification ASGCPUUtilization, TargetValue 50.0) over a StartTime..EndTime window of ±24h returns HTTP 200 with LoadForecast[0].Timestamps a strictly increasing hourly grid, len(Timestamps) == len(Values) > 0, CapacityForecast.Timestamps identical to the load grid, len == len(Values) > 0, and every point NaN in both series (no CloudWatch history). Actual (emulator): HTTP 200 with load=[] and cap=[] — `AssertionError: GetPredictiveScalingForecast returned an empty or length-mismatched LoadForecast/CapacityForecast series: load=[] cap=[]` (check predictive-scaling-forecast-load-capacity-consistency) and `AssertionError: LoadForecast Timestamps/Values must be non-empty and length-aligned, even immediately after policy creation with no CloudWatch history` (check predictive-scaling-forecast-timestamp-value-alignment).

Cause 2 — expected (AWS): error code `ValidationError`, message `Policy <PolicyName> not found.` (fixed text `Policy ` / ` not found.`; variable part is the request's PolicyName). Actual (emulator): code `ValidationError`, message `Policy <PolicyName> not found` (no trailing period) — `AssertionError: expected message 'Policy sim2real-behav-as-nopol-24e01e4466bb not found.', got 'Policy sim2real-behav-as-nopol-24e01e4466bb not found'`. (The name in that line is this run's generated value; only the surrounding fixed text and the terminating period are the requirement.)

## Steps to Reproduce
1. Boot the autoscaling emulator (with ec2/ssm for the launch template AMI lookup).
2. Create a launch template and an Auto Scaling group with MinSize/MaxSize/DesiredCapacity 0 in one AZ of the shared network.
3. PutScalingPolicy with PolicyType=PredictiveScaling, PredictiveScalingConfiguration={MetricSpecifications:[{TargetValue:50.0, PredefinedMetricPairSpecification:{PredefinedMetricType:ASGCPUUtilization}}], Mode:ForecastOnly}.
4. Call GetPredictiveScalingForecast for that group/policy with StartTime=now-24h, EndTime=now+24h. Observe LoadForecast[0].Timestamps/Values and CapacityForecast.Timestamps/Values are all empty lists, instead of the strictly increasing hourly grid with length-aligned NaN values AWS returns (Cause 1).
5. Call GetPredictiveScalingForecast again on the same group with a PolicyName that was never created. Observe ValidationError with message `Policy <name> not found` instead of AWS's `Policy <name> not found.` (Cause 2).
6. Re-replay autoscaling.predictive-scaling-forecast-load-capacity-consistency, autoscaling.predictive-scaling-forecast-timestamp-value-alignment and autoscaling.predictive-scaling-policy-and-forecast to confirm.
