# ram catalog and share-permission reads serve incomplete data: ListResourceTypes publishes an emulator-authored resource-type catalog, ListResourceSharePermissions reports no attached permission

> _Note: this issue was identified against the code base at commit `c00bf07ce89c73b0369514a40ab33e3142015054`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
ListResourceTypes

## Description
Two net-new causes (Cause 1 of 2, Cause 2 of 2), both in ram, both grounded in wire divergences the replay reported as neither stub-blocked (stub_path empty) nor owned by an open issue (owned_by empty). Both are well-formed HTTP 200 bodies whose contents diverge: a read of RAM's shareable-resource-type catalog, and the share-scoped read of a share's attached managed permissions.

Cause 1 of 2 — ListResourceTypes serves an emulator-authored resource-type catalog: a different set of resource types, in a different publication order, and every entry omits restrictToServiceLinkedShares. Fixture ram-catalog-list-resource-types, step task#1.
  AWS: ListResourceTypes "lists the resource types that can be shared by RAM". Smithy (com.amazonaws.ram): ListResourceTypes input {nextToken, maxResults @range 1..500, resourceRegionScope: ResourceRegionScopeFilter ALL|GLOBAL|REGIONAL}, output {resourceTypes: ServiceNameAndResourceTypeList, nextToken}, http POST /listresourcetypes 200, paginated {inputToken nextToken, outputToken nextToken, pageSize maxResults}; shape ServiceNameAndResourceType members {resourceType (service-code:resource-code, case-insensitive), serviceName, resourceRegionScope: ResourceRegionScope enum}. Each element MUST describe one resource type RAM can actually share, with serviceName the owning service code and resourceRegionScope that type's visibility scope, and the response MUST be the service's published catalog — not a locally authored subset. The recording additionally carries a boolean member restrictToServiceLinkedShares on every element (false for all of them), which the on-disk Smithy model's ServiceNameAndResourceType does NOT declare: for that member this is recorded behavior only — AWS's live ListResourceTypes emits it on each entry, and the checked-in model is stale relative to the wire. The order the recording publishes the catalog in is also not resource-type-alphabetical (the recorded page begins ssm:Document, ec2:SecurityGroup, servicediscovery:Namespace, resource-explorer-2:View, fsx:Volume, ec2:TrafficMirrorTarget, network-firewall:ContainerAssociation, ...).
  Emulator: HTTP 200 with a resourceTypes list in which EVERY element diverges — the divergence_key names all 84 positions $.resourceTypes[0] .. $.resourceTypes[83]. The emulator publishes its own catalog in resource-type alphabetical order (actual [0] acm-pca:CertificateAuthority, [1] apigateway:Domainnames, [2] appmesh:Mesh, [3] cloudtrail:EventDataStore, [4] codebuild:Project, [5] codebuild:ReportGroup, [6] codeconnections:Connection, ...) where the recording's positions hold entirely different types, and no element carries restrictToServiceLinkedShares at all (expected false, got absent on every entry). Both the catalog's membership/ordering and each entry's shape diverge.
  Why: ListResourceTypes is how a client discovers what RAM can share in this partition. A client enumerating it to validate a resource ARN before CreateResourceShare, to build a picker of shareable types, or to decide whether a type must be restricted to service-linked shares, gets a list that does not match the service: a type AWS shares is reported as unshareable (and vice versa), and restrictToServiceLinkedShares is unreadable, so code that branches on it sees no value where AWS always supplies a boolean. Because this same catalog also gates which resource ARNs a share may carry and which types a customer-managed permission may be created for in this emulator, the divergence is observable far beyond this read.
  Fix: the ListResourceTypes handler's projection and the resource-type catalog it reads, plus the output shape/serializer for the entry type — the catalog must carry AWS's published type set in AWS's publication order, the entry must gain the restrictToServiceLinkedShares member (the checked-in Smithy model also lacks it, so the model refresh belongs with the fix), and the member must be serialized on every element. File and line citations are under Traces.
  Traces: wire fixture ram-catalog-list-resource-types, step task#1 (ListResourceTypes). Reference only, this checkout: services/service-com-amazonaws-ram-amazonresourcesharing/src/ops/list_resource_types.rs:203-233 builds each entry from crate::state::RESOURCE_TYPES with exactly three members (resource_type, service_name, resource_region_scope) and no restrict_to_service_linked_shares; the module header documents the catalog as "this service's own".

Cause 2 of 2 — ListResourceSharePermissions reports an EMPTY permissions list for a share a managed permission was just attached to, so the fixture's poll for status ASSOCIATED never terminates. Fixture ram-resource-share-permission-association, step task#8.
  AWS: ListResourceSharePermissions "lists the RAM permissions that are associated with a resource share". Smithy (com.amazonaws.ram): input {resourceShareArn required, nextToken, maxResults @range 1..500}, output {permissions: ResourceSharePermissionList, nextToken}, http POST /listresourcesharepermissions 200, paginated; AssociateResourceSharePermission input {resourceShareArn required, permissionArn required, replace, clientToken, permissionVersion} -> output {returnValue, clientToken}. Every managed permission currently governing the share — because CreateResourceShare named it in permissionArns, because AssociateResourceSharePermission attached it, or because it is the shared resource type's default managed permission — MUST be reported as one ResourceSharePermissionSummary carrying arn, resourceType, version (the attached version, as a string), defaultVersion, featureSet and status. ResourceSharePermissionSummary$status is a plain String in the model with no enumerated values, so the concrete value ASSOCIATED for a permission attached to a share is recorded behavior only: the recording shows the entry present with status "ASSOCIATED", defaultVersion true, featureSet "STANDARD", resourceType "imagebuilder:Component" and version "1".
  Emulator: HTTP 200 whose permissions list has no element at index 0 at all ($.permissions[0]: missing — expected {arn: <the attached managed permission>, defaultVersion true, featureSet "STANDARD", resourceType "imagebuilder:Component", status "ASSOCIATED", version "1"}, got None), and the step's poll on $.permissions[0].status gave up after 40 attempts because the value never became ASSOCIATED (got None). The preceding AssociateResourceSharePermission step answered as recorded, so the emulator reports the attach as succeeded and then never reports the attachment.
  Why: this is the only public read that says which managed permissions govern a share. A client that attaches a permission and then enumerates the share's permissions — to confirm the attach, to audit which permission governs a resource type, or to obtain the ARN/version for a later ReplacePermissionAssociations or DisassociateResourceSharePermission — concludes nothing is attached. Any code that waits for the entry (or for status ASSOCIATED) hangs, and re-attaching can then be refused for a collision on an attachment the read never showed. No retry recovers, because the state is unobservable.
  Fix: the share-permission attachment state and the ListResourceSharePermissions handler's projection of it — an attachment a successful AssociateResourceSharePermission recorded must appear in every later share-scoped read, with the share-attachment status rather than nothing, and the projection must not silently drop an attachment whose permission or version it cannot resolve. File and line citations are under Traces.
  Traces: wire fixture ram-resource-share-permission-association, step task#8 (ListResourceSharePermissions). Reference only, this checkout: services/service-com-amazonaws-ram-amazonresourcesharing/src/ops/list_resource_share_permissions.rs (the handler projects store.share_permissions(&resource_share_arn)) and services/service-com-amazonaws-ram-amazonresourcesharing/src/state/permission_attachments.rs (share_permissions() filter_maps away unresolvable attachments; attach_share_permission() is the only writer).
