# CreateTransformJob against an empty TransformInput S3 prefix never resolves for the client: the check hangs in the propagation-retry window and times out

> _Note: this issue was identified against the code base at commit `3ba50c32d06f7606ecc26210a28cec377b010e0f`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
CreateTransformJob

## Description
One net-new root cause on the SageMaker batch-transform admission path.

Cause 1 of 1: CreateTransformJob's synchronous refusal of a TransformInput S3 prefix that holds no object does not let a client settle the call — the whole check never completes inside its 60 s budget, so the accepted/refused verdict for batch transform input is unobservable.

AWS: CreateTransformJob resolves TransformInput.DataSource.S3DataSource.S3Uri before the job exists and refuses a location holding no object synchronously with HTTP 400 ValidationException; nothing is persisted, and ListTransformJobs(NameContains=<name>) reports no summary for the refused name. (Smithy, com.amazonaws.sagemaker#CreateTransformJob: TransformInput and TransformOutput are required; the only modeled errors are ResourceInUse, ResourceLimitExceeded and ResourceNotFound — the no-objects refusal is NOT modeled, so it is recorded behavior only.) The recorded behavior is also that this refusal is a TERMINAL answer to the client, i.e. it is not the message AWS returns while a just-created role's grants propagate: the check treats the training-job sentence 'No S3 objects found under S3 URL "<s3-uri>" given in input data source. Please ensure that the bucket exists in the selected region (<region>), that objects exist under that S3 prefix, and that the role "<role-arn>" has "s3:ListBucket" permissions on bucket "<bucket>". Error message from S3: <s3 message>' as a RETRYABLE propagation message (together with 'is not authorized', 'cannot be assumed', 'Unable to assume', 'Could not assume role', 'Could not access model data') and retries for 90 s on it, yet the recorded AWS run of this check settles well inside the suite's 60 s budget. In that sentence the fixed text is everything outside the quotes; the S3 URL, region, role ARN, bucket and the trailing S3 message are values taken from the request and from the S3 answer — they are never literal constants.

Emulator: the check gets no settled answer at all. Every call it makes in this flow is served by the emulator (S3 CreateBucket/PutObject, IAM CreateRole/PutRolePolicy, SageMaker CreateModel, then CreateTransformJob against the empty prefix s3://<bucket>/input_empty/ and against the populated prefix s3://<bucket>/input_populated/), and the check is killed with 'Check timed out after 60.0s'. The only place in the check that can absorb that wall clock is the 90 s propagation-retry loop, which is held only while the emulator keeps answering one of the retryable sentences above. Hypothesis (neither the model nor the recording states which): services/service-com-amazonaws-sagemaker-sagemaker/src/ops/create_transform_job.rs refuses the empty input location with crate::state::no_s3_objects_found — the handler's own comment says it is worded 'the same way' as CreateTrainingJob's crate::state::absent_input_objects — so the transform refusal carries the retryable 'No S3 objects found' sentence; the alternative holder of the window is CreateModel's artifact admission (crate::state::could_not_access_model_data, 'Could not access model data'), which would be refusing a ModelDataUrl the execution role is explicitly granted s3:GetObject on.

Why: a client cannot distinguish a terminal rejection of its transform input from a transient 'role still propagating' condition. SDK/CLI callers and wrappers that retry on the propagation sentences (as this check does, as the SageMaker Python SDK's own job-submission retries do) spin until their own deadline instead of surfacing the input error, and a caller that waits out the window never learns whether the job exists. The negative control (empty prefix must be rejected and absent from ListTransformJobs) and the positive control (populated prefix must be accepted and not Failed) are both unreachable, so the whole batch-transform admission contract is unverifiable against this emulator.

Fix: the CreateTransformJob handler's input-location admission and the refusal sentence it returns — the S3-listing refusal path in the operation's handler and the shared wording it draws on in the service's state module (the no-objects / denied-read refusal used for TransformInput), plus whatever on that path (CreateModel's artifact admission on the same request's execution role) keeps answering a retryable refusal. The refusal must be a terminal 400 ValidationException worded as AWS words the transform-input refusal, not CreateTrainingJob's propagation-shaped sentence, and it must leave no transform job behind.

Related but NOT covering this: open issue 20261029T211510Z-s3-sagemaker-sagemaker-jobs-never-execute-and-are-never-validated.md (its Cause 4 covers CreateTrainingJob/CreateProcessingJob synchronous validation only, and it does not carry this check's replay key).
