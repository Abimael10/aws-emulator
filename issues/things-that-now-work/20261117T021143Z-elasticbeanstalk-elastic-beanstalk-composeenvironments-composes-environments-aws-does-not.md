# Elastic Beanstalk: ComposeEnvironments composes environments AWS does not create for a grouped multi-tier manifest set, and a composed environment with no IamInstanceProfile reaches Ready with no launch-failure event (2 causes)

> _Note: this issue was identified against the code base at commit `60a7b9a0bf6692dd1e40a5836045b2f8d091fd03`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
ComposeEnvironments

## Description
TWO distinct net-new root causes in the elasticbeanstalk emulator, both in the same service, both grounded in failing behavioral checks of this suite. TWO causes must be closed before submitting.

Both causes concern the ComposeEnvironments path AFTER it was made to succeed. The adjacent OPEN issue 20261107T192913Z-elasticbeanstalk-elastic-beanstalk-composeenvironments-refuses-manifest-bearing-bundles-with.md describes neighbouring ground (its Cause 1: ComposeEnvironments refusing every request with MissingParameter) and even lists these two check ids, but the suite did NOT mark either check OWNED: the refusal is gone — the handler (services/service-com-amazonaws-elasticbeanstalk-awselasticbeanstalkservice/src/ops/compose_environments.rs) now resolves manifests and composes environments — and both checks now fail on NEW signatures described below. The OPEN issue 20261115T170910Z-elasticbeanstalk-elastic-beanstalk-composeenvironments-reports-an-unprocessed-version-of.md covers only the UNPROCESSED-version refusal classification and neither cause here.

Cause 1 of 2: a composed environment whose env.yaml manifest supplies no IamInstanceProfile launches successfully and never reports a failure — no launch-failure event is ever recorded and the environment does not leave the normal Launching -> Ready path. Failing check: elasticbeanstalk.compose-environments-insufficient-privileges-denied.
AWS: Smithy (com.amazonaws.elasticbeanstalk#ComposeEnvironments): input ApplicationName (@length 1..100), GroupName (@length 1..19), VersionLabels; output EnvironmentDescriptionsMessage{Environments, NextToken}; modeled errors only InsufficientPrivilegesException (403) and TooManyEnvironmentsException (400) — nothing in the model describes instance-profile validation, so this is recorded behavior only. Recorded behavior: ComposeEnvironments ACCEPTS (HTTP 200) a manifest set whose env.yaml declares only AWSConfigurationTemplateVersion, SolutionStack and EnvironmentName and therefore supplies no aws:autoscaling:launchconfiguration/IamInstanceProfile, and the environment it materializes then FAILS: DescribeEvents for that environment carries an explicit launch failure naming the missing instance profile (the event text states the environment failed to launch / names the instance profile, per DescribeEvents -> EventDescriptionList), and DescribeEnvironments never reports Status='Ready' for it — it settles in a terminal non-Ready state (Terminated/Terminating). The refusal is in the environment's event stream, not in the API response, so the requirement is the event plus the non-Ready status, not a status code.
Emulator: the composition is accepted and the environment is launched like any other (compose_environments.rs calls store.compose_environment(...), which 'starts Launching and reaches Ready the way every other launch does'); no instance-profile precondition is evaluated, so DescribeEvents never yields an instance-profile/launch-failure event and the environment goes to Ready. The check therefore polls DescribeEvents/DescribeEnvironments for the rejection until the harness cap and the check ends 'Check timed out after 60.0s' with no frame — the emulator never produces a terminal observation for a manifest AWS cannot launch.
Why: a client (or a test) that composes a group from a manifest missing the instance profile gets a healthy, Ready environment from the emulator where AWS gives it a dead environment with a diagnostic event. Every caller that waits for the launch to fail hangs instead, and any failure-handling or guardrail path exercised against the emulator is silently a false pass.
Fix: the ComposeEnvironments launch path and the composed-environment state machine — the composed environment's option settings must be validated for a resolvable instance profile and, when there is none, the environment must record the launch-failure event and end in a non-Ready terminal status instead of being driven to Ready (services/service-com-amazonaws-elasticbeanstalk-awselasticbeanstalkservice/src/ops/compose_environments.rs and the compose_environment/materialize_due_transitions environment state module it drives).
Traces: elasticbeanstalk.compose-environments-insufficient-privileges-denied.

Cause 2 of 2: for a grouped two-tier manifest set (env.yaml names ending in '+', GroupName supplied, WebServer/Standard plus Worker/SQS-HTTP tiers, EnvironmentLinks wired), ComposeEnvironments reports composed environments and creates them, where AWS reports none and creates none. Failing check: elasticbeanstalk.e2e-compose-multi-tier-application-environments.
AWS: Smithy as above (output Environments is EnvironmentDescriptionsList; GroupName is documented as usable 'only if the environment name defined in each target environment's manifest ends with a + (plus) character'). Recorded behavior: the call returns HTTP 200 with an EMPTY Environments list for this doc-conformant grouped manifest set, and no environment is created — DescribeEnvironments(ApplicationName=app, EnvironmentNames=['front-<group>','worker-<group>'], IncludeDeleted=False) stays empty afterwards, while plain CreateEnvironment on the SAME solution stack and IAM setup reaches Ready (the check's positive control), so the empty answer is specific to the grouped compose path and not a broken account.
Emulator: the call returns two EnvironmentDescriptions, one per version label, and actually creates both environments under the manifest names completed by GroupName — the check fails with 'AssertionError: ComposeEnvironments reported environments for a doc-conformant two-tier manifest set ({...: ..., ...: ...})', where the two names shown are the per-run group-suffixed names ('front-<group>', 'worker-<group>'); the fixed part of the divergence is that Environments is non-empty and that the two named environments exist.
Why: a client that composes a multi-tier group sees a success it will never see on AWS and then depends on two environments (and their EnvironmentLinks) that AWS never materialized; conversely a client coded against AWS's empty answer, which must fall back to CreateEnvironment per tier, now creates duplicates against the emulator. Group/tier behavior validated on the emulator does not transfer.
Fix: the ComposeEnvironments handler's grouped-manifest path — the grouped, '+'-named multi-tier composition must answer Environments=[] and create nothing, rather than launching one environment per resolved manifest (services/service-com-amazonaws-elasticbeanstalk-awselasticbeanstalkservice/src/ops/compose_environments.rs, the composed_environment_name/compose_environment seam it uses).
Traces: elasticbeanstalk.e2e-compose-multi-tier-application-environments.
