# cognito-identity: an in-place update of the principal-tag attribute map is readable through GetPrincipalTagAttributeMap but never reaches the credential-vending path, so GetCredentialsForIdentity sessions carry no aws:PrincipalTag for the newly mapped key

> _Note: this issue was identified against the code base at commit `4cf7211f237a5c930178a3131e9243c3c3eb5dd6`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
GetCredentialsForIdentity

## Description
One cause (Cause 1 of 1): after the principal-tag attribute map for a (IdentityPoolId, IdentityProviderName) pair is changed in place — here by a non-replacing CloudFormation Modify of AWS::Cognito::IdentityPoolPrincipalTag, i.e. the same state SetPrincipalTagAttributeMap writes — the new map is stored and read back correctly, but credentials subsequently vended by GetCredentialsForIdentity do not carry a session tag for the new key, so an IAM policy scoped on aws:PrincipalTag/<new key> matches nothing and every read it should allow is refused.
Failing check ids for this cause: cognito-identity.deploy-cognito-identity-3-cfn-principal-tag-governs-tenant-access.

AWS: the principal-tag attribute map maps an identity-provider token claim to a session tag name, and the map IN FORCE AT VEND TIME is what GetCredentialsForIdentity passes as session tags into the sts:AssumeRoleWithWebIdentity it performs for the pool's role; those tags are what aws:PrincipalTag/<name> resolves to in the role's policies (Smithy, com.amazonaws.cognitoidentity#AWSCognitoIdentityService: SetPrincipalTagAttributeMap input IdentityPoolId @required @length{1,55} @pattern ^[\w-]+:[0-9a-f-]+$, IdentityProviderName @required @length{1,128}, UseDefaults boolean, PrincipalTags map @length{0,50}; GetPrincipalTagAttributeMap returns the same four members; GetCredentialsForIdentity output IdentityId + Credentials, errors ExternalServiceException 400, InvalidIdentityPoolConfigurationException 400, InvalidParameterException 400, NotAuthorizedException 403, ResourceConflictException 409, ResourceNotFoundException 404, TooManyRequestsException 429, InternalErrorException 500). Setting a new PrincipalTags map REPLACES the previous one, so sessions vended after the change carry the new tag keys and no longer carry the removed ones; a role statement whose Resource is arn:aws:s3:::<bucket>/org/${aws:PrincipalTag/org}/* must therefore authorise s3:GetObject on org/<claim value>/obj for a token whose mapped claim is <claim value>. The model says nothing about the vending-time join itself (recorded behavior only for that linkage): the recording shows it, because the SAME check's first phase — map {"tenant": "custom:tenant"} — vends credentials that read tenant/<tenant>/obj with its exact bytes and that are refused on the other tenant's object, on the un-mapped org/ prefix and on the un-mapped user/ prefix, each with HTTP 403 AccessDenied and the message 'User: arn:aws:sts::<account>:assumed-role/<role name>/CognitoIdentityCredentials is not authorized to perform: s3:GetObject on resource: "arn:aws:s3:::<bucket>/<key>" because no identity-based policy allows the s3:GetObject action' (fixed text is everything outside the angle brackets, including the literal Cognito session name CognitoIdentityCredentials; the account id, role name, bucket and key are values from state and from the request).
Emulator: phase 1 of the check passes in full, so the emulator does store the declared map and does join it onto the vended session for the originally declared key. The in-place change to PrincipalTags={"org": "custom:tenant"} is also accepted and observable on the control plane: the change set is the single non-replacing Modify of the PrincipalTag resource, the identity pool and the PrincipalTag physical ids are unchanged, and GetPrincipalTagAttributeMap answers 200 with PrincipalTags={"org": "custom:tenant"}, UseDefaults=false. What does not change is the vended session: freshly minted GetCredentialsForIdentity credentials for the same identity are never able to read org/<their tenant>/obj — every poll of the loop is refused for the whole remaining window, and the check ends at its _wait_for_read for 'org/tenant-a/obj' (TimeoutError "credentials able to read their own 'org/tenant-a/obj': the run budget ended first"). Hypothesis: the credential-vending path reads a copy of the attribute map captured when the mapping was first created (or keyed on the old tag name), so the updated map is visible to the getter and invisible to the vender; nothing in the recording states the mechanism.
Why: a client that re-points a tenant-isolation boundary at a different session-tag key — the normal way such a boundary is evolved, through an in-place infrastructure-as-code update — is told by both CloudFormation and Cognito that the new mapping is live, and then every principal that should be authorised under the new key is denied. The isolation is not weakened in this direction, it is broken closed: the application loses access to its own data with an AccessDenied that names no cause, and the only way out is to recreate the pool. The mirror risk is the same cache in the other direction: a key REMOVED from the map would keep authorising sessions that should no longer carry it.
Fix: the cognito-identity credential-vending path for GetCredentialsForIdentity — it must resolve the principal-tag attribute map for (IdentityPoolId, IdentityProviderName) from the same live state GetPrincipalTagAttributeMap reads, at each vend, and build the session tags from it (including after SetPrincipalTagAttributeMap or a CloudFormation update of AWS::Cognito::IdentityPoolPrincipalTag has replaced it), rather than from state captured when the mapping was created.
Traces: cognito-identity.deploy-cognito-identity-3-cfn-principal-tag-governs-tenant-access (phases 1 and 2's control-plane legs pass; the run ends at phase 2's first data-plane read, so phase 2's cross-tenant denials and phase 3's UseDefaults=true default map {"client": "aud", "username": "sub"} were never exercised).

Related but NOT covering: open issue 20261113T003009Z-cognito-identity-a-create-complete-aws-cognito-identitypoolprincipaltag.md is about the CFN provider writing NO mapping at all (GetPrincipalTagAttributeMap refusing with ResourceNotFoundException). In this check the mapping is written and read back correctly in both phases; the defect here is downstream of that, in the vending path's use of an UPDATED map.
