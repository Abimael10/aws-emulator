=== Cause 1 of 3: the log-access DBInstanceNotFound sentence does not distinguish 'never existed' from 'still creating' ===
AWS: Smithy (services/service-com-amazonaws-rds-amazonrdsv19/smithy-model/com-amazonaws-rds-amazonrdsv19.json): DescribeDBLogFiles and DownloadDBLogFilePortion both declare DBInstanceNotFoundFault, errorKind client, httpError 404, awsQueryError code DBInstanceNotFound ('DBInstanceIdentifier doesn't refer to an existing DB instance'). The model does not state the message text, so the wording below is recorded behavior only, as the checks assert it: RDS words TWO different sentences behind that one code. For an instance that EXISTS but has not finished being created, the log endpoints answer the instance-scoped sentence 'DBInstance <DBInstanceIdentifier> not found.' — fixed text 'DBInstance ' + the identifier from the request + ' not found.'. For an identifier that resolves to NO instance at all, they answer the control-plane sentence 'DBInstance not found: <DBInstanceIdentifier>' — fixed text 'DBInstance not found: ' followed by the identifier from the request, with no trailing period. Status 404 and code DBInstanceNotFound are the same in both cases; only the sentence differs.
Emulator: both cases get the first sentence. describe-db-log-files on a never-created identifier answered {'Type':'Sender','Code':'DBInstanceNotFound','Message':'DBInstance <id> not found.'} where the control-plane form 'DBInstance not found: <id>' is required; log-file-access-on-not-ready-instance-error got the right sentence for the two still-'creating' calls and the wrong one for the never-existed control ('DBInstance <id> not found.' instead of 'DBInstance not found: <id>'). The handler's own comment states the collapse deliberately: 'Either miss is ONE error class, so both carry the single sentence this service words that class with'.
Why: a client cannot tell 'this instance is not ready yet, retry' from 'this identifier does not exist, stop retrying' — the only signal AWS gives for that distinction on these two operations is the message sentence, since the code and status are identical. Wait/retry loops and log-collection tooling keyed on the sentence either spin forever on a typo or abandon an instance that is merely provisioning.
Fix: the DBInstanceNotFoundFault construction in the two log-access handlers must choose between the instance-scoped sentence (identifier resolves to an instance that is not yet past 'creating') and the shared control-plane not-found sentence (identifier resolves to no instance in the request's region), instead of calling the single state helper for both.
Traces: rds.describe-db-log-files, rds.log-file-access-on-not-ready-instance-error. Code: services/service-com-amazonaws-rds-amazonrdsv19/src/ops/describe_db_log_files.rs lines 186-204 (the `match` whose `_` arm covers both misses) and the equivalent arm in src/ops/download_db_log_file_portion.rs; the shared sentence is crate::state::db_instance_not_found_message.

=== Cause 2 of 3: CancelExportTask's InvalidExportTaskStateFault message is emulator-authored ===
AWS: Smithy: CancelExportTask declares InvalidExportTaskStateFault, errorKind client, httpError 400, awsQueryError code InvalidExportTaskStateFault, documented 'You can't cancel an export task that has completed.' The recorded refusal sentence is 'The export <ExportTaskIdentifier> can\u2019t be canceled.' — fixed text 'The export ' + the ExportTaskIdentifier from the request + ' can\u2019t be canceled.', with a U+2019 RIGHT SINGLE QUOTATION MARK in 'can\u2019t', and no mention of the task's status.
Emulator: answers the right code with its own sentence 'ExportTask <id> is in state <STATUS> and can't be canceled' — a different fixed text, an ASCII apostrophe, and it interpolates the stored status (COMPLETE in the replay) that AWS never puts in this message.
Why: the export-lifecycle contract is 'a finished export cannot be canceled'; a client that matches AWS's sentence (or renders it to an operator) sees an unrecognised string, and one that parses the status out of it reads a field AWS does not supply there. The status belongs in DescribeExportTasks, not in this fault.
Fix: the InvalidExportTaskStateFault message built in the CancelExportTask handler must be AWS's fixed sentence with the requested identifier substituted, not a status-bearing paraphrase.
Traces: rds.export-task-lifecycle. Code: services/service-com-amazonaws-rds-amazonrdsv19/src/ops/cancel_export_task.rs lines 196-206.

=== Cause 3 of 3: a CloudFormation DBParameterGroupName in-place update never shows up on the live DB instance ===
AWS: recorded behavior only. Changing an AWS::RDS::DBInstance's DBParameterGroupName to a different group of the same family is an in-place modification: the stack reaches UPDATE_COMPLETE, DbiResourceId is unchanged (no replacement), and DescribeDBInstances then reports DBParameterGroups[0].DBParameterGroupName = the new group with ParameterApplyStatus 'in-sync' (for a dynamic, modifiable parameter no reboot is needed), while DescribeDBParameters on the new group reports the template's value with Source 'user'.
Emulator: the stack update is accepted and _wait_stack_status reaches UPDATE_COMPLETE, but the instance's association never reports the new group in-sync: the check dies in _poll_until_param_group with TimeoutError 'instance <id> parameter group <group-b> in-sync: the run budget ended first; not graded', so the no-replacement, apply-status and parameter-value assertions after it are never reached. Hypothesis: the AWS::RDS::DBInstance update path does not propagate a changed DBParameterGroupName onto the stored instance (or never settles ParameterApplyStatus out of 'applying'), so the condition can never be satisfied however long a client polls.
Why: a client that updates a parameter group through CloudFormation has no way to observe the change landing — every wait on the instance's reported parameter group or apply status hangs, and the subsequent effective-parameter read is unreachable. This is the normal way RDS configuration is managed, so it blocks the whole flow rather than one assertion.
Fix: the CloudFormation AWS::RDS::DBInstance update handler (parameter-group association) together with the DB-instance state's pending-modification settlement must apply a changed DBParameterGroupName in place and drive ParameterApplyStatus to 'in-sync' for a dynamic parameter, keeping DbiResourceId stable.
Traces: rds.deploy-cfn-stack-update-modifies-live-parameter-group.
