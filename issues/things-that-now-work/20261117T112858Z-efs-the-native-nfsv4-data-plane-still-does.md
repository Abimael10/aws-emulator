# efs: the native NFSv4 data plane still does not serve an `available` mount target — both NFS checks now fail with the SSM mount script ending Status 'Failed' and no output at all

> _Note: this issue was identified against the code base at commit `384e9c06f8b850c3e6c1129231f41c38ae5339ba`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
CreateMountTarget

## Description
One net-new root cause in the EFS native (NFS) data plane, grounded in the two failing checks the suite lists under '### efs' that the replay report does NOT mark ALREADY FILED or OWNED.

Related open issues, neither of which covers these checks as the report now scores them: 20261108T113459Z-efs-the-native-nfsv4-data-plane-never-serves.md and 20261107T090413Z-efs-the-native-nfsv4-data-plane-checks-never.md both describe this family, but their recorded replay keys were taken when the checks were CUT OFF by the suite cap with no assertion reached ('Check timed out after 180.0s', Issue-Key ...|probe#29|Timeout|...). The failure mode has since changed: both checks now run to their first real assertion and fail on it, so neither check is marked owned and both are filed here. A fixer should close these together with those two issues if they share one backing gap. Control-plane EFS findings (20261104T054216Z-efs-mount-target-file-system-refusals-use-emulator.md, 20261029T195311Z-elasticfilesystem-efs-mount-targets-ignore-ec2-subnet-state.md) and the Lambda/ECS compute flows (20261110T174333Z, 20261116T030849Z) are different paths and do not cover the mount itself.

Cause 1 of 1: a mount target whose LifeCycleState the control plane reports as `available` does not serve NFSv4.1 at the IpAddress it reports, so the shell script that mounts it, writes through it and probes the mount type never succeeds — the SSM AWS-RunShellScript invocation reaches terminal Status 'Failed' with empty StandardOutputContent and empty StandardErrorContent, on one node and on two nodes alike. Failing checks: efs.efs-nfs-mount-write-read-round-trip, efs.efs-nfs-two-node-posix-coherence-and-a-nonempty-rmdir-is-rejected.
AWS: Smithy (efs): CreateMountTarget (POST /2015-02-01/mount-targets, 200) returns MountTargetDescription with required MountTargetId (^fsmt-[0-9a-f]{8,40}$), FileSystemId, SubnetId and LifeCycleState, plus IpAddress, NetworkInterfaceId, AvailabilityZoneName and VpcId; DescribeMountTargets (GET /2015-02-01/mount-targets, 200) is the documented read-back of LifeCycleState and IpAddress. Its modelled refusals (AvailabilityZonesMismatch, BadRequest, FileSystemNotFound 404, IncorrectFileSystemLifeCycleState 409, IpAddressInUse 409, MountTargetConflict 409, NetworkInterfaceLimitExceeded 409, NoFreeAddressesInSubnet 409, SecurityGroupLimitExceeded, SecurityGroupNotFound, SubnetNotFound, UnsupportedAvailabilityZone) say nothing about what `available` promises; that promise is recorded behavior only: once DescribeMountTargets reports LifeCycleState `available`, the NFSv4.1 server answers on TCP 2049 at that IpAddress from inside the VPC, `mount -t nfs4 -o nfsvers=4.1,rsize=1048576,wsize=1048576,hard,timeo=600,retrans=2,noresvport <IpAddress>:/ <dir>` succeeds, a file written through the mount is read back byte-for-byte, `findmnt -no FSTYPE <dir>` is exactly `nfs4` and `stat -f -c %T <dir>` is exactly `nfs`, and two instances in two AZs mounting the same file system see each other's files (the two-node check uses files on the shared mount as barriers and additionally requires POSIX `os.link`/`os.rename`/`os.rmdir` semantics, including a non-empty rmdir failing with ENOTEMPTY). Separately, recorded behavior for SSM: a failed AWS-RunShellScript invocation still carries the script's output — GetCommandInvocation returns the StandardErrorContent the script wrote (here 'mount attempt <i> failed, retrying in 10s' and 'mount never succeeded within the retry window' from the script's own `exit 32` path) — so a terminal 'Failed' with both output members empty tells a client nothing about what failed.
Emulator: the single-node check reaches its first assertion and fails: invocation['Status'] is 'Failed' and StandardErrorContent is empty, so none of SIM2REAL_CONTENT / SIM2REAL_FSTYPE / SIM2REAL_MAGIC is ever produced. The two-node check fails identically on node A: "node A's script ended 'Failed'; stderr tail ''; stdout tail ''". The EFS control plane answers CreateFileSystem/CreateMountTarget, hands back an fsmt- id with an IpAddress and reports LifeCycleState `available`, but nothing behind that address completes a mount — and the SSM invocation that attempted it reports failure with no diagnostic output at all.
Why: a client that provisions EFS exactly as documented — CreateFileSystem, wait `available`, CreateMountTarget, wait `available`, read IpAddress, mount from an instance in the VPC — gets no filesystem. `available` cannot be trusted as a signal that the file system is usable, every workload layered on an EFS mount (write/read round trip, cross-node coherence, POSIX link/rename/rmdir) is unreachable, and because the failing SSM invocation returns empty stdout and stderr the client cannot even tell whether the mount, the write or the probe failed.
Fix: the EFS native data plane — the NFSv4.1 listener a mount target's reported IpAddress must answer on, whatever binds a mount-target record in the EFS service crate's state to that listener, and the mount-target lifecycle transition that may report `available` only once that listener answers. Secondarily, the SSM RunCommand invocation path, which must return the script's captured StandardOutputContent/StandardErrorContent on a 'Failed' invocation instead of empty strings.
Traces: efs.efs-nfs-mount-write-read-round-trip, efs.efs-nfs-two-node-posix-coherence-and-a-nonempty-rmdir-is-rejected.

2. Replay simparity-behavioral-aws-v1 checks efs.efs-nfs-mount-write-read-round-trip and efs.efs-nfs-two-node-posix-coherence-and-a-nonempty-rmdir-is-rejected.

4. Create a dedicated VPC (e.g. 10.91.0.0/24) with EnableDnsSupport and EnableDnsHostnames true, a public subnet with MapPublicIpOnLaunch, an internet gateway and a default route, and a security group allowing TCP 2049 ingress from itself.
5. CreateMountTarget(FileSystemId=..., SubnetId=..., SecurityGroups=[sg]); poll DescribeMountTargets until LifeCycleState == 'available' and read IpAddress.
6. RunInstances in that subnet with an AmazonSSMManagedInstanceCore instance profile; wait for the instance_running waiter and for SSM DescribeInstanceInformation PingStatus == 'Online'.
7. SendCommand(DocumentName='AWS-RunShellScript', TimeoutSeconds=180) with: mkdir the mount point; `mount -t nfs4 -o nfsvers=4.1,rsize=1048576,wsize=1048576,hard,timeo=600,retrans=2,noresvport <IpAddress>:/ /mnt/x` retried six times 10 s apart (else `exit 32`); write a marker through the mount with `tee`; `cat` it back as SIM2REAL_CONTENT:; `findmnt -no FSTYPE /mnt/x` as SIM2REAL_FSTYPE:; `stat -f -c %T /mnt/x` as SIM2REAL_MAGIC:; `umount /mnt/x`.
8. Poll GetCommandInvocation to a terminal status. Expect Status 'Success', the marker echoed byte-for-byte, FSTYPE exactly 'nfs4' and statfs magic exactly 'nfs'. Observe Status 'Failed' with StandardOutputContent and StandardErrorContent both empty, even though DescribeMountTargets already reported LifeCycleState 'available'.
9. Two-node repro: repeat with two instances in two different AZs, each with its own mount target on the same file system, and have both nodes use files on the shared mount as barriers; observe node A's invocation ending 'Failed' with no output before any cross-node assertion runs.
