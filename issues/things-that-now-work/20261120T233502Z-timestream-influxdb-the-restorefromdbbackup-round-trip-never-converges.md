# timestream-influxdb: the RestoreFromDbBackup round trip never converges — create instance → backup → restore → AVAILABLE cannot complete, each lifecycle transition costs the client a whole probe interval

> _Note: this issue was identified against the code base at commit `783077cd783724858ba947c044602be1843996e1`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
RestoreFromDbBackup

## Description
One net-new root cause in the timestream-influxdb emulator, grounded in the one failing behavioral check of this service that is neither ALREADY FILED (ListDbBackups stub) nor OWNED by an open issue.

Cause 1 of 1: the backup/restore round trip of this service never reaches its terminal state for a polling client. A workflow that creates a DB instance, waits for it to be AVAILABLE, takes an on-demand backup, waits for it to be COMPLETED, restores it and waits for the restored instance to be AVAILABLE does not converge: the check that walks exactly that sequence exhausts its whole budget and is reported as `Check timed out after 60.0s`, never reaching its final assertions. No call in the sequence is refused — every one answers 2xx — so the divergence is purely that the lifecycle the API announces is not reached in a time a client that polls the API can observe.

AWS: Smithy model of this service — `RestoreFromDbBackup` output carries `restoredDbResourceId` (DbResourceId), `restoreStatus` (RestoreStatus, whose only member is RESTORING), `resourceType` (ResourceType; the recording shows AWS puts the wire value `db-instance` here) and `deploymentType`; `GetDbInstance$status` is the `Status` enum (CREATING, AVAILABLE, DELETING, MODIFYING, UPDATING, DELETED, FAILED, UPDATING_DEPLOYMENT_TYPE, UPDATING_INSTANCE_TYPE, MAINTENANCE, REBOOTING, REBOOT_FAILED, RESTORING, RESTORE_FAILED); `GetDbBackup$status` is the `DbBackupStatus` enum (IN_PROGRESS, COMPLETED, FAILED, DELETING, DELETED); `CreateDbBackup` is documented "Creates a new on-demand backup of a Timestream for InfluxDB resource" and `RestoreFromDbBackup` "Restores a Timestream for InfluxDB resource from a backup. By default, a new resource is created." The transition timing itself is recorded behavior only: AWS takes minutes per transition, and the requirement the recording establishes is that EVERY one of the three transitions is eventually REACHED and observable through the polled read — CreateDbInstance's record leaves CREATING for AVAILABLE, CreateDbBackup's record leaves IN_PROGRESS for COMPLETED, and the resource RestoreFromDbBackup mints leaves RESTORING for AVAILABLE with `name` equal to the restore request's `name` and an `id` distinct from the source instance's — so a client's wait loop terminates.

Emulator: the sequence never terminates inside the budget the suite gives a check. Verdict [mismatch], detail `Check timed out after 60.0s`; no error code, no non-2xx status and no failed assertion is reported, so the poll loops themselves are what consumed the time. Hypothesis (the model says nothing about timing, so this names the emulator code the behavior comes from rather than a recorded value): every lifecycle record in this service owes its settle exactly one TRANSITION_SPAN = 25 ms after the call that announced the transient status — `TRANSITION_SPAN` in services/service-com-amazonaws-timestreaminfluxdb-amazontimestreaminfluxdb/src/state.rs, applied by `DbInstance::begin_transition`/`DbInstance::settle` in the same file, by `insert_db_backup` (IN_PROGRESS + settles_at = now + TRANSITION_SPAN) in src/state/backups.rs, by `restored_db_instance` (RESTORING + settles_at = now + TRANSITION_SPAN) in src/state/restores.rs, and re-dated from after the socket bind by `serve_over` in src/state/influx_data_plane.rs. 25 ms is on the ORDER of a client's loopback round trip rather than reliably shorter than it, so a client that issues its next read immediately after the announcing call still observes the transient status (CREATING / IN_PROGRESS / RESTORING) and then sleeps a whole probe interval. This workflow chains THREE such transitions, whose probe intervals are 30 s + 20 s + 30 s = 80 s of client sleeping — more than the whole check has — so the restore workflow can never finish, while the single-transition checks of this service (16 of 19 pass) still fit. A second candidate in the same cause: `RestoreFromDbBackup`'s handler AWAITS the data-plane publish (`st::influx_data_plane::restore_db_instance_plane`, src/ops/restore_from_db_backup.rs), which binds a fresh socket for the minted instance and re-dates the owed settle to 25 ms AFTER that bind, so the restored instance's transition is owed from the latest point of the three.

Why: backup and restore is the disaster-recovery path of this service, and a client that uses it cannot complete it. Every call answers success, the restore even reports `restoreStatus=RESTORING` and a `restoredDbResourceId`, and then the client's wait loop — the normal way the AWS SDKs, the CLI's `wait`-style loops and infrastructure tools consume an asynchronous lifecycle — never observes the terminal status within any budget proportional to an emulator's speed. The failure mode is the worst kind: no error to handle, just a workflow that hangs until the caller's own deadline, and a caller that bounds its wait concludes the restore failed when the emulator reports no failure at all.

Fix: the lifecycle-settle timing of this service's state, for all three records the workflow walks — the DB instance (`TRANSITION_SPAN`, `begin_transition`, `settle` in src/state.rs), the DB backup (`insert_db_backup`, `DbBackup::settle` in src/state/backups.rs) and the restored record (`restored_db_instance` in src/state/restores.rs, plus the re-dating in `serve_over` in src/state/influx_data_plane.rs). The owed transition must already be due by the time a polling client's NEXT read arrives — e.g. settle on the first reporting read that follows the announcing call, or a span an order of magnitude below a loopback round trip — while keeping the transient status observable in the announcing call's own response, so a chained create → backup → restore workflow costs no probe interval per transition. The awaited data-plane publish inside `RestoreFromDbBackup`'s handler must not be what the restored instance's settle is dated from.

The per-transition cost is what the emulator chooses: the settle of each record is owed exactly one `TRANSITION_SPAN` (25 ms) after the announcing call — src/state.rs (`TRANSITION_SPAN`, `DbInstance::settle`, `DbInstance::begin_transition`), src/state/backups.rs (`insert_db_backup`: status IN_PROGRESS, settles_at = now + TRANSITION_SPAN; `DbBackup::settle`), src/state/restores.rs (`restored_db_instance`: status RESTORING, settles_at = now + TRANSITION_SPAN), src/state/influx_data_plane.rs (`serve_over` re-dates settles_at to now + TRANSITION_SPAN after the socket bind, reached from `restore_db_instance_plane`, which src/ops/restore_from_db_backup.rs awaits). 25 ms is not reliably shorter than the round trip a client needs to issue its next read, which is the assumption the code's own comment states; three chained transitions at 30 s + 20 s + 30 s probe intervals is 80 s of client sleeping against a 60 s budget. Instance ids, backup ids, names and the exact interval arithmetic of any one run are that run's values; the defect is that the restore workflow does not converge for a client that polls the API.

## Steps to Reproduce
1. Create (or reuse) a VPC with at least two subnets and a security group.
2. CreateDbInstance(name=<SRC>, password=<8-64 chars matching ^[a-zA-Z0-9]+$>, dbInstanceType="db.influx.medium", vpcSubnetIds=[<two subnets>], vpcSecurityGroupIds=[<sg>], allocatedStorage=20, dbStorageType="InfluxIOIncludedT1", deploymentType="SINGLE_AZ"); keep the returned `id` as <src id>.
3. Poll GetDbInstance(identifier=<src id>) every 30 s until `status` is AVAILABLE or FAILED. Note that the FIRST read, issued immediately after step 2, still reports CREATING, so the loop sleeps 30 s.
4. CreateDbBackup(name=<BKP>, dbResourceId=<src id>, retentionDays=1); keep the returned `id` as <backup id>.
5. Poll GetDbBackup(identifier=<backup id>) every 20 s until `status` is COMPLETED or FAILED. The first read, issued immediately after step 4, still reports IN_PROGRESS, so the loop sleeps 20 s.
6. RestoreFromDbBackup(name=<RESTORED>, dbBackupId=<backup id>); keep `restoredDbResourceId` as <restored id>. (`restoreStatus`=RESTORING and `resourceType`="db-instance" are returned correctly.)
7. Poll GetDbInstance(identifier=<restored id>) every 30 s until `status` is AVAILABLE or FAILED.
   EXPECTED: the whole sequence converges — the restored instance reports status AVAILABLE, `name`=<RESTORED> and an `id` distinct from <src id>.
   ACTUAL: each of the three transitions costs the poller a full probe interval (30 s + 20 s + 30 s = 80 s of sleeping), so the sequence cannot finish inside the suite's 60 s per-check budget; the run ends as `Check timed out after 60.0s` with no error and no failed assertion, and the restored instance's terminal status is never observed.
