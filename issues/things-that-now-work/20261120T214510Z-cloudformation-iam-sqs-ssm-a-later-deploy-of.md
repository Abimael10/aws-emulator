# cloudformation__iam__sqs__ssm: a later deploy of a stack created with a RoleARN exits 1 and leaves the stack CREATE_COMPLETE — the update never runs under the stack's recorded role, so no AccessDenied CREATE_FAILED event and no UPDATE_ROLLBACK_COMPLETE

> _Note: this issue was identified against the code base at commit `d480a9c819aca039333e6ccd75fa51254e2ac722`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
UpdateStack

## Description
Cause 1 of 1: a stack update issued without an explicit RoleARN on a stack that RECORDS one never runs: the deploy exits 1, the stack is left in its pre-update status CREATE_COMPLETE, and the failing resource's AccessDenied event and the UPDATE_ROLLBACK_COMPLETE it should settle into never appear (failing check: cloudformation__iam__sqs__ssm.cdk-deploy-role-arn-stays-the-stacks-role-for-later-deploys).
AWS: a stack created with `--role-arn` stores that role (DescribeStacks reports it as RoleARN) and CloudFormation keeps acting as it for every later operation that does not name another one. So a later deploy that adds an AWS::SQS::Queue while the stack's role is granted only ssm:* fails the queue, rolls the stack back, and leaves it UPDATE_ROLLBACK_COMPLETE with RoleARN still set and the role-created SSM parameter intact. The queue emits exactly one CREATE_FAILED stack event whose ResourceStatusReason is AWS's resource-handler wording: `Resource handler returned message: "User: arn:aws:sts::<account>:assumed-role/<role>/<session> is not authorized to perform: sqs:createqueue on resource: arn:aws:sqs:<region>:<account>:<queue> because no identity-based policy allows the sqs:createqueue action (Service: Sqs, Status Code: 403, Request ID: <uuid>) (SDK Attempt Count: <n>)" (RequestToken: <uuid>, HandlerErrorCode: AccessDenied)` — fixed text as quoted, with the assumed-role ARN (account, role name, session name), the target queue ARN, the per-run request id/token and the attempt count as its variable parts. GetQueueUrl for that queue then answers AWS.SimpleQueueService.NonExistentQueue / "The specified queue does not exist." Smithy (cloudformation): DescribeStacks output Stack.RoleARN, Stack.StackStatus -> StackStatus enum (includes UPDATE_ROLLBACK_COMPLETE); DescribeStackEvents output StackEvent.ResourceStatusReason.
Emulator: the deploy that adds the queue exits 1, but DescribeStacks (by stack id) still reports StackStatus 'CREATE_COMPLETE' with RoleARN unchanged — the stack never enters UPDATE_IN_PROGRESS, never emits a CREATE_FAILED event for the queue, and never reaches UPDATE_ROLLBACK_COMPLETE. The RoleARN itself is recorded correctly; what is missing is the update ever being attempted under it. Hypothesis: the deploy dies before planning anything, in the same place the other CDK re-deploys in this sweep die — DeleteChangeSet refuses the change set the first deploy executed ("Cannot delete ChangeSet in execution status EXECUTE_COMPLETE", HTTP 400 InvalidChangeSetStatusException), which is filed as its own cause for the cloudformation__ssm and cloudformation__sqs__ssm headings in this same sweep and as open issue 20261120T150300Z-cloudformation-deletechangeset-refuses-an-executed-change-set-so.md. If this check still fails after that refusal is lifted, the residual is the stack-role authorization path itself: the update must be executed as the stack's recorded role, the queue must fail AccessDenied with AWS's resource-handler wording, and the stack must settle UPDATE_ROLLBACK_COMPLETE.
Why: the recorded RoleARN is a security boundary — it is how an operator pins what a stack may do regardless of who deploys it. An emulator that records the role but never acts as it cannot show a client the refusal it exists to produce: a deploy that AWS would stop with AccessDenied either does nothing observable or (once the stack does update) would silently succeed with the deploying principal's permissions, and a caller polling StackStatus is told 'CREATE_COMPLETE' after an operation that failed, so the standard "wait for a terminal update status, then read the failure event" loop never terminates on a real verdict.
Fix: the stack-update path and its change-set prelude in the cloudformation service — a deploy on a stack holding a RoleARN must plan and execute under that role, surface a resource handler's authorization failure as a single CREATE_FAILED stack event with AWS's `Resource handler returned message: "..." (RequestToken: ..., HandlerErrorCode: AccessDenied)` wording, and settle the stack at UPDATE_ROLLBACK_COMPLETE with the role and the previously created resources intact.
Traces: cloudformation__iam__sqs__ssm.cdk-deploy-role-arn-stays-the-stacks-role-for-later-deploys.

## Evidence
cloudformation__iam__sqs__ssm.cdk-deploy-role-arn-stays-the-stacks-role-for-later-deploys: the first `cdk deploy --role-arn <role>` succeeds and DescribeStacks correctly reports ('CREATE_COMPLETE', RoleARN=<role arn>) with the role-created parameter holding 'made-by-role'. The later deploy that adds the queue exits 1 as expected, but then `AssertionError: the deploy without --role-arn left 'CREATE_COMPLETE' with RoleARN 'arn:aws:iam::<account>:role/sim2real-cdk-rolearn-<id>'`. Expected ('UPDATE_ROLLBACK_COMPLETE', the same RoleARN), exactly one CREATE_FAILED event for logical id 'Queue' whose ResourceStatusReason matches AWS's `Resource handler returned message: "User: arn:aws:sts::<account>:assumed-role/<role>/<session> is not authorized to perform: sqs:createqueue on resource: arn:aws:sqs:<region>:<account>:<queue> because no identity-based policy allows the sqs:createqueue action (Service: Sqs, Status Code: 403, Request ID: <uuid>) (SDK Attempt Count: <n>)" (RequestToken: <uuid>, HandlerErrorCode: AccessDenied)`, GetQueueUrl answering ('AWS.SimpleQueueService.NonExistentQueue', 'The specified queue does not exist.'), and the parameter still 'made-by-role'. Actual: no UPDATE_* status and no such event at all. The request id, request token, session name and attempt count in that message are per-run values; the quoted sentence around them is the requirement.

## Steps to Reproduce
1. Clone the repo and boot the emulator built from it.
2. iam CreateRole(<role>) trusting cloudformation.amazonaws.com and PutRolePolicy granting only ssm:* on *.
3. `cdk deploy <stack> --require-approval never --role-arn <role arn>` for an app holding one AWS::SSM::Parameter — the stack reaches CREATE_COMPLETE and DescribeStacks reports RoleARN.
4. `cdk deploy <stack> --require-approval never` for the same app plus an AWS::SQS::Queue (no --role-arn).
5. DescribeStacks(StackName=<stack id>) — observe StackStatus 'CREATE_COMPLETE' instead of 'UPDATE_ROLLBACK_COMPLETE', and DescribeStackEvents — observe no CREATE_FAILED event for the Queue.
