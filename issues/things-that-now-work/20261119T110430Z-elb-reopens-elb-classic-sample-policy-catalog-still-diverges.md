# REOPENS: ELB Classic sample-policy catalog still diverges - DescribeLoadBalancerPolicies PolicyAttributeDescriptions are not in AWS's reported attribute order

> _Note: this issue was identified against the code base at commit `b448d9011382618e887f073932b66b1aa6876ff6`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
DescribeLoadBalancerPolicies

## Description
Cause 1 of 1: a DescribeLoadBalancerPolicies request that names no LoadBalancerName (and no PolicyNames) answers HTTP 200 with a PolicyDescriptions list in which NONE of the sample-policy descriptions AWS reports is present, because each description's PolicyAttributeDescriptions list is emitted in a different attribute order than AWS reports it in. Fixture elb-catalog-describe-load-balancer-policies, step task#1.

This REOPENS the already-resolved issue 20261104T095914Z-elb-classic-describeloadbalancerpolicies-omits-the-published-sample-policy.md ("ELB Classic DescribeLoadBalancerPolicies omits the published sample-policy catalog"), whose fix grew the catalog from two protocol-only entries to eleven entries carrying the whole SSL-negotiation attribute set. The member COUNT and the per-attribute values now line up, but replay still reports every one of the eleven recorded PolicyDescriptions members as missing, so the catalog as served is still not the catalog AWS serves. That issue is resolved and therefore covers nothing; this is the net-new remaining divergence.

AWS: DescribeLoadBalancerPolicies is documented (Smithy: com.amazonaws.elasticloadbalancing#DescribeLoadBalancerPolicies, doc trait) as "If you don't specify a load balancer name, the action returns descriptions of the specified sample policies, or descriptions of all sample policies. The names of the sample policies have the ELBSample- prefix." Output member PolicyDescriptions targets a list of PolicyDescription {PolicyName, PolicyTypeName, PolicyAttributeDescriptions}; PolicyAttributeDescriptions is a LIST, i.e. an ordered wire member, not a set. The model states no ordering rule for it, so for the order itself this is recorded behavior only: the recording shows each sample policy described by the whole SSL-negotiation attribute set in a fixed published order - the protocol attributes (Protocol-TLSv1, Protocol-SSLv3, Protocol-TLSv1.1, Protocol-TLSv1.2), then Server-Defined-Cipher-Order, then one attribute per cipher suite, with the ephemeral-Diffie-Hellman suites interleaved among the ECDHE/AES suites: DHE-RSA-AES128-SHA is reported immediately AFTER ECDHE-RSA-AES128-SHA and BEFORE ECDHE-ECDSA-AES256-GCM-SHA384, and DHE-DSS-AES128-SHA immediately after AES256-SHA and before CAMELLIA128-SHA. Every attribute of the policy type is reported, each valued 'true' or 'false' according to whether that policy's configuration enables it. The requirement is the catalog and its attribute order as AWS publishes them; the particular policy names and the individual true/false values in the recording are the catalog's content, not one run's values.

Emulator: the service predefines eleven ELBSample-* policies and projects each over its whole attribute set, but it emits the cipher attributes in its OWN order, with both DHE suites moved to the tail of the cipher roster (... AES256-GCM-SHA384, AES256-SHA256, AES256-SHA, DHE-RSA-AES128-SHA, DHE-DSS-AES128-SHA, CAMELLIA128-SHA, ...) instead of interleaved where AWS reports them. Replay therefore reports $.DescribeLoadBalancerPoliciesResponse.DescribeLoadBalancerPoliciesResult.PolicyDescriptions.member[0] through member[10] as 'missing' - all eleven recorded descriptions - against an actual 200 response, with no cluster member matching on attribute content. Hypothesis: the attribute order is the only remaining difference for the first member, since the recorded member[0] values (TLS-only protocols, Server-Defined-Cipher-Order 'true', the ECDHE/AES suites 'true', the DHE and CAMELLIA suites 'false') are exactly the configuration the emulator holds for its first entry ELBSample-ELBSecurityPolicy-2016-08; only the position of DHE-RSA-AES128-SHA/DHE-DSS-AES128-SHA inside the list differs.

Why: a client that enumerates the predefined SSL negotiation policies - to pick a cipher policy, to diff a load balancer's SSLNegotiationPolicyType attributes against a sample, or to render the catalog in a console or an IaC plan - compares a sample's PolicyAttributeDescriptions positionally or re-serializes it, and gets a list that matches no published policy. Because the call still answers HTTP 200, the mismatch is accepted as authoritative rather than retried or failed, and any index-based read of the attribute list lands on the wrong cipher.

Fix: the sample-policy catalog data in this service's state - the cipher-attribute roster the sample descriptions are projected over, and nothing in the handler's filtering/projection path, which is already correct - must list the attributes in the order AWS reports them, with the ephemeral-Diffie-Hellman suites in their published positions among the ECDHE/AES suites rather than appended after them.
