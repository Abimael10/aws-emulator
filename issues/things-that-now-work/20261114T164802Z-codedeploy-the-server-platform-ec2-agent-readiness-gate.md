# codedeploy: the Server-platform (EC2 agent) readiness gate still never completes — a sent SSM Run Command invocation on a running managed node never reaches a terminal status, so no EC2 CodeDeploy deployment is ever created (1 cause)

> _Note: this issue was identified against the code base at commit `d55a3288bccfe55e7c52387cacb77214d56a079f`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
CreateDeployment

## Description
One net-new root cause in the codedeploy behavioral group, carrying replay keys that no open issue holds.

Relation to what is already filed: open issue 20261114T130417Z-codedeploy-the-server-platform-ec2-agent-surface-is.md describes the same symptom family under its Cause 1, and open issues 20261107T094623Z-codedeploy-no-server-platform-ec2-agent-deployment-check.md and 20261110T134745Z-codedeploy-the-minimumhealthyhosts-concurrency-check-cannot-start-the.md own the older variant (the host never reaching PingStatus 'Online'). None of them carries these six checks' current replay keys — in this replay all six end at the harness's 60 s cap with no frame at all ("Check timed out after 60.0s"), whereas the filed keys for these same ids record a hang inside `_invoke_command`'s poll (`_invoke_command#NN|Timeout|time.sleep(3)`). The suite therefore did not mark any of these six owned, and they are re-filed here so a fixer has a re-replayable key for them.

=== Cause 1 of 1: an SSM Run Command sent to the Server-platform host never reaches a terminal invocation status, so the host-readiness gate never passes and no EC2/on-premises CodeDeploy deployment is created or graded ===
Failing check ids for this cause: codedeploy.agent-hands-the-hook-the-real-deployment-identifiers, codedeploy.applicationstop-hook-failure-blocks-redeploy-until-ignored, codedeploy.auto-rollback-on-deployment-failure-reinstalls-the-prior-artifact, codedeploy.hook-failure-skips-later-lifecycle-events-and-fails-the-target, codedeploy.lifecycle-event-order-and-applicationstop-only-on-redeploy, codedeploy.minimum-healthy-hosts-bounds-observed-concurrent-unavailability.

AWS: every Server-platform (computePlatform 'Server') check first proves the launched host is usable by running a shell command on it through Systems Manager Run Command — ssm:SendCommand(InstanceIds=[<id>], DocumentName='AWS-RunShellScript', Parameters={commands:['systemctl is-active codedeploy-agent']}) followed by ssm:GetCommandInvocation(CommandId, InstanceId). On AWS a reachable managed node leaves the transient part of the status set within seconds: Smithy (ssm) models CommandInvocationStatus as an enum whose values are Pending, InProgress, Delayed, Success, Cancelled, TimedOut, Failed, Cancelling — Pending/InProgress/Delayed are transient, and the invocation settles on Success (or Failed/TimedOut) with StandardOutputContent carrying the command's stdout and ResponseCode set. Only after the agent unit reads 'active' do these checks call codedeploy:CreateDeployment with an S3 revision and then read the on-host effect back through the same channel. Smithy (codedeploy, com.amazonaws.codedeploy#CodeDeploy_20141006) states what is then meant to be observable and is currently unobservable: DeploymentStatus = Created|Queued|InProgress|Baking|Succeeded|Failed|Stopped|Ready; LifecycleEvent.status via LifecycleEventStatus = Pending|InProgress|Succeeded|Failed|Skipped|Unknown; Diagnostics.errorCode via LifecycleErrorCode = Success|ScriptMissing|ScriptNotExecutable|ScriptTimedOut|ScriptFailed|UnknownError; and ErrorCode values including HOOK_EXECUTION_FAILURE, ALARM_ACTIVE, HEALTH_CONSTRAINTS and AGENT_ISSUE.
Emulator: the instance launches and is reported Online, SendCommand is accepted and returns a CommandId, and the subsequent GetCommandInvocation poll never observes a status outside the transient set and never yields StandardOutputContent. The readiness helper (`_wait_agent_active` / `_wait_fleet_ready` -> `_invoke_command`) therefore loops until the harness's per-check cap fires: all six checks report only "Check timed out after 60.0s", with the hang located in `_invoke_command`'s `time.sleep(3)` poll. No codedeploy:CreateDeployment for the Server platform is issued in this replay, so nothing about the Server compute platform is graded. Hypothesis: the emulated Run Command execution plane records a sent invocation but has no step that completes it against a running instance, so the status stays Pending forever rather than ever becoming Success/Failed/TimedOut.
Why: a client cannot use this emulator for any EC2/on-premises CodeDeploy workflow. AppSpec file installs and fileExistsBehavior, the documented in-place lifecycle event order, ApplicationStop-only-on-redeploy, hook-failure propagation with ScriptFailed diagnostics and later events Skipped, the hook environment variables the agent must export (APPLICATION_NAME, DEPLOYMENT_GROUP_NAME, DEPLOYMENT_ID, DEPLOYMENT_GROUP_ID, LIFECYCLE_EVENT), alarm gating and minimumHealthyHosts concurrency, and auto-rollback artifact reinstall are all unreachable. Because the blocking symptom is a status that never advances rather than a modeled error, a client's own wait loops hang instead of failing fast — which is strictly worse than a refusal.
Fix: two components, in order. First the SSM Run Command execution plane for an emulated managed node — the state behind SendCommand/GetCommandInvocation/ListCommandInvocations must advance an invocation sent to a running instance to a terminal CommandInvocationStatus and populate StandardOutputContent/StandardErrorContent/ResponseCode for AWS-RunShellScript. Then the CodeDeploy Server-platform deployment driver, the instance-target lifecycle execution path behind CreateDeployment/GetDeploymentTarget/ListDeploymentTargets, which is what these six checks go on to exercise once a host answers commands.
Traces: codedeploy.agent-hands-the-hook-the-real-deployment-identifiers, codedeploy.applicationstop-hook-failure-blocks-redeploy-until-ignored, codedeploy.auto-rollback-on-deployment-failure-reinstalls-the-prior-artifact, codedeploy.hook-failure-skips-later-lifecycle-events-and-fails-the-target, codedeploy.lifecycle-event-order-and-applicationstop-only-on-redeploy, codedeploy.minimum-healthy-hosts-bounds-observed-concurrent-unavailability — all six cut off in the same host-readiness setup before any CreateDeployment.

## Evidence
Expected (AWS): after the launched host reports PingStatus 'Online', ssm:SendCommand(DocumentName='AWS-RunShellScript', Parameters={commands:['systemctl is-active codedeploy-agent']}) followed by ssm:GetCommandInvocation(CommandId, InstanceId) settles within seconds on a terminal CommandInvocationStatus — Success for a reachable node, otherwise Failed or TimedOut — with StandardOutputContent carrying the command's stdout ('active' for a running codedeploy-agent unit). A Server-platform codedeploy:CreateDeployment can then be driven through its instance-target lifecycle events: deploymentInfo.status advancing Created -> InProgress -> Succeeded/Failed, per-event LifecycleEvent.status values from LifecycleEventStatus, and Diagnostics.errorCode from LifecycleErrorCode on a failed hook.

Actual (emulator): SendCommand is accepted and returns a CommandId; GetCommandInvocation for that CommandId never leaves the transient set ('Pending','InProgress','Delayed') and StandardOutputContent is never produced. Each of the six checks is cut off by the harness cap inside the readiness gate, verbatim:
- codedeploy.agent-hands-the-hook-the-real-deployment-identifiers: "Error: Check timed out after 60.0s" (hang in _wait_agent_active -> _invoke_command poll)
- codedeploy.applicationstop-hook-failure-blocks-redeploy-until-ignored: "Error: Check timed out after 60.0s"
- codedeploy.auto-rollback-on-deployment-failure-reinstalls-the-prior-artifact: "Error: Check timed out after 60.0s"
- codedeploy.hook-failure-skips-later-lifecycle-events-and-fails-the-target: "Error: Check timed out after 60.0s"
- codedeploy.lifecycle-event-order-and-applicationstop-only-on-redeploy: "Error: Check timed out after 60.0s"
- codedeploy.minimum-healthy-hosts-bounds-observed-concurrent-unavailability: "Error: Check timed out after 60.0s"
No codedeploy:CreateDeployment with computePlatform 'Server' is reached in any of the six, so no deployment status, lifecycle event, diagnostic or errorInformation value is produced to compare.

Per-run values that are NOT part of the requirement: instance ids (i-...), generated application / deployment-group / bucket names, the deployment id, the command id, the 60 s harness cap itself. The requirement is only that a Run Command sent to a running managed node reaches a terminal CommandInvocationStatus with its output, and that a Server-platform deployment then advances through its lifecycle.

## Steps to Reproduce
1. Create a VPC with a public subnet and an instance profile granting AmazonSSMManagedInstanceCore plus S3 read; read the AL2023 AMI id from the public SSM parameter /aws/service/ami-amazon-linux-latest/al2023-ami-kernel-default-x86_64.
2. ec2:RunInstances one t3.micro with that profile, tagged with the key the deployment group will filter on, and user data installing the SSM Agent and the CodeDeploy agent; wait for instance state 'running'.
3. Poll ssm:DescribeInstanceInformation(Filters=[{Key:'InstanceIds',Values:[<id>]}]) until PingStatus == 'Online' (this step succeeds today).
4. ssm:SendCommand(InstanceIds=[<id>], DocumentName='AWS-RunShellScript', Parameters={commands:['systemctl is-active codedeploy-agent']}), then poll ssm:GetCommandInvocation(CommandId=<returned id>, InstanceId=<id>).
5. Observe Status remains in ('Pending','InProgress','Delayed') indefinitely and StandardOutputContent is never populated, so the agent-readiness gate never passes.
6. Because of step 5, codedeploy:CreateApplication(computePlatform='Server') + CreateDeploymentGroup(ec2TagFilters=[...], deploymentStyle={deploymentType:'IN_PLACE',deploymentOption:'WITHOUT_TRAFFIC_CONTROL'}) + CreateDeployment with an S3 zip revision is never issued; none of the in-place lifecycle behaviors (event order, ApplicationStop on redeploy only, hook failure skipping later events, hook environment variables, minimumHealthyHosts concurrency, auto-rollback reinstall) can be observed.
