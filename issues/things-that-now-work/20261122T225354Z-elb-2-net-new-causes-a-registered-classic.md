# elb: 2 net-new causes — a registered Classic ELB instance never reaches InService, and the data plane answers 504 for the instance it selected instead of forwarding to it, so all six Classic data-plane scenarios are cut off at the 60 s cap

> _Note: this issue was identified against the code base at commit `f2e6a4662e66854bb360a08423e8578f1603b4d0`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
DescribeInstanceHealth

## Description
2 net-new causes, both in the ELB Classic (elasticloadbalancing) emulator. None of the six failing checks below is marked ALREADY FILED or OWNED in this replay report, so none is gated by an existing issue; the open issues that report the same faults from other recorded units are named per cause.

Cause 1 of 2 — a registered, serving instance never reaches DescribeInstanceHealth State='InService', so every Classic data-plane scenario burns its whole budget inside the bounded health poll without ever reaching a data-plane assertion. Failing checks: elb.registered-instance-serves-real-http-through-elb-dns-name, elb.instance-health-decides-whether-real-http-reaches-the-backend, elb.out-of-service-instance-blocked-from-receiving-traffic, elb.lb-cookie-stickiness-pins-a-client-to-one-registered-instance, elb.lb-cookie-stickiness-pins-client-to-one-instance, elb.cross-zone-load-balancing-spreads-requests-beyond-the-node-zone.
AWS: Smithy (com.amazonaws.elasticloadbalancing#ElasticLoadBalancing_v7): DescribeInstanceHealth input {LoadBalancerName required (AccessPointName), Instances}, output DescribeEndPointStateOutput {InstanceStates: InstanceState {InstanceId, State, ReasonCode, Description}}; errors AccessPointNotFoundException -> LoadBalancerNotFound (awsQueryError 400) and InvalidEndPointException -> InvalidInstance (awsQueryError 400). InstanceState$State doc: 'Valid values: InService | OutOfService | Unknown'; ReasonCode doc: 'Valid values: ELB | Instance | N/A'; Description's enumerated strings include 'N/A' and 'Instance has not passed the configured HealthyThreshold number of health checks consecutively.' ConfigureHealthCheck input {LoadBalancerName required, HealthCheck required} with HealthCheck {Target required, Interval 5..300, Timeout 2..60, UnhealthyThreshold 2..10, HealthyThreshold 2..10}. State is the OUTCOME of the load balancer probing each registered instance on the stored Target: after HealthyThreshold consecutive successful probes of Target (the checks configure 'HTTP:80/ping' or 'HTTP:80/ok', Interval 5, Timeout 2, both thresholds 2) the member reads State='InService', ReasonCode='N/A', Description='N/A' — those three strings are AWS's fixed text and only InstanceId comes from the request; an instance that then fails UnhealthyThreshold consecutive probes reads State='OutOfService' with ReasonCode='Instance' and the fixed Description 'Instance has failed at least the UnhealthyThreshold number of health checks consecutively.'
Emulator: all six checks end with 'Error: Check timed out after 60.0s' and report no assertion value at all — each is still inside its bounded DescribeInstanceHealth poll for State='InService' (the checks' own deadlines, 300–420 s, are far longer than the harness cap) when the wrapper ends it. The poll cannot be satisfied by construction: the crate's own data-plane documentation states that a registered backend is only an EC2 instance id with no server of this emulator listening on the instance port, so every HTTP health probe of that instance fails and the instance can never accumulate HealthyThreshold consecutive successes.
Why: a client cannot distinguish a healthy backend from a failed one, and every registration/deploy gate that waits for InService before sending traffic blocks until its own timeout. Everything behind that gate is unreachable too: listener forwarding, withdrawal of an unhealthy instance, the 503/504 statuses, cross-zone spreading and the AWSELB stickiness contract are all unobservable. A Classic load balancer that never has an InService instance never serves traffic at all.
Fix: the health-check evaluation that feeds the per-load-balancer instance-health state read by the DescribeInstanceHealth handler, together with the probe path it depends on — a registered instance whose backend is serving must pass its probes and be reported as the InService / 'N/A' / 'N/A' triple, and one whose backend stops answering must fall to OutOfService / 'Instance' with AWS's fixed Description. This requires the EC2 side of the emulator to let a launched instance serve on a port, which is the platform half of the cause.

Cause 2 of 2 — once the load balancer HAS selected a registered instance, the data plane answers a synthesised 504 instead of forwarding the request to that backend, so no Classic request ever carries a backend's own status, body or the load balancer's injected headers. Failing checks: elb.registered-instance-serves-real-http-through-elb-dns-name, elb.instance-health-decides-whether-real-http-reaches-the-backend, elb.out-of-service-instance-blocked-from-receiving-traffic, elb.lb-cookie-stickiness-pins-a-client-to-one-registered-instance, elb.lb-cookie-stickiness-pins-client-to-one-instance, elb.cross-zone-load-balancing-spreads-requests-beyond-the-node-zone.
AWS: recorded behavior only for the data plane (it is not modelled in Smithy). An unsigned HTTP GET of the address CreateAccessPointOutput$DNSName published is forwarded by the listener (the recordings use Protocol HTTP, LoadBalancerPort 80, InstanceProtocol HTTP, InstancePort 80) to one eligible registered instance, and the client receives that instance's OWN status and body — including a 404 with the backend's own body on a path the backend itself denies — plus the headers the load balancer injects (X-Forwarded-Proto 'http', X-Forwarded-Port '80', X-Forwarded-For). Classic ELB answers 503 only when it has no in-service instance to send the request to, and 504 only when the connection to a selected instance genuinely cannot be established. With a duration-based policy attached by CreateLBCookieStickinessPolicy + SetLoadBalancerPoliciesOfListener the listener mints Set-Cookie: AWSELB=<opaque> and pins every request carrying it to the one instance that served it, while a cookie-less client is still spread over the eligible instances; with CrossZoneLoadBalancing$Enabled at its modelled default false each load-balancer node serves only its own zone's instances, and enabling it makes the same node serve both zones'.
Emulator: the plane resolves the load balancer and selects an instance, then returns INSTANCE_UNREACHABLE_STATUS = 504 unconditionally for that selection — the crate documents this as deliberate: 'this plane does not read what the server behind such an instance serves, so the connection the load balancer makes to the instance it selected is reported as one that could not be established', and 'Neither a body nor a status is invented for a backend that never answered.' No backend status/body, no X-Forwarded-* header, no Set-Cookie: AWSELB and no per-node zone scoping can therefore ever be observed; the six checks never get past their bounded 200-body polls and are cut off at 60 s.
Why: a client of a Classic load balancer gets 504 for a correctly registered, healthy backend, so nothing behind a Classic ELB works: a smoke test of a deployed service, a stickiness-dependent session, a blue/green cutover gated on a 200 through the load balancer and any check that distinguishes 503 (no capacity) from 504 (backend unreachable) all take the wrong branch. 504 for every request is indistinguishable from a total backend outage.
Fix: the data plane's connection to the selected instance — services/.../src/service/data_plane.rs must relay the request to the backend the registered instance id names and return that backend's status, headers and body, reserving NO_IN_SERVICE_INSTANCE_STATUS (503) for the no-eligible-instance case and INSTANCE_UNREACHABLE_STATUS (504) for a backend that really does not accept the connection; the stickiness seam (src/service/stickiness.rs) must then mint and honour the AWSELB cookie on the response, and node/zone eligibility (eligible_instances) must be observable through the published address.
Traces: checks elb.registered-instance-serves-real-http-through-elb-dns-name, elb.instance-health-decides-whether-real-http-reaches-the-backend, elb.out-of-service-instance-blocked-from-receiving-traffic, elb.lb-cookie-stickiness-pins-a-client-to-one-registered-instance, elb.lb-cookie-stickiness-pins-client-to-one-instance, elb.cross-zone-load-balancing-spreads-requests-beyond-the-node-zone.
