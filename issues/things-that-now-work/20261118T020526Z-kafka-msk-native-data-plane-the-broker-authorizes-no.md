# MSK native data plane: the broker authorizes no IAM action on Produce, answers CORRUPT_MESSAGE for a headered record batch, accepts an unknown topic compression.type, cannot sustain a two-member consumer group, and three more checks reach no verdict (6 causes)

> _Note: this issue was identified against the code base at commit `775d8b7a5dc0233a720d935fa0de7ffef061d5f2`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
GetBootstrapBrokers

## Description
SIX distinct net-new root causes on the kafka (MSK) NATIVE data plane — the Apache Kafka wire protocol the emulator serves on the endpoints GetBootstrapBrokers advertises. Each is a separate root cause and must be closed separately; all six must be closed before this issue is submitted. None of the seven failing checks below is marked ALREADY FILED or OWNED in the replay report. The Kafka wire protocol is not described by the Smithy model, so every AWS statement here is recorded behavior plus the Apache Kafka 3.9 protocol and the MSK IAM access-control contract (https://docs.aws.amazon.com/msk/latest/developerguide/iam-access-control.html); the error numbers quoted are Kafka protocol constants, not per-run values.

Cause 1 of 6: the broker performs NO per-topic IAM authorization on Produce — a principal without kafka-cluster:WriteData writes successfully.
AWS: on a SASL/IAM cluster, every data-plane request is authorized against the caller's IAM policy per action and resource. A principal granted kafka-cluster:Connect, DescribeCluster, DescribeTopic, ReadData, DescribeGroup and AlterGroup but NOT kafka-cluster:WriteData has its Produce refused by the broker with the topic-scoped error TOPIC_AUTHORIZATION_FAILED (Kafka error 29); nothing is appended, so the partition's end offset is unchanged and the record never appears in the log, while the SAME credentials can still fetch the records a privileged producer wrote.
Emulator: the restricted session completes the AWS_MSK_IAM handshake (the check proves the produce signed with the restricted session by matching the access key's last four characters) and the Produce is ACKNOWLEDGED — the check reports the record landed at partition 0, offset 1. No authorization decision is taken at all.
Why: this is the emulator being over-permissive on the exact control that protects a topic. A least-privilege policy validated against the emulator passes while the same policy's deny is the thing MSK enforces; conversely a client's handling of TOPIC_AUTHORIZATION_FAILED is never exercised, and data a real cluster would reject is written into the log.
Fix: the native broker plane's Produce path in the kafka crate (the Kafka wire-protocol handler reached through crate::state::broker_plane) must evaluate the SASL/IAM principal's policy per request — kafka-cluster:WriteData on the topic resource for Produce — and answer error 29 TOPIC_AUTHORIZATION_FAILED per topic-partition without appending, instead of acknowledging unconditionally.
Traces: kafka.kafka-iam-policy-without-write-permission-fails-produce-and-a-read-still-succeeds.

Cause 2 of 6: Produce of a v2 record batch carrying headers and an explicit CreateTime is answered CORRUPT_MESSAGE.
AWS: a Produce of one record with a key, a ~2.4 KB value, four headers (repeated keys, an empty value and a 256-byte binary value — header order and bytes are part of the record, KIP-82) and an explicit timestamp_ms is accepted on every codec a client may use (none, gzip, zstd), and the ack carries the assigned offset and the producer's own CreateTime; the records then read back byte for byte with their headers, timestamp and timestamp_type 0.
Emulator: the Produce fails with Kafka error 2, CORRUPT_MESSAGE (kafka-python raises CorruptRecordError: [Error 2] CorruptRecordError: None) on the first record of the codec sequence, so no record is ever stored and the whole codec/headers/timestamp surface — the offsets_for_times lookups, LogAppendTime, partition growth, idempotent and transactional sequences that follow — is unreachable.
Why: CORRUPT_MESSAGE tells a client its batch is damaged, so a client (or a retry layer) that sees it on a perfectly valid batch concludes the data is bad and drops or endlessly retries it. The emulator's broker cannot ingest the record shape real producers send by default once headers or an explicit timestamp are present.
Fix: the native broker plane's Produce record-batch decoder in the kafka crate — accept RecordBatch v2 with a header array and an explicit CreateTime (and the compressed forms gzip/zstd) rather than failing validation, and keep the headers, timestamp and timestamp_type for the fetch path.
Traces: kafka.kafka-native-codecs-headers-timestamps-partition-growth-transactions-and-seeks.

Cause 3 of 6: CreateTopics accepts an unknown topic compression.type instead of refusing that topic.
AWS: CreateTopics validates each topic's config entries per topic and answers per topic. A topic whose configs name compression.type=brotli is refused with error_code 40 (INVALID_CONFIG) and error_message "Invalid value brotli for configuration compression.type: String must be one of: uncompressed, zstd, lz4, snappy, gzip, producer" — the connective text and the valid-value list are fixed, and the offending value (here 'brotli') is the one part taken from the request — while a legal neighbour in the SAME request (compression.type=lz4) is created with error_code 0; the refused topic does not appear in a later topic listing.
Emulator: BOTH topics answer error_code 0, so the brotli topic is CREATED with an impossible codec and no refusal is produced.
Why: a client's topic-provisioning code is told an unusable configuration was accepted and only discovers it at produce time; the per-topic partial-failure contract of CreateTopics (one topic refused, its neighbour created in the same request) is unverifiable, and config-validation tests pass vacuously.
Fix: validate each topic's config entries in the native broker plane's CreateTopics path against the broker's allowed value set, and answer error 40 INVALID_CONFIG with the message template above for the offending topic only, creating the others.
Traces: kafka.kafka-native-snappy-and-lz4-records-round-trip-and-a-topic-codec-recompresses-them.

Cause 4 of 6: CreateTopics encodes error_message as an empty string where the protocol encodes null for a successful topic.
AWS: in the CreateTopics response, a topic created successfully carries error_code 0 and a NULL error_message (the field is a nullable string), which a client decodes as None.
Emulator: the successful lz4 topic is answered error_code 0 with error_message '' — an empty string rather than null — as the same assertion's actual value shows ({'lz4': (0, '')} where (0, None) is required).
Why: a client that tests `error_message is not None` (or logs any non-null message) treats every successful topic as carrying a diagnostic, so success-path logging and error detection both misread the response. It is the serializer, not the validation, so it diverges even once Cause 3 is fixed.
Fix: the native broker plane's CreateTopics response serializer must emit a null nullable-string for error_message when there is no error, not an empty string.
Traces: kafka.kafka-native-snappy-and-lz4-records-round-trip-and-a-topic-codec-recompresses-them.

Cause 5 of 6: a two-member consumer group never settles — the second member's session dies at the stable-two-members stage.
AWS: with two members in one group over SASL/IAM, the coordinator completes the second rebalance and DescribeGroups reports the group Stable with 2 members, the four partitions split by the range assignor (two per member); both member sessions stay alive while they heartbeat, and each then reports its own assignment.
Emulator: the check's two member processes join, but while waiting (up to 150 s, polling DescribeGroups every 3 s) for the coordinator to report state 'Stable' with members == 2, the member session fails: the ops harness reports stage 'stable_two_members' failing with BrokenPipeError [Errno 32] Broken pipe when it next writes to a member, i.e. a member that was heartbeating to the emulator's broker is gone, so the group never reaches a stable two-member assignment and the range split, the session-timeout expiry and the reassignment this check exists to verify are never observed. The members' only external dependency is the emulator's broker endpoint.
Why: consumer-group rebalancing with more than one member is the core of the Kafka group protocol; a client scaled to two consumers cannot keep a session against the emulator, so assignment, heartbeat/session-timeout eviction and reassignment behavior is unverifiable and a scaled consumer application cannot run.
Fix: the native broker plane's group coordinator (JoinGroup/SyncGroup/Heartbeat/DescribeGroups) must sustain concurrent members on their own connections, complete the second rebalance to a Stable state reporting both members with a range assignment, and never drop a heartbeating member's connection.
Traces: kafka.msk-consumer-group-two-member-range-split-then-session-timeout-expiry-reassigns.

Cause 6 of 6: three more data-plane checks reach NO verdict at all — each ends on the bare 60 s ceiling with no HTTP status, no Kafka error and no assertion evaluated.
AWS: each of the three completes its bring-up and then its data-plane assertions well inside a client-sized budget: (a) committed consumer-group offsets survive a rebalance and no record is redelivered; (b) an IAM policy scoped to a group-name prefix denies a consumer-group join with GROUP_AUTHORIZATION_FAILED (Kafka error 30) while an assign()-based read on the same topic still succeeds; (c) 25 records produced in order to a single-partition topic are consumed back in exactly that order (the per-partition FIFO guarantee) over the advertised SASL/SCRAM endpoint.
Emulator: all three time out with nothing asserted, so the bring-up barrier each shares — cluster CREATING -> ACTIVE, the topic/SCRAM or IAM grant steps, then a usable bootstrap endpoint from GetBootstrapBrokers — does not complete in the budget. Because the emulator is what announces those endpoints and owns those transitions, the stall is the emulator's, not the runner's.
Why: three whole behaviors (offset durability across a rebalance, group-scope authorization, per-partition ordering) are unmeasurable, and a client configuring itself from the control plane hangs until its own timeout.
Fix: the kafka crate's lifecycle transitions must settle on the write path (so a first probe after a create/update observes the terminal value) and the broker plane must accept connections and complete the SASL handshake on every endpoint it advertises.
