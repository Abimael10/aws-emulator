# appconfig__appconfigdata__iam__s3: an S3-backed configuration profile is never served — GetLatestConfiguration answers 404 ResourceNotFoundException "could not be retrieved from s3://<bucket>/<key>" because the external-source resolver has no S3 reader

> _Note: this issue was identified against the code base at commit `0cb56282b0b5db0d156916db95a8cefdc5d77df2`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
GetLatestConfiguration

## Description
REOPENS 20261114T120858Z-appconfig-ssm-an-ssm-parameter-store-backed-configuration.md: its fix left the call refused. That issue's Fix was "for a profile whose LocationUri is not the hosted store, resolve the content of the SOURCE version the deployment recorded" and named S3 among the stores the one resolver had to cover; only the ssm-parameter:// branch was implemented, so the same GetLatestConfiguration ResourceNotFoundException (same Issue-Key appconfigdata|GetLatestConfiguration|ResourceNotFoundException) is still returned for an s3:// profile, now with a different sentence.

Cause 1 of 1: a configuration profile whose LocationUri names an Amazon S3 object is accepted by the control plane and its deployment reaches a terminal COMPLETE state, but the data plane can never serve it: the shared external-source resolver recognises only the hosted store and ssm-parameter://, and classifies every other documented LocationUri scheme as "Elsewhere", for which it returns an unavailable-source refusal unconditionally. Failing checks: appconfig__appconfigdata__iam__s3.versioned-s3-configuration-profile-serves-the-deployed-object-version, appconfig__appconfigdata__iam__s3.deployment-rejects-an-s3-configuration-version-id-that-does-not-exist.

AWS: Smithy (services/service-com-amazonaws-appconfig-amazonappconfig/smithy-model/com-amazonaws-appconfig-amazonappconfig.json) documents CreateConfigurationProfile.LocationUri as "A URI to locate the configuration. You can specify the following: ... For an Amazon S3 object, specify the URI in the following format: s3://<bucket>/<objectKey>. Here is an example: s3://amzn-s3-demo-bucket/my-app/us-east-1/my-config.json", alongside hosted, ssm-parameter://, codepipeline://, secretsmanager:// and ssm-document://. StartDeployment.ConfigurationVersion is documented as "The configuration version to deploy. If deploying an AppConfig hosted configuration version, you can specify either the version number or version label. For all other configurations, you must specify the version number" — for an S3-backed profile that version number is the S3 object's VersionId. Recorded behavior: after StartDeployment of object version V reaches State COMPLETE, appconfigdata StartConfigurationSession + GetLatestConfiguration answer HTTP 200 with Configuration equal to the bytes S3 holds at that exact VersionId (not the bytes currently at the key), and a second deployment naming a different VersionId changes what every fresh session is served. AppConfig reads the object through the profile's RetrievalRoleArn.

Emulator: CreateConfigurationProfile(LocationUri="s3://<bucket>/<key>", RetrievalRoleArn=<appconfig-trusted role>, Type="AWS.Freeform") succeeds and echoes LocationUri/RetrievalRoleArn/Type; StartDeployment naming the real S3 VersionId is accepted and settles; but every GetLatestConfiguration over a session on that triple is refused HTTP 404, Error.Code "ResourceNotFoundException", Error.Message "Configuration version '<ConfigurationVersion>' of configuration profile '<profile-id>' could not be retrieved from <LocationUri>: Configuration version '<ConfigurationVersion>' could not be retrieved from <LocationUri>." In that message the fixed text is the emulator's own two concatenated sentences (an outer "... of configuration profile ... could not be retrieved from <uri>: " wrapper around an inner "Configuration version ... could not be retrieved from <uri>."); its variable parts are the deployed ConfigurationVersion and the profile id from state and the profile's LocationUri. AWS sends no refusal on this path at all — it answers 200 with the object version's bytes — so both the status and the error class are wrong, and the message is emulator-authored text with no AWS counterpart.

Why: every S3-sourced configuration profile is unusable end to end. An application that keeps its configuration in a versioned S3 object (one of the six documented LocationUri forms) gets a 404 ResourceNotFoundException from the data plane where AWS returns its configuration bytes, so it boots with no configuration and cannot distinguish "the profile does not exist" from "the source reader is missing". Because nothing is ever served, AWS's object-version pinning (a later PutObject to the same key must not reach running sessions until a deployment names the new VersionId) is unobservable too. The same gap blocks the negative class: with the control path refused, the check that StartDeployment refuses an S3 object VersionId that was never minted for the key — AWS answers BadRequestException whose Message is "An error occurred when calling the S3 GetObjectMetadata operation: Forbidden (Service: Amazon S3; Status Code: 403; Error Code: 403 Forbidden; Request ID: <id>; S3 Extended Request ID: <id>; Proxy: null)", where the only per-run values are AWS's two request ids — and leaves no deployment record behind, never gets to run.

Fix: the shared external-source resolver in the AppConfig state — services/service-com-amazonaws-appconfig-amazonappconfig/src/state/configuration_sources.rs, source_of()/ConfigurationSource and source_configuration() — needs an S3 branch beside the existing SsmParameter one: parse s3://<bucket>/<objectKey>, read that object at the VersionId the in-force deployment recorded out of the co-mounted S3 service's own store, and hand back its bytes with the object's content type, so both readers of a deployed configuration (appconfig GetConfiguration and the appconfigdata poll via crate::state::served_configuration -> source_content) serve it. The "could not be retrieved" SourceUnavailable sentence must then be confined to a source version that genuinely does not exist, and the matching gate belongs on StartDeployment's handler so a never-minted object version is refused synchronously with AWS's BadRequestException instead of being accepted and failing at serve time.

Traces: failing checks appconfig__appconfigdata__iam__s3.versioned-s3-configuration-profile-serves-the-deployed-object-version and appconfig__appconfigdata__iam__s3.deployment-rejects-an-s3-configuration-version-id-that-does-not-exist.
