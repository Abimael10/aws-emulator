# codecommit: a repository trigger never fires on a real reference update — PutFile moves a branch tip and publishes nothing to the trigger's SNS destination

> _Note: this issue was identified against the code base at commit `da1bdaf0970a5b39397b846da655b4a2fa6e7dc9`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
PutFile

## Description
ONE net-new root cause behind the codecommit deploy-trigger check. The check reaches its final poll and hangs to the harness cap because the notification a real ref update must produce is never sent.

=== Cause 1 of 1: a configured repository trigger produces no notification when a reference actually changes ===
AWS: Smithy com-amazonaws-codecommit-codecommit-20150413 — `RepositoryTrigger$events` is `RepositoryTriggerEventEnum` with values `all`, `updateReference`, `createReference`, `deleteReference`, and `RepositoryTrigger$destinationArn` is documented as "The ARN of the resource that is the target for a trigger (for example, the ARN of a topic in Amazon SNS)"; `RepositoryTrigger$branches` documents that "if you specify an empty array, the trigger applies to all branches". So a stored trigger exists to be acted on by the write path, not only by `TestRepositoryTriggers`: when a write moves a reference the trigger is in scope for, CodeCommit publishes one record to the destination. Recorded behavior for the record: a single `Records` entry with `eventSource` `aws:codecommit`, `eventName` `ReferenceChanges`, `eventSourceARN` equal to the repository ARN, `eventTriggerName` equal to the trigger's `name`, `eventTriggerConfigId` equal to the `configurationId` `PutRepositoryTriggers` returned, and `codecommit.references[0]` naming the fully qualified ref (`refs/heads/<branch>`, not the short branch name) together with the exact commit id the write created. The commit ids, repository names and config ids of any one run fill that template; they are not part of it.
Emulator: nothing is ever sent for a real reference change. The only code path in the crate that builds and sends a trigger record is `crate::state::trigger_notifications::test_notifications`, called solely from the `TestRepositoryTriggers` handler. `PutFile` validates, writes the commit, calls `repository.set_branch_tip(..)` and then only `crate::state::pull_request_events::publish_all_detached(published, ctx.callback())` — it never consults `repository.trigger_configuration`, so no SNS `Publish` (and no Lambda `Invoke`) happens for the branch it just moved. `CreateCommit`, `CreateBranch`, `DeleteBranch`, `DeleteFile`, merge operations and the git push path behave the same way.
Why: a client that wires a repository trigger to an SNS topic (the standard CodeCommit→SNS→SQS/Lambda notification pattern) gets a configuration it can read back and that passes `TestRepositoryTriggers`, but it never receives a single notification for an actual commit. Every consumer built on repository triggers — build kickoff, notification fan-out, audit — silently never runs, and the caller has no error to observe: the write returns 200 and the trigger config looks correct. `TestRepositoryTriggers` succeeding makes the gap actively misleading.
Fix: the reference-moving write path of the codecommit service — the one place a branch tip moves (`crate::state::Repository::set_branch_tip`, used by `PutFile`, `CreateCommit`, `CreateBranch`, `DeleteBranch`, `DeleteFile`, the merge handlers and `crate::service::git_http`) must, after releasing the store guard, select the stored `trigger_configuration`'s triggers whose `branches` include the moved branch (or are empty) and whose `events` include `all` plus the matching `createReference`/`updateReference`/`deleteReference`, render the same record `crate::state::trigger_notifications` already renders (with the STORED `configurationId`) and send it through the existing `TriggerNotification::send` seam. A trigger scoped to other branches, or to other events, must send nothing.
Traces: codecommit.deploy-codecommit-repository-trigger-enforced.

No open issue carries this check's current failure. Open issue 20261022T171422Z-codecommit-getrepositorytriggers-stub.md names this check, but it is about `GetRepositoryTriggers` answering 501: that handler is now implemented (it reads `repository.trigger_configuration` and returns it), the check now gets past that call and hangs in its post-commit poll instead, so this cause is net-new. ## Evidence
Check codecommit.deploy-codecommit-repository-trigger-enforced (mismatch): "Check timed out after 60.0s". The check deploys an AWS::CodeCommit::Repository with one trigger (DestinationArn = an SNS topic subscribed by an SQS queue, Events=['all'], Branches=[]), asserts GetRepositoryTriggers reflects it and that TestRepositoryTriggers reports successfulExecutions=[trigger] — those asserts do not fire — then calls PutFile(branchName='main') and polls the subscribed queue for up to 90 s for a record whose codecommit.references[*].commit equals the commit id PutFile returned. Expected: one message whose decoded SNS Message has Records[0].eventTriggerName = the trigger name, Records[0].eventSourceARN containing the repository name, and exactly one reference with ref 'refs/heads/main' and commit = the returned commit id. Actual: no message ever arrives; the 90 s poll outlives the 60 s check budget, so the run is killed with no verdict. Source corroboration: services/service-com-amazonaws-codecommit-codecommit-20150413/src/ops/put_file.rs lines 556-571 move the branch tip and publish only pull-request events; services/service-com-amazonaws-codecommit-codecommit-20150413/src/state/trigger_notifications.rs exposes only `test_notifications` (consumed by src/ops/test_repository_triggers.rs lines 240-267), so no reference change can produce a notification.

## Steps to Reproduce
1. Boot the emulator from this checkout and point botocore at it.
2. sns.create_topic, sqs.create_queue, set a queue policy allowing sns.amazonaws.com sqs:SendMessage for that topic, sns.subscribe(Protocol='sqs').
3. Create a CodeCommit repository (directly or via a CFN AWS::CodeCommit::Repository with Triggers) and PutRepositoryTriggers with one trigger: destinationArn = the topic, events=['all'], branches=[].
4. GetRepositoryTriggers — the trigger is stored. TestRepositoryTriggers — successfulExecutions=[trigger].
5. codecommit.put_file(repositoryName=R, branchName='main', filePath='TRIGGER.md', fileContent=b'x') and note the returned commitId.
6. sqs.receive_message on the subscribed queue: expect a notification whose Records[0].codecommit.references[0] is {ref:'refs/heads/main', commit:<that commitId>} with eventName 'ReferenceChanges', eventTriggerName = the trigger name and eventSourceARN = the repository ARN. Observe nothing arrives.
7. Re-replay codecommit.deploy-codecommit-repository-trigger-enforced; it must pass within its budget.
