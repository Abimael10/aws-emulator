Cause 1 of 1: with an internet-facing ALB whose only target is a lambda-type target group, driving a known mix of 200- and 500-answering requests through the load balancer produces no observable AWS/ApplicationELB series, and consequently neither a plain Sum alarm on HTTPCode_Target_5XX_Count nor a Metrics/Expression (metric-math) alarm on 100 * FILL(m1, 0) / m2 ever completes an evaluation. Failing check: cloudwatch__elbv2__s3.target-5xx-rate-alarm-stays-ok-under-a-low-error-rate-that-fires-a-count-alarm.
AWS: Smithy (cloudwatch, services/service-com-amazonaws-cloudwatch-graniteserviceversion20100801) PutMetricAlarm accepts either a single metric (Namespace/MetricName/Dimensions (0..30)/Statistic/Period (min 1)) or Metrics (MetricDataQueries, each with Id, optional MetricStat and optional Expression plus ReturnData), with EvaluationPeriods (min 1), DatapointsToAlarm (min 1), Threshold, ComparisonOperator and TreatMissingData; DescribeAlarms returns MetricAlarms[].StateValue and DescribeAlarmHistory returns AlarmHistoryItems with HistoryItemType StateUpdate whose HistoryData carries newState.stateValue. The models say nothing about which datapoints an ALB emits, so for the metric emission this is recorded behavior only: every request a load balancer answers is counted into the per-minute AWS/ApplicationELB series — RequestCount, and HTTPCode_Target_5XX_Count for a 5xx the target itself returned — under the LoadBalancer dimension (app/<name>/<id>) and, for target-scoped metrics, the TargetGroup dimension (targetgroup/<name>/<id>); a period-60, 1-of-1 alarm then transitions on those datapoints. The requirement is the closed loop and the differential it draws: one target 500 among nine 200s drives the COUNT alarm (Threshold 0, GreaterThanThreshold, TreatMissingData notBreaching) to ALARM while the RATE alarm completes an evaluation and reads OK with no ALARM in its StateUpdate history (the rate stays under its Threshold of 50), and once every request answers 500 BOTH alarms read ALARM. The specific request counts, names, ids and timings come from the run and are not part of the requirement; the check's 420 s active deadline and 600 s alarm deadline are declared ceilings to fail at, never asserted latencies.
Emulator: the check is killed by its ceiling with no answer to grade — "Error: Check timed out after 600.0s". Inside that window the count alarm never leaves its notBreaching state and the rate alarm never leaves INSUFFICIENT_DATA, so no alarm transition and no DescribeAlarmHistory StateUpdate is ever observed. Hypothesis (the replay output carries only the timeout): the AWS/ApplicationELB RequestCount / HTTPCode_Target_5XX_Count series is never published for the requests the load balancer is asked to serve — the defect the sibling issues above record for other checks under this heading — so both alarms evaluate over empty series; the alarm evaluator for Metrics/Expression alarms is equally unexercised.
Why: a client's only automated signal that a Lambda-backed ALB's targets are erroring is an alarm on these series, and the rate-vs-count differential is exactly what production alarming is built on — a count alarm pages on any target 5xx, a rate alarm tolerates a low background error rate and pages only on a real outage. Against the emulator neither alarm ever leaves its initial state, so deployment gates, rollbacks, SNS/scaling actions and pager routing hung off them all silently read "nothing wrong", and alarm configuration validated here will not page on real AWS.
Fix: the ELBv2 AWS/ApplicationELB metric publisher for load-balancer-served requests (per-request RequestCount and HTTPCode_Target_5XX_Count at period 60 under the LoadBalancer and TargetGroup dimensions, with target-vs-ELB attribution of a 5xx) together with the Lambda-target request path it observes, and the CloudWatch alarm evaluator for both plain-metric and Metrics/Expression (metric-math, FILL) alarms so a 1-of-1 period-60 alarm transitions on those datapoints and records a StateUpdate in DescribeAlarmHistory.
Traces: cloudwatch__elbv2__s3.target-5xx-rate-alarm-stays-ok-under-a-low-error-rate-that-fires-a-count-alarm.
