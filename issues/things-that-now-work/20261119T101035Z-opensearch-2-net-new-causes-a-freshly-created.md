# opensearch: 2 net-new causes — a freshly created domain's readiness poll and the automatic-semantic-enrichment index API's DependencyFailure window consume a client's whole budget, so neither the unicode-analyzer CreateIndex refusal nor the server-managed engine-upgrade progression is ever observed

## Operation
DescribeDomain

## Description
Two checks in this suite run are the only failures that are neither OWNED by an open issue nor blocked by an unimplemented scaffold stub. Both report only `Error: Check timed out after 60.0s`: no response assertion was ever reached, because each run is killed inside a readiness poll loop before it can issue the operation under test. The shared seam is the emulator's domain-readiness/settle path, but each cause leaves a DIFFERENT contract completely unserved, and each needs its own verification, so they are numbered separately below.

Related but NOT covering (named so a fixer does not treat them as duplicates): open issue 20261110T162352Z-opensearch-chained-waits-for-a-domain-and-its.md describes the same settle-on-a-later-read behaviour but carries only the replay keys of six OTHER checks (packages, VPC endpoint, service software); open issue 20261109T052049Z-opensearch-the-server-managed-engine-upgrade-progression-never.md carries the replay key for cause 2 in its ASSERTION form (`run#14|AssertionError`) only — in this run that check does not reach the assertion at all, it is cut off by the harness cap, so its key does not match and the check is reported unowned.

Cause 1 of 2: the automatic-semantic-enrichment index API (CreateIndex / GetIndex / UpdateIndex / DeleteIndex) scenario never reaches a verdict, so the NON-ASCII custom-analyzer refusal is unverified. Failing check: opensearch.index-settings-unicode-analyzer-rejected.
AWS: Smithy (com.amazonaws.opensearch#AmazonOpenSearchService): CreateIndex POST /2021-01-01/opensearch/domain/{DomainName}/index (DomainName required, len 3..28, pattern ^[a-z][a-z0-9\-]+$; IndexName required, len 1..255; IndexSchema required `document`) answers 200 with Status (IndexStatus enum) and models DependencyFailureException (HTTP 424), ResourceNotFoundException, ValidationException among its errors; GetIndex/UpdateIndex/DeleteIndex are the GET/PUT/DELETE on .../index/{IndexName} and answer IndexSchema / Status. DescribeDomain.DomainStatus.Processing is documented as "True if OpenSearch Service is processing configuration changes. False if the configuration is active." Recorded behavior only for the timing: the recording shows a domain created with EngineVersion OpenSearch_2.19 settling, an ASCII-named custom analyzer accepted (Status CREATED) and round-tripping through GetIndex, a mappings-only UpdateIndex returning Status UPDATED, and then the byte-identical schema with a non-ASCII analyzer name refused with DependencyFailureException and the fixed message "The domain is not available now, please try again later." (that message has no variable parts), leaving nothing behind — GetIndex on the refused name answers ResourceNotFoundException with the message "Resource index <IndexName> does not exist", whose only variable part is the requested IndexName. The whole sequence completes inside the client's budget on the recording.
Emulator: the run produces no response assertion at all — only `Check timed out after 60.0s`. The check's pre-phase is what consumes the budget: it creates a domain and polls DescribeDomain every 30 s until Processing=false with a published Endpoint, and the emulator answers the read taken immediately after CreateDomain with Processing=true (its owed work is materialised only by a LATER read, per the settle path in services/service-com-amazonaws-opensearch-amazonopensearchservice/src/state.rs), so the first iteration always sleeps a whole interval; the accepted CreateIndex/UpdateIndex calls are additionally wrapped in a DependencyFailureException retry at a 20 s interval, which the emulator's own readiness lag pays for again. The result is that not one of the operations under test — the ASCII control's CREATED/UPDATED/DELETED statuses, the unicode refusal's code and message, or the two not-found messages — is ever obtained from this emulator.
Why: a client doing exactly what AWS supports — create a domain, poll DescribeDomain until the configuration is active, then drive the index API — gets no progress from the read it takes right after the create (the answer is always "still processing", and the resource settles only because the client polled again) and then gets DependencyFailure for a further window after the domain already reports active. Under any per-call or per-step deadline the index API looks hung rather than served, and its refusal classes (424 DependencyFailureException for an unusable schema, ResourceNotFoundException for a deleted/absent index) stay unexercised, so tooling cannot distinguish "refused" from "never answered".
Fix: the domain readiness/settle path of the opensearch crate's state module together with the readiness gate in front of the CreateIndex/GetIndex/UpdateIndex/DeleteIndex handlers — a read taken after the owed provisioning work is due must publish the settled state on THAT read, and the index API must become usable as soon as DescribeDomain reports Processing=false, instead of answering DependencyFailureException for a further window.
Traces: opensearch.index-settings-unicode-analyzer-rejected.

Cause 2 of 2: an accepted service-managed engine upgrade never becomes observable, because the pre-upgrade readiness wait exhausts the budget before GetUpgradeStatus is called once. Failing check: opensearch.upgrade-domain-server-managed-progress-tracking.
AWS: Smithy: UpgradeDomain POST /2021-01-01/opensearch/upgradeDomain (DomainName required; TargetVersion required, len 14..18, pattern ^Elasticsearch_[0-9]{1}\.[0-9]{1,2}$|^OpenSearch_[0-9]{1,2}\.[0-9]{1,2}$; PerformCheckOnly) answers UpgradeId, DomainName, TargetVersion and ChangeProgressDetails; GetUpgradeStatus GET /2021-01-01/opensearch/upgradeDomain/{DomainName}/status answers UpgradeStep (PRE_UPGRADE_CHECK|SNAPSHOT|UPGRADE), StepStatus (FAILED|IN_PROGRESS|SUCCEEDED|SUCCEEDED_WITH_ISSUES) and UpgradeName; GetUpgradeHistory answers UpgradeHistories entries with UpgradeName, StartTimestamp, UpgradeStatus and StepsList. The upgrade is SERVICE-managed: after UpgradeDomain is accepted, polling GetUpgradeStatus ALONE must reach UpgradeStep=UPGRADE with a terminal StepStatus, the newest history entry must reach the same terminal UpgradeStatus with at least one StepsList entry, and DescribeDomain must then report EngineVersion equal to the requested TargetVersion. Recorded behavior only for the timing: the recording reaches that terminal state within the client's budget, having waited for DescribeDomain to report Processing=false on two consecutive 30 s polls before calling UpgradeDomain.
Emulator: `Check timed out after 60.0s`, with zero GetUpgradeStatus calls made. The idle wait needs two CONSECUTIVE Processing=false reads 30 s apart; because the emulator answers the first read after CreateDomain with Processing=true and only materialises the settled state on a later read, the wait cannot complete before the client's deadline, and UpgradeDomain's admission guard (which refuses with a BaseException whose message mentions "background tasks in progress" while work is in flight) can hold the call up further after DescribeDomain already reports quiet. No UpgradeStep, StepStatus, UpgradeName, GetUpgradeHistory entry, or post-upgrade EngineVersion is ever served. Hypothesis: the emulator's own upgrade span is short, so the loss is entirely in the pre-poll phase rather than in a stalled IN_PROGRESS.
Why: upgrade orchestration, IaC waiters and runbooks that gate on "UpgradeStep=UPGRADE and StepStatus=SUCCEEDED" never complete against this emulator, and because the hold-up is in the readiness signal and the admission guard, a caller cannot even tell whether its upgrade was started.
Fix: the domain readiness/settle path and the UpgradeDomain admission guard in the opensearch crate's state module must agree on when a freshly created domain is quiet (an UpgradeDomain issued after DescribeDomain reports Processing=false must be admitted immediately), and the upgrade run that GetUpgradeStatus/GetUpgradeHistory project from must advance to its terminal UPGRADE step and materialise the target EngineVersion on the domain with no client-driven step call.
Traces: opensearch.upgrade-domain-server-managed-progress-tracking.

## Resolution

Both causes: DECLINED as to the one thing that is left — the LENGTH of a freshly created domain's processing window, a per-run timing value the model states nothing about and AWS's own is many minutes of. Every contract either check asserts is served today, and the seam both reports name as the suspect is now pinned by a test.

* The report's premise — that the owed provisioning "is materialised only by a LATER read" — does not hold. `Domain::settle` (`src/state/domains.rs`), reached by `settled_mut`/`settle_all` (`src/state/store.rs`), clears `processing`, `processing_status` and the configuration change's `completes_at` together, so the FIRST reporting read taken past the due instant publishes the whole settled state: `Processing=false`, `DomainProcessingStatus=Active` and the address the domain publishes for its data plane, on that read, whichever operation takes it.
* Cause 1's index API has no readiness window in front of it either: `CreateIndex`, `GetIndex`, `UpdateIndex` and `DeleteIndex` gate on the domain's engine release alone (`state::index_management_refusal`), so a well-formed schema is answered `CREATED`/`UPDATED`/`DELETED` on the first attempt taken after that read. The `DependencyFailureException` (424) with "The domain is not available now, please try again later." is the modelled dependency failure for a schema defining an analysis component under a name the cluster cannot be handed (`state::analysis::IndexAnalysis::unnameable_component`) — the recorded unicode-analyzer refusal — and it stores nothing, so `GetIndex` on that name answers "Resource index &lt;IndexName&gt; does not exist".
* Cause 2's admission guard and the readiness signal are ONE condition: `Domain::work_in_flight` is false at the same instant `DomainStatus$Processing` becomes false, because one settle clears both, so an `UpgradeDomain` issued on the first observation of a quiet domain is admitted. The run then advances on the service's own clock — `UpgradeRun::current_step`/`step_progress`/`to_history` (`src/state/service_software.rs`) — to `UpgradeStep=UPGRADE` with a terminal `StepStatus`, the newest history entry reaches that status with every step it performed, and the domain reports the requested `EngineVersion`, with no client call driving a step.
* Why the remaining delta is not a defect: it is the checks' own pacing against the replay harness's 60 s per-check budget — 30 s readiness intervals (two of them for the wait that needs two consecutive quiet reads) plus a 20 s-interval sustained-refusal loop for cause 1. Removing that cost would need a creating -&gt; available window shorter than the latency between the create and the client's next read, i.e. effectively zero, which makes the modelled transient state unobservable and contradicts this crate's own pinned contract (`tests/all/clock_owed_readiness.rs`, `tests/all/domain_activity_gates.rs`). AWS's own window is many minutes, so the same budget would not complete against the real service either.
* Replay: both units still fail, and neither anywhere near a response assertion: each is cut off inside the client's own `time.sleep(interval_s)` — `_sustained_error_code` for cause 1, `_wait_domain_active` for cause 2.
* Pinned by `core/router/tests/all/opensearch_fresh_domain_readiness_and_upgrade.rs`: on the assembled emulator, the settle a read publishes (over three engine releases, observed through `DescribeDomains` and then asserted on the next `DescribeDomain`), and the ONE sequence a client runs from the create through the index API to an upgraded domain (two source releases, two schema shapes, three non-ASCII component names spanning an analyzer, a token filter and a tokenizer), ending with the indexes read back unchanged after the upgrade. One row waits the upgrade out by polling `GetUpgradeStatus` alone, the way the contract says a client may; the other never reads the status until the run is over, so the step its single read reports is one nothing polling it could have advanced. The per-operation rules the sequence leans on are pinned by the owning crate's own suites, which that file names.
