# cloudcontrol: 5 net-new causes — registry-schema refusals carry InvalidRequestException/handler codes instead of ValidationException + "Model validation failed (...)", downstream refusals are mis-coded, and RoleArn is ignored on DeleteResource

> _Note: this issue was identified against the code base at commit `70b7c678778f0d916154cffcdac6331922d5f986`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
CreateResource

## Description
FIVE net-new root causes, all in the cloudcontrol (Cloud Control API) service. A fixer must close all five. These are NOT the acceptance failures already filed as 20261102T095426Z-cloudcontrol-9-net-new-causes-desiredstate-patchdocument-are.md: the emulator now DOES refuse these requests, so the divergence has moved to the refusal's error code, its refusal plane and its message text. Model citations are from services/service-com-amazonaws-cloudcontrol-cloudapiservice/smithy-model/com-amazonaws-cloudcontrol-cloudapiservice.json.

Cause 1 of 5: every DesiredState/PatchDocument registry-schema violation is refused with InvalidRequestException and an emulator-authored one-line message, instead of ValidationException with AWS's "Model validation failed (...)" diagnostic.
AWS: Cloud Control validates DesiredState (and the post-patch model for UpdateResource) against the resource type's registry schema at the front door, BEFORE any handler runs, and refuses with error code ValidationException at HTTP 400. ValidationException is a service-common error of CloudApiService, distinct from the modeled InvalidRequestException (Smithy: CreateResource/UpdateResource both model InvalidRequestException, httpError 400, "The resource handler has returned that invalid input from the user has generated a generic exception") — InvalidRequestException is reserved for HANDLER-reported errors, so a front-door schema refusal must not use it. The message is a fixed template: the literal text `Model validation failed (` + the JSON-schema violation list + `)`. Its fixed parts per violation class, with the variable parts taken from the request and from the type schema (the JSON pointer of the offending member, the property name, the declared and found JSON type names), are:
  - required key missing: `Model validation failed (#: required key [<PropertyName>] not found)`
  - property absent from the schema: `Model validation failed (#: extraneous key [<PropertyName>] is not permitted)`
  - wrong JSON type: `Model validation failed (#/<PropertyName>: expected type: <DeclaredType>, found: <FoundType>)`
  - value outside an enum: `Model validation failed (#/<PropertyName>: #: only 1 subschema matches out of 2\n#/<PropertyName>: failed validation constraint for keyword [enum])`
  - a patch that removes a required property: the required-key form above, validated against the POST-patch model.
Emulator: HTTP 400 with error code InvalidRequestException and a hand-written message instead. Observed, for AWS::SSM::Parameter and AWS::SQS::Queue: `InvalidRequestException: Value is required by AWS::SSM::Parameter` (AWS: ValidationException `Model validation failed (#: required key [Value] not found)`); `InvalidRequestException: SimParityNotAProperty is not a property of AWS::SSM::Parameter` (AWS: ValidationException `Model validation failed (#: extraneous key [SimParityNotAProperty] is not permitted)`); `InvalidRequestException: Value must be a string` (AWS: ValidationException `Model validation failed (#/Value: expected type: String, found: Integer)`); `InvalidRequestException: Tier must be one of Advanced, Intelligent-Tiering, Standard` (AWS: ValidationException with the two-line enum diagnostic above naming #/Tier). The property names, type names and enum values in those messages are per-request/per-schema fill-ins; the surrounding text is the requirement and the emulator's surrounding text is wrong.
Why: a client branches on the error CODE. botocore raises ValidationException for a caller-side schema mistake and InvalidRequestException for a handler refusal; a caller that retries or escalates on handler errors but surfaces schema errors to the user does the wrong thing for every malformed template. Callers (and CloudFormation-style tooling) also parse the `Model validation failed (#/<path>: ...)` body to point at the offending property, and get nothing parseable here.
Fix: the front-door schema-validation step shared by the CreateResource and UpdateResource handlers (services/service-com-amazonaws-cloudcontrol-cloudapiservice/src/ops/create_resource.rs, update_resource.rs, and the validation helper they call) must raise ValidationException and render the JSON-schema violation list in AWS's "Model validation failed (...)" form rather than emitting InvalidRequestException with a bespoke sentence.
Failing checks: cloudcontrol.create-resource-malformed-desired-state-invalid-request, cloudcontrol.desired-state-unknown-property-rejected, cloudcontrol.desired-state-wrong-json-type-rejected, cloudcontrol.desired-state-enum-violation-rejected, cloudcontrol.patch-remove-required-property-rejected

Cause 2 of 5: for AWS::CloudWatch::Alarm the schema type check is not applied at the front door at all — the request is accepted and refused asynchronously by the handler.
AWS: the type mismatch is caught by the same synchronous registry-schema validation as Cause 1, so CreateResource itself raises ValidationException with `Model validation failed (#/Threshold: expected type: Number, found: String)` and no request token is minted. Nothing reaches a ProgressEvent.
Emulator: CreateResource answers 200 with a ProgressEvent, and the request later terminates OperationStatus=FAILED carrying ProgressEvent.ErrorCode="InvalidRequest" (a HandlerErrorCode value, not an exception code), i.e. the refusal happens in the handler plane rather than the front-door plane. This is the same validation gap as Cause 1 but a different fix site: the schema for this resource type is never consulted before the request is enqueued.
Why: the caller gets an accepted request and must poll to discover a mistake AWS reports synchronously; the refusal arrives as a HandlerErrorCode string rather than a raised exception, so `except ValidationException` never fires and the malformed request occupies the request history.
Fix: extend the front-door validation path so the type-schema type check covers every registered resource type (AWS::CloudWatch::Alarm included) and refuses before the request record is created, instead of deferring the check to the handler/materialisation path.
Failing check: cloudcontrol.invalid-schema-property-rejected

Cause 3 of 5: a terminal FAILED ProgressEvent for a downstream-service refusal reports the wrong HandlerErrorCode and a passthrough StatusMessage.
AWS: when the request is schema-valid and the OWNING service refuses it (an AWS::SSM::Parameter whose Value violates its own AllowedPattern — a constraint only SSM knows), Cloud Control does not translate the downstream diagnosis. The request terminates OperationStatus=FAILED with ProgressEvent.ErrorCode = GeneralServiceException (the AWS::SSM::Parameter handler's catch-all for a downstream error it does not map to a specific HandlerErrorCode) and StatusMessage naming only the downstream operation: fixed text `Error occurred during operation '<DownstreamOperation>'.` where <DownstreamOperation> is the API the handler called — `PutParameter` for a Create of AWS::SSM::Parameter. Smithy: ProgressEvent.ErrorCode targets HandlerErrorCode, whose members include both InvalidRequest and GeneralServiceException, so both are serialisable and the choice is the defect.
Emulator: ErrorCode="InvalidRequest" and a StatusMessage carrying the downstream service's own explanation instead of the operation-naming template.
Why: a client that distinguishes "my input was structurally wrong" (InvalidRequest, do not retry, fix the template) from "the owning service refused" (GeneralServiceException) is told the wrong class, and tooling that keys on the `Error occurred during operation '<Op>'.` template cannot attribute the failure to a downstream call.
Fix: the request materialisation/handler-result mapping that sets ProgressEvent.ErrorCode and StatusMessage (src/state.rs and the per-type handler result mapping) must map a downstream-service refusal that has no specific HandlerErrorCode to GeneralServiceException and render the operation-naming StatusMessage template.
Failing check: cloudcontrol.failed-request-progress-event-carries-error-code-and-status-message

Cause 4 of 5: the JSON-identifier ValidationException message is truncated — it ends "and no additional properties." instead of AWS's "and no additional properties can be specified".
AWS: GetResource (and the other Identifier-taking operations) accept Identifier either as the bare primary-identifier string or as a JSON object naming exactly the schema's primary identifier. A JSON identifier that names a non-identifier property, names more than one, or carries extra keys is refused with ValidationException whose message is the fixed template `When specifying the identifier as JSON, you must specify exactly one identifier from [[<primary identifier pointers>]], and no additional properties can be specified`, where the bracketed pointer list is taken from the resource type's primaryIdentifier (e.g. `/properties/QueueUrl` for AWS::SQS::Queue) — the pointer value is the per-type fill-in, the rest is fixed text.
Emulator: the code is right but the message's fixed tail is wrong — it emits `..., and no additional properties.` (trailing period, clause dropped) instead of `..., and no additional properties can be specified`.
Why: the message is part of the contract; a caller or test asserting on AWS's refusal text, or a human reading it, loses the statement of what is actually disallowed.
Fix: the identifier-parsing validation shared by the GetResource/UpdateResource/DeleteResource handlers must emit the full fixed text of that template.
Failing check: cloudcontrol.primary-identifier-accepted-as-json-derived-from-the-registry-schema

Cause 5 of 5: DeleteResource ignores RoleArn and performs the delete with the emulator's own privileges.
AWS: DeleteResource takes an optional RoleArn (Smithy: RoleArn, length 20..2048, pattern ^arn:.+:iam::[0-9]{12}:role/.+$) and performs the resource operation with THAT role's permissions, evaluated per downstream action — an explicit Deny on the single action the handler needs always wins. A role trusted by cloudformation.amazonaws.com that allows ssm:* but explicitly Denies ssm:DeleteParameter on the target parameter cannot delete it: the request terminates OperationStatus=FAILED with ProgressEvent.ErrorCode=GeneralServiceException (the AWS::SSM::Parameter handler's Delete path does not map a downstream AccessDeniedException to a specific HandlerErrorCode, unlike its Create path which maps it to AccessDenied) and StatusMessage `Error occurred during operation 'DeleteParameter'.`; the parameter survives with its Value and Version untouched. The same call WITHOUT RoleArn uses the caller's own session and succeeds.
Emulator: the request terminates OperationStatus=SUCCESS and the parameter is deleted — the RoleArn is accepted and then not evaluated, so the facade forwards with its own privileges. (The companion open issue 20261102T095426Z-cloudcontrol-9-net-new-causes-desiredstate-patchdocument-are.md Cause 7 covers RoleArn on CreateResource and authorization on GetResourceRequestStatus; it does not cover the DeleteResource path, and its replay keys do not include this check.)
Why: this is over-permissiveness on a destructive operation — a caller that scopes Cloud Control to a least-privilege service role, and relies on an explicit Deny to protect a resource, has that resource deleted anyway and is told SUCCESS. Least-privilege and guardrail testing against the emulator passes where real AWS would refuse.
Fix: the DeleteResource handler must assume/evaluate the named RoleArn's policy for the downstream action it is about to perform and, on denial, terminate the request FAILED with the handler's catch-all ErrorCode and the operation-naming StatusMessage, leaving the resource untouched — rather than ignoring RoleArn and deleting with ambient privileges.
Failing check: cloudcontrol.role-arn-service-role-policy-governs-the-downstream-delete

Traces: the failing check ids listed per cause above, collected in trace_ids. Code citations: services/service-com-amazonaws-cloudcontrol-cloudapiservice/src/ops/create_resource.rs, update_resource.rs, delete_resource.rs, get_resource.rs and the request/effect materialisation in src/state.rs.
