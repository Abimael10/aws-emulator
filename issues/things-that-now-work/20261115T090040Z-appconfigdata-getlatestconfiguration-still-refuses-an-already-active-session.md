# AppConfigData GetLatestConfiguration still refuses an already-active session's token after the configuration profile is deleted, instead of answering the no-change 200

> _Note: this issue was identified against the code base at commit `99f9186547f1799cdeb9842b49f33a85d7bdb1e3`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
GetLatestConfiguration

## Description
REOPENS 20261029T190019Z-appconfigdata-getlatestconfiguration-re-resolves-the-configuration-profile-on.md: its fix left the call refused.

One net-new root cause in the bootstrapped appconfigdata data plane, grounded in the replayed behavioral check appconfigdata.profile-deletion-does-not-immediately-break-active-session-token (the only surviving failure in this run; the sibling environment-deletion check is marked OWNED by 20261114T120858Z-appconfig-ssm-an-ssm-parameter-store-backed-configuration.md and is skipped here).

=== Cause 1 of 1: GetLatestConfiguration makes the continued existence of the session's AppConfig control-plane resources a precondition of EVERY poll, so deleting the configuration profile retroactively kills a token that was already minted and already served ===

AWS: GetLatestConfiguration takes exactly one input member. Smithy (services/service-com-amazonaws-appconfigdata-appconfigdata/smithy-model/com-amazonaws-appconfigdata-appconfigdata.json): GET /configuration, success 200, @readonly; input ConfigurationToken (@required, @httpQuery configuration_token, target Token, pattern ^\S{1,8192}$); output Configuration (@httpPayload, sensitive blob), NextPollConfigurationToken (@httpHeader Next-Poll-Configuration-Token), NextPollIntervalInSeconds (@httpHeader Next-Poll-Interval-In-Seconds, default 0), ContentType (@httpHeader Content-Type), VersionLabel (@httpHeader Version-Label); errors BadRequestException 400, InternalServerException 500, ResourceNotFoundException 404, ThrottlingException 429. The only bound the model places on a token is a TIME bound, stated in the ConfigurationToken/NextPollConfigurationToken documentation: the token is valid for up to 24 hours and an expired token yields BadRequestException. Nothing in the model makes a poll conditional on re-resolving the application, environment or configuration profile the session named — resolving that triple is StartConfigurationSession's job, which is where ResourceNotFoundException (with ResourceType / ReferencedBy) belongs. Recorded behavior: with a session already started and already polled once, deleting the victim's hosted configuration version and then its configuration profile through the appconfig control plane leaves the next poll on that session's NextPollConfigurationToken SUCCEEDING — HTTP 200 with an empty Configuration payload (the modeled no-change answer: nothing was redeployed), a fresh Next-Poll-Configuration-Token header and Next-Poll-Interval-In-Seconds. VersionLabel is empty per its own doc ("If the client already has the latest version of the configuration data, this value is empty").

Emulator: the post-deletion poll is REFUSED with error code ResourceNotFoundException, HTTP 404, where the expected answer is HTTP 200 with an empty body. The refusal is now stated as intended design rather than an oversight: services/service-com-amazonaws-appconfigdata-appconfigdata/src/ops/get_latest_configuration.rs module doc (lines 9-14) declares "A session is over LIVE control-plane state, so a triple that store no longer resolves ... is refused with the modelled ResourceNotFoundException for the resource that is gone", and STEP 2 (lines 383-452) calls crate::state::served_configuration(...) on every poll and maps Err(unresolved) straight to ResourceNotFoundException { message, resource_type, referenced_by }, rotating nothing. The STEP 1 session checks (token known, not expired, poll floor satisfied, lines 340-381) have all passed at that point, so the token is live; only the per-poll control-plane re-resolution refuses it. The message is the resolver's fixed per-resource-level not-found sentence (the sibling environment path in this same run produced the fixed text "Environment not found"; the profile path names the configuration-profile level the same way); its variable parts are the identifiers taken from the stored session, never one run's literal ids.

Why: a client that is polling correctly loses its poll chain because of an unrelated control-plane edit. AWS's contract is that a configuration client holds one long-lived poll loop and only has to handle BadRequestException (restart the session) or a no-change 200; here a profile deletion raises a 404 the client has no documented recovery for, and because the refusal rotates no successor token the chain cannot continue even after the resource is recreated. It also inverts the blast radius of a delete: in AWS an in-flight fleet keeps serving its last configuration, in the emulator every poller fails at once. Note the conflict a fixer must resolve deliberately: open issue 20261104T061112Z-appconfig-appconfigdata-keeps-serving-a-deleted-environment-a-pre.md asked for the opposite (an immediate refusal after DeleteEnvironment) and the current code implements that globally; the recorded behavior replayed here says a profile deletion does NOT break an already-active session within the poll window, so the refusal must not be applied to a session that is already bound to a served version.

Fix: the GetLatestConfiguration handler's STEP 2 resource-resolution path and the session state it reads (services/service-com-amazonaws-appconfigdata-appconfigdata/src/ops/get_latest_configuration.rs and crate::state::served_configuration): a token that resolves to a live, unexpired session must be served from what that session was last bound to, answering the no-change 200 (empty Configuration, ContentType, rotated NextPollConfigurationToken, NextPollIntervalInSeconds) when the triple can no longer be re-resolved but the session itself is valid. Keep ResourceNotFoundException on this operation for a session that was never bound to a deployed configuration at all, and keep the triple resolution at StartConfigurationSession.

3. Break exactly one thing on the victim, through the appconfig control plane: delete_hosted_configuration_version(ApplicationId, ConfigurationProfileId, VersionNumber), then delete_configuration_profile(ApplicationId, ConfigurationProfileId).
