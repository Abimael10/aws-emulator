# endusermessaging brand-profile attributes: 8 net-new causes — IMAGE attributeValue blanket-refused instead of S3-URL/exclusivity gates, category and file-type sniffing gates missing, clientToken mismatch accepted, duplicate-name refusal mis-classed, refusal wording re-worded, media download omits Content-Disposition

> _Note: this issue was identified against the code base at commit `5072087506065ecdd0a1040998aef0032fe2a15a`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
CreateBrandProfileAttributes

## Description
The brand-profile-attribute surface of endusermessaging diverges from AWS in eight independent ways: three gates AWS enforces are absent (unsupported `category`, attachment byte sniffing, clientToken parameter mismatch), one gate is enforced too broadly (any `attributeValue` on an IMAGE attribute), one refusal carries the wrong error class, two refusals are re-worded, and the media download endpoint omits a response header. This bundle carries 8 net-new causes; ALL 8 must be closed before the issue is submitted.

Model evidence used throughout (services/service-com-amazonaws-endusermessaging-endusermessaging/smithy-model/com-amazonaws-endusermessaging-endusermessaging.json): CreateBrandProfileAttributes POST /v1/brand-profiles/{brandProfileId}/attributes, output `attributes` required (BrandProfileAttributeOutputList @length 1..10), input `attributes` required @length 1..10, `clientToken` @idempotencyToken @length 1..128 pattern ^[\x21-\x7E]+$; errors ValidationException(400), ConflictException(409), ResourceNotFoundException(404). UpdateBrandProfileAttribute PUT /v1/brand-profiles/{brandProfileId}/attributes/{attributeName}. ListBrandProfileAttributes GET same collection, @paginated(inputToken: nextToken), NextToken doc "Opaque pagination token", @length 1..2048. BrandProfileAttributeInput.attributeName "The name is unique within a brand profile"; attributeType "TEXT stores an inline value. IMAGE and DOCUMENT store binary media that you upload"; attributeValue "The text value for the attribute. This value applies to attributes of type TEXT. For attributes of type IMAGE or DOCUMENT, provide the media through the attachment body instead"; attachmentBody "The binary content for an attribute of type IMAGE or DOCUMENT" @length 1..5242880; category BrandProfileAttributeCategory @length 1..64; ValidationException.message required, fieldList optional.

Cause 1 of 8 — an unsupported `category` value is ACCEPTED on create instead of refused.
AWS: `category` is validated against the service's supported set at runtime. An unsupported value is refused with HTTP 400 ValidationException whose message is "Invalid category '<value>'. Supported values: BUSINESS_IDENTITY, BUSINESS_ADDRESS, BUSINESS_CONTACT, MESSAGING_USE_CASE, OPT_IN_CONSENT, MESSAGE_CONTENT, COMPLIANCE_KEYWORDS, TERMS_AND_POLICY, BRAND_DISPLAY, SUPPORTING_DOCUMENT, OTHER". Fixed text: "Invalid category " + the rejected value in single quotes + ". Supported values: " + the supported list; only the rejected value is taken from the request. The supported list itself is recorded behavior only (the Smithy model only says category is a 1..64 string). The same gate applies on UpdateBrandProfileAttribute, where the value is also case-sensitive (a lowercase form of a supported name, e.g. "business_contact", is refused with the same sentence), and a refused update must leave the stored category unchanged.
Emulator: answers HTTP 200 and creates the attribute, echoing {attributeName, attributeType} with no error at all.
Why: a client that sends a category AWS rejects appears to succeed against the emulator and fails in production; later reads then return a category value AWS can never hold.
Fix: the CreateBrandProfileAttributes handler's input-validation stage (supported-category check), and the same check in the UpdateBrandProfileAttribute handler's validation stage.
Traces: endusermessaging.brand-profile-attribute-category-must-be-a-supported-value.

Cause 2 of 8 — any `attributeValue` on an IMAGE attribute is blanket-refused, so the S3-URL gate and the mutual-exclusion gate are both missing.
AWS: for an IMAGE attribute, `attributeValue` is a legal way to point at media as an s3:// URL. Two distinct refusals exist, each HTTP 400 ValidationException: (a) when BOTH attributeValue and attachmentBody are supplied, message "Only one of attributeValue or attachmentBody can be provided for attribute '<attributeName>'"; (b) when attributeValue is supplied but is not an s3://bucket/key URL, message "attributeValue must be an S3 URL (s3://bucket/key) for IMAGE attribute '<attributeName>'". On UpdateBrandProfileAttribute a non-S3 attributeValue is refused with "Either attributeValue (S3 URL) or attachmentBody must be provided for IMAGE attribute" (no name interpolated), and the refused update must leave mediaContentType/mediaSizeBytes untouched. In each sentence only <attributeName> comes from the request; the rest is fixed text. The s3://-URL affordance is recorded behavior only; the model says only that IMAGE/DOCUMENT media is "provide[d] through the attachment body instead".
Emulator: refuses EVERY IMAGE element that carries attributeValue with the generic envelope "1 validation error detected: Value at 'attributes.1.member.attributeValue' failed to satisfy constraint: Member must not be specified for an attribute of type IMAGE; supply attachmentBody instead" — the same message for the both-supplied case and for the bad-URL case, so neither of AWS's two sentences is ever produced and a valid s3:// URL would be refused too.
Why: a client cannot tell "you supplied both" from "your URL is malformed", and the legitimate s3:// form of an IMAGE attribute is unusable against the emulator.
Fix: the CreateBrandProfileAttributes validation stage — replace the blanket type/member exclusion with the exclusivity check plus an s3://bucket/key format check; mirror the update-side sentence in the UpdateBrandProfileAttribute validation stage.
Traces: endusermessaging.image-attribute-rejects-value-and-attachment-together, endusermessaging.image-attribute-value-must-be-an-s3-url.

Cause 3 of 8 — the "attachmentBody on a TEXT attribute" refusal is re-worded into the generic constraint envelope and loses the attribute name.
AWS: supplying attachmentBody for an element whose attributeType is TEXT is refused with HTTP 400 ValidationException whose message is "attachmentBody cannot be provided for TEXT attribute '<attributeName>'" on CreateBrandProfileAttributes, and "attachmentBody cannot be provided for TEXT attribute" (no name) on UpdateBrandProfileAttribute. Fixed text: "attachmentBody cannot be provided for TEXT attribute", plus, on create, the offending element's attributeName in single quotes taken from the request. The whole batch is atomic: when one element is refused, no element of the batch is created (a subsequent GetBrandProfileAttribute for the valid element must answer ResourceNotFoundException), and a refused update must leave attributeValue and the absence of media unchanged.
Emulator: answers "1 validation error detected: Value at 'attributes.2.member.attachmentBody' failed to satisfy constraint: Member must not be specified for an attribute of type TEXT; supply attributeValue instead" (and 'attributes.1.member.attachmentBody' in the single-element case) — AWS's sentence never appears and the attribute name is absent.
Why: the user is not told which attribute is wrong, and clients matching on AWS's message text do not recognise the refusal.
Fix: the CreateBrandProfileAttributes / UpdateBrandProfileAttribute validation stage — emit the service's sentence for the TEXT/attachment cross-member check instead of the generic constraint-envelope formatter.
Traces: endusermessaging.text-attribute-rejects-attachment-on-create-and-update, endusermessaging.create-brand-profile-attributes-batch-with-one-invalid-member-creates-none.

Cause 4 of 8 — a duplicate attributeName WITHIN one request is answered ConflictException(409) instead of ValidationException(400), and without fieldList.
AWS: a batch whose `attributes` list names the same attributeName twice is malformed input, not a state conflict: HTTP 400 ValidationException, message "Duplicate attribute name: '<attributeName>'", with one fieldList entry whose `path` is the JSONPointer to the offending element ("/attributes/<index>/attributeName", index taken from the request) and whose `message` repeats that sentence. Fixed text: "Duplicate attribute name: " + the duplicated name in single quotes. Neither element may be created. Smithy: ValidationException httpError 400 with fieldList; ConflictException httpError 409.
Emulator: answers HTTP 409 ConflictException with message 'Conflict occurred - Reason="RESOURCE_ALREADY_EXISTS" ResourceType="brand-profile-attribute"' and no fieldList.
Why: 409 is a retry-after-state-change signal, so SDK retry logic and user error handling take the wrong branch, and the client is never told which list element is duplicated.
Fix: the CreateBrandProfileAttributes handler's validation stage — check intra-request uniqueness during validation, before the state-conflict check, and emit the ValidationException with its fieldList.
Traces: endusermessaging.create-brand-profile-attributes-rejects-duplicate-names-within-request.

Cause 5 of 8 — a clientToken replayed with DIFFERENT parameters is accepted instead of refused.
AWS: `clientToken` is the operation's @idempotencyToken. Replaying it with the same body returns the first call's result without creating anything new; replaying it with a different body is refused with HTTP 400 ValidationException whose message is exactly "The idempotency token and parameters presented do not match" (entirely fixed text, no request values), and the mismatched request creates nothing — a following GetBrandProfileAttribute for its attribute must answer ResourceNotFoundException and the original attribute must still appear exactly once in ListBrandProfileAttributes.
Emulator: answers HTTP 200 and creates the differing attribute, echoing it in `attributes`, so the token is not recorded against the request parameters at all.
Why: a client relying on idempotency to make a retry safe silently gets a second, different attribute created; the emulator's state diverges from AWS's for the very flow the token exists to protect.
Fix: the CreateBrandProfileAttributes handler's idempotency stage — persist the token with a fingerprint of the request parameters and compare on replay, in the brand-profile attribute state layer.
Traces: endusermessaging.create-brand-profile-attributes-client-token-replay-and-mismatch.

Cause 6 of 8 — a forged/expired nextToken refusal is re-worded.
AWS: ListBrandProfileAttributes refuses a nextToken the service did not issue with HTTP 400 ValidationException whose message is exactly "Invalid or expired pagination token" — fixed text with no request values interpolated (the token is opaque; Smithy NextToken doc "Opaque pagination token").
Emulator: answers ValidationException with message 'nextToken forged-token is not a pagination token this service issued.' — a different sentence that additionally echoes the submitted token value and ends in a period.
Why: clients and tests that match AWS's message do not recognise the refusal, and echoing the caller's token leaks request content AWS deliberately keeps out of this message.
Fix: the ListBrandProfileAttributes handler's pagination-token decoder — emit the service's fixed sentence. NOTE: open issue 20261115T123417Z-endusermessaging-listbrandprofileattributes-diverges-default-attribute-projection-omits-category.md names a pagination-token re-wording for this operation but is not recorded as owning this check's replay key; close this cause against this check regardless.
Traces: endusermessaging.list-brand-profile-attributes-pages-cover-every-attribute-once.

Cause 7 of 8 — attachment bytes are not sniffed: unsupported content is accepted as IMAGE or DOCUMENT.
AWS: the service inspects the uploaded attachment bytes and refuses content that is not a supported media type with HTTP 400 ValidationException whose message is "Unsupported file type for attribute '<attributeName>'. Allowed: PDF, JPEG, PNG" — fixed text apart from the attribute name, taken from the request — for both attributeType IMAGE and DOCUMENT, and the refused attribute is not created (a following GetBrandProfileAttribute answers ResourceNotFoundException). Supported bytes are accepted and typed from their content (e.g. PDF bytes yield mediaContentType "application/pdf" and mediaSizeBytes equal to the uploaded length). Recorded behavior only: the model constrains attachmentBody by @length 1..5242880 and says nothing about content type.
Emulator: accepts plain-text bytes as an IMAGE attribute with HTTP 200 and even mints a mediaDownloadUrl for them, so no sniffing gate exists.
Why: a client uploading unsupported media succeeds against the emulator and fails in production, and the emulator stores media whose declared type AWS would never have allowed.
Fix: the CreateBrandProfileAttributes handler's media-validation stage (and the same stage used by UpdateBrandProfileAttribute) — sniff the attachment bytes before persisting and refuse unsupported types.
Traces: endusermessaging.media-attachment-rejects-unsupported-file-type.

Cause 8 of 8 — the media download endpoint serves no Content-Disposition header.
AWS: fetching a media attribute's mediaDownloadUrl answers HTTP 200 with the uploaded bytes, Content-Type equal to the sniffed media type, and Content-Disposition 'inline; filename="<attributeName>.<ext>"', where <ext> is the extension for the sniffed type (jpeg/png/pdf) and <attributeName> is the attribute's name from state; "inline; filename=" is fixed text. Recorded behavior only: the download URL is a data-plane endpoint outside the Smithy model.
Emulator: serves the correct bytes and Content-Type but no Content-Disposition header at all (header absent).
Why: a browser or client that relies on the header to name and inline-render the download gets an unnamed octet download instead, so a save/preview flow that works against AWS breaks.
Fix: the brand-profile-attribute media download handler's response serializer (the data-plane route that mediaDownloadUrl points at) — set Content-Disposition from the attribute name and the sniffed type's extension.
Traces: endusermessaging.media-attribute-download-serves-sniffed-type-and-named-file.
