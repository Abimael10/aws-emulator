# application-insights: component onboarding still yields nothing — a tag-filtered resource group resolves to no members, so ListComponents stays empty and every component flow hangs

> _Note: this issue was identified against the code base at commit `316bc8d4d27618b04e0a3739e3ce26f595ac855b`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
ListComponents

## Description
One net-new root cause, grounded in the two surviving failing checks of this service (neither is marked ALREADY FILED, neither is reported OWNED by an open issue in this run's report).

Context on prior art, so this is not read as a re-file: the resolved issue `20261109T180657Z-application-insights-an-application-never-discovers-its-resource.md` (status fixed) claimed to fix exactly this discovery gap, and its second cause (LifeCycle vocabulary) HAS landed — `state.rs` now defines LIFE_CYCLE_NOT_CONFIGURED and `Application::life_cycle` derives CREATING/NOT_CONFIGURED/ACTIVE from the components' `monitor` flag. The discovery cause has NOT: onboarding was implemented, but it resolves a membership that is always empty, which is a different defect from "nothing populates the component map" and is what this issue reports. The failures are hangs on HTTP 200 responses, not refusals, so this is not opened as a REOPENS. The open issue `20261110T060637Z-application-insights-an-ec2-instance-in-the-application.md` describes the EC2/custom-component surface and names the second check in its own trace ids, but the suite does not bind either check to it in this run, so both checks are unowned and are filed here; that issue does not describe the membership-resolution cause below.

Cause 1 of 1: an application created over a TAG_FILTERS_1_0 resource group onboards zero components, because the group membership Application Insights asks Resource Groups for is always empty for a tag query, so ListComponents answers 200 with an empty ApplicationComponentList forever and every component behavior behind it is unreachable.
Failing checks: application-insights.application-lifecycle-activates-on-component-monitoring, application-insights.custom-component-ec2-only-and-exclusive

AWS: ListComponents (Smithy: com.amazonaws.applicationinsights#ListComponents, input ResourceGroupName @required @length 1..256 @pattern ^[a-zA-Z0-9\.\-_]*$, output ApplicationComponentList, HTTP 200, paginated NextToken/MaxResults with MaxResults @range 1..40, errors ValidationException 400 / ResourceNotFoundException 404 / InternalServerException 500) is documented as listing "the auto-grouped, standalone, and custom components of the application". Creating an application over a resource group makes Application Insights ONBOARD every supported resource that group resolves to: each resource not held by a custom component becomes a standalone component whose ComponentName is that resource's own ARN, with Monitor=false until a configuration turns monitoring on. The rule is the requirement — one standalone component per resolved resource, named by its ARN — not any particular ARN: for a group whose TAG_FILTERS_1_0 query selects a tagged S3 bucket and a tagged EC2 instance, the component set is exactly those two resources' ARNs. Once that holds, the behaviors the two checks assert become reachable: DescribeApplication.ApplicationInfo.LifeCycle (Smithy: ApplicationInfo.LifeCycle is an unconstrained string, the model names no value list, so the recorded behavior is the reference) reports NOT_CONFIGURED while every onboarded component is unmonitored and ACTIVE once UpdateComponentConfiguration(Monitor=true) has been applied to one, with no further call; and CreateComponent (Smithy: ResourceGroupName/ComponentName/ResourceList all @required, ComponentName @length 1..128 @pattern ^[\d\w\-_\.+]*$; errors ValidationException 400, ResourceInUseException 400, ResourceNotFoundException 404) refuses a non-EC2 ARN with HTTP 400 ValidationException and message "Only EC2 Instance can be grouped." (recorded behavior only; entirely fixed text, no variable part) and refuses an already-grouped resource with HTTP 400 ValidationException and message "Component <resource-arn> is grouped in another component." where the fixed text is "Component " ... " is grouped in another component." and <resource-arn> is the ARN taken from the request's ResourceList (recorded behavior only).

Emulator: CreateApplication now DOES onboard (services/service-com-amazonaws-applicationinsights-ec2windowsbarleyservice/src/ops/create_application.rs builds `components: crate::state::onboarded_components(&members)`), and it obtains `members` by calling Resource Groups' ListGroupResources over the in-process callback (src/state/resource_groups.rs::group_resources). That call answers 200 with an empty `Resources` list for a tag-filtered group: Resource Groups resolves a stored query through `run_resource_query` -> `ComAmazonawsResourcegroupsArdiState::resources_matching`, which matches only (a) the stored resource GROUPS of the region, by their own group ARNs and stored tags, and (b) ARNs recorded as STATIC memberships by GroupResources — and (b) is skipped entirely whenever the query carries any tag filter, because membership tags are not recorded (`let memberships_can_match = filters.is_empty();`). A tagged S3 bucket or a tagged EC2 instance living in another emulated service is therefore never selected. Net effect, unchanged from the client's point of view: ListComponents answers HTTP 200 with an empty ApplicationComponentList for the life of the application. Both checks poll it (timeout_s=240, interval_s=10) for the bucket ARN, and for the instance ARN in the second, the predicate is never satisfied, and the harness kills each check: "Check timed out after 60.0s". Because the poll never returns, nothing downstream is ever issued: the NOT_CONFIGURED -> ACTIVE transition, UpdateComponentConfiguration/DescribeComponentConfiguration, the EC2-only refusal, the exclusive-ownership refusal, the absorption of an instance's attached EBS volume into DescribeComponent.ResourceList, and the delete-then-regroup cycle are all unverifiable and, on current state, have nothing to operate on.

Why: a client that creates an application and then waits for its components — the documented onboarding sequence, and the only way to reach UpdateComponentConfiguration, DescribeComponent or CreateComponent for a discovered resource — does not get a wrong answer it can detect. It hangs on a 200 with an empty list, forever. Every monitoring-configuration workflow built on Application Insights is then unreachable, and a client that skips the wait and calls CreateComponent directly never sees the EC2-only or already-grouped refusals AWS gives it.

Fix: the membership-resolution seam the application's onboarding depends on — either Application Insights' own group-membership resolution (src/state/resource_groups.rs::group_resources and the onboarding step in CreateApplication's handler, plus the state that keeps an application's component set in step with its group over the application's life, since onboarding is computed once at create time today) or, where it actually bottoms out, Resource Groups' tag-query evaluation (its state's run_resource_query / resources_matching), which must resolve a TAG_FILTERS_1_0 query to the tagged resources of other emulated services rather than only to group ARNs and untagged static memberships. Behind it, CreateComponent's validation (EC2-only, exclusive ownership) and the standalone-component transitions CreateComponent/DeleteComponent owe must hold once components exist.

Traces: application-insights.application-lifecycle-activates-on-component-monitoring, application-insights.custom-component-ec2-only-and-exclusive.
