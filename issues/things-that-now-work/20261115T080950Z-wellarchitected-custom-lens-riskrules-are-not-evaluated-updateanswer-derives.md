# Custom lens riskRules are not evaluated: UpdateAnswer derives Answer$Risk from the count of selected choices, so a `default` rule never yields HIGH

> _Note: this issue was identified against the code base at commit `c49ab90e9518fca4a0d62f5c8e5e4d50d5a70ed9`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Description
This bundle has 1 net-new cause, in service wellarchitected, grounded in 1 failing check of suite simparity-behavioral-aws-v1. The other wellarchitected failure in this run (wellarchitected.disassociate-default-lens-rejected) is marked OWNED by 20261113T122411Z-wellarchitected-disassociatelenses-discards-a-lens-review-s-recorded-answers.md and is deliberately not filed here.

Cause 1 of 1: UpdateAnswer against a CUSTOM (imported) lens ignores the lens document's authored riskRules and derives Answer$Risk from how many of the question's choices are selected, so a selection that matches only the `default` rule is graded MEDIUM where the authored rule says HIGH_RISK.
AWS: Smithy (services/service-com-amazonaws-wellarchitected-wellarchitectedapiservicelambda/smithy-model/com-amazonaws-wellarchitected-wellarchitectedapiservicelambda.json): UpdateAnswer PATCH /workloads/{WorkloadId}/lensReviews/{LensAlias}/answers/{QuestionId}, code 200, output UpdateAnswerOutput{WorkloadId, LensAlias, LensArn, Answer}; Answer$Risk -> Risk enum [UNANSWERED, HIGH, MEDIUM, NONE, NOT_APPLICABLE]; LensAlias @length 1..128 (the full custom-lens ARN for an imported lens). The model does not describe the risk-rule language, so the derivation itself is recorded behavior only: for a lens imported with ImportLens and published with CreateLensVersion, each question's `riskRules` list is evaluated IN ORDER against the set of currently selected choice ids, the first rule whose `condition` holds wins, and the authored `risk` maps to Answer$Risk (NO_RISK -> NONE, MEDIUM_RISK -> MEDIUM, HIGH_RISK -> HIGH); a condition is a boolean expression over the question's own choice ids (`c1 && c2` holds only when both are selected, a bare `c1` holds when that choice is selected), and the reserved condition `default` is the fallback that holds for any selection matching no earlier rule. An empty selection is UNANSWERED before any rule runs. The derived value is then counted into the lens review's RiskCounts, reported identically by GetLensReview and by each ListLensReviews summary.
Emulator: for a question whose authored rules are [{`q_c1 && q_c2` -> NO_RISK}, {`q_c1` -> MEDIUM_RISK}, {`default` -> HIGH_RISK}], selecting only the SECOND choice (`q_c2`) returns 200 with Answer$Risk 'MEDIUM' where the authored `default` rule requires 'HIGH'. The two preceding selections in the same check pass only coincidentally: selecting BOTH choices yields NONE and selecting the FIRST choice alone yields MEDIUM, which is exactly what a choice-count heuristic produces (all choices selected -> NONE, some selected -> MEDIUM, none -> UNANSWERED). Hypothesis: the handler grades a custom-lens answer by comparing the number of selected choices to the question's choice count and never parses or evaluates the `riskRules`/`condition` text stored with the imported lens, so no authored rule — and in particular no `default` fallback — can ever be reached.
Why: Risk is the whole point of a Well-Architected review. A client that imports a lens precisely to author its own risk rules gets answers graded by a rule it did not write: every selection that should fall through to the `default` HIGH_RISK rule is reported one level lower, the workload's high-risk findings disappear from GetLensReview/ListLensReviews RiskCounts and from the workload overview, and any lens whose rules are not shaped like 'all choices = no risk' is silently mis-graded. Risk dashboards and remediation gates built on those counts under-report risk against the emulator and change verdict against real AWS.
Fix: the custom-lens risk-rule evaluation behind the UpdateAnswer handler — parse each question's authored riskRules from the stored imported-lens document, evaluate the conditions in order against the selected-choice set (including the `default` fallback and the `&&` conjunction over choice ids), map the authored risk names to the Risk enum, and feed that value to the answer state the GetAnswer/ListAnswers projection and the lens review's RiskCounts aggregation read. Note the related FIXED issue 20261029T223409Z-wellarchitected-custom-lens-publish-path-empty-selection-risk-derivation.md: its cause 1 (CreateLensVersion 404) no longer refuses the call, so this check now reaches the risk assertions and exposes this distinct defect in the derivation itself; its cause 3 covered only the empty-selection -> UNANSWERED short-circuit, not rule evaluation. Related open issue 20261105T100547Z-wellarchitected-aws-official-lens-question-catalog-content-and-derived.md covers risk derivation for the AWS OFFICIAL lens catalog and explicitly excludes custom-lens authored riskRules, so it does not cover this check.
