# CreateConfiguration refuses KafkaVersions entry '3.8.link' — a version the same service's ListKafkaVersions publishes — so a configuration naming the published catalog cannot be created

> _Note: this issue was identified against the code base at commit `e59c78840a4af6413e0f9ee82bb3caeb7f80d398`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

CreateConfiguration

## Description
REOPENS 20261103T090515Z-kafka-createconfiguration-s-unsupported-kafkaversion-refusal-renders-the-wrong.md: its fix left the call refused. That issue's Cause 2 narrowed CreateConfiguration's accepted Kafka-version set so the refusal's valid-value list would stop advertising '3.8.link'; the narrowing was applied to the ACCEPTANCE GATE as well, and the gate now refuses '3.8.link' outright. The valid-value list and its order (that issue's Cause 1) are correct now — what is wrong is the gate.

ONE root cause, grounded in the 6 failing behavioral checks in trace_ids. None is marked ALREADY FILED or OWNED by the suite report, and no open kafka issue carries their replay keys.

Cause 1 of 1: CreateConfiguration's KafkaVersions admission gate is narrower than the version catalog the same service publishes — it omits the '3.8.link' row — so a CreateConfiguration whose KafkaVersions is the catalog ListKafkaVersions just published is refused 400 BadRequestException. Failing checks: kafka.e2e-cluster-scram-auth-produce-consume-teardown, kafka.scram-secret-disassociation-immediate-auth-revocation, kafka.topic-partition-key-hash-consistent-routing, kafka.topic-partition-key-ordering-preserved, kafka.topic-partition-message-order-preserved, kafka.topic-partition-message-ordering-preserved.

AWS: Smithy kafka#CreateConfiguration (services/service-com-amazonaws-kafka-kafka/smithy-model/com-amazonaws-kafka-kafka.json): POST /v1/configurations, code 200; input Name (@required), ServerProperties (@required, blob), KafkaVersions -> __listOf__string (jsonName 'kafkaVersions'); errors BadRequestException 400, ConflictException 409, ForbiddenException 403, UnauthorizedException 401, TooManyRequestsException 429, InternalServerErrorException 500, ServiceUnavailableException 503. kafka#ListKafkaVersions: GET /v1/kafka-versions -> KafkaVersions of KafkaVersion{Version, Status}, Status enum ACTIVE | DEPRECATED. The model enumerates no concrete versions, so WHICH versions a configuration may name is recorded behavior only. The recorded behavior these checks encode is the contract between the two operations: a configuration may name any version the catalog PUBLISHES, a DEPRECATED row included (a configuration is applied to clusters that still run older versions), so CreateConfiguration with KafkaVersions = every version ListKafkaVersions pages — the '3.8.link' row of that page included — is ACCEPTED and returns 200 with State and LatestRevision.Revision 1. All six checks build their cluster Configuration exactly that way, with the comment 'It lists every catalog version so it stays valid for whichever version the cluster gets', i.e. KafkaVersions = sorted({v['Version'] for v in list_kafka_versions()['KafkaVersions']}), and on the recording that create succeeds. The refusal 'Unsupported KafkaVersion [<v>]. Valid values: [<list>]' is AWS's wording for a version the service genuinely does not take (its fixed text is 'Unsupported KafkaVersion [', '], Valid values: [' and the closing ']'; the variable parts are the rejected entry, verbatim from the request, and the service's own version list) — it is not raised for a version the same service publishes.

Emulator: HTTP 400 BadRequestException, invalidParameter 'kafkaVersions', message 'Unsupported KafkaVersion [3.8.link]. Valid values: [4.2.x.kraft, 4.1.x.kraft, 2.8.2.tiered, 4.0.x.kraft, 2.4.1.1, 3.3.2, 3.5.1, 3.6.0, 3.1.1, 3.2.0, 3.3.1, 3.4.0, 2.1.0, 3.7.x, 3.8.x, 2.6.2, 2.7.1, 2.8.0, 2.6.3, 2.7.2, 2.8.1, 2.5.1, 2.6.0, 2.6.1, 2.7.0, 3.6.0.1, 3.9.x, 2.3.1, 2.4.1, 3.7.x.kraft, 2.2.1, 3.8.x.kraft, 3.9.x.kraft, 1.1.1]' (the rejected entry '3.8.link' comes from the request; the bracketed list is the emulator's configuration offering — the divergence is that the refusal is raised at all, and that its list omits a row the service publishes, not the literal strings). The same emulator's ListKafkaVersions publishes {'version': '3.8.link', 'status': 'DEPRECATED'}, so the catalog a client reads and the gate the next call is admitted on contradict each other: the only '3.8.link' a client can learn about is the one the catalog hands it, and feeding it straight back is refused.

Why: a client builds a cluster Configuration the documented way — enumerate ListKafkaVersions and declare the configuration valid for the versions the service publishes — and is refused 400 with a message naming a version it was just told exists. Because the create is refused the whole dependent flow never starts: SCRAM auth grant/revocation, partition-key routing and per-partition ordering are never exercised at all (six checks abort on this one call, before any cluster, topic or broker connection exists). A client that trims its list to the refusal's valid values then holds a configuration that is silently not declared for the '3.8.link' line, and one that treats the 400 as a bad request of its own retries forever.

Fix: the configuration version offering and the admission gate that reads it in the kafka crate's state module — services/service-com-amazonaws-kafka-kafka/src/state/kafka_versions.rs: KAFKA_VERSIONS_FOR_A_CONFIGURATION (lines 408-443, 34 entries, no '3.8.link') projected by valid_kafka_versions (lines 462-471) and tested by is_configuration_kafka_version (lines 480-482), which src/ops/create_configuration.rs calls at lines 265-278 to raise crate::state::unsupported_kafka_version_message. The configuration gate must admit every version KAFKA_VERSION_CATALOG publishes a row for (line 134 is the '3.8.link' row), so the gate is at least as wide as the published catalog; note the two facts are separable — the refusal's advertised valid-value list is recorded with 34 entries and no '3.8.link' (that is what the earlier fix was grounded in), while the acceptance gate must still take '3.8.link'. Keeping the advertised list and the gate the same object is what makes those two recordings unsatisfiable at once; they need to be separate constants. The handler's ordering and message template need no change.

Traces: all six checks abort with botocore BadRequestException from CreateConfiguration at the configuration-setup helper (_acl_configuration / _acl_enforced_configuration / _scram_public_configuration), before CreateCluster is reached. Related open issue that does NOT cover this cause: 20261102T083811Z-kafka-createconfiguration-s-unsupported-kafkaversions-refusal-message-is-the.md is about the refusal's TEMPLATE for a genuinely bogus version (now emitted correctly) and carries neither of these replay keys; 20261121T113417Z-kafka-createcluster-createclusterv2-refuse-active-kafka-versions-the-service.md is the same family of defect one operation over (the NEW-CLUSTER offering being narrower than the ACTIVE catalog rows) and does not name CreateConfiguration or any check listed here.

## Steps to Reproduce
1. Boot the emulator from this checkout (the kafka service answers).
2. `aws kafka list-kafka-versions` (GET /v1/kafka-versions) and collect every Version it publishes, DEPRECATED rows included. The page contains '3.8.link'.
3. Call CreateConfiguration with that whole list: `aws kafka create-configuration --name cfg-catalog --kafka-versions <all versions from step 2> --server-properties fileb://props` where props is `allow.everyone.if.no.acl.found=false\n` (POST /v1/configurations).
4. Expect HTTP 200 with Arn/Name/State and LatestRevision.Revision 1 — a configuration declared valid for every version the service publishes.
5. Observe instead HTTP 400 BadRequestException, invalidParameter 'kafkaVersions', message 'Unsupported KafkaVersion [3.8.link]. Valid values: [4.2.x.kraft, 4.1.x.kraft, ... 1.1.1]' (34 entries, '3.8.link' absent), and `aws kafka list-configurations` showing no 'cfg-catalog'.
6. Minimal form of the same cause: `aws kafka create-configuration --name cfg-link --kafka-versions 3.8.link --server-properties fileb://props` — refused with the same message, although step 2 published that version.
7. Control: the same create with --kafka-versions 3.9.x succeeds (200, ACTIVE), confirming only the catalog row omitted from the configuration offering is at fault.
8. Re-replay the six checks in trace_ids; each currently stops on this CreateConfiguration call during setup, before any cluster, topic or broker connection exists.
