# eks: 4 net-new root causes — successor-CA distribution, managed-node/pod convergence and the aws-auth ConfigMap mapping never settle, and the API server's Forbidden message names the IAM role instead of the caller's STS assumed-role session

> _Note: this issue was identified against the code base at commit `3e8f9d5a2fb1a000959cd8e747ffa597da57fada`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
CreateCertificateAuthority

## Description
Four distinct root causes in the emulator's EKS service, all grounded in failing behavioral checks that the suite reports as neither ALREADY FILED nor OWNED by an open issue.

=== Cause 1 of 4: a successor certificate authority's distributionStatus never advances, so every CA-rotation check burns its whole budget inside a bounded poll ===
Failing check ids: eks.e2e-certificate-authority-activation-to-teardown, eks.e2e-certificate-authority-issue-activate-disable-delete
  AWS: Smithy (services/service-com-amazonaws-eks-awswesleyfrontend/smithy-model/com-amazonaws-eks-awswesleyfrontend.json): CreateCertificateAuthority returns {update: Update, certificateAuthority: CertificateAuthoritySummary}; CertificateAuthorityDistributionStatus = IN_PROGRESS | COMPLETE | FAILED | DELETING and CertificateAuthoritySigningStatus = NOT_USED | ACTIVATING | IN_USE. The documented rule is that a successor CA can only be activated once its distributionStatus is COMPLETE. On AWS the record therefore SETTLES: an appended successor starts NOT_USED/IN_PROGRESS and progresses to COMPLETE (or terminally FAILED), ActivateCertificateAuthority then returns an Update whose DescribeUpdate status reaches a terminal value (Successful), after which the successor reads IN_USE and the outgoing CA reads NOT_USED. The refusals behind that gate are also fixed text: DeleteCertificateAuthority on the sole IN_USE signer is 409 ResourceInUseException with Message exactly "Cannot delete the active certificate authority. Activate a different CA first." (whole sentence fixed, no variable part), and ActivateCertificateAuthority / DescribeCertificateAuthority on a deleted id are 404 ResourceNotFoundException, the activate one worded "Certificate authority <certificateAuthorityId> is not in the trusted list for cluster <clusterName>" — fixed text with the CA id and cluster name taken from the request.
  Emulator: neither check reaches any assertion. Both are recorded as exactly "Error: Check timed out after 60.0s". Both poll DescribeCertificateAuthority for distributionStatus in (COMPLETE, FAILED) with a BOUNDED window (timeout_s=480, interval_s=15/20) and are explicitly written to tolerate a bounded miss — so the only way they can consume the suite budget is for the field to sit at a non-terminal value for the entire window. Hypothesis: the emulator creates the CA record with distributionStatus IN_PROGRESS (and an associated Update in a non-terminal status) and nothing ever advances either, so the status never becomes COMPLETE and never becomes FAILED.
  Why: a client rotating a cluster CA does create-successor -> wait for COMPLETE -> activate -> delete the retired CA. Against the emulator that client blocks forever on a documented precondition that can never be satisfied, and because no rotation can complete, every post-rotation state (IN_USE successor, NOT_USED retired CA, delete-while-active refusal, 404 on a deleted CA id) is unreachable through the public API.
  Fix: the certificate-authority lifecycle/state machinery of the eks service crate — the CreateCertificateAuthority and ActivateCertificateAuthority handlers and the CA/Update records in the service's state must drive distributionStatus IN_PROGRESS -> COMPLETE and drive the associated Update to a terminal status, flipping the successor's signingStatus to IN_USE and the outgoing CA's to NOT_USED.
  Traces: eks.e2e-certificate-authority-activation-to-teardown, eks.e2e-certificate-authority-issue-activate-disable-delete. Relation to an already-open issue: 20261106T022127Z-eks-a-successor-certificate-authority-never-finishes-distribution.md describes this same cause for a DIFFERENT check (eks.certificate-authority-delete-while-active-blocked) and does not carry either replay key above, so the suite reports both of these unowned; they are filed here and should be re-replayed with that issue's fix.

=== Cause 2 of 4: a managed node group's nodes never become Ready to the cluster's Kubernetes API and a scheduled pod never reaches a terminal phase ===
Failing check ids: eks.eks-delete-cluster-with-a-live-node-is-rejected, eks.eks-managed-nodegroup-node-joins-and-runs-a-targeted-pod, eks.eks-pod-identity-credentials-are-scoped-and-an-unallowed-bucket-is-denied
  AWS: Smithy: CreateNodegroup returns a Nodegroup whose status targets NodegroupStatus (CREATING | ACTIVE | UPDATING | DELETING | CREATE_FAILED | DELETE_FAILED | DEGRADED) and whose resources.autoScalingGroups name the ASG that owns its EC2 instances. Recorded behavior for the data plane: an ACTIVE managed node group's instances register with the cluster as Kubernetes Node objects whose spec.providerID ends in the instance id and whose status.conditions contain {type: Ready, status: "True"}, and a pod admitted to such a node runs and reaches status.phase Succeeded (or Failed). DeleteCluster with a dependent node group is then 409 ResourceInUseException with Message exactly "Cluster has nodegroups attached" (whole sentence fixed text), and the identical DeleteCluster is accepted with cluster.status DELETING once the node group is gone.
  Emulator: all three checks are recorded as exactly "Error: Check timed out after 60.0s" and reach no assertion. Each of them, after the control-plane calls, polls the served Kubernetes API for the node-group state to converge — GET /api/v1/nodes?labelSelector=eks.amazonaws.com/nodegroup=<ng> until the expected number of Ready nodes appears (timeout_s=900, interval_s=15), and GET /api/v1/namespaces/<ns>/pods/<pod> until status.phase is Succeeded or Failed (timeout_s=600). Hypothesis: the node-group's instances never appear as Ready Node objects on the served Kubernetes API (or appear without a Ready=True condition / without a providerID), and an admitted pod never leaves a non-terminal phase, so each poll runs to its own minutes-long deadline and the whole suite budget is consumed before the first assertion. The consequence is that the ResourceInUseException/"Cluster has nodegroups attached" refusal and the nodeSelector placement contract behind that barrier are never evaluated at all.
  Why: a client that creates a managed node group and then waits for its nodes to join, or that runs any pod on them, never makes progress; and the whole class of "a live dependent blocks the delete" behavior is unobservable, so an orchestrator can neither confirm a node joined nor confirm that a destructive call was correctly refused.
  Fix: the node-group lifecycle/state machinery and the served Kubernetes API of the eks service crate — the node-group state must materialize Node objects (providerID matching the ASG's instances, Ready=True condition, declared instance type labels) once the node group is ACTIVE, and the pod lifecycle served on that API must progress an admitted pod to a terminal phase.
  Traces: eks.eks-delete-cluster-with-a-live-node-is-rejected, eks.eks-managed-nodegroup-node-joins-and-runs-a-targeted-pod, eks.eks-pod-identity-credentials-are-scoped-and-an-unallowed-bucket-is-denied. Relation to already-open issues: 20261104T105252Z-eks-2-net-new-root-causes-the-metrics.md ("asynchronous EKS resources never reach a terminal state") and 20261113T151622Z-eks-10-net-new-root-causes-in-the.md (served Kubernetes API) describe neighbouring families, but neither carries these replay keys.

=== Cause 3 of 4: the aws-auth ConfigMap mapping never authorizes the mapped IAM principal at the cluster's Kubernetes API ===
Failing check id: eks.access-entry-takes-precedence-over-the-aws-auth-configmap
  AWS: recorded behavior only (this is the cluster's Kubernetes authentication plane, not a modeled EKS shape). On a cluster whose authenticationMode includes CONFIG_MAP, writing a mapRoles entry into kube-system/aws-auth makes the named IAM principal authenticate as that entry's username and groups, so a principal bound by RBAC to list pods gets 200 on GET /api/v1/namespaces/<ns>/pods?limit=1 within the mapping's propagation window; an EKS access entry for the same principal then TAKES PRECEDENCE, so SelfSubjectReview reports the access entry's username and kubernetesGroups with the ConfigMap's group absent, the pod/configmap read verdicts flip (200/403), and deleting the access entry falls back to the ConfigMap mapping.
  Emulator: the check is recorded as exactly "Error: Check timed out after 60.0s" and reaches no assertion. Its first barrier polls GET /api/v1/namespaces/<ns>/pods?limit=1 as the ConfigMap-mapped principal until it answers 200 (timeout_s=420, interval_s=10). Hypothesis: the served Kubernetes API never honours the aws-auth ConfigMap as an authentication/authorization source, so that read never becomes 200 and the poll runs to its own deadline; everything downstream (the access-entry precedence flip and the fall-back after DeleteAccessEntry) is therefore unreachable.
  Why: aws-auth is still the mapping mechanism for CONFIG_MAP / API_AND_CONFIG_MAP clusters. A client that grants cluster access by editing aws-auth gets no access at all from the emulator, and cannot observe the documented precedence of an access entry over a ConfigMap mapping for the same principal.
  Fix: the authentication/authorization path of the cluster Kubernetes API served by the eks service crate — it must resolve a sigv4/bearer caller through the cluster's aws-auth ConfigMap (mapRoles/mapUsers) as well as through access entries, with access entries winning for the same principalArn.
  Traces: eks.access-entry-takes-precedence-over-the-aws-auth-configmap. Relation to an already-open issue: 20261114T090701Z-eks-3-net-new-root-causes-deleteaccessentry-never.md covers DeleteAccessEntry not revoking authorization at the cluster API, a neighbouring cause on the same plane, but does not carry this check's replay key.

=== Cause 4 of 4: the Kubernetes API server's 403 Forbidden message names the access entry's IAM role ARN instead of the caller's STS assumed-role session ARN ===
Failing check id: eks.eks-view-access-policy-write-is-forbidden-by-the-api-server
  AWS: recorded behavior only for the message's User value; the Smithy model documents AccessEntry.username only as "The name of a user that can authenticate to your cluster". An EKS access entry whose principalArn is an IAM ROLE authenticates the caller under the IAM identity it actually presents, i.e. the STS assumed-role session, so the username the API server sees is of the form arn:aws:sts::<account>:assumed-role/<role-name>/<session-name>, with the account, role name and session name taken from the caller's assumed-role credentials — not the access entry's arn:aws:iam::<account>:role/<role-name>. The refusal itself is a standard Kubernetes Status object: HTTP 403, kind "Status", reason "Forbidden", code 403, details.kind "namespaces", and message of the fixed form '<resource-plural> is forbidden: User "<username>" cannot <verb> resource "<resource-plural>" in API group "<group>" at the cluster scope' — fixed text with the username, verb, resource and API group taken from the request and the authenticated identity.
  Emulator: the status, kind, reason, code and details.kind are all correct, but the message's User names the IAM role ARN rather than the assumed-role session that signed the request: 'namespaces is forbidden: User "arn:aws:iam::<account>:role/<role-name>" cannot create resource "namespaces" in API group "" at the cluster scope', where AWS would name 'arn:aws:sts::<account>:assumed-role/<role-name>/<session-name>'. (The recorded run's concrete account, role name and session name are only the values that filled that template.)
  Why: operators and tooling parse the User in a Forbidden message to identify which identity was refused and to map it back to an access entry or a session; naming the role ARN instead of the assumed-role session loses the session name entirely and does not match the principal any other AWS surface (CloudTrail userIdentity, sts:GetCallerIdentity, IAM policy conditions on aws:userid) reports for the same call, so attribution and any assertion on the refused principal are wrong.
  Fix: the identity-resolution step of the Kubernetes API authentication layer in the eks service crate (and the Forbidden Status serializer that formats the message) — the authenticated username for a role-principal access entry must be derived from the caller's STS assumed-role session, not copied from the access entry's principalArn.
  Traces: eks.eks-view-access-policy-write-is-forbidden-by-the-api-server (assertion at check line 510: "the API server's refusal does not name the calling principal").
