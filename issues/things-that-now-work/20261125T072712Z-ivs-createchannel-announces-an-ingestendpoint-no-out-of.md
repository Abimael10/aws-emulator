# IVS CreateChannel announces an ingestEndpoint no out-of-process client can dial, so the native RTMPS live-stream lifecycle check never reaches a publish

> _Note: this issue was identified against the code base at commit `b3137c600279931069b1d26adce40e89c135708e`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
CreateChannel

## Description
Cause 1 of 1: the contribute (ingest) authority an IVS channel announces in `channel.ingestEndpoint` is not an address a client of this emulator can connect to, so the whole native RTMPS live-broadcast path of the service is unreachable and the check ivs.native-rtmps-live-stream-lifecycle aborts on the very first use of the announced value, before any publish, PutMetadata, StopStream or InsertAdBreak leg is exercised.

Related filed issues, neither of which covers this check: the OPEN issue 20261124T065254Z-ivs-reopens-ivs-channel-rtmps-ingest-remains-undialable-createchannel.md describes the same root cause but carries only ivs.rtmps-ingest-live-stream-lifecycle and ivs.rtmps-ingest-native-protocol-round-trip on its replay key (Issue-Trace-Ids / Issue-Key), so ivs.native-rtmps-live-stream-lifecycle is not owned by it and would be closed unrun; that issue in turn REOPENS the FIXED 20261122T024053Z-ivs-the-channel-rtmps-ingest-data-plane-is.md, whose fix only inserted an `ivs` service label into the announced name and left the address undialable. The two OPEN wire issues 20261124T061238Z-ivs-announced-channel-endpoints-playbackurl-is-rooted-on.md and 20261123T105030Z-ivs-2-net-new-causes-createchannel-announces-loopback.md constrain only the recorded member FORM (hostname, no port) and not reachability.

AWS: Smithy (services/service-com-amazonaws-ivs-amazoninteractivevideoservice/smithy-model/com-amazonaws-ivs-amazoninteractivevideoservice.json, com.amazonaws.ivs, restJson1): CreateChannel — POST /CreateChannel, 200, output {channel: Channel, streamKey: StreamKey}; `Channel$ingestEndpoint` targets `IngestEndpoint`, a plain string with no @length and no @pattern, documented "Channel ingest endpoint, part of the definition of an ingest server, used when you set up streaming software"; `StreamKey$value` is @sensitive and is the secret the encoder authenticates the publish with. GetStream(channelArn required, @length 1..128, @pattern ^arn:aws:ivs:[a-z0-9-]+:[0-9]+:channel/[a-zA-Z0-9-]+$) -> {stream: Stream}, errors ChannelNotBroadcasting @httpError 404, ResourceNotFoundException 404, ValidationException 400. PutMetadata — POST /PutMetadata, 204. StopStream — POST /StopStream, 200. InsertAdBreak(channelArn required; durationSeconds required, @range 1..300) -> {adBreakId @length 12..12 @pattern ^[a-zA-Z0-9]+$}, errors ValidationException 400, ChannelNotBroadcasting 404, ConflictException 409. On AWS an encoder that completes an RTMPS handshake to rtmps://<channel.ingestEndpoint>:443/app/<streamKey.value> makes the channel live, and then: GetStream answers 200 with stream.state == "LIVE"; PutMetadata is accepted (204); StopStream is accepted and GetStream afterwards answers 404 ChannelNotBroadcasting whose message is the fixed text "Channel: " + the request's channelArn + " is not currently online" (the ARN is the only variable part, taken from the request); and InsertAdBreak on a channel with no ad configuration is refused 400 ValidationException with the fixed text "Request member: channelArn failed to satisfy the constraints: valid ad configuration is required to be associated with the channel requested for the ad break with ARN: " followed by the channelArn taken from the request — unconditionally, before ingest, while genuinely LIVE, and after StopStream. The member has no modeled form, so its spelling is free, but it exists only to be DIALED: whatever spelling is chosen must be an authority an out-of-process client of this emulator can actually connect to.

Emulator: CreateChannel answers 200 but announces `ingestEndpoint` as a name in a zone nothing resolves to this process, of the form <12-hex-label>.global-contribute.ivs.<zone> with no port, and the emulator announces no externally reachable RTMP/RTMPS listener for it. The harness refuses the composed URL before ffmpeg is ever started: `simparity.published.PublishedUrlRejected: endpoint_url was given rtmps://<12-hex>.global-contribute.ivs.<zone> (published by the emulator or built by the check): its host is not one of the emulator's own hosts; a customer of the emulator needs rtmps://127.0.0.1:<port>/<resource path>, or rtmps://<own host>:<port>/<path> on a per-resource listener`. Per the checkout, the contribute plane that is supposed to back this name is reachable only in-process (src/state/channel_endpoints.rs documents that the register serves "a connection with a pipe inside this process" and that "a client off this machine could not be served a pipe in this process whatever name it was told"), and the socket the plane actually binds is never announced in the response.

Why: a client that uses IVS the way AWS documents it — CreateChannel, read channel.ingestEndpoint and streamKey.value, point an encoder at rtmps://<ingestEndpoint>:443/app/<streamKey>, poll GetStream until LIVE, PutMetadata, StopStream — cannot get off the ground against this emulator. Ingest, the LIVE stream state, metadata insertion, StopStream and the entire live-path error semantics (400 ValidationException for a missing ad configuration, 404 ChannelNotBroadcasting "Channel: <channelArn> is not currently online") are unobservable, so code that works against AWS fails at the first contribution attempt here.

Fix: the announced-address projection together with the contribute plane it names — `announced_ingest_endpoint` / `contribute_host_in` in services/service-com-amazonaws-ivs-amazoninteractivevideoservice/src/state/channel_endpoints.rs and the plane the crate opens for ingest — must announce an authority this process answers RTMP/RTMPS on for an out-of-process client (one of the emulator's own hosts plus the port the plane bound, or a per-resource listener), the publish must be authenticated by the stream key at the /app/<streamKey> path, and it must drive the state the reads already derive from (a Stream in LIVE, and the unwind on StopStream or publisher exit back to ChannelNotBroadcasting), while the InsertAdBreak ad-configuration precondition stays state-independent in the InsertAdBreak handler's validation.

Traces: ivs.native-rtmps-live-stream-lifecycle (fails at ctx.endpoint_url(ingest_endpoint, scheme='rtmps', aws_port=443) on the value CreateChannel announced). The 12-hex label, the zone and the loopback port in the recorded refusal are one run's values and are not requirements.

## Steps to Reproduce
1. Boot the emulator from this checkout and point an ivs client at its data listener (region us-west-2).
2. CreateChannel(name=<unique>, tags={"sim2real-check": "native-rtmps-live-stream-lifecycle"}) and read channel.arn, channel.ingestEndpoint and streamKey.value from the 200 response.
3. Observe ingestEndpoint is a name of the form <12-hex>.global-contribute.ivs.<zone> with no port: it resolves to nothing outside the emulator process, so no client can dial it. The behavioral harness refuses it outright with PublishedUrlRejected "its host is not one of the emulator's own hosts; a customer of the emulator needs rtmps://127.0.0.1:<port>/<resource path>, or rtmps://<own host>:<port>/<path> on a per-resource listener".
4. Attempt the publish anyway from OUTSIDE the emulator process: ffmpeg -re -f lavfi -i testsrc=size=640x480:rate=15 -f lavfi -i sine=frequency=1000 -pix_fmt yuv420p -profile:v baseline -level 3.0 -r 15 -g 30 -c:v libx264 -preset veryfast -c:a aac -f flv -t 180 "rtmps://<ingestEndpoint>:443/app/<streamKey.value>". Nothing ingests it.
5. Poll GetStream(channelArn=<arn>) every 3 s for 90 s: stream.state never becomes "LIVE" (AWS reports LIVE within seconds of the handshake).
6. Because step 5 never succeeds, the live-path legs are never reached: PutMetadata while LIVE (expected 204), StopStream (expected 200), GetStream afterwards (expected 404 ChannelNotBroadcasting, Message "Channel: <channelArn> is not currently online"), and InsertAdBreak(channelArn, durationSeconds=6) with no ad configuration (expected 400 ValidationException, Message "Request member: channelArn failed to satisfy the constraints: valid ad configuration is required to be associated with the channel requested for the ad break with ARN: <channelArn>") before, during and after the broadcast.
7. Re-run: the hex label, zone and loopback port change and the refusal persists — the per-run values are not the finding, the undialable announced authority is.
8. Replay ivs.native-rtmps-live-stream-lifecycle to confirm a fix.
