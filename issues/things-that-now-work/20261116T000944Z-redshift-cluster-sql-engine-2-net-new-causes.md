# Redshift cluster SQL engine: 2 net-new causes — DATEDIFF's datepart keyword is parsed as a column reference, and enable_case_sensitive_identifier never reaches the engine even after a reboot

> _Note: this issue was identified against the code base at commit `29b314f84650008d56941927651d87480bd97baf`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
ExecuteStatement

## Description
Replay of simparity-behavioral-aws-v1 against the emulated Redshift provisioned-cluster data plane (redshift-data ExecuteStatement/DescribeStatement reaching a cluster created through CreateCluster) produced two failures that no open issue owns. This bundle carries TWO causes, both in the cluster SQL engine behind ExecuteStatement; BOTH must be closed before submitting.

Related but NOT covering them: 20261029T193810Z-redshift-cluster-sql-engine-multi-statement-sql-refused.md (multi-statement Sql, SQLite-shaped error text, pg_user/stv_blocklist, COPY/ENCODE/INTERVAL parsing), 20261114T083409Z-redshift-cluster-sql-engine-3-net-new-causes.md (COPY row/size accounting, MAXERROR) and 20261104T045922Z-redshift-publishes-a-cluster-endpoint-but-serves-no.md (no PostgreSQL wire data plane). Neither the DATEDIFF datepart face nor the enable_case_sensitive_identifier face is named in any of them, and the suite marked neither of these two checks OWNED or ALREADY FILED.

=== Cause 1 of 2: DATEDIFF(<datepart>, a, b) is parsed with its datepart as a column reference, so every date-part aggregate fails ===
AWS: Smithy (com.amazonaws.redshiftdata): ExecuteStatementInput.Sql is a @required StatementString and the model constrains no SQL dialect, and DescribeStatementResponse.Error is only documented as "The error message from the cluster if the SQL statement encountered an error while running" — so this is recorded behavior. Redshift's DATEDIFF takes a bare date-part keyword as its FIRST argument (microsecond/microsecs, second, minute, hour, day, week, month, quarter, year and their documented aliases), not an expression: `SELECT datediff(microsecond, min(ts), max(ts)), datediff(second, min(ts), max(ts)), sum(amt), count(*) FROM <table>` reaches Status FINISHED and returns one row whose first two fields are the integer span between the two instants in those units (the microsecond span of rows written with microsecond precision, and the whole-second span).
Emulator: the statement goes terminal with Status='FAILED' and Error='no such column: <datepart> in <the whole statement> at offset <position of the keyword>' — i.e. the leading date-part keyword is resolved as an identifier/column instead of a date part, so no DATEDIFF call can ever execute. The fixed text here is the emulator's own ("no such column: " + "... at offset N"); the variable parts are the keyword, the submitted SQL and the offset. Real Redshift neither emits that wording nor fails this statement at all.
Why: DATEDIFF is one of the most common Redshift expressions in reporting and ETL SQL. Every client that computes a span server-side gets a terminal FAILED statement with an error text (SQLite-shaped, no 'ERROR:' prefix, no PostgreSQL phrasing) that no Redshift error matcher recognises, and the whole temporal contract this check proves (microsecond fidelity preserved through to the engine's own aggregate) is unobservable. Everything earlier in the same check — TIMESTAMP/TIMESTAMPTZ/DATE/DECIMAL round-trip, Field discriminators, ColumnMetadata scale/tableName/schemaName, DescribeTable defaults — already passes, so this is the single remaining face.
Fix: the cluster SQL engine's expression parser and function layer behind ExecuteStatement — recognise the date-part keyword position of DATEDIFF (and the sibling DATE_DIFF/DATEADD/DATE_PART/EXTRACT forms) as a date part rather than a column reference, and evaluate it over TIMESTAMP/TIMESTAMPTZ/DATE operands at microsecond resolution.
Traces: redshift.data-api-temporal-types-round-trip-and-the-engine-computes-their-span.

=== Cause 2 of 2: enable_case_sensitive_identifier is accepted by the control plane but never reaches the engine, so quoted mixed-case identifiers stay folded after a reboot ===
AWS: recorded behavior only (the redshift Smithy model describes Parameter/ParameterApplyStatus but fixes no engine semantics; ClusterParameterStatus.ParameterApplyStatus is documented with the values in-sync, pending-reboot, applying, invalid-parameter, apply-deferred, apply-error, unknown-error). With `enable_case_sensitive_identifier` set to true in the cluster's parameter group and the cluster rebooted so the group reports in-sync, the engine becomes case-sensitive for delimited identifiers: `CREATE TABLE <t> ("c" INT, "C" INT)` FINISHES, DescribeTable then reports exactly two columns ['c','C'] in declaration order, and `INSERT INTO <t> VALUES (1, 2)` followed by `SELECT "c", "C" FROM <t>` returns (1, 2) from two distinct columns. Before the reboot the same DDL is still refused and `SHOW enable_case_sensitive_identifier` still reports the pre-change value — that pre-reboot half the emulator gets right.
Emulator: after ModifyClusterParameterGroup sets the parameter, the cluster reports the group awaiting a reboot, RebootCluster completes and the group returns to in-sync — but the identical DDL still goes terminal Status='FAILED' with Error='duplicate column name: C'. The engine therefore case-folds delimited identifiers unconditionally: the parameter is stored and reported by the control plane while the data plane ignores it, and the case-sensitive table can never be created. ('duplicate column name: ' is the emulator's own fixed text; the variable part is the column name from the DDL.)
Why: a client that flips enable_case_sensitive_identifier and reboots — the documented procedure for it, and the only one — is told by DescribeClusterParameters and the cluster's ParameterApplyStatus that the change is live, then has every mixed-case DDL and query rejected or silently folded. Schemas migrated from case-sensitive engines cannot be created at all, and the broader contract 'a static parameter takes effect at the reboot and not before' is only half-honoured (withheld before the reboot, still withheld after it), which is indistinguishable to a client from a cluster that never finished rebooting.
Fix: the cluster SQL engine's identifier resolution plus the plumbing from cluster parameter-group state into the engine's session/startup configuration — the engine must read the cluster's effective enable_case_sensitive_identifier at (re)start and preserve the case of delimited identifiers when it is true, so two quoted columns differing only in case are distinct storage; it must keep folding them when it is false.
Traces: redshift.static-parameter-change-needs-a-reboot-before-the-engine-sees-it.

2. Cause 1: execute_statement(Sql="CREATE TABLE t (k INT, ts TIMESTAMP, amt DECIMAL(12,4))"), insert a few rows with microsecond-precision timestamp literals, then execute_statement(Sql="SELECT datediff(microsecond, min(ts), max(ts)), datediff(second, min(ts), max(ts)), sum(amt), count(*) FROM t") and poll describe_statement -> expect FINISHED with the two integer spans; observe FAILED with Error 'no such column: microsecond ... at offset 16'.
3. Cause 2: create a cluster parameter group, associate it with the cluster, modify_cluster_parameter_group(Parameters=[{ParameterName:'enable_case_sensitive_identifier', ParameterValue:'true'}]), confirm the cluster reports the group pending-reboot, reboot_cluster, wait for 'available' and for ParameterApplyStatus 'in-sync'.
4. Then execute_statement(Sql='CREATE TABLE mixed ("c" INT, "C" INT)') -> expect FINISHED, and describe_table(Schema='public', Table='mixed') -> expect ColumnList names ['c','C']; observe the statement FAILED with Error 'duplicate column name: C'. Also check `SHOW enable_case_sensitive_identifier` now reports the new value.
5. Re-replay both check ids in trace_ids to confirm the fix.
