There is no BadRequestException shape in this model at all, so the 400 refusal's wording is recorded behavior only. The recorded response for this step is HTTP 403 with the body {"message": "Forbidden"} — the message is ENTIRELY fixed text with NO variable parts (it names neither the api nor the stage nor the connection), and the error code a restJson1 client resolves is ForbiddenException. The recording's ordering requirement is the point: the callback URL's host and invoke path are what scope the call to a deployment, so a form that addresses no deployed stage is refused BEFORE the ConnectionId is examined and before the connection store is read — which is why this step is 403 and not the 400 "Invalid connectionId: <ConnectionId>" that the same id earns on a properly addressed, deployed stage (steps task#6/task#7/task#10 of this same fixture, which now pass).

Emulator: HTTP 400 with x-amzn-errortype: BadRequestException and the body {"message": "Invalid connectionId: <the request's ConnectionId>"}. Replay detail for the step: "status: expected 403, got 400 / $.message: value_mismatch (expected 'Forbidden', got 'Invalid connectionId: AAAAAAAAAAAAAAA=') / $headers.x-amzn-errortype: shape_mismatch (expected '<shaped-not-asserted>', got 'BadRequestException')". The request therefore reached the operation handler at all: the pre-dispatch endpoint gate did not fire, and the handler's ConnectionId form check answered first. The gate exists and renders the right envelope — src/service/connections_endpoint.rs `forbidden()` builds exactly 403 / ForbiddenException / {"message":"Forbidden"} off the modelled error, and src/service.rs wires it as the `UndeployedEndpoint` seam in `Service::override_operation`, documented as deciding "before dispatch — ahead of the payload gate, the ConnectionId's own form and the connection store alike". What fails is WHICH addressings it recognises: `addresses_nothing` answers false (i.e. "serve it") whenever the invoke-path prefix in front of /@connections/ is empty, whenever no endpoint-authority cell has been installed into the shared state, and whenever the installed apigatewayv2 reading returns anything other than EndpointAuthority::Undeployed. Hypothesis: the callback-URL form this step uses is one of those — a host or an invoke path (for instance one carrying no stage segment, or a custom-domain/base-path or api-id form the authority reading does not resolve to an api+stage) that the reading does not classify as Undeployed — so the request is served as though the endpoint were the api's own deployed invoke endpoint.

Why: a client relying on AWS's behavior uses the status to tell a MISCONFIGURED callback URL from a BAD connection id. 403 ForbiddenException means "you may not invoke this endpoint" — the signal that the endpoint URL, host or stage is wrong, and the one thing that proves the per-stage boundary exists. 400 BadRequestException with "Invalid connectionId: …" blames the caller's connection id instead, so a client whose callback URL points at a stage AWS will not serve is told its ids are malformed: it "fixes" its id computation, discards or re-mints connection ids that were fine, and never discovers the endpoint defect — and then gets 403 in production for every connection on that stage. It also makes the emulator over-permissive in the other direction: any well-formed id sent through such an undeployed/unrecognised addressing is dispatched into the connection store rather than refused, so per-stage isolation is not observable here.

Fix: the @connections endpoint resolution in front of dispatch — `addresses_nothing` in this service's src/service/connections_endpoint.rs, its use from the `UndeployedEndpoint` seam in src/service.rs, and the EndpointAuthority reading apigatewayv2 installs into the shared cell. Decide from the request's own addressing (the endpoint host plus the whole invoke path in front of the modelled binding, including the case where that path carries no stage segment) whether the endpoint serves a DEPLOYED stage of some api, and refuse every other addressing with ForbiddenException — status 403, error code ForbiddenException, body {"message": "Forbidden"} with no variable parts — before any handler, before the ConnectionId form check and before the connection store is consulted. A properly addressed, deployed stage must keep its current answers: 400 BadRequestException "Invalid connectionId: " + the request's ConnectionId for an id that is not a connection identifier, and 410 GoneException for a well-formed id the store does not hold.
