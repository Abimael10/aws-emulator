# ecs: 4 net-new causes — the SSM read of an instance identity document ends Status=Failed, UpdateDaemon on a deleted daemon is mis-classified, ListDaemonDeployments refuses an unresolvable daemonArn, and the deployment circuit breaker never rolls back

> _Note: this issue was identified against the code base at commit `6b20299dda36b610e0eb6266197358af63fda05b`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
UpdateDaemon

## Description
Four independent ECS root causes. Each must be closed before this issue is submitted.

Cause 1 of 4: the AWS-RunShellScript invocation that reads an instance's identity document ends Status='Failed' (or returns no output), so no container instance can be registered.
AWS: recorded behavior only — the recordings launch an EC2 instance with an SSM-capable instance profile, wait for DescribeInstanceInformation PingStatus=Online, then SendCommand(AWS-RunShellScript) curling http://169.254.169.254/latest/dynamic/instance-identity/document and .../signature; GetCommandInvocation ends Status='Success' with both values in StandardOutputContent, well inside each check's budget, and the check then registers the container instance and exercises its ECS subject.
Emulator: GetCommandInvocation ends Status='Failed' for that invocation — "identity-document SSM command did not succeed: 'Failed'" (and once, on a run whose invocation returned nothing usable, "identity document/signature retrieval produced empty output") — so RegisterContainerInstance is never reached and nothing downstream runs. Hypothesis: the command the guest is asked to run cannot read the instance-identity document from the emulator's metadata source, so the shell script exits non-zero and the invocation is reported Failed.
Why: the whole ECS-on-EC2 agent plane is unreachable for a client following AWS's only supported registration path — container-instance attributes (PutAttributes/ListAttributes/DeleteAttributes), DeregisterContainerInstance, DiscoverPollEndpoint, UpdateContainerAgent, SubmitTaskStateChange / SubmitContainerStateChange / SubmitAttachmentStateChanges and ExecuteCommand on an EC2-launched task can never be driven, and the negative case "a malformed identity document is rejected" cannot even be set up.
Fix: the SSM Run Command execution path that runs a shell command inside an emulator-launched instance and the EC2 instance-metadata/identity-document source it reads; downstream, the ECS crate's register_container_instance op must accept the pair that path produces. The open issue 20261107T080429Z-ecs-2-net-new-causes-no-aws-signed.md names these same checks, but under their earlier replay keys (each then ended `Check timed out after 60.0s`); it does not carry the keys these checks fail on now, and the failure has moved from a timeout to an explicit Failed invocation.
Traces: ecs.attribute-put-list-delete-roundtrip, ecs.attributes-put-list-delete-lifecycle, ecs.container-instance-agent-update-rejected-missing-version, ecs.container-instance-deregister-not-found, ecs.container-instance-register-deregister-lifecycle, ecs.delete-attributes-missing-target-rejected, ecs.discover-poll-endpoint-returns-endpoint-for-registered-instance, ecs.execute-command-requires-enabled-flag, ecs.register-container-instance-malformed-identity-document-rejected, ecs.submit-attachment-state-changes-updates-attachment-status, ecs.submit-container-state-change-updates-container-status, ecs.submit-task-state-change-updates-task-status.

Cause 2 of 4: UpdateDaemon against a daemon that has been deleted is refused in the wrong error class.
AWS: recorded behavior — UpdateDaemon naming a daemon that DeleteDaemon has already removed is refused HTTP 400 with error code InvalidParameterException. Smithy: UpdateDaemon (input daemonArn, daemonTaskDefinitionArn, capacityProviderArns all @required) models ClientException, ClusterNotFoundException, DaemonNotActiveException, DaemonNotFoundException, InvalidParameterException, PlatformUnknownException and UnsupportedFeatureException, every one at httpError 400 — the classes are distinct and the code is the requirement.
Emulator: the same call is refused 'DaemonNotActiveException' with the message "Daemon was not ACTIVE." in one check, and 'DaemonNotFoundException' in the other — two different non-AWS classes for one request class.
Why: a client branching on InvalidParameterException to correct the request takes no branch at all, while DaemonNotActiveException reads as "retry when it becomes active" for a daemon that no longer exists, so a cleanup/update loop retries forever instead of stopping.
Fix: the refusal classification in the UpdateDaemon handler (the ECS crate's ops/update_daemon.rs) for a daemon whose record has been deleted. The open 20261114T160322Z-ecs-daemon-deployment-and-revision-reads-misclassify-refusals.md and 20261029T220901Z-ecs-express-gateway-and-daemon-operations-skip-validation.md carry other UpdateDaemon/daemon misclassifications (missing task definition, CreateDaemon) and do not carry these checks' keys.
Traces: ecs.daemon-update-after-delete-rejected, ecs.delete-daemon-with-active-deployment-succeeds.

Cause 3 of 4: ListDaemonDeployments refuses a daemonArn whose cluster segment names no cluster, instead of answering an empty list.
AWS: ListDaemonDeployments is a read whose only required input is daemonArn (Smithy: readonly; input daemonArn @required, status, createdAt, maxResults, nextToken; output daemonDeployments -> DaemonDeploymentSummaryList, nextToken) — the request carries no cluster member at all. For a daemonArn that resolves to nothing, AWS answers HTTP 200 with the modeled list present and empty (daemonDeployments: []); the sibling describes report the unresolvable ARN in failures[] rather than raising.
Emulator: HTTP 400 ClusterNotFoundException with the message "Cluster not found." — a cluster-scoped refusal for an operation that is not cluster-scoped.
Why: a client sweeping daemons across ARNs (some of whose clusters have since been deleted) gets an exception instead of zero rows and cannot finish the sweep; the "nothing to list" state is unrepresentable.
Fix: the cluster-resolution branch of the ListDaemonDeployments handler — resolve daemonArn and serve 200 with an empty daemonDeployments list, reserving the 400 classes for bad input. The open 20261114T160322Z-ecs-daemon-deployment-and-revision-reads-misclassify-refusals.md records the same 400-instead-of-200-empty-list for wire fixture steps but does not carry this check's key.
Traces: ecs.deployment-read-ops-on-missing-cluster-not-found.

Cause 4 of 4: a service deployment that cannot reach steady state is reported SUCCESSFUL — the deployment circuit breaker never requests or performs a rollback.
AWS: with deploymentConfiguration.deploymentCircuitBreaker {enable: true, rollback: true}, a deployment that keeps failing tasks transitions to a failed state and the service is rolled back to the last deployment that completed successfully (Smithy DeploymentCircuitBreaker$rollback: "Determines whether to configure Amazon ECS to roll back the service if a service deployment fails. If rollback is on, when a service deployment fails, the service is rolled back to the last deployment..."). The observable sequence on the serviceDeployment is IN_PROGRESS -> ROLLBACK_REQUESTED/ROLLBACK_IN_PROGRESS -> ROLLBACK_SUCCESSFUL (or ROLLBACK_FAILED); ServiceDeploymentStatus models exactly PENDING, SUCCESSFUL, STOPPED, STOP_REQUESTED, IN_PROGRESS, ROLLBACK_REQUESTED, ROLLBACK_IN_PROGRESS, ROLLBACK_SUCCESSFUL, ROLLBACK_FAILED.
Emulator: the failing deployment ends SUCCESSFUL — observed status history ['IN_PROGRESS', 'SUCCESSFUL'] — so no ROLLBACK_* status is ever published, and the companion check that waits for the rollback to the last good revision never sees a terminal rollback within its budget.
Why: a client that gates a release on the circuit breaker is told a broken rollout succeeded; it neither rolls back nor alerts, and the previous good task definition is never restored.
Fix: the service scheduler's deployment state machine — the circuit-breaker failure counter must fail the deployment and drive the ROLLBACK_* statuses that DescribeServiceDeployments/DescribeServices report. The open 20261110T175605Z-ecs-service-deployments-never-reflect-the-circuit-breaker.md and 20261106T115645Z-ecs-3-net-new-causes-a-cluster-scoped.md describe this behaviour for other checks and do not carry these two keys.
Traces: ecs.service-deployment-circuit-breaker-rollback-ordering, ecs.deployment-circuit-breaker-rolls-back-to-last-good.
