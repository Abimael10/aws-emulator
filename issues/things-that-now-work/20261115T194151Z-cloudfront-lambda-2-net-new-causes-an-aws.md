# cloudfront__lambda: 2 net-new causes — an AWS_IAM Lambda function URL refuses a correctly SigV4-signed invoke with 403 SignatureDoesNotMatch, and the geo-restriction edge check no longer completes

> _Note: this issue was identified against the code base at commit `10a111febd8f52adf7e9e5ffade91e26bd1c009a`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
InvokeFunctionUrl

## Description
TWO net-new root causes; a fixer must close both before submitting. Both of these check ids appear in the Issue-Trace-Ids of the open 20261110T105638Z-cloudfront-lambda-2-net-new-causes-a-lambda.md, but under DIFFERENT failure signatures (PublishedUrlRejected on the published FunctionUrl host, and an assertion on CloudFront-Viewer-Country). The published-URL refusal no longer occurs — the checks now get past function-URL publication and past the edge beats — so what is described below is not covered by that issue's replay keys and is not carried by 20261109T181319Z-cloudfront-lambda-edge-enforcement-over-a-lambda-origin.md or 20261102T102137Z-cloudfront-lambda-a-deployed-distribution-over-a-lambda.md either.

Cause 1 of 2: a Lambda function URL whose AuthType is AWS_IAM refuses a correctly SigV4-signed request with 403 and a signature-mismatch error, so the function is never invoked.
AWS: Smithy (lambda): CreateFunctionUrlConfig.AuthType is a required FunctionUrlAuthType enum, and the operation returns FunctionUrl, the HTTPS endpoint at which the function is invocable (http POST /2021-10-31/functions/{FunctionName}/url). For AuthType AWS_IAM, a request to that URL must be authenticated with AWS Signature Version 4 using the signing name `lambda` and the function's region; AddPermission with Action `lambda:InvokeFunctionUrl` (FunctionUrlAuthType AWS_IAM) grants a principal that right. A request carrying a VALID SigV4 signature from a principal permitted to invoke it is invoked and the function's own response is relayed verbatim — here HTTP 200 with the handler's JSON body (marker, method, query, header_names). Only a request whose computed signature does not match the presented one is refused 403 with the signature-mismatch error whose fixed text is "The request signature we calculated does not match the signature you provided. Check your AWS Secret Access Key and signing method. Consult the service documentation for details."; an unsigned or unauthorized request is refused 403 Forbidden. Recorded behavior: the same credentials sign the edge/control-plane calls in this check successfully, and the signed direct call is expected to succeed.
Emulator: the direct POST to the published FunctionUrl, SigV4-signed with signing name `lambda` and the check's region using the very credentials the emulator accepts on every other call in the run, is answered 403 with body {"message":"The request signature we calculated does not match the signature you provided. Check your AWS Secret Access Key and signing method. Consult the service documentation for details."} instead of 200 and the function's output. Everything before this beat passes: the GET through the distribution reaches the origin and is logged, both POSTs are refused 403 by CloudFront with X-Cache 'Error from cloudfront', and the barrier GET proves the origin is reachable — so the function-URL data plane is serving, it just rejects a valid signature. Hypothesis: the function-URL listener recomputes the canonical request over the host/path it was actually reached on (or over a signing name other than `lambda`) rather than over the signed Host/SigV4 scope the client used, so every signature presented against the published URL mismatches.
Why: a client cannot invoke an AWS_IAM function URL at all. The AuthType AWS_IAM mode of function URLs is unusable, every direct-vs-through-CloudFront differential test is impossible, and the one error class that should mean "your credentials or signing are wrong" is returned for correct signing — so a client debugging its own signer is sent after a non-existent fault.
Fix: the Lambda function-URL data-plane handler's SigV4 verification (the request authentication step that fronts InvokeFunctionUrl), and the publication path that mints FunctionUrl so that the host the signature is verified against is the one the emulator announces and serves.
Traces: cloudfront__lambda.deep-cloudfront-2-cf-edge-enforce-allowed-methods-post-rejected (the failing assertion is on the signed direct POST).

Cause 2 of 2: the geo-restriction edge check no longer completes — it reaches no assertion within the harness budget.
AWS: recorded behavior only: a distribution over a reachable origin with a GeoRestriction blocklist answers every viewer request promptly — a blocked viewer with 403 generated by CloudFront, a permitted viewer from the origin — and the edge forwards the CloudFront-Viewer-Country (ISO 3166-1 alpha-2) header it generates to an origin whose origin request policy includes it. Each individual call in that sequence returns; the check's own polls are bounded.
Emulator: the check produces no verdict at all: "Check timed out after 60.0s". Previously the same check reached and failed its CloudFront-Viewer-Country assertion (viewer country None) within the budget, so a call in the geo-restricted edge path has stopped returning rather than returning a wrong value, and the geo-restriction contract is now wholly unobservable. Hypothesis: a request on the blocklisted-viewer path (or the function-URL origin fetch behind it, the same data plane as Cause 1) hangs instead of being answered.
Why: a client that configures a GeoRestriction blocklist gets a request that never completes instead of a 403 or a 200; a hang has no error code to handle and stalls callers and tests until their own timeouts fire.
Fix: the CloudFront edge data plane's geo-restriction evaluation and its origin-fetch path (the generated CloudFront-Viewer-Country/-Address step and the request pipeline that must answer every viewer request, including a blocked one).
Traces: cloudfront__lambda.deep-cloudfront-2-cf-edge-enforce-geo-restriction-blocklist-blocked.

## Evidence
Cause 1 — cloudfront__lambda.deep-cloudfront-2-cf-edge-enforce-allowed-methods-post-rejected, at the signed direct POST to the published FunctionUrl (AuthType AWS_IAM, signed via SigV4Auth(credentials, "lambda", region)):
  AssertionError: the origin itself accepts POST: expected 200 from the signed direct call, got 403 / '{"message":"The request signature we calculated does not match the signature you provided. Check your AWS Secret Access Key and signing method. Consult the service documentation for details."}'
Expected: HTTP 200 with the function's JSON body (method == "POST", query == the request's own nonce query string, marker == the configured environment marker, and no x-amz-cf-id among the header names). Actual: 403 with the SigV4 signature-mismatch error. Fixed text of that message is the sentence quoted above; it is the correct message only for a genuinely mismatched signature, and it carries no variable parts. The function name, url-id, host:port, marker and nonce are per-run values and are not part of the requirement; the requirement is that a valid SigV4 signature for signing name `lambda` on an AWS_IAM function URL is admitted and the function's response relayed.
All earlier beats in the same check PASSED (edge GET served and logged, POST refused 403 with X-Cache 'Error from cloudfront' on both behaviors, zero POSTs leaked to the origin, barrier GET served), so the refusal is specific to function-URL SigV4 verification.

Cause 2 — cloudfront__lambda.deep-cloudfront-2-cf-edge-enforce-geo-restriction-blocklist-blocked:
  Error: Check timed out after 60.0s
Expected: every viewer request through the geo-restricted distribution is answered (403 generated by CloudFront for a blocklisted viewer, 200 from the origin otherwise) with CloudFront-Viewer-Country present as a two-letter code. Actual: no response/verdict — the run does not reach any assertion.
