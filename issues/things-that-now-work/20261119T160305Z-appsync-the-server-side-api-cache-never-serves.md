# appsync: the server-side API cache never serves a hit — every repeated identical request re-invokes the resolver under FULL_REQUEST_CACHING, OPERATION_LEVEL_CACHING and PER_RESOLVER_CACHING

> _Note: this issue was identified against the code base at commit `f97a2791479cf3e78acbdef1e7d516a9feec11d8`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
CreateApiCache

## Description
One net-new root cause in the emulator's AppSync server-side caching, reached through GraphqlApi$uris.GRAPHQL on APIs whose schema reached SUCCESS, whose UNIT resolvers are wired to an AMAZON_DYNAMODB data source that ADDs 1 to a counter item per invocation, and for which CreateApiCache reported status AVAILABLE with the requested apiCachingBehavior.

Related open issue 20261116T072149Z-appsync-8-net-new-causes-graphql-data-plane.md describes a neighbouring defect (its Cause 1 of 8, 'the API cache never serves a cached response', grounded in appsync.flush-api-cache-clears-cache / appsync.flush-api-cache-immediate-clear), but it does NOT carry the replay keys of the four checks below: those two checks observe only that a value changed between identical calls, whereas these four observe the backing store being mutated again and grade the cache KEY semantics of all three apiCachingBehavior modes, including cachingConfig.cachingKeys scoping and extensions.evictFromApiCache. They must be closed against these replay keys.

Cause 1 of 1: the API cache is control-plane metadata only — no cache entry is ever written or read by the data plane, so every request, identical or not, executes the resolver again.

AWS: Smithy ApiCache$apiCachingBehavior is an enum of FULL_REQUEST_CACHING | PER_RESOLVER_CACHING | OPERATION_LEVEL_CACHING, and ApiCache$ttl is documented 'TTL in seconds for cache entries. Valid values are 1-3,600 seconds'. Smithy CachingConfig carries a required ttl (1-3,600 s) and cachingKeys, documented as 'The caching keys for a resolver that has caching activated. Valid values are entries from the $context.arguments, $context.source, and $context.identity maps'. Once the cache for the API is AVAILABLE, a request whose cache key already has a live entry is answered FROM that entry: the resolver is NOT executed, no data-source call is made, and the stored response is replayed byte for byte (so a stale value is returned even after the backing store has moved on) until the entry's ttl expires, the entry is evicted by extensions.evictFromApiCache, or FlushApiCache drops the cache. The cache key depends on the behavior mode: under FULL_REQUEST_CACHING the whole request is the unit; under OPERATION_LEVEL_CACHING the whole operation response is the unit and the key includes the operation name and the variable values, so two documents that differ only by operation name do not share an entry and the same document with a new variable value misses; under PER_RESOLVER_CACHING only resolvers that declare a cachingConfig are cached and the key is composed of exactly the declared cachingKeys, so changing an argument that is NOT in cachingKeys HITS the existing entry while changing one that IS in cachingKeys misses. Recorded behavior for the counter resolvers: the first call for a key misses and advances the DynamoDB counter by exactly 1; the immediately repeated identical call advances it by 0 and returns the same integer.

Emulator: every call is a miss. With PER_RESOLVER_CACHING and cachingConfig {ttl: 3600, cachingKeys: ['$context.arguments.id']} on Query.counted, two reads for the same id left the counters at (2, 2) instead of (1, 1), and changing only the non-key argument 'noise' advanced the counter 1 -> 2 instead of leaving it at 1. With OPERATION_LEVEL_CACHING and a resolver that declares NO cachingConfig, repeating the identical named operation returned 2 and left the counter at 2 instead of returning 1 with the counter at 1. With FULL_REQUEST_CACHING (ttl 300) a second identical 'query { increment }' returned 2 instead of replaying the cached 1. CreateApiCache/GetApiCache themselves agree with the request (status AVAILABLE, the requested ttl and apiCachingBehavior are echoed), so the divergence is purely that the data plane never consults or populates the cache.

Why: a client that enables caching gets no caching. Every cached read reaches the data source, so cost/latency behavior is wrong, read-after-write semantics are inverted (AWS replays a stale cached response where the emulator always returns fresh state), and any assertion that FlushApiCache or extensions.evictFromApiCache changed something is unfalsifiable because flushed and unflushed behave identically. Resolver-level opt-in, cachingKeys scoping and operation-level key separation are all silently no-ops the client cannot detect from the control plane, which reports the cache as AVAILABLE.

Fix: the GraphQL data-plane request path (the executor's dispatch step, ahead of resolver/data-source invocation) must consult the API's api-cache state, compute the cache key per the cache's apiCachingBehavior — full request, operation name + variables, or the resolver's cachingConfig.cachingKeys — and on a hit replay the stored response without invoking the resolver; on a miss it must store the response under that key with the effective ttl. The same store must be the one FlushApiCache clears and the one extensions.evictFromApiCache removes a single (typeName, fieldName, key-map) entry from, leaving sibling keys intact.

## Evidence
All four failures are HTTP 200 responses with no errors envelope — the divergence is that the backing DynamoDB counter advanced on a call AWS answers from cache.

appsync.per-resolver-caching-keys-scope-cache-entries (PER_RESOLVER_CACHING, cachingConfig {ttl, cachingKeys: ['$context.arguments.id']} on Query.counted, control resolver Query.uncounted with no cachingConfig): expected the counter to stay at its post-miss value when only the non-key argument changes. Actual: AssertionError "noise is NOT in cachingKeys, so changing it must hit the entry written for id='ida-...': expected the counter to stay at 1, got 2" (the id is a per-run generated name; the requirement is the delta of 0).

appsync.deep-appsync-3-appsync-rt-operation-level-cache-separates-operation-names (OPERATION_LEVEL_CACHING, ttl 3600, counting resolver with NO cachingConfig): expected the repeated named operation to return 1 with the counter at 1. Actual: AssertionError "the repeated Alpha must HIT (delta 0): returned 2, counter 2".

appsync.deep-appsync-3-appsync-rt-evict-from-api-cache-spares-sibling-key (PER_RESOLVER_CACHING, ttl 3600, cachingKeys ['$context.arguments.id'], two distinct ids A and B): expected both repeated reads to hit, i.e. counters (A, B) == (1, 1). Actual: AssertionError "the second reads must both HIT (delta 0): counters (A, B) = (2, 2)" — the check never reached its eviction leg because no entry was cached to evict.

appsync.e2e-api-cache-flush-affects-resolver-invocation (FULL_REQUEST_CACHING, ttl 300, GetApiCache confirmed AVAILABLE/ttl=300): expected the second identical 'query { increment }' to replay the cached response. Actual: AssertionError "expected cache hit to replay the exact cached response (1), got 2" — so the post-flush leg, which requires the counter to advance only after FlushApiCache, is unreachable.

## Steps to Reproduce
For each leg: CreateGraphqlApi(authenticationType=API_KEY), StartSchemaCreation with the SDL below and poll GetSchemaCreationStatus to SUCCESS, CreateApiKey, create a PAY_PER_REQUEST DynamoDB table keyed on 'id' and an appsync.amazonaws.com-trusted IAM role allowed dynamodb:UpdateItem on it, CreateDataSource type=AMAZON_DYNAMODB with that role, and create APPSYNC_JS 1.0.0 UNIT resolvers whose request handler is an UpdateItem with update expression 'ADD #v :one' on key 'FIELD:' + ctx.args.id and whose response handler returns ctx.result.value (so every real invocation increments a durable counter and returns the post-increment value). Then CreateApiCache(type=SMALL) with the behavior below, poll GetApiCache to status AVAILABLE, and POST {"query": ...} with header x-api-key to GraphqlApi$uris.GRAPHQL.

1. PER_RESOLVER_CACHING, ttl 3600. SDL 'type Query { counted(id: ID!, noise: String!): Int uncounted(id: ID!): Int }'. CreateResolver Query.counted with cachingConfig {ttl: 3600, cachingKeys: ['$context.arguments.id']}; Query.uncounted with no cachingConfig. Query counted(id: A, noise: N1) -> counter advances 0 -> 1. Query counted(id: A, noise: N2) -> counter must STAY at 1 and the response must equal the first. Query counted(id: B, noise: N1) -> counter must advance 1 -> 2. Query uncounted twice -> the counter must advance on BOTH calls (a resolver without cachingConfig is never cached under this mode).

2. OPERATION_LEVEL_CACHING, ttl 3600. SDL 'type Query { plain(id: ID!): Int }'; one resolver Query.plain with NO cachingConfig (GetResolver must report none). Send 'query Alpha { plain(id: K) }' -> returns 1, counter 1. Send it again -> must return 1 with counter 1. Send 'query Beta { plain(id: K) }' (differs only by operation name) -> must miss, returning 2 with counter 2. Repeat Beta -> must hit its own entry (2, counter 2). Re-send Alpha -> must replay its OWN stale entry, returning 1 while the counter stays at 2. Then 'query Alpha($i: ID!) { plain(id: $i) }' with i=K2 twice (miss then hit) and with i=K3 (miss) -> variable values participate in the key.

3. PER_RESOLVER_CACHING, ttl 3600, plus eviction. SDL adds 'type Mutation { evict(id: ID!): ID ... }' on a NONE data source whose response handler calls extensions.evictFromApiCache('Query', 'counted', { 'context.arguments.id': ctx.args.id }). Read counted(id: A) and counted(id: B) once each (counters 1, 1), read both again -> both must HIT (counters still 1, 1). Then run mutation evict(id: A) -> the next read of A must miss (counter 2) while B still hits (counter 1).

4. FULL_REQUEST_CACHING, ttl 300. SDL 'type Query { increment: Int }' with a single resolver incrementing a fixed 'counter' item. Send 'query { increment }' -> 1. Send the identical query again -> must return 1 (no counter advance). Call FlushApiCache(apiId) -> the next identical query must re-invoke the resolver and return 2.
