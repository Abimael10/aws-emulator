## Operation
DescribeClusterV2

## Description
THREE net-new root causes on the emulated kafka (MSK) surface. Each is grounded in a failing behavioral check the suite lists under `### kafka` that the report marks NEITHER "ALREADY FILED" NOR "OWNED by" any open issue, and each leaves a DIFFERENT data-plane contract unobservable. All three are killed on the harness's bare per-check ceiling (`Error: Check timed out after 60.0s`) with no HTTP status, no AWS error code, no Kafka protocol error and not one assertion evaluated. The emulator owns both halves of what these checks wait on — the CreateClusterV2/CreateTopic lifecycle transitions served by the kafka control plane, and the native broker listener behind every address GetBootstrapBrokers advertises — so the stall is the emulator's, not the runner's.

=== Cause 1 of 3: consumer-group committed offsets across a rebalance are unobservable — the SASL/IAM bring-up never clears ===
AWS: Smithy kafka CreateClusterV2 (POST /api/v2/clusters; output State -> ClusterState) answers CREATING, DescribeClusterV2 (GET /api/v2/clusters/{ClusterArn}; output ClusterInfo -> Cluster; NotFoundException httpError 404) reports ACTIVE within a poll or two at an AWS-sized interval, and GetBootstrapBrokers (GET /v1/clusters/{ClusterArn}/bootstrap-brokers) publishes BootstrapBrokerStringSaslIam (jsonName bootstrapBrokerStringSaslIam). An in-VPC client then completes SASL_SSL / AWS_MSK_IAM on the advertised Serverless listener and is served ApiVersions, SaslHandshake, Metadata, CreateTopics, Produce, Fetch, JoinGroup, OffsetCommit, OffsetFetch and ListOffsets. The contract itself is recorded behavior plus the Apache Kafka protocol: a consumer that reads the first N records of a single-partition topic and commits through them leaves the GROUP COORDINATOR holding next-offset = N (OffsetFetch answers N for that topic:partition); a second consumer joining the SAME group in a fresh session resumes at N — nothing before N is redelivered and nothing after N is lost — and a committed read does not change the log, so ListOffsets still reports the full end offset. The AWS control plane cannot observe any of this; the Smithy model has no member for a committed group offset.
Emulator: `Error: Check timed out after 60.0s`, nothing asserted. The shared bring-up leg (CreateClusterV2 Serverless with Sasl.Iam -> poll DescribeClusterV2 for ACTIVE -> GetBootstrapBrokers.bootstrapBrokerStringSaslIam -> a listener that accepts TCP, completes TLS, and SERVES a Metadata fetch over AWS_MSK_IAM) does not finish inside the budget, so neither consumer session runs.
Why: a client relying on MSK's at-least-once-with-committed-offsets semantics — the single most common consumer pattern — cannot tell whether the emulator persists group offsets at all. An emulator that forgets commits (replay from 0) or that double-delivers across a handover is indistinguishable here from a correct one, so a consumer whose idempotency depends on the broker's committed offset is validated against nothing.
Fix: the cluster-lifecycle timing in the kafka crate's state layer — CREATING -> ACTIVE must be consumable by a first or second AWS-sized poll instead of outlasting a client's whole budget — plus the native broker plane's group coordinator (OffsetCommit/OffsetFetch persistence keyed by group + topic + partition, and resumption from the committed offset on a fresh session) behind the SASL/IAM listener.
Traces: kafka.kafka-consumer-group-offsets-survive-a-rebalance-and-no-record-is-redelivered.

=== Cause 2 of 3: MSK IAM group-scope authorization is unobservable — no GROUP_AUTHORIZATION_FAILED verdict is ever reached ===
AWS: on an IAM-authenticated MSK cluster the broker evaluates the kafka-cluster group resource per ACTION (see the MSK IAM access-control documentation): kafka-cluster:AlterGroup governs JoinGroup/SyncGroup/Heartbeat, kafka-cluster:DescribeGroup governs FindCoordinator and OffsetFetch. Consequently (recorded behavior plus the Apache Kafka protocol, which the Smithy model does not describe): a consumer whose group id IS covered by AlterGroup+DescribeGroup joins, is assigned the partition and reads the produced record back byte-exactly at the offset the producer was told; a consumer whose group id is covered by NEITHER action is REFUSED with Kafka error code 30, GROUP_AUTHORIZATION_FAILED (a protocol constant, not an account-varying value) and reads nothing — under subscribe() refused at JoinGroup, and under assign() still refused, because a consumer's first poll() issues FindCoordinator for its group id unconditionally; a group id covered by DescribeGroup ONLY succeeds under assign() (no JoinGroup fires) but is still refused with error 30 under subscribe(); and a refusal leaves the log untouched, so an independent authorized group still reads the one record and ListOffsets still reports end offset 1.
Emulator: `Error: Check timed out after 60.0s`, nothing asserted — the run dies in the same pre-data-plane bring-up, so neither the positive control, nor either refusal, nor the assign()/subscribe() split is exercised.
Why: an emulator that authorizes every JoinGroup, or one that refuses every JoinGroup, or one that never evaluates the group resource at all, all look identical from here. IAM group scoping is how multi-tenant consumers are isolated on MSK; a policy developed and "validated" against this emulator carries no evidence it denies anything.
Fix: the same bring-up/lifecycle path as Cause 1, and in the native broker plane the authorizer for the kafka-cluster group resource — per-action evaluation of AlterGroup (JoinGroup/SyncGroup/Heartbeat) and DescribeGroup (FindCoordinator/OffsetFetch) against the signing identity, answering Kafka error 30 GROUP_AUTHORIZATION_FAILED on refusal and appending/consuming nothing.
Traces: kafka.msk-iam-group-scope-denies-a-consumer-group-join-while-an-assigned-read-succeeds.

=== Cause 3 of 3: the per-partition FIFO ordering guarantee is unobservable — the SCRAM public-access bring-up never reaches the wire ===
AWS: ListKafkaVersions (GET /v1/kafka-versions) reports the broker version ACTIVE; CreateClusterV2 provisioned with Sasl.Scram plus public access, BatchAssociateScramSecret (POST /v1/clusters/{ClusterArn}/scram-secrets), then CreateTopic (POST /v1/clusters/{ClusterArn}/topics; required PartitionCount -> __integerMin1 and ReplicationFactor -> __integerMin1; output Status -> TopicState) moves CREATING -> ACTIVE, and GetBootstrapBrokers publishes BootstrapBrokerStringPublicSaslScram. The contract is the Apache Kafka per-partition guarantee (recorded behavior; no Smithy member describes it): records produced in sequence by ONE producer to a SINGLE-partition topic are appended in that sequence and consumed back from the earliest offset in exactly that order, with contiguous increasing offsets and no reordering, gap or duplicate.
Emulator: `Error: Check timed out after 60.0s`, nothing asserted. The budget is consumed by the control-plane waiters (cluster ACTIVE, topic ACTIVE) and/or by a SCRAM listener that never serves, so not one record is produced or consumed and the ordering assertion is never evaluated.
Why: ordering is the guarantee partitioned-stream consumers are built on. A faked data plane that returns records set-shuffled, or that merges partitions, passes unnoticed here, and any consumer whose correctness depends on in-order delivery per partition is validated against nothing.
Fix: the cluster/topic lifecycle timing in the kafka crate's state layer (the cluster create span, the topic activation span, and whatever gates the public bootstrap-broker strings behind cluster ACTIVE) plus the native broker plane's per-partition append log behind the advertised SASL/SCRAM listener, which must preserve produce order and contiguous offsets on Fetch.
Traces: kafka.topic-partition-message-ordering-preserved.

Note on what is NOT claimed: the 60.0 s figure is this runner's per-check ceiling, and the checks' own 15/30 s poll intervals and 900/1800 s internal budgets are their own. No literal duration is a requirement — the requirement is that each CREATING -> ACTIVE transition and each advertised endpoint's readiness be observable to a client polling at an AWS-sized interval, as they are on real MSK, and that the three data-plane contracts above then hold.
