# firehose: 3 net-new causes — the TagKey @pattern/@length constraint violation is answered InvalidArgumentException instead of ValidationException (TagDeliveryStream and UntagDeliveryStream), and the conflicting-destination refusal of CreateDeliveryStream is re-worded

> _Note: this issue was identified against the code base at commit `b90e82e778857331b034183013dcc14d9b1758a1`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
TagDeliveryStream

## Description
Three net-new root causes in the firehose control plane, all in how a refusal is coded/worded: two in the constraint validation of the tag-key member of TagDeliveryStream and UntagDeliveryStream, and one in the message CreateDeliveryStream uses when two S3 destination configurations are supplied at once. A fixer must close all three.

Cause 1 of 3: TagDeliveryStream refuses a reserved 'aws:' tag key with the wrong error code and an emulator-authored message.
AWS: Smithy: TagDeliveryStream.Tags targets TagDeliveryStreamInputTagList of com.amazonaws.firehose#Tag, whose required member Key targets com.amazonaws.firehose#TagKey with @length(min:1,max:128) and @pattern "^(?!aws:)[\\p{L}\\p{Z}\\p{N}_.:\\/=+\\-@%]*$". A key beginning with 'aws:' violates that modeled @pattern, so it is a framework constraint violation, refused before the operation's business logic — AWS answers HTTP 400 with error code ValidationException (the generic constraint-violation error, not one of the operation's modeled errors, which are InvalidArgumentException, LimitExceededException, ResourceInUseException and ResourceNotFoundException). The message is AWS's standard constraint-violation template: fixed text "1 validation error detected: Value at '<member path>' failed to satisfy constraint: Member must satisfy regular expression pattern: <the modeled pattern>"; the variable parts are the member path of the offending value (here the list/struct path of the Tags member's key, e.g. 'tags.1.member.key', the index coming from the request) and the pattern quoted from the model. Nothing in the message comes from the tag's value or the stream's name.
Emulator: HTTP 400 with Code 'InvalidArgumentException' and Message "Some tag keys in the request started with 'aws:'. System tags cannot be modified." — a business-logic error code and a sentence that is not AWS's constraint-violation template (it has no validation-error count, no member path and no pattern).
Why: a client that branches on the error code sees a business-logic argument rejection rather than an input-constraint violation, so SDK/caller logic that distinguishes "malformed input, do not retry, fix the request shape" from "the service refused this argument" takes the wrong branch; callers and tests that assert on the standard validation message (member path and pattern) never match, and the emulator accepts as plausible a refusal AWS words entirely differently.
Fix: the firehose request-validation layer for TagDeliveryStream — the modeled @pattern/@length constraints on TagKey must be enforced as the framework ValidationException with AWS's constraint-violation message, ahead of the handler's own 'aws:' check.
Traces: firehose.tag-reserved-aws-prefix-rejected.

Cause 2 of 3: UntagDeliveryStream refuses a reserved 'aws:' tag key with the same wrong code, and with a message that also omits the length clauses AWS emits for this member.
AWS: Smithy: UntagDeliveryStream.TagKeys targets com.amazonaws.firehose#TagKeyList, a list whose member targets TagKey with @length(min:1,max:128) and the same @pattern "^(?!aws:)[\\p{L}\\p{Z}\\p{N}_.:\\/=+\\-@%]*$". A member violating a modeled constraint is refused as HTTP 400 ValidationException. Here the message reports the member's whole constraint set: fixed text "1 validation error detected: Value at '<member path>' failed to satisfy constraint: Member must satisfy constraint: [Member must have length less than or equal to 128, Member must have length greater than or equal to 1, Member must satisfy regular expression pattern: <the modeled pattern>]"; the variable parts are the member path ('tagKeys'), the two length bounds and the pattern, all taken from the model, plus the count of validation errors from the request. The refused call must also leave the stream's existing tags untouched.
Emulator: HTTP 400 with Code 'InvalidArgumentException' and Message "Some tag keys in the request started with 'aws:'. System tags cannot be modified." — same emulator sentence as cause 1, so the two operations are indistinguishable and neither carries the member path or the constraint list.
Why: as in cause 1, the error class is wrong; additionally a client cannot tell which input member was rejected, because the member path AWS names ('tagKeys') is absent, and it is told nothing about the length bounds that the same member also enforces.
Fix: the firehose request-validation layer for UntagDeliveryStream — enforce TagKeyList's member @length and @pattern as a ValidationException carrying AWS's full constraint-set message, before the handler's 'aws:' check.
Traces: firehose.untag-delivery-stream-invalid-tag-key.

Cause 3 of 3: CreateDeliveryStream rejects a request carrying both S3DestinationConfiguration and ExtendedS3DestinationConfiguration with the right error code but the emulator's own wording.
AWS: Smithy: CreateDeliveryStream accepts the (deprecated) S3DestinationConfiguration and ExtendedS3DestinationConfiguration as separate optional members and models InvalidArgumentException ("The specified input parameter has a value that is not valid", client error, HTTP 400) for an argument the service refuses; supplying both is refused with HTTP 400 InvalidArgumentException and the fixed message "Exactly one of S3DestinationConfiguration or ExtendedS3DestinationConfiguration must be specified." That sentence is entirely fixed text — it names the two member names from the model and takes no value from the request — including its terminal period. The refused request must create no stream (DescribeDeliveryStream answers ResourceNotFoundException and the name never appears in ListDeliveryStreams), which the emulator does satisfy.
Emulator: HTTP 400 InvalidArgumentException with Message "Exactly one destination configuration is supported for a Firehose" — different wording, no member names, and no terminal period.
Why: the error code is right, so only the message distinguishes this refusal from every other invalid-argument refusal of CreateDeliveryStream; a client (or an operator reading a log) is not told which two members conflict, and callers and tests that match AWS's sentence do not match. The emulator's sentence also reads as a general "only one destination is supported" limitation rather than the specific either/or between these two members.
Fix: the CreateDeliveryStream handler's destination-configuration validation — the message emitted when more than one of the S3/ExtendedS3 destination members is present.
Traces: firehose.create-stream-conflicting-destination-configs and firehose.create-stream-conflicting-destinations-rejected (both assert the same message).
