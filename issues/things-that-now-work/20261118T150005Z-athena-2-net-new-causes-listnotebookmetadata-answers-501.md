ListNotebookMetadata

## Description
Two net-new root causes on Athena, both reached through the behavioral suite under the report heading `### athena`. Neither failing check is marked ALREADY FILED and neither is marked OWNED, so no filed issue carries their replay keys. This bundle carries 2 causes; BOTH must be closed before submitting.

Cause 1 of 2: ListNotebookMetadata is still a scaffold stub, so the non-Spark-workgroup refusal AWS gives for it never happens.
  AWS: Smithy (services/service-com-amazonaws-athena-amazonathena/smithy-model/com-amazonaws-athena-amazonathena.json) — ListNotebookMetadata input WorkGroup @required (target WorkGroupName, @pattern ^[a-zA-Z0-9._-]{1,128}$), optional Filters (FilterDefinition), MaxResults (MaxNotebooksCount @range 1..50) and NextToken (Token @length 1..1024); output NotebookMetadataList (NotebookMetadataArray) + NextToken; errors InvalidRequestException (client, httpError 400), TooManyRequestsException (400) and InternalServerException (500). The member doc states the WorkGroup is "The name of the Spark enabled workgroup to retrieve notebook metadata for", i.e. the operation only applies to a Spark-enabled workgroup. Recorded behavior: called with a workgroup whose engine is not Spark, ListNotebookMetadata is refused 400 InvalidRequestException with Message "Workgroup EngineVersion is not Spark." — entirely fixed text, with NO variable parts (AWS names neither the workgroup nor the engine version); it is the SAME refusal CreateNotebook gives for that workgroup, which is what the check asserts consistency on. Against a Spark-enabled workgroup (Configuration.EngineVersion.SelectedEngineVersion "PySpark engine version 3" + ExecutionRole) the operation answers 200 and lists the notebooks created in that workgroup.
  Emulator: the handler is an unimplemented scaffold — services/service-com-amazonaws-athena-amazonathena/src/ops/list_notebook_metadata.rs still carries the `SCAFFOLDED, NOT IMPLEMENTED` marker (line 4) and its `handle` returns `Scaffolded::not_implemented("ListNotebookMetadata")`, so every call answers HTTP 501 with Error.Code "NotImplemented" (message "operation ListNotebookMetadata is scaffolded but not implemented in this emulator"), for a non-Spark workgroup and for a Spark workgroup alike. Note the sibling path is now correct: in the same check CreateNotebook against the plain SQL workgroup does refuse 400 InvalidRequestException "Workgroup EngineVersion is not Spark." — only ListNotebookMetadata diverges.
  Why: a client cannot enumerate notebooks at all, and a client that probes a workgroup's type by calling the notebook API sees a 501 server-class failure (NotImplemented) where AWS gives a 400 client-class InvalidRequestException with a discriminating sentence. 501 is retried or escalated as a service outage instead of being handled as "this workgroup is not Spark", and no SDK paginator over NotebookMetadataList can ever advance.
  Fix: implement the ListNotebookMetadata handler (services/service-com-amazonaws-athena-amazonathena/src/ops/list_notebook_metadata.rs) over notebook/workgroup state — refuse a non-Spark workgroup with the fixed InvalidRequestException message through the same workgroup-engine validation CreateNotebook already uses, and otherwise project the workgroup's notebooks (with Filters/MaxResults/NextToken paging) — then delete the SCAFFOLDED marker.
  NOTE for the fixer: no stub issue exists for this operation (the filed athena stub issues cover CreateNotebook, ImportNotebook, ListNotebookSessions, GetNotebookMetadata, CreatePresignedNotebookUrl, not ListNotebookMetadata). The open issue 20261116T225150Z-athena-3-net-new-causes-deletecapacityreservation-s-not.md (Cause 2) carries the message WORDING for CreateNotebook/ListNotebookMetadata under this same check id, but its replay key is the CreateNotebook `assert message == not_spark` line, which now passes; the check now fails one assertion later, on ListNotebookMetadata's code. Closing that issue alone does not make this check pass.
  Traces: athena.create-notebook-on-sql-workgroup-rejected.

Cause 2 of 2: StartCalculationExecution answers 501 NotImplemented on a live IDLE Spark session, so its modeled refusal never happens and the session-unchanged invariant is unobservable.
  AWS: Smithy — StartCalculationExecution input SessionId @required (@length 1..256), CodeBlock (@length 0..68000), Description (@length 1..1024), ClientRequestToken (IdempotencyToken @length 32..128), CalculationConfiguration (deprecated); output CalculationExecutionId (@length 1..36) + State (CalculationExecutionState); errors InvalidRequestException (client, httpError 400), ResourceNotFoundException (client, 400) and InternalServerException (server, 500) — NO 501/NotImplemented is modeled. Recorded behavior: on the Spark engine version that GetResourceDashboard requires, StartCalculationExecution against an IDLE session is refused 400 InvalidRequestException with Message "Not authorized to make this request." — entirely fixed text with no variable parts — and the refusal has no effect: GetSessionStatus still reports State "IDLE" afterwards. The surrounding contract the same check asserts: GetResourceDashboard for a ready session's ARN (arn:aws:athena:<region>:<account>:workgroup/<wg>/session/<sessionId>) answers 200 with an https:// Url, and for a well-formed ARN naming an "s-<id>" session that was never issued it is refused 400 InvalidRequestException "ResourceARN is not found" (fixed text; the ARN is not interpolated).
  Emulator: services/service-com-amazonaws-athena-amazonathena/src/ops/start_calculation_execution.rs is an unimplemented scaffold answering HTTP 501 Error.Code "NotImplemented", so the call is refused with an unmodeled server-class error instead of the modeled 400 InvalidRequestException. The check's error helper reports code 'NotImplemented' where 'InvalidRequestException' is required, and the asserts that follow (session stays IDLE; GetResourceDashboard's not-found refusal) are never reached.
  Why: a client distinguishing "calculations are not permitted on this engine version" (a 400 it must surface to the user and stop) from a transient server fault (a 501/5xx it retries) gets the wrong class, and a Spark notebook driver that submits a calculation to a healthy IDLE session observes an emulator outage rather than the authorization refusal AWS gives.
  Fix: implement the StartCalculationExecution handler (services/service-com-amazonaws-athena-amazonathena/src/ops/start_calculation_execution.rs) over session state so that, on a Spark engine version that does not permit calculations, it returns InvalidRequestException with AWS's fixed message and leaves the session's State untouched.
  NOTE for the fixer: the open stub issue 20261117T053359Z-athena-startcalculationexecution-stub.md names this same handler, but it carries NO check id for this path — this check swallows the 501 inside its ClientError helper, so the suite could not attribute it and marked the check neither ALREADY FILED nor OWNED. One implementation can close both; re-replay the check id listed here as well.
  Traces: athena.get-resource-dashboard-returns-monitoring-url.
