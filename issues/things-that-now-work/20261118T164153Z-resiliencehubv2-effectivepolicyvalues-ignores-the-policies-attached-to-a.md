# resiliencehubv2 effectivePolicyValues ignores the policies attached to a service's associated user journeys

> _Note: this issue was identified against the code base at commit `b8754674c77ef7b2559f37a9d307034c37821ae3`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
GetService

## Description
Behavioral replay of the resiliencehubv2 suite against the emulator built from this checkout found ONE net-new root cause behind three failing checks in the `effective-policy` group. It must be closed before this issue is submitted. It is NOT covered by any open issue: 20261110T225437Z-resiliencehubv2-4-net-new-causes-availabilityslo-target-allowed.md owns the availabilitySlo allowed-set / clientToken / duplicate-name causes, 20261115T181817Z-resiliencehubv2-2-net-new-causes-updateservice-accepts-associations.md owns UpdateService's missing systemArn resolution and the DeleteSystem stub, and 20261111T074347Z-resiliencehubv2-error-bodies-diverge-from-aws-validation-messages.md owns error wording — none concerns the derivation of `effectivePolicyValues`.

=== Cause 1 of 1: a service's effectivePolicyValues is derived ONLY from the service's own policyArn; the policies of the user journeys it is associated with are never consulted, and no per-field strictest merge is performed ===
AWS: Smithy: `Service$effectivePolicyValues` targets `EffectivePolicyValues` ("Contains the effective resilience policy values for a service") with members `availabilitySlo` (SloSource), `multiAzRto`/`multiAzRpo`/`multiRegionRto`/`multiRegionRpo`/`dataRecoveryTimeBetweenBackups` (TargetSource) and `multiAzDrApproach`/`multiRegionDrApproach` (DisasterRecoverySource); each source carries `value`, `policyName` and `source`. `AssociatedSystem` carries `systemArn` plus `userJourneyIds` ("The list of user journey identifiers that associate this system with the service", @length max 20), and `UserJourney` carries its own optional `policyArn`. The model does not state the derivation rule, so that part is recorded behavior only: AWS derives the effective values from BOTH the service's own policy AND the policy of every user journey named in the service's `associatedSystems[].userJourneyIds`, taking for each target field the STRICTEST value across those policies — the HIGHEST availability SLO, the LOWEST RTO and the LOWEST RPO — and reporting under each field the `policyName` of whichever policy supplied the winning value. A field no contributing policy sets stays absent. A service with no own policy still inherits the journey's policy targets, and the association's own `policyArn` member stays absent on the service (the service does not acquire a policy pointer by inheritance). Narrowing the association back to the bare system (`associatedSystems=[{systemArn}]`, no `userJourneyIds`) drops the inherited fields, leaving `effectivePolicyValues` an empty object; pointing the journey at a different policy with UpdateUserJourney changes the service's effective values on the next GetService. Only a service's OWN `policyArn` counts toward a policy's `associatedServiceCount` — inheritance through a journey does not increment it. HTTP status is 200 throughout; no error is involved.
Emulator: `effectivePolicyValues` is derived exclusively from `ServiceRecord.policy_arn`. `state.rs` `service_view()` calls `self.effective_policy_values(record.policy_arn.as_deref(), &record.account_id)`, and `state/policies.rs` `effective_policy_values()` returns `EffectivePolicyValues::default()` whenever `policy_arn` is `None` and otherwise returns `PolicyRecord::effective_policy_values(source)` for that single policy. Nothing reads `record.associated_systems[].user_journey_ids`, resolves those journeys in the systems store, or merges two policies, so: (a) a service with NO own policy associated to a system+journey whose policy sets `availabilitySlo.target` reports `{}` instead of the journey's SLO; (b) a service WITH its own policy reports only its own policy's fields (and only its own policy's name) instead of the per-field strictest merge, so the journey policy's `multiRegionRto`/`multiRegionRpo` are missing entirely and `availabilitySlo`/`multiAzRto` report the laxer own-policy values; (c) UpdateUserJourney repointing a journey at another policy changes nothing a service reads.
Why: `effectivePolicyValues` is the field a client reads to learn which resilience targets a service is actually held to. A client that models targets at the user-journey level (the API's whole reason for `AssociatedSystem$userJourneyIds`) sees NO targets at all, so dashboards, drift checks and gating logic conclude the service is unconstrained and skip the enforcement AWS would have reported; a client that mixes a service policy with a stricter journey policy is told the laxer target is in force and under-provisions against the SLO/RTO/RPO it is actually held to, and attributes the target to the wrong `policyName`.
Fix: the service state's effective-policy derivation — `ComAmazonawsResiliencehubv2NgrhservicecoreState::effective_policy_values` in services/service-com-amazonaws-resiliencehubv2-ngrhservicecore/src/state/policies.rs and its caller `service_view` in src/state.rs — must collect the service's own policy plus the policy of every user journey resolved from `associated_systems[].user_journey_ids` (journeys live in the systems store, under the same lock) and fold them field-by-field, keeping the strictest value and that policy's name; `associated_service_count` must keep counting only own-`policy_arn` references. Every `Service` reader (CreateService/GetService/UpdateService) answers from this one path, so the fix belongs there rather than in a handler.
Traces: resiliencehubv2.system-association-without-journey-carries-no-journey-policy (no own policy: `{}` instead of the journey policy's availabilitySlo); resiliencehubv2.user-journey-policy-change-propagates-to-associated-service (no own policy: `{}`, and the UpdateUserJourney repoint is never reflected); resiliencehubv2.effective-policy-values-take-the-strictest-target-across-service-and-journey-policies (own policy present: only own-policy fields, no merge).
