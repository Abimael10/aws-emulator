# stepfunctions: 2 net-new causes — a JSONata TimeoutSeconds evaluation error is not catchable, and a Pass state's $$ context carries State.RetryCount

> _Note: this issue was identified against the code base at commit `518065cdf1c0387e4dc20c36bae80241fadcbe26`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
StartExecution

## Description
Two independent, net-new root causes in the Step Functions interpreter. Neither is marked owned by the replay report; where an open issue is adjacent it is named in the cause.

Cause 1 of 2: a States.QueryEvaluationError raised while evaluating a Task's JSONata `TimeoutSeconds` field is treated as a fatal fault — a `Catch` on `States.ALL` does not intercept it, so the execution FAILS instead of being handled.
AWS: recorded behavior only for the exact sentence (the Wait/Task field rules are documented at amazon-states-language-wait-state.html / amazon-states-language-task-state.html; Smithy sfn#DescribeExecution output carries `status` (ExecutionStatus enum), `error` (SensitiveError, max 256) and `cause` (SensitiveCause, max 32768)). A JSONata expression in a timing/duration field that evaluates to the wrong JSON type raises error `States.QueryEvaluationError` with cause of the form "An error occurred while executing the state '<StateName>' (entered at the event id #<id>). The JSONata expression '<expression>' specified for the field '<FieldName>' returned an unexpected result type. Expected '<expected>', but was '<actualJsonType>' for value: <renderedValue>" — fixed text is everything outside the angle brackets; `<StateName>`, `<id>`, `<expression>`, `<FieldName>`, `<expected>`, `<actualJsonType>` and `<renderedValue>` come from the definition and the execution's input. Crucially this is an ORDINARY, catchable state error, not a fatal fault: when the state declares Catch [{ErrorEquals:["States.ALL"], Output:{...}, Next:<handler>}], the catcher fires, the handler runs and the execution ends SUCCEEDED with `$states.errorOutput.Error` == "States.QueryEvaluationError". The same error raised on a Wait state's `Seconds`/`Timestamp` with no catcher does fail the execution (the emulator already matches that part, including the cause wording and the EvaluationFailed history event).
Emulator: for a Task with `TimeoutSeconds: "{% $states.input.t %}"` and a States.ALL catcher, the execution ends FAILED with error 'States.QueryEvaluationError' and cause "An error occurred while executing the state 'T' (entered at the event id #2). The JSONata expression '$states.input.t' specified for the field 'TimeoutSeconds' returned an unexpected result type. Expected 'a positive whole number of seconds', but was 'string' for value: \"10\"" — the error name and the cause are right, but the catcher is never consulted, so the declared handler state never runs and no output is produced.
Why: a client that guards a task with Catch/States.ALL (the documented way to handle any task error) cannot handle a mistyped timing expression at all: the whole execution dies where on AWS it continues down the catch branch, so error-handling workflows (compensation, fallbacks, retry ladders keyed on errorOutput) are skipped and the execution's terminal status flips from SUCCEEDED to FAILED.
Fix: the Task state's field-evaluation path, where the JSONata `TimeoutSeconds`/`HeartbeatSeconds` evaluation error is raised — it must be raised as a catchable state error that goes through the state's Retry/Catch matching (like any other States.* task error) rather than aborting the execution. Adjacent but different: open issue 20261116T170218Z-lambda-stepfunctions-a-waitfortasktoken-heartbeat-lapse-ignores-catch covers Catch ORDER for a heartbeat lapse; this cause is a catcher not firing at all for a query-evaluation error.
Traces: stepfunctions.jsonata-wait-field-runtime-type-and-format-errors-are-catchable

Cause 2 of 2: the context object `$$` handed to a non-Task state carries `State.RetryCount` even though that state was never retried, so the `$$` shape has a member AWS does not emit there.
AWS: recorded behavior only (context object documented at input-output-contextobject.html). For a Pass state with Parameters {"ctx.$": "$$"}, the resolved object's top-level keys are exactly Execution, State and StateMachine (no `Task` key outside a Task state); `Execution` carries Id, Name, Input and StartTime; `StateMachine` carries Id and Name; and `State` carries exactly Name and EnteredTime — NO `RetryCount` member, because the state was never retried. The key set is the requirement; the ARNs, names, marker input and timestamps are values from the request and the emulator's state.
Emulator: the execution SUCCEEDS and every other member matches, but `State` additionally carries `RetryCount` with value 0, so `"RetryCount" in $$.State` is true for a state that was never retried.
Why: a client that serializes or diffs `$$` (logging the context, hashing it for idempotency, or asserting on the context shape in tests) sees a member AWS never emits there and a retry count for a state that had no attempts, so context snapshots taken against AWS and against the emulator do not agree.
Fix: the context-object construction for a state — populate `State.RetryCount` only where AWS does (a state being retried), and omit the member otherwise. Note: this is the counterpart of open issue 20261121T033848Z-lambda-stepfunctions-xray-the-execution-context-object-s and cause 5 of open issue 20261121T230141Z-stepfunctions-7-net-new-causes-choice-arguments-runtime, which describe `$$.State.RetryCount` being ABSENT when a definition reads it; a fix must make the member resolvable where AWS resolves it without adding it to the serialized `$$` of a never-retried state, and these should be closed together.
Traces: stepfunctions.pass-context-object-shape-excludes-retry-count-and-task

The JSONata expression \'$states.input.t\' specified for the field \'TimeoutSeconds\' returned an unexpected result type. Expected \'a positive whole number of seconds\', but was \'string\' for value: "10"' — expected status SUCCEEDED with output {"caught": "States.QueryEvaluationError"} produced by the state's Catch [{ErrorEquals:["States.ALL"], Output:{"caught":"{% $states.errorOutput.Error %}"}, Next:"Handled"}]. The earlier assertions of the same check pass: the Wait `Seconds` string case, the Wait `Timestamp` number case and the non-ISO-8601 `Timestamp` case all report the documented error and cause, so only the catchability of the error diverges.

Cause 2: AssertionError: State carried a RetryCount of 0 though 'Ctx' was never retried — for definition {"StartAt":"Ctx","States":{"Ctx":{"Type":"Pass","Parameters":{"ctx.$":"$$"},"End":true}}}, the resolved $$.State was {Name: "Ctx", EnteredTime: "...Z", RetryCount: 0}; expected exactly {Name, EnteredTime}. Execution/StateMachine members and the top-level key set (Execution/State/StateMachine, no Task) matched.
