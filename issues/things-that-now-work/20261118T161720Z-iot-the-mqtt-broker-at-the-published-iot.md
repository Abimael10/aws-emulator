# iot: the MQTT broker at the published iot:Data-ATS endpoint never answers CONNACK, so the whole IoT Commands data plane ($aws/commands/* request/response topics) is unobservable and 4 command-execution checks reach no verdict

> _Note: this issue was identified against the code base at commit `53152f24252eb4c6b050f7ba33da4a3e7b513fd2`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
MQTT CONNECT (iot:Data-ATS data endpoint) / GetCommandExecution / DeleteCommandExecution

## Description
Cause 1 of 1: the MQTT broker behind the address DescribeEndpoint(endpointType='iot:Data-ATS') publishes accepts the TCP/TLS connection from a device holding a registered, ACTIVE certificate but never completes the MQTT CONNECT handshake, so no session is ever established. Because AWS IoT Commands is driven entirely over the reserved MQTT topics $aws/commands/things/{thingName}/executions/{executionId}/request/json and .../response/json, no command execution can ever be delivered to a device or reported back, and every behavior that depends on a genuine terminal-state transition (GetCommandExecution reaching SUCCEEDED, DeleteCommandExecution being permitted once terminal, the post-delete ResourceNotFoundException) is unreachable. Failing checks: iot.command-execution-delete-while-active-rejected, iot.e2e-command-execution-flow, iot.e2e-command-execution-lifecycle-and-cleanup, iot.e2e-command-issue-execute-and-observe-result.

AWS: recorded behavior only for the transport — the iot Smithy model binds only the HTTP control plane and carries no MQTT binding, so the model says nothing about CONNECT. The recordings show AWS IoT Core serving MQTT over TLS on port 8883 at the address DescribeEndpoint(iot:Data-ATS) returns: after the TLS handshake with a client certificate that is registered, ACTIVE and has an attached policy allowing iot:Connect/iot:Subscribe/iot:Receive/iot:Publish, the broker answers CONNACK with return code 0, then serves SUBSCRIBE on the filter $aws/commands/things/{thingName}/executions/+/request/json with a SUBACK, delivers the started execution's request on that topic, and PUBACKs a device PUBLISH of {"status":"SUCCEEDED"} on $aws/commands/things/{thingName}/executions/{executionId}/response/json. The control-plane consequences the recordings pin down are: GetCommandExecution then reports status SUCCEEDED (Smithy: GetCommandExecution output member `status` -> CommandExecutionStatus enum); DeleteCommandExecution on that now-terminal execution returns 200 with an empty body (Smithy: DeleteCommandExecution http DELETE /command-executions/{executionId}, code 200, output shape has no members); and a subsequent GetCommandExecution answers HTTP 404 ResourceNotFoundException (Smithy: GetCommandExecution errors include ResourceNotFoundException, httpError 404) whose message is 'Command execution <executionId> cannot be found.' — fixed text 'Command execution ' + ' cannot be found.' around the executionId taken verbatim from the request's executionId path label. The non-terminal refusal these checks also exercise is ValidationException (Smithy: DeleteCommandExecution errors include ValidationException, httpError 400) with the entirely fixed message 'Failed to delete command execution as it hasn't become terminal.' (no variable parts).

Emulator: the checks resolve the published endpoint, rewrite it onto the host:port the emulator is actually reached on, write the certificate and private key returned by CreateKeysAndCertificate to disk, and connect an MQTT 3.1.1 client (paho) to port 8883 with them. The socket connects — no TLS alert, no RST, no HTTP error — but on_connect never fires and no CONNACK arrives: two checks fail with 'AssertionError: MQTT connect to <host>:<port> timed out (rc=None)' after a 20 s wait (rc stays None, i.e. no CONNACK byte at all), and two fail with 'AssertionError: device never established the MQTT connection to IoT Core' / '... within 15s'. No SUBACK, no request delivery and no PUBACK are therefore observable either. Notably the pure control-plane half of iot.command-execution-delete-while-active-rejected passes first: the emulator does refuse DeleteCommandExecution on a CREATED execution with ValidationException and the exact message above, and leaves it retrievable — only the device-driven terminal transition that follows is blocked.

Why: a client relying on AWS's behavior gets neither a session nor a refusal. Real device code blocks on CONNACK until its own timeout instead of connecting or being told why it cannot, so an IoT Commands fleet cannot be exercised at all against the emulator: a started execution never leaves CREATED/IN_PROGRESS, nothing can drive it to SUCCEEDED/FAILED/REJECTED, DeleteCommandExecution therefore stays permanently refused with the non-terminal ValidationException, and the post-delete ResourceNotFoundException path and its message can never be reached. Application and test code that waits for a command result hangs rather than failing fast.

Fix: the data-plane MQTT listener/broker component serving the address published for iot:Data-ATS — it must complete the MQTT 3.1.1/5 CONNECT exchange (CONNACK, authenticating the presented client certificate against the certificate registry and its attached policies) once TLS finishes, then serve SUBSCRIBE/PUBLISH including the reserved $aws/commands/things/{thingName}/executions/{executionId}/request/json and .../response/json topics, and wire a device-reported status on the response topic into the command-execution state the GetCommandExecution / DeleteCommandExecution handlers read. This is not the iot control-plane operation handlers, whose non-terminal refusal already matches.

Related open issues do NOT cover these four checks: 20261117T200355Z-iot-the-published-iot-data-ats-mqtt-listener.md and 20261117T202147Z-iot-no-mqtt-broker-completes-a-session-at.md describe the same silent listener but carry only the publish/subscribe, wildcard, MQTT5, presence, shadow-delta and fleet-provisioning check keys; 20261109T120740Z-iot-data-the-mqtt-broker-address-published-by.md, 20261109T114414Z-iot-describeendpoint-announces-a-real-amazonaws-com-data.md, 20261110T222008Z-iot-data-no-mqtt-broker-answers-at-the.md and 20261115T062827Z-iot-a-claim-certificate-minted-by-createprovisioningclaim-completes.md concern the published hostname and the mTLS handshake, not the Commands reserved topics. The checks filed here already redirect the published address to the emulator's own host:port and still receive no CONNACK.

Traces: the four failing checks in trace_ids, as examples of this one cause.

## Evidence
Expected (AWS): CONNACK rc=0 on TLS/8883 at the published iot:Data-ATS address for a registered ACTIVE certificate with iot:Connect allowed; SUBACK for $aws/commands/things/{thingName}/executions/+/request/json; the started execution's request delivered on that topic; PUBACK for a device PUBLISH of {"status":"SUCCEEDED"} on $aws/commands/things/{thingName}/executions/{executionId}/response/json; GetCommandExecution then status=SUCCEEDED; DeleteCommandExecution 200 empty body; subsequent GetCommandExecution 404 ResourceNotFoundException, message 'Command execution <executionId> cannot be found.' (fixed text around the request's executionId).

Actual (emulator):
- iot.command-execution-delete-while-active-rejected: check line 102 -> _mqtt_connect line 192: 'AssertionError: MQTT connect to 127.0.0.1:34827 timed out (rc=None)'. The preceding control-plane assertions passed (ValidationException + "Failed to delete command execution as it hasn't become terminal." + execution still retrievable in CREATED/IN_PROGRESS). The host/port are this run's rewritten values, not a requirement.
- iot.e2e-command-issue-execute-and-observe-result: check line 83 -> _mqtt_connect line 196: 'AssertionError: MQTT connect to 127.0.0.1:36125 timed out (rc=None)'.

- iot.e2e-command-execution-lifecycle-and-cleanup: check line 129: 'AssertionError: device never established the MQTT connection to IoT Core within 15s'.

In every case the TCP/TLS connect itself succeeds (no connection or TLS error is reported); only the MQTT CONNACK is missing, so rc is None rather than any return code — the broker neither accepts nor refuses the session.

## Steps to Reproduce
1. Boot the emulator and call iot DescribeEndpoint(endpointType='iot:Data-ATS'); rewrite the returned address onto the host:port the emulator is reached on.
2. CreateThing; CreateKeysAndCertificate(setAsActive=true); CreatePolicy allowing iot:Connect/iot:Subscribe/iot:Receive/iot:Publish on '*'; AttachPolicy to the certificate ARN; AttachThingPrincipal.
3. CreateCommand(commandId=..., namespace='AWS-IoT', payload={content: b'{"action":"noop"}', contentType: 'application/json'}) and StartCommandExecution (iot-jobs-data against the iot:Data-ATS endpoint) for that thing's ARN; note executionId.
4. Confirm the control plane: DeleteCommandExecution(executionId, targetArn) is refused 400 ValidationException 'Failed to delete command execution as it hasn't become terminal.' and GetCommandExecution still returns the execution in CREATED/IN_PROGRESS (this part already matches).
5. Write the certificatePem and keyPair.PrivateKey to disk and connect a paho MQTT 3.1.1 client to <emulator host>:<mapped 8883> with tls_set(certfile=..., keyfile=...), then loop_start().
6. Observe the socket connects but on_connect never fires: no CONNACK within 15-20 s (rc stays None). The device can therefore never SUBSCRIBE to $aws/commands/things/{thingName}/executions/+/request/json nor PUBLISH {"status":"SUCCEEDED"} to .../response/json, so GetCommandExecution never reaches SUCCEEDED, DeleteCommandExecution stays refused, and the 404 ResourceNotFoundException path is never reached.
7. Replay the four checks in trace_ids to confirm.
