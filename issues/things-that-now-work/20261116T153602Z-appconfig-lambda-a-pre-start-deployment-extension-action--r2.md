=== Cause 1 of 1: a PRE_START_DEPLOYMENT extension action is never invoked, so StartDeployment is never gated, a raising target never vetoes it, and the deployment never settles ===
Failing check id: appconfig__lambda.extension-action-point-invokes-lambda-during-deployment.

AWS: Smithy (services/service-com-amazonaws-appconfig-amazonappconfig/smithy-model/com-amazonaws-appconfig-amazonappconfig.json) models CreateExtension — POST /extensions, success 201, @required Actions map (ActionsMap, length 1..5) — CreateExtensionAssociation — POST /extensionassociations, success 201, @required ExtensionIdentifier and ResourceIdentifier, output carrying ResourceArn — and StartDeployment — POST /applications/{ApplicationId}/environments/{EnvironmentId}/deployments, success 201, errors BadRequestException 400 / ConflictException 409 / ResourceNotFoundException 404 / InternalServerException 500, output Deployment carrying State (DeploymentState enum), PercentageComplete, EventLog and AppliedExtensions; GetDeployment — GET .../deployments/{DeploymentNumber}, success 200, same Deployment shape. The action-point event body and the veto message are NOT modelled — recorded behavior: with an extension declaring PRE_START_DEPLOYMENT [{Name, Uri=<function arn>, RoleArn}] and an association bound to the environment ARN arn:aws:appconfig:<region>:<account>:application/<app-id>/environment/<env-id>, StartDeployment synchronously invokes that target BEFORE the deployment record is created, with an event whose Type is 'PreStartDeployment' (PascalCase, against the SCREAMING_SNAKE 'PRE_START_DEPLOYMENT' key used on the request), whose Application.Id / Environment.Id / ConfigurationProfile.Id equal the ids on the request, whose ContentVersion is the request's ConfigurationVersion as a STRING, whose Content base64-encodes the exact candidate configuration bytes, and whose TriggeredBy is 'USER' for a customer-issued StartDeployment. A target that returns normally lets the deployment be created and reach State COMPLETE and the data plane then serves those bytes byte-exactly. A target that raises refuses StartDeployment with error code BadRequestException / HTTP 400 and the message template "Error invoking extension <extensionName>: Unhandled error, Lambda Request ID: <requestId>" — the fixed text is "Error invoking extension " and ": Unhandled error, Lambda Request ID: "; <extensionName> is the associated extension's name from state and <requestId> is the failing invocation's request id, both per-run values that only fill the template — creates NO deployment record (ListDeployments still shows only the earlier deployment) and leaves the previously deployed version in service. Restoring the target and repeating the identical call must then succeed and deliver the previously vetoed version to the data plane.

Emulator: the action point is never dispatched. The check is killed with exactly 'Error: Check timed out after 600.0s' (verdict [mismatch]); no assertion is ever reached, which is itself the finding, because every wait it contains is on something the emulator never produces: the StartDeployment barrier (which retries only on BadRequestException while the invoke role's trust propagates) never gets a deployment started, nothing ever arrives at the SQS observation queue the target forwards its event to, GetDeployment never reports State in (COMPLETE, ROLLED_BACK, REVERTED), and the refusal leg is never reached — so neither the 201 path, nor the event shape, nor the 400 veto, nor the 'no deployment record' invariant is observable. CreateExtension and CreateExtensionAssociation are accepted (VersionNumber 1, Actions and ResourceArn round-trip), so the association exists but is inert. Hypothesis: extension associations are stored as metadata only, with no action-point dispatch in the StartDeployment path (or with a dispatch that never resolves the association bound to the environment ARN).

Why: PRE_START_DEPLOYMENT is the one hook a customer uses to VETO a release. A client relying on AWS's behavior either never gets a release started at all (every StartDeployment poll hangs, as here), or — for an emulator that treats action points as fire-and-forget — has content its gate was written to reject reach the data plane with no refusal. The pre-flight approval, the exact candidate content handed to the approver, the 400 BadRequestException with AWS's wording and the guarantee that a vetoed attempt leaves no deployment record are all unobservable.

Fix: the AppConfig extension action-point dispatch seam called from the StartDeployment handler — resolve the extension associations bound to the target environment's ARN, synchronously invoke each matching action's Uri through its RoleArn with the documented event body (Type, Application, Environment, ConfigurationProfile, ContentVersion as a string, base64 Content, TriggeredBy), and map a target failure onto BadRequestException/400 with AWS's 'Error invoking extension ...' message while creating no deployment record; the deployment state machine must then advance the allowed deployment to a terminal COMPLETE state so GetDeployment settles.

## Steps to Reproduce
Boot the emulator and point appconfig, appconfigdata, lambda, iam and sqs clients at its data listener.

1. Create an SQS queue as the observation sink and an execution role allowing sqs:SendMessage on it; create a python3.12 Lambda whose handler forwards its event to that queue (adding the invocation's aws_request_id as a message attribute) and raises Exception('the extension action refuses this deployment') when its REFUSE env var is '1'.
2. lambda AddPermission for Principal appconfig.amazonaws.com on the function, and create a role appconfig.amazonaws.com can assume that allows lambda:InvokeFunction on the function ARN.
3. CreateExtension(Actions={'PRE_START_DEPLOYMENT': [{'Name':'gate','Uri':<fn-arn>,'RoleArn':<invoke-role-arn>}]}) and assert VersionNumber == 1 and the Uri round-trips.
4. CreateApplication, CreateEnvironment, CreateConfigurationProfile (hosted), then CreateHostedConfigurationVersion twice (versions 1 and 2, distinct bytes).
5. CreateExtensionAssociation(ExtensionIdentifier=<ext-id>, ResourceIdentifier='arn:aws:appconfig:<region>:<account>:application/<app-id>/environment/<env-id>').
6. CreateDeploymentStrategy(DeploymentDurationInMinutes=1, GrowthFactor=100, GrowthType='LINEAR', FinalBakeTimeInMinutes=0, ReplicateTo='NONE') — deliberately non-instant.
7. With REFUSE='0', StartDeployment for ConfigurationVersion '1'. EXPECTED: HTTP 201; one message on the observation queue whose body has Type 'PreStartDeployment', Application.Id/Environment.Id/ConfigurationProfile.Id equal to the request's ids, ContentVersion '1', Content base64-decoding to version 1's exact bytes and TriggeredBy 'USER'; GetDeployment reaching State COMPLETE; appconfigdata serving version 1's bytes byte-exactly. OBSERVED: nothing is enqueued and the deployment never settles — the sequence hangs until the harness kills it at 600 s.
8. Set REFUSE='1' (UpdateFunctionConfiguration, wait function_updated_v2) and StartDeployment for ConfigurationVersion '2'. EXPECTED: BadRequestException / HTTP 400 with Message 'Error invoking extension <extensionName>: Unhandled error, Lambda Request ID: <requestId>' (the request id being that of the invocation that just raised, visible as the queued message's RequestId attribute), the event for version 2 still delivered to the queue, ListDeployments still containing only the DeploymentNumber from step 7, and the data plane still serving version 1.
9. Restore REFUSE='0' and repeat the identical StartDeployment for version 2. EXPECTED: it is accepted, the action point is invoked again with ContentVersion '2', the deployment reaches COMPLETE and version 2's bytes reach the data plane.
