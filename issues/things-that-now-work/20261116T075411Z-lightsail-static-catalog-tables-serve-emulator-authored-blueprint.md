# Lightsail static catalog tables serve emulator-authored blueprint text, non-AWS catalog URLs, wrong Windows bundle prices and truncated row sets

> _Note: this issue was identified against the code base at commit `80627b993989a6360dca12b5c85f35436a07e2ec`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
GetBlueprints

## Description
THREE net-new root causes, all in the read-only static catalog tables behind Lightsail's catalog readers (GetBlueprints and GetBundles). Every affected step answers HTTP 200 with a correctly shaped, well-formed envelope, so no status or error-code divergence is involved: the fault is entirely in the CONTENTS and the ROW SET of the seeded tables. All three causes must be closed before submitting.

Cause 1 of 3: GetBlueprints serves emulator-authored description prose and non-AWS product/licence URLs on the rows it does serve, and stops short of the full catalog.
AWS: Smithy com.amazonaws.lightsail#GetBlueprints is an awsJson RPC operation (POST /ls/api/2016-11-28/GetBlueprints, success code 200, httpBindingsInert) whose output member `blueprints` is a BlueprintList of com.amazonaws.lightsail#Blueprint (members blueprintId, name, group, type, description, isActive, minPower, version, versionCode, productUrl, licenseUrl, platform, appCategory). The model documents the members but fixes no values, so the table's contents are RECORDED BEHAVIOR ONLY. The recording shows AWS serving, for every row, its own full marketplace description paragraph for that image, a `productUrl` under the AWS marketplace host (aws.amazon.com/marketplace/pp/<prodview-id>) and a `licenseUrl` under the AWS EULA host (d7umqicpi7263.cloudfront.net/eula/product/<id>/<id>.txt), and a complete catalog of 39 rows. The requirement is that these columns carry AWS's catalog text and AWS-hosted links for whichever rows the catalog generation contains; the particular paragraphs, prodview ids and EULA ids quoted below are the recording filling that template and are not themselves requirements.
Emulator: blueprintId, name, group, type, isActive, minPower, version and versionCode now match on the rows that are served, but `description` is emulator-authored prose that differs from AWS's paragraph for the same image, and `productUrl`/`licenseUrl` are reported by replay as verdict host_not_own across nearly the whole table (rows 1-32), i.e. they point at hosts other than the AWS marketplace/EULA hosts AWS serves. The emulator also serves a short list: the last six asserted positions ($.blueprints[33] .. $.blueprints[38]) are absent entirely, so the catalog ends early.
Why: a client that renders a blueprint description to a user, matches on it, or follows the product/licence link to present terms gets emulator prose and a link to a host AWS never returns; and a blueprint that is not listed cannot be selected at all, so any workflow that creates an instance from an omitted tier cannot be driven against the emulator. Because blueprintId and name are correct, the listing looks right and the divergence only surfaces downstream.
Fix: the static instance-blueprint catalog table seeding the GetBlueprints handler in the lightsail crate - the description, productUrl and licenseUrl columns on all rows, plus the omitted tail rows. Not handler, validation or serializer logic: the status, member set and envelope are already correct.
Traces: lightsail-catalog-get-blueprints#task#1 (divergence_key service=lightsail|GetBlueprints|status=200->200 over $.blueprints[0]..$.blueprints[38] and their per-row .productUrl/.licenseUrl).

Cause 2 of 3: the same blueprint table misgroups and misdescribes the Amazon Linux 2023 row and omits its licenseUrl, observable through the lifecycle fixture's catalog read.
AWS: recorded behavior only (as above, the model fixes no row values). The recording shows the amazon_linux_2023 blueprint carrying group 'amazon_linux_2023' (the group token equal to the blueprint id for this image), AWS's own description paragraph ("Amazon Linux 2023 is a modern, general purpose Linux-based OS that comes with 5 years of long term support. ..."), a `version` that is the AWS OS build string, a `productUrl` under aws.amazon.com (aws.amazon.com/linux/amazon-linux-2023) and a `licenseUrl` under the AWS EULA host.
Emulator: that row carries group 'amazon-linux' instead of the recorded group token, an emulator-authored description paragraph, a shortened `version`, a marketplace prodview productUrl instead of the AWS product page, and NO licenseUrl member at all; replay reports $.blueprints[6] as a whole-entry value_mismatch, alongside the same host_not_own productUrl/licenseUrl pattern on the surrounding rows.
Why: a client that filters or groups blueprints by `group` (the documented way to collate the versions of one image family) puts this image in a group AWS does not use, so family-based selection misses it; and a client that reads `licenseUrl` to present the EULA before launch gets no value where AWS always supplies one. This is a separate cause from cause 1 because it is a wrong-column/absent-member fault on a specific identified row reached through a different fixture path, and correcting the description/URL columns of the Windows rows does not close it.
Fix: the same static instance-blueprint catalog table - the amazon_linux_2023 row's group, description, version and productUrl columns, and its missing licenseUrl column.
Traces: lightsail-catalog-and-operations-lifecycle#task#4 (divergence_key service=lightsail|GetBlueprints|status=200->200|keys=...,$.blueprints[6],...).

Cause 3 of 3: GetBundles serves wrong monthly prices for the Windows bundle tiers and a truncated bundle list.
AWS: Smithy com.amazonaws.lightsail#GetBundles is an awsJson RPC operation (POST /ls/api/2016-11-28/GetBundles, success code 200, httpBindingsInert) whose output member `bundles` is a BundleList of com.amazonaws.lightsail#Bundle (members bundleId, name, price, cpuCount, diskSizeInGb, ramSizeInGb, power, transferPerMonthInGb, instanceType, isActive, supportedPlatforms, publicIpv4AddressCount). The model fixes no prices or row set, so this is RECORDED BEHAVIOR ONLY: the requirement is that each bundleId carries the price and spec AWS publishes for it, and that the whole bundle catalog is listed. The recording shows the WINDOWS-platform 3.0 tiers priced micro_win_3_0 = 14.0, small_win_3_0 = 22.0, medium_win_3_0 = 44.0, large_win_3_0 = 74.0, and asserts bundle rows out to index 99.
Emulator: the same bundleIds are served with every other spec column correct (cpuCount, diskSizeInGb, ramSizeInGb, power, transferPerMonthInGb, instanceType, supportedPlatforms, publicIpv4AddressCount all match) but with a different `price` on each Windows tier - 16.0, 26.0, 46.0 for micro/small/medium where AWS serves 14.0, 22.0, 44.0 - and replay reports $.bundles[12] through $.bundles[99] as missing, i.e. the asserted tail of the bundle catalog is not served at all.
Why: price is the value a client reads to cost a plan before creating an instance or to render a plan picker, so a wrong price is silently wrong output rather than an error; and a bundle that is not listed cannot be chosen, so any create-instance flow that selects an omitted tier (or validates a bundleId against the listing) fails against the emulator while succeeding on AWS. This is a separate cause from causes 1 and 2 because it is a different operation and a different table.
Fix: the static bundle catalog table seeding the GetBundles handler in the lightsail crate - the price column on the Windows tiers, and the omitted tail rows.
Traces: lightsail-catalog-get-bundles#task#1 (divergence_key service=lightsail|GetBundles|status=200->200|keys=$.bundles[12]..$.bundles[99]).
