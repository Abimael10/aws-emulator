# dynamodb: 3 net-new causes — the TransactItems 100-action cap refusal dumps the whole request, TransactGetItems emits an empty Item, and a self-delete of a CREATING GSI is refused

> _Note: this issue was identified against the code base at commit `c5b9149d70e2a9aad6a1bceb8aa9795c91a9cab7`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
TransactWriteItems

## Description
Three independent root causes in the DynamoDB emulator, all grounded in failing checks the behavioral suite lists under '### dynamodb'. Each must be closed before this issue is submitted. Related items that do NOT carry these replay keys: open 20261119T231740Z-dynamodb-4-net-new-causes-getitem-batchgetitem-drop.md (its Cause 1 is the OPPOSITE requirement — GetItem/BatchGetItem/Query must PRESENT an empty Item — and it covers neither TransactGetItems nor the index lifecycle); open 20261117T172826Z-dynamodb-control-plane-and-request-deserialization-10-net.md and 20261111T170613Z-dynamodb-non-constraint-validationexception-messages-are-wrapped-in.md (other operations' refusal wording). The fixed issue 20261117T172826Z-dynamodb-5-net-new-causes-malformed-sigv4-answers.md claimed two of these behaviors as its Cause 3 (the BatchWriteItem over-25 request dump) and its Cause 4 (TransactGetItems' empty Item); BatchWriteItem's aggregate refusal now passes, but the TransactItems cap and the TransactGetItems Item member still fail with the identical assertions, so that fix did not reach either path and a resolved issue does not cover them.

Cause 1 of 3: the TransactItems 100-action cap is reported through a generic constraint reporter that serialises the entire request list into the message. Failing checks: dynamodb.transact-get-items-over-the-item-cap-rejected, dynamodb.transact-write-items-over-the-item-cap-rejected, dynamodb.transact-write-exceeds-100-items.
AWS: Smithy: TransactGetItems.TransactItems targets TransactGetItemList and TransactWriteItems.TransactItems targets TransactWriteItemList, both @required with @length(min: 1, max: 100). A request carrying 101 actions is refused 400 ValidationException with AWS's framework constraint message, which names the MEMBER PATH and the bound and never echoes the rejected value: "1 validation error detected: Value at 'TransactItems' failed to satisfy constraint: Member must have length less than or equal to 100". Every part of that sentence is fixed text except the member path ('TransactItems') and the bound (100), which come from the model; the count of errors leads the sentence. Nothing is written (a 100-action transaction in the same check is applied in full, so the cap itself is correct).
Emulator: refuses with the right status and code (400 ValidationException) but with the "Value '<rejected value>' at ..." variant of the constraint reporter applied to the whole list, so the message opens "1 validation error detected: Value '[TransactWriteItem(conditionCheck=null, put=Put(item={pk=AttributeValue(s=..., n=null, b=null, iNT=null, dECIMAL=null, dOUBLE=null, sS=null, nS=null, bS=null, iNTSET=null, dECIMALSET=null, dOUBLESET=null, m=null, l=null, nULL=null, bOOL=null)}, tableName=..., conditionExpression=null, ...), delete=null, update=null), TransactWriteItem(..." and runs on for kilobytes. TransactGetItems produces the same shape with TransactGetItem(get=Get(...)) entries. The message is Rust/Java struct debug output: it leaks internal field names (iNTSET, dECIMALSET, workloadProfileName) that are not part of any AWS wire shape, and it grows with the request, so it is unbounded.
Why: a client that keys on AWS's documented constraint sentence — to tell a request-shape violation from a data refusal, to extract the offending member path, or to assert on it in tests — never matches. The reply is also orders of magnitude larger than AWS's and echoes every item key the caller submitted, so a refusal of a large transaction returns the caller's data back in an error log.
Fix: the request-shape validation for TransactGetItems/TransactWriteItems in the DynamoDB request deserializer/validation layer must report a list @length violation through the "Value at '<member>' failed to satisfy constraint: Member must have length less than or equal to <max>" form instead of the value-echoing variant — the same correction already made for BatchWriteItem's aggregate count, applied to the TransactItems member of both transaction operations.
Traces: dynamodb.transact-get-items-over-the-item-cap-rejected (101 Gets), dynamodb.transact-write-items-over-the-item-cap-rejected (101 Puts, which also asserts nothing was written), dynamodb.transact-write-exceeds-100-items (100 Puts accepted, the 101st rejected).

Cause 2 of 3: TransactGetItems serialises an empty Item member for a Get whose projection matches nothing. Failing check: dynamodb.transact-get-items-top-level-vs-cancellation-error-class.
AWS: Smithy: TransactGetItemsOutput.Responses targets ItemResponseList of ItemResponse, whose single member Item (AttributeMap, "Map of attribute data consisting of the data type and attribute value") is OPTIONAL. Recorded behavior: a Get that names an existing item but whose ProjectionExpression resolves to none of its attributes still succeeds (HTTP 200) and the matching Responses entry carries NO Item member at all — the member is absent, not an empty map. (Note this is the reverse of GetItem/BatchGetItem, where AWS does present "Item": {}; the two operations differ and must not share one serializer rule.)
Emulator: answers 200 with Responses[0] == {'Item': {}} — the member present and empty.
Why: callers test membership of Item to decide whether the slot produced anything; an empty map passes that test, so the caller takes the "found" branch and then dereferences attributes that are not there. Code written against AWS's TransactGetItems shape and code written against its GetItem shape both misread the emulator.
Fix: the TransactGetItems response serializer / per-slot ItemResponse construction must omit Item when the projected attribute map is empty, independently of the GetItem/BatchGetItem rule.
Traces: dynamodb.transact-get-items-top-level-vs-cancellation-error-class (final arm; the top-level ResourceNotFoundException, ProjectionExpression syntax-error and cancellation-reason arms of the same check passed).

Cause 3 of 3: UpdateTable refuses the deletion of the global secondary index that is itself still being created. Failing check: dynamodb.gsi-creating-blocks-other-index-but-accepts-self-delete.
AWS: Smithy: UpdateTable takes GlobalSecondaryIndexUpdates (GlobalSecondaryIndexUpdate with Create/Update/Delete) and models LimitExceededException and ResourceInUseException, both client errors at HTTP 400. Recorded behavior: while one GSI is CREATING, an UpdateTable that CREATES a second, different index is refused 400 LimitExceededException with "Subscriber limit exceeded: Only 1 online index can be created or deleted simultaneously per table" (the emulator gets this arm right), but an UpdateTable that DELETES the very index being built is ACCEPTED: the TableDescription echoes that index with IndexStatus DELETING, the index then disappears, the attribute definition only it needed is dropped with it, a later Query naming it is refused ValidationException "The table does not have the specified index: <indexName>", and the base table keeps every item.
Emulator: refuses the self-delete 400 ResourceInUseException with "Attempt to change a resource which is still in use: Index creation is in resource allocation phase. Retry deletion during backfilling phase or when the index is active. Table: <tableName> Index: <indexName>" (fixed text plus the table and index names from the request/state). The index is therefore never removable until it finishes building, and the rest of the lifecycle — DELETING status, attribute-definition pruning, the post-deletion Query refusal — is unreachable.
Why: cancelling a mis-specified index build is the documented escape hatch; a client that issues the self-delete is told the resource is in use and either gives up or spins retrying, and a provisioning flow (CloudFormation-style rollback of a failed index add) cannot undo its own change.
Fix: the UpdateTable handler's global-secondary-index update admission check in the DynamoDB control plane: the one-online-index-operation guard must exempt a Delete whose IndexName is the index currently CREATING, moving that index to DELETING instead of raising ResourceInUseException, and the index-removal path must then drop the attribute definitions no remaining key schema references.
Traces: dynamodb.gsi-creating-blocks-other-index-but-accepts-self-delete (the LimitExceededException arm for the second, different index passed; the failure is on the immediately following self-delete).
