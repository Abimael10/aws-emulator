# apigateway: 2 net-new causes — ImportRestApi refuses a malformed definition with "Invalid OAS input" instead of AWS's "Invalid OpenAPI input.", and CreateBasePathMapping racing DeleteRestApi is serialized so the concurrent delete is refused instead of accepted (orphan path unreachable)

> _Note: this issue was identified against the code base at commit `9b3ec711581582504a687984a45cdda758f31515`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
ImportRestApi, DeleteRestApi

## Description
2 net-new root causes, both in the apigateway (REST API Gateway) emulator, grounded in the only 2 failing behavioral checks under the `### apigateway` heading that the replay report marks neither "ALREADY FILED" nor "OWNED by" an open issue.

Cause 1 of 2: ImportRestApi's refusal MESSAGE for a body that cannot be parsed as an API definition is the wrong sentence.
Failing check: apigateway.import-rest-api-invalid-openapi-fails
AWS: Smithy (services/service-com-amazonaws-apigateway-backplanecontrolservice/smithy-model/com-amazonaws-apigateway-backplanecontrolservice.json) models ImportRestApi as POST /restapis?mode=import, success 201, input member `body` (Blob, @httpPayload, required — "The POST request body containing external API definitions. Currently, only OpenAPI definition JSON/YAML files are supported"), error BadRequestException at HTTP 400 ("The submitted request is not valid, for example, the input is incomplete or incorrect. See the accompanying error message for details."). The model does not state the message text, so the text itself is recorded behavior only: a body whose parse cannot be finished (truncated JSON, an unterminated collection or scalar, text that is no document) is refused with HTTP 400, Error.Code `BadRequestException` and Error.Message `Invalid OpenAPI input.` — that message is entirely FIXED text, including the trailing period, and carries NO variable part (no byte offset, no parser complaint, no member name). The refusal must also leave no partially created RestApi behind.
Emulator: the code and the 400 are right, but the message is `Invalid OAS input` — a different sentence ("OAS" for "OpenAPI") and missing the trailing period. The check fails at `assert message == "Invalid OpenAPI input."` with `AssertionError: unexpected rejection message 'Invalid OAS input'`. The sentence is the shared definition reader's constant: services/service-com-amazonaws-apigateway-backplanecontrolservice/src/ops/put_rest_api.rs line 428, `pub const UNPARSEABLE_DEFINITION: &str = "Invalid OAS input";`, which ImportRestApi reaches through `super::put_rest_api::parse_definition` (imported at src/ops/import_rest_api.rs lines 144-147), so PutRestApi serves the same wrong sentence for the same class of body.
Why: the error message is part of the contract for this refusal class. A client, CLI wrapper, CI assertion or importer that branches on API Gateway's "Invalid OpenAPI input." (the only signal distinguishing an unreadable document from the other BadRequestException causes of this operation, which share code 400/BadRequestException) does not match and falls through to generic error handling, so a broken definition is reported as an unknown failure.
Fix: the shared definition reader's refusal text in the apigateway crate — the `UNPARSEABLE_DEFINITION` constant in src/ops/put_rest_api.rs that ImportRestApi's and PutRestApi's validation raise when the body does not parse.
Traces: apigateway.import-rest-api-invalid-openapi-fails.

Cause 2 of 2: CreateBasePathMapping and DeleteRestApi issued concurrently for the same RestApi are mutually exclusive in the emulator, so when the mapping lands first the concurrent DeleteRestApi is REFUSED 400 instead of accepted 202 — the interleaving AWS exhibits (both calls succeed, leaving a mapping that is NOT cascade-deleted) never occurs, and the orphan behavior the check exists to verify is unreachable.
Failing check: apigateway.delete-rest-api-racing-base-path-mapping-leaves-orphaned-mapping
AWS: Smithy models DeleteRestApi as DELETE /restapis/{restApiId} with success code 202 (an ACCEPTED, asynchronous removal) and errors BadRequestException (400), ConflictException (409), NotFoundException (404), TooManyRequestsException (429), UnauthorizedException (401); CreateBasePathMapping as POST /domainnames/{domainName}/basepathmappings, success 201, required members domainName and restApiId. The model states no precondition and no concurrency semantics, so this is recorded behavior only: API Gateway's base-path-mapping guard on DeleteRestApi and the mapping write are not evaluated atomically against each other, so a CreateBasePathMapping issued concurrently with DeleteRestApi for the same restApiId can succeed WITH the delete (the delete answers 202). The resulting mapping is then NOT cascade-deleted with the API: GetBasePathMappings on the domain still lists it, GetRestApi on the deleted id answers NotFoundException `Invalid API identifier specified <accountId>:<restApiId>` (fixed text "Invalid API identifier specified " plus the caller's account id and the requested restApiId), the orphaned mapping still OCCUPIES its (domainName, basePath) slot so mapping that slot to a second, live RestApi is refused with ConflictException `Base path already exists for this domain name` (wholly fixed text), and the orphaned mapping's own DeleteBasePathMapping is refused with BadRequestException `Invalid REST API identifier specified`. Where one of the racers does lose, AWS's answers are the ones this check grades exactly: a losing CreateBasePathMapping gets BadRequestException `Invalid REST API identifier specified`, a losing DeleteRestApi gets BadRequestException `Deleting RestApi <restApiId> failed. Please remove all base path mappings related to the RestApi in your domains: <domainNames>` (fixed text around the restApiId from the request and the domain name(s) from state), or either is throttled with TooManyRequestsException `Too Many Requests`.
Emulator: both operations take the same exclusive store lock (src/ops/delete_rest_api.rs `let mut store = state.lock();` at line 168, guard at lines 188-199 via `store.domain_names_mapping_rest_api(...)`), so the two concurrent requests are strictly serialized and the outcome is decided by lock order alone. In the replayed round the CreateBasePathMapping won the lock, the mapping was written, and the concurrent DeleteRestApi was then refused 400 BadRequestException (message text correct) — recorded as `(basePath, mapping error, delete error) per round: [('v1', None, 'BadRequestException')]`, after which the check fails at `assert mapping_ok and delete_ok` with "expected a round where both CreateBasePathMapping and DeleteRestApi succeed". Because the mapping write and the delete's guard cannot interleave, a mapping created in the delete's in-flight window turns the delete into a refusal rather than producing the orphan the handler's own comment (lines 178-187: "a mapping written while the accepted removal is still in flight resolved the id against state that still held the API") says it should produce.
Why: a client doing exactly what AWS tolerates — mapping a base path while a delete of the same API is in flight — gets a 400 the real service does not return, and the state AWS leaves behind (a live mapping whose RestApi is gone, still holding its base path against a replacement API) is unreachable in the emulator. Teardown/migration code written against AWS, which must detect and remove such an orphan (DeleteBasePathMapping refused with `Invalid REST API identifier specified`, the slot still Conflicting for a new API, the domain delete removing it), is never exercised, and clients that rely on the delete being accepted under concurrency see a spurious precondition failure. Note the check never got past the race, so the emulator's downstream behavior for an orphaned mapping (no cascade delete; the ConflictException and its message; the NotFoundException message of GetRestApi after an accepted delete) is unverified by this run and must be confirmed once the interleaving is reachable.
Fix: the concurrency scope of DeleteRestApi's base-path-mapping precondition in the apigateway crate — DeleteRestApi's handler/validation (src/ops/delete_rest_api.rs) together with CreateBasePathMapping's handler and the shared store in src/state.rs (`domain_names_mapping_rest_api`, `rest_api_referenceable`, `accept_rest_api_delete`): the guard must not be evaluated atomically against a concurrently arriving mapping write, so that a mapping created in the accepted delete's in-flight window yields the 202 plus the surviving orphaned mapping rather than flipping the delete to a refusal.
Traces: apigateway.delete-rest-api-racing-base-path-mapping-leaves-orphaned-mapping.
