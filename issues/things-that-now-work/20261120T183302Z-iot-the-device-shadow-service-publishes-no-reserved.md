# iot: the Device Shadow service publishes no reserved $aws/things/<thing>/shadow/update/{delta,accepted,documents} messages over MQTT, so the recomputed-delta push contract never reaches a verdict

> _Note: this issue was identified against the code base at commit `e29493f7fa963c41f6d31aa90ff930f470cca778`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
UpdateThingShadow

## Description
Cause 1 of 1: an accepted UpdateThingShadow produces no MQTT publication on the reserved classic-shadow topics, so the shadow's push model — and in particular the rule that the delta is RECOMPUTED against `reported` rather than accumulated — is unobservable. The check that exercises it burns its whole budget and is killed by the harness ('Check timed out after 60.0s') without reaching any of its graded assertions.

AWS: Smithy com.amazonaws.iotdataplane#UpdateThingShadow — POST /things/{thingName}/shadow, `thingName` as @httpLabel (@length 1-128, @pattern ^[a-zA-Z0-9:_-]+$), optional `shadowName` as @httpQuery "name", `payload` as @httpPayload (JsonDocument blob), success code 200 with the merged state document as the payload; modeled errors ConflictException(409), InvalidRequestException(400), MethodNotAllowedException(405), RequestEntityTooLargeException(413), ThrottlingException(429), UnauthorizedException(401), UnsupportedDocumentEncodingException(415), ServiceUnavailableException(503), InternalFailureException(500). The model describes the HTTP call only; the MQTT side is recorded behavior of the IoT Core broker: every accepted shadow update is announced on the reserved topics $aws/things/<thingName>/shadow/update/accepted and $aws/things/<thingName>/shadow/update/documents, and — only when `desired` and `reported` disagree — on $aws/things/<thingName>/shadow/update/delta. A certificate principal whose attached policy allows iot:Connect/iot:Subscribe/iot:Receive/iot:Publish gets CONNACK rc=0 and SUBACK granted QoS [1] for each of those three reserved filters (granted 128 would be a refusal). The recorded contract has four parts: (a) a desired-only write pushes a delta whose `state` holds every desired leaf that differs from reported — including leaves stored by earlier updates, not an echo of the just-written keys — and a monotonically increasing `version`; (b) a write that makes `reported` agree with `desired` pushes /update/accepted (whose state.reported echoes the written value) and /update/documents (whose `current.state` holds the merged document and whose `previous.state` is the pre-update document, so previous != current) but pushes NO delta; (c) a later write that re-diverges a single leaf pushes a delta containing only that leaf, because the delta is recomputed against the current reported state; (d) the document version advances across every accepted update.

Emulator: nothing is delivered on any of the three reserved shadow topics. The check resolves the host via DescribeEndpoint(endpointType="iot:Data-ATS"), provisions a thing, a policy allowing iot:Connect/Subscribe/Receive/Publish and a certificate from CreateKeysAndCertificate, opens a mutual-TLS MQTT 3.1.1 session, subscribes to $aws/things/<thing>/shadow/update/{delta,accepted,documents}, then calls UpdateThingShadow with {"state":{"desired":{...}}}; the subscriber's inbox stays empty and the bounded wait for the first delta never completes, so the harness kills the check at 60 s before a single assertion ((a)-(d) above) is graded. No delta, no /update/accepted and no /update/documents message is observed at all.

Why: the shadow's entire value to a device is the push. A device that follows AWS's prescribed pattern — subscribe to $aws/things/<thing>/shadow/update/delta, then act on the desired state the service pushes — never acts, because the message never arrives; and a backend that waits on /update/accepted or /update/documents to learn an update landed hangs. A hang is worse than a refusal: the client has no error code to branch on, so the caller stalls indefinitely rather than failing fast. The recompute rule is the part most likely to be got wrong silently: an implementation that accumulates deltas re-delivers already-satisfied desired leaves and makes a device re-apply settings forever, and none of that can be caught here because no delta is published in the first place.

Fix: the IoT data plane's Device Shadow publication path — the component that serves the reserved $aws/things/+/shadow/* topic namespace in the broker — together with the delta computation behind UpdateThingShadow. An accepted update must publish /update/accepted and /update/documents (with `previous` being the pre-update document and `current` the merged one), must compute the delta as the difference of the full merged `desired` against the full merged `reported` at that moment (not as the set of keys in the request), must publish /update/delta only when that difference is non-empty, and must carry the advancing document `version` on each of those messages.
