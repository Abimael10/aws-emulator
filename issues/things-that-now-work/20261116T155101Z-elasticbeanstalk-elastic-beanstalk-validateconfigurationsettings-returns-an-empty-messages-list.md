# Elastic Beanstalk ValidateConfigurationSettings returns an empty Messages list (2 causes)

> _Note: this issue was identified against the code base at commit `68169c86c7603a2902f84035dfc94fd02b30ddfc`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
ValidateConfigurationSettings

## Description
Wire replay of simparity-wire-aws-v1 produced 20 divergence clusters, all on service=elasticbeanstalk. 18 of them carry a non-empty owned_by (platform-branch catalog, configuration-template TemplateUrl / resolved configuration-settings reads, not-found message texts, environment reads) and are skipped. The 2 causes below carry owned_by [] and stub_path "": both are on ValidateConfigurationSettings, whose success body is served with an EMPTY Messages list no matter what the submitted OptionSettings contain. Each cause must be closed and re-replayed separately.

Cause 1 of 2: ValidateConfigurationSettings on a legal-but-incomplete option set omits AWS's warning-severity ValidationMessage, returning an empty Messages list (fixture elasticbeanstalk-configuration-template-lifecycle-and-validation, step task#10).
AWS: Smithy (com.amazonaws.elasticbeanstalk#AWSElasticBeanstalkService): ValidateConfigurationSettings(ApplicationName required, TemplateName, EnvironmentName, OptionSettings required) -> ConfigurationSettingsValidationMessages{Messages: ValidationMessagesList}; ValidationMessage{Message, Severity, Namespace, OptionName} with ValidationSeverity enum values 'error','warning' and the modeled doc stating that 'warning: This message is providing information you should take into account'. Modeled errors are only InsufficientPrivilegesException (403) and TooManyBucketsException (400), so a validation finding is NOT an error response: it is reported as a member of Messages in the HTTP 200 body. The specific advisory text is recorded behavior only: when the settings being validated carry no aws:autoscaling:launchconfiguration / IamInstanceProfile option, AWS returns HTTP 200 with exactly one ValidationMessage {Severity: 'warning', Namespace: 'aws:autoscaling:launchconfiguration', OptionName: 'IamInstanceProfile', Message: "The environment does not have an IAM instance profile associated with it. To improve deployment speed please associate an IAM instance profile with the environment."}. That Message is entirely fixed text — it interpolates nothing from the request or from state — and the Severity/Namespace/OptionName triple identifies the option the advice is about.
Emulator: answers HTTP 200 with the Messages element present but empty (replay classifies $.ValidateConfigurationSettingsResponse.ValidateConfigurationSettingsResult.Messages as type_mismatch: expected a Messages element containing one member, got ''). No warning of any severity is produced.
Why: a client validating a configuration before applying it is told the settings are completely clean. On AWS it is told, in a machine-readable member scoped to (aws:autoscaling:launchconfiguration, IamInstanceProfile), that the environment will launch without an instance profile — the standard pre-flight signal that deployment will be degraded. Tooling and consoles that surface the warning list show nothing, and any caller that asserts on the presence of warnings before a write sees a false all-clear.
Fix: the ValidateConfigurationSettings handler's validation engine must run the platform's advisory (warning-severity) checks in addition to error-severity ones and project each finding into the Messages list of the 200 body, with the warning's Severity/Namespace/OptionName and AWS's fixed advisory sentence. Related open issue 20261115T085940Z-elasticbeanstalk-elastic-beanstalk-configuration-option-validation-unknown-namespaces-options.md concerns unknown namespaces/options and two error-message wordings found by the BEHAVIORAL suite; it does not carry this fixture/step pair and does not cover the missing warning-severity check, so it does not close this cause.
Traces: elasticbeanstalk-configuration-template-lifecycle-and-validation#task#10.

Cause 2 of 2: ValidateConfigurationSettings on an option set with an invalid value returns no error-severity ValidationMessage at all, so an invalid configuration validates clean (fixture elasticbeanstalk-configuration-template-lifecycle-and-validation, step task#11).
AWS: Smithy as above (the operation reports per-option findings in Messages, not as a modeled error); the message text is recorded behavior only. For an OptionSettings entry whose Value is not a number on a numeric option, AWS returns HTTP 200 whose Messages list contains an error-severity member for that option plus the instance-profile warning from cause 1 — in this recording member[0] = {Severity: 'error', Namespace: 'aws:autoscaling:asg', OptionName: 'MinSize', Message: "Invalid option value: 'not-a-number' (Namespace: 'aws:autoscaling:asg', OptionName: 'MinSize'): Value is not a number"} and member[1] = the IamInstanceProfile warning. The fixed text of the error message is "Invalid option value: '" + "' (Namespace: '" + "', OptionName: '" + "'): Value is not a number"; its variable parts are the submitted value, the namespace and the option name, all taken verbatim from the request (the 'not-a-number'/'aws:autoscaling:asg'/'MinSize' values in this recording are the request's fill-ins, not part of the requirement).
Emulator: answers HTTP 200 with no members in Messages — replay reports both Messages.member[0] (the error) and Messages.member[1] (the warning) as missing, got None. The emulator neither flags the non-numeric value nor emits the advisory, so a configuration AWS rejects as invalid is reported by the emulator as having nothing wrong with it.
Why: ValidateConfigurationSettings is the pre-write gate: a client calls it, sees Messages empty, and proceeds to UpdateConfigurationTemplate / UpdateEnvironment with a value the platform cannot honour. The caller gets no option-scoped diagnostic to show a user or to fail a deployment on, and the per-option value checks it relies on are silently absent.
Fix: the per-option value validation in the ValidateConfigurationSettings handler must type-check each submitted Value against the option's declared type from the configuration-option catalog and append an error-severity ValidationMessage (Severity 'error', Namespace and OptionName echoed from the request, Message in AWS's "Invalid option value: '<value>' (Namespace: '<namespace>', OptionName: '<optionName>'): Value is not a number" form) for every failure, alongside the warning-severity checks of cause 1 — i.e. the same Messages projection, which is currently returning an empty list on both paths.
Traces: elasticbeanstalk-configuration-template-lifecycle-and-validation#task#11.
