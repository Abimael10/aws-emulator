# signin: CreateOAuth2TokenWithIAM answers the unsupported-grant-type class with INVALID_REQUEST instead of the RFC unsupported_grant_type error object

> _Note: this issue was identified against the code base at commit `352f4536081af191daff3bc92f8d9fe5d775df3a`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
CreateOAuth2TokenWithIAM

## Description
One net-new cause in AWS Sign-In's IAM-authenticated OAuth 2.0 token endpoint (POST /v1/token?x-amz-client-auth-method=iam). The endpoint now answers EVERY grant type it will not serve with the single INVALID_REQUEST refusal, so the one grant-type class the recorded wire answers with RFC 6749's unsupported_grant_type error object no longer exists in the emulator at all. Status (400) and error shape (ValidationException) are right; the OAuth 2.0 error code and the refusal sentence are wrong.

=== Cause 1 of 1: the grant-type refusal of the IAM-signed /v1/token form carries error INVALID_REQUEST and the invalid-request sentence where AWS carries error unsupported_grant_type and RFC 6749 §5.2's sentence (fixture signin-oauth2-token-with-iam-grant-type-and-token-shape-rejected, step task#1) ===
AWS: Smithy (services/service-com-amazonaws-signin-signin/smithy-model/com-amazonaws-signin-signin.json): CreateOAuth2TokenWithIAM is http POST /v1/token?x-amz-client-auth-method=iam, auth aws.auth#sigv4; input grantType targets ClientCredentialsGrantType, jsonName 'grant_type', @required, @pattern ^client_credentials$; resource @required @length(1..2048); the modelled errors include ValidationException with @httpError(400), whose members are error (OAuth2ErrorCode, @required) and message (@required). The model's OAuth2ErrorCode enum does NOT declare 'unsupported_grant_type', so for this refusal class the recorded wire is the authority: recorded behavior shows the endpoint answers the grant-type class HTTP 400 as ValidationException with error 'unsupported_grant_type', error_description 'The authorization grant type is not supported by the authorization server.' and message carrying that same sentence. Both the code and the sentence are wholly FIXED text for this class — they interpolate nothing from the request (no member name, no offending value) and nothing from state; only the selection of the class depends on the request. The same code/sentence pair is what the anonymous /v1/token form records for its own unsupported grant types, so this is one service-wide refusal class, not a per-fixture value.
Emulator: HTTP 400 ValidationException (status and shape match) with error 'INVALID_REQUEST', error_description and message both 'The request is missing a required parameter, includes an invalid parameter value, or is otherwise malformed.' — the INVALID_REQUEST sentence, returned for this step where the wire records the unsupported_grant_type object. services/service-com-amazonaws-signin-signin/src/service/oauth2_token_endpoint.rs collapses the whole grant-type decision of the Endpoint::IamSigned arm into one refusal: any body whose 'grant_type' is not exactly 'client_credentials' — absent, empty, or supplied with another value — returns malformed_request(), and nothing in that arm can ever return unsupported_grant_type() any more. (The constant and constructor still exist and are still used by the Endpoint::ClientAuthenticated arm.) This is the mirror image of open behavioral issue 20261124T145312Z-signin-createoauth2tokenwithiam-refuses-a-granttype-outside-client-credentials, which required the INVALID_REQUEST wording for a grantType the request SUPPLIES with an out-of-pattern value; that requirement was satisfied by applying the wording to every case, which destroyed this one. Hypothesis: the two classes are distinct and must be split, as that issue's own note says — a grant type the request supplies with an out-of-pattern value is an invalid parameter VALUE (INVALID_REQUEST), while the class this fixture records — a request that leaves the endpoint with no usable grant to act on (the earlier resolved wire issue 20261109T154022Z-signin-5-net-new-causes-in-the-oauth observed the emulator reading this step's grantType as null) — is the grant-type class and keeps unsupported_grant_type with RFC 6749 §5.2's sentence. The split, not a single wording, is the requirement; the recorded wire of each step decides which class it belongs to.
Why: the OAuth 2.0 'error' code is the only machine-readable discriminator a token client has here — the HTTP status (400) and the SDK-visible error code (ValidationException) are identical for both classes — so a client that branches on 'unsupported_grant_type' to fall back to another grant, or that logs/asserts the refusal sentence, now sees 'your parameters are malformed' for a request whose parameters AWS accepted as well-formed but whose grant the endpoint does not serve. It will retry or report the wrong thing, and no retry of the same request can ever surface the class AWS reports.
Fix: the grant-type layer of the IAM-signed token endpoint — the Endpoint::IamSigned arm of refusal_for in crate::service::oauth2_token_endpoint, together with the unsupported_grant_type()/malformed_request() constructors it selects between. That arm must distinguish the grant-type class (answered with the unsupported_grant_type code and RFC 6749 §5.2's description, as both /v1/token forms record it) from an invalid supplied parameter value (answered with the INVALID_REQUEST code and the INVALID_REQUEST sentence), instead of returning one refusal for every grant type that is not client_credentials. Both this fixture step and the behavioral check named above must pass together after the change.
Traces: fixture signin-oauth2-token-with-iam-grant-type-and-token-shape-rejected step task#1 (the cluster's only member). Related, NOT covering: open issue 20261124T145312Z-signin-createoauth2tokenwithiam-refuses-a-granttype-outside-client-credentials (behavioral corpus, the opposite direction of the same decision, and it carries no wire replay key); open issues 20261029T191246Z / 20261102T032217Z-signin-resource-policy-and-console-authorization-operations-are-0875c7 concern signin host advertisement and resource-policy refusals and carry neither this fixture nor this operation.
