=== Cause 1 of 3: GetPipelineState publishes ActionState.entityUrl on console.aws.amazon.com, a host the emulator does not serve (fixture codepipeline-gpn-traj-creation-run-failed-at-source-read-path, step task#10) ===
AWS: Smithy (services/service-com-amazonaws-codepipeline-codepipeline-20150709/smithy-model/com-amazonaws-codepipeline-codepipeline-20150709.json) models GetPipelineState output.stageStates -> StageStateList of StageState, whose actionStates -> ActionStateList of ActionState; ActionState.entityUrl targets Url (@length 1..2048) and is documented "A URL link for more information about the state of the action, such as a deployment group details page". AWS resolves it from the action type's entityUrlTemplate with the action's configuration and the request's Region substituted. The recording does not assert the URL's value (expected '<shaped-not-asserted>'), only that the member is present and shaped as a URL the serving endpoint can be followed to; the replay's own check is the host: an emulator must publish URLs on the host it is reached on, because that is the only host a client of the emulator can resolve and fetch. That rule is established behavior for this project, not an invention of this issue: it is the same defect class already filed as 20261109T163411Z-codecommit-codepipeline-glue-iam-lambda-lambda-getfunction-publishes-a-code-location-on-an.md (Lambda Code.Location on an amazonaws.com host) and 20261111T061123Z-codepipeline-publishes-webhook-urls-on-a-webhooks-aws.md (CodePipeline webhook URLs on a webhooks.aws host). Neither of those covers ActionState.entityUrl and neither carries this replay key.
Emulator: for the CodeCommit Source action it answers an entityUrl of the form 'https://console.aws.amazon.com/codesuite/codecommit/repositories/<repo>/browse/refs/heads/<branch>?region=<region>' (replay verdict value_mismatch) and for the Lambda Invoke action 'https://console.aws.amazon.com/lambda/home?region=<region>#/functions/<function>' (replay verdict host_not_own). In both the fixed template text is right and only the HOST is wrong: it names the public AWS console rather than the address the emulator announced and is reached on. The repository name, branch, function name and region in those URLs are request/state-derived values that FILL the template and are not themselves requirements.
Why: entityUrl exists to be followed. A client of the emulator (a console surface, a CI job that deep-links an operator to the failing action, any automation that fetches the link) resolves a host the emulator does not serve: at best it leaves the emulated environment, at worst name resolution or egress is refused and the link is dead. Because the response is 200 and the member is present, the client cannot distinguish a usable link from an unusable one.
Fix: the GetPipelineState response projection in the codepipeline service crate — specifically the entityUrl/revisionUrl resolution step that expands the action type's entityUrlTemplate. It must expand the template against the endpoint the emulator is serving on (the same host:port the request arrived on) instead of hard-coding the public console host; the per-action path and query parts stay as AWS words them.
Traces: codepipeline-gpn-traj-creation-run-failed-at-source-read-path#task#10 ($.stageStates[0].actionStates[0].entityUrl, $.stageStates[1].actionStates[0].entityUrl).

=== Cause 2 of 3: ListPipelines serializes PipelineSummary.created / PipelineSummary.updated at the emulator clock's native precision (fixture codepipeline-list-pipelines-membership-and-pagination, step task#8) ===
AWS: Smithy ListPipelines output.pipelines -> PipelineList of PipelineSummary; PipelineSummary.created ("The date and time the pipeline was created, in timestamp format.") and PipelineSummary.updated ("The date and time of the last update to the pipeline, in timestamp format.") both target Timestamp. The service speaks awsJson1_1, whose default timestamp form is epoch-seconds as a JSON number. The model types the member but says nothing about precision, so for precision this is recorded behavior only: every CodePipeline timestamp in the recorded corpus carries at most three fractional digits (millisecond resolution), e.g. a recorded ListActionExecutions lastUpdateTime of 1793700369.272. The instants themselves are per-run values and are not asserted by the recording (expected '<shaped-not-asserted>') — only the serialized number's shape is a requirement.
Emulator: both pipeline summaries on this step come back with six or more fractional digits (seven on one of them), i.e. the raw float the internal clock produced; created and updated are additionally bit-identical to each other rather than merely close. Hypothesis: a seconds-since-epoch f64 is handed straight to the JSON serializer instead of being truncated/rounded to milliseconds.
Why: a client that parses these numbers with a millisecond-resolution epoch-seconds decoder (as the AWS SDKs do), or that digests/compares a ListPipelines response against an AWS-recorded one, sees a number shape AWS never emits; strict parsers error and equality/checksum comparisons fail even where the instant is irrelevant.
Fix: the codepipeline response serializer's epoch-seconds Timestamp encoding, as used by the ListPipelines handler's PipelineSummary projection — round or truncate to millisecond resolution. This is one shared encoder rather than one operation: the same excess precision shows on GetPipelineState created/updated/lastStatusChange and PutApprovalResult approvedAt in this very replay (those steps are owned by other open issues for their other faults, so they are not re-filed here).
Related open issues that describe this same scalar-projection fault but do NOT own this replay key (the replay reports the cluster unowned, because the keys of the earlier filings embed previous runs' generated pipeline names): 20261111T061123Z-codepipeline-listpipelines-reports-pipelinetype-v1-and-timestamps-carry.md, 20261111T185123Z-codepipeline-listpipelines-summarizes-a-created-pipeline-as-pipelinetype.md, 20261112T032208Z-codepipeline-listpipelines-pipelinesummary-still-reports-v1-for-a-v2.md, 20261112T103336Z-codepipeline-listpipelines-summary-projection-reports-pipelinetype-v1-and.md, 20261112T195134Z-codepipeline-listpipelines-scalar-projection-pipelinetype-v1-for-a.md, 20261114T065137Z-codepipeline-listpipelines-serializes-pipelinesummary-created-updated-with-sub.md, 20261114T155321Z-codepipeline-control-plane-round-trip-createpipeline-refuses-a.md and 20261114T163808Z-codepipeline-listpipelines-serializes-pipelinesummary-created-and-updated-at.md. Note that the pipelineType V1-for-V2 half of those issues no longer reproduces in this replay: only the timestamp precision does.
Traces: codepipeline-list-pipelines-membership-and-pagination#task#8 ($.pipelines[*].created, $.pipelines[*].updated for both listed pipelines).

=== Cause 3 of 3: ListActionExecutions records an action execution with no ActionExecutionResult.externalExecutionId and with a roleArn on an action that has none (fixture codepipeline-s3-source-manual-approval-run-succeeds, step task#11) ===
AWS: Smithy ListActionExecutions output.actionExecutionDetails -> ActionExecutionDetailList of ActionExecutionDetail {pipelineExecutionId, actionExecutionId, pipelineVersion, stageName, actionName, startTime, lastUpdateTime, updatedBy, status, input: ActionExecutionInput, output: ActionExecutionOutput}. ActionExecutionOutput.executionResult -> ActionExecutionResult, whose externalExecutionId is "The action provider's external ID for the action execution" and externalExecutionSummary is "The action provider's summary for the action execution". ActionExecutionInput.roleArn is "The ARN of the IAM service role that performs the declared action. This is assumed through the roleArn for the pipeline." Recorded behavior for the two members at issue: for the AWS/Approval/Manual action the recording carries output.executionResult.externalExecutionId equal to that action execution's own id (the approval provider's external id for the approval) alongside externalExecutionSummary (the approver's comment), and its input carries NO roleArn — a manual approval is performed by a principal, not by an assumed service role, so AWS omits the member rather than substituting the pipeline role.
Emulator: the approval entry's output.executionResult holds externalExecutionSummary only — externalExecutionId is absent — and its input additionally carries roleArn = the pipeline's service role ARN, a member the recorded response does not have. The entry's own actionExecutionId differs from the recording's uuid, which is a per-run identifier and is NOT claimed as a defect here (it matches the id the emulator reports for the same action elsewhere in the run). The replay reports the Source entry (actionExecutionDetails[1]) as diverging too, but truncates its expected body after 'input.actionTypeId', so the only sub-fault this issue claims for it is the same record-level one: the S3 source action's execution result carries no provider external id either, consistent with the externalExecutionId loss that 20261111T061123Z-codepipeline-s3-source-read-path-loses-the-source.md documents for GetPipelineState (that issue owns the GetPipelineState/GetPipelineExecution steps task#10 and task#12 of this same fixture, and does NOT own this ListActionExecutions step or cover its projection).
Why: ActionExecutionResult.externalExecutionId is the only API-visible correlation key between a CodePipeline action run and the provider-side artifact it produced (the approval record, the S3 object version, the external build). A client that reads the execution history to correlate an action with the provider system — the standard audit and traceability path — gets a result block with no external id and must guess; the spurious roleArn makes a manual approval look as if a service role performed it, which misattributes the action in any audit that reads input.roleArn.
Fix: the action-execution history/state in the codepipeline crate plus the ListActionExecutions ActionExecutionDetail projection — record the provider's external id on each action execution's result and emit it as output.executionResult.externalExecutionId, and emit input.roleArn only for action categories that actually assume the pipeline role, omitting it for AWS/Approval/Manual.
Traces: codepipeline-s3-source-manual-approval-run-succeeds#task#11 ($.actionExecutionDetails[0], $.actionExecutionDetails[1]).
