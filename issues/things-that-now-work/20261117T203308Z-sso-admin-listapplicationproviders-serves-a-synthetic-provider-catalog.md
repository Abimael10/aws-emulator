# sso-admin ListApplicationProviders serves a synthetic provider catalog with wrong DisplayData

> _Note: this issue was identified against the code base at commit `bacf77a60d804999808e0888de33963fa01292f8`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
ListApplicationProviders

## Description
ListApplicationProviders returns a hand-seeded placeholder set of application providers instead of the IAM Identity Center application-provider catalog. Two distinct causes, both filed here because they share the service, the operation and the seeded-catalog root cause.

Cause 1 of 2 — DisplayData.IconUrl is emitted with an off-emulator, non-reproducible icon host on providers that carry no icon (fixture sso-admin-application-provider-describe-round-trip, step task#1).
AWS: Smithy ssoadmin ListApplicationProviders -> ListApplicationProvidersResponse.ApplicationProviders: list<ApplicationProvider>; ApplicationProvider.DisplayData -> DisplayData with optional members DisplayName (@length 1..100), IconUrl (@length 1..768, @pattern ^(http|https)://.*$) and Description (@length 1..128). IconUrl is optional and documented as "A URL that points to an icon that represents the application provider" — it is present only for the providers whose catalog entry actually has an icon, and the URL must be one the caller can resolve against the serving endpoint. Recorded behavior only for which providers carry it: in this recording the providers the emulator returns at ApplicationProviders[0] and ApplicationProviders[3] have NO DisplayData.IconUrl member at all.
Emulator: emits DisplayData.IconUrl on those entries, pointing at a host it does not serve — the static AWS icon CDN (scheme+host of the form https://static.global.sso.amazonaws.com/..., with an app-<hex> path segment and /icons/default.png). The replay check reports "host_not_own (expected None, got <that URL>)" for $.ApplicationProviders[0].DisplayData.IconUrl and $.ApplicationProviders[3].DisplayData.IconUrl. The fixed part of the defect is that an IconUrl is synthesized at all for a provider that has none, and that when one is synthesized its host is not the endpoint the emulator is reached on; the app-<hex> path segment is a per-run generated value, not a requirement.
Why: a client that renders the portal entry for a provider follows DisplayData.IconUrl. Against the emulator it is handed a URL on a host outside the emulator, so the client either egresses to the real AWS CDN (defeating the point of an isolated emulator, and failing in a sandbox with no egress) or renders a broken icon for a provider that AWS says has no icon. Callers that treat IconUrl's presence as "this provider has custom display data" also branch the wrong way.
Fix: the ListApplicationProviders response serializer / the DisplayData projection in the sso-admin crate's application-provider catalog state — do not populate IconUrl for a catalog entry that has none, and when one is populated derive its scheme+host from the request's endpoint rather than hard-coding an amazonaws.com host.
Traces: sso-admin-application-provider-describe-round-trip#task#1 (verdict mismatch, expected_status 200, actual_status 200).

Cause 2 of 2 — the provider catalog itself is almost entirely missing, mis-ordered and stripped of per-provider fields (fixture sso-admin-catalog-list-application-providers, step task#1).
AWS: Smithy ssoadmin ListApplicationProviders is @paginated (inputToken NextToken, outputToken NextToken, pageSize MaxResults, items ApplicationProviders) with MaxResults @range 1..100, and returns the full managed catalog of application providers, one ApplicationProvider per catalog entry. Each entry carries ApplicationProviderArn (required, @pattern ^arn:aws(-[a-z]{1,5}){0,3}:sso::aws:applicationProvider/[a-zA-Z0-9-/]+$), FederationProtocol (SAML or OAUTH), DisplayData, and — for OAUTH providers that expose scopes — ResourceServerConfig (ResourceServerConfig.Scopes keyed by scope name with DetailedTitle/LongDescription). Recorded behavior only for the catalog's size and membership: the recorded response enumerates several hundred entries (indices up to $.ApplicationProviders[393]), each a distinct catalog provider, with SAML catalog providers under arn:aws:sso::aws:applicationProvider/catalog/<Name> and managed-service providers under arn:aws:sso::aws:applicationProvider/<service> (for example the Glue provider at .../applicationProvider/glue, FederationProtocol OAUTH, with a ResourceServerConfig scope entry).
Emulator: returns only a small fixed stub list in a different order. Every index from $.ApplicationProviders[1] through $.ApplicationProviders[393] is reported missing or wrong; concretely the replay reports (a) catalog entries present by ARN but with DisplayData.IconUrl dropped (the catalog/DuoNetworkGateway and catalog/DruvaInSync entries come back with DisplayName and Description but no IconUrl, where AWS supplies one), and (b) a wholly different provider at the position AWS fills with the Glue provider — the emulator serves arn:aws:sso::aws:applicationProvider/custom ("SSO Custom Application Provider") there, with no ResourceServerConfig. Status matches (200 vs 200); only the body diverges.
Why: this operation is how a client discovers which application providers it may pass to CreateApplication/CreateApplicationAssignment. Against the emulator the discovery step returns a near-empty catalog, so any flow that looks up a provider ARN by name (Glue, a SAML catalog app, anything past the first entry) finds nothing and fails before it ever reaches the operation under test, and a client that pages with MaxResults never sees a second page. Clients that read ResourceServerConfig.Scopes to build a trusted-identity-propagation request get no scopes at all for OAUTH providers.
Fix: the sso-admin crate's seeded application-provider catalog (the state the ListApplicationProviders handler reads) — seed the full managed catalog with each entry's ARN, FederationProtocol, complete DisplayData and, for OAUTH providers, ResourceServerConfig.Scopes, and have the handler page over it in the recorded order honouring MaxResults/NextToken rather than returning a fixed stub list.
Traces: sso-admin-catalog-list-application-providers#task#1 (verdict mismatch, expected_status 200, actual_status 200).

Neither cause is covered by the open sso-admin issues (20261109T124858Z-...-createtokenwithiam and 20261117T113350Z-sso-admin-createapplication-accepts-signinoptions-origin-identity-center-for-an): those concern CreateTokenWithIAM and CreateApplication validation, not the ListApplicationProviders catalog.
