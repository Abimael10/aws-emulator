## Description

=== Cause 1 of 2: CreateInvalidation against a well-formed but absent distribution id is refused with an error code that is not one of the operation's modeled error shapes, so the SDK surfaces a generic ClientError instead of NoSuchDistribution ===
AWS: Smithy (services/service-com-amazonaws-cloudfront-cloudfront2020-05-31) CreateInvalidation — http {method POST, uri /2020-05-31/distribution/{DistributionId}/invalidation, code 201}; input DistributionId: string @httpLabel @required with NO @pattern and NO @length, InvalidationBatch @httpPayload @required; modeled errors AccessDenied (client, httpError 403), BatchTooLarge (413), InconsistentQuantities (400), InvalidArgument (400), MissingBody (400), NoSuchDistribution (client, httpError 404), TooManyInvalidationsInProgress (400). Because the model constrains the id's form in no way, an id that is syntactically acceptable but names no distribution reaches the state lookup and AWS refuses it with HTTP 404, Error.Type 'Sender', Error.Code 'NoSuchDistribution' and Error.Message 'The specified distribution does not exist.' — that message is entirely FIXED text for this error class; AWS interpolates nothing from the request, so the submitted id never appears in it. Crucially the error CODE is the contract an SDK keys on: botocore maps the wire Error.Code onto the modeled error shape, so a caller gets cloudfront.exceptions.NoSuchDistribution (exception class name 'NoSuchDistribution'), which is what the check asserts on.
Emulator: the refusal the in-Lambda boto3 CloudFront client receives for DistributionId 'E1234567890ABC' (a well-formed id that names no distribution in state) does NOT resolve to any CloudFront-modeled error shape — botocore falls back to the generic botocore.exceptions.ClientError, so the handler reports cf_outcome 'error:ClientError' where AWS yields 'error:NoSuchDistribution'. Hypothesis (neither the model nor the recording states which): the response either carries an Error.Code string that is not in CloudFront's modeled error set (anything other than NoSuchDistribution/InvalidArgument/AccessDenied/MissingBody/BatchTooLarge/InconsistentQuantities/TooManyInvalidationsInProgress resolves to the generic class), or carries a REST-XML error envelope whose ErrorResponse/Error/Code member the parser cannot read, leaving botocore with no code to map. Either way the operation's modeled 404 NoSuchDistribution is not what reaches the client. The preceding assertions in the same check PASSED (the target reported invoked=True and the event detail arrived unchanged), so the call did reach the CloudFront handler and was answered by it.
Why: every client that branches on CloudFront's modeled exceptions takes the wrong branch. Code written as `except cf.exceptions.NoSuchDistribution: recreate_or_reresolve()` never fires; an unmapped code is indistinguishable from a transport or server fault, so invalidation drivers, CI scripts and SDK wrappers either retry a non-retryable condition or abort instead of re-resolving the distribution, and a permission-boundary test can no longer tell 'not allowed' (403 AccessDenied) from 'does not exist' (404 NoSuchDistribution) because neither code survives to the SDK.
Fix: CreateInvalidation's distribution-lookup refusal path and its REST-XML error serializer in the CloudFront invalidation handler — an unresolved but well-formed DistributionId must be serialized as the modeled NoSuchDistribution error (HTTP 404, Error.Code exactly 'NoSuchDistribution', Error.Type 'Sender', Error.Message the fixed text 'The specified distribution does not exist.') inside the ErrorResponse/Error envelope the protocol's error parser reads, rather than as an error whose code names no modeled shape.
Traces: cloudfront__events.iam-role-trusts-events-service-for-rule-target-invocation.

=== Cause 2 of 2: an EventBridge rule target invoked through a RoleArn trusting events.amazonaws.com never produces the target Lambda's SQS signal, so the check exhausts the run budget ===
AWS: recorded behavior only — the role/target wiring is not expressible in the Smithy model. A rule created by PutRule with an EventPattern matching {source, detail-type}, State ENABLED, and a target added by PutTargets whose RoleArn names a role whose trust policy allows sts:AssumeRole for Service events.amazonaws.com and whose inline policy allows lambda:InvokeFunction on the target function's ARN, is accepted by PutTargets (FailedEntryCount 0) and, on a matching PutEvents, EventBridge assumes that role and invokes the Lambda within seconds. The function then performs the calls its own execution role permits (here cloudfront:ListDistributions with MaxItems '1', then sqs:SendMessage to the signal queue), so the signal message appears on the queue on the first fired event. The sibling check in this same suite exercises the identical shape (target RoleArn trusting events.amazonaws.com, Lambda target, SQS signal) and the emulator delivered it inside the same budget, so the delivery path as such is not what is missing here.
Emulator: no signal message ever arrives. The check fires a fresh event and waits 30 s for a matching message, up to 4 rounds, and still has nothing when the runner's 60 s budget ends — 'Check timed out after 60.0s'. Its fast path contains no fixed sleep that could consume 60 s on its own (every wait in it returns as soon as the expected condition holds), so the budget was spent waiting for a delivery that did not happen. Hypothesis (not stated by the model or the recording): either PutTargets keeps refusing the freshly created events-trusted RoleArn with ValidationException, which the check absorbs in a propagation retry for up to 45 s, or EventBridge assumes the role and invokes the function but the function's own cloudfront:ListDistributions call fails, so the handler dies before it reaches SendMessage and no signal is ever produced.
Why: a client cannot use an IAM execution role as the alternative to a Lambda resource-based policy for an EventBridge target — the documented and supported wiring — because nothing arrives downstream. Any event-driven automation built on 'rule -> role-assumed Lambda -> queue' silently produces no effect, and because the failure is a silence rather than a refusal the caller sees no error to act on: it waits forever for a message that will not come.
Fix: the EventBridge target-invocation path for a target carrying a RoleArn — PutTargets' validation/acceptance of a role whose trust policy names events.amazonaws.com, the assume-then-invoke step of the rule dispatcher, and the CloudFront ListDistributions read the invoked function makes with its execution-role credentials (whichever of the two refuses, it must not be the one that swallows the delivery).
Traces: cloudfront__events.events-role-trust-policy-allows-assume-for-cloudfront-target.

NOT filed, and why (both are runner-budget artifacts whose own fixed waits exceed the 60 s cap no matter how the emulator answers, so the emulator did not cause them): cloudfront__events.cloudfront-distribution-inprogress-event-filtered-by-pattern drains its queue with a 90 s deadline and an early exit only at 10 collected messages, while the scenario can produce at most 1, so it always runs the full 90 s; cloudfront__events.eventbridge-rule-role-arn-wrong-trust-execution-not-started asserts a bounded ABSENCE with a 75 s poll that by construction returns only after its full deadline.
