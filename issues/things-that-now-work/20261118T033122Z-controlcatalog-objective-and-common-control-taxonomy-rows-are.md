# ControlCatalog objective and common-control taxonomy rows are absent from filtered listings

> _Note: this issue was identified against the code base at commit `027d9e9288dfd341f60d75b6ca76c3164fcd4263`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
ListObjectives

## Description
The emulator's seeded ControlCatalog taxonomy is not the AWS taxonomy: ListObjectives and ListCommonControls both answer 200 with a well-formed list, but the list does not contain the catalogued rows AWS returns. Catalogued objective and common-control ARNs are simply absent from the response, while entries keyed by identifiers AWS does not publish appear in the same cluster's key set, and the rows that are present carry emulator-authored Description prose instead of the catalog's published text. Two causes are bundled here; both are the same root cause (the seeded objective/common-control tables), and a fixer must close both.

SHARED STATEMENT OF THE FAULT

AWS: Smithy (com.amazonaws.controlcatalog#ControlCatalog). ListObjectives -> POST /objectives, HTTP 200, paginated (inputToken NextToken / outputToken NextToken / pageSize MaxResults / items Objectives); output Objectives is @required list<ObjectiveSummary>. ObjectiveSummary$Arn is @required with pattern ^arn:(aws(?:[-a-z]*)?):controlcatalog:::objective/[0-9a-z]+$, and Name, Description, Domain, CreateTime and LastUpdateTime are all @required; Description is documented "The description of the objective". ListCommonControls -> POST /common-controls, HTTP 200, paginated, items CommonControls, output CommonControls @required list<CommonControlSummary>; CommonControlSummary$Arn @required pattern ^arn:(aws(?:[-a-z]*)?):controlcatalog:::common-control/[0-9a-z]+$, with Name, Description, Domain, Objective, CreateTime and LastUpdateTime all @required. Both operations enumerate a FIXED, AWS-published taxonomy: for a given filter the membership of the returned list and each row's ARN, Name and Description are AWS-owned catalog content, not values the caller or the server chooses. For the exact membership and strings the recording is the authority (recorded behavior only); the model is the authority for these being required, AWS-owned catalog fields keyed by a published ARN.

Emulator: for the filters replayed it returns 200 with a list that omits catalogued rows entirely (the comparison reports the expected row as `missing ... got None`), lists rows under identifiers that do not occur in the recorded catalog, and rewrites the Description of rows it does serve into shorter emulator-authored sentences with the same general sense.

Why: a client enumerating the control catalog uses these two operations as the authoritative index - it walks ListObjectives/ListCommonControls to build a compliance framework mapping, then resolves each row by its ARN through ListControlMappings/GetControl. A row that is absent cannot be selected or resolved at all, so a framework build silently loses whole objectives and common controls and reports partial coverage as complete; a row served under an ARN AWS never published resolves nowhere against real AWS, so code validated against the emulator breaks on the real service; and a rewritten Description misstates to an auditor what the objective or common control requires.

Fix: the seeded taxonomy state behind the controlcatalog crate's ListObjectives and ListCommonControls handlers - the stored ObjectiveSummary and CommonControlSummary rows must be the full published catalog, keyed by the published ARNs, carrying the published Name/Description verbatim, so that a filtered listing returns exactly the catalogued membership. Status, paging and wire shape are already correct; this is a state/data-fidelity defect, not a serializer defect.
