# ds: the Managed Microsoft AD full-lifecycle chain (create→Active, delete→gone) settles only after the probe that follows each call, so the directory-description/ENI/teardown scenario reaches no verdict inside the 60 s check budget

> _Note: this issue was identified against the code base at commit `de88c05476b7f65268320bb33e4dfb6016cc8d82`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
DescribeDirectories

## Description
Cause 1 of 1: the ds Managed Microsoft AD lifecycle scenario ds.simple-ad-small-lifecycle-to-active-then-deleted is killed with "Check timed out after 60.0s" while asleep in a poll loop, so not one of its ~40 assertions on the DirectoryDescription, the directory's ENIs/security group, or the post-delete not-found classes is ever evaluated. Failing check id: ds.simple-ad-small-lifecycle-to-active-then-deleted.

AWS: the stages are modelled — Smithy com.amazonaws.directoryservice#DirectoryStage = [Requested, Creating, Created, Active, Inoperable, Impaired, Restoring, RestoreFailed, Deleting, Deleted, Failed, Updating]. CreateMicrosoftAD input {Name @required pattern ^([a-zA-Z0-9]+[\\.-])+([a-zA-Z0-9])+$, Password @required @sensitive, VpcSettings @required, ShortName, Description @length(0,128), Edition, NetworkType} / output {DirectoryId pattern ^d-[0-9a-f]{10}$}, errors ClientException(400), DirectoryLimitExceededException(400), InvalidParameterException(400), UnsupportedOperationException(400), ServiceException(500). DescribeDirectories input {DirectoryIds, NextToken, Limit} / output {DirectoryDescriptions, NextToken}, errors ClientException(400), EntityDoesNotExistException(400), InvalidNextTokenException(400), InvalidParameterException(400), ServiceException(500). DeleteDirectory input {DirectoryId @required} / output {DirectoryId}, errors ClientException(400), EntityDoesNotExistException(400), ServiceException(500). GetSnapshotLimits input {DirectoryId @required} / output {SnapshotLimits}, same three errors. So AWS accepts the call and answers BEFORE the directory settles, and exposes the walk through DescribeDirectories; for the wall clock there is recorded behavior only (on real AWS the create leg alone takes tens of minutes, so the 60 s per-check ceiling is the emulator environment's, not the recording's).

Emulator: no status, error-code, message or shape divergence is reported for this check — the only output is "Check timed out after 60.0s". The scenario owes TWO clock-owed legs and probes each immediately after the call that starts it: create_microsoft_ad then poll describe_directories at 30 s intervals until Stage is terminal/'Active' (30 s owed, because the first probe lands on a transient stage and the settled value becomes observable only after the sleep), then delete_directory then poll describe_directories at 30 s intervals until the id reads back gone (another 30 s owed) — 60 s of pure sleeping inside a 60 s ceiling, before the ec2 ENI/security-group reads and the three not-found probes that follow. This is the same clock-owed-transition mechanism already filed for other ds legs in 20261113T164150Z-ds-3-net-new-causes-the-msad-stage.md (directory-data-access toggles, RemoveRegion/DeleteDirectory, the trust state machine) and in its siblings 20261111T120514Z-ds-the-directory-data-access-disable-re-enable-c3f4bd.md, 20261110T232837Z-ds-the-directory-data-access-disable-re-enable.md, 20261107T061500Z-ds-data-access-cycle-check-cannot-fit-its-sixty-second-budget.md and 20261111T085740Z-ds-the-ldaps-enable-disable-and-directory-data.md; the replay report does NOT mark this check as OWNED by any of them, so none of them covers it, and it should be resolved as one work item with them.

Why: a client gets no verdict at all on the single richest ds contract in the suite. Unverified today: that a Standard Managed Microsoft AD reaches Stage 'Active' only through the legal transient stages {Requested, Creating, Created}; that the settled DirectoryDescription echoes Name/ShortName/Edition and reports the derived Size 'Small', Type 'MicrosoftAD', SsoEnabled false, Alias defaulting to the DirectoryId, an AccessUrl whose leading label is the DirectoryId, LaunchTime and StageLastUpdatedDateTime populated with StageLastUpdatedDateTime >= LaunchTime, DesiredNumberOfDomainControllers 2, a non-empty OsVersion, RegionsInfo.PrimaryRegion equal to the request region with no AdditionalRegions, NetworkType 'IPv4' with no DnsIpv6Addrs, and never the password; that VpcSettings reports the caller's VpcId/SubnetIds, exactly the two distinct AvailabilityZones of those subnets, and an sg- SecurityGroupId; that DnsIpAddrs are exactly the private addresses of the two ENIs ds itself created, one per subnet, described 'AWS created network interface for directory <directoryId>', all inside the VPC CIDR and all in the directory's own group, which is named '<directoryId>_controllers', lives in the caller's VPC, and carries ingress scoped only to the VPC CIDR; and the whole post-delete refusal taxonomy — DescribeDirectories on a deleted id SUCCEEDS with an empty DirectoryDescriptions list while a well-formed but never-issued id is refused HTTP 400 / Error.Code 'EntityDoesNotExistException' with the invalid-id sentence 'Invalid directory ID(s): <directoryId>. : RequestId: <requestId>' (fixed text 'Invalid directory ID(s): ', '. : RequestId: '; the id comes from the request and the RequestId from the response), whereas a second DeleteDirectory and a GetSnapshotLimits on the deleted id are each refused HTTP 400 / 'EntityDoesNotExistException' with the does-not-exist sentence "Directory: '<directoryId>' does not exist. : RequestId: <requestId>" (fixed text "Directory: '", "' does not exist. : RequestId: "; the id from the request, the RequestId from the response) — and that deletion releases the ENIs. No run's literal id, address or RequestId is part of any of these requirements. An emulator that never reached 'Active', that passed through an illegal stage, that bookkept DnsIpAddrs with no backing ENIs, that refused a deleted id from DescribeDirectories, or that conflated the invalid-id and does-not-exist wordings would pass unnoticed today.

Fix: this is not an operation-handler response defect — no ds handler is reported answering wrongly in this check. The owner is the ds state machine's clock-owed-transition contract where it meets the suite's per-check ceiling: either shorten the transition spans the ds directory state applies to the create chain (Requested/Creating/Created -> Active) and the delete chain (Deleting -> gone) so a settled value is observable on the client's FIRST probe after the call (accepting that the transient stages and any refusal that depends on them, e.g. DirectoryUnavailableException, stop being observable and that in-tree suites pinning them must be loosened), or the harness's per-check budget and poll intervals for this scenario. Resolve together with 20261113T164150Z-ds-3-net-new-causes-the-msad-stage.md and its siblings listed above.
