Modelled errors: NoSuchKey (errorKind client, httpError 404, 'The specified key does not exist.') and InvalidObjectState (403) — AWS serves NoSuchKey only when the key is genuinely absent. That a file written through the mount IS such a key is recorded behavior only: the recording shows the object readable at the key under the file system's prefix with HTTP 200, the body exactly the bytes written, accept-ranges 'bytes', a Last-Modified / ETag / x-amz-version-id for the new object, x-amz-server-side-encryption 'AES256', a CRC64NVME checksum with x-amz-checksum-type 'FULL_OBJECT', a Content-Type derived from the file (text/plain for the recorded .txt), and the POSIX/file-system attributes s3files stamps as user metadata: x-amz-meta-file-owner, -file-group, -file-permissions, -file-btime/-atime/-mtime, -fs-id (the writing file system's id with its generation/inode suffix) and x-amz-meta-user-agent 'aws-s3-files'. Emulator: the same GET answers HTTP 404 with an XML error body {'Error': {'Code': 'NoSuchKey', 'Message': 'The specified key does not exist.', 'Key': <requested key>, 'RequestId': ..., 'HostId': ...}} and content-type 'application/xml', on every attempt until the replay's poll is capped (replay: "status: expected 200, got 404", "$: poll capped at 60s", "$: poll: status 404 not in [200] after 5 attempt(s)"); none of accept-ranges, last-modified, etag, x-amz-version-id, x-amz-server-side-encryption, x-amz-checksum-crc64nvme, x-amz-checksum-type or any x-amz-meta-* header is present, and content-type is the error body's 'application/xml' instead of 'text/plain'. Message anatomy: 'The specified key does not exist.' is NoSuchKey's fixed AWS text and 'Key' is the key taken from the request, so the refusal is correctly WORDED — the defect is that it is served at all for a key AWS has by this point; RequestId/HostId are per-run values and are not part of this finding. Hypothesis: there is no s3files-to-S3 write-through path, so nothing the file system receives is ever materialised as an object; in this fixture the in-guest write is additionally never performed because the SSM Run Command invocation that mounts and writes ends Failed with ResponseCode 127 (steps task#28/task#29 of this fixture, owned by the two ssm issues named above).

Why: the entire premise of s3files is that file-system writes are S3 objects. A client that writes through the mount and then reads the key with the S3 API — the canonical round-trip, and how data-landing checks, ETL hand-offs and lifecycle rules observe the data — gets a hard 404 forever and concludes the data was lost; SDK retries cannot help and an 'object exists' precondition fails. Because the body never arrives, every downstream assertion on the object (byte equality, CRC64NVME/FULL_OBJECT checksum reporting, SSE state, the inferred content type, and the POSIX/provenance metadata a permission-preserving restore reads back off x-amz-meta-file-* / x-amz-meta-fs-id) is unreachable as well.

Fix: the s3files data-plane write-through into S3 object state and the object-metadata stamping it must perform (the s3files file-system write path and the S3 object store it writes into), so the key exists with its bytes, size, etag, inferred content type, version id, SSE state and CRC64NVME/FULL_OBJECT checksum, plus the x-amz-meta-file-*/fs-id/user-agent user metadata. The GetObject handler's 404/NoSuchKey path needs no change once the object is present; any residual gap in projecting those members belongs in the GetObject response-header serializer. The ssm Run Command failure named above is a prerequisite for the write to be attempted at all.
