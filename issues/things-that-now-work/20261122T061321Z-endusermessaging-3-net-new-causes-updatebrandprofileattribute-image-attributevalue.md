# endusermessaging: 3 net-new causes — UpdateBrandProfileAttribute IMAGE attributeValue refusal re-worded, ListJobs operationType refusal re-worded, and the media download served after an attachment replacement omits Content-Disposition

> _Note: this issue was identified against the code base at commit `b20300340ddfd95fa2f862f6c06bba5164a73eba`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
UpdateBrandProfileAttribute

## Description
Three independent divergences survive on the endusermessaging surface after the scaffold-stub and already-owned clusters are excluded. This bundle carries 3 net-new causes; ALL 3 must be closed before the issue is submitted.

Model evidence used throughout (services/service-com-amazonaws-endusermessaging-endusermessaging/smithy-model/com-amazonaws-endusermessaging-endusermessaging.json): UpdateBrandProfileAttribute PUT /v1/brand-profiles/{brandProfileId}/attributes/{attributeName}, @idempotent, input attributeValue (BrandProfileAttributeValue @length 0..4096, @sensitive) and attachmentBody (Blob) both optional, output requires attributeName/attributeType/createdAt/updatedAt and carries mediaContentType/mediaSizeBytes; errors ValidationException (httpError 400, defaulted), ConflictException 409, ResourceNotFoundException 404. ListJobs GET /v1/jobs, @readonly, @paginated(inputToken nextToken, items jobs); operationType is an httpQuery member targeting JobOperationType, a plain string @length 1..128 — NOT a modeled enum, documented only as "The type of mutating operation that created the job.", so the legal set is enforced at runtime by the service; errors ValidationException (400, defaulted), AccessDeniedException 403, ThrottlingException 429, InternalServerException 500. The media download URL is a data-plane endpoint outside the Smithy model (recorded behavior only).

Cause 1 of 3 — UpdateBrandProfileAttribute refuses a non-S3 attributeValue on an IMAGE attribute with the wrong sentence.
AWS: updating an IMAGE attribute with an attributeValue that is not an s3://bucket/key URL is refused with HTTP 400 ValidationException whose message is exactly "Either attributeValue (S3 URL) or attachmentBody must be provided for IMAGE attribute". The whole sentence is fixed text — nothing from the request or from state is interpolated on the update path (unlike the create path, which names the attribute). The refused update must be a no-op: a following GetBrandProfileAttribute must still report the previously uploaded media's mediaContentType and mediaSizeBytes unchanged. Recorded behavior only for the sentence itself; the model states only that attributeValue is an optional 0..4096 string and that ValidationException is the 400 refusal for this operation.
Emulator: refuses with the right code (ValidationException) but the message "attributeValue cannot be provided for IMAGE attribute" — a different sentence that frames attributeValue as never allowed on an IMAGE attribute rather than as requiring the S3-URL form or an attachment.
Why: a client or test matching AWS's refusal text does not recognise the refusal, and the message tells the user the wrong rule — that attributeValue is forbidden on IMAGE attributes, when in fact an s3:// URL is the legal way to point an IMAGE attribute at media.
Fix: the UpdateBrandProfileAttribute handler's input-validation stage — emit the service's update-path sentence for the IMAGE attributeValue/attachmentBody check. NOTE: open issue 20261117T003651Z-endusermessaging-brand-profile-attributes-8-net-new-causes.md (cause 2) describes the create-path S3-URL and exclusivity gates and quotes this update-path sentence, but it does not own this check's replay key any more — the create-path assertion it was keyed on now passes and the check fails further down, on the update-path message. Close this cause against this check.
Traces: endusermessaging.image-attribute-value-must-be-an-s3-url.

Cause 2 of 3 — ListJobs' unknown-operationType refusal is re-worded (different sentence, different value list formatting).
AWS: an operationType outside the four asynchronous job operations is refused with HTTP 400 ValidationException whose message is "Invalid value for 'operationType': unknown operation type: <value>. Valid values: CreateRegistrationsFromBrandProfile | UpdateRegistrationsFromBrandProfile | CreateBrandProfileFromRegistration | UpdateBrandProfileFromRegistration". Fixed text: "Invalid value for 'operationType': unknown operation type: ", then ". Valid values: ", then the four operation names in that order separated by " | "; only <value> is taken from the request. Because JobOperationType is an unconstrained string in the model, this is a runtime gate, not a modeled enum refusal (recorded behavior only for the wording). A ListJobs filtered by a brand profile that ran no job answers jobs == [] (that part passes).
Emulator: answers ValidationException with "Invalid operationType 'CreateBrandProfile'. Supported values: CreateBrandProfileFromRegistration, CreateRegistrationsFromBrandProfile, UpdateBrandProfileFromRegistration, UpdateRegistrationsFromBrandProfile" — a different lead-in, the rejected value in single quotes instead of after a colon, "Supported values" instead of "Valid values", and the four names comma-separated in a different (alphabetical) order.
Why: clients and tests that match AWS's message text do not recognise the refusal, and a caller parsing the valid-value list out of the message gets a different separator and ordering than AWS produces.
Fix: the ListJobs handler's input-validation stage (the operationType value check) — emit the service's sentence with the pipe-separated list in the service's order.
Traces: endusermessaging.list-jobs-rejects-unknown-operation-type.

Cause 3 of 3 — the media download endpoint serves no Content-Disposition header after an attachment replacement.
AWS: after UpdateBrandProfileAttribute replaces an IMAGE attribute's media with a new attachmentBody, GetBrandProfileAttribute returns a mediaDownloadUrl that answers HTTP 200 with the replacement bytes, Content-Type equal to the sniffed type of the new bytes, and Content-Disposition 'inline; filename="<attributeName>.<ext>"' — "inline; filename=" is fixed text, <attributeName> comes from the attribute in state and <ext> is the extension of the sniffed media type (jpeg/png/pdf). Recorded behavior only: the download endpoint is outside the Smithy model.
Emulator: serves the replacement bytes and the correct Content-Type but no Content-Disposition header at all (absent), on the post-update download just as on the post-create download.
Why: a browser or client that relies on the header to name and inline-render the download gets an unnamed octet download instead, so a save/preview flow that works against AWS breaks — and here specifically a replaced attachment is served nameless.
Fix: the brand-profile-attribute media download handler's response serializer (the data-plane route mediaDownloadUrl points at) — set Content-Disposition from the attribute name and the sniffed type's extension, on every download including those served after an update. NOTE: 20261117T003651Z-endusermessaging-brand-profile-attributes-8-net-new-causes.md cause 8 describes the same missing header on the post-CREATE download and owns only that check; it does not carry this check's replay key, so this cause must be closed against this check too.
Traces: endusermessaging.update-media-attribute-attachment-replaces-served-bytes.
