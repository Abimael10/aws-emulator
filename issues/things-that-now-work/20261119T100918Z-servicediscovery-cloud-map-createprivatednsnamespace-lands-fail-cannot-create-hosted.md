# Cloud Map: CreatePrivateDnsNamespace lands FAIL/CANNOT_CREATE_HOSTED_ZONE ('<name> is reserved by AWS!') for any single-label namespace name, and a CloudFormation PrivateDnsNamespace still reaches CREATE_COMPLETE after that failure

> _Note: this issue was identified against the code base at commit `e91c89e9d6482fa7ae1cb641524eb980150715bc`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
CreatePrivateDnsNamespace

## Description
TWO net-new root causes in the servicediscovery (Cloud Map) emulator, both grounded in failing checks of the behavioral replay against this bootstrapped service. They are numbered below and EACH must be closed before this issue is submitted: Cause 1 of 2 and Cause 2 of 2, each with its own failing check ids. Model citations use services/service-com-amazonaws-servicediscovery-route53autonaming-v20170314/smithy-model/com-amazonaws-servicediscovery-route53autonaming-v20170314.json.

Cause 1 of 2: a private DNS namespace whose Name is a SINGLE DNS label (no dot) can never be created — the asynchronous CREATE_NAMESPACE operation always lands FAIL with ErrorCode CANNOT_CREATE_HOSTED_ZONE and ErrorMessage '<the requested name> is reserved by AWS!', and the staged namespace is rolled back.
AWS: Smithy CreatePrivateDnsNamespace{Name (required), CreatorRequestId, Description, Vpc (required), Properties, Tags} -> {OperationId}; Name targets NamespaceNamePrivate with @length 0..253 and @pattern ^(?!arn:)[!-~]{1,253}$ — printable ASCII, a dot is NOT required, so a one-label name such as 'myns-abc123' is a modelled-valid namespace name. Operation.Status is one of SUBMITTED|PENDING|SUCCESS|FAIL and Operation.ErrorCode's documented values include CANNOT_CREATE_HOSTED_ZONE (for a zone AWS genuinely cannot create). Recorded behavior: CreatePrivateDnsNamespace(Name='<one label>', Vpc=<a VPC of the account>) is accepted and its CREATE_NAMESPACE operation is observed SUBMITTED/PENDING and then SUCCESS, with Targets.NAMESPACE naming a namespace that GetNamespace/CreateService/RegisterInstance/DiscoverInstances then drive normally — Cloud Map backs the namespace with a PRIVATE Route 53 hosted zone, and a private zone's name need not be a registrable multi-label domain. Only the PUBLIC-zone rule ('you can't create a hosted zone for a top-level domain') restricts one-label names.
Emulator: the create call returns 200 + OperationId, then GetOperation reports {'Type': 'CREATE_NAMESPACE', 'Status': 'FAIL', 'ErrorCode': 'CANNOT_CREATE_HOSTED_ZONE', 'ErrorMessage': '<requested name> is reserved by AWS!'} and the namespace record is removed by the operation's rollback effect. The refusal comes from the backing Route 53 CreateHostedZone path, which applies the top-level-domain reservation rule to EVERY zone, private ones included: a name of fewer than two labels is refused InvalidDomainName with the message '<requested name>' + the fixed text ' is reserved by AWS!'. The fixed text of that message is ' is reserved by AWS!' and its only variable part is the name copied from the request; the whole refusal must simply not happen for a private (VPC-associated) zone.
Why: every Cloud Map workflow that names its namespace with a single label — the common 'internal'-style private namespace — is unusable against the emulator: the namespace never exists, so CreateService, RegisterInstance, GetService, GetInstance and DiscoverInstances on it cannot run at all, and a client that polls the create operation sees a terminal FAIL for input AWS accepts. Four otherwise-unrelated checks fail at this one call before reaching what they test (SOA/TTL persistence, the RegisterInstance required-attribute refusal, the instance lifecycle).
Fix: the zone-name validation on the private-zone path — gate the 'fewer than two labels is reserved' refusal in Route 53's CreateHostedZone handler on the zone being PUBLIC (no VPC named), so the namespace-create hop (crate::state::route53_zone::create_namespace_zone, called from CreatePrivateDnsNamespace's handler) gets ZoneCreation::Created for a one-label private namespace name and the CREATE_NAMESPACE operation settles SUCCESS with the zone id on the namespace record.
Traces: servicediscovery.async-operation-completes-without-polling-action, servicediscovery.e2e-service-discovery-full-flow, servicediscovery.namespace-dns-record-ttl-persists, servicediscovery.register-instance-missing-required-dns-attribute-rejected, servicediscovery.deploy-private-dns-namespace-via-cloudformation.

Cause 2 of 2: a CloudFormation stack whose AWS::ServiceDiscovery::PrivateDnsNamespace create FAILS asynchronously still reaches CREATE_COMPLETE and publishes a NamespaceId output for a namespace that does not exist.
AWS: recorded behavior only (no Smithy statement) — a CloudFormation resource that wraps an asynchronous Cloud Map create waits for that operation: AWS::ServiceDiscovery::PrivateDnsNamespace only reaches CREATE_COMPLETE once the CREATE_NAMESPACE operation reaches SUCCESS, and a namespace create that lands FAIL fails the resource, so with OnFailure=DELETE the stack never reports CREATE_COMPLETE and never publishes a Namespace Id/Arn output. In the recording the stack reaches CREATE_COMPLETE and the namespace it created is immediately resolvable: DiscoverInstances(NamespaceName=<the stack's namespace name>, ServiceName=<the stack's service name>, HealthStatus='ALL') answers the registered instance with AWS_INSTANCE_IPV4 as declared.
Emulator: the stack reaches CREATE_COMPLETE, DescribeStacks reports Outputs NamespaceId and ServiceId, yet DiscoverInstances on that namespace name is refused NamespaceNotFound (HTTP 404) — the namespace the outputs name was rolled back by the FAILed CREATE_NAMESPACE operation of cause 1, and nothing propagated that failure into the stack. Hypothesis: the AWS::ServiceDiscovery::PrivateDnsNamespace resource provider treats the synchronous 200 + OperationId as success and never polls GetOperation for the terminal status.
Why: a stack that reports CREATE_COMPLETE for a resource that was never created is the worst possible outcome for any deploy — every consumer of the stack's NamespaceId/ServiceId output (ECS serviceRegistries, a registering task, a dependent stack) proceeds against an identifier no Cloud Map read resolves, and no rollback or failure signal ever reaches the operator.
Fix: the AWS::ServiceDiscovery::PrivateDnsNamespace resource provider in the CloudFormation emulator — after CreatePrivateDnsNamespace, poll GetOperation until the CREATE_NAMESPACE operation is terminal and fail the resource (carrying the operation's ErrorCode/ErrorMessage) when it lands FAIL, so the stack rolls back instead of completing. This cause stays even once cause 1 is fixed: any namespace create that fails for another reason (an absent Vpc, which the same handler also settles FAIL/CANNOT_CREATE_HOSTED_ZONE) must fail the stack.
Traces: servicediscovery.deploy-private-dns-namespace-via-cloudformation.

Neither cause is covered by the open issue 20261104T035823Z-servicediscovery-cloud-map-5-net-new-behavioral-causes-same.md: that issue lists servicediscovery.register-instance-missing-required-dns-attribute-rejected for a DIFFERENT failure of that check (RegisterInstance accepting an instance with no AWS_INSTANCE_IPV4), which the check can no longer reach because its namespace create now fails here.
