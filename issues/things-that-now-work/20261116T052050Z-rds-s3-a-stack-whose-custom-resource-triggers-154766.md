# rds__s3: a stack whose Custom:: resource triggers RDS StartExportTask never reaches a terminal status, so the snapshot-export-via-custom-resource path hangs instead of answering

> _Note: this issue was identified against the code base at commit `73ee5db70c54544c27a351cd5968d4682ba0e095`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
StartExportTask

## Description
One net-new root cause in the rds__s3 behavioral suite: this is the only failing rds__s3 check in this replay that the report marks neither OWNED by an open issue nor ALREADY FILED as blocked by an unimplemented operation.

Duplicate-risk note for triage: the open issue 20261107T093145Z-rds-s3-a-stack-whose-custom-resource-triggers.md records this very check id in its Issue-Trace-Ids, but its stored replay key (`rds__s3.deploy-cfn-rds-export-task-custom-resource-positive|_poll_until#15|Timeout|time.sleep(interval_s)`) no longer matches the key this replay produced, which is why the suite did not mark the check owned and why it is re-filed here rather than dropped. If triage confirms the keys describe the same stall, merge this into that issue instead of fixing it twice. Also related but NOT covering it: 20261108T043811Z-cloudformation-s3-a-lambda-backed-cloudformation-custom-resource-never-completes.md and 20261112T140000Z-cloudformation-hooks-are-never-enforced-and-a-lambda-backed-custom-resource-never-completes.md describe the same class of non-settling Lambda-backed Custom:: resource under the cloudformation__s3 / cloudformation headings, with different replay keys.

Cause 1 of 1: CreateStack on a template containing a `Custom::RdsExportTrigger` resource whose ServiceToken is an inline python3.12 Lambda that calls RDS StartExportTask never reaches a terminal CREATE status, so nothing downstream of the stack is observable.

AWS: a CloudFormation stack containing a Lambda-backed `Custom::<Type>` resource always terminates. CloudFormation invokes the ServiceToken function with the Create provider request, the provider PUTs its {"Status": "SUCCESS"|"FAILED", "PhysicalResourceId", "Data"} document to the presigned ResponseURL, and the stack settles: CREATE_COMPLETE when the provider answers SUCCESS, or CREATE_FAILED followed by ROLLBACK_COMPLETE when it answers FAILED or does not answer within the resource's timeout — in which case the provider's Reason appears as the custom resource's CREATE_FAILED ResourceStatusReason in DescribeStackEvents. After CREATE_COMPLETE, Fn::GetAtt on the custom resource resolves the key the provider returned in Data (here `S3Arn`), and the stack Outputs carry it. On the RDS leg, Smithy (com-amazonaws-rds-amazonrdsv19) models StartExportTask with required ExportTaskIdentifier, SourceArn, S3BucketName, IamRoleArn and KmsKeyId, and with the modeled refusals DBSnapshotNotFoundFault (404), DBClusterSnapshotNotFoundFault (404), ExportTaskAlreadyExistsFault (400), IamRoleNotFoundFault (404), IamRoleMissingPermissionsFault (400), InvalidS3BucketFault (400), InvalidExportOnlyFault (400), InvalidExportSourceStateFault (400) and KMSKeyNotAccessibleFault (400); on success it returns an ExportTask whose DescribeExportTasks Status progresses to a terminal COMPLETE (or FAILED/CANCELED with FailureCause). Either way the provider gets an answer, so the stack can always settle. Each of those refusals carries the AWS sentence for its class as fixed text, with the snapshot ARN, role ARN, bucket name or KMS key id taken from the request — the identifiers in any one recording are template fillers, not part of the requirement.

Emulator: not one of the check's assertions is reached. The replayed result is only `Error: Check timed out after 60.0s`. The exercised flow is CreateDBSubnetGroup -> CreateDBInstance -> poll DescribeDBInstances to `available` -> CreateDBSnapshot -> poll DescribeDBSnapshots to `available` -> CreateStack (AWS::S3::Bucket, AWS::KMS::Key, an export role trusting export.rds.amazonaws.com, a lambda role, an inline python3.12 AWS::Lambda::Function, and the Custom::RdsExportTrigger) -> poll DescribeStacks for a terminal status -> read Outputs `BucketName` (Ref) and `ResolvedS3Arn` (Fn::GetAtt [TriggerResource, S3Arn]) -> poll DescribeExportTasks for a terminal status -> ListObjectsV2. No terminal stack status, no resolved Fn::GetAtt Output, no terminal export status and no object listing is ever observed; the check is still polling when its budget expires. This is the only rds__s3 check carrying a Custom:: resource and the only one that hangs rather than failing on an assertion or an error response, so the stall is specific to the custom-resource settling path and not to the suite budget. Hypothesis: the Lambda-backed Custom:: provider is never invoked, or its ResponseURL callback is never ingested, so the resource stays non-terminal and DescribeStacks keeps answering a non-terminal CREATE status; StartExportTask's own state is a secondary contributor. Note that even a refused StartExportTask must not hang: the provider would answer FAILED and the stack would roll back to ROLLBACK_COMPLETE.

Why: a client that deploys a stack is entitled to a stack that finishes. Here CreateStack never resolves, so a CI pipeline, a CDK/CFN deploy or any wait-for-stack poller blocks indefinitely instead of seeing a completed stack or a rollback with an actionable CREATE_FAILED ResourceStatusReason. Everything downstream is unreachable: Fn::GetAtt yields no S3 ARN, the export task is never started or observable through DescribeExportTasks, and no S3 objects are written. An unbounded wait is also the worst failure mode for an emulator, because there is no error to diagnose.

Fix: the CloudFormation custom-resource provisioner that drives `Custom::<Type>` resources with a Lambda ServiceToken — the component that invokes the provider function with the Create request, accepts the provider's response document on the presigned ResponseURL, records its Data for Fn::GetAtt, and transitions the resource to CREATE_COMPLETE or to CREATE_FAILED with a rollback. It must bound the wait so a provider that never answers lands the stack in a terminal status rather than leaving it non-terminal. Paired with it, the RDS StartExportTask handler and the export-task state DescribeExportTasks reports must answer — a modeled ExportTask with a progressing Status, or one of the modeled faults above — so the provider has something to report.
