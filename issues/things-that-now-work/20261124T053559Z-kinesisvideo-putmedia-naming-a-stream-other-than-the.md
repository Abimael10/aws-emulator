# kinesisvideo: PutMedia naming a stream other than the one its ingest endpoint was discovered for is refused 400 InvalidEndpointException (with the model's documentation prose as the message) instead of 404 ResourceNotFoundException "...not found or not active."

> _Note: this issue was identified against the code base at commit `3c85b1e84177fad89070056cfc3db9067a84c48d`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
PutMedia

## Description
REOPENS 20261107T191028Z-kinesisvideo-3-net-new-root-causes-the-discovered.md: its fix left the call refused. That issue's Cause 2 carried this exact check's replay key and asked for "HTTP 404, x-amzn-ErrorType: ResourceNotFoundException, an acknowledgement Message containing the fixed clause 'not found or not active', and nothing persisted". The acceptance (200 + PERSISTED) it reported is gone — the ingest host now does scope requests to a stream — but the refusal it installed is the wrong one, so the call this issue was closed on is still refused with a status and an error class AWS never returns here.

One root cause, grounded in 1 failing behavioral check.

=== Cause 1 of 1: a PutMedia request arriving on a stream's ingest host but naming a different stream (or a name that exists nowhere) is classified as a wrong-endpoint fault (HTTP 400 InvalidEndpointException) instead of an unresolvable-stream fault (HTTP 404 ResourceNotFoundException), and the message it carries is the Smithy shape's documentation prose rather than an AWS refusal sentence ===
AWS: recorded behavior only for the ingest front end — PutMedia is bound by no model (smithy_query on services/service-com-amazonaws-kinesisvideomedia-awsacuityinletservice/smithy-model/com-amazonaws-kinesisvideomedia-awsacuityinletservice.json reports operation 'PutMedia' not found, GetMedia only; the kinesisvideo control model binds no /putMedia path either). The refusal CLASS is modeled, and the two classes are distinct: Smithy com.amazonaws.kinesisvideomedia#ResourceNotFoundException is errorKind client, httpError 404, member Message, doc "Status Code: 404, The stream with the given name does not exist" (com.amazonaws.kinesisvideo#ResourceNotFoundException likewise 404, "Amazon Kinesis Video Streams can't find the stream that you specified"), while com.amazonaws.kinesisvideomedia#InvalidEndpointException is httpError 400 and means the CALLER used the wrong endpoint for the stream it named. A DataEndpoint is discovered per stream (GetDataEndpoint takes StreamName/StreamARN precisely so the host it returns belongs to that stream), so a request whose x-amzn-stream-name does not resolve to an active stream served by this host is a stream-resolution failure: the recording shows HTTP 404, response header x-amzn-ErrorType: ResourceNotFoundException, and an error acknowledgement whose Message contains the fixed clause "not found or not active" (AWS's sentence for this class is "The requested stream is not found or not active." — that sentence is entirely fixed text; the stream name appears only in the request's x-amzn-stream-name header, never interpolated into the message). The same 404 refusal is recorded for a name that exists nowhere. Nothing is persisted by the refused request: neither the named stream nor the host's own stream gains a fragment.
Emulator: the request is answered HTTP 400 with an empty HTTP body and a single acknowledgement object carrying only {"Message": "Caller used wrong endpoint to write data to a stream. On receiving such an exception, the user must call GetDataEndpoint with AccessMode set to \"READ\" and use the endpoint Kinesis Video returns in the next GetMedia call."} — no EventType member, no error code, and the status is the InvalidEndpointException 400 rather than 404. Two separate divergences in one refusal: (a) the wrong error class/status (400 InvalidEndpointException where AWS returns 404 ResourceNotFoundException, and the check never reaches its x-amzn-ErrorType assertion because the status already differs); (b) the message is verbatim the documentation string of the Smithy InvalidEndpointException shape ("Status Code: 400, Caller used wrong endpoint to write data to a stream. On receiving such an exception, the user must call GetDataEndpoint with AccessMode set to \"READ\" and use the endpoint Kinesis Video returns in the next GetMedia call."), i.e. shape prose addressed to a reader of the API reference, emitted on the wire as the refusal sentence; AWS's wire sentence for the class this request belongs to is the fixed "The requested stream is not found or not active." Replay: AssertionError: PutMedia naming another ACTIVE stream of this account on <this stream>'s ingest host expected HTTP 404, got 400 (acks [{'Message': 'Caller used wrong endpoint to write data to a stream. ...'}]). (Stream names and ports in that output are per-run values and are not part of the requirement.)
Why: a producer cannot tell "the stream you named does not exist / is not active" from "you are talking to the wrong host", and the two have opposite remedies. 404 ResourceNotFoundException is the signal to stop writing and re-create or correct the stream name; 400 InvalidEndpointException is the signal to call GetDataEndpoint again and retry the same fragment against a new host. A producer receiving the 400 re-discovers an endpoint it was already correctly using and retries forever for a stream that will never resolve, while the ResourceNotFoundException handler (re-create the stream, fail the session) never fires. 400 is also a client-fault class most SDK/application retry layers treat as non-retryable, so the media is dropped with a diagnosis that names the wrong subsystem. A client matching the documented "not found or not active" text, or branching on x-amzn-ErrorType, matches nothing. Shipping shape documentation as the message also leaks a fabricated sentence (and the "Status Code: 400" / GetMedia READ-mode advice is nonsense for an ingest write) to anything that logs or parses it.
Fix: the PutMedia ingest handler's request-admission/stream-resolution stage on the announced data plane, and the acknowledgement/error serializer it refuses through. Resolving x-amzn-stream-name/x-amzn-stream-arn against the stream registry must distinguish the two outcomes: a name that does not resolve to an active stream this host serves is refused HTTP 404 with x-amzn-ErrorType: ResourceNotFoundException and an error acknowledgement whose Message is the fixed "The requested stream is not found or not active." (with an EventType of the acknowledgement stream's error kind), persisting nothing to either stream; InvalidEndpointException 400 must stay reserved for the wrong-host case the recordings put it on. The refusal sentence must come from the handler's error table, not from the Smithy shape's documentation trait.
Traces: kinesisvideo.putmedia-naming-another-stream-on-this-ingest-host-rejected (both halves of the check — another ACTIVE stream of the account, and a stream name that exists nowhere — refuse this way; the positive control on the host's own stream still answers 200 with two PERSISTED fragments).
