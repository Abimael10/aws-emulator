# Workload catalog is seeded with invented entries: list reads diverge and real workloads 404

> _Note: this issue was identified against the code base at commit `48ab13f61564abe631f24038b106fee51cab80bf`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
ListWorkloadDeploymentPatterns

## Description
The Launch Wizard workload catalog the emulator serves is emulator-authored rather than the AWS-published catalog: the set of workloads is incomplete, the deployment patterns under each workload carry generated names/versions/display text instead of the published ones, and workloads that exist in the service are absent altogether, so a pattern listing for them is refused ResourceNotFoundException (404) where AWS answers 200 with a pattern list. Every read of the catalog therefore diverges, and the catalog is the entry point of every Launch Wizard flow (a client picks a workload, then a deployment pattern, then a pattern version, before it can create a deployment). 5 causes.

NOTE: the only prior issue covering list-shaped catalog divergences on this service token, 20261029T234833Z-launch-wizard-catalog-returns-placeholder-workload-data-listworkloads.md, is RESOLVED, and the replay still reports every one of these steps as diverging with no owning open issue. The two open launchwizard issues (20261109T152700Z-launchwizard-getworkload-serves-an-off-emulator-icon-url-and.md and 20261110T073938Z-launchwizard-deployment-pattern-version-responses-ignore-pagination-and-omit.md) own the GetWorkload / pattern-version steps on the 'launchwizard' token and cover none of the causes below.

--- Cause 1 of 5: a pattern listing for a workload the catalog does not contain is refused 404 instead of returning the workload's patterns (fixture launch-wizard-catalog-list-workload-deployment-patterns, step task#4; cluster also covers task#5, task#6, task#7) ---
AWS: Smithy: ListWorkloadDeploymentPatterns, POST /listWorkloadDeploymentPatterns, success 200 with output member workloadDeploymentPatterns: WorkloadDeploymentPatternDataSummaryList; errors InternalServerException (500), ResourceNotFoundException (404, documented 'The specified workload or deployment resource can't be found.'), ValidationException (400). ResourceNotFoundException is reserved for a workloadName that names no workload in the service catalog. Which workloads the service publishes is recorded behavior only: the recording shows the catalog containing solution-style workloads (e.g. the AWS-Solutions distributed-load-testing workload) with several ACTIVE patterns each, returned 200.
Emulator: HTTP 404 for those workloadName values, and $.workloadDeploymentPatterns absent from the body, for four distinct workloads in the one replayed task sequence (expected 200 with a non-empty pattern list each time).
Why: the workload is a real, listable workload, so a client that walked the catalog (or that hard-codes a published workload name, as the Launch Wizard console and the solution deployment guides do) gets a not-found error for a workload the service offers. There is no way to proceed to a pattern version or a deployment for any of those workloads: the flow dead-ends at a 404 the client has no reason to retry or recover from, and a workload-coverage test reads the service as not offering the workload at all.
Fix: the workload-catalog seed in the launchwizard crate (services/service-com-amazonaws-launchwizard-launchwizard/src/state.rs) — the catalog must contain every workload the service publishes, with its deployment patterns, so ListWorkloadDeploymentPatterns resolves them 200 and the ResourceNotFoundException path is reached only for a genuinely unknown workloadName. The 404 handler itself is correct; its input set is wrong.
Traces: launch-wizard-catalog-list-workload-deployment-patterns#task#4 (representative), with task#5, task#6 and task#7 in the same cluster.

--- Cause 2 of 5: deployment patterns of the image-transformation solution workload carry invented names and versions (fixture launch-wizard-catalog-list-workload-deployment-patterns, step task#1) ---
AWS: Smithy: ListWorkloadDeploymentPatterns output member workloadDeploymentPatterns: list of WorkloadDeploymentPatternDataSummary {workloadName, deploymentPatternName (@length 1..256, @pattern ^[A-Za-z0-9][a-zA-Z0-9-]*$), workloadVersionName, deploymentPatternVersionName (both @length 5..30, @pattern ^(([A-Za-z0-9][a-zA-Z0-9-]*)|(\d+\.\d+\.\d+))$), displayName, description, status, statusMessage, accountConstraints}. The published values of those members are recorded behavior only: the recording shows the solution's ECS and Lambda architecture patterns identified by the solution's own pattern names and carrying the solution's own version string for both workloadVersionName and deploymentPatternVersionName, with display names and descriptions naming the solution.
Emulator: 200, but every entry's deploymentPatternName is an emulator-generated CamelCase token rather than the published pattern name, both version members carry one single generated version string reused across all workloads instead of the workload's own published version, and displayName/description are emulator-authored prose instead of the published text.
Why: deploymentPatternName and the two version names are identifiers a client feeds straight back into GetWorkloadDeploymentPattern, ListDeploymentPatternVersions and CreateDeployment. A client that names the published pattern or version (from a deployment guide, a template, or its own fixture) is refused not-found, while a client that round-trips the emulator's invented ids works only against the emulator — so neither direction validates anything about the real service.
Fix: the workload-catalog seed in the launchwizard crate (src/state.rs) — store the published pattern names, per-workload version strings and display text instead of deriving them from the workload name.
Traces: launch-wizard-catalog-list-workload-deployment-patterns#task#1.

--- Cause 3 of 5: the Active Directory workload publishes only two generated patterns instead of its full published set (fixture launch-wizard-catalog-list-workload-deployment-patterns, step task#2) ---
AWS: Smithy as in Cause 2; the pattern set per workload is recorded behavior only. The recording shows this workload publishing six ACTIVE patterns, distinguished by directory type (AWS-managed vs self-managed/on-premises extension) crossed with network topology (new VPC vs existing VPC), each with its own deploymentPatternName, displayName and description, and with the workload's own version string in both version members.
Emulator: 200 with only two entries, whose deploymentPatternName values are generated tokens that collapse the topology dimension entirely, and whose version members again carry the single shared generated version string. The four topology-specific patterns are absent.
Why: a client cannot select the deployment topology it needs, because the pattern that expresses it is not in the list; and the two entries it does see cannot be used by their published names. Any flow that enumerates patterns and picks one by published name or by topology fails against the emulator while succeeding against AWS.
Fix: the workload-catalog seed in the launchwizard crate (src/state.rs) — seed the complete published pattern set per workload rather than a generated pair.
Traces: launch-wizard-catalog-list-workload-deployment-patterns#task#2.

--- Cause 4 of 5: the SAP workload's patterns are incomplete and their display text is emulator-authored (fixture launch-wizard-catalog-list-workload-deployment-patterns, step task#3) ---
AWS: Smithy as in Cause 2; values recorded behavior only. The recording shows this workload publishing eight ACTIVE patterns; the pattern names and version strings match what the emulator serves, but each entry's displayName and description are the service's published text (e.g. the HA pattern described as a cross-Availability-Zone high-availability deployment, the multi-node pattern as a scale-out architecture, the single-node pattern as a scale-up architecture).
Emulator: 200 with the correct deploymentPatternName and version members for the patterns it does carry, but displayName and description reworded by the emulator for every entry, and only six of the eight published patterns present.
Why: displayName and description are the strings a console-like client renders for the operator who is choosing an architecture, so reworded text makes the catalog unrecognisable and breaks any assertion on the published wording; the two missing patterns are architectures a client simply cannot choose.
Fix: the workload-catalog seed in the launchwizard crate (src/state.rs) — carry the published displayName/description verbatim per pattern and seed the full pattern set, instead of generating prose from the pattern name.
Traces: launch-wizard-catalog-list-workload-deployment-patterns#task#3.

--- Cause 5 of 5: ListWorkloads returns an incomplete workload set with generated display names and without the workload's descriptive members (fixture launch-wizard-catalog-list-workloads, step task#1) ---
AWS: Smithy: ListWorkloads, POST /listWorkloads, success 200, output member workloads: WorkloadDataSummaryList; errors InternalServerException (500), ValidationException (400). The on-disk model's WorkloadDataSummary declares only workloadName, displayName, status and accountConstraints, so the rest is recorded behavior only: the recording shows each listed workload additionally carrying a description, a documentationUrl pointing at the workload's documentation, and a workloadOwnerDisplayName naming the publishing team, and shows a catalog of seven ACTIVE workloads (the Launch Wizard first-party workloads plus the AWS-Solutions ones) with their published display names.
Emulator: 200, but each entry carries only workloadName/displayName/status/accountConstraints — description, documentationUrl and workloadOwnerDisplayName are absent — the displayName for a solution workload is a generated placeholder built from the solution code rather than the solution's published name, and the catalog is shorter than the published one (the workloads behind Cause 1's 404s are missing here too).
Why: ListWorkloads is the first call of every Launch Wizard flow. With the descriptive members absent a client that renders or asserts on them reads null where AWS always supplies a value; with placeholder display names the catalog is not recognisable; and with workloads missing the client never learns they exist, which is the same gap Cause 1 surfaces as a 404 downstream.
Fix: the workload-catalog seed plus the ListWorkloads projection in the launchwizard crate (src/state.rs and the ListWorkloads handler) — seed the full workload set with its published display name, description, documentation URL and owner display name, and serialize those members in the list projection.
Traces: launch-wizard-catalog-list-workloads#task#1.
