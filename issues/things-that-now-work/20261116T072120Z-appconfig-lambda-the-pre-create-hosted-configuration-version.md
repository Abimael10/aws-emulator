# appconfig__lambda: the PRE_CREATE_HOSTED_CONFIGURATION_VERSION transform scenario never settles — the stored bytes are never replaced by the action's returned Content and the deployment barrier never clears

> _Note: this issue was identified against the code base at commit `0cc1593284dc57d1fa665d25f671e4cff118eb06`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
CreateHostedConfigurationVersion

## Description
Cause 1 of 1: a configuration profile with a PRE_CREATE_HOSTED_CONFIGURATION_VERSION extension association never produces the transformed configuration the action point returns, and the scenario cannot reach the point where that could be observed: the check exhausts its budget without a verdict.
  AWS: recorded behavior only — the AppConfig Smithy model describes CreateHostedConfigurationVersion (POST /applications/{ApplicationId}/configurationprofiles/{ConfigurationProfileId}/hostedconfigurationversions, 201) and the extension/association control plane, but does not model action-point invocation semantics. The recording the check encodes shows: on CreateHostedConfigurationVersion, AppConfig synchronously invokes the Lambda bound to the profile's PRE_CREATE_HOSTED_CONFIGURATION_VERSION action point, passes it an event carrying the base64 `Content` the caller submitted, and when the action returns {"Content": "<base64>"} the version STORED (and therefore later served) is the replacement bytes, not the submitted bytes. The action also observes the event itself (the check forwards it to SQS because no AppConfig API reports it). The deployment of the resulting version then reaches Deployment$State 'COMPLETE'.
  Emulator: the whole journey produces no verdict within the harness budget — the check fails with 'Check timed out after 60.0s'. Two emulator behaviours lie on that path and both are known to stall it: the action point never invokes its Lambda (so no event is ever delivered to the observation queue and the stored content is never replaced), and the helper that waits for the deployment of the version to reach State 'COMPLETE' is fed PascalCase 'Complete' and so never terminates.
  Why: a customer using a PRE_CREATE_HOSTED_CONFIGURATION_VERSION extension to normalise, stamp or enrich configuration documents gets the raw submitted bytes stored and served instead of the transformed ones — silently, with a 201 on the create — so a pipeline that relies on the transform being applied server-side ships unprocessed configuration. A customer waiting for the deployment of that version never sees it finish.
  Fix: the appconfig extension action-point invocation path for PRE_CREATE_HOSTED_CONFIGURATION_VERSION (invoke the associated Lambda with the Content-bearing event and apply a returned Content as the stored bytes), plus the shared Deployment$State wire mapping in the appconfig deployment response projection.
  Traces: appconfig__lambda.pre-create-hosted-configuration-version-extension-transforms-stored-content.

Related open issues that the replay reports as NOT owning this check: 20261027T010737Z-appconfig-lambda-backed-extension-action-points-still-never.md and 20261105T111951Z-appconfig-lambda-appconfig-extension-action-points-never-invoke.md describe Lambda-backed action points never firing in general; 20261115T213820Z-appconfig-lambda-2-net-new-causes-getdeployment-serves.md carries the GetDeployment PascalCase cause for this service token and owns two sibling checks, but not this one. None of them binds this check's replay key, so it stays unverified if only those are closed.

## Evidence
Behavioral replay simparity-behavioral-aws-v1, service appconfig__lambda 0/4 (0%), 4 failures; three are marked OWNED by already-filed issues and were skipped. The surviving check appconfig__lambda.pre-create-hosted-configuration-version-extension-transforms-stored-content fails with 'Check timed out after 60.0s' — no response was ever asserted, so no status/error-code divergence is observable; the divergence is that the journey never settles.

What the check does, from its replayed source: it creates an IAM role and a python3.12 Lambda whose handler forwards the action-point event to an SQS queue and, when TRANSFORM=1, returns {"Content": base64(json with an added "stamped": <per-run stamp> member)}; it associates an AWS.AppConfig.Extension-style extension to the configuration profile ARN at PRE_CREATE_HOSTED_CONFIGURATION_VERSION; it then calls CreateHostedConfigurationVersion through `_create_version_when_extension_is_live` (bounded retry, 300s), drains one message from the observation queue with `_drain_one` (180s long-poll) to inspect the event AppConfig handed the action, deploys the version with `_deploy_and_wait_complete` which asserts Deployment$State == 'COMPLETE' (terminal set ('COMPLETE','ROLLED_BACK','REVERTED')), and finally polls fresh AppConfigData sessions with `_serve_until` for the exact transformed bytes. Its own budget is 600s; the harness cap is 60s, so the run ends inside the first blocking wait.

The environment-state constants in the same file (_ENV_TRANSITIONAL = ('Deploying','RollingBack')) confirm the recording's convention: AppConfig serves Environment$State in PascalCase but Deployment$State in SCREAMING_SNAKE, and the emulator serves the latter as 'Complete' — see the appconfig issue filed alongside this one. The per-run stamp value, generated ids, role/function/queue names and the harness port are per-run values, not requirements; the requirement is that the stored and served bytes equal the action's returned Content and that the deployment of that version reports 'COMPLETE'.

## Steps to Reproduce
1. Create an IAM role and a Lambda function whose handler returns {"Content": "<base64 of a modified document>"} and forwards its event to an SQS queue.
2. Create an AppConfig application, environment and hosted configuration profile; create an AppConfig extension with a PRE_CREATE_HOSTED_CONFIGURATION_VERSION action pointing at that function's ARN, and associate it to the configuration profile ARN.
3. Call CreateHostedConfigurationVersion with a JSON document. Expected (recorded AWS): 201, the Lambda is invoked synchronously with an event carrying the submitted base64 Content, and the stored version is the replacement bytes. Observed: no event reaches the queue and the stored bytes are the submitted ones.
4. Deploy that version and poll GetDeployment until State is terminal: AWS reports 'COMPLETE', the emulator reports 'Complete', so the wait never ends.
5. Start an AppConfigData session on the environment/profile and read the configuration: it must be byte-identical to the action's returned Content.
6. Re-replay appconfig__lambda.pre-create-hosted-configuration-version-extension-transforms-stored-content.
