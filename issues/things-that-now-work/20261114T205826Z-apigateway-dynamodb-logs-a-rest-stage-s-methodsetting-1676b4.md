# apigateway__dynamodb__logs: a REST stage's MethodSetting loggingLevel/dataTraceEnabled are inert — no execution-log event is ever delivered for OFF/ERROR/INFO/INFO+dataTrace and the scenario is killed at the replay cap

> _Note: this issue was identified against the code base at commit `525aa870f16e7d7c4a999697bf2db6dd4941c01e`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
UpdateStage

## Description
Cause 1 of 1: the per-method execution-logging controls of a deployed REST stage have no observable effect, so the OFF/ERROR/INFO/INFO+dataTrace trajectory never reaches a single graded assertion and the check is terminated at the replay cap. Failing check: apigateway__dynamodb__logs.deep-apigateway-1-apigw-methodsetting-logging-level-and-data-trace-gate-execution-logs.

AWS: Smithy (com.amazonaws.apigateway): MethodSetting.loggingLevel — "Specifies the logging level for this method, which affects the log entries pushed to Amazon CloudWatch Logs. Valid values are OFF, ERROR, and INFO. Choose ERROR to write only error-level entries to CloudWatch Logs, or choose INFO to include all ERROR events as well as extra informational events." — and MethodSetting.dataTraceEnabled (@default false), "Specifies whether data trace logging is enabled for this method". Both are set through UpdateStage patchOperations on /*/*/logging/loglevel and /*/*/logging/dataTrace and echoed by GetStage under methodSettings['*/*']. The delivery itself is recorded behavior only: once the account's cloudwatchRoleArn names a role holding arn:aws:iam::aws:policy/service-role/AmazonAPIGatewayPushToCloudWatchLogs, execution logs land in the log group API-Gateway-Execution-Logs_<rest-api-id>/<stage-name>, each line prefixed with "(<requestId>)" where <requestId> is the response's x-amzn-RequestId. Per level: at OFF nothing is delivered for either a successful or a failing request; at ERROR only the failing request is logged and only at error verbosity — the line "Execution failed due to configuration error" appears and "Starting execution for request" does not; at INFO the successful request logs "Starting execution for request" and no data-trace lines; with dataTraceEnabled=true the same request additionally logs exactly one "Endpoint request body after transformations: " line carrying the transformed integration request, one "Endpoint response body before transformations: " line carrying the backend response, and one "Method response body after transformations: " line equal to the body the client received. Those prefixes are AWS's fixed text; the request id, the marker, the table name and the bodies are values taken from the request and from state.

Emulator: nothing settles. The replay reports only "Error: Check timed out after 60.0s". Not one phase barrier is satisfied: neither the readiness barrier for the deployed endpoints (200 on the resource whose AWS integration targets DynamoDB UpdateItem, and 500 "Execution failed due to configuration error" on the sibling resource whose integration credentials name a role that does not exist) nor any of the three MethodSetting flips landing events in API-Gateway-Execution-Logs_<api-id>/<stage>. No execution-log event is observed at any logging level, so OFF cannot be distinguished from INFO and dataTraceEnabled reveals nothing.

Why: loggingLevel and dataTraceEnabled are the only switches a client has over REST execution logging, and API-Gateway-Execution-Logs_<api-id>/<stage> is where an operator diagnoses a 500 coming out of a misconfigured integration. Switches that are accepted and echoed by GetStage but inert make a client believe logging is on while nothing is captured: a configuration-error failure leaves no trace, data tracing exposes no request/response bodies, and turning logging OFF is indistinguishable from leaving it at INFO.

Fix: the API Gateway REST data plane's execution-logging path — the per-request logger that must honour the stage's effective MethodSetting (OFF/ERROR/INFO and dataTraceEnabled) and deliver "(<requestId>) ..." events to API-Gateway-Execution-Logs_<api-id>/<stage> once the account cloudwatchRoleArn is set — together with the AWS-integration execution path it logs (the DynamoDB UpdateItem integration, and the configuration-error refusal for an absent credentials role) and the UpdateStage/GetStage methodSettings state it reads. NOTE: the open issues 20261114T110649Z-apigateway-dynamodb-logs-the-methodsetting-logginglevel-datatraceenabled-scenario.md and 20261113T163938Z-apigateway-dynamodb-logs-a-rest-stage-s-methodsetting.md describe this same scenario, but this replay did not report the check as owned by either of them (their recorded replay keys were taken at an _until_logged timeout, while the check now dies at the whole-check cap), so it is filed here to keep the failing check attached to an open work item — fold it into whichever of those causes is still open.

Traces: apigateway__dynamodb__logs.deep-apigateway-1-apigw-methodsetting-logging-level-and-data-trace-gate-execution-logs.

## Evidence
Expected (AWS): with the account cloudwatchRoleArn pointing at a role holding arn:aws:iam::aws:policy/service-role/AmazonAPIGatewayPushToCloudWatchLogs, FilterLogEvents on API-Gateway-Execution-Logs_<rest-api-id>/<stage>, indexed by the "(<requestId>)" prefix, yields per request id: nothing at loggingLevel OFF (for both the successful and the failing request); at ERROR only the failing request, carrying "Execution failed due to configuration error" and NOT "Starting execution for request", with no events at all for a successful request; at INFO with dataTrace false the successful request carrying "Starting execution for request" and no data-trace content; at INFO with dataTrace true the same plus exactly one "Endpoint request body after transformations: " line containing the transformed integration request (table name and the marker derived from the query string), exactly one "Endpoint response body before transformations: " line containing the backend response, and one "Method response body after transformations: " line byte-equal to the body the client received.

Actual (emulator): "Error: Check timed out after 60.0s" — the check never gets past its first readiness barrier. No 200 from the DynamoDB AWS-integration resource and no 500 "Execution failed due to configuration error" from the absent-role resource are observed, and no event whatsoever appears in API-Gateway-Execution-Logs_<api-id>/<stage> for any of OFF, ERROR, INFO or INFO+dataTrace. Every per-level assertion is therefore unreached.
