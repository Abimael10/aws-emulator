# ElastiCache reference catalogs are emulator-authored: engine defaults, cache parameters, reserved-node offerings and service updates all diverge (4 causes)

> _Note: this issue was identified against the code base at commit `7e081c0d0a956f09d8276e607b12ee6e057271df`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
DescribeEngineDefaultParameters

## Description
FOUR net-new root causes, all in the elasticache crate, all read-only catalog reads that answer HTTP 200 with a body the service itself composed instead of the catalog AWS publishes. The fault they share is the crate's seeded ElastiCache reference data (engine-default parameters, per-group cache parameters, reserved-cache-node offerings, service updates) and the handlers that project it: every one of these four operations is a pure catalog read, so there is no request-derived state that could explain the difference. A fixer must close all FOUR before submitting.

Related open issues that do NOT cover these steps (none of these four clusters is owned — the replay reports owned_by empty and stub_path empty for each): 20261030T130325Z-elasticache-parameter-catalog-is-incomplete-describecacheparameters-omits-cachenodetypespecificparameters.md names the DescribeCacheParameters catalog, but only for fixture elasticache-catalog-describe-cache-parameters, and carries none of the replay keys below; 20261114T012429Z-elasticache-user-group-and-serverless-cache-projections-omit.md covers the serverless-cache projections, not the catalogs.

Cause 1 of 4: DescribeEngineDefaultParameters serves a different engine-default parameter set (fixture elasticache-cache-parameter-group-workflow, step task#3).
AWS: Smithy: DescribeEngineDefaultParameters(CacheParameterGroupFamily required: String, MaxRecords, Marker) -> DescribeEngineDefaultParametersResult{EngineDefaults}; EngineDefaults{CacheParameterGroupFamily, Marker, Parameters: ParametersList, CacheNodeTypeSpecificParameters: CacheNodeTypeSpecificParametersList}; paginated{inputToken Marker, outputToken EngineDefaults.Marker, items EngineDefaults.Parameters, pageSize MaxRecords}; errors InvalidParameterValueException (400/InvalidParameterValue), InvalidParameterCombinationException (400/InvalidParameterCombination). Shape Parameter carries ParameterName, ParameterValue, Description, Source, DataType, AllowedValues, IsModifiable, MinimumEngineVersion, ChangeType; CacheNodeTypeSpecificParameter additionally carries CacheNodeTypeSpecificValues (one CacheNodeType/Value pair per supported node type). The catalog CONTENT is recorded behavior only: AWS returns the named family's complete published engine-default set, every Parameter fully populated with that family's real name/value/description/data type/allowed range/minimum engine version, a populated CacheNodeTypeSpecificParameters list (the recording's first member has AllowedValues '0-', MinimumEngineVersion '7.0.0' and a CacheNodeTypeSpecificValues list spanning the family's node types), and the EngineDefaults.Marker the recording shows for that page.
Emulator: 200, but the body is a different catalog — Parameters.Parameter[0..19] diverge on ParameterName, ParameterValue, Description, DataType, AllowedValues, MinimumEngineVersion and (for some entries) IsModifiable/ChangeType; CacheNodeTypeSpecificParameters.CacheNodeTypeSpecificParameter[0] is a different record than the one AWS returns; and EngineDefaults.Marker diverges from the recorded pagination marker.
Why: a client that reads the engine defaults before ModifyCacheParameterGroup validates its intended values against AllowedValues/IsModifiable/MinimumEngineVersion. Against the emulator it validates against parameter names and ranges that do not exist on the family, so correct modifications look invalid and invalid ones look permitted; and because EngineDefaults.Marker is not the recorded one, a paginating client walks a page sequence AWS never produced.
Fix: the elasticache crate's seeded engine-default parameter catalog (the reference data the DescribeEngineDefaultParameters handler reads from the crate's state/catalog module) and that handler's projection of EngineDefaults, including the Marker it emits.
Traces: elasticache-cache-parameter-group-workflow#task#3.

Cause 2 of 4: DescribeCacheParameters on the workflow's parameter group serves the wrong parameter records (fixture elasticache-cache-parameter-group-workflow, step task#5; the same cluster also covers task#7).
AWS: Smithy: DescribeCacheParameters(CacheParameterGroupName required, Source, MaxRecords, Marker) -> CacheParameterGroupDetails{Marker, Parameters: ParametersList, CacheNodeTypeSpecificParameters: CacheNodeTypeSpecificParametersList}; errors CacheParameterGroupNotFoundFault (404/CacheParameterGroupNotFound), InvalidParameterValueException (400/InvalidParameterValue), InvalidParameterCombinationException (400/InvalidParameterCombination). Content is recorded behavior only: the group's effective parameter set is its family's full default set, with each CacheNodeTypeSpecificParameter returned as a list member carrying ParameterName, AllowedValues, MinimumEngineVersion and one CacheNodeType/Value pair per supported node type (the recording's first member: AllowedValues '0-', MinimumEngineVersion '7.0.0').
Emulator: 200, with CacheNodeTypeSpecificParameters.CacheNodeTypeSpecificParameter[0] reported value_mismatch (a different record than AWS's) and the Parameters.Parameter[0..62+] entries diverging across AllowedValues, DataType, Description, MinimumEngineVersion, ParameterName, ParameterValue, IsModifiable and ChangeType — i.e. the same seeded catalog defect as cause 1, reached through the per-group read rather than the engine-default read.
Why: this is the read a client uses to discover what it may tune on a group it just created, and the read it uses to confirm a ModifyCacheParameterGroup took effect. With a re-authored parameter set the confirm step compares against records AWS never returns, so the parameter-group workflow cannot be validated against the emulator.
Fix: same component as cause 1 — the seeded parameter catalog plus the DescribeCacheParameters handler's projection of Parameters/CacheNodeTypeSpecificParameters.
Traces: elasticache-cache-parameter-group-workflow#task#5 (cluster also covers task#7).

Cause 3 of 4: DescribeReservedCacheNodesOfferings serves a synthesized offering catalog instead of the published offerings (fixture elasticache-catalog-describe-reserved-cache-nodes-offerings, step task#1; the same cluster also covers task#2 and task#3).
AWS: Smithy: DescribeReservedCacheNodesOfferings(ReservedCacheNodesOfferingId, CacheNodeType, Duration, ProductDescription, OfferingType, MaxRecords, Marker) -> ReservedCacheNodesOfferingMessage{Marker, ReservedCacheNodesOfferings: ReservedCacheNodesOfferingList}; errors ReservedCacheNodesOfferingNotFoundFault (404/ReservedCacheNodesOfferingNotFound), InvalidParameterValueException (400/InvalidParameterValue), InvalidParameterCombinationException (400/InvalidParameterCombination). Shape ReservedCacheNodesOffering{ReservedCacheNodesOfferingId, CacheNodeType, Duration, FixedPrice, UsagePrice, ProductDescription, OfferingType, RecurringCharges}. Content is recorded behavior only, but it is a PUBLISHED catalog, not per-account state: each offering id is a stable catalog identifier that the client hands back to PurchaseReservedCacheNodesOffering, and each id is bound to one (CacheNodeType, Duration, ProductDescription, OfferingType) combination with that combination's FixedPrice, UsagePrice and RecurringCharges. The recording shows the offerings AWS returns for the queried filters, in the order AWS returns them.
Emulator: 200, but every member of ReservedCacheNodesOfferings diverges: ReservedCacheNodesOffering[0..5] are reported 'missing' against the recorded members — the offering ids are emulator-minted values that appear in no AWS catalog, and the records served for a given list position carry a different OfferingType and a different FixedPrice/UsagePrice/RecurringCharges triple than the recorded offering at that position.
Why: offering ids are the only way to purchase a reservation. A client that lists offerings, picks one by OfferingType/Duration/price and calls PurchaseReservedCacheNodesOffering is working from ids and prices that do not identify any real offering, so cost-planning and reservation-purchase flows cannot be exercised, and a client that filters on OfferingType gets a set AWS would not have returned.
Fix: the elasticache crate's seeded reserved-cache-node offering catalog and the DescribeReservedCacheNodesOfferings handler's filtering/ordering over it (ids must be stable catalog ids, not generated per boot).
Traces: elasticache-catalog-describe-reserved-cache-nodes-offerings#task#1 (cluster also covers task#2, task#3).

Cause 4 of 4: DescribeServiceUpdates serves an invented service-update list (fixture elasticache-catalog-describe-service-updates, step task#1).
AWS: Smithy: DescribeServiceUpdates(ServiceUpdateName, ServiceUpdateStatus: list length 0..3, MaxRecords, Marker) -> ServiceUpdatesMessage{Marker, ServiceUpdates: ServiceUpdateList}; errors ServiceUpdateNotFoundFault (404/ServiceUpdateNotFoundFault), InvalidParameterValueException (400/InvalidParameterValue), InvalidParameterCombinationException (400/InvalidParameterCombination). Shape ServiceUpdate{ServiceUpdateName (documented as 'The unique ID of the service update'), ServiceUpdateReleaseDate, ServiceUpdateEndDate, ServiceUpdateSeverity (enum), ServiceUpdateRecommendedApplyByDate, ServiceUpdateStatus (enum), ServiceUpdateDescription, ServiceUpdateType (enum), Engine, EngineVersion, AutoUpdateAfterRecommendedApplyByDate, EstimatedUpdateTime}. Content is recorded behavior only, and again it is a published catalog: the recording shows AWS's real service updates (e.g. an engine-major-version-update named for the Redis OSS v6 EOL path, ServiceUpdateStatus 'available', ServiceUpdateSeverity 'important', AutoUpdateAfterRecommendedApplyByDate false, with its own description and apply-by/end dates).
Emulator: 200, but all 73 members diverge — ServiceUpdate[0..72] are reported 'missing' against the recorded list. The emulator serves updates of its own invention (a memcached 'security-update' record whose ServiceUpdateStatus is 'expired' and whose description is emulator-authored prose) in place of AWS's published updates, so neither the names, the types/severities, the statuses nor the dates correspond to AWS's.
Why: ServiceUpdateName is the handle for BatchApplyUpdateAction / BatchStopUpdateAction and for the ServiceUpdateName filter on DescribeUpdateActions. A client that discovers an update here and then applies it is naming an update that exists only inside the emulator, while an operator script that looks for AWS's real update names finds none and concludes the fleet is compliant; filtering by ServiceUpdateStatus 'available' returns nothing because every synthesized record is 'expired'.
Fix: the elasticache crate's seeded service-update catalog and the DescribeServiceUpdates handler's filtering/projection over it.
Traces: elasticache-catalog-describe-service-updates#task#1.
