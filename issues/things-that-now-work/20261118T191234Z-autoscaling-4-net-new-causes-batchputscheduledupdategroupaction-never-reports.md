# autoscaling: 4 net-new causes — BatchPutScheduledUpdateGroupAction never reports a name conflict, the 125-action LimitExceeded sentence is re-worded, and DetachInstances / GetPredictiveScalingForecast answer NotImplemented instead of their ValidationError refusals

> _Note: this issue was identified against the code base at commit `a3ffbfdb343cbfec4c8be7bae3ef508c5777c283`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
BatchPutScheduledUpdateGroupAction

## Description
Four net-new root causes in the Auto Scaling control plane, bundled only because they all belong to one service. Each must be closed separately before this issue is submitted.

Cause 1 of 4 — BatchPutScheduledUpdateGroupAction silently upserts an existing scheduled-action name instead of reporting it in FailedScheduledUpdateGroupActions and failing the batch.
AWS: Smithy (com.amazonaws.autoscaling#AutoScaling_2011_01_01) models BatchPutScheduledUpdateGroupAction with output member FailedScheduledUpdateGroupActions (list of FailedScheduledUpdateGroupActionRequest{ScheduledActionName required, ErrorCode XmlStringMaxLen64, ErrorMessage XmlString}; the shape's own doc: "Describes a scheduled action that could not be created, updated, or deleted"), and binds the error AlreadyExistsFault (awsQueryError code AlreadyExists, HTTP 400). Recorded behavior for the batch path: an entry whose ScheduledActionName already exists on the group with different parameters is a conflict, not an upsert — AWS returns HTTP 200 and reports that entry in FailedScheduledUpdateGroupActions (ErrorCode naming the already-exists condition, ErrorMessage its accompanying sentence), the whole batch is rejected atomically so the brand-new name submitted in the SAME batch is reported failed too, the pre-existing action keeps its stored MinSize/MaxSize/DesiredCapacity, and the new name is not created.
Emulator: the call returns HTTP 200 with FailedScheduledUpdateGroupActions == [] — no entry of the batch is reported as failed, so the conflicting name is treated as an ordinary upsert and the conflict is invisible to the caller.
Why: a client that reconciles its schedule by submitting a batch and inspecting FailedScheduledUpdateGroupActions concludes every entry was accepted. It therefore overwrites an existing schedule it meant to leave alone (AWS would have preserved it), and it gets a partially-applied batch where AWS applies none of it — the atomicity the API advertises is gone, so a half-written schedule can never be detected or retried correctly.
Fix: BatchPutScheduledUpdateGroupAction's handler and the scheduled-action store it writes through — detect a per-group ScheduledActionName collision before any entry is committed, fail the whole batch, and populate FailedScheduledUpdateGroupActions (name + ErrorCode + ErrorMessage) for every entry of the batch.
Traces: autoscaling.batch-put-scheduled-action-duplicate-fails.

Cause 2 of 4 — the per-group 125-scheduled-action LimitExceeded refusal is emulator-authored prose, not AWS's sentence.
AWS: Smithy binds LimitExceededFault to PutScheduledUpdateGroupAction and BatchPutScheduledUpdateGroupAction with awsQueryError code LimitExceeded and HTTP 400; the message text is recorded behavior only. Once a group already holds the maximum number of scheduled actions, a further PutScheduledUpdateGroupAction is refused with HTTP 400, Error.Code LimitExceeded and Error.Message "The maximum limit of <limit> scheduled actions has been reached." — fixed text "The maximum limit of " + the per-group scheduled-action limit in force (125 in this account/region) + " scheduled actions has been reached.", ending in a period. The refusal changes nothing: the stored action set stays at the limit, and freeing one slot lets the same request succeed.
Emulator: the status (400) and code (LimitExceeded) are right, but the message is "You have already reached the limit of 125 scheduled actions per Auto Scaling group" — different wording, different sentence shape and no trailing period. The numeric limit itself is correct; only the sentence diverges.
Why: the message is part of the refusal contract. A client (or CLI/console/support tooling) that matches AWS's sentence to distinguish the scheduled-action cap from any other LimitExceeded on the same operation never recognizes the emulator's text, and any golden/snapshot comparison of the error body fails.
Fix: the LimitExceeded refusal in PutScheduledUpdateGroupAction's validation (shared with BatchPutScheduledUpdateGroupAction) — emit AWS's sentence with the limit interpolated, instead of the locally-worded one.
Traces: autoscaling.batch-put-scheduled-update-group-action-limit-exceeded-rejected.

Cause 3 of 4 — DetachInstances answers NotImplemented, so the non-member refusal never happens.
AWS: Smithy models DetachInstances (input DetachInstancesQuery: AutoScalingGroupName required, InstanceIds, ShouldDecrementDesiredCapacity required; output DetachInstancesAnswer.Activities), so the operation exists and succeeds for a member instance. The membership check is recorded behavior only: an InstanceIds entry that is not a member of the named group is refused with HTTP 400, Error.Code ValidationError and Error.Message "The instance <instance-id> is not part of Auto Scaling group <group-name>." — fixed text "The instance ", then the offending instance id from the request, " is not part of Auto Scaling group ", then the AutoScalingGroupName from the request, then a period. The refusal is total: group membership and DesiredCapacity are unchanged, and a subsequent DetachInstances on a real member still succeeds (the member leaves the group and, with ShouldDecrementDesiredCapacity=true, DesiredCapacity drops).
Emulator: the request is answered with Error.Code NotImplemented — the operation is an unimplemented scaffold, so neither the refusal nor the successful detach of a real member is reachable.
Why: a client cannot detach an instance at all, and the guard that tells it an id is not a member of the group is replaced by a code no AWS SDK models for this operation — error handling keyed on ValidationError falls through to generic retry/abort paths. Note: the open stub issue naming DetachInstances and services/service-com-amazonaws-autoscaling-autoscaling-2011-01-01/src/ops/detach_instances.rs does NOT carry these two checks' replay keys, and merely making the handler answer is not enough — the non-member ValidationError sentence above is the requirement these checks assert.
Fix: services/service-com-amazonaws-autoscaling-autoscaling-2011-01-01/src/ops/detach_instances.rs — implement the operation against the group's membership state and add the pre-commit non-member check emitting AWS's ValidationError sentence with the request's instance id and group name interpolated.
Traces: autoscaling.detach-instances-foreign-instance-rejected, autoscaling.instance-attach-detach-lifecycle.

Cause 4 of 4 — GetPredictiveScalingForecast answers NotImplemented, so a policy of the wrong type is never refused.
AWS: Smithy models GetPredictiveScalingForecast (input GetPredictiveScalingForecastType: AutoScalingGroupName, PolicyName, StartTime, EndTime all required; output GetPredictiveScalingForecastAnswer with required LoadForecast, CapacityForecast and UpdateTime), so a PolicyName naming a real PredictiveScaling policy returns a document carrying LoadForecast and CapacityForecast. The type check is recorded behavior only: a PolicyName that names a real, existing policy whose PolicyType is anything other than PredictiveScaling is refused with HTTP 400, Error.Code ValidationError and Error.Message "Policy <policy-name> is not a predictive scaling policy." — fixed text "Policy ", the PolicyName from the request, " is not a predictive scaling policy.".
Emulator: the request is answered with Error.Code NotImplemented, for an existing StepScaling policy on an existing group — neither the refusal nor the forecast document is reachable.
Why: a caller that distinguishes "wrong policy type" (fix the PolicyName) from "no forecast available" cannot do so, and the unmodelled NotImplemented code is not in the operation's error set, so SDK error handling cannot classify it. The open stub issue naming GetPredictiveScalingForecast and services/service-com-amazonaws-autoscaling-autoscaling-2011-01-01/src/ops/get_predictive_scaling_forecast.rs does not carry this check's replay key, and implementing the happy path alone leaves this refusal missing.
Fix: services/service-com-amazonaws-autoscaling-autoscaling-2011-01-01/src/ops/get_predictive_scaling_forecast.rs — implement the operation and add the policy-type validation ahead of forecast generation, emitting AWS's ValidationError sentence with the request's PolicyName interpolated.
Traces: autoscaling.get-predictive-scaling-forecast-non-predictive-policy-rejected.
