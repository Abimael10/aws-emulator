# redshift__sqs: no 'Redshift Data Statement Status Change' event reaches an EventBridge rule's SQS target, so both CLI wrong-target-ARN and purge-queue checks stall out at the harness budget

> _Note: this issue was identified against the code base at commit `360dea7200cfaf15b2eb2bc3d0288559a6d49d3a`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
ExecuteStatement

## Description
One net-new root cause carrying two failing checks. NOTE for the fixer: two OPEN issues describe the same underlying cause but do NOT carry these two replay keys, and the harness did not mark either check as OWNED by them: 20261029T082153Z-redshift-sqs-a-data-api-statement-submitted-with.md and 20261024T115115Z-redshift-sqs-redshift-data-api-executestatement-with-withevent-true-publishes.md (both list only redshift__sqs.data-api-with-event-emits-a-real-statement-event-and-the-default-emits-none). They are filed here so these two surviving failures are not dropped; if those issues are still open, treat all of them as one cause and close them together — but these two check ids must be re-replayed to confirm the fix, because neither of those issues can discover them.

Cause 1 of 1: a redshift-data statement submitted with WithEvent=true publishes no EventBridge envelope, so an SQS target of a rule matching it is never written and any check whose positive control is that delivery makes no progress.
Failing checks: redshift__sqs.cli-eventbridge-put-rule-wrong-target-arn-negative, redshift__sqs.cli-sqs-purge-queue-then-no-stale-redshift-event-negative

AWS: Smithy (redshift-data) ExecuteStatementInput$WithEvent, target Boolean, documented as 'A value that indicates whether to send an event to the Amazon EventBridge event bus after the SQL statement runs.' When WithEvent is true and the statement reaches a terminal status, the Data API publishes exactly one envelope on the account's default bus with source 'aws.redshift-data' and detail-type 'Redshift Data Statement Status Change'; detail.statementId equals the ExecuteStatement response Id and detail.state is the terminal status ('FINISHED' here), and account/region/resources are taken from the caller, the request region and the cluster the statement ran on — none of them fixed text. An EventBridge rule whose pattern names only that source and detail-type therefore forwards the envelope to its SQS target, authorised by the queue's resource policy. WithEvent has no modeled default and its absence means no event.

Emulator: no envelope is ever delivered. Both checks create the cluster, the rule, the queues and the queue policies, run `aws redshift-data execute-statement --with-event`, poll DescribeStatement to a terminal status, then long-poll the correctly-wired SQS target for a body whose detail.statementId equals that statement Id. Nothing arrives, so each check sits in that drain window and is killed: 'Error: Check timed out after 60.0s', with no stack frame — the replay output states only the timeout. Hypothesis (neither the model nor the replay output states the stall point): the redshift-data statement state machine never publishes to EventBridge, exactly as the two open issues above describe, so the rule has nothing to match. The EventBridge->SQS hop itself is known to work in this suite (20261029T193114Z-redshift-sqs-3-net-new-causes-eventbridge-sqs.md records redshift cluster-event envelopes being delivered to these queues — over-permissively), which points the stall at the publication, not the delivery.

Why: every assertion either check exists to make is downstream of that one delivery and is therefore never evaluated. The wrong-target-ARN check cannot show that PutTargets accepts a same-account ARN naming a nonexistent queue and that the event then lands only on the correctly wired target; the purge check cannot show that PurgeQueue's deleted message stays gone past its documented 60-second window while a fresh statement's event is still delivered. Worse, both are negative-delivery checks: an emulator that delivers nothing at all satisfies their absence halves vacuously, so a real over-delivery regression on this wiring is undetectable. A client driving asynchronous completion handling off WithEvent waits forever with no error and no way to tell 'WithEvent honoured' from 'WithEvent silently ignored'.

Fix: the redshift-data ExecuteStatement handler and the statement state machine that moves a statement to a terminal status — on terminal transition, and only when the request set WithEvent=true, publish one envelope to the default EventBridge bus with source 'aws.redshift-data', detail-type 'Redshift Data Statement Status Change', account/region from the caller and request, resources naming the cluster (or workgroup) ARN resolved from the request, and detail.statementId / detail.state from the statement record, so the existing rule-to-SQS routing delivers it. A statement submitted without WithEvent must publish nothing.

Traces: redshift__sqs.cli-eventbridge-put-rule-wrong-target-arn-negative, redshift__sqs.cli-sqs-purge-queue-then-no-stale-redshift-event-negative

## Evidence
Expected (both checks): after `aws redshift-data execute-statement --cluster-identifier <cluster> --database dev --db-user <user> --sql 'SELECT 1' --with-event` on an available single-node cluster reaches Status=FINISHED, ReceiveMessage on the SQS queue targeted by a rule whose pattern is {"source":["aws.redshift-data"],"detail-type":["Redshift Data Statement Status Change"]} returns a body whose detail.statementId equals the ExecuteStatement Id.

Actual (both checks): 'Error: Check timed out after 60.0s'. No frame is reported; nothing ever arrives on the correctly-wired target, so each check stays in its first delivery long-poll (timeout_s=180.0 in the check's own _poll_for_statement_message) and is killed by the harness before any graded assertion runs. Verdict recorded as mismatch for redshift__sqs.cli-eventbridge-put-rule-wrong-target-arn-negative and redshift__sqs.cli-sqs-purge-queue-then-no-stale-redshift-event-negative.

## Steps to Reproduce
1) redshift CreateClusterSubnetGroup over the run's subnets; redshift CreateCluster (single-node ra3.xlplus, DBName dev) and poll DescribeClusters to ClusterStatus='available'. 2) events PutRule(EventPattern={"source":["aws.redshift-data"],"detail-type":["Redshift Data Statement Status Change"]}, State='ENABLED'); note RuleArn. 3) sqs CreateQueue; GetQueueAttributes(['QueueArn']); SetQueueAttributes with a Policy allowing Principal Service events.amazonaws.com sqs:SendMessage on that queue ARN conditioned on aws:SourceArn = the RuleArn; events PutTargets with that queue ARN. 4) `aws redshift-data execute-statement --cluster-identifier <cluster> --database dev --db-user <user> --sql 'SELECT 1' --with-event`; poll `aws redshift-data describe-statement --id <id>` to FINISHED. 5) sqs ReceiveMessage(MaxNumberOfMessages=10, WaitTimeSeconds=10) in a loop looking for detail.statementId == <id> — nothing ever arrives and the loop runs until the harness kills the check. Replay: redshift__sqs.cli-eventbridge-put-rule-wrong-target-arn-negative, redshift__sqs.cli-sqs-purge-queue-then-no-stale-redshift-event-negative.
