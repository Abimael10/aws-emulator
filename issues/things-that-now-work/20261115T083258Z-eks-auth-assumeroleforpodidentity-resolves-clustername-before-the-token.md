# eks-auth: AssumeRoleForPodIdentity resolves clusterName BEFORE the token's kid, so an unresolvable-kid token on an unknown cluster is 404 ResourceNotFoundException instead of 400 InvalidTokenException (1 cause)

> _Note: this issue was identified against the code base at commit `f7b60fee7b066cbc6f1eedeac1b0cd0f17c7dcd0`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
AssumeRoleForPodIdentity

## Description
REOPENS 20261113T144021Z-eks-auth-assumeroleforpodidentity-an-unknown-clustername-presented-with.md: its fix left the call refused. That issue's Cause 1 asked for the clusterName label to be resolved as a resource and answered with the modelled ResourceNotFoundException; the fix moved the cluster lookup AHEAD of every state-reading token layer, so the whole kid-resolution layer is now unreachable for any clusterName the emulator does not hold, and four behavioral checks that were passing at that commit are now refused with the resource error. This is not a new defect — it is the same cluster-vs-token layering, now mis-ordered in the other direction.

One root cause in service eks-auth, on the only operation it binds (AssumeRoleForPodIdentity, POST /clusters/{clusterName}/assume-role-for-pod-identity, restJson1).

Cause 1 of 1: the clusterName label is resolved against state before the token's `kid` is resolved, so a token whose `kid` names no key any cluster published is answered as a missing resource (404 ResourceNotFoundException) instead of as a bad token header (400 InvalidTokenException), and eks-auth now reveals whether a cluster exists.
AWS: Smithy (services/service-com-amazonaws-eksauth-eksauthfrontend/smithy-model/com-amazonaws-eksauth-eksauthfrontend.json) models on AssumeRoleForPodIdentity both InvalidTokenException (httpError 400, "The specified Kubernetes service account token is invalid.") and ResourceNotFoundException (httpError 404, "The specified resource could not be found."); clusterName is @httpLabel @required @length 1..100 @pattern ^[0-9A-Za-z][A-Za-z0-9\-_]*$ and token is @required @sensitive @pattern ^[A-Za-z0-9-_=]+\.[A-Za-z0-9-_=]+\.[A-Za-z0-9-_=]+$. The LAYER ORDER is recorded behavior only, and the recordings state it in three ways: (a) for a clusterName that is pattern-valid and names no cluster in the account, a well-formed RS256 header carrying a non-blank `kid` that resolves to no published key is refused with HTTP 400 / InvalidTokenException and the message "The token included in the request has invalid header - kid." — the deepest state AWS reaches without a real cluster; (b) the same holds for every clusterName that merely satisfies the model constraints ('a', '0', 'a'*100, a trailing '-', an inner '_'): the constraint layer passes them through to token validation, which fails at the kid layer, so none of them is answered 404; (c) the shallowest-wins ordering around it is also recorded — a pattern-invalid clusterName wins over any token fault (400 InvalidParameterException, "1 validation error detected: Value '<value>' at 'clusterName' failed to satisfy constraint: Member must satisfy regular expression pattern: [0-9A-Za-z][A-Za-z0-9\-_]*"), then header parse ("Failed to parse the token included in the request."), then a non-RS256 alg ("The token included in the request has invalid header - alg."), then an absent-or-blank kid ("The token included in the request has missing header - kid."), then kid resolution ("The token included in the request has invalid header - kid."). In each of those messages the quoted sentence is FIXED text; the only request-derived parts are the offending value and the member name in the InvalidParameterException sentence. Nothing in these recordings reaches a claim: five semantically different claim bodies (valid, expired, wrong aud, empty, not even JSON) all collapse onto the one kid-resolution identity, so ExpiredTokenException/AccessDeniedException/ResourceNotFoundException/InvalidRequestException are unreachable from the presented token. The 404 this operation DOES serve is reachable one layer deeper, with a kid that resolves (the genuine cluster-issued token of the reopened issue) and a clusterName that names no cluster. Hypothesis: AWS resolves the `kid` against the signing keys it holds rather than against the named cluster's JWKS alone, which is why kid resolution can precede cluster resolution.
Emulator: cluster resolution is unconditionally first, so the kid layer and everything after it are skipped for an unknown clusterName. AssumeRoleForPodIdentity(clusterName='sim2realbehavabsentcluster', token=<RS256 header, random 43-char kid, any payload>) is answered HTTP 404 / ResourceNotFoundException with message "No cluster found for name: sim2realbehavabsentcluster." — EKS-proper's own not-found sentence, with the cluster name taken from the request. The same answer comes back for 'a', '0', 'a'*100, 'sim2realbehav-' and 'sim2real_behav-CN9', i.e. every name that clears the model constraints, and for all five claim variants. The shallower layers are correct and still pass: a pattern-invalid name is 400 InvalidParameterException, a header missing `alg` is the parse failure, alg='HS256' is the alg failure and kid='' is the missing-header failure — all on the same absent cluster — which locates the divergence precisely at the kid-resolution layer. Code grounding: services/service-com-amazonaws-eksauth-eksauthfrontend/src/ops/assume_role_for_pod_identity.rs, module doc steps 2-3 (lines 20-31, "The label is a RESOURCE identity, so it is resolved as one, and before anything about the presented token is judged against state") and the lookup at lines 269-290, where `guard.cluster(&input.cluster_name).ok_or_else(|| no_cluster(...))?` runs ahead of the `cluster.publishes_signing_key(&token_headers.key_id)` test.
Why: two things a client relies on break. First, the error class is wrong for an agent: the EKS Pod Identity Agent keys its remediation on 400 InvalidTokenException "invalid header - kid" (re-read the projected service-account token; the key rotated) versus 404 ResourceNotFoundException (the agent is pointed at a cluster that is not there, do not retry), and 404 vs 400 also changes SDK error classification; a stale-token path is now diagnosed as a missing cluster. Second, it is an information disclosure: on real AWS eks-auth validates clusterName's pattern but never discloses whether the name resolves to a cluster unless the caller already holds key material that cluster published, so AssumeRoleForPodIdentity cannot be used to enumerate cluster names; the emulator now answers "No cluster found for name: X" to any caller with any junk token, and eks-auth and EKS proper return the same code for the same absent name, which the recordings require to differ.
Fix: the ordering of the state-reading layers in the operation's handler — the block at services/service-com-amazonaws-eksauth-eksauthfrontend/src/ops/assume_role_for_pod_identity.rs lines 269-290 and the step list in its module doc. Resolve the header's `kid` against the signing keys the service holds first and refuse an unresolvable one with InvalidTokenException (400, "The token included in the request has invalid header - kid."); only once the kid resolves may the clusterName label be resolved and ResourceNotFoundException (404) raised for a name that names no cluster — which keeps the reopened issue's genuine-token case answered 404. The shallower layers (model constraints, header parse, alg, kid presence) keep their current, correct precedence, and no claim may be read before the kid layer.
Traces: eks-auth.pod-identity-clustername-constraint-boundaries-rejected, eks-auth.pod-identity-header-rejection-layers-are-ordered, eks-auth.pod-identity-token-claims-are-never-evaluated, and eks__eks-auth.pod-identity-absent-cluster-rejected-on-token-not-existence (listed by the suite under the cross-service heading `eks__eks-auth`; its eks-proper legs — DescribeCluster and ListPodIdentityAssociations on the absent name — pass, and only the eks-auth leg diverges).
