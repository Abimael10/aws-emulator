## Description

Cause 1 of 3: `Ref` on an AWS::Athena::CapacityReservation resolves to the reservation's Name instead of its ARN.
  AWS: recorded behavior only for the CFN resolution itself (CloudFormation resource resolution is not described by the Athena Smithy model). Smithy (services/service-com-amazonaws-athena-amazonathena/smithy-model/com-amazonaws-athena-amazonathena.json): CreateCapacityReservation takes Name (CapacityReservationName, len 1..128, pattern ^[a-zA-Z0-9._-]+$) and TargetDpus, and the CapacityReservation shape carries an Arn member, which is the resource's primary identifier. AWS resolves `{"Ref": "<CapRes logical id>"}` to that ARN, of the general form `arn:aws:athena:<region>:<account-id>:capacity-reservation/<Name>` — the fixed parts are the partition/service/resource-type literals `arn:aws:athena:` and `:capacity-reservation/`, the variable parts are the stack's region, the caller's account id and the reservation Name from the template. A stack Output whose Value is that Ref therefore reads back as an ARN, and it changes when a rename replaces the reservation.
  Emulator: the stack reaches CREATE_COMPLETE, but the Output resolves to the bare reservation name — e.g. an OutputValue of `<reservation-name>` where AWS serves `arn:aws:athena:<region>:<account>:capacity-reservation/<reservation-name>`. (The per-run reservation name, region and account in the recording are request/environment values, not part of the requirement; the ARN TEMPLATE is.)
  Why: a `Ref` of this resource is the documented way a template hands the reservation to anything that needs an ARN — an IAM policy Resource, a tag value, a cross-stack Export, or a consumer calling Athena with the ARN. Fed a bare name, every one of those silently produces a malformed ARN and the downstream policy or call fails far from the actual defect; a client comparing the pre- and post-update Ref to detect replacement also compares the wrong thing.
  Fix: the CloudFormation resource provider for AWS::Athena::CapacityReservation — its Ref/primary-identifier resolution must return the reservation ARN (built from the stack's partition, region, account and the resource's Name), not the Name attribute.
  Traces: athena.deploy-capacity-reservation-cloudformation-lifecycle (fails at the first Output assertion, so the in-place-TargetDpus-update and rename legs of that check are unverified behind this cause).

Cause 2 of 3: assigning a workgroup that another ACTIVE capacity reservation still holds is accepted instead of refused, so a rename-while-assigned stack update completes instead of rolling back.
  AWS: Smithy: PutCapacityAssignmentConfiguration takes CapacityReservationName (required) and CapacityAssignments (required) and models only InvalidRequestException (client, HTTP 400) and InternalServerException (500); CreateCapacityReservation models the same client error. Recorded behavior: a capacity assignment naming a workgroup that is already assigned to a different ACTIVE reservation is refused 400 InvalidRequestException with Message "One or more workgroups are assigned to another active reservation. Update your reservation assignments to continue." — entirely FIXED text, with no workgroup name, reservation name or count interpolated. Through CloudFormation, renaming the reservation while the template still carries the assignment is a replacement: the replacement reservation cannot claim the workgroup its still-live predecessor holds, so the resource handler fails, the stack ends UPDATE_ROLLBACK_COMPLETE, and the CapRes failure event's ResourceStatusReason is the wrapped handler form `Resource handler returned message: "<the Athena message> (Service: Athena, Status Code: 400, Request ID: <id>) (SDK Attempt Count: 1)" (RequestToken: <token>, HandlerErrorCode: InvalidRequest)` — the request token and request id are per-run values, the HandlerErrorCode `InvalidRequest`, the status code 400 and the Athena sentence are the requirement. The original reservation is left untouched (still ACTIVE at its original TargetDpus under the original Name) and the replacement never exists.
  Emulator: the rename-while-assigned update is accepted end to end — the stack reaches UPDATE_COMPLETE — because the capacity-assignment path never checks whether a named workgroup is already held by another ACTIVE reservation. No CapRes *_FAILED event is produced, so there is no handler failure reason to read, and the stack's reservation state is the replaced one rather than the preserved original.
  Why: the whole point of the conflict refusal is that one workgroup's capacity cannot be served by two reservations at once. A client that relies on the refusal (or on CloudFormation rolling the update back) gets a silently double-assigned workgroup and a stack whose resources no longer match what AWS would have left behind; a template that AWS rejects deploys here, so the divergence is only discovered in production.
  Fix: Athena's capacity-assignment validation — the store mutation behind PutCapacityAssignmentConfiguration (services/service-com-amazonaws-athena-amazonathena/src/ops/put_capacity_assignment_configuration.rs calls `put_capacity_assignments` in services/service-com-amazonaws-athena-amazonathena/src/state.rs, which validates size, the reservation's existence and whether the reservation itself holds the workgroup, but not whether ANOTHER active reservation does), plus the same validation on whatever path the CFN AWS::Athena::CapacityReservation provider uses to apply CapacityAssignmentConfiguration, so the modeled InvalidRequestException is raised with AWS's fixed sentence and the stack update rolls back.
  Traces: athena.deploy-capacity-reservation-rename-with-assigned-workgroup-rejected (expected UPDATE_ROLLBACK_COMPLETE, got 'UPDATE_COMPLETE'). The same check's later assertions on the failure reason, on the original reservation surviving and on the positive control rename are unverified behind this cause.

Cause 3 of 3: GetQueryResults(QueryResultType=DATA_MANIFEST) against a query that generates no manifest is refused with emulator-authored prose instead of AWS's message.
  AWS: Smithy: GetQueryResults input QueryResultType (enum DATA_MANIFEST | DATA_ROWS), documented "Only the query types CREATE TABLE AS SELECT, UNLOAD, and INSERT can generate a manifest file. If you use DATA_MANIFEST for other query types, the query will fail"; the operation's client errors are InvalidRequestException (HTTP 400) and TooManyRequestsException (400). Recorded behavior: asking for DATA_MANIFEST on a SUCCEEDED plain SELECT is refused 400 InvalidRequestException with Message "Manifest files are only available for INSERT, CTAS (CREATE TABLE AS SELECT), and UNLOAD queries. query <QueryExecutionId> does not generate a manifest file." The fixed text is "Manifest files are only available for INSERT, CTAS (CREATE TABLE AS SELECT), and UNLOAD queries. query " … " does not generate a manifest file."; the single variable part is the refused execution's own QueryExecutionId, taken from the request.
  Emulator: same status (400) and same code (InvalidRequestException), but Message "Query result type DATA_MANIFEST is not available: this query wrote no data manifest" — emulator-authored text that names neither the query types that do generate a manifest nor the refused execution's id.
  Why: InvalidRequestException is the only client error this operation models for bad input, so the Message is the sole discriminator between "this query type has no manifest" and any other refusal. A client that matches AWS's sentence (or parses the execution id out of it to report which query was refused) never matches, and the actionable part of AWS's message — that INSERT/CTAS/UNLOAD are the manifest-producing types — is lost.
  Fix: the DATA_MANIFEST branch of the GetQueryResults handler (services/service-com-amazonaws-athena-amazonathena/src/ops/get_query_results.rs lines 223-231, the `None =>` arm that formats the refusal) must raise its modeled InvalidRequestException with AWS's wording, interpolating the request's QueryExecutionId.
  Traces: athena.get-query-results-data-manifest-type-unload-vs-select (the UNLOAD manifest listing, the independent S3 head of the manifest-listed object, the empty DATA_ROWS and the SELECT positive control all passed; only this refusal's message diverges).
