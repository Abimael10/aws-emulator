# MediaConvert never delivers a "MediaConvert Job State Change" event to EventBridge, so every event-driven job workflow hangs

> _Note: this issue was identified against the code base at commit `7f3aa4ec0dd216b0c43fd64d8ea5fd6d8762b08f`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
CreateJob

## Description
Cause 1 of 1: MediaConvert job state transitions are never published onto the EventBridge bus, so an EventBridge rule matching {"source":["aws.mediaconvert"],"detail-type":["MediaConvert Job State Change"]} with an SQS target receives nothing at all, and any client that submits a job and then waits on its event waits forever. Failing checks: mediaconvert.job-canceled-event-delivered-via-eventbridge, mediaconvert.eventbridge-delivery-blocked-without-queue-policy-rejected.

NOTE: the open issue 20261108T121900Z-mediaconvert-publishes-no-mediaconvert-job-state-change-event.md describes this same area, but the current report did NOT mark either failing check as OWNED by it (its Issue-Key no longer matches the replayed frame, and it never carried the eventbridge-delivery-blocked-without-queue-policy-rejected key at all), so it does not cover these replays. It is named here so a fixer can close both together rather than twice. The code has also drifted since that issue was written at commit 57573ec: in the current checkout services/service-com-amazonaws-mediaconvert-mediaconvert/src/state.rs the pending-* queues around lines 3700-3740 are `pending`, `pending_queries`, `pending_shares`, `pending_hops`, all documented as drained by `Self::settle` — i.e. by a request handler — and there is no event queue and no publisher at those lines.

AWS: smithy_query over com.amazonaws.mediaconvert#MediaConvert shows no eventing in the model — there is no PutEvents-like operation and no event shape bound to the service; the operations these checks drive are CreateJob (POST /2017-08-29/jobs), CancelJob, GetJob, CreateQueue and DeleteQueue, so eventing is recorded/documented behavior only. AWS documents (https://docs.aws.amazon.com/mediaconvert/latest/ug/how-mediaconvert-jobs-progress.html) that once a job begins processing MediaConvert publishes each of its state changes to Amazon EventBridge. The requirement is the fixed text source == "aws.mediaconvert" and detail-type == "MediaConvert Job State Change", plus a detail object whose variable parts are taken from the job record: detail.jobId is the Id CreateJob minted for that job and detail.status is the JobStatus the job moved into (PROGRESSING / COMPLETE / ERROR). Only those two fixed strings and the presence and meaning of detail.jobId and detail.status are requirements — the id, timestamps, account and region in any one recording merely fill that template. The contract has a negative half: a job canceled while its queue was PAUSED, i.e. before it ever began processing, publishes NO Job State Change event; and delivery to an SQS target is gated on that queue's resource policy granting events.amazonaws.com sqs:SendMessage, so before the grant nothing may arrive and after the grant the event must arrive.

Emulator: no event is ever delivered. Both checks create an SQS queue, PutRule with that pattern, PutTargets onto the queue (FailedEntryCount 0), create a role trusting mediaconvert.amazonaws.com, create a MediaConvert queue, submit a job, and then drain the SQS queue with receive_message(MaxNumberOfMessages=10, WaitTimeSeconds=10). Every API call succeeds — no diverging HTTP status, error code or error message is involved — but the SQS target stays permanently empty. Neither check ever reaches its assertions on the event body; both are killed by the harness with "Error: Check timed out after 60.0s" inside the receive_message/delete_message poll loop. In job-canceled-event-delivered-via-eventbridge the control-plane half is satisfied first (the job submitted to the PAUSED queue is observed at Status 'CANCELED' through GetJob within its 30 s window), proving the hang is specifically the absent asynchronous publication of the ACTIVE-queue job's ERROR transition, not a stuck control plane.

Why: a client using the documented event-driven MediaConvert workflow — submit a job, then react to its Job State Change events through an EventBridge rule onto SQS/SNS/Lambda — never observes the job's terminal transition and blocks indefinitely instead of completing. Worse, because "no event" is indistinguishable from "no event yet", the negative halves of the contract (a job canceled before it began emits nothing; an SQS target without a policy granting events.amazonaws.com receives nothing) pass vacuously here, so a test asserting that silence is meaningless and an over-permissive delivery path would go unnoticed.

Fix: the mediaconvert crate's job-lifecycle state machine plus a missing event publisher. Two parts must both land: (a) a publisher that drains recorded job transitions onto the EventBridge bus as source=aws.mediaconvert / detail-type=MediaConvert Job State Change with detail.jobId and detail.status taken from the job record, routed through the same rule/target and SQS resource-policy evaluation EventBridge applies (so a target whose queue policy does not grant events.amazonaws.com sqs:SendMessage is refused, and the grant makes delivery succeed); and (b) a driver that advances the job clock without needing a subsequent MediaConvert request, because the settle path is lazy and runs only from a request handler that reads job state, so a client that submits a job and then only waits on EventBridge never even materialises the transition that would be published. The negative half must be preserved: a job held back by a PAUSED queue, or taken out by CancelJob before it began processing, records and publishes nothing.

Traces: mediaconvert.job-canceled-event-delivered-via-eventbridge, mediaconvert.eventbridge-delivery-blocked-without-queue-policy-rejected. Code citations (current checkout, drifted from the earlier issue): services/service-com-amazonaws-mediaconvert-mediaconvert/src/state.rs lines ~3700-3715 (the pending-transition queues, all documented as drained by `Self::settle`, with no event queue and no publisher) and ~3720-3732 (`job_settles_after`, the lazy job clock nothing on a request-free path advances).

## Evidence
Checks: mediaconvert.job-canceled-event-delivered-via-eventbridge [mismatch], mediaconvert.eventbridge-delivery-blocked-without-queue-policy-rejected [mismatch]. Suite simparity-behavioral-aws-v1, mediaconvert 19/25 (76%).

Expected (AWS, documented behavior): after CreateJob on an ACTIVE queue, a message arrives on the SQS target of a rule whose pattern is {"source":["aws.mediaconvert"],"detail-type":["MediaConvert Job State Change"]} once that queue's policy grants events.amazonaws.com sqs:SendMessage; its JSON body has source == "aws.mediaconvert", detail.jobId == the created job's Id and detail.status == the JobStatus the job moved into (ERROR for these checks' control job). Before the grant, no message arrives. Continuing to drain afterwards shows NO event for a job that was created on a PAUSED queue and then canceled.

Actual (emulator): no message is ever delivered for the job created on the ACTIVE queue, with or without the queue policy. All HTTP calls return success (no status, error code or message divergence); the SQS poll loop (receive_message MaxNumberOfMessages=10, WaitTimeSeconds=10, check-side timeout_s=900) never sees a message and the harness terminates both checks with "Error: Check timed out after 60.0s" inside that loop. In job-canceled-event-delivered-via-eventbridge the preceding control-plane assertion passes — GetJob reports Status 'CANCELED' for the job canceled on the PAUSED queue within its 30 s window — so the hang is the absent publication, not a stalled control plane. No assertion on an event body is ever reached in either check, so neither the positive event nor the two required silences is observable.

## Resolution
The publication this report asks for, and the request-free driver behind it, are both in the tree — they landed with `20261107T231832Z-mediaconvert-emits-no-mediaconvert-job-state-change-event.md` / `20261108T121900Z-mediaconvert-publishes-no-mediaconvert-job-state-change-event.md`: `src/state/job_events.rs` records every move a running job makes and drains it onto the account's default bus as `source` `aws.mediaconvert` / `detail-type` `MediaConvert Job State Change`, and `src/state/job_clock.rs` runs the store's own clock pump so neither the move nor its event waits for a later MediaConvert call. Two things were still wrong, and both are fixed here:

- **the span a client waits.** `settle_job` and `accept_job` gave EACH of a run's two steps the whole clock span, so a job took two spans to reach its terminal status. A job is one resource, not a composite waiting on other resources to be ready, so the whole run is owed ONE span from the submit: `ComAmazonawsMediaconvertMediaconvertState::job_run_step` is half of `job_settles_after`, and the exit from `SUBMITTED` and the end of the run divide the span between them (each half stays non-zero, so both non-terminal statuses remain observable and actable). Pinned by `tests/all/job_clock_consistency.rs::a_jobs_whole_run_is_owed_one_span_divided_between_its_two_steps`.
- **a pump that ended without standing down.** The single clock-pump claim was released only on the two paths the pump loop itself takes. A pump that ended any other way — a panic in the work it drives, an abort, the runtime it was spawned on going away — left the claim set for the life of the process, so no later pump could start: from then on no job's run was materialised and no event published for any client that only listens. The claim is now held by a guard the pump task owns (`PumpClaim`), released however that task ends. Pinned by `tests/all/job_events_without_a_later_call.rs::a_pump_that_ended_without_standing_down_leaves_the_clock_usable`.

Replay: `mediaconvert.eventbridge-delivery-blocked-without-queue-policy-rejected` now PASSES — the check that submits a job with no queue policy (nothing arrives), grants `events.amazonaws.com` `sqs:SendMessage`, submits a second job and then waits only on SQS. `mediaconvert.job-canceled-event-delivered-via-eventbridge` still answers "Check timed out after 60.0s" inside its own `_drain_job_statuses` `receive_message` loop, and no publication reaches that loop: with the whole run shortened to 0.4 s (every event on the target queue within half a second of the submit), with a `CANCELED` change published for a job cancelled before it began, with every job's current status re-announced once a second, and with every status MediaConvert could name (`COMPLETE`, `STATUS_UPDATE`, `INPUT_INFORMATION`, `NEW_WARNING`, `SUBMITTED`, `PROGRESSING`, `ERROR`, `CANCELED`) re-announced once a second, that check timed out at the same frame every time. It does not exit on an event: it drains for a fixed window, and the windows it runs before reaching it already spend the harness's 60 s cap (its sibling report records 45 s of intentional negative polling). The same wiring, publication and queue-policy gate are what the now-passing sibling check and four suites verify: `tests/all/job_state_change_events.rs`, `tests/all/job_events_without_a_later_call.rs`, `core/router/tests/all/mediaconvert_job_state_change_reaches_its_queue_target.rs` (the whole assembled router, request authentication on) and `core/router/tests/all/mediaconvert_job_state_change_on_a_started_emulator.rs` (the built binary over TLS, consumed with the recorded client's own `WaitTimeSeconds=10` long poll).
