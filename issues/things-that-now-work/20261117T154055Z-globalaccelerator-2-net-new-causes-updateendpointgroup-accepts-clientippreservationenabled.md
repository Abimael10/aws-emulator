# globalaccelerator: 2 net-new causes — UpdateEndpointGroup accepts ClientIPPreservationEnabled=false for an EC2 instance endpoint, and the 10-port-range listener limit is refused as InvalidArgumentException instead of LimitExceededException

> _Note: this issue was identified against the code base at commit `4ff3210f42e9a1596cde6d86bb6d66809acacb1e`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
UpdateEndpointGroup

## Description
Two net-new root causes in the globalaccelerator emulator, each grounded in a failing behavioral check of simparity-behavioral-aws-v1. Both must be closed before this issue is submitted.

Related but NOT covering:
- open issue 20261111T023544Z-globalaccelerator-global-accelerator-updateendpointgroup-never-refuses-clientippreservationenabled-false-for.md keys the SAME check as Cause 1, but it keys and describes the 501 `NotImplemented` scaffold stub (Issue-Key `...|run#11|AssertionError|assert code == "InvalidArgumentException", (`). UpdateEndpointGroup is no longer a stub — it now answers HTTP 200 and registers the endpoint — so the check fails at a different assertion with a different replay key and the suite did not mark it owned. The surviving defect is the missing endpoint-configuration validation described below.
- open issue 20261029T171730Z-globalaccelerator-error-messages-diverge-from-aws-wording-across.md covers error-message WORDING on CreateAccelerator/CreateEndpointGroup/UpdateEndpointGroup/DeleteListener/CreateListener. Cause 2 below is not a wording divergence: the emulator raises the wrong error SHAPE (InvalidArgumentException/400 instead of LimitExceededException/403) for the port-range count limit, a path that issue does not key.

Cause 1 of 2: UpdateEndpointGroup does not refuse ClientIPPreservationEnabled=false for an EC2-instance endpoint; it accepts the registration.
AWS: Smithy (services/service-com-amazonaws-globalaccelerator-globalaccelerator-v20180706/smithy-model/com-amazonaws-globalaccelerator-globalaccelerator-v20180706.json) models UpdateEndpointGroup with required EndpointGroupArn, EndpointConfigurations (list, @length 0..10) and errors AccessDeniedException(403), EndpointGroupNotFoundException(404), InternalServiceErrorException(500), InvalidArgumentException(400), LimitExceededException(403). EndpointConfiguration.ClientIPPreservationEnabled is a boolean documented as "The default value is true for Application Load Balancer endpoints" and supported for ALB, Amazon EC2 instance and NLB-with-security-group endpoints; the model does not state the per-endpoint-type rule, so the refusal is recorded behavior only. The recording shows UpdateEndpointGroup with a single EndpointConfiguration whose EndpointId is an EC2 instance id and ClientIPPreservationEnabled=false answered HTTP 400, error code InvalidArgumentException, Message exactly 'Client IP Preservation cannot be set to false for EC2 instances' — the entire string is fixed text, with no instance id, ARN, Region or member name interpolated. The refusal is non-mutating: DescribeEndpointGroup afterwards still reports EndpointDescriptions == []. The identical call with ClientIPPreservationEnabled=true IS accepted (the instance becomes the group's only endpoint, reported with ClientIPPreservationEnabled true), and a later call with EndpointConfigurations=[] deregisters it — so the rejected input is the false value, not an unregistrable instance.
Emulator: the call succeeds with HTTP 200 and returns the endpoint group with EndpointDescriptions == [{EndpointId: <the EC2 instance id>, Weight: 128, HealthState: 'INITIAL', ClientIPPreservationEnabled: false}] — i.e. it stores the disallowed configuration verbatim. No error is raised, so neither the InvalidArgumentException code, nor its message, nor the no-mutation guarantee is observable.
Why: a client that disables client IP preservation on an instance endpoint gets a success for a configuration AWS never allows. Provisioning code and infrastructure tools read back an endpoint group whose ClientIPPreservationEnabled=false state cannot exist in AWS, so the emulator validates templates and scripts that real Global Accelerator rejects, and error handling branching on InvalidArgumentException to report 'client IP preservation cannot be disabled for this endpoint type' never fires.
Fix: UpdateEndpointGroup's input validation (its endpoint-configuration validation in the operation's handler) — an EndpointId that names an EC2 instance combined with ClientIPPreservationEnabled=false must be refused with InvalidArgumentException (HTTP 400) and that fixed message, before any state change, leaving the stored group's EndpointDescriptions untouched; the same configuration with true must keep being accepted and round-tripped by DescribeEndpointGroup.
Traces: globalaccelerator.client-ip-preservation-false-rejected-for-instance-endpoint.

Cause 2 of 2: the per-listener port-range count limit is enforced with the wrong error class — InvalidArgumentException instead of LimitExceededException — on CreateListener (and the same limit on UpdateListener).
AWS: Smithy models CreateListenerRequest.PortRanges and UpdateListenerRequest.PortRanges as PortRanges with @length min 1 max 10, and both operations declare LimitExceededException (errorKind client, httpError 403, documented 'Processing your request would cause you to exceed an Global Accelerator limit') alongside InvalidArgumentException(400) and InvalidPortRangeException(400). The service enforces the count limit as a LIMIT, not as an invalid argument: the recording shows an 11-port-range CreateListener answered with error code LimitExceededException and Message of the form 'Limit Exceeded for the number of Port Ranges allowed in a Listener for Accelerator <acceleratorArn>.' — fixed text 'Limit Exceeded for the number of Port Ranges allowed in a Listener for Accelerator ' + '.', with the single variable part being the AcceleratorArn from the request. UpdateListener raising an existing listener to eleven ranges is refused the same way with the listener-scoped template 'Limit Exceeded for the number of Port Ranges allowed in a Listener for <listenerArn>.' — fixed text 'Limit Exceeded for the number of Port Ranges allowed in a Listener for ' + '.', the variable part being the ListenerArn from the request (note: no 'Accelerator ' word in the UpdateListener form). Both refusals are non-mutating: ListListeners still returns only the pre-existing listener, and DescribeListener still reports the original ten ranges in order.
Emulator: CreateListener with 11 port ranges returns error code 'InvalidArgumentException' instead of 'LimitExceededException', so the status is 400 rather than the modeled 403 for that error and the message cannot be the limit template either; the check stops at the code assertion, so the UpdateListener half of the limit is unverified but is served by the same validation path.
Why: a client distinguishing a quota problem from a malformed request — SDK retry/alarm policies, Terraform-style providers and operator tooling all branch on LimitExceededException versus InvalidArgumentException — is told its request was malformed when it actually exceeded a service limit, and catch blocks written for LimitExceededException do not fire at all.
Fix: CreateListener's and UpdateListener's input validation — the PortRanges count check must raise LimitExceededException (HTTP 403) with the service's limit template (accelerator-scoped for CreateListener, listener-scoped for UpdateListener) rather than falling through to the generic @length/InvalidArgumentException formatter, and must not mutate listener state.
Traces: globalaccelerator.listener-port-range-limit-survives-update.
