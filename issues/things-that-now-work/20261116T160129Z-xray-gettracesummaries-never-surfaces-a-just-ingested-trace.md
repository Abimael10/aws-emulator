# xray GetTraceSummaries never surfaces a just-ingested trace in a minutes-wide recent window: the window is cut on the absolute hour grid, and within a slice the page is selected in trace-id order and capped at 5 instead of "the most recent results"

> _Note: this issue was identified against the code base at commit `8e5b1ec434632f47c13d48c4e6ea99d92dd8271f`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

GetTraceSummaries

=== Cause 1 of 2: a window of a few minutes is cut on the ABSOLUTE hour grid, so a window that straddles the top of an hour serves only the slice its EndTime falls in and the rest of the SAME requested window sits behind a NextToken ===
Failing checks: xray.e2e-trace-lifecycle-group-filter-consequence, xray.get-trace-summaries-returns-time-descending-order, xray.put-trace-segments-missing-trace-id-rejected.

AWS: Smithy (services/service-com-amazonaws-xray-awsxray/smithy-model/com-amazonaws-xray-awsxray.json) models GetTraceSummaries as POST /TraceSummaries, success 200, StartTime/EndTime required, @paginated {inputToken: NextToken, outputToken: NextToken, items: TraceSummaries}, errors InvalidRequestException (client, 400) and ThrottledException (client, 429). GetTraceSummariesResult$NextToken is documented: "If the requested time frame contained more than one page of results, you can use this token to retrieve the next page. The first page contains the most recent results, closest to the end of the time frame." Whether a second page exists is therefore keyed on how many RESULTS the requested time frame holds — not on how many absolute hour boundaries the frame happens to cross. For the narrow-window case this is recorded behavior only: each of the three recordings queries a window of 10 minutes or less that holds the 1-3 traces PutTraceSegments has just accepted, and reads the complete answer out of ONE call.

Emulator: the requested window is cut into one-hour slices on the absolute epoch-hour grid and exactly ONE slice is served per page — the slice the window's EndTime falls in — with any earlier part of the same requested window deferred behind a NextToken. services/service-com-amazonaws-xray-awsxray/src/state/trace_pages.rs: TRACE_PAGE_SECONDS = 60*60, hour_boundary_at_or_before(), window_page_boundaries(), window_page(); services/service-com-amazonaws-xray-awsxray/src/ops/get_trace_summaries.rs selects candidates only where `instant >= page.start && instant < page.end` and composes next_token from page.earlier. Consequence: a window such as [now-300s, now+300s] evaluated shortly after the top of an hour is served as the slice [hour, now+300s) only, so a segment recorded a minute or two earlier — inside the requested window, and counted by TracesProcessedCount — is absent from the first (and, for a caller that does not paginate, only) response. Nothing is refused: the call answers 200 with a short or empty TraceSummaries list plus a NextToken, and the split is clock-dependent, so the identical request a minute later returns a different subset.

Why: querying a short, recent window is the primary way a client finds a trace it just submitted, and what every "last 5/10 minutes" view and every post-submit poll does. The client gets 200 with no trace and cannot tell "not ingested yet" from "in an earlier slice of the window I asked about"; it only ever sees the whole answer if it paginates a window it had no reason to believe was paginated. Results are also not reproducible across the boundary.

Fix: the paging of GetTraceSummaries — derive page boundaries from the REQUESTED window (walking back from EndTime in page-long steps) and/or from the number of summaries selected, so a window shorter than one page is always a single page holding every matching trace in [StartTime, EndTime), while a multi-hour window keeps being paged and keeps reporting an ApproximateTime inside the requested window and a NextToken while results remain. The component is the boundary derivation and token form in services/service-com-amazonaws-xray-awsxray/src/state/trace_pages.rs together with the candidate selection and next_token composition in services/service-com-amazonaws-xray-awsxray/src/ops/get_trace_summaries.rs.

=== Cause 2 of 2: within a slice, the page is taken in TRACE-ID order and capped at 5 summaries, so the first page is not "the most recent results, closest to the end of the time frame" and an unfiltered query over a busy window never shows the caller its own just-ingested trace ===
Failing check: xray.e2e-trace-lifecycle-group-filter-consequence (its first poll is UNFILTERED; the other two checks scope their polls with an annotation FilterExpression and so narrow the candidate set, which is why this cause is grounded in this check).

AWS: Smithy, same operation. GetTraceSummariesResult$NextToken: "The first page contains the most recent results, closest to the end of the time frame" — the first page of a time frame is its most RECENT results, i.e. the selection inside a page is ordered by time descending from EndTime. The model declares no page size. Recorded behavior: the recording issues one unfiltered GetTraceSummaries over [now-300, now+300] and expects both trace ids it has just submitted (the newest two traces in that window) in that one response.

Emulator: candidates are collected by walking `store.traces`, a BTreeMap keyed by trace id, so the page's membership is decided in LEXICOGRAPHIC TRACE-ID order, not by time; the first TRACE_SUMMARIES_PAGE_SIZE = 5 matches in that order become the page and the 6th becomes the resume token (services/service-com-amazonaws-xray-awsxray/src/ops/get_trace_summaries.rs, the pass-one candidate walk and the `selected.len() == TRACE_SUMMARIES_PAGE_SIZE` branch; TRACE_SUMMARIES_PAGE_SIZE is declared in the same file). Hypothesis (not stated by the model and not shown directly by the report): with more than five traces stored inside the requested hour slice — which the suite accumulates, since every xray check that puts segments adds some — an unfiltered query's first page is five arbitrary trace ids and the caller's own newest traces are behind one or more NextTokens, so a poll that re-asks the same unpaginated query never converges. Note also that the page is additionally capped by a work budget whose exhaustion answers ThrottledException (429) with FILTER_BUDGET_SPENT_MESSAGE rather than a short page, so a filtered query over a large candidate set can be refused instead of answered.

Why: a client that asks for a short window and reads one response gets five traces chosen by the hex spelling of their ids. The trace it just wrote is invisible unless it walks every page, and "the most recent results" — the contract clients and the AWS console both rely on — is not what the first page holds. Ordering by id also makes the answer unstable as unrelated traffic is written.

Fix: the selection and ordering inside one page of GetTraceSummaries — order candidates by the window instant descending (newest first, from EndTime) before the page is cut, and make the emulator's page size large enough that a window holding a handful of traces is one page; the resume token must then name a position in that time order rather than a trace id in the keyspace walk. The component is the pass-one candidate walk, the pass-two page fill and TRACE_SUMMARIES_PAGE_SIZE in services/service-com-amazonaws-xray-awsxray/src/ops/get_trace_summaries.rs, with the token form in services/service-com-amazonaws-xray-awsxray/src/state/trace_pages.rs.

Traces: xray.e2e-trace-lifecycle-group-filter-consequence, xray.get-trace-summaries-returns-time-descending-order, xray.put-trace-segments-missing-trace-id-rejected.
