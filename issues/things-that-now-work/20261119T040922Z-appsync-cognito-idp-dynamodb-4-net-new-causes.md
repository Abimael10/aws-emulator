# appsync__cognito-idp__dynamodb: 4 net-new causes — expired Cognito tokens accepted, cognito_groups field authorization not enforced, data-source role permissions ignored, and mutations never pushed to realtime subscribers

> _Note: this issue was identified against the code base at commit `91a8ed8ebce8c6b25be2c9f1b5253611a954e20f`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
GraphQL (AppSync data plane: Query/Mutation/Subscription execution)

## Description
Four distinct root causes on the AppSync GraphQL/realtime data plane of a Cognito-user-pool-authorized, DynamoDB-backed API. Each cause below must be closed before submitting.

Cause 1 of 4: a Cognito user-pool access token past its validity window is still accepted by the GraphQL endpoint.
AWS: for an API with authenticationType AMAZON_COGNITO_USER_POOLS, AppSync validates the presented user-pool token (signature, issuer, audience and the exp/validity window) before executing anything; once the token is past its validity window the POST to uris.GRAPHQL is answered HTTP 401 and the operation is not executed (recorded behavior of the data plane; the app client in the check sets AccessTokenValidity/TokenValidityUnits so the window is minutes). AWS's own wording for this refusal is the UnauthorizedException-class body AppSync serves with the 401.
Emulator: the same request is answered HTTP 200 and the mutation runs — replay recorded 200 with {'data': {'putItem': {'id': 'item-...'}}} (the id is this run's value; the requirement is that an expired token must not execute the field).
Why: a client's session never actually ends — a leaked or stale token keeps read/write access to the API indefinitely, which is exactly the boundary token expiry exists to draw.
Fix: user-pool token validation in the AppSync GraphQL data-plane authorization layer (validate exp/validity before resolver dispatch and answer 401). Open issue 20261114T070045Z-appsync-cognito-idp-dynamodb-vtl-mapping-template-resolvers.md notes missing data-plane Cognito token validation for invalid/foreign-pool tokens but does not carry this check's replay key.
Traces: appsync__cognito-idp__dynamodb.appsync-cognito-expired-token-unauthorized-negative.

Cause 2 of 4: field-level cognito_groups authorization is not applied — a user whose ID token lacks the required group still gets the guarded field.
AWS: a field annotated @aws_auth(cognito_groups: ["Admins"]) (equivalently @aws_cognito_user_pools(cognito_groups: [...]), and with userPoolConfig.defaultAction DENY for the whole type) is served only to callers whose ID token carries that group in its cognito:groups claim. A caller without the group is answered HTTP 200 with a field-level GraphQL error whose errorType is "Unauthorized" and whose message is AWS's field-level denial text naming the field and type ("Not Authorized to access <fieldName> on type <TypeName>" — fixed text with the field and type names taken from the query), data for that field null, and no side effect: the DynamoDB write behind a guarded mutation does not happen. A caller WITH the group gets the normal result (recorded behavior; the directive semantics are AWS-documented, the model does not describe the data plane).
Emulator: the non-member call is answered HTTP 200 with the field's real value and no errors — recorded data {'adminField': {'id': 'item-...', 'value': 'admin-only'}} for the query case, and {'data': {'createItem': {'id': 'sim2real-xsvc-plainitem-...', 'value': 'x'}}} for the CloudFormation-deployed mutation case, i.e. the guarded write is also performed.
Why: group-based authorization is a no-op, so any authenticated user of the pool can read and write admin-only fields; a client relying on AWS's Unauthorized error to hide privileged data leaks it.
Fix: field-level auth directive evaluation (@aws_auth / @aws_cognito_user_pools cognito_groups, plus userPoolConfig.defaultAction) in the GraphQL execution/authorization path, with the Unauthorized GraphQL error emitted before the resolver runs. Open issue 20261114T140817Z-appsync-4-net-new-causes-the-graphql-endpoint.md mentions ignored field-level @aws_* auth for the plain `appsync` suite but does not carry these checks' replay keys.
Traces: appsync__cognito-idp__dynamodb.appsync-cognito-groups-claim-authorization-positive, appsync__cognito-idp__dynamodb.deploy-appsync-cognito-groups-field-authorization-positive.

Cause 3 of 4: a DynamoDB data source whose serviceRoleArn lacks the required action still succeeds — the data source's IAM role is never used.
AWS: an AMAZON_DYNAMODB data source assumes its serviceRoleArn, so a resolver whose role policy omits dynamodb:PutItem is answered HTTP 200 with a GraphQL error of the access-denied class (errorType carrying AccessDenied / a message of the form "User: arn:aws:sts::<account>:assumed-role/<role>/... is not authorized to perform: dynamodb:PutItem on resource: <tableArn> ..." — fixed text with the role, action and table ARN taken from state), the field resolves to null, and nothing is written to the table; a sibling resolver whose role does have the permission writes to the same table successfully (recorded behavior; IAM-propagation retries are already built into the checks).
Emulator: the unauthorized write is answered HTTP 200 with no errors and the item is created — recorded {'data': {'createItemBad': {'id': 'sim2real-xsvc-baditem-...', 'value': 'should-not-persist'}}}. The second check of this cause never reaches a verdict at all and exhausts its 60 s budget ("Check timed out after 60.0s") because it polls for a denial that never comes.
Why: the data source role stops being a permission boundary — a resolver can touch any table regardless of its role, so least-privilege configurations cannot be validated against the emulator, and a check that expects the denial hangs instead of failing fast.
Fix: data-source service-role assumption and IAM authorization on the DynamoDB data-source invocation path (evaluate the role's policy for the action/resource and surface the access-denied GraphQL error instead of executing the write).
Traces: appsync__cognito-idp__dynamodb.deploy-appsync-ddb-missing-datasource-role-negative, appsync__cognito-idp__dynamodb.appsync-ddb-datasource-missing-role-permission-negative.

Cause 4 of 4: a mutation is never published to active realtime subscriptions.
AWS: after a client connects to uris.REALTIME, sends a subscription start and receives start_ack, a mutation whose field is named by a @aws_subscribe-linked Subscription field causes the mutation's result to be pushed to every matching subscriber as a `data` message on that subscription id (the payload is the selection set of the subscription), within seconds; subscription filters (owner/group argument filters) decide which subscribers receive it (recorded behavior of the AppSync realtime protocol).
Emulator: the WebSocket connect and the start_ack succeed and the mutation itself succeeds (HTTP 200, and the item is in DynamoDB), but no data message is ever delivered — the replay records "no subscription event delivered within 30s of the mutation", "in-group subscriber never received the mutation push" and "matching-owner mutation was never delivered to the filtered subscriber". The negative half of the filter check cannot even be judged because its positive leg never arrives.
Why: every subscription-based client (live queries, Amplify subscriptions) sees nothing after a write, so no event-driven behavior — including the group/owner filtering that decides who may see an event — can be exercised or trusted.
Fix: the subscription registry and mutation-to-subscriber publication path in the AppSync realtime data plane (register start subscriptions, match mutation results against subscription fields and filters, and emit the data message on the subscription id). Open issue 20261112T152034Z-appsync-cognito-idp-dynamodb-2-net-new-causes.md covers the realtime upgrade being refused / endpoints published on unserved hosts; here the upgrade and start_ack succeed and the publication itself is missing, and it does not carry these checks' replay keys.
Traces: appsync__cognito-idp__dynamodb.appsync-mutation-triggers-subscription-positive, appsync__cognito-idp__dynamodb.appsync-subscription-payload-format, appsync__cognito-idp__dynamodb.appsync-subscription-cognito-group-filter-positive, appsync__cognito-idp__dynamodb.appsync-subscription-filter-mismatch-no-delivery-negative.
