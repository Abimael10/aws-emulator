# iot: package-version auto-versioning never happens — a succeeded job's destinationPackageVersions is dropped at CreateJob and no "$package" named shadow is ever written

> _Note: this issue was identified against the code base at commit `bdeab38f08235e16190fe33dc246d4235cdc81f4`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
UpdatePackageConfiguration

## Description
Cause 1 of 1: with versionUpdateByJobsConfig enabled, a job that carries destinationPackageVersions and whose execution reaches SUCCEEDED must have the installed package version reported into the targeted thing's reserved "$package" named shadow by the service itself. The emulator never performs that write, because the job's package-version association is discarded at creation time. Failing check: iot.update-package-configuration-auto-versioning-applied.

AWS: Smithy (services/service-com-amazonaws-iot-awsiotservice/smithy-model/com-amazonaws-iot-awsiotservice.json) documents UpdatePackageConfigurationRequest$versionUpdateByJobsConfig as "Configuration to manage job's package version reporting. This updates the thing's reserved named shadow that the job targets", and CreateJobRequest$destinationPackageVersions as "The package version Amazon Resource Names (ARNs) that are installed on the device when the job successfully completes. The package version must be in either the Published or Deprecated state when the job deploys." So once versionUpdateByJobsConfig.enabled is true (with its roleArn), the SERVICE — not the client — writes the reserved "$package" named shadow of each targeted thing when that thing's job execution reaches SUCCEEDED: the shadow document's state.reported gains an entry keyed by the package name whose "version" member is the version named by the job's destinationPackageVersions ARN (`arn:aws:iot:<region>:<account>:package/<packageName>/version/<versionName>`). The package name, version name, thing name and job id in that document are all values taken from the request and the emulator's state, never from any one recording. For the version reporting to be readable, CreateJob must also persist destinationPackageVersions (up to 25 ARNs) and a reader must report it on the Job.

Emulator: UpdatePackageConfiguration stores versionUpdateByJobsConfig and GetPackageConfiguration reads it back (enabled=true with the roleArn), but nothing consumes it. CreateJob accepts destinationPackageVersions and silently drops it — the member is never copied onto the stored job record — and when the IoT Jobs data plane moves the execution to SUCCEEDED, no shadow is written. iot-data GetThingShadow(thingName=<thing>, shadowName="$package") therefore keeps answering ResourceNotFoundException forever: the check's poll for the "$package" shadow never satisfies and the check is cut by the harness cap ("Check timed out after 60.0s") while polling it. The same gap is visible on the read side — the control plane's Job projection hard-codes destinationPackageVersions to None, so even a persisted association could not be read back.

Why: a client that enables version reporting by jobs and then deploys a package version through a job relies on the service to record what each device now runs. Against the emulator, the "$package" shadow is never created, so fleet-indexing queries over the reserved $package shadow, any consumer reading reported package versions per thing, and any "which version is installed" dashboard see nothing at all — and the call that is supposed to arrange it (UpdatePackageConfiguration) still reports success, so the failure is silent. A client cannot distinguish "no device has reported yet" from "this effect is not implemented", so it hangs waiting, exactly as the check does.

Fix: the job-execution terminal-status path of the IoT Jobs data plane plus the package-configuration state of the IoT control plane. CreateJob's handler must persist destinationPackageVersions on the shared job record (and validate each ARN names an existing package version in a deployable state); the handler that drives an execution to SUCCEEDED must, when package_configuration.version_update_by_jobs_config is enabled, write/merge the reserved "$package" named shadow of the targeted thing in the iot-data shadow store; and the control plane's Job projection must report the persisted destinationPackageVersions instead of None.

Traces: failing check iot.update-package-configuration-auto-versioning-applied (hangs at the "$package" shadow poll, cut at the 60 s cap). Supporting file citations in the checkout: services/service-com-amazonaws-iot-awsiotservice/src/ops/create_job.rs lines 356-376 (the RegisteredJob is built without input.destination_package_versions) and lines 436-449 (executions are queued with no package association); services/service-com-amazonaws-iot-awsiotservice/src/state.rs lines 3294-3345 (to_job documents destinationPackageVersions as deliberately omitted and sets it to None); services/service-com-amazonaws-iot-awsiotservice/src/ops/update_package_configuration.rs lines 154-167 (the configuration is stored and nothing else reads it). Note: the open issues "Implement iot UpdatePackageConfiguration: unimplemented scaffold stub" (20261030T100625Z) and "Implement iot GetPackageConfiguration: unimplemented scaffold stub" (20261113T145638Z) do NOT cover this: both operations are now implemented in the checkout and answer 200 — what is missing is the shadow-writing effect they configure.

## Evidence
Expected (AWS): after update_package_configuration(versionUpdateByJobsConfig={enabled:true, roleArn:<role>}) and a job created with destinationPackageVersions=[<packageVersionArn>] whose execution is reported SUCCEEDED by the device, iot-data GetThingShadow(thingName=<thing>, shadowName="$package") returns HTTP 200 with a shadow document whose state.reported contains an entry keyed by <packageName> with {"version": "<versionName>"} — the service writes it; the client never calls UpdateThingShadow. DescribeJob/ListJobs also report the job's destinationPackageVersions.

Actual (emulator): update_package_configuration → 200; get_package_configuration → versionUpdateByJobsConfig {enabled: true, roleArn: <role>} (read-back is correct); create_job with destinationPackageVersions → 200, the member is discarded; start_next_pending_job_execution → execution IN_PROGRESS; update_job_execution(status="SUCCEEDED") → 200; then iot-data GetThingShadow(thingName=<thing>, shadowName="$package") answers ResourceNotFoundException indefinitely. The check's poll for a "$package" shadow containing the package name never satisfies, and the harness cuts the check: "Check timed out after 60.0s". Code evidence: create_job.rs never reads input.destination_package_versions; state.rs to_job() sets destination_package_versions: None.

## Steps to Reproduce
1. iot.update_indexing_configuration(thingIndexingConfiguration={thingIndexingMode:"REGISTRY_AND_SHADOW", namedShadowIndexingMode:"ON", filter:{namedShadowNames:["$package"]}}) and wait for DescribeIndex(AWS_Things) to report ACTIVE.
2. iot.create_package(packageName=P); iot.create_package_version(packageName=P, versionName="1.0.0") → note packageVersionArn; iot.update_package_version(packageName=P, versionName="1.0.0", action="PUBLISH").
3. iot.update_package_configuration(versionUpdateByJobsConfig={enabled:true, roleArn:<an iot.amazonaws.com-assumable role>}, clientToken=<uuid>); confirm iot.get_package_configuration() reports enabled=true with that roleArn.
4. iot.create_thing(thingName=T); iot.create_job(jobId=J, targets=[<thingArn of T>], targetSelection="SNAPSHOT", document=..., destinationPackageVersions=[<packageVersionArn>]).
5. iot-jobs-data.start_next_pending_job_execution(thingName=T) until status IN_PROGRESS, then iot-jobs-data.update_job_execution(jobId=J, thingName=T, status="SUCCEEDED", executionNumber=..., expectedVersion=...).
6. Poll iot-data.get_thing_shadow(thingName=T, shadowName="$package"). AWS: within a short window the shadow exists and state.reported[P]["version"] == "1.0.0". Emulator: ResourceNotFoundException forever (the call never 200s), so the poll never completes.
7. Also observe iot.describe_job(jobId=J): destinationPackageVersions is absent from the Job.
