# ecr__ecs__logs: a task whose execution role is denied ecr:GetAuthorizationToken is stopped with CannotPullContainerError instead of ResourceInitializationError

> _Note: this issue was identified against the code base at commit `3fd6090c6180e74798ad464a124672539521deef`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
DescribeTasks

## Description
One net-new root cause. This check is marked neither ALREADY FILED nor OWNED, and no open issue carries its replay key. The closest open issue, 20261111T030649Z-cloudwatch-ecr-ecs-logs-an-ecs-task-whose.md, is a different cause (awslogs log-driver initialization is not authorized at all, and the task is reported as EssentialContainerExited); here the task IS correctly failed at start with stopCode TaskFailedToStart and an IAM-aware message, but it is attributed to the wrong failure phase/error class.

Cause 1 of 1: ECS collapses an execution-role denial of ecr:GetAuthorizationToken into the container-pull error class.
AWS: ECS evaluates the task execution role in two distinct phases, and the stoppedReason error class names which phase failed. Retrieving the ECR registry authorization token happens in the execution-role resource-initialization phase, BEFORE any registry request for the image is made, so a denial of ecr:GetAuthorizationToken stops the task with lastStatus STOPPED, stopCode TaskFailedToStart and a stoppedReason that begins with the fixed prefix `ResourceInitializationError:` and contains the fixed text `unable to retrieve ecr registry auth`, the underlying refusal `AccessDeniedException`, the exact denied action `ecr:GetAuthorizationToken`, and the assumed-role session ARN of the execution role (`arn:aws:sts::<account>:assumed-role/<execution-role-name>/<session-name>`). Only the role name/session, account and registry/repository values come from the request and the emulator's IAM state; the prefix and the quoted phrases are fixed text. `CannotPullContainerError` is reserved by AWS for a failure of the pull ITSELF (a valid token but the repository-scoped actions such as ecr:BatchGetImage denied, which AWS reports as `CannotPullContainerError: ... 403 Forbidden ...` naming the image). The container never runs in the auth-token case, so its DescribeTasks container entry carries no exitCode and no awslogs stream is created for it. Smithy: ecs TaskStopCode enum = TaskFailedToStart | EssentialContainerExited | UserInitiated | ServiceSchedulerInitiated | SpotInterruption | TerminationNotice | InfrastructureHealth; the stoppedReason wording is AWS-documented behavior (ECS task execution IAM role / stopped-task troubleshooting), not modelled — recorded behavior and AWS docs only for the message text.
Emulator: for an execution role granted the repository-scoped pull actions and logs actions but NOT ecr:GetAuthorizationToken, DescribeTasks reports stopCode TaskFailedToStart with a stoppedReason that opens with `CannotPullContainerError: failed to resolve ref <registry-host>/<repository>:<tag>: pull access denied, repository does not exist or may require authorization: User: <role arn> is not authorized to perform: ecr:GetAuthorizationToken on resource: * because no identity-based policy allows the ecr:GetAuthorizationToken action`. It never emits the `ResourceInitializationError:` prefix, never emits the `unable to retrieve ecr registry auth` phrase, uses the plain role ARN rather than the assumed-role session ARN, and uses the error class AWS reserves for the next leg of the check (repository actions denied).
Why: the error class in stoppedReason is the contract a client branches on to tell WHICH of the execution role's permissions is wrong. Because the emulator answers CannotPullContainerError for a registry-auth denial, the auth-token leg and the repository-permission leg are indistinguishable, and any automation or operator runbook keyed on the `ResourceInitializationError:` prefix (or on its absence to conclude the pull itself was attempted) draws the wrong conclusion and remediates the wrong IAM statement.
Fix: the ECS task-start path that simulates the execution role against ECR (the RunTask/task-placement resource-initialization step and the stoppedReason it stores on the task record read back by DescribeTasks) must classify a denial of ecr:GetAuthorizationToken as a resource-initialization failure — emitting the `ResourceInitializationError:` prefix with the `unable to retrieve ecr registry auth`/`AccessDeniedException` wording and the assumed-role session ARN — and reserve CannotPullContainerError for failures of the image pull after a token was obtained.

## Evidence
Cause 1 — Expected: DescribeTasks stoppedReason begins with 'ResourceInitializationError:' and contains 'unable to retrieve ecr registry auth', 'AccessDeniedException', 'ecr:GetAuthorizationToken' and 'assumed-role/<execution-role-name>/'; it must NOT contain 'CannotPullContainerError'. Actual (replay): AssertionError: a denied ECR auth token fails the task in the EXECUTION-ROLE resource-initialization phase, so the reason must open with 'ResourceInitializationError:'; got: 'CannotPullContainerError: failed to resolve ref <registry-host>/<repo>/docker/library/busybox:latest: pull access denied, repository does not exist or may require authorization: User: arn:aws:iam::<account>:role/<path>/<exec-role-name> is not authorized to perform: ecr:GetAuthorizationToken on resource: * because no identity-based policy allows the ecr:GetAuthorizationToken action'. (The registry host, repository prefix, account id and generated role name are per-run values, not requirements; the diverging parts are the error-class prefix, the missing 'unable to retrieve ecr registry auth'/'AccessDeniedException' fixed text, and the plain role ARN where AWS reports the assumed-role session ARN.)

## Steps to Reproduce
1. Create a CloudWatch Logs log group and an ECR repository (the check uses a pull-through-cache repository) holding a pullable image.
2. Create an IAM role trusted by ecs-tasks.amazonaws.com granting ONLY the repository-scoped pull actions (ecr:BatchCheckLayerAvailability, ecr:GetDownloadUrlForLayer, ecr:BatchGetImage, ecr:BatchImportUpstreamImage on the repository ARN) plus logs:CreateLogStream/logs:PutLogEvents — deliberately omitting ecr:GetAuthorizationToken.
3. RegisterTaskDefinition with that role as executionRoleArn and a container using the private image with the awslogs driver pointed at the log group; RunTask on a Fargate cluster.
4. Poll DescribeTasks until lastStatus == STOPPED.
Observed: stopCode TaskFailedToStart, stoppedReason opening 'CannotPullContainerError: failed to resolve ref ... pull access denied ... not authorized to perform: ecr:GetAuthorizationToken ...'. Expected: stoppedReason opening 'ResourceInitializationError:' containing 'unable to retrieve ecr registry auth', 'AccessDeniedException', 'ecr:GetAuthorizationToken' and the execution role's assumed-role session ARN, with no 'CannotPullContainerError' in it.
