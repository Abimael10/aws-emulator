## Description
Two net-new root causes in the codedeploy behavioral group. Both are net-new relative to what is already filed: open issue 20261107T094623Z-codedeploy-no-server-platform-ec2-agent-deployment-check.md and open issue 20261110T134745Z-codedeploy-the-minimumhealthyhosts-concurrency-check-cannot-start-the.md own the OLDER symptom (a launched instance never reported PingStatus 'Online' in SSM, hanging _wait_ssm_online/_wait_fleet_ready's first phase); in this replay the hosts DO come Online and the Server-platform checks now hang one step later, in the in-guest command plane, so those issues' replay keys no longer match these failures and the suite did not mark them owned. Open issues 20261107T224322Z-codedeploy-lambda-deployments-reach-succeeded-without-shifting-the.md and 20261109T135826Z-codedeploy-traffic-shifting-is-not-clock-paced-or.md are the nearest relatives of Cause 2, but neither covers the second-deployment alias shift under a Failed AfterAllowTraffic hook described here, and neither carries this check's replay key.

=== Cause 1 of 2: an SSM Run Command sent to the Server-platform host never reaches a terminal invocation status, so no EC2/agent CodeDeploy deployment can even be created ===
Failing check ids for this cause: codedeploy.deployment-group-alarm-in-alarm-state-blocks-the-deployment, codedeploy.ec2-agent-deployment-runs-appspec-hook-on-instance, codedeploy.file-exists-behavior-disallow-blocks-foreign-file-and-overwrite-replaces-it, codedeploy.agent-hands-the-hook-the-real-deployment-identifiers, codedeploy.applicationstop-hook-failure-blocks-redeploy-until-ignored, codedeploy.auto-rollback-on-deployment-failure-reinstalls-the-prior-artifact, codedeploy.hook-failure-skips-later-lifecycle-events-and-fails-the-target, codedeploy.lifecycle-event-order-and-applicationstop-only-on-redeploy, codedeploy.minimum-healthy-hosts-bounds-observed-concurrent-unavailability.

AWS: every Server-platform check first proves the launched host is usable by running a shell command on it through Systems Manager Run Command: ssm:SendCommand(InstanceIds=[<id>], DocumentName='AWS-RunShellScript', Parameters={commands:['systemctl is-active codedeploy-agent']}) followed by ssm:GetCommandInvocation(CommandId, InstanceId). On AWS the invocation leaves the non-terminal part of the status set within seconds. Smithy (ssm): CommandInvocationStatus is an enum with values Pending, InProgress, Delayed, Success, Cancelled, TimedOut, Failed, Cancelling — Pending/InProgress/Delayed are transient and a reachable managed node settles on Success (or Failed/TimedOut), after which StandardOutputContent carries the command's stdout. Only once the agent unit reads 'active' do these checks call codedeploy:CreateDeployment and then read the on-host effect (payload files, the hook run-log) back through the same Run Command channel. Smithy (codedeploy) states what is then meant to be observable and is currently unobservable: DeploymentStatus (Created|Queued|InProgress|Baking|Succeeded|Failed|Stopped|Ready), LifecycleEvent.status via LifecycleEventStatus (Pending|InProgress|Succeeded|Failed|Skipped|Unknown), Diagnostics{errorCode (LifecycleErrorCode: Success|ScriptMissing|ScriptNotExecutable|ScriptTimedOut|ScriptFailed|UnknownError), scriptName, message, logTail} and ErrorCode values such as HOOK_EXECUTION_FAILURE, ALARM_ACTIVE and HEALTH_CONSTRAINTS.
Emulator: DescribeInstanceInformation now reports the launched instance Online (the first phase of the harness's readiness gate passes, which it did not in the run that produced the two older issues), and SendCommand is accepted and returns a CommandId. GetCommandInvocation for that CommandId then stays in a non-terminal status indefinitely — the poll loop never sees a status outside ('Pending','InProgress','Delayed') and never obtains StandardOutputContent, so the agent-readiness gate never passes. Three checks carry the explicit frame: `_wait_agent_active` / `_wait_fleet_ready` -> `_invoke_command` -> "TimeoutError: the command ['systemctl is-active codedeploy-agent'] on 'i-…' finishing: the run budget ended first; not graded" (the instance id in that message is a per-run value, not a requirement). The remaining six are cut off by the harness's 60 s cap ("Check timed out after 60.0s") inside the same host-readiness setup, before any CreateDeployment is issued. Consequently zero Server-platform deployments are created in this replay and nothing about the Server compute platform is graded.
Why: a client cannot use this emulator for any EC2/on-premises CodeDeploy workflow. AppSpec file installs and fileExistsBehavior, the documented in-place hook order, ApplicationStop-only-on-redeploy, hook failure propagation with ScriptFailed diagnostics, the hook environment variables (APPLICATION_NAME, DEPLOYMENT_GROUP_NAME, DEPLOYMENT_ID, DEPLOYMENT_GROUP_ID, LIFECYCLE_EVENT), alarm gating, minimumHealthyHosts concurrency and auto-rollback artifact reinstall are all unreachable. Because the blocking symptom is a status that never advances rather than an error, a client's own wait loops hang instead of failing fast.
Fix: the SSM Run Command execution plane for an emulated managed node — the state behind GetCommandInvocation/ListCommandInvocations must advance a sent invocation to a terminal CommandInvocationStatus and populate StandardOutputContent/StandardErrorContent/ResponseCode for AWS-RunShellScript against a running instance. Once a host answers commands, the CodeDeploy Server-platform deployment driver (the instance-target lifecycle execution path behind CreateDeployment/GetDeploymentTarget) is what these checks go on to exercise.
Traces: the nine check ids listed above; three of them show the hang frame verbatim in _invoke_command, the other six end at the 60 s cap in the same setup.

=== Cause 2 of 2: a Lambda AllAtOnce deployment whose AfterAllowTraffic hook reports Failed never moves the alias to TargetVersion ===
Failing check id for this cause: codedeploy.after-allow-traffic-hook-failure-triggers-deployment-failure-rollback.

AWS: with CodeDeployDefault.LambdaAllAtOnce, CodeDeploy shifts 100% of the alias to the revision's TargetVersion BEFORE the AfterAllowTraffic lifecycle event runs, then invokes the hook function, which calls codedeploy:PutLifecycleEventHookExecutionStatus with a LifecycleEventStatus. So on the second deployment of the same alias (CurrentVersion=v2, TargetVersion=v3) lambda:GetAlias must report FunctionVersion=v3 while AfterAllowTraffic is still outstanding, and live invokes of the alias must reach that same version; only afterwards does a hook reporting 'Failed' fail the deployment with errorInformation.code HOOK_EXECUTION_FAILURE (Smithy codedeploy: ErrorCode includes HOOK_EXECUTION_FAILURE; LifecycleEventStatus includes Failed) and spawn the DEPLOYMENT_FAILURE auto-rollback named in rollbackInfo.rollbackDeploymentId. Recorded behavior shows the first (hook-approves) leg of this exact flow working against the emulator, so the shift is reachable at least once.
Emulator: the check's positive control passes — the first Lambda deployment reaches Succeeded, GetAlias reads the control's TargetVersion with no residual AdditionalVersionWeights and no rollback — and then the second deployment, identical except that its AfterAllowTraffic hook function reports 'Failed', never moves the alias: the poll of lambda:GetAlias(FunctionName, Name) never observes FunctionVersion == the new TargetVersion for the whole remaining wait, and the check ends in `_poll` at the GetAlias wait with "TimeoutError: the run budget ended before this wait finished; not graded". Nothing downstream (the Failed status, HOOK_EXECUTION_FAILURE, the AfterAllowTraffic event status, rollbackInfo) is reached. Hypothesis: the emulator performs the alias shift only as part of completing a deployment successfully rather than at the AllowTraffic step, so a deployment that is going to fail its post-traffic hook (or one whose hook Lambda is never invoked and therefore never settles) leaves the alias at CurrentVersion.
Why: a client validating a canary/all-at-once Lambda rollout cannot observe the invariant the AfterAllowTraffic hook exists to validate — that traffic is already on the new version when the hook runs — and a client testing rollback never sees the pre-rollback state. The alias silently staying on the old version while the deployment is InProgress also makes a failing-hook rollback indistinguishable from a deployment that never shifted at all.
Fix: the Lambda deployment execution path behind CreateDeployment — the alias/traffic-shift step must run at the AllowTraffic lifecycle event (before AfterAllowTraffic is dispatched) and must be independent of the eventual deployment verdict; the hook dispatch and PutLifecycleEventHookExecutionStatus handling then gate only the deployment's terminal status and its auto-rollback.
Traces: codedeploy.after-allow-traffic-hook-failure-triggers-deployment-failure-rollback (fails in the GetAlias poll after its positive-control leg passed).

## Steps to Reproduce
Cause 1:
1. Create a VPC/public subnet and an instance profile granting AmazonSSMManagedInstanceCore plus S3 read, and read the AL2023 AMI id from the public SSM parameter /aws/service/ami-amazon-linux-latest/al2023-ami-kernel-default-x86_64.
2. ec2:RunInstances one t3.micro with that profile and user-data installing SSM Agent and the CodeDeploy agent; wait for state 'running'.
3. Poll ssm:DescribeInstanceInformation(Filters=[{Key:'InstanceIds',Values:[<id>]}]) until PingStatus=='Online' (this now succeeds).
4. ssm:SendCommand(InstanceIds=[<id>], DocumentName='AWS-RunShellScript', Parameters={commands:['systemctl is-active codedeploy-agent']}) and then poll ssm:GetCommandInvocation(CommandId=<id>, InstanceId=<id>).
5. Observe Status stays Pending/InProgress/Delayed forever and StandardOutputContent is never produced, so no Server-platform codedeploy:CreateDeployment against that tagged host is ever attempted.

Cause 2:
1. Create a Lambda function with three published versions (v1, v2, v3) and an alias pointing at v1; create two hook functions that call codedeploy:PutLifecycleEventHookExecutionStatus with 'Succeeded' and 'Failed' respectively.
2. codedeploy:CreateApplication(computePlatform='Lambda') and CreateDeploymentGroup with deploymentConfigName='CodeDeployDefault.LambdaAllAtOnce' and autoRollbackConfiguration={enabled:true, events:['DEPLOYMENT_FAILURE']}.
3. CreateDeployment with an AppSpec whose Resources name the alias with CurrentVersion=v1/TargetVersion=v2 and Hooks AfterAllowTraffic=<approving hook>; wait for Succeeded and confirm lambda:GetAlias reads v2 (passes today).
4. CreateDeployment again with CurrentVersion=v2/TargetVersion=v3 and Hooks AfterAllowTraffic=<failing hook>.
5. Poll lambda:GetAlias(FunctionName, Name=<alias>) while the deployment is InProgress. Observe FunctionVersion never becomes v3 — AWS shifts to TargetVersion before AfterAllowTraffic runs — so the subsequent Failed/HOOK_EXECUTION_FAILURE/rollbackInfo behavior is never observable.
