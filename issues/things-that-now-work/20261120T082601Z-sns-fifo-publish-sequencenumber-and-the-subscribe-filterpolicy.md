=== Cause 1 of 2: a FIFO topic's Publish answers a zero-padded, consecutive, store-global counter where SNS answers a large non-consecutive per-MessageGroupId sequence number ===
Fixture/step: sns-fifo-topic-publish-requires-message-group-id#task#3.
AWS: Smithy (com.amazonaws.sns#PublishResponse$SequenceNumber, target String) documents it exactly: "This response element applies only to FIFO (first-in-first-out) topics. The sequence number is a large, non-consecutive number that Amazon SNS assigns to each message. The length of SequenceNumber is 128 bits. SequenceNumber continues to increase for each MessageGroupId." So the modelled requirements on the member's FORM are: large (128-bit scale, hence a long decimal with NO leading zeros), non-consecutive (a client cannot derive the next one), and monotonically increasing WITHIN a MessageGroupId. Recorded behavior confirms the form: the first Publish to a freshly created FIFO topic is answered a 20-digit decimal with no leading zero that is nowhere near 1. Its exact digits are a per-recording value and are NOT the requirement — the requirement is the shape of the value and its per-group monotonicity.
Emulator: PublishResult.SequenceNumber is a zero-padded count of publishes starting at 1 for the first message of a fresh process. state.rs `next_sequence_number()` does `self.sequence_counter = self.sequence_counter.saturating_add(1)` and then `format!("{:020}", self.sequence_counter)`; ops/publish.rs reaches it as `topic.is_fifo.then(|| store.next_sequence_number())`. That counter is (a) consecutive, (b) leading-zero padded, and (c) GLOBAL to the store rather than per MessageGroupId, so two message groups of one topic consume one shared run of numbers.
Why: a client that treats SequenceNumber as the documented large non-consecutive number gets a value AWS never serves. Leading zeros break a strict numeric parse and any equality against the 20-significant-digit form; a consecutive counter lets a client predict the next message's sequence number, which the model explicitly says it cannot; and because the counter is shared across message groups, the per-group "continues to increase for each MessageGroupId" guarantee is observable only by accident — interleaved groups see gaps that AWS's independent per-group progression does not produce. Ordering/dedup logic keyed on the member therefore behaves differently against the emulator.
Fix: the SNS state's FIFO sequence-number assignment (state.rs `next_sequence_number` and the `sequence_counter` field it advances, called from the Publish handler in ops/publish.rs) — mint a large, non-consecutive, leading-zero-free decimal of 128-bit scale, advanced PER MessageGroupId and strictly increasing within a group, and carry the same value into the delivered notification envelope's `SequenceNumber` member (ops/publish.rs already copies it there).
Traces: sns-fifo-topic-publish-requires-message-group-id#task#3.

=== Cause 2 of 2: Subscribe's refusal of a bad FilterPolicy document drops the 'Attributes Reason: ' frame, so it names a request member Subscribe does not have ===
Fixture/step: sns-filter-policy-numeric-operator-non-numeric-operand-rejected#task#3.
AWS: Smithy (com.amazonaws.sns#Subscribe) has NO FilterPolicy member — the document arrives inside the `Attributes` map (SubscriptionAttributesMap), whose doc lists "FilterPolicy - The simple JSON object that lets your subscriber receive only a subset of messages"; the operation declares InvalidParameterException (errorKind client, httpError 400, awsQueryError code `InvalidParameter`). Recorded behavior: a filter policy whose `numeric` operator is given a non-numeric operand is refused 400 / `InvalidParameter` with Error.Type Sender and Error.Message framed by the member it arrived in: `Invalid parameter: Attributes Reason: FilterPolicy: Value of <operator> must be numeric\n at [Source: (String)"<the policy document, echoed>"; line: <line>, column: <column>]`. FIXED text of that message: `Invalid parameter: `, ` Reason: `, `: Value of `, ` must be numeric`, `\n at [Source: (String)"`, `"; line: `, `, column: `, `]`. VARIABLE parts, all taken from the request: the member the attribute arrived in (`Attributes`), the attribute name (`FilterPolicy`), the comparison operator from the submitted policy (`>` in this step), the submitted policy document echoed verbatim, and the line/column the reader stopped at. Nothing in it comes from a per-run value.
Emulator: status 400 and Error.Code `InvalidParameter` are right, and the reader's own clause and source frame are byte-identical; the message is `Invalid parameter: FilterPolicy: Value of > must be numeric\n at [Source: ...]` — the `Attributes Reason: ` frame is missing. state.rs's FilterPolicy arm of the attribute-value refusal maps `filter_policy::DocumentFault::Grammar(reason)` through `AttributeMember::Named.refusal(name, &reason)` — unconditionally the BY-NAME framing — while the sibling `DocumentFault::Limit(reason)` arm goes through `member.refusal(name, &reason)` and therefore does get the frame. The crate already states the rule it is breaking in that same file: "a request that carried it in an `Attributes` MAP is told which member it has to change, and one that was given the attribute BY NAME needs no such frame", with recorded evidence cited for RawMessageDelivery (`Invalid parameter: Attributes Reason: RawMessageDelivery: ...` through Subscribe vs `Invalid parameter: RawMessageDelivery: ...` through SetSubscriptionAttributes). A grammar fault is simply routed around that rule.
Why: the frame is how SNS tells a client WHICH request member to change. Against the emulator a Subscribe caller is pointed at a `FilterPolicy` member that does not exist on Subscribe, and the Subscribe refusal becomes byte-identical to the SetSubscriptionAttributes refusal, where the un-framed sentence is the correct one — so clients, assertion matchers and log pipelines keyed on AWS's text cannot tell the two refusals apart and cannot locate the offending member.
Fix: SNS subscription-attribute validation (state.rs, the `FILTER_POLICY_ATTRIBUTE` arm of the attribute-value refusal that maps `filter_policy::DocumentFault`) — frame a `Grammar` fault by the `member` the document arrived in, exactly as the `Limit` fault already is, so the same reader sentence is reported with the `Attributes Reason: ` frame through Subscribe and without it when the attribute was given by name. The reader's own clause and `[Source: ...]` suffix must not change.
Traces: sns-filter-policy-numeric-operator-non-numeric-operand-rejected#task#3.
