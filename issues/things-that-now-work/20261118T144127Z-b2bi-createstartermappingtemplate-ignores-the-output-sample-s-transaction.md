# b2bi CreateStarterMappingTemplate ignores the output sample's transaction-body values: body elements are the bare word PLACEHOLDER instead of "PLACEHOLDER: <sample value>"

> _Note: this issue was identified against the code base at commit `4e36bbfa0b5661aa2fd9826663b014bc119c6585`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
CreateStarterMappingTemplate

## Description
Cause 1 of 1 — the starter template generated for a request that names `outputSampleLocation` carries NOTHING the sample's transaction body said: every body-segment element is the bare literal `PLACEHOLDER`, where AWS surfaces the value it read out of the sample for that element position as a placeholder carrying that value. Failing check: b2bi.create-starter-mapping-template-with-output-sample. (Related but NOT the same cause as the open issue 20261118T004349Z-b2bi-createstartermappingtemplate-returns-a-starter-template-whose-interchange.md, which is about the KEY `ISA_11_StandardsId` vs `ISA_11_InterchangeControlStandardsId` in the interchange header; this one is about the VALUES of the transaction-body elements and that issue does not cover it.)

AWS: Smithy models CreateStarterMappingTemplate with input `mappingType` (required, MappingType enum), `templateDetails` (required, TemplateDetails.x12 transactionSet/version) and `outputSampleLocation` (S3Location), output a single required `mappingTemplate` String, HTTP 200, errors AccessDeniedException/InternalServerException/ResourceNotFoundException/ValidationException (services/service-com-amazonaws-b2bi-b2bi/smithy-model/com-amazonaws-b2bi-b2bi.json). The model documents `outputSampleLocation` only as "Specify the location of the sample EDI file that is used to generate the mapping template" and says nothing about the contents of the returned string, so the content rule is RECORDED BEHAVIOR ONLY: with a sample EDI document supplied, AWS reads that document and the generated template surfaces each element value it found at a body-segment element position as a placeholder that CARRIES that value — the fixed prefix `PLACEHOLDER: ` followed by the element's value taken verbatim from the sample at that position (so a sample whose BEG segment's third element holds a purchase-order number yields `BEG_03` = `PLACEHOLDER: <that PO number>`, and a line-item segment's vendor item id yields `PO1_09` = `PLACEHOLDER: <that item id>`). Element positions the sample does not fill stay the bare word `PLACEHOLDER`. The same document is what TestMapping produces when the generated template is applied, so the sample-derived placeholder values must survive into `mappedFileContent` as well. Only the fixed text `PLACEHOLDER: ` and the rule "value from the sample at that element position" are the requirement; the particular PO number / item id in any one run are the sample's values, not part of the template.

Emulator: the handler reads the sample and then applies it to the ENVELOPE ONLY. services/service-com-amazonaws-b2bi-b2bi/src/ops/create_starter_mapping_template.rs:1535 builds the document purely from the transaction-set table, and :1576 calls `fill_envelope_from_sample(&mut document, Some(&parsed), ENVELOPE_LEVELS)`; the module doc at :19-:56 states this as intent — "the sample fills envelope VALUES only ... every element of a body segment is the PLACEHOLDER its table position asks for" and "none of the reader's own members (the `segment_id` of a segment, its detail-table loops such as `PO1-8000_loop`...) reaches a template". Replay: the ISA envelope assertions pass (ISA_06_SenderId `SENDER`, ISA_13_InterchangeControlNumber `000000001` echoed from the sample), then the body assertion fails — `AssertionError: expected the PO number from the sample surfaced as a placeholder, got 'PLACEHOLDER'` for `BEG_03`, i.e. the emulator returned `PLACEHOLDER` where AWS returns `PLACEHOLDER: <PO number from the sample>`. HTTP status is 200 and the response shape is correct; only the body of `mappingTemplate` diverges. Hypothesis (the check's next assertion is unreached because BEG_03 fails first, and the handler's own doc at :54-:56 says so explicitly): the same omission also drops the sample's detail-table loop member (the check next looks for a `PO1-8000_loop` member holding `PO1_09` = `PLACEHOLDER: <vendor item id>`), so the fix must carry the sample's body structure as well as its values; a fixer should confirm that second assertion after fixing the first.

Why: a starter template's placeholder values are the only thing that tells a caller WHICH field of its own input belongs at each EDI element position — that is the point of supplying an output sample. A client that takes this template sees an undifferentiated wall of identical `PLACEHOLDER` tokens with no trace of the sample it just paid to have read, so it cannot tell `BEG_03` (purchase order number) from any other element, and a client that diffs the emulator's template against AWS's sees two different documents. Downstream, TestMapping run on the template reproduces the same value-less document, so an integration test that asserts the mapped output contains the sample's business values passes against AWS and fails here.

Fix: the CreateStarterMappingTemplate handler's sample-application step — the sample fill currently restricted to the envelope levels must also walk the parsed transaction's body segments (and the detail-table loops they sit in), matching each parsed element to the template's `<SEGMENT>_<position>` member and rendering it as the `PLACEHOLDER: ` prefix plus the sample's value at that position, for both the JSONATA and the XSLT rendering; the TestMapping evaluation path must then carry those values through to `mappedFileContent`.
