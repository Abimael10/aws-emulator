# athena: 4 net-new causes — StartCalculationExecution refuses every submission into a live Spark session ('Not authorized to make this request.'), calculations never execute, the TERMINATED-session refusal is the wrong sentence, and TerminateSession never cancels in-flight calculations

> _Note: this issue was identified against the code base at commit `2901dc6a3b1a6d3c36a8ae908870ebb8c494c947`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
StartCalculationExecution

## Description
REOPENS 20261118T150005Z-athena-2-net-new-causes-listnotebookmetadata-answers-501.md: its fix left the call refused. That issue's Cause 2 read AWS's generic authorization sentence off ONE recording (a session started for a notebook-less probe) and the handler now applies that refusal to every submission whose session carries no NotebookId, so StartCalculationExecution is still refused on the sessions where AWS accepts it — 10 behavioral checks under the heading `### athena` now fail on that refusal. The open stub issue 20261117T053359Z-athena-startcalculationexecution-stub.md names the same handler file but describes the pre-fix 501 NotImplemented and carries only one check id; it does not cover these refusals. None of the 10 failing checks is marked ALREADY FILED or OWNED.

This bundle carries 4 causes. ALL FOUR must be closed before submitting.

Cause 1 of 4: StartCalculationExecution refuses a submission into a live IDLE Spark session that was started without a NotebookId.
  AWS: Smithy (services/service-com-amazonaws-athena-amazonathena/smithy-model/com-amazonaws-athena-amazonathena.json) — StartCalculationExecution input SessionId @required (@length 1..256), CodeBlock (@length 0..68000), Description, ClientRequestToken (IdempotencyToken @length 32..128), CalculationConfiguration (deprecated); output CalculationExecutionId (@length 1..36) + State (CalculationExecutionState: CREATING|CREATED|QUEUED|RUNNING|CANCELING|CANCELED|COMPLETED|FAILED); errors InvalidRequestException (client, httpError 400), ResourceNotFoundException (client, 400), InternalServerException (server, 500). The operation doc says it "Submits calculations for execution within a session" — it is bound to a SESSION, not to a notebook, and NotebookId is not an input of StartSession's required set. Recorded behavior: on a PySpark-engine workgroup (Configuration.EngineVersion.SelectedEngineVersion 'PySpark engine version 3' + ExecutionRole), StartSession with only WorkGroup + EngineConfiguration (no NotebookId) reaches State IDLE, and StartCalculationExecution(SessionId=<that session>, CodeBlock=<python>) answers HTTP 200 with a CalculationExecutionId. AWS's sentence 'Not authorized to make this request.' (entirely fixed text, no variable parts) is what AWS answers for an id it will not act on — an UNKNOWN session id and an UNKNOWN CalculationExecutionId — not for a healthy session: athena.start-calculation-execution-terminated-session-not-found asserts exactly that pairing (a random uuid SessionId is refused with that sentence, the live session is accepted), and athena.calculation-ops-reject-unknown-calculation asserts the same sentence from Get/GetStatus/GetCode/StopCalculationExecution for an unknown calculation id.
  Emulator: services/service-com-amazonaws-athena-amazonathena/src/ops/start_calculation_execution.rs requires the session record to carry a notebook_id that still resolves in the notebook store, and otherwise returns `invalid_request(crate::state::SESSION_NOT_FOUND)` — HTTP 400 Error.Code 'InvalidRequestException', Message 'Not authorized to make this request.'. Every suite session is started through plain StartSession (WorkGroup + EngineConfiguration, no NotebookId), so every submission is refused and no calculation is ever minted.
  Why: the whole Spark/notebook data plane is unreachable. A client that provisions a session and submits a cell gets a 400 client-class refusal it must surface to the user as an authorization failure, where AWS returns a CalculationExecutionId; every id-dependent follow-up (GetCalculationExecution, GetCalculationExecutionStatus, GetCalculationExecutionCode, StopCalculationExecution, ListCalculationExecutions) is unreachable, and the refusal is indistinguishable from AWS's genuine unknown-id refusal.
  Fix: the StartCalculationExecution handler (services/service-com-amazonaws-athena-amazonathena/src/ops/start_calculation_execution.rs) — accept a submission against any session this store holds in an accepting state and stop making a bound notebook a precondition; keep the SESSION_NOT_FOUND sentence for a session id the store does not hold.
  Traces: athena.spark-calculation-returns-computed-stdout-result, athena.calculation-execution-lifecycle-start-get-status-code-stop, athena.calculation-ops-reject-unknown-calculation, athena.calculation-execution-exceeds-timeout-marked-timed-out, athena.start-calculation-execution-on-terminated-session-rejected, athena.start-calculation-execution-terminated-session-not-found, athena.e2e-notebook-session-calculation-teardown, athena.e2e-query-lifecycle-dashboard-and-workgroup-teardown, athena.telemetry-resource-dashboard-emitted-for-workgroup, athena.telemetry-resource-dashboard-reflects-reservation-usage.

Cause 2 of 4: an accepted calculation is never executed — it never leaves its submission state, writes no stdout/result object and reports no statistics.
  AWS: Smithy — GetCalculationExecution output carries Status (CalculationStatus: SubmissionDateTime, CompletionDateTime, State, StateChangeReason), Statistics (CalculationStatistics: DpuExecutionInMillis (long), Progress) and Result (CalculationResult: StdOutS3Uri, StdErrorS3Uri, ResultS3Uri — each S3Uri @pattern ^(https|s3|S3)://([^/]+)/?(.*)$ — and ResultType), plus SessionId and WorkingDirectory; CalculationExecutionState documents the progression CREATING -> CREATED -> QUEUED -> RUNNING -> COMPLETED ('The calculation has completed without error'). Recorded behavior: a submitted code block RUNS. A calculation reaches State RUNNING while a long sleep is in flight and State COMPLETED when it finishes; GetCalculationExecution then reports SessionId = the submitting session, Result.StdOutS3Uri pointing at an object inside the workgroup's own ResultConfiguration.OutputLocation bucket whose body is the program's stdout, and Statistics.DpuExecutionInMillis > 0; GetCalculationExecutionCode returns the exact CodeBlock submitted, and ListCalculationExecutions(SessionId=...) lists the calculation with that terminal State.
  Emulator: the handler stores a CalculationRecord and returns its fixed state; its own module doc states 'Nothing here runs the code block … so no answer and no record claims a run, a result or a duration'. So even once Cause 1 is lifted, no calculation reaches a terminal state, no stdout/stderr/result object is written under the workgroup output location, and DpuExecutionInMillis stays 0 — the polls in these checks run to their deadline instead.
  Why: a notebook driver can submit work but never observe a result: it polls a never-terminal state until timeout, finds no Result URIs to fetch, and reads zero DPU time for work it is billed for. Anything built on 'submit a cell, read its output' cannot work at all.
  Fix: the calculation execution model in the service's state (crate::state CalculationRegistry/CalculationRecord) plus the Get/Status/Code/Stop/List calculation handlers — carry the calculation through its modeled states, run or simulate the code block to a COMPLETED terminal state with SubmissionDateTime/CompletionDateTime, write the stdout/stderr/result artifacts under the session workgroup's resolved OutputLocation and report their S3 URIs in Result, and report a non-zero DpuExecutionInMillis.
  Traces: athena.spark-calculation-returns-computed-stdout-result, athena.calculation-execution-lifecycle-start-get-status-code-stop, athena.calculation-ops-reject-unknown-calculation, athena.start-calculation-execution-terminated-session-not-found, athena.start-calculation-execution-on-terminated-session-rejected, athena.e2e-notebook-session-calculation-teardown.

Cause 3 of 4: a submission into a session that exists but is TERMINATED takes the unknown-id sentence instead of AWS's state-naming refusal.
  AWS: Smithy — the same InvalidRequestException (client, 400) is the error class, and its doc is 'Indicates that something is wrong with the input to the request.' Recorded behavior: after TerminateSession and GetSessionStatus reporting State 'TERMINATED', StartCalculationExecution(SessionId=<that session>, CodeBlock=...) is refused HTTP 400 InvalidRequestException with Message 'Session is in the TERMINATED state; needs to be IDLE to accept Calculations.' — fixed text apart from the state name, which is the session's current State from service state ('TERMINATED' here) and the required state 'IDLE'; the session still exists, so this is NOT the not-found/not-authorized sentence. The refused call must also mint nothing: ListCalculationExecutions(SessionId=...) returns the same number of entries before and after.
  Emulator: the handler's `if !session.is_active_at(now)` branch returns `invalid_request(crate::state::SESSION_NOT_FOUND)` — 400 InvalidRequestException 'Not authorized to make this request.' — deliberately collapsing this condition into the unknown-id sentence (the handler comment says no recording covers it; the recording above does).
  Why: a client cannot tell 'this session is finished, start a new one' from 'this id is unknown or you are not permitted' — the first is recoverable by starting a session, the second is an IAM/ownership problem, and the emulator gives both the same text.
  Fix: the StartCalculationExecution handler's session-state gate — refuse a session that exists but is not accepting calculations with the state-naming message, interpolating the session's current State and keeping the SESSION_NOT_FOUND sentence only for ids the store does not hold.
  Traces: athena.start-calculation-execution-on-terminated-session-rejected.

Cause 4 of 4: TerminateSession leaves an in-flight calculation untouched instead of forcing it to CANCELED.
  AWS: Smithy — CalculationStatus.StateChangeReason is documented as 'The reason for the calculation state change (for example, the calculation was canceled because the session was terminated)', and CANCELED is documented as 'The calculation is no longer running as the result of a cancel request'. Recorded behavior: with a calculation observed in State RUNNING, TerminateSession on its session drives that calculation to the terminal State CANCELED (never COMPLETED, never left RUNNING), observable through GetCalculationExecutionStatus.
  Emulator: no calculation ever runs (Cause 2) and nothing in the termination path touches the calculation registry, so a calculation's state is never changed by TerminateSession.
  Why: a client that terminates a session to stop runaway work sees the calculation's state never settle, so it cannot account for the work as cancelled or release it from a waiting queue.
  Fix: the session-termination path (TerminateSession handler and the session/calculation state it owns) — force every non-terminal calculation of the session to CANCELED with the session-terminated StateChangeReason.
  Traces: athena.calculation-execution-exceeds-timeout-marked-timed-out.
