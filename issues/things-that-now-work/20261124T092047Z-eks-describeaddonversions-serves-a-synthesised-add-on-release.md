# eks DescribeAddonVersions serves a synthesised add-on release history instead of the catalog's published versions

> _Note: this issue was identified against the code base at commit `0ed36ac69b61f04777ef4cd85714b039c0593841`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Description
One net-new root cause in the eks service, found by replaying the wire fixture corpus (trace set simparity-wire-aws-v1) against the emulator built from this checkout. The replay reports this cluster as unowned (owned_by empty, stub_path empty): no open issue carries its replay key.

Adjacent open issues that do NOT cover this cause (named so a fixer does not close it as a duplicate): 20261121T151648Z-eks-describeaddonversions-catalog-record-selection-and-registercluster-invalid.md covers DescribeAddonVersions selecting the wrong RECORD at addons[0] for a filtered query (and that record's Marketplace productUrl) under the key eks|DescribeAddonVersions|...|keys=$.addons[0],$.addons[0].marketplaceInformation.productUrl; 20261123T162615Z-eks-read-only-catalog-and-schema-discovery-reads.md covers the broader synthesised-catalog clusters the replay attributes to it. The divergence below carries a different replay key (keys=$.addons[0].addonVersions[0],$.addons[0].addonVersions[1]): here the correct add-on RECORD is served but the per-release version history INSIDE it is synthesised, and the replay lists it as owned by neither.

Cause 1 of 1: for a named add-on, the addonVersions list inside the served AddonInfo is not the add-on's published release history — different addonVersion strings, different computeTypes, different compatibility rows, and every compatibility row flagged defaultVersion true.
  AWS: DescribeAddonVersions is GET /addons/supported-versions, HTTP 200, with the request's filters bound as @httpQuery (kubernetesVersion, addonName, types, publishers, owners, maxResults, nextToken) and @paginated items=addons (Smithy: services/service-com-amazonaws-eks-awswesleyfrontend/smithy-model/com-amazonaws-eks-awswesleyfrontend.json; errors InvalidParameterException 400, ResourceNotFoundException 404, ServerException 500). Each addons element is an AddonInfo whose addonVersions targets AddonVersionInfoList, documented as "information about available add-on versions and compatible Kubernetes versions". Each AddonVersionInfo carries that one published release's addonVersion, architecture, computeTypes ("the compute type of the add-on version"), compatibilities, and the flags requiresConfiguration and requiresIamPermissions (both Boolean @default false). Each Compatibility carries clusterVersion, platformVersions and defaultVersion (Boolean @default false) - so for a given cluster version exactly the release EKS defaults to on that cluster version is flagged defaultVersion true and the other releases of the same add-on are flagged false. The list is the catalog's actual release history for the add-on, filtered by the request, not a generated set. The response status is 200; no error class is at stake, so the requirement is purely the payload's content.
  Emulator: answers 200 and serves an addons[0] record for the requested add-on, but its addonVersions entries are not the published releases. The replay reports addonVersions[0] and addonVersions[1] both diverging: in place of the catalog's consecutive older releases (a release whose compatibilities span a long run of older cluster versions, every row defaultVersion false because a newer release is the default, computeTypes limited to ['ec2'], requiresIamPermissions true / requiresConfiguration false) it serves a single synthesised newest-style release (a much higher addonVersion, computeTypes extended with 'auto', and compatibilities covering only the newest cluster versions with defaultVersion true on EVERY row). The older releases the catalog publishes for that add-on are absent entirely, and no served row ever carries defaultVersion false.
  Why: this listing is the only way a client discovers which versions of an add-on may be installed on a given cluster version and which one EKS defaults to. Because the historical releases are absent, a client that pins, upgrades or - critically - ROLLS BACK an add-on to a previously published version is told that version does not exist, and CreateAddon/UpdateAddon with that addonVersion is refused. Because every compatibility row is flagged defaultVersion true, a client that resolves "the default version for cluster version X" gets several mutually exclusive answers (or the wrong one) and installs a version EKS would not have chosen. computeTypes that advertise 'auto' for a release that does not support it leads an installer to schedule the add-on onto a compute type it cannot run on.
  Fix: the add-on catalog data behind DescribeAddonVersions' handler and that handler's per-record version projection - addonVersions must be built from the catalog's published release rows for the selected add-on (one AddonVersionInfo per release, newest first, each with its own architecture, computeTypes, compatibilities and requiresConfiguration / requiresIamPermissions), with defaultVersion true only on the release that is actually default for that clusterVersion, rather than synthesised from a single current release.
  Traces: eks-mbes-traj-create-addon-request-mistakes#task#7 (representative; 1 affected step).
