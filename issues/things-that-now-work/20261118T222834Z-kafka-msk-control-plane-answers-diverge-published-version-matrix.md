=== Cause 1 of 2 - GetCompatibleKafkaVersions, called with no ClusterArn, publishes the wrong upgrade matrix: wrong source rows, blanket (source-independent) target lists, and a short page. Fixture kafka-catalog-get-compatible-kafka-versions, step task#1.

AWS: Smithy kafka#GetCompatibleKafkaVersions (services/service-com-amazonaws-kafka-kafka/smithy-model/com-amazonaws-kafka-kafka.json): GET /v1/compatible-kafka-versions, ClusterArn bound as an OPTIONAL httpQuery, HTTP 200 -> GetCompatibleKafkaVersionsResponse.CompatibleKafkaVersions (jsonName compatibleKafkaVersions), a list of CompatibleKafkaVersion{SourceVersion (jsonName sourceVersion), TargetVersions (jsonName targetVersions)}; modeled errors BadRequestException 400, NotFoundException 404, ForbiddenException 403, UnauthorizedException 401, TooManyRequestsException 429, InternalServerErrorException 500, ServiceUnavailableException 503. The model enumerates no concrete versions and states no ordering, so WHICH rows the matrix holds, in WHICH order, and WHICH targets each source carries is recorded behavior only. The recorded behavior is: with no ClusterArn MSK publishes its whole upgrade matrix - one row per version its catalog publishes, in the service's own fixed published order, and each row's targetVersions is that SOURCE's own upgrade ladder (a per-source subset, EMPTY for a terminal version such as sourceVersion '3.8.link' -> [] or '4.1.x.kraft' -> []), never one blanket list repeated under every source. The requirement is that rule, not one run's literal strings: the matrix must hold exactly the versions the same service publishes through ListKafkaVersions (including the KRaft and link rows: '3.9.x.kraft', '3.8.x.kraft', '3.7.x.kraft', '4.0.x.kraft', '4.1.x.kraft', '3.8.link'), each paired with the ladder the service would actually accept for an UpdateClusterKafkaVersion from that source.

Emulator: HTTP 200 (status agrees) with a matrix whose rows disagree with the service's catalog in three independent ways. (a) Wrong/missing source rows: where the recording publishes a KRaft or link source the emulator publishes an old standard version instead - at the asserted positions expected sourceVersion '3.9.x.kraft' vs served '2.1.0', expected '3.8.link' vs served '2.3.1', expected '3.7.x.kraft' vs served '2.4.1', expected '3.9.x.kraft' vs served '2.8.2.tiered'. (b) Blanket target lists: every one of those old sources is served the SAME targetVersions ['3.6.0', '3.7.x', '3.8.x', '3.9.x'], i.e. a single list shared by many sources rather than each source's own ladder, and conversely rows that AWS publishes as terminal or short are served longer ladders ('4.1.x.kraft' expected [] but served ['4.2.x.kraft']; '4.0.x.kraft' expected ['4.1.x.kraft'] but served ['4.1.x.kraft', '4.2.x.kraft']; '3.6.0' expected ['3.9.x', '3.8.x'] but served the '3.8.x' -> ['3.9.x'] row at that position). (c) Short page: positions the recording asserts are absent altogether - expected {'sourceVersion': '3.8.x', 'targetVersions': ['3.9.x']} and {'sourceVersion': '1.1.1', 'targetVersions': []} both came back None - while the emulator emits an extra row at the head of the list. Fifteen asserted matrix positions diverge in one response.

Why: this call with no ClusterArn is how a client discovers the legal upgrade graph before it calls UpdateClusterKafkaVersion. A client reading the emulator's matrix is told a cluster on 2.1.0 may be moved straight to 3.9.x and that a cluster on 4.1.x.kraft may be moved to 4.2.x.kraft, while the same emulator's update gate (and the real service) honours a different ladder, so an upgrade planner proposes hops the service refuses and, because the KRaft and link sources are absent from the matrix, finds NO ladder at all for a cluster running '3.9.x.kraft' or '3.8.link' and concludes that cluster is terminal. Version-planning tooling that diffs the published matrix against MSK's sees the wrong rows at the wrong positions. No status or error code diverges: the defect is entirely in the response body's rows.

Fix: the published catalog rows and the per-source ladder derivation in the kafka crate's state module - crate::state::KAFKA_VERSION_CATALOG, projected by crate::state::published_kafka_versions and crate::state::compatible_target_versions, which the handler copies verbatim (services/service-com-amazonaws-kafka-kafka/src/ops/get_compatible_kafka_versions.rs, the no-ClusterArn branch at lines 251-272, which maps each published source through compatible_target_versions and therefore cannot itself be the source of the wrong values). The catalog must publish the same row sequence ListKafkaVersions pages (KRaft/link rows included) and each source must resolve to its OWN ladder, empty for a terminal version, so the matrix, the version listing and the update gate are one catalog seen three ways.

=== Cause 2 of 2 - DescribeClusterOperation on a cluster-operation ARN the service holds no operation for is refused as an authorization failure (403 AccessDeniedException) instead of the modeled not-found refusal (404 NotFoundException). Fixture kafka-cluster-operations-and-policy-notfound-error-paths, step task#3.

AWS: Smithy kafka#DescribeClusterOperation: GET /v1/operations/{ClusterOperationArn} (ClusterOperationArn @required, httpLabel), HTTP 200 -> ClusterOperationInfo; modeled errors BadRequestException 400, ForbiddenException 403, NotFoundException 404, UnauthorizedException 401, InternalServerErrorException 500. NotFoundException carries invalidParameter and message members. Which refusal a well-formed-but-unknown cluster-operation ARN draws is recorded behavior only; the recording is HTTP 404 with header x-amzn-errortype: NotFoundException and body {"invalidParameter": "clusterArn", "message": "The requested resource doesn\u2019t exist."}. In that message every character is FIXED text - it carries no value from the request or from state - and the requirement on invalidParameter is that it names the offending member in the service's lowerCamel wire vocabulary ('clusterArn' here, the cluster the operation ARN is scoped to). So: a well-formed cluster-operation ARN this region/account holds no operation for is a NOT-FOUND, and MSK answers it as such even when the ARN's account id is not the caller's.

Emulator: HTTP 403 with header x-amzn-errortype: AccessDeniedException and message "User: arn:aws:iam::<account>:user/<user> is not authorized to perform: kafka:DescribeClusterOperation on resource: <the submitted cluster-operation ARN> because no resource-based policy allows the kafka:DescribeClusterOperation action" (the recorded instance names account 000000000000, user 'emulator' and the probe's own operation ARN - those are per-run values, the divergence is the class and wording, not the literals), and it emits NO invalidParameter member at all (expected 'clusterArn', got None). Four asserted facets diverge at once: status 404 -> 403, errortype NotFoundException -> AccessDeniedException, the message text, and the missing invalidParameter.

Why: the status class and error code are what a client branches on. An SDK caller probing whether a cluster operation exists - polling an operation ARN returned by an earlier update, or reconciling an operation list - gets a retry/credential-remediation signal (403 AccessDenied, which SDK and Terraform-style error handling treat as a permissions problem to escalate, never as "absent") where AWS gives a plain 404 NotFoundException it would handle as "this operation is gone". Polling loops therefore abort as mis-permissioned instead of concluding absence, and code that reads invalidParameter to learn WHICH member was at fault gets nothing. The emulator also leaks an authorization decision for a resource it simply does not hold.

Fix: the refusal ordering in the operation's handler - services/service-com-amazonaws-kafka-kafka/src/ops/describe_cluster_operation.rs runs crate::state::authorization::authorize_cluster_operation_target (lines 164-169) BEFORE the registry lookup at lines 190-200, so an ARN that matches no stored operation is answered by the authorization path and never reaches the NotFoundException branch. Resolve existence first (or scope the authorization decision so that a well-formed cluster-operation ARN naming no operation of this region falls through to the modeled 404), and have that 404 carry invalidParameter 'clusterArn' with the service's single not-found message text.
