# bedrock-agent-runtime__lambda__s3vectors: the Python Lambda runtime provides none of the AWS SDK's dependency packages (s3transfer), so even a handler that bundles boto3+botocore in its own zip dies with Runtime.ImportModuleError and every in-function s3vectors call is unreachable

> _Note: this issue was identified against the code base at commit `775d8b7a5dc0233a720d935fa0de7ffef061d5f2`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
Invoke

## Description
One net-new root cause, grounded in all 10 surviving failing checks listed under `### bedrock-agent-runtime__lambda__s3vectors` in this run (no failure of this service is marked ALREADY FILED or OWNED).

Cause 1 of 1: the emulator's managed Python Lambda execution environment does not provide the AWS SDK for Python's dependency packages on the handler's import path. Each of these checks builds its own deployment archive containing index.py plus the `boto3` and `botocore` packages (the check's `_BUNDLE_MODULES = ("boto3", "botocore")`), so boto3 and botocore themselves are present in the function's code. `import boto3` still fails, because boto3/botocore pull in their declared dependency `s3transfer` (and, by the same mechanism, `jmespath`, `dateutil`/`python-dateutil`, `urllib3`), which the emulator's runtime sandbox has nowhere on sys.path. The runtime therefore fails module initialisation before the handler ever runs, and every in-Lambda s3vectors call in this service (CreateVectorBucket, CreateIndex, PutVectors, GetVectors, ListVectors, DeleteVectors, QueryVectors and the three negative paths) is unreachable.

AWS: Smithy (com.amazonaws.lambda) models Invoke as POST /2015-03-31/functions/{FunctionName}/invocations with code 200 and output InvocationResponse{StatusCode (@httpResponseCode), FunctionError (@httpHeader X-Amz-Function-Error), LogResult, Payload (@httpPayload), ExecutedVersion}. FunctionError is not a modeled error shape: on an otherwise successful 200 it is set in-band only when the function's own code or its module initialisation raises. AWS's managed Python runtimes ship the complete AWS SDK for Python installation — boto3, botocore AND their dependencies s3transfer, jmespath, python-dateutil, urllib3, six — preinstalled under the runtime's own site-packages (/var/runtime, /var/lang/.../site-packages), which sit on sys.path after the function's /var/task. Consequently, on AWS a function whose zip bundles only boto3+botocore imports cleanly: the bundled boto3/botocore shadow the runtime copies while `import s3transfer` resolves from the runtime's preinstalled packages. Invoke then answers 200 with NO X-Amz-Function-Error header and Payload equal to the handler's own return document (here `{"ok": true, "result": {...}}` for a successful s3vectors call, or `{"ok": false, "code": "<ErrorCode>", "message": "..."}` when the SDK call is refused). The response keys are the contract; the ARNs, bucket/index names, vector values and ids in any one run are per-run state and are not part of the requirement.

Emulator: Invoke answers HTTP 200 with X-Amz-Function-Error set and the Payload is the runtime's init-failure document, verbatim from the replay: {"errorMessage": "Unable to import module 'index': No module named 's3transfer'", "errorType": "Runtime.ImportModuleError", "requestId": "", "stackTrace": []}. In that message the fixed text is the Lambda runtime's own "Unable to import module '<handler-module>': <python ImportError text>" with errorType 'Runtime.ImportModuleError'; `<handler-module>` ('index') comes from the function's configured Handler and the ImportError text names the module Python could not find — the missing name `s3transfer` is the diagnosis, not a per-run value. The handler body never executes, so no s3vectors request is ever issued by the function.

Why: calling another AWS service from a Lambda handler with boto3 is the core Lambda pattern, and every check of this service depends on it. A client gets a 200 whose FunctionError header says the function blew up and whose payload is a runtime import error instead of the handler's JSON, so it cannot read back an indexArn, cannot round-trip PutVectors/GetVectors, and cannot distinguish 'the s3vectors call was refused' from 'the runtime could not load my code'. In particular the properties these checks exist to prove are unobservable: that a CreateIndex-returned indexArn later resolves on its own for PutVectors/GetVectors, that a dimension mismatch yields ValidationException with AWS's wording, that an indexArn naming an unrelated bucket yields NotFoundException ("The specified index could not be found"), and that a role lacking s3vectors:PutVectors / s3vectors:QueryVectors yields AccessDeniedException. Worse, because module init fails identically whatever the request is, a user cannot work around it by bundling the SDK: the dependency gap is in the runtime, not the archive.

Related but NOT covering this: several open issues report that this runtime provides NO AWS SDK at all and that handlers importing boto3 fault Runtime.ImportModuleError (20261105T074953Z-lambda-scheduler-the-python3-12-invoke-runtime-provides.md, 20261105T112044Z-dynamodb-lambda-s3-the-lambda-python-runtime-provides.md, 20261105T094343Z-dynamodb-events-lambda-the-lambda-python-runtime-provides.md, 20261105T105042Z-lambda-s3-s3control-the-python3-12-invoke-runtime.md), and others report missing CPython extension/stdlib pieces (_socket, _ssl, os.register_at_fork) or a missing in-SDK service client (20261116T201949Z-batch-ecr-lambda-logs-the-in-lambda-aws.md). None of them names `s3transfer` or the case here, where the function supplies boto3/botocore itself and the runtime still cannot satisfy the SDK's transitive dependency set — a different component (the sandbox's preinstalled dependency set) and a different fix.

Fix: the lambda crate's Invoke execution path — the component that builds the Python runtime sandbox and provisions its preinstalled packages. The sandbox's runtime site-packages must carry a complete AWS SDK for Python installation including its dependencies (s3transfer, jmespath, python-dateutil, urllib3, six) ahead of nothing and behind /var/task, so that a handler which bundles boto3/botocore (or bundles nothing and relies on the runtime copy) imports cleanly and Invoke answers 200 with no X-Amz-Function-Error header and the handler's return value as Payload.

Traces: all 10 failing checks of this service — bedrock-agent-runtime__lambda__s3vectors.lambda-s3vectors-createindex-positive, .lambda-s3vectors-createvectorbucket-positive, .lambda-s3vectors-deletevectors-positive, .lambda-s3vectors-dimension-mismatch-negative, .lambda-s3vectors-listvectors-positive, .lambda-s3vectors-missing-putvectors-permission-negative, .lambda-s3vectors-missing-queryvectors-permission-negative, .lambda-s3vectors-putvectors-positive, .lambda-s3vectors-queryvectors-positive, .lambda-s3vectors-wrong-vector-bucket-arn-negative.
