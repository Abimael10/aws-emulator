# config__sqs: a queue created under a running allSupported recorder never gets an AWS::SQS::Queue configuration item, so the unrecorded-vs-recorded refusal check cannot even establish its control (1 cause)

> _Note: this issue was identified against the code base at commit `bc3baab5128630830c7cde96b2247dfe3082e9b7`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
GetResourceConfigHistory

## Description
ONE root cause (1 of 1), grounded in 1 failing behavioral check of this replay. Service token taken from the suite heading `### config__sqs`. The gate's bootstrap report lists crate tokens (pending is empty; both services involved — services/service-com-amazonaws-configservice-starlingdoveservice and services/service-com-amazonaws-sqs-amazonsqs — are bootstrapped and answering), so this is filed as a fidelity finding, not a bootstrap gap.

Cause 1 of 1: the configuration-recorder recording pass writes no AWS::SQS::Queue configuration item for a queue created while a customer-managed recorder with recordingGroup {allSupported: true} is RECORDING and a delivery channel is in place, so every Config read path for that queue stays empty and the check's positive control ("a queue that IS recorded") can never be established. Failing check: config__sqs.config-history-rejects-unrecorded-queue-while-batch-get-omits-it.

AWS: Recorded behavior only for the recording itself — the Smithy model (com.amazonaws.configservice#StarlingDoveService) models the reads, not discovery. GetResourceConfigHistory takes required resourceType (enum ResourceType) and resourceId (@length 1..768), returns configurationItems (ConfigurationItemList) + nextToken, and declares errors InvalidLimitException / InvalidNextTokenException / InvalidTimeRangeException / NoAvailableConfigurationRecorderException / ResourceNotDiscoveredException / ValidationException (all client, HTTP 400). BatchGetResourceConfig takes resourceKeys (@length 1..100) and returns baseConfigurationItems + unprocessedResourceKeys. On AWS, once such a recorder is recording, CreateQueue causes Config to discover the queue and write a configuration item for AWS::SQS::Queue asynchronously, so GetResourceConfigHistory for that queue returns at least one configurationItem (whose arn identifies the queue) and BatchGetResourceConfig returns one baseConfigurationItem for its resourceKey. Only against that recorded control is the refusal leg meaningful: GetResourceConfigHistory for a never-created queue of the same shape must answer HTTP 400 ResourceNotDiscoveredException with the message `Resource <resourceId> of resourceType:AWS::SQS::Queue is unknown or has not been discovered` — fixed text `Resource `, ` of resourceType:`, ` is unknown or has not been discovered`, with the resourceId and resourceType taken verbatim from the request — while BatchGetResourceConfig and SelectResourceConfig answer the same absence by omission (empty baseConfigurationItems, empty unprocessedResourceKeys, empty Results) and HTTP 200, not by an error.

Emulator: no configuration item for the queue ever exists. The check sets up the delivery bucket, recorder and delivery channel, StartConfigurationRecorder succeeds and DescribeConfigurationRecorderStatus reports recording=true with lastStatus 'Pending', creates a queue with VisibilityTimeout 137, and then waits for that queue's history item; it fails in _await_history_items with `Last result: None. Recorder status: [{'name': ..., 'recording': True, 'lastStatus': 'Pending', 'lastErrorCode': None, 'lastErrorMessage': None}]`. Honest caveat about this one run: the control window had collapsed to 0.0 s (the check derives it from ctx.time_left() minus a 180 s reserve, and the setup had already consumed the budget), so the harness reports "not met within 0.0s" and the history read was not actually polled in this replay. What IS grounded is the state the emulator was left in — a recorder reporting recording=true that has produced nothing — and the identical, already-confirmed behavior of the same recording path on the same resource type: open issue 20261029T184030Z-config-sqs-a-running-allsupported-recorder-still-produces.md observed GetResourceConfigHistory for an AWS::SQS::Queue stay empty for a full 60 s poll under exactly this setup. That issue carries only the replay keys of config__sqs.config-queue-deletion-recorded-as-resource-deleted-configuration-item and config__sqs.config-recorded-queue-configuration-item-echoes-live-attributes, and this check is marked neither ALREADY FILED nor OWNED in this replay, so its key is filed here. Related: 20261113T185146Z-config-sqs-a-restarted-configuration-recorder-never-resumes.md (restart path) and 20261104T093105Z-config-a-running-recorder-never-discovers-an-ec2.md (ListDiscoveredResources / AWS::EC2::Instance) describe the same recording gap on other surfaces and do not carry this key either.

Why: a client that uses Config as its SQS inventory sees an account that contains no queues. Because nothing is ever recorded, ResourceNotDiscoveredException becomes the answer to every GetResourceConfigHistory call, so the error loses its meaning: a caller cannot distinguish "this resource was never created" from "Config records nothing at all", and the omission answers of BatchGetResourceConfig/SelectResourceConfig are indistinguishable from an empty account. Drift, audit and compliance tooling that gates on a resource being discovered therefore blocks on its first wait, and the refusal-vs-omission contract across the three read paths is untestable.

Fix: the configuration-recorder recording pass in the configservice crate — while a customer-managed recorder is RECORDING and its recordingGroup covers the type, resources created/changed/deleted in the other emulated services (here AWS::SQS::Queue from the SQS service) must be captured into Config's configuration-item state, which today only grows from an explicit PutResourceConfig write; GetResourceConfigHistory's handler must then return those items and reserve ResourceNotDiscoveredException for ids genuinely absent from that state, with BatchGetResourceConfig's and SelectResourceConfig's handlers projecting the same state by omission.

Traces: config__sqs.config-history-rejects-unrecorded-queue-while-batch-get-omits-it (_await_history_items for the CONTROL queue, check file line 588 calling the helper at line 414).
