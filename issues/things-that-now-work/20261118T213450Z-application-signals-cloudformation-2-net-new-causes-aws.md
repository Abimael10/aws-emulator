# application-signals__cloudformation: 2 net-new causes — AWS::ApplicationSignals::GroupingConfiguration gets no physical id or AccountId (stack Outputs omit OutputValue), and AWS::ApplicationSignals::InstrumentationConfig's Ref is its ARN instead of the composite primary identifier

> _Note: this issue was identified against the code base at commit `05d9ae115d48e8b01abfc6288b26f7d49ce19993`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
DescribeStacks

## Description
Two net-new root causes in CloudFormation's AWS::ApplicationSignals::* resource handling. Both are about the IDENTITY CloudFormation publishes for a deployed Application Signals resource — the value `Ref` resolves to and the attributes `Fn::GetAtt` reads — so both surface through `DescribeStacks` `Stack$Outputs` on a CREATE_COMPLETE stack. The resources themselves are really created (the provisioner arms in services/service-com-amazonaws-cloudformation-cloudformation/src/state/provisioner/application_signals.rs do call PutGroupingConfiguration / CreateInstrumentationConfiguration); what diverges is what the stack reports about them.

Cause 1 of 2: AWS::ApplicationSignals::GroupingConfiguration has no naming rule and no return values, so `Ref` and `Fn::GetAtt AccountId` resolve to nothing and the stack's Outputs entries come back with an OutputKey and NO OutputValue.
AWS: the CloudFormation resource reference for AWS::ApplicationSignals::GroupingConfiguration states that the type's primary identifier is the account, so `Ref` on the logical id returns the AWS account ID of the account whose single grouping configuration the resource is, and `Fn::GetAtt` publishes `AccountId` (that same 12-digit account id) and `UpdatedAt`. The service model agrees that the resource is the account's singleton: Smithy `PutGroupingConfiguration` takes only `GroupingAttributeDefinitions` (required) and no identifier at all, and answers `GroupingConfiguration` with `GroupingAttributeDefinitions` + `UpdatedAt` — the account id is not a wire member, it is the account the call was signed for. A `DescribeStacks` on a stack whose template declares `Outputs: {GroupingRef: {Ref: Grouping}, GroupingAccountId: {Fn::GetAtt: [Grouping, AccountId]}}` therefore reports both entries with an OutputValue equal to the caller's account id.
Emulator: both outputs are served with an OutputKey and no OutputValue, so the client's `{o["OutputKey"]: o["OutputValue"] for o in stack["Outputs"]}` raises `KeyError: 'OutputValue'`. The cause is that the type is absent from the naming/return-value tables in src/state/template.rs (no `GroupingConfiguration` entry exists there at all), and the provisioner arm answers `Created::attributes(...)` carrying only `UpdatedAt` (`grouping_configuration_attributes`), never the account id and never a physical resource id — so `template::evaluate_outputs` has nothing to resolve `Ref` or `AccountId` against and, by its documented "yield no value rather than a guessed one" rule, emits the output key bare.
Why: a client reads the identifier of what CloudFormation created out of the stack Outputs. With no OutputValue there is nothing to read: every consumer that indexes `OutputValue` (the AWS CLI's `--query 'Stacks[0].Outputs'` pipelines, CDK cross-stack references, any `o["OutputValue"]` in SDK code) fails with a key/attribute error on a stack AWS reports as fully deployed, and a nested stack that passes this Ref to a parent propagates an empty value instead.
Fix: CloudFormation's resource naming/return-values table for this type (src/state/template.rs — the `provision`/`return_values`/`conventional_attributes` path) must give AWS::ApplicationSignals::GroupingConfiguration a physical resource id of the deploying account's id and publish `AccountId` (the same account id) alongside the `UpdatedAt` the provisioner arm in src/state/provisioner/application_signals.rs already reports.
Traces: check application-signals__cloudformation.deploy-application-signals-grouping-configuration-singleton-round-trip-and-delete (the stack reaches CREATE_COMPLETE, then `stack_outputs()` raises KeyError: 'OutputValue').

Cause 2 of 2: AWS::ApplicationSignals::InstrumentationConfig's `Ref` resolves to the configuration's ARN instead of the type's composite primary identifier.
AWS: the CloudFormation resource reference for AWS::ApplicationSignals::InstrumentationConfig gives the type a COMPOSITE primary identifier built from the four dimensions that address one configuration plus the location hash the service computes, so `Ref` returns `<InstrumentationType>|<Service>|<Environment>|<SignalType>|<LocationHash>` — pipe-joined, in that order — where the first four are the values the declaration states and the last is the `LocationHash` the create answered. The ARN is a separate, additionally published attribute: `Fn::GetAtt Arn` (and `LocationHash`, `CreatedAt`). Smithy backs the split: `CreateInstrumentationConfiguration` answers both `ARN` (pattern `^arn:[^:]+:application-signals:[^:]+:[0-9]{12}:instrumentationConfig/.+/[0-9a-f]{16}$`) and a required 16-character `LocationHash`, and every later read/delete addresses the configuration by `InstrumentationType`/`Service`/`Environment`/`SignalType` + `LocationIdentifier.LocationHash`, not by the ARN. Fixed text of the Ref is the three `|` separators; every other part is a value from the request (`InstrumentationType`, `Service`, `Environment`, `SignalType`) or from the create's answer (`LocationHash`).
Emulator: `Ref` resolves to the ARN — the output came back as an `arn:aws:application-signals:<region>:<account>:instrumentationConfig/<service>/<environment>/<signalType>/<locationHash>` string where the composite id was due, while `Fn::GetAtt Arn` correctly carries that same ARN. src/state/provisioner/application_signals.rs::create_instrumentation_config sets `Created { physical_resource_id: Some(arn), .. }` from the `Arn` attribute, and src/state/template.rs carries no naming rule for the type to override it, so the resource's physical id — what `Ref`, `StackResource$PhysicalResourceId` and the delete path all use — is the ARN.
Why: a client that feeds this Ref back to Application Signals, or to Cloud Control / an import, is handing over a value that is not the type's primary identifier: imports and `cloudcontrol` reads keyed on the composite id fail, and the stack's reported PhysicalResourceId does not match what the resource schema says identifies the resource. It also makes the two outputs indistinguishable, hiding whether a template asked for the id or the ARN.
Fix: the resource naming rule for AWS::ApplicationSignals::InstrumentationConfig (src/state/template.rs) must compute the composite `<InstrumentationType>|<Service>|<Environment>|<SignalType>|<LocationHash>` physical id from the declaration plus the create's answered `LocationHash`, and the provisioner arm (src/state/provisioner/application_signals.rs::create_instrumentation_config) must stop substituting the ARN for the physical id while continuing to publish it as the `Arn` attribute; the delete path that reconstructs the identity from the stored resource must read the same composite.
Traces: check application-signals__cloudformation.deploy-application-signals-instrumentation-config-and-slo-round-trip-and-delete (AssertionError: InstrumentationConfig Ref 'arn:aws:application-signals:...:instrumentationConfig/.../.../SNAPSHOT/...' where `PROBE|<service>|<environment>|SNAPSHOT|<locationHash>` was expected).

Neither cause is covered by an existing open issue. The open issues about stack Outputs omitting OutputValue (20261117T134552Z-cloudformation-lexv2-models-..., 20261117T150412Z-cloudformation-ec2-neptune-..., 20261117T163512Z-cloudformation-ec2-neptune-..., 20261117T184012Z-appconfig-cloudformation-...) are the same SYMPTOM on other resource types' naming tables and do not give AWS::ApplicationSignals::GroupingConfiguration an identity; the open application-signals issues (20261113T135822Z-application-signals-responses-diverge-..., the CreateServiceLevelObjective ConflictException pair) are about that service's own API responses, not CloudFormation-published identities.

## Steps to Reproduce
Cause 1:
1. CreateStack with a template whose Resources declare one `AWS::ApplicationSignals::GroupingConfiguration` with a single GroupingAttributeDefinitions entry (GroupingName / GroupingSourceKeys ['aws.local.service'] / DefaultGroupingValue), and whose Outputs declare `GroupingRef: {"Value": {"Ref": "Grouping"}}` and `GroupingAccountId: {"Value": {"Fn::GetAtt": ["Grouping", "AccountId"]}}`.
2. Poll DescribeStacks(StackName=<returned StackId>) until CREATE_COMPLETE.
3. Read Stacks[0].Outputs: both entries carry OutputKey and no OutputValue. AWS returns the caller's account id as the OutputValue of each.
4. (The grouping definitions themselves do read back through application-signals ListGroupingAttributeDefinitions and are removed by the stack delete; only the published identity is missing.)

Cause 2:
1. CreateStack with a template declaring `AWS::ApplicationSignals::InstrumentationConfig` (InstrumentationType: PROBE, Service: <s>, Environment: <e>, SignalType: SNAPSHOT, Location.CodeLocation set, CaptureConfiguration.CodeCapture.CaptureLimits.MaxHits: 10) and Outputs for `{"Ref": "InstrumentationConfig"}`, `Fn::GetAtt Arn` and `Fn::GetAtt LocationHash`.
2. Poll DescribeStacks until CREATE_COMPLETE and read the Outputs.
3. Compare the Ref output with `"PROBE|" + <s> + "|" + <e> + "|SNAPSHOT|" + <LocationHash output>`: the emulator's Ref is the ARN instead, equal to the Arn output. Also compare DescribeStackResources' PhysicalResourceId for the logical id, which carries the same ARN.
