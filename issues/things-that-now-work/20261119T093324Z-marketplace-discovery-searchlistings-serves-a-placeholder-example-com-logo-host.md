# SearchListings serves a placeholder example.com logo host and a shared constant review sourceUrl on every listing summary

> _Note: this issue was identified against the code base at commit `beb502dc206615fd20b8344434a1e343c0b615d7`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
SearchListings

## Description
This issue bundles 4 causes, all in marketplace-discovery, all on SearchListings, all the SAME two defects in the ListingSummary projection the search pages return, observed in four separate replay clusters (a facet-refined search, the search that opens the drill-down flow, and both steps of a paginated search). Each cause is one replay cluster and each needs its own re-replay before this issue can be closed. In every one the emulator answers HTTP 200 with the right number of summaries and the right totalResults, but two URL members of each summary are machine-minted rather than read off a listing record: logoThumbnailUrl is built on a reserved placeholder host the emulator does not serve, and reviewSummary.reviewSourceSummaries[].sourceUrl is one hard-coded landing-page URL emitted for every listing in every response, including listings whose recorded summary carries no sourceUrl at all.

RELATED, NOT COVERING: open issue 20261109T122558Z-marketplace-discovery-searchlistings-listing-summaries-announce-an-unservable-placeholder-logo.md describes the same two defects, but the replay reports owned_by EMPTY for all four clusters below (its Issue-Key lines are written against a generalized $.listingSummaries[*] key and do not bind these clusters' replay keys), so none of these failures is gated by it and all four are filed here with their own bindings. Also NOT claimed here: $.nextToken, which appears in these clusters' diverging-key sets. The recorded token values ('<shaped-not-asserted>', 'opaque-continuation-token-placeholder-000', and the recording's long AWS blob) are per-run/per-environment continuation-token bytes, the emulator now serves an opaque token that satisfies NextToken's @pattern ^[a-zA-Z0-9+/=]+$ and @length(0..8192), and a token's literal bytes are not a requirement — so no nextToken claim is made in any cause.

=== Cause 1 of 4: a facet-refined SearchListings page returns ten summaries whose logoThumbnailUrl is on a placeholder host and whose review sourceUrl is one shared constant ===
AWS: Smithy (services/service-com-amazonaws-marketplacediscovery-awsmarketplacediscovery/smithy-model/com-amazonaws-marketplacediscovery-awsmarketplacediscovery.json) SearchListings POST /2026-02-05/searchListings, success 200, output listingSummaries ListingSummaryList @required of ListingSummary{logoThumbnailUrl -> URL @required @length(1..2048) @pattern ^https?://.*$, doc "The URL of the logo thumbnail image for the listing"; reviewSummary -> ReviewSummary @required of ReviewSourceSummary{sourceName @required, sourceId @required, averageRating @required, totalReviews @required, sourceUrl -> URL OPTIONAL @length(1..2048) @pattern ^https?://.*$, doc "The URL where the reviews can be accessed at the source"}}. The model constrains the shape and not the literal host, so for content this is recorded behavior only: logoThumbnailUrl is the address at which the service ACTUALLY serves that listing's logo image, one distinct path per listing derived from the listing's stored media record (the recording shows a per-listing path on the marketplace's own media CDN, not a path built from the listing's name); and sourceUrl, being OPTIONAL, is PRESENT only when the review source has a reviews page for that listing, and when present is the deep link to THAT listing's own reviews (the recording shows .../marketplace/reviews/reviews-list/<that listing's own review-source id>), never a shared landing page. Listings whose record has no reviews page omit the member entirely.
Emulator: 200 with the ten summaries, but every logoThumbnailUrl is of the form https://example.com/logos/<slug>.png — a URL on example.com, a reserved placeholder domain the emulator neither owns nor is reached on, so it announces an address other than its own data listener and nothing serves the image; and every reviewSummary.reviewSourceSummaries[0].sourceUrl is the single constant 'https://aws.amazon.com/marketplace/reviews', identical across all ten summaries and emitted even for the summaries whose recorded response has NO sourceUrl member (expected None, got that constant).
Why: a client rendering a result page fetches logoThumbnailUrl; against AWS it gets an image, against the emulator it addresses a host the emulator does not serve, so every result tile fails to load and the failure reads as a client or network fault rather than as emulator fidelity. sourceUrl is the control a client turns into a per-listing 'read the reviews' link, and its ABSENCE is what tells the client not to render that link: a constant present on every summary makes the link always appear and makes every listing point at the same page, so a client cannot tell a listing with reviews-at-source from one without, and deep-linking is impossible.
Fix: the SearchListings listing-summary projection and the catalog seeding behind it, in the marketplace-discovery crate's state module — the per-row logo URL must be an address the emulator itself serves for that listing (the crate already owns such a plane for SaaS fulfillment pages, state::saas_fulfillment) instead of a slug-built example.com path, and the review-source summary must carry sourceUrl only when the stored record has one, per listing, instead of a shared constant. The handler-side projection merely restates both members off the record, so the defect is in what is seeded/derived, not in the copy.
Traces: marketplace-discovery-search-facets-refine-search#task#3 (SearchListings, expected 200 / got 200; 20 diverging listing-summary keys — logoThumbnailUrl and reviewSummary.reviewSourceSummaries[0].sourceUrl on each of listingSummaries[0..9]). Code read for the component only: services/service-com-amazonaws-marketplacediscovery-awsmarketplacediscovery/src/state.rs:759 (listing_summary restates logo_thumbnail_url off the record), :762 (restates review_summary), :2311-2320 (reviews() hard-codes source_url), :3900 and :3916/:3954 (seed builds the logo as format!("https://example.com/logos/{slug}.png") and stores it on both listing and product), :2569/:2788/:2907/:3008/:3179/:3292 (the same literal host in the hand-seeded rows).
