# bedrock ListFoundationModels emits inferenceAPIsSupported as a flat string list and drops per-model converse limits

> _Note: this issue was identified against the code base at commit `0be2d8cde67a061e1bdd818ed7a4b8faca2d2bae`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
ListFoundationModels

## Description
The bedrock foundation-model catalog that ListFoundationModels serves diverges from AWS in the SHAPE of its per-model capability members and in the per-model converse metadata it carries. The status is correct (200) and the fault is entirely in the response body, so a client sees a well-formed-looking catalog whose capability fields cannot be interpreted the way the AWS wire form is.

Cause 1 of 1: ListFoundationModels serves modelSummaries entries whose capability members have the wrong type and whose converse block is incomplete.

AWS: Smithy bedrock#ListFoundationModels -> GET /foundation-models, http code 200, readonly; input is query-bound only (byProvider @pattern ^[A-Za-z0-9- ]{1,63}$, byCustomizationType, byOutputModality, byInferenceType); the single output member modelSummaries targets FoundationModelSummaryList. Smithy: FoundationModelSummary declares modelArn (required, @pattern ^arn:aws(-[^:]+)?:bedrock:[a-z0-9-]{1,20}::foundation-model/...$), modelId (required, BedrockModelId @length max 140), modelName and providerName (BrandedName @length 1..20), inputModalities / outputModalities (ModelModalityList), responseStreamingSupported (Boolean), customizationsSupported (ModelCustomizationList), inferenceTypesSupported (InferenceTypeList) and modelLifecycle (FoundationModelLifecycle). Modeled errors: ValidationException 400, AccessDeniedException 403, ThrottlingException 429, InternalServerException 500. The on-disk model declares NO inferenceAPIsSupported, converse, featuresSupported, batchSupported, explicitPromptCaching, intelligentPromptRouting, guardrailsSupported, latencyOptimizationSupported, modelFamily or description member on FoundationModelSummary, and it says nothing about which models the catalog contains, so for all of those: recorded behavior only. The recording shows AWS serving, per model, (a) inferenceAPIsSupported as a STRUCTURE with nested per-API members -- {"asyncInvoke": <bool>, "converse": {"streaming": <bool>, "sync": <bool>}, "invokeModel": {"bidirectionalStreaming": <bool>, "responseStreaming": <bool>, "sync": <bool>}, "openAiChatCompletions": <bool>, "openAiResponses": <bool>} -- not a list of API names; (b) a converse block carrying additionalRequestFieldsSchema (a JSON-encoded string, '{}' when the model takes no extra fields), maxTokensMaximum (integer), userDocumentTypesSupported and userImageTypesSupported (lists, which may legitimately be empty), and reasoningSupported present ONLY on models that expose reasoning; (c) batchSupported.baseModelSupported / .crossRegionSupported and featuresSupported.* flags whose values are per-model facts; and (d) inferenceTypesSupported entries drawn from the InferenceType enum, with INFERENCE_PROFILE (not ON_DEMAND) for models reachable only through an inference profile.

Emulator: the call answers 200 as expected, but modelSummaries diverges across most of the catalog. (1) TYPE: inferenceAPIsSupported is serialized as a flat list of API-name strings -- got ['converse', 'invokeModel', 'openAiChatCompletions', 'openAiResponses'] where AWS serves the nested structure above; the replay classifies this as type_mismatch, so it is a wire-shape defect and not a value difference, and it recurs on essentially every entry in the cluster's key list. (2) MISSING CONVERSE METADATA: converse.additionalRequestFieldsSchema, converse.maxTokensMaximum, converse.stopSequencesDefault, converse.maxTokensDefault, converse.userDocumentTypesSupported and converse.userImageTypesSupported are absent (got None) where AWS reports values -- for example on a reasoning-capable OpenAI entry AWS reports additionalRequestFieldsSchema '{"reasoning_config":{"type":"enum","default":"medium","enum":["low","medium","high","xhigh","max"]}}' and maxTokensMaximum 131072 and the emulator reports neither; conversely converse.reasoningSupported is EMITTED as {'isSupported': False, 'embedded': False} on an entry for which AWS emits no reasoningSupported member at all, so the member is both under- and over-populated. (3) WRONG CAPABILITY VALUES: inferenceTypesSupported[0] is ON_DEMAND where AWS reports INFERENCE_PROFILE; featuresSupported.promptOptimization is true where AWS reports false; batchSupported.baseModelSupported is false where AWS reports true. (4) The cluster's key list shows the same classes of divergence (converse.*, inferenceAPIsSupported, modelFamily, modelLifecycle.startOfLifeTime/endOfLifeTime/legacyTime/publicExtendedAccessTime/status, explicitPromptCaching, intelligentPromptRouting, featuresSupported.*) across the amazon.nova-*, amazon.titan-embed-*, anthropic.claude-*, cohere.* and deepseek.* families, plus whole-entry keys with no sub-path (cohere.command-text-v14, cohere.command-light-text-v14, cohere.embed-english-v3:0, cohere.embed-multilingual-v3:0 and their :7:4k / :0:512 variants) meaning the emulator and AWS do not agree on whether those model ids are listed at all.

Why: ListFoundationModels is the discovery call every Bedrock client makes before it invokes anything. A client that reads inferenceAPIsSupported as the modelled structure gets a type error or silently sees no API as supported, because a list of strings has no 'converse.sync' or 'invokeModel.responseStreaming' member to read; a client that sizes a request from converse.maxTokensMaximum or builds additional request fields from converse.additionalRequestFieldsSchema finds them null and either skips the feature or sends an unbounded request; a client that routes on inferenceTypesSupported picks direct ON_DEMAND invocation for a model AWS only serves through an inference profile and the subsequent invoke fails; and a client that enumerates the catalog to pick a model never sees, or wrongly sees, the cohere.* entries whose membership diverges.

Fix: the ListFoundationModels output serializer, for the members whose structured wire form is being flattened (inferenceAPIsSupported must be emitted as the nested per-API structure, not a name list) and for the converse block's optional-member handling (emit the members the catalog carries; do not emit reasoningSupported for models that have none); and the bedrock built-in foundation-model catalog seed -- the static table the ListFoundationModels handler serves -- for the per-model converse limits (additionalRequestFieldsSchema, maxTokensMaximum, maxTokensDefault, stopSequencesDefault, the user*TypesSupported lists), the capability flags (featuresSupported.promptOptimization, batchSupported.baseModelSupported, inferenceTypesSupported), the modelLifecycle timestamps and the membership of the cohere.* entries.
