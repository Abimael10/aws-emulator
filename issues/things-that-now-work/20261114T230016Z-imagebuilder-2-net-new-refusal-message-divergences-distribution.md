# imagebuilder: 2 net-new refusal-message divergences — distribution-configuration not-found wording, and CreateInfrastructureConfiguration's invalid-instance-profile wording

> _Note: this issue was identified against the code base at commit `fa1c1c9d2e17cac1aa32d43ac054c126cd511eb8`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
GetDistributionConfiguration

## Description
This bundle carries TWO distinct causes, both in the Image Builder emulator's refusal-message formatting. Both must be closed before this issue is submitted.

(Related but NOT covering — each carries its own replay keys and none carry the behavioral check ids listed below: open issues 20261105T162014Z-imagebuilder-image-builder-refusal-error-types-and-messages-are.md, 20261105T162014Z-imagebuilder-image-builder-distribution-configuration-validation-deletion-and-update.md, 20261106T010945Z-imagebuilder-2-net-new-distribution-configuration-refusal-divergences.md and 20261107T064925Z-imagebuilder-3-net-new-refusal-message-divergences-resourcealreadyexistsexception.md.)

Cause 1 of 2: a read or mutation of a distribution-configuration ARN that does not exist is refused with the emulator's generic "resource ARN ... was not found" message instead of AWS's resource-labelled not-found template.
AWS: recorded behavior only for the message (the Image Builder Smithy model does not bind ResourceNotFoundException to GetDistributionConfiguration/UpdateDistributionConfiguration — it models the shape com.amazonaws.imagebuilder#ResourceNotFoundException, client error, httpError 404, member `message`, doc "At least one of the resources referenced by your request does not exist."). The recorded refusal is error code ResourceNotFoundException with message "The following required resource 'DistributionConfiguration' cannot be found: '<distributionConfigurationArn>'." The fixed text is "The following required resource 'DistributionConfiguration' cannot be found: '" ... "'."; the only variable part is the distribution-configuration ARN taken from the request. The same recording shows the sibling resource label in use for image recipes ("The following required resource 'ImageRecipe' cannot be found: '<imageRecipeArn>'."), which the emulator already words correctly, and shows that the infrastructure-configuration path legitimately uses a different template ("The resource ARN '<arn>' was not found.") — so this is a per-resource template, not a service-wide one.
Emulator: same code ResourceNotFoundException, but the message is "The resource ARN '<distributionConfigurationArn>' was not found." — the infrastructure-configuration template applied to the distribution-configuration path. It diverges on both GetDistributionConfiguration (after the configuration was deleted) and, per the same check, on the subsequent UpdateDistributionConfiguration of the dead ARN.
Why: the error message is a requirement. A client (or an operator reading the log) that branches on, or parses, AWS's resource-labelled not-found text cannot tell WHICH referenced resource is missing — AWS names the resource type in the message, the emulator names only the ARN — so dependency-resolution and user-facing error reporting diverge even though the code and status agree.
Fix: the not-found refusal of the distribution-configuration read/update path in the imagebuilder service crate (the GetDistributionConfiguration and UpdateDistributionConfiguration handlers' lookup-miss branch and the shared not-found message formatter) must use the resource-labelled template with the 'DistributionConfiguration' label.
Traces: imagebuilder.create-distribution-configuration-get-roundtrip; ec2__iam__imagebuilder.ibp-delete-resources-referenced-by-a-pipeline-rejected (its 'dist' lookup after the delete; its 'infra' and 'recipe' lookups matched).

Cause 2 of 2: CreateInfrastructureConfiguration's unknown-instance-profile refusal re-words AWS's "Invalid parameter value for <member>: ..." message as "The value supplied for parameter '<member>' is not valid. ...".
AWS: recorded behavior only (Smithy: CreateInfrastructureConfiguration.instanceProfileName is required, target InstanceProfileNameType, length 1..256, pattern ^[\w+=,.@-]+$; the operation's modeled 400 errors are ClientException, IdempotentParameterMismatchException, InvalidRequestException, ResourceAlreadyExistsException and ResourceInUseException, and the model defines com.amazonaws.imagebuilder#InvalidParameterValueException, client, httpError 400, doc "The value that you provided for the specified parameter is invalid."). The recorded refusal is error code InvalidParameterValueException with message "Invalid parameter value for instanceProfileName: The provided instance profile does not exist. Please specify a different instance profile and try again." Fixed text: "Invalid parameter value for " + <member name> + ": The provided instance profile does not exist. Please specify a different instance profile and try again."; the only variable part is the member name (`instanceProfileName`) — the profile name the caller supplied does not appear in AWS's message.
Emulator: same error code and status, message "The value supplied for parameter 'instanceProfileName' is not valid. The provided instance profile does not exist. Please specify a different instance profile and try again." — the leading clause uses the emulator's own "The value supplied for parameter '<member>' is not valid." prefix instead of AWS's "Invalid parameter value for <member>:" prefix.
Why: the message is a requirement; a client, harness or operator matching AWS's fixed text on an otherwise correct refusal sees a mismatch, and emulator-authored prose is not portable back to real AWS.
Fix: the CreateInfrastructureConfiguration handler's instance-profile existence validation in the imagebuilder service crate (the message template it passes to the InvalidParameterValueException it raises).
Traces: imagebuilder.create-infrastructure-configuration-invalid-instance-profile-rejected (the rest of that check — the InvalidParameterValueException code, the effect-absent ListInfrastructureConfigurations probe and the positive control — behaved correctly).
