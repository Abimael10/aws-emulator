# rds__rds-data__secretsmanager: every cross-surface Data-API/native-SQL check is ungradeable — an Aurora cluster's published Endpoint is an unserved '.rds.localhost' host paired with the served Port

> _Note: this issue was identified against the code base at commit `28e13556b346bec2a9903044f83d66021b33e840`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
DescribeDBClusters

## Description
Cause 1 of 1: the connection endpoint an Aurora DB cluster publishes (CreateDBCluster / DescribeDBClusters -> DBCluster.Endpoint, together with DBCluster.Port) is a cluster-domain DNS name under the suffix '.rds.localhost' that the emulator neither resolves nor serves, while DBCluster.Port is the real, ephemeral port of the listener the emulator opened for that cluster's engine. The announced authority is therefore half real: the port answers, the host does not exist. Every check in this group that must open a NATIVE MySQL/PostgreSQL session on the same cluster it drives through the RDS Data API dies on the very first use of the published endpoint, before any cross-surface assertion is reached.

AWS: Smithy: rds DBCluster.Endpoint — "The connection endpoint for the primary instance of the DB cluster"; DBCluster.Port is the port that endpoint accepts connections on. On AWS the value is a resolvable DNS name of the form <DBClusterIdentifier>.cluster-<cluster hash>.<region>.rds.amazonaws.com — the fixed parts are the '.cluster-' infix and the regional 'rds.amazonaws.com' suffix, the variable parts are the identifier from the request and the hash/region from the service's state — and once DBCluster.Status is 'available' a client that dials Endpoint:Port gets an engine session. The structural requirement these checks depend on is only that the announced Endpoint:Port is an address the responding service actually answers on.

Emulator: the create and the describe both succeed (HTTP 200, no error code; the checks' earlier assertions on HttpEndpointEnabled and MasterUserSecret pass), and the cluster reports Endpoint '<identifier>.cluster-<hash>.<region>.rds.localhost' with Port set to the emulator's own listener port. The published-endpoint guard refuses the pair: "endpoint_host was given <host>:<port> (published by the emulator or built by the check): its host is not one of the emulator's own hosts; a customer of the emulator needs an own host[:port]: the endpoint host, a documented own host or, for a loopback endpoint, a loopback address". In that message the fixed text is the whole sentence; <host>:<port> is the value the emulator published (one run showed 'sim2real-behav-clus-93b2aea23500.cluster-3b6i7wfrdg22.us-west-2.rds.localhost:45357' — identifier, hash, region and port are per-run values and are NOT part of the requirement). There is no status or error-code divergence: the control-plane read is fine, the value it publishes is unusable.

Why: a client doing exactly the documented thing — read Endpoint and Port from an available cluster and connect — cannot reach the database at all. Nothing downstream of that connection exists: no native session, so no comparison of what the Data API wrote against what a native session reads, no transaction-visibility or row-lock semantics, no typed-value agreement, no post-failover/backtrack/snapshot-restore verification, and no check that native SQL still works while the HTTP endpoint is disabled. The emulator's RDS data plane is unaddressable from its own API answer.

Fix: the RDS DB-cluster endpoint publication path — the component that computes DBCluster.Endpoint / ReaderEndpoint / Port from the cluster record and the listener opened for it (services/service-com-amazonaws-rds-amazonrdsv19/src/ops/create_db_cluster.rs around the EngineEndpointPlan / open_engine_endpoint / served_endpoint assignment, and the DbClusterRecord -> DBCluster projection in services/service-com-amazonaws-rds-amazonrdsv19/src/state.rs that falls back to the minted DNS-form host). It must announce an authority the emulator answers on — an own host or loopback address for the cluster's listener — or make the cluster-domain name resolvable and served. Neighbouring open issues describe the same unserved-host value from other check groups but do not carry any of these 22 replay keys: 20261121T053640Z-logs-rds-an-available-aurora-postgresql-cluster-publishes.md, 20261121T064921Z-rds-s3-3-net-new-causes-an-aurora.md, 20261118T181500Z-rds-the-published-endpoint-of-a-served-engine-is-the-core-listeners.md and 20261120T153000Z-pi-rds-the-published-db-instance-endpoint-is-unreachable-from-the-replay-client.md.

Traces: all 22 failing checks listed in trace_ids, each failing at ctx.endpoint_host(cluster['Endpoint'], int(cluster['Port'])) with PublishedUrlRejected.

## Evidence
Expected: an 'available' Aurora DB cluster reports an Endpoint/Port pair a client of the emulator can resolve and connect to, so a native MySQL/PostgreSQL session can be opened on the same cluster the RDS Data API is driving.

Actual: 22/23 checks in this group fail identically at the first use of the published endpoint:
simparity.published.PublishedUrlRejected: endpoint_host was given <identifier>.cluster-<hash>.<region>.rds.localhost:<served port> (published by the emulator or built by the check): its host is not one of the emulator's own hosts; a customer of the emulator needs an own host[:port]: the endpoint host, a documented own host or, for a loopback endpoint, a loopback address

Observed values across runs (per-run, illustrative only): 'sim2real-behav-clus-93b2aea23500.cluster-3b6i7wfrdg22.us-west-2.rds.localhost:45357', 'sim2real-behav-xsurf-f764d57afbe3-c0.cluster-6r7nxbpj0sdt.us-west-2.rds.localhost:46765', 'sim2real-behav-httpep-43dc7a870d89-c.cluster-s0hj862owsi0.us-west-2.rds.localhost:40211'. The port is the emulator's own ephemeral listener port; only the HOST is unserved, so the emulator announces an address other than the one it is reached on. Earlier assertions in the same checks (HttpEndpointEnabled=True, the managed master secret holding the master username) already passed, so the endpoint host is the sole divergence reached.

## Steps to Reproduce
1. CreateSecret / let RDS manage the master password, then CreateDBCluster with Engine aurora-mysql or aurora-postgresql, EnableHttpEndpoint=true, and create its writer instance; wait until DescribeDBClusters reports Status 'available'.
2. Read DBCluster.Endpoint and DBCluster.Port from the create or describe response.
3. Resolve and dial that host:port from a client of the emulator (a native MySQL/PostgreSQL driver) — the '.rds.localhost' authority is not a host the emulator serves or resolves, while the port is the emulator's real listener port.
4. Replay any of the 22 checks listed in trace_ids; each aborts at ctx.endpoint_host(cluster['Endpoint'], int(cluster['Port'])) with simparity.published.PublishedUrlRejected before reaching its cross-surface assertion.
