Cause 1 of 1: the stage response cache is not observable end to end — the whole stale-until-flush trajectory produces no verdict. The check is killed with 'Error: Check timed out after 60.0s' having graded none of its cache assertions, although its own waits are far longer (backend stage serving v1: 150 s; cacheClusterStatus settling: 900 s; front stage priming GET: 180 s; post-flush GET: 180 s), so the entire budget was consumed inside one blocking poll. Hypothesis: the front API's non-proxy HTTP integration to the backend stage URL never answers 200 carrying the backend's body (the divergence the two non-proxy-HTTP issues above record for other checks), so the priming GET loop spins; the alternative stall is the backend MOCK stage itself never becoming servable. Either way the emulator serves no response a client can observe on this path, and FlushStageCache's effect on a primed cache is ungraded.

AWS: a stage cache is provisioned, primed, stale and flushable. Smithy (com.amazonaws.apigateway): Stage$cacheClusterEnabled — "Specifies whether a cache cluster is enabled for the stage. To activate a method-level cache, set CachingEnabled to true for a method"; Stage$cacheClusterSize; Stage$cacheClusterStatus -> CacheClusterStatus enum [CREATE_IN_PROGRESS, AVAILABLE, DELETE_IN_PROGRESS, NOT_AVAILABLE, FLUSH_IN_PROGRESS]; MethodSetting$cachingEnabled — "Specifies whether responses should be cached and returned for requests. Beyond the model, recorded behavior only: with cacheClusterStatus AVAILABLE and the method's cachingEnabled true with a long TTL, two identical GETs to the stage return the byte-identical cached body; after the BACKEND the stage integrates with is repointed and redeployed — and proven directly to serve the new body — the FRONT stage keeps serving the stale body; FlushStageCache (202) invalidates the entry so the very next GET reaches the integration again and returns the new body. The front API is never reconfigured after deployment, so caching is the only thing that can explain the stale answer.

Emulator: the trajectory produces nothing to grade. No priming body, no second identical body, no stale-after-backend-change body and no post-flush body is ever observed; the check is killed at the harness ceiling. The stage-cache state machine itself exists (services/service-com-amazonaws-apigateway-backplanecontrolservice/src/ops/flush_stage_cache.rs takes a cluster through FLUSH_IN_PROGRESS back to AVAILABLE over CACHE_CLUSTER_FLUSH_SPAN and calls stage.flush_response_cache()), so what is missing is the data-plane answer that would populate and then re-populate that cache: a deployed stage whose GET method has a type=HTTP (non-proxy) integration pointing at another deployed stage's invoke URL never returns 200 with the integration's body.

Why: a client that puts a stage cache in front of a backend cannot observe caching at all. The two behaviours it buys — a repeated request served from the cache without touching the backend, and FlushStageCache making the next request reach the backend again — are both unverifiable, and the simpler contract underneath (a non-proxy HTTP integration returning its backend's response through the stage) yields no usable response, so the request hangs or fails where AWS answers 200.

Fix: the execute-api data plane for a deployed stage — the non-proxy HTTP integration dispatcher and the response-cache lookup/store it wraps (services/service-com-amazonaws-apigateway-backplanecontrolservice/src/service/invoke.rs) — plus the stage/method-setting state that gates it (src/ops/create_stage.rs, src/ops/update_stage.rs for /{resource}/{method}/caching/enabled and /caching/ttlInSeconds). FlushStageCache's own handler already models the flush.

## Evidence
Expected (AWS): a BACKEND REST API with a GET MOCK method whose integration response template is {"version":"<v1>"} is deployed to stage 'b' and serves 200 {"version":"<v1>"} directly. A FRONT REST API with a GET type=HTTP (non-proxy) integration whose uri is that backend stage URL is deployed to stage 'test' with cacheClusterEnabled=true, cacheClusterSize='0.5', and UpdateStage patches /<resource>/GET/caching/enabled=true and /caching/ttlInSeconds=300; GetStage then reports cacheClusterStatus 'AVAILABLE' and methodSettings['<resource>/GET'].cachingEnabled true. The first GET to the front stage returns 200 with {"version":"<v1>"}; an immediate second GET returns the byte-identical body. After the backend's integration response is repointed to {"version":"<v2>"} and redeployed (and the backend itself is proven to serve <v2> directly), the front stage STILL returns {"version":"<v1>"}. FlushStageCache(restApiId=<front>, stageName='test') answers 202 and the next GET to the front stage returns {"version":"<v2>"}. The <v1>/<v2> markers are per-run values filling the template; the requirement is the stale-then-fresh sequence.

Actual (emulator): none of those bodies is ever observed. Replay verdict: mismatch, 'Error: Check timed out after 60.0s'. The check's bounded GET loops never see a 200 carrying the expected marker, so the cache-hit assertion, the stale-while-backend-changed assertion and the post-flush assertion are all unreached. The 60 s figure is the harness ceiling, not an AWS requirement — the divergence reported is a deployed stage that serves no observable response through a non-proxy HTTP integration, leaving the stage response cache and FlushStageCache's effect unverifiable.
