# ssm: 2 net-new behavioral causes — PutComplianceItems is unserved (NotImplemented) and UpdateMaintenanceWindowTarget's DoesNotExistException message is re-worded

> _Note: this issue was identified against the code base at commit `0129204ced37f63133d2cc688ac6df5b5ea216be`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
PutComplianceItems

## Description
Two independent net-new SSM fidelity defects found by replaying the behavioral suite (simparity-behavioral-aws-v1) against this checkout. This bundle carries 2 causes, numbered below; a fixer must close BOTH before submitting this issue. Smithy model used throughout: services/service-com-amazonaws-ssm-amazonssm/smithy-model/com-amazonaws-ssm-amazonssm.json.

Cause 1 of 2: PutComplianceItems is not served at all — every call is refused with error code 'NotImplemented', so neither its modeled refusals nor its write path exist.
- AWS: Smithy PutComplianceItems input ResourceId (required, @length 1..100), ResourceType (required, ComplianceResourceType, @length 1..50), ComplianceType (required, @pattern ^([A-Za-z0-9_\-]\w+|Custom:[a-zA-Z0-9_\-]\w+)$), ExecutionSummary (required), Items (required, 0..10000); modeled errors InvalidResourceType, InvalidResourceId, InvalidItemContentException, ItemSizeLimitExceededException, TotalSizeLimitExceededException, ComplianceTypeCountLimitExceededException (all client, httpError 400) and InternalServerError. A ResourceType other than the supported one is refused HTTP 400 with code InvalidResourceType; the message's fixed text for this error class is "Resource type <ResourceType> is not supported, example resource type are [ManagedInstance]" — the fixed sentence frame plus the rejected ResourceType taken verbatim from the request, and the bracketed list of supported types from the service. A well-formed call with ResourceType=ManagedInstance against a registered managed node succeeds (HTTP 200, empty body) and the item becomes visible through ListComplianceItems; with the ssm:PutComplianceItems grant removed the identical call is refused AccessDeniedException.
- Emulator: the operation answers error code 'NotImplemented' (the handler is an unimplemented scaffold stub), so a client never sees InvalidResourceType for a bad ResourceType, never gets a successful write, and a poll that waits for the call to succeed under a granted identity policy never terminates.
- Why: a client cannot distinguish "this resource type is unsupported" or "you are not authorized" from "this emulator does not implement compliance reporting". NotImplemented is not a modeled error of the operation, so SDK error handling falls through to a generic non-retryable server failure; patch/compliance reporters that write items and then read them back through ListComplianceItems are permanently stuck, and negative tests asserting the InvalidResourceType contract cannot run.
- Fix: implement the PutComplianceItems handler in the ssm service crate (services/service-com-amazonaws-ssm-amazonssm/src/ops/put_compliance_items.rs) over the compliance-item store that backs ListComplianceItems, including the ResourceType validation path (400 InvalidResourceType with AWS's sentence) and the IAM authorization refusal path.
- Related open issue: 20261114T143448Z-ssm-putcomplianceitems-stub.md names the same operation and handler file, but the replay report carried NEITHER of the two checks below on it (they were marked neither 'ALREADY FILED' nor 'OWNED by'), so their replay keys are recorded here.
- Hypothesis for the second check: ssm.put-compliance-items-limit-exceeded-rejected does not assert on the stub directly — it polls until the same restricted-identity PutComplianceItems call succeeds and exhausts the run budget. The sibling check shows that call answering NotImplemented, which is why the poll can never observe the success; if the handler is implemented and the poll still never converges, the IAM grant-propagation path for ssm:PutComplianceItems is the remaining suspect.
- Traces: ssm.compliance-items-invalid-resource-type-rejected, ssm.put-compliance-items-limit-exceeded-rejected.

Cause 2 of 2: UpdateMaintenanceWindowTarget against a deregistered WindowTargetId returns the right error code with an emulator-authored message instead of AWS's not-found sentence.
- AWS: Smithy UpdateMaintenanceWindowTarget input WindowId (required, @length 20..20, @pattern ^mw-[0-9a-f]{17}$) and WindowTargetId (required, @length 36..36, uuid @pattern); modeled errors DoesNotExistException (client, httpError 400) and InternalServerError. Recorded behavior for a target that was deregistered from a still-live window: HTTP 400, code DoesNotExistException, message "Maintenance window target <WindowTargetId> does not exist" — the fixed text is "Maintenance window target " … " does not exist" and the only variable part is the WindowTargetId taken from the request. The message names the TARGET only; it does not name the window.
- Emulator: same code (DoesNotExistException) but the message is "Maintenance window <WindowId> has no target <WindowTargetId>" — a different sentence that additionally interpolates the WindowId from the request.
- Why: the error message is the only human- and machine-readable description of which entity is missing. Tooling that matches AWS's sentence (reconcilers that distinguish a dead target from a dead window, and negative tests asserting the refusal text) mis-handles the refusal even though the status and code are right; the emulator's wording also blurs the target-not-found and window-not-found conditions, which AWS words differently.
- Fix: the UpdateMaintenanceWindowTarget handler's target-resolution refusal path (services/service-com-amazonaws-ssm-amazonssm/src/ops/update_maintenance_window_target.rs) — render AWS's fixed target-not-found sentence with the request's WindowTargetId substituted.
- Related open issue: 20261115T084659Z-ssm-10-net-new-behavioral-causes-maintenance-window.md Cause 2 covers DeregisterTargetFromMaintenanceWindow being non-idempotent (it quotes the same emulator wording as a symptom) but does not carry UpdateMaintenanceWindowTarget's message, and this check is not on its Issue-Trace-Ids.
- Traces: ssm.maintenance-window-target-rejects-unknown-id-after-deregister.
