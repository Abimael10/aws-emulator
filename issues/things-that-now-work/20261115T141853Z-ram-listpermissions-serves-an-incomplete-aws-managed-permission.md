# ram ListPermissions serves an incomplete AWS-managed permission catalog

> _Note: this issue was identified against the code base at commit `7b0cd7b14eb321355db06251cc80d3f9fa1c4d53`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
ListPermissions

## Description
ListPermissions is backed by a managed-permission catalog that holds only a small fraction of RAM's AWS_MANAGED permissions, and the few entries it does hold are missing a field and carry a diverging version. Two net-new causes, both on ListPermissions, both rooted in that catalog.

Cause 1 of 2: ListPermissions returns a truncated AWS_MANAGED catalog, and the entries it does return are incomplete (fixture ram-catalog-list-permissions, step task#1).
AWS: Smithy: ListPermissions -> ListPermissionsResponse.permissions : ResourceSharePermissionList of ResourceSharePermissionSummary (arn, name, version, defaultVersion, isResourceTypeDefault, permissionType, resourceType, status, creationTime, lastUpdatedTime, featureSet, tags); input filters resourceType / permissionType (PermissionTypeFilter = ALL | AWS_MANAGED | CUSTOMER_MANAGED), maxResults @range 1..500, paginated via nextToken. AWS publishes one AWS_MANAGED managed permission per shareable resource type (plus the named variants), so an unfiltered ListPermissions in any account enumerates that whole published catalog: every AWSRAMDefaultPermission*/AWSRAMPermission*/AWSRAMLFEnabled* entry, each with permissionType=AWS_MANAGED, status=ATTACHABLE, defaultVersion=true and the resourceType it governs. Recorded behavior only for the member `restrictToServiceLinkedShares`: it is NOT a modeled member of ResourceSharePermissionSummary, but the recording shows AWS emits it on every catalog entry as a boolean (false for these AWS-managed permissions), so a wire-faithful response must carry it.
Emulator: answers 200 with a permissions list that omits well over a hundred of the catalog's ARNs outright — e.g. arn:aws:ram::aws:permission/AWSRAMBlankEndEntityCertificateAPIPassthroughIssuanceCertificateAuthority (acm-pca:CertificateAuthority), AWSRAMDefaultPermissionAPIGatewayDeveloperPortalProduct (apigateway:Portalproducts), AWSRAMDefaultPermissionCoipPool, AWSRAMDefaultPermissionImageBuilderComponent, AWSRAMDefaultPermissionOutpost, the whole AWSRAMDefaultPermissionNetworkFirewall*/ODB*/SageMaker*/SMSVoice*/Glue*/LFTag* families — each reported `missing (expected {...}, got None)`. For the entries it DOES serve (AWSRAMDefaultPermissionAppMesh, ...CapacityReservation, ...CodeBuildProject, ...CodeBuildReportGroup, ...DedicatedHost, ...GlueDatabase, ...GlueTable, ...ImageBuilderImage, ...LicenseConfiguration, ...PrefixList, ...ResolverRule, ...ResourceGroup, ...Subnet, ...TransitGateway, APIGatewayPrivateDomainNameManagementPolicyDefaultPermission, AWSRAMPermissionGlueDatabaseReadWrite) it emits no `restrictToServiceLinkedShares` at all (expected False, got None), and for AWSRAMDefaultPermissionAppMesh / AWSRAMDefaultPermissionCapacityReservation / AWSRAMDefaultPermissionTransitGateway / AWSRAMPermissionGlueDatabaseReadWrite the `version` it reports differs from the catalog's.
Why: a client that discovers a managed permission before using it — the console's share wizard, Terraform's aws_ram_permission lookups, any CreateResourceShare/AssociateResourceSharePermission flow that first resolves the default permission ARN for a resource type — concludes that resource type cannot be shared at all, because its permission is absent from the only enumeration API. A client that reads restrictToServiceLinkedShares gets None where AWS always sends a boolean, so a strict deserializer faults and a lenient one mis-renders service-linked-share scoping. A diverging version makes a pinned permission version unresolvable.
Fix: the ram service's AWS-managed permission catalog (the seeded managed-permission state the service is built with) is the wrong component to be hand-authoring a handful of entries from — it must carry RAM's full published AWS_MANAGED catalog, each entry with restrictToServiceLinkedShares and the published version; the ListPermissions handler then projects it.

Cause 2 of 2: ListPermissions filtered by resourceType returns an empty list for a resource type whose AWS-managed default permission exists (fixture ram-resource-share-permission-association, step setup#2).
AWS: Smithy: ListPermissions input member `resourceType` (String, documented as service-code:resource-code, case-insensitive, e.g. ec2:subnet) filters the catalog to the permissions governing that resource type; errors InvalidParameterException / InvalidNextTokenException / OperationNotPermittedException. A ListPermissions scoped to imagebuilder:Component therefore returns at least AWSRAMDefaultPermissionImageBuilderComponent, with permissionType=AWS_MANAGED, resourceType=imagebuilder:Component, isResourceTypeDefault=true, defaultVersion=true, status=ATTACHABLE and version as published.
Emulator: answers 200 with an empty permissions list — $.permissions[0]: missing (expected the AWSRAMDefaultPermissionImageBuilderComponent summary, got None) — so the resource-type-scoped read finds nothing to attach and the whole share/permission-association scenario is built on a permission the service claims not to exist.
Why: the documented way to find the permission ARN to pass to CreateResourceShare(permissionArns=...) or AssociateResourceSharePermission is a resourceType-scoped ListPermissions. Getting an empty page back makes every resource type outside the emulator's short seed list unshareable, and clients that treat the empty page as authoritative report 'no permission available for imagebuilder:Component' rather than failing loudly.
Why this is not already covered: the open issues 20261113T145122Z-ram-listresourcesharepermissions-omits-a-managed-permission-attached-to.md and 20261110T181341Z-ram-listresourcesharepermissions-never-reports-a-share-attachment-status.md are about ListResourceSharePermissions (the share-scoped read and its ASSOCIATED status) and neither covers the account-wide ListPermissions catalog or its resourceType filter.
Fix: same component as cause 1 — the seeded managed-permission catalog — plus the ListPermissions handler's resourceType filter, which must match case-insensitively against the catalog's full resourceType set rather than only the seeded subset.
