# greengrassv2 legacy Greengrass routes diverge: service-role 404 error code, UpdateConnectivityInfo refusal envelope/wording, and GetConnectivityInfo returns an empty success instead of 404 (3 net-new causes)

> _Note: this issue was identified against the code base at commit `051d1ca879f4768e0cde48b6e9d78ea8677353f9`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
GetServiceRoleForAccount

## Description
Three net-new root causes on the LEGACY Greengrass routes this service co-hosts (`/greengrass/servicerole` and `/greengrass/things/{thingName}/connectivityInfo`). All three are in greengrassv2 and none is covered by an existing open issue: the nearest open issues are 20261103T065241Z-greengrassv2-refusal-responses-diverge-from-aws-10-net.md (component/deployment/ARN refusal wording), 20261103T145648Z-greengrass-greengrassv2-wire-refusal-paths-diverge-wrong-status-error.md and 20261109T003358Z-greengrassv2-associateserviceroletoaccount-accepts-a-non-arn-rolearn-with.md (the AssociateServiceRoleToAccount 400, which now fires correctly); the suite marked none of the checks below as owned by them.

Cause 1 of 3: GetServiceRoleForAccount names its "no role associated" 404 with the error code `NotFoundException`, a code AWS never returns on this route.
  AWS: Smithy (com.amazonaws.greengrassv2#GetServiceRoleForAccount) declares GET /greengrass/servicerole, 200, and only InternalServerException (HTTP 500) — no not-found shape at all. Recorded behavior only: an account with no service role associated is answered at HTTP 404 with the fixed sentence "You need to attach an IAM role to this AWS account." in a capitalized `Message` body member, and the response does NOT name a modeled error type, so a botocore client surfaces Error.Code as the HTTP status string `404` (the suite's checks accept exactly `404` or `ResourceNotFoundException` as the not-found code for this call). The sentence is entirely fixed text — the operation takes no input, so it quotes no request value.
  Emulator: HTTP 404 with the right message, but the response names the error type `NotFoundException` (via x-amzn-errortype/__type), so botocore reports `An error occurred (NotFoundException) when calling the GetServiceRoleForAccount operation: You need to attach an IAM role to this AWS account.` — the code is neither `404` nor `ResourceNotFoundException`.
  Why: every client that branches on "is a service role attached?" compares the error code. With an invented code, that probe raises an unrecognized ClientError instead of reading as absence, so the whole associate/get/disassociate lifecycle is unusable against the emulator even though the state machine itself works — all three service-role checks abort on their FIRST GetServiceRoleForAccount call, before exercising anything else.
  Fix: the legacy not-found refusal's wire code for this service — the not-found arm of the legacy refusal class shared by the `/greengrass/servicerole` route (its code constant and the `shape_name`/error-type it renders), not the handler's state logic, which is already correct.
  Traces: greengrassv2.associate-service-role-untrusted-role-is-accepted, greengrassv2.disassociate-service-role-idempotent-when-none-associated, greengrassv2.service-role-association-lifecycle. Code under src/state/legacy_refusals.rs (LEGACY_NOT_FOUND_CODE, aliased to the tagging not-found code) as rendered for src/ops/get_service_role_for_account.rs.

Cause 2 of 3: UpdateConnectivityInfo refuses a malformed connectivityInfo entry with the wrong error code AND the wrong message.
  AWS: Smithy (com.amazonaws.greengrassv2#UpdateConnectivityInfo) binds PUT /greengrass/things/{thingName}/connectivityInfo with required `connectivityInfo` and models ValidationException (HTTP 400) / InternalServerException (500) — no BadRequestException. Recorded behavior only: an entry missing the required hostAddress is refused at HTTP 400 whose body names no error type (botocore Error.Code = the status string `400`) with the fixed message "Invalid json format found in the request body." That sentence is entirely fixed text: it names no member, value or limit from the request.
  Emulator: refuses at 400 but names the error type `BadRequestException` (botocore Error.Code = "BadRequestException"), and words the body "The following required parameter(s) are unparsable: connectivityInfoList." — a sentence AWS does not use for this class on this route (its one variable part, the member name, is not part of AWS's template at all).
  Why: a client that classifies the refusal by code sees an unknown code, and one that matches or logs the message sees text no AWS client or runbook expects; retry/validation logic keyed to the documented wording does not fire. The refusal itself is otherwise correct (nothing is overwritten).
  Fix: the legacy bad-request refusal rendering for this operation — its wire code (name no error type so the status is the code) and its message text, in the UpdateConnectivityInfo validation path / the legacy refusal class it uses.
  Traces: greengrassv2.connectivity-info-round-trip-and-malformed-entry-rejected (assert code == "400" failed with "BadRequestException" before the message assert was reached). Code: src/ops/update_connectivity_info.rs refusal arm plus UNPARSABLE_CONNECTIVITY_INFO_MESSAGE / LEGACY_BAD_REQUEST_CODE in src/state/legacy_refusals.rs.

Cause 3 of 3: GetConnectivityInfo answers 200 with an empty connectivityInfo list for a thing that has published nothing, instead of refusing with a 404 about the missing connectivity info.
  AWS: Smithy declares GET /greengrass/things/{thingName}/connectivityInfo, 200, with InternalServerException (500) and ValidationException (400) — no not-found shape, so this is recorded behavior only: a core-device thing with no published connectivity information is answered at HTTP 404 (botocore Error.Code = `404`) whose message references the missing connectivity info; the thing name is the variable part of that sentence, the rest is fixed text. A thing that HAS published info returns 200 with its entries (the check's positive control proves the emulator gets that part right).
  Emulator: returns HTTP 200 with `connectivityInfo: []` for an unpublished thing — the handler reads the store and substitutes an empty list for a missing record (`.unwrap_or_default()`).
  Why: a client cannot distinguish "this core device has published no connectivity information" from "this core device publishes an empty endpoint set"; discovery and provisioning code that expects the 404 to branch (create/publish, then read) instead proceeds with an empty endpoint list and silently connects nowhere.
  Fix: the GetConnectivityInfo handler's absent-record path — refuse in the same legacy 404 envelope used by the service-role route (with the 404 code from Cause 1) rather than defaulting to an empty list.
  Traces: greengrassv2.get-connectivity-info-empty-for-new-thing ("expected GetConnectivityInfo to raise for a thing with no connectivity info"). Code: src/ops/get_connectivity_info.rs, the `unwrap_or_default()` on the stored record.

## Evidence
Cause 1 — expected: HTTP 404, Error.Code `404` (status fallback; `ResourceNotFoundException` also accepted by the checks), Message "You need to attach an IAM role to this AWS account."; actual: HTTP 404, Error.Code `NotFoundException`, same message. Replay: `botocore.exceptions.ClientError: An error occurred (NotFoundException) when calling the GetServiceRoleForAccount operation: You need to attach an IAM role to this AWS account.` raised out of the checks' _get_role_or_none helper, which only tolerates codes ("ResourceNotFoundException", "404").

Cause 2 — expected: HTTP 400, Error.Code `400`, Message "Invalid json format found in the request body." for UpdateConnectivityInfo(thingName=<thing>, connectivityInfo=[{"id":"1","portNumber":1883}]) (hostAddress omitted); actual: HTTP 400 with Error.Code `BadRequestException` and Message "The following required parameter(s) are unparsable: connectivityInfoList." Replay: `assert code == "400", code` -> `AssertionError: BadRequestException`.

Cause 3 — expected: GetConnectivityInfo(thingName=<thing with nothing published>) raises with Error.Code `404` and a message referencing the missing connectivity info; actual: HTTP 200 with `{"connectivityInfo": []}`. Replay: `AssertionError: expected GetConnectivityInfo to raise for a thing with no connectivity info`. The same check's positive control (a sibling thing with info published) returned its single entry, so only the absent case diverges.
