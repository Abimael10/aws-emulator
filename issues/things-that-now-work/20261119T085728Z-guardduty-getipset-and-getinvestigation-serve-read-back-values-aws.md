# GetIPSet and GetInvestigation serve read-back values AWS never emitted for these steps

> _Note: this issue was identified against the code base at commit `e7e3130cf0de41955ad6ab1cedf8900a344f8afc`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
GetIPSet

## Description
This issue carries 2 net-new root causes in the guardduty service, both found by replaying the simparity-wire-aws-v1 wire corpus against the booted emulator. Both are READ-BACK PAYLOAD causes: the operation answers the right status with the right members present, but one member carries a value the emulator synthesised or passed through unchanged where the recorded AWS answer carries a value of a different shape. They are bundled because they share a service and a fault family (the value one read-back serialises for a free-form member), NOT because they share a handler: each has its own fixture, its own step and its own fix site, and BOTH must be closed before this issue is submitted.

=== Cause 1 of 2: GetIPSet announces an uploaded-list Location on a host this emulator does not serve (fixture guardduty-ipset-tags-unicode-value-round-trip, step task#3) ===

AWS: Smithy (services/service-com-amazonaws-guardduty-guarddutyapiservice/smithy-model/com-amazonaws-guardduty-guarddutyapiservice.json) models GetIPSet -> GET /detector/{DetectorId}/ipset/{IpSetId}, success code 200, output member Location (jsonName `location`, required, target Location, @length 1..300, no @pattern), documented as "The URI of the file that contains the IPSet"; modeled errors are BadRequestException 400 and InternalServerErrorException 500 only. CreateIPSet carries the identical member. The model states no normalization rule, so the LITERAL bytes of the member are not a wire requirement and the corpus does not assert them: the recorded value is environment-specific and the expectation for `$.location` is `<shaped-not-asserted>`. What the corpus DOES assert about it is the shape every URL in a served payload must satisfy — the authority it names must be an address this emulator is reached on, because a location the emulator advertises is the address a client then resolves to fetch the list.

Emulator: GetIPSet serialises the stored string unchanged — services/service-com-amazonaws-guardduty-guarddutyapiservice/src/ops/get_ip_set.rs line 184 calls crate::state::announced_list_location(&ip_set.location), and that helper (src/state/announced_list_location.rs lines 29-31) is now the identity function. The fixture's CreateIPSet supplied a path-style URL on the real AWS S3 service, so the read-back answers HTTP 200 with a `location` whose authority is `s3.amazonaws.com` — a third-party, real-AWS host the emulator neither is reached on nor serves. Replay verdict: mismatch, `$.location: host_not_own`. The bucket and key in the recorded value are this corpus's per-run names and are not the requirement; the requirement is that the announced authority be one the emulator answers on.

Why: `location` is not decoration, it is the address a client dereferences. A client that reads an IPSet back and fetches the list it names leaves the emulator entirely: it either egresses to real AWS S3 (and gets someone else's 404/403, or a credential error) or fails name resolution, with no way to retrieve the object the emulator was told about. Anything that mirrors or validates the configured list (a console view, a drift check, a sync job) therefore reports the emulated resource as unfetchable, and the emulator has announced an address it cannot stand behind.

Fix: the `location` projection the uploaded-list read-backs share — src/state/announced_list_location.rs, consumed by get_ip_set.rs and its ThreatIntelSet / entity-set siblings. NOTE THE CONFLICT and reconcile it rather than flipping the helper back and forth: open issue 20261118T195055Z-guardduty-getipset-getthreatintelset-rewrite-the-stored-location-into-an.md (HIGH, behavioral) is why the helper is the identity today, and resolved issue 20261110T102233Z-guardduty-read-backs-serve-content-the-emulator-cannot.md is why it used to rewrite every value to the emulator's authority. Neither extreme satisfies both corpora, and they do not actually overlap: every behavioral check that demands a byte-exact round-trip stores an `s3://<bucket>/<key>` URI, which names NO host at all and so can never point outside the emulator, while this wire step stores a URL whose authority is an AWS-owned S3 host. A helper that leaves a host-less `s3://` URI exactly as stored and re-announces only an authority the emulator does not serve (mapping the bucket/key onto the authority the request arrived on) satisfies both, and must keep the STORED value untouched so create/update validation (crate::state::is_s3_location) and update-time comparison still see the caller's own string.

Traces: guardduty-ipset-tags-unicode-value-round-trip#task#3 (GetIPSet, expected 200 / got 200, `$.location` host_not_own). Cluster size 1.

=== Cause 2 of 2: GetInvestigation serves a locally templated investigation summary instead of the analysis report AWS returns (fixture guardduty-tagging-created-with-tags, step setup#4) ===

AWS: Smithy models GetInvestigation -> GET /detector/{DetectorId}/investigation/{InvestigationId}, success code 200, output Investigation (required), whose `Summary` member (jsonName `summary`) targets plain `String` with NO @length and NO @pattern, documented as "A structured summary of the investigation findings, including affected resources, threat assessment, and recommended remediation steps". Because the model constrains nothing about the text, this is recorded behavior only: the recording's own summary text is environment-specific, so the corpus asserts its SHAPE rather than its bytes (`$.investigation.summary` expected `<shaped-not-asserted>`), and the emulator's value fails that shape class — replay verdict mismatch, `$.investigation.summary: value_mismatch`, with both sides answering HTTP 200 and every other member of the investigation agreeing. The asserted content is the summary GuardDuty's AI Analyst produced for the investigation; it is generated text the service serves, not an account-specific identifier or a per-run clock value.

Emulator: the summary is not read off any investigation result at all — it is a fixed local template. src/state/investigation_analysis.rs `summary_text` (lines 372-391) formats four hard-coded markdown sections ("## Investigation summary", "## Affected resources", "## Threat assessment", "## Recommended remediation"), filling counts from whatever findings the detector happens to hold, and src/state/investigations.rs `InvestigationRecord::settle` (lines 225-253) computes it once, 500ms after the create, from `evidence_for_prompt`. In these fixtures the detector holds no findings, so every slot collapses to its degenerate branch and the served summary is the canned text: "## Investigation summary\nGuardDuty analysed 0 findings in account <emulator account> (<region>) and assessed the activity as Info risk.\n\n## Affected resources\nNone: the pass analysed no findings, so no resource was implicated.\n\n## Threat assessment\nNo GuardDuty findings had been produced for this account and Region when the pass ran, so there was no threat activity to assess and the risk is Info.\n\n## Recommended remediation\n1. Keep GuardDuty enabled so later activity is analysed." (the account id and region in that text are this environment's values and are not themselves the finding; the template around them is). Nothing in it is derived from the investigation's own trigger prompt beyond finding-id selection, so the generated report neither echoes what the caller asked to be investigated nor reflects the recorded summary's shape. Hypothesis (stated by neither the model nor the recording): the recorded summary is a machine-consumable structured document, where the emulator serves free prose under markdown headings, which is why the shape class rejects it.

Why: `Summary` is the entire product of an investigation — it is what a console renders and what an automation parses to decide whether to escalate. A client built against AWS gets a differently shaped document, so a parser keyed on the real structure finds nothing, and a human reader is handed a report that asserts "0 findings ... no resource was implicated ... Info risk" about an investigation AWS summarised differently. Because the text is fixed, every investigation in the emulator with an empty detector reads identically, so the member carries no information about the investigation at all.

Fix: the investigation analysis projection in the guardduty crate's state — src/state/investigation_analysis.rs (`summary_text` and the section helpers it calls) and the point that stores it, src/state/investigations.rs `InvestigationRecord::settle`; the read handler src/ops/get_investigation.rs line 223 only copies `analysis.summary` and needs no change beyond whatever the stored shape becomes.

Traces: guardduty-tagging-created-with-tags#setup#4 (representative) and guardduty-tagging-round-trip#setup#4 — GetInvestigation, expected 200 / got 200, `$.investigation.summary` value_mismatch. Cluster size 2.
