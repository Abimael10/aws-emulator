# sesv2: 7 net-new refusal-fidelity causes — SendEmail resolves a template name ahead of the sender-identity gate, and six refusals carry the wrong error type or an emulator-authored message

> _Note: this issue was identified against the code base at commit `03a0508b3aa0858110fb1a346ba54180a1d13415`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
SendEmail

## Description
Seven net-new root causes in the SESv2 refusal surface: one validation-ordering defect on the send path and six refusals whose error type or message text is not AWS's. This issue bundles 7 causes; all seven must be closed before submitting.

Cause 1 of 7 — SendEmail resolves Content.Template.TemplateName BEFORE the sender-identity gate.
AWS: Smithy SendEmail errors include MessageRejected(400) and NotFoundException(404). With an unverified FromEmailAddress, the identity gate fires first and MASKS template-name resolution: a request naming a template that exists and a request naming a template that does not exist return the SAME refusal, 400 MessageRejected with `Email address is not verified. The following identities failed the check in region <REGION>: <ADDRESS>` (fixed text, variable parts: the region in upper case and the FromEmailAddress from the request). Template-DATA validation, by contrast, runs AHEAD of the identity gate and agrees with TestRenderEmailTemplate: malformed TemplateData yields that operation's own BadRequestException code, distinct from MessageRejected. Emulator: the request naming a missing template answers NotFoundException while the identical request against the existing template answers MessageRejected — the template store is consulted before the identity check. Why: a caller whose sender is not verified can enumerate which template names exist in the account (an information leak AWS deliberately closes), and a caller distinguishing "fix my template name" from "verify my sender" is sent down the wrong branch. Fix: the SendEmail handler's refusal ordering — template-DATA validation, then the FromEmailAddress identity gate, then template-NAME resolution. Related open issue 20261114T220956Z-sesv2-sendemail-with-content-template-answers-501-notimplemented.md recorded the earlier 501 on this path and does not cover the ordering. Traces: sesv2.send-email-template-resolution-precedes-the-sender-verification-gate.

Cause 2 of 7 — TestRenderEmailTemplate's malformed-JSON refusal is re-worded.
AWS: Smithy TestRenderEmailTemplate input {TemplateName (required), TemplateData (required, @length 0..262144)}, errors BadRequestException(400)/NotFoundException(404)/TooManyRequestsException(429). TemplateData that is not syntactically valid JSON is refused 400 BadRequestException with `Template rendering data is invalid` — fixed text, no variable parts, no trailing period — distinct from the refusal for JSON that is well formed but omits a referenced attribute, which is `Attribute '<NAME>' is not present in the rendering data.` (variable part: the placeholder name from the template). Emulator: the malformed-JSON case answers 400 BadRequestException `The template data is not a valid JSON object`, an emulator-authored sentence. Why: a client that branches on the message (or logs/matches it) cannot recognise the malformed-data refusal, and the two render refusals stop being distinguishable in the way AWS words them. Fix: the TestRenderEmailTemplate handler's template-data validation message. Traces: sesv2.test-render-email-template-malformed-json-and-missing-attribute-refusals.

Cause 3 of 7 — PutAccountSuppressionAttributes' invalid-enum refusal uses the wrong constraint-violation form.
AWS: Smithy PutAccountSuppressionAttributes input {SuppressedReasons (list of SuppressionListReason), ValidationAttributes}, error BadRequestException(400); SuppressionListReason is an enum with values [BOUNCE, COMPLAINT]. An unknown member value is refused 400 BadRequestException with `1 validation error detected: Value at 'suppressedReasons' failed to satisfy constraint: Member must satisfy constraint: [Member must satisfy enum value set: [BOUNCE, COMPLAINT]]` — the variable parts are the input member path `suppressedReasons` and the enum value set from the model; AWS names the LIST member only, with the nested `Member must satisfy constraint: [...]` wrapper, and does NOT include the offending element's index. The refusal also leaves GetAccount's SuppressionAttributes.SuppressedReasons at its prior value. Emulator: `1 validation error detected: Value at 'suppressedReasons.2.member' failed to satisfy constraint: Member must satisfy enum value set: [BOUNCE, COMPLAINT]` — it appends the element index and `.member` to the path and drops the nested wrapper. Why: a client parsing the member path out of the validation message (a common pattern for mapping a violation back to a request field) reads a path AWS never emits. Fix: the shared constraint-violation message formatter for list-of-enum members as used by the PutAccountSuppressionAttributes handler's validation. Traces: sesv2.account-suppression-attributes-invalid-reason-rejected.

Cause 4 of 7 — PutConfigurationSetSuppressionOptions' invalid-reason refusal is the generic constraint sentence instead of its own message.
AWS: Smithy PutConfigurationSetSuppressionOptions input {ConfigurationSetName (httpLabel, required), SuppressionScope, SuppressedReasons (list of SuppressionListReason), ValidationOptions}, errors BadRequestException(400)/NotFoundException(404). Although the member targets the SAME enum as Cause 3, this operation words the refusal differently: 400 BadRequestException `Reason <VALUE> is invalid, must be one of [BOUNCE, COMPLAINT].` — fixed text `Reason ` + the rejected value taken verbatim from the request + ` is invalid, must be one of [BOUNCE, COMPLAINT].`, with a trailing period and no element index. Emulator: the generic serializer-level sentence `1 validation error detected: Value at 'suppressedReasons.1.member' failed to satisfy constraint: Member must satisfy enum value set: [BOUNCE, COMPLAINT]`. Why: one generic validator is applied to two operations AWS words differently, so a client matching either operation's text fails on the other. Fix: an operation-specific invalid-reason refusal in the PutConfigurationSetSuppressionOptions handler, ahead of the generic enum validator. Traces: sesv2.sesv2-configuration-set-suppression-options-lifecycle.

Cause 5 of 7 — CreateConfigurationSet's invalid-name refusal is an emulator-authored sentence.
AWS: Smithy CreateConfigurationSet input {ConfigurationSetName (required), ...}, errors AlreadyExistsException(400)/BadRequestException(400)/NotFoundException(404)/.... A name containing characters outside [A-Za-z0-9_-] is refused 400 BadRequestException with `Invalid configuration set name <<NAME>>: only alphanumeric ASCII characters, '_', and '-' are allowed.` — fixed text `Invalid configuration set name <` + the ConfigurationSetName exactly as submitted + `>: only alphanumeric ASCII characters, '_', and '-' are allowed.` — and the refusal persists nothing, leaving the name reusable. Emulator: `Configuration set name <NAME> is invalid. The name can contain up to 64 alphanumeric characters, including letters, numbers, hyphens (-) and underscores (_) only.` — the model's documentation prose, unbracketed name, wrong sentence shape. Why: a client matching AWS's refusal text, or extracting the rejected name from between the angle brackets, does not recognise the error. Fix: the CreateConfigurationSet handler's name-validation message. Traces: sesv2.sesv2-configuration-set-create-refusals-persist-nothing-then-name-reusable.

Cause 6 of 7 — CreateTenant/GetTenant's invalid-name refusal is an emulator-authored sentence.
AWS: Smithy CreateTenant input {TenantName (required, @length min 1), Tags, SuppressionAttributes}, error BadRequestException(400); the TenantName shape documents "up to 64 alphanumeric characters, including letters, numbers, hyphens (-) and underscores (_) only" but AWS's refusal is worded `Invalid tenant name <<NAME>>: only alphanumeric ASCII characters, '_', and '-' are allowed.` — fixed text `Invalid tenant name <` + the TenantName exactly as submitted + `>: only alphanumeric ASCII characters, '_', and '-' are allowed.` GetTenant validates the name shape before any lookup and returns the IDENTICAL message, not NotFoundException. Emulator: `Invalid tenant name: <NAME>. The name can contain up to 64 alphanumeric characters, including letters, numbers, hyphens (-) and underscores (_) only.` — a colon instead of angle brackets, plus the doc prose. Why: a client matching AWS's text (or parsing the bracketed name) does not recognise the refusal; the same divergence appears on the read path. Fix: the shared tenant-name validation message used by the CreateTenant and GetTenant handlers. Traces: sesv2.tenant-name-validation-and-associated-resource-delete-blocked.

Cause 7 of 7 — PutConfigurationSetDeliveryOptions refuses an unknown SendingPoolName with the wrong error TYPE and message.
AWS: Smithy PutConfigurationSetDeliveryOptions input {ConfigurationSetName (httpLabel, required), TlsPolicy, SendingPoolName, MaxDeliverySeconds (range 300..50400)}, errors BadRequestException(400)/NotFoundException(404)/TooManyRequestsException(429). A SendingPoolName naming a dedicated IP pool that does not exist is refused 400 BadRequestException with `SendingPool <<NAME>> doesn't exist` — fixed text `SendingPool <` + the SendingPoolName from the request + `> doesn't exist`, with NO trailing period — i.e. AWS classifies the unknown pool as a bad REQUEST parameter, not as a missing resource. Emulator: 404 NotFoundException `The requested pool <<NAME>> does not exist.` — wrong error shape, wrong HTTP status, and an emulator-authored sentence. Why: the error type drives client control flow (NotFoundException is commonly treated as "the configuration set is gone" and as retryable-after-create, BadRequestException as a caller bug), and the modeled 404 vs 400 status changes SDK retry/exception classification. Fix: the PutConfigurationSetDeliveryOptions handler's sending-pool resolution — raise BadRequestException with AWS's sentence instead of NotFoundException. Traces: sesv2.sesv2-configuration-set-put-delivery-pool-rejection-and-field-update-scope.
