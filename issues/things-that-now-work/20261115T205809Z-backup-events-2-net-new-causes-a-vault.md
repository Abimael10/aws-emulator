# backup__events: 2 net-new causes — a vault-ARN-scoped rule never receives the native 'Backup Job State Change' event, and the Lambda-target invoke-permission gate scenario reaches no verdict

> _Note: this issue was identified against the code base at commit `46d55b66024c420c7c691480750eaf9f45a9af94`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
StartBackupJob / PutEvents / PutTargets

## Description
Two distinct net-new causes in AWS Backup's EventBridge delivery surface. Neither failing check is reported as ALREADY FILED or OWNED by the suite, so neither carries an existing issue's replay key. Related open issues naming neighbouring causes of the same family (they do NOT cover these two checks): 20261107T205257Z-backup-events-4-net-new-causes-backup-emits.md (its Cause 3 is the COMPLETED 'Backup Job State Change' event not reaching a CFN- or CLI-created rule's target), 20261111T065053Z-backup-events-the-failed-backup-job-state-change.md (the FAILED state-change event), 20261115T200918Z-backup-events-no-recovery-point-state-change-event.md (the 'Recovery Point State Change' event).

Cause 1 of 2: no native 'Backup Job State Change' event is published for a real StartBackupJob, so a rule whose pattern filters on one backup vault's ARN in the event detail never delivers to its SQS target and the vault-ARN scoping of the rule cannot be observed at all.
AWS: a StartBackupJob against a vault publishes an event on the default bus with source 'aws.backup', detail-type 'Backup Job State Change' and a detail carrying backupJobId and backupVaultArn for each state transition of that job; a rule with EventPattern {"source":["aws.backup"],"detail-type":["Backup Job State Change"],"detail":{"backupVaultArn":[<vault arn>]}} and an SQS target whose queue policy allows events.amazonaws.com must receive the envelope for a job in that vault and must receive nothing for an otherwise identical job in a different vault. The Smithy model for backup documents the operations only and carries no event documentation, so this is recorded behavior only: the recording shows one envelope on the queue whose detail.backupJobId is the target job and whose detail.backupVaultArn is exactly the vault ARN the pattern names, and no envelope for the other vault's job.
Emulator: nothing is ever published for the job, so the shared observation window makes no progress and the check is cut off at the 60 s run budget with no verdict ('Check timed out after 60.0s'). The positive assertion ('event for the exact target vault ARN must be delivered') is never satisfiable because the emulator emits no aws.backup job-state-change event at all; consequently the negative half (no leak for the other vault ARN) is also unverified.
Why: a client that scopes an EventBridge rule to a single vault's ARN to drive per-vault automation (notification, compliance, downstream copy) sees the rule never fire for jobs in that vault, and gets no signal that the rule's detail-level scoping works; vault-scoped backup pipelines silently do nothing.
Fix: the Backup service's event-publication path — a backup job's state transitions must put an 'aws.backup' / 'Backup Job State Change' event (detail including backupJobId and backupVaultArn) on the default event bus, so EventBridge's existing pattern matching on detail.backupVaultArn can route it.
Traces: backup__events.eventbridge-rule-scoped-to-specific-backup-vault-arn.

Cause 2 of 2: the Lambda-target invoke-permission gate for an EventBridge rule reaches no verdict — the rule/target/PutEvents round trip produces no observable delivery, so the check is cut off at the 60 s budget before either the negative or the positive control resolves.
AWS: a rule matching a custom-source event ({"source":["sim2real.backup"],"detail-type":["Backup Job State Change"],"detail":{"state":["COMPLETED"]}}) with a Lambda target must NOT invoke the function while the function's resource policy carries no lambda:InvokeFunction grant for events.amazonaws.com scoped to that rule ARN, and MUST invoke it once AddPermission grants it — the handler then forwards the event's detail marker to SQS. Recorded behavior only (no model statement covers target invocation); the recording shows no marker message in the first window and exactly the latest attempt's marker after the grant.
Emulator: the scenario makes no progress inside the run budget and is killed ('Check timed out after 60.0s'), so the post-grant positive control ('positive control: Lambda was not invoked even after granting the invoke permission') is never reached and the permission gate is unobservable.
Why: a client cannot tell whether EventBridge honours a Lambda target's resource policy — either an unauthorized rule silently invokes the function (over-permissive) or an authorized one never does (delivery lost). Both are security- and reliability-relevant and neither is currently observable.
Fix: the EventBridge rule-target dispatch path for Lambda targets — it must evaluate the target function's resource policy (principal events.amazonaws.com, SourceArn = rule ARN) and invoke only when permitted, and must invoke promptly once AddPermission has granted it, so the delivery completes within a normal observation window.
Traces: backup__events.eventbridge-rule-missing-target-permission-backup-job-event-not-invoked.

## Evidence
Cause 1 — Expected: one SQS message whose body is an EventBridge envelope with source 'aws.backup', detail-type 'Backup Job State Change', detail.backupJobId equal to the job started in the target vault and detail.backupVaultArn equal to the vault ARN named in the rule pattern (the job id and vault ARN are per-run values; the fixed part is the source, the detail-type and the presence of the two detail members), and NO message for the job started in the other vault. Actual: no message of either kind arrives; the shared 220 s observation window makes no progress and the runner reports 'Error: Check timed out after 60.0s' with no verdict. No aws.backup job-state-change event is emitted by the emulator at all.

Cause 2 — Expected: first window: no SQS marker message (Lambda not invoked without an invoke permission for the rule); after lambda AddPermission(Principal=events.amazonaws.com, Action=lambda:InvokeFunction, SourceArn=<rule arn>): a marker message whose 'marker' equals the detail.backupJobId of the latest PutEvents attempt. Actual: 'Error: Check timed out after 60.0s' — the check is cut off before the positive control, so no delivery (permitted or not) is observed.

## Steps to Reproduce
Cause 1: CreateTable (two DynamoDB tables), CreateBackupVault twice (target + other), create a backup service role; PutRule Name=<r> EventPattern={"source":["aws.backup"],"detail-type":["Backup Job State Change"],"detail":{"backupVaultArn":[<target vault arn>]}} State=ENABLED; SetQueueAttributes to allow events.amazonaws.com with ArnEquals aws:SourceArn=<rule arn>; PutTargets Rule=<r> Targets=[{Id:sqs-target,Arn:<queue arn>}]; StartBackupJob for the other vault/table and for the target vault/table; ReceiveMessage in a loop — expect exactly one envelope for the target job and none for the other, observe nothing at all.

Cause 2: CreateQueue; CreateRole + CreateFunction (python3.12 handler forwarding event['detail']['backupJobId'] to the queue); PutRule EventPattern={"source":["sim2real.backup"],"detail-type":["Backup Job State Change"],"detail":{"state":["COMPLETED"]}}; PutTargets with the function ARN; PutEvents one matching entry and poll the queue (expect nothing); lambda AddPermission(StatementId=AllowEventBridgeInvoke, Action=lambda:InvokeFunction, Principal=events.amazonaws.com, SourceArn=<rule arn>); PutEvents again with a fresh marker and poll (expect the marker).
