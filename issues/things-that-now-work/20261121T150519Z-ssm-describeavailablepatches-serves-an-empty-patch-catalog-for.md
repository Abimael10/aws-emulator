# SSM DescribeAvailablePatches serves an empty patch catalog for every filter

> _Note: this issue was identified against the code base at commit `b61d91764c5b64113b88eda248364bbad90afe06`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
DescribeAvailablePatches

## Description
Three net-new causes under one heading: SSM's `DescribeAvailablePatches` read surface answers HTTP 200 with a `Patches` list that holds none of the vendor patch records AWS's patch catalogue serves, for an unfiltered read, for a product/classification-filtered read, and for the read a freshly created patch baseline is inspected with. They share one fault — the service's built-in patch catalogue is not seeded, so the operation is a 200 that always projects an empty list — but each is a separate recorded step a fixer must re-replay.

Cause 1 of 3: an unfiltered/default DescribeAvailablePatches returns none of the Windows patch records.
AWS: Smithy (ssm): DescribeAvailablePatches input {Filters: PatchOrchestratorFilterList @length 0..5, MaxResults: PatchBaselineMaxResults @range 1..100, NextToken}; output {Patches: PatchList, NextToken}; @paginated(items: "Patches", pageSize: "MaxResults"); the only modeled error is InternalServerError (500). Recorded behavior: the call answers 200 with a page of `Patch` records drawn from the service-owned patch catalogue, each carrying Id, KbNumber, MsrcNumber, MsrcSeverity, Classification, Product, ProductFamily, Vendor, Language, Title, Description, ContentUrl and ReleaseDate. The requirement is that the catalogue EXISTS and is paged — the particular patch ids, KB numbers and release dates in any one recording are that recording's values, not the requirement.
Emulator: HTTP 200 with a `Patches` list that contains no element at all for any of the requested ids — every expected record reports `missing (expected {...}, got None)`, i.e. the projection has nothing to project.
Why: a client that enumerates available patches to build or validate a patch baseline (Patch Manager's whole discovery path, and any tool that resolves a KB number or an MSRC severity to a patch) sees an empty catalogue and silently concludes there is nothing to patch. Because the answer is a 200 and not an error, the emptiness is indistinguishable from "no patches match", so callers do not retry or fail loudly.
Fix: the service's seeded patch catalogue and the DescribeAvailablePatches handler that reads it — the built-in catalogue has to be populated with the vendor patch records the operation serves, and the handler must page them through MaxResults/NextToken.
Traces: ssm-catalog-describe-available-patches#task#1.

Cause 2 of 3: a filtered DescribeAvailablePatches (product/classification filters) returns none of the matching records.
AWS: Smithy (ssm): DescribeAvailablePatches.Filters -> PatchOrchestratorFilterList (@length 0..5), applied against the catalogue's `Patch` members (PRODUCT, CLASSIFICATION, MSRC_SEVERITY, PATCH_ID and the other documented keys). Recorded behavior: a filtered read answers 200 with exactly the catalogue entries matching the filter — e.g. a WindowsServer2022 `Updates` read answers with the KB-numbered cumulative-update records for that product.
Emulator: HTTP 200 with an empty `Patches` list; every expected record is `missing ... got None`. Filtering cannot be exercised at all because the set it filters is empty.
Why: filter-driven patch selection is how a caller narrows the catalogue before approving patches; an empty answer makes every filter look like a filter that matches nothing, so approval rules are built against an empty candidate set.
Fix: same component as cause 1 — once the catalogue is seeded, the Filters evaluation in the DescribeAvailablePatches handler must be exercised against it.
Traces: ssm-catalog-describe-available-patches#task#2.

Cause 3 of 3: DescribeAvailablePatches after CreatePatchBaseline returns none of the patches the baseline is inspected for.
AWS: Smithy (ssm): DescribeAvailablePatches as above; the catalogue is service-owned and independent of any baseline, so creating a baseline does not change what the catalogue serves. Recorded behavior: the read answers 200 with the catalogue records selected by the step's filter — in this recording the ServicePacks entries for the Windows7 / WindowsServer2008R2 product family.
Emulator: HTTP 200 with no `Patches` elements ($.Patches[0], $.Patches[1], $.Patches[2] all `got None`).
Why: the create-baseline-then-inspect-patches flow is the normal way a client checks which patches a baseline's rules would approve; with an empty catalogue the flow reports that the baseline governs nothing.
Fix: same component as cause 1.
Traces: ssm-create-patch-baseline-and-inspect-patches#task#2.
