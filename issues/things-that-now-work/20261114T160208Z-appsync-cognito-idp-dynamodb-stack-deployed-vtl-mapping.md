# appsync__cognito-idp__dynamodb: stack-deployed VTL mapping-template resolvers are never executed, and a Cognito token from a foreign user pool is admitted with HTTP 200 instead of 401 (2 causes)

> _Note: this issue was identified against the code base at commit `4cf7211f237a5c930178a3131e9243c3c3eb5dd6`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
PostGraphQL (AppSync GraphQL data plane) / CreateResolver

## Description
Two net-new root causes on the AppSync GraphQL data plane, both reached through the CloudFormation/stack-deployed (`deploy-*`) legs of this service grouping. Both must be closed before submitting. Cause 2 is security-relevant (a token minted by an unrelated user pool is served), so the bundle is HIGH.

Cause 1 of 2: a resolver that a deployed stack defines with VTL request/response mapping templates is never run. Every guarded field answers HTTP 200 with data.<field> null and a single emulator-authored `errors` entry demanding APPSYNC_JS code, so neither the success legs nor the refusal legs (field-level group authorization, a data-source role without the DynamoDB action) of a template-defined API can be observed. Failing checks: appsync__cognito-idp__dynamodb.deploy-appsync-ddb-cognito-stack-positive, appsync__cognito-idp__dynamodb.deploy-appsync-schema-resolver-mapping-positive, appsync__cognito-idp__dynamodb.deploy-appsync-multi-datasource-pipeline-positive, appsync__cognito-idp__dynamodb.deploy-appsync-cognito-groups-field-authorization-positive, appsync__cognito-idp__dynamodb.deploy-appsync-ddb-missing-datasource-role-negative, appsync__cognito-idp__dynamodb.deploy-cognito-userpool-client-appsync-auth-config-negative.
AWS: Smithy (services/service-com-amazonaws-appsync-awsdeepdishcontrolplaneservice) models mapping templates as a first-class way to define a resolver — Resolver$requestMappingTemplate and Resolver$responseMappingTemplate target MappingTemplate (@length min 1, max 65536), and Resolver$code is documented as the ALTERNATIVE ("When code is used, the runtime is required. The runtime value must be APPSYNC_JS"); APPSYNC_JS is never a precondition for running a resolver. For Resolver$kind UNIT over an AMAZON_DYNAMODB data source AWS evaluates the "version": "2018-05-29" request template (PutItem/GetItem/Query/UpdateItem/BatchPutItem plus the $util.dynamodb.* helpers), performs the DynamoDB call under the data source's serviceRoleArn, and renders the result through the response template; for kind PIPELINE it does the same for each function in the order given. A resolved field is HTTP 200 with data.<field> populated and NO `errors` member. A data-source failure is HTTP 200 with data.<field> null and an `errors` entry whose errorType/message come from the failure — an access-denied class (errorType containing "AccessDenied"/"not authorized") when the service role lacks the action. A field the schema restricts to a Cognito group the caller is not in is HTTP 200 with data.<field> null and an `errors` entry whose errorType is exactly "Unauthorized".
Emulator: every such field answers HTTP 200 with data.<field> null and errors: [{"path": ["<field>"], "message": "This field's resolver is defined by mapping templates, which this endpoint does not run; define it with APPSYNC_JS code."}]. For a pipeline function the same sentence is prefixed with "<functionName>: ". The whole sentence is fixed emulator-authored text that AWS never emits; the only variable parts are `path` (the field being resolved) and that function-name prefix. CreateResolver/the stack deployment accept the templates, so the divergence is purely in execution: nothing is written, read or queried, so the positive legs see null data and the two negative legs see this message instead of AWS's access-denied error and its "Unauthorized" errorType.
Why: a client that uses the documented VTL resolver style — which is what CDK/CloudFormation AWS::AppSync::Resolver templates emit — gets a 200 whose payload says the field could not be resolved and whose side effect never happened; a client asserting an access-denied or field-level Unauthorized refusal sees this message instead, so both the success and the refusal contracts of a template-backed API are wrong and authorization outcomes are indistinguishable from the engine gap.
Fix: the GraphQL data-plane resolver-execution path needs a VTL mapping-template engine alongside the APPSYNC_JS runtime — evaluate requestMappingTemplate with the $util/$ctx bindings (including $ctx.identity and $ctx.args), dispatch the rendered operation to the resolver's data source under its serviceRoleArn (including the IAM evaluation that yields the access-denied error), run each PIPELINE function in order, then render responseMappingTemplate into data/errors; the schema's group-based field authorization must be evaluated on that path so it can produce errorType "Unauthorized".

Cause 2 of 2: an AMAZON_COGNITO_USER_POOLS GraphQL API deployed by a stack admits an ID token minted by a DIFFERENT user pool — the request reaches resolver execution and is answered HTTP 200 instead of being refused. Failing check: appsync__cognito-idp__dynamodb.deploy-cognito-userpool-client-appsync-auth-config-negative.
AWS: recorded behavior only (the data-plane authorization contract is not in the control-plane Smithy model): a request to a user-pool-authorized API whose Authorization token does not verify against the API's configured userPoolConfig — signature not from that pool's JWKS, or iss/aud not matching the configured pool and app client — is refused with HTTP 401 and an UnauthorizedException GraphQL error, and the field is never resolved. Only a token signed by the configured pool and issued to the configured app client reaches a resolver.
Emulator: the foreign-pool token is answered HTTP 200 with body {'data': {'createItem': None}, 'errors': [{'path': ['createItem'], 'message': "This field's resolver is defined by mapping templates, which this endpoint does not run; define it with APPSYNC_JS code."}]} — i.e. it got past authorization and failed only on Cause 1. No 401 and no UnauthorizedException is produced. The 200 status is the divergence; it is independent of Cause 1, because AWS refuses the request before any resolver is consulted.
Why: the API's authorization mode is inert for a stack-deployed API, so any bearer string shaped like a JWT from any pool is as good as a real one. An API that must be closed to other pools' users is open to them, and a client (or a test) asserting the 401 refusal sees success against the emulator.
Fix: the data plane's AMAZON_COGNITO_USER_POOLS authorizer — verify the presented token's signature against the configured user pool's JWKS and check issuer/audience (client_id) against the API's userPoolConfig BEFORE any resolver runs, answering HTTP 401 with the UnauthorizedException error body when it fails.
Traces: appsync__cognito-idp__dynamodb.deploy-cognito-userpool-client-appsync-auth-config-negative. Open issue 20261114T070045Z-appsync-cognito-idp-dynamodb-vtl-mapping-template-resolvers.md owns the sibling tampered-signature and wrong-pool checks on the directly-created API but does not carry this stack-deployed check's replay key.

## Steps to Reproduce
1. Boot the emulator from this checkout and replay the behavioral suite (service heading: appsync__cognito-idp__dynamodb).
2. Deploy a CloudFormation stack containing: an AWS::Cognito::UserPool + UserPoolClient; an AWS::DynamoDB::Table; an AWS::AppSync::GraphQLApi with AuthenticationType AMAZON_COGNITO_USER_POOLS and UserPoolConfig naming that pool; an AWS::AppSync::GraphQLSchema with createItem/getItem (and a group-restricted field); an AWS::AppSync::DataSource of Type AMAZON_DYNAMODB with a ServiceRoleArn allowing the needed actions; and AWS::AppSync::Resolver resources (one UNIT per field, plus a PIPELINE resolver with AWS::AppSync::FunctionConfiguration members) defined with RequestMappingTemplate '{"version": "2018-05-29", "operation": "PutItem", "key": {"id": $util.dynamodb.toDynamoDBJson($ctx.args.id)}, "attributeValues": {...}}' and ResponseMappingTemplate '$util.toJson($ctx.result)'.
3. Mint an ID token for a user in that pool and POST the createItem mutation to the API's GraphQL URL. Observed: HTTP 200 with data.createItem null and errors[0].message "This field's resolver is defined by mapping templates, which this endpoint does not run; define it with APPSYNC_JS code.", and the table stays empty. Expected: HTTP 200 with data.createItem populated and the item written. Repeat for the getItem query and for the pipeline field (observed: same message, prefixed with the function name).
4. Repeat step 3 with a resolver whose data-source ServiceRoleArn omits the write action — expect HTTP 200 with data null and an access-denied errorType; and with a field restricted to a Cognito group the caller is not in — expect errorType "Unauthorized". Observed: the mapping-template message in both cases.
5. Create a SECOND, unrelated Cognito user pool and app client, mint a valid ID token there, and POST the same mutation to the first API. Observed: HTTP 200. Expected: HTTP 401 with an UnauthorizedException GraphQL error and no resolver execution.
