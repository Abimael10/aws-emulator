# MSK data plane and lifecycle: bootstrap string carries one endpoint for an N-broker cluster, the native broker has no CreateTopics (api key 19), the SASL/SCRAM listener never serves, and the replicator lifecycle never settles (4 causes)

> _Note: this issue was identified against the code base at commit `e13abbd45115774a2130a0adf52b114a76179055`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
GetBootstrapBrokers

## Description
Four net-new root causes in the emulated MSK surface, all grounded in failing behavioral checks of service `kafka`. None of them is marked ALREADY FILED or OWNED in the replay report. Open issues that look adjacent but do NOT cover these are named per cause.

Cause 1 of 4: GetBootstrapBrokers publishes a single hostname:port pair no matter how many broker nodes the cluster has.
AWS: Smithy (kafka, GetBootstrapBrokers -> GetBootstrapBrokersResponse.BootstrapBrokerString / .BootstrapBrokerStringTls / .BootstrapBrokerStringSaslScram / .BootstrapBrokerStringSaslIam, jsonName bootstrapBrokerString*): "A string containing one or more hostname:port pairs." A cluster created with NumberOfBrokerNodes = N advertises N comma-separated hostname:port pairs, one per broker node, in each applicable broker-string variant; the count of pairs is the cluster's broker count, and each pair addresses a distinct broker.
Emulator: for a cluster created through CloudFormation with NumberOfBrokerNodes: 2 the broker string holds exactly one pair (replay shows a single host and a single host:port, e.g. one `<host>` / one `<host>:<port>` entry where two were expected). The Metadata response of the native listener likewise describes both brokers behind the same single host:port.
Why: a client that splits the bootstrap string to size its connection pool, to pin a replication factor to the broker count, or to fail over to a second broker sees a one-broker cluster. Every multi-broker assumption (replication factor 2, leader failover, per-broker reachability probes) silently degrades to a single endpoint even though DescribeCluster reports two brokers.
Fix: the GetBootstrapBrokers handler and the cluster state that backs it must emit one endpoint per provisioned broker node (and keep the pairs distinct per broker) in every variant it serves. This is NOT the already-open 20261104T171616Z-kafka-getbootstrapbrokers-serves-every-broker-string-variant-regardless-of.md (which is about WHICH variants are populated) nor 20261109T211434Z-kafka-msk-bootstrap-endpoints-are-published-as-real-aws.md (which is about the host name published); the defect here is the NUMBER of pairs.
Traces: kafka.deploy-cfn-msk-cluster-active-and-reachable, kafka.deploy-msk-cluster-cfn-active-and-bootstrap-brokers, kafka.deploy-msk-cluster-cfn-bootstrap-brokers-reachable.

Cause 2 of 4: the native Kafka broker does not implement CreateTopics — its ApiVersions response omits api key 19, and a CreateTopics request on the PLAINTEXT listener is answered by closing the socket.
AWS: recorded behavior only (the Kafka wire protocol is not in the kafka Smithy model; the model covers the control plane). A real MSK broker on the KafkaVersion the cluster reports (3.9.x here) advertises the topic-admin api keys in its ApiVersions response — CreateTopics (19) and DeleteTopics (20) among them — and an AdminClient.create_topics over SASL/AWS_MSK_IAM (9098) or PLAINTEXT (9092) creates the topic and returns a CreateTopics response.
Emulator: ApiVersions advertises 19 api keys and key 19 is not among them: [0, 1, 2, 3, 8, 9, 10, 11, 12, 13, 14, 17, 18, 22, 29, 30, 31, 32, 36]. kafka-python therefore refuses before sending: `IncompatibleBrokerVersion: [Error 35] IncompatibleBrokerVersion: Kafka broker does not support the 'CreateTopicsRequest' Kafka protocol.` When a client sends CreateTopics anyway (the in-VPC raw-protocol probe), the broker closes the connection: `CreateTopics on controller: ConnectionError: broker closed after 0 of 4 bytes` — no error response, no error code, just a dropped socket. ApiVersions and Metadata do answer, so the listener is up; only the topic-admin half of the protocol is missing.
Why: every customer path that administers topics from a client (kafka-python/Java AdminClient, `kafka-topics.sh`, Spring/Flink connectors that auto-create their topics, Lambda ESM producers that pre-create a topic) fails at setup with a broker-version error that tells the user their BROKER is too old rather than that the operation is unimplemented. Producing, consuming, consumer-group, transaction and open-monitoring behavior all become unobservable because the topic can never be created.
Why (distinct from what is filed): 20261104T171616Z-kafka-no-kafka-broker-answers-on-the-advertised-bootstrap.md and 20261105T101629Z-kafka-every-native-msk-data-plane-check-is.md describe a broker that accepts NO connection / a runner that cannot probe at all. Here the socket IS accepted and ApiVersions and Metadata are served correctly; the divergence is the missing CreateTopics (and the silent close instead of a protocol error), so those issues do not cover it.
Fix: the emulated Kafka wire-protocol broker — its ApiVersions table must advertise the api keys it actually serves, and CreateTopics (19)/DeleteTopics (20) must be handled on the listener (returning a CreateTopics response, with a Kafka error code when it refuses, never an abrupt close).

Cause 3 of 4: on a SASL/SCRAM + TLS provisioned cluster, no SASL/SCRAM client ever succeeds, so the post-association produce/consume never becomes possible.
AWS: recorded behavior only for the wire leg; the control-plane contract is Smithy kafka BatchAssociateScramSecret -> UnprocessedScramSecrets empty on success, and AWS documents that an associated secret's credential propagates to the brokers (MSK "syncs the credential data periodically"), after which a SCRAM-SHA-512 client on the bootstrapBrokerStringSaslScram endpoint produces and consumes, and the topic's configs are readable through DescribeConfigs.
Emulator: these checks reach no verdict at all — each hangs in the loop that polls for the first successful SCRAM produce after BatchAssociateScramSecret and is killed at the suite's 60 s cap (`Check timed out after 60.0s`). The SASL/SCRAM leg of the advertised endpoint never completes a produce, so the association is unobservable.
Why: a client that authenticates with a Secrets Manager SCRAM secret — the documented MSK password path — can never write or read, and it gets no refusal to act on either: the call simply never succeeds. The emulator reports association success while the credential is never usable.
Fix: the SASL/SCRAM listener of the emulated broker and the state that joins an associated secret to broker-side credentials, so an associated SCRAM user authenticates and its produce/fetch/DescribeConfigs complete (and a non-associated one is refused). Adjacent but not covering: 20261107T210159Z-kafka-three-more-msk-data-plane-checks-reach-no.md (different checks, connection never accepted).
Traces: kafka.e2e-cluster-scram-auth-produce-consume-teardown, kafka.e2e-cluster-topic-lifecycle-produce-consume-teardown, kafka.topic-retention-config-echoed-over-scram-message-readable.

Cause 4 of 4: the replicator path never settles — the CREATING-state guard sequence cannot be exercised because the cluster/operation/replicator lifecycle never reaches its terminal state.
AWS: Smithy kafka UpdateStorage/UpdateRebalancing/UpdateReplicationInfo all model BadRequestException (400) for a resource in the wrong state, with AWS's fixed messages — "This operation is only valid for resources that are in one of the following states :[ACTIVE]" for the cluster guard and "Invalid parameter replicatorArn: This operation is only valid for resources that are in one of the following states: [RUNNING]" for the replicator guard (fixed text; only the parameter name `replicatorArn` and the state list are variable) — and the same calls are ACCEPTED once DescribeClusterV2 reports ACTIVE / DescribeReplicator reports RUNNING, with DescribeClusterOperation reaching a terminal status and CurrentVersion advancing.
Emulator: the check never reaches a verdict (`Check timed out after 60.0s`): after the CREATING-state probes it waits for both clusters to become ACTIVE, for the UpdateStorage ClusterOperationArn to finish and for the replicator to reach RUNNING, and one of those waits never completes.
Why: a client that polls for ACTIVE/RUNNING before mutating — the documented way to use these APIs — blocks forever, and the positive half of the state guard (the update that must be accepted once the resource settles) can never be reached.
Fix: the asynchronous state machines behind CreateClusterV2/UpdateStorage/CreateReplicator — cluster state, cluster-operation status and replicator state must advance to their terminal values and bump CurrentVersion. Related open issue 20261114T065925Z-kafka-msk-asynchronous-lifecycles-never-settle-channel-configuration-delete.md names other replicator checks but does not carry this check's replay key.
Traces: kafka.cluster-replicator-updates-blocked-while-creating-rejected.
