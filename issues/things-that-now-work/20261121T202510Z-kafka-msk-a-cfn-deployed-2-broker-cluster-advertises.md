=== Cause 1 of 2: GetBootstrapBrokers publishes ONE hostname:port pair for a cluster whose NumberOfBrokerNodes is 2 (failing check: kafka.deploy-cfn-msk-cluster-active-and-reachable) ===

AWS: Smithy (services/service-com-amazonaws-kafka-kafka/smithy-model/com-amazonaws-kafka-kafka.json) GetBootstrapBrokers = GET /v1/clusters/{ClusterArn}/bootstrap-brokers, success code 200; input ClusterArn (@httpLabel, required); output members BootstrapBrokerString (jsonName bootstrapBrokerString), BootstrapBrokerStringTls, BootstrapBrokerStringSaslScram, BootstrapBrokerStringSaslIam plus the Public*/VpcConnectivity*/*Ipv6 siblings, each a __string documented as "a string containing one or more hostname:port pairs". CreateCluster = POST /v1/clusters, code 200, with required numberOfBrokerNodes (__integerMin1Max15) and brokerNodeGroupInfo.clientSubnets. On real MSK the bootstrap string is a comma-separated list carrying ONE entry per broker node of the cluster: a provisioned cluster with numberOfBrokerNodes = N placed across N client subnets advertises N distinct broker hosts on the mechanism's port. The CARDINALITY (entries == numberOfBrokerNodes) is the requirement; the concrete host names and port numbers are environment values and are not.

Emulator: for a cluster created through CloudFormation's AWS::MSK::Cluster with NumberOfBrokerNodes: 2 and two ClientSubnets in distinct AZs, the cluster reaches ACTIVE and GetBootstrapBrokers answers 200, but the broker string holds a SINGLE hostname:port pair — replayed as `AssertionError: expected 2 bootstrap broker hosts (NumberOfBrokerNodes=2), got ['127.0.0.1']` (check_kafka_deploy_cfn_msk_cluster_active_and_reachable.py line 104). The literal '127.0.0.1' and its ephemeral port are this environment's values and fill the template; the divergence is that one entry is emitted where the cluster's broker count demands two, i.e. the string is not built from the cluster's materialised broker list.

Why: a client hands the bootstrap string straight to a Kafka client as bootstrap.servers, or derives the broker set from it for per-broker fan-out (open-monitoring/Prometheus scrape targets, per-broker health probes, admin tooling that enumerates brokers, security-group and firewall templates). Against this emulator an N-broker cluster looks like a one-broker cluster: fan-out silently collapses to a single node, a broker-level fault is invisible, and a client that pins exactly numberOfBrokerNodes endpoints (as a CFN-deployed estate does from its own template) fails with a configuration error on a cluster the control plane reports ACTIVE.

Fix: the GetBootstrapBrokers handler's broker-string assembly in the kafka service, together with the cluster/broker state it reads — materialise one broker endpoint per broker node at CreateCluster/CreateClusterV2 time (including the CloudFormation AWS::MSK::Cluster path, which is where this replay creates the cluster) and render every bootstrapBrokerString* member from that list so the entry count equals numberOfBrokerNodes, instead of emitting a single endpoint.

=== Cause 2 of 2: a provisioned cluster carrying a ConfigurationInfo never becomes observable within a client-sized budget, so the broker's application of the Configuration's num.partitions / default.replication.factor cannot be reached at all (failing check: kafka.msk-cluster-configuration-num-partitions-default-is-applied-by-the-broker) ===

AWS: recorded behavior only for the timing; the model states the surface. Smithy CreateConfiguration stores ServerProperties (a blob of server.properties lines); CreateCluster carries configurationInfo (ConfigurationInfo { arn, revision }); DescribeClusterV2 reports Provisioned.CurrentBrokerSoftwareInfo.ConfigurationArn / ConfigurationRevision; GetBootstrapBrokers publishes the PLAINTEXT bootstrapBrokerString for a cluster whose encryptionInfo.encryptionInTransit.clientBroker is PLAINTEXT and clientAuthentication.unauthenticated.enabled is true. The recording shows the whole path completing and then the subject being asserted: the cluster settles to ACTIVE, the advertised PLAINTEXT endpoint accepts TCP, answers a hand-framed ApiVersions with error_code 0 advertising api keys 0 (Produce), 3 (Metadata), 19 (CreateTopics) and 32 (DescribeConfigs), and the BROKER then substitutes the attached Configuration's num.partitions=N and default.replication.factor=R for a CreateTopics that asks for the server default (num_partitions=-1, replication_factor=-1) — N partitions with ids 0..N-1 and R replicas each — while every broker's own describe_configs reports num.partitions=N, an explicit-count control topic keeps its explicit count, and a produce to a never-created topic is refused with Kafka errno 3 (UNKNOWN_TOPIC_OR_PARTITION) because the Configuration declares auto.create.topics.enable=false.

Emulator: the check reaches NO verdict — 'Error: Check timed out after 60.0s'. Nothing in the CreateConfiguration -> DescribeConfigurationRevision -> CreateCluster(ConfigurationInfo) -> DescribeClusterV2 ACTIVE -> GetBootstrapBrokers -> TCP accept -> ApiVersions sequence completes inside the client-sized budget, so not one broker response is asserted on. Hypothesis: either the provisioned cluster lifecycle does not settle out of CREATING promptly, or nothing accepts and serves the Apache Kafka protocol on the PLAINTEXT endpoint the emulator advertises, so the check's internal readiness poll spends the whole budget.

Why: a customer who centralises topic defaults in an MSK Configuration — the documented way to set num.partitions and default.replication.factor fleet-wide — gets no answer at all: a PLAINTEXT, unauthenticated cluster that the control plane reports ACTIVE hangs at connection setup instead of serving CreateTopics/Metadata/DescribeConfigs or failing with an error. The behaviour presents as a broker outage rather than a configuration error, and no client-side change recovers it; every Configuration-honouring, auto-create and replication-factor guarantee of the data plane stays unobservable.

Fix: the kafka service's provisioned-cluster lifecycle state (CreateCluster/DescribeClusterV2 must reach ACTIVE promptly) and the emulated native broker listener that bootstrapBrokerString advertises — it must accept on the host:port it publishes and serve the Kafka wire protocol (ApiVersions, Metadata, CreateTopics, DescribeConfigs, Produce) over PLAINTEXT; then the CreateTopics path must resolve a -1 partition count / -1 replication factor from the ServerProperties of the Configuration attached via ConfigurationInfo rather than from a hard-coded default.
