# ssm: 7 net-new behavioral causes — GetInventorySchema refuses the published AWS:ComplianceItem type, inventory deletion/type-name and custom-schema validation paths misreport, CreateOpsMetadata is never IAM-authorized, CreateCloudConnector accepts a fabricated Azure tenant

> _Note: this issue was identified against the code base at commit `48d9d0ee5625876130172571538589ce856f53ef`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

GetInventorySchema

## Description
Seven net-new root causes in the ssm crate, every one grounded in a failing behavioral check the suite report lists under '### ssm' and marked neither 'ALREADY FILED' nor 'OWNED by'. THIS ISSUE HAS 7 CAUSES — Cause 1 of 7 through Cause 7 of 7 — and each must be closed and re-replayed before it is submitted.

Cause 1 of 7: GetInventorySchema refuses TypeName 'AWS:ComplianceItem' — an inventory type Systems Manager publishes — with 400 InvalidTypeNameException instead of answering 200 with that type's schema.
AWS: Smithy (services/service-com-amazonaws-ssm-amazonssm/smithy-model/com-amazonaws-ssm-amazonssm.json): GetInventorySchema.TypeName targets InventoryItemTypeNameFilter (@length 0..100, NO pattern constraint — it is a filter, not a strict name), output Schemas -> InventoryItemSchemaResultList, @paginated (MaxResults @range 50..200); the modelled client errors are InvalidNextToken and InvalidTypeNameException (both HTTP 400, awsQueryError InvalidTypeName). AWS's published inventory catalog includes AWS:ComplianceItem (its schema carries the compliance attributes ComplianceType, ExecutionId, ExecutionType, ExecutionTime, Id, Title, Status, Severity), so a GetInventorySchema call filtered to TypeName 'AWS:ComplianceItem' is a successful read: HTTP 200 with a Schemas entry for that type. InvalidTypeNameException is reserved for a name that breaks the ^(AWS|Custom):.*$ rule, the AWS: case-sensitivity rule or the ^(Custom:)([a-zA-Z0-9]{3,93})$ custom-name rule — not for a type the service itself publishes.
Emulator: HTTP 400 InvalidTypeNameException with the message 'The parameter type name isn't valid: AWS:ComplianceItem. An inventory type name is Custom:<name> or one of the type names Systems Manager publishes.' — prose built from the InvalidTypeNameException shape doc ('The parameter type name isn't valid.'), asserting the name is invalid while naming the very catalog the type belongs to. The emulator's schema catalog evidently has no AWS:ComplianceItem entry, so the filter falls through to a rejection.
Why: AWS:ComplianceItem is the schema every compliance client reads to discover which Details attributes PutComplianceItems/ListComplianceItems accept. A hard 400 on that discovery call aborts the whole compliance flow before any compliance call is made (six checks die here, in their setup, never reaching PutComplianceItems or ListComplianceItems), and a client that validates type names against this catalog concludes the account supports no compliance inventory at all.
Fix: the GetInventorySchema handler and the inventory-schema catalog data it reads in the ssm service — the catalog must contain the published AWS: types (AWS:ComplianceItem among them) and a TypeName filter naming a published type must project that schema under HTTP 200, reserving InvalidTypeNameException for names that violate the documented naming rules.
Related but not covering: open issue 20261116T133835Z-ssm-inventory-apis-getinventoryschema-serves-one-stale-schema.md (wire corpus) records in its cause 1 that the unfiltered GetInventorySchema catalog serves a single AWS:InstanceInformation entry and that AWS:ComplianceItem is one of the missing ones, but it carries only wire replay keys (no behavioral check id) and does not describe the filtered-lookup REFUSAL; open issue 20261103T215115Z-ssm-getinventoryschema-stub.md was filed when the operation was an unimplemented stub (it now answers). Neither gates these six checks.
Traces: ssm.compliance-item-numeric-and-timestamp-precision-preserved, ssm.compliance-item-timestamp-precision-preserved, ssm.compliance-items-invalid-resource-type-rejected, ssm.put-compliance-items-limit-exceeded-rejected, ssm.put-compliance-items-then-list-roundtrip, ssm.resource-compliance-summary-reflects-resource-state.

Cause 2 of 7: DescribeInventoryDeletions misclassifies a malformed DeletionId as InvalidDeletionIdException instead of the standard input-constraint ValidationException.
AWS: Smithy: DescribeInventoryDeletions.DeletionId targets UUID with @pattern ^[a-f0-9]{8}-[a-f0-9]{4}-[a-f0-9]{4}-[a-f0-9]{4}-[a-f0-9]{12}$; modelled client errors are InvalidDeletionIdException and InvalidNextToken. A DeletionId that violates that member pattern is refused by request validation, before any deletion lookup, with error code ValidationException and AWS's standard constraint message: fixed text '1 validation error detected: Value '' + the rejected value taken verbatim from the request + '' at 'deletionId' failed to satisfy constraint: Member must satisfy regular expression pattern: ' + the member's pattern. InvalidDeletionIdException is the answer for a well-formed id whose deletion cannot be resolved — and a well-formed, never-issued id is not an error at all: AWS answers 200 with InventoryDeletions == [] (recorded behavior).
Emulator: a malformed DeletionId is refused with error code InvalidDeletionIdException and the message 'The ID specified for the delete operation doesn't exist or isn't valid. Verify the ID and try again.' — the wrong error class, and a message that conflates 'does not exist' with 'is not valid'.
Why: the two classes mean different things to a client: ValidationException says 'fix the request string', InvalidDeletionIdException says 'that deletion is unknown'. Collapsing them hides the member-level pattern diagnostic (which member, which pattern), so a caller cannot tell a typo from a stale id, and the constraint-class negative tests clients ship against AWS can never pass.
Fix: DescribeInventoryDeletions' input validation in the ssm handler (services/service-com-amazonaws-ssm-amazonssm/src/ops/describe_inventory_deletions.rs) — validate DeletionId against the UUID member pattern first and emit ValidationException with AWS's '1 validation error detected: ...' template, leaving InvalidDeletionIdException for the resolution path.
Related but not covering: open issue 20261116T021504Z-ssm-describeinventorydeletions-stub.md names the operation as an unimplemented stub (it now answers) and cause 3 of 20261116T133835Z covers a plain LISTING answering 400; neither carries this check id or this refusal class.
Traces: ssm.describe-inventory-deletions-unknown-id-rejected.

Cause 3 of 7: after a DeleteInventory with SchemaDeleteOption='DeleteSchema' reaches LastStatus 'Complete', ListInventoryEntries still answers 200 for the deleted custom type instead of refusing it as undefined.
AWS: Smithy: ListInventoryEntries requires InstanceId and TypeName (InventoryItemTypeName, @length 1..100, @pattern ^(AWS|Custom):.*$) and models InvalidTypeNameException (client, HTTP 400, awsQueryError InvalidTypeName). Once DeleteSchema has removed a Custom: type, that type name is no longer defined for the account, so a read of it is refused exactly as a type that never existed is: HTTP 400 InvalidTypeNameException with the message 'Inventory type name <TypeName> is not defined.' — fixed text 'Inventory type name ' and ' is not defined.', with <TypeName> taken from the request (recorded behavior only for the text).
Emulator: HTTP 200 with a success body {'TypeName': <the deleted custom type>, 'InstanceId': <id>, 'Entries': []} — the type is still served, merely empty, even though the same check's DescribeInventoryDeletions poll reported the deletion Complete for that TypeName.
Why: this is a silent wrong answer. A client verifying a schema deletion cannot: the only independent proof that the data and the schema are gone is the refusal, and the emulator reports an existing-but-empty type instead. Teardown and compliance-of-deletion checks pass against an emulator that never deleted anything, and the deletion state machine's Complete status is not backed by any observable effect.
Fix: the DeleteInventory handler's schema-deletion state transition plus ListInventoryEntries' type-name resolution in the ssm service — a completed DeleteSchema must remove the custom type's registration so subsequent reads take the InvalidTypeNameException ('... is not defined.') path.
Traces: ssm.delete-inventory-then-list-deletions.

Cause 4 of 7: PutInventory does not enforce a registered custom schema's attribute set — a later write that drops a registered attribute is accepted with 200.
AWS: Smithy: PutInventory models InvalidItemContentException (with a TypeName member), ItemContentMismatchException, UnsupportedInventorySchemaVersionException and CustomSchemaCountLimitExceededException, all client HTTP 400 — i.e. item content is validated server-side against the registered schema. The first PutInventory for a new Custom: type registers its attribute set at the given SchemaVersion; a later write under the SAME SchemaVersion whose Content omits a registered attribute is refused with error code InvalidItemContentException and the message 'Custom inventory item doesn't match schema: input item [<attributes present, each followed by a space>] but required [<registered attributes, each followed by a space>].' — fixed text 'Custom inventory item doesn't match schema: input item [', '] but required [', '].', with the two attribute lists taken from the request and from the registered schema (recorded behavior only for the text; the recorded '[Widget ] but required [Widget Stage ]' is just that run's attribute names filling the template). The rejected write must leave the registered schema unchanged.
Emulator: HTTP 200 with an empty body (content-length 2) — the short write is accepted, so no schema enforcement happens at all on this path.
Why: inventory consumers rely on a custom type's attribute set being stable; accepting a write that silently drops an attribute corrupts the type's data (rows missing a column that queries and aggregators assume) and makes the InvalidItemContentException branch dead code. The caller is told its malformed agent payload was accepted.
Fix: PutInventory's item validation in the ssm handler (services/service-com-amazonaws-ssm-amazonssm/src/ops/put_inventory.rs) and the custom-schema registry it must compare against — compare each item's Content keys with the registered attribute set for that TypeName/SchemaVersion and refuse mismatches with the templated InvalidItemContentException, writing nothing.
Related but not covering: open issue 20261114T143448Z-ssm-putinventory-stub.md was filed when PutInventory was an unimplemented stub; it now answers 200 and carries no validation requirement and not this check id.
Traces: ssm.inventory-custom-schema-server-side-validation.

Cause 5 of 7: PutInventory's CustomSchemaCountLimitExceededException message is emulator-authored prose that describes the emulator rather than AWS's refusal.
AWS: Smithy: CustomSchemaCountLimitExceededException is a client error, HTTP 400, awsQueryError code CustomSchemaCountLimitExceeded, doc 'You have exceeded the limit for custom schemas. Delete one or more custom schemas and try again.'. When a PutInventory would register a custom inventory type beyond the account/Region cap, AWS refuses with that code and the message 'Total custom inventory schema count exceeded the limit <limit>.' — fixed text 'Total custom inventory schema count exceeded the limit ' and '.', with <limit> the enforced cap (20 in the recording). Deleting one schema makes the identical call succeed.
Emulator: the error code is correct (CustomSchemaCountLimitExceededException) but the message is 'This emulator holds at most 20 custom inventory types per Region' — text that names the emulator, omits AWS's sentence and omits the trailing period.
Why: a message that announces 'this emulator' leaks the emulator into client-visible output and never matches the string operators and log tooling match against; it is also the one place the enforced limit is reported in AWS's wording.
Fix: PutInventory's custom-schema cap path in the ssm handler — render AWS's templated sentence with the enforced limit interpolated instead of emulator-authored prose.
Traces: ssm.put-inventory-custom-schema-limit-exceeded-rejected.

Cause 6 of 7: CreateOpsMetadata is never IAM-authorized — a principal with no ssm:CreateOpsMetadata grant is served the create (or an argument-validation refusal) instead of AccessDeniedException.
AWS: Smithy: CreateOpsMetadata requires ResourceId (OpsMetadataResourceId, @length 1..1024, @pattern ^(?!\s*$).+$) and models OpsMetadataAlreadyExistsException, OpsMetadataInvalidArgumentException, OpsMetadataLimitExceededException and OpsMetadataTooManyUpdatesException; the IAM refusal itself is not modelled, so for the authorization answer: recorded behavior only. A request signed by an assumed role whose policies allow nothing is refused with error code AccessDeniedException and AWS's standard identity-based-denial sentence: fixed text 'User: ' , ' is not authorized to perform: ssm:CreateOpsMetadata on resource: ', ' because no identity-based policy allows the ssm:CreateOpsMetadata action', with the principal (arn:aws:sts::<account>:assumed-role/<role>/<session>) taken from the signing credentials and the resource (arn:aws:ssm:<region>:<account>:opsmetadata/*) from the request's region/account. Authorization precedes argument validation, so even a ResourceId AWS would reject as invalid is answered with AccessDeniedException, and nothing is registered (an admin ListOpsMetadata filtered on that ResourceId stays empty).
Emulator: for a well-formed ResourceId the unauthorized call SUCCEEDS with HTTP 200 and a minted OpsMetadataArn ('arn:aws:ssm:<region>:<account>:opsmetadata/aws/ssm/<resource-id>/opsmetadata'); for a non-ARN-safe ResourceId it is refused with OpsMetadataInvalidArgumentException 'Invalid ResourceId. Specify the ID of an Application Manager application and try again.' — i.e. the validation path is reached because no authorization is evaluated at all.
Why: least-privilege behavior is unverifiable and, worse, inverted: a role deliberately granted nothing can create account-wide Application Manager metadata, and every client/test that asserts the AccessDeniedException (and parses the principal and resource out of its message) sees either a success or the wrong error class. The ordering also matters: a caller probing permissions with a deliberately invalid argument is told about the argument, never about the denial.
Fix: the CreateOpsMetadata handler's authorization step (services/service-com-amazonaws-ssm-amazonssm/src/ops/create_ops_metadata.rs) and the shared SSM IAM evaluation it must call — evaluate the signing principal's identity-based policies for ssm:CreateOpsMetadata on arn:aws:ssm:<region>:<account>:opsmetadata/* BEFORE argument validation and before any state is written, and render AWS's denial sentence.
Traces: ssm.ops-metadata-create-duplicate-rejected, ssm.ops-metadata-invalid-argument-rejected.

Cause 7 of 7: CreateCloudConnector accepts a fabricated Azure tenant/application and answers 200, instead of refusing the connector at the cross-cloud credential/federation gate.
AWS: Smithy: CreateCloudConnector requires DisplayName, RoleArn (@pattern ^arn:aws[a-z0-9-]*:iam::\d{12}:role\/[\w-\/.@+=,]{1,1017}$), Configuration and ConfigConnectorArn; its modelled errors (ConflictException, ServiceQuotaExceededException, InternalServerError) do NOT include the refusal AWS actually sends, so: recorded behavior only. Once the RoleArn resolves to a real role that trusts ssm and carries permissions (the nonexistent-role gate, which the emulator now passes, answers ValidationException 'Nonexistent role or missing ssm service principal in trust policy: <RoleArn>'), AWS still refuses a Configuration whose AzureConfiguration names a tenant/application that does not exist, with error code ValidationException and — according to the account's outbound federation setting — exactly one of two fixed sentences, with no variable parts: 'Unable to create Azure credentials. Please verify the Azure tenant ID, application ID, and federated identity credential configuration are correct.' (federation enabled) or 'Outbound web identity federation is disabled for this AWS account. Enable it to use cross-cloud authentication with Azure.' (federation disabled). A refused create leaves no connector: ListCloudConnectors never shows the DisplayName.
Emulator: HTTP 200 with a freshly minted CloudConnectorId for an AzureConfiguration built from placeholder uuids (all-1s TenantId, all-2s ApplicationId, all-3s subscription) — the Azure credential/federation gate is never reached, so the connector is created and listed.
Why: a cross-cloud connector that can never authenticate to Azure is reported healthy, so the operator discovers the broken wiring only when cross-cloud data never arrives; the two sentences above are the only diagnostics distinguishing 'your Azure tenant/app is wrong' from 'this account has outbound federation switched off', and both are unreachable.
Fix: the CreateCloudConnector handler's validation chain in the ssm service — after the RoleArn/trust-policy gate, evaluate the account's outbound web-identity-federation setting and the AzureConfiguration's tenant/application before any connector state is written, and refuse with ValidationException carrying the matching sentence.
Related but not covering: open issue 20261113T190530Z-ssm-6-net-new-causes-cloudconnector-delete-validate.md covers the earlier gates of the same operation (cause 3: nonexistent RoleArn; cause 4: the sts:GetWebIdentityToken sentence) but carries different check ids and neither Azure-tenant sentence; the gate described here is the one reached AFTER those, so fixing it does not close this check. Note: this check is tagged 'sweep:never' in the suite because a full pass needs a run-owned Azure application; the assertion that fails here is nonetheless about the emulator's own response — it answered 200 where the recording is a refusal.
Traces: ssm.cloud-connector-full-lifecycle.
