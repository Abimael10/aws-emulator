# apigatewayv2__cognito-idp__lambda: a route behind a JWT authorizer refuses a freshly minted access token from the configured user pool and client with 401 Unauthorized, so no JWT leg (claims, scopes, audience/issuer, expiry) is ever observable

> _Note: this issue was identified against the code base at commit `af00353512b8f96b4224cdf0a6e66e42785b9365`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
CreateAuthorizer

## Description
One net-new root cause covering all four failing JWT-authorizer checks of this service grouping.

Cause 1 of 1: an HTTP API route whose AuthorizationType is JWT never admits a valid token issued by the user pool and app client named in the authorizer's JwtConfiguration — every request is refused HTTP 401 with body {"message":"Unauthorized"} and the integration is never invoked. Failing checks: apigatewayv2__cognito-idp__lambda.jwt-authorizer-expired-token-rejected-never-reaches-lambda, apigatewayv2__cognito-idp__lambda.http-api-jwt-authorizer-rejects-foreign-issuer-and-audience, apigatewayv2__cognito-idp__lambda.jwt-authorizer-claims-reach-the-lambda-event, apigatewayv2__cognito-idp__lambda.http-api-jwt-authorization-scope-mismatch-not-delivered.
AWS: Smithy (services/service-com-amazonaws-apigatewayv2-apigatewayv2): CreateAuthorizer — POST /v2/apis/{ApiId}/authorizers, 201; AuthorizerType=JWT with IdentitySource ['$request.header.Authorization'] and JwtConfiguration : JWTConfiguration, whose Issuer is documented as 'The base domain of the identity provider that issues JSON Web Tokens. For example, an Amazon Cognito user pool has the following format: https://cognito-idp.{region}.amazonaws.com/{userPoolId}' and whose Audience is documented as 'A list of the intended recipients of the JWT. A valid JWT must provide an aud that matches at least one entry in this list' (RFC 7519 §4.1.3; for a Cognito ACCESS token the matching claim is client_id). CreateRoute carries AuthorizationType=JWT, AuthorizerId and optional AuthorizationScopes. The data-plane rule is documented plus recorded behavior: API Gateway fetches the issuer's OIDC/JWKS material, verifies the token's signature, iss, aud/client_id and exp, and on success invokes the integration with requestContext.authorizer.jwt.claims (and .scopes) populated — the response is then the integration's own (HTTP 200 with its body). It refuses with HTTP 401 and body {"message":"Unauthorized"} only for a token that is missing, malformed, expired, or whose iss/aud does not match the authorizer, and with HTTP 403 {"message":"Forbidden"} when the token is valid but lacks a required AuthorizationScopes entry. 'Unauthorized' and 'Forbidden' are the fixed message texts; there are no variable parts.
Emulator: a token obtained from the SAME emulator's cognito-idp AdminInitiateAuth (ADMIN_USER_PASSWORD_AUTH) for the pool and app client the authorizer names, presented seconds after minting as 'Authorization: Bearer <token>' on the guarded route, is refused HTTP 401 with body {"message":"Unauthorized"} for the whole polling budget: 'GET /expiry with a freshly minted, still-valid token (https://<host>/_aws/execute-api/<api-id>/expiry) never reached an accepted status within 180.0s. Last: 401 \'{"message":"Unauthorized"}\''. The other three checks poll the same positive-control leg and are killed at the suite budget instead of reaching a verdict ('GET /guarded with a token from the configured pool and client (...): the run budget ended first; not graded'; 'Check timed out after 60.0s'). CreateAuthorizer itself succeeds, so the divergence is in the data-plane verification, not the control plane. Hypothesis: the pool's OIDC discovery/JWKS document is not served (or not consulted) for an issuer that points at the emulator's own cognito-idp endpoint, so every token fails verification.
Why: a client gets 401 Unauthorized for a request AWS serves 200, and the refusal is indistinguishable from a genuinely bad token — the authorizer is 'fail closed' for everything. Nothing behind a Cognito JWT authorizer can be exercised on the emulator: handlers never see requestContext.authorizer.jwt.claims, the scope-mismatch 403 and the expired-token 401 can never be told apart from the always-401, and an estate whose entire API surface is JWT-guarded is unusable.
Fix: the JWT authorizer path of the apigatewayv2 execute-api HTTP data-plane handler — resolve JwtConfiguration.Issuer, fetch/verify against the issuing pool's signing keys, check iss, aud/client_id and exp, then invoke the integration and populate requestContext.authorizer.jwt.claims/.scopes — together with the cognito-idp side that must publish the pool's OIDC discovery and JWKS material for an issuer URL on the emulator's own host, and the AuthorizationScopes gate that must answer 403 {"message":"Forbidden"} rather than 401.
