# ListSchemas AWS-managed catalogue entries report a placeholder LastModified, and the seeded entry set still differs from the published catalogue (2 causes)

> _Note: this issue was identified against the code base at commit `3908104fc3618d25db548802831d02456e41bcc4`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
ListSchemas

## Description
Paging the service-owned (AWS-managed) registry with ListSchemas answers 200, but the `Schemas` list does not match the catalogue AWS publishes. All 51 net-new divergence clusters on fixture `schemas-catalog-list-schemas` (214 mismatched steps of 289 replayed, score 26.0%) are instances of the TWO causes below. Both live in the catalogue SEED data, not in the ListSchemas handler, its pagination codec or the serializer, so they are filed together.

This is NOT any open schemas issue: `20261118T060835Z-schemas-response-payload-framing-still-diverges-from-aws.md` is about the GetCodeBindingSource archive size and the TagResource 204 framing, `20261029T203553Z-schemas-empty-body-204-responses-omit-the-content-length.md` about Content-Length on 204s, `20261121T082019Z-schemas-aws-managed-cloudtrail-catalogue-document-is-emulator.md` about the `Content` document DescribeSchema/ExportSchema serve, and `20261022T034503Z-schemas-tagresource-stub.md` about a stub. None of them changes which entries ListSchemas lists or what `LastModified` it reports. The resolved issues `20261030T050932Z-schemas-listschemas-serves-a-fabricated-aws-managed-catalogue-digest.md` and `20261110T235024Z-schemas-listschemas-omits-aws-managed-schemas-from-the.md` are closed and cover nothing: the digest-derived `LastModified` they describe is gone, replaced by the single constant below, and the entry set is still wrong in the two directions described in Cause 2.

Cause 1 of 2: every catalogue entry reports one hardcoded placeholder `LastModified` instead of the instant the catalogue published it.
AWS: Smithy: `ListSchemas` -> output member `Schemas` targets `__listOfSchemaSummary`; `SchemaSummary.LastModified` targets `__timestampIso8601` with `@timestampFormat("date-time")` and is documented "The date and time that schema was modified." The model does not state the value, so this is recorded behavior only: the recording shows an entry's instant is a property of the PUBLICATION that wrote it — entries published together report the SAME whole-second `date-time`, the bulk of the catalogue reports instants drawn from one narrow publication window, and a handful of named entries report their own, older publication instant (e.g. `<source>@AWSAPICallViaCloudTrail` entries at `2019-12-01T00:59:xxZ`, `aws.tag@TagChangeOnResource` at `2022-03-24T16:40:20Z`, `aws.health@AWSHealthEvent` in a `2026-03-12T21:12:2xZ` pass). The value is identical on every request; it is catalogue data, not a clock read.
Emulator: every entry whose name is not listed in the service's own `MANAGED_PUBLICATIONS` seed table reports the single constant `CATALOGUE_PUBLICATION_INSTANT` = `2019-12-01T00:00:00Z`. Replay shows, for an identically named entry, the recorded publication instant against `2019-12-01T00:00:00Z` for essentially every entry of every page: clusters at `task#1`, `task#2`, `task#3`, `task#4`, `task#5`, `task#6`, `task#10`, `task#14`, `task#64`, `task#88`, `task#101`, `task#106`, `task#130` ... `task#206`.
Why: `LastModified` is the field a client compares against its cached copy of a schema to decide whether to re-fetch, and the field "changed since" filtering, cache invalidation and any ordering or reporting by modification time read. Against the emulator the whole catalogue looks like it was written at one instant years before the entries were published, and distinct publications are indistinguishable, so a client never re-fetches a schema that did change and sees modification times that bear no relation to the ones the same call returns against AWS.
Fix: the AWS-managed catalogue seed in the schemas service's state module — `managed_last_modified` and the data it reads (`MANAGED_PUBLICATIONS` / `CATALOGUE_PUBLICATION_INSTANT`). The catch-all constant must go: the instant of the publication that wrote the bulk of the catalogue has to be seeded from the published catalogue (entries published together sharing one instant), not defaulted to the registry's launch date. Nothing in the ListSchemas handler, the NextToken codec or the timestamp serializer needs to change — the format on the wire is already correct `date-time`.
Traces: `schemas-catalog-list-schemas#task#1` (representative), `#task#2`, `#task#3`, `#task#4`, `#task#5`, `#task#6`, `#task#10`, `#task#14`, `#task#64`, `#task#88`, `#task#101`, `#task#106`, `#task#130`, `#task#206`.

Cause 2 of 2: the seeded entry SET is not the published one — it omits the legacy case-variant entries AWS publishes for some sources and carries extra entries ahead of other sources — so pages carry the wrong entries and every later page boundary moves.
AWS: recorded behavior only (`ListSchemas` is `@paginated` with `inputToken=NextToken`, `outputToken=NextToken`, `items=Schemas`, `pageSize=Limit`; the registry's entry set is service data the model does not describe). Entries come back in schema-name order, so the entry set fixes both each page's contents and where each page ends. The recording shows the catalogue publishes, for some sources, a legacy capital-V `<source>@AWSAPICallViaCloudTrail` entry that sorts immediately AHEAD of the ordinary `<source>@AWSAPICallviaCloudTrail` one and carries its own historical instant — `aws.ec2@AWSAPICallViaCloudTrail` (`2019-12-01T00:59:39Z`), `aws.ecs@AWSAPICallViaCloudTrail` (`2019-12-01T00:59:47Z`), `aws.sagemaker@AWSAPICallViaCloudTrail`.
Emulator: it does not publish those entries, so each affected source's block starts one entry early and the walk runs ahead of the recording (`task#70`: `$.Schemas[0]` expected `aws.ec2@AWSAPICallViaCloudTrail`, got `aws.ec2@AWSAPICallviaCloudTrail`, and every later index on the page is shifted by one; same at `task#75` for `aws.ecs` and at `task#168`, where the page should already be in `aws.sagemaker-geospatial@*` but is still emitting `aws.sagemaker@*`). In the other direction the emulator's catalogue carries entries the recording has no room for at that point, so the walk LAGS: at `task#32` the page should have moved on to `aws.autoscaling@*` but is still emitting `aws.autoscaling-plans@*`, and at `task#203` it should have reached `aws.tag@InvalidEffectiveTagPolicy` but is still emitting `aws.tag@AWSAPICallviaCloudTrail` .. `aws.tag@AWSServiceEventviaCloudTrail`. Because every insertion or omission shifts all following pages, the damage is not confined to the affected sources.
Why: a client enumerating the AWS-managed registry gets a schema list that is not the published one — entries AWS publishes are missing, entries it does not publish appear, and a `NextToken` walk visits a different sequence of pages than against AWS, so a paged crawl can both see an entry twice and skip a real one, and code generated or validated from the enumeration is built against the wrong schema list.
Fix: the AWS-managed catalogue seed data in the schemas service's state module — the per-source published-event seed the catalogue entries are built from (and the `MANAGED_PUBLICATIONS` names that must agree with it). The legacy `AWSAPICallViaCloudTrail` entry has to be seeded for exactly the sources that publish one, and the per-source generic CloudTrail/ServiceEvent set seeded per source rather than fanned out, so the entry set — and therefore the page boundaries — matches the published catalogue. The pagination codec is not implicated: the tokens resume correctly, they just resume a different catalogue.
Traces: `schemas-catalog-list-schemas#task#70` (cause representative), `#task#75`, `#task#168`, `#task#32`, `#task#203`.
