# athena: 5 net-new causes — CTAS StatementType is DML not DDL, INSERT INTO a CTAS table fails with SQLite 'no such table', DataScannedInBytes ignores columnar projection and partition projection, and a DATA_MANIFEST result carries a 'path' ColumnInfo

> _Note: this issue was identified against the code base at commit `ea39dba1da951c7945754830175526ec44cfb5ae`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
StartQueryExecution

## Description
Five net-new root causes in the Athena data plane, all reached through StartQueryExecution / GetQueryExecution / GetQueryResults against external and CTAS-materialised tables over S3. None of the six failing checks below was marked OWNED or ALREADY FILED by the replay report. Open issues that describe the same engine but do NOT carry these checks' replay keys (named here only for context, they do not cover these causes): 20261104T163600Z-athena-statements-are-executed-by-a-sqlite-engine.md, 20261111T090701Z-athena-s-sql-engine-refuses-trino-hive-statements.md, 20261121T213708Z-athena-2-net-new-causes-an-integer-varchar.md, 20261115T222915Z-athena-query-execution-and-result-reads-diverge-columninfo.md. In this replay the Hive DDL and the CTAS `CREATE TABLE ... WITH (...) AS SELECT` forms those issues describe now SUCCEED, so the divergences below are the ones the same checks reach next.

Cause 1 of 5: a CTAS execution reports StatementType DML where AWS reports DDL.
AWS: `CREATE TABLE <db>.<tbl> WITH (format='PARQUET', external_location='s3://<bucket>/<prefix>/') AS SELECT ...` settles SUCCEEDED and GetQueryExecution reports QueryExecution.StatementType = 'DDL' — a CREATE TABLE statement is classified by its DDL form even though it materialises data through the embedded SELECT (Smithy: QueryExecution.StatementType, enum StatementType DDL/DML/UTILITY; note the model's prose on that member lists `CREATE TABLE AS SELECT` under DML, while the recorded AWS behavior this check encodes is DDL — recorded behavior governs: the check comment states it is measured real-AWS behavior).
Emulator: StatementType = 'DML' for the same CTAS. The surrounding legs pass — the execution reaches SUCCEEDED and the table is queryable — so the classification is the sole divergence.
Why: a client that branches on StatementType (query-history UIs, cost/lineage tools, JDBC drivers that only fetch a ResultSet for DML) treats a CTAS as a data-manipulation statement, fetches results that do not exist, and mis-attributes the statement in query history.
Fix: the statement-classification step of the Athena query-execution engine that populates QueryExecution.StatementType in the StartQueryExecution/GetQueryExecution path — CREATE TABLE AS SELECT must classify as DDL.
Traces: athena.ctas-creates-queryable-table.

Cause 2 of 5: INSERT INTO a table the engine itself created by CTAS fails with the SQLite diagnostic 'no such table: <db>.<tbl>' instead of appending rows.
AWS: `INSERT INTO "<db>"."<tbl>" VALUES (...), (...)` and `INSERT INTO "<db>"."<dest>" SELECT <cols> FROM "<db>"."<src>" GROUP BY ... ORDER BY ...` against an Athena-managed table created by a preceding CTAS settle SUCCEEDED with StatementType 'DML' (Smithy: QueryExecutionStatus.State enum QUEUED/RUNNING/SUCCEEDED/FAILED/CANCELLED; QueryExecution.StatementType). Each statement appends one new data object under the table's location without replacing earlier ones, and a later SELECT returns the union of the inserted rows.
Emulator: the execution settles FAILED with Status.StateChangeReason `no such table: <database>.<table>` — SQLite's own missing-table text, whose fixed part is `no such table: ` followed by the dotted name taken from the statement. The table demonstrably exists: in athena.group-by-aggregation-matches-independently-computed-values the immediately preceding `SELECT category, total FROM "<db>"."<dest>" ORDER BY category` over the same CTAS-created table SUCCEEDED and returned the expected rows, and in athena.insert-into-appends-rows-visible-to-subsequent-select the CTAS that created the target SUCCEEDED. So only the INSERT path fails to resolve the qualified name — it looks the name up as a single literal identifier rather than database+table the way the SELECT path does. Separately, AWS's wording for a genuinely absent table is Athena's `line <l>:<c>: Table '<catalog>.<database>.<table>' does not exist`, never SQLite text.
Why: INSERT INTO is the documented way to append to an Athena-managed table; a client cannot load data at all, and the failure names the table it just created as nonexistent, which sends the operator looking for a catalog problem that does not exist. Every downstream read of the appended rows and every UpdateCount assertion fails with it.
Fix: qualified-name resolution in the INSERT path of the Athena query-execution engine's SQL layer (services/service-com-amazonaws-athena-amazonathena, the statement translation/execution component behind StartQueryExecution), plus the append side effect that writes one new data object per INSERT; and the failure path must emit Athena's diagnostic rather than the embedded engine's `no such table:` text.
Traces: athena.insert-into-appends-rows-visible-to-subsequent-select, athena.group-by-aggregation-matches-independently-computed-values.

Cause 3 of 5: DataScannedInBytes for a columnar (Parquet) table reports the whole object size, so no column projection is accounted for.
AWS: for a query over a Parquet table, QueryExecution.Statistics.DataScannedInBytes is 'the number of bytes in the data that was queried' (Smithy: QueryExecutionStatistics.DataScannedInBytes, long). Reading one column of a multi-column Parquet object therefore reports strictly fewer bytes than the object holds, reading two columns reports the sum of the two single-column reads, and `count(*)` — answerable from the file footer's row count — reports 0. Recorded behavior only for the exact per-column byte figures, which depend on the writer's encoding.
Emulator: `SELECT sum(n) FROM <parquet table>` reports DataScannedInBytes equal to the full size of the Parquet object (the replay: the 12862-byte object reported DataScannedInBytes=12862, where the projected column carries about 1/100 of each row's bytes). The statistic is the size of the objects under the table location, independent of which columns the statement projects.
Why: DataScannedInBytes is the number clients bill, budget and alarm on, and it is the only signal that a columnar layout is paying off; a client sees a Parquet table cost exactly as much as the row-format source, so cost estimates and workgroup BytesScannedCutoffPerQuery thresholds are wrong by two orders of magnitude, and no client can verify that projection pushdown happens.
Fix: the scan accounting in the Athena query-execution engine — column-chunk level byte accounting for columnar formats, fed into the Statistics.DataScannedInBytes the GetQueryExecution response reports.
Traces: athena.columnar-projection-reads-a-fraction-of-the-row-format-bytes.

Cause 4 of 5: a predicate on a projected partition key does not bound the scan — DataScannedInBytes covers every partition prefix under the table location, including one outside the declared projection range.
AWS: for a table declared with partition projection (TBLPROPERTIES 'projection.enabled'='true', 'projection.<key>.type'='date', 'projection.<key>.range'='<from>,<to>', 'projection.<key>.format'='yyyy-MM-dd'), Athena computes partitions from the properties alone and reads only the prefixes the predicate and the declared range select. `SELECT id FROM <tbl> WHERE dt = '<in-range date>'` therefore reports Statistics.DataScannedInBytes equal to the bytes of that one partition prefix; an unpredicated scan reports the sum of the in-range prefixes only; a predicate on a date outside the declared range returns zero rows and scans 0 bytes even though an object exists under that prefix (Smithy: QueryExecutionStatistics.DataScannedInBytes; the projection semantics are Athena's documented partition-projection rule — recorded behavior for the byte totals).
Emulator: the predicated query returns the right rows but reports DataScannedInBytes equal to the total size of ALL partition prefixes under the location (the replay: 18 bytes, the sum of the three objects of 4, 6 and 8 bytes, where only the 4-byte dt=<first date> prefix is selected). Nothing prunes: the out-of-range prefix the projection excludes is counted too, so the partition predicate and the declared range have no effect on what is read.
Why: partition projection exists to bound scans on high-cardinality partitioned tables; a client gets no pruning, pays for and times out on the whole table, and cannot rely on the declared range to exclude objects that are physically present but not partitions — the per-partition and whole-table byte counts become indistinguishable.
Fix: partition enumeration/pruning in the Athena query-execution engine's scan planner (honour the projection TBLPROPERTIES and the partition predicate when selecting prefixes) and the byte accounting that feeds Statistics.DataScannedInBytes.
Traces: athena.partition-projection-bounds-the-scan-with-no-metastore-partitions.

Cause 5 of 5: GetQueryResults with QueryResultType=DATA_MANIFEST returns a fabricated 'path' column in ResultSetMetadata.ColumnInfo where AWS returns none.
AWS: GetQueryResults(QueryExecutionId=<an UNLOAD/CTAS/INSERT execution>, QueryResultType='DATA_MANIFEST') returns the manifest listing — one Row per object written — and ResultSet.ResultSetMetadata.ColumnInfo EMPTY, because a manifest listing is not tabular query output (Smithy: QueryResultType enum DATA_MANIFEST/DATA_ROWS; ResultSetMetadata.ColumnInfo list; recorded behavior for the empty list).
Emulator: ColumnInfo carries one synthesised entry describing a column named `path` — {CatalogName: 'hive', SchemaName: '', TableName: '', Name: 'path', Label: 'path', Type: 'string', Precision: 0, Scale: 0, Nullable: 'UNKNOWN', CaseSensitive: false} — i.e. the manifest listing is serialised through the same tabular-metadata path as a SELECT result.
Why: a client that drives its result decoding off ColumnInfo (the JDBC/ODBC drivers and the console do) sees a one-column result set that AWS never describes, so it binds the manifest rows to a column that does not exist and cannot distinguish a manifest response from tabular data.
Fix: the GetQueryResults handler/serializer for the DATA_MANIFEST branch in services/service-com-amazonaws-athena-amazonathena — the manifest branch must emit ResultSetMetadata with an empty ColumnInfo list instead of reusing the tabular column-metadata builder.
Traces: athena.get-query-results-data-manifest-type-unload-vs-select.

## Evidence
Replay of suite simparity-behavioral-aws-v1 against the emulator built from this checkout. Overall 354/443 (79.9%); service athena 252/329 (77%). Every other athena failure in this replay was marked OWNED by an open issue or ALREADY FILED against an unimplemented stub; the six checks below were not.

Cause 1 — athena.ctas-creates-queryable-table. After `CREATE DATABASE <db> LOCATION 's3://<bucket>/db/'` (SUCCEEDED), the statement `CREATE TABLE <db>.<tbl> WITH (format='PARQUET', external_location='s3://<bucket>/ctas/<tbl>/') AS SELECT 42 AS num, 'hello' AS txt` reached SUCCEEDED. Expected GetQueryExecution QueryExecution.StatementType == 'DDL'; actual 'DML'. Suite assertion: `assert ctas_exec["StatementType"] == "DDL"` -> `AssertionError: DML`.

Cause 2 — athena.insert-into-appends-rows-visible-to-subsequent-select. Setup: `CREATE DATABASE \`<db>\``, `CREATE EXTERNAL TABLE \`<db>\`.\`<src>\` (...) ROW FORMAT DELIMITED FIELDS TERMINATED BY ',' STORED AS TEXTFILE LOCATION 's3://<data>/src/'`, then `CREATE TABLE "<db>"."<tbl>" WITH (format='PARQUET', external_location='s3://<data>/inserted/') AS SELECT id, name FROM "<db>"."<src>" WHERE 1 = 0` — all SUCCEEDED, and the zero-row CTAS correctly wrote no data object. The next statement `INSERT INTO "<db>"."<tbl>" VALUES (1, 'alpha-<marker>'), (2, 'bravo-<marker>')` (QueryExecutionContext.Database=<db>) reached FAILED: `statement reached FAILED, expected SUCCEEDED ... -- no such table: <db>.<tbl>`.
athena.group-by-aggregation-matches-independently-computed-values: the GROUP BY aggregate, its DataScannedInBytes, its ColumnInfo types, the HAVING leg, the CTAS `CREATE TABLE "<db>"."<dest>" WITH (format='TEXTFILE', external_location='s3://<data>/dest/') AS SELECT category, sum(amount) AS total ... HAVING ...` AND the following `SELECT category, total FROM "<db>"."<dest>" ORDER BY category` all passed; then `INSERT INTO "<db>"."<dest>" SELECT category, sum(amount) AS total FROM "<db>"."<src>" GROUP BY category ORDER BY category` reached FAILED with `no such table: <db>.<dest>` — the same table the preceding SELECT had just read.

Cause 3 — athena.columnar-projection-reads-a-fraction-of-the-row-format-bytes. 4000 rows of one narrow bigint `n` and one 200-char `pad` string; the TEXTFILE baseline `SELECT sum(n)` correctly reported DataScannedInBytes == the uploaded object size; the CTAS to PARQUET wrote a 12862-byte object. Expected `0 < DataScannedInBytes < 12862` for `SELECT sum(n) FROM "<db>"."<parquet tbl>"`; actual: `AssertionError: projecting \`n\` must read some but NOT all of the 12862-byte Parquet object, got DataScannedInBytes=12862`. The later legs of the same check (additivity of per-column reads, and count(*) scanning 0 bytes) are unreachable behind it.

Cause 4 — athena.partition-projection-bounds-the-scan-with-no-metastore-partitions. Three prefixes `proj/dt=2024-01-01/rows.csv` (4 bytes), `proj/dt=2024-01-02/rows.csv` (6 bytes) and `proj/dt=2024-01-09/rows.csv` (8 bytes) under a table declared with 'projection.enabled'='true', 'projection.dt.type'='date', 'projection.dt.range'='2024-01-01,2024-01-02', 'projection.dt.format'='yyyy-MM-dd'. SHOW PARTITIONS correctly returned nothing and `SELECT id FROM "<db>"."<tbl>" WHERE dt = '2024-01-01' ORDER BY id` returned exactly that prefix's rows. Expected DataScannedInBytes == 4; actual: `AssertionError: the projected predicate must read exactly the 4 bytes of dt=2024-01-01/rows.csv, got DataScannedInBytes=18 (sizes {'2024-01-01': 4, '2024-01-02': 6, '2024-01-09': 8})` — 18 = 4+6+8, i.e. every prefix including the out-of-range one.

Cause 5 — athena.get-query-results-data-manifest-type-unload-vs-select. `UNLOAD (SELECT 1 AS col) TO 's3://<bucket>/unloaded/' WITH (format='JSON')` reached SUCCEEDED and GetQueryResults(QueryResultType='DATA_MANIFEST') returned exactly one Row. Expected ResultSet.ResultSetMetadata.ColumnInfo == []; actual `[{'CatalogName': 'hive', 'SchemaName': '', 'TableName': '', 'Name': 'path', 'Label': 'path', 'Type': 'string', 'Precision': 0, 'Scale': 0, 'Nullable': 'UNKNOWN', 'CaseSensitive': False}]`. The later legs of the check (the manifest URI pointing at a real object, DATA_ROWS staying empty, and the InvalidRequestException `Manifest files are only available for INSERT, CTAS (CREATE TABLE AS SELECT), and UNLOAD queries. query <id> does not generate a manifest file.` for DATA_MANIFEST on a plain SELECT) are unreachable behind it.
