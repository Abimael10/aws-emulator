# ecr__eks__logs: 2 net-new root causes in the served cluster Kubernetes API — the core/v1 events collection is answered 405 MethodNotAllowed, and a pod admitted onto a Fargate profile never leaves Pending

> _Note: this issue was identified against the code base at commit `22429b7a0c0ae7d0c87a7901239a937fd78a2091`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
DescribeCluster

## Description
Two independent defects in the Kubernetes API the emulator serves for an EKS cluster. Both were reached on a cluster that answered: CreateCluster/CreateFargateProfile/CreateNodegroup succeeded, the published endpoint was reachable, the namespace and the aws-logging ConfigMap were accepted and the Pod objects were created and read back — so neither cause is an unreachable-endpoint or an unloadable-CA case. Each cause below is a separate defect and must be closed separately; its failing check ids are listed with it. 2 causes in total.

Cause 1 of 2: listing core/v1 Events in a namespace is refused 405 MethodNotAllowed.
AWS: recorded behavior only — the cluster's Kubernetes API server is not part of the EKS Smithy model (smithy_query on com.amazonaws.eks#AWSWesleyFrontend models only DescribeCluster -> Cluster.endpoint / Cluster.certificateAuthority; it says nothing about the data plane). A real EKS cluster serves GET /api/v1/namespaces/<namespace>/events (list), including the fieldSelector form involvedObject.name=<pod name>, and answers HTTP 200 with a core/v1 EventList; events is advertised in the /api/v1 discovery document. The kubelet records the image-pull lifecycle of every pod there: a reason "Pulling"/"Pulled" Event whose message has the fixed shape 'Successfully pulled image "<image>"' (the image reference is the value from the pod's container spec), and reason "Failed"/"BackOff" Events on a failed pull. A 405 with the fixed message shape 'the server does not allow <VERB> on <path>' is correct only for a verb a collection genuinely does not support, and list is always supported on events.
Emulator: GET /api/v1/namespaces/default/events?fieldSelector=involvedObject.name=<pod> is answered HTTP 405 with {"kind":"Status","apiVersion":"v1","metadata":{},"status":"Failure","message":"the server does not allow GET on /api/v1/namespaces/default/events","reason":"MethodNotAllowed","details":null,"code":405} — in that message only the verb (GET) and the path are request-derived; the rest is fixed text. The typed client raises kubernetes.client.exceptions.ApiException: (405) Reason: Method Not Allowed. The collection is therefore registered for writes/other verbs only, never for list, so no event can ever be read for any object.
Why: a client relying on AWS's behavior learns everything about asynchronous workload progress from Events — `kubectl describe pod`, `kubectl get events`, every operator and every CI gate that waits for "Pulled" or detects ImagePullBackOff. A 405 says the verb is permanently unsupported for that resource, which is non-retryable, so the client aborts instead of polling; image-pull behavior (a node role, a Fargate pod execution role, or IRSA pulling a private ECR image, and the denial case when ecr:BatchGetImage/GetDownloadUrlForLayer is missing) is unobservable.
Fix: the core/v1 Event collection handler and the /api/v1 discovery document of the served cluster Kubernetes API — it must route list (GET) on events, honour the fieldSelector involvedObject.* predicates, and the pod lifecycle must record the Pulling/Pulled/Failed/BackOff Events a kubelet records.
Traces: ecr__eks__logs.eks-fargate-execution-role-pulls-ecr-image, ecr__eks__logs.eks-irsa-role-pulls-ecr-image-without-imagepullsecret, ecr__eks__logs.eks-nodegroup-pulls-private-ecr-image, ecr__eks__logs.eks-pod-image-pull-fails-without-ecr-permission-rejected.

Cause 2 of 2: a pod created in a namespace selected by an ACTIVE Fargate profile stays in phase Pending forever.
AWS: recorded behavior only. On a real cluster with an ACTIVE Fargate profile whose selector matches the pod's namespace, the pod is admitted, scheduled onto Fargate capacity and its status.phase moves Pending -> Running (and -> Succeeded for a short-lived command), with status.containerStatuses populated; this takes tens of seconds, not an unbounded time. Fargate pod log routing (the aws-logging ConfigMap in the aws-observability namespace) only ever delivers once the pod runs.
Emulator: the pod object is created, but every subsequent GET /api/v1/namespaces/default/pods/<name> keeps reporting status.phase "Pending" for the whole polling window the check is given (the check's own wait is 420 s), so the wait never observes Running or Succeeded and the check ends in its budget-bounded timeout ("pod <name> leaving Pending"). No workload ever runs, so nothing is ever written to the configured CloudWatch Logs group either, which also makes the negative control vacuous — the "no delivery without logs permission" assertion passes for the wrong reason.
Why: a client relying on AWS's behavior waits for its pod to become Running before doing anything else (reading logs, probing the service, declaring a deployment healthy). A pod pinned in Pending makes every such wait hit its own timeout, and it makes the Fargate logging contract untestable: both an allowed and a denied pod execution role produce exactly the same observation (nothing).
Fix: the Fargate scheduling/pod status state machine of the served cluster Kubernetes API (the component that should admit a pod matched by an ACTIVE Fargate profile's selector and advance its status.phase and containerStatuses), together with the pod log router that feeds the aws-logging ConfigMap's destination log group.
Traces: ecr__eks__logs.eks-fargate-pod-logs-delivered-to-cloudwatch (explicit "pod <name> leaving Pending" timeout), ecr__eks__logs.eks-fargate-logging-without-execution-role-permission-no-delivery (same flow, cut at the harness timeout before the 420 s pod-phase wait could complete).

## Evidence
Cause 1 (4 checks, identical failure): kubernetes.client.exceptions.ApiException: (405) Reason: Method Not Allowed; HTTP response body {"kind":"Status","apiVersion":"v1","metadata":{},"status":"Failure","message":"the server does not allow GET on /api/v1/namespaces/default/events","reason":"MethodNotAllowed","details":null,"code":405}, raised from core_v1.list_namespaced_event(namespace, field_selector="involvedObject.name=<pod>"). Expected HTTP 200 and a core/v1 EventList containing, once the image is pulled, an Event with reason "Pulled" and message 'Successfully pulled image "<repositoryUri>:<tag>"' (the image reference is request-derived; the rest of the sentence is fixed kubelet text). Cause 2: TimeoutError: pod <pod name> leaving Pending — _wait_pod_phase(..., lambda p: p in {"Running","Succeeded"}, timeout_s=420) never observed a phase other than "Pending" for a pod in the default namespace matched by an ACTIVE Fargate profile selector, and the destination log group received no event carrying the pod's marker; expected status.phase Running (or Succeeded) and the marker delivered to the log group named by the aws-logging ConfigMap's cloudwatch_logs OUTPUT.

## Resolution
A cluster now runs the pods its Fargate profiles select on the capacity those profiles provide: an ACTIVE profile whose selector names a pod's namespace (and every label it names) makes the cluster provision one node for that pod, register it under the profile's Pod execution role, bind the pod to it and take that capacity away again once no pod needs it. The kubelet of whatever capacity took a pod pulls the pod's container images as THAT capacity's IAM role and records the pull lifecycle as Events of the pod's namespace, so the `Pulling`/`Pulled` and `Failed`/`BackOff` Events of a Fargate pod are there to be listed (the collection itself, its `fieldSelector` and the `/api/v1` row were already served). The pod reports `PodScheduled` true, the node it was placed on, its `startTime` and its container statuses, and it leaves `Pending`. Pinned by `services/service-com-amazonaws-eks-awswesleyfrontend/tests/all/kubernetes_fargate_scheduling.rs` and `core/router/tests/all/eks_fargate_pod_execution_role_pulls.rs`.

What the phase `Running` and the Fargate log route ask for is RUNNING the container image, which a generated emulator has no runtime for (`vendor/engine/src/lib.rs`: "Containers and external processes are not available to a generated emulator yet"), so no status and no log event is reported for a container nothing ran: a pod of this emulator ends in the phase Kubernetes reports for containers that terminated without running, naming that condition. The two Fargate logging checks wait for `Running`/`Succeeded` and so still end in their own timeout; `eks-irsa-role-pulls-ecr-image-without-imagepullsecret` now diverges earlier, in STS `AssumeRoleWithWebIdentity` refusing an EKS-issued service-account token, which `20261120T190252Z-ecr-eks-logs-sts-assumerolewithwebidentity-never-accepts-an.md` owns.
