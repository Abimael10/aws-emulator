# lambda__rds__secretsmanager: 2 net-new causes — the Data API's Aurora PostgreSQL engine has no information_schema catalog, and ExecuteStatement never authorizes the caller for secretsmanager:GetSecretValue on secretArn (an ungranted call succeeds)

> _Note: this issue was identified against the code base at commit `8d928d0c08d20b91c4628e31dbb749e55b735770`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
ExecuteStatement

## Description
Two net-new root causes, both grounded in failing checks of the lambda__rds__secretsmanager suite group and both in the RDS Data API (rds-data ExecuteStatement) surface exercised from a deployed Lambda. Neither failing check is marked ALREADY FILED or OWNED in the replay report.

Cause 1 of 2: the SQL engine behind rds-data ExecuteStatement on an Aurora PostgreSQL cluster has no information_schema catalog, so a standard catalog read is refused as a database error.
AWS: Aurora PostgreSQL implements the SQL-standard information_schema, and the Data API is a signed HTTP front door onto that same engine. `SELECT COUNT(*) FROM information_schema.tables WHERE table_name = '<table>'` is answered with HTTP 200 and one record holding a longValue (0 when the table does not exist, 1 when it does). Smithy (com.amazonaws.rdsdata#RdsDataService): ExecuteStatement models DatabaseErrorException (errorKind client, httpError 400) for SQL the engine itself rejects; a read of an existing catalog view is not that case, and information_schema.tables is never a missing relation on PostgreSQL.
Emulator: ExecuteStatement answers the modeled error DatabaseErrorException (HTTP 400) with the message `ERROR: relation "information_schema.tables" does not exist; SQLState: 42P01`. The fixed text is `ERROR: relation "<relation>" does not exist; SQLState: 42P01`; the variable part is the relation named in the request's sql — here the catalog view itself, i.e. the engine exposes no information_schema at all. Observed through a Lambda whose role has BOTH rds-data:ExecuteStatement and secretsmanager:GetSecretValue (the check's positive control), so this is not an authorization effect.
Why: catalog introspection is how clients decide whether to create a schema object, whether a migration already ran, or — as here — whether a refused statement left any effect behind. Against AWS the query returns a count; against the emulator it is a hard 400, so idempotent DDL, migration tools, ORMs that reflect schema, and any "effect absent" verification cannot run at all, and the client is told its own SQL is at fault.
Fix: the SQL dialect/catalog layer backing the rds-data ExecuteStatement (and BatchExecuteStatement) handler — expose the PostgreSQL information_schema views (at minimum tables and columns) over the backing store for aurora-postgresql/postgres clusters. Related but distinct open issues: 20261111T084329Z-rds-five-sql-data-plane-divergences-on-the.md (missing information_schema.processlist on the NATIVE MySQL/MariaDB endpoint — a different engine and surface, and it does not carry this check's replay key) and 20261108T035337Z-rds-rds-data-secretsmanager-5-net-new-causes.md (the Data API and the native endpoint being separate stores).

Cause 2 of 2: ExecuteStatement does not authorize the calling identity for secretsmanager:GetSecretValue on the secret named by secretArn — a caller with no such grant gets a successful 200 and its statement is really executed.
AWS: the Data API retrieves the credentials in secretArn on behalf of the CALLER, so a request needs both rds-data:ExecuteStatement on the cluster and secretsmanager:GetSecretValue on the secret. A principal granted only the former is refused with HTTP 403 and error code AccessDeniedException, and the SQL never runs. Smithy: ExecuteStatement's modeled errors include AccessDeniedException (errorKind client, httpError 403, doc "You don't have sufficient access to perform this action.") and ForbiddenException (client, 403). The message AWS returns for an identity-policy denial has the form `User: arn:aws:sts::<account-id>:assumed-role/<role-name>/<session-name> is not authorized to perform: secretsmanager:GetSecretValue on resource: <secret ARN>` — the fixed text is `User: ... is not authorized to perform: secretsmanager:GetSecretValue on resource: ...`; the principal ARN, session name and secret ARN come from the invoking identity and the request. The check asserts the code, not a literal message.
Emulator: the ungranted call is served successfully — ExecuteStatement answers HTTP 200 with an ExecuteStatementResponse and the handler returns `{'ok': True, ...}`, i.e. the `CREATE TABLE IF NOT EXISTS <table> (id int)` the denied role issued is actually executed against the cluster. The secret leg of the request's precondition chain is never evaluated against the caller's policy, so a role granting only rds-data:ExecuteStatement is indistinguishable from one that also grants secretsmanager:GetSecretValue. Note the sibling leg IS enforced: in the companion check, a role lacking rds-data:ExecuteStatement is correctly refused with AccessDeniedException, so only the Secrets Manager authorization is missing.
Why: least privilege is unenforceable and untestable on the Data API's most security-relevant input. A client cannot verify that a function is confined to the one secret it was granted; a missing secret grant produces no failure in test/CI and a 403 only in production; a negative test that asserts the denial passes silently with a 200; and because the statement runs, the denied caller leaves real side effects (DDL/DML) in the database that AWS would never have applied.
Fix: the authorization leg of the shared rds-data request precondition chain in the ExecuteStatement/BatchExecuteStatement handler — resolve secretArn through Secrets Manager under the invoking principal (evaluating its identity policy, including the statement's Resource, for secretsmanager:GetSecretValue) BEFORE the SQL is executed, and refuse with the modeled AccessDeniedException at HTTP 403 when no statement allows it. Related but distinct open issues: 20261023T045849Z-rds-data-skips-resource-secret-and-transaction-preconditions.md covers the VALIDITY of the retrieved secret (InvalidSecretException/SecretsErrorException), not the caller's permission to read it, and 20261115T213820Z-lambda-rds-secretsmanager-2-net-new-causes-an-2b6510.md covers the RDS awsQuery control plane (DescribeDBInstances); neither carries this check's replay key.
Traces: lambda__rds__secretsmanager.deploy-cfn-missing-secretsmanager-permission-negative.

## Steps to Reproduce

Shared setup (both checks): deploy a CloudFormation stack with an aurora-postgresql DBCluster (ManageMasterUserPassword=true, EnableHttpEndpoint=true) plus a db.serverless instance, and two Lambda functions on two roles — a "denied" role missing exactly one grant and a "control" role granting both `rds-data:ExecuteStatement` on the cluster ARN and `secretsmanager:GetSecretValue` on the cluster's MasterUserSecret.SecretArn. Each handler calls rds-data execute_statement(resourceArn=$CLUSTER_ARN, secretArn=$SECRET_ARN, database='postgres', sql=<event.sql>) and reports ok/errorCode.

Cause 1: Invoke the CONTROL function (both grants) with `SELECT COUNT(*) FROM information_schema.tables WHERE table_name = '<some name>'`. Observe HTTP 400 DatabaseErrorException `ERROR: relation "information_schema.tables" does not exist; SQLState: 42P01` instead of a 200 whose records[0][0].longValue is 0 or 1.

Cause 2: Invoke the DENIED function whose role grants only `rds-data:ExecuteStatement` (no secretsmanager:GetSecretValue) with `CREATE TABLE IF NOT EXISTS <table> (id int)`. Observe a 200 success (`ok: true`) and the table actually created, instead of HTTP 403 AccessDeniedException with no effect. Then grant secretsmanager:GetSecretValue on the secret and invoke again — the outcome is identical, showing the grant is never consulted. For contrast, the companion check's denied role (which lacks rds-data:ExecuteStatement instead) IS correctly refused with AccessDeniedException.
