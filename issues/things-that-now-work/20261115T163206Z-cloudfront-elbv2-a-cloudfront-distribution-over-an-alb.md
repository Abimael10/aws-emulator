# cloudfront__elbv2: a CloudFront distribution over an ALB custom origin never serves at the edge, so both ALB-origin enforcement checks are cut off at the 60 s budget with no verdict

> _Note: this issue was identified against the code base at commit `e35c80769d1da1628850625a18b81ebe6990b182`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
CreateDistribution

## Description
Cause 1 of 1 — a CloudFront distribution whose Origins[].DomainName is an Application Load Balancer DNS name (CustomOriginConfig) never produces a served response at the distribution's edge domain, so every check in the cloudfront__elbv2 group burns its whole budget on its positive control and is killed before it can assert anything. Failing checks: cloudfront__elbv2.xsvc-cloudfront-2-alb-origin-protocol-policy-mismatch-rejected, cloudfront__elbv2.xsvc-cloudfront-2-alb-origin-secret-header-direct-request-forbidden. These are the only two checks in the group (0/2 passed) and neither is covered by an existing issue.

AWS: CreateDistribution accepts a custom (non-S3) origin and CloudFront then proxies viewer requests to it. Smithy (com.amazonaws.cloudfront): Origin.CustomOriginConfig -> CustomOriginConfig with required HTTPPort, HTTPSPort and OriginProtocolPolicy; OriginProtocolPolicy is an enum with values http-only | match-viewer | https-only, documented as "http-only - CloudFront always uses HTTP to connect to the origin", "match-viewer - CloudFront connects to the origin using the same protocol that the viewer used to connect to CloudFront", "https-only - CloudFront always uses HTTPS to connect to the origin". Smithy: Origin.CustomHeaders -> CustomHeaders/OriginCustomHeader with required HeaderName and required, sensitive HeaderValue, which CloudFront adds to every origin request. Recorded behavior for the data plane: once the distribution Status is Deployed, a GET at the distribution domain on a behavior bound to an http-only ALB origin returns HTTP 200 carrying the ALB listener's fixed-response body; a behavior bound to an https-only origin whose ALB admits tcp/80 only fails at the edge with HTTP 504 and must not carry the origin body; the same match-viewer origin returns 200 over an HTTP viewer and 504 over an HTTPS viewer. Also recorded: with CustomHeaders carrying the secret header, the edge request matches the ALB listener rule and gets 200, while a direct GET at the ALB DNS name without (or with a wrong) secret header gets the listener default's 403 and its body, and one with the correct value gets 200.

Emulator: both checks end with "Error: Check timed out after 60.0s" and no assertion ever evaluates. Each check first polls elbv2 DescribeLoadBalancers for State.Code == 'active' (600 s budget) and cloudfront GetDistribution for Status == 'Deployed' (900 s budget), then polls the distribution domain for a 200 (300 s budget, 20 s per request). None of those convergence points is reached inside the harness's 60 s cap: the group produces no served edge response at all, so the ALB-origin data path is unobservable. The two subjects the checks exist to verify therefore remain entirely unverified in the emulator: (a) which origin port OriginProtocolPolicy makes the edge dial, and the 504 it must answer when that port is not reachable, and (b) that Origin.CustomHeaders are injected into the origin request so the ALB's header rule — and not CloudFront's network position — is the gate.

Why: a client that fronts an ALB with CloudFront cannot test any of it against the emulator. An origin-protocol misconfiguration that AWS surfaces as a fast 504 at the edge produces nothing, and a secret-header origin lock (the standard way to stop viewers bypassing the distribution) can neither be shown to work through the edge nor to refuse a direct caller. Any suite that waits on a CloudFront-over-ALB response hangs rather than failing with a diagnosis.

Fix: the CloudFront edge data plane's origin-fetch path for CustomOriginConfig origins — origin host resolution for an ELBv2-published DNSName, the port choice driven by OriginProtocolPolicy (including match-viewer following the viewer scheme), the injection of Origin.CustomHeaders into the origin request, and the edge's 504 when the chosen origin port cannot be opened (honouring ConnectionAttempts/ConnectionTimeout) — together with whatever leaves the distribution short of Deployed or the load balancer short of 'active' in this combination. Related but non-covering open issues: 20261112T140934Z-elbv2-7-net-new-causes-loadbalancer-dnsname-is.md and 20261109T153103Z-elbv2-4-net-new-causes-the-published-dnsname.md describe the ALB's published DNSName not being an address the emulator serves, and 20261105T111951Z-cloudfront-dynamodb-lambda-a-deployed-distribution-never-serves.md describes a deployed distribution not serving a Lambda-URL origin; neither carries a cloudfront__elbv2 check, so the ALB-origin combination is unowned.

Traces: the two failing checks listed above; re-replay both to confirm, and both must get past their positive control (a 200 with the ALB listener body through the http-only origin) before the 504 and secret-header assertions can be judged.

## Evidence
Expected (AWS): after CreateDistribution over an ALB custom origin reaches Status 'Deployed' and the ALB reaches State.Code 'active', GET https://<distribution-domain>/<path-on-an-http-only-behavior> -> HTTP 200 with the ALB listener's fixed-response body; GET on the https-only behavior against an ALB with no reachable 443 -> HTTP 504 and the origin body absent; GET http://<domain>/<match-viewer path> -> 200 with the body, GET https://<domain>/<same match-viewer path> -> 504 without it. With Origin.CustomHeaders={x-origin-secret: <secret>}: GET through the edge -> 200 with the header-matched rule's body; direct GET at the ALB DNS name with no header or a wrong value -> 403 with the listener default's body; direct GET with the correct value -> 200 with the rule's body. (Domains, ALB DNS names, secrets and body markers are per-run values; the statuses, the port each OriginProtocolPolicy dials, and which body is served are the requirements.)

Actual (emulator): both checks terminate with 'Error: Check timed out after 60.0s'. No assertion is reached, so no status, body or origin-request header is ever observed. The checks' own convergence polls (ALB 'active' 600 s, distribution 'Deployed' 900 s, first 200 through the edge 300 s at 20 s per request) all exceed the harness cap without the emulator answering. cloudfront__elbv2 per-service rate: 0/2 (0%), 2 failed.

## Steps to Reproduce
1. Create a VPC with two public subnets and a security group admitting tcp/80 only from the CloudFront origin-facing managed prefix list; create an internet-facing ipv4 Application Load Balancer in it and an HTTP:80 listener whose default action is a fixed-response 200 carrying a known body marker.
2. CreateDistribution with Enabled=true, a CustomOriginConfig origin whose DomainName is the ALB's DNSName (HTTPPort 80, HTTPSPort 443, ConnectionAttempts 1, ConnectionTimeout 2), one origin per OriginProtocolPolicy (http-only, https-only, match-viewer), cache behaviors routing /tls/* to the https-only origin and /mv/* to the match-viewer origin, the managed CachingDisabled cache policy, and a CustomErrorResponses entry for 504 with ErrorCachingMinTTL 0.
3. Poll elbv2 DescribeLoadBalancers until State.Code == 'active' and cloudfront GetDistribution until Status == 'Deployed'.
4. GET https://<distribution-domain>/plain/a — expect 200 with the marker; the emulator never answers, and the check is cut at 60 s. Then GET /tls/a (expect 504, no marker), http://<domain>/mv/a (expect 200 + marker) and https://<domain>/mv/a (expect 504, no marker).
5. For the second check: same ALB/VPC, but the listener default is a fixed-response 403 with a denial body and a priority-1 rule matching http-header x-origin-secret == <secret> returns 200 with a marker; create a single-origin distribution with Origin.CustomHeaders = {x-origin-secret: <secret>}. After Deployed, GET through the edge (expect 200 + marker), then GET the ALB DNS name directly with no header and with a wrong header value (expect 403 + denial body) and with the right value (expect 200 + marker).
