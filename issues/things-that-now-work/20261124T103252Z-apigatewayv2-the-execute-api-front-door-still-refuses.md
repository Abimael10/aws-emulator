# apigatewayv2: the execute-api front door still refuses every Origin-bearing HTTP-API request with 403 text/plain 'cross-site origin', so the whole CORS data plane is unobservable (1 cause, 4 checks)

## Description
REOPENS 20261112T084959Z-apigatewayv2-3-net-new-causes-in-the-http.md and 20261114T123844Z-apigatewayv2-3-net-new-causes-the-cors-preflight.md: their fix left the call refused. Both of those reports carried the replay keys of the checks below and both are now under issues/things-that-now-work/; the CORS decoration/preflight work they describe cannot be observed, because the request that carries an Origin header is now refused by the front door before any of it runs. This is not described as a new defect, it is the same calls still being refused.

Cause 1 of 1: any request to a deployed HTTP api's execute-api endpoint that carries an Origin header is answered HTTP 403 with content-type 'text/plain; charset=utf-8' and the body 'cross-site origin', before route matching, the route's authorizer, the integration, or the api's CorsConfiguration is consulted. The gate is evidently a server-side same-origin comparison against the loopback host:port the emulator is reached on, not an evaluation of the api's CorsConfiguration.AllowOrigins: in two of the four checks the Origin sent is the single entry of AllowOrigins, so no correct allowlist evaluation could refuse it. Failing checks: apigatewayv2.deploy-apigatewayv2-3-cdk-http-api-cors-lambda-default-route-serves-then-destroys, apigatewayv2.http-api-cors-preflight-caught-by-any-route-is-authorized, apigatewayv2.http-api-cors-configuration-overrides-backend-cors-headers, apigatewayv2.http-api-cors-preflight-origin-allowlist-and-delete.
AWS: Smithy (services/service-com-amazonaws-apigatewayv2-apigatewayv2/smithy-model/com-amazonaws-apigatewayv2-apigatewayv2.json): CreateApi member CorsConfiguration : Cors — AllowOrigins (CorsOriginList, jsonName allowOrigins), AllowMethods (jsonName allowMethods), AllowHeaders, ExposeHeaders (jsonName exposeHeaders), AllowCredentials, MaxAge @range -1..86400, every member documented 'Supported only for HTTP APIs', shape doc linking https://docs.aws.amazon.com/apigateway/latest/developerguide/http-api-cors.html; CreateRoute members RouteKey and AuthorizationType (AWS_IAM); CreateIntegration IntegrationType AWS_PROXY with PayloadFormatVersion '2.0'; DeleteCorsConfiguration DELETE /v2/apis/{ApiId}/cors, 204. The model does not describe the data plane, so the dispatch rule is the documented CORS rule plus recorded behavior: CORS is a BROWSER mechanism and API Gateway NEVER refuses a request because of its Origin. The request is served on its own merits and only the RESPONSE differs: (a) a GET on a route with AuthorizationType NONE whose Origin is in AllowOrigins is served 200 with the integration's body plus access-control-allow-origin equal to the request's Origin and access-control-expose-headers equal to the configured ExposeHeaders; (b) the same GET from an origin NOT in AllowOrigins is STILL served 200 with the same body and NO access-control-* header at all, and any Access-Control-* header the integration itself returned is stripped; (c) an OPTIONS preflight (Origin + Access-Control-Request-Method) that no route matches is answered by the gateway itself, 204, with access-control-allow-origin/-allow-methods/-allow-headers/-max-age taken from the api's own CorsConfiguration; (d) a preflight a route DOES match (ANY /{proxy+}, or the CDK $default catch-all) is routed like any other request — on an AWS_IAM route an unsigned preflight is refused HTTP 403 with body exactly {"message":"Forbidden"} ('Forbidden' is fixed text, there are no variable parts), and on an unauthorized $default route it reaches the Lambda and answers 200 with the integration's body. In all of these the status, the header names and the JSON error shape are the fixed part; the origin string, the method/header lists, the max-age number and the handler's marker are values taken from the request and from the api's own CorsConfiguration.
Emulator: every Origin-bearing leg is refused 403 'cross-site origin'. In apigatewayv2.deploy-apigatewayv2-3-cdk-http-api-cors-lambda-default-route-serves-then-destroys the SAME url served 200 with the Lambda's body one call earlier with no Origin header, and then 'GET / with an allowed Origin answered 403 \'cross-site origin\'' — the only difference between the two requests is the Origin header, and that origin is the one allow-listed by the stack's CorsConfiguration. In apigatewayv2.http-api-cors-preflight-caught-by-any-route-is-authorized the unsigned GET (no Origin) is correctly 403, but the preflight (Origin + Access-Control-Request-Method) is answered with a 403 whose body is not JSON at all, so the assertion on AWS's {"message":"Forbidden"} dies in the decoder: json.decoder.JSONDecodeError: Expecting value: line 1 column 1 (char 0) — the body is the plain text 'cross-site origin', not an API Gateway error document. In apigatewayv2.http-api-cors-configuration-overrides-backend-cors-headers and apigatewayv2.http-api-cors-preflight-origin-allowlist-and-delete the first, positive leg is an Origin-bearing GET polled for 200 (_poll_http(url, 200, headers={'Origin': <allow-listed origin>})); it never reaches 200 and the checks are killed at the harness's 60 s cap ('Check timed out after 60.0s'), so the preflight, allowlist-deny, header-stripping and DeleteCorsConfiguration legs those two checks exist to observe are never reached. Note that services/service-com-amazonaws-apigatewayv2-apigatewayv2/src/service/invoke.rs says in its own docs (~line 843) that 'an invoke whose browser-set headers read as cross-site … is exactly the request an api's CorsConfiguration exists for, so it is served like any other' — the refusal is therefore being applied ahead of this module, not by it.
Why: a client relying on AWS's behavior gets the opposite of the contract twice over. First, the very requests CORS exists to permit are destroyed: a browser page, or any fetch/XHR wrapper that forwards Origin, is refused 403 by an api whose allowlist explicitly names its origin, so a correctly configured single-page application cannot call its own HTTP api at all, and no CORS behavior (decoration, allowlist denial, backend-header stripping, preflight, DeleteCorsConfiguration taking effect) can be observed. Second, server-side Origin enforcement is not a CORS mechanism: code written against the emulator will treat AllowOrigins as an access control, whereas in AWS the request is served regardless and only response headers differ — an application that believes it is protected is in fact open. The invented plain-text body additionally breaks every client that parses API Gateway's {"message":...} JSON error shape, and it masks the 403 {"message":"Forbidden"} that an AWS_IAM route's authorization must produce, so an authorization refusal and an Origin refusal are indistinguishable.
Fix: the shared HTTP front-door/edge middleware that applies the same-origin gate ahead of the apigatewayv2 execute-api data plane (the gate is not in services/service-com-amazonaws-apigatewayv2-apigatewayv2/src/service/invoke.rs, whose docs state such a request must be served) — remove the server-side Origin check so the request proceeds to resolve/stage/route matching, the route's authorizer and its integration, and let the api's CorsConfiguration shape only the RESPONSE (the existing cors_decoration path in that module) on the 200, the 204 preflight and the 403 {"message":"Forbidden"} branch alike.

## Resolution

Cause 1: FIXED, and PINNED by a test — the refusal this report was filed against is gone from the
tree the report was written against (`9b3ec711`) by the time it was picked up, and all four checks
replay as passing. The gate was never in `src/service/invoke.rs`: the address an HTTP api publishes
is a SOCKET of this service's own (`src/service/invoke_plane_socket.rs`), and the endpoint serving it
re-applied the core's browser (`Origin` / `Sec-Fetch-Site`) reading to every request on it and
answered the plain-text `403` itself, before any record of the api was read. That reading is now
scoped by what the socket being served STANDS FOR (`src/service/websocket/endpoint_http.rs`'s
`Arrival`): it is still applied, exactly as a core HTTP listener applies it, wherever the address may
be addressed at something other than an api's own data plane, and it is not applied where the
socket's own record has already resolved the request to an invoke of an api of this account. The
router still reads those fields for every request it NAMES AN OPERATION for, and `src/service.rs`
leaves such an invoke unnamed so its routing seam answers it with the api's own records and the
`CorsConfiguration`'s decoration.

What this change adds is the evidence, over a real connection to the address the control plane
publishes: `tests/all/published_endpoint_cors_browser_fields.rs`. An `Origin` decides nothing about
whether the published address serves a request — the route's function answers it and reports the
origin it was given, for an origin the configuration admits, one it does not, the `null` origin, and
each `Sec-Fetch-Site` classification beside them — and the only Origin-dependent difference is the
`Access-Control-*` decoration, which REPLACES the `Access-Control-*` fields the function returned for
itself (a field of the function's that is not one of those reaches the client untouched) and is
absent entirely for an origin `AllowOrigins` does not hold. A preflight no route matches is the
gateway's own `204` carrying the configuration's origin, methods, headers and `MaxAge`; one an
`ANY /{proxy+}` route matches is routed and authorized like any other request, so an unsigned caller
earns `403` `{"message":"Forbidden"}` as JSON — never a transport-level refusal — with that same
decoration on it; and `DeleteCorsConfiguration` leaves the api serving the same body with no
`Access-Control-*` field at all, the preflight the gateway used to answer going back to the api's own
`404` `{"message":"Not Found"}`.
