# Route 53 Resolver managed domain lists carry caller-account ARNs and name-derived ids

=== Cause 1 of 1: the service-published (managed) firewall domain lists are published with identifiers minted for the CALLER's account instead of the service-published ones ===

AWS: Smithy: ListFirewallDomainLists(MaxResults @range 1..100, NextToken) -> ListFirewallDomainListsResponse{NextToken, FirewallDomainLists: FirewallDomainListMetadataList}; errors AccessDeniedException | InternalServiceErrorException | ThrottlingException | ValidationException (all httpError 400); paginated items=FirewallDomainLists. FirewallDomainListMetadata models Id (ResourceId @length 1..64, "The ID of the domain list"), Arn (@length 1..255), Name (@length 0..64, @pattern ^(?!^[0-9]+$)([a-zA-Z0-9\-_' ']+)$), CreatorRequestId, ManagedOwnerName (ServicePrinciple, doc: "The owner of the list, used only for lists that are NOT managed by you. For example, the managed domain list AWSManagedDomainsMalwareDomainList has the managed owner name Route 53 Resolver DNS Firewall"), ManagedListType (enum DomainListType) and Category. WHAT identifiers a managed list carries is recorded behavior only: AWS serves every account in a Region the SAME four service-published threat lists, each with an Id and an Arn that belong to the DNS Firewall service itself and are identical for every caller in that Region — i.e. the Arn's account-id field is the service's own publishing account, NOT the requesting account, which is what makes the entry consistent with ManagedOwnerName "Route 53 Resolver DNS Firewall" (a list not managed by you cannot be a resource of your account). The recorded response for us-west-2 shows the four entries as Name/CreatorRequestId AWSManagedDomainsAmazonGuardDutyThreatList (Category "Amazon GuardDuty Threat List"), AWSManagedDomainsBotnetCommandandControl ("Botnet/Command and Control"), AWSManagedDomainsAggregateThreatList ("Aggregate Threat List") and AWSManagedDomainsMalwareDomainList ("Malware"), all ManagedListType THREAT, ManagedOwnerName "Route 53 Resolver DNS Firewall", each with a stable published Id of the form rslvr-fdl-<hex> under an Arn arn:aws:route53resolver:<region>:<dns-firewall-publishing-account>:firewall-domain-list/<that id>. The requirement is the SHAPE of that identity — one published id per managed list, stable across accounts, and an Arn whose account field is the publishing service's, not the caller's. The concrete account number and hex ids in the recording are the values AWS publishes for that Region; they fill the template and are not themselves re-derivable by the emulator.

Emulator: HTTP 200. The four managed names, categories, ManagedListType and ManagedOwnerName are all served correctly, but each managed entry's Id is minted by hashing the list name (SHA-256 over "managed-firewall-domain-list/v1" + name -> rslvr-fdl-<hex>) and its Arn is built with the emulator's generic ARN helper, which roots it in the REQUESTING account. The replay therefore reports every managed entry AWS serves as absent — "$.FirewallDomainLists[Arn=\"arn:aws:route53resolver:us-west-2:229214028842:firewall-domain-list/rslvr-fdl-23584f0fb4c24ebb\"]: missing (expected {...}, got None)" and the same for rslvr-fdl-c80983a1f0284c99, rslvr-fdl-d252ee1944404e15 and rslvr-fdl-fe17696f22a445f6 — while four extra entries keyed on caller-account ARNs (rslvr-fdl-1bc724e346019cfb, rslvr-fdl-4ab5894cbe1429d4, rslvr-fdl-cb4f4cfd74cafd8a, rslvr-fdl-d57b208eeaea0f26) stand in their place in the response.

Why: the managed threat lists are the documented way to build a DNS Firewall rule group, and a FirewallRule references a domain list by Id. A client that looks a managed list up by Arn, filters the catalog by owning account, or caches a managed list's published Id (they are Region constants in AWS, so clients hard-code or pin them) resolves nothing against the emulator, and a client that derives ownership from the Arn concludes the list is a resource of its own account even though ManagedOwnerName says it is not — an account that in AWS cannot delete, update or import domains into that list. The response contradicts itself: a list declared "not managed by you" is published inside your account's ARN space.

Fix: the DNS Firewall managed-catalog entries in the crate's state module — the published-list id minting and the ARN construction for ManagedFirewallDomainList (the id() / arn() pair feeding both to_metadata, which ListFirewallDomainLists projects, and to_domain_list, which GetFirewallDomainList projects, plus the id -> managed-list resolver every operation consults) must carry the service's published identifiers under the DNS Firewall publishing account rather than hashing the name and reusing the account-scoped emulator ARN helper; whatever id is chosen must stay stable across processes and resolve back through GetFirewallDomainList. Open issue 20261108T111412Z-route53resolver-route-53-resolver-dns-firewall-responses-diverge-managed.md described an EARLIER state of this step (managed entries absent from the catalog entirely) and its Cause 1 is now partly served — the names/categories/ManagedListType/ManagedOwnerName arrive — but the replay still reports this cluster unowned and the identity members still diverge, so this cause must be closed and re-replayed on its own. Open issue 20261107T012050Z-route53resolver-route-53-resolver-list-projections-drop-managed-domain.md likewise does not own this cluster.
