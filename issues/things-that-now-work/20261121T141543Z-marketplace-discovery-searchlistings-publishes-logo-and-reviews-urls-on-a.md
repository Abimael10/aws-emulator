# SearchListings publishes logo and reviews URLs on a loopback authority nothing answers at

> _Note: this issue was identified against the code base at commit `8c92c7c2cb0689aef734153d4944deecfb6a59a7`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
SearchListings

## Description
This issue bundles 4 causes, all in marketplace-discovery, all on SearchListings, all the SAME defect in the two FETCHABLE members of the ListingSummary projection — logoThumbnailUrl and reviewSummary.reviewSourceSummaries[].sourceUrl: the emulator composes both addresses on an authority that is NOT the authority the answering request reached it on, so every URL a search page hands a client addresses a port this process does not serve. Each cause is one replay cluster with its own fixture/step binding and EACH MUST BE RE-REPLAYED before this issue is closed: Cause 1 = marketplace-discovery-search-facets-refine-search#task#3, Cause 2 = marketplace-discovery-search-listings-and-drill-into-listing#task#1, Cause 3 = marketplace-discovery-search-listings-pagination#task#1, Cause 4 = marketplace-discovery-search-listings-pagination#task#2. In all four the HTTP status is right (200), the summary count and totalResults are right, and the plane path plus the media/reviews id inside each announced URL are the emulator's own and correct; only the scheme+authority the URL is published on is wrong.

NOT CLAIMED anywhere in this issue, because they are per-environment or per-run values: the recorded marketplace media-CDN host and its hash path, the recorded prodview/listing/review-list ids, the emulator's own generated media ids, and $.nextToken. $.nextToken appears in the diverging-key set of all four clusters, but its recorded values are '<shaped-not-asserted>', 'opaque-continuation-token-placeholder-000' and, in one recording, a long AWS continuation blob — i.e. continuation-token BYTES, a per-run opaque value — and the token the emulator serves is opaque and satisfies NextToken's @length(0..8192) and @pattern ^[a-zA-Z0-9+/=]+$, so its literal bytes are not a requirement. The only requirement claimed is that an address this service publishes for a client to dereference is published on the scheme and authority the answering request arrived on, which is where the emulator itself serves that resource.

=== Cause 1 of 4: a facet-refined SearchListings page publishes ten logo addresses and four reviews addresses on an authority the request did not reach ===
AWS: Smithy (services/service-com-amazonaws-marketplacediscovery-awsmarketplacediscovery/smithy-model/com-amazonaws-marketplacediscovery-awsmarketplacediscovery.json) SearchListings POST /2026-02-05/searchListings, success 200, output {totalResults @required, listingSummaries @required, nextToken @length(0..8192) @pattern ^[a-zA-Z0-9+/=]+$}. ListingSummary$logoThumbnailUrl targets URL, @required, @length(1..2048), @pattern ^https?://.*$, documented 'The URL of the logo thumbnail image for the listing'; ReviewSourceSummary$sourceUrl targets URL, OPTIONAL, same constraints, documented 'The URL where the reviews can be accessed at the source'. Both are addresses a client FETCHES, not text it displays, so the requirement is that the published address dereferences to that listing's logo image resp. that listing's reviews page. The model fixes no host and AWS serves these off the marketplace's own media and reviews hosts, so for the host itself this is recorded behavior only: the recording shows one distinct media-CDN path per listing and a per-listing reviews deep link. The emulator cannot be on those hosts, and its own design states the rule it must follow instead — src/state/listing_logo.rs: 'what it publishes is an address of its OWN: the endpoint the request being answered reached this emulator at ... A URL published on any other host is one a client can render but never dereference.'
Emulator: 200 with the right ten summaries, but every listingSummaries[i].logoThumbnailUrl is of the form https://<authority>/_aws/marketplace-discovery-listing-media/<mediaId>/logo.png where <authority> is NOT the authority the replayed request reached the emulator on, and the four summaries whose review record keeps a reviews page publish reviewSourceSummaries[0].sourceUrl the same way, on the same drifting authority. The replay checker classifies each such member resource_not_identified: the published address identifies no resource. One emulator served the whole replay and its data listener is the one that accepted every request, yet the announced authority is a different loopback port — and a DIFFERENT wrong port in each of the four clusters, so the drift is per response, not one static misconfiguration.
Why: a client rendering a result page dereferences logoThumbnailUrl for every tile and turns sourceUrl into the 'read the reviews' link. Against AWS both resolve; against the emulator both address an authority it is not serving, so every tile image and every reviews link fails with a connection error that reads as a client or network fault rather than as emulator fidelity — even though the emulator DOES serve both resources at its real front door (state/listing_logo.rs logo_route + listing_logo_image, state/listing_reviews.rs reviews_page_route + listing_reviews_page). The round trip is unreachable purely because of what the API announced.
Fix: the announced-address resolution the SearchListings summary projection uses — state::saas_fulfillment::announced_page_base (src/state/saas_fulfillment.rs, shared by all three published planes) and the authority ordering it consults in service_common::data_plane_addressing (reached_emulator_endpoint_of_parts -> served_endpoint_authority -> url_authority, scheme hard-coded https) — must yield the scheme and authority the answering request actually arrived on, which src/state.rs listing_summary() then stamps into logoThumbnailUrl via LogoMedia::announced and into sourceUrl via ReviewRecord::announced. Not the handler's serializer and not the seeded catalog: the plane path, the media id and the reviews-list id are already correct.
Traces: marketplace-discovery-search-facets-refine-search#task#3 (SearchListings, expected 200 / got 200, verdict mismatch; 15 diverging keys — logoThumbnailUrl on listingSummaries[0..9], reviewSummary.reviewSourceSummaries[0].sourceUrl on listingSummaries[1], [4], [6], [8], plus $.nextToken, which is not claimed).
