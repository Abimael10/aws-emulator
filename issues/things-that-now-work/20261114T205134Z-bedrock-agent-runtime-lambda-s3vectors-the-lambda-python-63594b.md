# bedrock-agent-runtime__lambda__s3vectors: the Lambda Python runtime's bundled botocore still has no s3vectors service data, so an in-handler boto3.client("s3vectors") raises UnknownServiceError where the role's denial should produce 403 AccessDeniedException

## Description
One net-new root cause, reached through the one CFN stack-update check the suite did not mark owned.

Related open work (none of it carries this check's replay key, so none of it covers it): 20261107T175916Z-bedrock-agent-runtime-lambda-s3vectors-lambda-python-runtime-s-bundled-botocore-knows-no.md and 20261106T131020Z-bedrock-agent-runtime-lambda-s3vectors-the-lambda-python.md describe the same execution-environment area when BOTH s3vectors and bedrock-agent-runtime were unknown to the sandbox SDK. What this check now observes is narrower and happens at a different point: bedrock-agent-runtime DOES resolve and its call succeeds inside the handler (the check's first poll, whose predicate is r["bedrock"]["ok"], now returns), while s3vectors alone still fails client construction. 20261107T054220Z / 20261107T143421Z / 20261107T085049Z describe the CFN stack-update lifecycle hanging; that no longer happens here either — create and update both settle and the invocation returns a payload.

=== Cause 1 of 1: the SDK the managed Python runtime exposes to a handler carries no service data for s3vectors, so client construction fails client-side and no request is ever made ===
Failing check id (1): bedrock-agent-runtime__lambda__s3vectors.cfn-stack-update-add-s3vectors-permission-positive

AWS: recorded behavior only for the CONTENTS of the managed runtime — the Smithy model describes Invoke's wire shape, not the execution environment. On AWS's managed python3.12 runtime a handler built from Code.ZipFile containing only index.py can call boto3.client("s3vectors") successfully: the preinstalled boto3/botocore carry service data for every service the account can address, so the client constructs and the request goes out, after which the OUTCOME is decided by the function's execution role. Smithy (s3vectors ListVectorBuckets): http {method POST, uri /ListVectorBuckets}, success 200 with required output member vectorBuckets; modeled errors include AccessDeniedException (errorKind client, httpError 403). So a role whose inline policy omits s3vectors:ListVectorBuckets must produce exactly that modeled 403 AccessDeniedException — a service-authored refusal — and a role that grants it must produce 200 with a vectorBuckets list. Smithy (lambda Invoke): StatusCode is the httpResponseCode, FunctionError is header X-Amz-Function-Error, Payload is the httpPayload blob.

Emulator: inside the deployed function boto3.client("s3vectors") raises botocore's UnknownServiceError, which botocore raises when it can find no data file for the requested service name. The handler catches it and reports the exception class name, so the invocation's payload carries {"s3vectors": {"ok": false, "error_code": "UnknownServiceError"}} both BEFORE and AFTER the stack update that adds the permission, while {"bedrock": {"ok": true, "count": <int>}} shows the sibling client resolving normally. The text raised is botocore's own, not AWS's: its fixed part is "Unknown service: '<service-name>'. Valid service names are: ..." and its only variable part is the service name taken from the boto3.client() call — there is no HTTP status, no AWS error code and no AWS message at all, because nothing left the sandbox. The expected refusal is HTTP 403 with error code AccessDeniedException, whose message is AWS's own access-denied sentence naming the caller's role ARN and the action s3vectors:ListVectorBuckets (identity and action taken from the request/state; no literal value from a single run is part of the requirement).

Why: a client gets a Lambda that runs, imports the SDK, and can address bedrock-agent-runtime but not s3vectors — the service these functions exist to call. Both arms of an IAM test collapse into one indistinguishable answer: a role with the grant and a role without it both return UnknownServiceError, so neither the success nor the modeled 403 AccessDeniedException is ever observable, and a stack update that adds a permission appears to change nothing. A user concludes their deployment package or the service name is wrong, when the identical function works unmodified on real AWS.

Fix: the Lambda service's execution-environment component — the part that assembles the interpreter and the boto3/botocore install placed on the handler's sys.path for Invoke. The SDK exposed in the sandbox must carry service data for EVERY service the emulator serves (s3vectors here, alongside the services that already resolve) and be pointed at the emulator's endpoints and credentials, the way the managed python3.12 runtime resolves any service name. Not the Invoke serializer: the Invoke response shape (200, FunctionError/Payload) is correct; and not s3vectors' own authorization, which is never reached.

Traces: bedrock-agent-runtime__lambda__s3vectors.cfn-stack-update-add-s3vectors-permission-positive (see trace_ids).

The required refusal instead is HTTP 403 with error code AccessDeniedException and AWS's access-denied wording, whose variable parts (the assumed-role identity and the action s3vectors:ListVectorBuckets) come from the request and the emulator's state.
