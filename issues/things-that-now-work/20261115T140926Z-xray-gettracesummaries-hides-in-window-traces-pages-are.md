# xray GetTraceSummaries hides in-window traces: pages are cut on the ABSOLUTE hour grid, so a minutes-wide window that straddles the top of an hour serves only its tail and the rest sits behind a NextToken

> _Note: this issue was identified against the code base at commit `528a6d6592798fe22b481151e8f2c3cf0578535a`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
GetTraceSummaries

## Description
ONE net-new root cause in the xray service. Both failing checks are listed by the suite under `### xray` (SERVICES = ['xray']) and neither is marked ALREADY FILED or OWNED in this replay report. The xray service answers (144/160 xray checks pass in this run), so this is a fidelity defect, not a bootstrap gap.

RELATED, NOT COVERING (named for the fixer; none of these carries these two checks' replay keys):
- 20261103T034719Z-xray-gettracesummaries-hourly-paging-missing-and-getservicegraph-echoes.md is FIXED and is where hour-based paging came from (it required an hour-aligned ApproximateTime inside the requested window and a NextToken while pages remain). - 20261109T114723Z-xray-segment-derived-trace-reads-lose-data-gettracesummaries.md and 20261025T043615Z / 20261115T022714Z (GetServiceGraph, ResponseTimeRoot, TraceSummary members) are about the CONTENT of a summary or of the graph, not about which summaries a page carries.

Cause 1 of 1: a single GetTraceSummaries call over a window of a few minutes does not return the traces that window holds, because the response is restricted to the one-hour slice of the ABSOLUTE hour grid that the window's EndTime falls in.

AWS: Smithy (services/service-com-amazonaws-xray-awsxray/smithy-model/com-amazonaws-xray-awsxray.json) models GetTraceSummaries as POST /TraceSummaries (success 200), StartTime/EndTime required, @paginated {inputToken: NextToken, outputToken: NextToken, items: TraceSummaries}, errors InvalidRequestException (client, 400) and ThrottledException (429). GetTraceSummariesResult$NextToken is documented "If the requested time frame contained more than one page of RESULTS, you can use this token to retrieve the next page. The first page contains the most recent results, closest to the end of the time frame", and ApproximateTime as "The start time of this page of results" — i.e. whether a second page exists is keyed on how many RESULTS the requested time frame holds, not on how many hour boundaries the frame happens to cross. For the narrow-window case this is recorded behavior only: both recordings query a window of 12 and 20 minutes respectively, each holding 2 traces just accepted by PutTraceSegments, and read the complete answer out of ONE call with no NextToken following (the `trace-summaries-ordered-by-time` recording additionally asserts that exactly the 2 in-window traces come back, that neither has a StartTime outside [StartTime, EndTime), and that an immediate repeat of the identical window returns the identical ids in the identical order).

Emulator: the window is cut into one-hour slices on the absolute epoch hour grid and exactly ONE slice is served per page — the slice the window's EndTime falls in — with any earlier part of the SAME requested window deferred behind a NextToken, and at most 5 summaries per page (services/service-com-amazonaws-xray-awsxray/src/state/trace_pages.rs: TRACE_PAGE_SECONDS = 60*60, hour_boundary_at_or_before / window_page_boundaries / window_page; services/service-com-amazonaws-xray-awsxray/src/ops/get_trace_summaries.rs: page selection and the `next_token` composition, TRACE_SUMMARIES_PAGE_SIZE = 5). Consequence: a window such as [now-600s, now+120s] evaluated shortly after the top of an hour is served as the slice [hour, now+120s) only, so traces recorded one or two minutes earlier — inside the requested window, and counted by TracesProcessedCount — are absent from the first (and, for a caller that does not paginate, only) response. The first page can be entirely EMPTY while the window demonstrably holds matching traces. Nothing is refused: the call answers 200 with a short or empty TraceSummaries list and a NextToken.

Why: GetTraceSummaries over a short, recent window is the primary way a client finds a trace it just submitted, and what every "last 5/10 minutes" view and every post-submit poll does. A client gets 200 with no trace, or an arbitrary subset of its own window, and cannot distinguish "not ingested yet" from "in an earlier slice of the window I asked about"; it only ever sees the whole answer if it paginates a window it had no reason to believe was paginated. The split is also clock-dependent — the same request made a minute later returns a different subset — so results are not reproducible and the "identical window returns identical ids in identical order" property clients rely on does not hold across the boundary.

Fix: the paging of GetTraceSummaries — derive page boundaries from the REQUESTED window (walking back from EndTime in page-long steps) and/or from the number of summaries selected, so that a window shorter than one page is always a single page containing every matching trace in [StartTime, EndTime), while a multi-hour window keeps being paged (and keeps reporting an ApproximateTime inside the requested window and a NextToken while results remain, as the fixed issue 20261103T034719Z requires). The component is services/service-com-amazonaws-xray-awsxray/src/state/trace_pages.rs (boundary derivation, token form) together with the candidate-selection and next_token composition in services/service-com-amazonaws-xray-awsxray/src/ops/get_trace_summaries.rs; the emulator-chosen page size of 5 summaries belongs in the same decision.

Note for the fixer: both checks are cut off at the harness's 60 s ceiling INSIDE a GetTraceSummaries poll, so the assertions after the poll were never reached and are still unverified — the group-scoped `group.name = "<group>"` query must return the trace matching the group's FilterExpression and exclude the non-matching one, and the repeat query must return the same ids in the same order. Re-replay both ids in trace_ids.

Traces: xray.trace-summaries-ordered-by-time, xray.deploy-group-via-cloudformation-filters-traces.
