# CodePipeline action-type catalog diverges: ListActionTypes entries and the entityUrl it resolves

> _Note: this issue was identified against the code base at commit `9cd823483c6bf9bc21049a15587772110eae227a`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
ListActionTypes

## Description
The emulator's built-in CodePipeline action-type catalog does not match the catalog AWS serves, and the URL templates that catalog is supposed to supply are either absent from it or resolved into links the emulator does not serve. The same wrong catalog surfaces twice: directly, when a client lists action types to discover providers and their configuration properties, and indirectly, when GetPipelineState projects an action state's entityUrl from the action type's entityUrlTemplate. Every affected call answers 200, so the divergence is silent. 3 causes.

Cause 1 of 3: ListActionTypes returns a catalog whose entries and order differ from AWS's at every index, and several entries carry no settings URL templates (fixture codepipeline-catalog-list-action-types, step task#1).
AWS: Smithy ListActionTypes -> output.actionTypes (ActionTypeList, @required), input filters actionOwnerFilter (ActionOwner enum) / regionFilter / nextToken, paginated {inputToken nextToken, outputToken nextToken, items actionTypes}; ActionType = {id: ActionTypeId @required, settings: ActionTypeSettings, actionConfigurationProperties: ActionConfigurationPropertyList @length 0..10, inputArtifactDetails: ArtifactDetails @required, outputArtifactDetails: ArtifactDetails @required}; ActionTypeSettings members entityUrlTemplate / executionUrlTemplate / revisionUrlTemplate (UrlTemplate @length 1..2048) and thirdPartyConfigurationUrl (Url @length 1..2048); ActionConfigurationProperty = {name @required, required @required, key @required, secret @required, queryable, description @length 1..160, type}. The membership and ordering of the catalog itself is not in the model, so this is recorded behavior only: AWS returns a fixed, ordered set of action types for the region, each with its documented configuration properties and its URL templates. In the recording the first entry is id {category Source, owner AWS, provider S3, version 1} with actionConfigurationProperties S3Bucket, S3ObjectKey, PollForSourceChanges and AllowOverrideForS3ObjectKey, inputArtifactDetails {minimumCount 0, maximumCount 0}, outputArtifactDetails {minimumCount 1, maximumCount 1} and settings.entityUrlTemplate set; the recorded list runs to at least index 27.
Emulator: answers 200 with a different catalog. The cluster reports every one of $.actionTypes[0] .. $.actionTypes[27] as diverging: at index 0 the emulator serves id {category Approval, owner AWS, provider Manual, version 1} with settings {} (no URL template at all), three configuration properties (NotificationArn, CustomData, ExternalEntityLink) and outputArtifactDetails {minimumCount 0, maximumCount 0}, where the recording has the S3 source type described above. The clustered key list also names settings.entityUrlTemplate on indexes 1, 6, 8, 10, 11, 12, 16, 17, 18, 20, 21, 22 and 23 and settings.executionUrlTemplate on indexes 1 and 22, i.e. the entries the emulator does serve are missing the template members that make them usable.
Why: ListActionTypes is how a client (console, CDK/CloudFormation tooling, a pipeline linter) discovers which provider/category/version triples exist and which configuration keys each one requires, and whether a key is required, a key property, or secret. A catalog with different members, a different order and missing URL templates makes that discovery wrong: a client validating a pipeline declaration against the catalog rejects action types that exist, offers ones that do not, and can build no deep links because entityUrlTemplate/executionUrlTemplate are absent.
Fix: the built-in action-type catalog data the codepipeline crate serves (the table ListActionTypes projects), which must carry AWS's entries, in AWS's order, each with its full settings block and configuration-property set; plus the ListActionTypes handler's projection of it.
Traces: codepipeline-catalog-list-action-types#task#1.

Cause 2 of 3: the ThirdParty-owner slice of the same catalog is also a different set in a different order (fixture codepipeline-catalog-list-action-types, step task#2).
AWS: same model surface as Cause 1 (ListActionTypes with actionOwnerFilter selecting ThirdParty-owned types). Recorded behavior only: the recording's first ThirdParty entry is id {category Test, owner ThirdParty, provider GhostInspector, version 1} with configuration properties ClientId, ClientToken (secret), TestId and ExtraParams, inputArtifactDetails {0,1}, outputArtifactDetails {0,0} and settings carrying entityUrlTemplate, executionUrlTemplate and thirdPartyConfigurationUrl.
Emulator: answers 200 with id {category Source, owner ThirdParty, provider GitHub, version 1} at index 0 (settings thirdPartyConfigurationUrl / entityUrlTemplate / revisionUrlTemplate, properties Owner, Repo, Branch, ...). The cluster reports $.actionTypes[0] .. $.actionTypes[4] as diverging, plus $.actionTypes[0].settings.revisionUrlTemplate and $.actionTypes[0].settings.thirdPartyConfigurationUrl, so the whole ThirdParty slice is a different set of providers in a different order and with a different settings shape per entry.
Why: a client that filters the catalog by owner to offer the third-party integrations available in the environment gets providers AWS does not list and misses the ones it does, and the per-entry settings it reads (sign-up URL, revision URL) belong to the wrong provider.
Fix: the same built-in action-type catalog data and the actionOwnerFilter selection over it.
Traces: codepipeline-catalog-list-action-types#task#2.

Cause 3 of 3: GetPipelineState resolves ActionState.entityUrl to a real-AWS console address the emulator does not serve, and the resolved path does not match the action type's template (fixture codepipeline-gpn-traj-creation-run-failed-at-source-read-path, step task#10).
AWS: Smithy GetPipelineState -> output.stageStates (StageStateList); ActionState.entityUrl is a Url @length 1..2048, documented as 'A URL link for more information about the state of the action, such as a deployment group details page'. AWS builds it by resolving the action type's settings.entityUrlTemplate (Cause 1's member) against the action's configuration and the request's region. The recording's two values are shape-asserted ('<shaped-not-asserted>'), so the requirement is the URL's shape and its host, never a literal link from one run.
Emulator: both action states in this run fail that shape check while answering 200. For the CodeCommit source action it emits 'https://console.aws.amazon.com/codesuite/codecommit/repositories/<repository name>/browse/refs/heads/<branch>?region=<region>' (verdict value_mismatch); for the Lambda invoke action it emits 'https://console.aws.amazon.com/lambda/home?region=<region>#/functions/<function name>' (verdict host_not_own) - the emulator announces an address on console.aws.amazon.com, a host it neither serves nor is reached on. Hypothesis for the first verdict: the source link interpolates the full git ref ('refs/heads/<branch>') where the CodeCommit action type's entityUrlTemplate takes the plain branch name from the action's BranchName configuration, so the path is built ad hoc rather than by resolving the catalog's template.
Why: entityUrl exists so a client can follow the link to the resource the action acted on. A link on a host the emulator does not serve takes the client out of the emulated environment: in a sealed environment it does not resolve at all, and where it does resolve it points at real AWS and at resources that do not exist there, so any console-like surface or automation that dereferences entityUrl is broken. Same class as the already-open Lambda issue 20261109T163411Z-codecommit-codepipeline-glue-iam-lambda-lambda-getfunction-publishes-a-code-location-on-an.md (Code.Location on an amazonaws.com host the emulator does not serve).
Fix: the GetPipelineState action-state projection that produces entityUrl - resolve the action type's entityUrlTemplate from the catalog against the action's configuration and the request region, and emit it on the endpoint host the emulator is reached on.
Traces: codepipeline-gpn-traj-creation-run-failed-at-source-read-path#task#10.
