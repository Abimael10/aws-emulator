# iot control-plane refusals diverge: wrong error class, status and emulator-authored not-found text

> _Note: this issue was identified against the code base at commit `db1b3ad25a652e4a15df88815e8c32da3f07f40e`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
DeleteCommandExecution

## Description
Six net-new causes on iot refusal paths. In every one the emulator chooses a different error class, a different HTTP status, or its own wording for a refusal AWS words in a fixed way. SIX causes must be closed before this issue is submitted.

Cause 1 of 6: DeleteCommandExecution does not authorize targetArn. AWS: recorded behavior only — the modeled error set for DeleteCommandExecution (Smithy: DeleteCommandExecution errors = ConflictException 409, InternalServerException 500, ThrottlingException 400, ValidationException 400; input members executionId @httpLabel @required and targetArn @httpQuery @required) does not include the authorization refusal, so the requirement comes from the recording: when the required targetArn names a target that is not in the caller's account, AWS refuses the delete with HTTP 403, header x-amzn-errortype 'AccessDeniedException:http://internal.amazon.com/coral/com.amazon.coral.service/', and a Coral-shaped body whose capitalised member 'Message' carries the fixed sentence 'targetArn not found in account' (that sentence is entirely fixed text — it interpolates nothing from the request). Emulator: answers HTTP 200 with an empty JSON body ({}), i.e. it reports the delete as having succeeded. Why: a client deleting a command execution against a target it does not own is told the delete succeeded; cross-account isolation is unobservable and any test that asserts the 403 refusal passes against a silent success. Fix: the DeleteCommandExecution handler must resolve targetArn and reject a target outside the caller's account with the AccessDenied refusal above before performing any state change. Traces: iot-command-duplicate-and-execution-errors#task#4.

Cause 2 of 6: DeleteCommandExecution checks executionId syntax before targetArn ownership. AWS: recorded behavior only, same refusal as cause 1 — when the request carries BOTH an executionId that violates its modeled constraint and a targetArn outside the account, AWS answers the ownership refusal first: 403, x-amzn-errortype 'AccessDeniedException:http://internal.amazon.com/coral/com.amazon.coral.service/', body Message = 'targetArn not found in account'. Emulator: answers 400 with x-amzn-errortype 'ValidationException' and message "1 validation error detected: Value at 'executionId' failed to satisfy constraint: Member must satisfy regular expression pattern: [a-zA-Z0-9_-]+" (Smithy: CommandExecutionId @length 1..64, @pattern ^[a-zA-Z0-9_-]+$ — note AWS's own validation sentence reports the anchored pattern as modeled, and the emulator strips the ^...$ anchors here too). Why: the two refusals are distinguishable by clients — one means 'retry with a valid id', the other means 'you do not own this target'. A client that keys on the error class takes the wrong branch, and the ordering difference also leaks which executionIds exist in another account. Fix: in the DeleteCommandExecution handler, order the ownership/authorization check ahead of member-syntax validation, and when the ValidationException path does run, keep the modeled pattern's anchors in the message. Traces: iot-command-duplicate-and-execution-errors#task#5.

Cause 3 of 6: DeleteThingType is not idempotent. AWS: recorded behavior only for the absent-resource path — deleting a thing type that does not exist (here, one deleted by an earlier step of the same fixture) answers HTTP 200 with an empty body; ResourceNotFoundException is modelled on the operation (Smithy: DeleteThingType errors = InternalFailureException 500, InvalidRequestException 400, ResourceNotFoundException 404, ServiceUnavailableException 503, ThrottlingException 400, UnauthorizedException 401; http DELETE /thing-types/{thingTypeName}, success code 200) but the recording shows AWS does not use it for a repeat delete. Emulator: answers 404 with body {"__type": "ResourceNotFoundException", "message": "Thing Type <account>:<thingTypeName> not found."} — both the status and the account-qualified sentence are the emulator's. Why: teardown and retry logic that deletes a thing type twice (or deletes one it never created) fails against the emulator where it succeeds on AWS, so idempotent cleanup paths break. Fix: the DeleteThingType handler must treat an absent thing type as a successful no-op (200, empty body). Traces: iot-thing-type-and-thing-lifecycle#task#7, iot-thing-type-create-delete-then-error#task#1.

Cause 4 of 6: DescribeScheduledAudit's not-found sentence is emulator-authored. AWS: Smithy DescribeScheduledAudit (GET /audit/scheduledaudits/{scheduledAuditName}) raises ResourceNotFoundException (httpError 404) for an unknown name; the recorded 404 body words it 'Resource scheduledAuditName=<name> was not found' — fixed text 'Resource scheduledAuditName=' + the requested name from the request path + ' was not found', with no account qualifier and no trailing period. Emulator: same status 404 but message 'Scheduled audit <name> does not exist.' Why: the status is right, so a client that matches on the message (log scrapers, assertion suites, error-classifying wrappers) misreads an otherwise correct refusal. Fix: the DescribeScheduledAudit not-found refusal in its handler/validation must emit AWS's template with the requested name substituted. Traces: iot-scheduled-audit-duplicate-and-not-found-errors#task#2, iot-scheduled-audit-invalid-daymonth-error#task#2, iot-scheduled-audit-not-found-paths#task#1, iot-scheduled-audit-weekly-lifecycle#task#3.

Cause 5 of 6: ListV2LoggingLevels' NotConfiguredException sentence is reworded. AWS: Smithy ListV2LoggingLevels raises NotConfiguredException (httpError 404, member message); the recorded body words it exactly 'SetV2LoggingOptions was not previously called. No logging levels have been set.' — wholly fixed text, nothing interpolated. Emulator: 404 with 'SetV2LoggingOptions was not previously called. No logging options have been set.' ('logging options' for AWS's 'logging levels'). Why: the message is the only thing distinguishing this refusal's cause to an operator or a message-matching client; the altered noun makes the emulator's text a defect even though the status and error class are right. Fix: correct the fixed sentence in the ListV2LoggingLevels handler's not-configured refusal. Traces: iot-v2-logging-for-thing-group#task#3.

Cause 6 of 6: DescribeFleetMetric's 404 message does not match the recording. AWS: Smithy DescribeFleetMetric (GET /fleet-metric/{metricName}) raises ResourceNotFoundException (httpError 404) for an unknown metric. Recorded behavior only for the text: the recorded 404 asserts the message 'An error occurred (ResourceNotFoundException) when calling the DescribeFleetMetric operation: FleetMetric <account>:<metricName> not found.', whereas the emulator sends only the trailing 'FleetMetric <account>:<metricName> not found.' The fixed parts are the error-class/operation prefix and the ' not found.' suffix; '<account>:<metricName>' comes from the caller's account and the request path. Hypothesis: the recorded expectation is the client-library stringification of the ClientError rather than a second wire member, in which case the emulator's own sentence is the AWS-shaped one and this cause is a capture artefact — confirm against AWS's DescribeFleetMetric 404 body before changing the message, and if the prefix is real it belongs in the DescribeFleetMetric not-found refusal. Fix: the DescribeFleetMetric handler's not-found refusal text (verify first, per the hypothesis above). Traces: iot-fleet-indexing-error-paths#task#1, iot-fleet-indexing-error-paths#task#4, iot-fleet-metric-lifecycle#task#4, iot-fleet-metric-lifecycle#task#7.
