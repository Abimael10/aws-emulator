# CodeDeploy: a zero-match Server deployment group fails INVALID_REVISION instead of NO_INSTANCES, an on-premises instance target goes straight to Failed instead of InProgress, and the DEPLOYMENT_FAILURE auto-rollback sequence never completes (3 causes, 4 checks)

> _Note: this issue was identified against the code base at commit `69e9858202f2bcdead1dc90355ba2555eebc8e9a`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
CreateDeployment

## Description
Three distinct, independent root causes in the CodeDeploy EC2/On-premises (Server) deployment execution path, found by four behavioral checks. Each must be closed before this issue is submitted.

None of these is carried by an existing open issue. 20261120T163729Z-codedeploy-server-platform-deployments-never-resolve-ec2tagfilters-to.md describes the INVERSE of Cause 1 (NO_INSTANCES emitted although tagged instances exist) and its replay keys are on different checks; 20261120T191449Z-codedeploy-in-place-deployment-never-resolves-instance-targets.md and 20261121T045802Z-codedeploy-server-platform-in-place-deployments-now-reach.md describe EC2 in-place target resolution, file installation, lifecycleEvents population and the minimumHealthyHosts schedule, not the error-code precedence of Cause 1, the on-premises target status of Cause 2, nor the non-termination of Cause 3.

=== Cause 1 of 3: a Server-platform deployment whose deployment group matches zero targets is failed with errorInformation.code INVALID_REVISION, because the revision bundle is validated BEFORE target resolution. ===
Failing check ids for this cause: codedeploy.deploy-codedeploy-application-behaves, codedeploy.e2e-application-deployment-revision-flow.
AWS: Smithy (codedeploy, CodeDeploy_20141006) models DeploymentInfo.errorInformation as ErrorInformation{code: ErrorCode, message}, and ErrorCode's enum contains both NO_INSTANCES and INVALID_REVISION (documented under "Error Codes for CodeDeploy"). NO_INSTANCES is the code for a deployment group whose selectors (ec2TagFilters / onPremisesInstanceTagFilters / autoScalingGroups) resolve to no target at all. Recorded behavior only for the PRECEDENCE between the two: both recordings create a Server-platform group whose only selector is an ec2TagFilters KEY_AND_VALUE filter on a tag value no instance carries, then CreateDeployment with an S3 revision whose object is deliberately NOT a valid bundle (plain bytes, no appspec.yml), and real AWS still ends the deployment Failed with errorInformation.code NO_INSTANCES — i.e. the empty-fleet check is evaluated before the bundle is fetched or parsed, so a bad bundle never masks an empty fleet. The required message for that class is AWS's fixed text "The deployment failed because no instances were found for your deployment group. Check your deployment group settings to make sure the tags for your Amazon EC2 instances or Auto Scaling groups correctly identify the instances you want to deploy to, and then try again." (fixed text only; it carries no request- or state-derived variable parts).
Emulator: CreateDeployment is accepted and the deployment does reach terminal status Failed (that assertion passes), but errorInformation reads {'code': 'INVALID_REVISION', 'message': 'The AppSpec file cannot be located in the specified S3 bucket. Verify your AppSpec file is present and that the name and key value pair specified for your S3 bucket are correct. The S3 bucket must be in your current region'} instead of NO_INSTANCES with the text above. The emulator evidently parses/validates the revision bundle first and short-circuits, so the empty-fleet condition is never reported. The bucket/key/tag values in the recordings are per-run values; the requirement is the code (and its message) a zero-match group must yield regardless of bundle contents.
Why: a client cannot distinguish a deployment-group targeting mistake from a packaging mistake. Pipelines and runbooks branch on errorInformation.code — NO_INSTANCES means "fix your tags/fleet", INVALID_REVISION means "fix your bundle" — so every zero-fleet deployment sends the operator to investigate an artifact that is not the problem, and automation that retries on NO_INSTANCES (waiting for instances to register) never fires.
Fix: the CreateDeployment execution path's failure classification for compute platform Server — target resolution must run before revision retrieval/AppSpec parsing, and a deployment group that resolves no target must terminate the deployment Failed with errorInformation.code NO_INSTANCES and AWS's NO_INSTANCES message; INVALID_REVISION must only be reachable once at least one target resolved.
Traces: codedeploy.deploy-codedeploy-application-behaves (CFN-created application/group), codedeploy.e2e-application-deployment-revision-flow (API-created application/group).

=== Cause 2 of 3: an on-premises instance target is reported Failed as soon as it leaves Pending, instead of InProgress once CodeDeploy dispatches to it. ===
Failing check ids for this cause: codedeploy.deployment-target-lifecycle-transitions.
AWS: Smithy (codedeploy, CodeDeploy_20141006) — ListDeploymentTargets/GetDeploymentTarget return DeploymentTarget{deploymentTargetType: 'InstanceTarget', instanceTarget: InstanceTarget{targetId, targetArn, status: TargetStatus, lastUpdatedAt, lifecycleEvents}}; TargetStatus's enum is Pending | InProgress | Succeeded | Failed | Skipped | Unknown | Ready, and InstanceTarget.status is documented as "The status an EC2/On-premises deployment's target instance". Recorded behavior: for a Server-platform group selected by onPremisesInstanceTagFilters over instances registered with RegisterOnPremisesInstance (no agent ever polls, because there is no host behind the registration), AWS enumerates the target and moves it Pending -> InProgress when it dispatches the deployment to it, and it STAYS InProgress — the service does not fail a target merely because the registered on-premises agent has not reported; failure requires either a hook/lifecycle result or a timeout.
Emulator: the target is listed (targetIds contains the registered instance name) and GetDeploymentTarget returns deploymentTargetType 'InstanceTarget' with the right targetId, but instanceTarget.status leaves Pending for 'Failed' immediately: "expected InProgress (target is enumerated as soon as codedeploy dispatches to it, before any on-premises agent ever polls), got 'Failed'". The instance name and deployment id are per-run values; the requirement is the status an enumerated, just-dispatched target reports.
Why: a client polling GetDeploymentTarget / BatchGetDeploymentTargets to follow an on-premises rollout sees an immediate, unexplained target failure and concludes its registered host rejected the deployment. Any orchestration that treats a Failed target as terminal (alerting, aborting the pipeline, rolling back) fires on the very first poll, and the normal Pending -> InProgress progression on which progress reporting depends is never observable.
Fix: the on-premises branch of the deployment execution path's instance-target state machine — a target that has been dispatched to must be recorded InProgress (with lastUpdatedAt) and only transition to Failed on an actual lifecycle-event failure or timeout, not as the default terminal state when no agent reports.
Traces: codedeploy.deployment-target-lifecycle-transitions.

=== Cause 3 of 3: the automatic DEPLOYMENT_FAILURE rollback sequence never completes — the check hangs and is killed by the harness, with no terminal state or rollback attribution observable. ===
Failing check ids for this cause: codedeploy.auto-rollback-on-deployment-failure-reinstalls-the-prior-artifact.
AWS: Smithy (codedeploy, CodeDeploy_20141006) — CreateDeploymentGroup/DeploymentGroupInfo carry autoRollbackConfiguration (AutoRollbackConfiguration{enabled, events: AutoRollbackEvent[]}) whose AutoRollbackEvent enum includes DEPLOYMENT_FAILURE. When a deployment of such a group ends Failed, CodeDeploy itself creates a NEW deployment of the last successful revision: GetDeployment on the failed deployment reports rollbackInfo.rollbackDeploymentId pointing at it, and GetDeployment on the rollback reports creator 'codeDeployRollback' (DeploymentCreator enum) and rollbackInfo.rollbackTriggeringDeploymentId pointing back at the failed deployment, reaching a terminal status (Succeeded) with the prior revision's bytes reinstalled on the target. Recorded behavior: the recording deploys revision A successfully, then revision B whose ValidateService hook exits 1, and observes the failed deployment reach terminal Failed, the rollback deployment appear and reach Succeeded, and the host's deployed file read back as revision A's content.
Emulator: the whole sequence never gets there — the replay ends "Check timed out after 60.0s" with no assertion reached, so the emulator never drove this group's failure-then-rollback progression to any observable terminal/attributed state inside the budget in which its sibling Server-platform checks (e.g. codedeploy.ec2-agent-deployment-runs-appspec-hook-on-instance, codedeploy.file-exists-behavior-disallow-blocks-foreign-file-and-overwrite-replaces-it) now complete. The check's blocking waits are, in order: revision B's bytes appearing on the host, the failing deployment reaching a terminal status, rollbackInfo.rollbackDeploymentId appearing on it, and the rollback deployment reaching a terminal status — so the stall is in that chain. Hypothesis: no rollback deployment is created for autoRollbackConfiguration {enabled: true, events: ['DEPLOYMENT_FAILURE']}, so rollbackInfo stays empty and the wait never satisfies. Note that this check id appears in the trace lists of open issues 20261120T163729Z and 20261121T045802Z, but under different replay keys (assertions on the positive control's deployment status and on the installed payload) — this non-termination is a distinct failure neither carries.
Why: a client relying on CodeDeploy's own safety net gets neither the rollback nor a terminal answer. A failed deployment that never produces rollbackInfo leaves the broken revision live on the fleet while the caller's poll loop spins, so automated rollback — the main reason autoRollbackConfiguration is set — is unusable and failure handling in the client hangs instead of erring.
Fix: the deployment state machine's auto-rollback trigger in the Server-platform execution path — when a deployment of a group whose autoRollbackConfiguration names DEPLOYMENT_FAILURE ends Failed, it must create a distinct rollback deployment of the last successful revision, set rollbackInfo.rollbackDeploymentId on the failed deployment and creator 'codeDeployRollback' + rollbackInfo.rollbackTriggeringDeploymentId on the rollback, and drive that rollback to a terminal status (reinstalling the prior revision on the target); every leg of the chain must advance to a terminal/attributed state rather than never settling.
Traces: codedeploy.auto-rollback-on-deployment-failure-reinstalls-the-prior-artifact.

## Evidence
Cause 1 — zero-match deployment group, wrong errorInformation.code.
  Expected (AWS): GetDeployment -> deploymentInfo.status 'Failed' and errorInformation {'code': 'NO_INSTANCES', 'message': 'The deployment failed because no instances were found for your deployment group. Check your deployment group settings to make sure the tags for your Amazon EC2 instances or Auto Scaling groups correctly identify the instances you want to deploy to, and then try again.'} — even when the S3 object named by the revision is not a valid bundle, because target resolution precedes revision validation. That message is fixed text with no variable parts.
  Actual (emulator): status 'Failed' (correct) but
    - codedeploy.deploy-codedeploy-application-behaves: "expected errorInformation.code=NO_INSTANCES for a zero-match deployment group, got {'code': 'INVALID_REVISION', 'message': 'The AppSpec file cannot be located in the specified S3 bucket. Verify your AppSpec file is present and that the name and key value pair specified for your S3 bucket are correct. The S3 bucket must be in your current region'}"
    - codedeploy.e2e-application-deployment-revision-flow: "expected errorInformation.code=NO_INSTANCES, got 'INVALID_REVISION'"
  Bucket names, keys, tag values, application/group names and deployment ids are per-run values.

Cause 2 — on-premises instance target status.
  Expected (AWS): after ListDeploymentTargets returns the registered on-premises instance name, GetDeploymentTarget returns deploymentTargetType 'InstanceTarget' and instanceTarget.status 'InProgress' once dispatched (Pending beforehand); it is not 'Failed' merely because no agent reports.
  Actual (emulator): codedeploy.deployment-target-lifecycle-transitions — "expected InProgress (target is enumerated as soon as codedeploy dispatches to it, before any on-premises agent ever polls), got 'Failed'". The target leaves Pending directly for the terminal Failed status. Instance name and deployment id are per-run values.

Cause 3 — DEPLOYMENT_FAILURE auto-rollback never settles.
  Expected (AWS): with autoRollbackConfiguration {enabled: true, events: ['DEPLOYMENT_FAILURE']}, the deployment whose ValidateService hook exits 1 reaches terminal 'Failed'; GetDeployment on it then reports rollbackInfo.rollbackDeploymentId (a DIFFERENT deployment id); GetDeployment on that rollback reports creator 'codeDeployRollback', rollbackInfo.rollbackTriggeringDeploymentId = the failed deployment, a terminal status, and the previous revision's bytes back in the deployed file on the host.
  Actual (emulator): codedeploy.auto-rollback-on-deployment-failure-reinstalls-the-prior-artifact — "Check timed out after 60.0s". No assertion was reached, so the exact stall point in the (install B -> terminal Failed -> rollbackInfo appears -> rollback terminal) chain is not pinned by the replay; sibling Server-platform EC2/SSM checks that share this fixture shape complete within the same budget in this run, and the group's autoRollbackConfiguration is read back correctly before the sequence starts (that assertion is upstream of the stall).

## Steps to Reproduce
Cause 1:
1. codedeploy:CreateApplication(applicationName=<app>, computePlatform='Server') (directly, or via an AWS::CodeDeploy::Application CFN resource).
2. iam:CreateRole trusted by codedeploy.amazonaws.com with AWSCodeDeployRole attached; codedeploy:CreateDeploymentGroup(applicationName=<app>, deploymentGroupName=<dg>, serviceRoleArn=<role>, ec2TagFilters=[{Key:'sim2real-unmatched-tag', Value:'<value no instance carries>', Type:'KEY_AND_VALUE'}]).
3. s3:CreateBucket + s3:PutObject(Key='app.zip', Body=b'not-a-zip').
4. codedeploy:CreateDeployment(applicationName=<app>, deploymentGroupName=<dg>, revision={revisionType:'S3', s3Location:{bucket, key:'app.zip', bundleType:'zip'}}).
5. Poll codedeploy:GetDeployment until terminal. Observe status 'Failed' with errorInformation.code 'INVALID_REVISION' ("The AppSpec file cannot be located in the specified S3 bucket...") instead of 'NO_INSTANCES' with AWS's no-instances message.

Cause 2:
1. codedeploy:CreateApplication(computePlatform='Server'); iam:CreateUser; codedeploy:RegisterOnPremisesInstance(instanceName=<name>, iamUserArn=<user arn>); codedeploy:AddTagsToOnPremisesInstances(tags=[{Key:'sim2real-tag', Value:<v>}], instanceNames=[<name>]).
2. codedeploy:CreateDeploymentGroup with onPremisesInstanceTagFilters=[{Key:'sim2real-tag', Value:<v>, Type:'KEY_AND_VALUE'}] and a codedeploy service role.
3. s3:PutObject a minimal zip (b'PK\x05\x06' + 18 zero bytes); codedeploy:CreateDeployment with that S3 revision.
4. Poll codedeploy:ListDeploymentTargets(deploymentId) until non-empty (DeploymentNotStartedException before that), then codedeploy:GetDeploymentTarget(deploymentId, targetId=<name>) until instanceTarget.status != 'Pending'.
5. Observe instanceTarget.status 'Failed' instead of 'InProgress', with no agent having reported anything.

Cause 3:
1. s3:PutObject two Server revisions: A whose ValidateService hook exits 0, B whose ValidateService hook exits 1 (blocking until a release marker file is touched), both installing a payload file carrying a distinct marker.
2. Launch one tagged t3.micro instance that becomes an Online SSM managed node; codedeploy:CreateApplication(computePlatform='Server'); codedeploy:CreateDeploymentGroup(deploymentConfigName='CodeDeployDefault.AllAtOnce', ec2TagFilters matching that tag, autoRollbackConfiguration={enabled:true, events:['DEPLOYMENT_FAILURE']}).
3. Deploy revision A and wait for 'Succeeded'.
4. Deploy revision B; once its bytes are on the host, release its ValidateService hook so it exits 1, and poll codedeploy:GetDeployment until terminal.
5. Poll codedeploy:GetDeployment on the failed deployment for rollbackInfo.rollbackDeploymentId, then poll the rollback deployment for a terminal status, creator 'codeDeployRollback' and rollbackInfo.rollbackTriggeringDeploymentId. Observe the sequence never settles (the client poll loop never satisfies within minutes), so no rollback deployment or attribution is ever readable and the host keeps revision B's bytes.
