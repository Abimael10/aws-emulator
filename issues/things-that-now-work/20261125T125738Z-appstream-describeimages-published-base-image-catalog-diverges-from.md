# appstream DescribeImages published base-image catalog diverges from AWS: wrong record fields and the Rocky Linux 8 graphics families are missing entirely

> _Note: this issue was identified against the code base at commit `f468f37ea639de53f535b93618c112f23df311d1`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
DescribeImages

## Description
Four net-new causes, all in the seeded published base-image catalog that DescribeImages reads (services/service-com-amazonaws-appstream-photonadminproxyservice/src/state/images.rs) and in the ImageRecord -> Image projection it is rendered through. Three causes are the SAME set of wrong/absent record fields observed on three different reads of the catalog (a multi-image listing, a RHEL 8 read, a Rocky Linux 8 read); the fourth is a whole family of published images the catalog does not contain at all, which turns a request AWS answers 200 into an HTTP 400 refusal. A fixer must close all four. No open appstream issue covers DescribeImages or the image catalog (the open ones are the asvpce CreateStack/UpdateStack validation bundle, the CloudFormation AWS::AppStream::* resource-type refusal, and the UpdateAppBlockBuilder / AssociateApplicationToEntitlement stubs).

AWS: Smithy: DescribeImages -> DescribeImagesResult{Images: ImageList} of Image; Image.Description (String, len 1.., doc "The description to display"), Image.CreatedTime (Timestamp, doc "The time the image was created"), Image.PublicBaseImageReleasedDate (Timestamp), Image.SupportedInstanceFamilies (StringList), Image.ImageSoftwareMetadata -> ImageSoftwareMetadata{nvidiaGridDriverVersion, @pattern ^[0-9]+(\.[0-9]+){1,2}$, doc "The version of the NVIDIA GRID driver installed on the image. For a PUBLIC base image AWS reports, per image: (a) the published description AWS words per operating system and per accelerator, in the form "AppStream <operating system as AWS words it> image for launching [Graphics <accelerator> ]image builder instances" — the recording shows 'AppStream redhat linux (RHEL 8) image for launching image builder instances' for the general-purpose RHEL 8 image, 'AppStream redhat linux image (RHEL 8) for launching Graphics G4dn image builder instances' for its G4dn variant and 'AppStream Rocky Linux 8 image for launching image builder instances' for Rocky Linux 8 (those strings are examples of the published text, not a template to interpolate); (b) CreatedTime as the instant the image was actually built — a per-image, millisecond-precision timestamp strictly later than both the batch date in the image's name and the recipe release instant (e.g. 1762839393.965 for the 11-10-2025 RHEL 8 image); (c) SupportedInstanceTypeGroups ALWAYS present, as an empty list on a published base image; (d) appStreamRecipeArn as the ARN of the EC2-Image-Builder-style recipe the image was built from, in the `amifarm` namespace, owned by an AWS-internal account, naming a recipe shared by all images of one operating-system/accelerator combination with a trailing version segment that advances per release batch (e.g. arn:aws:amifarm:us-west-2:121014824124:recipe/AppStreamRHEL8GraphicsG4Recipe/10 then .../11 for the next batch); (e) appStreamRecipeReleaseTimestamp as that recipe's own release instant, which does NOT track the image's name date and is shared across batches (the recording reports the same 1762819200.0 on images of the 11-10-2025, 02-18-2026 and 04-16-2026 batches); (f) ImageSoftwareMetadata populated with nvidiaGridDriverVersion on the graphics images of the newest batches; (g) for the Graphics-NV image, four SupportedInstanceFamilies entries (indices 0-3 all diverge; the replay detail truncates the expected values).
Emulator: images.rs derives all of this from the row instead of carrying what the catalog publishes. Description is generated as "AppStream 2.0 {accelerator} graphics base image for {os}" / "AppStream 2.0 base image for {os}" (PublishedImage::description), so the listing answers e.g. 'AppStream 2.0 G4dn graphics base image for Red Hat Enterprise Linux 8' and 'AppStream 2.0 base image for Red Hat Enterprise Linux 8'. CreatedTime and appStreamRecipeReleaseTimestamp are both set to midnight UTC of the date in the image's name (PublishedImage::record: `let released = instant("<date>T00:00:00Z")`, then `created_time: released` and `appstream_recipe_released: Some(released)`), so both lose the published instants and collapse to one value. appStreamRecipeArn is synthesised in this service's own namespace from the image's own name (published_recipe_arn -> arn:aws:appstream:<region>::recipe/<image name>). ImageRecord has no SupportedInstanceTypeGroups field at all, so the key is absent from the response (replay: "SupportedInstanceTypeGroups: missing (expected [], got None)"). image_software_metadata is hardcoded `None` for every published row. supported_instance_families for a graphics row is the single invented `Graphics <token>` family of its accelerator.
Why: a client picking an image from the catalog reads these fields. The description is what consoles and inventory tooling display and what users match on ("image for launching image builder instances"); an absent SupportedInstanceTypeGroups key makes code that iterates the list raise instead of seeing an empty list; the recipe ARN is the provenance pointer to the build the image came from, and an `appstream` ARN derived from the image name resolves to nothing and tells a client the wrong owning service; a CreatedTime pinned to midnight of the release date makes every image of a batch look simultaneous and makes recipe-release vs image-build ordering comparisons wrong; a missing ImageSoftwareMetadata hides the NVIDIA GRID driver version that GPU workloads gate on; and a Graphics-NV image advertising one family instead of four makes a client reject instance types the image really supports.
Fix: the seeded catalog rows and their projection in services/service-com-amazonaws-appstream-photonadminproxyservice/src/state/images.rs — carry the published description, build instant, recipe ARN (namespace/account/recipe name/version), recipe release instant, software metadata and supported instance families per published image rather than deriving them from the row's name/accelerator, and add SupportedInstanceTypeGroups to ImageRecord/ImageRecord::to_image so it is always reported (empty on a base image).
