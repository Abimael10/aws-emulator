# agent-registry: 3 net-new causes — SearchDiscoverableRegistryRecords never matches a multi-word query, ListDiscoverableRegistryRecords does not validate filter VALUES, BatchGet per-record errors carry a message AWS omits

> _Note: this issue was identified against the code base at commit `83b924bfca64d21d2064b8fa56823232662207f8`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

SearchDiscoverableRegistryRecords

## Description
Three net-new root causes on service `agent-registry` (AgentRegistry, sdkId 'Agent Registry', restJson1, sigv4, 3 bound operations), all grounded in failing behavioral checks of the discovery data plane. The service IS reachable and IS bootstrapped in this build (crate service-com-amazonaws-agentregistry-agentregistry present, get_bootstrap_status reports nothing pending): registries and records created through AgentRegistryControl are now visible to the data plane, list returns 200 with records, and batch-get returns partial results — so these are handler/validation/search-ranking gaps, not a bootstrap or shared-state gap. All THREE causes must be closed and the named checks re-replayed; they are independent of one another.

Relation to already-open issues (none covers these three): 20261111T095408Z-agent-registry-discovery-reads-answer-404-registry-not-found-for.md is a WIRE issue whose Cause 2 describes the same filter rule but as a 404 'Registry not found' PRE-EMPTING validation; that pre-emption is gone (the call now SUCCEEDS with 200 and records), so what remains is the absence of the validation itself, which that issue's keys (status=400->404) do not describe. 20261107T045822Z-agent-registry-listdiscoverableregistryrecords-validationexception-enumerates-the-filter-name-enum-value.md concerns only the ORDER of the enum value set inside the filter-NAME ValidationException message, not filter VALUES. 20261111T015212Z-agent-registry-discovery-reads-never-see-a-registry.md describes the shared-state root cause, which no longer reproduces. The suite marked none of these checks ALREADY FILED or OWNED.

--- Cause 1 of 3: ListDiscoverableRegistryRecords accepts a `recordType` filter carrying more than one value (and an unknown value) and serves 200 instead of refusing it with 400 ValidationException.
AWS: Smithy ListDiscoverableRegistryRecords (POST /registries/{registryId}/discoverable-records-list, http code 200, @readonly, @paginated) input member `filters` -> RegistryRecordFilterList @length max 10 of RegistryRecordFilter{name: REQUIRED enum RegistryRecordFilterName [recordType, descriptorType], values: REQUIRED DiscoverableFilterValues @length 1..10}; modeled error ValidationException errorKind client httpError 400, members message (required), reason (required, enum, default FieldValidationFailed), fieldList. The list shape admits up to 10 values, so the single-value rule is recorded behavior, not a model constraint: AWS refuses a filter with two values with HTTP 400 ValidationException and message "Filter recordType must specify exactly one value." — fixed text "Filter " ... " must specify exactly one value." with the filter NAME taken from the request as its only variable part — and refuses a filter whose value is not a member of the filtered field's value set with HTTP 400 ValidationException and message "Invalid value for filter recordType: NOTATYPE" — fixed text "Invalid value for filter " ... ": " with the filter name and the offending value both taken from the request. (The names/values shown are the request's own values filling that template, not literals of the contract.)
Emulator: the two-value filter is served as a successful read — HTTP 200 with content-type application/json and a `registryRecords` list containing BOTH the AGENT record and the CUSTOM record (the values are OR-ed), so the check's expected rejection never happens. The unknown-value case is never reached because the run stops at the first assertion, but the same handler path shows no value validation at all: it validates only the filter NAME against the RegistryRecordFilterName value set and then applies the values as a match set.
Why: a client that mis-spells a record type or passes a list where exactly one value is allowed is silently served a WIDER result set than it asked for instead of being told its input is wrong — a filter typo degrades into a full, unfiltered-looking listing, and discovery logic that trusts the filter to narrow the page acts on records it explicitly excluded. Error classifiers never see the ValidationException branch (no 400, no reason, no fieldList).
Fix: the ListDiscoverableRegistryRecords input-validation path in the agent-registry crate — after the filter-name check, enforce one value per filter and membership of each value in the filtered dimension's value set, emitting the modeled ValidationException (400, x-amzn-errortype ValidationException, required message/reason) with the two message templates above, before any record is read.
Traces: agent-registry.list-discoverable-filters-by-record-and-descriptor-type (the recordType=[MCP] and descriptorType=[a2aAgentCard] positive filters in the same check PASS; only the refusals diverge). Source: services/service-com-amazonaws-agentregistry-agentregistry/src/ops/list_discoverable_registry_records.rs lines 157-178 validate `filters[].name` only; `values` is never checked for count or membership.

--- Cause 2 of 3: SearchDiscoverableRegistryRecords matches a record only when the ENTIRE searchQuery occurs as a contiguous substring of one stored text field, so a multi-word natural-language query never returns the records it matches on AWS.
AWS: Smithy SearchDiscoverableRegistryRecords (POST /discoverable-records-search, http code 200), documented "Searches the discoverable registry records in a registry using a natural language query. Returns metadata for the matching records ordered by relevance"; input searchQuery (SearchQuery, len 0..256) REQUIRED, registryIds REQUIRED (exactly one), maxResults (1..20, default 10), filters (MetadataFilterExpression); output registryRecords REQUIRED. The matching rule is recorded behavior only: a search whose query words occur, in any order and not adjacently, in a discoverable record's description returns that record — the recordings search for "harbor tide forecast" and AWS returns the APPROVED record described "Tide and storm surge forecasts for harbor pilots" (and only the APPROVED one; its DRAFT and PENDING_APPROVAL twins with the same description are excluded).
Emulator: the search returns an EMPTY registryRecords list for that query, forever — both checks poll SearchDiscoverableRegistryRecords until the record becomes searchable and the record never appears, so each check ends on its poll (reported as the run budget expiring, i.e. the wait never converged rather than a wrong single response; the responses themselves are HTTP 200 with registryRecords: []). The mechanism is a whole-query substring test: relevance() lowercases the query and asks whether one of name / displayName / description `contains` that entire string, so any query of more than one word — the documented natural-language case — can only match text containing that exact phrase.
Why: the service's only natural-language read is unusable. A caller that publishes a record and then searches for it by a human query gets an empty page with HTTP 200 (not an error it can retry or diagnose), so publish-then-discover never completes; relevance ordering, maxResults truncation and the APPROVED-only projection are all unobservable behind the empty result.
Fix: the SearchDiscoverableRegistryRecords handler's relevance/matching component in the agent-registry crate — match the query's TERMS against the record's searchable text (name, displayName, description) rather than requiring the whole query string as one substring, and keep ordering by the most specific field matched. The customMetadata $eq filter evaluation in the same handler is not implicated: the filter walk is only reached for records that already matched the query.
Traces: agent-registry.search-excludes-unapproved-records, agent-registry.search-custom-metadata-filter-narrows-results. Source: services/service-com-amazonaws-agentregistry-agentregistry/src/ops/search_discoverable_registry_records.rs lines 196 and 312-324 (`query = input.search_query.to_lowercase()` then `text.to_lowercase().contains(query)`).

--- Cause 3 of 3: BatchGetDiscoverableRegistryRecord populates a `message` on every per-record RESOURCE_NOT_FOUND error, where AWS returns the error entry with registryId, recordId and errorCode only.
AWS: Smithy BatchGetDiscoverableRegistryRecord (POST /discoverable-records-batch, http code 200); output registryRecords and errors both REQUIRED; BatchGetDiscoverableRegistryRecordError members registryId (REQUIRED, echoed from the request), recordId (REQUIRED, echoed in the format supplied), errorCode (REQUIRED, enum [RESOURCE_NOT_FOUND, ACCESS_DENIED, INTERNAL_ERROR]) and message (OPTIONAL). Recorded behavior only for whether it is populated: for a record that is not discoverable, AWS emits exactly {registryId, recordId, errorCode: RESOURCE_NOT_FOUND} and emits NO message member for this error class — in both recordings (an unpublished/absent record, and a record withdrawn by deprecation) the entry has three members.
Emulator: each error entry additionally carries message: "No discoverable registry record was found for this identifier." — a fixed sentence the handler hard-codes for every RESOURCE_NOT_FOUND entry. Status (200), errorCode, registryId and recordId echoing all match; the extra member is the only divergence.
Why: the per-entry error object is part of the response contract: a client that compares, hashes or logs whole error entries (or asserts on them in tests) sees a member AWS never sends, and a consumer that reads `message` on AWS gets nothing there while on the emulator it gets a sentence AWS does not word — exactly the programmatic dependence the member's own doc warns against, induced by the emulator.
Fix: the BatchGetDiscoverableRegistryRecord handler/serializer in the agent-registry crate — leave `message` absent for a per-record RESOURCE_NOT_FOUND entry so the serialized entry carries only registryId, recordId and errorCode.
Traces: agent-registry.batch-get-reports-unpublished-records-per-entry, agent-registry.deprecating-approved-record-removes-it-from-discovery (in the second check the deprecated record is correctly withdrawn from both the listing and the batch read — only the extra message member fails the assertion). Source: services/service-com-amazonaws-agentregistry-agentregistry/src/ops/batch_get_discoverable_registry_record.rs lines 236-246.
