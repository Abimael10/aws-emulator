# apigatewayv2: 3 net-new causes — the CORS preflight layer answers OPTIONS even when a route matches it (authorizer and integration bypassed), a CFN in-place update never clears CorsConfiguration, and a created custom domain name is not a served host

> _Note: this issue was identified against the code base at commit `af00353512b8f96b4224cdf0a6e66e42785b9365`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
CreateApi

## Description
Three net-new root causes in the apigatewayv2 HTTP-API data plane and its CloudFormation/custom-domain surface. Each cause is listed with its own failing check ids; all three must be closed before submitting.

Cause 1 of 3: the CORS layer intercepts every OPTIONS preflight ahead of route matching, so a preflight that a route DOES match is answered by the gateway (204) instead of being served by that route — its authorization and its integration are both skipped. Failing checks: apigatewayv2.http-api-cors-preflight-caught-by-any-route-is-authorized, apigatewayv2.deploy-apigatewayv2-3-cdk-http-api-cors-lambda-default-route-serves-then-destroys.
AWS: Smithy (services/service-com-amazonaws-apigatewayv2-apigatewayv2): CreateApi member CorsConfiguration : Cors (AllowOrigins/AllowMethods/AllowHeaders/ExposeHeaders/AllowCredentials/MaxAge @range -1..86400, 'Supported only for HTTP APIs', doc link https://docs.aws.amazon.com/apigateway/latest/developerguide/http-api-cors.html); CreateRoute member AuthorizationType (AWS_IAM) and RouteKey. The model does not describe the data plane, so the dispatch rule is the documented CORS rule plus recorded behavior: API Gateway answers the preflight ITSELF only when no route matches the OPTIONS request. When a route matches it — 'ANY /{proxy+}', or the '$default' catch-all CDK creates for a defaultIntegration — the OPTIONS request is routed like any other request: the route's authorizer runs first and the integration is invoked, and the CORS headers are then stamped on that response. Required shapes: (a) an unsigned preflight matched by an AWS_IAM route is refused HTTP 403 with body {"message":"Forbidden"} ('Forbidden' is the fixed text, there are no variable parts); (b) a preflight matched by a '$default' AWS_PROXY route reaches the Lambda and is answered HTTP 200 with the integration's own body, plus access-control-allow-origin equal to the request's Origin and access-control-allow-methods equal to the configured AllowMethods; (c) only once no route matches OPTIONS (route narrowed to 'GET /{proxy+}') is the preflight answered 204 by CORS.
Emulator: OPTIONS is short-circuited by the CORS layer in all three situations. On the AWS_IAM 'ANY /{proxy+}' route the unsigned preflight is answered 204 with an empty body instead of 403 {"message":"Forbidden"} ('a preflight matched by the ANY route must be authorized by it; expected 403, got 204'), while the unsigned GET on the same route is correctly 403 — so the 204 is the CORS layer bypassing the route's authorization. On the CDK '$default' catch-all route the preflight is answered 204 with an empty body instead of 200 with the Lambda's {"marker":...,"path":"/","method":"OPTIONS"} answer ('preflight OPTIONS / from the allowed origin answered 204 \'\'; real AWS forwards it through the $default route to the Lambda and answers 200').
Why: a request AWS refuses 403 is served 204 by the emulator, so an AWS_IAM- or authorizer-protected route silently admits an unauthenticated OPTIONS — an authorization bypass that only shows up in AWS. Symmetrically, an application whose catch-all route must see the OPTIONS request (to emit its own headers or to count the call) never receives it, and the 204/200 and empty/integration-body difference makes browser and client behavior diverge.
Fix: the OPTIONS dispatch order in the apigatewayv2 execute-api HTTP data-plane handler: match the route first and let a matching route (including ANY and $default) own the request — authorizer, then integration — and apply the gateway-answered preflight only when no route matches the OPTIONS method.
Traces: apigatewayv2.http-api-cors-preflight-caught-by-any-route-is-authorized; apigatewayv2.deploy-apigatewayv2-3-cdk-http-api-cors-lambda-default-route-serves-then-destroys. Related but not covering: open issue 20261112T084959Z-apigatewayv2-3-net-new-causes-in-the-http.md (cause 1) filed the opposite defect — the preflight being 404'd instead of answered — and the suite did not attribute these failures to it; the gateway now answers the preflight but does so unconditionally.

Cause 2 of 3: a CloudFormation in-place update that drops CorsConfiguration from an AWS::ApiGatewayV2::Api leaves the old CORS configuration on the API. Failing check: apigatewayv2.deploy-apigatewayv2-1-http-api-cors-removed-in-place-then-api-replaced.
AWS: Smithy: UpdateApi — PATCH /v2/apis/{ApiId}, 200, member CorsConfiguration : Cors; DeleteCorsConfiguration — DELETE /v2/apis/{ApiId}/cors, 204. CloudFormation applies a removed resource property by resetting it on the live resource: an update whose change set is Modify/Replacement=False on the Api must leave the ApiId unchanged, apply the new Description, and remove the CORS configuration (the provisioner's job, via DeleteCorsConfiguration), after which GetApi returns NO CorsConfiguration member at all and a preflight with no OPTIONS route falls through to route matching and is answered 404.
Emulator: the physical ApiId and the new Description are correct, but GetApi still returns the pre-update configuration — 'removing CorsConfiguration from the template must remove it from the Api, GetApi still returns {\'AllowHeaders\': [...], \'AllowMethods\': [...], \'AllowOrigins\': [...], \'MaxAge\': ...}' (the member values shown are the create-phase template's values; the requirement is that the member is absent, not any particular value). Because the configuration survives, the preflight also keeps being answered instead of falling through.
Why: removing a property is the normal way an estate turns a feature off. A client that deploys the CORS-free template gets an API that still advertises the old allowlist and still answers preflights, so the deployed state silently differs from the template and from AWS — and re-enabling CORS later cannot be distinguished from never having removed it.
Fix: the AWS::ApiGatewayV2::Api update path of the CloudFormation provisioner in this emulator (reset properties absent from the new template — here by calling DeleteCorsConfiguration/clearing the Api's CorsConfiguration) together with UpdateApi's handling of a cleared CorsConfiguration in the apigatewayv2 crate.
Traces: apigatewayv2.deploy-apigatewayv2-1-http-api-cors-removed-in-place-then-api-replaced. Related but not covering: open issues 20261106T180247Z-apigatewayv2-a-cfn-provisioned-http-api-with-corsconfiguration.md (describes this check as a hang) and 20261027T053233Z-apigatewayv2-9-net-new-root-causes-api-mapping.md (CFN-declared CorsConfiguration never materialising); neither owns this check's replay key and the emulator now gets past both prefixes.

Cause 3 of 3: a custom domain name created through CreateDomainName / AWS::ApiGatewayV2::DomainName is not one of the hosts the emulator serves, so an API mapping on that domain can never be exercised. Failing check: apigatewayv2.deploy-api-mapping-cfn-behaves.
AWS: Smithy: CreateDomainName — POST /v2/domainnames, 201, member DomainNameConfigurations : DomainNameConfiguration (ApiGatewayDomainName, DomainNameStatus AVAILABLE, EndpointType, HostedZoneId); CreateApiMapping — POST /v2/domainnames/{DomainName}/apimappings, 201, members ApiId/Stage/ApiMappingKey. On AWS the customer CNAMEs the custom domain at ApiGatewayDomainName; the client then connects to that address but sends the custom domain as the TLS SNI and the Host header, and API Gateway resolves the API mapping from that domain + base path, reaching the mapped stage's integration (here an HTTP_PROXY to the check's own MOCK backend, answered 200 with the backend's token). The control-plane reads are already correct: GetApiMapping returns the stack's ApiId and Stage '$default', and GetDomainName reaches DomainNameStatus AVAILABLE.
Emulator: the custom domain host itself is never served. ApiGatewayDomainName is now accepted as an emulator host (the connect leg passes), but resolving a request addressed to the custom domain is refused by the harness before any request is made: simparity.published.PublishedUrlRejected 'endpoint_url was given http://<custom-domain> (published by the emulator or built by the check): its host is not one of the emulator\'s own hosts; a customer of the emulator needs http(s)://127.0.0.1:<port>/<resource path>, or http(s)://<own host>:<port>/<path> on a per-resource listener'. The custom domain in the recording is a per-run generated name and is not itself a requirement; what is required is that a domain a customer creates becomes reachable. With no reachable domain the API mapping has no observable effect at all.
Why: the whole point of a custom domain + API mapping is that clients address the API by that domain. A client that configures one on the emulator can drive the control plane but can never send it traffic, so base-path routing, multi-API mappings and domain-level TLS are untestable and an estate built on custom domains cannot run end to end.
Fix: CreateDomainName/UpdateDomainName (and the AWS::ApiGatewayV2::DomainName provisioner) in the apigatewayv2 crate must register the created domain as a served host — a per-resource listener / host alias on the emulator — and the execute-api front door must resolve an incoming Host/SNI naming a custom domain through the domain's API mappings (base path -> ApiId + Stage) to the mapped stage's integration.
Traces: apigatewayv2.deploy-api-mapping-cfn-behaves. Related but not covering: open issue 20261109T154749Z-apigatewayv2-5-net-new-root-causes-the-published.md (cause 2) covered the unreachable ApiGatewayDomainName value, which now resolves; the surviving gap is the custom domain host, and the suite did not attribute this failure to that issue.
