# CodeDeploy Server-platform deployments never resolve ec2TagFilters to tagged EC2 instances: every in-place deployment ends Failed/NO_INSTANCES (1 cause, 8 checks)

> _Note: this issue was identified against the code base at commit `eb149afeb17c64df33e2fc28f71e5890f0d7e7b3`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
CreateDeployment

## Description
Cause 1 of 1: a Server (EC2/on-premises) compute-platform deployment against a deployment group whose only target selector is ec2TagFilters is never matched to the running, tagged EC2 instances in the account. CreateDeployment is accepted (200, a deploymentId is returned), but the deployment immediately settles to status 'Failed' with errorInformation code NO_INSTANCES, so no instance target is ever created and no lifecycle event ever runs.

Failing check ids for this cause: codedeploy.agent-hands-the-hook-the-real-deployment-identifiers, codedeploy.applicationstop-hook-failure-blocks-redeploy-until-ignored, codedeploy.auto-rollback-on-deployment-failure-reinstalls-the-prior-artifact, codedeploy.deployment-group-alarm-in-alarm-state-blocks-the-deployment, codedeploy.ec2-agent-deployment-runs-appspec-hook-on-instance, codedeploy.file-exists-behavior-disallow-blocks-foreign-file-and-overwrite-replaces-it, codedeploy.hook-failure-skips-later-lifecycle-events-and-fails-the-target, codedeploy.lifecycle-event-order-and-applicationstop-only-on-redeploy.

AWS: CodeDeploy resolves a Server-platform deployment group's target fleet at deployment time by evaluating the group's EC2 tag selectors against the EC2 instances in the account/region. Smithy (codedeploy, CodeDeploy_20141006): DeploymentGroupInfo/CreateDeploymentGroupInput carry ec2TagFilters (EC2TagFilter{Key, Value, Type}) with EC2TagFilterType enum KEY_ONLY | VALUE_ONLY | KEY_AND_VALUE — a KEY_AND_VALUE filter selects every instance carrying that exact tag key and value. When at least one running instance matches, the deployment resolves that instance as an instanceTarget and drives it through the in-place lifecycle (ApplicationStop, DownloadBundle, BeforeInstall, Install, AfterInstall, ApplicationStart, ValidateService), reaching status 'Succeeded' when all hooks succeed. The modeled ErrorInformation.code enum value NO_INSTANCES (documented under "Error Codes for CodeDeploy") is reserved for the case where the group's selectors match NO instance at all; with a matching tagged instance present, AWS does not return it. Recorded behavior for these checks: each one launches one or two t3.micro AL2023 instances in a single RunInstances call with TagSpecifications tagging the instance at creation with the key/value the deployment group then filters on (Type=KEY_AND_VALUE), waits for the host to be a ready managed node, and expects the deployment to reach 'Succeeded'.

Emulator: every such deployment ends 'Failed' with errorInformation {'code': 'NO_INSTANCES', 'message': 'The deployment failed because no instances were found for your deployment group. Check your deployment group settings to make sure the tags for your Amazon EC2 instances or Auto Scaling groups correctly identify the instances you want to deploy to, and then try again.'} even though the tagged instances exist and are running (the checks hold their concrete instance ids and have already passed the host-readiness gate — e.g. the single-host checks report the target host id and its AZ in the assertion text). The error code and message text themselves match AWS's NO_INSTANCES wording; the divergence is that this outcome is produced at all — the emulator evidently does not evaluate ec2TagFilters against EC2's instance/tag state (or does not see EC2 instances from CodeDeploy's deployment execution path), so it treats every in-place group as having an empty fleet.

Why: the whole Server compute platform is unusable against this emulator. A client deploying to EC2 hosts by tag gets a deployment that fails instantly with NO_INSTANCES, so nothing downstream is observable or testable: AppSpec file installs, hook execution and hook environment variables (DEPLOYMENT_ID / APPLICATION_NAME / DEPLOYMENT_GROUP_NAME / LIFECYCLE_EVENT), the documented in-place lifecycle event order, ApplicationStop-only-on-redeploy semantics, hook-failure propagation to the instance target, fileExistsBehavior, alarm gating of a deployment, and auto-rollback reinstall of the previous revision. Worse, the failure is reported as a fleet-configuration mistake, so a client reading the message will go looking for a tagging bug in its own deployment group that does not exist.

Fix: the Server-platform target resolution step of the CreateDeployment execution path (the instance-target driver / deployment state machine for compute platform Server) must resolve the deployment group's ec2TagFilters — honouring KEY_ONLY, VALUE_ONLY and KEY_AND_VALUE — against EC2 instance tag state, register each matching running instance as an instanceTarget, and drive its lifecycle events; NO_INSTANCES must be emitted only when that resolution genuinely yields no instance. Related open issue 20261107T094623Z-codedeploy-no-server-platform-ec2-agent-deployment-check.md covers the earlier, upstream symptom for these same eight checks (a launched instance never becoming an Online SSM managed node) and does not cover this one: the checks now get past host readiness and fail at the deployment itself, so that issue does not carry this failure.

Traces: the eight failing check ids listed above; each stops at its first assertion on deployment status (the 'positive control' leg in the alarm, auto-rollback, fileExistsBehavior and hook-failure checks), with the identical NO_INSTANCES errorInformation.

## Evidence
Expected (AWS): with one or more running EC2 instances tagged Key=<tag>, Value=<value> and a Server-platform deployment group whose ec2TagFilters is [{Key:<tag>, Value:<value>, Type:'KEY_AND_VALUE'}], codedeploy:CreateDeployment with an S3 zip revision resolves those instances as deployment targets and GetDeployment reports deploymentInfo.status 'Succeeded' with instance targets carrying lifecycleEvents (Install, AfterInstall, ...) 'Succeeded'. errorInformation.code NO_INSTANCES is produced only when the group's selectors match no instance.

Actual (emulator): GetDeployment reports status 'Failed' with errorInformation {'code': 'NO_INSTANCES', 'message': 'The deployment failed because no instances were found for your deployment group. Check your deployment group settings to make sure the tags for your Amazon EC2 instances or Auto Scaling groups correctly identify the instances you want to deploy to, and then try again.'} on every one of the eight checks. Verbatim assertion text:
- codedeploy.ec2-agent-deployment-runs-appspec-hook-on-instance: "the agent deployment 'd-…' ended 'Failed' with errorInformation {'code': 'NO_INSTANCES', 'message': 'The deployment failed because no instances were found …'}"
- codedeploy.lifecycle-event-order-and-applicationstop-only-on-redeploy: "the first deployment 'd-…' to 'i-…' in 'us-west-2a' ended 'Failed' with errorInformation {'code': 'NO_INSTANCES', …}; nothing below can be read until a deployment reaches this host at all"
- codedeploy.deployment-group-alarm-in-alarm-state-blocks-the-deployment: "positive control: with the alarm at OK the deployment 'd-…' ended 'Failed' with errorInformation {'code': 'NO_INSTANCES', …}"
- codedeploy.auto-rollback-on-deployment-failure-reinstalls-the-prior-artifact, codedeploy.file-exists-behavior-disallow-blocks-foreign-file-and-overwrite-replaces-it, codedeploy.hook-failure-skips-later-lifecycle-events-and-fails-the-target, codedeploy.applicationstop-hook-failure-blocks-redeploy-until-ignored, codedeploy.agent-hands-the-hook-the-real-deployment-identifiers: the same 'Failed' + NO_INSTANCES errorInformation on their first/positive-control deployment.

The NO_INSTANCES message's text above is AWS's fixed text for that error class and is reproduced correctly; it carries no request- or state-derived variable parts. The deployment ids (d-…), instance ids (i-…) and availability zone in these assertions are per-run values, not part of the requirement — the requirement is that a deployment group whose ec2TagFilters match a running tagged instance resolves that instance instead of reporting an empty fleet.

## Steps to Reproduce
1. Create an S3 bucket and put a Server-platform revision zip (appspec.yml declaring a files section and an AfterInstall hook, plus the hook script) at key revision.zip.
2. Create a VPC/subnet and an instance profile allowing SSM + S3 read.
3. ec2:RunInstances one t3.micro AL2023 instance in that subnet with the instance profile and TagSpecifications ResourceType='instance', Tags=[{Key:'sim2real-codedeploy-target', Value:'<unique>'}]; wait for it to be running and ready.
4. codedeploy:CreateApplication(computePlatform='Server') and codedeploy:CreateDeploymentGroup with deploymentConfigName='CodeDeployDefault.AllAtOnce', deploymentStyle={IN_PLACE, WITHOUT_TRAFFIC_CONTROL} and ec2TagFilters=[{Key:'sim2real-codedeploy-target', Value:'<unique>', Type:'KEY_AND_VALUE'}].
5. codedeploy:CreateDeployment with revision {revisionType:'S3', s3Location:{bucket, key:'revision.zip', bundleType:'zip', eTag}}.
6. Poll codedeploy:GetDeployment until terminal. Observe status 'Failed' with errorInformation.code 'NO_INSTANCES' and no instance targets (ListDeploymentTargets/ListDeploymentInstances empty), although the tagged instance matching the group's filter is running.
