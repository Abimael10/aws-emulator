# autoscaling__ec2__events__kms__sqs: no 'EC2 Instance Launch Unsuccessful' EventBridge event is ever published for a launch blocked by a disabled CMK, so the disabled-key event/activity contract never completes

> _Note: this issue was identified against the code base at commit `6d844bf2d7a54913ccf026b8beb416d1976fa525`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
SetDesiredCapacity

## Description
Cause 1 of 1: a capacity increase whose launch cannot succeed (the launch template's root-volume BlockDeviceMapping names a CMK that is Disabled) produces no Auto Scaling lifecycle event at all, so a consumer waiting on EventBridge for the failure never hears anything and the check exhausts its time bound.

AWS: when a group's launch fails, Auto Scaling cancels the attempt and publishes an EventBridge event with source "aws.autoscaling" and detail-type "EC2 Instance Launch Unsuccessful", whose resources[0] is the group's AutoScalingGroupARN and whose second resource is arn:aws:ec2:<region>:<account>:instance/<instance id>; detail carries AutoScalingGroupName (the requested group name), ActivityId (the id of the group's own Cancelled activity), EC2InstanceId (the instance the activity describes), StatusCode "Cancelled" and StatusMessage equal to that activity's StatusMessage. For this failure class the StatusMessage is the fixed text "Instance became unhealthy while waiting for instance to be in InService state. Termination Reason: Client.InvalidKMSKey.InvalidState: The KMS key provided is in an incorrect state" — the whole string is fixed for the class; the group name, activity id, instance id, region and account in the envelope and detail are values from the request and from the emulator's state. DesiredCapacity must stay at the requested 1 and the group must retry; after kms.EnableKey the group's own retry must publish "EC2 Instance Launch Successful" on the same rule/queue and reach one InService instance. The Auto Scaling model does not describe EventBridge emission, so the event shape is recorded behavior only; Smithy does fix the activity side: Activity.StatusCode is required and targets ScalingActivityStatusCode, which includes "Cancelled", and Activity.Progress is 0..100 (100 for a terminal activity).

Emulator: the check reaches its 60 s bound with nothing delivered — "Check timed out after 60.0s". The first blocking wait in the check is the SQS collection for an "EC2 Instance Launch Unsuccessful" event for the named group; every step before it (VPC/subnet, the EventBridge rule and SQS target, CreateKey, CreateLaunchTemplate, CreateAutoScalingGroup, the ServiceLinkedRoleARN assertion, the key-policy grant, DisableKey + DescribeKey reporting Disabled, SetDesiredCapacity) is a bounded call. Hypothesis: the timeout is that wait, and it never completes because the emulator does not cancel the launch under an unusable CMK at all — its sibling checks in autoscaling__ec2__kms show the same disabled-CMK launch recorded StatusCode 'Successful' with no StatusMessage — so no failure activity exists to event, and no "EC2 Instance Launch Unsuccessful" is ever published.

Why: a client whose operational tooling is wired to Auto Scaling lifecycle events (an EventBridge rule filtering source aws.autoscaling / detail-type "EC2 Instance Launch Unsuccessful" / detail.AutoScalingGroupName, fanned out to SQS) is told nothing when capacity silently fails to appear. There is no alarm, no ActivityId to correlate to a Cancelled activity, and no EC2InstanceId to inspect, so the only signal of a broken encryption key is an indefinite wait. Any consumer that blocks on the failure event hangs rather than failing, which is strictly worse than an error.

Fix: the Auto Scaling launch path and its event emitter — the component that performs the EC2 launch for a capacity change must honour the refusal (an encrypted root volume under a CMK that is not Enabled cannot be created), record the terminal activity as Cancelled with the message above, and publish the corresponding aws.autoscaling "EC2 Instance Launch Unsuccessful" event (group ARN plus instance ARN in resources, and ActivityId/EC2InstanceId/StatusCode/StatusMessage in detail) onto the account's event bus so a matching rule delivers it; the "EC2 Instance Launch Successful" counterpart must be published by the group's own retry once the key is re-enabled. Related open issues, neither of which carries this check's replay key: 20261111T024602Z-autoscaling-ec2-kms-an-asg-scale-out-from.md (the activity is recorded Successful) and 20261107T075601Z-ec2-events-kms-sqs-an-instance-whose-root-volume-is-under-a.md (EC2 keeps such an instance running).

Termination Reason: Client.InvalidKMSKey.InvalidState: The KMS key provided is in an incorrect state", detail.ActivityId naming one of the group's Cancelled activities (Progress 100, same StatusMessage) and detail.EC2InstanceId the instance that activity's Description names; no "EC2 Instance Launch Successful" event, no InService instance, DesiredCapacity still 1; the instance terminated with StateReason {Code: "Client.InvalidKMSKey.InvalidState", Message: "Client.InvalidKMSKey.InvalidState: The KMS key provided is in an incorrect state"}; then, after kms.EnableKey, an "EC2 Instance Launch Successful" event for a NEW instance and exactly one InService instance.
Actual (emulator): Error: Check timed out after 60.0s — nothing is delivered. The first blocking wait is the collection of the "EC2 Instance Launch Unsuccessful" event; the sibling autoscaling__ec2__kms checks show the same disabled-CMK launch recorded as StatusCode 'Successful' with StatusMessage None, i.e. there is no cancelled launch for the emulator to event.

Smithy (com.amazonaws.autoscaling): Activity.StatusCode required, targets ScalingActivityStatusCode (includes "Cancelled"); Activity.StatusMessage XmlStringMaxLen255; Activity.Progress 0..100. EventBridge emission is not modelled — recorded behavior only.

## Steps to Reproduce
1. Create a VPC/subnet; create an SQS queue and an EventBridge rule with pattern {"source": ["aws.autoscaling"], "detail-type": ["EC2 Instance Launch Unsuccessful", "EC2 Instance Launch Successful"], "detail": {"AutoScalingGroupName": [<group>]}} targeting the queue.
2. kms.CreateKey (symmetric CMK).
3. ec2.CreateLaunchTemplate with LaunchTemplateData.BlockDeviceMappings[0] = {DeviceName: <AMI root device>, Ebs: {Encrypted: true, KmsKeyId: <CMK ARN>, VolumeSize: 8, VolumeType: gp3, DeleteOnTermination: true}}.
4. autoscaling.CreateAutoScalingGroup(<group>, MinSize 0, MaxSize 1, DesiredCapacity 0, LaunchTemplate={LaunchTemplateId: <lt>, Version: "$Latest"}, VPCZoneIdentifier=<subnet>); read ServiceLinkedRoleARN and add the documented Auto Scaling statements for it to the CMK key policy.
5. kms.DisableKey(KeyId=<CMK>); confirm DescribeKey reports KeyState="Disabled".
6. autoscaling.SetDesiredCapacity(AutoScalingGroupName=<group>, DesiredCapacity=1), then receive from the queue.
   -> AWS: an "EC2 Instance Launch Unsuccessful" envelope as described above arrives; DescribeScalingActivities shows a Cancelled activity with the same ActivityId/StatusMessage; DescribeInstances shows the attempt terminated with StateReason.Code "Client.InvalidKMSKey.InvalidState". Emulator: no message ever arrives and the check hits its 60 s bound.
7. kms.EnableKey(KeyId=<CMK>) and keep receiving -> AWS: an "EC2 Instance Launch Successful" event for a new instance and exactly one InService instance, DesiredCapacity still 1.
