# bedrock automated-reasoning policy definitionHash is not AWS's definition digest, and the version create it gates is refused

> _Note: this issue was identified against the code base at commit `53ddd9e1b1293a4c57ae86daee3ceced4b490c2e`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
GetAutomatedReasoningPolicy

## Description
Three net-new wire divergences on the bedrock Automated Reasoning policy surface, all three rooted in ONE emulator defect: the digest the emulator computes for an `AutomatedReasoningPolicyDefinition` is not the digest AWS publishes for the same definition document. Causes 1 and 2 are the wrong digest being SERVED; cause 3 is the same wrong digest being ENFORCED as a concurrency token, which turns a create AWS accepts into a refusal. A fixer must close all three and re-replay all three steps.

Cause 1 of 3 — GetAutomatedReasoningPolicy serves a `definitionHash` that is not the recorded digest of the policy definition (fixture bedrock-automated-reasoning-policy-lifecycle, step task#2).
AWS: `GET /automated-reasoning-policies/{policyArn}`, 200, `@readonly`; output member `definitionHash` targets `AutomatedReasoningPolicyHash`, **required**, `@length(min: 128, max: 128)`, `@pattern("^[0-9a-z]{128}$")` — a 128-character lowercase-hex digest — documented as "The hash of the policy definition" (`smithy_query(query="operation",operation="GetAutomatedReasoningPolicy")` on services/service-com-amazonaws-bedrock-amazonbedrockcontrolplaneservice/smithy-model/com-amazonaws-bedrock-amazonbedrockcontrolplaneservice.json). The model fixes the WIDTH and ALPHABET of the value but not the canonicalization or the digest function, so the exact digest is recorded behavior only: for a given definition document AWS publishes one stable 128-hex digest, and every read of that same definition — the policy read, the policy update's echo, and the version cut from it — must publish that same value. The recorded 200 body is the authority for what that digest is.
Emulator: 200 with a well-formed 128-hex value of its own that is not AWS's digest of the same definition (replay: `$.definitionHash` value_mismatch — expected the recorded digest beginning `f16ba1ce...`, got `edd737bc...`). The value is internally consistent across the emulator's own reads, so the defect is the digest function/canonical form rather than per-call instability.
Why: `definitionHash` is a concurrency token, not decoration. A client reads the policy, carries the hash into `CreateAutomatedReasoningPolicyVersion.lastUpdatedDefinitionHash` or compares it against a stored value to decide whether the draft moved, so a client that pins or compares the AWS digest sees a policy that looks permanently modified and either refuses to version it or loops re-reading it.
Fix: the policy-definition digest helper in the bedrock control-plane crate's state — `crate::state::policy_definition_hash`, the canonical form it digests (documented at services/service-com-amazonaws-bedrock-amazonbedrockcontrolplaneservice/src/state/automated_reasoning_policies.rs:22-38, which stamps the document with `POLICY_DEFINITION_FORMAT_VERSION`) — and nothing in the individual operation handlers, which all read `policy.definition_hash` back out of state.
Traces: bedrock-automated-reasoning-policy-lifecycle#task#2 (expected 200 / actual 200, body mismatch); the same cluster also covers bedrock-automated-reasoning-policy-lifecycle#task#5 and bedrock-automated-reasoning-policy-unset-vs-present-description-preserved#task#3 and #task#4.

Cause 2 of 3 — UpdateAutomatedReasoningPolicy echoes the same non-AWS digest for the definition it just wrote (fixture bedrock-automated-reasoning-policy-lifecycle, step task#4).
AWS: `PATCH /automated-reasoning-policies/{policyArn}`, 200, `@idempotent`; input `policyDefinition` **required**, output `definitionHash` targets `AutomatedReasoningPolicyHash`, **required**, same `@length(128,128)` / `@pattern("^[0-9a-z]{128}$")` (`smithy_query(query="operation",operation="UpdateAutomatedReasoningPolicy")`). The echoed hash is the digest of the definition the update stored, so it must equal what a subsequent Get of that policy reports; the digest value itself is recorded behavior only.
Emulator: 200, and the echoed `definitionHash` diverges from the recording for the UPDATED definition too (replay: `$.definitionHash` value_mismatch — expected the recorded digest beginning `7c5fd5b1...`, got `2177d747...`). This is the same digest function applied to a second, different definition document, which rules out a one-off seed and confirms the function/canonicalization is wrong for any input.
Why: the update's echo is how a client refreshes its concurrency token without a second round trip, so a client that writes a definition and then immediately versions it carries a token AWS would never have issued.
Fix: the same digest helper as cause 1 (`crate::state::policy_definition_hash`); the update handler itself only re-reads the stored hash.
Traces: bedrock-automated-reasoning-policy-lifecycle#task#4 (expected 200 / actual 200, body mismatch).

Cause 3 of 3 — CreateAutomatedReasoningPolicyVersion refuses 400 ConflictException the version create AWS accepts with 200 (fixture bedrock-automated-reasoning-policy-lifecycle, step task#6).
AWS: `POST /automated-reasoning-policies/{policyArn}/versions`, 200, `@idempotent`; input `lastUpdatedDefinitionHash` **required**, documented "The hash of the current policy definition used as a concurrency token to ensure the policy hasn't been modified since you last retrieved it"; output `policyArn` (the VERSIONED ARN), `version`, `name`, `description`, `definitionHash`, `createdAt`, all required but `description`; `ConflictException` is modeled at HTTP 400 (`smithy_query(query="operation",operation="CreateAutomatedReasoningPolicyVersion")`). The rule is that a `lastUpdatedDefinitionHash` equal to the policy draft's CURRENT definition digest is accepted and cuts the next version; only a hash that is not the draft's current digest is a conflict. The recorded response for this step is 200 with the versioned ARN `arn:aws:bedrock:<region>:<account>:automated-reasoning-policy/<policyId>:<version>`, `version` the next version number as a decimal string, `name` and `description` copied from the draft, and `definitionHash` the draft's digest.
Emulator: 400 with an empty success body — `status: expected 200, got 400`, and every modeled output member missing (`$.policyArn`, `$.version`, `$.name`, `$.description`, `$.definitionHash`, `$.createdAt`). The handler compares the request's `last_updated_definition_hash` against its own `policy.definition_hash` and, because that stored digest is the wrong value from causes 1-2, never matches a token AWS issued; it then answers `ConflictException` carrying the fixed sentence `crate::state::AUTOMATED_REASONING_POLICY_DEFINITION_HASH_CONFLICT` (services/service-com-amazonaws-bedrock-amazonbedrockcontrolplaneservice/src/ops/create_automated_reasoning_policy_version.rs:251-267). AWS raises no error here at all, so the requirement for this request class is the 200 body above, not a reworded conflict message. Hypothesis: the gate itself is correct AWS behavior and only the digest it compares is wrong, so fixing the digest function should clear this cause; if the digest is fixed and this step still refuses, the comparison or the draft-vs-version hash bookkeeping is a second defect.
Why: this is the only way to cut an immutable policy version, so the entire version lifecycle (version create, versioned read, export, guardrail attachment of a published policy version) is unreachable for a client that obtained its token the documented way — a hard functional block rather than a cosmetic field difference.
Fix: primarily the digest helper above; secondarily the concurrency-token gate in the CreateAutomatedReasoningPolicyVersion handler and the draft/version `definition_hash` bookkeeping in the policy state record.
Traces: bedrock-automated-reasoning-policy-lifecycle#task#6 (expected 200 / actual 400).

Not covered by any open issue. The nearest open reports are 20261119T063504Z-bedrock-exportautomatedreasoningpolicyversion-returns-policy-definition-format-version-1.md (the definition FORMAT version token `"1.0"` vs `"1"` on export — a different member), 20261117T165421Z-bedrock-resource-refusal-paths-diverge-deleteautomatedreasoningpolicy-accepts-a.md and 20261119T014720Z-bedrock-deleteautomatedreasoningpolicy-answers-404-for-the-second-teardown.md (the DELETE paths of the same resource family).
