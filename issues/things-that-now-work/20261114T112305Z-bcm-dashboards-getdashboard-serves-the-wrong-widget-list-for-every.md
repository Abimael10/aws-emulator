# GetDashboard serves the wrong widget list for every AWS-managed dashboard in the seeded catalog

> _Note: this issue was identified against the code base at commit `9f1f60a0e7cf7d39d2cd24e9b1d356e68ef5f505`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
GetDashboard

## Description
Every AWS-managed dashboard that a fresh bcm-dashboards account already holds is now REACHABLE in the emulator (all five reads answer HTTP 200 and every scalar member — arn, name, description, type, createdAt, updatedAt — matches), but the `widgets` list each read returns is not the list AWS publishes for that dashboard. Five causes follow, one per managed dashboard read in the fixture; they share one root cause (the AWS-managed catalog seed's per-dashboard widget builders) but are five distinct divergence clusters and a fixer must close all five.

AWS (common to all five causes): GetDashboard is @readonly, input `arn` -> DashboardArn (@required, @length 20..2048, @pattern ^arn:aws[-a-z0-9]*:bcm-dashboards::[0-9]{12}:dashboard/(\*|[-a-z0-9]+)$), and output carries arn/name/type/widgets/createdAt/updatedAt @required plus optional description, with `widgets` -> WidgetList @length 0..20; modelled errors are AccessDeniedException 403, ValidationException 400, ResourceNotFoundException 404, ThrottlingException 429, InternalServerException 500 (Smithy: services/service-com-amazonaws-bcmdashboards-awsbcmdashboardsservice/smithy-model/com-amazonaws-bcmdashboards-awsbcmdashboardsservice.json, query=operation GetDashboard). No error applies to any of these reads: AWS answers 200, and so does the emulator, so there is NO status, error-code or error-message divergence in this issue — the defect is purely the CONTENT of the @required `widgets` list. The model says nothing about what the AWS-managed catalog contains (DashboardType enumerates the custom case only), so the published widget sets below are RECORDED BEHAVIOR ONLY: the requirement is that the emulator serve, for each managed dashboard, the widget set AWS publishes for it — each widget's `id`, `title`, `description`, `width`, `height`, `horizontalOffset` and `configs` (displayConfig variant and queryParameters union member with its filter/granularity/groupBy/metrics/timeRange). The widget ids, titles and description strings quoted below are the recording's values filling those slots; they illustrate the published catalog, they are not a per-run literal to echo.

Emulator (common): the GetDashboard handler projects the stored dashboard record faithfully; what is wrong is the record. The store is seeded at construction — `Default::default()` for ComAmazonawsBcmdashboardsAwsbcmdashboardsserviceState sets `dashboards: managed_dashboard_catalog()` (services/service-com-amazonaws-bcmdashboards-awsbcmdashboardsservice/src/state.rs line 544) — and that seed's per-dashboard widget builders hand-write widget sets that differ from the published ones in membership, in widget prose, in layout width, and in which `QueryParameters` union member and `WidgetDisplayConfig` variant each widget carries.

Why (common): the managed dashboards are the first thing a console-like client renders and the only dashboards a brand-new account has. A client that renders one draws panels AWS never published and omits panels AWS does publish; a client that reads a widget's `configs` to re-issue the underlying cost query issues a different query than AWS's dashboard does (a budget panel served as a cost-and-usage panel, a utilization/coverage panel served as a cost-and-usage panel, a table panel served as a graph); and a scheduled report whose `widgetIds` name a published widget of a managed dashboard resolves no such widget, because the ids the emulator serves for four of the five dashboards are disjoint from the published ones.

Fix (common): the AWS-managed catalog seed in the service state — the per-dashboard widget builders behind `managed_dashboard_catalog()` in services/service-com-amazonaws-bcmdashboards-awsbcmdashboardsservice/src/state.rs (installed at line 544). The GetDashboard handler (services/service-com-amazonaws-bcmdashboards-awsbcmdashboardsservice/src/ops/get_dashboard.rs) and its serializer are correct given a correct store and no change belongs there.
