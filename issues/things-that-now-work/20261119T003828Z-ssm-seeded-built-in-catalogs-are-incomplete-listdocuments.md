# SSM seeded built-in catalogs are incomplete: ListDocuments, ListDocumentVersions and GetInventorySchema

> _Note: this issue was identified against the code base at commit `0a8d788699eb3929d2d95f97973e466fa561ffef`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
ListDocuments

## Description
3 causes, all in the emulator's seeded read-only catalogs for Systems Manager (AWS-owned documents and default inventory schemas). The catalogs the emulator ships are a small, stale subset of what AWS serves, so catalog reads either omit entries or refuse a valid name.

Cause 1 of 3: ListDocuments does not serve AWS's Amazon-owned document catalog, and the few entries it does serve are projected incompletely (fixture ssm-catalog-list-documents, step task#1).
AWS: Smithy: ListDocuments output DocumentIdentifiers -> DocumentIdentifierList of DocumentIdentifier{Name, CreatedDate, Owner, PlatformTypes, DocumentVersion, DocumentType, SchemaVersion, DocumentFormat, TargetType, Tags, ...}. On a real account an unfiltered ListDocuments enumerates the whole Amazon-owned catalog - the AWS-*, AWSConfigRemediation-*, AWSConformancePacks-*, AWSSupport-*, AWSCodeDeployAgent* families - each with Owner 'Amazon', a populated PlatformTypes, SchemaVersion, DocumentType, DocumentFormat, an empty Tags list, and (recorded behavior only - Categories is not a member of DocumentIdentifier in the on-disk model) a Categories list such as ['InstanceManagement'] or ['ConfigurationManagement'].
Emulator: the response carries only a handful of documents. Hundreds of modeled entries are absent entirely (e.g. AWS-ASGEnterStandby, AWS-ASGExitStandby, AWS-AddOpsItemDedupStringToEventBridgeRule, AWS-ApplyChefRecipes, AWS-ApplyDSCMofs, AWS-ApplyPatchBaseline, the entire AWSConfigRemediation-* and AWSConformancePacks-* families), and the entries that are present drop Categories and Tags (served as absent where AWS sends a list / an empty list) and carry diverging CreatedDate, DocumentFormat, SchemaVersion, TargetType and PlatformTypes values (e.g. AWS-ConfigureS3BucketVersioning, AWS-CreateSnapshot, AWS-DeleteSnapshot, AWS-DisableS3BucketPublicReadWrite, AWS-EnableS3BucketEncryption, AWS-FindWindowsUpdates, AWS-JoinDirectoryServiceDomain, AWS-RunPowerShellScript, AWS-RunShellScript).
Why: any client that discovers runbooks/command documents by listing (consoles, Config remediation wiring, automation that picks a document by name from the catalog) sees an account with almost no documents, and a client that reads Categories/Tags/PlatformTypes off a listed document gets a null where AWS always sends a value. Open issue 20261114T164648Z ('SSM: 2 net-new causes - ... ListDocuments serves no Amazon-owned document catalog') describes the same area but does not carry this fixture step's replay key, so this cause is not gated by it.
Fix: the ssm crate's seeded Amazon-owned document catalog (state) plus the ListDocuments response projection, which must emit every modeled DocumentIdentifier member for each seeded document.
Traces: ssm-catalog-list-documents#task#1.

Cause 2 of 3: ListDocumentVersions refuses a published AWSSupport-* document with 400 instead of listing its versions (fixture ssm-catalog-list-document-versions, step task#16).
AWS: Smithy: ListDocumentVersions input Name (DocumentARN, required) and output DocumentVersions -> list of DocumentVersionInfo, with InvalidDocument modeled only for a document that does not exist. AWSSupport-TroubleshootSSH is an Amazon-owned document present in every account; the recorded response is 200 with five DocumentVersionInfo entries (DocumentVersion '5' ... '1', DocumentFormat 'JSON', Status 'Active', IsDefaultVersion true on version 5).
Emulator: status 400 and no DocumentVersions member at all, because the seeded catalog contains no AWSSupport-* documents - the request is treated as naming a non-existent document.
Why: a client reading the version history of an AWS-published support runbook gets a hard client error on a name that always resolves on AWS, so any version-pinning or default-version discovery against AWSSupport-* documents fails instead of returning data.
Fix: the ssm crate's seeded document catalog (state) must include the AWSSupport-* family with their versions, so the ListDocumentVersions handler resolves the name rather than raising InvalidDocument.
Traces: ssm-catalog-list-document-versions#task#16.

Cause 3 of 3: GetInventorySchema serves stale default inventory schemas (fixture ssm-catalog-get-inventory-schema, step task#1).
AWS: Smithy: GetInventorySchema output Schemas -> list of InventoryItemSchema{TypeName (required, ^(AWS|Custom):.*$), Version, Attributes (required, 1..50 of {Name, DataType}), DisplayName}. The recorded response carries AWS:ComplianceItem at Version '1.1' with 21 attributes - ComplianceType, ExecutionId, ExecutionType, ExecutionTime, Id, Title, Status, Severity, DocumentName, DocumentVersion, Classification, PatchBaselineId, PatchSeverity, PatchState, PatchGroup, InstalledTime, InstallOverrideList, DetailedText, DetailedLink, CVEIds, DocumentExecutionTime.
Emulator: AWS:ComplianceItem is served at Version '1.0' with only 17 attributes (InstallOverrideList, DetailedText, DetailedLink and DocumentExecutionTime are missing), and the schema entries the replay keys as $.Schemas[3], [4], [5], [7], [8] and [13] likewise diverge from or are absent in the served list.
Why: inventory query filters are composed from this schema, so a client that builds a filter on an attribute AWS publishes (for example AWS:ComplianceItem.PatchState or .DetailedLink) finds no such attribute, and a client that keys behavior off the schema Version reads 1.0 for a type AWS publishes at 1.1. Open issue 20261116T180456Z ('ssm: 7 net-new behavioral causes - GetInventorySchema refuses the published AWS:ComplianceItem type ...') is adjacent but carries no replay key for this fixture step.
Fix: the ssm crate's seeded default inventory-schema table (state), read by the GetInventorySchema handler.
Traces: ssm-catalog-get-inventory-schema#task#1.
