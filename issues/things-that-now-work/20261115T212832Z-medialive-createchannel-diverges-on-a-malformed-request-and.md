# medialive CreateChannel diverges on a malformed request and on its 201 body: the roleArn 422 preempts the 400 inputAttachment refusal, and the created channel omits its maintenance surface

> _Note: this issue was identified against the code base at commit `13bb1fd79957359dc01e15dbf78292366937d23b`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
CreateChannel

## Description
MediaLive's CreateChannel handler diverges from AWS in two places that the wire corpus exercises: the order and class of its request refusals, and the channel body it serves on a successful create. This bundle has 2 causes; both must be closed.

Cause 1 of 2 - a CreateChannel request that specifies no input attachment is refused 422 UnprocessableEntityException about its roleArn instead of 400 BadRequestException about the missing attachment (fixture medialive-cmc-traj-create-channel-request-mistakes, step task#5; the same cluster also covers task#6).
AWS: CreateChannel is Smithy POST /prod/channels with success code 201; its modeled error set is BadRequestException (httpError 400), ConflictException (409), ForbiddenException (403), UnprocessableEntityException (httpError 422, members Message jsonName "message" and ValidationErrors jsonName "validationErrors" of ValidationError{elementPath, errorMessage}), TooManyRequestsException (429), InternalServerErrorException (500), BadGatewayException (502), GatewayTimeoutException (504). The input member InputAttachments (jsonName "inputAttachments", target __listOfInputAttachment) carries no @required and no @length in the model, so the rule is recorded behavior only: AWS validates the request's own structure FIRST and refuses a channel that attaches no input with HTTP 400 BadRequestException whose message is the fixed sentence "At least one inputAttachment must be specified" - the whole message is fixed text, it has no variable parts. Only after the request shape is accepted does AWS resolve the request's RoleArn against IAM and check the role's trust policy, which is the separate 422 UnprocessableEntityException path (message "roleArn Make sure the role '<roleArn from the request>' exists in the user account and medialive.amazonaws.com is a trusted service", fixed text around the role ARN echoed from the request). A request that is both structurally incomplete and names an unusable role therefore gets the 400, not the 422.
Emulator: the step answers HTTP 422 with header x-amzn-errortype "UnprocessableEntityException" and $.message set to the roleArn trust sentence - the replay reports "status: expected 400, got 422" and "$.message: value_mismatch (expected 'At least one inputAttachment must be specified', got \"roleArn Make sure the role '<roleArn>' exists in the user account and medialive.amazonaws.com is a trusted service\")". The missing-inputAttachment check either does not exist or is ordered behind the IAM role resolution, so the structural defect in the request is never reported.
Why: a client gets the wrong status class and the wrong diagnosis. Code that branches on 400/BadRequestException ("my request is malformed, fix the payload") versus 422/UnprocessableEntityException ("the request is well-formed but a referenced resource is unusable, fix the IAM role") takes the IAM branch and goes off rewriting role trust policies while the actual defect is an empty inputAttachments list; the message names a member the client did not get wrong and never names the one it did. Retry logic that treats 422 as a semantic validation report and reads validationErrors[].elementPath is pointed at "roleArn" instead of "inputAttachments".
Fix: CreateChannel's request validation in its handler - add the structural check that at least one inputAttachment is present and raise BadRequestException with AWS's wording, and order the whole request-shape validation ahead of the roleArn/IAM resolution that currently short-circuits it.
Traces: medialive-cmc-traj-create-channel-request-mistakes#task#5 (representative), plus task#6 in the same cluster.

Cause 2 of 2 - a successful CreateChannel returns 201 but the channel body it serves carries no maintenance settings (fixture medialive-cmc-traj-role-mistakes-and-idempotent-retry, step task#9; the same cluster also covers task#11).
AWS: CreateChannel (Smithy POST /prod/channels, success code 201) returns output member Channel (jsonName "channel", target Channel). The Channel shape binds Maintenance (jsonName "maintenance", target MaintenanceStatus), and MaintenanceStatus is {MaintenanceDay (jsonName maintenanceDay, enum, "The currently selected maintenance day"), MaintenanceStartTime (jsonName maintenanceStartTime, "The currently selected maintenance start time. Time is in UTC"), MaintenanceDeadline (jsonName maintenanceDeadline, "Maintenance is required by the displayed date and time"), MaintenanceScheduledDate (jsonName maintenanceScheduledDate)}. CreateChannel's own input accepts the companion MaintenanceCreateSettings (jsonName "maintenance"), so a channel ALWAYS has a maintenance day and start time from the moment it is created - chosen by the client or assigned by the service - and the create response reports them. Recorded behavior only for the exact projection names the trajectory asserts ($.channel.maintenanceWindow and $.channel.maintenanceStatus, the fixture's normalized view of that modeled maintenance sub-structure): the recording carries the maintenance window as a present, shaped value and the maintenance scheduling state as a present empty string, i.e. present and not yet scheduled.
Emulator: the step answers 201 (the status matches) and returns a channel, but both maintenance keys are absent from the body - the replay reports "$.channel.maintenanceWindow: missing (expected '<shaped-not-asserted>', got None)" and "$.channel.maintenanceStatus: missing (expected '', got None)". The channel is persisted with no maintenance settings at all, so the distinction between "no maintenance is scheduled" (a present, empty scheduling state) and "this field does not exist" is lost at creation time.
Why: CreateChannel's response is where a client learns the maintenance window the service assigned to the channel it just made. A client that records or displays that window from the create response gets nothing; an SDK deserializes Maintenance as absent, so render and reconcile paths see no maintenance day or start time. Infrastructure tooling that creates a channel and then diffs desired against actual state reports perpetual drift on the maintenance block or keeps re-applying it. Note this is NOT covered by the open issue 20261115T001055Z-medialive-channel-responses-omit-the-maintenance-surface-on.md, which carries the replay keys for DescribeChannel and DeleteChannel only and says nothing about the create path; the replay reports no owner for this step.
Fix: the channel record in medialive state must be populated with maintenance settings when CreateChannel persists it (defaulted when the request omits the maintenance input, as AWS assigns one), and CreateChannel's response serializer must project them onto the returned channel. Fixing the state write here is the upstream half of the Describe/Delete projection gap filed separately.
Traces: medialive-cmc-traj-role-mistakes-and-idempotent-retry#task#9 (representative), plus task#11 in the same cluster.

Other open medialive issues named for context, none of which carries either of these two replay keys (the replay reports owned_by empty for both clusters): 20261114T181641Z-medialive-createchannel-commits-a-refused-channel-the-rolearn.md (the roleArn trust refusal not firing at all, and the attachment leak it caused - its cause 2 claimed task#9 was refused 409, whereas this run shows task#9 now succeeding 201 with an incomplete body), 20261103T014723Z-medialive-refusals-missing-or-misworded-cross-field-reference.md (the behavioral counterpart covering roleArn, DELETED-input attachment, destination-settings and conflict refusals - it does not cover the missing-inputAttachment structural refusal or the refusal ordering), and 20261115T001055Z-medialive-channel-responses-omit-the-maintenance-surface-on.md (the same maintenance projection on DescribeChannel/DeleteChannel).

All ARNs, role names, channel and input ids in the replay output are per-run fillers for the variable slots of these messages and documents, not literal requirements.
