# appsync__lambda: 2 net-new causes — an APPSYNC_JS resolver's runtime.earlyReturn value is dropped (field null, no errors), and BatchInvoke on an AWS_LAMBDA data source never dispatches or maps per-item errors

> _Note: this issue was identified against the code base at commit `37301ce23688d3043715086de5be7f765b8fadfc`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
GraphQL (AppSync data-plane POST on the API's GRAPHQL uri)

## Description
Two net-new root causes in the AppSync GraphQL data plane. Both are in the same service, so they are bundled here; a fixer must close BOTH before submitting. Every control-plane call these checks make (CreateGraphqlApi, StartSchemaCreation, CreateDataSource, CreateResolver, Lambda AddPermission) succeeds with 200, and the Lambda authorizer itself is now reached (the authorization barrier poll settles on a 200 with no `errors`), so the divergence is in field resolution and in the BatchInvoke dispatch, not in configuration. Resolved issue 20261114T003845Z-appsync-lambda-2-net-new-causes-direct-lambda.md previously covered the whole AWS_LAMBDA data-source/authorizer gap; its fix landed the Invoke path and the authorizer invocation (the xsvc-appsync-3-direct-lambda-* and identityValidationExpression checks now pass) but left the two causes below, and a resolved issue never covers a live failure. Open issue 20261114T070045Z-appsync-cognito-idp-an-appsync-js-resolver-over.md describes the same APPSYNC_JS-resolves-to-null symptom under a different service heading; it does not carry either check below.

Cause 1 of 2: a UNIT resolver with runtime=APPSYNC_JS over a NONE data source resolves its field to null, with the `data` key present and NO `errors` key, instead of serving the value the resolver returned.
AWS: Smithy: appsync#Resolver carries `kind` (UNIT), `dataSourceName`, `runtime` (AppSyncRuntime, which must be APPSYNC_JS when `code` is used) and `code` (@length 1..32768); the model covers only the control plane, so the execution contract is recorded behavior only (AppSync developer guide, 'JavaScript resolvers' / 'runtime.earlyReturn'). A request function that calls `runtime.earlyReturn(v)` short-circuits the data-source call and makes `v` the resolver's result; the response function then returns `ctx.result`, and AppSync answers HTTP 200 with that value as the field value and no `errors` member. With a NONE data source there is nothing else that could null the field. The value is whatever the resolver computed — a literal constant in one check, `ctx.identity.resolverContext.token` in the other — so the requirement is 'the resolver's returned value is the field value', not any one recorded string.
Emulator: the endpoint answers HTTP 200 with every such field null and no `errors` member: `{'data': {'open': None, 'secret': None}}` for a two-field query whose resolvers both early-return a constant, and `{'data': {'whoami': None}}` for the identity-echoing resolver. Because the constant-returning leg is also null, this is not a resolverContext-binding gap: the APPSYNC_JS resolver's result is discarded whatever it is. Hypothesis: the APPSYNC_JS evaluator runs but neither `runtime.earlyReturn`'s value nor the response function's return value is wired into the field value, so the field falls back to null. No HTTP refusal is involved.
Why: a client reading a field whose value the resolver early-returns gets a successful-looking 200 whose data is null and whose error channel is empty, so a resolver that worked cannot be distinguished from a legitimately null field. In these checks it also makes the Lambda-authorizer contract unobservable: with `deniedFields` empty every field must resolve, and under `authorizerResultTtlInSeconds` a cached grant must still carry its resolverContext — neither can be seen when every field is null.
Fix: the AppSync data-plane resolver executor — the APPSYNC_JS evaluation path for a UNIT resolver (the `runtime.earlyReturn` short-circuit and the response function's return value feeding the field value), not CreateResolver's validation or the control-plane projections, which already round-trip runtime/code.
Traces: appsync__lambda.deep-appsync-2-appsync-authz-denied-fields-nulls-only-the-denied-field, appsync__lambda.appsync-lambda-authorizer-result-ttl-caches-exactly-one-invocation.

Cause 2 of 2: a resolver on an AWS_LAMBDA data source with `operation: BatchInvoke` never merges sibling field resolutions into one invocation, and a per-element error in a batch result is never mapped to a GraphQL error.
AWS: Smithy: appsync#Resolver.maxBatchSize (@range min 0 max 2000) is the modeled knob; the dispatch contract is recorded behavior only (AppSync developer guide, 'Direct Lambda resolvers' → batching, and tutorial-lambda-resolvers 'Returning individual errors'). With `operation: 'BatchInvoke'` and maxBatchSize >= N, AppSync merges the N sibling resolutions of one field in a single GraphQL request into exactly ONE Lambda invocation whose event is a bare JSON list of N context documents, and maps returned element i onto sibling i in request order. Each element is the envelope `{"data": ..., "errorMessage": ..., "errorType": ...}`; when exactly one element carries a non-null errorMessage/errorType, AppSync answers HTTP 200 with exactly one `errors` entry for that element's own field (its `errorType` taken from the element's errorType and its `message` from the element's errorMessage) while every sibling still resolves its `data` normally.
Emulator: the merge never happens — the check that waits for the single merged invocation and the ordered result mapping never settles and is cut off at the harness cap ('Check timed out after 60.0s'), i.e. the function is never invoked for the BatchInvoke resolver. Where the endpoint does answer, the per-item error envelope is ignored: a response in which exactly one element carries errorMessage/errorType produces `errors` length 0 (`expected exactly one GraphQL error, got 0: []`) instead of exactly one entry. The plain (non-batch) Invoke path does reach the function, so this is specific to BatchInvoke.
Why: a client that batches a per-parent field through one Lambda to avoid the N+1 problem gets either a request that never completes or a 200 in which a declared per-item failure has vanished — the failing sibling looks successfully resolved and the error is never surfaced, so partial-failure handling written against AWS silently does nothing here.
Fix: the AppSync data-plane resolver executor's AWS_LAMBDA data-source dispatch — the BatchInvoke branch (sibling collection up to maxBatchSize, the bare-list event builder, and the ordered element→sibling result mapping) and its per-element errorMessage/errorType → `errors[]` mapper.
Traces: appsync__lambda.appsync-batch-invoke-merges-sibling-fields-into-one-invocation, appsync__lambda.appsync-batch-invoke-partial-item-error-isolates-the-failing-sibling.
