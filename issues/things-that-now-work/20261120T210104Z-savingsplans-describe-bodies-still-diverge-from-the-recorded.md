# savingsplans Describe bodies still diverge from the recorded rate card and plan record

> _Note: this issue was identified against the code base at commit `1dbde5f983a37bee92f053a876b051c36fca920d`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Description
Replay of the savingsplans wire corpus (simparity-wire-aws-v1, 6 fixtures / 27 steps, 23 passed, 4 mismatched, score 85.2%) reports TWO net-new causes in the savingsplans crate (service-com-amazonaws-savingsplans-awssavingsplan). BOTH must be closed before this issue is submitted. They share one fault: the Describe* response projections report values the handler COMPUTES at request time from its own in-crate ladders/tables instead of the per-combination rate catalog row and the stored plan record the operation is defined to return, so each body is correctly shaped but its contents are not the service's data.

Previously closed, still diverging: resolved issue 20261119T095638Z-savingsplans-describe-responses-return-synthesized-values-instead-of.md filed these same two clusters and is marked fixed, but the replay still reports both as unowned mismatches (owned_by empty), so they are re-filed here with their own fixture/step linkage. One claim in that resolved issue was WRONG and must not be re-implemented: it called the usage-operation suffix '00g0' non-hexadecimal and therefore invalid. AWS's published usage-operation table does use 'g' in these codes (Red Hat BYOL Linux is 'RunInstances:00g0', Ubuntu Pro is 'RunInstances:0g00'), and the crate's own EC2_PLATFORMS table (services/service-com-amazonaws-savingsplans-awssavingsplan/src/state.rs) now carries that table correctly. The remaining divergence is about rate VALUES, amount SPELLING and row/property ORDER, not about the codes being malformed.

=== Cause 1 of 2: DescribeSavingsPlanRates serves a computed rate card (wrong rate values, wrong amount spelling, wrong row and property order), so no returned row matches the recorded card at any index — fixture savingsplans-queued-plan-delete-lifecycle, step task#8 ===

AWS: Smithy (com.amazonaws.savingsplans#DescribeSavingsPlanRates, POST /DescribeSavingsPlanRates, http code 200): input savingsPlanId (SavingsPlanId, @required), filters (SavingsPlanRateFilterList), maxResults (MaxResults, @range 1..1000), nextToken (PaginationToken, @length 0..1024, pattern '^[A-Za-z0-9/=\+]+$'); output searchResults -> SavingsPlanRateList of SavingsPlanRate{rate: Amount (string — so the RENDERING is the wire value), currency: CurrencyCode, unit: SavingsPlanRateUnit, productType: SavingsPlanProductType, serviceCode: SavingsPlanRateServiceCode, usageType: SavingsPlanRateUsageType (@length 0..255, pattern '^[a-zA-Z0-9_ \/.:-]+$'), operation: SavingsPlanRateOperation (@length 0..255, pattern '^[a-zA-Z0-9_ \/.:-]*$'), properties: list of SavingsPlanRateProperty{name: SavingsPlanRatePropertyKey enum [region|instanceType|instanceFamily|productDescription|tenancy], value}}; modeled errors ValidationException (400), ResourceNotFoundException (404), InternalServerException (500). The model fixes no rate value, no row order and no property order, so for the card's CONTENT this is recorded behavior only. The recording shows AWS answering HTTP 200 with a 32-row card for one plan, where (a) each row's `rate` is the catalog rate of that row's own dimension tuple, spelled at the catalog's own precision — 'Linux/UNIX' m5.large us-east-1 shared at '0.066', 'Linux with SQL Server Web' at '0.133', 'Windows with SQL Server Standard' at '0.638' — i.e. a short decimal, not a value padded to a fixed scale; (b) the rows arrive in the catalog's own order, with licensed-platform rows (operation 'RunInstances:0006', then 'RunInstances:0200') ahead of the unlicensed 'RunInstances' row; (c) each row's properties list arrives in the catalog's order tenancy, instanceType, region, productDescription. The requirement is that the card is SERVED from a stored per-combination catalog — rate, row order and property order taken from the catalog entry — not computed per request. The specific numbers, codes and index positions in the recording are catalog values filling that template, not themselves the requirement.

Emulator: HTTP 200 (status matches) but every one of the 32 compared positions diverges ($.searchResults[0] .. $.searchResults[31] all reported missing). At index 0 AWS's card has operation 'RunInstances:0006' / productDescription 'Windows with SQL Server Standard' / rate '0.638'; the emulator answers operation 'RunInstances' / 'Linux/UNIX' / rate '0.06696960'. At index 1 AWS has 'RunInstances:0200' / 'Linux with SQL Server Web' / '0.133'; the emulator answers 'RunInstances:00g0' / 'Red Hat BYOL Linux' / '0.06696960'. At index 2 AWS has 'RunInstances' / 'Linux/UNIX' / '0.066'; the emulator's unlicensed row is not there. Three distinct departures: the rate VALUE is derived rather than catalogued ('0.06696960' for the Linux/UNIX m5.large row where AWS answers '0.066'); every Amount is rendered at a FIXED eight fractional digits (state.rs AMOUNT_WIRE_DIGITS / format_amount) where AWS spells the rate at the catalog's precision; and the rows, and the properties inside each row, are emitted in the crate's own table order (Linux/UNIX, Red Hat BYOL Linux, ... / instanceType, productDescription, region, tenancy) rather than the recorded order. Hypothesis: the handler walks its own in-crate catalog lazily and prices each row through the chosen discount ladder (discount_basis_points -> discounted_units -> format_amount) at request time, so the price and the ordering are properties of the generator rather than of a stored card.

Why: DescribeSavingsPlanRates IS the price lookup for a purchased commitment. A client that sizes or compares a commitment reads a price that is wrong in the last digits and wrongly scaled in its spelling, and because `rate` is a STRING any client that compares, displays or hashes it sees a value AWS never emits. A client that walks the card positionally, or that pages it and joins row N of a page to a usage line item, lines up against the wrong platform entirely — the first row it reads is the unlicensed Linux row where AWS puts a Windows/SQL Server row — and no error signals any of it.

Fix: the DescribeSavingsPlanRates handler and the rate catalog it projects from (the operation's handler plus the rate-catalog and amount-rendering code in the crate's service state): rows must be served from a stored per-combination catalog keyed by serviceCode/usageType/operation/productDescription/region/tenancy/instanceType, in the catalog's order, with each row's rate and each row's property order taken from that entry, and the amount rendered as the catalog holds it rather than padded by the service-wide fixed-scale amount formatter.

=== Cause 2 of 2: DescribeSavingsPlans projects an empty tag map and omits the plan's unset dimension members — fixture savingsplans-queued-plan-delete-lifecycle, step task#11 ===

AWS: Smithy (com.amazonaws.savingsplans#DescribeSavingsPlans, POST /DescribeSavingsPlans, http code 200): output savingsPlans -> SavingsPlanList of SavingsPlan, whose members include tags (TagMap: TagKey -> TagValue, with NO length or pattern constraint on either), region (Region), ec2InstanceFamily (EC2InstanceFamily), state (SavingsPlanState enum), start/end/returnableUntil (String), commitment/upfrontPaymentAmount/recurringPaymentAmount (Amount), termDurationInSeconds (long, @default 0); modeled errors ValidationException (400), InternalServerException (500). Tag-key spelling is unconstrained by the model, so for the tag behavior this is recorded behavior only: the recording shows AWS returning the plan with its tag set exactly as written on it, INCLUDING a key carrying the reserved 'aws:' prefix ('aws:tag:<name>' -> its value), and carrying the dimension members that do not apply to a Compute plan (region, ec2InstanceFamily) as explicit nulls rather than dropping them. Requirement: the described plan's tags map is the stored tag set projected verbatim — every key byte-for-byte as supplied, mapped to its supplied value — and a member with no value for this plan type is still serialized, as null.

Emulator: HTTP 200 (status matches) and every other field of the record agrees (savingsPlanId, savingsPlanArn, offeringId, description, state 'queued-deleted', savingsPlanType, paymentOption, productTypes, currency, commitment, upfront/recurring amounts, termDurationInSeconds, and the start/end/returnableUntil relationships end = start + termDurationInSeconds - 1s and returnableUntil = start + 7 days), but the plan comes back with tags = {} — the reserved-prefix tag written earlier in the same fixture, on a write that answered success, is simply gone — and the serialized plan OMITS the region and ec2InstanceFamily keys where the recorded body carries them as null. The ABSOLUTE start/end/returnableUntil instants differ only because they are per-run clock values and are explicitly NOT part of this finding. Hypothesis: the tag-ingestion path filters keys beginning with 'aws:' before they reach the plan record (state.rs check_tags validates only count and key/value lengths, so the drop happens outside it), and the plan-to-wire projection skips members whose stored value is None.

Why: a client that tags a Savings Plan and reads it back through DescribeSavingsPlans sees a tag it successfully wrote disappear, so tag-driven cost allocation, inventory filtering and tag-based authorization all evaluate against a truncated set — and since both the write and the read answered 200, nothing tells the client state was discarded. Clients and SDK-adjacent code that read a fixed key set off the plan object, rather than probing for presence, break on the missing null members.

Fix: the DescribeSavingsPlans handler's plan-to-wire projection plus the tag ingestion into the plan record in the crate's service state — project the stored tag map unfiltered (reserved-prefix keys included) and serialize the plan's unset dimension members as null instead of skipping them; if a reserved-prefix key is to be rejected at all, reject it at write time with the modeled ValidationException (400) rather than accepting it and discarding it.
