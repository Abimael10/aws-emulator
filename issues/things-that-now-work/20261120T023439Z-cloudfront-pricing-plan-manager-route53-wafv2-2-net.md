# cloudfront__pricing-plan-manager__route53__wafv2: 2 net-new root causes — the tier-incompatibility refusal of AssociateResourcesToSubscription is worded as the generic eligibility refusal, and the hosted-zone join/leave scenario never reaches a verdict because its closing CancelSubscription never completes

AssociateResourcesToSubscription

## Description
Two net-new root causes, both grounded in the two failing checks of this suite run that are NOT marked ALREADY FILED or OWNED (every other failure in the run carries one of those markers and is skipped here).

=== Cause 1 of 2: AssociateResourcesToSubscription refuses a resource the subscription's PLAN TIER does not cover with the generic "not eligible for this subscription tier" sentence instead of AWS's tier-incompatibility message, so the refusal's Error.Message diverges. Failing check: cloudfront__pricing-plan-manager__route53__wafv2.free-subscription-refuses-a-key-value-store-and-keeps-its-resources ===

AWS: Smithy (services/service-com-amazonaws-pricingplanmanager-awspricingplanmanager/smithy-model/com-amazonaws-pricingplanmanager-awspricingplanmanager.json): AssociateResourcesToSubscription (POST /v1/AssociateResourcesToSubscription, success code 200) takes arn @required (SubscriptionArn, @length 1..2048), resourceArns @required (@length 1..10), ifMatch @required bound to the If-Match header and an optional clientToken; it answers the Subscription payload plus the @required ETag header and models ValidationException (httpError 400, @required message plus optional resourceId, doc "The request failed a business rule validation..."), ConflictException (409), ResourceNotFoundException (404), AccessDeniedException (403), ThrottlingException (429) and InternalServerException (500). The operation's own documentation says a CloudFront-family subscription "must include exactly one Amazon CloudFront distribution and one WAF web ACL. You can also include other supported resources, such as Amazon Route 53 hosted zones, and CloudFront KeyValueStores" — i.e. WHICH of those optional resources a subscription may carry is a property of the plan, and the model publishes no message text for refusing one. Recorded behavior: adding a CloudFront KeyValueStore to an ACTIVE CloudFront-family subscription bought at the FREE tier is refused HTTP 400 with Error.Code "ValidationException" and Error.Message "Resources are incompatible with plan tier 'FREE': modify resources or select a different tier." — the whole sentence is FIXED text except the quoted tier, which is the subscription's own planTier value ('FREE' here, any of FREE/PRO/BUSINESS/PREMIUM in general); the message names NO resource ARN at all. The same recording shows the refusal is inert: GetSubscription afterwards still reports exactly the resources the subscription already covered, status ACTIVE and the UNMOVED eTag, and that same eTag still admits the next legitimate associate (a Route 53 hosted zone).

Emulator: the status class and error code are right — HTTP 400 ValidationException — but the message is the OTHER refusal class's wording: "The following resources are not eligible for this subscription tier: arn:aws:cloudfront::<account>:key-value-store/<id>." The handler builds every eligibility refusal through one constructor: src/ops/associate_resources_to_subscription.rs lines 222-251 calls crate::state::ineligible_resources (src/state/resource_eligibility.rs, which merges two distinct questions — "does the plan TIER cover this resource kind" at covered_by_plan_tier, and "is this distribution actually fronted by a named web ACL") and then renders both through ineligible_resources_message (src/state/resource_eligibility.rs lines 78-83, the single format! of "The following resources are not eligible for this subscription tier: {list}."). That wording is correct for the association-prerequisite class (it is what the FIXED issue 20261109T121305Z-cloudfront-pricing-plan-manager-wafv2-createsubscription-does-not.md established for a distribution with no web ACL), but AWS words the TIER-incompatibility class differently, as a plan-tier statement naming the tier and no resource. Note this is NOT a REOPENS of that fixed issue: AWS also refuses this call, the refusal class and code match, and only the message text diverges. The rest of the check's assertions on this path (resources unchanged, status ACTIVE, eTag unmoved) were never reached because the message assertion fired first.

Why: the message is the only part of a 400 that tells a client WHICH rule it broke, and the two rules have opposite remedies. AWS's sentence says "modify resources or select a different tier" and names the tier, so a client (or an operator reading a log) upgrades the subscription or drops the resource. The emulator's sentence says the resources are not eligible and names an ARN, which reads as "this particular resource can never join" — the remedy AWS reserves for the missing-web-ACL prerequisite. Anything matching on the message (a retry-with-a-higher-tier path, a support runbook, a test asserting the refusal reason) takes the wrong branch, and the two refusal classes become indistinguishable because they are rendered identically.

Fix: the tier question's refusal needs its own wording, separate from the association-prerequisite one — crate::state's eligibility module (services/service-com-amazonaws-pricingplanmanager-awspricingplanmanager/src/state/resource_eligibility.rs: covered_by_plan_tier and the single ineligible_resources_message) and its two callers (src/ops/associate_resources_to_subscription.rs and the CreateSubscription handler), so a resource refused because the plan TIER does not cover it is answered with AWS's plan-tier sentence carrying the subscription's planTier, while a resource refused for the missing web-ACL association keeps the existing wording.

=== Cause 2 of 2: the hosted-zone join/leave scenario never reaches a verdict — its closing CancelSubscription is answered 200 but never completes, so the cancel-and-wait poll consumes the whole run budget. Failing check: cloudfront__pricing-plan-manager__route53__wafv2.hosted-zone-joins-and-leaves-a-free-subscription ===

AWS: Smithy (same model): CancelSubscription (POST /v1/CancelSubscription, success 200) takes arn @required and ifMatch @required bound to If-Match, answers the Subscription payload plus the @required ETag header, and GetSubscription (POST /v1/GetSubscription, @readonly) models ResourceNotFoundException (httpError 404, doc "The specified subscription was not found. Verify that the ARN is correct and that the subscription belongs to your account."). CancelSubscription's documentation: "For active subscriptions, the cancellation is scheduled to take effect at the end of the current billing period", and "For subscriptions in PENDING_APPROVAL status, the subscription is deleted immediately". Recorded behavior for the FREE CloudFront-family tier this check exercises: after CancelSubscription with the CURRENT eTag the subscription reaches its terminal state inside the check's own poll window — GetSubscription answers HTTP 404 with Error.Code "ResourceNotFoundException" and Error.Message "Subscription not found: <arn>. Verify the ARN is correct and the subscription exists in your account." (fixed text "Subscription not found: " and ". Verify the ARN is correct and the subscription exists in your account.", with the ARN copied from the request) and ListSubscriptions stops reporting it. Hypothesis: a FREE-tier subscription carries no billing commitment, so there is no period left to run out and the cancellation is processed promptly; what the recording fixes is that the terminal state IS reached, not any particular delay.

Emulator: the check is reported as "Error: Check timed out after 60.0s" with no assertion having fired, so none of the behaviour it exists to assert (the associate response listing the hosted zone, the subscription reading back as CloudFront/FREE, ListSubscriptions agreeing, the disassociate returning it to the required pair, and the post-cancel 404 with AWS's message) ever gets a verdict. Every wait in the check except the last is satisfied promptly by this emulator: its sibling check (Cause 1) reaches its own assertion through the identical create-distribution/deploy/create-web-ACL/attach/subscribe-to-ACTIVE setup inside the same 60 s cap, and the resource-change waits settle because src/state.rs SYNC_SPAN_MILLIS is 3_000 (begin_sync at src/state.rs:320-324, cleared by apply_due_changes at src/state.rs:524-537) — shorter than the check's 5 s poll interval. The one unbounded wait left is the closing _cancel helper: CancelSubscription(arn, ifMatch=<current eTag>) followed by a GetSubscription poll every 5 s with a 180 s deadline that breaks only on Error.Code "ResourceNotFoundException". The emulator answers that cancel 200 while leaving the record in status ACTIVE with a pending CANCELLATION change dated to the first instant of the NEXT calendar month (src/ops/cancel_subscription.rs attaches the change for any non-PENDING_APPROVAL record; src/state.rs end_of_billing_period at lines 614-628 mints that boundary and apply_due_changes removes the record only once the clock has passed it), so inside a session the record is never due, GetSubscription answers HTTP 200 / "ACTIVE" on every poll and the loop cannot terminate — it eats the remaining budget and the check dies there. Open issues reporting the SAME emulator behaviour from other recorded units, which do NOT carry this check's replay key and therefore do not cover it: 20261114T092337Z-cloudfront-pricing-plan-manager-wafv2-the-createsubscription-eligibility.md, 20261115T024858Z-cloudfront-pricing-plan-manager-wafv2-cancelsubscription-with-the.md and the wire-corpus issue 20261111T105841Z-pricing-plan-manager-cancelling-a-free-subscription-never-completes-and-publishes.md; this cause is the grounding of that defect from the Route 53 hosted-zone scenario and should be closed together with them.

Why: cancellation is the only observable end of a subscription's life, and a client written against AWS cancels and then waits for the subscription to disappear — that is what every teardown, every IaC destroy and every "is this resource still billing?" reconciliation does. Against the emulator that wait never returns and the client is killed by its own timeout. Everything keyed on "a live subscription still covers this resource" also stays armed forever: the CloudFront web-ACL removal lock cannot be released, a resource can never be re-subscribed, cross-service scenarios cannot clean up after themselves, and the emulator's own subscription capacity (src/state.rs MAX_SUBSCRIPTIONS) is consumed by subscriptions the client believes it cancelled.

Fix: the CancelSubscription handler (services/service-com-amazonaws-pricingplanmanager-awspricingplanmanager/src/ops/cancel_subscription.rs — the arm that attaches a pending CANCELLATION change to a non-PENDING_APPROVAL record) together with the scheduled-change processing in crate::state (src/state.rs, apply_due_changes / end_of_billing_period): complete the cancellation for a subscription that carries no billing commitment (the FREE tier, alongside the PENDING_APPROVAL case the handler already deletes immediately), so GetSubscription answers the modeled ResourceNotFoundException (404) with AWS's message and ListSubscriptions stops reporting it.
