# sagemaker: 2 net-new causes — StopNotebookInstance on a deleted instance answers the reader's "RecordNotFound. Notebook Instance Arn: …" instead of "Notebook Instance <arn> does not exist", and the CreateDomain duplicate-name scenario reaches no verdict because every Studio Domain transition costs a polling client a whole interval

> _Note: this issue was identified against the code base at commit `ba6912b745241f4a8c68b84730217fa4109e44cb`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
StopNotebookInstance, CreateDomain, DescribeDomain, DeleteDomain

## Description
TWO root causes, both grounded in failing checks the suite report lists under `### sagemaker` and neither marked ALREADY FILED nor OWNED by an open issue. They are numbered and each carries its own failing check ids; BOTH must be closed before this issue is submitted.

=== Cause 1 of 2: StopNotebookInstance on a notebook instance that no longer exists is refused with the READER's sentence ("RecordNotFound. Notebook Instance Arn: <arn>") instead of the transition's own "Notebook Instance <arn> does not exist" ===
AWS: Smithy — StopNotebookInstance takes NotebookInstanceName (required, @length 0..63, pattern ^[a-zA-Z0-9](-*[a-zA-Z0-9])*$), returns Unit, and declares `errors: []`, so a name the account holds no instance under travels as the service-common ValidationException on HTTP 400 (DeleteNotebookInstance and DescribeNotebookInstance model no errors either). Recorded behavior: the two families word the one fact differently — DescribeNotebookInstance on a deleted instance answers 400 ValidationException whose Message is the bare sentinel token `RecordNotFound` (no ARN, nothing from the request), while StopNotebookInstance on that same deleted name answers 400 ValidationException with `Notebook Instance <notebook-instance arn> does not exist`. In that message `Notebook Instance ` and ` does not exist` are the fixed text and `<notebook-instance arn>` is the arn:aws:sagemaker:<region>:<account>:notebook-instance/<name> the requested name resolves to in the region and account the request signed for — it is NOT a literal from any one run. The check states the same split in its own helper doc: "SageMaker reports a missing notebook instance as ValidationException 'RecordNotFound' (describe) or '... does not exist' (stop/delete)".
Emulator: the create/InService/stop/Stopped/delete legs and the post-delete DescribeNotebookInstance refusal (`ValidationException` / `RecordNotFound`) are all correct — only the stop-after-delete sentence diverges. StopNotebookInstance answers 400 ValidationException with `RecordNotFound. Notebook Instance Arn: arn:aws:sagemaker:<region>:<account>:notebook-instance/<name>` because the handler deliberately reuses the reader's token plus an ARN clause for the transitions (services/service-com-amazonaws-sagemaker-sagemaker/src/ops/stop_notebook_instance.rs:160-175 calls `crate::state::notebook_instance_record_not_found_at(&arn)`, defined at services/service-com-amazonaws-sagemaker-sagemaker/src/state/notebook_instance.rs:109-112 as `format!("{NOTEBOOK_INSTANCE_RECORD_NOT_FOUND}. Notebook Instance Arn: {arn}")`).
Why: `RecordNotFound` is the sentinel a client compares against to tell "this notebook is gone" from any other bad request, and AWS keeps it bare for the READER only. A client that cleans up (stop, then delete, then stop again idempotently) and matches the stop refusal on AWS's `... does not exist` text sees an unrecognized message and treats a benign already-gone instance as an unclassified failure; conversely a client that string-matches `RecordNotFound` on the stop path passes here and breaks against AWS. The status (400) and code (ValidationException) are right; only the wording is wrong, which is exactly the part a client branches on because the operation models no typed error.
Fix: the StopNotebookInstance handler's missing-instance branch and the message helper it uses — services/service-com-amazonaws-sagemaker-sagemaker/src/ops/stop_notebook_instance.rs (the `else` arm on the `notebook_instances` lookup) and services/service-com-amazonaws-sagemaker-sagemaker/src/state/notebook_instance.rs (`notebook_instance_record_not_found_at`; the slice already carries a `... does not exist` sentence for the presigned-URL mint, so the stop needs that form, not the reader's token). The helper is currently shared with DeleteNotebookInstance, so give the stop its own recorded sentence rather than re-wording both blindly.
Traces: sagemaker.notebook-instance-create-stop-delete-lifecycle.

=== Cause 2 of 2: every clock-owed Studio Domain transition (Pending->InService 3 s, Deleting->gone 3 s) is only materialised by a read that falls at or after the stored due instant, so a client polling at a realistic interval pays one whole interval per transition and the CreateDomain duplicate-name scenario is cut off with no verdict ===
AWS: the model states the lifecycle this scenario walks — CreateDomain answers DomainArn/DomainId and models ResourceInUse (400) and ResourceLimitExceeded (400); DescribeDomain.Status targets the DomainStatus enum and models ResourceNotFound (400); ListDomains is paginated over Domains. Recorded behavior for the refusals the scenario asserts: a second CreateDomain while the name is held answers 400 ResourceInUse with `The Domain Name '<domain name>' already exists in this account in this region.` (fixed text around the DomainName from the request), and after DeleteDomain both DescribeDomain and UpdateDomain on the dead id answer 400 ResourceNotFound with `Domain [<domain arn>] does not exist.` (fixed text around the ARN of the domain the id resolves to). Reaching any of those requires the documented poll-until-settled pattern, and every status in the chain has to be reachable by a client polling at a realistic interval.
Emulator: no call is refused wrongly — the scenario never gets far enough to assert anything. Each Studio Domain transition is deferred behind a stored wall-clock instant that the first read after the mutation always misses: `DOMAIN_IN_SERVICE_AFTER: Duration = Duration::from_secs(3)` and `DOMAIN_RELEASED_AFTER = DOMAIN_IN_SERVICE_AFTER` (services/service-com-amazonaws-sagemaker-sagemaker/src/state/domain.rs:45-62), materialised only by a reporting call (`Domain::settle_status` / `Domain::is_released`). The check probes immediately after each mutation, reads the transient value (Pending after create, still-describable after delete, Pending after the re-create) and then sleeps its own full interval. Hypothesis for the arithmetic: the three waits alone (DescribeDomain until InService at interval_s=20, DescribeDomain until refused after DeleteDomain at interval_s=20, DescribeDomain until InService on the identical re-create at interval_s=20) consume 60 s of pure sleeping, and the replay is cut off with `Check timed out after 60.0s` with no verdict — the ResourceInUse message, the "exactly one domain under this name" listing assertion, the ResourceNotFound wording for the dead id and the name-release-then-recreate restore are never exercised. Open issue 20261122T002913Z-sagemaker-3-net-new-causes-reopens-the-hyperpod.md describes this same clock-owed-span cause as its Cause 2, but for a DIFFERENT set of checks (its Issue-Trace-Ids are the app-lifecycle, create-app-already-running, domain-delete-with-active-user-profile and domain-user-profile-app-teardown checks); it does not carry this check's replay key, so this check is not covered by it and the duplicate-name/name-release scenario it blocks is not described there.
Why: a client (or `aws sagemaker wait`) that polls at a realistic interval sees the transient status on the describe that immediately follows each mutation and pays its whole interval for every transition; a scenario that creates, deletes and re-creates a domain pays it three times, so a perfectly ordinary Studio flow is unobservably slow even though the emulator holds the settled state a few seconds later. Everything past the waits — the duplicate-name ResourceInUse refusal, the proof that the rejected create left no second domain, the dead-id ResourceNotFound wording and the fact that deleting a domain releases its name — cannot be verified against the emulator at all.
Fix: the Studio Domain slice's clock-owed spans and the readers that materialise them — `DOMAIN_IN_SERVICE_AFTER` / `DOMAIN_RELEASED_AFTER` with `Domain::settle_status` / `Domain::is_released` (services/service-com-amazonaws-sagemaker-sagemaker/src/state/domain.rs), together with src/ops/describe_domain.rs, src/ops/list_domains.rs and src/ops/delete_domain.rs. The transient status must stay observable to the read that immediately follows the mutation WITHOUT costing a polling caller a full interval — e.g. settle on the first read AFTER the one that observed the transient value, instead of on whichever read happens to fall past a fixed wall-clock instant.
Traces: sagemaker.create-domain-duplicate-name-rejected.

## Steps to Reproduce
Against the booted emulator with boto3/botocore pointed at it (region and account as the harness signs for):

Cause 1 (sagemaker.notebook-instance-create-stop-delete-lifecycle):
1. Create an IAM role trusting sagemaker.amazonaws.com.
2. CreateNotebookInstance(NotebookInstanceName=n, InstanceType='ml.t3.medium', RoleArn=<role arn>).
3. Poll DescribeNotebookInstance until NotebookInstanceStatus='InService'; keep the returned NotebookInstanceArn.
4. StopNotebookInstance(NotebookInstanceName=n); poll DescribeNotebookInstance until 'Stopped'.
5. DeleteNotebookInstance(NotebookInstanceName=n); poll DescribeNotebookInstance until it is refused — it answers 400 ValidationException with Message exactly `RecordNotFound` (correct).
6. Call StopNotebookInstance(NotebookInstanceName=n) again. Expect HTTP 400, Error.Code 'ValidationException', Error.Message `Notebook Instance <the NotebookInstanceArn from step 3> does not exist`. Observed Error.Message: `RecordNotFound. Notebook Instance Arn: <that same ARN>`.

Cause 2 (sagemaker.create-domain-duplicate-name-rejected):
1. Create a Studio execution role trusting sagemaker.amazonaws.com and pick a VPC and one of its subnets.
2. CreateDomain(DomainName=d, AuthMode='IAM', DefaultUserSettings={'ExecutionRole': <role arn>}, VpcId=.., SubnetIds=[..]).
3. Poll DescribeDomain(DomainId=<new id>)['Status'] at a realistic interval (20 s) until 'InService'. The FIRST probe, taken straight after the create, reports 'Pending', so the client sleeps a whole 20 s interval before it can continue.
4. Repeat the identical CreateDomain and assert it is refused 400 ResourceInUse with `The Domain Name '<d>' already exists in this account in this region.`, and that ListDomains (all pages) shows exactly one domain named d.
5. DeleteDomain(DomainId=<id>, RetentionPolicy={'HomeEfsFileSystem': 'Delete'}) and poll DescribeDomain(DomainId=<id>) at 20 s until it is refused: again the first probe still succeeds, costing another full interval. Expect 400 ResourceNotFound with `Domain [<domain arn>] does not exist.`, and the same code/message from UpdateDomain on the dead id.
6. Re-issue the identical CreateDomain (the name must now be free) and poll to InService at 20 s — a third full interval.
Observed: the replay is cut off at `Check timed out after 60.0s` during these waits, so none of the assertions in steps 4-6 is ever reached. The emulator answers each call correctly a few seconds after the mutation, so the divergence is purely that the settle instant always falls after the read that follows the mutation.
