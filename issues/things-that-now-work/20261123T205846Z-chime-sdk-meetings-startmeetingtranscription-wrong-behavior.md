# Stop refusing Amazon Transcribe parameter combinations the model documents as a TranscriptFailed event

_Filed: 2026-11-23T20:58:46Z_
_Operation: StartMeetingTranscription | Class: wrong-behavior_

> _Note: this issue was identified against the code base at commit `0a450d5985d134a3d0e137cc6415ae1356d316f1`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Description

`StartMeetingTranscription` refuses the whole call with `BadRequestException` (HTTP 400) and persists nothing whenever the request's `EngineTranscribeSettings` breaks one of the Amazon Transcribe parameter-combination rules stated in the prose of its members (PreferredLanguage without LanguageOptions, VocabularyNames/VocabularyFilterNames without IdentifyLanguage, VocabularyName/VocabularyFilterName with IdentifyLanguage, LanguageOptions without IdentifyLanguage, IdentifyLanguage together with LanguageModelName, ...).

The model says the opposite about how an invalid COMBINATION of those settings is reported: it is not a synchronous failure of this API at all, it is a `TranscriptFailed` event carrying the `BadRequestException` that Amazon Transcribe generated. So for every one of these inputs the handler turns a documented acceptance (200, configuration becomes the one in force for the meeting) into a 400 with nothing stored, and the meeting keeps whatever it was transcribing before.

The handler's engine-choice check (neither or both of `EngineTranscribeSettings`/`EngineTranscribeMedicalSettings`) is NOT part of this finding: that rule is stated by `TranscriptionConfiguration` itself ("Must contain EngineTranscribeSettings or EngineTranscribeMedicalSettings."). Only the per-combination rules inside `EngineTranscribeSettings` are the ones the model routes to a `TranscriptFailed` event.

## Evidence

Smithy, `EngineTranscribeSettings` shape documentation (`smithy_query(query="shape",shape="EngineTranscribeSettings")`): "Settings specific for Amazon Transcribe as the live transcription engine. If you specify an invalid combination of parameters, a `TranscriptFailed` event will be sent with the contents of the `BadRequestException` generated by Amazon Transcribe. For more information on each parameter and which combinations are valid, refer to the StartStreamTranscription API in the Amazon Transcribe Developer Guide."

Smithy, the operation's own documentation (`smithy_query(query="doc",shape="StartMeetingTranscription")`) repeats it: "If you specify an invalid configuration, a `TranscriptFailed` event will be sent with the contents of the `BadRequestException` generated by Amazon Transcribe. For more information on each parameter and which combinations are valid, refer to the StartStreamTranscription API ..."

Handler does the opposite — `services/service-com-amazonaws-chimesdkmeetings-chimemeetingssdkservice/src/ops/start_meeting_transcription.rs:215`:
```
        if let Some(problem) = configuration_problem(&input.transcription_configuration) {
            return Err(StartMeetingTranscriptionErrorModeled::BadRequestException(
                crate::state::bad_request(problem),
            )
            .into());
        }
```
and the combination rules it refuses on, same file, e.g. `:333`:
```
    if settings.preferred_language.is_some()
        && (!identify_language || settings.language_options.is_none())
    {
        return Some(
            "EngineTranscribeSettings can only include PreferredLanguage together with \
             IdentifyLanguage and LanguageOptions"

```
and `:377`:
```
    if !identify_language && settings.vocabulary_names.is_some() {

```
(The member these are drawn from only states guidance, not an error: `VocabularyNames` documents "If you don't include `IdentifyLanguage` and want to use a custom vocabulary with your transcription, use the `VocabularyName` parameter instead.")

Current coverage pins the refusals: `tests/all/meeting_transcription.rs:11` — "a configuration that breaks a combination rule the model documents is refused with `BadRequestException` (HTTP 400)" and `:612` asserts `(400, Some("BadRequestException"))` for "one row per documented combination rule"; that stated reason is what the `EngineTranscribeSettings` sentence above contradicts.

## Steps to Reproduce

1. CreateMeeting(ClientRequestToken='tok-1', MediaRegion='us-east-1', ExternalMeetingId='ext-1') and keep the MeetingId.
2. StartMeetingTranscription(MeetingId=<id>, TranscriptionConfiguration={EngineTranscribeSettings:{LanguageCode:'en-US', VocabularyNames:'vocab-a,vocab-b'}}) — a combination the model documents as reported by a TranscriptFailed event, so the call itself is accepted.
3. Observe HTTP 400 BadRequestException "EngineTranscribeSettings that includes no IdentifyLanguage must name its custom vocabulary in VocabularyName instead of VocabularyNames" instead of a success, and no transcription recorded on the meeting.
4. Repeat with {EngineTranscribeSettings:{IdentifyLanguage:true, PreferredLanguage:'en-US'}} — same synchronous 400 for another Amazon Transcribe combination rule.
