# appsync__dynamodb: 3 net-new causes — a VERSIONED AMAZON_DYNAMODB data source never stamps _version/_lastChangedAt, the Sync operation is refused outright, and a forged nextToken is accepted by the Query resolver

> _Note: this issue was identified against the code base at commit `864dd26a02416cc990250070e65c7b703d06755e`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
Mutation/Query over an AMAZON_DYNAMODB data source (PutItem/UpdateItem/DeleteItem/Query/Sync)

## Description
Three distinct root causes in the AppSync GraphQL data plane's AMAZON_DYNAMODB data-source resolver, all reached through the emulator's own GraphQL endpoint. All three are net-new for this service heading: the open issue 20261119T081201Z-appsync-dynamodb-lambda-a-versioned-amazon-dynamodb-data.md describes the same _version symptom but is bound to the appsync__dynamodb__lambda heading and does not carry any of the replay keys below; 20261114T140817Z-appsync-dynamodb-every-dynamodb-data-source-resolver-check.md owns a different set of checks (hangs) and not these.

=== Cause 1 of 3: a VERSIONED (conflict-detection) AMAZON_DYNAMODB data source never stamps _version / _lastChangedAt ===
AWS: recorded behavior only for the stamping itself; the AppSync conflict-detection contract is documented by AWS: when a data source is created with versioned=true (DeltaSyncConfig / conflict detection VERSION), every write performed through its resolver stamps the system attributes `_version` (a monotonically increasing integer, 1 for the first write of an item) and `_lastChangedAt` (epoch millis) on the stored item and returns them in the selection set. Conflict detection then compares the caller's `expectedVersion` against the stored `_version` and, on a mismatch, answers a GraphQL error with errorType `ConflictUnhandled` (or the configured conflict-handler outcome) carrying the server-side item and its `_version` in `error.data`. Automerge resolves disjoint writes by merging and incrementing `_version` once per accepted write; a stale delete is refused and writes no tombstone.
Emulator: the first write through a versioned data source returns `_version: null` (and `_lastChangedAt: null`) in the response payload and never stores either attribute, e.g. `{'data': {'putPost': {'id': 'post-…', 'title': 'titleA-…', '_version': None}}}` and `{'id': 'post-…', 'title': 'seed-…', 'alpha': None, 'beta': None, 'gamma': None, '_version': None}`. Because no version is ever recorded, nothing downstream can engage: no conflict is ever detected, no automerge happens, no distinct versions are handed out to concurrent stale writers, and the stale-delete refusal never fires.
Why: a client built on AppSync's DataStore/delta-sync model relies on `_version` to detect conflicts. With `_version` always null, `expectedVersion` can never mismatch, so every stale write silently overwrites the server's value — a last-writer-wins data loss where AWS refuses the write — and `if (e.errorType === 'ConflictUnhandled')` retry branches are dead code.
Fix: the AMAZON_DYNAMODB data-source resolver's versioned-write path (the component that applies a resolver's PutItem/UpdateItem/DeleteItem request against the table) must maintain and project `_version`/`_lastChangedAt` and route a version mismatch through the data source's conflict handler.

=== Cause 2 of 3: the AMAZON_DYNAMODB data source does not implement the Sync operation ===
AWS: recorded behavior only. A versioned AMAZON_DYNAMODB data source accepts a resolver request-mapping `operation: "Sync"` and answers a delta-sync page: the items changed since `lastSync` (including tombstoned items, which carry `_deleted: true`), plus `startedAt` and `nextToken`. `Sync` is a first-class operation of that data-source type alongside GetItem/PutItem/UpdateItem/DeleteItem/Query/Scan/BatchGetItem/BatchPutItem/BatchDeleteItem/TransactWriteItems.
Emulator: the field resolves to null with HTTP 200 and a GraphQL error whose message is emulator-authored and enumerates a short, wrong operation list: `{'data': {'syncPosts': None}, 'errors': [{'path': ['syncPosts'], 'message': 'An AMAZON_DYNAMODB data source serves the operations GetItem, PutItem, UpdateItem, DeleteItem, Query, Scan, and this request names "Sync".', 'errorType': 'Code'}]}`. No such sentence exists in AWS; `errorType: 'Code'` is not an AppSync errorType either.
Why: a delta-sync client can never perform its initial or incremental sync — every `syncX` query returns null plus an error, so the entire offline/DataStore flow is unavailable, and the refusal text misleads the operator into believing Sync is not an AppSync operation.
Fix: the AMAZON_DYNAMODB data-source resolver's operation dispatch (add `Sync`, backed by the versioned store's change log), and the GraphQL error serializer that currently emits the hand-written sentence and `errorType: 'Code'`.
Traces: appsync__dynamodb.deep-appsync-1-appsync-conflict-sync-delta-returns-only-changes-after-lastsync-with-tombstone

=== Cause 3 of 3: the Query resolver accepts a nextToken AppSync never minted ===
AWS: recorded behavior only. A `nextToken` presented to an AMAZON_DYNAMODB Query resolver is an AppSync-minted, encrypted/opaque cursor. A token the service never issued (a forged or corrupted string) is refused: the field resolves to null and the response carries an `errors` entry for that path; it is never treated as "no cursor".
Emulator: the forged token is accepted and the query answers success with an empty page and no errors: `{'data': {'listItems': {'items': None, 'nextToken': None}}}` — status 200, `errors` absent.
Why: a client that corrupts or replays a stale cursor is told, indistinguishably from a genuine end-of-results, that the collection is empty. Pagination silently truncates instead of failing loudly, so partial result sets are mistaken for complete ones.
Fix: the AMAZON_DYNAMODB data-source resolver's Query/Scan pagination-token decoder — an undecodable or unauthenticated token must produce a field error rather than a null/empty page.
Traces: appsync__dynamodb.appsync-ddb-query-resolver-malformed-next-token-rejected

## Evidence
Cause 1 — expected: the first write through a versioned data source returns and stores _version = 1 (and a non-null _lastChangedAt); subsequent writes increment it, and a stale expectedVersion is refused with a ConflictUnhandled-class GraphQL error carrying the server item and its version. Actual: `AssertionError: a versioned data source must stamp the first write with _version 1: {'data': {'putPost': {'id': 'post-65baa8aa2ec3', 'title': 'titleA-b2d19125b550', '_version': None}}}` and `AssertionError: a versioned create must stamp _version 1: {'id': 'post-1d37363ef54f', 'title': 'seed-91c582696f42', '_version': None, '_deleted': None, '_lastChangedAt': None}`. (The ids/titles shown are per-run values; the requirement is that _version is 1 and _lastChangedAt is present, not these literals.)

Cause 2 — expected: HTTP 200 with `data.syncPosts` populated (items changed after lastSync, tombstones flagged _deleted, plus startedAt/nextToken) and no `errors`. Actual: HTTP 200 with `{'data': {'syncPosts': None}, 'errors': [{'path': ['syncPosts'], 'message': 'An AMAZON_DYNAMODB data source serves the operations GetItem, PutItem, UpdateItem, DeleteItem, Query, Scan, and this request names "Sync".', 'errorType': 'Code'}]}`. The whole message sentence and the errorType value `Code` are emulator-authored text with no AWS counterpart; the only request-derived part is the quoted operation name ("Sync").

Cause 3 — expected: the response for a forged nextToken carries a non-empty `errors` array. Actual: `AssertionError: a nextToken AppSync never minted was accepted: {'data': {'listItems': {'items': None, 'nextToken': None}}}` — success, no errors.
