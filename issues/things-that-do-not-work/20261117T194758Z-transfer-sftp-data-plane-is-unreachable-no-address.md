# Transfer SFTP data plane is unreachable: no address or SSH listener is served for a server's public endpoint <serverId>.server.transfer.<region>.amazonaws.com, and the regional endpoint zone is not served either (2 causes)

> _Note: this issue was identified against the code base at commit `e001304b013b7ad6eb10330af0cea4f05bddc43e`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
CreateServer

## Description
TWO root causes, grounded in 28 failing behavioral checks. Every one of them stops before its first assertion because the emulator offers NO address for the Transfer Family SFTP endpoint namespace: the harness egress hook refuses with `CapabilityNotOffered: the target serves no address for <host>` / `simparity.egress.EgressRefused: egress refused: '<host>' is not the endpoint under test (127.0.0.1) ... If the host came from a URL the emulator returned, the emulator announces an address other than the endpoint it is reached on`. The control plane answers (CreateServer/StartServer/CreateUser all succeed and DescribeServer reaches ONLINE), so the server is announced as provisioned and ONLINE while nothing anywhere terminates SSH for it.

Cause 1 of 2 — the per-server PUBLIC SFTP endpoint serves no address and no SSH listener (27 checks).
AWS: Smithy: CreateServer(Protocols 1..4 containing SFTP, EndpointType default PUBLIC, IdentityProviderType, HostKey) -> ServerId (required, pattern ^s-([0-9a-f]{17})$); StartServer(ServerId) -> Unit; DescribeServer(ServerId) -> DescribedServer whose State reaches ONLINE. The model describes only the control plane; the data plane is recorded behavior only: for a PUBLIC-endpoint server AWS publishes the hostname `<serverId>.server.transfer.<region>.amazonaws.com`, that name resolves to one or more addresses, TCP 22 on it answers with an `SSH-2.0-...` identification string, and a user created with CreateUser(SshPublicKeyBody=...) can authenticate with the matching private key and read/write objects in the backing S3 bucket under its HomeDirectory. The recordings exercise exactly that: wait for the SSH banner on port 22, then run the real `sftp`/paramiko client against it.
Emulator: the host is not served at all. The first socket to `<serverId>.server.transfer.us-west-2.amazonaws.com:22` (and the `getaddrinfo` behind it) is refused by the egress gate with `CapabilityNotOffered: the target serves no address for s-00000000000000001.server.transfer.us-west-2.amazonaws.com` (also observed for the second and third server minted in a run, s-00000000000000002 / s-00000000000000003), i.e. the emulator never registers/announces a listener for the endpoint name its own ServerId implies, so no SSH banner, no authentication, no SFTP session, no workflow OnUpload trigger and no connector transfer can ever happen. Nothing in the trace is a per-run value: the host template is `<ServerId from CreateServer>.server.transfer.<region of the client>.amazonaws.com` and only the id and region vary.
Why: a client that follows AWS's documented flow — CreateServer, StartServer, poll DescribeServer to ONLINE, CreateUser with an SSH key, then connect `sftp -i key user@<serverId>.server.transfer.<region>.amazonaws.com` — gets a connection/resolution failure against an endpoint the control plane reports ONLINE. Everything downstream of a session is unobservable too: logical/PATH home-directory jails, scope-down session policies, security-policy algorithm negotiation, the presented host key, pre-authentication banners, SETSTAT handling, rename/remove against the backing S3 object, service-managed key rejection, stopped-server refusal, OnUpload workflow executions (and therefore DescribeExecution/SendWorkflowStepState on a real execution) and connector send/retrieve flows.
Fix: the Transfer server data plane — the component that should stand up an SSH/SFTP listener per server record and register (announce) its endpoint address under the server's PUBLIC endpoint hostname — plus the server state machine that gates it on StartServer/StopServer and the user/identity-provider and S3-backed filesystem layers behind it. The ONLINE state reported by DescribeServer must only be reachable when that listener actually answers on TCP 22 for the announced name.

Cause 2 of 2 — the Transfer SFTP endpoint zone apex of any other enabled region is not served either, so the cross-region isolation check cannot even derive a second region (1 check).
AWS: recorded behavior only (the Smithy model binds no DNS behavior): `server.transfer.<region>.amazonaws.com` is a published zone for every region where Transfer Family is enabled, so it resolves to at least one address, while `<serverId>.server.transfer.<other-region>.amazonaws.com` for a server minted in a different region does NOT resolve, and DescribeServer in that other region answers ResourceNotFoundException with message `Unknown server` (fixed text, no request values) and ListServers there omits the id. The recording's assertion is the pair: the zone exists, the id under it does not.
Emulator: the probe of the zone apex is refused outright — `CapabilityNotOffered: the target serves no address for server.transfer.ap-northeast-1.amazonaws.com` — so the emulator serves no address for a second region's SFTP endpoint zone at all and the check dies at its precondition, before the positive control (an SFTP session under the server's own region, which needs Cause 1) and before the cross-region absence assertions on the data plane and on DescribeServer/ListServers. The region name is environment-derived (the first enabled region other than the one under test, sorted); the requirement is the zone template `server.transfer.<region>.amazonaws.com`, not `ap-northeast-1`.
Why: a client cannot distinguish 'this region has no Transfer Family endpoint' from 'this server does not exist in that region'. Region scoping is unverifiable: the emulator can neither show that a region's endpoint zone exists nor that a server id is absent under it.
Fix: the same endpoint-announcement layer as Cause 1, extended to the regional endpoint zone — the emulator must serve/announce `server.transfer.<region>.amazonaws.com` for each region it emulates while serving NO per-server name for a server that was not created in that region, and the regional partitioning of the server store must keep DescribeServer/ListServers in another region from seeing the id (DescribeServer there answering ResourceNotFoundException / `Unknown server`).
