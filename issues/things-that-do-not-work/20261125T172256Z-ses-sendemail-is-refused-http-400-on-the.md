# ses SendEmail is refused HTTP 400 on the inbound receipt-rule scenario, so the send that must trigger receipt-rule delivery never returns a MessageId

> _Note: this issue was identified against the code base at commit `f5795699eb089f612d9502594c73cb000f614fb8`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
SendEmail

## Description
One cause, on service token ses, in fixture ses-inbound-mail-published-by-receipt-rule-sns-action.

Cause 1 of 1: a classic-SES SendEmail issued after the fixture's receiving setup (identity established, receipt rule set + receipt rule with an SNS action created and activated) is refused with HTTP 400 and an error body, where AWS accepts the send with HTTP 200 and a minted MessageId.

AWS: Smithy (com.amazonaws.ses#SendEmail, awsQuery): input Source/Destination/Message are @required (Source target Address, Destination target Destination with ToAddresses/CcAddresses/BccAddresses, Message target Message with required Subject/Body), ConfigurationSetName/Tags/ReplyToAddresses/ReturnPath/SourceArn/ReturnPathArn optional; output SendEmailResponse carries MessageId (@required). SUCCESS status is 200, and on the awsQuery wire the body is SendEmailResponse { SendEmailResult { MessageId }, ResponseMetadata { RequestId } }. The ONLY refusals the model declares are AccountSendingPausedException (400, awsQueryError AccountSendingPausedException), ConfigurationSetDoesNotExistException (400, ConfigurationSetDoesNotExist), ConfigurationSetSendingPausedException (400, ConfigurationSetSendingPausedException), MailFromDomainNotVerifiedException (400, MailFromDomainNotVerifiedException) and MessageRejected (400, MessageRejected); the operation's own documentation states the conditions that produce them (unverified sending identity, >10 MB message, no recipient, an address not of the form UserName@[SubDomain.]Domain.TopLevelDomain, more than 50 recipients, sending quota). Recorded behavior: with the sending identity and the active receipt rule set established by the preceding steps of this same fixture (all of which replay as passing), this send is ACCEPTED — HTTP 200 with SendEmailResult.MessageId and ResponseMetadata.RequestId, both per-run values the recording asserts by shape only ('<shaped-not-asserted>'), so no literal id or request id is a requirement. The requirement is that a well-formed send from the established sending identity to a recipient in the receiving domain is accepted with 200 and a freshly minted MessageId, not refused.

Emulator: answers HTTP 400 and serves no SendEmailResponse at all — replay: "status: expected 200, got 400" and "$.SendEmailResponse: missing (expected {'SendEmailResult': {'MessageId': '<shaped-not-asserted>'}, 'ResponseMetadata': {'RequestId': '<shaped-not-asserted>'}}, got None)". The step asserts only the status and the response body, so the refusal's awsQuery error code and message are NOT captured by this divergence; whichever modeled refusal the handler raises, it is raised on a request AWS accepts, and none of the modeled conditions applies here (the identity, the rule set and the rule all exist, created by earlier passing steps of the same fixture, no configuration set is involved, the request carries one valid recipient and a small body). Hypothesis (to be confirmed by capturing the response body): the send is refused by the unverified-sender gate in the handler, which answers MessageRejected with the fixed text "Email address is not verified. The following identities failed the check in region <REGION>: <identities>" (the region token upper-cased from the request's credential scope and the identity list taken from the request — the only variable parts of that message); the gate reads this surface's own identity table, whose records only leave VerificationStatus::Pending once a synthetic 3-second span has elapsed and which is reconciled against the shared account identity registry, so a sending identity the fixture established through the setup steps can read as not-verified at send time. The other 400 gates on this path (empty recipient set, >50 recipients, illegal address, account sending paused, configuration-set absent/paused, 24-hour quota) are the alternatives a fixer should rule out from the captured error code.

Why: SendEmail is the only step that can put a message into the receiving half of SES, so a client that sets up a receipt rule set with an SNS action and then sends to an address in its own receiving domain is told its message was rejected, gets no MessageId to correlate on, and no inbound message is ever composed, matched against the active receipt rule set, or published to SNS. Every downstream consumer of the receipt-rule notification sees nothing and cannot distinguish "no mail arrived" from "the send was refused"; the two sqs steps that follow in this fixture (task#10 GetQueueAttributes, task#11 ReceiveMessage) therefore also fail, and they are owned by the open issue 20261124T235503Z-sqs-a-queue-subscribed-to-an-ses-configuration.md.

Fix: the SendEmail handler's refusal gating and the identity/verification state the sender gate reads — services/service-com-amazonaws-ses-simpleemailservice/src/ops/send_email.rs (the gate chain in handle(): the recipient-set checks, the sender gate at the is_verified_sender call, and the account/configuration-set pauses) together with services/service-com-amazonaws-ses-simpleemailservice/src/state.rs (is_verified_sender / holds_verified_key, Identity::settle_verification and IDENTITY_VERIFICATION_SPAN, reconcile_identities). A send whose request is well formed, whose sending identity the account has established and which names no configuration set must pass the chain and return 200 with a minted MessageId; only the modeled conditions may refuse it, and when one does the awsQuery error code and message must be the modeled one for that condition.
