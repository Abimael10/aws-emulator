# ds: the Managed Microsoft AD create→Active and DeleteDirectory→gone legs each settle only AFTER the probe that follows the call, so the full MSAD lifecycle check reaches no verdict at the 60 s budget

> _Note: this issue was identified against the code base at commit `0139b649892491ec475f7b8e31445a257f779000`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
DescribeDirectories

## Description
One net-new cause, grounded in one failing behavioral check.

Cause 1 of 1: the whole Managed Microsoft AD lifecycle scenario — create → Active with a fully populated DirectoryDescription and real ENIs/security group, then DeleteDirectory → gone with the three distinct not-found answers — reaches NO verdict: it is killed with "Check timed out after 60.0s" while asleep in a poll loop (failing check id: ds.simple-ad-small-lifecycle-to-active-then-deleted).

AWS: the lifecycle is modelled. Smithy (services/service-com-amazonaws-directoryservice-directoryservice-20150416/smithy-model/com-amazonaws-directoryservice-directoryservice-20150416.json): CreateMicrosoftAD input {Name @required pattern ^([a-zA-Z0-9]+[\\.-])+([a-zA-Z0-9])+$, Password @required @sensitive, VpcSettings @required, Edition enum DirectoryEdition, Description @length 0..128}, output {DirectoryId pattern ^d-[0-9a-f]{10}$}, errors ClientException(400)/DirectoryLimitExceededException(400)/InvalidParameterException(400)/UnsupportedOperationException(400)/ServiceException(500) — i.e. AWS answers CreateMicrosoftAD before the directory is usable. DirectoryStage = [Requested, Creating, Created, Active, Inoperable, Impaired, Restoring, RestoreFailed, Deleting, Deleted, Failed, Updating], so the Requested/Creating/Created → Active walk and the Deleting → Deleted walk are modelled as observable chains. DescribeDirectories input {DirectoryIds, NextToken, Limit @range min 0} / output {DirectoryDescriptions, NextToken}, errors incl. EntityDoesNotExistException(400). DeleteDirectory input {DirectoryId @required pattern ^d-[0-9a-f]{10}$} / output {DirectoryId}, errors ClientException(400)/EntityDoesNotExistException(400)/ServiceException(500). GetSnapshotLimits input {DirectoryId @required} / output {SnapshotLimits}, same error set. For the wall clock there is recorded behavior only: on real AWS the create leg alone takes tens of minutes, so the 60 s per-check ceiling belongs to the emulator environment, not to the recording — what the emulator owns is WHEN a clock-owed transition becomes observable.

Emulator: no status, error code, message or shape divergence is reported for this check at all — the only output is "Check timed out after 60.0s". The scenario owes two clock-owed legs and probes each immediately after the call that starts it: create_microsoft_ad then poll describe_directories for Stage in {Active, Inoperable, Impaired, Failed, Deleted} at interval 30 s, and delete_directory then poll describe_directories until the directory is gone at interval 30 s. Because each transition lands only AFTER the first probe, a client pays one FULL poll interval per leg: 30 s + 30 s = exactly the 60 s ceiling, so the check dies inside the second sleep (plus the sts/ec2/ds traffic the scenario also issues for the VPC substrate), before the cleanup reaper even runs.

Why: a client relying on AWS's behavior gets no verdict on the single richest ds contract in the suite, and a regression in any of it passes unnoticed today — that a Standard MicrosoftAD reaches Stage 'Active' having passed only through {Requested, Creating, Created}; that the DirectoryDescription echoes Name/ShortName/Edition and reports the DERIVED members (Type 'MicrosoftAD', Size 'Small', SsoEnabled false, Alias defaulting to the DirectoryId, AccessUrl leading with the alias, LaunchTime and StageLastUpdatedDateTime with StageLastUpdatedDateTime >= LaunchTime, DesiredNumberOfDomainControllers 2, a concrete OsVersion, RegionsInfo.PrimaryRegion == the creation Region with no AdditionalRegions, NetworkType 'IPv4' with no DnsIpv6Addrs, and never the password); that VpcSettings reports the caller's VpcId/SubnetIds, exactly two distinct AvailabilityZones and an sg- SecurityGroupId; that the two DnsIpAddrs are the private addresses of two real EC2 ENIs, one per subnet, described 'AWS created network interface for directory <directoryId>', inside the directory's VPC CIDR and members of that security group; that the minted group is named '<directoryId>_controllers', lives in the caller's VPC and scopes every ingress rule to the VPC CIDR; and that DeleteDirectory drives the directory to gone and releases those ENIs. It also leaves unverified the three DISTINCT not-found answers the check exists to separate: DescribeDirectories on a DELETED id succeeds 200 with an EMPTY DirectoryDescriptions list; DescribeDirectories on a well-formed id this account was NEVER issued is refused HTTP 400 / Error.Code 'EntityDoesNotExistException' with the invalid-id sentence — fixed text 'Invalid directory ID(s): ' + '. : RequestId: ', the id taken from the request and the RequestId from the response; and every operation that must resolve the id to a LIVE directory (a second DeleteDirectory, GetSnapshotLimits) is refused HTTP 400 / 'EntityDoesNotExistException' with the does-not-exist sentence instead — fixed text "Directory: '" + "' does not exist. : RequestId: ", again with the id from the request and the RequestId from the response. No literal id, address, group id or RequestId from any single run is part of those templates.

Related open issues that this replay did NOT mark as owning this check, and which therefore do not cover it: 20261113T164150Z-ds-3-net-new-causes-the-msad-stage.md (same clock-owed-transition mechanism on the data-access toggle, the RemoveRegion/DeleteDirectory leg and the trust state machine) and 20261118T131546Z-ds-logs-the-directory-service-log-subscription-delivery.md. This cause extends the same mechanism to the FULL create→describe→delete→not-found-contrast lifecycle, which neither names; it should be resolved as one work item with them.

Fix: this is not an operation-handler response defect — no ds handler is reported answering wrongly here. The owner is the ds state machine's clock-owed-transition contract in the directory-service crate's state (the directory-stage chain Requested/Creating/Created → Active and Deleting → gone, and the EC2-side ENI/security-group materialisation and release that hangs off it) as it meets the suite's per-check ceiling: either those transition spans are applied so that a settled value is observable on the client's FIRST probe after the call — accepting that the transient stages and the refusals depending on them (DirectoryUnavailableException) stop being observable, and loosening the in-tree suites that pin them — or the harness's per-check budget and poll intervals for this scenario.

Traces: ds.simple-ad-small-lifecycle-to-active-then-deleted (verdict 'mismatch', detail "Check timed out after 60.0s", killed inside the _poll helper's time.sleep(interval_s)).
