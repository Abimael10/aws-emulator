# apigateway: 4 net-new wire causes — control-plane responses report emulator-minted identities and measurements instead of the ones AWS reports

> _Note: this issue was identified against the code base at commit `1bab6ccfadd8e456dfdfaa55eb16233f496412b2`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
CreateDocumentationPart

## Description
FOUR (4) net-new root causes in the API Gateway REST control plane (service token `apigateway`), all reported by the simparity-wire-aws-v1 replay with verdict=mismatch, empty `stub_path` and empty `owned_by`. They share one family — the emulator answers with an IDENTITY or a MEASUREMENT it mints itself rather than the one the recorded service reports for the same request, so the status code can agree while the response describes a different resource or a value that was never measured. Each is its own handler and each must be closed and re-replayed separately. Causes are numbered 1 of 4 .. 4 of 4 below; a fix that closes only one leaves the other three open.

NOTE ON PRIOR COVERAGE: causes 1 and 2 are REGRESSIONS. Issue 20261116T063445Z-apigateway-duplicate-location-createdocumentationpart-mints-a-second-part.md asserted exactly these two rules, but it is RESOLVED (listed [fixed]), so it covers nothing — the replay reports both clusters with owned_by=[] and the behavior still diverges. Cause 2 is additionally surprising because the current DeleteRestApi handler DOES carry an existence check (services/service-com-amazonaws-apigateway-backplanecontrolservice/src/ops/delete_rest_api.rs lines 174-179), so the check is not reached, or not reached with the state the recorded account was in, for this delete.

=== Cause 1 of 4: CreateDocumentationPart for a location the REST API already documents mints a brand-new part id instead of reporting the existing part's id ===
AWS: Smithy (services/service-com-amazonaws-apigateway-backplanecontrolservice/smithy-model/com-amazonaws-apigateway-backplanecontrolservice.json) models CreateDocumentationPart as POST /restapis/{restApiId}/documentation/parts, http success code 201, input { restApiId (httpLabel, required), location: DocumentationPartLocation (required), properties: String (required) }, output DocumentationPart { id, location, properties }; modeled errors BadRequestException(400), ConflictException(409), LimitExceededException(429), NotFoundException(404), TooManyRequestsException(429), UnauthorizedException(401). The per-location IDENTITY rule is recorded behavior only: the model names ConflictException but does not spell out part identity. The fixture asserts this response's `id` BY REFERENCE to the documentation-part id already bound earlier in the same fixture for the same location (the harness prints the expectation as the capture token `{{first_part_id}}`, not as a literal id), and the recorded service answers 201 reporting THAT id — i.e. a documentation part is identified by its (restApiId, location) pair, so a create naming a location that already has a part resolves to the part that is already there instead of adding a second one. Hypothesis (the recording establishes only the id equality): AWS keys the documentation-part collection on the normalized location, which is also why ConflictException exists for this operation at all.
Emulator: the same request is answered 201 carrying a freshly generated 10-character documentation-part id, so `$.id` diverges from the id of the part that already exists for that location. The id STRING observed in any one run is a per-run value and is NOT the requirement; the requirement is the EQUALITY with the existing part's id.
Why: re-asserting documentation for a location is the normal pattern (documentation regenerated from source control, or the same call retried after a timeout). Against the emulator a client silently accumulates one extra documentation part per call instead of landing on the one part for that location; it cannot correlate the returned id with the part it already tracks, GetDocumentationParts then enumerates duplicates for a single entity, and GetExport/OpenAPI publication renders that location's documentation more than once. Nothing in the response signals the duplication.
Fix: the CreateDocumentationPart handler and the documentation-part state it writes — match the incoming location against the restApi's existing parts and resolve to that part (reporting its id, location and properties) instead of inserting a new entry under a new id.
Traces: apigateway-documentation-part-conflict-duplicate-location#task#2 (representative of this issue); cluster also covers apigateway-documentation-parts-multiple-locations-and-listing#task#5, #task#6, #task#7.

=== Cause 2 of 4: DeleteRestApi for a restApiId the account does not hold is absorbed with 202 instead of being refused 404 NotFoundException ===
AWS: Smithy models DeleteRestApi as DELETE /restapis/{restApiId} with http success code 202 and output Unit (empty body); modeled errors BadRequestException(400), ConflictException(409), NotFoundException(404), TooManyRequestsException(429), UnauthorizedException(401). A DELETE naming a REST API id the account does not hold — one that never existed, or one a previous delete already removed — is REFUSED, not absorbed: the recorded service answers HTTP 404 and the error is the modeled NotFoundException (the REST protocol reports it in x-amzn-errortype and in the JSON body's `message`). The recorded step asserts the STATUS for this cause (the divergence's key list is `status` only); the error class is the modeled NotFoundException and the message is API Gateway's fixed invalid-REST-API-identifier sentence whose only variable part is the identifier taken from the request path — the same sentence this crate already mints for its other missing-REST-API refusals (crate::state::no_such_rest_api). No part of that message is drawn from one run's state.
Emulator: the same DELETE is answered 202 with an empty body — byte-for-byte the response of a delete that did remove an API — so no x-amzn-errortype and no message are produced at all. The emulator therefore reports a successful destructive operation on a REST API the recorded account no longer has. Hypothesis (neither the model nor the replay output states the mechanism): the id is still resolvable in the emulator's state when the delete arrives, so the existence check at delete_rest_api.rs:174 passes — note the delete-acceptance window that same handler documents (`store.accept_rest_api_delete`, lines 192-203, keeping a deleted API referenceable to callers that race the delete), which is exactly the kind of retained record that makes a repeat delete look like a first one.
Why: DeleteRestApi is how a client both deletes AND probes. A caller deleting an API it already deleted, or deleting with a stale or mistyped id, is told the delete succeeded, so idempotency and reconciliation logic concludes the named API existed and was removed. A teardown loop that drives deletion until it observes NotFoundException never sees completion here, a reconciler believes a resource it never created was present, and a typo'd restApiId is reported as a successful destructive call instead of being rejected.
Fix: the DeleteRestApi handler's existence check against the REST API state (including whatever retained/accepted-delete record keeps a removed id resolvable) — answer the modeled NotFoundException (404) whenever the account holds no live API under that id, rather than the 202 success code.
Traces: apigateway-stage-method-settings-duplicate-spelling#teardown#12.

=== Cause 3 of 4: CreateUsagePlan reports a freshly minted usage-plan id instead of the id of the usage plan the recorded service resolves the create to ===
AWS: Smithy models CreateUsagePlan as POST /usageplans with http success code 201, input { name (required), description, apiStages, throttle, quota, tags }, output UsagePlan { id, name, description, apiStages, throttle, quota, productCode, tags }; modeled errors BadRequestException(400), ConflictException(409), LimitExceededException(429), NotFoundException(404), TooManyRequestsException(429), UnauthorizedException(401). The model says nothing about usage-plan identity, so this is recorded behavior only: the fixture asserts this response's `id` BY REFERENCE to the usage-plan id already bound earlier in the same fixture (the harness prints the expectation as the capture token `{{usage_plan_id}}`, not as a literal id), and the recorded 201 reports THAT id — i.e. the create resolves to the usage plan the scenario already tracks rather than adding a second one under a new identity. Hypothesis (the recording establishes only the id equality, and the model's ConflictException is the only hint): AWS treats a usage plan already held under that name as the resource being named, so a repeated or retried create lands on it.
Emulator: the same create is answered 201 with a newly generated 10-character id, so `$.id` names a plan the client's scenario does not hold. The id string in this run is a per-run value and is NOT the requirement; the EQUALITY with the already-bound plan's id is.
Why: usage-plan creates are routinely retried (a timed-out call, a re-run of a provisioning step). Against the emulator each attempt yields a distinct plan id, so GetUsagePlans enumerates duplicate plans for one logical plan, every later call that keys off the id the client recorded first (UpdateUsagePlan, CreateUsagePlanKey, GetUsage, tag calls) addresses a plan that is not the one metering traffic, and quota/throttle state is split across plans with no signal in the response.
Fix: the CreateUsagePlan handler and the usage-plan state it writes — resolve the create against the usage plan the account already holds for that name and report its id, instead of unconditionally minting a new id and inserting a second record.
Traces: apigateway-tag-usageplan-bulk-tags-and-pagination#setup#1.

=== Cause 4 of 4: TestInvokeMethod always reports latency 0 — the invocation duration is never measured ===
AWS: Smithy models TestInvokeMethod as POST /restapis/{restApiId}/resources/{resourceId}/methods/{httpMethod}, success 200, output TestInvokeMethodResponse { status: Integer, body, headers, multiValueHeaders, log: String, latency: Long }. smithy_query query=doc shape=TestInvokeMethodResponse member=latency -> "The execution latency, in ms, of the test invoke request." The member is therefore the MEASURED duration of the test invocation in milliseconds, and the recorded response reports a non-zero measurement for a completed invoke. The particular number in any one recording is a per-run value and is NOT the requirement; the requirement is that the member carries the invocation's measured elapsed time (a positive number of milliseconds for an invoke that ran) rather than the shape's default.
Emulator: the same TestInvokeMethod is answered 200 with `latency: 0` — the Smithy default for the Long member — on an invoke that did run and returned a body, i.e. the handler never times the invocation.
Why: latency is the only timing TestInvokeMethod reports and it is what console/CLI users and CI gates read to judge whether a method's integration responds at all. A client that asserts latency > 0 to confirm the integration was actually exercised, that records the figure, or that compares it between configurations, reads a constant 0 here and concludes nothing was executed (or divides by zero computing a ratio) where AWS reports a measurement.
Fix: the TestInvokeMethod handler's response assembly — measure the elapsed wall time across the integration invocation it performs and report it in milliseconds in `latency`, instead of leaving the member at its default 0. (Sibling defect, separately owned: the same operation's `log` member shape is carried by open issue 20261121T033135Z-apigateway-3-net-new-wire-causes-getdeployments-empty.md, whose cause 2 names the log builder only and does not mention `latency` or this fixture step — the replay reports this latency cluster with owned_by=[].)
Traces: apigateway-resource-method-integration-full-lifecycle#task#23.
