# AppSync EvaluateMappingTemplate: the VTL evaluator cannot parse a #foreach range expression [a..b], so a range loop never renders and the per-evaluation processing limit is unreachable

> _Note: this issue was identified against the code base at commit `de014b3026fe0bf980e23e8d36c49dd531cd5e09`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
EvaluateMappingTemplate

## Description
One net-new root cause, in the VTL evaluator `crate::service::graphql_api::mapping_template` that the EvaluateMappingTemplate handler delegates to. Relationship to what is already filed, stated explicitly because the SYMPTOM has moved: the open issue 20261121T235951Z-appsync-evaluatemappingtemplate-a-vtl-parse-failure-is-a.md lists this same check and its cause 2 describes a range `#foreach` refused with HTTP 400 BadRequestException 'This is not an expression.' — that refusal is GONE (the handler now serves 200 and reports template faults through the output `error` member, as `services/service-com-amazonaws-appsync-awsdeepdishcontrolplaneservice/src/ops/evaluate_mapping_template.rs` lines 290-361 do), so the replay no longer matches that issue's key and it no longer describes the behaviour. The fixed issue 20261121T212257Z-appsync-evaluatemappingtemplate-vtl-evaluator-and-response-envelope-diverge.md claimed `#foreach` in its cause 4, but only for iteration over a LIST held in the context; a range expression is still unparseable. This is not a refusal — the call is served 200 — so it is reported as a live defect of the evaluator rather than as a reopened refusal.

Shared Smithy basis: Smithy (appsync) EvaluateMappingTemplate — POST /v1/dataplane-evaluatetemplate, HTTP success code 200; required input `template` (Template, @length 2..65536, @pattern ^[\s\S]*$) and `context` (Context, @length 2..28000, @pattern ^[\s\S]*$); output members `evaluationResult` (@length 0..65536), `error` (ErrorDetail{message}), `logs` (list<String>), `stash`, `outErrors`; modeled errors AccessDeniedException|403, BadRequestException|400, InternalFailureException|500. The operation's documentation states mapping templates are written in the Apache Velocity Template Language (VTL). Because `error` is an OUTPUT member of a 200 response, an evaluation failure is reported in the body.

Cause 1 of 1: a `#foreach` whose iterable is a literal range `[a..b]` fails VTL PARSING, so the loop body never runs and AppSync's per-evaluation processing ceiling can never be reported.
AWS: recorded behavior only (the Smithy model describes the operation, not the template language). A template that loops over a literal range and accumulates the loop counter — the general form `#set($n=0)#foreach($i in [1..N])#set($n=$velocityCount)#end$util.toJson($n)` — is EVALUATED and answered HTTP 200 with `evaluationResult` equal to the accumulated value (N when N is at or below the ceiling) and NO `error`. `$velocityCount` is bound inside the body and counts from 1. One iteration PAST AppSync's per-evaluation processing limit is reported through the output `error` member: HTTP 200, `error.message` exactly the fixed text `A processing limit has been exceeded` (this sentence has no variable parts), and no usable `evaluationResult`; a template back at the ceiling renders again, i.e. the limit is per-evaluation and carries no state across calls. N and the ceiling itself are service limits/request values, not part of the requirement's text.
Emulator: HTTP 200, no `evaluationResult`, and `error.message` is an Apache Velocity PARSE diagnostic for the AT-ceiling template: `org.apache.velocity.exception.ParseErrorException: Encountered "..1000])#set($n=$velocityCount)#" at line 1, column 28.` — i.e. the evaluator reads `[1..N]` as far as the `[1` and then cannot parse the `..` range operator, so the whole directive is rejected as unparseable. In that message the fixed text is the exception class name `org.apache.velocity.exception.ParseErrorException` plus `Encountered "…" at line …, column …`; the quoted token, the line and the column are values taken from the submitted template. Consequence: the loop body never executes, `$velocityCount` is never bound, and because the over-ceiling template fails the same way there is NO processing-limit behaviour at all — AWS's `A processing limit has been exceeded` is never produced for any input.
Why: a range `#foreach` is ordinary VTL and appears in AppSync's own mapping-template examples. A client linting or developing a correct template in the sandbox is told its template does not parse, with a parse diagnostic pointing at valid syntax, and so concludes its resolver template is malformed. The same evaluator backs a resolver's `requestMappingTemplate`/`responseMappingTemplate`, so any resolver using a range loop is equally unevaluable on the data plane. Separately, a client probing the processing limit — to build splitting or retry logic around large templates — can never observe AWS's limit report, because every range template fails earlier with a different message and a different cause.
Fix: the `#foreach` iterable parsing/evaluation of the VTL engine (`crate::service::graphql_api::mapping_template`, the one reader of this language the crate holds, which `src/ops/evaluate_mapping_template.rs` lines 94-97 name): accept a literal range expression `[a..b]` as an iterable, bind `$velocityCount`/`$foreach` inside the body, and enforce the per-evaluation iteration ceiling by surfacing it as the evaluator fault the handler already maps onto the output `error` member (the `Answered::Unevaluable` arm, lines 347-354) with AWS's fixed sentence `A processing limit has been exceeded` rather than a Velocity parse diagnostic.
Traces: appsync.evaluate-mapping-template-foreach-iteration-limit.

## Steps to Reproduce
Against the emulator, as a principal allowed appsync:EvaluateMappingTemplate, call POST /v1/dataplane-evaluatetemplate (aws appsync evaluate-mapping-template --template ... --context ...):
1. Submit a range-loop template at or below the per-evaluation ceiling, e.g. template `#set($n=0)#foreach($i in [1..1000])#set($n=$velocityCount)#end$util.toJson($n)` with context `{"arguments":{}}`. Expected: HTTP 200, no `error`, `evaluationResult` equal to the accumulated counter (1000 here). Observed: HTTP 200 with `error.message` = 'org.apache.velocity.exception.ParseErrorException: Encountered "..1000])#set($n=$velocityCount)#" at line 1, column 28.' and no `evaluationResult`.
2. Shrink the range to a trivially small loop (e.g. `[1..3]`) with the same context — it fails with the same ParseErrorException class and a column pointing at the `..`, confirming the failure is the range OPERATOR, not the iteration count.
3. Control: replace the iterable with a list taken from the context (e.g. a context carrying `{"arguments":{"xs":[1,2,3]}}` and `#foreach($i in $context.arguments.xs)`) — that evaluates, so only the literal-range iterable diverges.
4. Submit the same range template with ONE more iteration than the ceiling. Expected: HTTP 200 with `error.message` exactly 'A processing limit has been exceeded' and no usable `evaluationResult`. Observed: the identical parse diagnostic from step 1, so the limit report is never produced for any input.
5. Submit the at-ceiling template from step 1 again. Expected: it renders the accumulated counter again (the limit is per-evaluation). Observed: the same parse diagnostic.
