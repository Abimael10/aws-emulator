# GetBootstrapBrokers advertises one distinct broker host for a 2-broker provisioned cluster (now two identical host:port entries), so per-broker addressing and MSK open monitoring are unreachable

> _Note: this issue was identified against the code base at commit `9d1fbc0791b9f580b1541f328a603c71fb48ed53`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
GetBootstrapBrokers

## Description
ONE net-new root cause on the emulated kafka (MSK) surface. It is the only failing behavioral check under the `### kafka` heading in this run that the report marks neither ALREADY FILED nor OWNED by an open issue; every other kafka / cloudformation__kafka / kafka__lambda / kafka__logs__s3 failure in this sweep carries an owned_by and was skipped.

Cause 1 of 1: GetBootstrapBrokers publishes a BootstrapBrokerString whose entries all name the SAME host, so a cluster created with NumberOfBrokerNodes=2 advertises only 1 distinct broker endpoint.

AWS: Smithy (services/service-com-amazonaws-kafka-kafka/smithy-model/com-amazonaws-kafka-kafka.json) GetBootstrapBrokers = GET /v1/clusters/{ClusterArn}/bootstrap-brokers, success code 200; input ClusterArn (@httpLabel, required); output BootstrapBrokerString (jsonName bootstrapBrokerString, target __string) alongside the Tls / SaslScram / SaslIam / Public* / VpcConnectivity* / *Ipv6 siblings; errors BadRequestException 400, ConflictException 409, ForbiddenException 403, UnauthorizedException 401, InternalServerErrorException 500. The model types the member only as a string, so the string's internal structure is recorded behavior only: on real MSK the string is a comma-separated host:port list with ONE ENTRY PER BROKER NODE, each entry naming a DIFFERENT broker (the documented per-broker name form b-<n>.<cluster-name>.<id>.<n>.kafka.<region>.amazonaws.com, one per broker index), and all entries sharing the single port of that access method (9092 for the PLAINTEXT string). The invariant a client depends on is therefore: count of DISTINCT hosts == NumberOfBrokerNodes, one shared port, and every advertised host is an address the responder actually accepts on. Per-broker identity is what makes per-broker surfaces addressable at all — MSK open monitoring documents the JMX exporter on the fixed port 11001 and the node exporter on 11002 of EACH broker host.

Emulator: for a provisioned 2-broker cluster (kafka.t3.small, KafkaVersion 3.9.x, 2 client subnets, OpenMonitoring.Prometheus{JmxExporter.EnabledInBroker=true, NodeExporter.EnabledInBroker=false}) the PLAINTEXT BootstrapBrokerString has two entries that are IDENTICAL — same host and same port — parsing to 1 distinct host. No status or error code diverges: the response is a 200 whose BootstrapBrokerString content is wrong. The check reaches this only after the cluster reports ACTIVE, the string is published, the endpoint accepts TCP and the broker answers a hand-framed ApiVersions with error_code 0 advertising api keys 0/3/19/32 — the control plane and the listener are up; only the per-broker addressing of the bootstrap string is wrong. The literal host, the port value, the generated cluster/topic names, ARNs and VPC/subnet/security-group ids in the recording are per-run values of this environment and are NOT the requirement; the requirements are the distinct-host count, the per-broker host identity and the shared access-method port. Note the symptom has MOVED since it was last reported: the earlier observation was two entries on one host with two DIFFERENT ports ('127.0.0.1:37565,127.0.0.1:46483'), and today the two entries share one port ('127.0.0.1:36687,127.0.0.1:36687') — the per-access-method port is now right, the per-broker host is still missing.

Why: a client cannot reach broker N. Anything that iterates the bootstrap hosts and dials a fixed per-broker port — the 11001/11002 open-monitoring scrapers, dashboards, per-broker health checks — lands on the same single broker, so a cluster in which only one broker serves looks healthy and a per-broker outage is invisible. Code that derives broker identity from the bootstrap string (replica placement, partition-leader affinity, rack mapping) is wrong against the emulator, and the whole downstream of this check (JMX exporter serving Prometheus text per broker, the disabled node exporter refusing on each broker, and the UpdateMonitoring enable leg) is unverifiable.

Fix: the GetBootstrapBrokers handler in the kafka crate (services/service-com-amazonaws-kafka-kafka) and the broker-endpoint allocation it reads in that crate's state layer (the broker-plane addressing/authority component that renders each bootstrapBrokerString* member). A provisioned cluster must materialise one distinctly named, dialable broker endpoint per broker node, with the access method's single port shared across them, and every bootstrap string member must list those per-broker hosts rather than one host repeated N times.

Context a fixer should read first, not a duplicate: resolved issue 20261125T225220Z-kafka-msk-control-plane-answers-diverge-createclusterv2-s-both.md filed this same check and closed as fixed with its Cause 2 recorded BLOCKED on the read-only core (a service cannot bind a second loopback address at an already-assigned port, cannot request the fixed ports 11001/11002, and the core drops the accepted connection's local address), so the check still fails on the identical assertion. A resolved issue does not cover a live failure, so it is re-filed here with the current observation. Open issue 20261121T133835Z-kafka-msk-getbootstrapbrokers-advertises-an-unserved-host-and-createcluster.md (Cause 1, verdict host_not_own) and the resolved 20261121T065645Z / 20261121T025935Z port-allocation issues are the neighbouring causes in this family; none of them carries this check's replay key, and the host-ownership constraint from the first is exactly why the per-broker names were withdrawn — the fix must satisfy BOTH: N distinct hosts that the emulator really answers on.
