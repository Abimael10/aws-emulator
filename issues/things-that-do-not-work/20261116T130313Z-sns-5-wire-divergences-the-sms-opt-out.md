=== Cause 1 of 5: CheckIfPhoneNumberIsOptedOut refuses a phone number AWS reports on — 400 InvalidParameter instead of 200 isOptedOut=false ===
Fixture/step: sns-sms-account-configuration-and-opt-out-check#task#7.
AWS: Smithy (com.amazonaws.sns#CheckIfPhoneNumberIsOptedOut) — the input member is `phoneNumber` targeting `com.amazonaws.sns#PhoneNumber`, an UNCONSTRAINED @sensitive string (no @pattern, no @length); contrast `PhoneNumberString`, the member of the sandbox/publish operations, which the model DOES constrain (@length 0..20, @pattern ^(\+[0-9]{8,}|[0-9]{0,9})$). The output member `isOptedOut` is a boolean defaulting to false, documented "false – The phone number is opted in". The operation's only client refusal for a bad member is InvalidParameterException (awsQueryError `InvalidParameter`, HTTP 400). Recorded behavior: this step's number is answered HTTP 200 with CheckIfPhoneNumberIsOptedOutResult.isOptedOut = 'false' — AWS treats a number it holds no opt-out record for as opted in and does NOT refuse the read. The absence of an opt-out record is not a formatting verdict.
Emulator: the call answers HTTP 400 with no CheckIfPhoneNumberIsOptedOutResponse body at all. services/.../src/ops/check_if_phone_number_is_opted_out.rs calls `state::phone_number_refusal(&input.phone_number)` before the store is consulted; that rule is `state::is_e164` -> `destination_number::destination_number_fault` (state.rs MIN_E164_DIGITS=8 / MAX_E164_DIGITS=15, leading '+', digits only, no leading zero), lifted from the CONSTRAINED `PhoneNumberString` member of a different operation. Any value outside that narrow rule — including national/separator forms AWS answers for — becomes a 400.
Why: the opt-out check is the pre-flight a sender runs before an SMS send. A client that asks AWS "may I message this number?" is told false (send it); against the emulator it gets a 400 it has no reason to expect and must treat as fatal, so the whole SMS path is unusable for every number the narrower rule rejects.
Fix: the CheckIfPhoneNumberIsOptedOut handler's argument validation (check_if_phone_number_is_opted_out.rs, and the shared `state::phone_number_refusal` rule it uses) — do not hold this operation's unconstrained `phoneNumber` to the constraint the model places on a different, constrained member. Keep refusing a value that is not a phone number at all (the behavioral check sns.check-phone-number-opted-out-invalid-fails requires 400 InvalidParameter `Invalid parameter: PhoneNumber Reason: input incorrectly formatted` for the literal `not-a-phone`), and answer 200 isOptedOut=false for any plausible number with no stored opt-out. Both boundaries hold at once.

=== Cause 3 of 5: ConfirmSubscription's refusal of a token that confirms nothing is re-worded 'Invalid parameter: Token' instead of AWS's 'Invalid token' ===
Fixture/step: sns-subscription-pending-and-error-paths#task#11.
AWS: Smithy: ConfirmSubscription takes @required `Token` and declares InvalidParameterException (awsQueryError `InvalidParameter`, HTTP 400) and NotFoundException (404). Recorded behavior: confirming with a token of valid FORM that is not a confirmation token of the topic is refused HTTP 400 / `InvalidParameter` with the message exactly 'Invalid token' — wholly fixed text, no `<member> Reason:` frame and no part taken from the request (the token is opaque and is not echoed). The refusal creates no subscription.
Emulator: status 400 and code `InvalidParameter` are right, but the message is 'Invalid parameter: Token'. services/.../src/ops/confirm_subscription.rs returns `state::INVALID_CONFIRMATION_TOKEN_REFUSAL` for every token that matches no pending confirmation, and state.rs now defines that constant as "Invalid parameter: Token" — one sentence for both conditions.
Why: 'Invalid token' is how SNS distinguishes "this token confirms nothing" (an expired or already-used confirmation link) from "your request member is malformed" (a client bug); the message is the only machine-readable carrier of that distinction, so clients, matchers and confirmation-endpoint log pipelines keyed on AWS's text misclassify the refusal.
Fix: the ConfirmSubscription handler's token validation (confirm_subscription.rs + the state constant it uses) — judge the token's FORM first and refuse that class with 'Invalid parameter: Token' (what the behavioral check sns.op-confirm-subscription-invalid-token-rejected requires for a 64-character run of one letter), and keep 'Invalid token' for a well-formed token that matches no pending confirmation of the named topic. Two conditions, two sentences; neither creates a subscription.

=== Cause 4 of 5: the topic's SubscriptionsDeleted counter is taken up inside the window a client's counter-convergence loop covers, where AWS still reports 0 ===
Fixture/step: sns-cnt-topic-subscription-counters-settle#task#7.
AWS: Smithy: GetTopicAttributesResponse$Attributes documents the three computed counters — "SubscriptionsConfirmed – The number of confirmed subscriptions for the topic", "SubscriptionsPending – The number of subscriptions pending confirmation", "SubscriptionsDeleted – The number of deleted subscriptions for the topic". Recorded behavior: Unsubscribe removes the subscription synchronously — it stops being listed and the confirmed/pending counts follow immediately — while the per-topic DELETED count is taken up on a cycle of the service's own. In this recording, a client that unsubscribed and then polled GetTopicAttributes until the confirmed and pending counts had settled read SubscriptionsDeleted = '0' on every read of that loop, this step included (the attribute map's entry[7] for an unencrypted topic, the SubscriptionsDeleted entry under the reported order Policy, Owner, SubscriptionsPending, TopicArn, EffectiveDeliveryPolicy, SubscriptionsConfirmed, DisplayName, SubscriptionsDeleted).
Emulator: that entry reads '1'. state.rs sets `SUBSCRIPTION_DELETION_SETTLES_AFTER = Duration::from_secs(3)` and `TopicRecord::count_deleted_subscription` queues the deletion at `now + 3s`, so `reported_subscriptions_deleted()` folds it into the count a few seconds after the Unsubscribe — i.e. while the same convergence loop is still running — and the step that AWS answers '0' is answered '1'.
Why: a client that reads the three counters together after an Unsubscribe sees a topic state AWS never serves at that point in the sequence; any drift check, snapshot comparison or assertion that the deleted count has NOT yet moved while confirmed/pending settle fails, and the counter's timing becomes an emulator-specific invention rather than the lagging counter AWS exposes.
Fix: the SNS topic-state counter model (state.rs `SUBSCRIPTION_DELETION_SETTLES_AFTER`, `TopicRecord::count_deleted_subscription` / `reported_subscriptions_deleted`, and the Unsubscribe path that calls them) — the deleted count must still lag the Unsubscribe long enough that a client polling the confirmed/pending counters to settlement keeps reading the pre-Unsubscribe value, while remaining observable to a client that keeps polling (the resolved behavioral issue 20261113T050453Z-sns-2-net-new-causes-subscribe-s-malformed.md, Cause 2, shows a 15-minute delay is too long: its check observes SubscriptionsDeleted >= 1 within a 60s budget at 2s intervals). Both constraints are recorded behavior and must hold together; 3 seconds satisfies only the second.

=== Cause 5 of 5: ListSubscriptions omits NextToken on a page AWS returns a continuation token with ===
Fixture/step: sns-cnt-list-subscriptions-token-refused-then-listed#task#4.
AWS: Smithy: ListSubscriptions is @paginated (inputToken/outputToken NextToken, items Subscriptions) and ListSubscriptionsResponse$NextToken is documented "Token to pass along to the next ListSubscriptions request. This element is returned if there are more subscriptions to retrieve." Recorded behavior: on this step the response carries BOTH the account's subscription list — which the emulator reproduces exactly, so the page is not a full 100-item page — AND a non-empty NextToken (an opaque base64 string; its bytes are a per-recording value, never a requirement). Hypothesis: SNS mints a continuation token for this account-wide listing whether or not the page it just served exhausted the listing, so the caller's loop takes one more (possibly empty) page; what is recorded, and what a client can rely on, is that the member is PRESENT and that passing it back is accepted (the earlier steps of this fixture show a token the service never minted being refused 400 InvalidParameter, and the emulator already matches those).
Emulator: the member is absent (`NextToken: None`). services/.../src/ops/list_subscriptions.rs returns whatever `state::paginate(all, input.next_token, state::PAGE_SIZE)` hands back, which is `None` whenever the page it produced is the last one, so a short listing never carries a token.
Why: a client paginating ListSubscriptions branches on the presence of NextToken; against AWS it takes a further request and against the emulator it stops, so the two disagree about how many calls the listing costs and about whether an opaque token round-trips at all — and any test that asserts the paginator issued a follow-up call, or that feeds the served token back, has nothing to feed.
Fix: the ListSubscriptions handler's pagination (list_subscriptions.rs together with `state::paginate` / `state::PAGE_SIZE`) — serve an opaque, service-minted NextToken on this listing's last page as the recording does, and accept it on the following request (answering the remaining, possibly empty, page) while keeping the existing refusal of a token this service never minted.
Traces: sns-cnt-list-subscriptions-token-refused-then-listed#task#4.
