## Description
This issue has 1 cause; it must be closed before submitting.

Related open issues, named because a reader will find them and neither claimed this replay key: 20261103T175414Z-pipes-updatepipe-re-installing-filtercriteria-on-a-running.md covers UpdatePipe REPLACING FilterCriteria on a live pipe (a different member and a different data-plane stage), and 20261111T093805Z-pipes-4-net-new-causes-pipe-failure-statereason.md covers StateReason text and CloudFormation classification. Neither covers the DesiredState run/stop toggle driven through UpdatePipe, and the replay in this run reported this check as an unowned failure.

Cause 1 of 1: UpdatePipe used as the run/stop control (DesiredState=STOPPED, then DesiredState=RUNNING) never produces the two observable data-plane effects a client depends on — a message sent while the pipe is settled STOPPED must be WITHHELD (absent from the target, still counted visible on the source) and must then be DELIVERED after the pipe is put back to RUNNING. The check that exercises exactly that sequence never reaches either verdict. Failing check: pipes.update-pipe-desired-state-halts-then-resumes-delivery.

AWS: Smithy (services/service-com-amazonaws-pipes-pipes/smithy-model/com-amazonaws-pipes-pipes.json) — com.amazonaws.pipes#UpdatePipe, PUT /v1/pipes/{Name}, success 200, idempotent; input Name (PipeName, httpLabel, required, @length 1..64, @pattern ^[\.\-_A-Za-z0-9]+$), RoleArn (required) and DesiredState -> RequestedPipeState (RUNNING | STOPPED), documented as "The state the pipe should be in"; modeled errors ConflictException 409, NotFoundException 404, ValidationException 400, ThrottlingException 429, InternalException 500. DescribePipe (GET /v1/pipes/{Name}, 200) reports DesiredState (RequestedPipeStateDescribeResponse) and CurrentState (PipeState: CREATING/STARTING/RUNNING/STOPPING/STOPPED/UPDATING/...), which is how a client observes the toggle settling; UpdatePipe's own documentation states EventBridge updates only the fields specified, so an UpdatePipe carrying DesiredState alone (plus the required RoleArn) moves only the run state. The data-plane consequence is recorded behavior only (the model covers the control plane): a pipe that rests in STOPPED consumes nothing from its source — a record sent while it is stopped stays on the source, visible and counted (SQS ApproximateNumberOfMessages includes it) and never reaches the target — and the next transition back to RUNNING resumes consumption of the whole backlog that accumulated while it was stopped, so that withheld record is then delivered to the target. UpdatePipe is the toggle IaC tools use, so this must hold for DesiredState changes and not only for StopPipe/StartPipe.

Emulator: the check never completes. Replay reports `[mismatch] pipes.update-pipe-desired-state-halts-then-resumes-delivery / Error: Check timed out after 60.0s`, with no frame captured, so none of the three decisive assertions is ever evaluated: (a) a message sent after UpdatePipe(DesiredState=STOPPED) settled is absent from the target over a quiet drain window, (b) the source still reports ApproximateNumberOfMessages == 1 for that withheld message, and (c) UpdatePipe(DesiredState=RUNNING) delivers exactly that withheld body to the target. The control-plane half is implemented — services/service-com-amazonaws-pipes-pipes/src/ops/update_pipe.rs writes `pipe.desired_state`, calls `begin_transition(UPDATING, &settled)` (settle span 500 ms, crate::state::STATE_SETTLE_DELAY) and then calls `crate::state::data_plane::drive_pipe(...)` only when `settled == requested_state::RUNNING`, under the comment "an update that stopped it needs no call, because the poller ends itself as soon as the pipe is no longer RUNNING" — so the halt depends entirely on the running poller re-reading the record and the resume depends on `claim_poller` having been released by the ending poller before the resuming UpdatePipe calls `drive_pipe` (services/service-com-amazonaws-pipes-pipes/src/state/data_plane.rs, `drive_pipe` returns silently when `claim_poller` answers false). Hypothesis (the replay reached no stage, so this is NOT confirmed by it): either the stopped pipe's in-flight poll still consumes the record sent after the stop settled (so it never stays visible on the source), or the resuming UpdatePipe finds the previous poller's claim still held and starts no poller, so the withheld record is never delivered and the check's probe loop waits out its budget.

Why: a client that toggles a pipe through UpdatePipe uses STOPPED as a hard gate — maintenance windows, cost control, draining a bad consumer — and then relies on the backlog being delivered when it sets RUNNING again. If a stopped pipe still consumes, records are delivered during a window the client believes is closed and are deleted from the source, which is unrecoverable data movement; if the resume never re-attaches a poller, the pipe reads RUNNING in DescribePipe while its source silently accumulates for ever. Both are indistinguishable from a healthy pipe from the control plane alone, because DesiredState/CurrentState read correctly in each case.

Fix: the UpdatePipe handler's hand-off to the data plane and the poller's run gate / claim lifecycle — services/service-com-amazonaws-pipes-pipes/src/ops/update_pipe.rs (the branch that calls `drive_pipe` only for a settled RUNNING state, and the UPDATING->STOPPED/RUNNING settle it leaves behind) together with services/service-com-amazonaws-pipes-pipes/src/state/data_plane.rs (the per-read run gate, so a poll in flight takes nothing more from the source once the record says the pipe no longer runs, and the claim release, so an UpdatePipe that makes the pipe RUNNING again always ends up with a live poller).
