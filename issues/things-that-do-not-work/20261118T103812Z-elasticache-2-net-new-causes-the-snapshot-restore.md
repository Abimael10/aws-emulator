# elasticache: 2 net-new causes — the snapshot→restore round trip and the user-group access-revocation flow never converge, so both checks are killed at their budget with no assertion

> _Note: this issue was identified against the code base at commit `814109981af2f415bf041bb2099ef5ad4140d55d`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
CreateSnapshot

## Description
Two net-new root causes, grounded in the only two elasticache failing checks in this replay that the report binds to no open issue and does not mark ALREADY FILED. Both end with exactly `Error: Check timed out after 60.0s` and no failing assertion, i.e. the emulator answered 200 at every control-plane step while never reaching the state (or the data plane) the flow waits on, so the client burns its whole wall-clock budget. Related open issues report the same family but do NOT cover these two checks: 20261111T005655Z-elasticache-data-plane-still-unreachable-and-multi-wait.md (unreachable cache endpoint + multi-wait flows), 20261108T152921Z-elasticache-in-vpc-data-plane-unverifiable-the-emulator.md (no _ssl module / no host network for a VPC-attached Lambda) and 20261111T233000Z-elasticache-single-node-redis-cache-cluster-never-completes.md (the single-node SET/GET round trip). Neither names these check ids as owned, so they are filed here so they are not closed unrun.

Cause 1 of 2: the full create → write → snapshot → delete → restore round trip of a Redis cache cluster never completes, so data written to a cluster can never be shown to survive a snapshot restore. Failing check: elasticache.e2e-cluster-snapshot-restore-data-persists.
AWS: Smithy (services/service-com-amazonaws-elasticache-amazonelasticachev9/smithy-model/com-amazonaws-elasticache-amazonelasticachev9.json): CreateCacheCluster returns CacheCluster$CacheClusterStatus and accepts SnapshotName to seed a new cluster from an existing snapshot; CreateSnapshot returns Snapshot, whose SnapshotStatus is documented "Valid values: creating | available | restoring | copying | deleting"; DescribeSnapshots(SnapshotName=...) returns that snapshot; CacheNode$Endpoint is "The hostname for connecting to this cache node", Endpoint$Address "The DNS hostname of the cache node", Endpoint$Port "The port number that the cache engine is listening on"; DeleteCacheCluster removes the cluster so DescribeCacheClusters answers CacheClusterNotFound (404, awsQueryError code CacheClusterNotFound). Recorded behavior: each stage settles on the first read issued after its transition is due — the source cluster reaches CacheClusterStatus 'available', the published CacheNodes[0].Endpoint accepts TCP from inside the cluster's own VPC and speaks RESP (SET answers `+OK`), the snapshot reaches SnapshotStatus 'available', the deleted cluster disappears, and a cluster created with SnapshotName=<that snapshot> reaches 'available' and serves the previously written key, GET answering the bulk string `$<value>`. The id, key and value are per-run values; the requirement is that whatever Address/Port the control plane publishes is one the emulator serves RESP on, that each status poll reads back the settled status, and that the restored cluster's keyspace contains what the snapshot captured.
Emulator: the check is killed at the per-check budget (`Error: Check timed out after 60.0s`) with no assertion fired — so no `available` snapshot, no post-delete CacheClusterNotFound, and no restored-cluster GET reply was ever observed. Its own verdicts (`expected snapshot <name> to be available, got <status>`, `restored cluster data mismatch: <read_back> != <value>`, and `condition not met within 900s; last value=<...>`) were never reached.
Why: snapshot-and-restore is the ElastiCache durability story. A client that snapshots a cache, tears it down and restores from the snapshot hangs instead of either succeeding or failing diagnosably, and can never verify its backups; SDK waiters and CI pipelines block forever because every control-plane call keeps returning 200 while the state never converges.
Fix: the elasticache crate — (a) the status-settling path of its state, so a cluster/snapshot whose transition is already due reads back settled to the FIRST Describe that observes it; (b) the snapshot handlers' state (CreateSnapshot/DescribeSnapshots/DeleteCacheCluster) so a snapshot reaches 'available' and CreateCacheCluster(SnapshotName=...) seeds the new cluster's keyspace from it; and (c) the ElastiCache data plane, so the address/port published in CacheNodes[].Endpoint is served with RESP from inside the cluster's VPC.
Traces: elasticache.e2e-cluster-snapshot-restore-data-persists.

Cause 2 of 2: removing a user from a user group attached to a replication group is never observable — neither the control-plane convergence nor the engine-side revocation of that user's AUTH ever completes. Failing check: elasticache.e2e-user-group-access-revocation-flow.
AWS: Smithy (same model): CreateUserGroup/ModifyUserGroup return UserGroup{UserGroupId, Status, UserIds, PendingChanges, ReplicationGroups}; ModifyUserGroup takes UserIdsToAdd/UserIdsToRemove (each @length min 1) and is modeled with InvalidUserGroupStateFault (400, code InvalidUserGroupState) and UserNotFoundFault (404, code UserNotFound); ModifyReplicationGroup takes UserGroupIdsToAdd/UserGroupIdsToRemove/RemoveUserGroups with ApplyImmediately and returns ReplicationGroup, modeled with InvalidUserGroupStateFault and UserGroupNotFoundFault (404, code UserGroupNotFound); ReplicationGroup carries Status and NodeGroups[].PrimaryEndpoint. Recorded behavior: after ModifyUserGroup(UserIdsToRemove=[user]) the group goes 'modifying' and then 'active' with the user absent from UserIds, the attached replication group returns to 'available', and the running engine then refuses the identical RESP `AUTH <user> <password>` that succeeded moments earlier (an error reply, not `+OK`); adding the user back with ModifyUserGroup(UserIdsToAdd=[user]) restores 'active' with the user present and the identical AUTH succeeds again. The user/group/replication-group ids and the password are per-run values; the requirement is that the group and replication group settle to 'active'/'available' on the first read after the transition is due, and that RBAC membership is enforced by whatever serves NodeGroups[0].PrimaryEndpoint.
Emulator: the check is killed at the per-check budget (`Error: Check timed out after 60.0s`) with no assertion fired — the positive-control AUTH, the post-removal AUTH refusal and the post-restore AUTH success were all never observed, and neither was the group/replication-group convergence (`condition not met within 600s; last value=<...>`, `expected <group> attached to <rg>, got UserGroupIds=<...>`, `expected <user> restored to <group>, got UserIds=<...>`).
Why: a client that revokes access by removing a user from a user group has no way to see the revocation take effect, and no way to see it reversed. Credentials a client believes it revoked may still be usable against the cache, which is a security-relevant divergence — and because every control-plane call answers 200 while nothing settles, the caller cannot tell 'still applying' from 'never applied'.
Fix: the elasticache crate — the ModifyUserGroup / ModifyReplicationGroup handlers and the user-group state they mutate (settle Status 'modifying'→'active' and ReplicationGroup Status to 'available' so the first Describe after the transition is due reads the settled value, and reflect UserGroupIds on the replication group), plus the ElastiCache data plane so the endpoint published in NodeGroups[].PrimaryEndpoint is reachable in-VPC and enforces user-group membership on AUTH.
Traces: elasticache.e2e-user-group-access-revocation-flow.
