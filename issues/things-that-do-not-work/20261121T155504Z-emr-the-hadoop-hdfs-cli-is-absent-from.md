# emr: the Hadoop/HDFS CLI is absent from the step environment — every command-runner.jar step that invokes `hadoop fs` or `hdfs getconf` settles FAILED with exit status 127 instead of COMPLETED

> _Note: this issue was identified against the code base at commit `2c5dcf2b9a89c9dd56a9400ba366d007bab5eb92`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
AddJobFlowSteps

## Description
Cause 1 of 1: a `command-runner.jar` step whose script uses the cluster's Hadoop command-line tools (`hadoop fs ...`, `hdfs getconf ...`) is executed in an environment where those executables do not exist, so the shell exits 127 ("command not found") and the step settles FAILED. This is net-new relative to the two open step-execution issues: it is NOT "the step never runs its command" (the step does run, and the emulator even reports the shell's 127 exit status back through FailureDetails), and it is NOT the empty-`fs.s3.impl` configuration gap. Related open issues that do not cover it: 20261118T213929Z-emr-cluster-steps-never-execute-their-command-every.md (step command never executed at all) and 20261119T185618Z-emr-5-net-new-root-causes-outside-the.md (whose Cause 1 is the missing `hadoop`/`spark-submit` binaries observed as the probe's own ABSENT sentinel, and whose Cause 2 is `fs.s3.impl` resolving to the empty string — in both of those the step itself still COMPLETED, so the write/read data plane was reachable; here the step dies before any of that can be observed, because the same script is run under `set -eu` and the first `hadoop`/`hdfs` invocation aborts it).

AWS: Smithy (com.amazonaws.emr#ElasticMapReduce): a step is a HadoopJarStepConfig{Jar (required), MainClass, Args, Properties}; `Jar=command-runner.jar` with `Args=["bash","-c",<script>]` runs that script in the primary node's shell. StepStatus{State: StepState = PENDING|CANCEL_PENDING|RUNNING|COMPLETED|CANCELLED|FAILED|INTERRUPTED, StateChangeReason, FailureDetails{Reason, Message, LogFile}, Timeline}. On an `emr-6.15.0` cluster launched with `Applications=[{Name: Hadoop}]`, the Hadoop distribution is installed on the node and `hadoop` and `hdfs` are on the PATH of the step's shell, so a script that does `hdfs getconf -confKey fs.s3.impl`, `hadoop fs -mkdir -p`, `hadoop fs -put`, `hadoop fs -cat`, `hadoop fs -du -s`, `hadoop fs -stat` or `hadoop fs -rm` exits 0 and the step reaches State=COMPLETED with no FailureDetails. Recorded behavior: all three checks assert the write/mutate step reaches COMPLETED, i.e. on AWS none of these Hadoop invocations fails.

Emulator: the step is accepted, runs, and settles State=FAILED. StateChangeReason.Message is "The command the step submitted exited with a non-zero status." and FailureDetails is {Reason: "The command the step submitted exited with a non-zero status.", Message: "The command the step submitted exited with status 127.", LogFile: "s3://<log-bucket>/logs/<cluster-id>/steps/<step-id>/stderr.gz"}. Status 127 is the POSIX shell's "command not found", and it is reported for the first Hadoop-CLI line of the script under `set -eu`; the same scripts' `aws s3 cp` legs and plain shell builtins work elsewhere in this suite, so the shell and its S3 client exist and only the Hadoop/HDFS client binaries are missing. (The fixed text here is the two sentences above plus the "...exited with status <N>." template; <N> is the shell's exit status, and the cluster id, step id and log bucket in LogFile are per-run values, not part of the requirement.)

Why: a client cannot use HDFS or EMRFS from a step at all. Every EMR data-plane idiom built on the Hadoop CLI — staging a payload into HDFS so a later step on the same cluster reads it, writing through EMRFS to s3:// so the object is byte-identical over the S3 API, deleting an EMRFS path and observing that a subsequent read is refused, reading a replication factor or a Hadoop config key — is impossible: the step is reported FAILED and nothing it was supposed to write exists. Worse, the failure is indistinguishable from the client's own script being wrong: DescribeStep says the submitted command exited 127, so an operator concludes their job's command is broken rather than that the cluster has no Hadoop installation, and ActionOnFailure=TERMINATE_*/CANCEL_AND_WAIT chains fire off a defect that is not in the request.

Fix: the cluster-node / step execution environment in the EMR crate (the step runner's node image and PATH, which must provide the `hadoop` and `hdfs` clients — and an HDFS that lives for the cluster's lifetime, with the core/DataNode placement RunJobFlow asked for — for every release whose `Applications` include Hadoop), not the DescribeStep/ListSteps serializers: the status shape and the FailureDetails wiring are already correct, which is exactly how the 127 is visible.

Traces: emr.emrfs-write-through-hadoop-fs-is-read-by-the-next-step (EMRFS write step, exit 127), emr.scaling-emrfs-read-of-a-deleted-object-is-rejected-and-writes-no-output (EMRFS mutate step, exit 127), emr.hdfs-write-survives-the-step-boundary (HDFS write step, non-zero exit).
