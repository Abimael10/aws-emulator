# SearchListings result pages announce unfetchable logo and review addresses and serve a different page-1 row

> _Note: this issue was identified against the code base at commit `f76eca197ef04c4659e4143c4eabad332d65bf41`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Description
This issue bundles 4 causes, all in marketplace-discovery, all on SearchListings, all in the projection a search page is built from (ComAmazonawsMarketplacediscoveryAwsmarketplacediscoveryState::search_matches -> listing_summary, src/state.rs). Each cause is ONE replay cluster with its own fixture/step binding and EACH MUST BE RE-REPLAYED before this issue is closed: Cause 1 = marketplace-discovery-search-facets-refine-search#task#3, Cause 2 = marketplace-discovery-search-listings-and-drill-into-listing#task#1, Cause 3 = marketplace-discovery-search-listings-pagination#task#1 (the representative bound in Issue-Trace/Issue-Step, and the only cause with a CONTENT claim), Cause 4 = marketplace-discovery-search-listings-pagination#task#2. In all four the HTTP status is right (expected 200, got 200) and no error is involved, so every divergence is in the response body.

The shared fault in causes 1, 2, 3b and 4 is that the two FETCHABLE members of the ListingSummary projection - logoThumbnailUrl and reviewSummary.reviewSourceSummaries[].sourceUrl - are published on a scheme+authority that is NOT the authority the answering request reached this emulator on, so every address a search page hands a client addresses a port this process does not serve; the replay classifies each such member resource_not_identified (the published address identifies no resource). Cause 3 carries an ADDITIONAL, independent defect: the first page of a paginated search returns a DIFFERENT listing record at index 0 than the recording returns for the same query.

NOT CLAIMED anywhere in this issue, because they are per-environment or per-run values: the recorded marketplace media-CDN host and its hash path, the recorded prodview/listing/review-list identifiers, the emulator's own generated media ids, and $.nextToken. $.nextToken appears in the diverging-key set of all four clusters, but its recorded values are '<shaped-not-asserted>', 'opaque-continuation-token-placeholder-000' and, in one recording, a long AWS continuation blob - i.e. continuation-token BYTES, a per-run opaque value - and the token the emulator serves is opaque and satisfies NextToken @length(0..8192) @pattern ^[a-zA-Z0-9+/=]+$, so its literal bytes are not a requirement.

=== Cause 1 of 4: a facet-refined SearchListings page publishes ten logo addresses and four review addresses on an authority the request did not reach ===
AWS: Smithy (services/service-com-amazonaws-marketplacediscovery-awsmarketplacediscovery/smithy-model/com-amazonaws-marketplacediscovery-awsmarketplacediscovery.json) SearchListings POST /2026-02-05/searchListings, success http 200, @readonly, @paginated {inputToken nextToken, outputToken nextToken, pageSize maxResults, items listingSummaries}; output {totalResults @required, listingSummaries @required, nextToken @length(0..8192) @pattern ^[a-zA-Z0-9+/=]+$}. ListingSummary$logoThumbnailUrl targets URL, @required, @length(1..2048), @pattern ^https?://.*$, documented 'The URL of the logo thumbnail image for the listing'; ReviewSourceSummary$sourceUrl targets URL, optional, same constraints, documented 'The URL where the reviews can be accessed at the source'. Both are addresses a client FETCHES, not text it renders, so the requirement is that the published address dereferences to that listing's logo image resp. that listing's reviews page. The model fixes no host and AWS serves these off the marketplace's own media and reviews hosts, so for the host itself this is recorded behavior only: the recording shows one distinct media-CDN path per listing and a per-listing reviews deep link. The emulator cannot be on those hosts, and its own design states the rule it must follow instead - src/state.rs module header lines 20-24: the addresses a record publishes for a client to FETCH are 'each announced on the address this process answers requests at (announced_page_base) and served by crate::service'.
Emulator: 200 with the right ten summaries, but every listingSummaries[i].logoThumbnailUrl has the form https://<authority>/_aws/marketplace-discovery-listing-media/<mediaId>/logo.png where <authority> is NOT the authority the replayed request reached the emulator on, and the four summaries whose review record keeps a reviews page publish reviewSummary.reviewSourceSummaries[0].sourceUrl the same way, on the same drifting authority. One emulator served the whole replay and its data listener is the one that accepted every request, yet the announced authority is a different loopback port - and a DIFFERENT wrong port in each cluster of this replay, so the drift is per response, not one static misconfiguration.
Why: a client rendering a result page dereferences logoThumbnailUrl for every tile and turns sourceUrl into the 'read the reviews' link. Against AWS both resolve; against the emulator both address an authority it is not serving, so every tile image and every reviews link fails with a connection error that reads as a client or network fault rather than as emulator infidelity - even though the emulator DOES serve both resources at its real front door (src/state/listing_logo.rs logo_route/listing_logo_image, src/state/listing_reviews.rs reviews_page_route/listing_reviews_page). The round trip is unreachable purely because of what the API announced.
Fix: the announced-address resolution the SearchListings summary projection uses - state::saas_fulfillment::announced_page_base (src/state/saas_fulfillment.rs, shared by all three published planes) and the authority ordering it consults in service_common::data_plane_addressing (reached_emulator_endpoint_of_parts -> served_endpoint_authority -> url_authority, scheme hard-coded https) - must yield the scheme and authority the answering request actually arrived on, which src/state.rs listing_summary() then stamps into logoThumbnailUrl and into sourceUrl. Not the handler's serializer and not the seeded catalog: the plane path, the media id and the reviews-list id are already correct.
Traces: marketplace-discovery-search-facets-refine-search#task#3 (SearchListings, expected 200 / got 200, verdict mismatch; 15 diverging keys - logoThumbnailUrl on listingSummaries[0..9], reviewSummary.reviewSourceSummaries[0].sourceUrl on listingSummaries[1], [4], [6], [8], plus $.nextToken, which is not claimed).

=== Cause 3 of 4: the first page of a paginated SearchListings returns a different listing record at index 0 than the query's recorded page, and publishes its logo address on an authority the request did not reach ===
AWS: same operation and members as cause 1. The model does not fix search CONTENT, so for the page's composition this is recorded behavior only: for a given searchText/filters/sortBy/sortOrder/maxResults, page 1 of the match set begins with the listing the ranking puts first, and each listingSummaries[i] is the stored record of that listing - its own listingId, listingName, publisher, shortDescription, catalog, categories, badges, fulfillmentOptionSummaries, pricingModels, pricingUnits, reviewSummary and associatedEntities, all @required members of ListingSummary. The sibling clusters of causes 1, 2 and 4 - where ONLY the announced authority drifts - report member-level keys and never the containing element, so the whole-element report here is a divergence beyond the announced URL: the record this page puts at index 0 is not the record the recording returns for that query. Hypothesis (neither the model nor the recording states the mechanism): the emulator answers out of its own seeded catalog (src/state.rs module header lines 5-9: 'the emulator therefore owns a seeded catalog here, built once on Default'; the breadth seed rows around lines 4030-4339 are synthetic rows such as 'Delta Forms Reader' and 'Equinox Retail Planner'), and search_matches/matches_every_search_filter plus the shared page cursor (page_cursor: encode_page_token/decode_page_token/page) order or compose the match set so a different row lands at index 0 of page 1 - note the CONTINUATION page of the same fixture (cause 4) carries the recorded record correctly, so the defect is in what page 1 selects, not in the record projection as such.
3b, the same announced-authority defect as cause 1 on this page: $.listingSummaries[0].logoThumbnailUrl is published under /_aws/marketplace-discovery-listing-media/<mediaId>/logo.png on an authority other than the one the request was accepted on, flagged resource_not_identified.
Why: a client that searches and then pages gets a first page whose leading result is a listing other than the one the query ranks first, with status 200 asserting the search succeeded. Everything downstream is wrong without any signal: the listingId it drills into, the product it then fetches, the offer it prices, and any 'top result' it shows a buyer. A paginating client is also the one most likely to persist the announced logo address across pages, so an address already unreachable when handed out stays unreachable for the whole walk.
Fix: for the content defect, the match-set composition and ordering SearchListings pages over in the marketplace-discovery crate's state (src/state.rs search_matches/matches_every_search_filter and the shared page_cursor paging) must put the query's ranked records on page 1 in the recorded order, and the seeded catalog must contain the records the corpus's catalog publishes for the searched text; for 3b, the same announced-address resolution as cause 1.
Traces: marketplace-discovery-search-listings-pagination#task#1 (SearchListings, expected 200 / got 200, verdict mismatch; diverging keys $.listingSummaries[0], $.listingSummaries[0].logoThumbnailUrl and $.nextToken - the last not claimed).
