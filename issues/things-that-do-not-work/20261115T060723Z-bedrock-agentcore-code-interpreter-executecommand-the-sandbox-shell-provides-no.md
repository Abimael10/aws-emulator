# Code Interpreter executeCommand: the sandbox shell provides no `sort` (and no other coreutils text utility beyond its 5-program catalog), and a command it cannot run exits 127 with both streams empty and no diagnostic (2 causes)

> _Note: this issue was identified against the code base at commit `3e93d103c367b3f539a01bb50ca5553fc9a2ef76`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
InvokeCodeInterpreter

## Description
TWO net-new root causes in bedrock-agentcore's InvokeCodeInterpreter `executeCommand` tool plane (built-in interpreter aws.codeinterpreter.v1). Both are visible in ONE replayed check, whose earlier phases now PASS: the file tools write/read/list in the session workspace, and every out-of-sandbox path (`../` traversal and absolute) is now refused IN BAND with isError=true, the fixed lead-in `Error executing tool ` and a reason naming path traversal, with no links. So this is NOT the routing failure of the open issue 20261029T215145Z-bedrock-agentcore-agentcore-data-plane-invocation-unserved-invokecodeinterpreter-and-invokeharness.md (InvokeCodeInterpreter answering UnknownService), and it is NOT Cause 1 or Cause 3 of the open issue 20261102T063922Z-bedrock-agentcore-code-interpreter-tool-plane-diverges-python-executecode-the.md as those are worded there: the path escape is no longer refused out of band as 400 ValidationException, and executeCommand no longer answers `ToolOutcome::NothingRan` with a structuredContent holding only stderr — it now runs a real shell and reports stdout/stderr/exitCode/executionTime. What follows is what that served shell gets wrong. Neither issue carries this check's replay key, so these causes must be replayed even if either is closed first. The companion wire issue 20261102T113600Z-bedrock-agentcore-invokecodeinterpreter-result-events-carry-the-wrong-codeinterpreterresult-member.md is about WHICH result members are serialized and is unrelated to what the shell computes.

Cause 1 of 2: a command line that names a standard text utility the emulator's sandbox catalog does not hold (here `sort`) runs nothing at all, so the pipeline produces no output and exits 127.
AWS: Smithy (services/service-com-amazonaws-bedrockagentcore-amazonbedrockagentcore/smithy-model/com-amazonaws-bedrockagentcore-amazonbedrockagentcore.json): InvokeCodeInterpreter's ToolName includes `executeCommand`, ToolArguments carries `command` ("The command to execute with the tool"), and CodeInterpreterResult.structuredContent is ToolResultStructuredContent {taskId, taskStatus, stdout ("The standard output from the tool execution"), stderr, exitCode ("The exit code from the tool execution"), executionTime}. Recorded behavior: AWS's Code Interpreter sandbox is a Linux environment with the ordinary coreutils installed, so a command line of the form `ls -1 <missing-path-a> <missing-path-b> 2>&1 | sort -u` runs both stages: `ls` writes one `No such file or directory` diagnostic per missing operand, the `2>&1` sends it into the pipe, `sort -u` reads it and writes those lines, and the pipeline's exitCode is the LAST stage's (0 for a `sort` that succeeded). The fixed text of the diagnostic is the utility's own (`ls: cannot access '<path>': No such file or directory`); the variable part is the path from the command line.
Emulator: the same call answers a result whose structuredContent is `{'stdout': '', 'stderr': '', 'exitCode': 127, 'executionTime': <per-run>}` — exitCode 127 is `Statuses::could_not_run` ("the utility to be executed could not be found"), and because the pipeline's status is its last stage's, the whole line reports 127 and nothing at all on either stream. The reason is the catalog: `sort` is in none of the four catalogs the sandbox shell resolves a name against — service-common's BUILT_IN_COMMANDS (echo, cat, true, false, :, exit, export, unset), VOLUME_COMMANDS (printf, mkdir, touch, rm, test, [, sh, bash, ., source, sleep), TEXT_FILTER_COMMANDS (wc, cut, head, sha256sum, sha512sum) nor the sandbox's own SANDBOX_PROGRAMS (ls, head, tail, wc, pwd). Hypothesis: `sort` is the stage that was not found, since `ls` IS provided and 127 is the not-found status; any other common utility (sort, grep, sed, awk, tr, uniq, find, diff, cp, mv, basename, dirname, xargs, env, date) is in the same position.
Why: the shell is one of the three views of a code-interpreter sandbox, and agents write `executeCommand` lines against ordinary coreutils and pipe them. Such a client gets an empty stdout and a 127 for a line that works on AWS, so it reads "the command produced no output" where AWS produced output; any assertion about the sandbox's filesystem made THROUGH the shell (here: that a refused writeFiles left no file outside the working directory) cannot be made at all, and a security-relevant verification silently turns into a vacuous one.
Fix: the sandbox's program catalog for the command plane — services/service-com-amazonaws-bedrockagentcore-amazonbedrockagentcore/src/state/code_interpreter_programs.rs (SANDBOX_PROGRAMS / SandboxPrograms::run), which is what the shell asks for a name its own catalogs do not hold, and/or the shared text-filter catalog in services/common/src/posix_shell_text_filters.rs if the utility belongs to every session. The utilities must compute over the session tree the shell already hands them (ProgramFiles) — no host process and no host path.
Traces: bedrock-agentcore.agc-code-interpreter-file-tool-path-escape-rejected.

Cause 2 of 2: a command the shell could not run reports NO diagnostic — stderr is empty beside the 127.
AWS: POSIX (Shell Command Language, Command Search and Execution) states that when the command cannot be found "the shell shall write an error message and the exit status shall be 127", and every shell an AWS sandbox ships writes that message, naming the command it could not run, to standard error. So a 127 on AWS always arrives WITH a diagnostic that names the offending command name; the fixed part is the shell's own "not found" wording and the variable part is the command name taken from the request's command line. Recorded behavior for the exit status itself: 127.
Emulator: the result carries exitCode 127 with stdout '' AND stderr '' — the shell's own catalog miss is latched into the status and nothing is written for it, so the only signal a client has is a bare number with no indication of which stage of the pipeline failed or why. The same silence applies to every other fail-closed condition the shared session answers with could_not_run (a command FORM it does not perform, a line past its bounds).
Why: a client cannot distinguish "your command is not installed in this sandbox" from "your command ran and printed nothing", and an agent loop that inspects stderr to decide whether to retry, rewrite or report gets an empty string; because the refusal is also not isError-flagged as a tool failure, the call looks like a successful-but-silent run.
Fix: the shell session's command-resolution failure path in services/common/src/posix_shell_session.rs (the Statuses::could_not_run arms) must write the shell's "command not found" diagnostic, naming the command, onto the session's error stream (ShellSession::errors), which bedrock-agentcore's command plane already propagates verbatim into the result's structuredContent.stderr (services/service-com-amazonaws-bedrockagentcore-amazonbedrockagentcore/src/state/code_interpreter_shell.rs run_command -> ops/invoke_code_interpreter.rs execute_command / ran_outcome).
Traces: bedrock-agentcore.agc-code-interpreter-file-tool-path-escape-rejected.
