# eks read-only catalog and schema discovery reads serve synthesised payloads instead of the published AWS catalog

> _Note: this issue was identified against the code base at commit `ab053b44c0c4551c75ed9277db4b5c52abcaed14`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
DescribeAddonVersions

## Description
FIVE net-new root causes in the eks service share one fault: the read-only EKS discovery surface (DescribeAddonVersions, DescribeClusterVersions, DescribeAddonConfiguration) answers HTTP 200 with the right response SHAPE but with emulator-authored content, so the add-on catalog rows, the cluster-version catalog rows and the per-add-on configuration JSON schema a client validates against are not the ones AWS publishes. No status code and no error class is at stake in any of the five; only the served catalog payload diverges. All five clusters are reported by the replay with an empty owned_by and an empty stub_path, i.e. no open issue carries their replay keys.

Adjacent OPEN issues that do NOT carry these five replay keys (named so a fixer does not close these causes as duplicates): 20261114T191058Z-eks-catalog-reads-publish-synthesised-control-plane-constraints.md (clusterVersions[*].controlPlaneComponentConfig constraint bounds on fixture eks-ekscc-traj-version-and-support-mistakes#task#8 and addonVersions rows on eks-mbes-traj-create-addon-request-mistakes#task#7 — a different set of keys and fixtures from the five below, and it does not cover a MISSING catalog ROW or a missing clusterVersions row at all); 20261121T151648Z-eks-describeaddonversions-catalog-record-selection-and-registercluster-invalid.md (whose DescribeAddonVersions cause was keyed on $.addons[*].marketplaceInformation.productUrl only — the replay now reports the record itself absent at $.addons[0] on that same step and lists the cluster as unowned, so Cause 2 below is re-filed with the widened key); 20261104T105252Z-eks-2-net-new-root-causes-the-metrics.md (metrics-server configuration schema, a different add-on and fixture); 20261117T115837Z-eks-iam-describeaddonconfiguration-s-podidentityconfiguration-recommends-the-wrong.md (wrong recommendedManagedPolicies inside a podIdentityConfiguration entry, not a missing entry).

In every cause below, the literal add-on names, version strings, cluster versions, dates and schema property names quoted from the recording are cited only to identify WHICH published rows/properties are missing or altered. The requirement is that the served catalog be the published AWS catalog selected by the request's filters — never these literal values.

Cause 1 of 5: a filtered DescribeAddonVersions query omits the catalog record the request selects, serving a different record at addons[0] (82 affected steps).
  AWS: Smithy (services/service-com-amazonaws-eks-awswesleyfrontend/smithy-model/com-amazonaws-eks-awswesleyfrontend.json): DescribeAddonVersions is GET /addons/supported-versions, code 200, output addons : Addons + nextToken, @paginated(items=addons, pageSize=maxResults); the input members kubernetesVersion, addonName, types, publishers, owners, maxResults, nextToken are ALL @httpQuery, i.e. they SELECT which catalog rows are returned. Each element is an AddonInfo{addonName, type, addonVersions : AddonVersionInfoList, publisher, owner, marketplaceInformation, defaultNamespace}; addonVersions is documented as "information about available add-on versions and compatible Kubernetes versions", each AddonVersionInfo carrying addonVersion, architecture, computeTypes, compatibilities (clusterVersion / platformVersions / defaultVersion) and requiresConfiguration / requiresIamPermissions. Errors InvalidParameterException 400, ResourceNotFoundException 404, ServerException 500 — none applies here. Recorded behavior: for the fixture's filter set the catalog returns the observability add-on record (recorded as addonName 'adot', type 'observability') whose addonVersions is a multi-release history, newest release flagged defaultVersion true per compatible clusterVersion and older releases false, each release with its own architecture ['amd64','arm64'] and computeTypes set.
  Emulator: answers 200 but the record the catalog publishes at addons[0] for the requested filters is absent ($.addons[0]: missing); a different, synthesised record occupies that position. The same divergence repeats across 82 steps of this fixture, i.e. the filter combinations exercised by a catalog walk systematically do not select published rows.
  Why: this listing is how a client discovers which add-ons exist and which versions of each may be installed on a given cluster version. With the published record absent, an installer enumerating add-ons for a cluster never sees the add-on at all, and a client that pins, upgrades or rolls back to a named version is told that version does not exist, while CreateAddon in production accepts it.
  Fix: the add-on catalog data behind DescribeAddonVersions' handler and that handler's httpQuery filter selection — the filters must select rows from the catalog instead of driving generation of a plausible listing.
  Traces: eks-catalog-describe-addon-versions-accuknox-kubearmor-eg-innovations-eg-universal-agent-operator#task#2 (representative; 82 affected steps in the cluster).

Cause 2 of 5: the same omission on a Marketplace-owned storage record, together with a marketplaceInformation.productUrl in the wrong form.
  AWS: as Cause 1 for the operation; additionally Smithy MarketplaceInformation{productId, productUrl} with productUrl documented "The product URL from the Amazon Web Services Marketplace" — the catalog's published URL for that productId. Recorded behavior: the filter selects a Marketplace storage record (recorded as addonName 'netapp_trident-operator', type 'storage') whose addonVersions is the add-on's published release history over the cluster versions it supports, with requiresConfiguration/requiresIamPermissions per release.
  Emulator: answers 200 with $.addons[0] missing, and where a Marketplace record is served its marketplaceInformation.productUrl is a different URL form than the catalog publishes for the same product.
  Why: a client cannot install or subscribe to a Marketplace add-on it never sees, and one that follows productUrl for a subscription or legal check lands on a URL that does not identify the product.
  Fix: same component as Cause 1 (catalog data + filter selection), plus the Marketplace productUrl carried on the catalog record.
  Traces: eks-catalog-describe-addon-versions-eks-node-monitoring-agent-vpc-cni#task#20.

Cause 3 of 5: DescribeClusterVersions' unfiltered catalog read returns none of the published cluster-version rows.
  AWS: Smithy: DescribeClusterVersions is GET /cluster-versions, code 200, output clusterVersions : ClusterVersionList + nextToken, @paginated(items=clusterVersions); httpQuery filters clusterType, clusterVersions, defaultOnly, includeAll, versionStatus (and the deprecated status, deprecated since 2025-02-15). Each ClusterVersionInformation carries clusterVersion, clusterType, defaultPlatformVersion, defaultVersion (@default false), releaseDate, endOfStandardSupportDate, endOfExtendedSupportDate, status/versionStatus, kubernetesPatchVersion, controlPlaneScalingTiers (ControlPlaneScalingTierList, @length 0..10 — "the available provisioned control plane scaling tiers and their capabilities for this Kubernetes version") and controlPlaneComponentConfig ("the default control plane component configuration and constraints for this Kubernetes version"). Recorded behavior: the read returns the published rows newest-first, each with its platform version, support dates, patch version, versionStatus and its scaling-tier table (tier name, apiRequestConcurrency, podSchedulingRatePerSecond, clusterDatabaseSizeGb and the per-tier component-config overrides).
  Emulator: answers 200 but every one of the published rows the recording expects is absent — the replay reports $.clusterVersions[0] through $.clusterVersions[6] all missing, so the catalog this read serves is a different set of rows entirely.
  Why: this listing is the contract a client reads to choose a Kubernetes version, to decide whether a version is in standard or extended support, and to size a provisioned control plane. With the published rows absent, version-selection and support-lifecycle logic picks versions AWS does not offer (or refuses versions AWS does), and scaling-tier selection has no tier table to choose from.
  Fix: the cluster-version catalog data behind DescribeClusterVersions' handler and its filter/pagination selection over that data.
  Traces: eks-catalog-describe-cluster-versions#task#1.

Cause 4 of 5: DescribeAddonConfiguration serves a configurationSchema whose property set and placement are not the published schema for that add-on version, and drops a podIdentityConfiguration entry.
  AWS: Smithy: DescribeAddonConfiguration is GET /addons/configuration-schemas, code 200, input addonName and addonVersion both @required @httpQuery, output addonName, addonVersion, configurationSchema : String ("A JSON schema that's used to validate the configuration values you provide when an add-on is created or updated") and podIdentityConfiguration : AddonPodIdentityConfigurationList of AddonPodIdentityConfiguration{serviceAccount, recommendedManagedPolicies}. Errors InvalidParameterException 400, ResourceNotFoundException 404, ServerException 500 — none applies. The schema is therefore VERSION-SPECIFIC: for the add-on version named in the request it must be the exact JSON schema document the add-on publishes, property-for-property, including where each property sits in the object tree and its type/constraints, because that document is what a client uses to validate the configurationValues it will send to CreateAddon/UpdateAddon. Recorded behavior for this step: the aws-efs-csi-driver schema with draft 2019-09 $schema, additionalProperties false, and the controller/node/useFIPS object tree in which deleteAccessPointRootDir sits UNDER properties.controller (a boolean, "For dynamic provisioning, control whether the access point directory is deleted on unmount"), plus a podIdentityConfiguration list with more than one entry.
  Emulator: answers 200 with a configurationSchema string that differs from the published document for the requested addonName/addonVersion pair (value_mismatch on $.configurationSchema), and with $.podIdentityConfiguration[1] absent — the list is served short of its published entries.
  Why: a client that validates its configurationValues against the served schema accepts configuration AWS's schema rejects (or rejects configuration AWS accepts) and so fails at CreateAddon/UpdateAddon in production; with a podIdentityConfiguration entry missing, the IAM role an operator builds for the add-on omits one of the service accounts/policies the add-on needs and the add-on fails at runtime.
  Fix: the per-add-on-version configuration-schema and pod-identity catalog data behind DescribeAddonConfiguration's handler, and the handler's addonName+addonVersion lookup into it (it must return the stored document for that exact version, not a schema shared across versions).
  Traces: eks-efsfips-traj-catalog-and-schema-discovery#task#1.

Cause 5 of 5: the same DescribeAddonConfiguration read for a DIFFERENT add-on version serves the same schema document, so the version-to-schema mapping is collapsed.
  AWS: as Cause 4. The published schema evolves between add-on versions — in the recording the two versions queried in this fixture differ precisely in where deleteAccessPointRootDir sits: nested under properties.controller for one version and a TOP-LEVEL property of the schema for the other. AWS returns each version's own document, which is why addonVersion is @required on the request.
  Emulator: answers 200 with a configurationSchema that does not match the document published for the requested version (value_mismatch on $.configurationSchema), consistent with one schema being served regardless of the addonVersion asked for.
  Why: a client that reads the schema for the exact version it is about to install gets another version's rules, so it validates its configurationValues against the wrong contract and the install fails where the emulator said it would succeed.
  Fix: same component as Cause 4 — the addonVersion key must select the schema document, not be ignored.
  Traces: eks-efsfips-traj-catalog-and-schema-discovery#task#2 (2 affected steps: also eks-eks-catalog-read-only-discovery#task#3).

All five causes must be closed before this issue is resolved; each has its own fixture/step listed above and each must be re-replayed.
