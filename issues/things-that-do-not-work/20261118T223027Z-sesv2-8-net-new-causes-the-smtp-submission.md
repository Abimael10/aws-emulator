# sesv2: 8 net-new causes — the SMTP submission data plane does not exist, and seven control-plane validations accept input AWS refuses

> _Note: this issue was identified against the code base at commit `03a0508b3aa0858110fb1a346ba54180a1d13415`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
SendRawEmail

## Description
Eight net-new root causes in the SESv2 surface: the SMTP submission data plane is not served at all, and seven control-plane operations accept a request AWS refuses, persisting state AWS never creates. This issue bundles 8 causes; all eight must be closed before submitting.

Cause 1 of 8 — the SES SMTP submission endpoint is not served.
AWS: recorded behavior only (the SMTP submission data plane is not in the Smithy model; the model describes only the signed restJson1 API). SES exposes an SMTP submission listener that is a SEPARATE listener from the signed API, accepting an implicit-TLS ("TLS wrapper") connection on port 465, answering a 220 greeting, advertising its ESMTP capability keywords in the EHLO reply, authenticating with SMTP AUTH using credentials derived from an IAM access key, and then running a MAIL FROM/RCPT TO/DATA transaction. Emulator: nothing accepts a TCP connection on that port at all — every one of the eight SMTP checks dies in its connect helper with `AssertionError: DATAPLANE_UNIMPLEMENTED: nothing accepted a TCP connection on <host>:465; the SES SMTP submission data plane is a separate listener from the signed API (ConnectionRefusedError(111, 'Connection refused'))`. Why: a client that submits mail over SMTP (every mail library, every appliance, every `smtplib`/JavaMail integration, anything using SES SMTP credentials rather than the API) cannot connect, so it never gets as far as an SES error; and eight distinct documented behaviors are unobservable — the DATA byte-count ceiling with no SIZE advertisement to trust, refusal of ESMTP parameters absent from the EHLO advertisement, functionality of every advertised AUTH mechanism plus refusal of an unadvertised one, the identity gate reading the RFC 5322 From header rather than the envelope sender, the envelope recipient ceiling, the session transaction state machine, IAM-policy evaluation at submission, and resolution of the X-SES-CONFIGURATION-SET header. Fix: a new SMTP submission listener component (its own TLS-wrapped socket listener, EHLO capability advertisement, SASL AUTH against the IAM-derived SMTP credential, and a transaction state machine that hands the assembled message to the same send path SendRawEmail uses) alongside the existing signed-API server. Traces: sesv2.smtp-data-byte-count-is-enforced-with-no-size-declaration-to-trust, sesv2.smtp-esmtp-parameters-absent-from-the-ehlo-advertisement-are-refused-not-ignored, sesv2.smtp-every-advertised-auth-mechanism-is-functional-and-an-unadvertised-one-is-refused, sesv2.smtp-identity-gate-reads-the-rfc5322-from-header-not-the-envelope-sender, sesv2.smtp-recipient-ceiling-is-enforced-at-the-envelope-and-the-accepted-recipients-survive, sesv2.smtp-session-is-a-transaction-state-machine-not-a-stateless-verb-bag, sesv2.smtp-submission-evaluates-the-iam-policy-and-reverts-when-it-is-restored, sesv2.smtp-x-ses-configuration-set-header-is-resolved-at-submission.

Cause 2 of 8 — CreateContactList does not enforce the 500-character Description ceiling.
AWS: Smithy declares CreateContactList input {ContactListName (required), Topics, Description, Tags} with error BadRequestException (400); the Description shape carries no length constraint, so the limit is service-side (recorded behavior only). A Description of 501 characters is refused 400 BadRequestException with the message `List description can contain up to 500 characters.` — fixed text, no variable parts — and the list is NOT created (a following GetContactList answers NotFoundException `List with name: <NAME> doesn't exist.`). A Description of exactly 500 characters is accepted and round-trips verbatim. Emulator: the 501-character create is ACCEPTED with 200 and an empty body. Why: a client relying on the refusal silently stores an over-long description, and a client exercising the boundary cannot distinguish the legal 500 from the illegal 501. Fix: CreateContactList's input validation (the Description length check must run before the list is inserted into state). Traces: sesv2.contact-list-create-limit-boundaries.

Cause 3 of 8 — CreateContactList does not enforce the 64-character ContactListName ceiling, which AWS checks before existence.
AWS: ContactListName is an unconstrained string in the model, so the rule is service-side (recorded behavior only). A 65-character name is refused 400 BadRequestException with `ContactListName can contain up to 64 characters. Only alphanumeric characters, underscores(_) and hyphens(-) are allowed.` — fixed text, no variable parts — on CreateContactList AND on GetContactList, i.e. the name-shape check runs BEFORE any existence lookup, so an over-long name never yields NotFoundException. A never-created 64-character name is instead refused NotFoundException `List with name: <NAME> doesn't exist.` (variable part: the ContactListName from the request). Emulator: CreateContactList with a 65-character name is ACCEPTED with 200 and an empty body. Why: a client gets a stored list under a name AWS would never accept, and validation-ordering logic (shape error vs not-found) is inverted. Fix: shared ContactListName shape validation invoked at the head of the CreateContactList and GetContactList handlers, ahead of the state lookup. Traces: sesv2.contact-list-name-length-checked-before-existence.

Cause 4 of 8 — UpdateContactList does not enforce the 20-topic ceiling.
AWS: Smithy UpdateContactList input {ContactListName (httpLabel, required), Topics, Description}, errors BadRequestException(400)/NotFoundException(404); the Topics list carries no length constraint, so the ceiling is service-side (recorded behavior only). A Topics list of 21 entries is refused 400 BadRequestException with `Maximum of <20> topics allowed per ContactList` — the fixed text wraps the limit in angle brackets, `<20>` being the service limit and not a request value, and there is no trailing period — and the refusal persists nothing: the previously stored Topics and Description are unchanged. A 20-topic update then applies. The same ceiling and message apply on CreateContactList. Emulator: the 21-topic UpdateContactList is ACCEPTED with 200 and an empty body. Why: a client that treats the refusal as the limit check stores more topics than AWS permits, and a refusal that should be atomic instead mutates the list. Fix: the UpdateContactList handler's validation (and the shared contact-list topic validator used by CreateContactList), run before any mutation of stored state. Traces: sesv2.update-contact-list-over-topic-limit-rejected.

Cause 5 of 8 — CreateEmailIdentity accepts a domain whose leftmost label starts with a hyphen.
AWS: Smithy CreateEmailIdentity input {EmailIdentity (required, @length min 1), Tags, DkimSigningAttributes, ConfigurationSetName}, errors include BadRequestException(400). A domain whose leftmost label begins with '-' is not valid DNS syntax and is refused 400 BadRequestException with `Identity <IDENTITY> is invalid. Must be a valid email address or domain.` — fixed text `Identity ` + the EmailIdentity exactly as submitted + ` is invalid. Must be a valid email address or domain.` GetEmailIdentity for the same string is refused with the distinct sentence `Email identity <<IDENTITY>> is invalid.` (fixed text `Email identity <` + the identity + `> is invalid.`). The same domain with the leading hyphen stripped is created and reads back IdentityType DOMAIN. Emulator: the invalid domain is ACCEPTED with 200, returning IdentityType DOMAIN, VerifiedForSendingStatus false and a full DkimAttributes block with three freshly minted tokens. Why: a client that validates identity syntax through the API gets a verification workflow started for a domain that can never resolve, and no later call tells it the name is unusable. Fix: EmailIdentity syntax validation in the CreateEmailIdentity handler plus the matching check in GetEmailIdentity, ahead of state insertion/lookup. Traces: sesv2.create-email-identity-leading-hyphen-domain-label-rejected.

Cause 6 of 8 — CreateEmailIdentity ignores a ConfigurationSetName that does not exist.
AWS: Smithy CreateEmailIdentity declares NotFoundException(404) among its errors and takes an optional ConfigurationSetName. Naming a configuration set that does not exist is refused 404 NotFoundException with `Configuration set <<NAME>> does not exist.` (fixed text `Configuration set <` + the ConfigurationSetName from the request + `> does not exist.`), and the identity is NOT created — a following GetEmailIdentity answers 404 NotFoundException `Email identity <<IDENTITY>> does not exist.` The identical call naming a configuration set that does exist succeeds and GetEmailIdentity reports that ConfigurationSetName. Emulator: the call naming a nonexistent configuration set is ACCEPTED with 200 (IdentityType EMAIL_ADDRESS, DkimAttributes present), creating the identity. Why: a client pointing an identity at a mistyped configuration set gets no error and an identity whose default configuration set silently does not exist, so later sends behave differently from what the create implied. Fix: the CreateEmailIdentity handler must resolve ConfigurationSetName against configuration-set state and raise NotFoundException before inserting the identity. Traces: sesv2.create-email-identity-unknown-configuration-set-rejected.

Cause 7 of 8 — CreateEmailTemplate accepts a reserved `aws:`-prefixed tag key.
AWS: Smithy CreateEmailTemplate input {TemplateName (required), TemplateContent (required), Tags}, errors AlreadyExistsException(400)/BadRequestException(400)/LimitExceededException(400)/TooManyRequestsException(429). A Tags entry whose Key begins with the reserved prefix `aws:` is refused 400 BadRequestException with `Invalid tags` — fixed text, no variable parts, no trailing period — and NO template is created, so the name stays free: GetEmailTemplate answers 404 NotFoundException `Template <NAME> does not exist.` and a later CreateEmailTemplate on the same name with a legal tag succeeds and lists exactly that one tag. Emulator: the create carrying `aws:`-prefixed tags is ACCEPTED with 200 and an empty body. Why: a client gets a template tagged in AWS's reserved namespace, and a create/retry flow that expects the name to still be free instead collides with the template this call should never have made. Fix: reserved-tag-prefix validation in the CreateEmailTemplate handler's tag handling, ahead of template insertion. Traces: sesv2.create-email-template-aws-tag-prefix-rejected-name-freed.

Cause 8 of 8 — PutTenantSuppressionAttributes accepts SuppressedReasons without SuppressionScope.
AWS: Smithy PutTenantSuppressionAttributes input {TenantName (required, @length min 1), SuppressedReasons (list of SuppressionListReason), SuppressionScope (enum SuppressionListScope)}, errors BadRequestException(400)/NotFoundException(404)/TooManyRequestsException(429). The two members are a pair: supplying SuppressedReasons with no SuppressionScope is refused 400 BadRequestException with `SuppressedReasons cannot be specified without SuppressionScope.` — fixed text naming the two member names, no variable parts — and an already-established tenant suppression configuration is left unchanged. Supplying the full pair then updates it, and a call naming only TenantName clears it. Emulator: the half-pair call is ACCEPTED with 200 and an empty body. Why: a client making a partial update believes a suppression scope was applied when none was, and the half-applied write diverges from AWS's all-or-nothing pair semantics. Fix: cross-member validation in the PutTenantSuppressionAttributes handler, before the tenant suppression state is written. Traces: sesv2.tenant-suppression-half-pair-rejected-baseline-unchanged.
