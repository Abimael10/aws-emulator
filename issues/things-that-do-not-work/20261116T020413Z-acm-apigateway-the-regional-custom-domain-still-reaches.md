# acm__apigateway: the REGIONAL custom domain still reaches no verdict — the ISSUED-certificate presentation leg produces neither a handshake nor a refusal and the check is killed at the 60 s cap

> _Note: this issue was identified against the code base at commit `78a28d66acabd31f329494a20428d6e048dfa41c`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
CreateDomainName

## Description
1 net-new root cause for the acm__apigateway pair. The replay report marked this failure neither ALREADY FILED nor OWNED, so no open issue carries its replay key. A RESOLVED issue names this same check id — issues/things-that-now-work/20261114T121226Z-acm-apigateway-a-regional-custom-domain-s-data.md — and its Resolution closed only the Route 53 leg (TestDNSAnswer now resolves an alias whose target names an address) while stating in so many words what it left open: the check dials the resolved address on 443 because an A record carries no port, but the custom-domain listener takes no requested port (it binds an OS-assigned port inside the emulator's listener range) and the core TLS has no per-connection certificate resolver, so the front door can neither answer on 443 nor present the domain's ACM leaf. A resolved issue does not cover a still-failing check, and this one still produces no verdict at all; this filing records the cause as it reproduces now. The failure is a HANG, not a refusal, so it is not a reopened refusal.

Cause 1 of 1: the apigateway REGIONAL custom-domain data plane produces no terminal observation. The check is killed with 'Error: Check timed out after 60.0s' having graded none of its later beats, against a trajectory whose own waits are much longer (imported certificate -> ISSUED 120 s, domainNameStatus -> AVAILABLE 300 s, ALIAS -> INSYNC 120 s, TestDNSAnswer -> A record 60 s, first verified TLS handshake 60 s), so the whole budget was consumed inside one blocking readiness/handshake loop rather than by a wrong field value.

AWS: a REGIONAL custom domain is a real TLS terminator reachable through DNS, and CreateDomainName gates the certificate's STATE. Smithy (com.amazonaws.apigateway): CreateDomainName -> POST /domainnames, success 201, errors BadRequestException (400), ConflictException (409), LimitExceededException (429), TooManyRequestsException (429), UnauthorizedException (401); DomainName$regionalCertificateArn — "The reference to an Amazon Web Services-managed certificate that will be used for validating the regional domain name. Certificate Manager is the only supported source"; DomainName$regionalDomainName — "The domain name associated with the regional endpoint for this custom domain name. You set up this association by adding a DNS record that points the custom domain name to this regional domain name"; DomainName$regionalHostedZoneId — "The region-specific Amazon Route 53 Hosted Zone ID of the regional endpoint"; DomainName$domainNameStatus; DomainName$securityPolicy — the TLS version + cipher suite for this DomainName. Beyond the model, recorded behavior only: CreateDomainName naming a certificate that is not ISSUED is refused HTTP 400 BadRequestException with message exactly 'Certificate is not in an ISSUED state, and cannot be used' (all fixed text — it carries no ARN, no observed status and no member name, which is what keeps it distinct from a malformed-ARN refusal) and leaves no domain behind; regionalDomainName is a DNS HOST that a Route 53 ALIAS targeted with regionalHostedZoneId resolves to IPv4 A records; a TLS handshake to one of those addresses on port 443 with ClientHello SNI = the custom domain presents byte-for-byte the leaf whose ARN was given as regionalCertificateArn (SNI selection, RFC 6066 §3), negotiates TLS 1.2 or 1.3 when securityPolicy is TLS_1_2, and the HTTP layer behind the terminator answers status 403 for a custom domain with no base path mapping; GetDomainNames then lists the domain.

Emulator: nothing on the far side of the control plane is observable. No presented-certificate DER, no negotiated TLS version, no HTTP status line and no final GetDomainNames listing is ever produced — the check is killed at the harness ceiling. services/service-com-amazonaws-apigateway-backplanecontrolservice/src/ops/create_domain_name.rs opens a listener through crate::state::open_custom_domain_endpoint and stores regionalDomainName/regionalHostedZoneId, and src/service/custom_domain_socket.rs is the front door, but that listener is reached only on the OS-assigned port it was given and the process TLS presents one static certificate with no SNI-driven resolver, so a client dialling <resolved address>:443 with SNI = the custom domain gets neither a completed handshake nor a TLS alert. Hypothesis: the dial to 443 is refused or hangs and the check's handshake retry loop spins until the cap; the alternative — an address resolving but presenting the wrong leaf — would have failed with a certificate assertion instead of a timeout, which it did not.

Why: a client relying on AWS's behavior cannot serve or verify TLS on a REST custom domain. CreateDomainName becomes a write-only config: the ARN is echoed, but no client is ever presented that certificate, the securityPolicy floor is unenforced, and the documented 403-for-unmapped-domain never arrives. Worse than a refusal, the connection HANGS, so nothing distinguishes 'not ready yet' from 'will never be ready' and a deployment or test that pins the leaf or probes the domain blocks instead of passing or failing.

Fix: the apigateway REGIONAL custom-domain data plane together with the core listener/TLS seam it depends on. The front door behind the published regionalDomainName must be reachable on 443, must present the leaf referenced by the record's regionalCertificateArn selected by ClientHello SNI, must honour securityPolicy as a minimum-version floor, and must answer HTTP 403 when no base path mapping matches the Host; the control-plane record already carries every needed field, and its certificate-state gate (the BadRequestException wording above) is correct.

Traces: acm__apigateway.regional-custom-domain-refuses-a-pending-certificate-then-serves-the-issued-one (mismatch, 'Error: Check timed out after 60.0s'). Component files: services/service-com-amazonaws-apigateway-backplanecontrolservice/src/ops/create_domain_name.rs (open_custom_domain_endpoint, regionalDomainName publication); src/service/custom_domain_socket.rs (the front door, 977 lines); src/state.rs (DomainNameEntry endpoint/security_policy/mutual_tls_authentication); src/state/acm_certificate_state.rs (the correct certificate-state gate); vendor/server/src/listeners.rs (binds an OS-assigned port, takes no requested port) and vendor/server/src/tls_certificate_authority.rs (one process certificate, no per-connection resolver).

## Evidence
Expected (AWS): acm:ImportCertificate of a self-signed leaf whose DNS SAN is <domain> reaches Status=ISSUED; acm:RequestCertificate(ValidationMethod=DNS) for the same name stays PENDING_VALIDATION; apigateway:CreateDomainName(domainName=<domain>, regionalCertificateArn=<issued>, endpointConfiguration={types:[REGIONAL]}, securityPolicy=TLS_1_2) answers 201 echoing regionalCertificateArn; the same create with the PENDING_VALIDATION ARN is refused HTTP 400 BadRequestException with message exactly 'Certificate is not in an ISSUED state, and cannot be used' and leaves no domain behind; the re-created domain reaches domainNameStatus=AVAILABLE with non-empty regionalDomainName AND regionalHostedZoneId; a Route 53 A ALIAS for <domain> targeting {DNSName: regionalDomainName, HostedZoneId: regionalHostedZoneId} reaches INSYNC and TestDNSAnswer answers NOERROR with IPv4 RecordData; a TLS connection to one of those addresses on port 443 with server_hostname=<domain>, trusting only the importing root, completes, presents exactly the imported leaf's DER, negotiates TLSv1.2 or TLSv1.3, and the tunnel carries a well-formed 'HTTP/1.1 403 ...' status line because no base path mapping exists; GetDomainNames then lists <domain>.

Actual (emulator): no terminal assertion is reached. Replay verdict: mismatch, 'Error: Check timed out after 60.0s'. No IPv4-dialled handshake completes, no peer certificate DER, no negotiated TLS version, no HTTP status line and no final GetDomainNames listing is ever observed. The 60 s figure is the harness ceiling, not an AWS requirement: the divergence reported is a custom-domain front door that neither completes nor refuses a TLS connection on the port a client reaches it on, and that presents no per-domain certificate. The control-plane handlers themselves answer promptly, which is why this manifests as a hang in a retry loop rather than as an API error.

## Steps to Reproduce
1. Mint a private RSA-2048 root CA and a leaf signed by it carrying DNS SAN = <domain>, where <domain> is a label under a random parent under a real TLD.
2. acm:ImportCertificate(Certificate=<leaf PEM>, PrivateKey=<leaf key PEM>, CertificateChain=<root PEM>) -> issued_arn; poll acm:DescribeCertificate until Status=ISSUED.
3. acm:RequestCertificate(DomainName=<domain>, ValidationMethod=DNS) -> pending_arn; confirm DescribeCertificate reports PENDING_VALIDATION.
4. apigateway:CreateDomainName(domainName=<domain>, regionalCertificateArn=issued_arn, endpointConfiguration={types:[REGIONAL]}, securityPolicy=TLS_1_2, tags={...}). Expect 201 with regionalCertificateArn echoed. DeleteDomainName and poll GetDomainNames until the name is gone.
5. CreateDomainName again with regionalCertificateArn=pending_arn. Expect HTTP 400 BadRequestException with message exactly 'Certificate is not in an ISSUED state, and cannot be used', and GetDomainNames still not listing <domain>.
6. CreateDomainName again with issued_arn; poll GetDomainName until domainNameStatus=AVAILABLE and read regionalDomainName + regionalHostedZoneId.
7. route53:CreateHostedZone(Name=<parent>); ChangeResourceRecordSets CREATE an A ALIAS for <domain> with AliasTarget={DNSName: regionalDomainName, HostedZoneId: regionalHostedZoneId}; poll GetChange until INSYNC; poll route53:TestDNSAnswer(RecordName=<domain>, RecordType=A) until NOERROR with IPv4 RecordData.
8. TCP-connect to the resolved address on port 443, wrap it in a TLS client context trusting ONLY the private root with check_hostname=True and server_hostname=<domain>, then send 'GET / HTTP/1.1' with Host: <domain>. Expect a completed handshake, peer DER == the imported leaf's DER, negotiated version in {TLSv1.2, TLSv1.3} and an 'HTTP/1.1 403' status line. Observed: the handshake retry loop is still retrying when the harness cap fires and the check is killed with no verdict.
9. GetDomainNames must list <domain>. Observed: unreachable.
