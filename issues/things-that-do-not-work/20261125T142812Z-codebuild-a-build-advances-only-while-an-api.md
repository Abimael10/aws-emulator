# codebuild: a build advances only while an API request is in flight — no build is observable IN_PROGRESS beside a completed one, polls block for the whole command duration, and StopBuild does not cut the running phase short (2 causes)

> _Note: this issue was identified against the code base at commit `34f8b997a46d03b643856bad1989006f24f5aecc`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
BatchGetBuilds

## Description
TWO net-new root causes in the codebuild crate (services/service-com-amazonaws-codebuild-codebuild-20161006). BOTH must be closed before this issue is resolved. These are the only failing codebuild checks of this sweep that the suite report does not mark OWNED or ALREADY FILED.

Context, not a reopen: the resolved issue 20261121T155806Z-codebuild-3-net-new-causes-batchdeletebuilds-deletes-an.md carried three of these five check ids and its fix did land the behaviour it described (BatchDeleteBuilds now withholds, StartBuild now has a concurrency gate, and the stopped build's phase list now attributes STOPPED to the phase that was running). None of these five checks is refused by any operation — every call answers HTTP 200 — so this is not a refusal left behind by that fix; the three checks now fail at different assertions, on the two timing causes below, together with two further checks that now exhaust the harness budget.

Cause 1 of 2: a build's phases only advance while the emulator is serving a request for it, so a build is never observable in a live intermediate state and a read on one build does not come back until the work of the in-flight build(s) has been run to the end.
AWS: Smithy BatchGetBuilds(ids: BuildIds, required, 1..100) -> {builds: Builds, buildsNotFound: BuildIds}, only error InvalidInputException (client, 400); Build carries currentPhase (BuildPhaseType: SUBMITTED, QUEUED, PROVISIONING, DOWNLOAD_SOURCE, INSTALL, PRE_BUILD, BUILD, POST_BUILD, UPLOAD_ARTIFACTS, FINALIZING, COMPLETED), buildStatus (StatusType: SUCCEEDED, FAILED, FAULT, TIMED_OUT, IN_PROGRESS, STOPPED), buildComplete, startTime/endTime and phases. A build runs ASYNCHRONOUSLY of the API: StartBuild returns immediately and BatchGetBuilds is a point-in-time read that answers in well under a second with whatever state the build is in AT THAT MOMENT. Consequently, on real AWS, a build whose build phase runs `sleep 30` reports currentPhase 'BUILD' with buildComplete false for about thirty seconds and can be polled there, and two builds started back to back progress independently of each other, so a build running `echo` reports buildComplete true while its twin running `sleep 90` still reports buildComplete false. Recorded behaviour: all four checks below poll BatchGetBuilds every 2-5 s and depend on exactly those intermediate observations.
Emulator: the intermediate state is not observable and the read does not return promptly. (a) Two builds of one project started back to back with buildspecOverride `echo ...` and `sleep 90`: the poll for the short build's completion only comes back once the long one has also finished, and the immediately following BatchGetBuilds on the long build reports currentPhase 'COMPLETED', buildStatus 'SUCCEEDED', buildComplete true with endTime = startTime + ~91 s and every phase SUCCEEDED — there is no instant at which one is complete and the other in progress. (b) A project with concurrentBuildLimit=1 whose build phase is `echo ...; sleep 30`: the very first BatchGetBuilds after StartBuild already reports the whole timeline finished — phases [(SUBMITTED, SUCCEEDED), (QUEUED, SUCCEEDED), (PROVISIONING, SUCCEEDED), (DOWNLOAD_SOURCE, SUCCEEDED), (INSTALL, SUCCEEDED), (PRE_BUILD, SUCCEEDED), (BUILD, SUCCEEDED), (POST_BUILD, SUCCEEDED), (UPLOAD_ARTIFACTS, SUCCEEDED), (FINALIZING, SUCCEEDED), (COMPLETED, None)] — so the single slot is never observably held and the concurrency refusal can never be exercised. (c) Two checks that poll BatchGetBuilds for currentPhase == 'BUILD' on a build whose build phase is `sleep 60` / `sleep 90` get no answer in time and the check exhausts the 60 s harness budget with no verdict. Hypothesis (neither the model nor the recording states the mechanism): the build's commands are run to completion inside the request that reads the build, rather than by a clock that advances the build independently.
Why: the whole in-flight half of the build data plane is unusable to a client. BatchGetBuilds is the only way to observe a running build, and a client that polls it cannot see currentPhase/buildStatus IN_PROGRESS at all, cannot act on a running build (stop it, wait for a phase, reconcile two concurrent builds), and has its call blocked for as long as the build's commands take instead of getting an immediate point-in-time answer — a build with a multi-minute command hangs every caller that asks about it. Any differential that distinguishes a running build from a finished one (in-progress protection on BatchDeleteBuilds, concurrentBuildLimit enforcement, stopping a build) cannot be reached.
Fix: the build-execution/clock component of the codebuild crate (the module that runs the builds the clock owes a run, and the build queue that holds a build while it runs) together with the BatchGetBuilds read path — advance a build's phases on wall clock independently of request handling, and serve BatchGetBuilds from the state as of now without driving pending builds to their end inside the request.
Traces: codebuild.batch-delete-builds-partial-failure-isolated, codebuild.codebuild-concurrent-build-limit-rejects-the-second-start-and-no-second-build-appears, codebuild.stop-build-on-completed-build-is-an-idempotent-no-op, codebuild.stop-build-race-idempotent-single-transition.

Cause 2 of 2: StopBuild does not interrupt the work of the phase that is running — the stopped phase reports almost the full elapsed time of the command it was supposed to cut short.
AWS: Smithy StopBuild(id: NonEmptyString, required) -> {build: Build}; modeled errors InvalidInputException and ResourceNotFoundException (both client, httpError 400). BuildPhase{phaseType, phaseStatus, startTime, endTime, durationInSeconds, contexts}, where durationInSeconds is documented as "How long, in seconds, between the starting and ending times of the build's phase". A StopBuild issued while the build reports currentPhase 'PRE_BUILD' terminates that phase's commands at the stop, so the stopped PRE_BUILD's endTime is the stop instant and its durationInSeconds is the elapsed time until the stop — strictly less than the same phase of a twin build on the same project that was allowed to run a SHORTER pre_build sleep to completion. The requirement is comparative, not a fixed number: subject PRE_BUILD duration < twin PRE_BUILD duration, and far below the subject's own declared sleep.
Emulator: with the subject's pre_build running `sleep 300` and the stop issued within about five seconds of the build first reporting currentPhase 'PRE_BUILD' (the check polls at a 5 s interval and stops as soon as it sees it), the settled build reports PRE_BUILD durationInSeconds=257 against the twin control's completed PRE_BUILD (`sleep 60`) durationInSeconds=60 — i.e. the interrupted phase reports more than four times the elapsed time of a phase that ran to the end, and nearly the whole 300 s sleep. buildStatus STOPPED, the endTime and the STOPPED attribution to PRE_BUILD are all correct; only the interruption of the running work is missing.
Why: StopBuild's contract is that it cancels work. A client reading the phase timeline of a stopped build cannot tell a stop from a run-to-completion, so it cannot attribute cost/duration, cannot verify that a runaway command was actually killed, and cannot use a stop to free capacity: the commands keep running to their natural end behind a record that claims they were stopped.
Fix: the StopBuild transition in the codebuild build-execution component — terminate the running phase's shell session when the stop is applied, and close that phase with endTime/durationInSeconds taken from the stop instant rather than from the phase's planned end.
Traces: codebuild.stop-build-during-pre-build-stops-exactly-that-phase-and-leaves-the-rest-unrun.
