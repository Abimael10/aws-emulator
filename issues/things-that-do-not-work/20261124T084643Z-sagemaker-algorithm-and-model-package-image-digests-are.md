# sagemaker algorithm and model-package image digests are fabricated, not resolved from the referenced ECR image

> _Note: this issue was identified against the code base at commit `8148416be87f6b2e89717c854691e87b6c3cc940`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
DescribeAlgorithm

## Description
2 causes, ONE shared fault, both in the sagemaker emulator, both answering HTTP 200 so nothing signals the loss: a container-image digest that AWS reports as a property of the referenced Amazon ECR image is instead reported as a value the emulator computes from the image reference STRING. A fixer must close BOTH causes.

This REOPENS the digest half of resolved issue 20261114T143020Z-sagemaker-algorithm-and-model-package-describes-report-an.md (status fixed) and of 20261102T105242Z-sagemaker-model-package-and-algorithm-image-digest-is.md (status fixed). The CreatedBy.IamIdentity.Arn half of the former now passes (it no longer appears in the divergence detail); the digest half still diverges, with exactly the same expected/actual pair. A resolved issue covers nothing, so both clusters are re-filed here; the replay reports them with owned_by: [] and stub_path: "".

Cause 1 of 2: DescribeAlgorithm reports a TrainingSpecification.TrainingImageDigest that is not the digest of the training image the algorithm references (fixture sagemaker-algorithm-duplicate-and-missing-errors, step task#4; cluster also covers sagemaker-algorithm-lifecycle#task#3).
AWS: Smithy (services/service-com-amazonaws-sagemaker-sagemaker/smithy-model/com-amazonaws-sagemaker-sagemaker.json): DescribeAlgorithm output member TrainingSpecification -> TrainingSpecification; TrainingSpecification.TrainingImage -> ContainerImage (@length 0..255, @pattern ^[\S]+$), documented "The Amazon ECR registry path of the Docker image that contains the training algorithm"; TrainingSpecification.TrainingImageDigest -> ImageDigest (@length 0..72, @pattern ^[Ss][Hh][Aa]256:[0-9a-fA-F]{64}$), documented as the hash "that identifies the Docker image used for training". The value is therefore a property of the IMAGE the reference names, not of the algorithm record: its fixed text is the literal prefix `sha256:`, and its variable part is the 64 hex characters of the content digest the registry holding that image reports for it (the same digest that registry's own DescribeImages/BatchGetImage report). One image has ONE digest, the same on every read and in every operation that names it. Status 200, no error.
Emulator: answers 200 with a well-formed but DIFFERENT 64-hex digest for the referenced image, and returns that same wrong digest for the same image under DescribeModelPackage (cause 2) and across four fixtures — i.e. the value is stable and image-reference-scoped, but it is not the registry's digest.
Why: TrainingImageDigest is how a client pins an immutable image. Tooling compares it against the digest it obtained from ECR before it will launch a training job, and reproducibility/supply-chain checks pull `registry/repository@<digest>` built from this field. Against the emulator that comparison always fails and the pinned pull reference addresses a manifest no registry holds, so a client that enforces digest pinning cannot use a registered algorithm at all.
Fix: the digest resolution the CreateAlgorithm write path runs — services/service-com-amazonaws-sagemaker-sagemaker/src/state/image_digest.rs (`materialise_training_specification` -> `resolved_image_digest`), reached from src/ops/create_algorithm.rs — together with the ECR-registry lookup it depends on (`registry_image_digest`). Hypothesis: `registry_image_digest` resolves nothing for the reference the fixture names (the repository/tag is not found in the ECR state under the spelling the request uses, or the push that should have placed it there never recorded a manifest), so the last resort `derived_image_digest` — a SHA-256 over the reference string itself — is stored and reported as if it were the image's digest. Either the registry lookup must find the image the fixture pushed, or the fabricated fallback must not be reported in an ImageDigest member.
Traces: sagemaker-algorithm-duplicate-and-missing-errors#task#4 (representative); also sagemaker-algorithm-lifecycle#task#3.

Cause 2 of 2: DescribeModelPackage reports the same fabricated digest in InferenceSpecification.Containers[].ImageDigest (fixture sagemaker-model-package-create-and-verify, step task#3; cluster also covers sagemaker-model-package-metric-numeric-precision-preserved#task#4).
AWS: Smithy (same model): DescribeModelPackage output member InferenceSpecification carries Containers, a list of ModelPackageContainerDefinition whose Image -> ContainerImage ("The Amazon Elastic Container Registry (Amazon ECR) path where inference code is stored", and the member's doc states SageMaker supports both `registry/repository[:tag]` and `registry/repository[@digest]` path formats) and whose ImageDigest -> ImageDigest (@length 0..72, @pattern ^[Ss][Hh][Aa]256:[0-9a-fA-F]{64}$) — again the digest of that referenced image: fixed prefix `sha256:` plus the registry's 64 hex characters for the image the container's Image member points at. Status 200, no error.
Emulator: answers 200 with the identical wrong digest reported in cause 1 for the same image reference, instead of the digest the registry holds.
Why: a client pinning the inference container by digest — the standard way a model-package consumer guarantees the container it deploys is the one the package was registered against — gets a value that resolves to no manifest, so every digest comparison fails and a deploy that pulls by the reported digest pulls nothing.
Fix: the same shared resolution helper, reached on this path through `materialise_inference_specification`/`materialise_container` in services/service-com-amazonaws-sagemaker-sagemaker/src/state/image_digest.rs from src/ops/create_model_package.rs. Closing cause 1 alone does not close this one unless the fix is made in that shared helper and both read-backs are re-replayed. Note: the related clusters on DescribeTrainingJob/DescribeEndpoint ResolvedImage are owned by open issues 20261120T143955Z-sagemaker-training-job-and-endpoint-read-backs-lose.md and 20261122T164956Z-sagemaker-describetrainingjob-read-back-omits-algorithm-metric-definitions.md and are NOT re-filed here, but they are the same helper and a fixer should expect one root cause behind all of them.
Traces: sagemaker-model-package-create-and-verify#task#3 (representative); also sagemaker-model-package-metric-numeric-precision-preserved#task#4.

Not requirements, deliberately excluded: the literal digest values quoted in the evidence are this corpus's values filling the template. The requirement is that the reported digest be the content digest of the image the reference names — identical for the same image across operations and fixtures — not any one recording's hex string. No per-run clock value, request id or generated name forms part of either cause.
