# rds: 2 net-new causes — the emulated MySQL/MariaDB endpoint does not evaluate CURRENT_USER(): SHOW GRANTS FOR CURRENT_USER() is refused with 1141 and SELECT CURRENT_USER() with 1146 'no such table'

> _Note: this issue was identified against the code base at commit `29b314f84650008d56941927651d87480bd97baf`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
CreateDBInstance

## Description
This issue bundles 2 net-new root causes in the rds service, grounded in failing behavioural checks the suite marked neither ALREADY FILED nor OWNED by an open issue. Both live in the SQL engine served on a DB instance's published endpoint, and both are the same missing primitive seen on two statement paths: the function CURRENT_USER() is never evaluated. They are NOT the replay keys of the open issue 20261105T224225Z-rds-2-net-new-causes-the-mysql-endpoint.md (CREATE TABLE table options / @@GLOBAL variable reads refused with 1064) — the signatures here are 1141 ER_NONEXISTING_GRANT and 1146 ER_NO_SUCH_TABLE. A fixer must close BOTH causes below before submitting.

=== Cause 1 of 2: SHOW GRANTS FOR CURRENT_USER() is refused with 1141, CURRENT_USER taken as a literal account name ===
AWS: recorded behavior only (the engine surface is a MySQL/MariaDB contract, not a Smithy one). On an RDS for MySQL or RDS for MariaDB DB instance, `SHOW GRANTS FOR CURRENT_USER()` is accepted and is equivalent to `SHOW GRANTS`: it evaluates the CURRENT_USER() function to the session's authenticated account and returns that account's grant rows, e.g. `GRANT SELECT, INSERT, UPDATE, ... ON *.* TO `<master-user>`@`%``. The master user's privilege list is exactly what a client reads to establish that the RDS master user does NOT hold SUPER. No error is raised: the session's own account always exists. MySQL's error 1141 (ER_NONEXISTING_GRANT) exists only for an account that has no grants; its fixed text is "There is no such grant defined for user '<user>' on host '<host>'", with <user> and <host> taken from the account named in the statement.
Emulator: the statement is refused — pymysql.err.OperationalError: (1141, "There is no such grant defined for user 'CURRENT_USER' on host '%'"). The user part of the message is the literal string `CURRENT_USER`, i.e. the emulator parsed the function call `CURRENT_USER()` as an account name instead of evaluating it, then reported the (correctly worded) 1141 for that non-existent account. AWS raises no error at all here.
Why: a client cannot discover the privileges of the session it is on. Every privilege-boundary check a caller makes against RDS — proving the managed master user lacks SUPER before attempting SET GLOBAL, auditing what an application user was granted, tooling that prints `SHOW GRANTS FOR CURRENT_USER()` — fails with a hard error instead of returning rows, and the downstream behaviour (SET GLOBAL refused with 1227 "Access denied; you need (at least one of) the SUPER privilege(s) for this operation" while the DB parameter group changes the same variable successfully) is unreachable.
Fix: the engine data plane's MySQL/MariaDB statement handling — resolve CURRENT_USER / CURRENT_USER() (and USER()/SESSION_USER()) to the session's authenticated account in the `SHOW GRANTS FOR <account>` grammar, and serve grant rows for the master user from the account's stored privileges.
Traces: rds.mariadb-admin-user-lacks-super-set-global-rejected, rds.mysql-master-user-lacks-super-set-global-rejected.

=== Cause 2 of 2: SELECT CURRENT_USER() is refused with 1146 and a backing-store 'no such table: <user>@<host>' message ===
AWS: recorded behavior only. On an RDS for MySQL DB instance, `SELECT CURRENT_USER()` returns exactly one row with one string column holding the authenticated account as `<user>@<host>` — for an account created with `CREATE USER '<role>'@'%' IDENTIFIED WITH AWSAuthenticationPlugin AS 'RDS'` and logged in with an IAM auth token, that value is `<role>@%`. No error is raised. MySQL's error 1146 (ER_NO_SUCH_TABLE) is only for a missing table and its fixed text is "Table '<db>.<table>' doesn't exist".
Emulator: the statement is refused — pymysql.err.ProgrammingError: (1146, 'no such table: <user>@<host>') (observed as 'no such table: sim2real@127.0.0.1'). Two divergences compound: the function's value is spliced into the query as a bare identifier instead of being returned as a string literal, so the backing store resolves it as a table name; and the message is the backing store's own "no such table: X" text, not MySQL's "Table 'X.Y' doesn't exist" wording for errno 1146. The variable part of the emulator's message is the session account the engine computed — proving the account IS known, only unquoted.
Why: a client cannot ask the engine who it is authenticated as. This is the standard confirmation that an RDS IAM auth token logged in as exactly the user it names (and that a token minted for another user, an expired one, or one with a tampered signature was refused with 1045), so the whole IAM-database-authentication binding contract is unverifiable, and any application or connection-pool health check that selects CURRENT_USER()/USER() errors out.
Fix: the engine data plane's MySQL expression evaluation — CURRENT_USER()/USER()/SESSION_USER() must evaluate to the session account as a quoted string value in a select list; and errno 1146 must carry MySQL's "Table '<db>.<table>' doesn't exist" text rather than the backing store's message.
Traces: rds.mysql-iam-db-auth-token-binding-and-validity-enforced.

## Evidence
Cause 1: `SHOW GRANTS FOR CURRENT_USER()` on the published endpoint of an available RDS MariaDB instance (and of an RDS MySQL instance) answers pymysql.err.OperationalError: (1141, "There is no such grant defined for user 'CURRENT_USER' on host '%'"). Fixed text of 1141 is "There is no such grant defined for user '<user>' on host '<host>'"; here the <user> value is the un-evaluated literal `CURRENT_USER`. AWS returns the session account's grant rows (`GRANT ... ON *.* TO `<master-user>`@`%``) and raises nothing.
Cause 2: `SELECT CURRENT_USER()` on the published endpoint of an available RDS MySQL instance, on a session authenticated with an RDS IAM auth token, answers pymysql.err.ProgrammingError: (1146, 'no such table: <user>@<host>') — recorded as 'no such table: sim2real@127.0.0.1'. AWS returns [('<role>@%',)] for a token-authenticated AWSAuthenticationPlugin user, and MySQL's errno 1146 text is "Table '<db>.<table>' doesn't exist", never 'no such table: ...'.
