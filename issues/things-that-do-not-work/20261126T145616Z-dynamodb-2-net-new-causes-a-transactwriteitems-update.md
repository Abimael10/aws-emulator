# dynamodb: 2 net-new causes — a TransactWriteItems Update that grows a stored item past 409600 bytes is refused ValidationException instead of cancelled, and UpdateTable accepts deleting a still-CREATING vector index

> _Note: this issue was identified against the code base at commit `e1287cf409e72f27d41b5362b1ef9b2f278addc7`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
TransactWriteItems, UpdateTable

## Description
Two net-new root causes, both in dynamodb. Neither failing check is owned by an open issue (the replay report marks neither), and both touch areas where existing issues pull in other directions — those issues are named per cause so the fixer can reconcile rather than flip a switch.

Cause 1 of 2: a TransactWriteItems Update whose change grows an already-stored item one byte past the flat 409600-byte item-size ceiling is answered as a request-level ValidationException instead of the transaction-cancellation envelope.
Failing check: dynamodb.transact-write-items-put-and-update-accept-flat-409600-byte-item.

AWS:      Smithy: TransactWriteItems errors include TransactionCanceledException (errorKind client, httpError 400); its documentation lists as a cancel circumstance "An item size becomes too large (larger than 400 KB), or a local secondary index (LSI) becomes too large, or a similar validation error occurs because of changes made by the transaction". TransactionCanceledException models Message plus CancellationReasons (CancellationReasonList, @length min 1 max 100); CancellationReason models Code/Message/Item and is documented as "An ordered list of errors for each item in the request ... ordered according to the ordering of the TransactWriteItems request parameter. If no error occurred for the associated item an error with a Null code and Null message will be present." The error class is modeled; the texts are recorded behavior: HTTP 400, Error.Code TransactionCanceledException, Error.Message "Transaction cancelled, please refer cancellation reasons for specific reasons [<per-slot code list>]" — the sentence up to the bracket is fixed text and the bracketed list is a value derived from the request, one code per TransactItems slot in request order (a single offending slot yields "[ValidationError]"); the offending slot's CancellationReason carries Code "ValidationError" and Message "Item size to update has exceeded the maximum allowed size" (that whole sentence is fixed text, carrying no request value), and blameless slots carry Code "None" with no Message. The at-limit legs AWS accepts also hold: a TransactWriteItems Put of an item whose flat encoded size (attribute-name bytes plus value bytes, key included) is exactly 409600 bytes is stored and reads back whole, and an Update that grows a stored item to exactly 409600 bytes is accepted; only one byte beyond it fails, and the stored item must be left unchanged.
Emulator: the over-ceiling Update is answered HTTP 400 with Error.Code "ValidationException" and Error.Message "Item size to update has exceeded the maximum allowed size" — a flat request-level refusal, so no CancellationReasons list is produced and no per-slot verdict is available. The check's at-limit Put and at-limit Update legs pass, which isolates the divergence to the one-byte-over branch's error class and message.
Why:      a client cannot tell a cancelled transaction from a malformed request. TransactionCanceledException means the transaction was rejected as a unit and the per-slot CancellationReasons say which action to fix (and which siblings are blameless); ValidationException means the request itself is bad. An SDK transaction helper that catches TransactionCanceledException and unpacks CancellationReasons to attribute the failure to a TransactItems slot never enters that branch, and in a multi-action transaction cannot tell which item to shrink; code asserting on AWS's cancellation message never sees it.
Fix:      the TransactWriteItems handler's projected-item-size check and error-assembly path — growth that crosses the ceiling because of bytes the stored item already held must raise the transaction-cancellation error and build CancellationReasons over all TransactItems slots in request order (offending slot with Code/Message, others Code "None"), with the top-level Message's bracketed list derived from that same list. Note two open issues that pull the other way and do NOT carry this check's replay key: 20261124T164916Z-dynamodb-transactwriteitems-an-over-size-update-is-cancelled.md (three checks expecting the request-level ValidationException for an Update whose own payload cannot fit in an item at all) and 20261121T173852Z-dynamodb-transactwriteitems-an-over-size-update-is-refused.md (the wire corpus, same direction as this cause). The two surfaces must be reconciled over WHICH bytes cross the ceiling — a statement that asks for an impossible item refuses, growth over bytes already stored cancels — rather than by flipping a global switch, which closes one direction and reopens the other.
Traces:   dynamodb.transact-write-items-put-and-update-accept-flat-409600-byte-item.

Cause 2 of 2: UpdateTable with VectorIndexUpdates=[{Delete}] on a vector index that is still CREATING is accepted (HTTP 200) instead of refused, and the accepted call mutates the index state.
Failing check: dynamodb.vector-index-creating-blocks-table-and-index-delete.

AWS:      Smithy: UpdateTable models ResourceInUseException (errorKind client, httpError 400), documented as "The operation conflicts with the resource's availability. For example: ... You tried to delete a table currently in the CREATING state. ... You tried to update a resource that was already being updated."; VectorIndexDescription.IndexStatus enumerates CREATING/ACTIVE/DELETING and Backfilling is documented as "Specifies whether the index is currently backfilling". Recorded behavior for the message: an UpdateTable deleting a vector index that is still in the resource-allocation (CREATING) phase is refused HTTP 400 ResourceInUseException with Message "Attempt to change a resource which is still in use: Index creation is in resource allocation phase. Retry deletion during backfilling phase or when the index is active. Table: <TableName> Index: <IndexName>" — everything up to "Table:" is fixed text, and the table and index names are values taken from the request. The refusal must leave the index exactly as it was (still CREATING, still listed), and once the index settles ACTIVE its description carries no Backfilling key and DeleteTable then succeeds.
Emulator: the same UpdateTable returns HTTP 200 with a TableDescription (TableStatus UPDATING) whose VectorIndexes entry for the named index shows IndexStatus "DELETING" and Backfilling true — the delete is not gated on the index's CREATING state at all, it is applied, so no ResourceInUseException is raised and the index the caller must still be able to use is torn down. The sibling gate works: DeleteTable while that index is CREATING is already refused ResourceInUseException with AWS's text, so the gap is specific to the VectorIndexUpdates Delete path.
Why:      a client that handles index-lifecycle contention by catching ResourceInUseException and retrying "during backfilling phase or when the index is active" gets a success it must trust; the index it believed was being built is instead destroyed mid-allocation, so subsequent SearchVectors/DescribeTable see state AWS would never produce, and the emulator also reports an impossible combination (IndexStatus DELETING together with Backfilling true) for an index that never finished creating.
Fix:      the UpdateTable handler's VectorIndexUpdates Delete branch and the vector-index state machine it consults — reject the delete while the target index's status is CREATING with the modeled ResourceInUseException and the message above, before any state is staged, leaving the index description untouched. Related open issues, neither of which carries this check's replay key: 20261029T180026Z-dynamodb-global-tables-replica-auto-scaling-indexed-query.md and 20261119T104646Z-dynamodb-9-net-new-causes-vector-index-projection.md.
Traces:   dynamodb.vector-index-creating-blocks-table-and-index-delete.
