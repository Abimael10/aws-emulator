# Neptune DBCluster projection publishes the emulator's listener port instead of the engine's default 8182

> _Note: this issue was identified against the code base at commit `21e2cf74f286a150d85ee889b7043f42704cf062`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
CreateDBCluster

## Description
Every Neptune operation that projects a DBCluster renders it from one shared RDS-generic projection, and that projection now publishes the EMULATOR'S OWN data-listener port as the cluster's Port instead of the engine's default graph port. The same projection also still inverts the AutoMinorVersionUpgrade default, synthesises HostedZoneId per deployment instead of using the region's published Neptune hosted zone, and drops the cluster's CustomEndpoints. Related open issue 20261109T113627Z-neptune-cluster-reports-still-invert-autominorversionupgrade-synthesise-hostedzoneid.md describes the AutoMinorVersionUpgrade/HostedZoneId/CustomEndpoints members on these same fixture steps, and 20261103T175309Z-neptune-db-cluster-and-cluster-snapshot-reports-omit.md covers other members of the same projection; NEITHER owns these three clusters — this replay reports them with owned_by=[] and stub_path="" because the Port member is a new divergence in each key — so they are filed here. THIS ISSUE HAS 3 CAUSES — all three must be closed before submitting.

Cause 1 of 3: CreateDBCluster's DBCluster reports a non-engine Port, AutoMinorVersionUpgrade true and a synthesised HostedZoneId. AWS: CreateDBCluster returns CreateDBClusterResult.DBCluster (Smithy: CreateDBCluster -> CreateDBClusterResult.DBCluster -> com.amazonaws.neptune#DBCluster). Smithy: DBCluster.Port (IntegerOptional) doc 'Specifies the port that the database engine is listening on', and CreateDBClusterMessage.Port doc 'The port number on which the instances in the DB cluster accept connections. Default: 8182' — so when a create request does not name a port, the created cluster is reported with the Neptune engine default 8182, a FIXED engine constant, never a port chosen by the host process. Smithy: DBCluster.HostedZoneId doc 'Specifies the ID that Amazon Route 53 assigns when you create a hosted zone' — for this engine that id is the region's fixed Neptune hosted-zone constant, identical for every cluster in the region, not a per-deployment value. AutoMinorVersionUpgrade is NOT a member of neptune#DBCluster nor of CreateDBClusterMessage, so recorded behavior only: the front door reports a freshly created Neptune cluster with AutoMinorVersionUpgrade 'false'. Emulator: Port comes back the emulator's own ephemeral data-listener port, AutoMinorVersionUpgrade comes back 'true', and HostedZoneId comes back a per-deployment synthesised id. Why: a client that builds its Gremlin/openCypher/SPARQL connection string from DBCluster.Port (the documented way to learn where the engine listens) points at a port the engine does not serve on in AWS and whose value differs on every boot; a client reading AutoMinorVersionUpgrade concludes the cluster auto-upgrades when the service never said so; a client that builds a Route 53 alias or DNS-failover record from HostedZoneId builds it against a zone that does not exist in the region. Fix: the CreateDBCluster handler's DBCluster projection and the cluster state it writes — the engine-default port constant, the per-region hosted-zone constant and the AutoMinorVersionUpgrade default must all come from Neptune engine metadata, never from the serving process's bound socket. Traces: neptune-db-cluster-lifecycle-and-custom-endpoint#task#1.

Cause 2 of 3: DescribeDBClusters confirms cause 1's three wrong members on the read-back path. AWS: DescribeDBClusters returns DBClusterMessage.DBClusters, a list of the same neptune#DBCluster (Smithy: DescribeDBClusters -> DBClusterMessage, paginated items=DBClusters). The same rules hold on read-back: Port is the engine default the cluster was created with (8182 when the create named no port), HostedZoneId is the region's fixed Neptune hosted-zone id, and (recorded behavior only) AutoMinorVersionUpgrade is 'false'. Emulator: the describe echoes the identical wrong trio — the emulator's listener port for Port, 'true' for AutoMinorVersionUpgrade, and the synthesised HostedZoneId. Why: describe is the call a client polls after create/modify to confirm what the service actually stored, so the wrong values are not merely emitted once, they are confirmed; a client that reconciles its own record of the cluster against the service never converges on AWS's values, and a connection-string builder that re-reads the port on reconnect gets a different wrong port after each emulator restart. Fix: the shared DBCluster projection the DescribeDBClusters handler uses (the same projection as causes 1 and 3) and the cluster state it reads. Traces: neptune-db-cluster-lifecycle-and-custom-endpoint#task#2.

Cause 3 of 3: ModifyDBCluster loses the cluster's custom endpoints in addition to repeating the three defects above. AWS: ModifyDBCluster returns the modified cluster as a neptune#DBCluster (Smithy: ModifyDBCluster -> ModifyDBClusterResult.DBCluster). CustomEndpoints is not a modeled member of neptune#DBCluster, so recorded behavior only: once a custom endpoint has been created against the cluster, the cluster report carries CustomEndpoints as a LIST with one member per custom endpoint, each member that endpoint's DNS name. That hostname is derived from the endpoint identifier, the cluster's resource token and the region, so only the member's PRESENCE, list shape and count are the requirement — never a recorded hostname. Emulator: CustomEndpoints comes back as an empty scalar rather than a one-member list (type_mismatch: expected a list with one member, got ''), while Port is the emulator's listener port, AutoMinorVersionUpgrade is 'true' and HostedZoneId is synthesised, exactly as in causes 1 and 2. Why: this is a loss of state the emulator itself created — a client that creates a custom endpoint and then reads the cluster back to confirm it, or that enumerates a cluster's endpoints to choose one to connect through, is told the cluster has no custom endpoints at all. Fix: the ModifyDBCluster handler's DBCluster projection and the cluster state that records custom endpoints created against the cluster. Traces: neptune-db-cluster-lifecycle-and-custom-endpoint#task#9.

Not claimed as a requirement in any cause: the same clusters report Endpoint/ReaderEndpoint hostnames that differ only in the generated per-cluster resource token, and the recorded HostedZoneId/CustomEndpoints literals are example values — the requirements are 'the region's fixed Neptune hosted-zone id' and 'a list with one member per custom endpoint', not the recorded strings.

## Note added while fixing 20261109T113928Z-neptunedata-is-still-entirely-unreachable-the-neptune-db.md (the Port cause only)

The Port this report asks for — the engine default 8182, the same value on every boot — and the requirement of that CRITICAL report — that `https://<DBCluster.Endpoint>:<DBCluster.Port>` be an address this emulator ANSWERS the neptunedata graph API on, which is the only address any of its 43 data-plane operations can be reached at — cannot both hold in one process. The core assigns the port of every listener a service opens: `Listeners::http`, `Listeners::tcp` and `Listeners::tcp_plaintext` take no port argument, and the binds behind them use port 0 or walk the operator's `EMULATOR_LISTENER_PORT_RANGE` (`vendor/server/src/listeners.rs`), so nothing a service can do makes this emulator answer on a model-fixed 8182 — and two clusters of one process could not both hold that port in any case. AWS satisfies both at once because it owns a DNS name per cluster on the one engine port.

So while that holds, the shared DBCluster/Endpoint projection of the RDS front door, which serves this control plane's model too (`services/service-com-amazonaws-rds-amazonrdsv19/src/state/clusters.rs`, `.../instances.rs`, `.../api_plane_address.rs`), publishes the address the plane is actually served at — host AND port — which is the reading `services/common/src/data_plane_addressing.rs` states for every served data plane and the one this crate already applies to the engines whose native wire it serves. The port the create configured stays on the cluster record, is what the port-range refusal and `ModifyDBCluster` read, and is what a cluster whose data plane this emulator serves in no way at all publishes. This report's other two members (HostedZoneId, AutoMinorVersionUpgrade) and the CustomEndpoints list are untouched by that and still stand as filed.

The core change this report's Port value needs first: a listener API that binds the port its caller asks for (for example `Listeners::http_on(port, handler, policy)`), so a resource whose published connection endpoint must report a model-fixed port can be served on exactly that port.
