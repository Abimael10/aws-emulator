# ses__sesv2: 4 net-new causes — the account-wide sending flag is two private copies instead of one shared switch, and three v1/v2 refusals carry the wrong code or wording

> _Note: this issue was identified against the code base at commit `2b493b29800d7a854b42f905b4db8bab42375d7a`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
PutAccountSendingAttributes

## Description
Four net-new behavioral root causes where the SES v1 and SESv2 surfaces must be one service. None of the seven failing checks below was marked ALREADY FILED or OWNED by the replay report.

Cause 1 of 4: the account-wide sending switch is stored twice — once per API version — so a write through one API is invisible to the other, and the v1 data plane never sees a v2 pause.
AWS: Smithy models the same account singleton on both surfaces: com.amazonaws.ses#UpdateAccountSendingEnabled {Enabled} / GetAccountSendingEnabled -> {Enabled}, and com.amazonaws.sesv2#PutAccountSendingAttributes (PUT /v2/email/account/sending, {SendingEnabled}) / GetAccount (GET /v2/email/account) -> {SendingEnabled, ...}. SES v1 and SESv2 are two APIs over ONE service: there is exactly one account-level sending flag per account per Region, so v1 UpdateAccountSendingEnabled(Enabled=X) is read back by v2 GetAccount.SendingEnabled=X and v2 PutAccountSendingAttributes(SendingEnabled=X) is read back by v1 GetAccountSendingEnabled.Enabled=X. The same flag gates the data plane: with sending enabled, a v1 SendEmail from an unverified source is refused MessageRejected "Email address is not verified. The following identities failed the check in region <REGION>: <source>" (fixed text plus the Region and the source address from the request); once the account flag is false — whichever API wrote it — the identical send is refused AccountSendingPausedException "Sending is paused for this account." (fixed text, no interpolation), and re-enabling reverts it to the identity-gate refusal.
Emulator: each crate keeps its own account record. The v1 write lands at services/service-com-amazonaws-ses-simpleemailservice/src/ops/update_account_sending_enabled.rs line 163 (`state.lock().account.sending_enabled = input.enabled`, on the ses crate's store) and the v2 write at services/service-com-amazonaws-sesv2-simpleemailservice-v2/src/ops/put_account_sending_attributes.rs line 158 (`store.account.sending_enabled = input.sending_enabled`, on the sesv2 crate's store). Consequently a v1 write is never observed by v2 GetAccount (polled 30-60 s, last observation still True) and a v2 write is never observed by v1 GetAccountSendingEnabled (still True), and the v1 SendEmail refusal never changes from the identity gate to the account pause after a v2 disable.
Why: the account sending pause is the emergency stop for an account's mail flow. A client that pauses sending through one API and verifies it (or has its sends gated) through the other sees the pause silently ignored: mail keeps being accepted after an operator pauses the account, and automation that polls the other API's read to confirm the pause never converges. It also makes the AccountSendingPausedException class unreachable from a v2-authored pause.
Fix: one shared account record for the SES service, read and written by both crates (the ses crate's `crate::state::service_state(...).account` and the sesv2 crate's equivalent must resolve to the same store), so both the v1 and v2 readers and the send-path gate consult a single `account.sending_enabled`.
Traces: ses__sesv2.account-sending-switch-is-shared-between-v1-and-v2, ses__sesv2.account-sending-toggle-crosses-api-versions, ses__sesv2.put-account-sending-attributes-disable-reroutes-send-email-refusal-to-account-pause, ses__sesv2.v1-v2-shared-store-account-config-set-and-identity-policy (this last one spends its whole 60 s budget on the first cross-API read and times out).

Cause 2 of 4: v1 UpdateConfigurationSetSendingEnabled on a configuration set that does not exist answers the not-found class instead of AWS's update-conflict refusal.
AWS: Smithy (com.amazonaws.ses#UpdateConfigurationSetSendingEnabled) takes {ConfigurationSetName required, Enabled required} and models only ConfigurationSetDoesNotExistException (awsQuery code ConfigurationSetDoesNotExist, 400), but that is not what the service answers for an unknown set: recorded behavior is HTTP 400 code `Throttling`, message "Update conflict when updating configuration set <NAME>." — fixed text around the configuration-set name copied from the request. The v2 counterpart for the same unknown set answers NotFoundException "Configuration set <NAME> does not exist.", and v1 DescribeConfigurationSet answers ConfigurationSetDoesNotExist with that same sentence, so the three refusals deliberately differ by operation.
Emulator: HTTP 400 code `ConfigurationSetDoesNotExist`, message "Configuration set <NAME> does not exist." — the describe-path refusal reused for the v1 update path.
Why: Throttling is retryable and ConfigurationSetDoesNotExist is terminal, so a client's retry/abandon decision inverts; and a caller distinguishing "the set is gone" from "the write conflicted" cannot, since every v1 toggle against an unknown set now reads as a hard not-found. (Same root cause as the reputation-metrics toggle filed in the sibling `ses` issue of this sweep; both v1 configuration-set toggles share the refusal path.)
Fix: the unknown-set branch of services/service-com-amazonaws-ses-simpleemailservice/src/ops/update_configuration_set_sending_enabled.rs — answer the awsQuery Throttling error with AWS's update-conflict sentence naming the requested set, leaving the v2 NotFoundException and the v1 describe refusal as they are.
Traces: ses__sesv2.configuration-set-sending-toggle-unknown-set-v1-v2.

Cause 3 of 4: SESv2 CreateEmailIdentity's AlreadyExistsException sentence is re-worded.
AWS: Smithy (com.amazonaws.sesv2#CreateEmailIdentity, POST /v2/email/identities) models AlreadyExistsException 400 among its errors. Recorded behavior for an address SES is already verifying — including one started through v1 VerifyEmailIdentity, since the identity store is shared — is HTTP 400 code `AlreadyExistsException` with the message "Email identity <ADDRESS> already exist." — fixed text "Email identity " + the EmailIdentity value from the request + " already exist." (AWS's wording is the ungrammatical "already exist."). The refusal leaves the pending identity untouched: v1 GetIdentityVerificationAttributes still reports VerificationStatus=Pending and v2 GetEmailIdentity still reports PENDING.
Emulator: the same code, but the message is "Email identity <ADDRESS> already exists." — "exists" where AWS writes "exist".
Why: the error code matches but the message does not, so message-matching clients and golden-output comparisons diverge; this is the only thing separating the emulator from AWS on this path (the cross-API detection itself works).
Fix: the duplicate-identity refusal message in services/service-com-amazonaws-sesv2-simpleemailservice-v2/src/ops/create_email_identity.rs — use AWS's exact sentence "Email identity <identity> already exist."
Traces: ses__sesv2.create-email-identity-rejects-one-verifying-through-v1.

Cause 4 of 4: v1 PutIdentityPolicy refuses a policy for an identity that was never created with an emulator-authored ValidationException instead of AWS's InvalidParameterValue sentence.
AWS: Smithy (com.amazonaws.ses#PutIdentityPolicy) takes {Identity required, PolicyName required @length 1-64, Policy required @length min 1} and models only InvalidPolicyException (awsQuery code InvalidPolicy, 400); recorded behavior for an Identity that is not a verified email address or domain of the account is HTTP 400 code `InvalidParameterValue` with the fixed message "Invalid identity. Must be a verified email address or domain." — the sentence carries NO interpolated value, it never names the identity. The refusal stores nothing (v1 ListIdentityPolicies for that identity answers an empty PolicyNames), and the v2 counterpart CreateEmailIdentityPolicy answers NotFoundException "Email identity <ADDRESS> does not exist." for the same identity.
Emulator: HTTP code `ValidationException` with the message 'Identity "<ADDRESS>" is not a verified identity of this account; verify it before attaching a sending authorization policy to it' — an emulator-authored sentence that interpolates the identity and uses an error class the v1 awsQuery surface does not model at all.
Why: ValidationException is not in this operation's (or SES v1's) error vocabulary, so a client branching on InvalidParameterValue — the code AWS returns for every invalid-identity refusal on the v1 sending-authorization APIs — never matches, and botocore surfaces an unmodeled class it cannot map to a typed exception.
Fix: the identity gate in services/service-com-amazonaws-ses-simpleemailservice/src/ops/put_identity_policy.rs — refuse with the awsQuery InvalidParameterValue error carrying exactly "Invalid identity. Must be a verified email address or domain." and store nothing.
Traces: ses__sesv2.identity-policy-refused-by-both-apis-for-an-identity-never-created.
