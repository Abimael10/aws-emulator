=== Cause 1 of 3: the member-constraint clause list of a list-typed input member now always ends with ", Member must not be null", including on the members whose recorded AWS refusal carries ONLY the pattern clause (DescribeDirectories$directoryIds, CreateConditionalForwarder$dnsIpAddrs). Failing checks: ds.describe-directories-id-outside-the-d-hex10-pattern-rejected-validation, ds.create-conditional-forwarder-invalid-dns-ip-rejected.

AWS: recorded behavior only for the sentence text (the model states the constraints, not the message). A @pattern violation on an entry of a list-typed input member is refused HTTP 400 with error code ValidationException and the message `<n> validation error(s) detected: Value '[<entries joined with ", ">]' at '<memberPath>' failed to satisfy constraint: Member must satisfy constraint: [<clause>[, <clause>...]]`. Fixed text is everything outside the variable slots; the variable slots are `<n>` (number of detected violations), the joined request entries, `<memberPath>` (the lowercase-initial input-member path) and the published regular expression. The clause SET is per member and is NOT a global property of "dense list": for DescribeDirectories.DirectoryIds the recorded refusal is `... at 'directoryIds' failed to satisfy constraint: Member must satisfy constraint: [Member must satisfy regular expression pattern: ^d-[0-9a-f]{10}$]` and for CreateConditionalForwarder.DnsIpAddrs it is `... at 'dnsIpAddrs' failed to satisfy constraint: Member must satisfy constraint: [Member must satisfy regular expression pattern: ^(?:(?:25[0-5]|2[0-4][0-9]|[01]?[0-9][0-9]?)\.){3}(?:25[0-5]|2[0-4][0-9]|[01]?[0-9][0-9]?)$]` — one clause only, no `, Member must not be null` — while the recording for CreateMicrosoftAD's VpcSettings.SubnetIds DOES carry both clauses in the order `[<pattern>, Member must not be null]`. Smithy (services/service-com-amazonaws-directoryservice-directoryservice-20150416/smithy-model/com-amazonaws-directoryservice-directoryservice-20150416.json): `DirectoryIds` is a list (no @sparse) whose member targets `DirectoryId` @pattern `^d-[0-9a-f]{10}$`; `DnsIpAddrs` is a list (no @sparse) whose member targets `IpAddr` with the dotted-quad @pattern, and `CreateConditionalForwarderRequest$DnsIpAddrs` is OPTIONAL with an added default `[]`; `DescribeDirectoriesRequest$DirectoryIds` is OPTIONAL; by contrast `DirectoryVpcSettings$SubnetIds` (targeting `SubnetIds`, member @pattern `^(subnet-[0-9a-f]{8}|subnet-[0-9a-f]{17})$`) is @required inside a @required structure member. Hypothesis: AWS appends the non-null clause only where the list member itself is required (SubnetIds), not for an optional/defaulted list (directoryIds, dnsIpAddrs) — the model states no rule, so what is REQUIRED here is simply that the clause set reproduce AWS per member. Error: ValidationException, HTTP 400, raised at the front door before the handler.

Emulator: HTTP 400 ValidationException with the right code, count, quoted entries, member path and anchored pattern, but the clause list is rendered with the non-null clause appended unconditionally: `... at 'directoryIds' failed to satisfy constraint: Member must satisfy constraint: [Member must satisfy regular expression pattern: ^d-[0-9a-f]{10}$, Member must not be null]` and `... at 'dnsIpAddrs' failed to satisfy constraint: Member must satisfy constraint: [Member must satisfy regular expression pattern: ^(?:(?:25[0-5]|2[0-4][0-9]|[01]?[0-9][0-9]?)\.){3}(?:25[0-5]|2[0-4][0-9]|[01]?[0-9][0-9]?)$, Member must not be null]`. The clause is now correct for vpcSettings.subnetIds (the pairwise leg of ds.create-microsoft-ad-simultaneous-modeled-pattern-violations-ordered-in-one-validation-exception, which open issue 20261115T013046Z-ds-createmicrosoftad-s-validationexception-for-a-list-member.md was filed on, passes in this run), so the clause has been added as ONE global switch over every dense list instead of per member. That open issue asks for the clause on subnetIds and does not cover these two members or carry either of these checks' replay keys; landing them together means making the renderer reproduce AWS's clause set per member rather than flipping the global switch the other way.

Why: the status, the error code and the message are all requirements of this error class. A client, SDK conformance test or CLI user that asserts on AWS's refusal sentence for a malformed directory id or DNS IP never matches, and anything that parses the bracketed clause list to learn what constraints a member carries is told directoryIds/dnsIpAddrs forbid null entries where AWS advertises only the pattern. Because the clause is emitted structurally, every ds operation validating an optional list of pattern-constrained strings diverges the same way, not just these two.

Fix: this crate's shared request-constraint validation layer — the centralized deserialize -> validate -> handle validate step that formats a constraint violation into the ValidationException message (the renderer feeding `crate::scaffolded::Scaffolded::validation`), specifically the branch that builds a collection member's `Member must satisfy constraint: [...]` clause list. No operation handler is involved; neither handler is reached.

=== Cause 2 of 3: when all four modeled-@pattern members of CreateMicrosoftAD are simultaneously invalid, the aggregated ValidationException loses the @sensitive password violation entirely (count 3, not 4) and emits the remaining three in the wrong order. Failing check: ds.create-microsoft-ad-simultaneous-modeled-pattern-violations-ordered-in-one-validation-exception.

AWS: recorded behavior only for the sentence text. CreateMicrosoftAD aggregates EVERY simultaneous modeled-pattern violation into ONE ValidationException (HTTP 400) in one fixed order independent of which members break: password, then vpcSettings.vpcId, then vpcSettings.subnetIds, then name — `4 validation errors detected: Value at 'password' failed to satisfy constraint: Member must satisfy regular expression pattern: <password pattern>; Value '<vpcId>' at 'vpcSettings.vpcId' failed to satisfy constraint: Member must satisfy regular expression pattern: ^(vpc-[0-9a-f]{8}|vpc-[0-9a-f]{17})$; Value '[<subnet entries>]' at 'vpcSettings.subnetIds' failed to satisfy constraint: Member must satisfy constraint: [Member must satisfy regular expression pattern: ^(subnet-[0-9a-f]{8}|subnet-[0-9a-f]{17})$, Member must not be null]; Value '<name>' at 'name' failed to satisfy constraint: Member must satisfy regular expression pattern: ^([a-zA-Z0-9]+[\\.-])+([a-zA-Z0-9])+$`. Fixed text is everything outside the variable slots (`<n>`, the quoted request values, the member paths, the patterns); because `CreateMicrosoftADRequest$Password` is @sensitive its violation elides the value and reads `Value at 'password' ...`. Smithy: Name @pattern `^([a-zA-Z0-9]+[\\.-])+([a-zA-Z0-9])+$`, Password @required @sensitive with the multi-class look-ahead @pattern, VpcSettings -> DirectoryVpcSettings{VpcId @pattern, SubnetIds list @pattern}; error ValidationException, HTTP 400.

Emulator: the same request answers `3 validation errors detected: Value 'bad-vpc-id' at 'vpcSettings.vpcId' ...; Value '<name>' at 'name' ...; Value '[bad-subnet-1, bad-subnet-2]' at 'vpcSettings.subnetIds' ...` — the password violation is absent (so the count is 3 where AWS counts 4) and name is emitted BEFORE subnetIds where AWS emits subnetIds before name. The two pairwise legs of the same check pass (password+name aggregates in the right order, vpcId+subnetIds aggregates in the right order), so the divergence is specifically in composing MORE THAN TWO violations: a violation is dropped and the per-pair orders are not interleaved into AWS's one fixed four-way order.

Why: a client is told only three of the four things wrong with its request, so it fixes those, resubmits, and is refused again for a password it was never told about — and the count in the sentence contradicts the list that follows it. Any test or tool that asserts AWS's refusal sentence, or that enumerates violations to present them to a user, diverges on every multi-member bad request.

Fix: the same shared validate step as Cause 1 — the violation COLLECTION and ORDERING stage that gathers constraint violations across all input members before rendering (the path feeding `crate::scaffolded::Scaffolded::validation`), not the per-violation renderer and not ops/create_microsoft_ad.rs: the handler is never reached. It must collect every violating member (including @sensitive ones, whose value is elided but whose violation is still reported) and emit them in AWS's fixed order password, vpcSettings.vpcId, vpcSettings.subnetIds, name.

=== Cause 3 of 3: the two-directory trust create/verify/delete flow reaches NO verdict — it is killed at the suite's 60 s per-check budget while polling clock-owed transitions, so none of the trust state machine's states or refusal texts is graded. Failing check: ds.e2e-trust-create-verify-delete-flow.

AWS: recorded behavior only. This is a poll-and-wait flow: on AWS a Managed Microsoft AD stays Requested/Creating for tens of minutes and trust transitions take minutes, so a client polls at human intervals (20 s for DescribeDirectories, 15 s for DescribeTrusts here) and eventually reads the settled value. The contract graded is: two Managed Microsoft AD directories reach Stage=Active and report non-empty DnsIpAddrs; CreateTrust on each side settles TrustState in {Created, Verified}; VerifyTrust then drives the trust to Verified; DeleteTrust makes it leave DescribeTrusts (or read TrustState=Deleted, or be refused EntityDoesNotExistException); and a SECOND DeleteTrust on the same id is refused HTTP 400 EntityDoesNotExistException with the message `Trust: <trust id> does not exist : RequestId: <rid>` — fixed text `Trust: ` and ` does not exist : RequestId: `, with the trust id taken from the request and the request id from that call.

Emulator: the check ends "Check timed out after 60.0s" with no exception frame and no response divergence — nothing was asserted. Hypothesis (mechanism, as already documented in this crate by the two open issues named below): every clock-owed transition is materialised only by a LATER call, so a client probing right after the call that starts a transition always reads the transient value and learns the settled one a full poll interval later, one interval paid per transition. This flow pays that per directory (two of them, 20 s interval), per trust settle (15 s), per verify (15 s) and per delete (15 s), which exceeds the 60 s ceiling before any assertion is reached.

Why: the whole ds trust plane is ungraded by this suite for this flow — the Created/Verified transitions, VerifyTrust's effect, the delete's disappearance and the double-delete refusal class and sentence. A regression in any of them is invisible, and a real client polling at these intervals reads a transient value where AWS has settled.

Fix: this crate's clock-owed transition spans and the chains built on them (services/service-com-amazonaws-directoryservice-directoryservice-20150416/src/state.rs TRANSITION_SPAN / DIRECTORY_BUILD_SPAN / directory_active_at, the trust transitions advance_clock materialises, and src/state/directory_deletion.rs's teardown chain) — a settled value must be reachable by a client polling at the intervals this flow uses, within the per-check budget, WITHOUT erasing the modeled transient values. Related open issues that do NOT own this failure and carry none of its replay keys: 20261112T080746Z-ds-2-net-new-causes-registereventtopic-s-topicname.md (its Cause 2 is the same mechanism on the single-directory ds.trust-lifecycle-create-verify-delete flow) and 20261113T164150Z-ds-3-net-new-causes-the-msad-stage.md (the MSAD stage timing). This check creates TWO directories plus security-group and conditional-forwarder setup before any trust call, so it is a distinct, strictly larger budget path.

Traces: ds.describe-directories-id-outside-the-d-hex10-pattern-rejected-validation, ds.create-conditional-forwarder-invalid-dns-ip-rejected (Cause 1); ds.create-microsoft-ad-simultaneous-modeled-pattern-violations-ordered-in-one-validation-exception (Cause 2); ds.e2e-trust-create-verify-delete-flow (Cause 3).
