# redshift: a batch sub-statement's RedshiftQueryId is forced to 0, so DescribeStatement never names the cluster query a batch statement ran as

> _Note: this issue was identified against the code base at commit `28e13556b346bec2a9903044f83d66021b33e840`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
DescribeStatement

## Description
Cause 1 of 1: Every statement of a BatchExecuteStatement submission reports RedshiftQueryId = 0, so a batch's statements cannot be correlated with the cluster's own query log and are indistinguishable from one another.

AWS: Smithy (services/service-com-amazonaws-redshiftdata-redshiftdata/smithy-model/com-amazonaws-redshiftdata-redshiftdata.json) models SubStatementData.RedshiftQueryId as a Long with default 0 and documents it as "The identifier of the query generated by Amazon Redshift. These identifiers are also available in the query_id column of the SYS_QUERY_HISTORY system view." The default 0 is the absent-value marker for a statement the warehouse recorded no query for (one that has not run, or a batch submission itself, which is not a query). A batch sub-statement that has FINISHED on the cluster HAS run as a query: Amazon Redshift logs one query per statement of the batch, each with its own query_id in SYS_QUERY_HISTORY / stl_query / stl_wlm_query, and DescribeStatement reports that id in the matching SubStatements[] entry. SubStatementData.Id's own documentation ("<uuid>:2 has a suffix of :2 that indicates the second SQL statement of a batch query") presumes exactly this per-statement identity. Recorded behavior confirms it: the suite's check reads the last sub-statement's RedshiftQueryId and then uses it as a `query` value in `SELECT query, service_class ... FROM stl_wlm_query WHERE query IN (<tagged>, <untagged>)`, which is only expressible because AWS returns a real, non-zero, per-statement query id there.

Emulator: the sub-statement's RedshiftQueryId is always the modelled default 0. The engine actually mints and records a query id for each batch statement (state.rs run_statement calls database.system.next_ids() and effects.bound.record_query(query), and records a stl_query/stl_wlm_query row under it), and then the batch runner explicitly throws that id away for every statement before the Execution is reported, on the stated premise that "the Data API leaves SubStatementData.RedshiftQueryId at its modelled default for the statements of a batch submission". That premise is wrong. Observed in replay: the labelled batch ["SET query_group TO 'sim2real'", "SELECT count(*) FROM stv_recents"] FINISHED and its last sub-statement reported RedshiftQueryId 0, while the same SELECT submitted through ExecuteStatement reported a real id (3), producing `AssertionError: the two statements must be two distinct cluster queries, got 0 and 3`. Because 0 is also the absent marker, a client cannot tell "not recorded" from "recorded as query 0", and all N statements of a batch collapse onto the same value.

Why: a client that reads a batch's SubStatements to find which cluster queries its statements ran as gets 0 for all of them. Every downstream join on query_id breaks: WLM/service-class inspection (stl_wlm_query, stv_wlm_query_state), query-history lookups (SYS_QUERY_HISTORY, stl_query), per-statement cancel/diagnosis, and any `WHERE query IN (...)` filter built from the response either returns nothing or silently selects the wrong row. Session-scoped behavior established inside a batch (a `SET query_group` and the statement it labels must be one session, which only BatchExecuteStatement expresses) therefore becomes unobservable through the API, even though the emulator's own system tables hold the right rows.

Fix: the batch execution path of the Redshift Data API state/engine — the per-statement Execution reporting in run_batch_on (services/service-com-amazonaws-redshiftdata-redshiftdata/src/state.rs), which must keep the query id the database gave each statement instead of overwriting it with NO_WAREHOUSE_QUERY_ID; the DescribeStatement serializer path (src/ops/describe_statement.rs sub_statement_data -> Statement::redshift_query_id) should then report each sub-statement's own recorded id, while the BATCH record itself correctly keeps 0 because a batch is not a query. The reported value must be the same id the statement's row carries in the cluster's query log, so `SubStatements[n].RedshiftQueryId` and `stl_wlm_query.query` / SYS_QUERY_HISTORY.query_id name one query; the ids are per-run values, not fixed constants.

Traces: redshift.redshift-wlm-queue-assignment-is-observable-in-the-cluster-system-tables (asserts the labelled batch statement and the unlabelled single statement are two distinct cluster queries; fails with tagged=0).

## Evidence
Failing check: redshift.redshift-wlm-queue-assignment-is-observable-in-the-cluster-system-tables

Expected (AWS): after a BatchExecuteStatement of ["SET query_group TO 'sim2real'", "SELECT count(*) FROM stv_recents"] reaches FINISHED, DescribeStatement(Id=<batch id>) returns SubStatements[1].RedshiftQueryId = the non-zero query_id Amazon Redshift recorded for that SELECT (visible as stl_wlm_query.query / SYS_QUERY_HISTORY.query_id), distinct from the id of any other statement, including the separately submitted ExecuteStatement of the same SQL.

The id is minted and logged a few lines earlier in run_statement (database.system.next_ids(); effects.bound.record_query(query); database.system.record_query(QueryEntry{ query, ... })), so the data exists and is only discarded on the reporting path. src/ops/describe_statement.rs:302-316 (sub_statement_data) then serializes that zero into SubStatementData.RedshiftQueryId.

Model: SubStatementData.RedshiftQueryId -> Long, default 0, doc "The identifier of the query generated by Amazon Redshift. These identifiers are also available in the query_id column of the SYS_QUERY_HISTORY system view."; SubStatementData.Id doc describes the ":<n>" suffix as addressing "the second SQL statement of a batch query".

## Steps to Reproduce
1. Create a cluster parameter group with wlm_json_configuration set to two manual WLM queues (one matching query_group 'sim2real', one default), create a single-node cluster with that parameter group attached, and wait for the cluster to be available and the group to report ParameterApplyStatus=in-sync.
2. redshift-data BatchExecuteStatement(ClusterIdentifier=<cluster>, Database=devdb, DbUser=adminuser, Sqls=["SET query_group TO 'sim2real'", "SELECT count(*) FROM stv_recents"]).
3. Poll DescribeStatement(Id=<batch id>) until Status=FINISHED, then read SubStatements[-1].RedshiftQueryId.
   -> emulator returns 0; AWS returns the non-zero query_id the cluster recorded for that SELECT.
4. redshift-data ExecuteStatement(ClusterIdentifier=<cluster>, Database=devdb, DbUser=adminuser, Sql="SELECT count(*) FROM stv_recents"); poll to FINISHED and read RedshiftQueryId -> a real non-zero id (e.g. 3), showing the single-statement path does assign one.
5. Attempt to use the two ids: ExecuteStatement("SELECT query, service_class FROM stl_wlm_query WHERE query IN (<tagged>, <untagged>) ORDER BY query"). With the batch id reported as 0 the row for the batch statement can never be selected, so WLM routing is unobservable through the API even though the emulator's system tables hold the row.
