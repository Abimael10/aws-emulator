# rds__rds-data__secretsmanager: 2 net-new causes — exact-numeric columns (NUMERIC/DECIMAL, BIGINT UNSIGNED) are stored as binary floating point and silently rounded, and BLOB bytes are corrupted by a UTF-8 round trip

> _Note: this issue was identified against the code base at commit `9f15073fe42cc4661a8a99924cff5eec339d1b59`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
ExecuteStatement

## Description
Two net-new root causes in how the shared Aurora engine stores and returns values on the native wire. Both are silent data corruption: every call succeeds, and the bytes come back different from the bytes written. Reached only now that a native session can connect (the still-open 20261121T083106Z-rds-rds-data-secretsmanager-every-cross-surface-data.md holds the superseded PublishedUrlRejected keys for these checks and covers neither cause).

Cause 1 of 2: exact-numeric column types are backed by binary floating point, so values are rounded to double precision on write and read back changed, on both engines.
AWS: recorded behavior only for the wire; the engines' type rules are the requirement. PostgreSQL NUMERIC(p,s) and MySQL DECIMAL(p,s) are EXACT numerics — a value that fits the declared precision and scale round-trips digit for digit — and MySQL BIGINT UNSIGNED is an exact 64-bit unsigned integer with maximum 18446744073709551615. So a native session that inserts and re-selects gets back exactly what it wrote: NUMERIC(20,5) holding 123456789012345.12345 returns Decimal('123456789012345.12345'); DECIMAL(38,9) holding 12345678901234567890123456789.123456789 returns that same 38-digit value; BIGINT UNSIGNED holding 18446744073709551615 returns the integer 18446744073709551615, not a float. A value exceeding the declared precision is REFUSED (MySQL 1264 ER_WARN_DATA_OUT_OF_RANGE / PostgreSQL 22003 numeric_field_overflow), never silently rounded.
Emulator: every INSERT succeeds and the re-read returns a double. On aurora-postgresql, NUMERIC(20,5) 123456789012345.12345 reads back as Decimal('123456789012345.13') — 17 significant digits, the IEEE-754 double nearest the written value, re-rendered with 2 decimals. On aurora-mysql, DECIMAL(38,9) 12345678901234567890123456789.123456789 reads back as Decimal('12345678901234568000000000000') and BIGINT UNSIGNED 18446744073709551615 reads back as the float 1.8446744073709552e+19 (a Python float, not an int). Other columns in the same rows are fine (DATETIME(6) microseconds, JSON/JSONB, BOOLEAN, TIMESTAMPTZ, NULL and the small BIGINT 9007199254740993 all survive), which localises the cause to the exact-numeric types. The specific literals are the checks' values; the requirement is that any value within the declared precision/scale is returned unchanged and that the declared type's width is honoured, not a double's 53-bit mantissa.
Why: this is the classic reason money and identifiers are declared DECIMAL. A client writing a balance, a price or a 64-bit unsigned id through a driver reads back a different number with no error anywhere, and the two surfaces then disagree about the same row; ledgers silently fail to balance and ids collide. It also makes the modelled follow-on behavior unreachable: the Data API is supposed to refuse its own read of a BIGINT UNSIGNED above signed-Long range with DatabaseErrorException (Smithy: rds-data ExecuteStatement -> DatabaseErrorException, client, HTTP 400) and the message 'Exception when parsing result set: Value <value> is outside of valid range for type Long' — fixed text with the stored value interpolated — which cannot be exercised while the value is not stored exactly.
Fix: the column storage and value-binding layer of the shared SQL engine (services/service-com-amazonaws-rds-amazonrdsv19/src/state/data_plane/, the type mapping between a declared column type and the backing engine's storage class, plus the native wire's result encoder): NUMERIC/DECIMAL must be carried as exact decimals of the declared precision and scale, and BIGINT UNSIGNED as an exact unsigned 64-bit integer; out-of-precision values must be refused rather than rounded.
Traces: rds__rds-data__secretsmanager.typed-values-agree-between-the-data-api-and-a-native-session (NUMERIC(20,5)) and rds__rds-data__secretsmanager.typed-values-agree-between-the-data-api-and-a-native-mysql-session (DECIMAL(38,9) and BIGINT UNSIGNED).

Cause 2 of 2: binary column values are passed through a UTF-8 text round trip, so every byte that is not valid UTF-8 comes back as the replacement character.
AWS: recorded behavior only for the wire; MySQL BLOB is an opaque byte string. A native session that inserts the 7 bytes 00 01 FF DE AD BE EF into a BLOB column reads back exactly those 7 bytes, byte for byte and length for length, with no transcoding — binary columns are never interpreted as text.
Emulator: the same column reads back as 12 bytes, 00 01 EF BF BD DE AD EF BF BD EF BF BD: each byte that is not a valid UTF-8 sequence (FF, BE, EF) has been replaced by the 3-byte UTF-8 encoding of U+FFFD REPLACEMENT CHARACTER, and the valid-looking bytes (00, 01, DE, AD) passed through. The write and the read both report success. The particular bytes are the check's; the requirement is byte-exact round-tripping of a binary column, which this lossy decode can never satisfy — the original bytes are unrecoverable.
Why: any client storing binary data — a serialised protobuf, an encrypted or compressed blob, an image thumbnail, a hash — gets corrupted bytes back from an operation that reported success, and the corruption is irreversible, so there is no client-side workaround. It also makes BLOB values incomparable across the Data API and a driver.
Fix: the binary value path of the shared engine and the native wire codec (same component as Cause 1): BLOB/BYTEA values must be stored and transmitted as bytes, with no UTF-8 decode/encode step on the way in or out.
Traces: rds__rds-data__secretsmanager.typed-values-agree-between-the-data-api-and-a-native-mysql-session (observed in the same failing row comparison as Cause 1's DECIMAL and BIGINT UNSIGNED values; the graded assertion stops on the numeric columns first, so this cause becomes the next failure once Cause 1 is fixed).
