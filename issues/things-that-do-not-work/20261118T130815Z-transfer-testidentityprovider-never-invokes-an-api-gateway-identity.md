# Transfer TestIdentityProvider never invokes an API_GATEWAY identity provider: StatusCode 0 and no Response instead of the endpoint's status and body, so every API_GATEWAY positive control times out

> _Note: this issue was identified against the code base at commit `1ebe89a8f0367d7febc931808a6a13e6eae28984`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
TestIdentityProvider

## Description
ONE net-new root cause in the transfer emulator, grounded in the three failing behavioral checks of this replay that were marked neither 'ALREADY FILED' nor 'OWNED by'.

=== Cause 1 of 1: TestIdentityProvider on a server whose IdentityProviderType is API_GATEWAY never makes the authentication request against the configured Url, so it answers StatusCode 0 (the member's modeled 'no status' default) with no Response and an emulator-authored Message, instead of the invoked endpoint's own HTTP status and response body ===
Failing checks: transfer.test-identity-provider-invokes-configured-endpoint, transfer.test-identity-provider-service-managed-rejected, transfer.test-identity-provider-invalid-request-error.

AWS: Smithy com.amazonaws.transfer#TestIdentityProvider — input {ServerId @required len 19..19 pattern ^s-([0-9a-f]{17})$, UserName @required len 3..100 pattern ^[\w][\w@.-]{2,99}$, ServerProtocol (Protocol enum AS2|FTP|FTPS|SFTP), SourceIp len 0..32, UserPassword @sensitive len 0..1024}; output {StatusCode (integer) @required @default(0), Response, Message, Url @required len 0..255}; modeled errors InternalServiceError 503, InvalidRequestException 400, ResourceNotFoundException 404, ServiceUnavailableException 503. The model documents StatusCode as 'The HTTP status code that is the response from your API Gateway or your Lambda function', Response as 'The response that is returned from your API Gateway or your Lambda function', Url as 'The endpoint of the service used to authenticate a user', and the operation itself as the way to test 'whether your identity provider is set up successfully' when IdentityProviderType is AWS_DIRECTORY_SERVICE or API_Gateway. So for a server whose IdentityProviderType is API_GATEWAY and whose IdentityProviderDetails names {Url, InvocationRole}, this operation's answer is the OUTCOME of an authentication request the service makes against that REST endpoint (assuming InvocationRole): StatusCode is the HTTP status that endpoint answered, Response carries that endpoint's response body verbatim, and Url is the endpoint that was invoked. Recorded behavior: against an API_GATEWAY server whose Url names a deployed REST API that answers 200 with a JSON body ({"Role": <a syntactically valid IAM role ARN in the caller's account>, "HomeDirectory": "/<path>"}), TestIdentityProvider answers HTTP 200 with StatusCode 200 and that JSON present inside Response. While the InvocationRole is still propagating in IAM, the recording shows the call still answers HTTP 200 but with a non-200/absent StatusCode and a Message naming the assume-role failure — i.e. the status and message track the real attempt — which is why the checks poll. The endpoint host/port, the rest-api id, the account, the region and the marker value in the body are per-environment values and are NOT requirements; the requirement is that StatusCode is the invoked provider's HTTP status and Response is the provider's body as returned.

Emulator: the refusal half of this operation is correct and those assertions pass — an unknown ServerId is refused HTTP 404 ResourceNotFoundException 'Unknown server' (fixed text, no variable part), and a SERVICE_MANAGED server is refused HTTP 400 InvalidRequestException '<ServerId> not configured for external auth' (fixed text 'not configured for external auth' with the ServerId taken from the request). Past that gate, though, the handler makes no request at all: for every external provider it unconditionally returns HTTP 200 with StatusCode = state::IDENTITY_PROVIDER_NO_RESPONSE_STATUS (= 0), Response absent entirely, Url = the stored IdentityProviderDetails.Url, and Message = the emulator-authored text state::IDENTITY_PROVIDER_NOT_INVOKED ('The stored identity provider configuration is complete, but the authentication request could not be made: this emulator opens no outbound connection and runs no customer identity provider, so the provider returned no response.'). Because StatusCode can therefore never become 200, each of the three checks spins in its documented IAM-propagation poll for its full 60 s budget and the check is killed: 'Error: Check timed out after 60.0s'. No outbound connection is in fact needed here — the API Gateway REST API the server's Url points at is created by these same checks through this emulator's own apigateway emulation (ctx.rest_api_url(rest_api_id, 'test')), so the provider is reachable in-process, exactly as the transfer crate already reaches an emulated Lambda for a CUSTOM workflow step (src/state/connector_delivery.rs builds an SDK client over smithy_server_runtime::EmbeddedEmulator's callback http_client).

Why: a client cannot test an API_GATEWAY-backed custom identity provider at all, and cannot even tell a working provider from a broken one. StatusCode 0 is the modeled DEFAULT meaning 'no HTTP status', so a caller that branches on StatusCode == 200 — the documented way to decide whether the provider is set up successfully — always takes the failure branch, and a caller that parses Response to validate the Role / HomeDirectory / HomeDirectoryDetails / Policy its endpoint returns has nothing to parse. Worse, the answer is a 200 carrying a success-shaped envelope with a Message that asserts the request 'could not be made', so troubleshooting flows built on the operation AWS 'highly recommend[s] you call ... as soon as you create your server' report every healthy API Gateway provider as broken, and any test harness that polls for StatusCode 200 (as all three of these checks do) hangs until its own deadline instead of failing fast.

Fix: the TestIdentityProvider handler (services/service-com-amazonaws-transfer-transferservice/src/ops/test_identity_provider.rs, the branch after the external-identity-provider gate) together with the identity-provider answer helpers in src/state.rs. For a server past that gate whose provider endpoint this emulator serves, the handler must actually perform the authentication request — for API_GATEWAY, invoke the REST endpoint named by IdentityProviderDetails.Url over the in-process callback client the crate already uses, as the configured InvocationRole — and report that invocation's HTTP status in StatusCode and its response body in Response, with Url the endpoint invoked. The no-response answer (StatusCode = state::IDENTITY_PROVIDER_NO_RESPONSE_STATUS with the explanatory Message) must be kept only for a provider endpoint this emulator genuinely does not serve, and the SERVICE_MANAGED / unknown-server refusals must stay exactly as they are.

Related already-filed issue that does NOT cover this: open issue 20261107T194602Z-transfer-testidentityprovider-never-invokes-an-aws-lambda-provider.md reports the same handler never invoking an AWS_LAMBDA provider and scopes its cause, evidence and fix to IdentityProviderDetails.Function and a Lambda invocation; the API_GATEWAY path (IdentityProviderDetails.Url + InvocationRole, invoked over HTTP) is a separate provider kind with its own invocation seam, and the suite marked these three checks as owned by no issue.

Traces: transfer.test-identity-provider-invokes-configured-endpoint, transfer.test-identity-provider-service-managed-rejected, transfer.test-identity-provider-invalid-request-error.
