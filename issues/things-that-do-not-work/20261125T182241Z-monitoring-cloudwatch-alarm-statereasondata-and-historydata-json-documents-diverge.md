# CloudWatch alarm StateReasonData and HistoryData JSON documents diverge from AWS's document

> _Note: this issue was identified against the code base at commit `6aa2a86c3a95f1aaa5bab53f9c9597e382f3838c`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
DescribeAlarms

## Description
4 causes, one shared fault: every alarm read that embeds a JSON document inside a string member (MetricAlarm$StateReasonData, AlarmHistoryItem$HistoryData) answers 200 but serializes a document whose member naming, member order and member set are not the ones AWS produces, so a client that parses the embedded document reads a different structure than it reads against AWS. All four causes are on the monitoring (CloudWatch) service and none is carried by an open issue's replay key.

Cause 1 of 4: DescribeAlarms StateReasonData for a metric alarm whose state was decided with missing datapoints treated as breaching (fixture cloudwatch-alarm-firing-describe-filter-mistakes, step task#4; the cluster also covers cloudwatch-albos-alarm-lookup-and-state-mistakes#task#4 and #task#6, cloudwatch-sftp-traj-add-alarm-actions#task#7, cloudwatch-sftp-traj-alarm-reference-reads#task#2).
AWS: Smithy: MetricAlarm$StateReasonData — "An explanation for the alarm state, in JSON format." The model constrains neither the members nor their order, so recorded behavior only: the fixture asserts the SHAPE of the document (its members, their names and their structure) and deliberately does not assert the volatile values inside it, and the recorded response is a document the emulator's value does not match. The same corpus records AWS naming an alarm's statistic inside such a document with an extendedStatistic member (see Cause 4, where the recorded document reads "extendedStatistic":"AVERAGE"), and AWS's published StateReasonData form orders its members version, queryDate, startDate, the statistic member, period, recentDatapoints, threshold, evaluatedDatapoints.
Emulator: 200 with StateReasonData = {"version":"1.0","queryDate":"<instant>","startDate":"<instant>","statistic":"p90","period":60,"threshold":15000.0,"recentDatapoints":[],"evaluatedDatapoints":[{"timestamp":"<instant>"},{"timestamp":"<instant>"},{"timestamp":"<instant>"}]} — i.e. the alarm's EXTENDED statistic (the alarm is configured with ExtendedStatistic, per the recorded MetricAlarm in this same fixture) is named by a statistic member, and threshold is emitted BEFORE recentDatapoints. The instants, the threshold number and the percentile name are per-run/per-request values and are not themselves the requirement; the member names and their order are. Hypothesis: those two deviations are what fails the asserted shape — the document is otherwise structurally the one AWS returns for a breaching-missing-data transition.
Why: StateReasonData is the only machine-readable record of how an alarm state was decided. A client (or a dashboard/runbook) that reads document.extendedStatistic, or that round-trips the document through a schema, sees an absent member and an unexpected ordering, so an alarm the emulator reports as ALARM cannot be explained the way the same alarm is explained on AWS.
Fix: the StateReasonData builder in the CloudWatch crate's alarm-state evaluation (the document assembly that inserts version/queryDate/startDate/statistic/period/threshold/recentDatapoints/evaluatedDatapoints), not the DescribeAlarms serializer: the value is stored on the alarm by the evaluation and read back verbatim.

Cause 2 of 4: DescribeAlarmHistory HistoryData for a state-transition item embeds the same defective document (fixture cloudwatch-alarm-firing-describe-filter-mistakes, step task#6; the cluster also covers cloudwatch-albos-alarm-lookup-and-state-mistakes#task#8, cloudwatch-latency-alarm-history-query-mistakes#task#6, cloudwatch-sftp-traj-alarm-reference-reads#task#5).
AWS: Smithy: AlarmHistoryItem$HistoryData — "Data about the alarm, in JSON format." @length(1, 4095). Recorded behavior only: the fixture asserts the document's shape; the recorded AWS history document for a state update carries version, oldState{stateValue, stateReason} and newState{stateValue, stateReason, stateReasonData}, with the nested state-reason document in the form AWS returns from DescribeAlarms.
Emulator: 200 with HistoryData = {"version":"1.0","oldState":{"stateValue":"INSUFFICIENT_DATA","stateReason":"Unchecked: Initial alarm creation"},"newState":{"stateValue":"ALARM","stateReason":"Threshold Crossed: no datapoints were received for 3 periods and 3 missing datapoints were treated as [Breaching].","stateReasonData":{"version":"1.0",...,"statistic":"p90","period":60,"threshold":15000.0,"recentDatapoints":[],"evaluatedDatapoints":[...]}}} — the nested newState.stateReasonData carries exactly the Cause 1 deviations (statistic instead of extendedStatistic, threshold before recentDatapoints), and the asserted shape fails.
Why: alarm history is what an operator reads to reconstruct a past transition; the nested document is the evidence for it. A consumer parsing history items gets a stateReasonData whose structure differs from AWS's, so history replay and alarm-postmortem tooling diverge.
Fix: the alarm-history recorder in the CloudWatch crate — it must embed the corrected state-reason document (same builder as Cause 1) rather than its own rendering.

Cause 3 of 4: DescribeAlarmsForMetric returns the same defective StateReasonData on its own read path (fixture cloudwatch-alarm-firing-describe-filter-mistakes, step task#9; the cluster also covers cloudwatch-sftp-traj-alarm-reference-reads#task#8).
AWS: Smithy: DescribeAlarmsForMetric output member MetricAlarms (list of MetricAlarm), so it returns the SAME MetricAlarm shape as DescribeAlarms, including StateReasonData; recorded behavior only for the document's contents, asserted as a shape.
Emulator: 200 with the identical non-conforming document reported in Cause 1 (statistic for an extended-statistic alarm, threshold before recentDatapoints).
Why: the metric-scoped read of an alarm must describe it identically to the name-scoped read; a client that switches read paths to find alarms for a metric gets the same wrong explanation document.
Fix: same builder as Cause 1 — listed as its own cause because it is a separate read path and a separate replayable step, so a fix must be confirmed on it too.

Cause 4 of 4: DescribeAlarmHistory HistoryData for a CONFIGURATION-UPDATE item mis-names the statistic and over-reports originalUpdatedFields (fixture cloudwatch-rshealth-operator-fix-mistakes, step task#8).
AWS: recorded behavior only (the model says only "Data about the alarm, in JSON format."). The recorded AWS document is {"version":"1.0","type":"Update","updatedAlarm":{...,"extendedStatistic":"AVERAGE",...},"originalUpdatedFields":{"alarmConfigurationUpdatedTimestamp":"<previous instant>","comparisonOperator":"GreaterThanThreshold"}} — i.e. updatedAlarm names the statistic under extendedStatistic, and originalUpdatedFields carries ONLY the previous values of the members this update actually changed (here the configuration-updated timestamp and the comparison operator, which the request changed from GreaterThanThreshold to LessThanThreshold). The instants and the alarm/dimension names are per-run values; the member naming and the "only what changed" rule are the requirement.
Emulator: 200 with updatedAlarm naming the statistic "statistic":"Average", and originalUpdatedFields enumerating members that did NOT change, including null and empty placeholders (observed: "originalUpdatedFields":{"alarmConfigurationUpdatedTimestamp":"<instant>","dimensions":[],"alarmDescription":null,...}). The replay also reports the following history item's HistoryData and HistorySummary diverging and a third item differing from the recorded list, i.e. the update item is not the only history record this write path gets wrong.
Why: originalUpdatedFields is how a client diffs an alarm's configuration change. Reporting unchanged members (and nulls for members that were never set) makes every update look like it rewrote the whole alarm, so change-audit and drift-detection tooling reports false modifications; the statistic member naming compounds Cause 1 on the history path.
Fix: the alarm-configuration-update history recorder in the CloudWatch crate — it must compute the changed-member set by comparing the stored alarm with the write and emit only those members' PREVIOUS values, and name an extended statistic as extendedStatistic.
