# monitoring ListAWSDefaultServiceQuotas: 50 published quota rows have no citable QuotaCode-to-quota pairing

## Operation
ListAWSDefaultServiceQuotas

## Description
This is the RESIDUAL half of
`issues/things-that-now-work/20261113T121705Z-service-quotas-listawsdefaultservicequotas-default-catalog-omits-52-monitoring-cloudwatch-rows.md`,
split out so none of it is recorded as working. That report asked the default-quota
catalog of `ServiceCode` `monitoring` (Amazon CloudWatch) to publish a row for each of
52 absent `QuotaCode`s and to correct the `Value` of two rows it already served. It
STATES the quota behind two of the absent codes together with everything published under
them, and those two are now served (`L-E2310E7A` "Rate of DescribeAlarmsForMetric
requests", Value 9.0, not adjustable; `L-CA907765` "Rate of EnableAlarmActions requests",
Value 3.0, not adjustable), beside the corrected rates of `L-69C44FFD` and `L-6300B446`
(10.0 each). For the 50 codes above nothing available in this checkout — not the Smithy
model (which does not enumerate catalog contents), not that report, and not AWS's own
published CloudWatch quota documentation, which names each quota but no `QuotaCode` —
says WHICH quota AWS publishes under WHICH of them.

A `QuotaCode` is an opaque AWS-minted identifier: no rule derives it from a quota's name,
so the pairing can only be read off a recorded `ListAWSDefaultServiceQuotas` response of
this service code. Pairing them by guess would publish one quota's name, value,
adjustability, window and usage metric under another quota's code, which is the defect
class the catalog's own rule forbids (`src/state/quota_rows.rs`, module docs) and that
several reports have been filed for ("rows misbound", "rows carry another quota's
metadata"). So these 50 rows are left in the default-quota-set gap rather than published
under a code this catalog would be inventing a binding for.

ONE of the 50 is half-stated and still cannot be published: the report names `L-C234EDB6`
as "Rate of DisableInsightRules requests", but states neither the requests per second AWS
publishes it at nor whether AWS publishes it as adjustable. Those two members are the
quota itself — a row served with a rate chosen here would answer a capacity-planning
client with a limit AWS never set, and the per-API rate rows of this service are
published at rates as far apart as 3 and 1000 per second with both adjustabilities, so
neither member can be inferred from the class.

What is needed to close this: for each of the 50 codes, the quota AWS publishes under it
— its `QuotaName`, `Value`, `Unit`, `Adjustable`, `GlobalQuota`, `Period`, `UsageMetric`
and `Description` — as a recorded `ListAWSDefaultServiceQuotas` response of `monitoring`
states them. The constructors for both classes of row this service publishes already
exist (`src/state/quota_rows/monitoring.rs`: `cloudwatch_request_rate` for a
per-operation request rate, `quota(...)` for a rate on anything else), so each newly
cited pairing is one line in `monitoring_quotas()`.

## Evidence
Replay of `service-quotas-catalog-list-aws-default-service-quotas-monitoring#task#1`
against the emulator built with the two newly published rows and the two corrected rates:
HTTP 200, body-only divergence, the keys for `L-E2310E7A`, `L-CA907765`,
`$.Quotas[QuotaCode="L-69C44FFD"].Value` and `$.Quotas[QuotaCode="L-6300B446"].Value` no
longer reported, and the 50 codes above still reported as
`missing (expected {...}, got None)` — the whole `ServiceQuota` row, not one member.

The emulator's served `monitoring` catalog after that change
(`ListAWSDefaultServiceQuotas`, `ServiceCode=monitoring`) is six rows: `L-6FCAAA2E`,
`L-69C44FFD`, `L-6300B446`, `L-E2310E7A`, `L-CA907765` and `L-722EAE58`, each under
AWS's own code and self-consistent, pinned by
`tests/all/cloudwatch_published_default_rows.rs`.
