# rds: 3 net-new causes — RebootDBInstance publishes in-sync and an OS-assigned port, engine-default parameters carry emulator-authored text, and StartExportTask's KMS refusal is reworded

## Description
Three net-new root causes on the rds surface, found by replaying the wire fixture corpus (simparity-wire-aws-v1) against the emulator built from this checkout. All 63 divergence clusters in this replay were rds; the other 60 were reported OWNED by open issues that already carry their replay key, and none were blocked by an unimplemented scaffold stub. The three clusters below were reported neither owned nor blocked. They share one fault: the rds surface serves emulator-authored values (its own process state, its own prose) where AWS serves the resource's modelled value or the service's own fixed text.

Cause 1 of 3: RebootDBInstance reports the rebooted instance's parameter group as already applied, and publishes the process's listener port rather than the engine's. Operation RebootDBInstance; fixture rds-db-instance-provider-explicit-defaults-parameter-group-switch-reboot-and-not-found step task#19.
AWS: Smithy (services/service-com-amazonaws-rds-amazonrdsv19/smithy-model/com-amazonaws-rds-amazonrdsv19.json) models RebootDBInstance -> DBInstance, whose DBParameterGroups member is a list of DBParameterGroupStatus. ParameterApplyStatus is documented with the value set 'applying' | 'failed-to-apply' | 'in-sync' | 'pending-database-upgrade' | 'pending-reboot', where 'pending-reboot' means "the parameter group change will be applied after the DB instance reboots" and 'in-sync' means "the parameter group change is synchronized with the database". After a ModifyDBInstance that switches DBParameterGroupName, the instance's group is pending-reboot, and the RebootDBInstance response — taken while the instance is still rebooting — reports the status that is still outstanding, i.e. 'pending-reboot'; it only becomes 'in-sync' once the reboot has actually applied the group. The recorded response is 'pending-reboot'. The same response's DBInstance.Endpoint.Port is documented as "the port that the database engine is listening on" — for this instance the port it was created with, which for a MySQL instance defaults to 3306 — a stable property of the resource, not of the host process.
Emulator: the RebootDBInstance response reports ParameterApplyStatus 'in-sync' for a group that was switched and whose change has not been applied, and reports Endpoint.Port as an OS-assigned per-run listener port (this run: 36461) instead of the instance's engine port (3306).
Why: a client that switches a DB parameter group and then reboots reads 'in-sync' from the reboot response and concludes the change is live, so it never waits for, or re-issues, the apply — and every pending-reboot/in-sync convergence loop (Terraform, CloudFormation, CDK, operational runbooks) terminates one state too early. A client that reads Endpoint.Port to build a connection string dials a port that is not the database's; the modelled per-engine default is simply not observable.
Fix: the RebootDBInstance handler and the DBInstance state it reads — the parameter-group apply-status transition (set pending-reboot on a group switch and clear it to in-sync only when the reboot applies it) and the DBInstance endpoint publication, which must report the instance's own engine port rather than the bound listener's. NOTE: open issue 20261123T132332Z-rds-a-served-engine-s-dbinstance-endpoint-address.md describes the endpoint-publication half of this (Endpoint.Address/Port taken from the core listener) for DescribeDBInstances, and 20261108T233943Z-rds-db-cluster-envelopes-report-the-emulator-s-random.md / 20261121T073752Z-rds-db-cluster-envelopes-publish-the-emulator-s.md cover the DB *cluster* envelopes. None carries this wire step's replay key and none covers ParameterApplyStatus, so this step must be re-replayed on its own.
Traces: rds-db-instance-provider-explicit-defaults-parameter-group-switch-reboot-and-not-found#task#19.

Cause 2 of 3: DescribeEngineDefaultParameters serves an emulator-authored MySQL parameter catalog — paraphrased Descriptions, a wrong Source and wrong MinimumEngineVersion/IsModifiable values. Operation DescribeEngineDefaultParameters; fixture rds-db-parameter-group-lifecycle-and-engine-defaults step task#10.
AWS: Smithy models DescribeEngineDefaultParameters(DBParameterGroupFamily) -> EngineDefaults.Parameters, a list of Parameter whose Description "provides a description of the parameter", Source is "the source of the parameter value", MinimumEngineVersion is "the earliest engine version to which the parameter can apply", and IsModifiable indicates whether the parameter can be modified. These are catalog facts about the engine family, not emulator-chosen prose: AWS returns the engine's own published documentation string verbatim for each parameter, Source 'system' for a value that comes from the engine's own system defaults (as opposed to 'engine-default'/'user'), and the real earliest-applicable engine version. The recorded page carries, e.g., binlog_checksum Description "When enabled, this variable causes the master to write a checksum for each event in the binary log.", binlog_error_action "Controls what happens when the server cannot write to the binary log.", binlog_format "Row-based, Statement-based or Mixed replication" with Source 'system', binlog_group_commit_sync_no_delay_count "The maximum number of transactions to wait for before aborting the current delay as specified by binlog-group-commit-sync-delay.", and binlog_gtid_simple_recovery "Controls how binary logs are iterated during GTID recovery" with MinimumEngineVersion '5.7.23'.
Emulator: the same rows carry re-worded Descriptions of the emulator's own composition ("Whether the server writes a checksum for each event in the binary log.", "What the server does when it cannot write to the binary log.", "The format the server writes to the binary log in.", "The maximum number of transactions to wait for before aborting the current binary log commit delay.", "Controls how binary log files are iterated during the search for GTIDs when the server starts or restarts"), Source 'engine-default' where AWS reports 'system', MinimumEngineVersion '5.7.6' where AWS reports '5.7.23', and a diverging IsModifiable on the same row; eleven keys on the first page diverge.
Why: this operation exists so a client can discover the engine family's defaults. A console, a drift detector or a compliance report that renders the Description shows text AWS never emitted; a tool that gates a parameter change on MinimumEngineVersion or IsModifiable decides on a fabricated bound and either blocks a legal change or allows an illegal one; a client that distinguishes 'system' from 'engine-default' to decide whether a value was ever customised reads the wrong provenance.
Fix: the engine-default parameter catalog behind the DescribeEngineDefaultParameters handler in the rds crate (the per-family parameter table its serializer reads), which must carry the engine's published Description/Source/MinimumEngineVersion/IsModifiable rather than generated prose. NOTE: open issue 20261123T140000Z-rds-describedbparameters-five-mysql-parameter-descriptions-and-one-minimumengineversion.md reports the same defect on the sibling DescribeDBParameters reader; it does not carry this step's replay key and names a different operation, so this one is net-new and must be re-replayed on its own.
Traces: rds-db-parameter-group-lifecycle-and-engine-defaults#task#10.

Cause 3 of 3: StartExportTask's inaccessible-KMS-key refusal carries an emulator-authored message instead of the service's sentence. Operation StartExportTask; fixture rds-export-task-lifecycle step task#3.
AWS: Smithy models StartExportTask with KMSKeyNotAccessibleFault (errorKind client, httpError 400, awsQueryError code KMSKeyNotAccessibleFault, member message), documented as "an error occurred accessing an Amazon Web Services KMS key". The recorded refusal is HTTP 400 with that code and the message "The KMS key <kms-key-arn> doesn't exist or is disabled." — fixed text "The KMS key " ... " doesn't exist or is disabled." with exactly one variable part, the KmsKeyId the request sent (here an arn:aws:kms key ARN; the literal ARN of this recording is a per-run value, the template is the requirement).
Emulator: the status (400) and the error code match, but the Message is "The specified KMS key [<kms-key-arn>] does not exist, is not enabled or you do not have permissions to access it." — different fixed text, the key bracketed rather than inline, and an added permissions clause AWS does not emit for this error class.
Why: the message is a requirement of the error. Clients and SDK-level retry/classification helpers, CLI users and test assertions match on this sentence; a reworded one makes the key-not-found condition unrecognisable, and the invented "or you do not have permissions to access it" clause points an operator at an IAM/key-policy investigation for a key that simply does not exist or is disabled.
Fix: the StartExportTask handler's KMS-key validation in the rds crate — the KMSKeyNotAccessibleFault message template it formats, which must be AWS's fixed text with the request's KmsKeyId interpolated.
Traces: rds-export-task-lifecycle#task#3.
