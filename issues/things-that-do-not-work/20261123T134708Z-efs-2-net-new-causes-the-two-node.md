Every multi-node workload that treats EFS as a shared POSIX filesystem (lock/barrier files, atomic rename-into-place deploys, hard links, rmdir refusals) gets no behavior to test against.

That is the efs service crate's mount-target state plus whatever serves the NFS listener and the emulator's in-VPC name resolution; the EC2/SSM execution path that carries the script is already converging and is not the gap here.

Cause 2 of 2: GetCommandInvocation reports a terminal Status of 'Failed' for an AWS-RunShellScript invocation while returning EMPTY StandardOutputContent and EMPTY StandardErrorContent, so a failed command carries no diagnostic output whatsoever. Failing check: efs.efs-nfs-two-node-posix-coherence-and-a-nonempty-rmdir-is-rejected (the assertion message is the evidence: `stderr tail ''; stdout tail ''`).
AWS: Smithy (com.amazonaws.ssm#AmazonSSM): GetCommandInvocationResult.StandardOutputContent @length(0,24000), documented as "The first 24,000 characters written by the plugin to stdout. If the command has not finished running, if ExecutionStatus is neither Succeeded nor Failed, then this string is empty"; StandardErrorContent @length(0,8000), documented as "The first 8,000 characters written by the plugin to stderr. If the command hasn't finished running, then this string is empty"; ResponseCode is the "error level response code for the plugin script", -1 only when the command never started on the node. So once Status is the terminal 'Failed', AWS returns the script's captured stdout and stderr (truncated to those lengths) and a non-zero ResponseCode, and StatusDetails is 'Failed'. A shell script run under `set -e` that aborts always writes a diagnostic to stderr (e.g. mount's own failure text), so on AWS StandardErrorContent for this invocation is non-empty.
Emulator: Status 'Failed' with StandardOutputContent '' and StandardErrorContent '' — both members empty on a terminal, finished, failed invocation. The empty strings are legal only for an invocation that has not finished.
Why: this is the member clients read to find out WHY a command failed; emptying it turns every SSM-driven provisioning or debugging flow into a black box. Any automation that branches on, logs or surfaces the failing command's stderr (CI jobs, Run Command consoles, remediation documents) sees a bare 'Failed' and cannot distinguish a missing package from an unresolvable mount server from a syntax error — exactly what happened to cause 1 above, whose root step is unidentifiable from the emulator's response.
Fix: the SSM Run Command invocation state and the GetCommandInvocation handler's serializer — the executed plugin's captured stdout/stderr must be stored with the invocation and returned (truncated to 24,000 / 8,000 characters) whenever Status is terminal, together with the script's real exit status in ResponseCode and 'Failed' in StatusDetails.
Traces: efs.efs-nfs-two-node-posix-coherence-and-a-nonempty-rmdir-is-rejected.
