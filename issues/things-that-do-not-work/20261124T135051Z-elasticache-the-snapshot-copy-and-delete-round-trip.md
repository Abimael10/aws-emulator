# elasticache: the snapshot copy-and-delete round trip of a single-node cluster never reaches a verdict — six sequential transient phases are each held long enough to cost a polling client a full interval, so the check is killed at its budget (1 cause)

> _Note: this issue was identified against the code base at commit `78eeb93e75738c0cf0c5c47abcc6a48fc1935112`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
CopySnapshot

## Description
Cause 1 of 1: the CreateSnapshot → CopySnapshot → DeleteSnapshot → DeleteCacheCluster round trip of a single-node Redis cache cluster never converges inside the replay budget, so none of the copy's observable properties (its independence from the source, the source cluster it records, its one NodeSnapshot) is ever reached. Failing check: elasticache.snapshot-of-a-single-node-cluster-copies-and-deletes, whose whole detail is `Error: Check timed out after 60.0s` — no assertion fired, i.e. every control-plane call answered 200 while the flow never got through its six sequential state waits. Related open issue 20261118T103812Z-elasticache-2-net-new-causes-the-snapshot-restore.md reports the same family (checks killed at the budget because elasticache state does not settle promptly) but its Issue-Trace-Ids/Issue-Key name only elasticache.e2e-cluster-snapshot-restore-data-persists and elasticache.e2e-user-group-access-revocation-flow, so this check is not covered by it and would otherwise be closed unrun.

AWS: Smithy (services/service-com-amazonaws-elasticache-amazonelasticachev9/smithy-model/com-amazonaws-elasticache-amazonelasticachev9.json): CreateSnapshot(CacheClusterId, SnapshotName) returns Snapshot, whose SnapshotStatus is documented "Valid values: creating | available | restoring | copying | deleting"; CopySnapshot(SourceSnapshotName, TargetSnapshotName) returns an independent second Snapshot and is modeled with SnapshotAlreadyExistsFault (400), InvalidSnapshotStateFault (400) and SnapshotNotFoundFault (404, awsQueryError SnapshotNotFoundFault); DescribeSnapshots(SnapshotName=...) reports one snapshot and answers SnapshotNotFoundFault once it is gone; DeleteSnapshot(SnapshotName) returns the snapshot it is removing; DeleteCacheCluster removes the cluster so DescribeCacheClusters answers CacheClusterNotFound (404). The model states no timing. Recorded behavior only: each stage settles on the first read issued after its transition is due — the cluster reaches CacheClusterStatus 'available', the manual snapshot reaches SnapshotStatus 'available' carrying exactly one NodeSnapshot for a single-node cluster, the copy reaches 'available' recording the ORIGINAL source cluster's CacheClusterId with one NodeSnapshot, the copy survives deleting its source and stays 'available', both snapshots then stop resolving, and finally the cluster stops resolving. Names, ids and timestamps are per-run values; the requirement is that a client polling each stage converges and can observe those properties.

Emulator: the check is killed at the per-check budget (`Error: Check timed out after 60.0s`) with no assertion fired, so none of its own verdicts (`expected exactly 1 NodeSnapshot for a single-node cluster, got <n>`, `expected the copy to record the original source cluster <id>`, `expected both snapshots to coexist`, `expected the copy <name> to survive deleting its source`, `expected <name> to be gone after delete`) was ever reached. The flow has SIX sequential state waits (cluster→available, source snapshot→available, copy→available, source snapshot→gone, copy→gone, cluster→gone) and the client polls each at a 15 s cadence. The emulator holds every one of those transient phases for a deliberately non-zero span — services/service-com-amazonaws-elasticache-amazonelasticachev9/src/state.rs:468 `CLUSTER_TRANSITION: Duration = Duration::from_secs(3)`, :478 `SNAPSHOT_TRANSITION = CLUSTER_TRANSITION` (used for 'creating'/'copying' and for the removal a DeleteSnapshot owes, see `SnapshotRecord::pending_removal`) — and nothing settles at the call, so the first read after each starting call always observes the transient status and the waiting client always pays one whole poll interval per stage. Six stages therefore cost at least 6 × 15 s = 90 s against a 60 s budget: the check cannot finish no matter what the emulator would have answered, and CopySnapshot's semantics are left entirely unverified.

Why: a client that snapshots a cache, copies the snapshot, deletes the original and tears the cluster down gets no verdict at all — every call returns 200 while the sequence never completes, so the caller cannot distinguish 'still applying' from 'never applied', and SDK waiters and CI pipelines block. A snapshot copy is the ElastiCache backup-retention story; a client cannot confirm that its copy is independent of the snapshot it was taken from.

Fix: the elasticache crate — (a) the status-settling path of its state (`settled_snapshot_mut` / `settled_cluster_mut` / `purge_deleted_snapshots` and the `pending_status` / `pending_removal` clock in src/state.rs), so a record whose transition is already due reads back settled to the FIRST Describe that observes it and a multi-stage flow converges in a bounded number of polls rather than one full client poll interval per stage; and (b) the CreateSnapshot / CopySnapshot / DeleteSnapshot / DeleteCacheCluster handlers' use of that clock (src/ops/create_snapshot.rs, src/ops/copy_snapshot.rs), so the chain of six transitions completes inside a replay budget while each transient status remains reachable for a caller that acts immediately.

Traces: elasticache.snapshot-of-a-single-node-cluster-copies-and-deletes.
