# s3tables authorization is never evaluated: identity-based denies and table-bucket-policy explicit denies are ignored, so 4 refusal paths are unreachable

> _Note: this issue was identified against the code base at commit `2c9e097b66ada646a313dc09bbc30cfe7dbc4d7b`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
GetTableBucketEncryption

## Description
Four net-new root causes, all of one shape: the s3tables request path performs NO authorization at all. Neither the signing principal's identity-based policies nor the table bucket's resource policy is consulted, so every call is answered as if the caller were the bucket owner with full permissions. Related open issue 20261103T220427Z-s3tables-encryption-configuration-3-net-new-root-causes.md states the identity-denial and KMS-access semantics for PutTableBucketEncryption while that handler was a 501 stub; the handler now answers 200 and the denial is still absent, and that issue says nothing about GetTableBucketEncryption, DeleteTable, GetTableMaintenanceConfiguration or resource-based policies. No open issue covers the resource-policy enforcement path at all (20261106T132944Z-s3tables-puttablebucketpolicy-stub.md only asks that PutTableBucketPolicy exist, and the policy now stores and reads back correctly).

Cause 1 of 4: GetTableBucketEncryption applies no identity-based authorization — a principal with no s3tables permissions reads the bucket's encryption configuration.
AWS: Smithy (com.amazonaws.s3tables#S3TableBuckets) GetTableBucketEncryption = GET /buckets/{tableBucketARN}/encryption, 200, output encryptionConfiguration @required; AccessDeniedException is modeled on it with @httpError 403. The operation's documentation requires the s3tables:GetTableBucketEncryption permission. Recorded behavior: a caller whose credentials carry no identity-based policy granting the action is refused HTTP 403, code AccessDeniedException, message `User: <caller principal ARN> is not authorized to perform: s3tables:GetTableBucketEncryption on resource: <table bucket ARN> because no identity-based policy allows the s3tables:GetTableBucketEncryption action`. Fixed text: `User: `, ` is not authorized to perform: s3tables:GetTableBucketEncryption on resource: `, ` because no identity-based policy allows the s3tables:GetTableBucketEncryption action`. Variable parts, taken from the request's signing identity and the request's tableBucketARN — never from one recording: the caller's principal ARN and the bucket ARN. The refusal exposes no configuration, and the authorized owner's own read still returns the configuration.
Emulator: the unprivileged caller gets HTTP 200 with `{'encryptionConfiguration': {'sseAlgorithm': 'AES256'}}` — the configuration is disclosed and no authorization decision is made.
Why: a client (or a policy test) cannot distinguish a principal that may read a bucket's encryption posture from one that may not; least-privilege configurations cannot be validated, and the emulator discloses encryption state to any caller.
Fix: GetTableBucketEncryption's handler and the shared s3tables authorization step it must call — resolve the signing principal from the request context and evaluate s3tables:GetTableBucketEncryption before reading state.
Traces: s3tables.get-table-bucket-encryption-without-permission-denied.

Cause 2 of 4: an explicit Deny in an identity-based policy is ignored even when a broad Allow is present — the deny never overrides the allow.
AWS: IAM evaluation is deny-overrides: a role holding Allow s3tables:* on the bucket PLUS an explicit Deny on s3tables:GetTableBucketEncryption is refused HTTP 403, code AccessDeniedException, message `User: <assumed-role session ARN> is not authorized to perform: s3tables:GetTableBucketEncryption on resource: <table bucket ARN> with an explicit deny in an identity-based policy`. Fixed text: `User: `, ` is not authorized to perform: s3tables:GetTableBucketEncryption on resource: `, ` with an explicit deny in an identity-based policy` — note this trailer differs from cause 1's `because no identity-based policy allows ...`: AWS distinguishes an explicit deny from a missing allow. Variable parts: the caller's assumed-role session ARN (`arn:<partition>:sts::<account-id>:assumed-role/<role-name>/<session-name>`) and the request's tableBucketARN. The twin role carrying only the Allow reads AES256 successfully, so the deny — not a missing allow — is what must refuse the call.
Emulator: the denied role's read also returns HTTP 200 `{'encryptionConfiguration': {'sseAlgorithm': 'AES256'}}`; allow-only and allow+deny roles are indistinguishable.
Fix: the s3tables authorization step — evaluate the full policy set for the signing principal with deny-overrides semantics and emit the explicit-deny message variant when a Deny statement matches.
Traces: s3tables.cross-account-get-table-bucket-encryption-denied.

Cause 3 of 4: PutTableBucketEncryption applies no identity-based authorization, so an unprivileged principal can rewrite another caller's bucket encryption.
AWS: Smithy PutTableBucketEncryption = PUT /buckets/{tableBucketARN}/encryption, @idempotent, 200, Unit output, input tableBucketARN (@httpLabel, @required) + encryptionConfiguration (@required); ForbiddenException 403 is modeled (AccessDeniedException is modeled on the sibling Get but not on the Put, so the code below is recorded behavior only). The operation's documentation requires the s3tables:PutTableBucketEncryption permission. Recorded behavior: a freshly assumed role with no attached policies is refused HTTP 403, code AccessDeniedException, message `User: arn:<partition>:sts::<account-id>:assumed-role/<role-name>/<session-name> is not authorized to perform: s3tables:PutTableBucketEncryption on resource: <table bucket ARN> because no identity-based policy allows the s3tables:PutTableBucketEncryption action`. Fixed text: `User: `, ` is not authorized to perform: s3tables:PutTableBucketEncryption on resource: `, ` because no identity-based policy allows the s3tables:PutTableBucketEncryption action`; variable parts are the session ARN (partition from the bucket ARN, account id, role name, session name of the signing credentials) and the request's tableBucketARN. The refusal must write nothing — the owner's read returns the prior configuration unchanged — while the same put by the owner succeeds.
Emulator: the restricted session's put returns HTTP 200 with an empty body and the write is applied; no authorization decision is made.
Fix: PutTableBucketEncryption's handler — evaluate s3tables:PutTableBucketEncryption for the signing principal before mutating the encryption state.
Traces: s3tables.put-table-bucket-encryption-without-permission-denied.

Cause 4 of 4: the table bucket resource policy is stored and read back but never enforced — an explicit Deny in it blocks nothing, on either a mutating or a read operation.
AWS: a table bucket policy put with PutTableBucketPolicy participates in the authorization decision for every action on the bucket and the tables under it, deny-overrides. A policy statement {Effect: Deny, Principal: "*", Action: s3tables:DeleteTable, Resource: <table ARN>} makes DeleteTable (Smithy: DELETE /tables/{tableBucketARN}/{namespace}/{name}, success 204; AccessDeniedException is NOT among its modeled errors, so this code is recorded behavior only) answer HTTP 403, code AccessDeniedException, message `User: <caller principal ARN> is not authorized to perform: s3tables:DeleteTable on resource: <table ARN> with an explicit deny in a resource-based policy`, and the table must survive (GetTable still returns it). The same statement scoped to s3tables:GetTableMaintenanceConfiguration with Resource `<bucket ARN>/table/*` makes GetTableMaintenanceConfiguration (Smithy: GET /tables/{tableBucketARN}/{namespace}/{name}/maintenance, 200, output tableARN + configuration both @required; AccessDeniedException likewise unmodeled, recorded behavior only) answer HTTP 403 AccessDeniedException with the same message template naming s3tables:GetTableMaintenanceConfiguration and the table ARN, while every other action on that table (GetTable) stays allowed. Fixed text in both: `User: `, ` is not authorized to perform: `, ` on resource: `, ` with an explicit deny in a resource-based policy`; variable parts are the caller's principal ARN, the action name of the call being refused, and the ARN of the resource the call targets. Deleting the bucket policy lifts the denial and the identical call then succeeds with its pre-policy result.
Emulator: with the Deny policy stored (GetTableBucketPolicy round-trips the Deny statement verbatim), DeleteTable returns HTTP 204 and actually deletes the table, and GetTableMaintenanceConfiguration returns HTTP 200 with the full configuration. The policy is inert state.
Why: resource-policy guardrails are untestable and silently void — a client that relies on a bucket policy to protect tables from deletion sees the protection accepted and stored, then watches the protected table be deleted, which is strictly worse than no policy support at all.
Fix: the shared s3tables authorization step on the request path for every table-bucket and table operation (including DeleteTable and GetTableMaintenanceConfiguration), reading the stored table-bucket policy alongside the caller's identity policies and refusing a matching Deny with the resource-based-policy message variant before any state read or mutation.
Traces: s3tables.deploy-table-bucket-cfn-enforces-policy, s3tables.s3t-an-explicit-deny-in-the-bucket-policy-blocks-the-maintenance-read.
