# The mint-an-unused-id loop is written out once per stored kind instead of once over the store's one collection shape

_Filed: 2026-11-24T08:50:37Z_
_Operation: CreateComponent | Class: maintainability_

> _Note: this issue was identified against the code base at commit `d0c0dec7a64676a87d8e5d1e69b9a326815b9d69`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Description

crate::state holds four equivalent copies of one computation: draw the next UUID from next_uuid(), reject it when a record of this kind already holds that id in the addressed (appId, environmentName), loop. One copy per stored kind -- mint_component_id (called by CreateComponent), mint_codegen_job_id (StartCodegenJob), mint_form_id (CreateForm), mint_theme_id (CreateTheme) -- differing only in which HashMap<EnvironmentKey, Vec<T>> is searched and which field carries the id. That is exactly the shape this same file factors into ONE generic helper twice over and says so: classify_id_miss is 'The one place the classification lives' and record_named is 'The one place the name-conflict lookup lives', both generic over &HashMap<EnvironmentKey, Vec<T>> plus an accessor closure, so that the per-kind methods 'differ only in which collection they search and where the record carries its id'. The minting rule is the third rule of that shape and the only one left copied, so the copies can drift: an edit that widens one copy's uniqueness check past the app environment, or drops the collision loop from one of them, changes the id rule for a single resource kind and nothing ties the four together. The fix is the crate's own pattern -- one mint_unused_id(collections, key, record_id) the four methods call -- and leaves every response and every existing test unchanged: the ids minted, their layout and their per-environment uniqueness stay identical.
