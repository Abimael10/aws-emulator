# cloudfront__pricing-plan-manager__wafv2: CancelSubscription with the current ETag never completes, so the stale-ETag concurrency check's post-cancel poll exhausts the run budget

> _Note: this issue was identified against the code base at commit `58910a13d43d3b73c2360b68a02a8155ad53be29`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
CancelSubscription

## Description
One root cause, grounded in the single surviving failure of this suite run (every other failure is marked ALREADY FILED or OWNED).

Cause 1 of 1: CancelSubscription accepted with the subscription's CURRENT ETag is answered 200 but never reaches the subscription's terminal state, so GetSubscription keeps answering 200/ACTIVE and any cancel-then-wait-for-the-resource-to-disappear sequence never terminates. Failing check: cloudfront__pricing-plan-manager__wafv2.stale-etag-cancel-rejected-subscription-stays-active.

AWS: Smithy (services/service-com-amazonaws-pricingplanmanager-awspricingplanmanager/smithy-model/com-amazonaws-pricingplanmanager-awspricingplanmanager.json): CancelSubscription (POST /v1/CancelSubscription, http code 200) takes arn @required (SubscriptionArn, @length 1..2048), ifMatch @required bound to the If-Match header, and optional clientToken; it answers the Subscription payload plus the @required ETag header, and models ValidationException (httpError 400), ConflictException (409) and ResourceNotFoundException (404). GetSubscription (POST /v1/GetSubscription, readonly) models the same ResourceNotFoundException (404). CancelSubscription's own documentation: "For active subscriptions, the cancellation is scheduled to take effect at the end of the current billing period. The subscription remains active until that date. To revert a pending cancellation, use CancelSubscriptionChange." and "For subscriptions in PENDING_APPROVAL status, the subscription is deleted immediately without scheduling." Recorded behavior for the FREE CloudFront-family tier this check exercises: after CancelSubscription with the current eTag the subscription reaches its terminal state inside the check's poll window — GetSubscription answers HTTP 404 with Error.Code "ResourceNotFoundException" and Error.Message "Subscription not found: <arn>. Verify the ARN is correct and the subscription exists in your account." (fixed text "Subscription not found: " and ". Verify the ARN is correct and the subscription exists in your account."; the ARN is the value copied from the request) — and ListSubscriptions stops reporting it. Hypothesis: a FREE-tier subscription carries no billing commitment, so there is no billing period left to run out and the cancellation is processed promptly; what the recordings fix is that the terminal state IS reached, not any particular delay.

Emulator: the check's earlier, graded assertions on this path PASS — CancelSubscription with a stale If-Match is refused ValidationException "Invalid or outdated ETag '<stale>': retrieve current ETag and retry.", the subscription stays ACTIVE with no scheduledChange and its ETag is unmoved. The divergence is the step after it: CancelSubscription(arn, ifMatch=<current eTag>) is answered 200, but the subscription is left in status ACTIVE with a pending CANCELLATION change whose effectiveDate is a future calendar boundary, and nothing inside a session ever makes it due. GetSubscription therefore answers HTTP 200 / status "ACTIVE" on every poll instead of the modeled 404 ResourceNotFoundException, and the check's post-cancel poll (GetSubscription every 5 s waiting for Error.Code "ResourceNotFoundException") can never terminate; it consumes the whole remaining run budget and the check dies in that loop (TimeoutError raised at check line 291, "cancellation: the run budget ended first"), so the concurrency behaviour it exists to assert is never completed.

Why: cancellation is the only observable end of a subscription's life. A client written against AWS cancels and then waits for the subscription to disappear — every teardown, every IaC destroy, every "is this resource still billing?" reconciliation does exactly that — and against the emulator it waits forever and is killed by its own timeout. Everything keyed on "a non-terminated subscription still covers this resource" also stays armed forever: the CloudFront web-ACL removal lock cannot be released, a resource can never be re-subscribed, and the emulator's own subscription capacity is consumed by subscriptions the client believes it cancelled.

Fix: the CancelSubscription handler (services/service-com-amazonaws-pricingplanmanager-awspricingplanmanager/src/ops/cancel_subscription.rs — the arm that attaches a pending CANCELLATION change to a non-PENDING_APPROVAL record) together with the scheduled-change processing in crate::state (src/state.rs, apply_due_changes / end_of_billing_period): complete the cancellation for a subscription with no billing commitment (the FREE tier, alongside the PENDING_APPROVAL case the handler already deletes immediately) so GetSubscription answers the modeled ResourceNotFoundException (404) with AWS's message and ListSubscriptions stops reporting it.
