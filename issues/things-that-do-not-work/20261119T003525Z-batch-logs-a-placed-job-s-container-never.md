# batch__logs: a placed job's container never executes — stdout never reaches CloudWatch Logs, and attemptDurationSeconds, evaluateOnExit RETRY and the RUNNING window are all unobservable (4 causes)

> _Note: this issue was identified against the code base at commit `e822fa4ca12543e97642b0a71000bedf3ee319c6`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
SubmitJob

## Description
Four net-new root causes in the Batch job data plane as exercised by the batch__logs behavioral checks. Every one of them shares the same symptom family — a submitted job is marked terminal without the container image ever being run — but they are four separately-closable defects. Related open issues that do NOT cover these checks (the suite left these checks unowned): 20261107T153156Z-batch-logs-a-placed-batch-job-ends-failed.md (there jobs ended FAILED with an emulator-authored no-container-runtime reason; they now end SUCCEEDED instead), 20261112T013843Z-batch-retrystrategy-is-not-applied-a-job-whose.md, 20261114T101713Z-batch-logs-array-job-children-never-execute-so.md, 20261107T210820Z-batch-the-job-data-plane-never-executes-a.md.

Cause 1 of 4: the container's stdout is never delivered to the job's awslogs stream.
AWS: a job whose container definition carries the awslogs log driver has its container stdout delivered, one CloudWatch Logs event per line, into the configured log group under the stream name Batch reports in attempts[].container.logStreamName / container.logStreamName. Smithy: AttemptContainerDetail.logStreamName is documented as "The name of the CloudWatch Logs log stream that's associated with the container... Each container attempt receives a log stream name when they reach the RUNNING status"; AttemptContainerDetail.exitCode is "The exit code for the job attempt. A non-zero exit code is considered failed." The per-line delivery contract itself is documented at https://docs.aws.amazon.com/batch/latest/userguide/using_awslogs.html (recorded behavior only in the model).
Emulator: DescribeJobs reports status SUCCEEDED with container.exitCode 0, statusReason "Essential container in task exited" and a logStreamName of the form batch/<queue-or-ce>/<32-hex-id>, but no log event is ever written to that stream. Every check that reads back a line the container printed (an `echo IDX=$AWS_BATCH_JOB_ARRAY_INDEX`, a computed stdout value, a per-child marker) waits on its log-read deadline until the runner kills it at its 60 s budget, so the check never reaches a verdict. The exitCode 0 and the "Essential container in task exited" reason are synthesised: the image was never pulled and no process ran.
Why: a client that submits a job to produce work — anything whose result is read from the job's log stream or inferred from the container's exit code — sees a SUCCEEDED job that produced nothing. Code that gates on job success and then reads output deadlocks or silently processes empty results, and AWS_BATCH_JOB_ARRAY_INDEX injection into the container cannot be verified at all because no container ever observes it.
Fix: the Batch job data-plane runner — the component that places a RUNNABLE job onto its compute environment's backing ECS cluster, runs the container image, and the awslogs log-driver delivery path that writes the container's stdout lines into the named log group/stream. The status transition must follow the real container's exit, not precede it.
Traces: batch__logs.batch-array-child-index-drives-distinct-stdout, batch__logs.batch-job-stdout-matches-computed-output, batch__logs.batch-sequential-array-children-run-one-at-a-time-in-index-order, batch__logs.batch-sequential-array-child-failure-leaves-remaining-children-blocked.

Cause 2 of 4: timeout.attemptDurationSeconds is not enforced — a job that outlives its attempt timeout is reported SUCCEEDED.
AWS: Smithy: JobTimeout.attemptDurationSeconds — "The job timeout time (in seconds) that's measured from the job attempt's startedAt timestamp. After this time passes, Batch terminates your jobs if they aren't finished. The minimum value for the timeout is 60 seconds." A job killed by its attempt timeout reaches JobStatus FAILED (JobStatus enum: SUBMITTED, PENDING, RUNNABLE, STARTING, RUNNING, SUCCEEDED, FAILED), its container does not reach its completion marker, and the attempt's statusReason reports the timeout rather than a clean container exit (https://docs.aws.amazon.com/batch/latest/userguide/job_timeouts.html).
Emulator: the job submitted with a container that sleeps past attemptDurationSeconds is reported with status 'SUCCEEDED' and container.exitCode 0 — the check's assertion reads "a job past attemptDurationSeconds must be FAILED, got 'SUCCEEDED' (exitCode=0)". The timeout is accepted on SubmitJob and then never evaluated.
Why: a client that relies on attemptDurationSeconds as its only bound on a runaway job is told the job completed successfully. Retry/alerting logic keyed on FAILED never fires, and a job that AWS would have killed is indistinguishable from one that finished.
Fix: the job attempt lifecycle in the Batch job runner — the attempt must carry its startedAt deadline and be terminated into FAILED when it elapses, with the timeout reflected in the attempt's statusReason.
Traces: batch__logs.batch-attempt-timeout-kills-container-before-completion-marker.

Cause 3 of 4: retryStrategy.evaluateOnExit with action RETRY is never applied — one attempt is recorded and its exit code is forced to 0.
AWS: Smithy: RetryStrategy.attempts — "The number of times to move a job to the RUNNABLE status. You can specify between 1 and 10 attempts. If the value of attempts is greater than one, the job is retried on failure the same number of attempts as the value"; RetryStrategy.evaluateOnExit / EvaluateOnExit.onExitCode + action (RetryAction RETRY|EXIT) — "Specifies an array of up to 5 conditions to be met, and an action to take (RETRY or EXIT) if all conditions are met." A job with attempts=2 and an evaluateOnExit rule matching the first attempt's exit code is re-run, AWS_BATCH_JOB_ATTEMPT is incremented for the second container, and DescribeJobs reports two AttemptDetail entries, each with its own startedAt/stoppedAt and container.exitCode.
Emulator: DescribeJobs reports exactly one attempt and that attempt's container.exitCode is 0 with reason "Essential container in task exited" — the check asserts "a RETRY on exit 42 with attempts=2 must produce exactly 2 attempts, got 1". Because no container runs (Cause 1), the attempt never produces the non-zero exit code the evaluateOnExit rule matches, and the retry decision is therefore never taken.
Why: a client encoding its failure policy in retryStrategy/evaluateOnExit gets no retry at all, and the attempts array it reads to audit how many times the work actually ran under-reports by design. Work the client expects to be retried to success is silently run once.
Fix: the retry evaluation step of the Batch job state machine — after an attempt terminates, match its exit code / reason / statusReason against evaluateOnExit and re-queue to RUNNABLE up to attempts, appending one AttemptDetail per attempt and incrementing AWS_BATCH_JOB_ATTEMPT in the container environment.
Traces: batch__logs.batch-retry-attempt-number-visible-to-container-and-second-attempt-succeeds.

Cause 4 of 4: a job never passes through RUNNING — it is already terminal on the caller's first read, so TerminateJob of a running job is unreachable.
AWS: Smithy: JobStatus enumerates SUBMITTED, PENDING, RUNNABLE, STARTING, RUNNING, SUCCEEDED, FAILED, and AttemptDetail.startedAt is "the Unix timestamp (in milliseconds) for when the attempt was started (when the attempt transitioned from the STARTING state to the RUNNING state)" while stoppedAt is the transition "from the RUNNING state to a terminal state". A job whose container is still executing is observable as RUNNING for the duration of that execution, and TerminateJob on it stops the container and reports the caller's reason verbatim.
Emulator: the job is observed with status 'SUCCEEDED' before any RUNNING read can be taken — the check asserts "the victim must be observed RUNNING before TerminateJob, not already 'SUCCEEDED' -- a job terminated while still RUNNABLE never executed". The whole SUBMITTED→...→RUNNING window collapses to zero because the terminal status is written at placement time instead of at container exit.
Why: a client cannot observe, poll on, or act on a running job: progress UIs never show RUNNING, and TerminateJob can only ever be issued against a job that already finished, so cancellation is unimplementable against this emulator.
Fix: the Batch job state machine's status transitions in the job runner — RUNNING must be entered when the container starts and held until it exits, and TerminateJob must stop a RUNNING container and record the caller's reason.
Traces: batch__logs.batch-terminate-running-job-stops-container-before-completion-marker.

## Evidence
Cause 1 — expected: the container's `echo` lines are readable from the log stream DescribeJobs names, so a size-3 array job's three children each hold exactly one IDX= line and a computed-stdout job holds its computed value. Actual: no event is ever delivered to that stream; the four checks exhaust their log-read deadline and are killed by the runner with "Error: Check timed out after 60.0s" (batch-array-child-index-drives-distinct-stdout, batch-job-stdout-matches-computed-output, batch-sequential-array-children-run-one-at-a-time-in-index-order, batch-sequential-array-child-failure-leaves-remaining-children-blocked), while DescribeJobs reports SUCCEEDED/exitCode 0.

Cause 2 — expected: status FAILED, container's completion marker absent, attempt statusReason reporting the attempt timeout. Actual: AssertionError "a job past attemptDurationSeconds must be FAILED, got 'SUCCEEDED' (exitCode=0)".

Cause 3 — expected: 2 AttemptDetail entries, the first with the matching non-zero exitCode and the second exiting 0, AWS_BATCH_JOB_ATTEMPT visible as 1 then 2 inside the containers. Actual: AssertionError "a RETRY on exit 42 with attempts=2 must produce exactly 2 attempts, got 1: [{'container': {'taskArn': 'arn:aws:ecs:<region>:<account>:task/AWSBatch-<ce>/<task-id>', 'exitCode': 0, 'reason': 'Essential container in task exited', 'logStreamName': 'batch/default/<task-id>'}, 'startedAt': <ms>, 'stoppedAt': <ms>, 'statusReason': 'Essential container in task exited'}]" — the ids, ARNs and timestamps in that record are per-run values; the requirement is the two-entry attempts array and the first attempt's non-zero exitCode.

Cause 4 — expected: at least one DescribeJobs read returns status RUNNING before TerminateJob is issued. Actual: AssertionError "the victim must be observed RUNNING before TerminateJob, not already 'SUCCEEDED' -- a job terminated while still RUNNABLE never executed and the absence assertion would be vacuous".

Common fingerprint across all four: container.reason / statusReason is the fixed string "Essential container in task exited" with exitCode 0, emitted without the image having been pulled or any process having run.

## Steps to Reproduce
1. Create a MANAGED FARGATE compute environment and a job queue bound to it; wait for VALID.
2. RegisterJobDefinition with a container command that prints a marker (e.g. ["sh","-c","echo IDX=$AWS_BATCH_JOB_ARRAY_INDEX"]) and a logConfiguration using the awslogs driver pointed at a fresh log group.
3. Cause 1: SubmitJob (and SubmitJob with arrayProperties={"size":3}); poll DescribeJobs until SUCCEEDED, then FilterLogEvents/GetLogEvents on the logStreamName DescribeJobs reports — no events are ever returned.
4. Cause 2: SubmitJob with timeout={"attemptDurationSeconds":60} and a container that sleeps longer; poll DescribeJobs — status is SUCCEEDED with exitCode 0 instead of FAILED.
5. Cause 3: SubmitJob with retryStrategy={"attempts":2,"evaluateOnExit":[{"onExitCode":"42","action":"RETRY"}]} and a container that exits 42 on attempt 1; DescribeJobs reports one attempt with exitCode 0.
6. Cause 4: SubmitJob with a long-running container and poll DescribeJobs immediately — the first read already reports SUCCEEDED, so TerminateJob can never be issued against a RUNNING job.
