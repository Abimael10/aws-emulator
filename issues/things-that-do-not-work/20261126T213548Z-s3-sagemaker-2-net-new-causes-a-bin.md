# s3__sagemaker: 2 net-new causes — a /bin/bash processing-job entrypoint ends Failed with "AlgorithmError: , exit code: 127", and a /bin/sh entrypoint carrying its command inline ends Failed with no ExitMessage, so neither job's declared S3 output is ever written

> _Note: this issue was identified against the code base at commit `c1cd4212afc197fe1cfacedba13fee3a86116d28`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
CreateProcessingJob

## Description
Two net-new root causes in the SageMaker processing-job execution path reached over S3. This issue bundles TWO causes and BOTH must be closed before submitting; each has its own failing check listed under its Traces line.

Neither is covered by the open issue 20261024T160943Z-sagemaker-runs-no-job-work-processing-pipeline-step.md (whose Cause 1 describes a job that never runs at all and reports FailureReason "This emulator has no container runtime ..." — that reason is gone here, the executor now starts a program and reports a container exit code), nor by the fixed issue 20261116T100406Z-s3-sagemaker-2-net-new-causes-a-completed.md (a Completed /bin/sh job that uploaded nothing, and a python3 training entrypoint). Here the two jobs below never reach Completed at all, so they are a different failure point than those issues carry.

Cause 1 of 2: a processing job whose AppSpecification.ContainerEntrypoint is ["/bin/bash","-c"] with the shell command in ContainerArguments ends ProcessingJobStatus=Failed with FailureReason "AlgorithmError: , exit code: 127" instead of running the command.
AWS: Smithy (sagemaker): AppSpecification.ContainerEntrypoint — "The entrypoint for a container used to run a processing job" — with ContainerArguments supplying that entrypoint's arguments; DescribeProcessingJob returns the required ProcessingJobStatus enum plus the optional FailureReason ("the reason a processing job failed") and ExitMessage ("metadata from the processing container when the processing job exits"), and ProcessingS3Output.LocalPath is the directory SageMaker uploads to S3Uri at S3UploadMode=EndOfJob. Recorded AWS runs that entrypoint inside the named image, so an ordinary POSIX shell command (`mkdir -p`, a `for` loop over the input directory, `tr`) executes, the job reaches Completed and one object per file written under LocalPath appears under S3Output.S3Uri with identical bytes. Exit code 127 is "command not found"; AWS does not produce it for a well-formed bash entrypoint against an image that provides bash, and when AWS does surface a container failure it carries the container's own message, never an empty one.
Emulator: the job settles Failed with FailureReason "AlgorithmError: , exit code: 127" — i.e. the program named by the entrypoint (or a command the shell command uses) was not found, and the message's variable part (the container's exit message) is EMPTY: its fixed text is "AlgorithmError: " + ", exit code: <code>" with nothing in between and no ExitMessage. The declared output prefix stays empty, so the per-file GetObject that follows cannot be served.
Why: the single most common SageMaker Processing idiom — a shell entrypoint plus a one-line transform in ContainerArguments — never completes. A client polling DescribeProcessingJob to Completed takes the failure branch forever, and the reason it is handed names no missing program and carries no container output, so it cannot distinguish "my command is wrong" from "the service ran nothing".
Fix: the CreateProcessingJob execution path — the in-process container-program executor behind AppSpecification.ContainerEntrypoint/ContainerArguments (it must provide the shell the entrypoint names, `/bin/bash` included, and the coreutils an entrypoint command uses) and the terminal status plus FailureReason/ExitMessage the job state records, read back by DescribeProcessingJob.
Traces: s3__sagemaker.cli-s3-upload-then-sagemaker-processing-job-workflow.

Cause 2 of 2: a processing job whose ContainerEntrypoint carries its command INLINE — ["/bin/sh","-c","cp -r /opt/ml/processing/input/. /opt/ml/processing/output/"] with no ContainerArguments member — ends ProcessingJobStatus=Failed and DescribeProcessingJob reports no ExitMessage at all.
AWS: Smithy: ContainerEntrypoint is a list of strings and ContainerArguments is optional, so the whole command may be given as entrypoint members; recorded AWS runs it, the job reaches Completed, and the input object copied out of ProcessingS3Input.LocalPath appears at S3Output.S3Uri byte-for-byte (here the stack bucket's input/hello.txt re-appears as output/hello.txt). When a processing job does fail, DescribeProcessingJob carries ExitMessage (the container's own exit metadata) and/or FailureReason stating why — a Failed job with neither is not a state AWS reports.
Emulator: ProcessingJobStatus 'Failed' with ExitMessage absent (None in the read-back), and nothing under the declared output prefix. A /bin/sh entrypoint that takes its command from ContainerArguments is known to execute in this emulator, so the divergence is specific to the inline-command entrypoint form (and to `cp -r <dir>/. <dir>/`), which it does not run.
Why: a client using the inline-entrypoint form gets a Failed job with no explanation whatsoever — no ExitMessage, no container output — and the S3 round trip the job exists to perform silently produces nothing; a role/trust positive control built on such a job (as here, proving a CFN-created sagemaker.amazonaws.com-trusted role is actually assumed) can never be established, so a genuine authorization failure and a never-run container are indistinguishable.
Fix: the CreateProcessingJob execution path — argv assembly in the container-program executor when AppSpecification.ContainerEntrypoint already contains the command and ContainerArguments is absent, and the FailureReason/ExitMessage the job state must record for any job it ends Failed.
Traces: s3__sagemaker.deploy-cfn-sagemaker-execution-role-trust-policy-positive.
