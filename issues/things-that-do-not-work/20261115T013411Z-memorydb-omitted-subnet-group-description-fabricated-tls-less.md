# memorydb: omitted subnet-group Description fabricated, TLS-less CreateCluster accepted with a custom ACL, and an available cluster serves no RESP data plane

> _Note: this issue was identified against the code base at commit `ab88f803a4e379013b8a9f7f3c950c61c3772e52`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
CreateCluster

## Description
Replaying the behavioral corpus (simparity-behavioral-aws-v1) against the memorydb emulator left 4 checks failing, which cluster into THREE distinct root causes, all in memorydb. A fixer must close ALL THREE before submitting.

Related open issues that do NOT cover any of these: `20261104T053017Z-memorydb-createsubnetgroup-stub.md` ("Implement memorydb CreateSubnetGroup: unimplemented scaffold stub") — CreateSubnetGroup is now implemented and answers 200 in this replay, and all four checks get past it; and `20261114T234007Z-memorydb-subnet-group-operations-diverge-from-aws-on.md`, which owns the absent `SupportedNetworkTypes`, the acceptance of unknown subnet ids and the DescribeSubnetGroups MaxResults error shape. Nothing in either addresses the three faults below. (The `SupportedNetworkTypes` assertion later in the subnet-group check, line 1149, is that issue's Cause 1 and is deliberately NOT re-filed here; the check fails one line earlier, on Description.)

Cause 1 of 3: CreateSubnetGroup fabricates a Description for a request that omitted one.
  AWS: recorded behavior only — Smithy (com.amazonaws.memorydb) makes `CreateSubnetGroupRequest$Description` and `SubnetGroup$Description` optional `String` ("A description of the subnet group") and states no default. The recording shows that when `Description` is omitted from CreateSubnetGroup, the returned `SubnetGroup` carries NO `Description` member at all (the member is absent from the response document, so an SDK dict has no such key), and every later DescribeSubnetGroups of that group reports it the same way. Only a description the caller actually supplied is reported back.
  Emulator: the create succeeds (200) but the response's `SubnetGroup.Description` is present and set to a service-invented placeholder — a single space `' '` — because `create_subnet_group.rs` substitutes `crate::state::DEFAULT_SUBNET_GROUP_DESCRIPTION` for a missing `input.description` when building `StoredSubnetGroup`, so the fabricated value is persisted and re-reported by every describe too.
  Why: a client cannot distinguish "no description" from "a description that is one blank character". Code that branches on the member's presence (IaC drift detection, console rendering, round-trip tests that re-apply the described value) sees a description appear out of nowhere, reports permanent drift against a template that sets none, and may fail a non-empty/trimmed-text validation on read-back. The same fabricated value then flows into DescribeSubnetGroups and UpdateSubnetGroup read-backs.
  Fix: the CreateSubnetGroup handler and the subnet-group state projection — `StoredSubnetGroup.description` must stay optional and un-defaulted when the request omits it, and `to_api()` must leave `SubnetGroup$Description` unset rather than emitting a placeholder, so create, update and describe all report absence identically. Any other memorydb write path that defaults a description through the same constant needs the same treatment.
  Traces: memorydb.subnet-group-update-replaces-subnet-set.

Cause 2 of 3: CreateCluster accepts `TLSEnabled=false` together with an ACL other than the built-in `open-access`.
  AWS: a non-TLS MemoryDB cluster supports only the built-in `open-access` ACL. A CreateCluster whose `TLSEnabled` is `false` and whose `ACLName` names any customer-created ACL is refused with HTTP 400, error code `InvalidParameterValueException` (Smithy: `com.amazonaws.memorydb#InvalidParameterValueException`, client error, httpError 400, awsQueryError code `InvalidParameterValue`, documented "The specified parameter value is not valid." — a modeled error of CreateCluster), and message `Custom ACL [<ACLName>] is not supported for non TLS clusters. Supported ACLs are [open-access].` The fixed text is `Custom ACL [` … `] is not supported for non TLS clusters. Supported ACLs are [open-access].`; the only variable part is the ACL name, taken verbatim from the request's `ACLName`. The rule is about the ACL being customer-created, not about its contents: an ACL with no users attached is refused with the same code and the same message naming that ACL. Nothing is persisted, so a subsequent DescribeClusters for that cluster name answers `ClusterNotFoundFault` / `Cluster <name> not found.` The ordering also matters: with `ACLName="open-access"` and a `ParameterGroupName` that does not exist, AWS refuses for the parameter group instead (`ParameterGroupNotFoundFault`, `ParameterGroup not found: <name>`), i.e. the TLS-disabled + open-access combination is itself accepted.
  Emulator: the call is ACCEPTED. `CreateCluster(TLSEnabled=false, ACLName=<customer ACL>)` answers 200 with `Cluster.Status = "creating"`, inserts the cluster into state, and the clock later settles it to `available`; DescribeClusters then lists a cluster AWS would never have created. `services/.../src/ops/create_cluster.rs` validates the cluster name, node type, ACL name form, engine/version, shard and replica counts, description, tags, snapshot/multi-region names, subnet group, ACL existence and parameter group existence, but never compares `input.tls_enabled` against the resolved ACL, so no TLS/ACL combination rule exists anywhere in the handler.
  Why: a client that relies on AWS refusing this combination (a test suite asserting the rejection, or an IaC/deploy path that treats a 200 as "this configuration is supported") succeeds against the emulator and fails against AWS — and in the emulator it now holds a cluster whose advertised security posture (no in-transit encryption plus a password-authenticated custom ACL) AWS does not offer, so every later describe, update and delete operates on a resource that cannot exist. Because the acceptance also hides the refusal ordering, the open-access + missing-parameter-group case can no longer be distinguished either.
  Fix: the CreateCluster handler's validation — after the ACL is resolved against state (and before the cluster is built or inserted), refuse `TLSEnabled=false` with any ACL other than the built-in `open-access` as the modeled `InvalidParameterValueException` (HTTP 400) with the message above, independent of whether that ACL has users. UpdateCluster's ACL repoint and any TLS toggle must read the same rule from one place.
  Traces: memorydb.tls-disabled-cluster-with-a-custom-acl-rejected.

Cause 3 of 3: an `available` cluster advertises a ClusterEndpoint but serves no RESP data plane — nothing can connect to the address it announces.
  AWS: recorded behavior only (the data plane is not in the Smithy model). An `available` MemoryDB cluster accepts TCP connections at `Cluster.ClusterEndpoint.Address` : `Cluster.ClusterEndpoint.Port` from inside its VPC and speaks RESP2/RESP3 there — over TLS when the cluster was created with `TLSEnabled=true`, plain TCP otherwise. The recordings drive that socket from a Lambda function attached to the same subnets and security group and get real replies: `AUTH <user> <password>` succeeds and a wrong password is refused, `HELLO`/`INFO server` name the engine the control plane reports (`redis` for an Engine="redis" cluster, Valkey otherwise) and its version, `SET`/`GET` round-trip a key, commands the engine does not carry are answered as unknown, and a command issued before AUTH on an ACL-enforced cluster is refused by the ACL.
  Emulator: the control plane is fine up to this point — CreateSubnetGroup, CreateUser, CreateACL and CreateCluster all succeed, the cluster leaves `creating` as `available`, and it reports an `Engine`, an `EngineVersion` and a `ClusterEndpoint` with an address and port. But the announced endpoint answers nothing: the in-VPC probe's `socket` connect fails before a single command is written, with `OSError: a Lambda function in this emulator has no host network to reach`, and the probe reports the session as broken after zero replies (`DATAPLANE_UNIMPLEMENTED: ... broke after []`). It fails identically for the TLS Engine="redis" cluster and for the Valkey cluster's plain and TLS sessions, so no RESP conversation of any kind completes.
  Why: every client that actually uses MemoryDB talks to this socket — the control plane only tells it where to connect. A client built against the emulator gets a cluster that reports itself `available` with a usable endpoint and then cannot be used at all: connection attempts fail at the transport, so engine identity, ACL/AUTH enforcement, and ordinary key reads and writes are all unobservable, and any test that exercises cache behavior (or an application boot that waits for a successful PING) hangs or dies on connect while the control plane insists everything is healthy.
  Fix: the memorydb cluster's data-plane listener and the network path that reaches it — an `available` cluster must bind and serve RESP at exactly the address and port it advertises in `ClusterEndpoint` (and on each shard/node endpoint), TLS-wrapped when `TLSEnabled=true`, enforcing the cluster's ACL for AUTH, and the emulator's in-VPC compute (the Lambda execution environment created with a `VpcConfig` on the cluster's subnets) must be able to open a TCP connection to it instead of refusing every connect with "no host network to reach". The engine identity the data plane reports must come from the same stored cluster fields the control plane serializes, so `HELLO`/`INFO` cannot disagree with `DescribeClusters`.
  Traces: memorydb.redis-oss-cluster-identifies-as-redis-over-the-wire, memorydb.valkey-cluster-serves-acl-enforced-resp-over-tls-and-runs-its-lifecycle.
