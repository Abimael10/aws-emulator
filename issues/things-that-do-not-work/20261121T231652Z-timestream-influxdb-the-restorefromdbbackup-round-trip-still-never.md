# timestream-influxdb: the RestoreFromDbBackup round trip STILL never converges — create instance → backup → restore → AVAILABLE cannot complete, because every lifecycle settle is owed 3 s after the announcing call and costs a polling client a whole probe interval

> _Note: this issue was identified against the code base at commit `f6adbb8692a84d5fa8e9d4a779005b7b7af85337`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
RestoreFromDbBackup

## Description
One net-new root cause in the timestream-influxdb emulator, grounded in the only failing behavioral check of this service that is neither ALREADY FILED nor OWNED by an open issue (the other two timestream-influxdb failures are OWNED by 20261114T190856Z-...-duplicate-name-restore-round--r2.md and 20261116T094729Z-...-influxdb-v2.md, and both cloudformation__timestream-influxdb failures are OWNED by 20261109T183400Z-cloudformation-timestream-influxdb-....md).

Recurrence note: the resolved issue 20261120T233502Z-timestream-influxdb-the-restorefromdbbackup-round-trip-never-converges.md claimed this same workflow fixed. Its fix is visible in the checkout — `TRANSITION_SPAN` was raised from 25 ms to `Duration::from_secs(3)` (services/service-com-amazonaws-timestreaminfluxdb-amazontimestreaminfluxdb/src/state.rs) and the settle re-dating after the socket bind was removed from `serve_over` (src/state/influx_data_plane.rs) — but the check it was filed from still fails identically, so the workflow is still not reachable by a polling client. This is NOT a refusal: every call in the sequence answers 2xx. It is re-filed because a resolved issue does not cover a still-failing check.

Cause 1 of 1: the backup/restore round trip of this service never reaches its terminal state for a client that polls the API. A workflow that creates a DB instance, waits for AVAILABLE, takes an on-demand backup, waits for COMPLETED, restores it and waits for the restored instance to reach AVAILABLE does not converge: the check that walks exactly that sequence exhausts its whole budget and is reported as `Check timed out after 60.0s`, never reaching its final assertions. No call is refused and no assertion fails — the divergence is purely that the lifecycle the API announces is not REACHED within a time a client polling the API can observe.

AWS: Smithy model of this service — `RestoreFromDbBackup` output carries `restoredDbResourceId` (DbResourceId), `restoreStatus` (RestoreStatus, whose only member is RESTORING), `resourceType` (ResourceType: DB_CLUSTER | DB_INSTANCE; the recording shows AWS puts the wire value `db-instance` here) and `deploymentType`/`engineType`; `GetDbInstance$status` is the `Status` enum (CREATING, AVAILABLE, DELETING, MODIFYING, UPDATING, DELETED, FAILED, UPDATING_DEPLOYMENT_TYPE, UPDATING_INSTANCE_TYPE, MAINTENANCE, REBOOTING, REBOOT_FAILED, RESTORING, RESTORE_FAILED); `GetDbBackup$status` is the `DbBackupStatus` enum (IN_PROGRESS, COMPLETED, FAILED, DELETING, DELETED). `CreateDbBackup` is documented "Creates a new on-demand backup of a Timestream for InfluxDB resource" and `RestoreFromDbBackup` "Restores a Timestream for InfluxDB resource from a backup. By default, a new resource is created." The transition TIMING is recorded behavior only: AWS takes minutes per transition, and the requirement the recording establishes is that every one of the three transitions is eventually reached and observable through the polled read — CreateDbInstance's record leaves CREATING for AVAILABLE, CreateDbBackup's leaves IN_PROGRESS for COMPLETED, and the resource RestoreFromDbBackup mints leaves RESTORING for AVAILABLE with `name` equal to the restore request's `name` and an `id` distinct from the source instance's — so a client's wait loop terminates.

Emulator: the sequence never terminates inside the budget a check gets. Verdict [mismatch], detail `Check timed out after 60.0s`; no error code, no non-2xx status and no failed assertion, so the time was spent inside the check's poll loops. Hypothesis (the model says nothing about timing, so this names the emulator code the behavior comes from rather than a recorded value): every lifecycle record in this service owes its settle exactly one `TRANSITION_SPAN` = 3 s after the call that announced the transition — `TRANSITION_SPAN` in src/state.rs, applied by `DbInstance::begin_transition`/`DbInstance::settle` there, by `insert_db_backup` (status IN_PROGRESS, settles_at = now + TRANSITION_SPAN) and `DbBackup::settle` in src/state/backups.rs, and by `restored_db_instance` (status RESTORING, settles_at = now + TRANSITION_SPAN) in src/state/restores.rs. The constant's own doc comment states the intent — it is deliberately "WELL ABOVE the round trip a client needs to issue its next request" so the transient status stays client-visible — but that is exactly what makes a POLLING client pay: its first read after the announcing call still observes the transient status (CREATING / IN_PROGRESS / RESTORING) and it then sleeps a whole probe interval. This workflow chains THREE such transitions, whose probe intervals are 30 s + 20 s + 30 s = 80 s of client sleeping, more than the whole check has, so the restore workflow can never finish — while the single-transition checks of this service (16 of 19 pass) still fit. The previous fix only moved the span from 25 ms to 3 s, which is on the same side of a loopback round trip, so nothing about the convergence changed.

Why: backup and restore is the disaster-recovery path of this service, and a client cannot complete it. Every call answers success, the restore even reports `restoreStatus=RESTORING` and a `restoredDbResourceId`, and then the client's wait loop — the normal way the AWS SDK waiters, the CLI's wait-style loops and infrastructure tools consume an asynchronous lifecycle — never observes the terminal status within any budget proportional to an emulator's speed. The failure mode is the worst kind: no error to handle, just a workflow that hangs until the caller's own deadline, and a caller that bounds its wait concludes the restore failed while the emulator reports no failure at all.

Fix: the lifecycle-settle timing of this service's state, for all three records the workflow walks — the DB instance (`TRANSITION_SPAN`, `begin_transition`, `settle` in src/state.rs), the DB backup (`insert_db_backup`, `DbBackup::settle` in src/state/backups.rs) and the restored record (`restored_db_instance` in src/state/restores.rs). The owed transition must already be DUE by the time a polling client's NEXT read arrives, while keeping the transient status observable in the announcing call's own response — e.g. settle on the first reporting read that FOLLOWS the announcing call (count reads rather than wall-clock seconds), so that a chained create → backup → restore workflow costs no probe interval per transition. Raising or lowering a wall-clock span alone cannot satisfy both halves, which is why the previous attempt did not converge.

The per-transition cost is what the emulator chooses. In the current checkout: src/state.rs declares `pub const TRANSITION_SPAN: Duration = Duration::from_secs(3);` with a doc comment stating it is deliberately "WELL ABOVE the round trip a client needs to issue its next request"; `DbInstance::settle` flips to AVAILABLE only once `now >= settles_at`, and `DbInstance::begin_transition` sets `settles_at = Some(now + TRANSITION_SPAN)`; src/state/backups.rs `insert_db_backup` stores status IN_PROGRESS with `settles_at: Some(now + TRANSITION_SPAN)`; src/state/restores.rs `restored_db_instance` stores status RESTORING with `settles_at: Some(now + TRANSITION_SPAN)`. Three chained transitions at 30 s + 20 s + 30 s probe intervals is 80 s of client sleeping against a 60 s budget. (The earlier re-dating of the restored record's settle after the data-plane socket bind is gone from `serve_over` in src/state/influx_data_plane.rs, and `src/ops/restore_from_db_backup.rs` still awaits `restore_db_instance_plane` — that half of the earlier report is addressed; the per-transition span is not.) Instance ids, backup ids, names and the exact interval arithmetic of any one run are that run's values; the defect is that the restore workflow does not converge for a client that polls the API.

## Steps to Reproduce
1. Create (or reuse) a VPC with at least two subnets and a security group.
2. CreateDbInstance(name=<SRC>, password=<8-64 chars matching ^[a-zA-Z0-9]+$>, dbInstanceType="db.influx.medium", vpcSubnetIds=[<two subnets>], vpcSecurityGroupIds=[<sg>], allocatedStorage=20, dbStorageType="InfluxIOIncludedT1", deploymentType="SINGLE_AZ"); keep the returned `id` as <src id>.
3. Poll GetDbInstance(identifier=<src id>) every 30 s until `status` is AVAILABLE or FAILED. Note the FIRST read, issued immediately after step 2, still reports CREATING, so the loop sleeps 30 s.
4. CreateDbBackup(name=<BKP>, dbResourceId=<src id>, retentionDays=1); keep the returned `id` as <backup id>.
5. Poll GetDbBackup(identifier=<backup id>) every 20 s until `status` is COMPLETED or FAILED. The first read, issued immediately after step 4, still reports IN_PROGRESS, so the loop sleeps 20 s.
6. RestoreFromDbBackup(name=<RESTORED>, dbBackupId=<backup id>); keep `restoredDbResourceId` as <restored id>. (`restoreStatus`=RESTORING and `resourceType`="db-instance" are returned correctly.)
7. Poll GetDbInstance(identifier=<restored id>) every 30 s until `status` is AVAILABLE or FAILED.
   EXPECTED: the whole sequence converges — the restored instance reports status AVAILABLE, `name`=<RESTORED> and an `id` distinct from <src id>.
   ACTUAL: each of the three transitions costs the poller a full probe interval (30 s + 20 s + 30 s = 80 s of sleeping), so the sequence cannot finish inside the suite's 60 s per-check budget; the run ends as `Check timed out after 60.0s` with no error and no failed assertion, and the restored instance's terminal status is never observed.
