# sagemaker DescribeTrainingJob read-back omits algorithm metric definitions and image metadata

> _Note: this issue was identified against the code base at commit `53ca3190ddccd906197b0d4d5e8474d7add13c5d`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
DescribeTrainingJob

## Description
2 causes, one shared fault: the DescribeTrainingJob output projection does not report the detail AWS RESOLVES from the training container image onto the job. AWS answers a describe of a job launched from a first-party (built-in) algorithm image with the image's own metadata (what kind of image it is, and the digest-pinned path it resolved to) and with the algorithm's metric set; this emulator either omits those members or emits only a locally derived fragment of them. Both causes answer 200 with every other asserted member matching, so a client gets a well-formed response with the image/algorithm provenance silently absent. A fixer must close BOTH clusters.

Cause 1 of 2: DescribeTrainingJob omits ImageMetadata.ImageType for a job launched from an AWS built-in algorithm image, and fills ImageMetadata.ResolvedImage with a locally synthesized, foreign-host value (fixture sagemaker-train-host-and-invoke-xgboost-model, step task#6).
AWS: Smithy (services/service-com-amazonaws-sagemaker-sagemaker/smithy-model/com-amazonaws-sagemaker-sagemaker.json): DescribeTrainingJob input TrainingJobName required @length 1..63 @pattern ^[a-zA-Z0-9](-*[a-zA-Z0-9]){0,62}$; output shape DescribeTrainingJobResponse (required TrainingJobName, TrainingJobArn, ModelArtifacts, TrainingJobStatus, SecondaryStatus, StoppingCondition, CreationTime), single modelled error ResourceNotFound (client, httpError 400 [defaulted]). An ImageMetadata member is NOT declared in this checkout's DescribeTrainingJobResponse, so for that member it is recorded behavior only: the recorded 200 response for a completed job launched from an AWS-published built-in algorithm image carries ImageMetadata with an ImageType classifying the image as a SageMaker first-party algorithm image (the recording's value is 'SageMaker1PAlgorithm'), i.e. a classification that follows from WHICH image the job's AlgorithmSpecification.TrainingImage names, not from this run. The sibling member ImageMetadata.ResolvedImage carries the digest-pinned path of the image actually pulled, in the registry/repository@digest form AlgorithmSpecification.TrainingImage's doc describes ("SageMaker supports both registry/repository[:tag] and registry/repository[@digest] image path formats") - a property of the published image, identical on every account and run.
Emulator: answers 200 with $.ImageMetadata.ImageType absent (replay: "$.ImageMetadata.ImageType: missing (expected 'SageMaker1PAlgorithm', got None)") and with $.ImageMetadata.ResolvedImage carrying a value the replay flags host_not_own (expected None, got a real AWS ECR path with a sha256 digest the emulator derived locally) - the same locally derived digest the endpoint read-back shows for the same image. No error, no status divergence.
Why: a client that reads ImageMetadata to learn whether a job ran a first-party algorithm image or a customer-supplied container - the discriminator a pipeline uses before trusting the algorithm's built-in metric names, its hyperparameter contract or its artifact layout - gets no ImageType at all and reads the job as having no image classification, so first-party-only handling is skipped on a job that is first-party. Reading ResolvedImage to pin or audit the exact image version gets a digest that matches no published image, so provenance checks and image-drift alarms misfire on a healthy job.
Fix: the DescribeTrainingJob handler's output projection plus the training-job state it reads: CreateTrainingJob must resolve the named training image to its classification and its digest-pinned path, store both on the job, and the describe serializer must emit them rather than compute a digest at read time. Hypothesis: the digest is recomputed from the image URI on each read, which is why it is self-consistent but matches nothing published.
Traces: sagemaker-train-host-and-invoke-xgboost-model#task#6.
Not requirements in this cluster: $.CreationTime, $.LastModifiedTime, $.TrainingStartTime, $.TrainingEndTime and $.FinalMetricDataList[0].Timestamp are each reported against '<shaped-not-asserted>' - per-run clock values, excluded from the cause.
Ownership note: open issue 20261120T143955Z-sagemaker-training-job-and-endpoint-read-backs-lose.md names this same fixture/step, but the replay now reports this cluster with NO owner because its replay key changed - the key no longer carries $.AlgorithmSpecification.MetricDefinitions and now names the ImageMetadata SUB-members (service=sagemaker|DescribeTrainingJob|status=200->200|keys=$.CreationTime,$.FinalMetricDataList[0].Timestamp,$.ImageMetadata.ImageType,$.ImageMetadata.ResolvedImage,$.LastModifiedTime,$.TrainingEndTime,$.TrainingStartTime). The ImageType omission and the synthesized ResolvedImage are therefore unowned and filed here with the current key. Also related but not covering it: 20261115T014541Z-sagemaker-container-imagedigest-fields-are-locally-synthesized-instead.md reports the same synthesized-digest helper on DescribeAlgorithm.TrainingSpecification.TrainingImageDigest and DescribeModelPackage.InferenceSpecification.Containers[].ImageDigest.

Cause 2 of 2: DescribeTrainingJob drops AlgorithmSpecification.MetricDefinitions entirely, together with the same two ImageMetadata members, on a second training-job fixture (fixture sagemaker-training-job-hyperparameter-numeric-precision-preserved, step task#4).
AWS: Smithy: DescribeTrainingJob output member AlgorithmSpecification -> AlgorithmSpecification; AlgorithmSpecification.MetricDefinitions -> MetricDefinitionList, @length 0..40, documented "A list of metric definition objects. Each object specifies the metric name and regular expressions used to parse algorithm logs. SageMaker publishes each metric to Amazon CloudWatch." MetricDefinition is a structure with required Name (MetricName, @length 1..255, @pattern ^.+$, "The name of the metric") and required Regex (MetricRegex, @length 1..500, @pattern ^.+$, "A regular expression that searches the output of a training job and gets the value of the metric"). AlgorithmSpecification.EnableSageMakerMetricsTimeSeries documents that time-series metrics are generated without the flag when "You use one of the SageMaker built-in algorithms" - a built-in algorithm image brings its OWN fixed metric set, so AWS resolves that set onto the described job even when CreateTrainingJob supplied no MetricDefinitions, and returns one {Name, Regex} entry per metric the algorithm publishes. The requirement is the metric NAMES and their log-scraping regex templates, which follow from the algorithm image (the recorded set for this fixture's image is train:/validation:/test: families such as validation:binary_log_loss, test:dcg, train:progress, validation:mae, train:objective_loss, validation:macro_precision, test:mse, train:recall, with regexes of the algorithm's '#quality_metric: host=\\S+, <metric> <loss|score>=(\\S+)' / '#progress_metric: host=\\S+, completed (\\S+) %' template form) - not from this run. ImageMetadata: recorded behavior only, as in Cause 1.
Emulator: answers 200 with $.AlgorithmSpecification.MetricDefinitions absent (replay: "missing (expected [{'Name': 'validation:binary_log_loss', 'Regex': '#quality_metric: host=\\S+, validation binary_logloss <None>=(\\S+)'}, ...], got None)"), and with $.ImageMetadata.ImageType and $.ImageMetadata.ResolvedImage diverging the same way as Cause 1.
Why: MetricDefinitions is the only place a built-in algorithm's metric set is exposed. A client that reads it to learn which metric names a job emits and which regexes parse them - the standard SageMaker analytics and hyperparameter-tuning path - gets nothing, concludes the job publishes no metrics, collects none, and a tuning objective keyed on one of those names can never be satisfied.
Fix: the training-job state written by CreateTrainingJob (the algorithm image's metric set must be resolved onto the stored job) and the DescribeTrainingJob output projection that must echo AlgorithmSpecification.MetricDefinitions and the image metadata back. Same component as Cause 1; one shared resolution step is likely to close both.
Traces: sagemaker-training-job-hyperparameter-numeric-precision-preserved#task#4.

The metric names, regexes, image classification and digests quoted above are this corpus's values filling the templates; the requirements are that the metric set and the image classification follow from the algorithm image named in AlgorithmSpecification, and that the reported resolved image be the digest-pinned path of the image actually used.
