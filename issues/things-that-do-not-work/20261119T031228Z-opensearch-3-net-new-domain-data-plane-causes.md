# opensearch: 3 net-new domain data-plane causes — a terms aggregation with a nested `aggs` block is refused 400 parsing_exception, the `script` ingest processor is unregistered, and the ISM add/remove/explain routes are unhandled

> _Note: this issue was identified against the code base at commit `f404f97a3a4ab7778ea30dcdc06070c22261d90a`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
ESHttpPost

## Description
Three independent root causes on the OpenSearch domain REST data plane that the emulator serves on DomainStatus.Endpoint. All three are reached only AFTER a domain was created, became searchable and its data plane stopped answering 403, so the domain lifecycle itself is not at fault here — each cause is a specific data-plane surface answering wrongly. None of these checks is marked ALREADY FILED or OWNED in this suite run.

NOTE on the model: the domain REST data plane (`_search`, `_ingest/pipeline`, `_plugins/_ism`) is NOT described by the opensearch Smithy model — that model covers only the control plane (CreateDomain/DescribeDomain/...). For these three causes AWS's behaviour is therefore 'recorded behaviour only' plus the documented OpenSearch engine/plugin API that Amazon OpenSearch Service exposes on the domain endpoint; statuses, error types and error reasons below are quoted from the replayed responses.

=== Cause 1 of 3: a terms aggregation that carries a nested `aggs` sub-aggregation block is refused 400 instead of executed ===
AWS: recorded behaviour only. On a domain endpoint, `POST /<index>/_search` with a body such as `{"size":0,"aggs":{"<name>":{"terms":{"field":"<field>","size":<n>},"aggs":{"<sub>":{"avg":{"field":"price"}}}}}}` answers HTTP 200 and returns `aggregations.<name>.buckets`, each bucket carrying `key`, `doc_count` and the sub-aggregation results, with `sum_other_doc_count` holding the remainder when `size` truncates. The engine counts the aggregation TYPE keys inside an aggregation body while EXCLUDING the reserved keys `aggs` / `aggregations` / `meta`; the parsing_exception whose reason is the fixed text `[<agg name>] aggregation must name exactly one type` (the variable part is the aggregation's own name, taken from the request) is raised only when the body names zero or more than one actual aggregation type.
Emulator: any aggregation body that also contains a nested `aggs` key is refused. Both replayed checks get HTTP 400 with `{"error":{"root_cause":[{"type":"parsing_exception","reason":"[<name>] aggregation must name exactly one type"}],"type":"parsing_exception","reason":"[<name>] aggregation must name exactly one type"},"status":400}` — i.e. the reserved `aggs` key is counted as a second aggregation type, so `terms` + `aggs` reads as two types. The emulator-authored reason text is AWS's text for a genuinely malformed body, so the status/type/reason are right for a different request and wrong for this one: the request is well formed.
Why: a client that asks for the standard one-level-deep bucket-plus-metric aggregation (terms with avg/sum/stats sub-aggregations — dashboards, faceted search, any report that needs a per-bucket metric) gets a hard 400 parse error and has no way to express the query at all. Because the refusal is phrased as a client-side parse error, the caller concludes its own query is malformed and retries it unchanged against real AWS, where it works.
Fix: the aggregation-request parser of the domain data plane in the opensearch service crate — the code that validates 'exactly one type' per aggregation must skip the reserved keys `aggs`, `aggregations` and `meta` before counting, and then recurse into the nested `aggs` map and evaluate the sub-aggregations per bucket.
Traces: opensearch.osq-terms-aggregation-and-sorted-pagination (terms on `category` with `avg_price`/`sum_price` sub-aggs, `size:10`), opensearch.search-aggregation-query-bucket-ordering (terms on `category` with a `price_stats` stats sub-agg). Related but NOT covering: open issue 20261115T222423Z-opensearch-8-net-new-data-plane-causes-a.md ('aggregations are dropped') and 20261111T041122Z-opensearch-ten-search-engine-divergences-on-the-domain.md ('no terms buckets') describe aggregations MISSING from an HTTP 200 response; this cause is a 400 refusal of the request before any aggregation runs, and neither issue carries these two checks' replay keys.

=== Cause 2 of 3: the `script` (painless) ingest processor is not registered, so an ingest pipeline containing one cannot be created ===
AWS: recorded behaviour only. `PUT /_ingest/pipeline/<id>` with `{"description":...,"processors":[{"set":...},{"lowercase":...},{"convert":...},{"script":{"lang":"painless","source":"ctx.count_squared = ctx.count * ctx.count"}}]}` answers HTTP 200 with `{"acknowledged":true}`; `script` is one of the ingest processors Amazon OpenSearch Service supports on a domain, and the pipeline then rewrites documents on index (and `_ingest/pipeline/_simulate` predicts the same `_source`). The parse_exception whose reason is the fixed text `No processor type exists with name [<type>]` (the variable part is the processor type from the request) is AWS's refusal of an UNKNOWN processor type — `script` is not one.
Emulator: `PUT /_ingest/pipeline/<id>` answers HTTP 400 with `{"error":{"root_cause":[{"type":"parse_exception","reason":"No processor type exists with name [script]"}],"type":"parse_exception","reason":"No processor type exists with name [script]"},"status":400}`. The processor registry recognises `set`, `lowercase` and `convert` (the pipeline is parsed far enough to reach the fourth entry) but has no `script` processor, so a supported processor type is reported as nonexistent.
Why: a client cannot create any pipeline that computes a derived field, which is the single most common use of ingest pipelines; because the refusal says the type does not exist, the client cannot distinguish 'this processor is unsupported here' from 'my pipeline definition is misspelled'. Everything downstream of the pipeline (index.default_pipeline rewriting on write, `_simulate` agreeing with the stored `_source`, and the 400 illegal_argument_exception for a document the pipeline cannot process) is unreachable.
Fix: the ingest-pipeline processor registry and executor of the domain data plane in the opensearch service crate — register a `script` processor that evaluates a painless `source` against the document context (`ctx`), and make `_simulate` and the on-index pipeline run share that implementation so they cannot disagree.
Traces: opensearch.ingest-pipeline-rewrites-stored-source-and-simulate-predicts-it.

=== Cause 3 of 3: the ISM plugin's add/remove/explain routes are unhandled, so a stored ISM policy can never be attached to an index ===
AWS: recorded behaviour only. On a domain endpoint the Index State Management plugin serves `POST /_plugins/_ism/add/<index>` with `{"policy_id":"<id>"}` → HTTP 200 and a body carrying `failures:false`, `failed_indices:[]` and `updated_indices`; a second add of the same index → HTTP 200 with `failures:true` and a per-index failure whose reason names the update API; `GET /_plugins/_ism/explain/<index>` → HTTP 200 keyed by index name with `policy_id`, `state.name`, `action.name`, `action.failed`, `step.name`, `step.step_status` and `info.message`; `POST /_plugins/_ism/remove/<index>` → HTTP 200 with `failures:false`. The sibling route `PUT /_plugins/_ism/policies/<id>` is served by this emulator (it answered 201 with `_id`/`_version` in the replay), so the plugin surface is partially present.
Emulator: `POST /_plugins/_ism/add/<index>` answers HTTP 400 with the engine's unrouted-path body `{"error":"no handler found for uri [/_plugins/_ism/add/<index>] and method [POST]"}` — the path is not registered at all. Note the shape of that refusal too: `error` is a bare string, not the `{"error":{"type":...,"reason":...},"status":...}` object AWS returns, and AWS answers an unknown path 405/400 with a `root_cause`-bearing object, so a client's error parsing breaks as well.
Why: an ISM policy can be stored but never applied, so no index lifecycle automation works on this emulator: no state transition on a condition (`min_doc_count`), no `read_only` action setting `index.blocks.write`, no `explain` observability, and no detach. A client polling `_ism/explain` to confirm its policy took effect loops forever against a 400, and because the policy PUT succeeded it has every reason to believe ISM is available.
Fix: the domain data plane's route table and ISM plugin state in the opensearch service crate — register `POST /_plugins/_ism/add/<index>`, `POST /_plugins/_ism/remove/<index>` and `GET /_plugins/_ism/explain/<index>` alongside the already-served `/_plugins/_ism/policies/<id>`, back them with per-index managed-index state that evaluates the policy's transition conditions and runs the `read_only` action, and serve unrouted paths with the engine's object-shaped error envelope.
Traces: opensearch.ism-policy-transition-sets-read-only-and-unmet-condition-stays-writable.

## Evidence
Cause 1 — opensearch.osq-terms-aggregation-and-sorted-pagination: after creating a minimal single-node domain, indexing 12 documents and refreshing, `POST /<index>/_search` with body `{'size': 0, 'aggs': {'by_category': {'terms': {'field': 'category', 'size': 10}, 'aggs': {'avg_price': {'avg': {'field': 'price'}}, 'sum_price': {'sum': {'field': 'price'}}}}}}`.
  Expected: HTTP 200 with one bucket per category carrying doc_count and the avg/sum sub-metrics (the check's own expectation set is alpha 5, beta 4, gamma 2, delta 1 with matching avg/sum, plus sum_other_doc_count for the truncated remainder).
  Actual: HTTP 400 `{'error': {'root_cause': [{'type': 'parsing_exception', 'reason': '[by_category] aggregation must name exactly one type'}], 'type': 'parsing_exception', 'reason': '[by_category] aggregation must name exactly one type'}, 'status': 400}`.
opensearch.search-aggregation-query-bucket-ordering: same emulator, body `{'size': 0, 'aggs': {'by_cat': {'terms': {'field': 'category'}, 'aggs': {'price_stats': {'stats': {'field': 'price'}}}}}}` → HTTP 400 with the identical reason `[by_cat] aggregation must name exactly one type`. The only difference between the two requests is the aggregation's NAME, which is what the reason interpolates; in both the body names exactly one type (`terms`) plus the reserved `aggs` key. (Later in the same check, `{'aggs': {'by_cat': {'terms': {'field': 'category', 'order': {'_key': 'asc'}}}}}` — no nested `aggs` — is the form the check reaches only after this assertion, so the refusal is attributable to the nested block.)

Cause 2 — opensearch.ingest-pipeline-rewrites-stored-source-and-simulate-predicts-it: `PUT <domain-endpoint>/_ingest/pipeline/<pipeline>` with processors `[{set: {field: ingested_by, value: ...}}, {lowercase: {field: title}}, {convert: {field: count, type: integer}}, {script: {lang: painless, source: 'ctx.count_squared = ctx.count * ctx.count'}}]`.
  Expected: HTTP 200 `{'acknowledged': true}`, then the pipeline (set as index.default_pipeline) rewriting `{'title': 'MiXeD Case', 'count': '7'}` into `{'title': 'mixed case', 'count': 7, 'count_squared': 49, 'ingested_by': '<value>'}`, `_simulate` predicting the identical `_source`, and a document whose count cannot be converted refused HTTP 400 with error type `illegal_argument_exception` mentioning the offending value.
  Actual: HTTP 400 `{'error': {'root_cause': [{'type': 'parse_exception', 'reason': 'No processor type exists with name [script]'}], 'type': 'parse_exception', 'reason': 'No processor type exists with name [script]'}, 'status': 400}`. The check stops at the pipeline creation, so none of the downstream rewrite behaviour was observed.

Cause 3 — opensearch.ism-policy-transition-sets-read-only-and-unmet-condition-stays-writable: `PUT <domain-endpoint>/_plugins/_ism/policies/<policy-id>` for a two-state policy (`writable` with a transition to `locked` on `min_doc_count: 2`, `locked` with action `read_only`) was ACCEPTED (HTTP 201, `_id`/`_version` asserted and passed). The next call, `POST <domain-endpoint>/_plugins/_ism/add/<index>` with `{'policy_id': '<policy-id>'}`:
  Expected: HTTP 200 with `failures: false` and the index in `updated_indices`, then `GET /_plugins/_ism/explain/<index>` reporting the index's policy_id/state/action/step, the met index transitioning to state `locked` with step `set_read_only` `completed` and `info.message` 'Successfully set index to read-only [index=<index>]', writes to it refused while search still works, the unmet index staying writable with `condition_not_met`, and `POST /_plugins/_ism/remove/<index>` answering HTTP 200 `failures: false`.
  Actual: HTTP 400 `{'error': 'no handler found for uri [/_plugins/_ism/add/<index>] and method [POST]'}` — a bare-string `error` with no `status` member and no `root_cause`/`type`/`reason` object. Index names, policy ids and document counts above are per-run values; the requirement is the status/shape/semantics of the add, explain and remove routes.

## Steps to Reproduce
Common setup (all three causes): CreateDomain(DomainName=<name>, EngineVersion='OpenSearch_2.11', ClusterConfig={InstanceType:'t3.small.search', InstanceCount:1, DedicatedMasterEnabled:false, ZoneAwarenessEnabled:false}, EBSOptions={EBSEnabled:true, VolumeType:'gp3', VolumeSize:10}, AccessPolicies=<account root allowed es:* on the domain>); poll DescribeDomain until Processing=false and DomainStatus.Endpoint is published; let BASE = https://<Endpoint>; poll a SigV4('es')-signed `GET BASE/` until it stops answering 403.

Cause 1 (sub-aggregations refused):
1. PUT BASE/<index> with `{"settings":{"index":{"number_of_shards":1,"number_of_replicas":0}}}`.
2. Index a handful of documents with a keyword `category` and a numeric `price`, then POST BASE/<index>/_refresh.
3. POST BASE/<index>/_search with `{"size":0,"aggs":{"by_cat":{"terms":{"field":"category"},"aggs":{"price_stats":{"stats":{"field":"price"}}}}}}`. Observed: HTTP 400 parsing_exception '[by_cat] aggregation must name exactly one type'. Expected: HTTP 200 with aggregations.by_cat.buckets, each bucket carrying key, doc_count and price_stats.
4. Control: repeat step 3 WITHOUT the nested "aggs" block — the same request minus the sub-aggregation must behave differently, which shows the reserved key is what is being miscounted.

Cause 2 (script ingest processor):
5. PUT BASE/_ingest/pipeline/<pipeline> with `{"description":"t","processors":[{"set":{"field":"ingested_by","value":"x"}},{"lowercase":{"field":"title"}},{"convert":{"field":"count","type":"integer"}},{"script":{"lang":"painless","source":"ctx.count_squared = ctx.count * ctx.count"}}]}`. Observed: HTTP 400 parse_exception 'No processor type exists with name [script]'. Expected: HTTP 200 {"acknowledged":true}.
6. Control: send the same body with the `script` processor removed — it is accepted, so the registry recognises the other three types.
7. Then (currently unreachable) set the pipeline as index.default_pipeline, PUT a document `{"title":"MiXeD Case","count":"7"}?refresh=true`, and expect the stored _source to equal `{"title":"mixed case","count":7,"count_squared":49,"ingested_by":"x"}` and `_ingest/pipeline/_simulate` to predict the same document.

Cause 3 (ISM add/remove/explain unrouted):
8. PUT BASE/_plugins/_ism/policies/<policy-id> with a policy whose `writable` state transitions to `locked` on `{"min_doc_count":2}` and whose `locked` state has action `{"read_only":{}}`. Observed: HTTP 201 (this route works).
9. POST BASE/_plugins/_ism/add/<index> with `{"policy_id":"<policy-id>"}`. Observed: HTTP 400 `{"error":"no handler found for uri [/_plugins/_ism/add/<index>] and method [POST]"}`. Expected: HTTP 200 with `failures:false`, `failed_indices:[]` and the index listed in `updated_indices`.
10. Repeat step 9 for the same index: expected HTTP 200 with `failures:true` and a failure whose reason names the ISM update API.
11. GET BASE/_plugins/_ism/explain/<index>: expected HTTP 200 keyed by index name with policy_id, state.name, action.name, action.failed, step.name and step.step_status. POST BASE/_plugins/_ism/remove/<index>: expected HTTP 200 with `failures:false`.
12. DeleteDomain(DomainName=<name>) to clean up.
