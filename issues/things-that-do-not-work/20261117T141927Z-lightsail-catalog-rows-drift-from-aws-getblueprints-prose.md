# Lightsail catalog rows drift from AWS: GetBlueprints prose and URLs, GetBundles Windows prices, and truncated tails

> _Note: this issue was identified against the code base at commit `68210b19d373988c90b716d7b57ea91f683e4786`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
GetBlueprints

## Description
Two net-new root causes, both in the hand-maintained static reference tables that back Lightsail's read-only catalog operations (GetBlueprints and GetBundles). Both operations answer 200 with a correctly shaped, correctly serialized envelope, so no client can detect either divergence from the status, error or member set: the fault is entirely in the CONTENTS of the tables - wrong column values on served rows, and rows that are not served at all so the list is short and every later list position shifts. Both causes must be closed before submitting.

Cause 1 of 2: the instance-blueprint table's per-row text and catalog URLs are not AWS's, and the table's tail rows are absent.
AWS: Smithy com.amazonaws.lightsail#GetBlueprints is an awsJson RPC operation (POST /ls/api/2016-11-28/GetBlueprints, success code 200, httpBindingsInert) whose output member `blueprints` is a BlueprintList of com.amazonaws.lightsail#Blueprint; Blueprint models blueprintId (NonEmptyString, pattern \\S), name (ResourceName), group, type (BlueprintType enum os|app), description ("The description of the blueprint"), isActive, minPower, version ("The version number of the operating system, application, or stack"), versionCode, productUrl ("The product URL to learn more about the image or blueprint"), licenseUrl ("The end-user license agreement URL for the image or blueprint"), platform (InstancePlatform enum) and appCategory. The model fixes no catalog values, so the row set and the column values are recorded behavior only. The recording shows AWS serving, per row, its own complete marketplace description paragraph (not an abridged or re-stitched version of it), a productUrl under aws.amazon.com/marketplace/pp/ identifying THAT image's listing, a licenseUrl under the AWS EULA host d7umqicpi7263.cloudfront.net/eula/product/<id>/<id>.txt identifying THAT image's agreement, and a full catalog of 39 blueprint rows. The literal paragraphs, prodview ids, EULA ids and catalog dates in the recording are that catalog's contents filling the template; the requirement is that the row set and each row's text and links are AWS's catalog for that blueprintId, not locally authored or locally re-assigned values.
Emulator: replay reports every asserted position from $.blueprints[0] to $.blueprints[38] as divergent at status 200 -> 200. Three distinct column faults: (a) the description prose is a paraphrase of AWS's - on row 0 ('windows_server_2025') the emulator drops the sentence clause 'For business IT applications, ' from the middle of the paragraph while the rest of the identity members (blueprintId, name 'Windows Server 2025', group 'windows_2025', type 'os', minPower 500, version '2026.09.17', versionCode '1', platform 'WINDOWS') match, which isolates the fault to the text column; (b) productUrl and licenseUrl are on the right hosts but carry the WRONG identifiers for the row - replay's verdict is host_not_own on rows 1,2,3,4,5,7,8,9..32, e.g. for blueprints[1] it expects productUrl '.../pp/prodview-dq4sxno5vuy7m' and serves '.../pp/prodview-tn7bk2vqwm5zd', and for blueprints[2] it expects the legacy form '.../pp/B07QZ4XZ8F' and serves a prodview id; the licence ids under d7umqicpi7263.cloudfront.net are likewise substituted row by row, and on blueprints[4] AWS serves a marketplace '#pdp-usage' URL as the licenseUrl where the emulator serves a cloudfront EULA URL; (c) the table is short - positions $.blueprints[33] through $.blueprints[38] are reported entirely absent, so the emulator serves fewer rows than AWS's 39.
Why: a client that renders a blueprint description, or follows productUrl/licenseUrl to present terms to a user before launching an instance, gets abridged prose and a link to a DIFFERENT image's marketplace listing and licence agreement - a wrong-but-plausible link is worse than a missing one, because it resolves. A blueprint the table omits cannot be selected at all, so no workflow using an omitted image can be driven against the emulator, and a client that indexes the list by position reads the wrong image past the truncation point.
Fix: the static instance-blueprint catalog table backing the GetBlueprints handler in the lightsail crate - the description, productUrl and licenseUrl columns on all rows, plus the missing tail rows. Not handler, validation or serializer logic: the status, envelope, member set and member types are already correct.
Traces: lightsail-catalog-get-blueprints#task#1 (divergence_key service=lightsail|GetBlueprints|status=200->200 over $.blueprints[0]..$.blueprints[38] and their .productUrl/.licenseUrl).

Cause 2 of 2: the instance-bundle table carries wrong `price` values on the Windows tier and stops short of AWS's bundle catalog.
AWS: Smithy com.amazonaws.lightsail#GetBundles is an awsJson RPC operation (POST /ls/api/2016-11-28/GetBundles, success code 200) whose output member `bundles` is a BundleList of com.amazonaws.lightsail#Bundle; Bundle models bundleId (NonEmptyString), name, instanceType, isActive, power, price (float, documented as "The price in US dollars (5.0) of the bundle"), cpuCount, ramSizeInGb, diskSizeInGb, transferPerMonthInGb, supportedPlatforms (InstancePlatformList), supportedAppCategories and publicIpv4AddressCount. The model fixes no prices and no row set, so this is recorded behavior only: the recording shows AWS serving its published price for each bundleId and a catalog deep enough for the fixture to assert positions through index 99. The specific dollar figures below are that catalog's values filling the template - the requirement is that the price served for a bundleId is AWS's published price for it and that the catalog's rows are all present.
Emulator: status 200 -> 200, every asserted position from $.bundles[16] to $.bundles[99] reported divergent. The three positions the detail spells out differ ONLY in `price`, with every other member identical, which isolates the fault to the price column: 'xlarge_win_3_0' expected 124.0, served 140.0; '2xlarge_win_3_0' expected 244.0, served 260.0; '4xlarge_win_3_0' expected 574.0, served 500.0 (note the error runs in both directions, so it is not a uniform markup); '8xlarge_win_3_0' is expected at 1254.0. The remaining asserted positions ($.bundles[19] onward, through index 99) are reported as whole-entry divergences, i.e. the emulator's table supplies no matching row there - its bundle catalog ends well before AWS's.
Why: price is the value a client reads to cost a plan before launching, so a client sized against the emulator quotes and budgets the wrong figure for every Windows bundle, and the direction of the error is inconsistent so no client-side correction recovers it. A bundle the table omits cannot be passed to CreateInstances at all, so whole instance sizes are unreachable, and a client reading the list by position reads a different bundle's specs past the truncation point - including `power`, which AWS checks against a blueprint's minPower.
Fix: the static instance-bundle catalog table backing the GetBundles handler in the lightsail crate - the price column on the Windows (_win_) rows, and the absent tail rows with their full member sets. Again not handler or serializer logic.
Traces: lightsail-catalog-get-bundles#task#1 (divergence_key service=lightsail|GetBundles|status=200->200 over $.bundles[16]..$.bundles[99]).
