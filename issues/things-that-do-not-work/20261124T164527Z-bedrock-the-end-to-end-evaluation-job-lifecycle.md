# bedrock: the end-to-end evaluation-job lifecycle reaches no verdict — CreateEvaluationJob → Completed + S3 results → BatchDeleteEvaluationJob purge never converges, the check times out at 60s

> _Note: this issue was identified against the code base at commit `3f16eebaae6a975d537d43eeeb4dcff492da4b7d`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
GetEvaluationJob

## Description
One net-new root cause in the bedrock evaluation-job surface. bedrock answers (the service is bootstrapped; get_bootstrap_status reports no pending services), and no OPEN issue carries this check: the open 20261026T233704Z-bedrock-batchdeleteevaluationjob-s-non-terminal-status-refusal-uses.md covers only BatchDeleteEvaluationJob's refusal WORDING for a non-terminal job and the CloudFormation resource type, and the lifecycle issue it refers to, 20261024T230826Z-bedrock-an-accepted-automated-evaluation-job-is-pinned-inprogress.md, is marked FIXED — the status is no longer pinned in the store (a completion span is now stored), yet the end-to-end sequence that depends on it still reaches no verdict.

Cause 1 of 1: an accepted automated evaluation job's full lifecycle is not observable end to end.
Failing check: bedrock.e2e-evaluation-job-runs-and-is-purged

AWS: Smithy CreateEvaluationJob (POST /evaluation-jobs, success 202) answers only jobArn; EvaluationJobStatus is [InProgress, Completed, Failed, Stopping, Stopped, Deleting] and an accepted automated job is reported InProgress and then moves, on the service's own clock, to Completed. The results of the run ARE the S3 output: EvaluationOutputDataConfig$s3Uri is documented as "the Amazon S3 URI where the results of the evaluation job are saved", so a job reported Completed has objects under that prefix (the check reads them with s3:ListObjectsV2 on the configured prefix and requires KeyCount > 0). BatchDeleteEvaluationJob (POST /evaluation-jobs/batch-delete, 202) accepts a job in FAILED/COMPLETED/STOPPED, echoes the bare job id (the last ARN segment) in evaluationJobs[].jobIdentifier with an empty errors list, and the deletion is asynchronous: an independent GetEvaluationJob must EVENTUALLY answer ResourceNotFoundException (404) and ListEvaluationJobs must stop reporting the job.

Emulator: the sequence never completes — the check is killed by the harness: "Check timed out after 60.0s", so no assertion past the completion wait is ever reached and the suite records no verdict for Completed, for the S3 results, for the batch-delete echo or for the purge. The relevant emulator shape is that the whole lifecycle is CHOSEN-span and lazily materialised: ops/create_evaluation_job.rs stores status=InProgress with completed_due_at = now + EVALUATION_JOB_COMPLETE_AFTER (state/limits.rs: Duration::from_secs(3)) and starts the run in a task of its own (state/evaluation_run.rs::run_when_accepted), and the transition is only materialised "on the next call that touches the record". Two readings fit the observed timeout, neither of which the replay can separate (both labelled Hypothesis, because all the run produced is the timeout): Hypothesis A — the lifecycle legs are fine but nothing the emulator serves settles inside the window the suite allows this check, i.e. the first read after create is InProgress (correct for AWS) and the sequence then needs more wall clock than the emulator's spans and the harness together leave, so the check can only ever time out; Hypothesis B — one leg does not answer at all: CreateEvaluationJob repeatedly refused with AccessDeniedException/ValidationException (the check retries exactly those two for 60s, which alone would exhaust the window — the job is created under a freshly minted IAM role whose trust policy carries a StringEquals aws:SourceAccount condition and is passed through crate::state::job_pass_role_denial), or the acceptance-time run task (which reaches this emulator's own S3 and the Bedrock Runtime generation stage over the in-process callback) blocks the store lock the next GetEvaluationJob needs, or it writes no object under outputDataConfig.s3Uri so the ListObjectsV2 assertion could never pass. Re-replaying this one check after making the lifecycle observable is what distinguishes them.

Why: evaluation jobs are the one Bedrock control-plane resource whose whole value is the terminal state and the result objects. A client that submits a job and polls GetEvaluationJob for Completed, reads its results out of S3 and then purges it with BatchDeleteEvaluationJob gets no usable answer from this emulator: the one path that exercises all four steps together produces nothing at all, so a caller cannot tell a job that ran from a job that is wedged, and the asynchronous purge (GetEvaluationJob eventually 404 / ListEvaluationJobs dropping the job) is likewise unverified.

Fix: the evaluation-job lifecycle and its run, in this service's state rather than in one handler — the stored completion/deletion due instants and the lazy materialisation that reads them (state/limits.rs and state/store_access.rs, reached by ops/get_evaluation_job.rs, ops/list_evaluation_jobs.rs and ops/batch_delete_evaluation_job.rs), plus the acceptance-time run that writes the result records (state/evaluation_run.rs) and the iam:PassRole decision CreateEvaluationJob takes over the submitted roleArn (state/enforcement.rs::job_pass_role_denial). The requirement is that an accepted automated job reaches Completed with result objects under outputDataConfig.s3Uri, and that a batch delete of that terminal job is followed by GetEvaluationJob answering 404 ResourceNotFoundException and ListEvaluationJobs omitting it — all of it observable to a client that merely polls, without any handler blocking.

Traces: bedrock.e2e-evaluation-job-runs-and-is-purged (the only failing check for this cause; file and line citations above are pointers, not patches).

  Actual (emulator): the replay produced only — "Error: Check timed out after 60.0s". No status, no S3 listing, no batch-delete response and no purge observation was obtained; the check was killed before any of its post-creation assertions reported.
  Emulator shape behind it (for the fixer, not a recorded value): services/service-com-amazonaws-bedrock-amazonbedrockcontrolplaneservice/src/ops/create_evaluation_job.rs:390-467 stores status=EVALUATION_JOB_STATUS_IN_PROGRESS with completed_due_at = now + EVALUATION_JOB_COMPLETE_AFTER and hands the run to state::evaluation_run::run_when_accepted; .../src/state/limits.rs:476 sets EVALUATION_JOB_COMPLETE_AFTER = Duration::from_secs(3) and documents that the move is "materialised from the stored due instant on the next call that touches the record rather than waited on".
