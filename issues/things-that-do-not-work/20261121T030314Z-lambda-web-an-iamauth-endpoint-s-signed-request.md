# lambda-web: an IamAuth endpoint's SIGNED request is answered 501, so the unsigned-request 403 refusal can never be reached (1 cause)

> _Note: this issue was identified against the code base at commit `be68e03a3b164dfd55295662738d8b5c0a02662c`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
GetWebFunctionEndpoint

## Description
Cause 1 of 1: the HTTP data plane a web function endpoint publishes answers every AUTHORIZED (SigV4-presenting) request with a fixed HTTP 501 instead of the deployed revision's handler response. Because a client must first establish that the endpoint serves at all before an unsigned request's refusal means anything, this single 501 makes the whole IamAuth rejection contract unobservable: the positive control never reaches 200, so the endpoint's unsigned-request behaviour is never exercised. Failing check: lambda-web.unsigned-https-get-on-web-function-endpoint-rejected.

AWS: a web function endpoint IS an HTTP data plane, and the address it publishes is where a client sends its request. Smithy (services/service-com-amazonaws-lambdaweb-lambdaweb/smithy-model/com-amazonaws-lambdaweb-lambdaweb.json): GetWebFunctionEndpointResponse$domainName is required, DomainName @length min 4 max 256, @pattern ^([a-z0-9-]+\.)+[a-z]+$ — "The domain name assigned to the endpoint"; GetWebFunctionEndpointResponse$state (enum EndpointState), $authType (enum AuthType: ApplicationManaged | IamAuth) and $revisionWeights (RevisionWeightList, @length min 1 max 2, uniqueItems) say what that address serves and how a request to it is authorized; GetWebFunctionEndpoint is GET /2025-03-07/web-functions/{functionName}/endpoints/{endpointName}. The revision's code is a .zip deployment package in S3 (CreateWebFunction revisionConfig.buildConfig.codeConfig.s3Object) for the runtime revisionConfig.buildConfig.runtimeConfig.runtime names (a Node.js runtime identifier in the recording). The data-plane hop itself is NOT modelled — no operation shape, no restJson1 error envelope, no modelled status — so for what comes back this is recorded behavior only: once the endpoint's state is Active, a SigV4-signed HTTPS GET to domainName is answered with exactly what the deployed revision's handler returned (in the recording, HTTP 200 with the handler's literal body). Nothing fixed belongs to that hop: the status, headers and body are entirely the handler's, so there is no AWS-worded message and no error code on the success path. Only the REFUSAL path has fixed text: an unsigned request to an IamAuth endpoint earns HTTP 403 with the Forbidden page whose fixed text is "<!DOCTYPE html>\n<html>\n<head>\n    <title>HTTP Error 403</title>\n</head>\n<body>\n    <h1>403 Forbidden</h1>\n    <p>You are not authorized to access this endpoint.</p>\n    <p>Request ID: <id></p>\n</body>\n</html>" — its one variable part is that response's own id, which is also reported in the lambda-web-request-id response header (the concrete id in any single run fills that template and is not part of it).

Emulator: the terminal arm of serve_request in services/service-com-amazonaws-lambdaweb-lambdaweb/src/state/endpoint_plane.rs returns `attributed(plain(head, 501, NO_WEB_FUNCTION_HANDLER), &request_id)` for EVERY authorized request — HTTP 501, content-type text/plain; charset=utf-8, body the module constant "This web function endpoint is not implemented: the emulator runs no web function code, so the handler's own response cannot be served.\n". That is fixed for every endpoint, revision, path and method: no execution engine is mounted in the crate, so the revision's deployment package is read and judged as an archive (src/state/code_package.rs) but never run. The control plane still reports the endpoint Active with a domainName the emulator does answer on, so the gap appears only at the last hop. Consequently the check's positive control — a SigV4-signed GET polled until status == 200 — never terminates and the check is reported as "Check timed out after 60.0s" before it ever issues the unsigned GET. Note that the emulator's 403 arm (html(head, FORBIDDEN, &forbidden_document(&request_id)) plus the lambda-web-request-id header) is NOT itself observed as divergent by this check; it is simply never reached, so the unsigned-rejection contract is untested as long as the 501 stands.

Why: a client that reads domainName off an Active endpoint and issues its request there gets 501 for a function the control plane reports as healthy and serving, so no web function can be exercised end to end: a handler's status/headers/body cannot be asserted, revisionWeights routing is unobservable (both weights resolve to the same 501), and authType has no observable consequence because the only thing past the auth gate is the 501. A client treating 501 as a transient server fault retries forever — which is exactly how this check dies. Security-relevant behaviour is additionally hidden: an operator cannot confirm that an IamAuth endpoint refuses unsigned traffic, because the only way to prove the refusal is meaningful (a signed request being served) is unavailable.

Fix: the authorized-request arm of the endpoint data plane — the final arm of serve_request in the lambda-web crate's src/state/endpoint_plane.rs — must bridge the buffered request to the deployed revision's code (selected by the endpoint's revisionWeights) and return that handler's own status, headers and body, instead of a fixed 501 constant. That needs an execution layer for the revision's deployment package in this crate (containment and bounds first, then the request/response bridge); the emulated Lambda service's existing execution state is the closest reference and anything shared belongs in a shared crate rather than a second copy.

Related, already filed, named here rather than treated as covering this check: issues/things-that-do-not-work/20261111T133800Z-lambda-web-a-signed-request-to-an-active.md and issues/things-that-do-not-work/20261110T090000Z-lambda-web-endpoint-serves-no-handler-response.md describe the same 501 but carry only the lambda-web.signed-https-get-on-web-function-endpoint-serves-handler-response replay key, and issues/things-that-do-not-work/20261120T070133Z-lambda-web-an-applicationmanaged-endpoint-answers-an-unsigned.md carries only the ApplicationManaged check's key; the suite therefore did not report lambda-web.unsigned-https-get-on-web-function-endpoint-rejected as OWNED by any of them. Treat them as one work item and re-replay this check's id too before closing.

## Evidence
Check lambda-web.unsigned-https-get-on-web-function-endpoint-rejected (GROUP endpoint-invocation, SERVICES [lambda-web]) creates an execution role, a versioned S3 bucket holding a Node.js .zip deployment package whose handler returns a known literal body, and one web function via CreateWebFunction with endpointConfig {endpointName: "ep", endpointType: "HomeRegion", authType: "IamAuth"}; polls GetWebFunctionEndpoint until state == "Active" (asserted); reads domainName; then runs its positive control — a SigV4-signed GET (service "lambda", X-Amz-Content-SHA256 of the empty body) inside _poll_until(..., lambda r: r[0] == 200) with the comment "Positive control first: proves the endpoint is live and serving, so the 403 below cannot be explained by a not-yet-deployed endpoint" — and asserts status == 200 and body == the handler's literal output. Only after that does it issue the unsigned GET and assert 403, a lambda-web-request-id header, and the Forbidden page body.

Reported verdict: [mismatch] — "Error: Check timed out after 60.0s". The poll never observes a 200: the emulator answers every authorized request to the published address with HTTP 501, content-type text/plain; charset=utf-8, body "This web function endpoint is not implemented: the emulator runs no web function code, so the handler's own response cannot be served.\n" — the NO_WEB_FUNCTION_HANDLER constant returned by the terminal plain(head, 501, NO_WEB_FUNCTION_HANDLER) arm of serve_request (services/service-com-amazonaws-lambdaweb-lambdaweb/src/state/endpoint_plane.rs: constant declared ~line 122, returned ~line 479). That status and body are fixed for every authorized request and carry nothing from the request or the revision.

Expected per the recording: the deployed revision's handler response — HTTP 200 and that handler's own body (the probe's literal body in any single run is that handler's output filling the template, not fixed text of this hop). The emulator's 501 and its sentence are not AWS behaviour on this hop at all: AWS serves no fixed document there. Because the control never passes, the unsigned-request assertions that follow — HTTP 403, a lambda-web-request-id response header, and the Forbidden page whose only variable part is that response's own id — are never exercised at all, so the IamAuth refusal contract is unverified.

## Steps to Reproduce
1. CreateRole with a lambda.amazonaws.com trust policy; CreateBucket with versioning enabled plus a bucket policy letting lambda.amazonaws.com s3:GetObject/s3:GetObjectVersion; PutObject a valid Node.js .zip deployment package whose handler returns a known literal body.
2. CreateWebFunction with revisionConfig.buildConfig.codeConfig.s3Object pointing at that object, runtimeConfig.runtime "nodejs24.x", serviceConfig.executionRoleArn the role, and endpointConfig {endpointName: "ep", endpointType: "HomeRegion", authType: "IamAuth"}.
3. Poll GetWebFunctionEndpoint(functionName, endpointName="ep") until state == "Active"; read domainName off the response.
4. Issue an HTTPS GET to that address SigV4-signed for service "lambda" in the region, carrying X-Amz-Content-SHA256 for the empty body (the positive control).
5. Observed: HTTP 501, content-type text/plain; charset=utf-8, body "This web function endpoint is not implemented: the emulator runs no web function code, so the handler's own response cannot be served.\n" — on every retry, so a client polling for 200 never terminates and the check is killed at its 60s cap. Expected: the deployed revision's handler response, HTTP 200 with that handler's own body.
6. Consequently step 7 is never reached. Once step 4 is served 200, issue the SAME GET with no Authorization header and no X-Amz-Credential query parameter and confirm: HTTP 403, a lambda-web-request-id response header, and a body equal to the Forbidden page stating that same response id.
