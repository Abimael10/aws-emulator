# Image Builder image builds never run: StartImagePipelineExecution lands straight on AVAILABLE (no PENDING/BUILDING, no FAILED on bad infrastructure) and GetImage omits outputResources

> _Note: this issue was identified against the code base at commit `da3e7884167b3f933d6f1406ab01004ac62fd391`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
StartImagePipelineExecution

## Description
3 net-new root causes in the Image Builder image-build lifecycle and image read path. All three are reached through imagebuilder operations exercised by the ec2__iam__imagebuilder behavioral checks. None of the open imagebuilder issues covers them: 20261103T041241Z-ec2-iam-imagebuilder-image-builder-createimagepipeline-accepts-an-invalid-cron-schedule.md is about schedule validation, 20261114T011705Z-ec2-iam-imagebuilder-implement-imagebuilder-listimages-... is about ListImages, 20261114T230016Z-imagebuilder-2-net-new-refusal-message-divergences-distribution.md and 20261115T021705Z-imagebuilder-image-builder-teardown-paths-diverge-... are about distribution-configuration/teardown refusal wording, and 20261103T091826Z / 20261105T052823Z cover unrelated delete and CancelImageCreation stubs. Nothing filed describes the build state machine or Image.outputResources.

Cause 1 of 3: an image build started by StartImagePipelineExecution is never in flight — it is AVAILABLE on the first read, so DeleteImage is never refused ResourceDependencyException.
AWS: Smithy com.amazonaws.imagebuilder — ImageState.status targets the enum ImageStatus with values PENDING, CREATING, BUILDING, TESTING, DISTRIBUTING, INTEGRATING, AVAILABLE, CANCELLED, FAILED, DEPRECATED, DELETED, DISABLED, documented as "A new image moves through build, test, and distribution statuses during creation, and ends in the AVAILABLE, FAILED, or CANCELLED state." So after StartImagePipelineExecution returns an imageBuildVersionArn, GetImage on that ARN reports a non-terminal status (PENDING/CREATING/BUILDING/TESTING/DISTRIBUTING/INTEGRATING) for the duration of the build before it reaches AVAILABLE. While that build is in flight, DeleteImage is refused with modeled error ResourceDependencyException (errorKind client, httpError 400), message "Resource dependency error: The resource ARN '<imageBuildVersionArn>' has a running workflow." — the fixed text is "Resource dependency error: The resource ARN '" … "' has a running workflow." and the only variable part is the image build version ARN taken from the request. DeleteImagePipeline during that build is accepted and does not stop the build; after CancelImageCreation the image settles on CANCELLED and DeleteImage then succeeds, after which GetImage answers ResourceNotFoundException.
Emulator: the first GetImage after StartImagePipelineExecution already reports {'status': 'AVAILABLE'} — the build is created in its terminal state and no in-flight status is ever observable, so the whole running-build branch (the ResourceDependencyException refusal, the mid-build DeleteImagePipeline, the cancel-to-CANCELLED transition) can never be reached.
Why: a client that starts a pipeline execution and waits for or reacts to build progress sees an instantly finished build. Code that polls for BUILDING, that treats AVAILABLE as "the AMI exists and is distributed", or that relies on DeleteImage being refused while a workflow runs, all behave wrongly — deletes that AWS refuses are accepted, and no image ever reports a build phase.
Fix: the StartImagePipelineExecution handler and the image state it writes — the image resource must be created in a non-terminal ImageStatus and advanced to AVAILABLE/FAILED/CANCELLED by the build lifecycle, and the DeleteImage handler must consult that status and refuse with ResourceDependencyException while a workflow is running.
Traces: ec2__iam__imagebuilder.ibp-delete-image-is-rejected-while-its-build-runs (AssertionError: build is {'status': 'AVAILABLE'}, not running).

Cause 2 of 3: a pipeline whose infrastructure configuration names a nonexistent security group still builds successfully instead of ending FAILED.
AWS: recorded behavior only — the model does not constrain InfrastructureConfiguration.securityGroupIds against EC2 state, and Image Builder validates the network at build time, not at CreateInfrastructureConfiguration/CreateImagePipeline time. The recording shows the pipeline being created clean, and its first execution ending with ImageState.status FAILED (ImageStatus enum includes FAILED; ImageState.failureContext is set only when the status is FAILED), with the pipeline's ImagePipeline.lastRunStatus settling on FAILED. The same pipeline over an existing security group reaches BUILDING and, after CancelImageCreation, CANCELLED.
Emulator: the build started against securityGroupIds=["sg-0123456789abcdef0"] (an ID that exists in no VPC) reaches {'status': 'AVAILABLE'} — the launch of the build instance is never attempted or never fails, so no build ever ends FAILED and lastRunStatus never reports FAILED.
Why: a client cannot distinguish a broken build environment from a working one. Every pipeline reports success, so failure handling, retries and alarms keyed on FAILED / lastRunStatus never fire, and a user believes an AMI was produced from infrastructure that cannot launch an instance.
Fix: the build execution path behind StartImagePipelineExecution — it must resolve the referenced infrastructure configuration's security groups (and subnet/instance profile) against EC2 state when the build instance is launched and drive the image to FAILED with a reason, and propagate that status to ImagePipeline.lastRunStatus.
Traces: ec2__iam__imagebuilder.ibp-pipeline-run-against-a-missing-security-group-fails-and-a-valid-one-builds (AssertionError: the missing-SG build ended {'status': 'AVAILABLE'}, not FAILED).

Cause 3 of 3: GetImage returns an Image with no outputResources member, so the AMIs an image produced cannot be read.
AWS: Smithy com.amazonaws.imagebuilder — Image.outputResources targets OutputResources ("The output resources that Image Builder produces for this image"), whose amis member is an AmiList ("The Amazon EC2 AMIs created by this image. The list contains one entry per AMI, including copies that distribution created in each target Amazon Web Services Region and account"); each Ami carries region, image, name, description, state and accountId. For an AVAILABLE AMI-type image — including the AWS-managed parent images under arn:aws:imagebuilder:<region>:aws:image/<name>/x.x.x, which GetImage's imageBuildVersionArn pattern explicitly admits via the `aws` owner alternative — GetImage's image.outputResources.amis is present and lists the AMI(s) with the Region each one lives in, and that AMI ID resolves through EC2 DescribeImages in that Region only.
Emulator: GetImage on an AWS-managed parent image returns an image object with no outputResources key at all (KeyError: 'outputResources' when the response's image is indexed), so no produced AMI is discoverable from the Image Builder read path.
Why: a client that resolves an Image Builder image to the EC2 AMI it produced — to launch it, to copy it, or to assert which Regions it was distributed to — gets nothing to resolve. Region-scoping of parent images and distributed AMIs cannot be observed at all.
Fix: the GetImage serializer and the image state it reads — the Image structure must populate outputResources.amis (region, image, name, state, accountId) for AMI-type images, including the AWS-managed parent images the catalog serves.
Traces: ec2__iam__imagebuilder.ibp-pipeline-and-parent-image-arns-resolve-only-in-their-own-region (KeyError: 'outputResources').
