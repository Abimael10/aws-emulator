# cloudwatch: DescribeAlarmContributors refuses a Metrics Insights GROUP BY alarm as "not a multi time series alarm", so the operation now has no success path

> _Note: this issue was identified against the code base at commit `13e968f2d712b86cbfec63dd795b2bc21b7f9b4c`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
DescribeAlarmContributors

## Description
REOPENS 20261029T210614Z-cloudwatch-4-net-new-root-causes-putalarmmuterule-describealarmcontributors.md: its fix left the call refused.

That issue's Cause 2 asked DescribeAlarmContributors to stop answering NotImplemented and to separate a missing alarm (404 ResourceNotFoundException) from an alarm of the wrong TYPE (400 ValidationError "Alarm <name> is not a multi time series alarm"). The alarm-type gate now exists, but it matches EVERY alarm: the multi-time-series alarms the operation is defined for are refused with the same ValidationError, so the operation has no 2xx path at all and no later validation (pagination tokens, contributor ranking) is reachable. The open issue 20261108T191814Z-cloudwatch-describealarmcontributors-answers-200-for-an-alarm-aws.md lists two of the check ids below in its Issue-Trace-Ids, but it describes the OPPOSITE failure (200 with an empty AlarmContributors list) and its Cause 1 explicitly requires that "a GROUP BY Metrics Insights alarm IS contributor-based and must still succeed"; it does not carry this refusal, and the replay report marks none of these four checks ALREADY FILED or OWNED.

Cause 1 of 1: the alarm-type gate classifies a Metrics Insights GROUP BY expression alarm as not multi-time-series.
AWS: Smithy (services/service-com-amazonaws-cloudwatch-graniteserviceversion20100801/smithy-model/com-amazonaws-cloudwatch-graniteserviceversion20100801.json) — DescribeAlarmContributors takes AlarmName @required @length 1..255 plus NextToken, returns AlarmContributors @required, and models exactly InvalidNextToken (client, httpError 400, awsQueryError code InvalidNextToken) and ResourceNotFoundException (client, httpError 404). The alarm-type precondition is not modeled, so recorded behavior only: an alarm whose single ReturnData metric is a Metrics Insights expression of the form SELECT <AGG>(<metric>) FROM SCHEMA("<namespace>", <dim>) GROUP BY <dim> ORDER BY <AGG>() DESC LIMIT <n> IS a multi-time-series (contributor-based) alarm. For such an alarm the call succeeds with HTTP 200 and AlarmContributors carrying one entry per contributing time series, each with ContributorAttributes mapping the GROUP BY dimension name to that series' value, ordered by descending aggregate value and stable across repeat calls; a freshly created one has no contributors until the alarm has been evaluated. Only an alarm that is NOT multi-time-series — an ordinary single-metric alarm, or a composite alarm over one — is refused, with HTTP 400, error code ValidationError and message "Alarm <AlarmName> is not a multi time series alarm" (fixed text "Alarm " + " is not a multi time series alarm"; the single variable part is the AlarmName echoed verbatim from the request). A malformed NextToken sent against a genuine multi-time-series alarm must be refused with InvalidNextToken (400) and not with the alarm-type ValidationError.
Emulator: DescribeAlarmContributors against a GROUP BY Metrics Insights alarm created by PutMetricAlarm(Metrics=[{Expression: <the SELECT ... GROUP BY ... ORDER BY ... query>, Period: 60, ReturnData: true}]) is refused with HTTP 400, code ValidationError, message "Alarm <AlarmName> is not a multi time series alarm" — the refusal that belongs only to plain and composite alarms. The contributor-projection path and the InvalidNextToken guard are therefore dead code: the ranking check and the token check never get past the first call, and the check that polls for the alarm's members for 360 s (its helper swallows the ClientError and sees an empty list) never observes a single contributor.
Why: this refusal is the only signal a client has for "this alarm has no contributor dimension". With it returned for every alarm, contributor-driven diagnostics and dashboards conclude that a Metrics Insights GROUP BY alarm — the one kind that DOES have contributors — is not contributor-based, so the per-series breakdown that explains which group breached is unobtainable, and any code that branches on ValidationError to fall back to a single-series view takes that fallback universally. The InvalidNextToken contract on this operation is also unreachable, so a paging client cannot be tested at all.
Fix: the DescribeAlarmContributors handler's alarm-type gate in the cloudwatch service crate (services/service-com-amazonaws-cloudwatch-graniteserviceversion20100801/src/ops/describe_alarm_contributors.rs) and the alarm classification it reads — an alarm whose Metrics list carries a Metrics Insights SELECT ... GROUP BY ... expression must be classified multi-time-series and its contributors projected from the evaluated series; the ValidationError must stay scoped to plain metric alarms and composite alarms, and the pagination-token guard must run before/independently of it.
Traces: cloudwatch.describe-alarm-contributors-rejected-for-non-contributor-alarms, cloudwatch.alarm-contributors-ranking-order, cloudwatch.describe-alarm-contributors-invalid-next-token, cloudwatch.describe-alarm-contributors-reflects-composite-members.
