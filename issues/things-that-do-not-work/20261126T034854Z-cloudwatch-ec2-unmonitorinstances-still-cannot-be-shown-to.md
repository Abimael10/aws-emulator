# cloudwatch__ec2: UnmonitorInstances still cannot be shown to restore 5-minute CPUUtilization publication — no 1-minute datapoint is ever produced, so the check is cut at its 600 s budget

> _Note: this issue was identified against the code base at commit `857f59baf94ca876ddeb888a415f04d0868c32ab`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
UnmonitorInstances

## Description
One net-new root cause (Cause 1 of 1).

Cause 1 of 1: an instance moved to detailed monitoring with MonitorInstances never publishes an AWS/EC2 CPUUtilization datapoint off the 5-minute grid, so the scenario that grades UnmonitorInstances' return to 5-minute-only publication never gets past its first barrier and is killed at the harness budget. The Monitoring.State strings advance; the publication cadence they are supposed to select does not.
AWS: Smithy: UnmonitorInstances (com.amazonaws.ec2#AmazonEC2) takes InstanceIds and answers InstanceMonitorings, and declares errors: []; MonitorInstances is the same shape. The model says nothing about metric cadence, so the cadence itself is recorded behavior only, backed by AWS's documented rule (manage-detailed-monitoring: basic monitoring publishes metrics in 5-minute periods, detailed monitoring in 1-minute periods). The recording requires, in order: a launched instance reports Monitoring.State 'disabled'; MonitorInstances answers InstanceMonitorings=[{InstanceId: <that id>, Monitoring: {State: 'pending'}}] and the state settles to 'enabled'; from then on AWS/EC2 CPUUtilization for dimension {InstanceId} carries datapoints whose timestamps are NOT on the 5-minute grid (epoch-seconds % 300 != 0); UnmonitorInstances then answers Monitoring.State 'disabling', settles to 'disabled', and the series KEEPS being published but only on 5-minute boundaries, with no further 1-minute datapoint inside the first full 300 s window after the restore, while the earlier off-grid datapoints remain readable.
Emulator: the check makes no progress past the wait for the first off-grid datapoint and ends with 'Error: Check timed out after 600.0s'; the UnmonitorInstances half (the 'disabling' transition, the restored 5-minute bucket, and the absence of late 1-minute datapoints) is therefore never graded at all. Hypothesis: CPUUtilization is still emitted on one fixed schedule that ignores the instance's Monitoring.State, so enabling and then disabling detailed monitoring is unobservable in the metric stream.
Why: a client cannot distinguish detailed monitoring from basic monitoring, in either direction. MonitorInstances buys no finer resolution, so an alarm or dashboard written with Period=60 over AWS/EC2 CPUUtilization sits in INSUFFICIENT_DATA forever; and because the 1-minute cadence never appears, a client also has no way to observe that UnmonitorInstances restored the coarse cadence rather than stopping publication, which is the exact signal cost-control tooling reads after turning detailed monitoring off.
Fix: the EC2 metric-emission path that feeds AWS/EC2 into CloudWatch — the publication period for an instance's series must follow that instance's Monitoring.State (60 s while 'enabled', 300 s while 'disabled') and switch when MonitorInstances/UnmonitorInstances settle, instead of a single fixed cadence; re-bucketing on read cannot satisfy it because the cadence is decided at ingest.
Traces: cloudwatch__ec2.unmonitor-instances-restores-five-minute-cpu-publication-after-monitor-instances. The check's own budget for that step is _DETAILED_BUDGET_S = 600.0, the poll described as "a 1-minute (off 5-minute grid) CPUUtilization datapoint for <iid> after MonitorInstances", filtered as datapoints with Timestamp >= the instant Monitoring.State reached 'enabled' minus one minute and epoch-seconds % 300 != 0.
What had already succeeded before the barrier: the instance reached 'running', DescribeInstances reported Monitoring.State 'disabled' at launch, MonitorInstances answered Monitoring.State 'pending', and the state settled to 'enabled' within 180 s. What never happened: any off-5-minute-grid CPUUtilization datapoint.
Expected: at least one AWS/EC2 CPUUtilization datapoint for dimension {InstanceId} with epoch-seconds % 300 != 0 after Monitoring.State=enabled; then, after UnmonitorInstances settles to 'disabled', one on-grid bucket starting after the grace window and NO off-grid datapoint inside the following 300 s, with the earlier off-grid datapoints still readable.
