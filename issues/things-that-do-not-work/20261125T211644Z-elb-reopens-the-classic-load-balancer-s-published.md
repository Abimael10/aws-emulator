# elb: REOPENS — the Classic load balancer's published DNSName is a *.elb.localhost host the emulator is not reached on, so every Classic data-plane request through DNSName is refused

## Description
REOPENS 20261114T111813Z-elb-reopens-elb-classic-still-publishes-a-dnsname-the.md: its fix left the call refused. That issue is marked fixed and the published value did change shape (it is no longer a bare loopback `host:port`; it is now `[internal-]<name>-<id>.<region>.elb.localhost`, a bare host in AWS's name shape), but the address is still not one the emulator is reached on, so the three Classic data-plane checks below are still refused on the published URL rather than reaching the load balancer. This is reported as a reopen, not as a new defect.

Cause 1 of 1 — CreateLoadBalancer / DescribeLoadBalancers publish, as DNSName, a host in the loopback zone that the emulator does not answer on, so a client handed DNSName cannot reach the Classic data plane. Failing checks: elb.registered-instance-serves-real-http-through-elb-dns-name, elb.instance-health-decides-whether-real-http-reaches-the-backend, elb.out-of-service-instance-blocked-from-receiving-traffic.

AWS: Smithy (com.amazonaws.elasticloadbalancing#ElasticLoadBalancing_v7): CreateLoadBalancer input CreateAccessPointInput {LoadBalancerName required, Listeners required, AvailabilityZones/Subnets/SecurityGroups/Scheme/Tags}, output CreateAccessPointOutput {DNSName}; DescribeLoadBalancers -> DescribeAccessPointsOutput {LoadBalancerDescriptions}, each LoadBalancerDescription reporting the same DNSName. DNSName is the ONLY address a Classic client is given, and its contract is operational: a client RESOLVES that host (no scheme, no embedded port) and connects to it on the listener's LoadBalancerPort, the load balancer accepts the connection and relays the request to a registered InService instance, and the client is handed that backend's own status and bytes. The generated name, its id suffix, the host and the port are per-run values and are not requirements; what IS required is that the published address is an address the service actually answers on for the client that was handed it.

Emulator: the published name is minted as `[internal-]<label>-<id>.<region>.elb.<zone>` with zone = the loopback zone (services/service-com-amazonaws-elasticloadbalancing-elasticloadbalancing-v7/src/state/load_balancer_endpoint.rs, published_dns_name lines 110-123, announced_zone lines 139-146), and because the emulator IS served on an endpoint of its own no per-resource listener is opened for the load balancer (open_load_balancer_endpoint lines 182-197: `dialled_authority` is None whenever endpoint_authority(ctx) is Some). The result is a name with no port that the emulator does not serve: three checks that take DNSName and make an unsigned HTTP GET through it are refused before any request leaves, with `simparity.published.PublishedUrlRejected: endpoint_url was given http://<name>-<id>.<region>.elb.localhost/ (published by the emulator or built by the check): its host is not one of the emulator's own hosts; a customer of the emulator needs http(s)://127.0.0.1:<port>/<resource path>, or http(s)://<own host>:<port>/<path> on a per-resource listener` (the host label, region label and port digits are per-run values; the defect is announcing an address other than the one the emulator is reached on), and the third fails its own guard with `AssertionError: the emulator published http://<name>-<id>.<region>.elb.localhost: its host is not one of the emulator's own hosts`. Note the name also carries no port, so even if the loopback zone resolved to the bound interface, a GET on the listener port (80) would not arrive at the endpoint the API call was served on.

Why: a client that uses DNSName exactly as AWS documents it — an HTTP client, an external health probe, a Route 53 alias target, an integration test — is pointed at a host nothing answers on. Every Classic data-plane behavior is therefore unobservable through the only address AWS gives a client: listener forwarding of a request to the chosen backend, an InService instance serving its own 200/404, and an OutOfService instance being withheld from rotation while a healthy sibling keeps serving.

Fix: the published-address construction in the CreateLoadBalancer handler and the identical projection in DescribeLoadBalancers / the stored load balancer endpoint, plus the data-plane routing that must claim that host. The published DNSName must be an address the emulator answers on for the client that received it — either the emulator's own served authority (so a client can connect to it as-is) or a per-resource listener's authority — and the Host-header route for that name must be served by the load balancer's own plane on the endpoint the caller is already reaching.

Traces: checks elb.registered-instance-serves-real-http-through-elb-dns-name, elb.instance-health-decides-whether-real-http-reaches-the-backend, elb.out-of-service-instance-blocked-from-receiving-traffic.
