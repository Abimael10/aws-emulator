## Description
THREE (3) net-new divergence clusters on AWS Supply Chain (wire service token `scn`; sdkId `SupplyChain`, endpointPrefix/arnNamespace/sigv4Name `scn`, served by the bootstrapped crate `services/service-com-amazonaws-supplychain-galaxypublicapigateway`, so these are fidelity findings and not a bootstrap gap). Cause 1 of 3 — GetDataIntegrationEvent omits `datasetTargetDetails`, so the event's dataset load execution never reports a status (fixture `supplychain-data-integration-events`, step `task#4`). AWS: GetDataIntegrationEvent is GET /api-data/data-integration/instance/{instanceId}/data-integration-events/{eventId}, @readonly, SUCCESS_STATUS 200, output {event: DataIntegrationEvent @required} (Smithy). DataIntegrationEvent carries instanceId/eventId/eventType/eventGroupId/eventTimestamp (all @required) plus `datasetTargetDetails`: DataIntegrationEventDatasetTargetDetails, documented "The target dataset details for a DATASET event type", whose members datasetIdentifier (DataIntegrationDatasetArn), operationType (enum, APPEND among its values) and datasetLoadExecution (DataIntegrationEventDatasetLoadExecutionDetails {status @required, message}) are ALL @required when the structure is present (Smithy). Recorded behavior: an event accepted by SendDataIntegrationEvent for an ENTITY event type (the recorded one is a `scn.data.*` entity type, not `scn.data.dataset`) still reads back WITH `datasetTargetDetails` — `operationType` APPEND and `datasetLoadExecution.status` reaching the terminal value SUCCEEDED (`message` null for a load with no failure) — because such an event is loaded into the dataset the service keeps for that entity. The read is therefore the client's completion signal and the recorded step polls `$.event.datasetTargetDetails.datasetLoadExecution.status` until it is SUCCEEDED. Emulator: HTTP 200 whose event body carries only instanceId/eventId/eventType/eventGroupId/eventTimestamp — `$.event.datasetTargetDetails` is absent, so the poll never leaves `None`; it ran 37 attempts and was capped at the 180s poll ceiling. Why: a client that sends an event and then polls the event read to learn whether the load succeeded or failed (and to read the failure `message`) never gets a terminal status, so an ingest that the emulator has in fact accepted looks permanently in-flight: the client waits out its timeout and then either retries the send (duplicating data) or reports a false ingest failure. Fix: SendDataIntegrationEvent's handler plus the event record in the service state — the stored `DataIntegrationEventRecord.dataset_target_details` must be populated for every accepted event, not only for the request that carries an explicit `datasetTarget`, with `operationType` APPEND and `datasetLoadExecution.status` SUCCEEDED for a load the store accepted; the read's projection already copies whatever the record holds. Related open issue, which does NOT own this cluster (the replay reports `owned_by: []`, `stub_path: ""`): `20261114T215910Z-scn-data-integration-plane-serves-hollow-flow-and.md` covers the listing of events being EMPTY and the hollow flow projection; the send now records the event, so the empty page became this narrower omission of the dataset-target details, and the listing's own cluster (`supplychain-data-integration-events#task#5`) is still owned by that issue.

Cause 2 of 3 — SendDataIntegrationEvent accepts an unparseable `data` payload with 200 instead of refusing it (fixture `supplychain-data-integration-events`, step `task#6`). AWS: SendDataIntegrationEvent is POST /api-data/data-integration/instance/{instanceId}/data-integration-events, @idempotent, 200, input {instanceId @required, eventType @required, data: DataIntegrationEventData @required @length 1..1048576 @sensitive, eventGroupId @required, eventTimestamp, clientToken, datasetTarget}; `data` is documented as "The data payload of the event, should follow the data schema of the target dataset... To send single data record, use JsonObject format; to send multiple data records, use JsonArray format", and the operation declares ValidationException @httpError 400, documented "The input does not satisfy the constraints specified by an AWS service" (Smithy). A `data` string that is not well-formed JSON therefore does not satisfy that contract and is refused SYNCHRONOUSLY: HTTP 400 carrying the restJson1 `x-amzn-errortype` header and a `message` whose text for this error class is "Schema validation failed: Invalid JSON: Malformed JSON structure" — fixed text throughout, with no part taken from the request (the failure names the class of defect in the payload, not the payload's content). Emulator: HTTP 200 with an `eventId`, `$.message` absent and `$headers.x-amzn-errortype` absent — the payload is never parsed, so the event is recorded as if it had been accepted. Why: a client that submits a corrupt or truncated payload is told the event was accepted and gets an `eventId` for it, so the bad batch is never corrected or re-sent; worse, the client's error-handling path for malformed data is never exercised against the emulator, and data the real service would have rejected at the API boundary appears to be in the pipeline. Fix: SendDataIntegrationEvent's validation, ahead of the store write in its handler — parse the `data` member as JSON (a JsonObject or a JsonArray) and return the modeled ValidationException with AWS's schema-validation message above when it does not parse, recording nothing.

Cause 3 of 3 — GetDataIntegrationFlowExecution's not-found message is an emulator-authored sentence instead of AWS's (fixture `supplychain-instance-error-paths`, step `task#11`). AWS: GetDataIntegrationFlowExecution is GET /api-data/data-integration/instance/{instanceId}/data-integration-flows/{flowName}/executions/{executionId}, @readonly, 200, output {flowExecution @required}, and declares ResourceNotFoundException @httpError 404, documented "Request references a resource which does not exist" (Smithy). An `executionId` the addressed flow holds no run under is that 404, and the recorded message's FIXED text is "FlowExecution not found for given flowName: " + " and flowExecutionId: "; its VARIABLE parts are exactly two, both echoed from the request's @httpLabel members — the `flowName` and the `executionId` (the recorded run's literal flow name and all-zero UUID are that fixture's values filling the template, not the requirement). Emulator: HTTP 404 (status correct) with `$.message` = "Flow execution not found.", a fixed sentence that echoes neither label. Why: the status is right but the message is not AWS's, so a client or test that asserts on the refusal text, or that parses the message to learn WHICH flow and which execution id was rejected (the only place the service names them), sees neither identifier and cannot distinguish a bad execution id from a bad flow name. Fix: the operation's not-found branch — replace the fixed `crate::state::FLOW_EXECUTION_NOT_FOUND_MESSAGE` constant with AWS's flowName-and-executionId template rendered from the request's labels. Related open issue, which does NOT own this cluster (`owned_by: []`): `20261029T180412Z-scn-refusal-messages-are-emulator-authored-prose-instead.md` covers the same family of invented prose on GetInstance/CreateDataLakeNamespace and currently owns the CreateDataLakeNamespace pattern-message cluster (`supplychain-instance-error-paths#task#7`), not this flow-execution read.
