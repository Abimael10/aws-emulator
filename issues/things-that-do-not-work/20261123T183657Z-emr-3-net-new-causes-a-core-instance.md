# emr: 3 net-new causes — a CORE instance-group resize provisions no machine, notebook executions never reach a terminal NotebookExecutionStatus, and managed scaling never grows capacity when its ceiling is raised

> _Note: this issue was identified against the code base at commit `33ea92ed4461881d8f7ae2a85609594a4bd6a1fc`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
ModifyInstanceGroups

## Description
Three net-new root causes in the EMR cluster capacity/notebook data plane. Each is a separate convergence gate: in every case the emulator accepts the control-plane call with 200 and then never moves the state a client polls for, so the replay is cut off at the harness budget (`Error: Check timed out after 60.0s`) with no assertion reached. None of these three failures is marked ALREADY FILED or OWNED by the replay report, and no open issue carries them: the closest neighbours are 20261102T083234Z-elasticmapreduce-emr-cluster-and-instance-group-reads-omit-modeled.md (instance-group READ shape, not resize provisioning), 20261119T080047Z-elasticmapreduce-emr-auto-scaling-policy-refusals-name-the-cluster.md (auto-scaling policy refusal wording, not managed-scaling activity) and 20261104T102001Z-emr-8-net-new-root-causes-createvpcendpoint-refuses.md (different causes); none of them covers a resize that provisions nothing, a notebook execution that never settles, or a managed-scaling ceiling that produces no activity.

Cause 1 of 3: ModifyInstanceGroups on a CORE instance group raises no real capacity. Failing check: emr.core-instance-group-resize-adds-a-real-ec2-instance.
AWS: Smithy com.amazonaws.emr#ModifyInstanceGroups takes ClusterId plus InstanceGroups (InstanceGroupModifyConfigList carrying InstanceGroupId and InstanceCount) and returns an empty body (output_shape Unit); its only modeled error is InternalServerError (500). On a WAITING cluster, raising a CORE group's InstanceCount from 1 to 2 moves com.amazonaws.emr#InstanceGroup.RequestedInstanceCount ("The target number of instances for the instance group") to the new target, EMR then launches one additional EC2 instance of the group's InstanceType into the cluster's Ec2SubnetId, ListInstances (com.amazonaws.emr#ListInstances filtered by InstanceGroupId and InstanceStates) begins reporting a second, brand-new Ec2InstanceId in a non-TERMINATED com.amazonaws.emr#InstanceState (AWAITING_FULFILLMENT/PROVISIONING/BOOTSTRAPPING/RUNNING), InstanceGroup.RunningInstanceCount ("The number of instances currently running in this instance group") catches up to the target, EC2 DescribeInstances confirms the new id as a running instance of that type in that subnet, and the MASTER group's requested/running counts are untouched. The pre-existing instance id is kept — a resize ADDS a node, it does not replace one.
Emulator: the replay reaches no assertion at all — the check's progress gates are the describe_cluster poll to WAITING, then the 30 s ListInstances freeze window, then the post-ModifyInstanceGroups polls on RequestedInstanceCount and on the live Ec2InstanceId set; the 60 s budget is consumed inside that cycle, so the resize never becomes observable as either a raised RequestedInstanceCount or a second live instance id. Hypothesis: ModifyInstanceGroups stores (or discards) the new InstanceCount without driving an instance-group reconciliation, so no EC2 instance is launched and ListInstances/RunningInstanceCount stay at the initial count forever.
Why: a client that resizes a core group and then polls ListInstances or RunningInstanceCount for the new capacity — the normal way to wait for a resize — waits forever and cannot tell a resize still in flight from one that will never happen. Anything scheduled onto the added capacity (HDFS replication, YARN containers) silently never gets it.
Fix: the ModifyInstanceGroups handler and the instance-group reconciliation in the EMR cluster state (the component that turns RequestedInstanceCount into launched EC2 instances), plus the ListInstances / DescribeCluster projection that reports the group's RunningInstanceCount and member Ec2InstanceIds.
Traces: emr.core-instance-group-resize-adds-a-real-ec2-instance.

Cause 2 of 3: notebook executions never reach a terminal NotebookExecutionStatus, so ListNotebookExecutions' Status filter and ordering are unobservable. Failing check: emr.list-notebook-executions-ordering-and-status-filter.
AWS: Smithy com.amazonaws.emr#StartNotebookExecution returns StartNotebookExecutionOutput{NotebookExecutionId} for an execution submitted against an ExecutionEngine (the cluster id) with a ServiceRole and a NotebookS3Location; com.amazonaws.emr#DescribeNotebookExecution returns NotebookExecution whose Status is a com.amazonaws.emr#NotebookExecutionStatus — START_PENDING, STARTING, RUNNING, FINISHING, FINISHED, FAILING, FAILED, STOP_PENDING, STOPPING, STOPPED. A notebook whose cell succeeds progresses START_PENDING -> STARTING -> RUNNING -> FINISHING -> FINISHED; one whose cell raises ends FAILED. com.amazonaws.emr#ListNotebookExecutions takes an optional Status filter and ExecutionEngineId and returns NotebookExecutionSummary entries (NotebookExecutionId, Status, StartTime, EndTime, ExecutionEngineId): Status=FINISHED lists the finished execution and not the failed one, Status=FAILED lists the failed one and not the finished one, and two consecutive unfiltered listings of the same engine return the same ids in the same order.
Emulator: the replay reports `Error: Check timed out after 60.0s` with no assertion reached. The check's gates are the describe_cluster wait for WAITING/RUNNING and then the DescribeNotebookExecution polls for a Status in {FINISHED, FAILED}; the budget expires inside those polls, so no execution is ever presented in a terminal status and neither the Status partition nor the ordering stability is exercised. Hypothesis: the notebook-execution engine records the execution but never runs the notebook or advances its NotebookExecutionStatus past its initial value, so no execution ever becomes FINISHED or FAILED.
Why: a client polling DescribeNotebookExecution for completion never gets an outcome, and ListNotebookExecutions(Status=...) returns the same set regardless of the filter, so a succeeded execution is indistinguishable from a failed one. Scheduling or dashboarding code that partitions executions by Status reads an empty or undifferentiated list.
Fix: the notebook-execution runner and the StartNotebookExecution/DescribeNotebookExecution status state machine in the EMR service crate, which must execute the notebook and settle it in a terminal NotebookExecutionStatus, plus the ListNotebookExecutions handler's Status filtering and its stable ordering of NotebookExecutionSummary entries.
Traces: emr.list-notebook-executions-ordering-and-status-filter.

Cause 3 of 3: raising a managed-scaling ceiling produces no scaling activity — no additional core/task capacity is ever targeted or launched for pending YARN demand. Failing check: emr.scaling-managed-scaling-headroom-adds-real-instances-for-pending-yarn-work.
AWS: Smithy com.amazonaws.emr#PutManagedScalingPolicy (required ClusterId + ManagedScalingPolicy) and com.amazonaws.emr#GetManagedScalingPolicy (returns ManagedScalingPolicy) carry com.amazonaws.emr#ComputeLimits with required UnitType, MinimumCapacityUnits and MaximumCapacityUnits — "The upper boundary of Amazon EC2 units ... Managed scaling activit[y] ... is not allowed to go above or below these limits ... applies to the core and task nodes. The master node cannot be scaled after initial configuration." With MaximumCapacityUnits clamped to the already-provisioned core+task count, a deep pending YARN queue must NOT raise the groups' RequestedInstanceCount above that ceiling; once PutManagedScalingPolicy raises MaximumCapacityUnits, the same pending demand must make managed scaling target more core/task capacity (RequestedInstanceCount summed over the CORE and TASK groups rises above the old ceiling and stays at or below the new one) and those targets must become real instances — ListInstances reports more live non-primary Ec2InstanceIds than the clamp allowed, and EC2 DescribeInstances knows each added id as the groups' InstanceType.
Emulator: the replay reports `Error: Check timed out after 60.0s` with no assertion reached. The gates are the describe_cluster wait to WAITING, the ListInstances baseline, AddJobFlowSteps for the demand step, the clamp-observation window and then the post-PutManagedScalingPolicy polls over ListInstanceGroups/ListInstances; the budget expires inside that cycle, so neither the clamp arm nor the growth arm is ever observed. Hypothesis: there is no managed-scaling activity loop at all — PutManagedScalingPolicy/GetManagedScalingPolicy are a pure key/value store, and no pending-work signal ever changes the CORE/TASK groups' RequestedInstanceCount or launches an instance.
Why: managed scaling becomes a no-op that still reports a policy. A client that sizes a cluster by raising MaximumCapacityUnits and then waits for capacity never gets it; worse, because nothing ever scales, a clamped ceiling and an open ceiling are indistinguishable, so a cost guardrail expressed as MaximumCapacityUnits appears to be honoured while in fact nothing is enforced.
Fix: the managed-scaling activity loop in the EMR cluster state (the component that reads ComputeLimits plus pending cluster demand and moves the CORE/TASK groups' RequestedInstanceCount within MinimumCapacityUnits..MaximumCapacityUnits), together with the instance-group reconciliation that turns those targets into launched EC2 instances — the same reconciliation named in Cause 1.
Traces: emr.scaling-managed-scaling-headroom-adds-real-instances-for-pending-yarn-work.

## Evidence
All three failing checks are verdict `mismatch` with the same replay output: `Error: Check timed out after 60.0s` — no assertion in the check body was reached, because each check's convergence gate never passes.

Cause 1 — emr.core-instance-group-resize-adds-a-real-ec2-instance
Scenario replayed: an EMR service role (AmazonElasticMapReduceRole) and an EC2 instance profile (AmazonElasticMapReduceforEC2Role); a private VPC/subnet with an S3 gateway endpoint; RunJobFlow with ReleaseLabel emr-6.15.0, Applications [Hadoop], InstanceGroups MASTER m5.xlarge x1 and CORE m5.xlarge x1, KeepJobFlowAliveWhenNoSteps=true; wait for Status.State WAITING; ListInstanceGroups must expose exactly {MASTER, CORE}; a 30 s freeze window over ListInstances(InstanceGroupId=CORE, InstanceStates=[AWAITING_FULFILLMENT, PROVISIONING, BOOTSTRAPPING, RUNNING]) must agree and hold exactly 1 id; then ModifyInstanceGroups(InstanceGroups=[{InstanceGroupId: <core>, InstanceCount: 2}]).
Expected per AWS: ListInstanceGroups CORE.RequestedInstanceCount becomes 2; ListInstances reports exactly 2 live ids, a strict superset of the 1 pre-resize id (exactly one id added); CORE.RunningInstanceCount converges to 2; ec2.DescribeInstances on both ids reports State.Name "running", InstanceType "m5.xlarge" and the requested SubnetId; the MASTER group's (RequestedInstanceCount, RunningInstanceCount) pair is unchanged and holds exactly 1 live id disjoint from the CORE ids.
Actual from the emulator: the check never reaches the RequestedInstanceCount or ListInstances assertions — the 60 s budget is consumed inside the provision/freeze/resize poll cycle, so no raised target and no added instance id is ever observed.

Cause 2 — emr.list-notebook-executions-ordering-and-status-filter
Scenario replayed: an S3 bucket; a notebook-capable cluster plus its service role; wait for cluster Status.State in {WAITING, RUNNING}; upload two notebooks, one whose cell is `print(1 + 1)` and one whose cell is `raise RuntimeError(...)`; StartNotebookExecution for each against ExecutionEngine = the cluster id; poll DescribeNotebookExecution until NotebookExecution.Status is FINISHED or FAILED.
Expected per AWS: the printing notebook settles FINISHED and the raising notebook settles FAILED; ListNotebookExecutions(Status="FINISHED", ExecutionEngineId=<cluster>) contains the first id and not the second; ListNotebookExecutions(Status="FAILED", ExecutionEngineId=<cluster>) contains the second and not the first; two consecutive unfiltered ListNotebookExecutions(ExecutionEngineId=<cluster>) calls return identical id sequences, and that sequence contains both ids.
Actual from the emulator: the 60 s budget expires inside the DescribeNotebookExecution polling for a terminal status; no execution reaches FINISHED or FAILED, so neither the Status partition nor the order-stability assertion is ever evaluated.

Cause 3 — emr.scaling-managed-scaling-headroom-adds-real-instances-for-pending-yarn-work
Scenario replayed: a private VPC/subnet; an S3 bucket holding a PySpark job sized to 320 partitions x ~20 s of CPU burn; RunJobFlow with ReleaseLabel emr-6.15.0, one MASTER, one CORE and one TASK m5.xlarge (baseline core+task = 2) and a managed scaling policy whose ComputeLimits MinimumCapacityUnits=1 and MaximumCapacityUnits=2 (clamped to the provisioned capacity); wait for WAITING; GetManagedScalingPolicy must echo MaximumCapacityUnits=2; ListInstances must report exactly 2 live non-primary instances and ListInstanceGroups exactly 2 requested between CORE and TASK; AddJobFlowSteps submits the demand step; the clamped ceiling is then watched for 180 s; then PutManagedScalingPolicy raises MaximumCapacityUnits to 5 while the step is still PENDING/RUNNING.
Expected per AWS: during the clamp window the summed CORE+TASK RequestedInstanceCount never exceeds 2; after the ceiling is raised the summed RequestedInstanceCount exceeds 2 and stays <= 5, ListInstances reports more than 2 live non-primary instances, every added id is known to ec2.DescribeInstances as an m5.xlarge, and the step still ends COMPLETED having written exactly one part file plus _SUCCESS under the output prefix.
Actual from the emulator: the 60 s budget expires before the clamp window and the ceiling-raise arm are reached; no managed-scaling activity, no change to RequestedInstanceCount and no added instance is ever observed, so the clamp arm and the growth arm return the same (empty) observation.
