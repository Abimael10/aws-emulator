# geo-routes snapped positions, snapped geometry and match confidence are synthesized from the request coordinates instead of road-graph values

> _Note: this issue was identified against the code base at commit `789c7a890d26c428a053c99e86a00990d57bc346`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
SnapToRoads

## Description
Across CalculateRoutes and SnapToRoads the geo-routes emulator answers HTTP 200 with a structurally valid body, but every value that AWS derives from the road network - the snapped position, the interpolated snapped geometry and the point-match confidence - is instead produced by an arithmetic transform of the request coordinates. The request position that AWS is required to echo back verbatim is also quantized. This bundle carries THREE causes.

=== Cause 1 of 3: CalculateRoutes leg Place.Position is not the road-snapped point, and Place.OriginalPosition is not the request position echoed verbatim ===
AWS: Smithy com.amazonaws.georoutes#CalculateRoutes (POST /v2/routes, success 200; modeled errors ValidationException 400, AccessDeniedException 403, ThrottlingException 429, InternalServerException 500 - none in play, both sides answer 200, so no status, error code or error message diverges). The leg's Arrival/Departure Place is RouteVehiclePlace: member OriginalPosition targets Position23 (@length min 2 max 3, @sensitive) and is documented "Position provided in the request"; member Position is @required, targets Position23, and is documented "Position in World Geodetic System (WGS 84) format: [longitude, latitude]" - i.e. the position actually used for the leg, resolved onto the road network, which generally differs from the requested one. OriginalPosition is therefore an exact echo of the submitted coordinate at the precision the client sent, and Position is a road-graph result carried at the precision of that computed position (the recording shows 7 decimal places).
Emulator: OriginalPosition comes back as the request coordinate quantized to 4 decimal places, so the digits the client sent are discarded (expected -122.3088001, got -122.3088; expected 47.4501999, got 47.4502; expected -122.3410001, got -122.341). Position is not a road-graph resolution either: it is the quantized request coordinate plus a small fixed synthetic delta on one axis (got -122.308836 against the recorded snap -122.3029601; got -122.340836 against -122.3409556) while the other axis is left equal to the quantized request value (got 47.4502 against the recorded snap 47.45124; got 47.6089 against 47.6089359). Hypothesis: the handler builds both members from one rounded copy of the request coordinate and offsets it, rather than keeping the raw input for OriginalPosition and resolving the road graph for Position; the model states only the member semantics and the recording only shows resulting values, so the exact formula is recorded behavior only.
Why: a client that compares OriginalPosition with Position to decide "was my waypoint on a road, and how far is the access point?" gets a meaningless answer - the delta is a constant artifact, not a real snap displacement, and in the latitude case it is zero even though the true snap moved the point ~110 m. Quantizing OriginalPosition also breaks round-tripping: a client that re-submits the echoed OriginalPosition as a waypoint, or that keys its own records by the coordinate it sent, no longer matches. Both failures are silent, since the response is a 200 with correctly shaped two-element positions.
Fix: the CalculateRoutes handler's response synthesis in the geo-routes service crate - echo the request coordinate into Place.OriginalPosition unmodified, and populate Place.Position from a road-graph resolution of that coordinate at the resolved position's own precision.
Traces: geo-routes-calculate-routes-truck-travel-mode-options-wiring-success#task#1 (representative), geo-routes-calculate-routes-zero-max-alternatives-returns-single-route#task#1 (affected_count 2).

=== Cause 2 of 3: SnapToRoads SnappedGeometry.Polyline is invented, SnappedTracePoints[*].Confidence is a pseudo-random number, and SnappedPosition is not road-snapped ===
AWS: Smithy com.amazonaws.georoutes#SnapToRoads (POST /v2/snap-to-roads, success 200; same four modeled errors, none in play - both sides answer 200). Output SnappedGeometry is RoadSnapSnappedGeometry, documented "Interpolated geometry for the snapped route that is overlay-able onto a map", whose Polyline (@length min 1, @sensitive) is "an ordered list of positions used to plot a route on a map in a lossy compression format" - i.e. the encoded road-following path through the snapped trace points, not a path through the raw inputs. Each SnappedTracePoints entry is RoadSnapSnappedTracePoint with @required Confidence (SensitiveDouble, @range min 0 max 1) documented "Confidence value for the correctness of this point match", @required OriginalPosition "Position of the TracePoint provided within the request, at the same index", and @required SnappedPosition "Snapped position of the TracePoint provided within the request, at the same index". Confidence is therefore a property of the match (a point far from any road, or one matched ambiguously, scores low; a point squarely on a road scores 1), and the recording shows exactly that spread - 1, 0.05, 0.04, 0.12.
Emulator: the polyline is a much shorter, differently shaped encoding than the recorded interpolated geometry (expected 'BG0u856C326qpHwHnGgP3NgP3Nof_dkNvM8GnGoL_JkN7L8QvR8Lkc4IoVgKkX8B4D0UkwB8GoQ8G8Q', got 'BGoz856Cv16qpHAwQofAobAgEAofAofAAgVAoKofAofAAwI'), consistent with encoding the trace points themselves rather than an interpolated road path. Confidence is emitted as a long-tailed pseudo-random value in [0,1] that is uncorrelated with how well the point matched (got 0.5624402370375639, 0.9205739449522025, 0.5624154808054271, 0.562403101865775 where the recording has 1, 0.05, 0.04, 0.12) - note the near-identical 0.5624... values for three different points, the signature of a value derived from a hash/seed rather than from a match. SnappedPosition is again the request coordinate transformed: one axis quantized to 4 dp and the other offset by a fixed synthetic delta (got -122.3366/47.610164 against the recorded snap -122.33662/47.61009; got -122.336336/47.6111 against -122.33718/47.61071), so points that AWS reports as poorly matched are reported here as sitting essentially where they were sent.
Why: the entire purpose of SnapToRoads is to tell a client where its GPS trace really ran and how much to trust each match. A client that filters or flags trace points on Confidence (the documented use) keeps the bad points and drops the good ones, because the ordering of the scores is noise; a client that draws SnappedGeometry.Polyline on a map renders a path that cuts across the raw trace instead of following roads; and a client that stores SnappedPosition gets its own input back rather than a road-anchored point. Every one of these arrives as a 200 with in-range, correctly shaped values, so nothing surfaces the problem.
Fix: the SnapToRoads handler's response synthesis in the geo-routes service crate - snap each TracePoint against the road graph (honouring SnapRadius and TravelMode/TravelModeOptions), set Confidence from the resulting match quality, emit SnappedPosition at the snapped position's own precision with OriginalPosition echoing the submitted coordinate unmodified, and encode SnappedGeometry.Polyline from the interpolated road path through those snapped points.
Traces: geo-routes-snap-to-roads-basic-success#task#1 (affected_count 1).

The specific coordinates, polylines and confidence numbers above are those recordings' values and are examples, not literal requirements. The requirements are the rules: OriginalPosition echoes the submitted coordinate unmodified; Position / SnappedPosition is the road-graph resolution of that coordinate at the resolved position's own precision; Confidence reflects the quality of that point's match (poorly matched points score low, a point on a road scores 1), and the ordering of confidences across trace points must follow match quality; SnappedGeometry.Polyline encodes the interpolated road path through the snapped points. Note the emulator's tell-tale signatures: three different trace points receive confidences agreeing to four decimal places (0.5624...), and on each diverging position one axis is the request coordinate at 4 dp while the other carries a constant ~0.000036 delta.
