# appsync: 4 net-new causes — realtime delivery ignores the subscription's selection set, @aws-appsync/utils exports no `extensions` (no subscription filtering, no invalidation), and the unknown-Action refusal reached through an HTTP data source is re-worded

> _Note: this issue was identified against the code base at commit `c1e629eb7cbb6abd12d76d276265809665f4d5fd`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
GraphQL realtime subscription delivery (data plane); STS GetCallerIdentity/unknown Action via an HTTP data source

## Description
Four net-new root causes in the AppSync emulator, all surfaced by behavioral checks the suite lists under `### appsync`. Causes 1-3 are in the GraphQL/realtime data plane (subscription delivery, the APPSYNC_JS runtime's `extensions` module); cause 4 is the refusal the emulator serves to an AppSync HTTP data source when the backend query-protocol Action does not exist. A fixer must close all FOUR before submitting.

=== Cause 1 of 4: a delivered subscription frame carries fields the SUBSCRIPTION document did not select ===
Failing check ids: appsync.appsync-subscription-delivers-mutation-to-realtime-subscriber
AWS: not modeled in Smithy — GraphQL subscription delivery is AppSync's data plane, so this is AWS-documented + recorded behavior only. AWS documents that a mutation annotated with @aws_subscribe publishes its RESULT to the subscription field, and the service then resolves/projects that result against EACH subscriber's own subscription document: the data frame's `payload.data.<subscriptionField>` contains exactly the fields in that subscriber's selection set and nothing else. The mutation's own selection set is the publisher's, not the subscriber's; a field the subscription never asked for is never delivered (this is the documented mechanism behind using a non-selected field only as a filter/secret).
Emulator: with schema `type Post { id: ID! body: String secret: String }`, subscription document `subscription OnAdd { onAddPost { id body } }`, and mutation `mutation Add(...) { addPost(id,body,secret) { id body secret } }`, the frame delivered on the realtime socket is `payload.data.onAddPost = {id, body, secret}` — sorted keys ['body','id','secret']. The emulator forwards the mutation's own result/selection set verbatim instead of projecting it onto the subscription document.
Why: a client relying on AWS's projection is handed data it never requested. The documented pattern of keeping a field out of the subscription's selection set (an owner id, a token, a `secret`) stops being a boundary: every subscriber on the field receives the publisher's full selection, so an emulator-backed test cannot observe the over-delivery AWS prevents, and client code that trusts the shape of `payload.data` sees unexpected members.
Fix: the appsync service crate's realtime/subscription delivery component (the publisher that fans a mutation result out to live subscriptions) — it must resolve the stored subscription document's selection set against the published result per subscriber, not forward the mutation's response object.
Traces: appsync.appsync-subscription-delivers-mutation-to-realtime-subscriber (start_ack received, mutation 200 with secret stored, then AssertionError: "a field outside the SUBSCRIPTION's selection set was delivered: ['body', 'id', 'secret']").

=== Cause 2 of 4: a subscribe-time enhanced subscription filter (extensions.setSubscriptionFilter) is accepted and then ignored, so non-matching mutations are delivered ===
Failing check ids: appsync.appsync-subscription-filter-excludes-nonmatching-mutation
AWS: not modeled in Smithy (data plane) — AWS-documented + recorded behavior only. AWS documents enhanced subscription filtering: a subscription field's APPSYNC_JS resolver calls `extensions.setSubscriptionFilter({filterGroup: [{filters: [{fieldName, operator, value}]}]})` in its request handler at SUBSCRIBE time; the service stores that filterGroup against the subscription and evaluates it server-side against every publication, delivering ONLY publications whose fields satisfy it. A mutation whose `channel` is 'beta' therefore produces NO data frame for a subscription filtered on `channel eq 'alpha'`, while the 'alpha' mutation produces exactly one.
Emulator: the subscription is accepted (start_ack), both mutations resolve 200, and the FIRST data frame delivered is the non-matching one: `{'data': {'onAddPost': {'id': 'beta-<id>', 'channel': 'beta', 'body': 'beta-<id>'}}}`. The filter installed by the subscribe-time handler has no effect on delivery — every publication on the field is fanned out to every subscriber. (Cause 3 shows why: the runtime has no `extensions` export at all; here the subscribe-time path swallows that instead of refusing, so the subscription looks healthy while enforcing nothing.)
Why: enhanced subscription filtering is the server-side authorization/routing boundary for realtime data. A client that filters per-tenant or per-channel at subscribe time receives every other tenant's publications on the emulator, and a negative-delivery test (the only way to assert the filter works) always passes-through. Nothing in the frame tells the client the filter was dropped.
Fix: the appsync service crate's APPSYNC_JS resolver runtime (the `@aws-appsync/utils` module surface — see cause 3) plus the subscription registry/delivery path that must persist the filterGroup returned by the subscribe-time request handler and evaluate it against each publication before delivering. A subscribe-time handler whose module imports cannot be resolved must fail the subscribe rather than register an unfiltered subscription.
Traces: appsync.appsync-subscription-filter-excludes-nonmatching-mutation (AssertionError: "the first frame delivered was not the matching channel: {'data': {'onAddPost': {'id': 'beta-...', 'channel': 'beta', 'body': 'beta-...'}}}").

=== Cause 3 of 4: '@aws-appsync/utils' exports no `extensions`, so invalidateSubscriptions / setSubscriptionInvalidationFilter fail the resolver ===
Failing check ids: appsync.deep-appsync-3-appsync-rt-invalidation-completes-only-matching-subscriber
AWS: not modeled in Smithy (data plane) — AWS-documented + recorded behavior only. AWS documents `extensions` as part of the `@aws-appsync/utils` module available to APPSYNC_JS (runtimeVersion 1.0.0) resolvers: `extensions.setSubscriptionInvalidationFilter(filterGroup)` in a subscription field's request handler, and `extensions.invalidateSubscriptions({subscriptionField, payload})` in a mutation's RESPONSE handler. The mutation that raises the invalidation returns normally — HTTP 200 with its own data and NO `errors` member — and the service then ends exactly those live subscriptions whose invalidation filter matches the payload by sending them a `complete` frame on the still-open socket, leaving non-matching subscribers untouched.
Emulator: the mutation's response handler fails on the import itself. The GraphQL reply is HTTP 200 with `{'data': {'revoke': None}, 'errors': [{'path': ['revoke'], 'message': "Could not find export 'extensions' in module '@aws-appsync/utils'"}]}`. The resolver never returns its result, no invalidation is raised and no `complete` frame is ever sent, so subscription invalidation is entirely unavailable; the same missing export also silently neuters the subscribe-time invalidation filter.
Why: a client using the documented invalidation API gets a hard field error ('revoke' resolves to null) on a mutation AWS answers successfully, and the subscriptions it meant to end stay open and keep receiving data. Any session-revocation / entitlement-withdrawal flow built on invalidateSubscriptions is both broken and reported as a resolver error pointing at the SDK module rather than at anything the client did.
Fix: the appsync service crate's APPSYNC_JS runtime module registry — `@aws-appsync/utils` must export `extensions` with setSubscriptionFilter, setSubscriptionInvalidationFilter and invalidateSubscriptions — and the realtime subscription registry that must store the invalidation filter and, on invalidateSubscriptions, send `complete` to exactly the matching subscription ids.
Traces: appsync.deep-appsync-3-appsync-rt-invalidation-completes-only-matching-subscriber (AssertionError: "GraphQL call failed: 200 {'data': {'revoke': None}, 'errors': [{'path': ['revoke'], 'message': \"Could not find export 'extensions' in module '@aws-appsync/utils'\"}]}").

=== Cause 4 of 4: an unknown query-protocol Action reached through an AppSync HTTP data source is refused with an emulator-authored message (and diagnosed as a missing Action) ===
Failing check ids: appsync.http-data-source-resolver-forwards-backend-status-and-body
AWS: Smithy: the backend is AWSSecurityTokenServiceV20110615, protocol awsQuery, sigv4Name sts, xmlNamespace https://sts.amazonaws.com/doc/2011-06-15/ (service_info on services/service-com-amazonaws-sts-awssecuritytokenservicev20110615/smithy-model/com-amazonaws-sts-awssecuritytokenservicev20110615.json); `BogusAction` is bound to no operation of that service. The refusal itself is a framework (unmodeled) error, so its identity is recorded behavior only: an awsQuery request naming an Action the service does not have — here a GET with query parameters Action=<Action>&Version=<Version> — is refused with HTTP 400 and the awsQuery error document <ErrorResponse><Error><Type>Sender</Type><Code>InvalidAction</Code><Message>Could not find operation <Action> for version <Version></Message></Error><RequestId>…</RequestId></ErrorResponse>. Message template: the fixed text is "Could not find operation " … " for version "; the two variable parts are the request's own Action and Version parameter values (here BogusAction and 2011-06-15 — those literals are this run's request values filling the template, not part of it). RequestId is per-run and not part of the contract. AppSync side (documented HTTP-resolver contract, already honoured here): the non-2xx outcome is bound to $ctx.result as {statusCode, headers, body} and forwarded through the response template, so the GraphQL reply is 200 with no `errors` and the backend status/body visible in the selected fields.
Emulator: the forwarded statusCode is correct (400) but the body's error triple is (Type 'Sender', Code 'InvalidAction', Message 'unknown action: request is missing the `Action` field'). Two divergences in one message: AWS's wording is replaced by emulator-authored text, and that text asserts the `Action` field is MISSING when the request plainly carried Action=BogusAction in its query string (the sibling leg of the same check, Action=GetCallerIdentity on the same GET shape, is dispatched and refused 403 MissingAuthenticationToken correctly). Hypothesis: the awsQuery action dispatcher only reads `Action` from a form-encoded body, so on a GET it falls through to its generic missing-Action branch and never renders the requested action or version.
Why: a client (or an AppSync resolver inspecting $ctx.result.body, as this check does) that branches on the refusal text is told its request omitted a field it did send, so debugging is pointed at request construction instead of at the wrong action name; and any assertion on AWS's documented InvalidAction sentence — including the name of the operation that was not found and the API version it was looked up in — cannot hold against the emulator.
Fix: the awsQuery action-dispatch/refusal layer of the sts service crate (services/service-com-amazonaws-sts-awssecuritytokenservicev20110615): resolve `Action`/`Version` from the query string as well as the form body, and render the unknown-action refusal as HTTP 400 InvalidAction with AWS's sentence interpolating the request's own Action and Version, reserving the missing-`Action` diagnostic for a request that truly carries none.
Related-but-not-covering: 20261120T043537Z-appsync-an-http-data-source-s-unsigned-backend.md (open) carries this check id, but its replay key is the earlier `assert identity_error == (… MissingAuthenticationToken …)` step, which now passes; this check fails further down, on the bogus-action leg, which that issue does not describe or carry a key for.

## Evidence
Cause 1 — appsync.appsync-subscription-delivers-mutation-to-realtime-subscriber
Schema: type Post { id: ID! body: String secret: String }; Mutation.addPost(id, body, secret): Post; Subscription.onAddPost: Post @aws_subscribe(mutations: ["addPost"]).
Subscriber document: subscription OnAdd { onAddPost { id body } }. Publisher: mutation Add($id,$body,$secret) { addPost(...) { id body secret } }.
Expected (AWS): the data frame's payload.data.onAddPost contains exactly the subscription's selection set — keys ['body','id'] — with `secret` absent.
Actual (emulator): payload.data.onAddPost keys are ['body','id','secret'] → AssertionError: "a field outside the SUBSCRIPTION's selection set was delivered: ['body', 'id', 'secret'] -- AppSync must project the mutation result onto the subscription document, not forward the mutation's own selection set". (The frame is correctly addressed to the subscription id and carries the right id/body, so delivery itself works; only the projection is wrong.)

Cause 2 — appsync.appsync-subscription-filter-excludes-nonmatching-mutation
Subscribe-time APPSYNC_JS resolver: import { extensions } from '@aws-appsync/utils'; request(ctx) { extensions.setSubscriptionFilter({ filterGroup: [ { filters: [ { fieldName: 'channel', operator: 'eq', value: 'alpha' } ] } ] }); return { payload: null }; }
Sequence: subscribe (start_ack OK) → mutation with channel 'beta' (200) → mutation with channel 'alpha' (200) → read frames.
Expected (AWS): exactly ONE data frame, the 'alpha' publication; the 'beta' publication is suppressed server-side and never appears on the socket.
Actual (emulator): the first data frame is the suppressed-leg publication → AssertionError: "the first frame delivered was not the matching channel: {'data': {'onAddPost': {'id': 'beta-126bf090ccf7', 'channel': 'beta', 'body': 'beta-126bf090ccf7'}}}" (the 'beta-…' id/body are this run's generated markers, not a requirement — the requirement is that NO frame for the non-matching channel is delivered).

Cause 3 — appsync.deep-appsync-3-appsync-rt-invalidation-completes-only-matching-subscriber
Mutation response handler: import { extensions } from '@aws-appsync/utils'; response(ctx) { extensions.invalidateSubscriptions({ subscriptionField: 'onMsg', payload: { group: ctx.args.group } }); return ctx.result; } — paired with a subscribe-time extensions.setSubscriptionInvalidationFilter on the same module.
Expected (AWS): the revoke mutation answers HTTP 200 with data.revoke resolved and NO `errors`; subscriber A (invalidation filter group eq 'A') then receives a `complete` frame naming its own subscription id on a still-open socket, while subscriber B keeps receiving its own group's publications.
Actual (emulator): HTTP 200 with a field error → {'data': {'revoke': None}, 'errors': [{'path': ['revoke'], 'message': "Could not find export 'extensions' in module '@aws-appsync/utils'"}]}; the mutation never returns its result, so no invalidation is raised and no `complete` frame is sent.

Cause 4 — appsync.http-data-source-resolver-forwards-backend-status-and-body
HTTP data source endpoint https://sts.<region>.amazonaws.com; request template {"version":"2018-05-29","method":"GET","resourcePath":"/","params":{"query":{"Action":"BogusAction","Version":"2011-06-15"}}}; response template {"statusCode": $ctx.result.statusCode, "body": $util.toJson($ctx.result.body)}.
Expected (AWS): forwarded statusCode 400 and an ErrorResponse XML whose (Type, Code, Message) is ('Sender', 'InvalidAction', 'Could not find operation BogusAction for version 2011-06-15') — fixed text "Could not find operation … for version …" with the Action and Version taken from the request's own query parameters.
Actual (emulator): statusCode 400 is forwarded correctly, but the body parses to ('Sender', 'InvalidAction', 'unknown action: request is missing the `Action` field') → AssertionError: "unexpected bogus action error ('Sender', 'InvalidAction', 'unknown action: request is missing the `Action` field')". Type and status match; the Message is emulator-authored AND misdiagnoses a present Action as absent. The sibling leg of the same check (Action=GetCallerIdentity, same GET shape) is dispatched and refused 403 MissingAuthenticationToken as expected, so the request shape does reach the dispatcher.

## Steps to Reproduce
Common setup (causes 1-3): CreateGraphqlApi(name=<n>, authenticationType='API_KEY') → CreateApiKey(apiId) → StartSchemaCreation with the check's SDL (a Mutation field plus a Subscription field annotated @aws_subscribe(mutations:[<that mutation>])) → poll GetSchemaCreationStatus to SUCCESS → CreateDataSource(type='NONE') → CreateResolver(..., runtime={'name':'APPSYNC_JS','runtimeVersion':'1.0.0'}, code=<handler below>). Then open a WebSocket to uris.REALTIME with subprotocol graphql-ws, send connection_init, then a `start` frame whose payload.data is the subscription document and payload.extensions.authorization carries the API key.

Cause 1: schema `type Post { id: ID! body: String secret: String }`, Mutation.addPost(id, body, secret): Post, Subscription.onAddPost: Post @aws_subscribe(mutations:["addPost"]). Subscribe with `subscription OnAdd { onAddPost { id body } }`. POST `mutation Add($id: ID!, $body: String, $secret: String) { addPost(id: $id, body: $body, secret: $secret) { id body secret } }` to uris.GRAPHQL with x-api-key. Read the next `data` frame and list the keys of payload.data.onAddPost: AWS gives ['body','id']; the emulator gives ['body','id','secret'].

Cause 2: schema adds `channel: String` to Post and makes Mutation.addPost(id, channel!, body). Cause 3: schema `type Msg { group: String body: String }`, Mutation.publish(group!, body!): Msg and Mutation.revoke(group!): Msg, Subscription.onMsg(group: String!): Msg @aws_subscribe(mutations:["publish"]). The same divergence is reachable without AppSync by issuing GET https://sts.<region>.amazonaws.com/?Action=BogusAction&Version=2011-06-15 against the emulator.
