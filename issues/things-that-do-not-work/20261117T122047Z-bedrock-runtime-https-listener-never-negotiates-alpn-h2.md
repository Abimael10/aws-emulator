# bedrock-runtime: HTTPS listener never negotiates ALPN h2 (TLS alert 120) so ConverseStream is unreachable over HTTP/2, and Converse accepts a profile-only model id instead of refusing it

> _Note: this issue was identified against the code base at commit `c917baaf10025351922dbd2d0dcb1fd84ad836e2`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
ConverseStream

## Description
TWO net-new root causes on the bedrock-runtime data plane, both reached by the two hand-signed raw-transport ConverseStream checks (neither is marked already-filed/owned by the suite). Smithy consulted: services/service-com-amazonaws-bedrockruntime-amazonbedrockfrontendservice/smithy-model/com-amazonaws-bedrockruntime-amazonbedrockfrontendservice.json.

Cause 1 of 2 — the emulator's TLS endpoint does not offer the ALPN protocol 'h2', so a client that offers only h2 is rejected at the TLS handshake and ConverseStream cannot be driven over HTTP/2 at all.
AWS: ConverseStream is modeled POST /model/{modelId}/converse-stream -> 200 with an @streaming httpPayload event stream (output member `stream` -> ConverseStreamOutput, content-type application/vnd.amazon.eventstream). Real bedrock-runtime endpoints terminate TLS with ALPN advertising h2 (that is how the AWS SDKs carry the bidirectional/streaming inference operations); a TLS ClientHello whose ALPN list is exactly ['h2'] completes the handshake, the session reports alpnProtocol 'h2', and the signed request returns :status 200 with the event-stream content-type and the messageStart / contentBlockDelta / contentBlockStop / messageStop / metadata frames. The HTTP/1.1 form of the same signed request is served identically. Transport negotiation is not in the Smithy model, so the h2 availability itself is recorded behavior only.
Emulator: the TLS listener completes no handshake for an h2-only ALPN offer. The client aborts with 'SSL routines:ssl3_read_bytes:tlsv1 alert no application protocol' (TLS alert 120, no_application_protocol) — i.e. the server advertises no protocol the client offered, so only http/1.1 is announced. No HTTP request is ever made and nothing about the ConverseStream handler is exercised.
Why: any client pinned to HTTP/2 for Bedrock streaming (the AWS SDKs' h2 transports, grpc-style h2-only proxies, and any caller that disables HTTP/1.1 downgrade) cannot reach the emulator at all: the failure surfaces as an opaque TLS error long before the API, so a user cannot tell a transport mis-configuration from an unimplemented operation. It also makes every HTTP/2-only fidelity assertion unobservable.
Fix: the emulator's HTTPS/TLS termination layer (the front-door listener that builds the TLS server config for all services) — it must include 'h2' in the advertised ALPN protocol list alongside 'http/1.1' and serve the same routed response on an HTTP/2 connection as on HTTP/1.1, including the event-stream payload of ConverseStream.
Traces: bedrock-runtime.converse-stream-hand-signed-http2-and-http1-1-both-serve-the-event-stream (fails at the h2 handshake before any request). bedrock-runtime.converse-stream-hand-signed-http2-model-needing-inference-profile-rejected-as-plain-json also sends its raw requests over node:http2 and will hit this same handshake once Cause 2 is fixed.

Cause 2 of 2 — a model id that is reachable only through a cross-region inference profile is accepted and answered 200 instead of being refused.
AWS: ConversationalModelId permits a bare foundation-model id, but on-demand invocation of a model that is only offered through an inference profile is refused. Converse/ConverseStream model ValidationException (client, httpError 400); AWS returns 400 ValidationException whose message is the fixed sentence 'Invocation of model ID <modelId> with on-demand throughput isn\u2019t supported. Retry your request with the ID or ARN of an inference profile that contains this model.' — the fixed text is that whole sentence pair (note the curly apostrophe U+2019 in 'isn\u2019t'), and the single variable part is the model id taken verbatim from the request's modelId label (e.g. amazon.nova-micro-v1:0). Which ids are profile-only is recorded behavior only (the recordings show amazon.nova-micro-v1:0 refused this way while amazon.nova-lite-v1:0 is invocable by its bare id). On the streaming operation the refusal must be delivered as plain JSON, never as an event stream: :status 400, content-type application/json, header x-amzn-errortype starting 'ValidationException', body {"message": "<that sentence>"}.
Emulator: Converse against the profile-only model id succeeds — HTTP 200 with a normal completion — so no ValidationException of any kind is produced and the inference-profile routing rule does not exist. (The emulator's model catalogue treats every syntactically valid foundation-model id as on-demand invocable.)
Why: the emulator is overly permissive on a rule clients depend on: an application that mistakenly addresses a profile-only model by its bare id passes against the emulator and fails in production with a 400 it never exercised, and the inference-profile routing code path (resolve profile ARN -> member model) is never validated. The sibling negative-path check also cannot verify that a streaming refusal is framed as JSON rather than an event stream, because there is no refusal.
Fix: model-id resolution/validation in the Converse, ConverseStream, InvokeModel and InvokeModelWithResponseStream handlers (the stage that resolves modelId against the emulator's model catalogue) — it must mark profile-only models and refuse a bare-id invocation with 400 ValidationException carrying the sentence above, and the ConverseStream error serializer must emit that refusal as application/json with x-amzn-errortype, not as an event stream.
Traces: bedrock-runtime.converse-stream-hand-signed-http2-model-needing-inference-profile-rejected-as-plain-json.

Scope vs already-open issues: 20261028T194707Z-bedrock-runtime-generation-stage-serves-a-constant-emulator.md owns bedrock-runtime.bedrock-runtime-bare-model-id-needing-inference-profile-rejected, but only for its generated-content positive control (that check never reaches the routing assertion); it says nothing about profile-only model ids being accepted, and nothing about transport/ALPN. No open issue mentions HTTP/2 or ALPN.
