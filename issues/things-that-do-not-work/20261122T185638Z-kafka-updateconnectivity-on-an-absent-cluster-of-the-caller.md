=== Cause 1 of 1 - UpdateConnectivity, called with a well-formed MSK cluster ARN of the CALLER'S OWN account that this endpoint holds no cluster for, is answered with the modeled not-found refusal (404 NotFoundException) where MSK answers the authorization refusal (403 AccessDeniedException, "...because no resource-based policy allows the kafka:UpdateConnectivity action"). Fixture kafka-cluster-mutations-notfound-2, step task#2.

AWS: Smithy kafka#UpdateConnectivity (services/service-com-amazonaws-kafka-kafka/smithy-model/com-amazonaws-kafka-kafka.json): PUT /v1/clusters/{ClusterArn}/connectivity, ClusterArn @required @httpLabel, CurrentVersion @required (jsonName currentVersion), ConnectivityInfo/ZookeeperAccess optional; HTTP 200 -> UpdateConnectivityResponse{clusterArn, clusterOperationArn}. Modeled errors: BadRequestException 400, ForbiddenException 403, NotFoundException 404, UnauthorizedException 401, InternalServerErrorException 500, ServiceUnavailableException 503. The model declares BOTH a 404 and a 403 channel and states nothing about which one an absent-but-well-formed cluster ARN draws, so WHICH refusal this case takes is recorded behavior only. The recording is HTTP 403 with header x-amzn-errortype: AccessDeniedException and a message in AWS's standard IAM no-resource-policy sentence: the fixed text is "User: " <calling principal ARN> " is not authorized to perform: " <action> " on resource: " <resource ARN> " because no resource-based policy allows the " <action> " action"; its variable parts are taken from the request and the emulator's own identity - the calling principal (recorded as arn:aws:iam::000000000000:user/emulator), the action kafka:UpdateConnectivity (derived from the operation name), and the cluster ARN exactly as submitted (recorded as arn:aws:kafka:us-west-2:000000000000:cluster/sim2real-probe-kafka-missing-connectivity-90c735fd/aaaaaaaa-bbbb-cccc-dddd-aaaabbbbcccc-1 - a per-run probe name and uuid, not part of the requirement). The RULE the recording states is: kafka:UpdateConnectivity is an action scoped to a CLUSTER resource, so it can be granted only by a document attached to that cluster or by one of the caller's own that names it; a cluster the service holds no record of is granted by nothing, and MSK therefore refuses the mutation as unauthorized and discloses nothing about what the registry holds - even for an ARN inside the caller's own account.

Emulator: HTTP 404 with header x-amzn-errortype: NotFoundException and body message "The requested resource doesn\u2019t exist." (crate::state::RESOURCE_NOT_FOUND_MESSAGE) plus invalidParameter "ClusterArn". Three asserted facets diverge at once: status 403 -> 404, x-amzn-errortype AccessDeniedException -> NotFoundException, and the message text (AWS's IAM no-resource-policy sentence -> the service's fixed not-found sentence). The wording itself is not the problem - this crate already emits exactly AWS's sentence through crate::state::authorization::no_resource_policy_for_cluster / ::service_common::iam_authorization::not_authorized_by_resource_policy, and does so for other operations in the same corpus - the defect is WHICH gate this operation takes, so the refusal never reaches that sentence.

Why: the status class and the error code are what an SDK or an infrastructure tool branches on. A caller reconciling multi-VPC connectivity - reading a cluster list, then issuing UpdateConnectivity against an ARN that has since been deleted or that belongs to a region/account it may not touch - is told "this cluster is absent" (404 NotFoundException, which Terraform-style and SDK retry logic treats as a benign drift signal: drop the resource from state, stop reconciling) where AWS tells it "you are not authorized" (403 AccessDeniedException, which the same logic treats as a permissions problem to surface and escalate). The two drive opposite remediation, so a reconciler silently prunes a cluster it in fact had no permission to touch. The emulator also DISCLOSES registry contents by negative inference: because a present cluster answers 200 and an absent one answers 404, a caller can enumerate which cluster ARNs exist, which is precisely what AWS's single "you may not" answer for an unauthorized mutation withholds.

Fix: the authorization gate selected by the operation's handler. services/service-com-amazonaws-kafka-kafka/src/ops/update_connectivity.rs takes crate::state::authorization::authorize_caller_operation (lines 179-184), which decides only the caller's identity policies and the ARN's account segment and then lets the registry miss at lines 241-251 produce the modeled NotFoundException. This crate already holds the correct gate for a cluster MUTATION - crate::state::authorization::authorize_registered_cluster (services/service-com-amazonaws-kafka-kafka/src/state/authorization.rs), which asks the registry whether this endpoint holds a cluster under the submitted ARN and, when it does not, answers no_resource_policy_for_cluster (403 AccessDeniedException in AWS's no-resource-policy sentence). UpdateConnectivity must take that gate: an absent cluster is refused as unauthorized before the handler resolves anything, and the 404 NotFoundException branch is reached only where the model genuinely needs it. The sentence's variable parts must stay derived from the request and the emulator's identity (calling principal, kafka:<OperationName>, the ARN as submitted), never from a recorded literal.
