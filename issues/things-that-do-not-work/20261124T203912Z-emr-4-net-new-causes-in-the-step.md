# emr: 4 net-new causes in the step runner — Hadoop/MapReduce commands (s3-dist-cp, hadoop-mapreduce-examples) are never executed, step Args are shell-joined into one argument, a bash step's hadoop/aws CLI probes all fail and upload nothing, and the PySpark DataFrame shim has no inputFiles()

> _Note: this issue was identified against the code base at commit `83417ec3dff2f3efed8690d96b9cf1f73f5857f5`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
AddJobFlowSteps

## Description
Four distinct root causes in the EMR step execution path, all reached through AddJobFlowSteps/RunJobFlow Steps and observed through DescribeStep plus the step's S3 side effects. Related open issues that do NOT cover these checks (the replay report marked none of them ALREADY FILED or OWNED): 20261121T155504Z-emr-the-hadoop-hdfs-cli-is-absent-from.md (hadoop/hdfs CLI absent for other check ids), 20261119T185618Z-emr-5-net-new-root-causes-outside-the.md (no Hadoop/Spark binaries or EMRFS config on cluster nodes), 20261108T104909Z-emr-glue-s3-2-net-new-causes-cluster.md and 20261117T115411Z-emr-glue-s3-a-runjobflow-step-that-writes.md (steps ending FAILED without running an application for the emr__glue__s3 checks). They should be closed together with this one; these are the same family of defect still present for these four causes.

Cause 1 of 4: a command-runner.jar step whose command is a Hadoop/MapReduce tool is not executed at all, and the step is settled FAILED with an emulator-authored explanation. Failing checks: emr.deploy-emr-cluster-cfn-then-step-executes, emr.s3-dist-cp-group-by-aggregates-through-a-real-mapreduce-job.
AWS: Smithy com.amazonaws.emr#HadoopJarStepConfig carries Jar (required), MainClass, Args (XmlStringList) and Properties; com.amazonaws.emr#StepState enumerates PENDING, CANCEL_PENDING, RUNNING, COMPLETED, CANCELLED, FAILED, INTERRUPTED; com.amazonaws.emr#StepStatus carries StateChangeReason (StepStateChangeReason{Code,Message}) and FailureDetails (FailureDetails{Reason,Message,LogFile}), documented as "the details for the step failure including reason, message and log file path where the root cause was identified" — i.e. FailureDetails is a report OF a real failure observed in the step's own log, never a statement about the backend. On AWS the Jar `command-runner.jar` runs the first Arg as a command on the cluster with the remaining Args as its arguments (https://docs.aws.amazon.com/emr/latest/ReleaseGuide/emr-commandrunner.html); `s3-dist-cp --src/--dest/--groupBy/--targetSize` runs a real MapReduce job that aggregates every object matching the --groupBy capture group into one output object per group, leaves non-matching objects uncopied and leaves the sources in place, returning a non-zero exit code only if it cannot copy (https://docs.aws.amazon.com/emr/latest/ReleaseGuide/UsingEMR_s3distcp.html); a `hadoop-mapreduce-examples pi` command likewise runs and exits 0. The requirement is: the command runs, the step's own side effects on S3 happen, and DescribeStep reports Status.State COMPLETED with no FailureDetails. Per-run values (cluster id, step id, bucket name, nonce, timestamps) are not requirements.
Emulator: both steps reach FAILED. StateChangeReason.Message is the fixed emulator-authored sentence "This emulator runs the step lifecycle but executes no Hadoop jar, so the step ended without running its application.", FailureDetails.Reason repeats that same sentence and FailureDetails.Message is "No application was started for this step: this emulator holds the cluster's step state and runs no Hadoop, Spark or MapReduce runtime, so the step's own side effects did not happen." (FailureDetails.LogFile points at a steps/<step-id>/stderr.gz that is a per-run path). None of that text is AWS's: AWS has no such reason class, and the whole sentence is fixed emulator prose with no variable part taken from the request or from any log. No MapReduce job runs, so nothing is written under the --dest prefix.
Why: a client that submits a `s3-dist-cp` or `hadoop jar`-family step and polls DescribeStep sees a hard FAILED for a request AWS completes, and never gets the step's data-plane effect (the aggregated object under --dest). Retry logic keyed on step state gives up, and any error-string matching sees a sentence that cannot appear on AWS, so the failure is both wrong and undiagnosable.
Fix: the EMR step executor behind AddJobFlowSteps/RunJobFlow Steps in the emr service crate (the command-runner.jar command dispatch and the step state machine DescribeStep reads), which must run Hadoop/MapReduce commands — including s3-dist-cp with --groupBy aggregation semantics — and must only populate StateChangeReason/FailureDetails from an actual step failure, never with emulator self-description.
Traces: emr.deploy-emr-cluster-cfn-then-step-executes, emr.s3-dist-cp-group-by-aggregates-through-a-real-mapreduce-job.

Cause 2 of 4: the step's Args list is flattened into a single shell-joined argument before the program is started, so the program on the cluster observes one argv element instead of the submitted vector. Failing check: emr.emr-step-args-are-passed-verbatim-to-the-application.
AWS: Smithy com.amazonaws.emr#HadoopJarStepConfig$Args is a list of XmlString — "a list of command line arguments passed to the JAR file's main function when executed" — and HadoopStepConfig$Args echoes the same list on DescribeStep. Recorded behavior: the program the step starts receives each submitted Arg as its own byte-identical argv element, in order, with spaces, single and double quotes, `;`, `&`, glob metacharacters, `$`, multi-byte UTF-8 and a trailing space all preserved, and with exactly one exception — a zero-length argument is dropped by command-runner (while DescribeStep's Config.Args still records it). No shell re-splitting, re-quoting, glob expansion or variable expansion occurs.
Emulator: the program receives ONE argument containing every submitted argument concatenated with single spaces: `[b'plain two words has"double"quote has\'single\'quote semi;colon&amp star*glob? $NOT_EXPANDED \xc3\xbcn\xc3\xafcod\xc3\xa9-\xce\xbb-\xc3\xa9 trailing space ']` where nine separate elements were expected. Argument boundaries are destroyed, so any argument containing a space is silently re-split by the receiving program and the zero-length-argument contract cannot even be probed.
Why: every step whose arguments contain spaces, quotes or shell metacharacters is delivered wrong — a `--groupBy` regex, an S3 URI with a space, or a Spark `--conf k=v with spaces` reaches the application mangled, so jobs fail or, worse, silently process the wrong input. A client cannot pass any argument that is not a bare token.
Fix: the step launcher in the emr service crate's step executor — it must exec the command with the Args list as an argv vector rather than joining the Args into one string (or handing a joined string to a shell), preserving each element's bytes and dropping only the zero-length element.
Traces: emr.emr-step-args-are-passed-verbatim-to-the-application.

Cause 3 of 4: a `command-runner.jar` / `bash -c` step that probes EMRFS and the S3 API exits non-zero and leaves no object at all behind — not even the transcript it uploads with `aws s3 cp` — so neither the EMRFS write nor its SSE-KMS encryption is observable. Failing check: emr.security-configuration-sse-kms-applies-to-emrfs-writes.
AWS: command-runner.jar runs `bash -c <script>` on the cluster with the EC2 instance profile's credentials and the cluster's EMRFS configuration in place; on an emr-6.15.0 cluster `hadoop fs -ls/-mkdir -p/-put s3://<bucket>/...` goes through EMRFS and `aws s3 cp` goes through the plain S3 API, both succeed for a bucket the instance role may write, the step exits 0, and DescribeStep reports COMPLETED (Smithy com.amazonaws.emr#StepState). With a security configuration selecting SSE-KMS for S3 encryption, the object EMRFS wrote reports that encryption on HeadObject. The requirement is: the shell runs, the `hadoop` and `aws` CLIs exist on the node and authenticate as the instance profile, both objects and the uploaded transcript exist in S3 afterwards, and the step is COMPLETED.
Emulator: the step settles FAILED with StateChangeReason.Message "The command the step submitted exited with a non-zero status." — fixed emulator prose, not AWS wording and not drawn from any log — and GetObject on the transcript key the script uploads with `aws s3 cp ... || true` answers NoSuchKey ("The specified key does not exist."), so not one of the script's five S3/EMRFS probes produced an object. The step environment therefore provides neither a working `hadoop` CLI against s3:// nor a working `aws` CLI, and the step's S3 side effects do not happen.
Why: a client that uses a shell step to move data through EMRFS gets a bare non-zero FAILED with no diagnosable reason and no data written; the security configuration's SSE-KMS setting can never be shown to apply to an EMRFS write, so a client cannot verify that its at-rest encryption requirement is actually enforced.
Fix: the step execution environment in the emr service crate's step executor — the cluster node image/command environment must provide the `hadoop` CLI wired to EMRFS and the AWS CLI bound to the cluster's instance-profile credentials, the step's writes must land in S3, and the step's StateChangeReason/FailureDetails must carry the real command failure rather than the fixed sentence above. The EMRFS path must also apply the security configuration's SSE-KMS setting to objects it writes.
Traces: emr.security-configuration-sse-kms-applies-to-emrfs-writes.

Cause 4 of 4: the PySpark runtime served to a `spark-submit` step is a shim whose DataFrame type is missing `inputFiles()`, so a partitioned-read job that completed its write leg dies with an AttributeError. Failing check: emr.spark-partitioned-input-pruned-then-written-back-partitioned.
AWS: an EMR step `command-runner.jar` with Args ["spark-submit", "--deploy-mode", "client", s3://.../job.py, ...] runs real PySpark on the cluster (https://docs.aws.amazon.com/emr/latest/ReleaseGuide/emr-spark-submit-step.html). `pyspark.sql.DataFrame.inputFiles()` is part of the PySpark DataFrame API and returns the list of files composing the DataFrame; reading a Hive-partitioned Parquet dataset written with partitionBy recovers the partition column from the path while the leaf data files do not contain it. The requirement is that a job using the public PySpark DataFrame API runs to completion and the read step reports COMPLETED.
Emulator: the read step settles FAILED with StateChangeReason.Message "The application the step submitted exited with a non-zero status." and FailureDetails.Message "AttributeError: 'DataFrame' object has no attribute 'inputFiles'" — the Spark object served to the job does not implement the DataFrame API it advertises.
Why: any PySpark job that uses a DataFrame method the shim omits fails with an AttributeError that could never occur on EMR, so a client cannot tell a defect in its own job from a hole in the runtime, and partition-layout behavior (partition column recovered from the path, absent from leaf files) is unverifiable.
Fix: the PySpark/Spark runtime the emr step executor exposes to spark-submit steps — the DataFrame implementation must cover the public API, starting with inputFiles(), rather than raising AttributeError for methods real PySpark provides.
Traces: emr.spark-partitioned-input-pruned-then-written-back-partitioned.
