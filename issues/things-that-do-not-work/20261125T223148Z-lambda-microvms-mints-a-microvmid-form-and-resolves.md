# lambda-microvms mints a microvmId form and resolves an unpinned baseImageVersion AWS does not serve

> _Note: this issue was identified against the code base at commit `8beda664eef2534686c4de16bb7887f35213d53c`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

RunMicrovm

## Description
This issue bundles 2 distinct root causes in the lambda-microvms emulator, both observed on replay of wire corpus simparity-wire-aws-v1 against the emulator built from this checkout (emulator_up true, "/__admin/health answered 200 and the :46293 data listener accepts"; 13 fixtures replayed, 104 steps, 96 passed, 8 mismatched, 0 errored, 0 blocked, score 92.3%, 8 divergence clusters, bootstrap_signal false). Both causes are of one defect class: a response member whose value the SERVICE supplies — the identity it MINTS for a MicroVM, and the base-image pedigree it RESOLVES for a build that pinned none — is answered in a form this emulator chose for itself or from a per-service constant, rather than in the form AWS mints / from the resolution AWS performs. A fixer must close BOTH (Cause 1 of 2 and Cause 2 of 2) before submitting; each cause names the fixture steps it must be re-replayed on, and every cluster claimed below is reported by the replay with an EMPTY stub_path and an EMPTY owned_by.

=== Cause 1 of 2: the minted microvmId does not satisfy the recorded shape of a MicroVM identifier (it is now 'mvm-' + a hyphenated UUID) ===
Fixture lambda-microvms-run-suspend-resume-terminate-microvm, step task#7 (RunMicrovm, HTTP 200 on both sides; affected_count 1, so this is the only step whose minted id the corpus shape-asserts).

AWS: Smithy RunMicrovm is POST /2025-09-09/microvms -> 200; RunMicrovmResponse$microvmId is @required, targets MicrovmIdentifier (string, @length 1..256, "The ARN or ID of the MicroVm"), documented "The unique identifier of the MicroVM". The model fixes no concrete FORM and the corpus records this member as a shaped, non-asserted value ('<shaped-not-asserted>'), so this is recorded behavior only: the recorded id's text is a per-run value and must NOT be copied, but the FORM the recording fixes for a minted MicroVM id IS the requirement, and the replay's shape check is what the emulator's value fails. Hypothesis (neither model nor recording states it): AWS mints the suffix as a fixed-length, unhyphenated lowercase hex/alphanumeric token under the 'mvm-' prefix (the form other Lambda-minted resource ids take), which is why neither a 16-digit zero-padded counter nor a 36-character hyphenated UUID satisfies it.

Emulator: the step answers 200 and the replay reports `$.microvmId: value_mismatch (expected '<shaped-not-asserted>', got 'mvm-c9cad34d-1a7b-47cd-acea-dbe3cab1687d')` — i.e. the 'mvm-' prefix followed by a lowercase hyphenated 8-4-4-4-12 version-4 UUID (40 characters in all). The value is minted in the service state: next_microvm_id (src/state.rs:2660-2671) calls mint_prefixed_id(MICROVM_ID_PREFIX) (src/state.rs:1981-1983, prefix at src/state.rs:1960), which formats the prefix followed by mint_microvm_image_id (src/state.rs:1913-1917, service_common::uuid_from_random_bytes). The handler and every later read are faithful (GetMicrovm echoes the stored id and those steps pass), so the defect is in the MINTING, not in a projection. Note the history on this member: the resolved issue 20261117T040517Z-lambda-microvms-answers-microvm-and-image-version-reads.md reported the earlier form 'mvm-0000000000000000' (a zero-padded hex counter) against the same step; the counter was replaced by a hyphenated UUID, which is opaque and unique but still fails the same shape assertion — so the remaining work is the identifier's FORM (byte length and character class), not its uniqueness.

Why: microvmId is the only handle a client has on a MicroVM — it is the {microvmIdentifier} path label for GetMicrovm/Suspend/Resume/Terminate and the auth-token calls, the correlation key between a ListMicrovms row and a read-back, and the value a pipeline persists. A client that validates the identifier's form before re-sending it in a URI path, that keys a store with a fixed-width column or a form regex on it, or that parses the suffix gets a value AWS never mints, so that branch of the client is unreachable in emulation while it works live.

Fix: the MicroVM id allocation in the service state — next_microvm_id, through mint_prefixed_id/MICROVM_ID_PREFIX — must mint the identifier form the recording shows, keeping the id DRAWN (not counted) and keeping ListMicrovms' ordering on the record's own created_seq. Do not special-case the RunMicrovm projection: the same minted value is the path label and the listing/read value, and rewriting it in one handler would make the paths disagree.

Traces: lambda-microvms-run-suspend-resume-terminate-microvm#task#7 (RunMicrovm, 200 vs 200).

=== Cause 2 of 2: an unpinned baseImageVersion resolves to the label this emulator's catalogue assigns its NEWEST generation, so every projection of the image version reports the wrong base-image pedigree ===
Fixture lambdamicrovms-image-version-status-and-update, steps setup#2 (CreateMicrovmImage, 201/201), task#4 (UpdateMicrovmImageVersion, 200/200), task#5 (UpdateMicrovmImage, 200/200), task#6 (GetMicrovmImageVersion, 200/200) and task#7 (ListMicrovmImageVersions, 200/200). ONE root cause, five diverging steps: the value is resolved once when a version is minted, stored on the version record, and echoed by every later read — all five must pass before this cause is closed.

AWS: Smithy CreateMicrovmImage (POST /2025-09-09/microvm-images -> 201), UpdateMicrovmImage (PUT /2025-09-09/microvm-images/{imageIdentifier} -> 200), UpdateMicrovmImageVersion (PATCH .../versions/{imageVersion} -> 200), GetMicrovmImageVersion (GET .../versions/{imageVersion} -> 200) and ListMicrovmImageVersions (GET .../versions -> 200, @paginated) all carry baseImageVersion: optional, target Version, @length 1..2048, pattern ^[^\s]+$, documented "The specific version of the base MicroVM image to use" / "The specific version of the base MicroVM image" — the base-image release the image version was actually built from: the one the request pinned, or, for a request that pinned none, the one the service RESOLVES for the named baseImageArn. The model fixes no label, so the value is recorded behavior only: against the AWS-managed base image arn:aws:lambda:us-west-2:aws:microvm-image:al2023-1 with NO baseImageVersion in the request, every projection of this image in the recording reports baseImageVersion '1.0' — the create 201, the status update, the configuration update that mints the image's own version '2.0', the single-version read and both listing rows agree on one pedigree, and that pedigree is INDEPENDENT of the image's own imageVersion ('1.0' then '2.0'). The requirement is that the member report the release resolved from the base image the request named, identically on every path; the literal '1.0' is this recording's resolved value and not itself the contract.

Emulator: all five steps answer the recorded status and report baseImageVersion '2.0' — replay reports `$.baseImageVersion: value_mismatch (expected '1.0', got '2.0')` on setup#2, task#4, task#5 and task#6, and on task#7 the listing rows differ in exactly that member (the rows' other members match; createdAt/updatedAt are per-run instants and are not claimed here). The handlers and projections are faithful: ops/create_microvm_image.rs:388-390 and ops/update_microvm_image.rs:374-378 store `input.base_image_version.unwrap_or_else(|| store.resolve_base_image_version(...))` and output_of copies the stored field (ops/create_microvm_image.rs:564), so the wrong value enters at the RESOLUTION. resolve_base_image_version (src/state/regions.rs:254-267) returns, for a managed reference, latest_managed_base_image_version_label (src/state.rs:721-724) — the label the emulator's own catalogue table assigns the newest generation — and MANAGED_BASE_IMAGE_VERSIONS (src/state.rs:622-628) publishes generation "1" shipping release "2.0" and generation "0" shipping "1.0". Hence every unpinned create or configuration update on any managed base image is recorded with pedigree '2.0'. That the request pinned nothing is established by the code path: a pinned value is echoed verbatim, so the only way '2.0' can be served is the resolution. Hypothesis: the catalogue's generation-to-release mapping is inverted or off by one generation relative to what AWS publishes for al2023-1, so the unpinned resolution lands on the wrong release.

IMPORTANT for the fixer, so this is not "fixed" by moving a constant again: a per-service CONSTANT cannot satisfy the corpus. The resolved issue 20261117T040517Z-lambda-microvms-answers-microvm-and-image-version-reads.md reported the mirror image of this divergence (expected '2.0', got '1.0') on fixture lambdamicrovms-customer-image-lifecycle#setup#2 and #task#6, and it was closed by relabelling MANAGED_BASE_IMAGE_VERSIONS so the newest generation ships '2.0' — which made that fixture pass and made THIS fixture diverge the other way. The fix must make the resolution depend on what the request actually names (the base image, and the base-image generation a client pins after discovering it through ListManagedMicrovmImageVersions, which publishes bare generation counters) so that BOTH fixtures are satisfied at once; re-replay lambdamicrovms-customer-image-lifecycle#setup#2 and #task#6 alongside the five steps named here and confirm neither regresses.

Why: baseImageVersion is how a client pins and audits the base layer of an image it built. A reproducible-build gate, a CVE re-base sweep or a promotion check reads this member from the create response (the only place a client sees the configuration the service accepted), from the single-version read, or in bulk from the version listing, and is told every version was built on a release it was not — so it never learns a re-base is due, and because the emulator's value happens to equal the image's own version for the updated version it also cannot be told apart from "the image's own version was echoed".

Fix: the base-image version RESOLUTION in the service state — resolve_base_image_version (src/state/regions.rs:254-267) together with the catalogue releases it resolves from (MANAGED_BASE_IMAGE_VERSIONS, src/state.rs:622-628) — must resolve an unpinned reference to the release the NAMED base image publishes, and the version record must keep storing that one resolved value so the create, the two update paths, the single-version read and the listing row cannot disagree. Do NOT patch the five projections: they are faithful echoes, and rewriting any of them would split one pedigree into several.
