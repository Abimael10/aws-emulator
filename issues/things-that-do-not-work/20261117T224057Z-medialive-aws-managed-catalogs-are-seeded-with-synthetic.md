# medialive AWS-managed catalogs are seeded with synthetic placeholder entries instead of the AWS catalog (alarm template groups, alarm templates, reserved offerings)

> _Note: this issue was identified against the code base at commit `4d7305aa65b31c2ba867b543a285e7860fe3b54c`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
ListCloudWatchAlarmTemplateGroups

## Description
3 causes, all one root fault: the three read-only, AWS-managed MediaLive catalogs are not populated from the real AWS catalog. The emulator answers 200 with a list of machine-generated placeholder rows whose identifiers follow a dense synthetic counter (aws-1000001.., aws-2000001.., 10000000..) and whose content does not correspond to any AWS-published catalog entry, so none of the AWS-managed entries a client looks up by id/arn or by name is present.

Cause 1 of 3 - ListCloudWatchAlarmTemplateGroups omits the AWS-managed alarm template groups (fixture medialive-catalog-list-cloud-watch-alarm-template-groups, step task#1).
AWS: Smithy: ListCloudWatchAlarmTemplateGroups GET /prod/cloudwatch-alarm-template-groups -> 200, output member CloudWatchAlarmTemplateGroups (jsonName cloudWatchAlarmTemplateGroups, list of CloudWatchAlarmTemplateGroupSummary); the operation is paginated and takes scope=. The model does not enumerate the catalog contents, so for the entry set this is recorded behavior only: on a fresh account the recording shows the AWS-managed (scope AWS) groups, each with an arn of the form arn:aws:medialive:<region>::cloudwatch-alarm-template-group:<id>, the matching id, a stable AWS-published name (the AWS-<Workflow>Workflows family), a templateCount equal to the number of AWS-managed templates whose groupId is that group, a createdAt and tags {}. The id values are fixed AWS catalog ids, not a per-emulator counter.
Emulator: answers 200 but every AWS-managed group of the recorded catalog is absent from cloudWatchAlarmTemplateGroups (reported as 'missing ... got None' for each arn); what it returns instead are rows carrying densely numbered synthetic ids/arns (aws-1000001 ... aws-1000010) that no recorded AWS group uses, and where a recorded name does line up the templateCount disagrees with the number of templates actually in that group.
Why: a client that resolves an AWS-managed alarm template group by id or arn (to create a signal map, to attach the AWS-recommended alarms, or to walk group -> templates) gets a 404/empty result against the emulator for ids that exist on AWS, and any count-based or name-to-id mapping it has is wrong, so AWS-recommended monitoring cannot be wired up at all.
Fix: the medialive alarm-template-group state/seed for the AWS-scope catalog - the component that populates the AWS-managed groups at service start - plus the ListCloudWatchAlarmTemplateGroups handler that projects them.
Traces: medialive-catalog-list-cloud-watch-alarm-template-groups#task#1.

Cause 2 of 3 - ListCloudWatchAlarmTemplates omits the AWS-managed alarm templates (fixture medialive-catalog-list-cloud-watch-alarm-templates, step task#1).
AWS: Smithy: ListCloudWatchAlarmTemplates GET /prod/cloudwatch-alarm-templates -> 200, output member CloudWatchAlarmTemplates (jsonName cloudWatchAlarmTemplates, list of CloudWatchAlarmTemplateSummary), paginated, filterable by groupIdentifier= and scope=. The catalog contents are recorded behavior only: the recording shows the AWS-managed templates, each with arn arn:aws:medialive:<region>::cloudwatch-alarm-template:<id>, the matching id, the groupId of its AWS-managed group, an AWS-published name of the form AWS-<MetricCondition>-<GroupWorkflow>, and the full alarm definition members (targetResourceType, comparisonOperator, evaluationPeriods, metricName, period, statistic, treatMissingData, threshold, datapointsToAlarm, description, createdAt, tags {}).
Emulator: answers 200 but none of the recorded AWS-managed templates is present (each arn reported 'missing ... got None'); the returned rows carry synthetic ids aws-2000001.. with no relation to the AWS catalog ids and no AWS alarm definition behind them.
Why: the AWS-recommended CloudWatch alarm definitions are the whole point of this catalog - a client cannot read the metric/threshold/comparison an AWS template prescribes, cannot select templates by groupIdentifier, and cannot create a signal map from AWS-managed templates, because every id it would reference does not exist.
Fix: the medialive alarm-template state/seed for the AWS-scope catalog (same seeding component as cause 1, template level) and the ListCloudWatchAlarmTemplates handler.
Traces: medialive-catalog-list-cloud-watch-alarm-templates#task#1.

Cause 3 of 3 - ListOfferings omits the AWS reserved-capacity offering catalog (fixture medialive-catalog-list-offerings, step task#1).
AWS: Smithy: ListOfferings GET /prod/offerings -> 200, output member Offerings (jsonName offerings, list of Offering), paginated, filterable by resourceType=, codec=, resolution=, maximumBitrate=, channelClass=, duration=, specialFeature=, videoQuality=, channelConfiguration=. The catalog contents are recorded behavior only: the recording shows region-specific reserved offerings, each with arn arn:aws:medialive:<region>::offering:<offeringId>, the matching offeringId, a human-readable offeringDescription naming the reserved resource and region, a resourceSpecification (resourceType plus the dimensions that apply to it: codec, resolution, maximumBitrate, channelClass), region, offeringType, duration with durationUnits, and a usagePrice/fixedPrice in currencyCode.
Emulator: answers 200 but no recorded offering is present (each arn reported 'missing ... got None'); the rows it returns are a synthetic sequence (offeringId 10000000, 10000001, ... ) with ids no AWS offering uses.
Why: a client that prices or purchases reserved capacity reads ListOfferings and then calls PurchaseOffering with an offeringId; against the emulator every real offeringId is unknown and the prices/specifications it does return are invented, so reservation flows and any cost estimation built on them diverge silently.
Fix: the medialive offering catalog state/seed (the component that populates the reserved-offering catalog per region) and the ListOfferings handler's filtering/projection over it.
Traces: medialive-catalog-list-offerings#task#1.

Not covered by an existing issue: open issue 20261110T165405Z-medialive-reads-omit-committed-state-account-kmskeyid-and.md owns the lifecycle read where a just-created alarm template group is missing from ListCloudWatchAlarmTemplateGroups (and the alarm-group id mismatches seen alongside it); this issue is about the AWS-managed catalog never being seeded with the AWS entries at all, on the catalog fixtures, which that issue does not carry.
