# cloudwatch__ec2__ecs: 2 net-new causes — an EC2-launch-type task running `sleep 3600` stops immediately as EssentialContainerExited, and the managed-scaling targetCapacity scenario reaches no verdict

> _Note: this issue was identified against the code base at commit `2f24e314505ec85ef2a85cab010fe998301170cd`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
RunTask

## Description
Two independent defects on the ECS-on-EC2 capacity-provider path, each grounded in a failing behavioral check of this run. Both must be closed before this issue is submitted.

Cause 1 of 2: a task placed on a registered container instance is stopped immediately with stopCode EssentialContainerExited although its essential container's command is a long-running `sleep`.
AWS: recorded behavior only (the Smithy model states no runtime semantics). A task definition registered with requiresCompatibilities=['EC2'], networkMode='bridge', cpu/memory 256/256 and one essential container (image public.ecr.aws/docker/library/busybox:1.36, command ['sh','-c','sleep 3600']) that is run on an ACTIVE container instance of the cluster reaches DescribeTasks lastStatus 'RUNNING' and STAYS there for the hour the command sleeps: the container process does not exit, so ECS has no reason to stop the task. containerInstanceArn is the instance the task was placed on, and while it runs, AWS/ECS CPUReservation and MemoryReservation for the cluster equal the task's share of the instance's registeredResources, and AWS/ECS/ManagedScaling CapacityProviderReservation reads exactly 100.
Emulator: the task settles STOPPED almost at once with stopCode 'EssentialContainerExited' and stoppedReason 'Essential container in task exited' — the container's command is treated as having run to completion (or never run) rather than as a process that stays alive. Because the task never holds RUNNING, none of the downstream reservation metrics can be observed and the check fails at its first task assertion.
Why: the emulator cannot host any long-running workload on ECS-on-EC2: every consumer that waits for a task to be RUNNING (service schedulers, reservation metrics, capacity-provider scaling, in-container probes) is told the workload died with an exit of its essential container, which is also the stopCode a client uses to diagnose a crashed image. Correct configurations are indistinguishable from a crash-looping one.
Fix: the task-lifecycle/container-runtime state in the ecs service crate — an essential container whose command does not terminate must keep the task in RUNNING (and must not synthesize an EssentialContainerExited stop), on the EC2/bridge launch path as well as Fargate. Open issues 20261118T145001Z-ecs-2-net-new-causes-a-long-running.md and 20261118T145001Z-ecs-logs-fargate-containers-never-execute-tasks-go.md record the same symptom for Fargate tasks and do not carry this check's replay key; this one is an EC2-launch-type task on a capacity-provider-launched container instance.
Traces: cloudwatch__ec2__ecs.obs-ecs-3-reservation-metrics-match-registered-resources-and-pressure-exceeds-100.

Cause 2 of 2: the managed-scaling targetCapacity refusal scenario never reaches an observable step and is cut off at the 60 s harness cap, so neither the refusal nor the hold of the prior target is verdicted.
AWS: Smithy (ecs UpdateCapacityProvider) models ClientException (client, httpError 400) among its errors; recorded behavior for this scenario is: (a) CreateCapacityProvider with managedScaling {status ENABLED, targetCapacity 100} plus association to a cluster makes ECS create exactly one TargetTrackingScaling policy on the provider's ASG whose CustomizedMetricSpecification is AWS/ECS/ManagedScaling CapacityProviderReservation with dimensions {CapacityProviderName, ClusterName} and TargetValue 100, and an AlarmHigh (ComparisonOperator GreaterThanThreshold) on that metric with Threshold 100; (b) UpdateCapacityProvider targetCapacity=80 propagates to both the policy TargetValue and the AlarmHigh Threshold, and the provider settles updateStatus UPDATE_COMPLETE; (c) targetCapacity=101 is refused with ClientException and the fixed message 'The managed scaling target capacity value is invalid. Specify an integer greater than 0 and less than or equal to 100 and try again.', leaving the provider at 80 and the policy/alarm untouched.
Emulator: the scenario makes no observable progress — the suite reports only 'Check timed out after 60.0s', so the first blocking step (reading one target-tracking policy with TargetValue 100 and its AlarmHigh at Threshold 100) never satisfied inside the budget and the refusal was never exercised. Hypothesis: the ECS-owned target-tracking policy and CapacityProviderReservation alarm are not created (or not kept in step with targetCapacity), which is what the check waits on; open issue 20261115T003554Z-cloudwatch-ec2-ecs-ecs-createcapacityprovider-with-managedscaling-enabled-never-creates-the.md records that wiring being absent and does not carry this check's replay key — this check additionally requires the targetCapacity=101 refusal and the hold of the prior target.
Why: a client cannot discover that an out-of-range managed-scaling target is rejected, nor that a rejected update leaves the provider and its scaling wiring unchanged; it instead hangs waiting for scaling wiring that never appears, and a bad value may be silently retained.
Fix: the ECS capacity-provider managed-scaling reconciler in the ecs service crate (creating and updating the ASG target-tracking policy and its CloudWatch alarm) plus UpdateCapacityProvider's targetCapacity range validation and its ClientException message.
Traces: cloudwatch__ec2__ecs.managed-scaling-target-capacity-above-100-rejected-and-tracking-alarm-unchanged.

## Steps to Reproduce
Cause 1: Create a cluster, a launch template from the ECS-optimized AMI and an ASG, create a capacity provider over that ASG with managedScaling ENABLED and associate it to the cluster. RegisterTaskDefinition(requiresCompatibilities=['EC2'], networkMode='bridge', cpu='256', memory='256', containerDefinitions=[{name:'app', image:'public.ecr.aws/docker/library/busybox:1.36', essential:true, cpu:256, memory:256, command:['sh','-c','sleep 3600']}]). RunTask it through the capacity provider, wait for a container instance to register ACTIVE, then DescribeTasks the task. AWS: lastStatus RUNNING, containerInstanceArn == the registered instance. Emulator: lastStatus STOPPED with stopCode EssentialContainerExited.

Cause 2: With the same cluster/ASG/capacity provider (managedScaling {status ENABLED, targetCapacity 100}) associated to the cluster, (a) DescribePolicies on the ASG and DescribeAlarms on the policy's alarms — AWS shows one TargetTrackingScaling policy at TargetValue 100 and an AlarmHigh at Threshold 100 on AWS/ECS/ManagedScaling CapacityProviderReservation; (b) UpdateCapacityProvider(targetCapacity=80) and re-read — both become 80; (c) UpdateCapacityProvider(targetCapacity=101) — AWS refuses 400 ClientException with the fixed range message and leaves the provider at 80 with updateStatus UPDATE_COMPLETE. On the emulator step (a) never becomes true, so the scenario is cut off before (c).
