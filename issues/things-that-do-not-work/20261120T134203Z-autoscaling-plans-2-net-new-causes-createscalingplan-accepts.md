# autoscaling-plans: 2 net-new causes — CreateScalingPlan accepts a negative MinCapacity, and GetScalingPlanResourceForecastData fabricates a diurnal forecast for a resource with no metric history

> _Note: this issue was identified against the code base at commit `2934be5e771e52682b61be50f4141d9a3e4ec915`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
CreateScalingPlan

## Description
Two net-new root causes in the autoscaling-plans crate, both grounded in failing behavioral checks. Both are in this one service, so they are bundled here; a fixer must close BOTH before submitting.

Cause 1 of 2: CreateScalingPlan accepts a ScalingInstruction whose MinCapacity is NEGATIVE instead of refusing it with ValidationException.
AWS: Smithy (model com-amazonaws-autoscalingplans-anyscalescalingplannerfrontendservice) — CreateScalingPlan.ScalingInstructions is @required, binds ValidationException (client, httpError 400), and ScalingInstruction$MinCapacity targets ResourceCapacity, an integer with no @range trait, documented only as "The minimum capacity of the resource." The model therefore states no numeric floor, so the floor is recorded behavior only: the recording shows a create whose single instruction carries MinCapacity below zero answered HTTP 400, Error.Code 'ValidationException', Error.Message "Minimum capacity cannot be less than 1" — the whole sentence is FIXED text, with no part interpolated from the request or from state (the literal 1 in it is AWS's own wording of the rule, not a value echoed back). Note the complementary recording already filed as 20261114T175837Z-autoscaling-plans-reopens-createscalingplan-refuses-mincapacity-0-with-validationexception-minimum.md: MinCapacity 0 IS accepted (HTTP 200, ScalingPlanVersion 1). So the rule AWS enforces is "a negative minimum is refused with that fixed sentence, a zero minimum is accepted", and a rejected create leaves NO plan behind (DescribeScalingPlans for that name answers an empty ScalingPlans list).
Emulator: the create is accepted — HTTP 200 with a ScalingPlanVersion — and the plan is minted and stored with the negative minimum. The fix for the issue cited above removed the MinCapacity bound entirely rather than correcting where it was drawn: services/service-com-amazonaws-autoscalingplans-anyscalescalingplannerfrontendservice/src/state.rs:1424-1430, in validate_scaling_instruction, now checks only the cross-member relation (max_capacity < min_capacity -> "Maximum capacity cannot be less than minimum capacity") and nothing about MinCapacity on its own, so no negative value is ever refused. The sibling reject in the same check (MaxCapacity 2 < MinCapacity 9) passes, which locates the defect precisely at the missing per-member floor, not at the existence of instruction validation.
Why: a client that mis-computes or mis-signs a capacity floor gets a 200 and a plan AWS would never have created, so the emulator's state and AWS's diverge permanently from that call on; validation-and-repair logic that relies on the modelled ValidationException to detect a bad capacity band never fires, and a negative floor flows on into the capacity band every derived target-tracking policy and every forecast is computed from. It also makes the service unusable as a negative-path fixture: the error class simply does not exist.
Fix: the shared scaling-instruction validation used by both write paths — validate_scaling_instruction in the service's state module — must refuse a negative MinCapacity with ValidationException and AWS's fixed sentence, while continuing to ACCEPT MinCapacity 0 (the previously-filed recording), and the rejected create must not record a plan. Nothing in the create handler or the serializer changes.
Traces: autoscaling-plans.asp-create-rejects-capacity-and-target-bounds (the check aborts at this reject, so its two later rejects — the target-value range sentence "For target tracking scaling, target value must be between '8.51592E-109' and '1.174271E108', but was '<value>'." and "Must provide at least 1 scaling instruction" — and its positive control were never exercised and are NOT claimed here; re-replay the check after the fix to reach them). Code sites: src/state.rs:1424-1430 (validate_scaling_instruction, the capacity block), reached from src/ops/create_scaling_plan.rs and src/ops/update_scaling_plan.rs via state.rs:1376-1399 (validate_scaling_instructions).

Cause 2 of 2: GetScalingPlanResourceForecastData returns a synthesized, non-empty Datapoints list for a resource that has no load-metric history, where AWS returns an empty list.
AWS: Smithy — GetScalingPlanResourceForecastData binds only InternalServiceException (500, server) and ValidationException (400, client), and its output has the single @required member Datapoints (a list), so a successful answer always carries the member and carries it as the EMPTY list when there is no forecast to report. The operation's own documentation states where the values come from: "Capacity forecasts are represented as predicted values, or data points, that are calculated using historical data points from a specified CloudWatch load metric." Recorded behavior: for an Auto Scaling group created moments earlier — a group that has published no history for the instruction's PredefinedLoadMetricSpecification (ASGTotalCPUUtilization) — every ForecastDataType (LoadForecast, CapacityForecast, ScheduledActionMinCapacity, ScheduledActionMaxCapacity) over a 24-hour window answers HTTP 200 with Datapoints: []. No history means no forecast; the window is valid and the plan is Active.
Emulator: HTTP 200 but with a full hourly series — one datapoint per hour of the requested window, each Timestamp on the hour and each Value a deterministic function of the STORED INSTRUCTION rather than of any metric history. The handler says so in its own module documentation ("This emulator ingests no metric data, so it has no history to predict FROM and the baseline load it forecasts around is read off the stored instruction instead") and computes it as baseline_capacity() * load_per_unit * diurnal_factor(hour), i.e. a cosine cycle about the midpoint of the instruction's MinCapacity/MaxCapacity band. The result is a non-empty forecast for a resource AWS reports no forecast for at all.
Why: a client cannot distinguish "this plan has no forecast yet" from "this plan has a forecast", which is the whole point of the read: the documented workflow is to create a ForecastOnly plan, poll until forecast data exists, and only then enable scaling. Against the emulator the poll succeeds immediately with invented numbers, so capacity planning, dashboards and any test asserting an empty forecast for a cold resource all consume fabricated values; the series is also derived from the capacity band, so it changes shape when the band changes rather than when load does.
Why this is not the already-open forecast issue: 20261117T023048Z-autoscaling-plans-getscalingplanresourceforecastdata-refuses-forecast-windows-aws-serves-400-validationexception.md is about the operation's WINDOW VALIDATION refusing accepted envelopes with 400 instead of answering 200 with Datapoints: []. Here the window is accepted and the status is 200; the divergence is in the forecast COMPUTATION, which invents datapoints where AWS has none. Fixing the window bounds does not empty the series.
Fix: the forecast computation in the operation's handler — the ResourceForecast/forecast path in src/ops/get_scaling_plan_resource_forecast_data.rs — must issue datapoints only where the service actually holds load-metric history for the instruction's load metric, and answer the @required Datapoints member as the empty list otherwise, instead of substituting the stored instruction's capacity band for the missing history. The window validation and the serializer are not involved.
Traces: autoscaling-plans.asp-predictive-forecast-without-history-has-no-datapoints. Code sites: src/ops/get_scaling_plan_resource_forecast_data.rs — module doc lines 30-39, ResourceForecast::of / baseline_capacity / load / capacity / diurnal_factor (around lines 446-830) and the forecast() entry point.
