=== Cause 1 of 2: the AccessDenied authorization-details trailer is appended unconditionally, including to seven refusals whose recordings end at the deny-reason sentence ===
AWS: IAM speaks awsQuery (com.amazonaws.iam#AWSIdentityManagementV20100508, 2010-05-08). Smithy models no authorization error for the refused operations — ListGroups, ListRoles, ListUsers and ListInstanceProfiles model only ServiceFailureException (awsQueryError ServiceFailure, HTTP 500); ListPoliciesGrantingServiceAccess models InvalidInput(400) and NoSuchEntity(404); SimulateCustomPolicy models InvalidInput(400) and PolicyEvaluation(500); UntagPolicy models ConcurrentModification(409), InvalidInput(400), NoSuchEntity(404), ServiceFailure(500). AccessDenied / HTTP 403 is the authorization layer's service-common error and its text is recorded behavior only. For each of the seven refusals below the recorded Error.Message is ONE sentence and nothing after it. Fixed text per deny reason: `User: <caller-arn> is not authorized to perform: <service>:<Action> on resource: <resource-description> because no identity-based policy allows the <service>:<Action> action` (implicit deny) and `User: <caller-arn> is not authorized to perform: <service>:<Action> on resource: <resource-description> with an explicit deny in an identity-based policy` (explicit deny). The variable parts come from the signed request and emulator state: <caller-arn> is the ARN of the IAM user that signed the request, <service>:<Action> the refused action, <resource-description> how IAM names the evaluated resource for that action — `arn:aws:iam::<account>:group/` for iam:ListGroups, `arn:aws:iam::<account>:instance-profile/` for iam:ListInstanceProfiles, `arn:aws:iam::<account>:role/` for iam:ListRoles, `arn:aws:iam::<account>:user/` for iam:ListUsers, the request's `Arn` value for iam:ListPoliciesGrantingServiceAccess, a bare `*` for iam:SimulateCustomPolicy, and `policy <PolicyArn>` for iam:UntagPolicy. Crucially the trailer is NOT a blanket property of IAM denials: other recorded IAM denials DO carry it (that is the open issue 20261119T085411Z-iam-every-accessdenied-refusal-message-stops-at-action.md, 26 checks, where it is MISSING), while these seven carry none — iam:SimulateCustomPolicy is denied on resource `*` with no trailer even though another recorded denial on resource `*` has one, so the discriminator is the recorded refusal, not the resource shape. HTTP 403 and Error.Code AccessDenied are correct in the emulator and are not at issue.
Emulator: the deny-reason sentence is byte-for-byte right, then a second sentence AWS did not send for these refusals is appended: `. Go to https://us-east-1.console.aws.amazon.com/iam/home?region=us-east-1#/authorization-details/<authorization-id> for complete details, or call the GetRequestAuthorizationDetails API with the following authorization id: <authorization-id>`. The <authorization-id> inside it is a per-run token and is not the defect; the defect is the presence of the whole sentence, emitted by the shared denial serializer for every denial regardless of class. All seven checks assert message equality after asserting Error.Code == AccessDenied (which passes), and in the explicit-deny checks the preceding allow legs converged, so the allow/deny decision itself is right.
Why: a client relying on AWS's behavior matches, logs or asserts on the denial text; it is handed text AWS never sent, so message-equality assertions and policy-troubleshooting tooling built on real AWS break even though status and code match, and an operator is pointed at an authorization id that identifies nothing. Because the sibling family needs the trailer PRESENT, a blanket choice in either direction keeps half the corpus wrong.
Fix: the shared IAM authorization-refusal denial-message builder (the AccessDenied body serializer the iam operation handlers call) — the trailer must be emitted per denial recording/class, not unconditionally. Closing this must leave the trailer-bearing refusals of 20261119T085411Z passing too.
Traces: iam.op-contract-listGroups-missing-permission-denied, iam.op-contract-listInstanceProfiles-missing-permission-denied, iam.op-contract-listRoles-missing-permission-denied, iam.op-contract-listUsers-missing-permission-denied (explicit-deny flavour); iam.list-policies-granting-service-access, iam.simulate-custom-policy, iam.untag-policy (implicit-deny flavour).

=== Cause 2 of 2: every IAM-minted unique id is EMULATOR-prefixed, so an access key id is not in AWS's AKIA access-key-id class ===
AWS: Smithy iam#CreateAccessKey -> output AccessKey (required); AccessKey.AccessKeyId targets accessKeyIdType (@length 16-128, @pattern ^[\w]+$), so the model does not pin the form and the prefix requirement is AWS's documented unique-identifier scheme: a long-term IAM user access key id is 20 characters beginning with the literal `AKIA` (a temporary STS credential begins `ASIA`), and the other IAM entity unique ids carry their own documented kind prefixes (AIDA user, AROA role, AGPA group, AIPA instance profile, ANPA policy) as 21-character uppercase-alphanumeric tokens. The requirement is the id FORM — `AKIA` + 16 further characters — never any one run's literal id, which is per-run state; the same form must be projected by ListAccessKeys.
Emulator: CreateAccessKey answers HTTP 200 with an otherwise correct key, but AccessKeyId is `EMULATOR`-prefixed (one observed value: `EMULATORAKV2M7BV5EWJ`) — it satisfies the Smithy pattern and the 20-character length yet is not in AWS's access-key-id class, so the check's prefix assertion fails before it can reach the remaining entity-id and ARN-path assertions.
Why: a client relying on AWS's behavior classifies credentials by prefix — long-term vs temporary, secret scanners, policy linters, presign helpers and credential-provider chains all branch on `AKIA`/`ASIA`. Every key the emulator mints is misclassified, and a client that validates the documented prefix rejects it outright.
Fix: the IAM unique-id allocator behind the user access-key state (reached by CreateAccessKey, projected by ListAccessKeys/GetAccessKeyLastUsed) and the shared entity-id minting it wraps — not the serializer. The open issues 20261125T143516Z-iam-minted-access-key-ids-carry-an-emulator.md and 20261124T000913Z-iam-4-net-new-causes-access-key-ids.md (cause 1) describe the same prefix for OTHER recorded units and carry none of this check's replay key, so they do not cover it; closing this cause must make them pass together.
Traces: iam.minted-identifier-prefixes-and-arn-paths.
