# ElastiCache: 3 net-new causes — a 3-shard cluster-mode group's node endpoints all resolve to ONE address, and the snapshot→restore and user-group revocation flows never converge

> _Note: this issue was identified against the code base at commit `d55cf650942c4a6b4ff1dfedc9a2db716f53d877`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Description
Three net-new root causes in the elasticache emulator, grounded in the only three failing checks of this replay that the suite report binds to no open issue and does not mark ALREADY FILED. Each cause is independent and must be closed on its own; re-replay the check id(s) listed under each cause's Traces before submitting.

=== Cause 1 of 3: a cluster-mode-enabled replication group is ONE backend wearing N shard names — the N shard node endpoints all resolve to a single address ===
Failing check: elasticache.elasticache-cluster-mode-slot-routing-moved-and-crossslot.
AWS: Smithy (services/service-com-amazonaws-elasticache-amazonelasticachev9/smithy-model/com-amazonaws-elasticache-amazonelasticachev9.json): ReplicationGroup$NodeGroups is a list of NodeGroup, each with NodeGroupId, Slots ("The keyspace for this node group (shard)"), PrimaryEndpoint ("The endpoint of the primary node in this node group (shard)") and NodeGroupMembers of NodeGroupMember{CacheClusterId, CacheNodeId}; Endpoint{Address: "The DNS hostname of the cache node", Port: "The port number that the cache engine is listening on"} is documented "Represents the information required for client programs to connect to a cache node". A group created with NumNodeGroups=N therefore holds N distinct member cache clusters, and DescribeCacheClusters(ShowCacheNodeInfo=true) advertises a DISTINCT CacheNodes[0].Endpoint.Address per member: N shard names that resolve, from inside the VPC, to N DIFFERENT node addresses. Recorded behavior: that per-shard partition is what makes the data plane answer CLUSTER SLOTS with N non-overlapping ranges totalling 0-16383 whose advertised ip/port match the control plane's members, a key whose CRC16 slot belongs to another shard answer `-MOVED <slot> <ip>:<port>` naming the OWNING node (never the contacted node, never the configuration endpoint), and a multi-key MSET spanning two slots answer `-CROSSSLOT Keys in request don't hash to the same slot` with neither key written while hash-tagged keys answer `+OK`.
Emulator: the control-plane shard bookkeeping passes (NodeGroups count and the Slots partition), but all N shard endpoint names resolve to ONE address at the in-VPC vantage point, so the check aborts at its fan-out assertion: "[runner-in-vpc] the 3 shard node names resolved to only 1 distinct addresses: {'0001': ..., '0002': ..., '0003': ...}. Distinct shards sharing one address is a single backend wearing three names, which is the flat-keyspace failure this check exists to catch". Cause in this checkout: services/service-com-amazonaws-elasticache-amazonelasticachev9/src/state/cache_data_plane.rs, `own_node_address` (line 1062) only mints a per-node address when the core's bind is UNSPECIFIED (`if !bound.is_unspecified() { return None; }`), so under this run's bind every node is published at the single address its socket is bound on, differing only in port; the published host is then identical for every shard (line 1007-1010, 1028-1032). The concrete address value is per-environment and NOT part of the requirement — the requirement is N shard endpoints that resolve to N distinct backends. Because the check aborts there, CLUSTER SLOTS, the `-MOVED` redirect and the `-CROSSSLOT` refusal are never exercised at all. Note: fixed issue 20261123T004734Z-elasticache-3-net-new-causes-cluster-mode-shards.md reported this exact assertion and is marked resolved; a resolved issue does not cover a failure, and the identical fan-out is still served, so it is filed here rather than left closed-unrun.
Why: a cluster-aware client bootstrapping from the configuration endpoint is handed a topology the emulator does not have. Keys never redirect, so code paths that must handle `-MOVED` are never exercised; cross-slot multi-key commands that real ElastiCache refuses with `-CROSSSLOT` succeed locally, so applications ship hash-tag bugs that only surface against AWS; per-shard isolation and capacity cannot be modelled.
Fix: the elasticache crate's replication-group provisioning/state and its data-plane addressing — materialise one cache-node backend per node group and publish each member cache cluster's OWN address (cache_data_plane.rs `own_node_address` / `open_cache_data_plane` must give each node an address a connection is accepted at even when the core's bind is not unspecified), plus the served cache engine's cluster-mode surface (src/state/cache_data_plane/slot_routing.rs and commands.rs: CLUSTER SLOTS reporting the per-shard ranges actually built, CRC16 ownership with `-MOVED` to the owning node, `-CROSSSLOT` for multi-key commands spanning slots).
Traces: elasticache.elasticache-cluster-mode-slot-routing-moved-and-crossslot (assertion at check line 1276 / source line 8885 of the replay report).

=== Cause 2 of 3: the create → write → snapshot → delete → restore round trip of a cache cluster never reaches a verdict ===
Failing check: elasticache.e2e-cluster-snapshot-restore-data-persists, whose whole detail is `Error: Check timed out after 60.0s` — no assertion fired, i.e. every control-plane call answered while the flow never got through its four sequential state waits.
AWS: Smithy (same model): CreateCacheCluster accepts SnapshotName to seed a new cluster from an existing snapshot and returns CacheCluster$CacheClusterStatus; CreateSnapshot returns Snapshot whose SnapshotStatus is documented "Valid values: creating | available | restoring | copying | deleting"; DescribeSnapshots(SnapshotName=...) reports that snapshot; CacheNode$Endpoint / Endpoint{Address, Port} is the address "client programs" connect to; DeleteCacheCluster removes the cluster so DescribeCacheClusters answers 404 CacheClusterNotFound (awsQueryError CacheClusterNotFound). The model states no timing. Recorded behavior only: each stage settles so that a polling client converges — the source cluster reaches CacheClusterStatus 'available', the published CacheNodes[0].Endpoint speaks RESP from inside the cluster's VPC (`SET <key> <value>` → `+OK`), the snapshot reaches SnapshotStatus 'available', the deleted cluster stops resolving, and a cluster created with SnapshotName=<that snapshot> reaches 'available' and answers `GET <key>` with the bulk string `$<value>`. Ids, keys and values are per-run; the requirement is convergence plus the restored keyspace holding what the snapshot captured.
Emulator: the check is killed at the per-check budget with no assertion reached, so none of its own verdicts (`expected snapshot <name> to be available, got <status>`, `restored cluster data mismatch: <read> != <value>`) was ever produced. Mechanism in this checkout: the flow has four sequential waits (cluster→available, snapshot→available, cluster→gone, restored cluster→available) polled at a 20 s cadence, and every transient phase is held for a deliberately non-zero span that the FIRST read after the starting call still observes — services/service-com-amazonaws-elasticache-amazonelasticachev9/src/state.rs:468 `pub const CLUSTER_TRANSITION: Duration = Duration::from_secs(3);`, :478 `SNAPSHOT_TRANSITION = CLUSTER_TRANSITION`, :489 `REPLICATION_GROUP_TEARDOWN = CLUSTER_TRANSITION` ("The due instant is stored on the record and materialised by whichever later call reads it"). A client therefore pays one whole poll interval per stage: 4 × 20 s exceeds the 60 s budget no matter what the emulator would have answered, so snapshot/restore data persistence is wholly unverified. Related: open issue 20261111T005655Z-elasticache-data-plane-still-unreachable-and-multi-wait.md lists this check id but its replay key is pinned to a `_redis_cmd#16|AssertionError` frame the current failure no longer takes, and fixed issue 20261118T103812Z-elasticache-2-net-new-causes-the-snapshot-restore.md recorded this remainder as still diverging; neither covers it now.
Why: snapshot-and-restore is the ElastiCache durability story. A client that snapshots a cache, tears it down and restores hangs instead of succeeding or failing diagnosably, and can never verify a backup; because every call answers 200 while nothing converges, the caller cannot distinguish 'still applying' from 'never applied' and SDK waiters/CI pipelines block.
Fix: the elasticache crate's status-settling path (src/state.rs: the `pending_status`/due-instant clock and the `settled_cluster_mut` / `settled_snapshot_mut` readers) so a record whose transition is already due reads back settled to the FIRST Describe that observes it and a multi-stage flow converges in a bounded number of polls, while the create/modify/delete RESPONSE keeps reporting the transient status other checks assert; plus the CreateSnapshot / DeleteCacheCluster / CreateCacheCluster(SnapshotName=...) handlers' use of that clock and of the restored keyspace (src/ops/create_snapshot.rs, src/ops/create_cache_cluster.rs).
Traces: elasticache.e2e-cluster-snapshot-restore-data-persists.

=== Cause 3 of 3: removing a user from a user group attached to a replication group is never observable — the revocation flow never reaches a verdict ===
Failing check: elasticache.e2e-user-group-access-revocation-flow, whose whole detail is `Error: Check timed out after 60.0s` — no assertion fired.
AWS: Smithy (same model): UserGroup{UserGroupId, Status "Indicates user group status. Can be \"creating\", \"active\", \"modifying\", \"deleting\"", UserIds, PendingChanges, ReplicationGroups}; ModifyUserGroup takes UserIdsToAdd/UserIdsToRemove and is modeled with InvalidUserGroupStateFault (400, code InvalidUserGroupState) and UserNotFoundFault (404, code UserNotFound); ModifyReplicationGroup takes UserGroupIdsToAdd/UserGroupIdsToRemove/RemoveUserGroups with ApplyImmediately and returns ReplicationGroup (Status, NodeGroups[].PrimaryEndpoint), modeled with InvalidUserGroupStateFault and UserGroupNotFoundFault (404, code UserGroupNotFound). Recorded behavior only: after ModifyUserGroup(UserIdsToRemove=[user]) the group goes 'modifying' then 'active' with the user absent from UserIds, the attached replication group returns to 'available', and the running engine then refuses the identical RESP `AUTH <user> <password>` that succeeded moments earlier (an error reply, not `+OK`); ModifyUserGroup(UserIdsToAdd=[user]) restores 'active' with the user present and the identical AUTH succeeds again. User/group/replication-group ids and the password are per-run values; the requirement is that each status read converges and that RBAC membership decides AUTH on whatever serves NodeGroups[0].PrimaryEndpoint.
Emulator: the check is killed at the per-check budget with no assertion reached — the positive-control AUTH, the post-removal refusal and the post-restore success were never observed, and neither was convergence (`expected <group> attached to <rg>, got UserGroupIds=<...>`, `condition not met within 600s`). Mechanism: the same non-zero transient span as Cause 2 (src/state.rs:468) across this flow's replication-group-available, user-group-attached, group-'active'-after-removal and group-'active'-after-re-add waits, each polled at a 20 s cadence, so the client's sleeps alone exceed the 60 s budget. Related: fixed issue 20261118T103812Z-elasticache-2-net-new-causes-the-snapshot-restore.md named this check and recorded the remainder as still diverging; a resolved issue does not cover it.
Why: a client that revokes access by removing a user from a user group has no way to see the revocation take effect, nor to see it reversed — credentials believed revoked may still authenticate against the cache, a security-relevant divergence — and because every control-plane call answers 200 while nothing settles, the caller cannot tell 'still applying' from 'never applied'.
Fix: the elasticache crate — ModifyUserGroup / ModifyReplicationGroup handlers and the user-group/replication-group state they mutate (src/ops/modify_user_group.rs, src/ops/modify_replication_group.rs over the settling clock in src/state.rs), so Status 'modifying'→'active' and the group's ReplicationGroup Status→'available' are settled for the FIRST Describe taken once the transition is due and UserGroupIds is reflected on the group; plus the data plane's access control (src/state/cache_data_plane/access_control.rs) enforcing group membership on AUTH at the published PrimaryEndpoint.
Traces: elasticache.e2e-user-group-access-revocation-flow.
