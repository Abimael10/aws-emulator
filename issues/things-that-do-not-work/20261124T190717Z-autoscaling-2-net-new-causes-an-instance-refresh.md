# autoscaling: 2 net-new causes — an instance refresh reports Successful while replacing no member (Min/MaxHealthyPercentage window never observable), and the suspended-ScheduledActions skip activity carries emulator-authored wording

> _Note: this issue was identified against the code base at commit `fd80f4f777355605a1441a9a10919decac7ea7ef`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
StartInstanceRefresh

## Description
Two net-new root causes in the autoscaling engine. They are bundled only because both belong to one service; each must be closed separately.

Cause 1 of 2 — StartInstanceRefresh walks to a terminal Successful without replacing any instance, so neither the MaxHealthyPercentage surge nor the terminate-first dip nor the MinHealthyPercentage floor is ever observable.
AWS: Smithy (services/service-com-amazonaws-autoscaling-autoscaling-2011-01-01): StartInstanceRefresh takes Preferences -> RefreshPreferences and returns InstanceRefreshId; RefreshPreferences.MinHealthyPercentage @range 0..100, MaxHealthyPercentage -> IntPercent100To200 @range 100..200, InstanceWarmup @range min 0, SkipMatching boolean; DescribeInstanceRefreshes reports each refresh's Status. The MaxHealthyPercentage member documentation states the replacement contract directly: "When MaxHealthyPercentage is explicitly set and it is mathematically impossible to replace instances while honoring both MinHealthyPercentage and MaxHealthyPercentage bounds simultaneously, Auto Scaling launches a new instance before terminating an old one (temporarily exceeding the desired capacity). When MaxHealthyPercentage is omitted, Auto Scaling terminates an instance and launches its replacement simultaneously." So on AWS a refresh of a group at desired capacity N: (a) replaces EVERY pre-refresh member, so the group's membership after a Successful refresh is disjoint from the pre-refresh instance ids; (b) with MinHealthyPercentage=100 and MaxHealthyPercentage=200 holds, at some point in flight, strictly more than N live (pending/running) instances at EC2 and never fewer than N healthy InService — a replacement id appears BEFORE any original leaves pending/running; (c) with MaxHealthyPercentage omitted and MinHealthyPercentage=100, terminates first, so the live count visibly dips below N at some point; (d) with MinHealthyPercentage=P the healthy InService count never falls below ceil(N*P/100) while the refresh is InProgress, and the refresh stays InProgress long enough for that floor to be sampled (the window is a function of the group size and the replacement plan, not of one recording's clock).
Emulator: the refresh is a status-only no-op. DescribeInstanceRefreshes goes Pending -> InProgress -> Successful within a handful of seconds while the group's instance set never changes: no instance is launched, none is terminated, the live count at EC2 stays exactly at desired capacity for the whole refresh, and every original instance survives a Successful refresh. Consequently the surge above desired never happens, the terminate-first dip below desired never happens, and the refresh is terminal before any in-flight sample of the MinHealthyPercentage floor can be taken.
Why: a client that uses an instance refresh to roll out a new launch-template version or AMI is told the roll-out Succeeded while every old instance is still running the old configuration — the deployment silently does nothing, and capacity-sensitive callers that rely on the surge (MaxHealthyPercentage) never see the extra capacity they provisioned the group's MaxSize for, while callers that rely on terminate-first never see the dip they drain for.
Fix: the instance-refresh engine in the autoscaling service — the replacement plan driven from StartInstanceRefresh's Preferences (launch-before-terminate when MaxHealthyPercentage is set, terminate-and-launch when it is omitted, the MinHealthyPercentage floor as the gate on how many members may be out at once) and the group-membership/EC2 state it must mutate, with the refresh's Status only becoming Successful once every member has actually been replaced.
Note: open issue 20261118T161732Z-autoscaling-never-advances-instance-refresh-terminate-hook-or.md records these same three checks as timing out with the refresh never advancing. It does not cover this behavior: the refresh now DOES advance to Successful, and the defect is that it advances without replacing anything. The replay no longer matches that issue's keys, so this is filed as net-new.
Traces: autoscaling.deep-autoscaling-1-asg-recon-refresh-max-healthy-surge, autoscaling.deep-autoscaling-1-asg-recon-refresh-without-max-healthy-no-surge, autoscaling.deep-autoscaling-1-asg-recon-refresh-min-healthy-floor.

Cause 2 of 2 — the scaling activity recorded when a scheduled action is skipped because ScheduledActions is suspended uses emulator-authored wording.
AWS: recorded behavior only — Smithy models Activity.Description as a free XmlString ("A friendly, more verbose description of the activity") and does not fix its text, so the requirement is the recorded wording. When a group has the ScheduledActions process suspended (SuspendProcesses) and a recurring scheduled action comes due, AWS records exactly one activity for that occurrence whose Description is the fixed sentence "Skipping scheduled action <name> since scheduled actions are suspended for the group." — fixed text "Skipping scheduled action " + the ScheduledActionName from the group's scheduled action + the fixed tail " since scheduled actions are suspended for the group.". It does not execute the action (DesiredCapacity is unchanged), it leaves the recurring action scheduled, and it does not back-fill the missed occurrence on resume. A control group with nothing suspended records "Executing scheduled action <name>" for the same occurrence.
Emulator: for the same occurrence on the suspended group the single activity's Description is "Skipped scheduled action <name>" — different fixed text (past-tense "Skipped" instead of "Skipping", and the whole " since scheduled actions are suspended for the group." clause dropped). Only the action name is interpolated correctly.
Why: operators and tooling read DescribeScalingActivities to distinguish a suspended-process skip from a scheduler that simply missed an occurrence; code or dashboards matching AWS's sentence (or its "since scheduled actions are suspended for the group" reason clause) classify the activity as unknown, so a deliberately suspended schedule looks like a lost occurrence.
Fix: the scheduled-action scheduler in the autoscaling service, where it emits the skip activity for a group with ScheduledActions suspended (the Activity.Description it writes into the group's activity history).
Traces: autoscaling.asg-suspended-scheduled-actions-skip-an-occurrence-and-resume-without-backfill.

## Steps to Reproduce
Cause 1:
1. CreateLaunchTemplate with an Amazon Linux 2023 ImageId and InstanceType t3.micro; CreateAutoScalingGroup with that launch template, MinSize=0, MaxSize=2*N, DesiredCapacity=N (N=2) across two subnets; wait for N healthy InService instances and record their instance ids.
2. StartInstanceRefresh(AutoScalingGroupName=<group>, Preferences={MinHealthyPercentage:100, MaxHealthyPercentage:200, InstanceWarmup:0, SkipMatching:false}).
3. Poll DescribeInstanceRefreshes for the refresh Status and, at each sample, DescribeInstances/DescribeAutoScalingInstances for the group's live members. Observe Status reaches Successful in seconds while the live count never exceeds N and every recorded original instance id is still present — AWS surges above N (launch before terminate) and finishes with a member set disjoint from the originals.
4. Repeat with MaxHealthyPercentage omitted (MinHealthyPercentage=100) and observe the live count never dips below N (AWS terminates first).
5. Repeat at DesiredCapacity=4 with MinHealthyPercentage=75 and observe the refresh is terminal before any member is replaced, so the healthy floor is never exercised.

Cause 2:
1. Create two identical Auto Scaling groups at DesiredCapacity=0 over the same launch template.
2. SuspendProcesses(AutoScalingGroupName=<subject>, ScalingProcesses=['ScheduledActions']); leave the second group unsuspended.
3. PutScheduledUpdateGroupAction on BOTH groups with the same ScheduledActionName, a Recurrence whose next occurrence is ~1-2 minutes out, and DesiredCapacity=1.
4. Wait for the control group's DesiredCapacity to become 1, then call DescribeScalingActivities on the subject group.
5. Observe the single activity's Description is 'Skipped scheduled action <name>' instead of AWS's 'Skipping scheduled action <name> since scheduled actions are suspended for the group.'
