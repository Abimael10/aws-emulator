## Description
Two distinct net-new root causes behind the 23 failing checks of the backup__events group. Both are closed separately. None of these checks is marked ALREADY FILED or OWNED in the replay report (the two OWNED ones, eventbridge-rule-missing-target-permission-backup-job-event-not-invoked and eventbridge-rule-scoped-to-specific-backup-vault-arn, are carried by 20261115T205809Z-backup-events-2-net-new-causes-a-vault.md, and backup-job-failed-event-matches-pattern by 20261122T064544Z-backup-events-the-failed-backup-job-state-change--r2.md; none of those three is bundled here). Cause 1 is the SAME emulator defect filed for the `backup` service in this sweep, reported here because every check of this group is grounded in it and the group takes its own verdict.

=== Cause 1 of 2: every backup job started in this group settles FAILED/AccessDenied, so no COMPLETED/RUNNING state-change event, no copy job and no restore job is ever reachable ===
AWS: Smithy: StartBackupJob.IamRoleArn @required ("Specifies the IAM role ARN used to create the target recovery point"); DescribeBackupJob reports State, StatusMessage and MessageCategory (doc: "Example strings may include AccessDenied, SUCCESS, AGGREGATE_ALL, and INVALIDPARAMETERS"). IAM authorization is not modeled, so for the decision this is recorded behavior only: a backup service role whose trust policy trusts backup.amazonaws.com and which has arn:aws:iam::aws:policy/service-role/AWSBackupServiceRolePolicyForBackup attached IS authorized for the per-resource-type creating action (dynamodb:CreateBackup for a table), so the job progresses CREATED -> RUNNING -> COMPLETED, writes its recovery point, and each transition publishes an aws.backup 'Backup Job State Change' event whose detail carries backupJobId/state/backupVaultArn/resourceArn — which is what every rule, SNS/SQS/Lambda target and CFN-deployed notification in this group observes.
Emulator: each such job is settled FAILED about half a second after StartBackupJob with MessageCategory 'AccessDenied' and StatusMessage 'User: <IamRoleArn> is not authorized to perform: dynamodb:CreateBackup on resource: <ResourceArn> because no identity-based policy allows the dynamodb:CreateBackup action' (fixed text 'User: ', ' is not authorized to perform: ', ' on resource: ', ' because no identity-based policy allows the ', ' action'; variable parts are the request's IamRoleArn, the per-resource-type action and the request's ResourceArn), PercentDone '0.0', no recovery point. The denial is state::job_outcome::withheld_backup_denial asking service_common::iam_role::role_withholds_action, which counts every decision other than Allowed — including IAM's implicit deny, mapped to Decision::NotStated — as a withheld action; the emulator's IAM holds no document for the attached AWS managed policy, so SimulatePrincipalPolicy answers implicitDeny and the job dies. Consequently the only transition ever published is the FAILED one, and every positive control in this group ("expect the job to be running/completed", "expect a non-failed job", "expect the COMPLETED event on the queue/topic") is unsatisfiable; the copy-job and restore-job legs never get a recovery point to work from.
Why: a client building backup automation on EventBridge — notification on COMPLETED, copy-on-completion, restore-driven workflows, scheduled or CFN-deployed plans — observes only failures, and cannot distinguish a genuine delivery/eventing defect from this blanket authorization failure. The entire eventing surface of AWS Backup is unobservable.
Fix: the role-permission half of a job's outcome — services/service-com-amazonaws-backup-cryocontrollerusermanager/src/state/job_outcome.rs (withheld_backup_denial) and the shared reader services/common/src/iam_role.rs (role_withholds_action / role_action_decision_through): an attached managed policy whose document this account's IAM does not hold, and the implicit deny IAM returns for it, must leave the job's outcome alone rather than denying it; alternatively the IAM store must hold the AWS managed policy documents AttachRolePolicy accepts.

=== Cause 2 of 2: a real backup job's early 'Backup Job State Change' event never invokes an EventBridge rule's Lambda target ===
AWS: recorded behavior only (the backup model documents no events): a rule with EventPattern {"source":["aws.backup"],"detail-type":["Backup Job State Change"],"detail":{"state":["RUNNING","PENDING","CREATED","COMPLETED"]}} and a Lambda target the function's resource policy allows for events.amazonaws.com with SourceArn=<rule arn> is invoked for a real on-demand backup job as soon as the job reaches any of those states, and the function's CloudWatch Logs log group /aws/lambda/<fn> then contains the job's BackupJobId.
Emulator: nothing invokes the function inside the observation window — the check is cut off at the 60 s run budget with no verdict, so the log group never shows the BackupJobId marker. The job itself goes CREATED -> FAILED (Cause 1), and no matching non-terminal transition is delivered to the Lambda target, so even the CREATED state the pattern accepts produces no invocation.
Why: a client wiring per-job automation (tagging, notification, inventory) to a Lambda target behind a state-change rule sees the function never run, and gets no signal at all — not even a failed invocation — so the integration appears silently inert.
Fix: the Backup job state-change publication path and the EventBridge Lambda-target dispatch under it — a job's non-terminal transitions must be published on the default bus and must invoke a permitted Lambda target promptly, within a normal observation window.
Traces: backup__events.backup-job-state-change-invokes-lambda-target.
