# appconfig__iam__lambda: a Lambda handler that reads the AppConfig data plane in-process never produces an answer, so all four AppConfig-handler scenarios burn the whole harness deadline without reaching a verdict

> _Note: this issue was identified against the code base at commit `96b6253dc6ea8319b5f1ad39858d0c023680de77`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
Invoke

## Description
Cause 1 of 1: every scenario in the appconfig__iam__lambda family that invokes a deployed Lambda function which calls the AppConfigData data plane from inside the handler makes no observable progress. All four checks in this service time out at the harness ceiling (60.0 s) inside a bounded Invoke/poll loop, never observing ANY of the three distinguishable handler verdicts the family is built on (source='appconfig' with the deployed document, source='default' with code='AccessDeniedException', source='default' with code='ResourceNotFoundException').

AWS: a synchronous Invoke (InvocationType=RequestResponse) runs the deployment package and answers HTTP 200 with the handler's own payload and no X-Amz-Function-Error header when the handler returns normally. Inside such a handler, AppConfigData StartConfigurationSession (Smithy: POST /configurationsessions, success 201; errors BadRequestException 400, ResourceNotFoundException 404, ThrottlingException 429, InternalServerException 500) mints an InitialConfigurationToken, and GetLatestConfiguration (Smithy: GET /configuration, success 200, Configuration as the httpPayload blob) returns the bytes of the version the environment currently has deployed. When the identifiers name resources that do not exist, both operations answer 404 ResourceNotFoundException. When the caller's execution role grants none of appconfig:StartConfigurationSession / appconfig:GetLatestConfiguration / appconfig:GetConfiguration, the request is refused at the authorization layer with HTTP 403 and error code AccessDeniedException (recorded behavior only — AccessDeniedException is not in either operation's modeled error list; its message is AWS's standard identity-based-denial text whose fixed part is 'User: <principal arn> is not authorized to perform: <action> on resource: <resource arn> because no identity-based policy allows the <action> action', with principal, action and resource taken from the request, never literal values from one run). None of this is long-running: each of the four checks deploys with a 0-minute duration / 100% growth / 0-minute bake strategy, so the configuration is servable as soon as the deployment reports State=COMPLETE (Smithy: DeploymentState enum values BAKING | VALIDATING | DEPLOYING | COMPLETE | ROLLING_BACK | ROLLED_BACK | REVERTED).

Emulator: none of the four checks ever reaches a decidable answer. Each one is cut off by the harness with 'Check timed out after 60.0s' while sitting in a bounded loop (invoke-until-answer, or poll-deployment-until-terminal) whose own budget is 180-300 s, so no assertion is ever evaluated: the permitted function is never seen to return the deployed document, the under-privileged sibling is never seen to be denied AccessDeniedException, the handler given logical-id-shaped identifiers is never seen to fall back with ResourceNotFoundException, and the in-place identifier repair is never seen to flip the handler from default to appconfig. The replayed verdict is therefore an absence of any response content, not a wrong response.

Related open issues that do NOT carry these checks' replay keys and therefore do not cover them: 20261110T161251Z-appconfig-iam-lambda-a-lambda-handler-that-reads.md, 20261110T185149Z-appconfig-iam-lambda-a-lambda-handler-whose-execution.md, 20261108T015132Z-appconfig-iam-lambda-a-lambda-handler-s-in-1c3e49.md, 20261107T182959Z-appconfig-iam-lambda-a-lambda-handler-s-in-990472.md and 20261105T085348Z-appconfig-iam-lambda-the-in-process-lambda-python.md (the last of which describes the handler faulting Runtime.ImportModuleError, a different observable from the no-answer-at-all seen here).

Why: a client that reads a feature flag from AppConfig inside a Lambda cannot exercise any of the behaviours it depends on against this emulator. The success path (the handler receives the deployed document), the permission path (a role missing the three appconfig actions is denied AccessDeniedException rather than ResourceNotFoundException, which is what separates a permission fault from an identifier fault) and the repair path (fixing wrong identifiers makes the handler stop falling back) are all unobservable, so an over-permissive role, a mis-wired identifier and a correct deployment are indistinguishable.

Fix: the Lambda Invoke (RequestResponse) execution path, so a deployed package runs in-process and its payload is returned within the request; and the IAM authorization of AppConfigData StartConfigurationSession / GetLatestConfiguration when the caller is a Lambda execution role, so a role granting no appconfig action is refused 403 AccessDeniedException while a granting role receives the deployed bytes.

## Evidence
Expected (AWS): lambda.Invoke(FunctionName=<permitted fn>, InvocationType=RequestResponse) -> HTTP 200, no FunctionError, payload {"source": "appconfig", "config": {"useNewBackend": true}}; the sibling function whose execution role grants no appconfig action -> HTTP 200, payload {"source": "default", "code": "AccessDeniedException", "config": {"useNewBackend": false}} (the handler catches the 403 itself); the function whose APP_CONFIG_* variables hold logical-id-shaped values that resolve to nothing -> HTTP 200, payload {"source": "default", "code": "ResourceNotFoundException", ...}; and appconfigdata.StartConfigurationSession + GetLatestConfiguration under the check's own credentials still return the deployed bytes, proving the refusal is the principal's and not the resource's.

Actual (emulator): all four checks end with 'Error: Check timed out after 60.0s'. No assertion in any of the four is reached, so no status, error code or payload is produced at all for the handler's AppConfig read. The deployments involved use DeploymentDurationInMinutes=0, GrowthFactor=100, GrowthType=LINEAR, FinalBakeTimeInMinutes=0, ReplicateTo=NONE, so no wall-clock rollout is being waited on; the bounded loops the checks sit in (invoke-until-answer, 240-300 s; poll-deployment-until-terminal, 180 s) are an order of magnitude longer than the 60 s ceiling, which is why the harness cuts them off rather than an assertion firing.

## Steps to Reproduce
1. appconfig: CreateApplication, CreateEnvironment, CreateConfigurationProfile(LocationUri='hosted', Type='AWS.Freeform'), CreateDeploymentStrategy(DeploymentDurationInMinutes=0, GrowthFactor=100, GrowthType='LINEAR', FinalBakeTimeInMinutes=0, ReplicateTo='NONE'), CreateHostedConfigurationVersion(Content=b'{"useNewBackend": true}', ContentType='application/json'), StartDeployment; poll GetDeployment until State is COMPLETE.
2. iam: create two roles trusting lambda.amazonaws.com. Role A's inline policy grants appconfig:StartConfigurationSession, appconfig:GetLatestConfiguration and appconfig:GetConfiguration (plus logs:*); role B grants only logs:*.
3. lambda: CreateFunction twice (python3.12) with the same one-file handler that calls appconfigdata StartConfigurationSession + GetLatestConfiguration using APP_CONFIG_APPLICATION / APP_CONFIG_ENVIRONMENT / APP_CONFIG_CONFIGURATION environment variables and returns {"source": "appconfig", ...} on success or {"source": "default", "code": <error code>, ...} on any exception; wait for both to be Active.
4. Invoke the role-A function: expect HTTP 200, no FunctionError, source='appconfig' and the deployed document.
5. Invoke the role-B function: expect HTTP 200 and source='default' with code='AccessDeniedException'.
6. Create a third function whose three APP_CONFIG_* variables hold logical-id-shaped values that resolve to nothing and invoke it: expect source='default' with code='ResourceNotFoundException'; then correct the variables one at a time and re-invoke, expecting source='appconfig' only once all three are real.
7. Observe that no invoke ever yields any of these payloads and each scenario consumes the whole per-check deadline instead.
