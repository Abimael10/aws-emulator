# appconfig: GetDeployment serves Deployment$State as the SCREAMING_SNAKE enum member ('COMPLETE') instead of AWS's CamelCase wire token ('Complete'), so a client's settle barrier never releases and both experiment-run checks die ungraded at the harness cap

> _Note: this issue was identified against the code base at commit `5de8975540ca22ec41f789488a788a9a12b974db`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
GetDeployment

## Description
One net-new root cause in the appconfig service, grounded in 2 failing behavioral checks. Neither check is marked ALREADY FILED and neither is marked OWNED by an open issue in this replay.

Cause 1 of 1: Deployment$State is put on the wire as the Smithy enum MEMBER NAME ('COMPLETE', 'DEPLOYING', 'BAKING', ...) rather than the CamelCase token AppConfig actually serves ('Complete', 'Deploying', 'Baking', 'RollingBack', 'RolledBack', 'Reverted'), so no client that waits for a deployment to settle ever observes a settled deployment.
Failing check ids: appconfig.start-experiment-run-invalid-treatment-allocation-rejected, appconfig.stop-experiment-run-double-stop-conflict.

  AWS: Smithy (services/service-com-amazonaws-appconfig-amazonappconfig/smithy-model/com-amazonaws-appconfig-amazonappconfig.json) models Deployment$State -> com.amazonaws.appconfig#DeploymentState, an enum whose members are [BAKING, VALIDATING, DEPLOYING, COMPLETE, ROLLING_BACK, ROLLED_BACK, REVERTED] with no @enumValue override, and Environment$State -> EnvironmentState, members [READY_FOR_DEPLOYMENT, DEPLOYING, ROLLING_BACK, ROLLED_BACK, REVERTED]. The model therefore states member NAMES only and says nothing about the serialized casing. That the token AppConfig puts on the wire is the CamelCase form of each member — 'Complete' for a finished deployment, 'ReadyForDeployment' for a settled environment — is RECORDED BEHAVIOR ONLY: both failing checks build their settle barriers on exactly those two literals and record the source note "despite the documented SCREAMING_SNAKE_CASE enums, the real wire values are PascalCase ('Complete', 'ReadyForDeployment') -- confirmed against real AWS". The requirement is the mapping member -> CamelCase wire token for EVERY DeploymentState member, not any one run's state value. Both reads here are plain 200 responses; no error code or message is involved.

  Emulator: the member name is emitted verbatim for DeploymentState. GetDeployment on a settled deployment answers 200 with $.State = 'COMPLETE'. The sibling enum is already handled the other way in the same module — the service spells ENVIRONMENT_READY_FOR_DEPLOYMENT as 'ReadyForDeployment' and ENVIRONMENT_DEPLOYING as 'Deploying', while DEPLOYMENT_COMPLETE/DEPLOYMENT_DEPLOYING/DEPLOYMENT_BAKING are 'COMPLETE'/'DEPLOYING'/'BAKING' — so the two State enums disagree about their own wire form and only the deployment one diverges from the recording. Consequence in both checks: the setup barrier _poll_until(GetDeployment(...)['State'] == 'Complete', timeout_s=60.0, interval_s=2.0) can never be satisfied by any value the emulator can produce, the barrier consumes the whole per-check budget, and the harness kills each check with "Check timed out after 60.0s" before a single graded assertion is issued.

  Why: State is the only completion signal AppConfig offers for a deployment. Every client that waits for a release to settle before doing the next thing — a deploy script, a CI gate, a Step Functions poller, or (as here) the StartExperimentRun precondition that the experiment's configuration profile already have a completed deployment — compares State against the token real AWS sends. Against this emulator that comparison is false in every state, so such a client hangs until its own timeout instead of proceeding, and every code path gated behind a settled deployment becomes unreachable. Here it makes the whole StartExperimentRun treatment-override refusal (BadRequestException 'Invalid treatment name: <name>. Valid treatment names are: [<control key>, <treatment keys>]' — fixed text plus names taken from the request and the definition's own treatment keys — with no run created and the definition left IDLE) and the whole StopExperimentRun double-stop refusal (BadRequestException 'Experiment run <run number> for experiment definition <definition id> is not running.' — fixed text plus the run number from the request and the definition id it addressed) impossible to reach, so neither can be graded at all.

  Fix: the appconfig service's DeploymentState wire mapping — one shared place, not per handler: the response projection for Deployment / DeploymentSummary (GetDeployment, StartDeployment, StopDeployment, ListDeployments) must map each DeploymentState member to its CamelCase wire token, and the same mapping must be applied wherever a deployment State is interpolated into a refusal sentence (the StopDeployment terminal-state refusal prints the stored token today). The internal state machine's representation can stay as it is; the divergence is at the wire boundary. See the state module's DeploymentState constants (services/service-com-amazonaws-appconfig-amazonappconfig/src/state.rs:80-92) next to the EnvironmentState constants (same file, lines 111-115) that already carry the CamelCase form, and the completion transition that stores it (same file, around line 3205).

  CORPUS CONFLICT a fixer must reconcile before changing anything: this behavioral recording requires 'Complete', while the WIRE corpus recordings require the SCREAMING_SNAKE form and several issues filed from them were resolved by moving the emulator to it — open 20261116T014021Z-appconfig-serves-deployment-state-in-pascalcase-across-the.md (StartDeployment/StopDeployment/ListDeployments) and fixed 20261116T072120Z-appconfig-serves-deployment-state-in-pascalcase-complete-deploying.md, 20261115T214126Z-appconfig-appconfigdata-getdeployment-serves-deployment-state-in-pascalcase.md, 20261115T232640Z-appconfig-cloudwatch-getdeployment-serves-deployment-state-as-complete.md, 20261115T213820Z-appconfig-lambda-2-net-new-causes-getdeployment-serves.md. Conversely, fixed issue 20261110T191755Z-appconfig-getdeployment-getenvironment-serve-state-as-the-model.md states this very cause for the first check below and its effect has not survived in this checkout, so for the behavioral corpus this is a regression rather than a new defect. None of those issues carries this replay's keys for the two checks named here, so they do not cover them; a fix that flips the casing globally will re-break the wire steps those issues bind, so the two corpora's expectations must be reconciled (per-path or per-shape) rather than toggled.

  Traces: appconfig.start-experiment-run-invalid-treatment-allocation-rejected, appconfig.stop-experiment-run-double-stop-conflict. Generated application/environment/profile/strategy ids and names, deployment and run numbers, timestamps and the particular wall-clock instant the harness killed each check are per-run values; the requirement is the wire token for every DeploymentState member.

Expected (AWS, per the recording): GetDeployment answers 200 with State 'Complete' once the zero-duration/zero-bake deployment settles; GetEnvironment then answers 'ReadyForDeployment'. Both barriers release in seconds and each check proceeds to its graded call.
Actual (emulator): the DeploymentState member name is served instead — GetDeployment answers 200 with State 'COMPLETE'. The environment barrier would release ('ReadyForDeployment' IS served), so the deployment barrier alone burns the entire 60 s per-check budget and the harness kills both checks at exactly 60.0 s with every graded assertion ungraded: for the first check the BadRequestException 'Invalid treatment name: <name>. Valid treatment names are: [<control key>, <treatment key>]', ListExperimentRuns == [], GetExperimentDefinition Status 'IDLE', then Status 'RUNNING' for a valid key; for the second the DONE first stop, then BadRequestException 'Experiment run <run number> for experiment definition <definition id> is not running.' and the unchanged EndedAt.

Source in this checkout (services/service-com-amazonaws-appconfig-amazonappconfig/src/state.rs): line 84 `pub const DEPLOYMENT_COMPLETE: &str = "COMPLETE";` (with DEPLOYMENT_DEPLOYING/BAKING/ROLLING_BACK/ROLLED_BACK/REVERTED likewise the member names, lines 80-92) versus line 111 `pub const ENVIRONMENT_READY_FOR_DEPLOYMENT: &str = "ReadyForDeployment";` and line 113 `pub const ENVIRONMENT_DEPLOYING: &str = "Deploying";`; the completion transition assigns DEPLOYMENT_COMPLETE around line 3205. The module's own doc comment states the choice explicitly ("a deployment that finished reports COMPLETE ... the sibling Environment$State is the one enum of this service that does NOT work that way"), so the divergence is deliberate and not a stray literal.

Smithy consulted: DeploymentState values = [BAKING, VALIDATING, DEPLOYING, COMPLETE, ROLLING_BACK, ROLLED_BACK, REVERTED]; EnvironmentState values = [READY_FOR_DEPLOYMENT, DEPLOYING, ROLLING_BACK, ROLLED_BACK, REVERTED]; no @enumValue overrides, so the served casing is recorded behavior only.

## Steps to Reproduce
Boot the emulator and point an appconfig client at its data listener (region/credentials irrelevant).
1. CreateApplication(Name=<new>); CreateEnvironment(ApplicationId=<app>, Name=<new>).
2. CreateConfigurationProfile(ApplicationId=<app>, Name=<new>, LocationUri='hosted', Type='AWS.AppConfig.FeatureFlags'); CreateHostedConfigurationVersion with a feature-flag document defining one flag.
3. CreateDeploymentStrategy(DeploymentDurationInMinutes=0, GrowthFactor=100, FinalBakeTimeInMinutes=0, ReplicateTo='NONE'); StartDeployment of that version.
4. THE GRADED READ: GetDeployment(ApplicationId=<app>, EnvironmentId=<env>, DeploymentNumber=<n>) and inspect ['State'].
   EXPECTED (recording): the CamelCase token — 'Complete' once settled, and 'Deploying'/'Baking'/'Validating'/'RollingBack'/'RolledBack'/'Reverted' for the other members.
   OBSERVED: 'COMPLETE' (the Smithy member name), so a client comparing against 'Complete' never matches and a bounded poll exhausts its timeout.
5. Confirm GetEnvironment(ApplicationId=<app>, EnvironmentId=<env>)['State'] is 'ReadyForDeployment' (it already is) — that barrier is not the defect; only the deployment one is.
6. Confirm the same mapping on every other DeploymentState-bearing response: StartDeployment, StopDeployment, ListDeployments items — and on the sentence form: StopDeployment on a settled deployment should report its state with the same token the read serves.
7. Re-replay appconfig.start-experiment-run-invalid-treatment-allocation-rejected and appconfig.stop-experiment-run-double-stop-conflict: with the mapping aligned to the recording, both setup barriers release in seconds and each check reaches its graded StartExperimentRun / StopExperimentRun assertions instead of being killed at the 60 s cap.
