# logs: 2 net-new causes — Insights `parse` output columns never reach GetQueryResults rows, and DeleteQueryDefinition's not-found message carries the PutQueryDefinition guidance sentence

> _Note: this issue was identified against the code base at commit `4bf99a6da981b1c03b4c2a4da03064374e7befb5`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
GetQueryResults, DeleteQueryDefinition

## Description
Two net-new root causes in the CloudWatch Logs query surface, reached by 4 behavioral checks that are not carried as replay keys by any open issue. BOTH causes must be closed before this issue is submitted; each cause below names the failing check ids it is grounded in.

Cause 1 of 2 — an Insights pipeline whose only projection is `parse` returns rows that do not carry the parsed fields.
AWS: Smithy (logs, com.amazonaws.cloudwatchlogs#Logs_20140328) GetQueryResults output `results` is a list of rows of ResultField {field,value}; a row's columns are the pipeline's own output columns, and StartQuery/GetQueryResults model no error for this (status reaches `Complete`). Recorded behavior: for `filter @message like /<marker>/ | parse @message "svc=* lat=* status=*" as svc, lat, st | sort @timestamp asc` each matching row carries the parsed field names (`svc`, `lat`, `st`) with the values taken from the matched line, and for the named-capture regex form `parse @message /lat=(?<lat>\d+)/ | sort lat desc` each row carries `lat` and the rows are ordered by that parsed value. The parsed names are the ones the request's parse command declares; the values come from the ingested events.
Emulator: both pipelines reach `Complete` and return the right NUMBER of rows, but the parsed columns are absent from every row — reading them yields None. The glob form gives `[(None, None), (None, None)]` where the seeded values are `[('alpha','100'), ('beta','200')]`; the regex form gives `[None, None, None]` where the seeded latencies are `['300','200','100']`, so `sort lat desc` has nothing to order. The rows come back with the engine's default columns (`@message`/`@timestamp`/`@ptr`) only; the parsed columns surface only when a later `display`/`fields` command names them explicitly.
Why: extracting fields from unstructured log lines with `parse` and reading them off the result rows is the canonical Insights idiom (and what the console shows). A client doing it receives rows with no data in them, and any `sort`/`filter` on a parsed field is meaningless — with no error to diagnose, because the query is reported Complete.
Fix: the Insights query engine's row-projection / field-resolution stage behind StartQuery+GetQueryResults — fields a `parse` command creates must enter the row's output column set and replace the implicit default projection, for both the `"pattern" as a, b, c` glob form and the `(?<name>...)` named-capture regex form.
Traces: logs.logsquery-redefining-a-parsed-field-rejected (its positive-control leg; the MalformedQueryException leg of the check passes), logs.logsquery-parse-with-an-unclosed-regex-group-rejected (its positive-control leg; the MalformedQueryException leg passes). Related open issue 20261108T145640Z-logs-9-net-new-causes-cloudwatch-logs-insights.md describes the same projection defect as its Cause 1 but carries only the logsquery-parse-glob/display/sort replay keys, so neither of these two checks is covered by it; 20261108T120220Z-cloudwatch-lambda-logs-logs-insights-parse-with-named.md is a different cause (a bogus empty-key group for NON-matching records).

Cause 2 of 2 — DeleteQueryDefinition's ResourceNotFoundException message is the PutQueryDefinition guidance text, not the delete-path sentence.
AWS: Smithy (logs) DeleteQueryDefinition takes `queryDefinitionId` (QueryId, len 1..256, required) and models ResourceNotFoundException (client, HTTP 400). Recorded behavior for deleting an id that names no definition (including an id that was just deleted): HTTP 400, error code `ResourceNotFoundException`, message `Query definition id is invalid. (Service: AWSLogs; Status Code: 400; Error Code: ResourceNotFoundException; Request ID: <per-call request id>; Proxy: null)`. Fixed text: `Query definition id is invalid.` and the ` (Service: AWSLogs; Status Code: 400; Error Code: ResourceNotFoundException; Request ID: ...; Proxy: null)` suffix CloudWatch Logs appends; the only variable part is the per-call request id.
Emulator: the status (400) and the code (ResourceNotFoundException) are right, but the message is `Query definition id is invalid. If you are updating query definition, please provide correct query definition id; If you are creating new query definition, do not use --query-definition-id as a parameter (Service: AWSLogs; Status Code: 400; Error Code: ResourceNotFoundException; Request ID: <per-call request id>; Proxy: null)` — i.e. the sentence AWS adds only on the PutQueryDefinition path (where `queryDefinitionId` is the optional update selector) is appended to the delete-path refusal. Hypothesis: the refusal is built from one shared helper, `crate::state::query_definition_not_found_message()`, written for the Put path and reused by Delete.
Why: clients, the CLI and SDK error-message matching key on this message to tell an unknown query-definition id from other ResourceNotFoundException causes; the delete path advises the caller about `--query-definition-id` on a call that has no such option, and any assertion/log-scrape on AWS's wording fails.
Fix: DeleteQueryDefinition's not-found refusal construction — it must carry the delete-path message `Query definition id is invalid.` instead of the Put-path helper's text (the Put path keeps its own longer sentence).
Traces: logs.delete-query-definition-removes-resource, logs.op-contract-delete-query-definition. Code citation: services/service-com-amazonaws-cloudwatchlogs-logs-20140328/src/ops/delete_query_definition.rs lines 163-166 calls crate::state::query_definition_not_found_message() in services/service-com-amazonaws-cloudwatchlogs-logs-20140328/src/state.rs.
