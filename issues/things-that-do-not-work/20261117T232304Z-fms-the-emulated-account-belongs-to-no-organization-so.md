# The emulated account belongs to no organization, so organizations DescribeOrganization is refused 404 AWSOrganizationsNotInUseException and fms's management-account-only gate has no management account to name

> _Note: this issue was identified against the code base at commit `b90e82e778857331b034183013dcc14d9b1758a1`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
DescribeOrganization

## Description
One root cause.

Cause 1 of 1: on a freshly booted emulator the Organizations control plane holds no organization, so every organization-scoped read is refused and no caller can learn the organization's management account. Both Firewall Manager checks that depend on that identity abort on the refusal. Failing checks: fms.get-admin-scope-malformed-account-rejected, fms.list-admin-accounts-for-organization-unconfigured-not-found.

AWS: in the environment these two checks were recorded against, the caller's account IS a member of an organization and is NOT that organization's management account. Organizations DescribeOrganization therefore answers HTTP 200 with an Organization structure whose MasterAccountId is a 12-digit account id other than the caller's (Smithy, organizations model: DescribeOrganization input smithy.api#Unit, output DescribeOrganizationResponse{Organization}, errors AWSOrganizationsNotInUseException, ConcurrentModificationException; Organization$MasterAccountId -> AccountId, @length 0..12, @pattern ^\d{12}$, documented as "The unique identifier (ID) of the management account of an organization"). AWSOrganizationsNotInUseException (httpError 404) is the answer for an account that is a member of NO organization, and its message is entirely fixed text with no values from the request or state: "Your account isn't a member of an organization. To make this request, you must use the credentials of an account that belongs to an organization." Because the caller is a member but not the management account, Firewall Manager's management-account-only operations (fms Smithy: GetAdminScope and ListAdminAccountsForOrganization both declare InvalidOperationException, HTTP 400) refuse it with InvalidOperationException whose message is "<caller account id> is not the management account of the Organization but is attempting to perform an action that only the Organization management account can perform. The Organization management account is <Organization$MasterAccountId>" — everything outside the two substituted account ids is the fixed text, and the two ids are taken from the caller's identity and from Organizations' state, never literals.

Emulator: organizations DescribeOrganization answers 404 AWSOrganizationsNotInUseException ("Your account isn't a member of an organization. ...") on a freshly booted emulator with no prior request, because membership is never established: the Organizations service's construction seam deliberately establishes none (see its service.rs EmulatedService::new doc comment: "Mounting this control plane establishes NO organization") and CreateOrganization is the only writer of the organization slot. Both failing checks call organizations DescribeOrganization to read Organization.MasterAccountId as the expected value of the Firewall Manager refusal message, and botocore raises AWSOrganizationsNotInUseException there, so each check dies mid-way. In both checks the Firewall Manager assertions made BEFORE that call passed (GetAdminScope with AdminAccount "not-an-account-id" produced the exact ValidationException pattern message; GetAdminAccount produced ResourceNotFoundException with an empty message), so the divergence is entirely the organization-membership state, not those two fms answers. The same gap also makes the fms refusal message unsatisfiable even once the checks get past DescribeOrganization: the fms helper that supplies the management account falls back to the emulator's own presented account whenever Organizations holds no organization, which renders the message as "<caller> is not the management account ... The Organization management account is <caller>" — naming one account as both the offender and the management account, which AWS never emits.

Why: a client cannot discover the organization it is in, nor who administers it. The idiomatic probe — call DescribeOrganization, read MasterAccountId, and compare it with the caller to decide whether management-account-only calls are permitted — always takes the "not in an organization" branch, so Organizations-aware client logic (Firewall Manager admin onboarding, SCP-gated paths, delegated-administrator flows, consolidated-billing paths) either fails outright on the 404 or, if it falls through, is handed a management account identical to the caller and concludes it MAY perform management-account-only calls when the recorded service says it may not. Firewall Manager's entire management-account-only refusal class (GetAdminScope and ListAdminAccountsForOrganization answering InvalidOperationException that names the real management account) is consequently unobservable.

Fix: the Organizations crate's state/construction seam, which decides whether the presented account has an organization membership, plus the Firewall Manager cross-service read of the management account that currently papers over its absence with a fallback to the caller's own account. Note the tension a fixer must resolve rather than flip: the open issue 20261104T063936Z-account-organizations-describeorganization-reports-an-organization-on-a-freshly.md asks for exactly the opposite reading (it reports a mount-time seeded organization and asks for the 404), and the code now implements that request, which is what these two fms checks trip over. Both readings cannot be satisfied by one unconditional constant, so the membership (and the management account's identity relative to the presented account) has to become state these checks can establish or observe, not a compile-time choice; the fms helper must stop substituting the caller when Organizations holds no organization, because that silently produces a message AWS cannot produce.

Traces: fms.get-admin-scope-malformed-account-rejected and fms.list-admin-accounts-for-organization-unconfigured-not-found, both verdict 'error', both raising botocore.errorfactory.AWSOrganizationsNotInUseException from the DescribeOrganization call. Code citations: the organizations crate src/service.rs EmulatedService::new (lines 57-77, the deliberate no-seed, and its doc naming create_organization as the one writer); the fms crate src/state/management_account.rs organization_management_account (lines 60-70, the unwrap_or_else fallback to ::engine::emulator_account_id()), not_management_account (lines 81-92, the message template) and management_account_only_refusal (lines 101-107); the fms crate src/ops/get_admin_scope.rs lines 214-221 (where that refusal is raised).

## Steps to Reproduce
1. Boot the emulator fresh (no prior requests, no organizations CreateOrganization).
2. Call fms GetAdminScope with AdminAccount="not-an-account-id": it is refused ValidationException with the pattern message, as recorded (this part matches).
3. Call organizations DescribeOrganization with no input.
   Expected: HTTP 200 with Organization.MasterAccountId set to the organization's management account (an account id other than the caller's in the recorded environment).
   Actual: HTTP 404 AWSOrganizationsNotInUseException "Your account isn't a member of an organization. To make this request, you must use the credentials of an account that belongs to an organization."
4. Replay fms.get-admin-scope-malformed-account-rejected and fms.list-admin-accounts-for-organization-unconfigured-not-found: both abort at step 3's refusal, so fms GetAdminScope{AdminAccount="999999999999"} and fms ListAdminAccountsForOrganization are never called and their InvalidOperationException (naming the caller and the organization's management account) is never checked.
5. Call fms ListAdminAccountsForOrganization directly on the same fresh emulator: it answers InvalidOperationException whose message names the caller's own account as the Organization management account, because the cross-service read fell back to the presented account.
