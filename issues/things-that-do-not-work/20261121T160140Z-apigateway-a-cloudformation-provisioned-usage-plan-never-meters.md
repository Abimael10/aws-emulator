# apigateway: a CloudFormation-provisioned usage plan never meters a keyed invoke — the DAY-quota check reaches no verdict, so neither the three admissions nor the 429 "Limit Exceeded" refusal is ever served

> _Note: this issue was identified against the code base at commit `82319d48a946e26ab7d96dc7ca606472e537bd51`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
CreateUsagePlan

## Description
One net-new root cause. The suite marks this check neither ALREADY FILED nor OWNED, and no open issue carries its replay key. The nearest open neighbours are about other causes and do not cover it: 20261113T080205Z-apigateway-3-net-new-causes-in-usage-plan.md covers the CONTROL-plane usage surface only (GetUsage's 90-day and unknown-key refusal wording, and an UpdateUsagePlan quota repoint discarding a recorded remaining), and 20261109T152222Z-apigateway-stage-throttling-is-never-enforced-deleted-api.md covers the stage/method-settings RATE throttle never shedding a request (Cause 1) and anonymous requests to an authorizationType=NONE method being refused 403 by an execute-api IAM denial (Cause 7) — a neighbouring data-plane family, but neither is usage-plan QUOTA admission through an API key.

Cause 1 of 1: a usage plan with Quota{Limit:3, Period:DAY} bound to a deployed stage and an API key never meters a keyed request — the check makes no progress and is cut off by its time budget, so neither the admitted requests nor the quota refusal is ever observed.

AWS: Smithy models the configuration — QuotaSettings.limit is "The target maximum number of requests that can be made in a given time period", QuotaSettings.period is DAY|WEEK|MONTH, ApiStage binds the plan to {apiId, stage}, and GetUsage (GET /usageplans/{usagePlanId}/usage, startDate/endDate @required httpQuery) reports `values` keyed by API key id as daily [used, remaining] pairs and echoes usagePlanId/startDate/endDate. The data plane itself is not modelled (recorded behavior only): a method with ApiKeyRequired=true on a deployed stage admits a request carrying `x-api-key: <the key's value>` when the key is enabled and associated with a usage plan covering that stage — HTTP 200 and the integration's body — and once the plan's quota for the current period is consumed it refuses the next keyed request with HTTP 429 and the JSON body {"message": "Limit Exceeded"}. That sentence is entirely fixed text and is what distinguishes a quota exhaustion from a rate/burst throttle, which answers the same 429 status with {"message": "Too Many Requests"}. With Limit=3/DAY, exactly three keyed requests are admitted and the fourth is refused 429 "Limit Exceeded".

Emulator: the check reaches no assertion at all — it is cut off with `Check timed out after 60.0s`. None of its graded outcomes was produced: no 200 for an admitted keyed request, no 429, no "Limit Exceeded" body, no GetUsage read-back. The check's assertions are written to fire immediately on any status other than 200/403 (and immediately on a 200 once the quota is spent, which is the "quota not enforced" verdict), so no assertion firing means the keyed GET through the deployed stage kept answering 403 and the loops span 300 s and 120 s respectively — far past the budget. Hypothesis: the keyed request is never admitted, i.e. the API-key/usage-plan-key association the stack creates never reaches the execute-api invoke path (the x-api-key is not resolved to an enabled key associated with a plan covering <apiId,stage>), so quota accounting is never even reached; the other blocking wait in the check is the stack_create_complete waiter, which is the alternative stall point if the AWS::ApiGateway::ApiKey/UsagePlan/UsagePlanKey stack never reaches CREATE_COMPLETE.

Why: a client that provisions metering through CloudFormation gets an endpoint that cannot be used with its key at all and a quota that is never demonstrated — either every keyed call is refused 403 (a working integration appears broken) or, if a call is admitted, nothing caps it. Both failure modes are severe: the first makes API-key-protected APIs unusable, the second makes the plan's Limit inert and over-permissive, and the quota-specific "Limit Exceeded" wording a client branches on to tell exhaustion from throttling is never emitted.

Fix: the execute-api invoke path's API-key admission and usage-plan quota enforcement — resolution of the `x-api-key` header to an enabled API key, the key→usage-plan association for the invoked <apiId,stage>, the per-period counter that admits up to QuotaSettings.limit requests and then serves the LIMIT_EXCEEDED gateway response (429, body {"message": "Limit Exceeded"}, distinct from the THROTTLED response's "Too Many Requests"), and the usage records GetUsage reports. The CloudFormation handlers for AWS::ApiGateway::ApiKey / UsagePlan / UsagePlanKey belong in the same fix only insofar as the association they create must be the one the data plane reads, and the stack must reach CREATE_COMPLETE in bounded time.

Traces: apigateway.deploy-usage-plan-cfn-quota-enforced (mismatch, timed out after 60.0s).
