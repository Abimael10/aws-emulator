# appsync: the GraphQL data plane never answers an introspection query (__schema/__type unresolved), so introspectionConfig ENABLED/DISABLED has no observable effect

> _Note: this issue was identified against the code base at commit `d825fc3fd2c0acc0430183819db932c8e4399031`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
GraphQL data-plane POST /graphql (introspection) / UpdateGraphqlApi introspectionConfig

## Description
One net-new cause in the emulator's AppSync GraphQL data plane, reached through GraphqlApi$uris.GRAPHQL on an API_KEY API whose schema reached SUCCESS and which has a UNIT resolver over a NONE data source. Related open issues describe neighbouring data-plane defects but do NOT carry this check's replay key: 20261116T072149Z-appsync-8-net-new-causes-graphql-data-plane.md (its Cause 3 is __typename resolving to null, its Cause 7 is validation not running) and 20261114T140817Z-appsync-7-net-new-causes-the-graphql-data.md (VTL execution gaps). Neither covers introspection or introspectionConfig.

Cause 1 of 1: a standard introspection document is never answered successfully, and because introspection never works in the ENABLED (default) state, the DISABLED state is indistinguishable from it.
AWS: introspection is part of the GraphQL contract and AppSync serves it on the data plane by default — Smithy GraphqlApi$introspectionConfig: "Sets the value of the GraphQL API to enable (ENABLED) or disable (DISABLED) introspection. If no value is provided, the introspection configuration will be set to ENABLED by default. This field will produce an error if the operation attempts to use the introspection feature while this field is disabled." (enum GraphQLApiIntrospectionConfig = ENABLED | DISABLED). So for the SDL `schema { query: Query } type Query { ping: String widget: Widget } type Widget { id: ID! name: String }`, the document `query { __schema { queryType { name } } __type(name: "Widget") { name kind fields { name type { kind name ofType { kind name } } } } }` is answered HTTP 200 with NO errors array and data describing the compiled schema: data.__schema.queryType.name == the SDL's query root type name ("Query" here), data.__type.name == the requested type name and data.__type.kind == "OBJECT", data.__type.fields naming exactly the type's declared fields, with a non-null declaration introspecting as kind "NON_NULL" wrapping ofType.name == the inner scalar (`id: ID!` -> NON_NULL/ID) and a plain scalar as kind "SCALAR" with that scalar's name (`name: String` -> SCALAR/String). Recorded behavior for the DISABLED state (the model does not state the shape, only that it "will produce an error"): AppSync does NOT refuse the request; it strips the introspection fields out of the compiled schema, so the SAME document then fails ordinary GraphQL validation inside a 200 envelope — status 200, the data key PRESENT and null, nothing resolved, and one error per selected introspection subfield of the form "Validation error of type FieldUndefined: Field '<selected field>' in type '<meta type>' is undefined @ '<response path>'" (e.g. Field 'queryType' in type '__Schema' is undefined @ '__schema/queryType'); the fixed text is the rule phrase "Validation error of type FieldUndefined: Field ... in type ... is undefined", while the field name, the meta type name ('__Schema', '__Type') and the path come from the request document. Each such entry has no 'path' member and no 'errorType' (a validation error is not a typed AppSync data-plane error); the status is never 400 and the word "introspection" never appears in the response. The flag removes introspection ONLY: ordinary fields keep executing error-free, and __typename (a spec meta-field, not introspection) still resolves to the enclosing type's name. Re-enabling introspectionConfig makes the identical document resolve again.
Emulator: the introspection document is never answered with a successful envelope. The check polled `lambda res: res[0] == 200 and isinstance(res[1].get('data'), dict) and not res[1].get('errors')` against the published GraphQL endpoint and the suite killed it — "Check timed out after 60.0s" — i.e. the emulator never produced a 200 with a dict data and no errors for `{ __schema { queryType { name } } __type(name: "...") { ... } }`. Hypothesis: the executor has no introspection support at all, so __schema/__type are shaped into the response but never resolved (the same gap that leaves __typename null per the related issue's Cause 3), leaving data null / an error envelope forever; consequently the DISABLED leg, its FieldUndefined validation errors, and the re-enable restore leg are all unreachable too.
Why: introspection is how every GraphQL client, codegen tool and IDE (Amplify, Apollo, graphql-codegen, the AppSync console query editor) discovers the schema; against this emulator schema discovery simply hangs or returns nothing, so no client can generate types or validate documents. And because introspectionConfig has no observable effect, a client cannot verify that disabling introspection actually hides the schema — a security control silently does not exist.
Fix: introspection support in the GraphQL data-plane executor: build the introspection meta-types (__Schema, __Type, __Field, __TypeKind with NON_NULL/LIST wrappers) from the API's compiled schema and resolve the __schema and __type(name:) root meta-fields independently of resolvers; then gate those meta-types off the compiled schema when the API's introspectionConfig is DISABLED so the same document falls out as FieldUndefined validation errors in a 200 envelope, while leaving __typename and ordinary field execution untouched.
Traces: appsync.graphql-introspection-query-and-disabled-config.

## Evidence
Check appsync.graphql-introspection-query-and-disabled-config.
Expected (step 1, introspection ENABLED by default): POST {"query": "query { __schema { queryType { name } } __type(name: \"Widget\") { name kind fields { name type { kind name ofType { kind name } } } } }"} with header x-api-key to GraphqlApi$uris.GRAPHQL -> HTTP 200, no 'errors' key, data.__schema.queryType.name == "Query", data.__type == an OBJECT named "Widget" whose fields are exactly {id, name}, with id typed kind NON_NULL / ofType.name ID and name typed kind SCALAR / name String.
Actual: no such response is ever produced; the check's bounded poll for "the introspection query to succeed on the live endpoint" never satisfied `status == 200 and isinstance(data, dict) and not errors`, and the suite reported "Error: Check timed out after 60.0s".
Unreached as a consequence (same check, later steps): after UpdateGraphqlApi(introspectionConfig="DISABLED") the identical document must come back status 200 with the data key present and null and one error per selected introspection subfield, each message containing "Validation error of type FieldUndefined" and naming '__Schema' / '__Type' and 'queryType', each with no 'path' and no 'errorType'; `query { ping }` must still return data.ping == the resolver's value with no errors; `query { __typename ping }` must still return data.__typename == "Query" with no errors; and UpdateGraphqlApi(introspectionConfig="ENABLED") must restore the identical introspection result.
