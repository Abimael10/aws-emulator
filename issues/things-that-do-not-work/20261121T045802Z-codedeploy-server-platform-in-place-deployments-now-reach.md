# CodeDeploy Server-platform in-place deployments now reach Succeeded without doing any work on the target: no files installed, no AppSpec hooks executed, empty per-target lifecycleEvents, and no minimumHealthyHosts-bounded rolling schedule (3 causes, 9 checks)

> _Note: this issue was identified against the code base at commit `8921279fd8ae15999b154e4a4e4d9ed144931048`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
CreateDeployment

## Description
Nine Server (EC2/on-premises) compute-platform behavioral checks now get PAST the target-resolution gap that open issue 20261120T163729Z-codedeploy-server-platform-deployments-never-resolve-ec2tagfilters-to.md describes (deployments no longer end Failed/NO_INSTANCES, and the instance target id is reported), and fail further in at three distinct, later points. Neither that issue nor open issue 20261120T191449Z-codedeploy-in-place-deployment-never-resolves-instance-targets.md carries these failures or their replay keys: both describe the deployment never resolving a target at all, whereas every failure below happens on a deployment the emulator reports as having run. Related open issues 20261107T094623Z-codedeploy-no-server-platform-ec2-agent-deployment-check.md, 20261114T202732Z-codedeploy-the-alarm-gating-check-on-the-server.md, 20261115T031454Z-codedeploy-the-server-platform-host-readiness-gate-still.md, 20261115T085328Z-codedeploy-the-server-platform-appspec-hook-check-cannot.md and 20261116T030341Z-codedeploy-the-minimumhealthyhosts-concurrency-check-still-cannot-start.md all describe an EARLIER, upstream symptom (an EC2 instance never becoming an Online SSM managed node / the agent unit never active) that these replays no longer hit: SSM Run Command now succeeds on the host, which is exactly how the evidence below was read off the instance.

=== Cause 1 of 3: an in-place deployment that reports success never installs the revision's files nor executes any AppSpec hook on the target instance. ===
Failing check ids for this cause: codedeploy.ec2-agent-deployment-runs-appspec-hook-on-instance, codedeploy.agent-hands-the-hook-the-real-deployment-identifiers, codedeploy.auto-rollback-on-deployment-failure-reinstalls-the-prior-artifact, codedeploy.file-exists-behavior-disallow-blocks-foreign-file-and-overwrite-replaces-it, codedeploy.lifecycle-event-order-and-applicationstop-only-on-redeploy.
AWS: Smithy (codedeploy, CodeDeploy_20141006) models the inputs that drive this — CreateDeployment takes revision (RevisionLocation, revisionType S3 with s3Location{bucket,key,bundleType}) and fileExistsBehavior (DeploymentInfo.fileExistsBehavior enum DISALLOW|OVERWRITE|RETAIN, documented as "how CodeDeploy handles files that already exist in a deployment target location but weren't part of the previous successful deployment": DISALLOW = "The deployment fails" and is the default, OVERWRITE = "The version of the file from the application revision currently being deployed replaces the version already on the instance", RETAIN = "The version of the file already on the instance is kept"). The Smithy docs for DeploymentInfo.ignoreApplicationStopFailures state the contract directly: "During a deployment, the CodeDeploy agent runs the scripts specified for ApplicationStop, BeforeBlockTraffic, and AfterBlockTraffic in the AppSpec file from the previous successful deployment. (All other scripts are run from the AppSpec file in the current deployment.)" — i.e. an in-place deployment reaching Succeeded means the agent downloaded the bundle, copied every path in the AppSpec files section to its destination on the instance, and ran each declared hook script with the lifecycle environment (DEPLOYMENT_ID, APPLICATION_NAME, DEPLOYMENT_GROUP_NAME, DEPLOYMENT_GROUP_ID, LIFECYCLE_EVENT) exported, in the documented in-place order ApplicationStop, DownloadBundle, BeforeInstall, Install, AfterInstall, ApplicationStart, ValidateService — with ApplicationStop skipped on a first deployment, because it is taken from the previous successful revision's AppSpec which does not yet exist on the host. Per LifecycleEvent.lifecycleEventName the hook names are exactly those strings. Recorded behavior only for the on-host filesystem effects: the recordings read the installed path and the hook-written marker back off the instance with SSM Run Command after the deployment reports Succeeded, and they are present.
Emulator: the deployment settles to Succeeded, but nothing exists on the instance. Reading the installed/declared paths back with SSM Run Command returns a shell failure or an empty file: `cat /opt/sim2real/sentinel` ends 'Failed' with stdout 'cat: /opt/sim2real/sentinel: No such file or directory' (the file an AfterInstall hook script must write); `cat /opt/sim2real-cdenv/payload.txt` likewise 'No such file or directory' (the file the hook writes from its own $DEPLOYMENT_ID/$APPLICATION_NAME/$DEPLOYMENT_GROUP_NAME environment); `/opt/sim2real/payload.txt` reads '' instead of the revision's content after a revision installed successfully; `/opt/sim2real/app.txt` reads '' instead of the content the AppSpec files section declares. The hook-order check finds the ordered list of hooks that recorded their own $LIFECYCLE_EVENT on the host to be [] where AWS yields ['BeforeInstall','AfterInstall','ApplicationStart','ValidateService'] for a first deployment of a revision declaring those four scriptable hooks. The emulator is therefore reporting a successful install and a successful hook run it never performed; because the instance state is never written, fileExistsBehavior (DISALLOW must fail the deployment on a foreign file at a declared destination, OVERWRITE must replace it) and auto-rollback's reinstall of the previous revision's artifact are equally unobservable. The path names, marker strings and instance ids above are per-run values, not part of the requirement.
Why: a client cannot deploy anything. Every CI/CD pipeline that gates on CodeDeploy reporting Succeeded concludes its artifact is live on the fleet when no byte of it was written and no hook ran; rollback, validation hooks and fileExistsBehavior conflict handling are all silently no-ops while reporting success — the worst failure mode, because a green deployment is indistinguishable from a real one.
Fix: the Server-platform deployment execution path's agent-side revision application — the component that, per resolved instanceTarget, fetches the revision bundle, parses its appspec.yml, copies the files section's sources to their destinations honouring fileExistsBehavior, and runs each hooks entry's script on the instance with the lifecycle environment exported and in the documented in-place order (ApplicationStop taken from the previous successful revision and skipped when there is none) — must actually mutate the target instance before the deployment is allowed to report Succeeded, and a deployment whose install or hook step cannot be performed must not report Succeeded.

=== Cause 2 of 3: the per-instance-target lifecycleEvents list is always empty, so no lifecycle event status is ever readable for an in-place deployment. ===
Failing check ids for this cause: codedeploy.hook-failure-skips-later-lifecycle-events-and-fails-the-target, codedeploy.applicationstop-hook-failure-blocks-redeploy-until-ignored, codedeploy.deployment-group-alarm-in-alarm-state-blocks-the-deployment.
AWS: Smithy (codedeploy, CodeDeploy_20141006) — InstanceTarget carries member lifecycleEvents (LifecycleEventList), documented "The lifecycle events of the deployment to this target instance", returned by BatchGetDeploymentTargets (deploymentTargets[].instanceTarget) and by GetDeploymentInstance/BatchGetDeploymentInstances (instanceSummary.lifecycleEvents). Each LifecycleEvent carries lifecycleEventName ("such as ApplicationStop, BeforeInstall, AfterInstall, ApplicationStart, or ValidateService"), status (LifecycleEventStatus: Pending|InProgress|Succeeded|Failed|Skipped|Unknown), startTime, endTime and diagnostics. For an in-place deployment to a resolved host AWS reports one entry per lifecycle event the agent attempted: Succeeded for each event that ran cleanly, Failed for the event whose hook exited non-zero (with diagnostics), and Skipped for every event after it, with the instanceTarget status Failed. Recorded behavior for these checks: after the positive-control deployment reaches Succeeded, every scriptable event of the in-place sequence is present with status 'Succeeded'.
Emulator: the list is empty on every read. Verbatim: "positive control: the 'BeforeInstall' lifecycle event reads None, expected 'Succeeded'; the events the service reported were []"; "the first deployment's Install event reads None; the events recorded for 'i-...' were {}"; "positive control: the AfterInstall event reads None; the events recorded for 'i-...' were {}". The deployment and the instance target exist and report success, but lifecycleEvents is serialized as an empty list rather than the per-event record, so Succeeded/Failed/Skipped per event, hook-failure propagation to the target, ApplicationStop-failure-blocks-redeploy (and its ignoreApplicationStopFailures escape), and alarm gating cannot be read at all. The instance ids are per-run values.
Why: lifecycleEvents is the only API surface on which a client can see WHICH step of a deployment ran or failed. Code that polls BatchGetDeploymentTargets or GetDeploymentInstance to find the failing hook, to decide whether to retry with ignoreApplicationStopFailures, or to surface per-step progress in a dashboard, reads an empty list and cannot distinguish "nothing ran" from "everything succeeded".
Fix: the instance-target state in the Server-platform deployment execution path must record a LifecycleEvent per attempted event (name, status, startTime, endTime, diagnostics on failure) as the target advances, and the BatchGetDeploymentTargets / GetDeploymentInstance / BatchGetDeploymentInstances serializers must emit it on instanceTarget.lifecycleEvents and instanceSummary.lifecycleEvents, including Failed with diagnostics for the event whose script failed and Skipped for every later event.

=== Cause 3 of 3: the deployment's elapsed time ignores hook execution and the deployment config's minimumHealthyHosts bound, so a rolling deployment completes faster than its hooks could possibly run. ===
Failing check ids for this cause: codedeploy.minimum-healthy-hosts-bounds-observed-concurrent-unavailability.
AWS: Smithy (codedeploy, CodeDeploy_20141006) — CreateDeploymentConfig accepts minimumHealthyHosts (MinimumHealthyHosts{type: HOST_COUNT|FLEET_PERCENT, value}); its documentation states the scheduling rule: "In an example of nine instances, if a HOST_COUNT of six is specified, deploy to up to three instances at a time" — i.e. with h resolved hosts and HOST_COUNT value n, at most h-n hosts may be out of service simultaneously. DeploymentInfo carries createTime, startTime and completeTime and deploymentOverview. Consequently a deployment over h hosts whose BeforeInstall hook blocks for t seconds cannot complete in less than ceil(h/(h-n))*t by the service's own createTime/completeTime, while CodeDeployDefault.AllAtOnce bounds nothing and completes in about t.
Emulator: the bounded deployment completes essentially instantly and in no more time than the unbounded one. Verbatim: "subject leg: the bounded deployment took 6.2s by the service's own createTime/completeTime; deploying 2 hosts at most 1 at a time, each sleeping 45s in BeforeInstall, cannot finish in less than 50.0s. The control leg took 3.2s." Because the hook is never executed on the host (Cause 1) the deployment's duration is unrelated to the work the revision declares, and because the targets are advanced together rather than in waves sized by the deployment config, the HOST_COUNT bound has no effect on either the observed concurrency or the elapsed time. The specific second counts (6.2s, 3.2s) and the 45s hook sleep are per-run/per-revision values; the requirement is the inequality between the bound the config declares, the work the revision declares and completeTime-createTime.
Why: a client cannot test or rely on rolling deployments. A custom deployment config intended to keep part of the fleet in service is accepted and echoed back but changes nothing observable, so safe-rollout logic, canary dwell windows and anything reading deploymentOverview's InProgress bucket or completeTime-createTime to decide a deployment is actually progressing get an answer that is indistinguishable from an unbounded one.
Fix: the Server-platform rolling scheduler in the deployment execution path must advance resolved instanceTargets in waves bounded by the group's deployment config (at most resolved-hosts minus minimumHealthyHosts.value InProgress at once for HOST_COUNT, the equivalent fraction for FLEET_PERCENT, unbounded for CodeDeployDefault.AllAtOnce), each wave not completing until that target's hooks have actually been executed (Cause 1), with DeploymentInfo.createTime/startTime/completeTime and deploymentOverview reflecting that progression.

Traces: the nine failing check ids listed under the three causes above; each is a distinct example, and each cause must be closed before this issue is submitted.

## Steps to Reproduce
1. 2. Create a VPC/subnet and an instance profile allowing SSM + S3 read; ec2:RunInstances one t3.micro AL2023 instance with TagSpecifications Tags=[{Key:'sim2real-codedeploy-target', Value:'<unique>'}]; wait until it is an Online SSM managed node.
3. codedeploy:CreateApplication(computePlatform='Server'); codedeploy:CreateDeploymentGroup with deploymentStyle={IN_PLACE, WITHOUT_TRAFFIC_CONTROL}, deploymentConfigName='CodeDeployDefault.AllAtOnce' and ec2TagFilters=[{Key:'sim2real-codedeploy-target', Value:'<unique>', Type:'KEY_AND_VALUE'}].
4. codedeploy:CreateDeployment with revision {revisionType:'S3', s3Location:{bucket, key:'revision.zip', bundleType:'zip'}} and fileExistsBehavior='OVERWRITE'; poll codedeploy:GetDeployment until terminal. It reports 'Succeeded'.

7. Cause 3: launch a SECOND tagged instance; codedeploy:CreateDeploymentConfig(computePlatform='Server', minimumHealthyHosts={type:'HOST_COUNT', value:1}); create two deployment groups over the same ec2TagFilters, one with 'CodeDeployDefault.AllAtOnce' and one with the custom config; deploy a revision whose BeforeInstall hook sleeps 45s to each, and compare GetDeployment's completeTime - createTime.
