# SearchListings announces listing logo and reviews addresses on an authority the emulator is not reached on

> _Note: this issue was identified against the code base at commit `eee4f68c68307505bae8a02f2092b98d7bf30fee`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
SearchListings

## Description
This issue bundles 4 causes, all in marketplace-discovery, all on SearchListings, all the SAME defect in the two FETCHABLE members of the ListingSummary projection (logoThumbnailUrl and reviewSummary.reviewSourceSummaries[].sourceUrl): the emulator composes both addresses on an authority that is NOT the one the answering request reached it on, so every URL a search page hands a client is an address nothing answers at. Each cause is one replay cluster with its own fixture/step binding and each must be re-replayed before this issue is closed: Cause 1 = marketplace-discovery-search-facets-refine-search#task#3, Cause 2 = marketplace-discovery-search-listings-and-drill-into-listing#task#1, Cause 3 = marketplace-discovery-search-listings-pagination#task#1, Cause 4 = marketplace-discovery-search-listings-pagination#task#2. In all four the status is right (200), the summary count and totalResults are right, and the path and id in the announced URLs are the emulator's own and correct; only the authority the URL is published on is wrong.

NOT CLAIMED anywhere in this issue, because they are per-environment or per-run values: the recorded marketplace media-CDN host and path literals, the recorded prodview/listing/review-list ids, the emulator's own media ids, and $.nextToken (it appears in all four clusters' diverging-key sets; its recorded values are '<shaped-not-asserted>', 'opaque-continuation-token-placeholder-000' and one recording's long AWS blob, i.e. continuation-token bytes, and the served token is opaque and inside NextToken's @pattern ^[a-zA-Z0-9+/=]+$ / @length(0..8192) — a token's literal bytes are not a requirement). The requirement claimed is only that an address this service publishes for a client to dereference is published on the authority and scheme the answering request arrived on, which is the address the emulator itself serves that resource at.

RELATED, NOT COVERING: (a) open issue 20261119T070657Z-marketplace-discovery-listfulfillmentoptions-announces-a-saas-fulfillmenturl-on-an-address.md is the SAME root cause (announced_page_base) on ListFulfillmentOptions$fulfillmentUrl and owns that cluster only — the four SearchListings clusters here report owned_by EMPTY; (b) open issue 20261119T093324Z-marketplace-discovery-searchlistings-serves-a-placeholder-example-com-logo-host.md describes these same four clusters at an earlier commit, when the served logo host was https://example.com/logos/<slug>.png and sourceUrl was one shared constant — that symptom is gone (the emulator now mints per-record addresses under its own /_aws/ planes), its Issue-Key is written against $.nextToken, and the replay reports owned_by EMPTY for all four clusters, so none of them is gated by it; (c) open issue 20261109T122558Z-marketplace-discovery-getlisting-and-getproduct-detail-responses-restate-a-seeded.md covers detail-read content, not the announced authority.

=== Cause 1 of 4: a facet-refined SearchListings page publishes ten logo addresses and four reviews addresses on an authority the request did not reach ===
AWS: Smithy (services/service-com-amazonaws-marketplacediscovery-awsmarketplacediscovery/smithy-model/com-amazonaws-marketplacediscovery-awsmarketplacediscovery.json) SearchListings POST /2026-02-05/searchListings, success 200, output {totalResults @required, listingSummaries ListingSummaryList @required, nextToken}. ListingSummary$logoThumbnailUrl is URL @required @length(1..2048) @pattern ^https?://.*$, documented "The URL of the logo thumbnail image for the listing"; ReviewSourceSummary$sourceUrl is URL, OPTIONAL, same constraints, documented "The URL where the reviews can be accessed at the source". Both are addresses a client FETCHES rather than text it displays, so the requirement is that the published address dereferences to that listing's logo image / that listing's reviews page. The model fixes no host and AWS serves these off the marketplace's own media and reviews hosts, so for the host itself this is recorded behavior only: the recording shows one distinct media-CDN path per listing and a per-listing reviews deep link. The emulator cannot be on those hosts, and its own design states the rule it must follow instead: src/state/listing_logo.rs — "what it publishes is an address of its OWN: the endpoint the request being answered reached this emulator at ... A URL published on any other host is one a client can render but never dereference".
Emulator: 200 with the right ten summaries, but every logoThumbnailUrl is of the form https://<authority>/_aws/marketplace-discovery-listing-media/<mediaId>/logo.png where <authority> is NOT the authority the replayed request reached the emulator on, and the four summaries whose review record keeps a reviews page publish reviewSourceSummaries[0].sourceUrl the same way (https://<same drifting authority>/_aws/marketplace-discovery-listing-reviews/reviews-list/<reviewsListId>). The replay checker classifies each of these members `resource_not_identified`: the published address identifies no resource. In this replay the single booted emulator's data listener is the one that accepted the request, yet the announced authority is a different loopback port — and it is a DIFFERENT wrong port in each of the four clusters, so the drift is per response rather than a single static misconfiguration.
Why: a client rendering a result page dereferences logoThumbnailUrl for every tile and turns sourceUrl into the "read the reviews" link. Against AWS both resolve; against the emulator both address an authority it is not serving, so every tile image and every reviews link fails with a connection error that reads as a client or network fault rather than as emulator fidelity — even though the emulator DOES serve both resources at its real front door (state/listing_logo.rs logo_route + listing_logo_image, state/listing_reviews.rs reviews_page_route + listing_reviews_page). The round trip is unreachable purely because of what the API announced.
Fix: the announced-address resolution the SearchListings summary projection uses — state::saas_fulfillment::announced_page_base (shared by all three published planes) and the endpoint/authority ordering it consults in the shared data-plane addressing module — must yield the authority and scheme the answering request actually arrived on, which state.rs listing_summary() then stamps into logoThumbnailUrl via LogoMedia::announced and into sourceUrl via ReviewRecord::announced. Not the handler's serializer and not the seeded catalog: the path, the media id and the reviews-list id are already correct.
Traces: marketplace-discovery-search-facets-refine-search#task#3 (SearchListings, expected 200 / got 200; 15 diverging keys — logoThumbnailUrl on listingSummaries[0..9], reviewSummary.reviewSourceSummaries[0].sourceUrl on listingSummaries[1], [4], [6], [8], plus $.nextToken, which is not claimed).
