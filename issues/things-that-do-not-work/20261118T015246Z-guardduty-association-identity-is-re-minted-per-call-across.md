# Association identity is re-minted per call across Create, Get and List for custom detection rule associations

> _Note: this issue was identified against the code base at commit `86d32c23846cd48a29a50565dea948b0a247c0e9`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
CreateCustomDetectionRuleAssociation

## Description
This issue bundles 7 distinct net-new replay clusters. All 7 are in the guardduty service and all are on the IDENTITY members of a custom detection rule association (`associationId`, and the `/association/<id>` suffix of the `arn` derived from it) as served by CreateCustomDetectionRuleAssociation (2 clusters), GetCustomDetectionRuleAssociation (1 cluster) and ListCustomDetectionRuleAssociations (4 clusters). Fix ALL SEVEN causes and re-replay every fixture#step named under Traces (the representative in Issue-Trace/Issue-Step plus the six in trace_ids) before submitting; closing fewer than seven leaves this issue's remaining causes unexercised. None of the 7 is blocked by a stub (stub_path="") and none is marked owned by an open issue (owned_by=[]).

SHARED FAULT: an association does not have ONE identity for its lifetime. The emulator establishes the id at create time by asking the store for a fresh value (`state.mint_id()`), writes it onto the record keyed by (region, ruleId), and then every response that names the association - the create body, the detail read-back and every listing summary - repeats that per-call store value instead of the identity the scenario (and therefore the client) already holds for that association. Every one of the 7 clusters has the CORRECT HTTP status (200 expected, 200 served) and every other member of the payload matches: only the identity member is reported as a value_mismatch by the deterministic comparator.

READ THE REPORT CAREFULLY, THE RENDERING IS MISLEADING. On the two create clusters the report shows the expected side as an UNRESOLVED fixture template - `expected '{{assoc_conflict_id}}' / '{{assoc_lifecycle_id}}'`, got a 32-hex emulator value - i.e. the scenario's bound association identity was never satisfied by the response. On the Get and List clusters expected and actual render with the SAME visible hex digits, because the comparator resolves the selector/binding out of the live response before printing. Hypothesis (not stated by the model or the recording): the printed "expected" on those clusters is the emulator's own served id while the compared expected is the scenario's established identity, which is exactly what the create clusters show unresolved. A fixer should therefore NOT spend the session on a serialization hypothesis (JSON type / case / whitespace) first: the list projection cannot make the id and its own ARN suffix disagree, since services/service-com-amazonaws-guardduty-guarddutyapiservice/src/ops/list_custom_detection_rule_associations.rs builds both members from the one `record.association_id` through `crate::state::custom_detection_rule_association_arn`. Verify any fix BY INVARIANT, never by matching this run's digits: the id a create returns must be the id a Get accepts as its `AssociationId` path label and the id every listing advertises for that association, and must be byte-identical to the trailing `/association/<id>` segment of that same payload's own `arn`.
