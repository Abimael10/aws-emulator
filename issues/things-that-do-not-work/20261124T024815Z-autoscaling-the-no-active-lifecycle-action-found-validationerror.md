# autoscaling: the "No active Lifecycle Action found" ValidationError drops AWS's " and HookName <name>" clause when the instance still has an outstanding action for another hook (2 causes)

> _Note: this issue was identified against the code base at commit `5abb52f22cc381e1bc2d964ae40a640a2e0d853b`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
CompleteLifecycleAction

## Description
Two net-new causes in the autoscaling lifecycle-action refusal plane, one per sibling operation. In both the HTTP status (400) and the Query error code (ValidationError) are CORRECT; what diverges is the fixed text of the message — the emulator serves the SHORT form of AWS's sentence in a case where AWS serves the LONG, hook-qualified form. Each cause must be closed separately; they are bundled only because they are the same template defect in one service's refusal plane.

The rule the recordings establish: AWS's refusal sentence has two forms, selected by whether the addressed INSTANCE still has any outstanding lifecycle action.
  * When the instance has NO outstanding lifecycle action at all (the action was consumed and the instance has left Pending:Wait, or its hook was deleted), AWS answers the short form: 'No active Lifecycle Action found with instance ID <instance-id>'.
  * When the instance IS still held by an outstanding action but NOT one belonging to the LifecycleHookName in the request (that hook's own action was already consumed, or the request names a hook that is not on the group at all), AWS answers the hook-qualified form: 'No active Lifecycle Action found with instance ID <instance-id> and HookName <lifecycle-hook-name>'.
In the hook-qualified sentence 'No active Lifecycle Action found with instance ID ' and ' and HookName ' are FIXED text; the only variable parts are <instance-id>, taken verbatim from the request's InstanceId, and <lifecycle-hook-name>, taken verbatim from the request's LifecycleHookName. The emulator implements only the short form and so loses the whole ' and HookName ...' clause for the second case.

Cause 1 of 2 — CompleteLifecycleAction: completing an action that this hook has already consumed, while another hook still holds the instance, is refused with the short, un-qualified sentence.
AWS: Smithy (com.amazonaws.autoscaling#AutoScaling_2011_01_01): CompleteLifecycleAction.LifecycleHookName (AsciiStringMaxLen255, @length 1..255, required), .AutoScalingGroupName (ResourceName, required) and .LifecycleActionResult (required); .LifecycleActionToken (@length 36..36) and .InstanceId (XmlStringMaxLen19, @length 1..19) are both optional. The operation's only modeled error is ResourceContentionFault (500, awsQueryError ResourceContention), so this refusal is a server-side validation and is recorded behavior only. Recorded behavior: HTTP 400, ErrorResponse.Error.Code 'ValidationError', message 'No active Lifecycle Action found with instance ID <instance-id> and HookName <lifecycle-hook-name>' — the instance is still at Pending:Wait under the second EC2_INSTANCE_LAUNCHING hook, so the instance-level action exists and AWS qualifies the refusal by the hook it could not find an action for.
Emulator: HTTP 400 and Code 'ValidationError' (both right) with the message 'No active Lifecycle Action found with instance ID <instance-id>' — AWS's fixed sentence truncated before ' and HookName ', so the request's LifecycleHookName is never interpolated. The refused call does correctly leave the instance held at Pending:Wait; only the message diverges.
Why: 'ValidationError' is the single Query code behind every semantic refusal this operation raises, so the MESSAGE is the discriminator a client branches on. A caller, a recorded-golden comparison or a lifecycle-hook driver that matches AWS's hook-qualified sentence (equality, or a match anchored on 'and HookName <hook>') cannot tell "this hook's action is already consumed, the instance is still held by a sibling hook" from "this instance has no outstanding action at all" — two conditions with opposite remediations (wait on / complete the other hook, versus stop driving this instance). It reports an unknown failure instead of a benign, terminal double-complete.
Fix: the CompleteLifecycleAction handler's lifecycle-action lookup/validation, where the no-active-action ValidationError message is composed — select the hook-qualified sentence when the instance has outstanding action(s) but none for the requested LifecycleHookName, interpolating the request's InstanceId and LifecycleHookName, and keep the short sentence only when the instance has no outstanding action at all. Status 400 and code ValidationError stay as they are.
Traces: autoscaling.complete-lifecycle-action-reused-on-a-consumed-action-rejected-and-the-instance-stays-waiting.

Cause 2 of 2 — RecordLifecycleActionHeartbeat: a heartbeat naming a hook that is not on the group, for an instance that IS held at Pending:Wait, is refused with the short, un-qualified sentence.
AWS: Smithy: RecordLifecycleActionHeartbeat.LifecycleHookName (AsciiStringMaxLen255, required) and .AutoScalingGroupName (ResourceName, required) are required, .LifecycleActionToken (@length 36..36) and .InstanceId (XmlStringMaxLen19) optional; the only modeled error is ResourceContentionFault (500), so this too is recorded behavior only. Recorded behavior: HTTP 400, Code 'ValidationError', message 'No active Lifecycle Action found with instance ID <instance-id> and HookName <lifecycle-hook-name>', where the hook name is the nonexistent hook from the request. The instance is genuinely held by a real launching hook at the time of the call, and a heartbeat on the REAL hook is accepted — so the refusal is about the named hook, and AWS names it.
Emulator: HTTP 400 and Code 'ValidationError' (both right) with 'No active Lifecycle Action found with instance ID <instance-id>' — the same truncated sentence, so the unknown hook name the caller actually got wrong never appears in the message.
Why: the one piece of information that makes this refusal actionable — WHICH hook name has no action — is withheld, and a client keyed on AWS's hook-qualified sentence does not recognize the refusal. It also makes a typo'd/stale LifecycleHookName indistinguishable from an action that has simply already been resolved.
Fix: the RecordLifecycleActionHeartbeat handler's lifecycle-action lookup/validation — the same two-form message selection as cause 1, applied to this operation's refusal path; if the two handlers share one message-composition helper, both call sites must still be verified, since the suite exercises them separately.
Traces: autoscaling.complete-lifecycle-action-unknown-hook-rejected (the failing assertion is the RecordLifecycleActionHeartbeat leg).

Related but non-covering open issue: 20261123T122856Z-autoscaling-recordlifecycleactionheartbeat-s-no-active-lifecycle-action-found.md reports the OPPOSITE direction for the OTHER case — an emulator that appended ' and HookName <name>' where AWS's recording shows the short form, for an instance with no outstanding action left (action consumed, or hook deleted). The emulator now serves the short form unconditionally, which is why that case passes and these two fail; neither that issue nor any other open autoscaling refusal issue carries these two checks' replay keys. The correct end state is the conditional two-form message described above, satisfying both that issue's recordings and these two checks — do not re-unconditionalize in either direction.

## Steps to Reproduce
1. Create a launch template and an Auto Scaling group (MinSize=0, MaxSize=1, DesiredCapacity=0) in the shared VPC/subnets.
2. PutLifecycleHook TWICE on that group — hook_a and hook_b — each with LifecycleTransition='autoscaling:EC2_INSTANCE_LAUNCHING', HeartbeatTimeout=3600, DefaultResult='CONTINUE'. Confirm both are listed by DescribeLifecycleHooks.
3. SetDesiredCapacity(DesiredCapacity=1, HonorCooldown=False) and poll DescribeAutoScalingGroups until exactly one instance is in 'Pending:Wait'; note its InstanceId.
4. Cause 1: CompleteLifecycleAction(LifecycleHookName=hook_a, AutoScalingGroupName=<group>, LifecycleActionResult='CONTINUE', InstanceId=<iid>) — it is accepted and the instance stays at Pending:Wait under hook_b. Repeat that exact call and read ErrorResponse.Error.Code and .Message: the code is 'ValidationError' as AWS answers, but the message stops after the instance id instead of continuing ' and HookName <hook_a>'.
5. Cause 2: with the instance still held at Pending:Wait, call RecordLifecycleActionHeartbeat(LifecycleHookName=<a hook name never created on the group>, AutoScalingGroupName=<group>, InstanceId=<iid>) and read ErrorResponse.Error.Message: again the hook-qualified clause is missing. A heartbeat on the REAL hook must still succeed and must not release the instance.
6. Contrast (must keep working): resolve the instance's last outstanding action so it leaves Pending:Wait, then call RecordLifecycleActionHeartbeat again — there AWS's message IS the short form with no ' and HookName' clause.
