# kms ListAWSDefaultServiceQuotas: 52 published quota rows have no citable QuotaCode-to-quota pairing

## Operation
ListAWSDefaultServiceQuotas

## Description
This is the RESIDUAL half of
`issues/things-that-now-work/20261121T022613Z-service-quotas-kms-listawsdefaultservicequotas-default-catalog-omits-55-published-quota.md`,
split out so none of it is recorded as working. That report asked the default-quota
catalog of `ServiceCode` `kms` to publish a row for each of 55 absent `QuotaCode`s; it
STATES the quota behind three of them, and those three are now published
(`L-171660E4` `ListKeyRotations request rate`, `L-FB6513A2` `ListResourceTags request
rate`, `L-0E66C9C0` `On-demand rotations per CMK`). For the other 52 codes nothing
available in this checkout — not the Smithy model, not the report, not AWS's own
published KMS quota documentation, which names each quota but no `QuotaCode` — says
WHICH quota AWS publishes under WHICH of them.

A `QuotaCode` is an opaque AWS-minted identifier: no rule derives it from a quota's
name, so the pairing can only be read off a recorded `ListAWSDefaultServiceQuotas`
response of this service code. Pairing them by guess would publish one quota's name,
value, adjustability, window and usage metric under another quota's code, which is the
defect class the catalog's own rule forbids (`src/state/quota_rows.rs`, module docs) and
that several reports have been filed for ("rows misbound", "rows carry another quota's
metadata"). So these 52 rows are left in the default-quota-set gap rather than published
under a code this catalog would be inventing a binding for.

What is needed to close this: for each of the 52 codes, the quota AWS publishes under it
— its `QuotaName`, `Value`, `Unit`, `Adjustable`, `GlobalQuota`, `Period`, `UsageMetric`
and `Description` — as a recorded `ListAWSDefaultServiceQuotas` response of `kms` states
them. KMS publishes two classes of row and the constructors for both already exist
(`src/state/quota_rows/kms.rs`: `kms_request_rate` for the per-operation request rates,
`quota(...)` for a counted plane), so each newly cited pairing is one line in
`kms_quotas()`.

Beside them, one member of an already published row is unsourced: the recorded entry for
`L-0E66C9C0` is reported with its `Value` truncated, so that row's number is taken from
the on-demand rotation limit the KMS Developer Guide publishes (ten rotations per
customer managed key) and the replay reports it as the row's only divergent member. A
recorded response of `kms` that states this row's `Value` would settle it.

## Evidence
Replay of `service-quotas-catalog-list-aws-default-service-quotas-kms#task#1` against the
emulator built with the three newly published rows: HTTP 200, body-only divergence, the
rows for `L-171660E4` and `L-FB6513A2` no longer reported missing, `L-0E66C9C0` reported
only at `.Value`, and the 52 codes above still reported as
`missing (expected {...}, got None)` — the whole `ServiceQuota` row, not one member.

The emulator's served `kms` catalog after that change (`ListAWSDefaultServiceQuotas`,
`ServiceCode=kms`) is five rows: `L-0E66C9C0`, `L-171660E4`, `L-8A08DAEA`,
`L-FB6513A2`, `L-275D92F3`, each under AWS's own code and self-consistent, pinned by
`tests/all/kms_published_default_rows.rs`.
