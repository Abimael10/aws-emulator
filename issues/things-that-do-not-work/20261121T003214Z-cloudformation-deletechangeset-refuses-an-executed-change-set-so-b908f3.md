# cloudformation: DeleteChangeSet refuses an executed change set, so every second `cdk deploy` of a stack aborts and the stack never leaves its previous state

> _Note: this issue was identified against the code base at commit `4f8289a55da0569c35b4094a258c497c237277f1`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
DeleteChangeSet

## Description
Two net-new causes on the change-set cleanup path that `cdk deploy` walks on every redeploy. Both are grounded in failing behavioral checks of this suite; cause 2 is reported separately because its observable divergence is a stack status, not the refused call.

Cause 1 of 2: DeleteChangeSet on a change set whose execution has already finished (ExecutionStatus EXECUTE_COMPLETE) is refused with HTTP 400 InvalidChangeSetStatus instead of succeeding with an empty 200, so the spent plan is never discarded and any tool that tidies up after a deploy hard-fails.
AWS: Smithy: DeleteChangeSet input ChangeSetName (ChangeSetNameOrId, @required, @length 1..1600) plus optional StackName; output DeleteChangeSetOutput has NO members (an empty 200 body); the operation models exactly one error, InvalidChangeSetStatusException (httpError 400, awsQueryError code InvalidChangeSetStatus), documented as "The specified change set can't be used to update the stack. For example, the change set status might be CREATE_IN_PROGRESS, or the stack status might be UPDATE_IN_PROGRESS." The operation's own documentation states the intent plainly: "Deletes the specified change set. Deleting change sets ensures that no one executes the wrong change set. If the call successfully completes, CloudFormation successfully deleted the change set." Nothing in the model restricts which ExecutionStatus values are deletable (the enum is UNAVAILABLE | AVAILABLE | EXECUTE_IN_PROGRESS | EXECUTE_COMPLETE | EXECUTE_FAILED | OBSOLETE); the modelled refusal is for a change set that is still in flight. Recorded behavior: check cloudformation.delete-executed-changeset-error creates a change set (ChangeSetType CREATE), executes it, waits for the stack, then deletes that change set and expects the delete to be ACCEPTED and the change-set record to be gone.
Emulator: answers HTTP 400 InvalidChangeSetStatus with the message "Cannot delete ChangeSet in execution status EXECUTE_COMPLETE" (botocore raises InvalidChangeSetStatusException). The fixed text is "Cannot delete ChangeSet in execution status " followed by the stored ExecutionStatus value; it is the emulator's own wording, not AWS's, and AWS returns no error at all for this call.
Why: create / execute / delete is the normal change-set lifecycle and is exactly what the CDK deploy wrapper performs — before creating its change set, `cdk deploy` deletes the one the previous deploy left behind. Against the emulator that cleanup call returns a 400 client error, so the CLI prints "Cannot delete ChangeSet in execution status EXECUTE_COMPLETE" and exits 1 BEFORE submitting any change: `cdk deploy` of an already-deployed stack, `cdk destroy` after a protection-flipping deploy, and multi-stack deploys all fail, and the stack is left at its previous status with the new template never applied. A client that classifies InvalidChangeSetStatus as "stack busy, retry later" loops on a request that can never succeed.
Fix: the DeleteChangeSet handler's execution-status gate and the discardability predicate it calls on the stored change set (services/service-com-amazonaws-cloudformation-cloudformation/src/ops/delete_change_set.rs): a change set whose execution has reached a terminal state (EXECUTE_COMPLETE, EXECUTE_FAILED, OBSOLETE, and AVAILABLE/UNAVAILABLE once creation has settled) must be removed from the change-set store and answered 200 with the empty DeleteChangeSetOutput; the modelled InvalidChangeSetStatusException must be kept only for a change set that is still in flight (creation not settled, or EXECUTE_IN_PROGRESS).
Related open issue (does NOT carry these checks' replay keys): 20261120T150300Z-cloudformation-deletechangeset-refuses-an-executed-change-set-so.md reports the same refusal from a wire fixture, and sibling issues exist for other service headings (20261120T150929Z-cloudformation-s3-..., 20261120T162942Z-cloudformation-lambda-..., 20261120T214510Z-cloudformation-ssm-..., 20261120T214334Z-cloudformation-sns-sqs-..., 20261120T214510Z-cloudformation-sqs-ssm-..., 20261120T150929Z-cloudformation-iam-lambda-s3-...). None of them replays the four behavioral checks listed here, so this issue carries them.
Traces: cloudformation.delete-executed-changeset-error (the direct API call: DeleteChangeSet after ExecuteChangeSet); cloudformation.cdk-destroy-refused-while-termination-protection-is-enabled ("the unprotecting deploy exited 1; output tail ... 'Cannot delete ChangeSet in execution status EXECUTE_COMPLETE'"); cloudformation.deploy-cdk-cross-stack-export-ordering-and-in-use-guard ("`cdk deploy <producer>` exited 1, expected 0; output tail ... 'Cannot delete ChangeSet in execution status EXECUTE_COMPLETE'").

Cause 2 of 2: after an update that the resource handler refuses, the stack is still reported CREATE_COMPLETE instead of rolling back to UPDATE_ROLLBACK_COMPLETE, and no UPDATE_FAILED resource event carrying the handler's reason is emitted.
AWS: a stack update whose resource handler returns a failure is rolled back whole — the stack ends UPDATE_ROLLBACK_COMPLETE, the failing resource's event carries ResourceStatusReason of the form 'Resource handler returned message: "<the service's own refusal message> (Service: <service>, Status Code: <code>, Request ID: <uuid>) (SDK Attempt Count: <n>)" (RequestToken: <uuid>, HandlerErrorCode: <code>)', and the resource keeps its pre-update configuration. For the case this check exercises the handler message is Lambda's refusal of a reserved environment-variable key, "Lambda was unable to configure your environment variables because the environment variables you have provided contains reserved keys that are currently not supported for modification. Reserved keys used in this request: AWS_REGION", with Service: Lambda, Status Code: 400 and HandlerErrorCode: InvalidRequest; the uuids and the attempt count are per-run values, the rest is fixed text. Recorded behavior only for the stack-status sequence (CloudFormation does not model event text).
Emulator: the refused update leaves the stack at CREATE_COMPLETE ("stack '<name>' reached 'CREATE_COMPLETE' after the refused update, expected 'UPDATE_ROLLBACK_COMPLETE'") while `cdk deploy` exits non-zero. Hypothesis: the deploy aborts on cause 1's refused DeleteChangeSet before the update is ever submitted, so the update and its rollback are never exercised; this check must be re-replayed after cause 1 is fixed, and if the stack still ends CREATE_COMPLETE with no UPDATE_FAILED event, the update-rollback path (and the handler reason it must record) is a defect in its own right.
Why: a client cannot distinguish "the update was refused and rolled back" from "nothing was attempted": the stack reports the status of its original create, so drift tooling and CI gates that wait for UPDATE_ROLLBACK_COMPLETE hang or conclude the stack is untouched, and the handler reason that tells an operator WHY the update was refused is absent.
Fix: the stack-update state machine and its event writer (the update/rollback transition and the per-resource ResourceStatusReason relayed from the resource handler) in the CloudFormation crate's stack state, plus whatever makes the deploy abort before the update is submitted (cause 1).
Traces: cloudformation.deploy-cdk-update-rejected-by-aws-rolls-back-keeping-prior-config.

## Steps to Reproduce
1. CreateChangeSet with ChangeSetType=CREATE for a new stack whose template declares one resource (an AWS::SNS::Topic in the check); poll DescribeChangeSet until Status=CREATE_COMPLETE / ExecutionStatus=AVAILABLE.
2. ExecuteChangeSet and wait for the stack to reach CREATE_COMPLETE (the change set is now ExecutionStatus=EXECUTE_COMPLETE).
3. DeleteChangeSet(ChangeSetName=<that change set>, StackName=<the stack>). AWS answers HTTP 200 with an empty DeleteChangeSetResult and removes the record; the emulator answers HTTP 400 InvalidChangeSetStatus "Cannot delete ChangeSet in execution status EXECUTE_COMPLETE".
4. CDK path: `cdk deploy <stack>` a second time (or `cdk destroy` after a deploy that flips termination protection). CDK first deletes the change set left by the previous deploy, so the CLI exits 1 printing "Cannot delete ChangeSet in execution status EXECUTE_COMPLETE" and the new template is never applied; DescribeStacks still reports the stack's previous status.
5. Re-replay the behavioral checks cloudformation.delete-executed-changeset-error, cloudformation.cdk-destroy-refused-while-termination-protection-is-enabled, cloudformation.deploy-cdk-cross-stack-export-ordering-and-in-use-guard and cloudformation.deploy-cdk-update-rejected-by-aws-rolls-back-keeping-prior-config to confirm both causes are closed.
