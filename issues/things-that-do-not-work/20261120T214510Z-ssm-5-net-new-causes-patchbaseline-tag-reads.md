# ssm: 5 net-new causes — PatchBaseline tag reads refused InvalidResourceId, the patch-group register and baseline-delete refusals are re-worded, ListComplianceItems drops an absent Details, and an SSM-profile EC2 instance never reaches PingStatus=Online

> _Note: this issue was identified against the code base at commit `d480a9c819aca039333e6ccd75fa51254e2ac722`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
ListTagsForResource

## Description
REOPENS 20261109T142303Z-ssm-5-net-new-causes-managed-nodes-never.md: its fix left the call refused.

Five net-new root causes under this heading, each grounded in its own failing checks. Causes 1 and 5 are the two that fixed issue claimed to close (ListTagsForResource refusing a valid resource id, and managed nodes never registering); they are still failing, for a resource type and a path its fix did not reach.

Cause 1 of 5: ListTagsForResource refuses ResourceType=PatchBaseline with InvalidResourceId for a baseline that exists at the endpoint (failing checks: ssm.create-time-tags-list-exactly-across-resource-types, cloudformation__ssm.deploy-ssm-patchbaseline-via-cloudformation-then-lifecycle).
AWS: Smithy (ssm): ListTagsForResource input {ResourceType: ResourceTypeForTagging (required, one of Association | Automation | CloudConnector | Document | MaintenanceWindow | ManagedInstance | OpsItem | OpsMetadata | Parameter | PatchBaseline), ResourceId: ResourceId (required)}; output TagList (len 0..1000); errors InvalidResourceId (httpError 400, documented "The resource ID isn't valid. Verify that you entered the correct ID and try again.", with NO message member) and InvalidResourceType (400). CreatePatchBaseline models Tags, and AddTagsToResource documents the PatchBaseline id form as the minted baseline id ("PatchBaseline: pb-012345abcde"). So for a baseline this endpoint holds, ListTagsForResource answers HTTP 200 with that baseline's own tag set — the create-time tags for a baseline created with Tags, and the empty list for an untagged one. InvalidResourceId is reserved for an id naming no resource at all.
Emulator: HTTP 400 InvalidResourceId (empty message — the empty message is correct, the refusal is not) for the pb-<17 hex> id CreatePatchBaseline just minted, and for a baseline CloudFormation created inside a stack. The refusal is unconditional for this resource type: the tag plane's (ResourceType, ResourceId) resolver matches every ResourceTypeForTagging value EXCEPT PatchBaseline and falls through to `_ => None`, which the handler turns into InvalidResourceId — even though the baseline record already holds a `tags` map (the same map `tagged_resources` projects for the account-wide tag view). AddTagsToResource and RemoveTagsFromResource share that resolver, so a baseline cannot be tagged or untagged through SSM's tag plane either.
Why: a client cannot read, add or remove tags on a patch baseline at all — cost-allocation and ownership tags set at create time are invisible, tag-driven tooling that walks SSM resource types breaks on the baseline, and a CloudFormation stack that declares AWS::SSM::PatchBaseline cannot have its stack tags read back from the resource. The refusal also claims the id is invalid, pointing a caller at its own (correct) id instead of at a missing feature.
Fix: the shared tag-plane resolver that maps (ResourceType, ResourceId) to a resource's tag set — it needs a PatchBaseline arm resolving a baseline id (and its ARN) to the baseline record's tag set, in both the read and the write resolver, so what the create persisted is what the read reports.
Traces: ssm.create-time-tags-list-exactly-across-resource-types; cloudformation__ssm.deploy-ssm-patchbaseline-via-cloudformation-then-lifecycle. Code: services/service-com-amazonaws-ssm-amazonssm/src/state/tagging.rs:335-367 (resource_tags) and :371-407 (resource_tags_mut) — no TAGGING_TYPE_PATCH_BASELINE arm; services/service-com-amazonaws-ssm-amazonssm/src/ops/list_tags_for_resource.rs:183-188 raises the error.

Cause 2 of 5: RegisterPatchBaselineForPatchGroup's AlreadyExistsException message is emulator-authored (failing checks: ssm.patch-baseline-register-conflicting-os-rejected, ssm.register-patch-baseline-duplicate-patch-group-rejected, ssm.register-patch-baseline-duplicate-patchgroup-rejected, ssm.register-patch-baseline-for-patch-group-conflict-rejected).
AWS: Smithy (ssm): RegisterPatchBaselineForPatchGroup errors include AlreadyExistsException (client, httpError 400), documented "Error returned if an attempt is made to register a patch group with a patch baseline that is already registered with a different patch baseline". Registering a second baseline of an operating system a group is already mapped for is refused 400 AlreadyExistsException with the message "Patch Group <patch group> already has a baseline registered for OperatingSystem <OperatingSystem>." — fixed text "Patch Group ", " already has a baseline registered for OperatingSystem " and the trailing "."; the two variable parts are the PatchGroup value from the request and the OperatingSystem of the baseline the group is already registered with, taken from the emulator's state. The existing mapping is unchanged.
Emulator: the code is right (AlreadyExistsException) but the message is "Patch group <patch group> is already registered with patch baseline <baseline id>" — different fixed text ("Patch group " lower-cased, " is already registered with patch baseline ", no trailing period) and it names the already-registered BASELINE ID where AWS names the OPERATING SYSTEM. Nothing in AWS's sentence carries a baseline id.
Why: the registration is per operating system, and AWS's message is what tells a caller WHICH OS slot is occupied — the one fact needed to decide whether to deregister or to register a baseline of another OS. A client that surfaces or matches the service's message shows wording AWS never emits, and remediation keyed on the documented sentence does not fire.
Fix: the register handler's AlreadyExistsException path and the message builder it calls — the refusal value must carry the operating system of the conflicting registration rather than its baseline id, and the sentence must be AWS's. Code: services/service-com-amazonaws-ssm-amazonssm/src/state/patch_groups.rs:62-66 (already_registered_message) and :46-54 (RegistrationRefusal::AlreadyRegistered), used from services/service-com-amazonaws-ssm-amazonssm/src/ops/register_patch_baseline_for_patch_group.rs.
Traces: the four register checks above.

Cause 3 of 5: DeletePatchBaseline's ResourceInUseException message is emulator-authored (failing checks: ssm.delete-patch-baseline-rejects-when-registered-to-group, ssm.patch-baseline-delete-while-registered-rejected).
AWS: Smithy (ssm): DeletePatchBaseline errors include ResourceInUseException (client, httpError 400), documented "Error returned if an attempt is made to delete a patch baseline that is registered for a patch group." The refusal is HTTP 400 ResourceInUseException with the message "PatchBaseline to be deleted is used for Patch Group: <patch group>" — all fixed text up to and including the ": ", followed by the name of the patch group the baseline is registered to, taken from the emulator's state; the baseline and its registration stay intact.
Emulator: the status and code are right but the message is "Patch baseline is registered with patch group <patch group>" — entirely different fixed text; only the patch-group value matches.
Why: a client that matches or displays the service's sentence sees wording AWS never emits; the message is the only part of this refusal that carries information, so re-wording it is the whole of the divergence.
Fix: the DeletePatchBaseline handler's in-use refusal message builder. Code: services/service-com-amazonaws-ssm-amazonssm/src/state/patch_groups.rs:87-89 (baseline_in_use_message). Open issue 20261119T003828Z-ssm-deletepatchbaseline-and-getexecutionpreview-ignore-registered-state.md asked for exactly AWS's sentence back when the refusal was not made at all; the refusal is now made, but with the emulator's own wording, and that issue does not carry these checks' replay keys.
Traces: the two delete checks above.

Cause 4 of 5: ListComplianceItems omits Details entirely for an item that was put without a Details field (failing check: ssm.compliance-item-empty-vs-absent-details-preserved).
AWS: Smithy (ssm): PutComplianceItems input Items -> ComplianceItemEntry{Id, Title, Severity, Status, Details: ComplianceItemDetails (map)}; ListComplianceItems output ComplianceItems -> ComplianceItem{..., Details: ComplianceItemDetails}. Recorded behavior: AWS does not keep "Details: {}" and "no Details" distinct — every listed item carries an explicit Details member holding the empty map, so a client can read item["Details"] unconditionally.
Emulator: for the item put with no Details the listed item has NO Details key at all (the listed item is {ComplianceType, ResourceType, ResourceId, Id, Status, Severity, ExecutionSummary} and nothing else), so a client reading Details raises KeyError on exactly the items AWS normalizes.
Why: a client that indexes Details on every listed item — the safe thing to do against AWS, which always serializes it — crashes on items whose put omitted the field, and code that distinguishes "no details" from "empty details" draws a distinction AWS does not make.
Fix: the ListComplianceItems projection (or the PutComplianceItems store that feeds it) — an absent Details must be normalized to the empty map when the item is stored or when it is projected, so the member is always present.
Traces: ssm.compliance-item-empty-vs-absent-details-preserved.

Cause 5 of 5: an EC2 instance launched with an AmazonSSMManagedInstanceCore instance profile never becomes an Online SSM managed node, so the patch-group state check stops at its setup gate (failing check: ssm.patch-group-state-server-computed-from-baseline).
AWS: Smithy (ssm): DescribeInstanceInformation output InstanceInformationList -> InstanceInformation{InstanceId, PingStatus: enum Online | ConnectionLost | Inactive, PlatformType, ...}; an unregistered instance is simply ABSENT from the list — no error is modeled, which is why this surfaces as a never-satisfied poll rather than a refusal. Such an instance registers with Systems Manager shortly after boot and is then listed with PingStatus "Online", which is the precondition for DescribePatchGroupState counting it into a patch group.
Emulator: DescribeInstanceInformation never lists the launched instance, so PingStatus is never Online and the check fails with "instance <instance id> never reached PingStatus=Online (SSM Agent never registered)". DescribePatchGroupState's node count can therefore never be computed from managed-node inventory at all.
Why: every SSM path that needs a managed node — patch scanning and compliance, Run Command, inventory, maintenance-window targets — is unreachable, and the failure is silent (an empty list, not an error). Fixed issue 20261109T142303Z-ssm-5-net-new-causes-managed-nodes-never.md states this as its Cause 1 and is marked fixed; an EC2 instance launched with the SSM core policy still never registers.
Fix: the SSM managed-node registration path — an instance whose instance profile grants the SSM core policy must be registered and its InstanceInformation/PingStatus maintained, and DescribePatchGroupState must count the registered nodes carrying the group's "Patch Group" tag.
Traces: ssm.patch-group-state-server-computed-from-baseline.
