=== Cause 1 of 1: DeleteDomain classifies an id that was never allocated to any account as resource-not-found instead of an authorizer-configuration failure ===

AWS: recorded behavior only for the error class. Smithy (services/service-com-amazonaws-connecthealth-connecthealth/smithy-model/com-amazonaws-connecthealth-connecthealth.json): `DeleteDomain` is `DELETE /domain/{domainId}`, `@idempotent`, success 200, input member `domainId` -> `DomainId` (@required, @httpLabel, @length 20..25, pattern `^(hai-|dom-)[a-z0-9]+$`), and its ONLY modelled error is `ResourceNotFoundException` (errorKind client, httpError 404, single member `message`, doc "This error is thrown when the requested resource is not found."). `AuthorizerConfigurationException` is declared on no shape of this model, so it is unmodelled and must be hand-built. The recording nonetheless splits the unresolvable-id space in two, and the discriminator is ALLOCATION HISTORY, not liveness:
  * a well-formed `domainId` that was NEVER allocated to any account is refused with error code `AuthorizerConfigurationException` and NO `message` member at all — there is no text template on this path; the ABSENCE of the detail member is the requirement;
  * a `domainId` this account did own and that has since been purged is refused with the modelled `ResourceNotFoundException` at HTTP 404, message "Domain not found: <domainId>" — fixed text "Domain not found: " plus the `domainId` taken verbatim from the request's URI label. The ids appearing in any one recording (`dom-22222222222222222222`, `dom-b2b2b2b2b2b2b2b2b2b2b`, a run-minted `dom-<hex>`) only fill that template and are not part of it.
Hypothesis (as the check's own docstring records it): the front door cannot resolve an ARN for an id with no allocation history anywhere, so the authorizer's own configuration failure surfaces before resource lookup runs.

Emulator: every unresolvable id takes one branch. `src/ops/delete_domain.rs` lines 205-227 — the single `else` arm of `store.held_domain_mut(&region, &input.domain_id)` returns `DeleteDomainErrorModeled::ResourceNotFoundException { message: Some(domain_not_found_message(&input.domain_id)) }`, and the comment at lines 206-217 now states the opposite of the requirement outright: "the id's own allocation history cannot change the answer". The module header (lines 6-8) repeats it: "whatever the id's own history". Replay: `DeleteDomain(domainId="dom-" + "2"*20)` returned error code 'ResourceNotFoundException'; the check asserts `AuthorizerConfigurationException` with a null message and never reached its second assertion, so the message's absence is unverified beyond the code divergence. The positive control in the same check (CreateDomain -> DeleteDomain -> GetDomain 404 "Domain not found: <id>") passes and must stay passing.

Note for the fixer — resolving the conflict in the filed record is part of this work item. Fixed wire issues 20261029T202808Z-connecthealth-response-bodies-diverge-from-the-recorded-wire.md (Cause 2) and 20261123T070631Z-connecthealth-deletedomain-on-an-absent-domain-answers-403.md both assert 404 `ResourceNotFoundException` for their fixture's absent `domainId`, and each fix collapsed the two arms into one, which is what re-broke this check. Satisfying only one corpus at a time is what produces the oscillation. Both must hold simultaneously: an id with allocation history (created and purged, or double-deleted) keeps the modelled 404 and its "Domain not found: <id>" message and must never become a 403/5xx; an id with no allocation history anywhere is refused `AuthorizerConfigurationException` with no detail member. If the wire fixture's id truly has no allocation history in that fixture, its expectation and this check's cannot both be met by a liveness-only test — only by the allocation ledger below, against which that fixture's id must be checked explicitly rather than by re-collapsing the arms.

Why: a client cannot tell "this id was never valid anywhere" — a configuration or authorization fault that must surface — from "this Domain is already gone", which every idempotent-cleanup path treats as a benign no-op. Against this emulator a teardown routine that swallows `ResourceNotFoundException` also silently swallows a typo'd or wrong-account domain id: the deletion reports success and the real resource is never deleted. The detail member matters too: a client reading `Error.Message` on the never-allocated path gets text AWS does not send.

Fix: `DeleteDomain`'s id-resolution path (`services/service-com-amazonaws-connecthealth-connecthealth/src/ops/delete_domain.rs`) plus the allocation ledger it must consult in `src/state.rs` — the store has to remember ids it ever minted for an account, separately from the domains it currently holds, so the handler can distinguish "never allocated" from "allocated and purged". The handler's error channel must be able to express a refusal the model does not name, without routing it through a 5xx (an SDK retries server faults). The shared `domain_not_found_message` constructor in `src/service/error_detail.rs` is correct and stays in use for the allocated-but-purged arm only. Guard the result with both corpora so the next fix cannot collapse the arms again.
