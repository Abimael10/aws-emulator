# ListPurchaseOptions answers an empty page for products its own catalog publishes

> _Note: this issue was identified against the code base at commit `638af639c204b2c523dfe8732e7714679b6875fc`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
ListPurchaseOptions

## Description
This issue bundles 2 causes, both in marketplace-discovery, both on ListPurchaseOptions. Each cause is one replay cluster and each needs its own re-replay to be confirmed closed. Both clusters are reported by the replay with owned_by EMPTY: no filed issue carries their replay key, and no open marketplace-discovery issue mentions ListPurchaseOptions at all (the four open ones cover SearchListings addressing, GetListing/GetProduct seeded content and the ListFulfillmentOptions announced URL).

Cause 1 of 2: a purchase-option list narrowed by product and seller comes back with no rows.
AWS: Smithy ListPurchaseOptions (POST /2026-02-05/listPurchaseOptions, success http 200, @paginated {inputToken nextToken, outputToken nextToken, items purchaseOptions}); input filters PurchaseOptionFilterList @length 1..10 of PurchaseOptionFilter{filterType PurchaseOptionFilterType @required (PRODUCT_ID | SELLER_OF_RECORD_PROFILE_ID | PURCHASE_OPTION_TYPE | VISIBILITY_SCOPE | AVAILABILITY_STATUS), filterValues @required @length 1..10}; the operation doc states "Multiple filters are combined with AND logic. Multiple values within the same filter are combined with OR logic" and that the request must carry at least a PRODUCT_ID or a VISIBILITY_SCOPE filter. Output purchaseOptions is PurchaseOptionSummaryList @length ..100 of PurchaseOptionSummary{purchaseOptionId @required, catalog @required, purchaseOptionType @required (OFFER|OFFERSET), sellerOfRecord SellerInformation @required, associatedEntities @required @length ..100, badges @length ..20, purchaseOptionName, availableFromTime, expirationTime}. The modelled errors are AccessDeniedException 403, ValidationException 400, ThrottlingException 429, InternalServerException 500 - there is no "nothing matched" error, so the requirement is not an error but that a product which HAS a purchase option is reported as a row. For the row's content this is recorded behavior only: the recording answers 200 with one OFFER-type row whose associatedEntities names the filtered product together with the offer that sells it, whose sellerOfRecord and whose product's manufacturer both repeat the seller the request filtered on, whose catalog is the catalog of the request, and which carries the badge the offer has earned (badgeType AUTO_RENEW, displayName 'Auto-renew').
Emulator: 200, but purchaseOptions is an empty list - the replay reports $.purchaseOptions[0] as `missing` (expected a whole OFFER summary, got None). Nothing matched the PRODUCT_ID / SELLER_OF_RECORD_PROFILE_ID filter pair, so the operation reports the filtered product as having no purchase option of any kind, and hands back no nextToken either. Hypothesis: the candidate rows the handler filters are projected only from the seeded offers/offer_sets of this emulator's own synthesized catalog, and the identifiers those rows carry (entry.product_ids from Offer.product_ids, entry.seller_profile_id from Offer.seller_of_record.seller_profile_id) never join with the product and seller identifiers the discovery flow publishes for the record under test, so matches_every_filter rejects every candidate.
Why: this is the one operation a buyer-side client uses to enumerate what it can actually buy for a product. An empty page is not distinguishable from "this product cannot be purchased": a client stops before it ever reaches GetOffer/GetOfferTerms, renders no pricing, and a paginating client sees no nextToken and concludes the catalog is exhausted. It also makes the emulator internally inconsistent - a product it publishes through search and product detail has no purchasable option.
Fix: the ListPurchaseOptions handler's filter join and the purchase-option rows it reads - services/service-com-amazonaws-marketplacediscovery-awsmarketplacediscovery/src/ops/list_purchase_options.rs (matches_every_filter: PRODUCT_ID tested against entry.product_ids, SELLER_OF_RECORD_PROFILE_ID against entry.seller_profile_id) over the candidate list built by the state's purchase_options projection, plus the seeded offers/offer_sets those entries are projected from. A product that the service's own catalog reports must resolve to that product's offer (and offer-set) rows under a PRODUCT_ID filter, and to the same rows when a SELLER_OF_RECORD_PROFILE_ID filter for its seller of record is ANDed on.
Traces: marketplace-discovery-purchase-options-filter-by-product-and-seller#task#1 (representative) and marketplace-discovery-purchase-options-offer-drilldown#task#1, the second member of the same cluster.

Cause 2 of 2: the offer-set drill-down's purchase-option read is empty the same way.
AWS: same operation and same modelled contract as cause 1. Recorded behavior: the drill-down step answers 200 with a one-element purchaseOptions list - an OFFER-type summary whose associatedEntities carries the product (productId, productName, manufacturer{sellerProfileId, displayName}) and the offer (offerId, sellerOfRecord{sellerProfileId, displayName}), with catalog 'AWSMarketplace' and one AUTO_RENEW badge - so the offer set reached in the previous step resolves to the purchase options it bundles.
Emulator: 200 with $.purchaseOptions reported `value_mismatch`: expected a one-element list, got []. The list is present and empty, so the offer set the flow drilled into reports no constituent purchase option.
Why: a client walking offer set -> purchase options -> offer terms has its chain cut at the first hop, and because the response is a well-formed 200 with an empty list the client treats the offer set as empty rather than retrying or surfacing an error.
Fix: same component as cause 1 - the filter join in that handler plus the offer-set side of the state's purchase_options projection (the OFFERSET rows built from offer_sets and the product_ids it accumulates from each member offer), so that an offer set the catalog publishes and the products it bundles both resolve to rows.
Traces: marketplace-discovery-purchase-options-offerset-drilldown#task#2.

Explicitly NOT claimed as requirements here: the recorded literal identifiers and names (purchaseOptionId 'eyemnlrxh5or5zqsm99ih472r', productId 'fc9ecb41-af3a-4e4f-ae3d-36fb2f0405d3', sellerProfileId values, product/seller display names) and any clock-derived availableFromTime/expirationTime - those differ per environment and per run. The defect is that the filtered page carries NO rows at all where the operation must report the product's purchase options.
