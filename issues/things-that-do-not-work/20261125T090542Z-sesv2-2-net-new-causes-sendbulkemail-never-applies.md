# sesv2: 2 net-new causes — SendBulkEmail never applies the missing-DefaultContent TemplateData gate, and TestRenderEmailTemplate's malformed-JSON refusal is re-worded

> _Note: this issue was identified against the code base at commit `87ad42ce826020c3c25d7c413e65e0908692b03d`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
SendBulkEmail

## Description
Two net-new root causes on service token sesv2, both in the email-template rendering path: the gate that refuses a SendBulkEmail whose DefaultContent.Template carries inline TemplateContent but no TemplateData does not exist, and TestRenderEmailTemplate's refusal for syntactically invalid TemplateData carries an emulator-authored message instead of AWS's.

Cause 1 of 2 — SendBulkEmail does not refuse a request whose DefaultContent.Template supplies inline content but no TemplateData (failing check: sesv2.send-bulk-email-missing-default-template-data-rejected).
AWS: Smithy (sesv2, services/service-com-amazonaws-sesv2-simpleemailservice-v2/smithy-model/com-amazonaws-sesv2-simpleemailservice-v2.json): SendBulkEmail is POST /v2/email/outbound-bulk-emails, success 200, input member DefaultContent (BulkEmailContent, required) whose only member is Template (shape Template with TemplateName / TemplateArn / TemplateContent / TemplateData, TemplateData @length min 0 max 262144). Modeled refusals include BadRequestException (errorKind client, httpError 400, doc "The input you provided is invalid.") and MessageRejected (400). Recorded behavior: when DefaultContent.Template specifies TemplateContent (inline Subject/Text) and omits TemplateData, the WHOLE request is refused with HTTP 400, error code BadRequestException and the message "The default template data does not exist" — that message is entirely fixed text, with no variable parts. This request-shape gate is evaluated BEFORE the send-path identity-verification gate: the recording refuses on the missing default template data even though the From identity in the same request is unverified. The positive control in the same check — the identical request WITH TemplateData='{}' — is not refused with BadRequestException at all; it proceeds past this gate and is then refused by whatever send-path gate applies (here the unverified-sender refusal).
Emulator: the gate is absent. The emulator skips straight to the identity-verification gate and answers the unverified-sender refusal for the TemplateData-less request: replay reports expected ('BadRequestException', 'The default template data does not exist'), got ('MessageRejected', 'Email address is not verified. The following identities failed the check in region US-WEST-2: <from-address>'). Both the error code (MessageRejected instead of BadRequestException) and the message diverge.
Why: a client that omits TemplateData on a bulk send is told the problem is an unverified sender identity. It goes off verifying identities that are not the cause, and never discovers the malformed request. Code that branches on BadRequestException (fix the request) versus MessageRejected (fix the account/identity state) takes the wrong branch, and a caller whose sender IS verified gets no diagnosis of the missing template data at all — the request is either accepted or rejected for an unrelated reason.
Fix: the SendBulkEmail handler's request validation and its ordering relative to the send-path verification gate (services/service-com-amazonaws-sesv2-simpleemailservice-v2/src/ops/send_bulk_email.rs, plus the shared send-path validation module it calls): a DefaultContent.Template with inline TemplateContent and no TemplateData must be refused 400 BadRequestException "The default template data does not exist" before identity verification runs, and must NOT be refused when TemplateData is present (even the empty object '{}').
Traces: sesv2.send-bulk-email-missing-default-template-data-rejected.

Cause 2 of 2 — TestRenderEmailTemplate's malformed-JSON refusal uses an emulator-authored message (failing check: sesv2.test-render-email-template-malformed-json-and-missing-attribute-refusals).
AWS: Smithy (same model): TestRenderEmailTemplate is POST /v2/email/templates/{TemplateName}/render, success 200, input TemplateName (httpLabel, required) and TemplateData (required, @length min 0 max 262144); modeled errors BadRequestException (client, 400), NotFoundException (404), TooManyRequestsException (429). The message texts are recorded behavior only. Recorded behavior: against the same stored template, two DISTINCT BadRequestException messages are returned for two distinct inputs — (a) TemplateData that is not syntactically valid JSON is refused 400 BadRequestException with the fixed message "Template rendering data is invalid" (no variable parts), and (b) TemplateData that is valid JSON but omits an attribute the template references is refused 400 BadRequestException with "Attribute '<name>' is not present in the rendering data.", where "Attribute '" and "' is not present in the rendering data." are fixed text and <name> is the referenced template variable missing from the request's rendering data. Neither refusal changes the stored template content, and supplying every referenced attribute renders the template successfully.
Emulator: for the malformed-JSON input it answers the right status and error code but a different message — replay reports expected ('BadRequestException', 'Template rendering data is invalid'), got ('BadRequestException', 'Unable to parse template data (invalid JSON).'). The emulator-authored text "Unable to parse template data (invalid JSON)." is not AWS's wording for this error class. The check stops at this first assertion, so the missing-attribute message, the no-mutation-on-refusal property and the successful multipart render after it were never reached and remain unverified in this run; the fixer should confirm them too when re-replaying.
Why: the message is the only signal distinguishing "your rendering data is not JSON" from "your rendering data is missing an attribute" — both share status 400 and code BadRequestException. A client (or test suite, or log scraper) that matches on AWS's text cannot classify the failure, so a template-authoring tool reports the wrong remediation to its user.
Fix: the message composition in the TestRenderEmailTemplate handler's rendering-data validation (services/service-com-amazonaws-sesv2-simpleemailservice-v2/src/ops/test_render_email_template.rs and the template-rendering helper it uses): emit AWS's fixed text "Template rendering data is invalid" for unparseable TemplateData, and "Attribute '<name>' is not present in the rendering data." with <name> taken from the template's referenced variables for valid JSON missing a referenced attribute.
Traces: sesv2.test-render-email-template-malformed-json-and-missing-attribute-refusals.

Neither cause is carried by an open issue's replay key (the replay report lists both clusters as unowned and not stub-blocked).
