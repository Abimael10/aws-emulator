# ListFoundationModels serves wrong per-model capability members and omits retired cohere model ids

> _Note: this issue was identified against the code base at commit `e9549b1dd16f60dcc5781cad715703321b701533`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
ListFoundationModels

## Description
Cause 1 of 1: GET /foundation-models answers 200, but the per-model capability projection of each FoundationModelSummary diverges from the recorded catalog, and several recorded modelIds have no summary at all (fixture bedrock-catalog-list-foundation-models, step task#1).

AWS: ListFoundationModels is `GET /foundation-models`, 200, output `modelSummaries: FoundationModelSummaryList`, `@readonly`, errors AccessDeniedException(403)/InternalServerException(500)/ThrottlingException(429)/ValidationException(400) (smithy_query(query="operation", operation="ListFoundationModels") on services/service-com-amazonaws-bedrock-amazonbedrockcontrolplaneservice/smithy-model/com-amazonaws-bedrock-amazonbedrockcontrolplaneservice.json). The checked-in `FoundationModelSummary` declares only modelArn, modelId, modelName, providerName, inputModalities, outputModalities, responseStreamingSupported, customizationsSupported, inferenceTypesSupported and modelLifecycle (smithy_query(query="shape", shape="FoundationModelSummary")). Everything else the live service publishes on a summary -- `converse` (maxTokensDefault / maxTokensMaximum / stopSequencesDefault / reasoningSupported / additionalRequestFieldsSchema / userDocumentTypesSupported / userImageTypesSupported / userVideoTypesSupported), `featuresSupported` (promptOptimization, promptCaching, countTokens, provisionedThroughput, intelligentPromptRouting, batchInference.inRegion / .crossRegion), `batchSupported`, `explicitPromptCaching`, `intelligentPromptRouting`, `guardrailsSupported`, `inferenceAPIsSupported`, `latencyOptimizationSupported`, `modelFamily`, `description` and `modelLifecycle.startOfLifeTime` -- is recorded behavior only, so the recorded 200 body is the authority for both WHICH modelIds the account catalog offers and WHAT each summary says about them. The rule is per-model: each published fact belongs to the model row, it is not derivable from the few modeled attributes.

Emulator: 200, and the replay reports member-level divergences spread across the whole catalog (the cluster's divergence_key enumerates hundreds of `$.modelSummaries[modelId=...]` paths). Representative examples from the replay detail: for `openai.gpt-6-astra` the emulator emits no `converse.additionalRequestFieldsSchema` (recorded: a JSON schema string naming a `reasoning_config` enum), no `converse.maxTokensMaximum` (recorded: 131072), no `converse.userDocumentTypesSupported` (recorded: empty list), `featuresSupported.promptOptimization` true where the recording says false, and `inferenceTypesSupported[0]` ON_DEMAND where the recording says INFERENCE_PROFILE. For `nvidia.nemotron-nano-12b-v2` it emits `batchSupported.baseModelSupported` false where the recording says true, no `converse.additionalRequestFieldsSchema` / `converse.maxTokensMaximum` / `converse.userDocumentTypesSupported` / `converse.userImageTypesSupported` (recorded: png, jpeg, gif, webp), a `converse.reasoningSupported` object the recording does not carry at all, and the wrong `featuresSupported.batchInference.inRegion`. Across the rest of the catalog `modelFamily` and `modelLifecycle.startOfLifeTime` are absent on most summaries, and `modelName`, `description`, `guardrailsSupported`, `inferenceAPIsSupported`, `explicitPromptCaching`, `intelligentPromptRouting` and `latencyOptimizationSupported` carry different values. Four recorded cohere ids have no counterpart summary whatsoever -- the divergence_key names `$.modelSummaries[modelId="cohere.command-text-v14"]`, `[modelId="cohere.command-light-text-v14"]`, `[modelId="cohere.command-text-v14:7:4k"]`, `[modelId="cohere.command-light-text-v14:7:4k"]`, plus `[modelId="cohere.embed-english-v3:0"]`, `[modelId="cohere.embed-english-v3:0:512"]`, `[modelId="cohere.embed-multilingual-v3:0"]` and `[modelId="cohere.embed-multilingual-v3:0:512"]`, as whole-summary paths rather than member paths.

Why: discovery is the entry point for every other bedrock call. A client reads `converse.maxTokensMaximum`, `converse.stopSequencesDefault` and `converse.additionalRequestFieldsSchema` to build a Converse/InvokeModel request for a model it just listed, and `featuresSupported` / `batchSupported` / `guardrailsSupported` / `inferenceTypesSupported` to decide whether it may batch, guard, cache or route that model through an inference profile. Because the response is a 200 with a plausible shape, a wrong value is acted on rather than reported: a client sizes `maxTokens` against a limit the service does not publish, submits a batch job for a model the recording says cannot be batched in-region, or invokes ON_DEMAND a model the recording offers only via INFERENCE_PROFILE. A modelId the listing omits cannot be reached by a catalog-driven client at all, and a client that indexes or page-slices `modelSummaries` picks a different model than the recorded catalog would hand it.

Fix: the per-model published data behind the ListFoundationModels capability projection in the bedrock control-plane crate's foundation-model state (the catalog rows plus the lookup tables the summary projection reads for converse limits, reasoning support, published feature flags, provider document/image/video formats, model family and the lifecycle instants), not the handler's serializer: the handler shape is right and the values and the catalog membership are wrong. The projection must publish each summary's members from that model's recorded row instead of deriving them from a few generic attributes, and the catalog must carry the retired cohere command/embed ids the recording still offers.

Related open issue: 20261114T000000Z-bedrock-discovery-lists-per-model-capability-values-and-the-system-defined-profile-set.md describes the same operation under its Cause 2, but the replay reports this cluster as unowned (owned_by is empty), so its replay key is not carried by that issue and it is filed here; a fixer should treat the two together and close neither on the strength of the other.
