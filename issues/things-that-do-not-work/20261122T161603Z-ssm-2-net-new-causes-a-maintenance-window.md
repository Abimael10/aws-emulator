# ssm: 2 net-new causes — a maintenance window's cron/rate Schedule never produces a WindowExecution (the whole execution-history plane is empty), and DescribeAssociation's AssociationDoesNotExist message for a legacy Name/InstanceId lookup is emulator prose

> _Note: this issue was identified against the code base at commit `e3483ea57c457ab7b31d6d09f2c005f800b70f84`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
DescribeMaintenanceWindowExecutions

## Description
Two independent net-new causes in the SSM emulator, both reached by behavioral checks that are neither blocked by an unimplemented-scaffold issue nor owned by an open issue. Each is a separate defect and BOTH must be closed before this issue is resubmitted.

=== Cause 1 of 2: a maintenance window with a cron/rate Schedule never fires — no WindowExecution is ever created, so the entire execution/task/invocation read plane stays empty ===
AWS: a maintenance window created with CreateMaintenanceWindow(Schedule=<cron(...)|rate(...)>, Duration, Cutoff, AllowUnassociatedTargets) is driven by the service's own scheduler: at each scheduled occurrence Systems Manager opens a window execution, runs every registered task, and records the run. Smithy (services/service-com-amazonaws-ssm-amazonssm/smithy-model/com-amazonaws-ssm-amazonssm.json): DescribeMaintenanceWindowExecutions(WindowId required, @pattern ^mw-[0-9a-f]{17}$) -> WindowExecutions: MaintenanceWindowExecutionList, paginated on WindowExecutions; GetMaintenanceWindowExecution(WindowExecutionId required, @length 36, UUID @pattern) -> {WindowExecutionId, TaskIds: MaintenanceWindowExecutionTaskIdList, Status: MaintenanceWindowExecutionStatus enum, StatusDetails, StartTime, EndTime}, error DoesNotExistException (client, httpError 400); DescribeMaintenanceWindowExecutionTasks(WindowExecutionId required) -> WindowExecutionTaskIdentities; DescribeMaintenanceWindowExecutionTaskInvocations(WindowExecutionId, TaskId required) -> WindowExecutionTaskInvocationIdentities. The model therefore requires that a scheduled window yield WindowExecution records, each with task ids and, per task, invocation identities, driven to a terminal Status (SUCCESS/FAILED/TIMED_OUT/CANCELLED). Recorded behavior: with a window on a one-minute cron and one or more registered LAMBDA/RUN_COMMAND tasks, an execution appears within a few minutes and settles to a terminal Status; the checks poll for up to 200–360 s.
Emulator: CreateMaintenanceWindow and RegisterTaskWithMaintenanceWindow are accepted, but DescribeMaintenanceWindowExecutions(WindowId=<the new window>) answers HTTP 200 with WindowExecutions = [] forever. No execution is ever minted, so every downstream read has nothing to read: the checks fail with 'maintenance window schedule never produced an execution within the timeout', 'timed out after 360s waiting for the maintenance window schedule to produce an execution; last observed: None', "the cron Schedule 'cron(46 15 * * ? *)' (UTC) never produced a live WindowExecution for mw-<id> within the poll window", 'maintenance window never produced an execution', 'condition never satisfied, last value=[]', 'condition not met within 200.0s (last=[])', and two checks exhaust their 60 s budget outright ('Check timed out after 60.0s'). The empty-list symptom is the general behavior; the particular window id, cron text and poll budget in each message are per-run values, not requirements.
Why: the maintenance-window data plane does not exist for a client. Nothing a window is configured to do ever happens: registered Run Command / Lambda / Automation tasks never execute, Cutoff and TimeoutSeconds are never exercised, CancelMaintenanceWindowExecution has nothing to cancel, and every read (DescribeMaintenanceWindowExecutions, GetMaintenanceWindowExecution, DescribeMaintenanceWindowExecutionTasks, DescribeMaintenanceWindowExecutionTaskInvocations) reports an account with no history. A patch/maintenance orchestration client that polls for its window's execution hangs until its own timeout and can never observe, link or audit a run. It also masks the refusal semantics: a negative probe cannot establish that GetMaintenanceWindowExecution refuses an UNKNOWN WindowExecutionId with DoesNotExistException while a real one succeeds, because no real one can be obtained.
Fix: the maintenance-window scheduler/execution engine in the SSM crate — the component that evaluates a window's Schedule (cron/rate, ScheduleTimezone, ScheduleOffset) against the clock, opens a MaintenanceWindowExecution for each occurrence inside Duration, dispatches each registered task (honouring Priority, MaxConcurrency, MaxErrors, Cutoff and the task's TimeoutSeconds), records a MaintenanceWindowExecutionTask per task and a MaintenanceWindowExecutionTaskInvocation per target, and drives all three record levels to terminal Status. The read handlers (describe_maintenance_window_executions / get_maintenance_window_execution / describe_maintenance_window_execution_tasks / describe_maintenance_window_execution_task_invocations) then have state to project. Note: the open issue 20261111T143427Z-ssm-getmaintenancewindowexecution-stub.md covers GetMaintenanceWindowExecution being an unimplemented scaffold stub, and 20261116T061000Z-ssm-ops-center-maintenance-window-and-association-reads.md covers DeregisterTargetFromMaintenanceWindow / DescribeMaintenanceWindows projection — neither carries this cluster's replay keys and neither covers the scheduler never producing an execution.

=== Cause 2 of 2: DescribeAssociation's AssociationDoesNotExist message for a legacy Name/InstanceId lookup is emulator prose that names neither the document nor the instance ===
AWS: Smithy: DescribeAssociation takes Name (DocumentARN, @pattern ^[a-zA-Z0-9_\-.:/]{3,128}$), InstanceId (@pattern ^(^i-(\w{8}|\w{17})$)|(^mi-\w{17}$)$) and AssociationId, and declares error AssociationDoesNotExist (client error, httpError 400, awsQueryError code AssociationDoesNotExist). When the lookup is by the legacy Name/InstanceId pair (no AssociationId) and no association exists for that pair — because it was deleted, or because the document was never associated with that instance — the refusal message is AWS's documented Name/InstanceId template: "Association not found for documentName <Name> and instanceId <InstanceId>. Try using the association-id parameter if you are looking for an association created using targets." Its FIXED text is "Association not found for documentName ", " and instanceId " and ". Try using the association-id parameter if you are looking for an association created using targets."; its VARIABLE parts are the Name and the InstanceId copied from the request. This is a different template from the AssociationId form ("Association <AssociationId> does not exist.").
Emulator: the same call answers HTTP 400 with code AssociationDoesNotExist (correct) but Message "The specified association doesn't exist." — a single fixed sentence that names no document and no instance and omits the association-id hint entirely.
Why: the error message is a requirement. AWS's message identifies WHICH (documentName, instanceId) pair has no association and tells the caller that targets-created associations must be looked up by association id instead; the emulator's prose states neither. A client that confirms a delete by matching the text, that logs/reports the missing pair, or that follows the hint to retry with AssociationId cannot do any of it, and the same opaque sentence is returned for both the AssociationId and the Name/InstanceId lookup paths, so a caller cannot even tell which lookup form failed.
Fix: the not-found refusal text in the DescribeAssociation handler (the SSM crate's describe_association operation) and the association lookup that feeds it — select AWS's Name/InstanceId template when the request carries Name+InstanceId (interpolating both from the request) and the AssociationId template when it carries AssociationId. The open issue 20261113T123420Z-cloudformation-ec2-ssm-ssm-describeassociation-the-associationdoesnotexist-message-for-an-association.md covers only the AssociationId form of this message and does not carry these checks' replay keys; 20261105T101017Z and 20261112T101725Z touch association refusal wording elsewhere but not this template.
Traces: ssm.update-association-status-nonexistent-association-rejected, ssm.update-association-status-transitions-and-nonexistent-rejected.
