# cloudwatch__events__sqs: PutMetricAlarm does not reliably emit one 'CloudWatch Alarm Configuration Change' per write, so the alarm emit-scope check never converges (times out)

> _Note: this issue was identified against the code base at commit `861d02363efbdafabe99fc79477849a03b9381e9`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
PutMetricAlarm

## Description
This issue carries 1 net-new root cause for the cloudwatch__events__sqs path. NOTE: open issue 20261115T163456Z-cloudwatch-events-sqs-the-cloudwatch-alarm-configuration-change.md describes the same timeout as its Cause 2, but this replay no longer binds the failing check to that issue's replay key (the check is reported with no owning issue and with a bare 'Check timed out after 60.0s', not the keyed '_drain#25|Timeout' frame that issue recorded), so the failure is re-filed here rather than dropped. A fixer closing that issue's Cause 2 closes this one as well.

Cause 1 of 1: an alarm write does not reliably produce exactly one 'CloudWatch Alarm Configuration Change' event on the default bus, so a consumer polling for one event per write never converges.
AWS: recorded behavior only for the EventBridge payload — no Smithy trait describes the emitted event. Smithy (CloudWatch, GraniteServiceVersion20100801): PutMetricAlarm(AlarmName required, Namespace @pattern ^[^:] , MetricName, Statistic, Period @range min 1, EvaluationPeriods @range min 1, Threshold double, ComparisonOperator, TreatMissingData) returns Unit; DisableAlarmActions / EnableAlarmActions(AlarmNames required) return Unit; SetAlarmState(AlarmName, StateValue, StateReason required) returns Unit; TagResource(ResourceARN, Tags required). Against the recording, each alarm write that changes the alarm's configuration — the creating PutMetricAlarm, each subsequent PutMetricAlarm that changes any configuration member (e.g. Threshold), DisableAlarmActions and EnableAlarmActions — emits exactly ONE event with source 'aws.cloudwatch', detail-type 'CloudWatch Alarm Configuration Change', resources [the alarm ARN], detail.operation 'create' or 'update' and detail.configuration / detail.previousConfiguration describing the new and prior alarm; SetAlarmState emits only a 'CloudWatch Alarm State Change'; TagResource and a PutMetricAlarm identical to the stored alarm emit neither. The emission is per write and prompt, so a rule matching the alarm delivers one message to its SQS target for every such write, repeatedly, on the same alarm.
Emulator: the check never reaches any assertion — the replay reports 'Check timed out after 60.0s'. Its warm-up requires five CONSECUTIVE PutMetricAlarm writes to the same alarm to each deliver their own Configuration Change event (matched by detail.configuration.threshold == that write's threshold), any miss resetting the streak; that streak never completes, so the whole 60 s budget is consumed inside the warm-up and none of the six emit-scope facts (create/Disable/Enable emit a Configuration Change, SetAlarmState emits only a State Change, TagResource and a no-op put emit nothing) is ever observed. Hypothesis: the configuration-change emission fires for some writes but not for every repeated write to an existing alarm (sibling checks on the same service do receive such events, so the rule→queue path is not dead, only unreliable or late).
Why: a client that reacts to alarm changes through EventBridge (drift detection, configuration auditing, re-deriving dashboards, re-publishing alarm state) silently loses changes: an alarm is modified and no event arrives, so the consumer's view of the alarm diverges from CloudWatch's with no error anywhere. Any workflow that waits for the event of a write it just made hangs instead of completing.
Fix: the alarm event-emission path in the CloudWatch alarm write handlers (PutMetricAlarm, DisableAlarmActions, EnableAlarmActions, SetAlarmState, TagResource) and the state transition that decides whether a write changed the alarm — every configuration-changing write, including repeated writes to an already existing alarm, must emit exactly one 'CloudWatch Alarm Configuration Change' promptly, a state-only write must emit only a 'CloudWatch Alarm State Change', and a tag write or a no-op put must emit nothing.
Traces: cloudwatch__events__sqs.xsvc-cloudwatch-2-state-changes-tagging-and-noop-puts-emit-no-configuration-change-event.

## Evidence
Failing check: cloudwatch__events__sqs.xsvc-cloudwatch-2-state-changes-tagging-and-noop-puts-emit-no-configuration-change-event — verdict [mismatch], detail 'Check timed out after 60.0s'.

Expected (recorded AWS): with a rule on {"source":["aws.cloudwatch"],"detail-type":["CloudWatch Alarm Configuration Change","CloudWatch Alarm State Change"],"detail":{"alarmName":[<alarm>,<warm-up alarm>]}} targeting an SQS queue whose policy allows events.amazonaws.com sqs:SendMessage from the rule ARN, N successive PutMetricAlarm writes that differ only in Threshold deliver N Configuration Change messages, one per write, each with detail.configuration.threshold equal to that write's threshold. The check's warm-up then proves the path live after five consecutive hits and goes on to assert the six-write emit scope, finishing well inside the 60 s budget.

Actual (emulator): no assertion in the check body is ever reached; the harness kills the check at its 60 s cap while it is still inside the warm-up loop, i.e. five consecutive PutMetricAlarm writes each delivering their own Configuration Change event never occurred. No status code or error code is involved — every API call in the path returns success; the divergence is the missing/unreliable event emission. Consequently the downstream assertions that SetAlarmState emits only 'CloudWatch Alarm State Change' and that TagResource and an identical PutMetricAlarm emit nothing are also unverified.
