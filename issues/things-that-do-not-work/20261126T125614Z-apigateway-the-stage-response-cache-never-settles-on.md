# apigateway: the stage response cache never settles on a cached response — the whole check budget is consumed before the first priming GET, so FlushStageCache's TTL-bypass is still ungraded

Cause 1 of 1: a deployed stage with cacheClusterEnabled and per-method caching never produces an observable cache hit within the replay budget, so neither the cache-hit contract nor FlushStageCache's effect on a live cache entry can be graded. Failing check: apigateway.flush-caches-bypass-ttl.

AWS: Smithy (com.amazonaws.apigateway#BackplaneControlService): MethodSetting$cachingEnabled — "Specifies whether responses should be cached and returned for requests. A cache cluster must be enabled on the stage for responses to be cached"; MethodSetting$cacheTtlInSeconds — "Specifies the time to live (TTL), in seconds, for cached responses"; CacheClusterStatus enum [CREATE_IN_PROGRESS, AVAILABLE, DELETE_IN_PROGRESS, NOT_AVAILABLE, FLUSH_IN_PROGRESS]; FlushStageCache -> DELETE /restapis/{restApiId}/stages/{stageName}/cache/data, success code 202, errors BadRequestException(400) ConflictException(409) LimitExceededException(429) NotFoundException(404) TooManyRequestsException(429) UnauthorizedException(401); FlushStageAuthorizersCache -> DELETE /restapis/{restApiId}/stages/{stageName}/cache/authorizers, success code 202. Beyond the model, recorded behavior only: on a REGIONAL stage whose cacheClusterStatus has reached AVAILABLE and whose GET method carries cachingEnabled=true with a 300 s TTL, a short run of identical GETs to that method is answered from the cache — every response carries the SAME body (here the backend's $context.requestId), proving those requests did not reach the integration; FlushStageCache then answers 202 and, within a bound and while the flushed entry's 300 s TTL is still live, the cache settles on a DIFFERENT body, so the flush and not expiry invalidated it; FlushStageAuthorizersCache answers 202 back-to-back without disturbing cacheClusterStatus (still AVAILABLE). The id values are per-run values that fill the template; the requirement is the same-id run, then a different-id run after the 202.

Emulator: the first priming poll is reached with essentially no budget left and fails: 'AssertionError: the cache never settled on one response for 5 consecutive GETs within 1s; last ids [<one id>]' (check_apigateway_flush_caches_bypass_ttl.py line 117 -> _poll_for_stable_id line 246). The poll's own bound is computed as min(180 s, time_left - 150 s) and collapsed to the 1.0 s floor, and only ONE GET was issued, so the emulator spent the check's whole budget in the steps before it (the backend stage's first servable response and/or the cache cluster's CREATE_IN_PROGRESS -> AVAILABLE span, both of which the check polls). Hypothesis: the emulated cache-cluster provisioning span and/or the latency before a freshly deployed stage first answers are long enough to swallow the budget; the alternative is that the HTTP_PROXY-fronted stage answers a fresh body per request (no cache hit ever), which the single recorded id cannot distinguish. Either way, nothing after the stage-settings assertions is observable: no cache hit, no 202-then-fresh-body transition, no post-flush cacheClusterStatus read.

Why: a client that fronts a backend with a stage response cache cannot rely on any of the three behaviours it pays for — repeated requests being served without touching the integration, FlushStageCache invalidating an entry inside its TTL, and FlushStageAuthorizersCache being an independent cache that leaves the response cache cluster AVAILABLE. Code that primes a cache and then flushes it sees responses the emulator produces afresh, and a client waiting on the documented progression hangs instead of being served.

Fix: the execute-api data plane for a deployed stage — the response-cache lookup/store wrapped around integration dispatch, and the per-method caching settings (cachingEnabled / cacheTtlInSeconds) that gate it — plus the cache-cluster lifecycle timing that the stage read exposes as cacheClusterStatus, so provisioning settles in a span a client can observe. FlushStageCache's own handler already models the FLUSH_IN_PROGRESS -> AVAILABLE transition.

Traces: apigateway.flush-caches-bypass-ttl (mismatch). Component files: services/service-com-amazonaws-apigateway-backplanecontrolservice/src/service/invoke.rs (integration dispatch and response cache), src/ops/create_stage.rs and src/ops/update_stage.rs (cache cluster + /{resource}/{method}/caching/enabled and /caching/ttlInSeconds), src/ops/flush_stage_cache.rs (flush span, already modelled).
