# bedrock-agentcore: 2 net-new causes — the namespace-condition AccessDeniedException message is the wrong denial sentence, and IngestData's long-term extraction never produces a memory record

> _Note: this issue was identified against the code base at commit `39072a23a292d1585e88e2b56cabec6bc140b809`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
ListMemoryRecords

## Description
Two independent net-new root causes on the bedrock-agentcore (AgentCore Memory data-plane) surface in this sweep. Each is numbered below with its own failing check ids; BOTH must be closed before this work item is submitted.

=== Cause 1 of 2: a ListMemoryRecords denial caused by a FAILED bedrock-agentcore:namespace condition is reported with the "no identity-based policy allows the action" sentence instead of AWS's condition-failure sentence ===
AWS: Smithy models ListMemoryRecords as POST /memories/{memoryId}/memoryRecords with an optional `namespace` member (Namespace, @length 1..1024) and models AccessDeniedException with httpError 403 among its errors (source: smithy_query query="operation" operation="ListMemoryRecords" on services/service-com-amazonaws-bedrockagentcore-amazonbedrockagentcore/smithy-model/com-amazonaws-bedrockagentcore-amazonbedrockagentcore.json). The message text is not in the model — recorded behavior only: when the caller's ONLY Allow for bedrock-agentcore:ListMemoryRecords on the memory's ARN is conditioned on StringEquals of the service condition key `bedrock-agentcore:namespace`, a call naming a namespace the condition does NOT match is refused 403 AccessDeniedException whose message is exactly
  `User: <caller principal ARN> is not authorized to perform this operation`
The fixed text is `User: ` … ` is not authorized to perform this operation`; the ONE variable part is the request's signing identity (for an assumed role, arn:aws:sts::<account>:assumed-role/<role-name>/<session-name>). Nothing else varies: this denial sentence deliberately names NEITHER the action nor the resource, because the denial came from an unmatched condition key on an otherwise-matching Allow, not from the absence of any Allow for the action.
Emulator: the decision is now correct (403 AccessDeniedException on the sibling namespace, with the allowed namespace still permitted — the check's positive control passes), but the message is the generic no-policy sentence: `User: arn:aws:sts::<account>:assumed-role/<role>/<session> is not authorized to perform: bedrock-agentcore:ListMemoryRecords on resource: arn:aws:bedrock-agentcore:<region>:<account>:memory/<memoryId> because no identity-based policy allows the bedrock-agentcore:ListMemoryRecords action`. (The account id, role/session names, region and memory id in that string are per-run values; the divergence is the SENTENCE FORM — the appended `to perform: <action> on resource: <arn> because no identity-based policy allows the <action> action` clause, where AWS ends the sentence at `to perform this operation`.)
Why: clients and test suites classify AgentCore authorization failures by the denial sentence: the long form means "the principal has no grant for this action at all" and the short form means "a grant exists but a condition on it did not match". A client that keys its remediation (widen the condition vs. add the action) on that text, or asserts the documented message, mis-diagnoses every namespace-scoped denial, and a message assertion that passes against AWS fails against the emulator.
Fix: the memory data-plane authorizer's refusal rendering (crate::state::authorize_memory and the AccessDeniedException it builds for the *MemoryRecord* reads — ListMemoryRecords, RetrieveMemoryRecords, GetMemoryRecord) must distinguish "no Allow matched action+resource" from "an Allow matched action+resource but its condition on bedrock-agentcore:namespace did not", emitting the short `is not authorized to perform this operation` sentence for the latter.
Related but NOT covering this: open issue 20261121T033538Z-bedrock-agentcore-3-net-new-causes-listmemoryrecords-ignores.md carries this same check id, but it was grounded in the condition key being IGNORED ENTIRELY (HTTP 200 with the sibling namespace's record, failing at `assert denied["code"] == "AccessDeniedException"`). The condition key is now evaluated and the call is now denied; what remains is the later assertion on the denial's message, a different defect in a different component (refusal rendering, not policy evaluation).
Traces: bedrock-agentcore.namespace-condition-key-blocks-cross-namespace-memory-read (fails at `assert denied["message"] == ...`, after the AccessDeniedException code assertion and the positive control both pass).

=== Cause 2 of 2: content accepted by IngestData is never extracted into a memory record, so RetrieveMemoryRecords never surfaces the ingested fact and the check is killed on the clock ===
AWS: Smithy models IngestData as POST /memories/{memoryId}/ingest (202) taking source(ContentSource, inline only), contentTimestamp, actorId and an optional extractionConfig, and documents it as "Submits content directly for ingestion to generate long-term memory records in a AgentCore Memory resource"; RetrieveMemoryRecords is POST /memories/{memoryId}/retrieve with a required searchCriteria and a required memoryRecordSummaries output, and GetMemoryRecord is GET /memories/{memoryId}/memoryRecord/{memoryRecordId} with ResourceNotFoundException (httpError 404) modeled (source: smithy_query query="operation" operation="IngestData,RetrieveMemoryRecords,GetMemoryRecord" on the same model). Recorded behavior: after IngestData of a conversational payload into a memory whose semanticMemoryStrategy namespace template resolves to /semantic/{actorId}, the asynchronous extraction pipeline converges — ListMemoryExtractionJobs reports a job for that unit of work and it reaches a terminal status, and RetrieveMemoryRecords(namespace='/semantic/<actorId>', searchCriteria={searchQuery:<the ingested text>, topK:5}) eventually returns a memoryRecordSummary whose content reflects the ingested fact. After DeleteMemoryRecord of that record, GetMemoryRecord for it is refused 404 ResourceNotFoundException with the message `The memory record was not found` (fixed text, no variable part).
Emulator: IngestData accepts and persists the content (services/service-com-amazonaws-bedrockagentcore-amazonbedrockagentcore/src/ops/ingest_data.rs stores an IngestedContent and ListMemoryExtractionJobs renders a unit of work for it), but nothing ever turns that content into a memory record: RetrieveMemoryRecords (same crate, src/ops/retrieve_memory_records.rs) searches only the records held in the store, which stay empty, so its memoryRecordSummaries is permanently `[]`. The convergence poll never satisfies and the check is killed at the harness wall clock (`Error: Check timed out after 60.0s`) with no refusal text, so every later beat (DeleteMemoryRecord, and the terminal GetMemoryRecord 404 `The memory record was not found`) is never reached. The handler's own comment states the intent ("The content is persisted as submitted: it is what long-term extraction reads") — the extraction step itself is absent.
Why: generating long-term memory records is the entire purpose of IngestData. A client that ingests facts and then retrieves them gets a permanently empty namespace: every read-back, semantic search and record lifecycle (delete, then the modeled 404) is unreachable, and an agent built against the emulator silently has no long-term memory.
Fix: the memory data-plane extraction path/state behind IngestData (the same pipeline StartMemoryExtractionJob and ListMemoryExtractionJobs report over) must derive memory records from ingested content into the namespaces the memory's strategy templates resolve for the content's actorId/sessionId, so RetrieveMemoryRecords/ListMemoryRecords/GetMemoryRecord report them and DeleteMemoryRecord removes them.
Related but NOT covering this: open issue 20261121T033538Z-bedrock-agentcore-3-net-new-causes-listmemoryrecords-ignores.md Cause 3 is the CreateEvent-driven extraction path (POST /memories/{memoryId}/events and extractionMode=SKIP) and is grounded in a different check; this cause is the IngestData entry point and its extraction-job surface, and that issue asserts nothing about IngestData. Open issue 20261112T062114Z-bedrock-agentcore-startmemoryextractionjob-stub.md covers only that one operation's stub.
Traces: bedrock-agentcore.e2e-memory-extraction-to-retrieval. Note for the fixer: this check needs more wall clock than the 60s replay budget, so confirm the fix by driving the sequence directly (IngestData -> ListMemoryExtractionJobs -> RetrieveMemoryRecords on /semantic/<actorId> -> DeleteMemoryRecord -> GetMemoryRecord) as well as by re-replaying the check.
