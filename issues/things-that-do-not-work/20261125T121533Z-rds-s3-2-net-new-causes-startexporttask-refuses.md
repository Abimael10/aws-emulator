Cause 1 of 2: StartExportTask naming a destination S3 bucket that does not exist is refused with the WRONG modeled error — IamRoleMissingPermissions (HTTP 400) instead of InvalidS3BucketFault (HTTP 400). The export role, KMS key and source snapshot in these requests are all valid and the role's policy grants the full S3 action set on the bucket it was scoped to; the only broken thing is that the named bucket does not exist.
AWS: Smithy (services/service-com-amazonaws-rds-amazonrdsv19/smithy-model/com-amazonaws-rds-amazonrdsv19.json) models StartExportTask with required input members ExportTaskIdentifier, SourceArn, S3BucketName, IamRoleArn, KmsKeyId and, among its errors, InvalidS3BucketFault (errorKind client, httpError 400, awsQueryError code 'InvalidS3BucketFault') and IamRoleMissingPermissionsFault (client, httpError 400, awsQueryError code 'IamRoleMissingPermissions'). InvalidS3BucketFault is documented as "The specified Amazon S3 bucket name can't be found or Amazon RDS isn't authorized to access the specified Amazon S3 bucket." — i.e. the existence/locatability of the destination bucket is judged BEFORE, and separately from, the role's authorization on it. Recorded behavior for the refusal sentence: HTTP 400, Error.Code 'InvalidS3BucketFault', Error.Message "The S3 bucket <bucket name> isn't valid. Either it isn't located in the current AWS Region or it doesn't exist." The fixed text is "The S3 bucket ", " isn't valid. Either it isn't located in the current AWS Region or it doesn't exist."; the one variable part is the S3BucketName taken verbatim from the request. The refusal is answered on the StartExportTask call itself and no export task is created, so a following DescribeExportTasks does not list the identifier.
Emulator: the same request is refused with Error.Code 'IamRoleMissingPermissions' (the message then names the role and an S3 action rather than the bucket), so the bucket-existence check either never runs or runs after the role-authorization probe. The emulator reaches the role check because, to the emulator, the role's policy does not cover an ARN for a bucket the request invented — but AWS never gets that far: a bucket that cannot be found is InvalidS3BucketFault regardless of what the role is scoped to.
Why: the refusal misdiagnoses the request. A client that branches on Error.Code — and the AWS CLI/console surface, and every retry/remediation path keyed on it — is told the IAM role is under-privileged when the real fault is a typo'd, deleted or out-of-region bucket name. Acting on the emulator's answer leads an operator to widen an IAM policy that is already correct, while the actual cause (the bucket) is never named anywhere in the response, and InvalidS3BucketFault becomes unreachable for the one condition it exists for.
Fix: the input-validation order of the StartExportTask handler in services/service-com-amazonaws-rds-amazonrdsv19/src/ops/start_export_task.rs — resolve and validate S3BucketName (exists, and is in the request's region) and answer InvalidS3BucketFault with the documented sentence before probing the IamRoleArn's authorization on that bucket.

Cause 2 of 2: two export checks are still cut off at the per-check replay cap with NO graded assertion, so neither the refusal they assert nor their positive control is observable.
AWS: recorded behavior — DescribeDBInstances reports DBInstanceStatus 'available' and DescribeDBSnapshots reports snapshot Status 'available' promptly after creation, and the modeled StartExportTask refusals (InvalidS3BucketFault 400, IamRoleMissingPermissionsFault 400, IamRoleNotFoundFault 404, KMSKeyNotAccessibleFault 400) are answered on the start call itself rather than after any wait. Each of these two checks provisions (bucket(s), KMS key, export role, DB subnet group — in one case its own VPC and two subnets — DB instance, snapshot), then asserts one of those refusals and runs a positive control; every wait in both checks is a predicate poll with its own generous deadline (90–2400 s), never a fixed-duration sleep.
Emulator: both end with 'Error: Check timed out after 60.0s' and no assertion is ever evaluated; the budget is spent inside the checks' own terminal-state polls. Hypothesis: one of the states these checks wait on before they can call StartExportTask — the DB instance's DBInstanceStatus reaching 'available' via DescribeDBInstances, or the DB snapshot's Status reaching 'available' via DescribeDBSnapshots — is never advanced, so the export branch is never entered. (Sibling checks with the same provisioning chain DO reach their StartExportTask assertion, which is how Cause 1 above is observable, so this is a state that settles for some shapes and not these.)
Why: these scenarios of the snapshot-export surface are ungradeable. A caller following the documented provision → snapshot → export sequence hangs in a poll instead of receiving either an export task or one of the modeled refusals, and the negative paths these checks cover (a well-formed bucket name that does not exist via the CLI; a role scoped to bucket A targeting existing bucket B) cannot be exercised at all.
Fix: the RDS resource state progressions these reads serve — the DB-instance status behind DescribeDBInstances and the snapshot status behind DescribeDBSnapshots in the RDS crate's state must reach 'available' promptly, and StartExportTask's input validation must answer its modeled refusals on the start call.
Traces: rds__s3.cli-rds-export-invalid-bucket-name-negative, rds__s3.rds-export-task-wrong-bucket-negative.
