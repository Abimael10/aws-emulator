# bedrock ListFoundationModels catalogue entries diverge for newly recorded openai, nvidia and cohere models

> _Note: this issue was identified against the code base at commit `794ecb5f323f40e750b08b78a7a2af772a25b723`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Description
One cause, replayed from one fixture step.

Cause 1 of 1: the seeded foundation-model catalogue served by ListFoundationModels diverges from the recorded AWS catalogue across a large fraction of its entries — per-model capability members carry the wrong values or are absent, several models carry the wrong family/lifecycle metadata, and catalogue membership itself is wrong for a set of retired cohere ids. Fixture bedrock-catalog-list-foundation-models, step task#1.

AWS: ListFoundationModels is GET /foundation-models returning 200 with modelSummaries, a list of FoundationModelSummary (Smithy: services/service-com-amazonaws-bedrock-amazonbedrockcontrolplaneservice — ListFoundationModels http {method: GET, uri: /foundation-models, code: 200}; output member modelSummaries -> FoundationModelSummaryList; errors AccessDeniedException 403, InternalServerException 500, ThrottlingException 429, ValidationException 400). The on-disk Smithy model declares FoundationModelSummary members modelArn, modelId, modelName, providerName, inputModalities, outputModalities, responseStreamingSupported, customizationsSupported, inferenceTypesSupported and modelLifecycle -> FoundationModelLifecycle. The remaining members the recording asserts — converse (maxTokensDefault, maxTokensMaximum, stopSequencesDefault, additionalRequestFieldsSchema, reasoningSupported, userImageTypesSupported, userDocumentTypesSupported, userVideoTypesSupported), featuresSupported (promptOptimization, promptCaching, countTokens, provisionedThroughput, intelligentPromptRouting, batchInference.inRegion/.crossRegion), batchSupported (baseModelSupported, customModelSupported, crossRegionSupported), inferenceAPIsSupported (invokeModel.sync/.responseStreaming/.bidirectionalStreaming, converse.sync, openAiChatCompletions, openAiResponses), explicitPromptCaching.isSupported, intelligentPromptRouting.isSupported, latencyOptimizationSupported, guardrailsSupported, modelFamily, modelName, description and modelLifecycle.startOfLifeTime/legacyTime/publicExtendedAccessTime/endOfLifeTime/status — are recorded behavior only: the on-disk model does not describe them, so the recorded AWS response is the specification. AWS is a catalogue API: for a given region it returns one fixed, authoritative row per available model id, and every member of that row is part of the contract. The requirement is that the catalogue the emulator seeds reproduces that recorded row set and row contents, not that it carries any particular literal value from one run.

Emulator: answers 200 and serves a catalogue, but the rows disagree with the recording. Representative diffs reported by the replay for fixture bedrock-catalog-list-foundation-models step task#1:

Why: a client uses this catalogue to choose a model and to decide how to call it. With these rows a client reads 'ON_DEMAND' where AWS offers only 'INFERENCE_PROFILE' and builds a direct on-demand InvokeModel/Converse call that real Bedrock refuses; it sees no userImageTypesSupported and no IMAGE input modality for a vision-capable model and silently drops image content; it sees openAiChatCompletions/openAiResponses false and skips an API path AWS serves; it sees promptOptimization true everywhere and enables a feature AWS reports as unavailable; it sizes requests from the wrong converse.maxTokensMaximum/maxTokensDefault; and it resolves or fails to resolve retired cohere ids that disagree with the recorded catalogue, so capability probing and model-availability logic come out wrong in both directions. Lifecycle/startOfLifeTime drift makes deprecation-aware selection pick the wrong row.

Fix: the bedrock foundation-model catalogue seed and the ListFoundationModels serializer that projects it — the seed must carry one row per recorded model id with the recorded per-model capability members (converse limits and media type lists, featuresSupported, batchSupported, inferenceAPIsSupported, explicitPromptCaching, intelligentPromptRouting, latencyOptimizationSupported, guardrailsSupported, modelFamily, modelName, description, inputModalities/outputModalities, inferenceTypesSupported, customizationsSupported, responseStreamingSupported and the full modelLifecycle), and the serializer must emit nested capability objects rather than omitting members it has no seed value for.
