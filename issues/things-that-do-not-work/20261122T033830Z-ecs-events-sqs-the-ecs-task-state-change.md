Cause 1 of 1 — the ECS Fargate task lifecycle produces no observable STOPPED transition with a real exit status and publishes no 'ECS Task State Change' envelope onto the EventBridge bus, so neither the positive deliveries nor the negative (not-delivered) controls of exit-code-scoped rule routing can be observed, and the check exhausts its whole budget without reaching a single assertion. Failing check: ecs__events__sqs.events-workload-state-change-ecs-exit-code-rules-route-each-stopped-task-and-not-delivered-to-the-other.

AWS: RunTask with launchType FARGATE, networkMode awsvpc and a containerOverride command `sh -c "sleep 5; exit N"` places exactly one task (empty failures list). DescribeTasks then reports that task through lastStatus RUNNING and finally lastStatus STOPPED with containers[0].exitCode == N, stopCode == EssentialContainerExited and a non-empty stoppedReason. Smithy (com.amazonaws.ecs): Task$stopCode targets the TaskStopCode enum whose values are TaskFailedToStart | EssentialContainerExited | UserInitiated | ServiceSchedulerInitiated | SpotInterruption | TerminationNotice | InfrastructureHealth; Task$stoppedReason is a String; Container$exitCode is a BoxedInteger documented as "The exit code returned from the container"; Task$version is a Long whose own model documentation states "Every time a task experiences a change that starts a CloudWatch event, the version counter is incremented. If you replicate your Amazon ECS task state with CloudWatch Events, you can compare the version of a task reported by the Amazon ECS API actions with the version reported in CloudWatch Events for the task (inside the detail object)" — so the model itself fixes the requirement that the event detail's version tracks the API's. The event envelope itself is recorded behavior only (not modeled): ECS publishes events with source `aws.ecs`, detail-type `ECS Task State Change`, resources == [the task ARN], and a detail mirroring the task (clusterArn, taskArn, lastStatus, containers[].exitCode, stopCode, stoppedReason, version). EventBridge rules whose pattern scopes {source: ['aws.ecs'], detail-type: ['ECS Task State Change'], detail: {clusterArn: [...], lastStatus: ['STOPPED'], containers: {exitCode: [N]}}} therefore deliver each task's STOPPED event only to the rule whose exit-code filter matches, the complementary rule receives nothing, and a rule scoped to lastStatus ['RUNNING'] receives the earlier RUNNING events — which carry no exitCode member at all and a strictly lower detail.version than the STOPPED one.

Emulator: the check reaches none of those assertions. It creates the cluster, registers the FARGATE task definition, creates three queues with three exit-code/lastStatus-scoped rules, warms them up, calls RunTask twice (exit 7 and exit 0) and then blocks; the suite kills it at the per-check cap with `Error: Check timed out after 60.0s` and no further frame. The hang is therefore in one of the two legs that depend on the ECS lifecycle — DescribeTasks never reporting lastStatus STOPPED for the placed tasks, or the three SQS sinks never receiving any 'ECS Task State Change' message — and in either case nothing about exit-code-scoped routing is observable. This is the emulator's own surface: the replay reached it over the served endpoints and the preceding ECS, EventBridge and SQS control-plane calls in the same check all succeeded.

Why: an event-driven consumer of ECS cannot be built or validated at all. A client that alerts on a task that exits non-zero, or that fans a task's terminal state out to different queues by exit code, receives nothing, and — worse — cannot distinguish a correctly scoped rule from a broken one, because the negative control (the exitCode [0] rule must receive nothing for the task that exited 7) looks exactly like total non-delivery. A client that polls DescribeTasks for a terminal exit status instead also never gets one, so even the non-event path cannot report whether work succeeded.

Fix: the ECS task runtime and its lifecycle publisher — RunTask must drive a placed FARGATE task through RUNNING to STOPPED with the container's real exit code in containers[].exitCode, stopCode EssentialContainerExited and a stoppedReason, incrementing Task.version on each transition; and each transition must publish the 'ECS Task State Change' envelope (source aws.ecs, resources == [taskArn], detail mirroring the task including version and, for STOPPED only, containers[].exitCode/stopCode/stoppedReason) into the EventBridge bus, from which the existing rule/pattern matcher routes to the SQS targets.
