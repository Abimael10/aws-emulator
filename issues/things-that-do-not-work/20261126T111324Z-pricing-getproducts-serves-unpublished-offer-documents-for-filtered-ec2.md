# GetProducts serves unpublished offer documents for filtered EC2 price queries (2 causes)

> _Note: this issue was identified against the code base at commit `6234e6a4a0cc0c3d0cf2da5570bb140770bc92d9`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
GetProducts

## Description
TWO net-new root causes on service `pricing`, operation GetProducts, bundled because they share one fault: a filtered GetProducts query answers HTTP 200 with an offer document the emulator derived from its own seeded catalog drafts rather than the published aws_v1 offer document for the offer the filter set matches — and in one of the two the continuation token for the same query describes a different remaining population as well. Both clusters are reported by the replay with stub_path "" (empty) and owned_by [] (empty), so neither is already filed.

Shared model context (used by both causes). Smithy: services/service-com-amazonaws-pricing-awspricelistservice/smithy-model/com-amazonaws-pricing-awspricelistservice.json — GetProducts input {ServiceCode required, Filters @length 0..50, FormatVersion @length 1..32, NextToken, MaxResults @range 1..100}; output {FormatVersion @length 1..32, PriceList (PriceListJsonItems), NextToken}; @paginated {inputToken NextToken, outputToken NextToken, items PriceList, pageSize MaxResults}; modelled errors InvalidParameterException / NotFoundException / InvalidNextTokenException / ExpiredNextTokenException (httpError 400), AccessDeniedException (401), ThrottlingException (429), InternalErrorException (500, retryable). The model does NOT describe the CONTENT of a PriceList item (PriceListJsonItems is a list of opaque JSON strings), so for the document body this is recorded behavior only. Neither step carries an error: both recorded and actual status are 200, no error code and no error message — the requirement here is the BODY, not a status or a message.

Cause 1 of 2: the EC2 attribute-vocabulary TERM_MATCH filter set gets the wrong first offer document AND a NextToken for a different remaining set. Fixture pricing-ecc-traj-ec2-vocabulary-in-price-filters, step task#4; divergence_key "service=pricing|GetProducts|status=200->200|keys=$.NextToken,$.PriceList[0]"; affected_count 4.
AWS: recorded behavior only (plus the Smithy signature above). GetProducts(ServiceCode=AmazonEC2) with the TERM_MATCH filter set assembled from the attribute vocabulary discovered earlier in the same trajectory returns, as PriceList[0], the catalog's PUBLISHED offer document for the matched Compute Instance offer: product.productFamily "Compute Instance", product.sku the catalog's published SKU for that offer, serviceCode "AmazonEC2", product.attributes the FULL published EC2 attribute set for the offer (instanceType, instanceFamily, instanceFamilyCategory, operatingSystem, tenancy, capacitystatus, licenseModel, preInstalledSw, operation, usagetype, marketoption, memory, vcpu, storage, normalizationSizeFactor, clockSpeed, ecu, physicalProcessor, processorArchitecture, processorFeatures, networkPerformance, dedicatedEbsThroughput, dedicatedEbsThroughputDescription, enhancedNetworkingSupported, intelAvxAvailable, intelAvx2Available, intelTurboAvailable, classicnetworkingsupport, vpcnetworkingsupport, gpuMemory, availabilityzone, regionCode, location, locationType, servicecode, servicename), and terms carrying BOTH an OnDemand block whose usage dimension has unit "Hrs", beginRange "0", endRange "Inf" and description worded "$<rate> per On Demand <operatingSystem> <instanceType> Instance Hour", and a Reserved block whose usage dimension is worded "<platform>, <instanceType> reserved instance applied". In those descriptions the quoted wording is the FIXED text; <rate>, <operatingSystem>, <instanceType> and <platform> are variable parts taken from the matched product and its published rate. The SKU, rate codes, offer term codes, effectiveDate and the particular instance size that appear in the recording are that run's catalog values filling the template, never requirements. The NextToken returned with that page must continue THAT filtered set.
Emulator: answers 200 but the replay reports `$.PriceList[0]: value_mismatch` and names NextToken as diverging too (keys=$.NextToken,$.PriceList[0]). It serves a document rendered from its seeded product drafts instead of the published catalog document — derived sku and rate/term codes, product.attributes carrying only the keys the seed holds, formulaic OnDemand/Reserved terms — orders a different product first for the same filter set, and emits a continuation token that does not describe the same remaining population.
Why: a client prices a workload from PriceList[0] and then walks the rest of the filtered set with NextToken. A different first document is a different price and a different product identity for the same query, and a token for a different remainder means the rest of the walk covers different products — so a cost estimate assembled by paging GetProducts is wrong both in the figure it reports and in the inventory it covers, and anything keying a quote, order or cache off product.sku keys it off an identifier AWS never published. Status 200 and a structurally valid shape mean nothing signals the figures are not AWS's.
Fix: the pricing crate's GetProducts handler — its TERM_MATCH filter matching, result ordering, and NextToken encoding/decoding — together with the service's catalog state and its offer-document/terms builders, which must publish the catalog's published offer documents rather than documents rendered from seeded drafts.
Traces: pricing-ecc-traj-ec2-vocabulary-in-price-filters#task#4 (representative; this issue's Issue-Trace/Issue-Step), same cluster also at pricing-ecc-traj-get-products-request-mistakes#task#7, pricing-ecc-traj-upstream-lookup-page-token-and-os-split#task#1 and pricing-ecc-traj-upstream-lookup-page-token-and-os-split#task#4.

Cause 2 of 2: the OS-split lookup page gets a derived offer document for the matched offer (page token agrees, document does not). Fixture pricing-ecc-traj-upstream-lookup-page-token-and-os-split, step task#3; divergence_key "service=pricing|GetProducts|status=200->200|keys=$.PriceList[0]"; affected_count 1.
AWS: recorded behavior only (plus the Smithy signature above). The step's GetProducts page returns as PriceList[0] the published offer document for the other operating-system/instance-size branch of the same split — same published-document requirements as Cause 1, and in addition the Reserved term for this offer carries an upfront dimension with unit "Quantity" and the fixed description text "Upfront Fee" alongside the hourly reserved dimension. The instance size, rate values, SKU, rate codes and effectiveDate in the recording are that run's catalog values filling the template.
Emulator: answers 200, NextToken agrees, but the replay reports `$.PriceList[0]: value_mismatch` — the document served for the matched offer is again seed-derived: derived sku/rate codes, a reduced product.attributes set, and formulaic OnDemand/Reserved term blocks rather than the published per-term dimensions (including the "Upfront Fee" Quantity dimension).
Why: the trajectory splits a lookup by operating system and prices each branch from its own page. With a derived document the branch that paged successfully still yields a price and a product identity AWS never published, so an OS-split estimate reports wrong per-platform figures even though pagination itself behaved — and because this cluster's page token matches, a fix validated only on the token would leave the figure wrong.
Fix: the pricing crate's catalog state and its offer-document/terms rendering for the AmazonEC2 price list (published attribute-set membership and published per-term dimensions), reached through the GetProducts handler's result projection.
Traces: pricing-ecc-traj-upstream-lookup-page-token-and-os-split#task#3 (this cause's representative, listed in trace_ids).
