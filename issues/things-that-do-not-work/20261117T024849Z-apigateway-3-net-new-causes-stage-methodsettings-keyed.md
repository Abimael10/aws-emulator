# apigateway: 3 net-new causes — Stage methodSettings keyed by the escaped patch-path spelling (`~1<resource>/GET`), GetDeployments omits `items` for an API with no deployments, and a VTL-templated MOCK/HTTP integration is never served at a deployed stage

## Operation
GetStage

## Description
Three distinct net-new root causes in the apigateway service, all grounded in failing behavioral checks of this suite. None of the four checks below is marked ALREADY FILED and none is marked OWNED by an open issue.

=== Cause 1 of 3: Stage.methodSettings is keyed by the JSON-Pointer-escaped patch-path spelling instead of AWS's method path ===
Failing checks: apigateway.apigw-stage-cache-serves-a-stale-body-until-flush-invalidates-it, apigateway.deploy-stage-with-variables-cfn-behaves.
AWS: Smithy (com.amazonaws.apigateway#BackplaneControlService) `Stage$methodSettings` targets `MapOfMethodSettings` (key `String`, value `MethodSetting`) and is documented verbatim as "A map that defines the method settings for a Stage resource. Keys (designated as /{method_setting_key below) are method paths defined as {resource_path}/{http_method} for an individual method override, or /*/* for overriding all methods in the stage." So the response key for resource path `/c` + verb `GET` is exactly `c/GET`, and for `/cached` + `GET` it is `cached/GET` — the resource path with its separators literal and no leading slash, joined to the HTTP method. The `~1` sequence is a JSON-Pointer escape that belongs ONLY to `UpdateStage`'s `patchOperations[].path` (e.g. `/~1cached~1GET/caching/enabled`) and to the CloudFormation `AWS::ApiGateway::Stage` `MethodSettings[].ResourcePath` normalisation; it is never part of the response map key. Recorded behavior only for the fact that the leading slash is dropped rather than kept.
Emulator: GetStage returns the map keyed with the leading slash still escaped and the remaining separator left literal — `methodSettings` comes back as `{'~1c/GET': {...}}` and `{'~1cached/GET': {...}}`. The `MethodSetting` VALUES are correct in both runs (`cachingEnabled: True`, `cacheTtlInSeconds: 300`, plus the model's defaults for `metricsEnabled`, `dataTraceEnabled`, `throttlingBurstLimit`, `throttlingRateLimit`, `cacheDataEncrypted`, `requireAuthorizationForCacheControl`, `unauthorizedCacheControlHeaderStrategy`); only the key spelling diverges. The same wrong key form appears whether the settings were written by `UpdateStage` patchOperations (apigw-stage-cache-...) or by a CloudFormation `AWS::ApiGateway::Stage` with `MethodSettings: [{ResourcePath: /cached, HttpMethod: GET, CachingEnabled: true, CacheTtlInSeconds: 300}]` (deploy-stage-with-variables-cfn-behaves), so the defect is in the shared method-settings keying, not in one writer.
Why: a client cannot read back the per-method caching/throttling configuration it just applied. Every reconcile loop — CloudFormation/CDK drift detection, an idempotent re-apply, a console render, or a test that must confirm caching is ON before exercising cache staleness — looks up `{resource_path}/{http_method}`, finds nothing, and concludes the setting was never applied: it either re-applies forever or reports permanent drift. A client that combines a `/*/*` default with a per-method override cannot tell which override applies to which method.
Fix: the stage state's method-settings keying plus the `GetStage`/`UpdateStage`/`CreateStage` response paths in the apigateway service crate, and the CloudFormation `AWS::ApiGateway::Stage` MethodSettings ingest that feeds the same map — unescape the patch path / ResourcePath and store and emit each entry under the normalised `{resource_path}/{http_method}` key, with `/*/*` preserved as-is.
RELATED, NOT COVERING: open issue 20261116T220552Z-apigateway-cloudwatch-lambda-api-gateway-stage-methodsettings-are-keyed-by-the.md reports this same key spelling for service `apigateway__cloudwatch__lambda` and carries only that service's two check ids; neither of the two checks here is marked owned by it, and it does not name the CloudFormation-written MethodSettings path. Also related and not covering: 20261107T204751Z-apigateway-api-gateway-stage-method-settings-duplicate-resource-path.md and 20261104T130732Z-apigateway-updatestage-returns-an-extra-methodsettings-entry-keyed-by.md.

=== Cause 2 of 3: GetDeployments omits the `items` member entirely for a REST API with no deployments ===
Failing check: apigateway.deep-apigateway-3-apigw-private-public-host-rejected.
AWS: Smithy models `GetDeployments` as HTTP `GET /restapis/{restApiId}/deployments`, success 200, output shape `Deployments` with members `items` (`ListOfDeployment`, jsonName `item`) and `position`, and `paginated {inputToken: position, outputToken: position, items: items, pageSize: limit}`. The model does not state member presence, so for the empty case this is recorded behavior only: an AWS 200 listing always carries its collection member on the wire under the JSON key `item`, surfaced by SDKs as `items`; a collection holding nothing answers an empty list, never an absent member.
Emulator: the 200 body omits `item` entirely, so the parsed response has no `items` key and the idiomatic read raises `KeyError: 'items'`. The handler assigns `items: page.reported_items(items)` and that helper returns `None` for an empty sequence, after which the serializer drops `items` as an absent optional.
Why: the canonical "prove the refused call left no deployment behind" read — `apigw.get_deployments(restApiId=api)["items"]` — is unwritable; botocore raises `KeyError: 'items'` and typed SDKs get a missing/None list, exactly on the API that owns nothing yet. In this check the KeyError also ABORTS the scenario immediately after the PRIVATE-API refusal it exists to check (the `BadRequestException` / "Private REST API doesn't have a resource policy attached to it" leg had already passed), so the whole private-vs-public endpoint-type claim is never exercised.
Fix: the `GetDeployments` response path plus the shared `Page::reported_items` helper in the apigateway crate's state module — a 200 listing must report a present collection member (an empty list when there is nothing to report), not omit it.
RELATED, NOT COVERING: open issue 20261114T023619Z-apigateway-nine-empty-collection-listings-omit-the-items.md reports exactly this defect family for nine OTHER operations (GetAuthorizers, GetDomainNameAccessAssociations, GetUsagePlanKeys, GetDocumentationParts, GetVpcLinks, GetBasePathMappings, GetUsagePlans, GetApiKeys, GetRequestValidators). GetDeployments is not named by it and this check is not marked owned by it. A fix to the shared helper may close all of them at once; a fix scoped to those nine op files will not.

=== Cause 3 of 3: a deployed stage never serves a MOCK/HTTP method whose mapping templates do more than emit a literal body ===
Failing check: apigateway.apigw-vtl-request-and-response-templates-transform-a-real-body.
AWS: Smithy: `PutIntegration.type` -> `IntegrationType` (MOCK, HTTP, HTTP_PROXY, AWS, AWS_PROXY) with `requestTemplates` (`MapOfStringToString` of VTL), and `PutIntegrationResponse.selectionPattern`/`responseTemplates` select and shape the method response. API Gateway's template language binds `$input.path('$.<member>')`, `$util.escapeJavaScript(...)` and `$context.stage`, and supports the `#set`/`#if`/`#else`/`#end` directives; a MOCK integration's request template is what picks the integration status (`{"statusCode":404}` vs `{"statusCode":200}`), and the matching integration response's template is what the client receives. Recorded behavior only for the particular rendered bodies and the 200/404 pair this check asserts.
Emulator: the check produces NO asserted HTTP observation at all — it is killed by the harness with `Check timed out after 60.0s` while its bounded `_poll_http` (deadline 150.0 s, interval 3.0 s) is still re-issuing `POST <stage invoke URL>/a` waiting for the MOCK branch's 404. All the control-plane calls that build the scenario (CreateRestApi, CreateResource, PutMethod, PutIntegration with the `#set`/`#if` request template, PutMethodResponse, PutIntegrationResponse with `selectionPattern`, CreateDeployment, CreateStage) succeed, so the stage is configured; what never happens is the data plane evaluating the template and answering the branch status. The general rule: a stage answers a MOCK method whose only template is the literal `{"statusCode": 200}`, but a template that evaluates `$input.path`, `$util.escapeJavaScript`, `$context.stage` or a `#if` branch — and an HTTP (non-proxy) integration fronting it — never produces the asserted response inside the check's wall clock.
Why: mapping templates are the primary way a REST API shapes requests and responses. A client gets no response at all instead of the rewritten body; request-side rewriting, `$util.escapeJavaScript` quoting, response-side shaping and `$context.stage` resolution are all unobservable, and a negative control that must come back 404 hangs instead.
Fix: the execute-api data-plane VTL mapping-template evaluator (the `$input` / `$util` / `$context` bindings and `#set`/`#if` directive handling) and the non-proxy (type=HTTP) integration dispatcher in the apigateway service crate — each must complete or fail fast rather than leaving the request unanswered.

A fixer who closes that issue's Causes 1-2 closes this cause; it is recorded here so the re-sighting at the current commit is not lost.
