# ssm: 4 net-new behavioral causes — the public /aws/service EKS/Bottlerocket image_id namespaces are unpublished, CancelMaintenanceWindowExecution is a 501 stub, and PutParameter neither gates the advanced-only data types nor validates a typed value (only `integer`)

> _Note: this issue was identified against the code base at commit `3290805d7590518967b10144dc7f47163236b608`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
PutParameter

## Description
Four independent net-new root causes in the ssm service, each grounded in its own failing behavioral check. None is marked ALREADY FILED or OWNED by the replay report. A fixer must close all FOUR before submitting.

=== Cause 1 of 4: the AWS-published parameter catalog serves no EKS-optimized-AMI or Bottlerocket image_id namespace, so GetParameter answers ParameterNotFound for names AWS publishes in every Region ===
AWS: Smithy com.amazonaws.ssm#GetParameter — input Name (PSParameterName, @length 1-2048, required), output Parameter; modeled client error ParameterNotFound (400 on the wire, awsQueryError httpResponseCode 404) means "the parameter doesn't exist". The /aws/service hierarchy is AWS's own published catalog, readable from any account in any Region without anybody creating it; recorded behavior and the EKS documentation (https://docs.aws.amazon.com/eks/latest/userguide/retrieve-ami-id.html) have GetParameter on `/aws/service/eks/optimized-ami/<k8s-version>/amazon-linux-2023/x86_64/standard/recommended/image_id` and on `/aws/service/bottlerocket/aws-k8s-<k8s-version>/x86_64/latest/image_id` answer HTTP 200 with Parameter.Name echoing the requested name, Parameter.Type "String" and Parameter.Value an AMI id of the form ami-<17 hex>.
Emulator: both reads are refused HTTP 400 ParameterNotFound with an empty Message. The published catalog this endpoint serves under /aws is projected ONLY from two sources (services/service-com-amazonaws-ssm-amazonssm/src/state/public_parameters.rs::published_records): the Global Infrastructure reference data and EC2's `public_ssm_parameter_values` image catalog. No publisher contributes the EKS-optimized-AMI or Bottlerocket namespaces, so every name under them is an ordinary miss.
Why: a client that resolves its node AMI the documented way — the recommended/image_id public parameter, which is how EKS managed nodes, launch templates and CDK/Terraform node groups pick an image — cannot resolve any image at all and fails before it launches anything. The requested name and the k8s version are request values; the requirement is that these published namespaces resolve to a launchable AMI id.
Fix: the SSM public-parameter catalog projection (services/service-com-amazonaws-ssm-amazonssm/src/state/public_parameters.rs) and the publisher state it projects from — publish the EKS-optimized-AMI and Bottlerocket image_id names for the Kubernetes versions this endpoint's image catalog carries, resolving each to an AMI id that DescribeImages also reports, exactly as the ami-amazon-linux-latest names already do. Related but not covering: 20261117T065015Z-ec2-describeimages-result-set-does-not-match-the.md and 20261107T085711Z-ec2-describeimages-amazon-published-ami-records-omit-gp3.md describe the EC2 AMI catalog itself, not these parameter namespaces.
Traces: ssm.eks-optimized-and-bottlerocket-ami-public-parameters-resolve-to-image-ids.

=== Cause 2 of 4: CancelMaintenanceWindowExecution is an unimplemented scaffold stub answering 501 NotImplemented where AWS refuses an unknown execution id with DoesNotExistException ===
AWS: Smithy com.amazonaws.ssm#CancelMaintenanceWindowExecution — input WindowExecutionId (MaintenanceWindowExecutionId, required, @length 36, UUID @pattern), output WindowExecutionId; modeled client error DoesNotExistException (httpError 400), documented as "Error returned when the ID specified for a resource, such as a maintenance window or patch baseline, doesn't exist". Recorded behavior: a well-formed UUID that is not a live window execution is refused HTTP 400, Error.Code DoesNotExistException, Message "Resource does not exist in the data store." — entirely fixed text, carrying nothing from the request.
Emulator: the call answers HTTP 501 with Error.Code NotImplemented. services/service-com-amazonaws-ssm-amazonssm/src/ops/cancel_maintenance_window_execution.rs still carries the `//! SCAFFOLDED, NOT IMPLEMENTED` marker and its handle() body is `Err(crate::scaffolded::Scaffolded::not_implemented("CancelMaintenanceWindowExecution"))`.
Why: the operation is unusable and, worse, unobservably so: a client cannot cancel a window execution, and its negative path cannot be told apart from an emulator outage — 501 is not a modeled outcome of this operation, so retry/error-classification code written against AWS takes the server-error branch instead of the not-found branch. It also blocks the rest of a maintenance-window lifecycle check from reaching the task deregistration and dead-id reads that follow it.
Fix: implement the handler in services/service-com-amazonaws-ssm-amazonssm/src/ops/cancel_maintenance_window_execution.rs (resolve the WindowExecutionId in the maintenance-window state, cancel the execution and its not-yet-started tasks, else return DoesNotExistException with AWS's sentence) and delete the SCAFFOLDED marker. Note 20261122T161603Z-ssm-2-net-new-causes-a-maintenance-window.md covers the scheduler never MINTING a window execution; it does not carry this check's replay key and does not cover this operation being a 501 stub.
Traces: ssm.maintenance-window-task-update-and-schedule (assertion `assert code == "DoesNotExistException"` got "NotImplemented").

=== Cause 3 of 4: PutParameter accepts the advanced-only data types json and jsonc on a Standard-tier parameter ===
AWS: Smithy com.amazonaws.ssm#PutParameter — DataType targets ParameterDataType, a plain string with @length 0-128 and no enum, so the data-type set is open; what the service holds a put to is the value's form and the TIER the data type may be declared in. Recorded behavior (and https://docs.aws.amazon.com/systems-manager/latest/userguide/parameter-store-data-types.html): url, json and jsonc are advanced-tier-only data types, so PutParameter with Tier="Standard" and one of them is refused HTTP 400 ValidationException with "The <data type> data type is only supported for advanced parameters." — fixed text "The " + " data type is only supported for advanced parameters." with the data-type name taken from the request — and nothing is written (a following GetParameter is ParameterNotFound). The same DataType and value succeed with Tier="Advanced".
Emulator: only `url` is gated. services/service-com-amazonaws-ssm-amazonssm/src/state/parameter_data_types.rs defines ADVANCED_ONLY_DATA_TYPES = [DATA_TYPE_URL], so a Standard-tier put declaring DataType="json" (and "jsonc") is ACCEPTED: HTTP 200 {Version: 1, Tier: "Standard"} and the parameter is created.
Why: the tier rule is silently not enforced, so a client gets a standard-tier parameter AWS would never have created; code that depends on the refusal to decide it must upgrade the parameter's tier never sees it, and the account's tier accounting diverges from AWS's.
Fix: the advanced-only data-type set used by the PutParameter tier gate (ADVANCED_ONLY_DATA_TYPES / tier_rejection in services/service-com-amazonaws-ssm-amazonssm/src/state/parameter_data_types.rs) — include json and jsonc beside url; the message helper already renders AWS's sentence. The open issue 20261117T140330Z-ssm-6-net-new-behavioral-causes-putparameter-refuses.md described the OPPOSITE failure mode for this check (every typed data type refused with a closed-allow-list message); the emulator now accepts these two instead of refusing them, and that issue's replay key no longer matches, so this cause is net-new and not covered by it.
Traces: ssm.put-parameter-advanced-only-data-types-rejected-on-standard-tier.

=== Cause 4 of 4: PutParameter validates a value against its DataType for `integer` only — nine other typed data types accept a malformed value and advance the parameter's version ===
AWS: same operation and the same open DataType member; recorded behavior is that the declared data type states the FORM of the value and a value outside it is refused HTTP 400 ValidationException, each data type with its own entirely fixed sentence: aws:region -> "The parameter value is not a valid AWS Region. Please check https://docs.aws.amazon.com/global-infrastructure/latest/regions/aws-regions.html for the list of valid regions."; aws:account:id -> "The parameter value is not a valid AWS account ID."; boolean -> "The parameter value is not a valid boolean. Accepted values are true, True, TRUE, false, False, FALSE, 1 and 0."; float -> "The parameter value is not a valid float. A value must be a decimal number such as 1.5, .5 or 2.5e-8, with an optional minus sign and no leading zeros. NaN and Infinity are not accepted."; binary -> "The parameter value is not a valid binary number. A value must be one or more binary digits, 0 or 1, with no prefix, sign, separator or whitespace."; hostname -> "The parameter value is not a valid host name. It contains an underscore, which host names do not allow."; email -> "The parameter value is not a valid email address. It contains whitespace or a control character."; ipv4-address -> "The parameter value is not a valid IPv4 address. It may contain only the digits 0 to 9 and dots."; ipv6-address -> "The parameter value is not a valid IPv6 address. It may contain only hexadecimal digits, colons, and the dots of an embedded IPv4 address. Zone IDs, brackets and prefix lengths are not accepted." The refusal happens before anything is written, so the parameter keeps its previous value and its version does not advance.
Emulator: value_rejection() in services/service-com-amazonaws-ssm-amazonssm/src/state/parameter_data_types.rs matches only DATA_TYPE_INTEGER and returns None for every other data type, so an Overwrite put of a malformed value under any of the nine types above is ACCEPTED: HTTP 200 {Version: 2, Tier: "Standard"}, and the stored value becomes the malformed one.
Why: typed parameters exist precisely so Parameter Store rejects a bad region, account id, boolean, address or host name at write time. Here every such write succeeds, so the store accumulates values AWS would have refused, the parameter's version counter diverges, and any consumer that trusts the data type (a launch template reading an ipv4-address, a pipeline reading aws:region) is handed a value that cannot be used.
Fix: the per-type value validators behind value_rejection() in services/service-com-amazonaws-ssm-amazonssm/src/state/parameter_data_types.rs (reached from the PutParameter handler) — implement one form test and one sentence per documented data type, exactly as `integer` already is, and refuse before the write so no version is allocated. Same note as Cause 3 regarding 20261117T140330Z-ssm-6-net-new-behavioral-causes-putparameter-refuses.md: it recorded these types being refused outright; they are now accepted without validation.
Traces: ssm.put-parameter-rejects-malformed-typed-values.
