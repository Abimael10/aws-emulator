# DocDB Elastic tag-op not-found refusals serve an x-amzn-errortype that fails the recorded shape, and UntagResource also the wrong Content-Type

> _Note: this issue was identified against the code base at commit `a1915270e40223bfb23a5a7de86fe74aa15a3df0`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
TagResource

## Description
The DocDB Elastic error path for the ARN-addressed tag operations (POST/DELETE /tags/{resourceArn}) refuses an ARN no resource carries with the correct status and error class (404 / ResourceNotFoundException) but stamps response HEADERS a real restJson1 DocDB Elastic response never carries. Both causes below are the same shared service-wide error-serializer fault seen on two operations, and the tag-delete path adds a second wrong header on top. This bundle contains 2 causes; BOTH must be closed before submitting.

Shared AWS requirement - x-amzn-errortype: the Smithy model says nothing about this header (the service only @cors-exposes x-amzn-errortype, alongside x-amzn-requestid and x-amzn-trace-id), so for the header this is recorded behavior only. The corpus asserts the header's SHAPE rather than a literal value, and the stable part of that shape is that the value's LEADING token is the error code of the modeled error being served - here exactly 'ResourceNotFoundException', fixed text taken from the error shape name (Smithy: com.amazonaws.docdbelastic#ResourceNotFoundException, @error client, httpError 404, required members message/resourceId/resourceType) with nothing in it drawn from the request or from emulator state. The recorded shape is a QUALIFIED value: a bare error code with no qualifier does not satisfy it, and the qualifier's own text is environment-dependent and is NOT itself the requirement. Hypothesis: AWS serves the code followed by a ':'-separated qualification of the modeled error shape (e.g. the shape id), so only the leading code is stable across runs; an Amazon-internal Coral namespace URL is not part of the public contract either. Note the oscillation here: a now-resolved issue (20261104T053156Z-docdb-elastic-error-serializer-emits-a-coral-namespace.md) removed the Coral URL suffix and left the header as the bare code - which still fails the same shape assertion. The fix must satisfy the recorded SHAPE (code + qualifier), not flip between two literals.

Shared AWS requirement - Content-Type: Smithy ChimeraDbLionfishServiceLambda (sdkId "DocDB Elastic", version 2022-11-28) declares protocols [restJson1] over sigv4 with no @mediaType override, so a JSON response payload - on the success path and on the modeled-error path alike - is announced as Content-Type: application/json. That string is fixed text of the protocol; no part of it comes from the request or from state.

Cause 1 of 2: TagResource against an ARN no resource carries (fixture docdb-elastic-tag-resource-ops-missing-cluster-not-found, step task#1).
AWS: 404 ResourceNotFoundException. Smithy: TagResource is POST /tags/{resourceArn} with resourceArn @required @httpLabel @length 1-1011 and tags @required (TagMap); errors ResourceNotFoundException (404), ValidationException (400), ThrottlingException (429), InternalServerException (500). The refusal carries an x-amzn-errortype whose leading token is the fixed error code 'ResourceNotFoundException', in the qualified shape the recording asserts.
Emulator: status 404, error class and this response's content-type are correct, but x-amzn-errortype is the bare 'ResourceNotFoundException', which does not satisfy the recorded header shape (replay: $headers.x-amzn-errortype shape_mismatch, expected '<shaped-not-asserted>', got 'ResourceNotFoundException'; divergence_key service=docdb-elastic|TagResource|status=404->404|keys=$headers.x-amzn-errortype).
Why: x-amzn-errortype is the header SDKs, proxies and log pipelines read to classify an error BEFORE parsing the body. A client that validates the header's shape (or splits it at ':'/'#' and requires the qualified form AWS serves) sees a value AWS never serves and falls into a generic-failure branch instead of the not-found branch, so retry policy and resource-provisioning logic keyed on ResourceNotFoundException takes the wrong path against the emulator but the right one against AWS.
Fix: the DocDB Elastic crate's restJson1 error-response serializer - the single place x-amzn-errortype is written for this service's modeled errors - not the TagResource handler, whose status, error selection and body are already correct.

Cause 2 of 2: UntagResource against an ARN no resource carries (fixture docdb-elastic-tag-resource-ops-missing-cluster-not-found, step task#3).
AWS: 404 ResourceNotFoundException. Smithy: UntagResource is DELETE /tags/{resourceArn}, @idempotent, resourceArn @required @httpLabel @length 1-1011 and tagKeys @required @httpQuery 'tagKeys' @length 0-50, with the same ResourceNotFoundException at httpError 404. The refusal carries Content-Type: application/json and an x-amzn-errortype leading with the fixed code 'ResourceNotFoundException' in the recorded qualified shape.
Emulator: 404 with the right error class, but the response announces content-type 'application/x-amz-json-1.1' where a restJson1 service answers 'application/json', AND x-amzn-errortype is the bare 'ResourceNotFoundException', failing the shape assertion (replay: $headers.content-type value_mismatch expected 'application/json' got 'application/x-amz-json-1.1'; $headers.x-amzn-errortype shape_mismatch expected '<shaped-not-asserted>' got 'ResourceNotFoundException'; divergence_key service=docdb-elastic|UntagResource|status=404->404|keys=$headers.content-type,$headers.x-amzn-errortype).
Why: in addition to the error-classification breakage of Cause 1, a client that dispatches on the response media type (strict SDK/middleware media-type checks, proxies, content negotiation, cassette matching) sees a media type AWS never serves for a restJson1 service, so a byte-identical body is handled differently than against AWS. The tag-delete path is also the only one of the three tag ops still announcing the awsJson media type, so the media-type fault is not uniformly fixed across the service.
Fix: same shared restJson1 error-response serializer for this service - it must announce application/json on the modeled-error path and emit an x-amzn-errortype in the shape AWS serves; the UntagResource handler's status, error selection and body need no change.
