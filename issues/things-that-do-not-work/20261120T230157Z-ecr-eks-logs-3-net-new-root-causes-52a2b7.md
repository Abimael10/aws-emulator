Cause 1 of 3: enabling control-plane log type 'api' with UpdateClusterConfig on a CloudFormation-provisioned cluster never creates /aws/eks/<cluster>/cluster, and no kube-apiserver-* log stream ever appears.
AWS: Smithy (services/service-com-amazonaws-eks-awswesleyfrontend): UpdateClusterConfig POST /clusters/{name}/update-config -> 200 {update: Update}; input member logging targets Logging{clusterLogging: list<LogSetup>}, LogSetup{types: list<LogType>, enabled: BoxedBoolean}, LogType enum values api|audit|authenticator|controllerManager|scheduler. LogSetup.enabled is documented 'If a log type is enabled, that log type exports its control plane logs to CloudWatch Logs. If a log type isn't enabled, that log type doesn't export its control plane logs.' DescribeUpdate GET /clusters/{name}/updates/{updateId} reports the update, whose status reaches Successful. AWS therefore (a) creates no control-plane log group while every log type is disabled — the template in this check declares no Logging property at all — and (b) once the update succeeds, creates the CloudWatch Logs group named /aws/eks/<clusterName>/cluster and begins writing streams whose names start with kube-apiserver-. The group name is a template: '/aws/eks/' and '/cluster' are its fixed text, the cluster name is the value taken from the request; the stream-name prefix 'kube-apiserver-' is fixed and the suffix is a per-run id.
Emulator: the check deploys the cluster through CloudFormation (AWS::EKS::Cluster with no Logging property), confirms the group is absent, calls UpdateClusterConfig with clusterLogging [{types:['api'], enabled:true}], then polls logs DescribeLogGroups(logGroupNamePrefix='/aws/eks/<cluster>/cluster') and DescribeLogStreams(logStreamNamePrefix='kube-apiserver-'). Neither the group nor any stream was ever observed; the check was still polling the empty state when the budget cut it off.
Why: a client that enables control-plane logging to drive audit or observability tooling sees DescribeLogGroups return no matching group and DescribeLogStreams return an empty logStreams list forever, so any consumer tailing control-plane logs — or any assertion that logging is now on — can never make progress against the emulator although the same code works on AWS.
Fix: the eks UpdateClusterConfig handler's logging side-effect and the state it shares with cloudwatchlogs — on the update reaching Successful it must materialise the /aws/eks/<cluster>/cluster group in logs state and emit at least one kube-apiserver-<id> stream; the CloudFormation AWS::EKS::Cluster resource handler must route to that same side-effect so a CFN-created cluster behaves like a CreateCluster one.
Traces: ecr__eks__logs.deploy-eks-cluster-without-logging-config-no-log-groups.

Cause 2 of 3: no Container Insights performance data is ever delivered — /aws/containerinsights/<cluster>/performance stays empty after the amazon-cloudwatch-observability add-on is ACTIVE with a pod-identity role carrying CloudWatchAgentServerPolicy, and it also stays empty after the missing permission is attached in the negative-control check.
AWS: recorded behavior only — the EKS Smithy model describes CreateAddon and CreatePodIdentityAssociation but not the add-on's data-plane emissions. The recordings show that once the cluster, the managed nodegroup, the eks-pod-identity-agent add-on and the amazon-cloudwatch-observability add-on are all ACTIVE and a pod identity association maps namespace amazon-cloudwatch / serviceAccount cloudwatch-agent to a role carrying arn:aws:iam::aws:policy/CloudWatchAgentServerPolicy, the CloudWatch Logs group /aws/containerinsights/<clusterName>/performance receives events whose message bodies parse as Embedded Metric Format records containing a CloudWatchMetrics key and a ClusterName equal to the cluster's name. The group name is a template: '/aws/containerinsights/' and '/performance' are fixed text, the cluster name is the request value. The negative control records the mirror image: with an agent role lacking CloudWatch write permission the group receives nothing, and after that policy is attached to the same role delivery starts without anything being recreated.
Emulator: both checks poll GetLogEvents/FilterLogEvents on that group (a deny window and then a delivery window, each minutes long). No performance event was ever observed in either check, so the positive assertion (performance events parse as EMF records tagged ClusterName=<cluster>) can never be satisfied and the negative control can never reach its post-attachment delivery half. Both ended on the suite budget while still polling an empty group.
Why: a client validating Container Insights — a dashboard, an alarm on an EMF-derived metric, or a test that the agent role's permissions are correct — observes a permanently empty log group and cannot distinguish 'permission denied' from 'the observability add-on produces nothing', which is exactly the distinction the negative control exists to make.
Fix: the eks add-on state machine's data-plane emission for amazon-cloudwatch-observability and the pod-identity authorization it consults — it must write EMF records into cloudwatchlogs state under /aws/containerinsights/<cluster>/performance, gated on the associated role's CloudWatch write permission.
Traces: ecr__eks__logs.eks-container-insights-metrics-logs-delivery, ecr__eks__logs.eks-container-insights-without-agent-permission-no-delivery.

Cause 3 of 3: a pod never reports an image-pull outcome for a private ECR image — no 'Pulled' event on a Fargate-profile pod whose pod execution role is authorized, and no pull-failure outcome on a pod whose node role lacks ECR permission.
AWS: Smithy: CreateFargateProfile POST /clusters/{clusterName}/fargate-profiles -> 200 {fargateProfile: FargateProfile}; FargateProfile carries podExecutionRoleArn, documented as 'The Amazon Resource Name (ARN) of the Pod execution role to use for any Pod that matches the selectors in the Fargate profile', plus selectors and status: FargateProfileStatus. Recorded behavior: with the profile ACTIVE, no nodegroup and no imagePullSecrets, a pod scheduled onto it pulls its private ECR image through that role (AmazonEKSFargatePodExecutionRolePolicy) and the cluster's Kubernetes API reports a core/v1 Event whose reason is 'Pulled', naming the image; when the role carries no ECR BatchGetImage/GetDownloadUrlForLayer permission the pull is refused and the pod reports the pull failure instead (reason 'Failed' with an ECR authorization message) rather than silently never progressing. 'Pulled' and 'Failed' are the fixed reason strings; the image reference and pod name are values from the request.
Emulator: both checks stand the cluster up (and for the Fargate case the private subnets and Fargate profile), create the pod, then poll the served cluster Kubernetes API for that pod's events for minutes. No pull outcome — neither success nor refusal — was ever observed; both checks were cut off by the suite budget while polling.
Why: a client cannot tell an authorized pull from an unauthorized one, because both look like a pod stuck with no events. Any workflow that gates on the pull result — waiting for a pod to run, or asserting that a missing ECR permission is what broke it — hangs instead of resolving, and the negative control that proves authorization is enforced cannot be expressed at all.
Fix: the served cluster Kubernetes API's pod admission/runtime path and the ECR authorization it consults — a pod must progress to an image-pull attempt and record the resulting core/v1 Event (reason 'Pulled' on success, a pull-failure Event when the pod execution or node role is not authorized for the repository).
Traces: ecr__eks__logs.eks-fargate-execution-role-pulls-ecr-image, ecr__eks__logs.eks-pod-image-pull-fails-without-ecr-permission-rejected.
