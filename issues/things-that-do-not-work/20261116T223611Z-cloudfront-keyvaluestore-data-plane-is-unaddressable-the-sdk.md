# cloudfront-keyvaluestore data plane is unaddressable: the SDK-derived host <accountId>.<endpoint-authority> is not an address the emulator serves, so all 46 KVS behavioral checks abort before any request is sent

> _Note: this issue was identified against the code base at commit `632c4df423382c9e7bd6d219524f5d2a3f63c78e`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
DescribeKeyValueStore

## Description
ONE root cause, grounded in all 46 failing cloudfront-keyvaluestore behavioral checks (Cause 1 of 1). Every check reaches the CloudFront control plane successfully (CreateKeyValueStore returns an ARN and DescribeKeyValueStore polls the store to READY) and then dies on its FIRST cloudfront-keyvaluestore data-plane call, before any HTTP request leaves the client: the host the SDK resolves for that call is not an address the emulator offers.

AWS: Smithy, services/service-com-amazonaws-cloudfrontkeyvaluestore-cloudfrontkeyvaluestore (com.amazonaws.cloudfrontkeyvaluestore#CloudFrontKeyValueStore, restJson1, sigv4Name cloudfront-keyvaluestore). The service shape carries smithy.rules#endpointBdd / smithy.rules#endpointRuleSet whose parameters are KvsARN, Region, UseFIPS and Endpoint (builtIn SDK::Endpoint). The ruleset parses KvsARN (aws.parseArn) and requires service == "cloudfront", an EMPTY region, resourceId[0] == "key-value-store" and partition "aws"; it then resolves, when no endpoint override is configured, the endpoint url "https://{parsedArn#accountId}.cloudfront-kvs.global.api.aws", and when Endpoint IS set, the url "{url#scheme}://{parsedArn#accountId}.{url#authority}{url#path}" — in both branches with properties.authSchemes [{name: sigv4a, signingName: cloudfront-keyvaluestore, signingRegionSet: ["*"]}]. So for EVERY one of the six data-plane operations (DescribeKeyValueStore GET /key-value-stores/{KvsARN}, GetKey, PutKey, DeleteKey, ListKeys, UpdateKeys) the request is addressed to a VIRTUAL HOST formed by prefixing the account id taken from the request's KvsARN to the endpoint authority. This is not optional client behavior: it is the modeled endpoint resolution every AWS SDK/botocore client performs, and real AWS answers on that account-prefixed host (wildcard under cloudfront-kvs.global.api.aws). The account id in the host is a value taken from the request's KvsARN; the authority is whatever endpoint the client is pointed at.

Emulator: the CloudFront control plane returns a well-formed store ARN of the form arn:aws:cloudfront::<accountId>:key-value-store/<id> (the emulator's account id, observed as 000000000000), the store reaches Status READY, and then the data-plane client resolves the modeled host <accountId>.<endpoint-authority> — which the emulator does not serve and does not announce. The harness's egress layer refuses it: "CapabilityNotOffered: the target serves no address for 000000000000.127.0.0.1" / "egress refused: '000000000000.127.0.0.1' is not the endpoint under test (127.0.0.1); an emulator run may reach only the emulator. If the host came from a URL the emulator returned, the emulator announces an address other than the endpoint it is reached on" (simparity.egress.EgressRefused). The host here is derived from the ARN the emulator itself returned, so the emulator is announcing a data-plane address other than the one it is reachable on. Nothing is delivered: there is no HTTP status, no error code and no body — a strictly worse outcome than the earlier recorded refusals of this same data plane (404 UnknownService, then 403 AccessDenied "Sign the request with the emulator credentials").

Why: no AWS client can talk to this service's data plane at all. Every SDK applies the ruleset above, so DescribeKeyValueStore, GetKey, PutKey, DeleteKey, ListKeys and UpdateKeys are unreachable; in particular the ETag that every conditional write (PutKey/DeleteKey/UpdateKeys IfMatch) requires can never be obtained, so the entire KVS workflow is impossible. The failure also surfaces to the client as an endpoint/name-resolution error rather than any modeled AWS error, so retry, create-or-repair and error-classification paths that a client builds around AccessDeniedException / ResourceNotFoundException / ValidationException never engage. Because the requests are never delivered, every behavioral expectation of this service is unverified: store counters (ItemCount, TotalSizeInBytes) and their byte-exact deltas, ETag bump-per-mutation and stale-ETag precondition failures (ValidationException "Pre-Condition failed during update of Key-Value-Store"), absent-key reads (ResourceNotFoundException "No such Key exists") and absent/deleted-store reads (ResourceNotFoundException "No such Key-Value-Store exists"), ListKeys default page size of ten and MaxResults @range 1..50 validation, NextToken handling, UpdateKeys atomicity and duplicate-key/batch-size/quota rejections, and the sigv4a signing path the ruleset selects.

Fix: the emulator's front-door host handling and served-address announcement for the cloudfrontkeyvaluestore crate. It must accept and route data-plane requests whose Host is the account-id-prefixed virtual host <accountId>.<endpoint-authority> (the same shape of fix S3 virtual-hosted-style buckets need), and it must declare that address among the ones it serves so the run can reach it; the CloudFront control plane's ARN construction (the account id it embeds in KeyValueStore.ARN) and the data-plane handlers' KvsARN resolution must agree with whatever the front door accepts, and the auth layer must accept the sigv4a scheme the ruleset selects once requests arrive. The host and port in the quoted message are per-run environment values and are NOT the requirement; the requirement is that the host the modeled ruleset derives from the KvsARN reaches the emulator.
