# glue: 2 net-new causes — a Glue ETL run over data its script cannot convert still ends SUCCEEDED, and Get/CancelDataQualityRulesetEvaluationRun skip RunId format validation

## Operation

## Description
Two net-new root causes on the glue emulator, both surfaced by behavioral checks the replay reports as unowned (no OWNED-by issue, no unimplemented-stub marker). Neither is covered by an open issue; the nearest items are named per cause below.

Cause 1 of 2 (severity HIGH): a Glue ETL job run does not fail when the script's own data conversion fails — the run settles SUCCEEDED with no ErrorMessage.
Failing check: glue.glue-job-rejects-a-type-violating-source-row-and-writes-no-output-or-partition.
AWS: recorded behavior only for the run outcome — the Smithy model fixes only the carrier, not the semantics: StartJobRun returns JobRunId; GetJobRun returns JobRun, whose JobRunState (JobRunState enum) and ErrorMessage (ErrorString) report how the run ended. The behavior AWS exhibits, and which the check's own positive control establishes within the same job, is that the job run's terminal state is derived from the script's execution: the SAME glueetl job (Glue 4.0, G.1X, 2 workers) run over clean CSV ends JobRunState 'SUCCEEDED' and writes its Parquet output plus one catalog partition per partition-key value, while the run over a source differing in exactly ONE cell — a row whose `amount` column holds a non-numeric string, cast to double under spark.sql.ansi.enabled=true — ends JobRunState 'FAILED' with an ErrorMessage that names the offending value, and leaves NO output object under the sink prefix and NO registered partition on the target table. The requirement is the state/error pair and the absence of the side effects: terminal JobRunState 'FAILED', and an ErrorMessage whose variable part is the unconvertible cell value taken from the job's input (here the literal from the source row); the fixed text is whatever Spark/Glue words for an ANSI cast failure. A run that produced no data must register no partition and must not rewrite the target table's StorageDescriptor.Location.
Emulator: the arm run reaches terminal JobRunState 'SUCCEEDED' and GetJobRun reports ErrorMessage None — the replay asserts "the run over a source whose row 7 carries amount='not-a-number' ended 'SUCCEEDED', expected 'FAILED'; error was None". The control arm passed (it reached SUCCEEDED, wrote objects and registered the three expected partitions), so the emulator does model a run's effects; what it does not do is read the source bytes or evaluate the script's conversions, so the terminal state is independent of the input data and every run of a valid job definition succeeds.
Why: a client that uses JobRunState to gate a pipeline gets a false green. Data-quality and schema-drift handling is driven entirely off FAILED runs: a run over corrupt input is reported as successful, no retry, alert or quarantine branch fires, and downstream consumers read a table whose partitions were announced for data the run never produced. Code that parses ErrorMessage to decide whether a failure is retryable (transient) or a data defect (poison input) never sees a message at all. The negative half of every Glue ETL test suite silently passes.
Fix: the Glue job-run execution component — the simulated run's terminal-state derivation in the StartJobRun/job-run driver and the state it writes (output objects and catalog partitions on the sink's target table). The run outcome must be a function of executing the script over the source the catalog table points at, so a conversion/runtime failure yields JobRunState FAILED with an ErrorMessage naming the offending value, and the run's sink effects (S3 objects under the output prefix, partitions on the target table, the target's Location) are not applied for a failed run. Related but NOT covering this: the open issues 20261025T000830Z-glue-job-runs-are-recorded-but-never-executed.md, 20261029T185330Z-glue-job-runs-are-recorded-but-never-executed-e42472.md and 20261025T072821Z-glue-job-runs-are-terminated-failed-without-executing.md all describe the OPPOSITE condition (runs settling FAILED with an emulator-authored ErrorMessage without executing); this cause is a run that settles SUCCEEDED when AWS fails it, and the replay reports it unowned.
Traces: glue.glue-job-rejects-a-type-violating-source-row-and-writes-no-output-or-partition (the arm run, after the clean-input control run in the same check passed).

Cause 2 of 2 (severity MEDIUM): GetDataQualityRulesetEvaluationRun and CancelDataQualityRulesetEvaluationRun perform no RunId format validation, so a malformed id is answered as a lookup miss instead of an input rejection.
Failing check: glue.data-quality-ruleset-evaluation-run-lookup-rejections.
AWS: Smithy: GetDataQualityRulesetEvaluationRun / CancelDataQualityRulesetEvaluationRun input RunId (HashString, @required, @length 1..255, @pattern ^[\u0020-\uD7FF\uE000-\uFFFD\uD800\uDC00-\uDBFF\uDFFF\t]*$); both model InvalidInputException (client, HTTP 400) AND EntityNotFoundException (client, HTTP 400). AWS distinguishes the two: a RunId outside the issued id shape — it does not carry the 'dqrun-' prefix every data-quality evaluation run id has — is a FORMAT rejection, InvalidInputException with the message "Invalid RunId: must start with 'dqrun-'" (all fixed text; no request- or state-derived part), raised before any lookup; a RunId that IS in shape ('dqrun-' + hex) but was never issued is a LOOKUP failure, EntityNotFoundException with "Cannot find Data Quality Run in account <accountId> with id <runId>", whose fixed text is "Cannot find Data Quality Run in account " / " with id " and whose two variable parts are the caller's account id and the RunId from the request. The check also pins that BatchGetDataQualityRulesetEvaluationRun treats the same in-shape-but-absent id as RunsNotFound rather than an error, so the three operations must not share one code path.
Emulator: the malformed-id call is answered with the lookup error instead of the format error — replay: expected ('InvalidInputException', "Invalid RunId: must start with 'dqrun-'"), got ('EntityNotFoundException', 'Cannot find Data Quality Run in account <accountId> with id <the malformed id>'). The emulator reaches the run table with whatever string it was given, misses, and reports a not-found; it never applies the id-shape precondition. The same handling is expected on CancelDataQualityRulesetEvaluationRun, whose assertion is the next one in the check.
Why: the two errors mean opposite things to a client. InvalidInputException says "your request is malformed, fix the id and never retry"; EntityNotFoundException says "the id is well-formed but gone — it may have expired, or you may be in the wrong account/region". A caller that threads a truncated, mis-copied or wrong-service identifier into these operations is told the run does not exist, so it re-polls, walks the wrong account, or reports a missing run to an operator instead of a bad identifier. Error-class dispatch and tests that assert the rejection class both take the wrong branch.
Fix: the input validation of the GetDataQualityRulesetEvaluationRun and CancelDataQualityRulesetEvaluationRun handlers — enforce the issued RunId shape ('dqrun-' prefix) up front and raise InvalidInputException (400) with AWS's fixed message before the run lookup runs, keeping EntityNotFoundException for in-shape ids that are absent and leaving BatchGetDataQualityRulesetEvaluationRun's RunsNotFound partitioning intact. Adjacent but NOT covering this: open issue 20261123T140534Z-glue-connection-type-and-data-quality-batch-reads.md names only BatchGetDataQualityRulesetEvaluationRun's missing RunIds validation (a wire-corpus finding on a different operation); it does not name Get or Cancel, and the replay reports this check unowned.
Traces: glue.data-quality-ruleset-evaluation-run-lookup-rejections.
