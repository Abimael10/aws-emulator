# emr: 2 net-new causes — an EMR Serverless sparkSubmit job run never reaches a terminal JobRunState (3 checks cut off at the cap), and a session with SessionIdleTimeoutInMinutes=1 never becomes active nor auto-terminates

> _Note: this issue was identified against the code base at commit `8cbf0dcd0020846f13fa76c0319ab04fca2e29a2`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
StartJobRun/GetJobRun/StartSession/GetSession

## Description
Four behavioral checks under the suite's '### emr' heading fail for two distinct root causes. None of the four is marked ALREADY FILED or OWNED by an open issue in this suite report; related open/fixed issues are named per cause and none of them carries these checks' replay keys.

Cause 1 of 2: an EMR Serverless `sparkSubmit` job run never reaches a terminal `JobRunState` inside the window a client (or the suite) waits in — three checks are cut off at the harness cap with the run still non-terminal.
Failing checks: emr.emr-serverless-spark-job-run-reaches-success, emr.emr-serverless-failing-script-reports-failed-and-writes-no-output, emr.emr-serverless-start-job-run-on-stopped-non-autostart-application-is-rejected (all three 'Check timed out after 60.0s').
AWS: Smithy (com.amazonaws.emrserverless#AwsToledoWebService) models StartJobRun as the submit of one unit of work and `JobRunState` = SUBMITTED | PENDING | SCHEDULED | RUNNING | SUCCESS | FAILED | CANCELLING | CANCELLED | QUEUED; `JobRun$state` and `JobRun$stateDetails` are both @required (stateDetails is String256, @length 1..256, pattern ".*\\S.*"), `JobRun$totalExecutionDurationSeconds` is documented as available "for job runs in a COMPLETED, FAILED, or CANCELLED state", `JobRun$startedAt` is "when the job moved to the RUNNING state" and `endedAt` "when the job was terminated". A minimal PySpark entry point (one `parallelize([...],1).saveAsTextFile(out_uri)`) submitted to a STARTED SPARK application settles in SUCCESS, with part-* objects under the output prefix, in well under a minute on AWS; an entry point that raises after building a SparkSession settles FAILED carrying the driver's own exception in stateDetails. Both are terminal states a poll reaches promptly — that promptness is the contract these checks rest on, including the third check, whose refusal assertions (ValidationException "Job run cannot be started as Application is not in STARTED state and auto-start is disabled", empty ListJobRuns, unchanged application state) pass and which is then cut off waiting for its byte-identical control run to settle.
Emulator: every one of the three scenarios is killed at the 60.0 s cap with no terminal state ever observed through GetJobRun — the run is accepted, walks the emulator's non-terminal stages and then sits there. The emulator's own code states the mechanism: services/service-com-amazonaws-emrserverless-awstoledowebservice/src/state.rs documents that no terminal state is owed by the clock ('what a run comes to REST in is ... what RUNNING the work the submit named came to'), and src/state/spark_job_run.rs documents 'A run whose workload has not answered never reaches a terminal state at all'. The call that starts the workload waits only WORKLOAD_FIRST_WAIT = 2 s, while one run may hold the host for WORKLOAD_HOST_CEILING = (INIT_PHASE_LIMIT + WORKLOAD_RUN_CEILING(60 s)) x 3, plus WORKLOAD_STOP_GRACE = 5 s before the emulator gives up on it (WORKLOAD_HOST_WAIT). Hypothesis: the in-process Spark execution of these entry points does not answer within that first 2 s slice, so the run stays RUNNING for minutes of host time — longer than the whole scenario's budget — and no read settles it meanwhile; the alternative reading of the same evidence is that the execution never answers at all.
Why: a client that submits a Spark job and polls for a terminal state — the only documented way to learn a job's outcome — never gets one. Neither the success path (SUCCESS, non-zero totalExecutionDurationSeconds, the driver's S3 writes) nor the failure path (FAILED with the driver's exception in stateDetails) is observable, so no EMR Serverless workflow, CI gate or orchestrator built on StartJobRun can complete or fail; it just hangs. The third check shows the blast radius: even a correctly-served refusal contract cannot be proven, because its positive control never settles.
Fix: the EMR Serverless job-run execution and settlement path — services/service-com-amazonaws-emrserverless-awstoledowebservice/src/state/spark_job_run.rs together with the settlement GetJobRun/ListJobRuns perform (src/ops/get_job_run.rs, src/ops/list_job_runs.rs) and the stage/terminal-state bookkeeping in src/state.rs. A submitted sparkSubmit run must reach a terminal state promptly enough for a polling client: SUCCESS with startedAt/endedAt and a non-zero totalExecutionDurationSeconds when the entry point completes, FAILED with the driver's exception text in stateDetails when it raises, and the executed driver's writes must land under the requested s3:// output prefix. A workload this emulator cannot answer for must be settled into a terminal state rather than left RUNNING forever.

Also related: 20261113T102950Z-athena-emr-serverless-glue-s3-an-emr-serverless.md (open). A fixer should close them together if one change covers all.

Cause 2 of 2: an EMR (on EC2) Spark Connect session started with SessionIdleTimeoutInMinutes=1 is never observed in an active state and is never auto-terminated — the check is cut off at the 600 s cap while polling GetSession.
Failing check: emr.session-idle-timeout-marks-session-stopped ('Check timed out after 600.0s').
AWS: Smithy com.amazonaws.emr#Session models `State` (@required) over SessionState = SUBMITTED | STARTING | STARTED | IDLE | BUSY | TERMINATING | TERMINATED | FAILED, with `StartedAt` = "the date and time that the session entered the STARTED state", `IdleSince` = "the date and time that the session last entered the IDLE state", `EndedAt` = "the date and time that the session was terminated or failed", `StateChangeReason` = "a human-readable message describing the most recent state change", and `SessionIdleTimeoutInMinutes` (also on StartSession's input) documented as "The idle timeout, in minutes. If the session is idle for this duration, Amazon EMR automatically terminates it." So a session started on a RUNNING/WAITING cluster first becomes observable in an active state (STARTED/IDLE/BUSY) and then, left untouched with no TerminateSession call, reaches TERMINATED on its own after the configured idle span — both transitions observable through GetSession.
Emulator: neither polled condition is ever satisfied. The scenario is killed at the 600 s cap: GetSession never reports the session in STARTED/IDLE/BUSY (nor FAILED/TERMINATED), so the automatic idle sweep is never reached either. The emulator serves these reads from memory and the other 219 checks of this service complete, so the budget is not the constraint.
Why: a client cannot use a Spark Connect session at all — it never becomes usable — and a client relying on EMR reclaiming idle sessions waits forever for TERMINATED while, on AWS, the session would have been reclaimed after the configured minute. Any wait-for-ready or wait-for-reclaim loop written against AWS never returns.
Fix: the EMR session state machine behind StartSession/GetSession in services/service-com-amazonaws-emr-elasticmapreduce — the session record's timed state advancement (SUBMITTED/STARTING -> STARTED/IDLE, stamping StartedAt and IdleSince) and the idle-timeout sweep that moves an idle session to TERMINATED, stamping EndedAt and a StateChangeReason, materialised by the next GetSession/ListSessions read.
Related (does not cover this check): 20261110T214521Z-emr-8-net-new-root-causes-runjobflow-skips.md (open) describes exactly this cause as its cause 5 but carries only the sibling check emr.session-idle-ttl-expires-without-explicit-terminate's replay key — the report marks that sibling OWNED and this check not; and 20261110T142808Z-emr-3-net-new-root-causes-the-spark.md (fixed) claimed the Spark-Connect session lifecycle, which this check shows still does not advance. This is a timeout, not a refusal, so it is reported as a live divergence rather than a reopened refusal.
Traces: emr.session-idle-timeout-marks-session-stopped.

## Steps to Reproduce
Cause 1 (EMR Serverless job runs never settle):
1. Create an S3 bucket; PUT a PySpark entry point that writes argv[1] to argv[2] via spark.sparkContext.parallelize([argv[1]],1).saveAsTextFile(argv[2]); create an execution role trusted by emr-serverless.amazonaws.com and scoped to that bucket.
2. emr-serverless CreateApplication(name=<unique>, releaseLabel='emr-6.15.0', type='SPARK', maximumCapacity={cpu:'8 vCPU', memory:'32 GB'}, autoStartConfiguration={enabled:true}, autoStopConfiguration={enabled:true, idleTimeoutMinutes:1}); poll GetApplication past CREATING; StartApplication if needed and poll to STARTED.
3. StartJobRun(applicationId=<app>, clientToken=<tok>, executionRoleArn=<role>, name=<n>, jobDriver={sparkSubmit:{entryPoint:'s3://<bucket>/<script>', entryPointArguments:[<nonce>, 's3://<bucket>/job-output'], sparkSubmitParameters:'--conf spark.executor.cores=1 --conf spark.executor.memory=2g --conf spark.driver.cores=1 --conf spark.driver.memory=2g --conf spark.executor.instances=1'}}).
4. Poll GetJobRun(applicationId, jobRunId) for a state in {SUCCESS, FAILED, CANCELLED}: it never arrives — the run stays non-terminal for the whole window. On AWS it is SUCCESS, with totalExecutionDurationSeconds > 0 and exactly one part-* object under 'job-output/'.
5. Repeat step 3 with an entry point that builds a SparkSession, does real work, then raises: AWS settles the run FAILED with the driver's exception in stateDetails and writes no output object; the emulator never settles it.
6. Repeat with autoStartConfiguration={enabled:false}: StartJobRun on the CREATED application is correctly refused ValidationException 'Job run cannot be started as Application is not in STARTED state and auto-start is disabled' with ListJobRuns still empty; then StartApplication, re-submit the identical request and poll GetJobRun — the control run never settles either.

Cause 2 (EMR session idle timeout):
1. RunJobFlow with ReleaseLabel='emr-spark-8.0.0', Applications=[{Name:'Spark'}], session support enabled, into a subnet; poll DescribeCluster to WAITING.
2. StartSession(ClusterId=<cluster>, Name=<unique>, SessionIdleTimeoutInMinutes=1) and note the returned Id.
3. Poll GetSession(ClusterId, SessionId)['Session']['State']: it must reach STARTED/IDLE/BUSY. The emulator never reports any of them (nor FAILED/TERMINATED) within 600 s.
4. Leave the session untouched and keep polling GetSession: on AWS the state reaches TERMINATED on its own after the configured idle minute, with EndedAt and StateChangeReason set and no TerminateSession call made.
