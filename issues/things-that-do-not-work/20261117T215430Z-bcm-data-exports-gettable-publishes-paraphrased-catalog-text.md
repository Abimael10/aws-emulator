# bcm-data-exports GetTable publishes paraphrased catalog text, a wrong column Type and a missing column

> _Note: this issue was identified against the code base at commit `dd3127e4eb2b89b6f81c1a107309f0256c31ef57`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
GetTable

## Description
SIX net-new causes, all in the same component: the data-export TABLE CATALOG that `GetTable` reports (`services/service-com-amazonaws-bcmdataexports-awsbillingandcostmanagementdataexports/src/state/catalog.rs`, read by `src/ops/get_table.rs::handle` via `crate::state::table_spec` + `TableSpec::schema`). `GetTable` answers HTTP 200 with the right shape in every case; what diverges is the DATA inside `Schema`. Per Smithy (`GetTable` output member `Schema` -> `ColumnList` of `Column{Name,Type,Description}`; `Column$Description` = "The description for a column", `Column$Type` = "The kind of data a column stores"), these are response VALUES a client consumes, not documentation. The catalog's own module header already states the rule it is breaking: "every string below is the dictionary's PUBLISHED text for that column or property, carried over as published, rather than a shorter re-wording of it: a paraphrase is a different value on the wire", and "A column the dictionary publishes for a table and the catalog omits is a column a client cannot discover or ask for in an export definition, so the column SET is part of the published data just as the text is."

The general defect: the catalog was authored by RE-WORDING the AWS Data Exports table dictionary instead of carrying its published text over verbatim, it normalises the dictionary's paragraph breaks away, it publishes one type token for a column whose dictionary publishes another, and it drops a column from one schema entirely. There are no error codes or messages in play — every step is 200 vs 200.

Cause 1 of 6 — carbon-emissions schema column descriptions are re-worded (fixture `bcm-data-exports-catalog-get-table`, step `task#1`).
AWS: recorded behavior only (the model types `Column$Description` as free text and does not pin the catalog's contents; the recorded 200 response is the authority). The recording publishes the dictionary text for `region_code`, `location`, `total_lbm_emissions_unit`, `total_mbm_emissions_unit`, `model_version`, `total_scope_1_emissions_unit/_value`, `total_scope_2_lbm_emissions_unit/_value`, `total_scope_2_mbm_emissions_unit/_value`, `total_scope_3_lbm_emissions_unit/_value`, `total_scope_3_mbm_emissions_unit/_value` — e.g. `region_code` ends "...within a geographical area. The Region code attribute has the same name as an AWS Region, and specifies where the AWS service is available. For example, us-east-1.", `location` ends "...For example, US East (N. Virginia). Emissions from Global Services, such as Amazon CloudFront, are reported under Global.", and the `*_unit` columns read "The unit of measure used for location-based method (LBM) emissions. ...".
Emulator: returns paraphrases for all 15 of those columns — "...within a geographic area. The Region code attribute specifies where the AWS service is available...", `location` truncated before the Global-Services sentence, and "The unit of measurement for the total estimated location-based method (LBM) emissions value...".
Why: a client that reads `Column.Description` to label, document or map a carbon-emissions export column gets text that is not what AWS publishes, and the dropped sentences carry real semantics (that Global-Services emissions are reported under `Global`; that `region_code` is literally an AWS Region name).
Fix: the carbon-emissions entry of the table catalog in `crate::state::catalog` (the `ColumnSpec` description strings), not the handler.
Traces: `bcm-data-exports-catalog-get-table#task#1`.

Cause 2 of 6 — cost-and-usage VIEW schema column descriptions are re-worded (fixture `bcm-data-exports-catalog-get-table`, step `task#2`).
AWS: recorded behavior only. The recorded 200 publishes, for example, `linked_account_name` = "The name of the account that used this line item. ...", `instance_type_family` = "The instance family that is associated with the given usage.", `platform` = "Describes the operating system of your Amazon EC2 instance.", `tenancy` = "The type of tenancy allowed on the Amazon EC2 instance.", `processor` = "Describes the processor on your Amazon EC2 instance.", `processor_features` = "Describes the processor features of your instances.", `database_engine` = "Describes the database engine for your instance.", `product_group` = "A construct of several products that are similar by definition, or grouped together."
Emulator: substitutes its own wording for 16 columns (`amortized_cost`, `current_generation`, `database_engine`, `instance_type_family`, `legal_entity`, `linked_account_name`, `platform`, `pricing_unit`, `processor`, `processor_features`, `product_group`, `product_to_location`, `ri_sp_trueup`, `ri_sp_upfront_fees`, `tenancy`, `unblended_cost`) — e.g. "The tenancy of the instance possible values are Shared, Dedicated, and Host." for `tenancy`.
Why: same as cause 1 — the description is response data; a paraphrase is a different value on the wire, and some paraphrases assert facts AWS does not (an enumerated value list for `tenancy`).
Fix: the cost-and-usage view entry of the table catalog in `crate::state::catalog`.
Traces: `bcm-data-exports-catalog-get-table#task#2`.

Cause 3 of 6 — the CUR 2.0 (line-item) schema OMITS a published column, and normalises a paragraph break out of another description (fixture `bcm-data-exports-catalog-get-table`, step `task#3`). This is the most severe cause of the bundle.
AWS: recorded behavior only. The recorded 200 carries a column `line_item_user_identifier` with `Type` `String` and `Description` "The unique identifier for the user that is responsible for this usage line item". It also carries `line_item_unblended_rate` with a BLANK LINE between its two paragraphs ("...an individual account's service usage.\n\nFor Amazon EC2 and Amazon RDS line items..."), and publishes its own text for ~50 further columns (`line_item_legal_entity`, `product_usagetype`, `product_sku`, `product_fee_code`, `product_location*`, `product_region_code`, `pricing_*`, the `reservation_*` family, the `savings_plan_*` family, `cost_category`, `discount`, `resource_tags`, `tags`, ...).
Emulator: the `line_item_user_identifier` column is ABSENT from `Schema`; `line_item_unblended_rate` collapses the blank line to a single `\n`; and the other ~50 descriptions are re-worded (e.g. `product_sku` "Describes a unique code for a product. The SKU is created by combining the ProductCode, UsageType, and Operation." instead of the published text that also explains size-flexible RIs; `line_item_legal_entity` truncated to "The Seller of Record of a specific product or service.").
Why: the column SET is part of the published data. A client that enumerates the CUR 2.0 schema to build an export definition can neither discover nor request `line_item_user_identifier`, so an export that AWS would accept is unbuildable (and an export definition naming it would be refused as an unknown column). The whitespace normalisation and paraphrases additionally corrupt every description a client renders.
Fix: the CUR 2.0 / cost-and-usage-report entry of the table catalog in `crate::state::catalog` — add the missing `ColumnSpec` and restore the dictionary text byte-for-byte, including embedded blank lines.
Traces: `bcm-data-exports-catalog-get-table#task#3`.

Cause 4 of 6 — the cost-optimization-recommendations schema publishes the WRONG column `Type` token, plus re-worded descriptions (fixture `bcm-data-exports-catalog-get-table`, step `task#4`).
AWS: recorded behavior only. The recorded 200 publishes `recommendation_lookback_period_in_days` with `Type` = `Int` and `Description` = "The lookback period that's used to generate the recommendation.", `estimated_savings_percentage_before_discount` / `_after_discount` without the comma before "relative to", and `last_refresh_timestamp` = "The time when the recommendation was last generated."
Emulator: publishes `Type` = `Integer` for `recommendation_lookback_period_in_days` (the crate's `const INTEGER: &str = "Integer"`, `src/state/catalog.rs`), and re-words all four descriptions (e.g. "The lookback period in days, used to calculate the savings.", and `last_refresh_timestamp` with an appended "in UTC. The format is YYYY-MM-DDTHH:mm:ssZ." that AWS does not publish for this column).
Why: `Column.Type` is the token a client casts on. A consumer that maps the published type vocabulary onto its own reader sees an unknown token `Integer` where AWS says `Int`, so the column is dropped or the cast fails — this is a functional break, not a wording nit.
Fix: the recommendations entry of the table catalog in `crate::state::catalog` — the per-dictionary type token for the day-count column, and the four description strings.
Traces: `bcm-data-exports-catalog-get-table#task#4`.

Cause 5 of 6 — `x_ServiceCode` is re-worded in the FOCUS schemas (fixture `bcm-data-exports-catalog-get-table`, step `task#5`; the same cluster also covers step `task#6`, i.e. both published FOCUS versions).
