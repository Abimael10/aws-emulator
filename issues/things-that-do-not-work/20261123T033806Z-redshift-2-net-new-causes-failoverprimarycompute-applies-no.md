# redshift: 2 net-new causes — FailoverPrimaryCompute applies no IAM identity authorization (a zero-policy principal reaches the cluster lookup instead of 403 AccessDenied), and an accepted DISTSTYLE KEY DISTKEY/SORTKEY table reports no keys in pg_table_def

## Operation
FailoverPrimaryCompute

## Description
Two net-new root causes in the `redshift` service, both grounded in failing behavioral checks the suite marked neither "ALREADY FILED" nor "OWNED by". Both belong to the one service `redshift`, so they are bundled here: a fixer must close BOTH before submitting.

=== Cause 1 of 2: FailoverPrimaryCompute performs no identity-based IAM authorization — a principal with no policies at all is admitted to the account's business logic ===
Failing checks: redshift.failover-primary-compute-unauthorized-denied, redshift.failover-primary-compute-unauthorized-blocked
AWS: FailoverPrimaryCompute is an IAM-authorized control-plane action. A request signed by an IAM identity that holds NO identity-based policy granting `redshift:FailoverPrimaryCompute` is refused at authorization, BEFORE the ClusterIdentifier is looked up, with HTTP 403, error code `AccessDenied` and the message `User: <caller-arn> is not authorized to perform: redshift:FailoverPrimaryCompute on resource: <cluster-arn> because no identity-based policy allows the redshift:FailoverPrimaryCompute action`. Fixed text: `User: `, ` is not authorized to perform: `, ` on resource: `, ` because no identity-based policy allows the `, ` action`. Variable parts, all taken from the request and the emulator's own state: the caller's ARN (`arn:aws:iam::<account-id>:user/<user-name>` for an IAM user), the action name `redshift:FailoverPrimaryCompute`, and the resource ARN built as `arn:aws:redshift:<region>:<account-id>:cluster:<ClusterIdentifier>` from the request's ClusterIdentifier — note the resource ARN is formed even when no such cluster exists, because authorization precedes resolution. The authorization outcome must also be sensitive to IAM state: once the SAME identity is granted `redshift:FailoverPrimaryCompute` (PutUserPolicy, Resource "*"), the identical call must stop being denied and reach the service layer, answering HTTP 404 `ClusterNotFound` / `Cluster not found: <ClusterIdentifier>` exactly as the fully privileged caller does. Smithy states the service-layer errors only — FailoverPrimaryCompute errors ClusterNotFoundFault (httpError 404, awsQueryError code `ClusterNotFound`), InvalidClusterStateFault, UnauthorizedOperation, UnsupportedOperationFault — so the AccessDenied code/status/message above is recorded behavior of the SigV4 authorization layer, not modeled.
Emulator: identity is ignored entirely. A brand-new IAM user created through the emulator's own IAM, with no attached or inline policies, signing with its own freshly minted access key, gets the SAME answer as the fully privileged caller: HTTP 404, code `ClusterNotFound`, message `Cluster not found: <ClusterIdentifier>`. No AccessDenied is ever produced (the checks polled the identical call for 30 s and never observed one), so there is no authorization boundary at all: every identity is treated as fully privileged. The fully privileged control call in both checks passes (code and message both correct), so the operation itself is served and only the authorization stage is missing.
Why: this is a fail-OPEN divergence. A client or test that proves least-privilege (that a role withOUT redshift:FailoverPrimaryCompute cannot fail a cluster over) passes against the emulator while the action is in fact universally permitted, so a policy regression is invisible; conversely, code that branches on AccessDenied (surfacing a permissions-remediation message, requesting elevation, retrying under another role) has a dead branch, and the account-id/caller-ARN/resource-ARN a client parses out of AWS's denial message is never available. Because denial must precede resolution, the emulator also inverts the precedence AWS gives these two refusals: it discloses that a cluster does not exist to a caller who is not authorized to ask.
Fix: the redshift service's request-authorization stage for FailoverPrimaryCompute (the per-operation IAM authorization gate that runs before the handler resolves ClusterIdentifier) — resolve the signing credential to its IAM identity, evaluate that identity's identity-based policies for `redshift:FailoverPrimaryCompute` on `arn:aws:redshift:<region>:<account>:cluster:<ClusterIdentifier>`, and on no matching Allow refuse with 403 / AccessDenied and AWS's message template above; re-evaluate after a grant so a newly added policy admits the same identity.
Traces: redshift.failover-primary-compute-unauthorized-denied, redshift.failover-primary-compute-unauthorized-blocked. Related OPEN issue 20261114T021829Z-redshift-5-net-new-behavioral-causes-failoverprimarycompute-clusternotfound.md covers FailoverPrimaryCompute's ClusterNotFound WORDING (that wording is now correct — both control calls above assert it and pass); it says nothing about authorization and does not carry these checks' replay keys, so this cause is filed here and that issue is named for context.

=== Cause 2 of 2: a CREATE TABLE with DISTSTYLE KEY DISTKEY(col) SORTKEY(col) is now accepted, but the declared distribution and sort keys are not recorded — pg_table_def reports no key on any column ===
Failing check: redshift.rsql-distkey-changes-the-join-plan
AWS: recorded behavior only (no Smithy surface describes SQL). On a Redshift cluster's native PostgreSQL-wire endpoint, `CREATE TABLE t (fid INT NOT NULL, dkey INT NOT NULL, amt DECIMAL(9,2)) DISTSTYLE KEY DISTKEY(dkey) SORTKEY(fid)` both succeeds AND materialises the declared physical design in the cluster's catalog: `SELECT "column", distkey, sortkey FROM pg_table_def WHERE tablename = '<t>'` returns one row per column with distkey TRUE for exactly the DISTKEY column and FALSE elsewhere, and sortkey = the column's 1-based position in the SORTKEY list (1 for the first sort column) and 0 for columns outside it — for the table above: fid (distkey false, sortkey 1), dkey (distkey true, sortkey 0), amt (distkey false, sortkey 0). The same declaration is reported per table by `svv_table_info.diststyle` as `KEY(<distkey-column>)`, and `DISTSTYLE EVEN` as `EVEN`; and it changes the planner's output, so EXPLAIN of a join on the distribution column of two KEY-distributed tables contains `DS_DIST_NONE` while a join against a DISTSTYLE EVEN table contains `DS_BCAST_INNER`. The fixed parts are the catalog relations and their column semantics and the `KEY(<col>)`/`EVEN` spellings; the table and column names are values from the statement.
Emulator: the DDL is now accepted and pg_table_def now answers (both were refusals previously), but the clause's content is discarded: every column comes back with no key at all — {fid: (distkey False, sortkey 0), dkey: (False, 0), amt: (False, 0)} — so the DISTKEY and SORTKEY declarations are parsed-and-dropped rather than recorded. The check stops at this assertion, so the dependent faces (svv_table_info.diststyle reporting KEY(dkey)/KEY(dkey)/EVEN, and EXPLAIN planning DS_DIST_NONE vs DS_BCAST_INNER) are not exercised and remain unverified behind the same missing state.
Why: pg_table_def is the Redshift way to verify a table's physical design. A migration tool, a schema-diff or a design linter that asserts a table was created with the distribution/sort keys it asked for reads "no keys" for a table it just declared with keys, so it either re-applies the DDL forever or reports a drift that does not exist; and because nothing records the keys, no distribution-dependent behavior (colocated vs broadcast joins) can ever be reproduced.
Fix: the cluster SQL engine's CREATE TABLE handling and the catalog state behind the native endpoint — persist the table-level DISTSTYLE/DISTKEY/SORTKEY (and column-level forms) with the table definition, project it into pg_table_def's distkey/sortkey columns per column and into svv_table_info.diststyle per table, and let the planner consult it.
Traces: redshift.rsql-distkey-changes-the-join-plan. Related OPEN issue 20261122T064140Z-redshift-cluster-native-sql-endpoint-5-new.md — correctly 20261122T064140Z-redshift-cluster-native-sql-endpoint-5-net-new.md — listed this check under its cause 2 while the DDL was still a SyntaxError ('near "KEY": syntax error') and pg_table_def did not exist; both of those failure points are now past, the check fails further on at a different observation, and the suite did not mark this failure OWNED, so the surviving cause is filed here and that issue (and 20261121T211635Z-redshift-cluster-native-sql-endpoint-7-net-new.md) are named for context.
