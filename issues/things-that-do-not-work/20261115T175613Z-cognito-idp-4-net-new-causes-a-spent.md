# cognito-idp: 4 net-new causes — a spent TOTP code is accepted by AdminRespondToAuthChallenge, the not-enrolled-TOTP MFA-preference refusal is emulator prose, a remembered device is never routed to DEVICE_SRP_AUTH, and the user-pool replica lifecycle still cannot be driven to completion

> _Note: this issue was identified against the code base at commit `30fa01f06dcb7c8c81ef33d3f3e651ba6ec46458`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
AdminRespondToAuthChallenge

## Description
Four net-new behavioral root causes in cognito-idp, all grounded in failing checks of the behavioral suite. ALL FOUR must be closed before submitting — they are numbered below and each carries its own failing check ids.

None of these is a wrongly-refused call that a fixed issue left refused, so none is a REOPENS: in Cause 1 and Cause 3 the emulator answers 200 where AWS refuses/challenges, in Cause 2 the refusal class is right and only its message text is wrong, and in Cause 4 nothing is refused at all.

=== Cause 1 of 4: a TOTP code that was already spent is accepted again, and tokens are issued. ===
AWS: a software-token code is single-use. A code already consumed — either by VerifySoftwareToken during enrolment, or by completing a SOFTWARE_TOKEN_MFA challenge — is refused the next time it is presented with ExpiredCodeException (Smithy: AdminRespondToAuthChallenge errors include ExpiredCodeException @httpError 400, CodeMismatchException 400, SoftwareTokenMFANotFoundException 400, NotAuthorizedException 403; ExpiredCodeException doc: "This exception is thrown if a code has expired.") and the message 'Your software token has already been used once.' — that message is entirely fixed text, with no part taken from the request or from state. Refusing the replay does NOT spend the challenge Session: the same Session is still live and completes as soon as the next 30-second TOTP window's code is presented.
Emulator: HTTP 200. The replayed code is accepted and the challenge completes — the response carries AuthenticationResult (replay reports the returned keys as ['AuthenticationResult', 'ChallengeParameters', 'ResponseMetadata']) where ExpiredCodeException is due. No consumed-code state is kept per user, so every code in the current time step is reusable without limit.
Why: a second factor that accepts a replayed code is not a second factor. Anyone who observes one OTP once (a logged proxy, a phished code, a shoulder-surfed screen) can present it again and get real tokens, and a client that keys on ExpiredCodeException to tell the user "that code was already used, wait for the next one" never sees that signal and cannot distinguish it from CodeMismatchException.
Fix: the SOFTWARE_TOKEN_MFA branch of the AdminRespondToAuthChallenge handler and its sibling RespondToAuthChallenge handler, over shared per-user software-token state that records which code/time-step has been consumed (the same state VerifySoftwareToken writes on enrolment); the refusal must be raised before the session is consumed so the session stays answerable with the next window's code.
Traces: cognito-idp.admin-respond-to-auth-challenge-refuses-a-replayed-totp-without-spending-the-session.

=== Cause 2 of 4: the (Admin)SetUserMFAPreference refusal for a user with no registered TOTP authenticator is emulator-authored prose. ===
AWS: preferring (or enabling) software-token MFA for a user who has not registered a TOTP authenticator is refused with InvalidParameterException (Smithy: SetUserMFAPreference and AdminSetUserMFAPreference both declare InvalidParameterException @httpError 400; the model's SoftwareTokenMfaSettings member states "Users must register a TOTP authenticator before they set this as their preferred MFA method") and the message 'User does not have delivery config set to turn on SOFTWARE_TOKEN_MFA' — entirely fixed text, with no part taken from the request or from state (no username, no pool id, no factor name is interpolated). Nothing is stored: the user's activated factors and preferred factor are unchanged, and after AssociateSoftwareToken + VerifySoftwareToken the identical call succeeds.
Emulator: the right status and code (HTTP 400 InvalidParameterException) with the message 'User has not verified software token mfa' — the emulator's own prose, differing in wording, capitalisation and in naming verification rather than delivery configuration.
Why: an HTTP status, an error code and an error message are all requirements. A client or fixture that matches AWS's sentence does not match the emulator's, and the emulator's wording points the caller at the wrong remedy (it reads as "verify your token" rather than AWS's delivery-config wording), so behavior recorded against AWS cannot be replayed.
Related but NOT covering this: open issue 20261103T075017Z-cognito-idp-eight-refusal-messages-are-emulator-authored.md Cause 1 is a different defect — AdminSetUserMFAPreference evaluating the factor-availability check BEFORE the two-preferred-factors conflict, so the wrong rule's message is returned for a conflicting request; at the time it was filed the emulator's text for that path was 'User does not have delivery config set to turn on SOFTWARE_TOKEN_MFA'. The emulator's text has since changed to 'User has not verified software token mfa', which is wrong for the plain not-enrolled case these three checks exercise, and those checks carry replay keys that open issue does not own (its two AdminSetUserMFAPreference checks are reported separately as already filed). Fixed issue 20261025T192709Z-cognito-idp-setusermfapreference-answers-501-notimplemented-instead-of.md only made this call refuse at all instead of answering 501.
Fix: the message on the shared MFA-preference rejection in src/state.rs (the rejection returned by User::set_mfa_preference, whose .message() both handlers render), used by src/ops/set_user_mfa_preference.rs and src/ops/admin_set_user_mfa_preference.rs; the per-factor availability rule itself is correct, only its sentence is not AWS's.
Traces: cognito-idp.admin-set-user-mfa-preference-method-not-enrolled-rejected, cognito-idp.set-software-token-mfa-preference-unregistered-rejected, cognito-idp.set-user-mfa-preference-conflicting-preferred-method-rejected.

=== Cause 3 of 4: a confirmed, remembered device is authenticated outright instead of being challenged DEVICE_SRP_AUTH, so the device-SRP handshake is unreachable. ===
AWS: with device tracking on (CreateUserPool DeviceConfiguration ChallengeRequiredOnNewDevice=true, DeviceOnlyRememberedOnUserPrompt=true) and a device that has been confirmed with a DeviceSecretVerifierConfig (ConfirmDevice) and marked remembered (UpdateDeviceStatus DeviceRememberedStatus='remembered'), an InitiateAuth whose AuthParameters carry DEVICE_KEY answers with ChallengeName=DEVICE_SRP_AUTH and a Session INSTEAD of the SOFTWARE_TOKEN_MFA challenge (Smithy: ChallengeNameType values include DEVICE_SRP_AUTH and DEVICE_PASSWORD_VERIFIER; InitiateAuth output declares ChallengeName/Session/ChallengeParameters/AuthenticationResult). Answering DEVICE_SRP_AUTH with SRP_A yields ChallengeName=DEVICE_PASSWORD_VERIFIER whose ChallengeParameters carry SRP_B, SALT and SECRET_BLOCK; a PASSWORD_CLAIM_SIGNATURE computed from the device password the stored verifier was derived from yields tokens (the access token carrying a device_key claim), while the same claim signed from a different device password is refused NotAuthorizedException 'Incorrect username or password.' (fixed text). Recorded behavior only for the SRP key schedule itself (the undocumented "Caldera" SRP-6a variant over the 3072-bit group) and for the handshake being eventually consistent after the remember, which is why the checks poll instead of asserting on the first read.
Emulator: that InitiateAuth answers HTTP 200 with AuthenticationResult and NO ChallengeName at all — authentication completes immediately on the strength of the DeviceKey alone. DEVICE_SRP_AUTH is therefore never issued and DEVICE_PASSWORD_VERIFIER is never reachable, so neither the verifier material nor the wrong-device-password refusal can ever be observed. Two of the three checks poll for DEVICE_SRP_AUTH for up to 60 s and consequently exhaust the per-check budget ("Check timed out after 60.0s"); the third asserts directly and reports ChallengeName None. The control legs of those checks pass, so this is specific to the device path: the same user signing in WITHOUT DEVICE_KEY is still correctly challenged SOFTWARE_TOKEN_MFA.
Why: the device-trust skip is granted without any proof of possession. A DeviceKey is not a secret — it is handed back in NewDeviceMetadata and is readable from ListDevices/GetDevice — so on the emulator knowing the password plus a DeviceKey bypasses MFA entirely, where AWS still requires the device to prove it holds the device secret through the SRP exchange. Any client that implements the documented device-tracking handshake (every AWS mobile SDK does) is also untestable, because the challenge it is written against never arrives.
Fix: the device-tracking branch of src/ops/initiate_auth.rs (and admin_initiate_auth.rs) must, for a DEVICE_KEY naming a confirmed+remembered device of that user, issue the DEVICE_SRP_AUTH challenge rather than completing authentication; src/ops/respond_to_auth_challenge.rs (and the admin sibling) must implement DEVICE_SRP_AUTH -> DEVICE_PASSWORD_VERIFIER against the salt/verifier ConfirmDevice stored for that device, including the NotAuthorizedException for a claim that does not verify.
Traces: cognito-idp.e2e-device-remember-skips-mfa-then-forget-reinstates, cognito-idp.e2e-remembered-device-skips-mfa-on-next-login, cognito-idp.device-srp-auth-completes-with-a-locally-computed-device-verifier.

=== Cause 4 of 4: the multi-Region user-pool replica lifecycle still cannot be driven to completion — a created replica stops being listed before it settles INACTIVE, and a deleted replica never leaves DELETING. ===
AWS: ListUserPoolReplicas returns UserPoolReplicas of UserPoolReplicaType {RegionName, Status, Role, UserPoolArn}, Status being ReplicaStatusType (CREATING | ACTIVE | INACTIVE | DELETING). The model documents the states: "CREATING — The replica is being created", "INACTIVE — The replica has been created, but is not accepting requests for end-users. Administrator configuration operations are supported", "ACTIVE — The replica is available for both end-user and administrator operations", "DELETING — The replica is being deleted". So a freshly created replica stays listed and settles INACTIVE, UpdateUserPoolReplica moves it between ACTIVE and INACTIVE, and DeleteUserPoolReplica removes it so ListUserPoolReplicas no longer names that Region and UpdateUserPoolReplica on it answers ResourceNotFoundException. Recorded behavior only for the transition durations: AWS takes minutes, which is why both checks poll.
Emulator: in cognito-idp.user-pool-replica-lifecycle the create succeeds and the Region is listed once, but the next read of that replica's status yields no status at all (the Region is absent from ListUserPoolReplicas) where INACTIVE is due — a created replica therefore never has a readable settled state. In cognito-idp.user-pool-replica-update-lifecycle the CREATING/ACTIVE/INACTIVE legs are served, but after DeleteUserPoolReplica the replica is still reported DELETING and is never removed from the listing within the remaining budget (the post-delete poll was already down to 0.0 s because the shared multi-Region-CMK prerequisite consumed the wall clock). Every individual call answers 200; what diverges is the listed state over time.
Why: multi-Region user-pool replication cannot be exercised end to end against the emulator — a client cannot observe a replica becoming usable (INACTIVE/ACTIVE) nor observe a delete actually completing, so any orchestration that waits on those states hangs, and the DELETING state is terminal rather than transient.
Note: fixed issue 20261103T200951Z-cognito-idp-2-net-new-causes-getprovisionedlimit-refuses.md Cause 2 claimed exactly this lifecycle, and both checks still fail on the identical assertions, so it is unresolved rather than regressed; nothing here is a refusal, so this is not a REOPENS.
Fix: the replica state machine and its listing — UserPool::replica_regions / UserPool::live_replica / UserPool::to_replica_in and the replica activation/deletion spans in src/state.rs, read by src/ops/list_user_pool_replicas.rs and written by src/ops/create_user_pool_replica.rs and src/ops/delete_user_pool_replica.rs — plus the latency of the multi-Region-key prerequisite those handlers depend on, which must not consume the whole budget before the lifecycle is observable.
Traces: cognito-idp.user-pool-replica-lifecycle, cognito-idp.user-pool-replica-update-lifecycle.
