# batch: 2 net-new causes — SubmitServiceJob's missing-quotaShareName refusal is emulator-authored, and the TerminateServiceJobs denial names the bulk action with no resource instead of per-job batch:TerminateServiceJob

> _Note: this issue was identified against the code base at commit `991354efed443a569b426643157f0d67ea150cda`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
SubmitServiceJob, TerminateServiceJobs

## Description
Two net-new root causes on the AWS Batch service-job plane, both grounded in failing behavioral checks that the replay report marks neither ALREADY FILED nor OWNED. Related but non-covering open issues: 20261029T234420Z-batch-refusal-contracts-diverge-not-found-arn-wording.md covers other SubmitServiceJob refusal ordering/wording (unauthorized-vs-not-found, GetJobQueueSnapshot/ListJobsByConsumableResource not-found text) and says nothing about quotaShareName; 20261024T120647Z-batch-overly-permissive-control-and-service-job-planes.md covers other service-job refusals; 20261117T124549Z-batch-terminateservicejobs-stub.md is the scaffold-stub issue for TerminateServiceJobs and covers only the unknown-id result shape, not the authorization decision below, which is taken before the stub and does answer.

Cause 1 of 2 — SubmitServiceJob omitting quotaShareName on a quota-share-scheduling queue is refused with the emulator's own sentence instead of AWS's fixed message.
AWS: Smithy (services/service-com-amazonaws-batch-awsbatchv20160810/smithy-model/com-amazonaws-batch-awsbatchv20160810.json): SubmitServiceJob, POST /v1/submitservicejob, required jobName/jobQueue/serviceRequestPayload/serviceJobType, optional quotaShareName/shareIdentifier; declared errors ClientException (httpError 400) and ServerException (500). The model states no message text, so the wording is recorded behavior only: submitting to a job queue whose schedulingPolicyArn carries a quotaSharePolicy without quotaShareName is refused HTTP 400, error code ClientException, message exactly "Job without quotaShareName cannot be submitted to a job queue with quota share scheduling policy." — the entire sentence is FIXED text with NO variable part: it names neither the queue, its ARN, nor the job. No job is created by the refused call.
Emulator: keeps status 400 and code ClientException but substitutes its own sentence, "quotaShareName must be specified for JobQueue <resolved job-queue ARN>." — wrong fixed text, and it interpolates the resolved job-queue ARN (region/account/queue-name from the request and state), which AWS's message does not contain at all.
Why: the message is a wire requirement. A client or test that keys its missing-quota-share handling on AWS's exact sentence (ClientException carries no sub-code, so the message is the only discriminator between the several ClientException causes of this operation) falls through to a generic error path; and a caller parsing the ARN out of the emulator's text gets a field AWS never supplies.
Emulator-authored ARN interpolation also makes the refusal queue-specific where AWS's is not.
Fix: the quota-share precondition in the SubmitServiceJob handler's validation (the batch crate's submit_service_job op) must emit the service's fixed sentence through the ClientException renderer rather than a hand-written, ARN-interpolating message.
Traces (examples): batch.submit-service-job-missing-quota-share-name-rejected, batch.submit-service-job-missing-required-quota-share-name-rejected — both fail on the identical substituted sentence, on a quota-share queue built two different ways (shared scheduling policy vs. per-check negative queue), which is what identifies this as one wording defect in the handler and not a queue-construction difference.

Cause 2 of 2 — TerminateServiceJobs' AccessDeniedException names the bulk action and no resource, instead of AWS's per-job batch:TerminateServiceJob denial naming the service-job ARN.
AWS: Smithy: TerminateServiceJobs, POST /v1/terminateservicejobs, input jobs (required StringList) + reason (required), output successful + errors (both required); modeled errors are only ClientException (400) and ServerException (500) — no AccessDeniedException shape exists in the model, so the refusal is recorded behavior only. The recording shows error code AccessDeniedException whose message follows AWS's standard identity-based-denial template: "User: <caller principal ARN> is not authorized to perform: batch:TerminateServiceJob on resource: <service-job ARN> because no identity-based policy allows the batch:TerminateServiceJob action". Fixed text: "User: ", " is not authorized to perform: ", " on resource: ", " because no identity-based policy allows the ", " action"; fixed action token: batch:TerminateServiceJob (the SINGULAR per-job action — the bulk API authorizes each requested job against that action). Variable parts taken from the request/state: the caller's assumed-role principal ARN and the service-job ARN (arn:aws:batch:<region>:<account>:service-job/<jobId>) of the job named in jobs[]. The effect must also be absent: the denied call leaves the job un-terminated (status not FAILED, isTerminated false/absent).
Emulator: answers AccessDeniedException with "User: <principal ARN> is not authorized to perform: batch:TerminateServiceJobs because no identity-based policy allows the batch:TerminateServiceJobs action" — it authorizes the PLURAL API name batch:TerminateServiceJobs and omits the " on resource: <service-job ARN>" clause entirely.
Why: the action token and the resource clause are the contract between the service and IAM. A principal granted exactly batch:TerminateServiceJob (the action AWS evaluates, and the only one documented for this API) is still denied by the emulator, and conversely a policy written against the emulator's batch:TerminateServiceJobs will not work on AWS; tooling that parses the denial to learn which resource to grant finds no resource at all, so automated least-privilege remediation produces the wrong policy.
Fix: the authorization gate ahead of the TerminateServiceJobs handler in the batch crate — it must evaluate the per-job action batch:TerminateServiceJob against each requested job's service-job ARN and render the denial with the resource clause of AWS's standard identity-based-denial template, not the bulk operation name with a resource-free message.
Traces (examples): batch.terminate-service-jobs-bulk-without-permission-denied.
