## Description
3 net-new root causes in SSM Run Command's guest-execution seam, grounded in the one failing check under the `ec2__iam` heading that is neither ALREADY FILED nor OWNED. The scenario's only observation point is the managed node itself: it swaps the role behind an instance profile and then asks the guest what IMDSv2 serves and what those credentials may do, by shipping a shell script with `AWS-RunShellScript`. Nothing it grades is observable unless that script runs.

Nearest open issues, none of which carries this check's replay key: 20261114T172248Z-ec2-s3-sqs-ssm-aws-runshellscript-invocations-that.md and 20261114T161545Z-ec2-route53-route53resolver-ssm-an-aws-runshellscript-script.md (same guest-execution seam, grounded on other services' checks, and neither names the line-by-line script assembly below); 20261107T075601Z-ec2-iam-ec2-dryrun-reports-every-caller-as-authorized-instance.md (says IMDS credentials never appear, but is grounded in DryRun/instance-profile-ARN causes); 20261114T143448Z-ec2-iam-s3-ssm-imds-role-credential-probes-never-complete-the-ssm.md (describes the invocation never reaching a terminal status — that is no longer what happens: it now reaches `Failed`). A fix to any of those closes none of the causes below.

Cause 1 of 3: the document's `commands` input is performed one list element per shell command instead of as ONE script, so a here-document (or any construct spanning several elements) never forms and the heredoc body and terminator are executed as shell commands.
  AWS: the SSM agent writes the resolved `commands` of an `aws:runShellScript` step into a single script file and runs that file with the guest's shell, so the list is one script: a line may open a here-document (`python3 - <<'PYSUM'`), later lines are its body, and a line equal to the terminator closes it. Variables, redirections and files therefore persist across lines, and GetCommandInvocation reports Status=`Success`, ResponseCode=0 and the script's stdout. Smithy: GetCommandInvocation output members `Status` (CommandInvocationStatus), `StatusDetails`, `ResponseCode` (integer, default 0), `StandardOutputContent` (@length 0..24000), `StandardErrorContent` (@length 0..8000); whether a script succeeds is the GUEST's outcome, not an API refusal, so no modelled error is involved and the per-shell wording of a shell diagnostic is recorded behavior only.
  Emulator: services/service-com-amazonaws-ssm-amazonssm/src/state/guest_execution.rs hands the step's `commands` vector to `perform_in_guest`, and `ComAmazonawsEc2Amazonec2State::run_in_instance_guest` (services/service-com-amazonaws-ec2-amazonec2/src/state/guest_commands.rs) loops `for command in commands { status = session.run(command) }` — each element is its own shell command. A heredoc opener therefore runs on its own, its body lines run as commands, and the bare terminator word (here `PYSUM`) runs as a command the session has no program for, which answers the status a shell answers for a utility it could not find; that element's status becomes the run's, so the invocation settles `Failed`. (Hypothesis: the same loop is bounded by `MAX_GUEST_RUN_COMMANDS` = 64 in that file, so a probe script longer than 64 lines — these IMDS probes are — is additionally abandoned part-way.)
  Why: a client that drives an instance by shipping it a program — the only way to observe anything that exists only inside the guest, and exactly what this scenario does — gets a failed invocation instead of its program's output and side effects. The behavior under test (IMDS listing the instance profile's role, serving ASIA temporary credentials, and those credentials' S3 verdicts inverting when the profile's role is swapped) is not observable at all, however faithful IAM, EC2 and S3 are.
  Fix: the script-assembly step of SSM's guest execution and the session seam it runs in — services/service-com-amazonaws-ssm-amazonssm/src/state/guest_execution.rs (`perform_in_guest`) and services/service-com-amazonaws-ec2-amazonec2/src/state/guest_commands.rs (`run_in_instance_guest`): the resolved `commands` must be performed as one script by one shell (here-document redirection, multi-line constructs, persisted variables and files), not as N independent commands.
  Traces: ec2__iam.instance-profile-role-swap-changes-the-credentials-imds-serves — AssertionError: "the probe script must run to completion (a denied PutObject does not fail it, because the rc is captured); SSM reports 'Failed', stderr=''". The script's last element is the bare heredoc terminator `PYSUM`.

Cause 2 of 3: the guest session provides no HTTP client, no interpreter and no AWS CLI, and reaches no network, so an in-guest IMDSv2 read and an in-guest AWS CLI call can never run.
  AWS: on the AMI these checks launch (the image named by the public parameter /aws/service/ami-amazon-linux-latest/al2023-ami-kernel-default-x86_64) the guest ships `curl`, `python3` and the `aws` CLI, and the link-local Instance Metadata Service answers inside the instance: `PUT http://169.254.169.254/latest/api/token` returns a token, `GET /latest/meta-data/iam/security-credentials/` lists the instance profile's role, `GET /latest/meta-data/iam/security-credentials/<role>` returns `{"Code":"Success","AccessKeyId":"ASIA…","SecretAccessKey":…,"Token":…,"Expiration":…,"Type":"AWS-HMAC"}`, and `GET /latest/meta-data/iam/info` returns the `InstanceProfileArn`. A request signed with those credentials is authorized as `arn:aws:sts::<account>:assumed-role/<role>/<instance-id>`.
  Emulator: services/service-com-amazonaws-ec2-amazonec2/src/state/guest_commands.rs states of the session that "there is no process, no socket and no host path in it" and that "every command the session provides no program for … runs nothing and answers the status a shell answers for a utility it could not find". So `curl`, `python3` and `aws` are not provided and 169.254.169.254 is unreachable from the guest: the probe's token request, role listing, credential document and CLI calls all run nothing.
  Why: the whole instance-credentials contract — that a guest receives role credentials from IMDS, that they are the role's and nothing more, and that they change when the profile's role changes — is unobservable from inside an instance, which is the only place it exists. Any client workload that relies on the instance-profile credential chain (every SDK default chain on EC2) cannot run.
  Fix: the guest program environment and link-local metadata service of the in-process session — services/service-com-amazonaws-ec2-amazonec2/src/state/guest_commands.rs together with the session's program set in service_common's posix_shell_session: provide an HTTP client able to reach the instance's own IMDS, a `python3` able to run a shipped script, and an `aws` CLI that signs with what IMDS served against the emulator's endpoints.
  Traces: ec2__iam.instance-profile-role-swap-changes-the-credentials-imds-serves (the probe's first lines are `T=$(curl -sS -X PUT "$IMDS/latest/api/token" …)` and `curl … "$IMDS/latest/meta-data/iam/security-credentials/$ROLE" > /tmp/doc.json`).

Cause 3 of 3: a Failed invocation reports an empty StandardErrorContent, so the failure carries no diagnostic at all.
  AWS: when a RunShellScript invocation ends non-zero, GetCommandInvocation reports the script's own stderr in `StandardErrorContent` beside the non-zero `ResponseCode` and a `StatusDetails` of `Failed`; for a line naming a program the shell cannot find, that stderr is the shell's own diagnostic — fixed text of the form `<program>: command not found`, whose only variable part is the program name taken from the failing script line (recorded behavior only for the exact per-shell wording; the requirement is that a non-empty diagnostic accompanies a Failed status).
  Emulator: `GuestRun` (services/service-com-amazonaws-ec2-amazonec2/src/state/guest_commands.rs) carries only `output` and `status` — there is no stderr stream anywhere in the seam — so every failed invocation answers `StandardErrorContent` `''`.
  Why: a client cannot tell a missing interpreter from a syntax error, a denied call or a killed probe; all of them look like an empty `Failed`. Automation that branches on `StandardErrorContent` to retry, classify or report has nothing to branch on.
  Fix: SSM's invocation-result projection and the GetCommandInvocation serializer — carry the session's stderr into `StandardErrorContent` (keeping `StatusDetails` and `ResponseCode` consistent) instead of dropping it.
  Traces: ec2__iam.instance-profile-role-swap-changes-the-credentials-imds-serves — the reported assertion ends in `stderr=''`.
