# DynamoDB transaction failures take the wrong error class and lose CancellationReasons, and a per-slot ItemResponse drops its Item member (4 causes)

> _Note: this issue was identified against the code base at commit `02c6380a70f664dba771786c55045481408bc4cc`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
TransactGetItems

## Description
THIS BUNDLE CONTAINS 4 CAUSES, all in the DynamoDB transaction operations. Three are failure-classification defects (an item-level transaction failure is reported as a request-level ValidationException instead of the modeled TransactionCanceledException / ResourceNotFoundException, so the per-slot CancellationReasons a client needs are never produced); the fourth is a success-path serializer defect in the per-slot ItemResponse. Each must be closed before this issue is submitted.

Cause 1 of 4 — TransactGetItems with a Get whose Key does not match the table's key schema is refused as a request-level ValidationException instead of the transaction-cancellation envelope. Fixture dynamodb-transact-get-items-empty-key-single-cancellation-reason, step task#4.
AWS: Smithy: TransactGetItems models TransactionCanceledException {errorKind client, httpError 400} among its errors; TransactionCanceledException has members Message (ErrorMessage) and CancellationReasons (CancellationReasonList, @length min 1 max 100), and its documentation lists "There is a user error, such as an invalid data format" among the cancel circumstances. CancellationReason has members Code, Message and Item and is documented as "An ordered list of errors for each item in the request which caused the transaction to get cancelled. The values of the list are ordered according to the ordering of the TransactWriteItems request parameter. If no error occurred for the associated item an error with a Null code and Null message will be present." The recorded response is HTTP 400 with __type 'com.amazonaws.dynamodb.v20120810#TransactionCanceledException', top-level Message 'Transaction cancelled, please refer cancellation reasons for specific reasons [<comma-separated per-slot codes>]' and CancellationReasons carrying one entry per TransactItems slot in request order. In that top-level Message the sentence 'Transaction cancelled, please refer cancellation reasons for specific reasons' is fixed text and the bracketed list is derived from the request — one code per slot (the single failing slot here yields '[ValidationError]'). The failing slot's entry is {Code: 'ValidationError', Message: 'The provided key element does not match the schema'}: that per-slot Message is the fixed text for a key/schema mismatch, its Code is that slot's defect class, and blameless slots carry a null Code with no Message. The status (400) and the error shape are modeled; the message texts are recorded behavior.
Emulator: answers HTTP 400 with __type 'com.amazon.coral.validate#ValidationException' and carries neither the Message member nor the CancellationReasons member (both absent, not empty) — the key defect is reported as a flat request-validation refusal under a different error class, with the text under a different member name.
Why: a client branches on the error class to decide what happened. TransactionCanceledException means the transaction was rejected as a unit and CancellationReasons says WHICH action to fix (and which siblings were blameless); ValidationException means the request itself was malformed. An SDK transaction helper that unpacks CancellationReasons to attribute the failure to a TransactItems slot finds no list and cannot identify the offending Get; code that catches TransactionCanceledException never enters that branch and falls into a generic handler that sees an error with no message member.
Fix: the TransactGetItems handler's error-assembly path — a per-slot key/schema defect must raise the transaction-cancellation error and build CancellationReasons over all TransactItems slots in request order (the offending slot with its Code/Message, every other slot with a null Code), with the top-level Message's bracketed code list derived from that same list.
Traces: dynamodb-transact-get-items-empty-key-single-cancellation-reason#task#4.

Cause 2 of 4 — TransactGetItems checks the duplicate-item rule before resource existence, so a Get on a table that does not exist is answered with the duplicate-operation ValidationException instead of ResourceNotFoundException. Fixture dynamodb-transact-get-items-expression-and-key-defects-outrank-cancellation-and-duplicates, step task#8.
AWS: Smithy: TransactGetItems models ResourceNotFoundException {errorKind client, httpError 400}, documented as "The operation tried to access a nonexistent table or index. The resource might not be specified correctly, or its status might not be ACTIVE." The recorded response is HTTP 400 with __type 'com.amazonaws.dynamodb.v20120810#ResourceNotFoundException' and message 'Requested resource not found' — the whole sentence is fixed text, with no variable part. The requirement this step pins is the PRECEDENCE: existence of the referenced table outranks the multiple-operations-on-one-item check, so the missing resource is reported even though the same request also repeats an item.
Emulator: answers HTTP 400 with __type 'com.amazon.coral.validate#ValidationException' and message 'Transaction request cannot include multiple operations on one item' — the duplicate-item check fires first and the nonexistent table is never reported.
Why: the two errors mean opposite things to a caller. ResourceNotFoundException tells it the table name/region is wrong (or the table is not ACTIVE) and the request can never succeed as written; the duplicate-operation ValidationException tells it to de-duplicate its TransactItems list. A client that de-duplicates and retries still gets a failure, and a provisioning flow that treats ResourceNotFoundException as "create the table first" never takes that branch.
Fix: the validation ordering in the TransactGetItems handler — resolve and existence-check every referenced table before applying the cross-slot duplicate-item rule.
Traces: dynamodb-transact-get-items-expression-and-key-defects-outrank-cancellation-and-duplicates#task#8.

Cause 3 of 4 — a successful TransactGetItems omits the Item member of a per-slot ItemResponse where AWS serializes it as an empty map. Fixture dynamodb-transaction-failure-class-discrimination, step task#14.
AWS: Smithy: TransactGetItemsOutput.Responses targets ItemResponseList (@length min 1 max 100) of ItemResponse, whose single member Item (AttributeMap, "Map of attribute data consisting of the data type and attribute value") is optional — the model permits either form, so this is recorded behavior only. The recording answers HTTP 200 with Responses[0] carrying an Item member whose value is an empty map ({}), i.e. the member is PRESENT and empty for the slot that produced no attributes.
Emulator: answers 200 with the Item member absent from Responses[0] altogether.
Why: callers test membership of Item to decide whether a slot produced anything and then read attributes from it. With the member absent, code written against the recorded shape dereferences a missing key (or takes the "slot failed" branch) for a slot AWS reports as a successful read, and the positional Responses list no longer has the shape the caller indexes into.
Fix: the TransactGetItems response serializer's per-slot ItemResponse construction. NOTE for the fixer: open behavioral issue 20261120T093536Z-dynamodb-3-net-new-causes-the-transactitems-100.md asserts the OPPOSITE for its own scenario (its Cause 2: a Get whose ProjectionExpression resolves to none of an existing item's attributes must omit Item entirely). The two surfaces pin different scenarios, so discriminate per slot outcome rather than flipping one global present/absent rule — closing one by inverting the serializer will reopen the other.
Traces: dynamodb-transaction-failure-class-discrimination#task#14.

Cause 4 of 4 — TransactWriteItems whose Update drives the target item past the item-size limit is refused as a request-level ValidationException instead of the cancellation envelope. Fixture transact-write-items-update-over-size-limit-cancellation-reason, step task#4 (same cause at task#6).
AWS: Smithy: TransactWriteItems models TransactionCanceledException {errorKind client, httpError 400}, whose documentation lists "An item size becomes too large (larger than 400 KB), or a local secondary index (LSI) becomes too large, or a similar validation error occurs because of changes made by the transaction" as a cancel circumstance — a size violation CAUSED BY the transaction cancels, it does not refuse the request. The recorded response is HTTP 400 with __type 'com.amazonaws.dynamodb.v20120810#TransactionCanceledException', top-level Message 'Transaction cancelled, please refer cancellation reasons for specific reasons [<per-slot codes>]' (fixed sentence plus the request-derived bracketed code list) and CancellationReasons with that slot's entry {Code: 'ValidationError', Message: 'Item size to update has exceeded the maximum allowed size'} — the per-slot sentence is fixed text for the over-size-update class.
Emulator: answers HTTP 400 with __type 'com.amazon.coral.validate#ValidationException' and neither Message nor CancellationReasons present.
Why: as Cause 1 — the per-slot verdict is unavailable, so in a multi-action transaction the client cannot tell which item to shrink, and retry-versus-shrink logic keyed on TransactionCanceledException never runs.
Fix: the TransactWriteItems handler's item-size check and error assembly — raise the cancellation error for a size violation produced by a staged Update and build CancellationReasons over all slots in request order.
Traces: transact-write-items-update-over-size-limit-cancellation-reason#task#4 (representative of its cluster), #task#6.
