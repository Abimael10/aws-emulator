# opensearch: 4 net-new causes — the domain REST data plane ignores the refresh contract and index write blocks, accepts a non-allow-listed _cluster/settings property, and the domain-work wall-clock window times out a fifth check

> _Note: this issue was identified against the code base at commit `3e484744f0554d26aabb45f062743f61b62726b4`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
PUT /_cluster/settings

## Description
Five behavioral checks of the opensearch service fail for four distinct root causes. All four belong to the same service, so they are bundled here; a fixer must close ALL FOUR numbered causes below before submitting.

=== Cause 1 of 4: PUT /_cluster/settings accepts a property outside the managed allow-list ===
Failing check: opensearch.cluster-settings-put-is-refused-for-a-non-allowlisted-property
AWS: recorded behavior only — the OpenSearch control-plane Smithy model (com.amazonaws.opensearch#AmazonOpenSearchService, version 2021-01-01, restJson1, sigv4Name `es`, 96 operations) models no domain REST data-plane operation at all, so the data plane's contract is only in Amazon OpenSearch Service's supported-operations table and in the recording. That table lists `PUT /_cluster/settings` as supported for a fixed short list of cluster properties only. A property OUTSIDE that list (the recording uses the dynamic, cluster-level open-source property `cluster.routing.allocation.enable`) is refused by the managed ACCESS layer, before the engine sees it: HTTP 401 with a bare `{"Message": ...}` body — not the engine's `{"error": {"type": ...}}` envelope. The recording asserts the status and that body shape; it does not record the Message text, so the requirement here is the 401 and the bare-Message envelope, and the message's wording is whatever AWS's access layer emits for a request it does not permit.
Emulator: answers HTTP 200 with an acknowledgement that echoes the property back as applied: `{'acknowledged': True, 'persistent': {'cluster': {'routing': {'allocation': {'enable': 'all'}}}}, 'transient': {}}`. No allow-list is consulted; the target behaves like an unrestricted self-managed OpenSearch cluster rather than a managed domain.
Why: a client that sets a cluster property the managed service forbids is told it succeeded, and then relies on an allocation/routing/recovery setting that a real domain never applied — so capacity, shard-allocation and recovery behavior silently differ between the emulator and AWS, and code that is supposed to handle the 401 and fall back to the documented index-level `_settings` alternative never exercises that path.
Fix: the `_cluster/settings` handler of the domain REST data plane in the opensearch service crate, specifically its missing access-layer validation step (an allow-list check that must run before the settings are written into index/cluster state and must refuse with 401 + bare Message).

=== Cause 2 of 4: the refresh contract is ignored — a ?refresh=false write into an index with refresh_interval=-1 is immediately searchable ===
Failing checks: opensearch.disabled-refresh-interval-hides-document-from-search-until-refresh, opensearch.osm-refresh-gates-search-while-get-by-id-is-realtime
AWS: recorded behavior only (no modeled data-plane shape, as above). OpenSearch's near-real-time contract: a document indexed with `?refresh=false` into an index whose `index.refresh_interval` is `-1` is NOT visible to `_search` until a refresh is forced (`POST /<index>/_refresh`, or a write with `?refresh=true`/`wait_for`), while `GET /<index>/_doc/<id>` IS realtime and returns it immediately. The recordings show exactly that split: 0 hits from `_search` right after the write, with the same document readable by id.
Emulator: `_search` on the index returns the document immediately — `hits={'total': {'value': 1, 'relation': 'eq'}, 'max_score': 1.0, 'hits': [{'_index': <index>, '_id': <id>, ...}]}` — 0.0 s after the write. Both `index.refresh_interval` and the write's `refresh` query parameter are accepted and then disregarded: every write is搜 searchable at once, so there is no segment-visibility model at all.
Why: visibility-after-write is the contract clients build indexing pipelines on. Bulk loaders disable `refresh_interval` for throughput and then refresh explicitly before reading; a client verifying that an un-refreshed write is NOT yet searchable gets the opposite answer on the emulator, and conversely code that forgets to refresh passes here and loses documents to a search on AWS. Any ISM/near-real-time or read-your-write test written against the emulator is unsound.
Fix: the search path and the index-write path of the domain REST data plane in the opensearch service crate — the per-index visibility (refresh) state that a write must enter and a refresh must publish, honoring `index.refresh_interval` (including `-1`) and the write's `refresh` parameter, while leaving GET-by-id realtime.

=== Cause 3 of 4: index.blocks.write is read back as true but not enforced ===
Failing check: opensearch.managed-domain-strips-index-blocks-write-but-honours-read-only
AWS: recorded behavior only. Either of AWS's two coherent outcomes is self-consistent: a managed domain that does not support `index.blocks.write` STRIPS it (so a `_settings` read-back does not report it as `true`), or it keeps it and ENFORCES it exactly like the supported `index.blocks.read_only: true` — a write is refused with HTTP 403 and an `{"error": {"type": "cluster_block_exception", "reason": ...}, "status": 403}` body, the same `type` as the read-only refusal with its own distinct `reason`. The recording takes the second branch: the setting reads back `true` and the subsequent write is refused 403 with `cluster_block_exception`. In that reason the fixed text is OpenSearch's block wording and the variable part is the index name taken from the request path (Hypothesis, since the recording compares the two refusals' reasons against each other rather than asserting a literal string: the write block reads `index [<index>] blocked by: [FORBIDDEN/8/index write (api)];` against read-only's `[FORBIDDEN/5/index read-only (api)]`). The requirements the recording does pin are: HTTP 403, `error.type` = `cluster_block_exception`, a reason distinct from the read-only one, enforcement that persists over a sustained window, and liftability by clearing the setting.
Emulator: accepts the setting, confirms `index.blocks.write: true` on the `_settings` read-back, and then accepts the write anyway — HTTP 201 `{'_index': <index>, '_id': <id>, '_version': 1, 'result': 'created', '_shards': {...}, '_seq_no': 1, '_primary_term': 1}`. It neither strips the setting nor enforces it, so its own read-back contradicts its own behavior.
Why: a client that write-blocks an index (to freeze it before a snapshot, a reindex or an ISM transition) is told the block is in place and then has its writes silently accepted, corrupting the frozen data set. Because the block is reported as active, there is no way for the client to detect the divergence from the API.
Fix: the index-write path of the domain REST data plane in the opensearch service crate — the index-block state must be consulted on every write and refuse with 403 `cluster_block_exception` (or, if the managed surface is modelled as stripping the setting, the settings handler must drop it so the read-back never claims it).

=== Cause 4 of 4: the domain-work wall-clock window exhausts the budget of the disabled-operation gating check ===
Failing check: opensearch.disabled-operation-gating-across-readonly-apis (Error: Check timed out after 60.0s — no assertion reached)
AWS: recorded behavior only — the check completes against AWS. Smithy: DomainStatus carries Created/Processing and DomainProcessingStatus; StartDomainMaintenance/GetDomainMaintenanceStatus/ListDomainMaintenances and ListVpcEndpointsForDomain are all modelled control-plane reads. AWS passes transient lifecycle values through and reaches the terminal one asynchronously; the number of successive client poll intervals a conforming implementation costs is bounded by what the client budgets, not by a fixed wall-clock span per transition.
Emulator: every call answers, but the check never reaches a verdict: it polls DescribeDomain at 30 s intervals until `Created && !Processing && Endpoint`, once after CreateDomain and again after UpdateDomainConfig(InstanceCount=3). Hypothesis (consistent with the observed 60 s timeout and with the already-filed cause below): the domain's work window is held for a wall-clock span and the terminal status is materialised only on the first read taken after that instant, so each of the two waits costs the client one full 30 s poll interval — 60 s of sleeps alone, and the RESTART_SEARCH_PROCESS gating, the fabricated-id not-found reads, the empty ListVpcEndpointsForDomain and the 3-node positive control are never exercised.
This is the same root cause as the already-filed open issue 20261121T121321Z-opensearch-wall-clock-transient-windows-cost-a-client.md (wall-clock transient windows, `state::DOMAIN_WORK` and the `Domain::settle` path), but this check is NOT in that issue's Issue-Trace-Ids, so it carries no replay key there and is filed here so it is re-replayed too. Fixing that issue is expected to fix this check; if it has already been fixed, verify with this check id.
Fix: the lifecycle state the opensearch control plane materialises transient statuses from (the domain-work window and the settle path that consumes its due instant) — gate the transition on observation rather than wall clock, as that issue describes.
