# REOPENS: ivs channel RTMPS ingest remains undialable — CreateChannel still announces an ingestEndpoint host that is not one of the emulator's own hosts, so no channel can go LIVE

> _Note: this issue was identified against the code base at commit `7da46b6b1932d16aabd60d53009a566532e618cc`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
CreateChannel

## Description
REOPENS 20261122T024053Z-ivs-the-channel-rtmps-ingest-data-plane-is.md: its fix left the call refused.

Cause 1 of 1: the contribute (ingest) address an IVS channel announces still cannot be dialed by a client of this emulator, so the whole live-broadcast path of the service is unreachable. The earlier issue carried exactly these two checks as its Issue-Trace-Ids and is marked fixed; the fix added an in-process contribute plane and inserted a service label into the announced name (the host is now `<12-hex-label>.global-contribute.ivs.<zone>` instead of `<12-hex-label>.global-contribute.<zone>`), but the announced host is still not an address this process answers on, and both checks abort on the very first use of it with the same refusal.

Failing checks for this cause: ivs.rtmps-ingest-live-stream-lifecycle, ivs.rtmps-ingest-native-protocol-round-trip.

AWS: recorded behavior only for the member's spelling. Smithy (services/service-com-amazonaws-ivs-amazoninteractivevideoservice/smithy-model/com-amazonaws-ivs-amazoninteractivevideoservice.json, com.amazonaws.ivs, restJson1): CreateChannel -> {channel: Channel, streamKey: StreamKey}, HTTP POST /CreateChannel, 200; `Channel$ingestEndpoint` -> `IngestEndpoint` is documented "Channel ingest endpoint, part of the definition of an ingest server, used when you set up streaming software" and is a plain string with no @length and no @pattern; `StreamKey$value` is the @sensitive secret the encoder authenticates the publish with; GetStream(channelArn required, @length 1..128, @pattern ^arn:aws:ivs:[a-z0-9-]+:[0-9]+:channel/[a-zA-Z0-9-]+$) -> {stream: Stream} with modeled errors ChannelNotBroadcasting (@httpError 404), ResourceNotFoundException (404), ValidationException (400). On AWS an encoder that completes an RTMPS handshake to rtmps://<ingestEndpoint>:443/app/<streamKey> makes the channel live, and then: GetStream answers 200 with stream.state == "LIVE" and stream.channelArn equal to the channel's ARN; the announced playbackUrl serves an HLS multivariant playlist (#EXTM3U) once segments are packaged; InsertAdBreak on a LIVE channel with no ad configuration is refused 400 ValidationException, message fixed text "Request member: channelArn failed to satisfy the constraints: valid ad configuration is required to be associated with the channel requested for the ad break with ARN: " followed by the channelArn taken from the request (that ARN is the only variable part); StopStream on a live channel is accepted and GetStream then answers 404 ChannelNotBroadcasting with fixed text "Channel: " + the request's channelArn + " is not currently online"; GetStreamSession for that streamId reports both startTime and endTime; and after DeleteChannel, GetChannel answers 404 ResourceNotFoundException "Resource: " + the ARN + " not found". The member has no modeled form, so its spelling is free — but it exists only to be DIALED, so whatever spelling is chosen must be an authority a client of this emulator can actually connect to.

Emulator: both checks raise before any publish is attempted, on the value CreateChannel announced. The behavioral harness refuses the composed URL: `simparity.published.PublishedUrlRejected: endpoint_url was given rtmps://<12-hex-label>.global-contribute.ivs.<zone> (published by the emulator or built by the check): its host is not one of the emulator's own hosts; a customer of the emulator needs rtmps://127.0.0.1:<port>/<resource path>, or rtmps://<own host>:<port>/<path> on a per-resource listener`. The announced name is composed per request and is a name in a zone no resolver maps to this process: services/service-com-amazonaws-ivs-amazoninteractivevideoservice/src/state/channel_endpoints.rs `announced_channel` (lines 136-156) fills `ingestEndpoint` (and the identical `srt.endpoint`) from `announced_ingest_endpoint` (lines 166-169) -> `contribute_host_in` (lines 188-197), which formats `{minted_host_label}.{CONTRIBUTE_DOMAIN_LABEL}.{SERVICE_DOMAIN_LABEL}.{zone}` with CONTRIBUTE_DOMAIN_LABEL = "global-contribute" (line 85) and SERVICE_DOMAIN_LABEL = "ivs" (line 90), carrying no scheme and no port by design (module header lines 7-23). The contribute plane the fix added is reachable only IN PROCESS — the module's own doc at lines 171-186 (`contribute_host_on_this_machine`) states the register serves "a connection with a pipe inside this process" and that "a client off this machine could not be served a pipe in this process whatever name it was told" — so an out-of-process publisher (the check's ffmpeg, and any real encoder) has no address it can dial: the announced name does not resolve to this process, and the socket the plane actually bound is never announced in the response.

Why: a client that uses IVS the way AWS documents it — CreateChannel, read channel.ingestEndpoint and streamKey.value, point an encoder at rtmps://<ingestEndpoint>:443/app/<streamKey>, poll GetStream until LIVE, fetch playbackUrl — cannot get off the ground. Ingest, live-stream monitoring, HLS playback, ad insertion and StopStream are all unreachable, and the live-path error semantics (400 ValidationException for a missing ad configuration, 404 ChannelNotBroadcasting after StopStream, 404 ResourceNotFoundException after DeleteChannel) can never be observed. Code that works against AWS fails at the first contribution attempt here.

Fix: the announced-address projection together with the contribute plane it is supposed to name — `announced_ingest_endpoint`/`contribute_host_in` in src/state/channel_endpoints.rs and the plane `ensure_ingest_plane` opens — must announce an authority this process answers RTMP/RTMPS ON for an out-of-process client (one of the emulator's own hosts plus the port the plane bound, or a per-resource listener), and the publish must be authenticated by the stream key at the /app/<streamKey> path and must drive the state the reads already derive from (a Stream in LIVE with its streamId and startTime, a packaged HLS multivariant playlist at the announced playbackUrl path, and the unwind on StopStream/publisher exit: GetStream -> ChannelNotBroadcasting and a StreamSession carrying startTime and endTime). Note two related OPEN wire issues, neither of which covers reachability — 20261124T061238Z-ivs-announced-channel-endpoints-playbackurl-is-rooted-on.md and 20261123T105030Z-ivs-2-net-new-causes-createchannel-announces-loopback.md — they constrain only the recorded HOST FORM of these members (hostname, no port); satisfying their form alone is exactly what leaves the address undialable, so the chosen value must satisfy both the recorded member form and reachability from outside this process.

Traces: ivs.rtmps-ingest-live-stream-lifecycle, ivs.rtmps-ingest-native-protocol-round-trip (both fail at ctx.endpoint_url(ingest_endpoint, scheme='rtmps', aws_port=443) on the value CreateChannel announced).
