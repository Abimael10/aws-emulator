# rds__s3: the AddRoleToDBCluster s3Import trust scenario reaches no verdict — the whole 60 s budget is consumed before the good role settles ACTIVE or the ec2-trusting role is refused InvalidParameterValue

> _Note: this issue was identified against the code base at commit `abb164e6ce3e65cba242bbd0cd4b0598950b9faf`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
AddRoleToDBCluster

## Description
Cause 1 of 1: the Aurora PostgreSQL s3Import role-association path makes no observable progress — the check that distinguishes an rds.amazonaws.com-trusting role (accepted, settles ACTIVE) from an ec2.amazonaws.com-trusting one (refused InvalidParameterValue on every retry) is cut off at the suite's 60 s budget without reaching either assertion.

AWS: Smithy — AddRoleToDBCluster takes DBClusterIdentifier (required) and RoleArn (required, @length 20..2048, @pattern `^arn:aws[a-z-]*:iam::[0-9]*:role/.*$`) plus FeatureName, and models the errors DBClusterNotFoundFault (404), DBClusterRoleAlreadyExistsFault (400), DBClusterRoleQuotaExceededFault (400) and InvalidDBClusterStateFault (400). The trust-policy check is not one of those modeled faults: recorded behavior only — AWS refuses a role whose trust policy does not allow rds.amazonaws.com to assume it with the common client error code `InvalidParameterValue`, and that refusal is stable (it is returned on every retry, not a propagation window). A role that does trust rds.amazonaws.com is accepted and appears in DescribeDBClusters AssociatedRoles with Status transitioning to `ACTIVE`; FeatureName is `s3Import` for the Aurora PostgreSQL S3 import feature.

Emulator: the check never reaches any assertion. The replay reports only `Check timed out after 60.0s` — the CFN deploy of the cluster and the two roles, followed by the first AddRoleToDBCluster beat, does not complete inside the suite's budget, so neither the acceptance-and-ACTIVE path nor the InvalidParameterValue refusal is observed. The retry discipline the check measures (the bad role is refused for at least 3x the good role's propagation lag) is never exercised.

Hypothesis: either the CFN-deployed Aurora PostgreSQL cluster never settles to a state in which AddRoleToDBCluster can be called, or the role association never leaves its pending status — the replay does not say which, and nothing in it names a step past the deploy.

Why: a client cannot tell from the emulator whether an s3Import role association was accepted or refused, and gets no stable InvalidParameterValue for a role whose trust policy names the wrong service principal — so a misconfigured trust policy that AWS rejects outright looks indistinguishable from a working one, and the Aurora S3 import feature cannot be modelled at all.

Fix: the AddRoleToDBCluster handler and its validation (trust-policy check against rds.amazonaws.com producing a stable InvalidParameterValue refusal; AssociatedRoles state carried to `ACTIVE` for an accepted role), together with the DBCluster state machine the CFN-deployed Aurora PostgreSQL cluster goes through so the association can be attempted. Nearby open issues cover other rds__s3 areas and do not carry this check: 20261117T083457Z-rds-s3-2-net-new-causes-startexporttask-reaches.md, 20261118T090316Z-rds-s3-2-net-new-causes-aws-rds.md, and the unimplemented-stub issue 20261104T053605Z-rds-addroletodbinstance-stub.md (AddRoleToDBInstance, a different operation).

## Steps to Reproduce
1. Boot the emulator from this checkout.
2. CreateStack a template with an Aurora PostgreSQL DB cluster and two IAM roles carrying the same S3 read policy: one whose trust policy allows rds.amazonaws.com to assume it, one whose trust policy allows only ec2.amazonaws.com.
3. Wait for the stack to reach CREATE_COMPLETE and the cluster to become available.
4. Call AddRoleToDBCluster with the rds.amazonaws.com-trusting role and FeatureName 's3Import', then poll DescribeDBClusters: on AWS the AssociatedRoles entry reaches Status 'ACTIVE'.
5. Call AddRoleToDBCluster with the ec2.amazonaws.com-trusting role and the same FeatureName, repeatedly: on AWS every attempt is refused HTTP 400 `InvalidParameterValue`.
6. Re-replay the check in trace_ids to confirm a fix.
