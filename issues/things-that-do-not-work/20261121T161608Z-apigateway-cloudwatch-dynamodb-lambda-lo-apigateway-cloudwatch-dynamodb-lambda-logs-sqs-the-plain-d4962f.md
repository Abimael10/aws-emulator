Cause 1 of 1: a CreateStack/UpdateStack of the hand-written order-intake template never reaches an observable terminal outcome, and nothing on the deploy path answers before the check's cap.
AWS: Smithy (cloudformation) DescribeStacks -> Stack.StackStatus targets com.amazonaws.cloudformation#StackStatus, whose members are CREATE_IN_PROGRESS, CREATE_FAILED, CREATE_COMPLETE, ROLLBACK_IN_PROGRESS, ROLLBACK_FAILED, ROLLBACK_COMPLETE, DELETE_IN_PROGRESS, DELETE_FAILED, DELETE_COMPLETE, UPDATE_IN_PROGRESS, UPDATE_COMPLETE_CLEANUP_IN_PROGRESS, UPDATE_COMPLETE, UPDATE_FAILED, UPDATE_ROLLBACK_IN_PROGRESS, UPDATE_ROLLBACK_FAILED, UPDATE_ROLLBACK_COMPLETE_CLEANUP_IN_PROGRESS, UPDATE_ROLLBACK_COMPLETE, REVIEW_IN_PROGRESS, IMPORT_IN_PROGRESS, IMPORT_COMPLETE, IMPORT_ROLLBACK_IN_PROGRESS, IMPORT_ROLLBACK_FAILED, IMPORT_ROLLBACK_COMPLETE. On AWS a CreateStack of this template (REST API with POST /orders, two Lambda functions, a DynamoDB table, an SQS queue, an event-source mapping, a log group and a CloudWatch alarm) always leaves its *_IN_PROGRESS status for one of the terminal members in bounded time, and every call on the deploy path (CreateStack, DescribeStacks, DescribeStackEvents, DescribeStackResources) returns a response: a resource handler that fails lands the stack in CREATE_FAILED/ROLLBACK_COMPLETE carrying a ResourceStatusReason for the failing logical resource, it does not stop answering. The per-leg application assertions that follow (queue delivery, the two structured JSON log lines, the metric datapoint, the alarm echoing its declared Period, the denied UpdateItem, the in-place second apply, the post-destroy refusals) are recorded behavior only.
Emulator: the check's entire detail is the single line 'Error: Check timed out after 60.0s'. No terminal StackStatus, no HTTP status line from the deployed stage, no response body, no error code and no error message were observed at all. The check's own per-leg ceilings are all far larger than the harness cap it died at (_DEPLOY_BUDGET_S = 600.0, _ROUTE_BUDGET_S = 180.0, _WORKER_BUDGET_S = 180.0, _LOG_BUDGET_S = 240.0, _METRIC_BUDGET_S = 300.0), so this is not a leg assertion firing on a converged-but-wrong stack — it is the absence of any observable outcome on the deploy path.
Why: a client deploying a plain CloudFormation application against the emulator gets neither a converged stack nor a diagnosable failure. Every waiter written against DescribeStacks (the AWS CLI's `cloudformation wait stack-create-complete`, the SDK StackCreateComplete waiters, any CI deploy script) blocks until its own timeout, no rollback reason is ever retrievable, and no behavior of the deployed estate is reachable.
Fix: the CreateStack/UpdateStack progression in the cloudformation crate's stack lifecycle state machine — a stack must always leave its *_IN_PROGRESS status for a modeled terminal StackStatus within bounded time, including when a nested resource handler errors (which must land as *_FAILED or ROLLBACK_COMPLETE carrying the ResourceStatusReason for the failing resource), and no call on that path (CreateStack, DescribeStacks, DescribeStackEvents, DescribeStackResources) may block instead of answering.

## Evidence
Expected: CreateStack of the order-intake CloudFormation template with Capabilities=[CAPABILITY_IAM, CAPABILITY_NAMED_IAM] reaches a terminal StackStatus — CREATE_COMPLETE on AWS, or a modeled *_FAILED/ROLLBACK_COMPLETE whose DescribeStackEvents carries a ResourceStatusReason naming the failing logical resource — after which POST /orders on the deployed stage answers 2xx with a body echoing the submitted orderId, and the wiring/worker/logs/metrics/alarm/denial/drift/teardown legs are graded.

Actual: the replayed check emits exactly one line — 'Error: Check timed out after 60.0s' — with no terminal stack status, no HTTP status line, no body, no error code and no error message. Zero of the nine legs are graded.

Status/code/message requirement: AWS never answers this path by not answering. A refusal here must be a modeled terminal StackStatus plus a ResourceStatusReason whose fixed text is AWS's wording for that resource type's failure class, with its variable parts (the logical resource id, the resource type, the offending property name and value) taken from the submitted template and the emulator's state. The ids, stack names and timestamps of any single run fill that template and are not part of it.
