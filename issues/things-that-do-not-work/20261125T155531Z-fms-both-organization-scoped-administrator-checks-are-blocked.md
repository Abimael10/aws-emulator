# fms: both organization-scoped administrator checks are blocked because organizations DescribeOrganization refuses 404 AWSOrganizationsNotInUseException where the recording serves the organization and its management account

> _Note: this issue was identified against the code base at commit `fbb1a06f1c20de0c01a698c058987963365385aa`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
DescribeOrganization

## Description
REOPENS 20261104T063936Z-account-organizations-describeorganization-reports-an-organization-on-a-freshly.md: its fix left the call refused.

One root cause.

Cause 1 of 1: the emulated caller belongs to no organization at all, so Organizations DescribeOrganization — the call both Firewall Manager organization-scoped checks make to learn the organization's management account before they exercise FMS — is refused instead of answered, and neither check reaches a single fms operation. Failing checks: fms.get-admin-scope-malformed-account-rejected, fms.list-admin-accounts-for-organization-unconfigured-not-found.

AWS: Smithy (services/service-com-amazonaws-organizations-awsorganizationsv20161128/smithy-model/com-amazonaws-organizations-awsorganizationsv20161128.json) models DescribeOrganization with input smithy.api#Unit and output DescribeOrganizationResponse{Organization}; errors AccessDeniedException (403), AWSOrganizationsNotInUseException (404), ConcurrentModificationException (409), ServiceException (500), TooManyRequestsException (429). Organization.MasterAccountId targets AccountId (@length 0..12, @pattern ^\\d{12}$) and is documented "The unique identifier (ID) of the management account of an organization". The operation's own documentation states "This operation can be called from any account in the organization" — i.e. a MEMBER account, not only the management account, reads it successfully. AWSOrganizationsNotInUseException is documented "Your account isn't a member of an organization. To make this request, you must use the credentials of an account that belongs to an organization." (all fixed text, no variable parts) and is therefore the answer ONLY for a standalone account. Recorded behavior for both of these checks: the caller is a member — but NOT the management account — of an organization, so DescribeOrganization answers HTTP 200 with a populated Organization whose MasterAccountId is a management account id different from the caller's account, and the FMS calls that follow are then refused with the modeled InvalidOperationException whose message names that management account (fixed text " is not the management account of the Organization but is attempting to perform an action that only the Organization management account can perform. The Organization management account is ", with the caller's account id leading the message and Organization.MasterAccountId closing it — both values taken from the request credentials and Organizations state, never literals from one run).

Emulator: DescribeOrganization answers HTTP 404 with error code "AWSOrganizationsNotInUseException" and message "Your account isn't a member of an organization. To make this request, you must use the credentials of an account that belongs to an organization." for every caller on a freshly booted emulator, because no organization is ever established: the organization slot stays None until a CreateOrganization request writes it (services/service-com-amazonaws-organizations-awsorganizationsv20161128/src/service.rs, EmulatedService::new, whose doc comment now states that mounting establishes NO organization), and the read handler takes its refusal arm on that None (src/ops/describe_organization.rs lines 134-143, with crate::state::NOT_IN_USE_MESSAGE as the message). The emulated environment has no account that is a member of an organization it does not manage, so the state both FMS checks presuppose is unreachable over the wire: the only membership a caller can create is one in which it IS the management account (CreateOrganization makes the calling account the management account), which is the opposite of what these two operations' gate requires. Both checks consequently abort with botocore.errorfactory.AWSOrganizationsNotInUseException raised from the DescribeOrganization call, after their FMS positive controls had already passed (GetAdminScope with AdminAccount="not-an-account-id" -> ValidationException with the exact pattern message; GetAdminAccount -> ResourceNotFoundException with an empty message).

Why: a client cannot discover the organization it is a member of, nor who the management account is. The idiomatic flow for every management-account-only control-plane call — read DescribeOrganization, compare MasterAccountId with the caller, and re-issue from (or report) the management account — always takes the "this account is in no organization" branch, so member-account behaviour of every organization-scoped service is unobservable: consolidated-billing and SCP-gated paths, delegated-administrator discovery, and in particular Firewall Manager's management-account gate, whose refusal is defined in terms of a management account the client must be able to read. A client that handles the 404 as "not enrolled" and calls CreateOrganization is then made the management account, which silently converts the member-account scenario into a management-account one and makes the gate's refusal disappear entirely. Both FMS refusals that the suite grades (GetAdminScope for a well-formed, unregistered 12-digit AdminAccount and ListAdminAccountsForOrganization with no arguments) are left completely unexercised — the fix claimed by the fixed issue 20261104T183010Z-fms-management-account-gate-answers-unmodeled-accessdeniedexception-instead.md (gate must answer the modeled InvalidOperationException with the management-account message rather than AccessDeniedException) can no longer be confirmed by either check, because neither reaches an fms call.

Fix: the Organizations control plane's state and construction seam — crate::state (the organization slot and create_organization) reached through services/service-com-amazonaws-organizations-awsorganizationsv20161128/src/service.rs EmulatedService::new — must be able to present the emulated account as a MEMBER of an organization whose management account is a different account, so DescribeOrganization serves 200 with Organization{Id, Arn, FeatureSet, MasterAccountId, MasterAccountArn, MasterAccountEmail} and MasterAccountId != the caller, while a genuinely standalone account keeps the existing 404 AWSOrganizationsNotInUseException arm. The fms side is then the gate and its two handlers (services/service-com-amazonaws-fms-awsfms-20180101/src/ops/get_admin_scope.rs and src/ops/list_admin_accounts_for_organization.rs together with crate::state's refusal construction), which must read that management account and refuse with the modeled InvalidOperationException message above. Note the two requirements that must be reconciled rather than flip-flopped: the account check account.start-primary-email-update-self-target-denied requires a caller in NO organization, while these two fms checks require a caller that is a member but not the management account; satisfying one by making the other impossible is what produced this regression, so membership must be expressible per caller/account rather than as a single global on/off.

Traces: fms.get-admin-scope-malformed-account-rejected (errored on organizations.describe_organization() after the ValidationException positive control passed) and fms.list-admin-accounts-for-organization-unconfigured-not-found (errored on organizations.describe_organization() after the GetAdminAccount ResourceNotFoundException positive control passed). Code citations: organizations crate src/service.rs lines 62-77 (no membership established at mount), src/ops/describe_organization.rs lines 134-143 (the refusal arm taken), src/state.rs NOT_IN_USE_MESSAGE and create_organization; fms crate src/ops/get_admin_scope.rs and src/ops/list_admin_accounts_for_organization.rs (the management-account gate call sites that are never reached).

1. Boot the emulator fresh (no prior requests; in particular no organizations CreateOrganization).
2. Call organizations DescribeOrganization with no input.
   Expected (recorded): HTTP 200 with Organization populated and Organization.MasterAccountId a 12-digit management account id that is NOT the caller's account.
   Actual: HTTP 404 "AWSOrganizationsNotInUseException" / "Your account isn't a member of an organization. To make this request, you must use the credentials of an account that belongs to an organization."
3. Because step 2 refuses, the two FMS refusals that depend on the management account cannot be reached. With step 2 fixed, verify them directly:

   c. fms GetAdminAccount -> ResourceNotFoundException with an empty Message (passes today; keep it passing).
   d. fms ListAdminAccountsForOrganization{} -> HTTP 400 "InvalidOperationException" with the same management-account message.
4. Equivalently, re-replay behavioral checks fms.get-admin-scope-malformed-account-rejected and fms.list-admin-accounts-for-organization-unconfigured-not-found; both must pass end to end, with the two positive controls still passing.
