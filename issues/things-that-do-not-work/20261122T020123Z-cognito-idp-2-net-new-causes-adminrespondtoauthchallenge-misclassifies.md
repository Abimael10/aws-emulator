# cognito-idp: 2 net-new causes — AdminRespondToAuthChallenge misclassifies a session bound to another app client/user as CodeMismatchException, and UpdateProvisionedLimit again accepts a same-as-current RequestedLimitValue

> _Note: this issue was identified against the code base at commit `9646fdd566ff3c090b230e575cd06b10ee53c1e6`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
AdminRespondToAuthChallenge

## Description
Two distinct net-new root causes on the cognito-idp challenge-session and account provisioned-limit planes. Each cause below must be closed before submitting.

Cause 1 of 2: AdminRespondToAuthChallenge refuses a Session the pool DID issue, but that belongs to another app client or another user, with the unissued-session error class instead of the session-binding one.
AWS: Smithy (AdminRespondToAuthChallenge): input Session -> SessionType (@length 20..4096, sensitive, optional), ClientId and UserPoolId required, ChallengeResponses a sensitive map; modeled errors include NotAuthorizedException (client, HTTP 403) and CodeMismatchException (client, HTTP 400). Recorded behavior: AWS distinguishes two refusals on the same operation. (a) A Session string the pool never issued is a code/session mismatch: HTTP 400, CodeMismatchException, message "Invalid code/session provided" (entirely fixed text, nothing interpolated). (b) A Session the pool genuinely issued, but presented under a DIFFERENT app client than the one it was issued to, or with a ChallengeResponses.USERNAME naming a different user than the session's, is a session-binding failure: HTTP 403, NotAuthorizedException, message "Invalid session for the user." (fixed text, nothing interpolated). The same 403 NotAuthorizedException "Invalid session for the user." is served when the session's user has been disabled mid-challenge. In every one of these refusals the challenge session is NOT spent: the original (client, user, session) triple still completes afterwards and issues all three tokens. In the same operation AWS keeps the other refusal classes separate too: a wrong ChallengeName for the live session is CodeMismatchException "Invalid code or auth state for the user.", a weak NEW_PASSWORD is InvalidPasswordException, a missing NEW_PASSWORD / missing USERNAME are InvalidParameterException.
Emulator: the cross-client and cross-user cases are refused as CodeMismatchException with the message "Invalid code/session provided" — i.e. the unissued-session class (HTTP 400) is served where AWS serves the session-binding class (HTTP 403 NotAuthorizedException "Invalid session for the user."). The wrong-ChallengeName case in the same check is answered correctly, so the handler has the other sentences; it is specifically the session-resolution branch that collapses "issued but bound elsewhere" into "not a session I know". The open issue 20261116T030210Z-cognito-idp-respondtoauthchallenge-a-session-the-pool-never.md asks for CodeMismatchException on the never-issued session only; it does not describe this binding case, and the two must not be answered with the same class.
Why: a client that branches on the modeled error takes the wrong path for every mis-routed session — a 400 CodeMismatchException tells the UI the user mistyped a code and should re-enter it, where AWS's 403 NotAuthorizedException tells it the session cannot be used by this client/user and authentication must be restarted; SDK layers that classify 4xx retry/throttle behavior by status also diverge (400 vs 403). Because the check stops at this refusal, the downstream AWS guarantees it asserts (the session survives every rejection and still completes, a disabled user's session is refused without changing the user's Enabled/UserStatus) are left unverified on the emulator.
Fix: the session-resolution branch of the AdminRespondToAuthChallenge handler (and the shared challenge-session validation it uses with RespondToAuthChallenge) in the cognito-idp crate: resolve the presented Session first, and when it resolves to a session issued for a different ClientId or a different username — or to a user that is now disabled — raise NotAuthorizedException (403) with "Invalid session for the user.", reserving CodeMismatchException "Invalid code/session provided" for a session the pool never issued; no refusal may consume the session.
Traces: cognito-idp.admin-respond-to-auth-challenge-rejects-bad-responses-without-spending-the-session.

Cause 2 of 2: UpdateProvisionedLimit accepts a RequestedLimitValue equal to the value already provisioned instead of refusing it as a no-op.
AWS: Smithy (UpdateProvisionedLimit): input {LimitDefinition (required), RequestedLimitValue (IntegerType, required)} -> output Limit (required, LimitType); modeled errors InvalidParameterException (client, 400) and ServiceQuotaExceededException (client, 400). Recorded behavior: for LimitDefinition {LimitClass: API_CATEGORY, Attributes: {Category: UserCreation}}, re-requesting the value GetProvisionedLimit currently reports as ProvisionedLimitValue is refused with HTTP 400 InvalidParameterException and the message "Requested value is the same as the current provisioned limit" — entirely fixed text, nothing interpolated from the request. A request above the account's Service Quotas ceiling is refused ServiceQuotaExceededException with "Requested value <requested> exceeds Service Quota ceiling of <ceiling>", whose fixed text is "Requested value " / " exceeds Service Quota ceiling of " and whose two variable parts are the request's RequestedLimitValue and the account's ceiling; a refused request must not move the persisted value, and an accepted one echoes the requested integer in Limit.ProvisionedLimitValue and reads back identically through GetProvisionedLimit.
Emulator: the same-value request is answered HTTP 200 with a Limit, so the no-op guard is absent again and the check fails with "UpdateProvisionedLimit accepted RequestedLimitValue=50 even though it already equals the current ProvisionedLimitValue" (50 is this account's FreeLimitValue/ProvisionedLimitValue in the run; the requirement is the equality, not the number).
Why: a client cannot tell an applied capacity change from a request AWS rejects — the guard AWS uses to make the operation non-idempotent on purpose (so a repeated submission surfaces as an error rather than silently re-provisioning) is gone, and automation that treats 200 as "the limit moved" acts on a change that never happened.
Fix: the UpdateProvisionedLimit handler and the account-level provisioned-limit state in the cognito-idp crate: compare RequestedLimitValue to the category's current ProvisionedLimitValue and refuse InvalidParameterException with AWS's sentence before applying anything. Note the history on this exact rule so the fix does not oscillate: the resolved issues 20261119T040922Z-cognito-idp-updateprovisionedlimit-accepts-a-requestedlimitvalue-equal-to.md and 20261116T030210Z-cognito-idp-updateprovisionedlimit-re-applying-the-account-s.md claimed this same-value refusal, and 20261119T121724Z-cognito-idp-reopens-cognito-idp-updateprovisionedlimit-again-refuses-re-applying.md reopened it in the opposite direction; a resolved issue covers nothing, and the guard must key strictly on equality with the CURRENT ProvisionedLimitValue so that re-applying the current value is refused while any different in-range value is still accepted and echoed. Cause 7 of the open issue 20261117T112621Z-cognito-idp-8-net-new-causes-cors-preflight.md describes the broader "UpdateProvisionedLimit accepts everything" surface but does not carry this check.
Traces: cognito-idp.provisioned-limit-numeric-precision-preserved.
