## Description
ONE net-new root cause on the emulated kafka (MSK) surface, grounded in a failing behavioral check the suite lists under `### kafka`. The check's current replay key is carried by NO open issue, so nothing gates it: the open issue 20261116T234316Z-kafka-msk-native-data-plane-the-concurrent-producer-check.md does list this same check id, but it carries the key `...|_prove_executor_in_vpc#2|AssertionError|raise _no_executor(` (a Lambda-with-VpcConfig egress refusal, errno 101 'a Lambda function in this emulator reaches no host'), while this replay produced no frame at all — the check was killed on the harness ceiling before it reached that assertion — so this failure is not covered by it and the suite did not mark it OWNED or ALREADY FILED. Two further open issues name the same family for OTHER check ids and carry none of this one: 20261118T020526Z-kafka-msk-native-data-plane-the-broker-authorizes-no.md (whose Cause 6 is exactly this 60 s-ceiling shape for three different check ids) and 20261116T210722Z-kafka-msk-native-data-plane-sasl-iam-bring-up.md.

Cause 1 of 1: the MSK Serverless bring-up path the native data plane depends on does not complete inside a client-sized budget, so the transactional abort/isolation behavior is unmeasurable — the check ends on the bare 60 s ceiling with no HTTP status, no Kafka protocol error and not one assertion evaluated.
AWS: CreateClusterV2 with a `serverless` request (Smithy: CreateClusterV2, POST /api/v2/clusters, input member Serverless -> ServerlessRequest, output member State -> ClusterState) answers State CREATING and the cluster settles to ACTIVE, observable via DescribeClusterV2 (Smithy: GET /api/v2/clusters/{ClusterArn}, output ClusterInfo -> Cluster). GetBootstrapBrokers (Smithy: GET /v1/clusters/{ClusterArn}/bootstrap-brokers, output member BootstrapBrokerStringSaslIam, jsonName bootstrapBrokerStringSaslIam, target __string) then publishes a comma-separated host:port list, and a client inside the cluster's own VPC completes a SASL_SSL / AWS_MSK_IAM handshake on tcp/9098 and is served ApiVersions, Metadata, CreateTopics, InitProducerId, Produce, ListOffsets and Fetch. The Kafka wire protocol itself is outside the Smithy model, so the data-plane half is recorded behavior plus the Apache Kafka transaction protocol: records flushed inside an OPEN transaction are invisible to a read_committed consumer and visible, in order and byte-identical, to a read_uncommitted one; ListOffsets(LATEST) answers the HIGH WATERMARK under read_uncommitted and the LAST STABLE OFFSET under read_committed for the same partition at the same instant; an ABORT and a COMMIT control batch each physically occupy one offset, so after 5 aborted + 5 committed records the committed batch begins at offset 6 and the log end is 12, with a gap at the abort marker's offset; and a second InitProducerId on the same transactional id bumps the epoch, so the first producer's commit_transaction() is refused with PRODUCER_FENCED (Kafka error 90) while its already-appended record stays visible to read_uncommitted and never becomes committed. (The topic names, transactional ids and the advertised host:port are per-run values; the offsets, the error name and the error number are the requirement.)
Emulator: the check produces the verdict `mismatch` with the single detail `Error: Check timed out after 60.0s`. Nothing was asserted: the bring-up barrier this check shares — serverless cluster CREATING -> ACTIVE, an in-VPC executor the emulator's Lambda surface must give a route, then an endpoint from GetBootstrapBrokers that both accepts TCP and serves a Kafka metadata request over SASL/IAM — does not complete in the budget. Because the emulator owns those lifecycle transitions, announces those endpoints, and (per the related issue above) is what restricts a VpcConfig function's egress to the X-Ray daemon address, the stall is the emulator's and not the runner's.
Why: a client that provisions an MSK Serverless cluster and connects a transactional AWS_MSK_IAM producer blocks until its own timeout instead of receiving acknowledgements or an error. The whole transactional-isolation contract — read_committed vs read_uncommitted visibility, per-isolation ListOffsets answers, control batches occupying real offsets, and PRODUCER_FENCED on epoch bump — is unverifiable against the emulator, so exactly-once application code validated here is validated against nothing.
Fix: the kafka crate's cluster-lifecycle state machine (CreateClusterV2/DescribeClusterV2 must settle to ACTIVE promptly on the write path, so a first probe after the create observes the terminal value) and the native broker plane reached through the endpoints GetBootstrapBrokers advertises — it must accept connections and complete the SASL/IAM handshake on every address it announces, and implement the transaction coordinator (InitProducerId, AddPartitionsToTxn, EndTxn with ABORT/COMMIT control batches, isolation-level-aware Fetch and ListOffsets, epoch fencing) rather than leaving the client hanging; the in-VPC reachability half belongs to the lambda crate's VpcConfig sandbox networking.
Traces: kafka.msk-transactional-abort-invisible-to-read-committed-visible-to-read-uncommitted.
