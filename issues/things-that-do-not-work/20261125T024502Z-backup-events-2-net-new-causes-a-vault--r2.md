=== Cause 1 of 2: no native 'Backup Job State Change' event is published for a real StartBackupJob, so a rule scoped to one backup vault's ARN in the event detail delivers nothing and the detail-level vault scoping cannot be observed at all ===
AWS: recorded behavior only for the EventBridge envelope — the backup model documents no events. Smithy (backup, com-amazonaws-backup-cryocontrollerusermanager): StartBackupJob PUT /backup-jobs 200, required BackupVaultName (pattern ^[a-zA-Z0-9\-\_]{2,50}$), ResourceArn, IamRoleArn, returns BackupJobId; DescribeBackupJob GET /backup-jobs/{BackupJobId} reports State (enum BackupJobState), StatusMessage, MessageCategory. Smithy (eventbridge): PutTargets Targets @required (1..100), PutEvents Entries @required (1..10). Recorded behavior: each state transition of an on-demand backup job is published on the default bus of the vault's Region as source="aws.backup", detail-type="Backup Job State Change", with a detail carrying at least backupJobId, state, backupVaultArn and resourceArn; an ENABLED rule whose EventPattern is {"source":["aws.backup"],"detail-type":["Backup Job State Change"],"detail":{"backupVaultArn":[<target vault arn>]}} with an SQS target whose queue policy grants events.amazonaws.com sqs:SendMessage under Condition ArnEquals aws:SourceArn=<rule arn> receives the envelope for a job started in THAT vault and receives nothing for an otherwise identical concurrent job in another vault. Job ids, vault ARNs, table names and timestamps are per-run values; the requirement is the envelope's source, its detail-type, the presence of detail.backupJobId / detail.backupVaultArn, and the exact-match scoping of the pattern.
Emulator: nothing is ever delivered. The replay reports '[mismatch] backup__events.eventbridge-rule-scoped-to-specific-backup-vault-arn — Error: Check timed out after 60.0s'. No call is refused and no error code or message diverges; the determinable fact is that the shared 220 s observation window (`_poll_sqs_for_target_and_leak`, sqs.ReceiveMessage with WaitTimeSeconds=10) makes no progress, so neither the positive assertion ('event for the exact target vault ARN must be delivered') nor the negative one ('event for a different vault ARN must not be delivered') is ever graded. The two StartBackupJob calls themselves are accepted. Hypothesis (stated by neither the model nor the recording, and the first thing to measure): no aws.backup 'Backup Job State Change' envelope is put on the default bus at all, and the jobs that would publish it die immediately with the AccessDenied outcome documented as Cause 1 of open issue 20261124T140401Z — instrument whether the publication is absent or whether the job never reaches a publishable state.
Why: a client that scopes an EventBridge rule to a single vault ARN to drive per-vault automation (notification, compliance reporting, copy-on-completion) sees the rule never fire, and cannot distinguish 'no backup happened' from 'the event was never delivered'. A negative test over another vault's ARN also passes vacuously, so an over-permissive rule match would go undetected.
Fix: the Backup job lifecycle's state-change publication path in the backup crate (start-backup-job / job-state machinery must put an aws.backup 'Backup Job State Change' event with backupJobId / state / backupVaultArn / resourceArn on the default bus for each transition), plus the latency of the job states the check waits on, so EventBridge's existing detail-level pattern matching and SQS target dispatch can route it inside a client's convergence window.
Traces: backup__events.eventbridge-rule-scoped-to-specific-backup-vault-arn.

=== Cause 2 of 2: the Lambda-target invoke-permission gate for an EventBridge rule is never exercised — a custom-source PutEvents round trip produces no observable delivery either before or after AddPermission ===
AWS: recorded behavior only (no model statement covers target invocation). Smithy (eventbridge): PutEvents Entries @required 1..10; PutTargets Rule/Targets @required. Recorded behavior: an ENABLED rule whose EventPattern is {"source":["sim2real.backup"],"detail-type":["Backup Job State Change"],"detail":{"state":["COMPLETED"]}} with a Lambda target must NOT invoke the function while the function's resource policy carries no lambda:InvokeFunction grant for principal events.amazonaws.com scoped to that rule ARN, and MUST invoke it once lambda.AddPermission grants exactly that; the invoked handler then forwards the event's detail.backupJobId marker to SQS. The markers are per-run UUIDs; the requirement is the two-sided outcome — no invocation without the grant, an invocation carrying the latest attempt's marker after it.
Emulator: the replay reports '[mismatch] backup__events.eventbridge-rule-missing-target-permission-backup-job-event-not-invoked — Error: Check timed out after 60.0s'. Nothing is refused; the check is cut off before the post-grant positive control ('positive control: Lambda was not invoked even after granting the invoke permission') is reached, so neither half of the permission gate is graded. This leg does not depend on a real backup job — the event is published by PutEvents under the non-reserved source 'sim2real.backup' — so the job-outcome defect of Cause 1 cannot explain it: the EventBridge rule→Lambda target dispatch leg itself yields no invocation inside the window.
Why: a client cannot tell whether EventBridge honours a Lambda target's resource policy. Both failure modes are consequential and both are currently unobservable: an unauthorized rule that silently invokes the function is a privilege escalation, and an authorized rule that never invokes it is silent data loss in the integration.
Fix: the EventBridge rule-target dispatch path for Lambda targets in the events crate — it must evaluate the target function's resource policy (principal events.amazonaws.com, SourceArn = the rule ARN), invoke only when permitted, and invoke promptly once AddPermission has granted it, so the delivery completes well inside a normal observation window.
Traces: backup__events.eventbridge-rule-missing-target-permission-backup-job-event-not-invoked.
