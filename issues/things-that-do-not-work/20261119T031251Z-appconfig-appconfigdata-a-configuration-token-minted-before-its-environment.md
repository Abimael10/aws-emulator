# appconfigdata: a configuration token minted before its environment was deleted keeps serving the withdrawn configuration forever when the same token is re-presented — the withdrawal deadline is written only onto the rotated successor session

> _Note: this issue was identified against the code base at commit `0cb56282b0b5db0d156916db95a8cefdc5d77df2`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
GetLatestConfiguration

## Description
One net-new root cause.

Cause 1 of 1: the AppConfig data plane never withdraws a configuration from a client that re-presents the SAME ConfigurationToken. The deadline that turns "the session's triple no longer resolves" into the modelled ResourceNotFoundException is recorded only on the SUCCESSOR session the poll mints, never on the session entry the presented token resolves to, so a client polling with a token minted before its environment was deleted is served HTTP 200 and the deleted environment's configuration bytes on every poll, for the token's whole 24-hour lifetime. Failing check: appconfig.session-against-deleted-environment-rejected.

AWS: deleting an environment withdraws it from the data plane, and a capability minted before the deletion is not a permanent grant on withdrawn state — appconfigdata GetLatestConfiguration answers the modelled ResourceNotFoundException (Smithy: appconfigdata common error ResourceNotFoundException, @httpError 404, "The requested resource could not be found.") for a token whose environment no longer exists, naming the resource that is gone (ResourceType/ReferencedBy on that shape). Re-presenting a token the client still holds is a supported client behaviour, not an error: Smithy doc for ConfigurationToken/NextPollConfigurationToken says "To support long poll use cases, the tokens are valid for up to 24 hours. If a GetLatestConfiguration call uses an expired token, the system returns BadRequestException" — the only thing that invalidates a token on its own is TIME, so the withdrawal must be decided by the state of the session's triple, independently of which token of the chain is presented. Recorded behavior only for HOW LONG the data plane may lag the control-plane delete: the check polls for the refusal rather than demanding it instantly, so any bounded convergence is acceptable; never converging is not.

Emulator: GetLatestConfiguration re-resolves the session's triple, finds the deleted environment unresolvable, and takes the `Resolution::FromBinding` branch — serving the configuration the session is bound to and making the refusal fall due one WITHDRAWAL_SPAN (3s) later. But that deadline is only ever assigned to `next_session`, the clone stored under the freshly minted successor token; the entry keyed by the token the caller actually presented is touched only by `record_token_use` (last_used_at) and keeps `withdrawal_due_at = None`. `Session::binding_in_force` treats `withdrawal_due_at == None` as "nothing withdrawn", so each poll of that same token re-enters the identical state: 200 + the withdrawn bytes, a brand-new successor carrying a brand-new 3-second deadline nobody will ever present, and no convergence. The check polls the pre-deletion token every 5s for up to 300s, never observes a refusal, and is killed by the harness: 'Check timed out after 60.0s'. Hypothesis (for the budget attribution only): this is the loop that consumed the budget — the check's other two waits do converge against this build (DeleteEnvironment removes the stored environment record outright, so GetEnvironment answers ResourceNotFoundException on the first try, and StartConfigurationSession resolves the triple against the control plane and refuses ResourceNotFoundException on the first try), while the pre-token poll provably cannot.

Why: a long-polling client — exactly the use case the 24-hour token lifetime exists for — is served configuration from a resource the account has deleted, indefinitely, and never learns the environment is gone. Deleted state stays readable through the data plane (an over-permissive read), a client that must fail closed when its configuration is withdrawn instead keeps running on stale bytes, and the documented recovery of re-presenting a token whose response was not persisted silently pins the client to withdrawn configuration rather than returning the 404 it would branch on. Note that the emulator's behaviour is correct for a client that follows the rotation (presents NextPollConfigurationToken each time), which is why the defect is invisible to the passing appconfigdata checks and shows up only on the re-presented token.

Fix: appconfigdata's GetLatestConfiguration handler and its session store — the withdrawal deadline belongs to the POLL CHAIN, not to one rotated entry, so the poll that first finds the triple withdrawn must record it on the session the presented token resolves to as well as on the successor it mints (and a live resolution must clear it on both), so the chain converges on the refusal whichever of its still-live tokens the client presents. Equivalently, hold the deadline on a per-session record the tokens of one chain share instead of copying it into each token's session clone.

## Evidence
Expected (recorded AWS, as the check encodes it): after DeleteEnvironment on a deployed environment, (a) GetEnvironment answers ResourceNotFoundException, (b) StartConfigurationSession for that environment answers ResourceNotFoundException, (c) GetLatestConfiguration presented with the ConfigurationToken minted BEFORE the deletion answers ResourceNotFoundException (HTTP 404) within the poll window, and (d) a sibling environment deployed with the same version keeps serving its exact bytes on a fresh session.

Actual (emulator): (c) never happens. The pre-deletion token is served HTTP 200 with the deleted environment's configuration on every poll; the check's loop (`while time.monotonic() < deadline: try acd.get_latest_configuration(ConfigurationToken=pre_token) ... time.sleep(5.0)`, _REFUSAL_TIMEOUT_S = 300) records no ClientError and the whole check is killed — replay detail, verbatim: `Error: Check timed out after 60.0s`. The assertion that would have fired is "a configuration token minted before the environment was deleted must stop serving with ResourceNotFoundException".

Mechanism, from the checkout: in get_latest_configuration.rs STEP 4, `state.record_token_use(&token, now)` records only `last_used_at` on the presented entry; the deadline goes to the clone — `next_session.withdrawal_due_at = match resolution { Live(_) => None, FromBinding(_) => Some(session.withdrawal_due_at.unwrap_or_else(|| withdrawal_deadline(now))) }` — which `state.store_session(next_session, now)` files under a NEW token. The presented entry therefore still has `withdrawal_due_at: None` (set at `start_session`), and `Session::binding_in_force` is `self.bound_configuration.as_ref().filter(|_| self.withdrawal_due_at.is_none_or(|due| now < due))`, i.e. unconditionally Some. Every poll of the same token is a first poll again.

Smithy (services/service-com-amazonaws-appconfigdata-appconfigdata/smithy-model/com-amazonaws-appconfigdata-appconfigdata.json): GetLatestConfiguration GET /configuration; common errors BadRequestException (400), InternalServerException (500), ResourceNotFoundException (404), ThrottlingException (429). ResourceNotFoundException carries Message, ResourceType and ReferencedBy, so the refusal must name the environment that is gone. The token members' own docs supply the 24-hour validity and the BadRequestException-on-expiry rule — the only time-based invalidation of a token.

## Steps to Reproduce
1. appconfig CreateApplication; CreateEnvironment twice (call them DOOMED and SIBLING); CreateConfigurationProfile LocationUri=hosted; CreateHostedConfigurationVersion Content='{"shared":"between-both-environments"}' ContentType=application/json.
2. appconfig CreateDeploymentStrategy DeploymentDurationInMinutes=0 GrowthFactor=100 FinalBakeTimeInMinutes=0 ReplicateTo=NONE; StartDeployment of that version into BOTH environments and wait for each to settle.
3. appconfigdata StartConfigurationSession(app, DOOMED, profile) -> keep the returned InitialConfigurationToken (call it PRE_TOKEN); GetLatestConfiguration(PRE_TOKEN) -> 200 with the deployed bytes. Do the same for SIBLING.
4. appconfig DeleteEnvironment(ApplicationId, EnvironmentId=DOOMED, DeletionProtectionCheck=BYPASS); confirm GetEnvironment(DOOMED) now answers ResourceNotFoundException and ListEnvironments no longer lists it.
5. appconfigdata StartConfigurationSession(app, DOOMED, profile) -> correctly refused ResourceNotFoundException.
6. appconfigdata GetLatestConfiguration(ConfigurationToken=PRE_TOKEN) — the SAME token, re-presented — and keep re-presenting it every 5 seconds: AWS converges on ResourceNotFoundException; the emulator answers HTTP 200 with the deleted environment's configuration every time and never converges (observed until the harness killed the check at 60s; by construction it would continue for the token's full 24-hour lifetime).
7. Contrast: present the NextPollConfigurationToken returned by the first post-deletion poll instead of PRE_TOKEN, and the second poll IS refused — showing the deadline lands only on the rotated successor.
8. Positive control: a fresh session on SIBLING still serves the exact deployed bytes.
