# cloudformation: DeleteChangeSet of an EXECUTED (EXECUTE_COMPLETE) UPDATE change set succeeds instead of being refused InvalidChangeSetStatus, and the plan is discarded

> _Note: this issue was identified against the code base at commit `2f896de1ccf99b872a06872b90b77c54f78fc307`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
DeleteChangeSet

## Description
One net-new cause, grounded in the behavioral check cloudformation.changeset-delete-invalid-status-rejected (GROUP error-semantics, axis:rejection).

Cause 1 of 1: DeleteChangeSet on an UPDATE change set whose execution has CONCLUDED (ExecutionStatus EXECUTE_COMPLETE, ChangeSetStatus CREATE_COMPLETE, stack UPDATE_COMPLETE) is ACCEPTED by the emulator, where AWS refuses it.

AWS: Smithy (services/service-com-amazonaws-cloudformation-cloudformation/smithy-model/com-amazonaws-cloudformation-cloudformation.json): DeleteChangeSet takes ChangeSetName (ChangeSetNameOrId, @required, @length 1..1600) plus optional StackName, returns an empty DeleteChangeSetOutput, and models exactly ONE error — InvalidChangeSetStatusException, httpError 400, awsQueryError code `InvalidChangeSetStatus`, doc "The specified change set can't be used to update the stack. For example, the change set status might be CREATE_IN_PROGRESS, or the stack status might be UPDATE_IN_PROGRESS." The model does not itself enumerate which ExecutionStatus values are deletable, so for the scope of the refusal this is recorded behavior only: the check records real AWS refusing the delete of a change set whose EXECUTION HAS STARTED — both while it is EXECUTE_IN_PROGRESS and again once it is EXECUTE_COMPLETE — with HTTP 400, wire error code `InvalidChangeSetStatus` (no "Exception" suffix on the wire; that suffix is only the modelled/botocore class name) and message `Cannot delete ChangeSet in execution status <ExecutionStatus>`. Fixed text of the message: `Cannot delete ChangeSet in execution status `; its only variable part is the change set's current ExecutionStatus taken from the emulator's own state — `EXECUTE_IN_PROGRESS` during execution, `EXECUTE_COMPLETE` after it. The refusal is also non-destructive: after it, DescribeChangeSet for the same ARN must still resolve the change set and return the same ChangeSetId. The check pins the positive control too: a never-executed CREATE_COMPLETE/AVAILABLE change set on the SAME stack deletes cleanly (200, empty body) and then reads back as 404 ChangeSetNotFound with message `ChangeSet [<identifier exactly as passed>] does not exist`, so the refusal must be specific to an executed change set, not DeleteChangeSet being broken for the stack.

Emulator: the first half of the check passes — DeleteChangeSet during EXECUTE_IN_PROGRESS is correctly refused 400 InvalidChangeSetStatus with `Cannot delete ChangeSet in execution status EXECUTE_IN_PROGRESS`. After the WaitCondition is signalled and the change set reaches EXECUTE_COMPLETE (stack UPDATE_COMPLETE), the SAME DeleteChangeSet call RETURNS 200 with an empty DeleteChangeSetOutput and no error at all; the check fails with `AssertionError: expected DeleteChangeSet of an executed change set to be rejected, but the call succeeded`. The handler's gate is `if !change_set.record_is_discardable()` (services/service-com-amazonaws-cloudformation-cloudformation/src/ops/delete_change_set.rs), and its own module doc states the intent explicitly: "one whose execution has already begun has no plan left to take away — the delete is accepted". So every terminal execution state (EXECUTE_COMPLETE, EXECUTE_FAILED, OBSOLETE) falls through the gate, the record is marked `discarded` and dropped from the stack's change-set reads, and `crate::state::cannot_delete_change_set` is never reached for an executed change set.

Why: a client cannot distinguish a plan AWS still holds from one it has retired. Tooling that deletes a spent change set and treats a 200 as "the plan is gone" gets the opposite answer from AWS (400 InvalidChangeSetStatus, plan retained and still describable), so idempotency/cleanup logic written against AWS either reports success where AWS reports a client error or, run against the emulator, silently discards a record AWS keeps — the deployed plan's identity and the name it deployed under stop being readable, and a caller that correctly handles the modelled InvalidChangeSetStatus error class never exercises that branch here.

NOTE — this cause is in direct tension with a cluster of open wire issues and with one RESOLVED issue, and a fixer must reconcile them rather than flip the gate wholesale: 20261109T073558Z-cloudformation-4-net-new-behavioral-causes-deletechangeset-accepts.md (status fixed) asked for exactly the behavior this check now sees as a defect, and 20261120T150300Z-cloudformation-deletechangeset-refuses-an-executed-change-set-so.md plus 20261120T150929Z-cloudformation-s3-deletechangeset-refuses-a-change-set-in.md, 20261120T150929Z-cloudformation-iam-lambda-s3-deletechangeset-refuses-the-change.md, 20261120T162942Z-cloudformation-lambda-deletechangeset-refuses-an-executed-change-set.md, 20261120T214334Z-cloudformation-sns-sqs-deletechangeset-refuses-a-change-set.md, 20261120T214510Z-cloudformation-sqs-ssm-deletechangeset-refuses-the-change-set.md, 20261120T214510Z-cloudformation-ssm-deletechangeset-refuses-a-change-set-in.md and 20261121T003214Z-cloudformation-deletechangeset-refuses-an-executed-change-set-so-b908f3.md all require the delete of an executed change set to SUCCEED. None of them covers this check (the report marks it neither OWNED nor ALREADY FILED). The discriminator visible in the evidence is the change set's TYPE and the stack path: the recordings those issues cite are CREATE-type change sets that brought a stack up from REVIEW_IN_PROGRESS, while this check's change set is `ChangeSetType="UPDATE"` on an already CREATE_COMPLETE stack. The gate therefore has to be keyed on more than "execution began" — it must refuse the executed UPDATE change set with the message above while still accepting the executed CREATE-type one those issues record as 200.

Fix: the status gate in the DeleteChangeSet handler and the discardability predicate it calls on the stored change set (services/service-com-amazonaws-cloudformation-cloudformation/src/ops/delete_change_set.rs; crate::state::StoredChangeSet::record_is_discardable / crate::state::cannot_delete_change_set), plus whatever the change-set store records about a change set's type so the two paths can be told apart. The refused path must keep writing nothing: no `discarded` flag, no removal from `store.change_sets`, so DescribeChangeSet afterwards still answers 200 with the same ChangeSetId.

Traces: behavioral check cloudformation.changeset-delete-invalid-status-rejected.
