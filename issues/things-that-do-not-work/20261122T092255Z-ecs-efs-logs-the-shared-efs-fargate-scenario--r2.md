# ecs__efs__logs: the shared-EFS Fargate scenario is again killed at its replay budget with no verdict — a poll loop over RunTask/DescribeTasks/awslogs delivery never converges

> _Note: this issue was identified against the code base at commit `c1fd53e63fe8f6cea373c6ef4b146b196d6d51b7`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
RunTask

## Description
One net-new root cause, keyed on a symptom no open issue carries. This failing check is NOT marked ALREADY FILED and is NOT marked OWNED by any open issue in this replay, so it is filed here. Related issues are named for a fixer's benefit but none of them covers this failure: the only OPEN issue for this check, 20261116T030849Z-ecs-efs-logs-a-stopped-fargate-task-s.md, is keyed on a `KeyError: 'exitCode'` raised at `assert _container(a_task)["exitCode"] == 0` — i.e. on the check getting far enough to read a STOPPED task's container record. In this replay the check never gets that far at all: it is killed at its 60.0s budget with no assertion reached, so the emulator never produced any verdict. Two earlier issues keyed on exactly this budget-kill shape are already marked FIXED (20261104T054216Z-ecs-efs-logs-the-shared-efs-fargate-scenario.md and 20261111T030649Z-ecs-efs-logs-an-efs-volume-shared-by.md); the check is once more non-terminating, so whatever those fixes changed, the scenario still does not converge. This is not reported as a REOPENS because the check fails on non-termination, not on a refusal: no operation answered with an error code or a non-2xx.

Cause 1 of 1: the ECS+EFS Fargate scenario never reaches an observable end state, so every bounded poll in the check spins until the replay budget expires.

AWS: the check only ever waits on states AWS reaches on its own, and the ECS/EFS models state that each of them is reported. Smithy (ECS `com.amazonaws.ecs#Task`): `Task$lastStatus` — "The last known status for the task" — reaches `STOPPED` for a run-to-completion task whose essential container's process ended; `Task$stopCode` (`TaskStopCode`) then carries the stop code and `Task$stoppedAt`/`Task$startedAt` the transition timestamps; `Task$attachments` carries the awsvpc ENI (`networkInterfaceId`) for a `networkMode=awsvpc` task. Smithy `com.amazonaws.ecs#Container`: `lastStatus` and `exitCode` (`BoxedInteger`, "The exit code returned from the container") are reported for a container that ran. Smithy `com.amazonaws.ecs#MountPoint$readOnly` (`BoxedBoolean`): "If this value is `true`, the container has read-only access to the volume. If this value is `false`, then the container can write to the volume." With an `awslogs` logConfiguration, the container's stdout lines are delivered as CloudWatch Logs events into `<awslogs-stream-prefix>/<containerName>/<taskId>` in the configured group and are readable with GetLogEvents; EFS reports the file system, mount target and access point reaching `LifeCycleState` `available` and later meters `DescribeFileSystems -> FileSystems[0].SizeInBytes.Value > 0` for a file system with bytes written to it. Each of those is a state AWS converges to within the check's own generous per-stage deadlines (task 900s, mount target 600s, awslogs 420s, metering 600s), so a real run reaches a pass/fail verdict.

Emulator: no verdict is produced at all. The replay reports only `Error: Check timed out after 60.0s` for `ecs__efs__logs.ecs-efs-volume-shared-across-two-fargate-tasks-and-readonly-mount-write-denied`, with no traceback and no assertion text, i.e. the process was killed inside one of the `_poll_until` loops rather than failing a comparison. Exactly which loop is the first not to converge is not attributable from the replay output — the suite surfaces no partial progress for a budget kill — so this issue states the behavior that IS observable: a scenario built entirely out of states AWS reaches by itself never reaches any of them to the point where the check can assert, and the check is terminated. The previous replay of this same check reached `assert _container(a_task)["exitCode"] == 0` (per the open issue above), so the emulator has regressed to not even getting the first task's output observable inside the budget.

Why: a client cannot distinguish "not yet" from "never" against this emulator. Every ECS client is a poller: it calls RunTask and then DescribeTasks until `lastStatus` is `STOPPED` (and then reads `stopCode`/`containers[0].exitCode`), and every awslogs consumer polls GetLogEvents until the expected output arrives. If those conditions are never reached, the client has no terminal state to act on: CI jobs, batch drivers, `aws ecs wait tasks-stopped`, CDK/Step Functions `.sync` integrations and ECS-backed test harnesses all hang until their own timeout and then report an infrastructure failure, never the task's result. Nothing about the task's actual outcome — did the shared EFS write land, was the read-only mount's write refused — is observable, so the entire ECS+EFS data-plane contract is unusable rather than merely wrong.

Fix: the ECS task data plane behind RunTask/DescribeTasks and its container runtime — the task lifecycle that must drive a placed Fargate task through PENDING -> RUNNING -> STOPPED and attribute `stopCode`, `stoppedAt`/`startedAt`, the awsvpc attachment and the container's `lastStatus`/`exitCode` (ECS crate `src/state/container_runtime.rs`, `src/state/state.rs` `TaskRecord` lifecycle, `src/state/container_shell.rs`, serialised by `src/ops/describe_tasks.rs`), together with the awslogs delivery path that must land the container's stdout as events in the configured log group/stream, and the EFS side that must mount an `efsVolumeConfiguration` volume (honouring `MountPoint$readOnly`) and meter `SizeInBytes`. The requirement is convergence: a task the emulator accepts from RunTask must reach a terminal, fully attributed state, and a container the emulator starts must have its output delivered — a scenario that stalls forever is the defect, independent of the values involved.

Traces: ecs__efs__logs.ecs-efs-volume-shared-across-two-fargate-tasks-and-readonly-mount-write-denied.

## Evidence
Cause 1 — Expected (real AWS): the check runs to a verdict. Concretely, every poll it issues converges: EFS `DescribeFileSystems`/`DescribeMountTargets`/`DescribeAccessPoints` report `LifeCycleState == "available"`; `DescribeTasks(cluster, tasks=[taskArn])` reports `tasks[0]["lastStatus"] == "STOPPED"` with `stopCode != "TaskFailedToStart"`, `startedAt`/`stoppedAt` set, an `attachments` entry carrying `networkInterfaceId`, and `containers[0]` carrying `lastStatus` plus `exitCode` (Smithy `Container$exitCode`, BoxedInteger — "The exit code returned from the container"); `GetLogEvents(logGroupName=<group>, logStreamName="<prefix>/app/<taskId>", startFromHead=True)` returns the container's stdout lines including the arm's sentinel (`A-DONE`, `B-DONE`, `C-DONE`, `D-DONE`); and `DescribeFileSystems(FileSystemId=<fs>)["FileSystems"][0]["SizeInBytes"]["Value"] > 0` after bytes were written. The check then either passes or fails a named assertion.

Actual (emulator): no assertion is ever reached. The replay reports, for this check, exactly:

    #### [mismatch] ecs__efs__logs.ecs-efs-volume-shared-across-two-fargate-tasks-and-readonly-mount-write-denied

There is no traceback and no assertion message — the diagnosis is the absence of one: the process was killed inside a `_poll_until` loop (the check's helper raises `AssertionError(f"{description} not met within {timeout_s}s. Last result: {last!r}")` only when its own per-stage deadline is hit, and none of those messages appears), so the emulator never produced the state any stage waits for within the replay budget. The check's own per-stage deadlines are far larger than the budget (`_TASK_TIMEOUT_S = 900`, `_MT_TIMEOUT_S = 600`, `_LOG_TIMEOUT_S = 420`, `_METER_TIMEOUT_S = 600`), which is why the budget, not a stage deadline, is what ends the run.

Status/error code/message: none to quote — no operation in this scenario answered with an error code or a non-2xx status. The divergence is the absence of any terminal response, not a wrong one.

Regression context (not part of the requirement, offered so a fixer can bisect): the open issue 20261116T030849Z-ecs-efs-logs-a-stopped-fargate-task-s.md records this same check previously progressing past awslogs delivery of `A-DONE` and failing at `assert _container(a_task)["exitCode"] == 0` with `KeyError: 'exitCode'`. ## Steps to Reproduce
1. Create an EFS file system (`CreateFileSystem`, Encrypted=True, PerformanceMode=generalPurpose, ThroughputMode=bursting) and poll `DescribeFileSystems` until `LifeCycleState == "available"`.
2. `CreateMountTarget` in the Fargate task's subnet with the task's security group; poll `DescribeMountTargets` until `LifeCycleState == "available"`.
3. `CreateAccessPoint` with `PosixUser={Uid:1000,Gid:1000}` and `RootDirectory={Path:"/data", CreationInfo:{OwnerUid:1000,OwnerGid:1000,Permissions:"0755"}}`; poll `DescribeAccessPoints` until `LifeCycleState == "available"`.
4. `CreateLogGroup` for the container's awslogs destination. Create the ECS cluster and ensure the ECS service-linked role exists.
5. `RegisterTaskDefinition` twice (identical except `mountPoints[0].readOnly`): `networkMode=awsvpc`, `requiresCompatibilities=[FARGATE]`, `cpu=256`, `memory=512`, an execution role and a task role, `volumes=[{name:"shared", efsVolumeConfiguration:{fileSystemId:<fs>, transitEncryption:"ENABLED", authorizationConfig:{accessPointId:<ap>, iam:"ENABLED"}}}]`, one essential busybox container named `app` with `mountPoints=[{sourceVolume:"shared", containerPath:"/mnt/shared", readOnly:<false|true>}]` and `logConfiguration={logDriver:"awslogs", options:{awslogs-group:<group>, awslogs-region:<region>, awslogs-stream-prefix:"efs"}}`.
6. `RunTask` (launchType=FARGATE, count=1, awsvpc networkConfiguration) on the read-write definition with the container override `command=["sh","-c",'set -e; echo "$MARKER" > /mnt/shared/payload; sync; echo "A-SIZE=$(wc -c < /mnt/shared/payload)"; echo "A-MODE=$(ls -l /mnt/shared/payload | cut -c1-10)"; echo A-DONE']` and `environment=[{name:"MARKER", value:<any>}]`.
7. Poll `DescribeTasks(cluster=<cluster>, tasks=[<taskArn>])` until `tasks[0]["lastStatus"] == "STOPPED"`, then poll `GetLogEvents(logGroupName=<group>, logStreamName="efs/app/<taskId>", startFromHead=True)` until a message containing `A-DONE` is returned.
   Observed: the run never reaches an assertion — the whole scenario is killed at the replay budget (`Check timed out after 60.0s`) while still polling; no terminal task/container state and no delivered container output ever appear.
   Expected: the task reaches `STOPPED` with `stopCode != "TaskFailedToStart"` and `containers[0].exitCode` present, and the container's `A-DONE` line is readable from the awslogs stream, so the check proceeds to its shared-read (arm B), read-only-refusal (arm C, `Read-only file system`) and no-trace (arm D) assertions and reaches a verdict.
