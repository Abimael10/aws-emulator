# dms__ec2__iam__s3: the S3-to-S3 replication lifecycle never settles, so the StopReplicationTask refusals and the reload-target restart are never reached (check cut at the 60 s cap)

> _Note: this issue was identified against the code base at commit `2c036246c52324f8f473f1b5e9b5314460be2843`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
StopReplicationTask

## Description
Cause 1 of 1: the DMS replication lifecycle this check walks does not converge, so the check reaches no graded assertion and is cut off at the harness's 60 s per-check cap. Every state it polls — the replication instance reaching ReplicationInstanceStatus 'available', the replication task reaching Status 'ready', and the started full load reaching Status 'stopped' — is read with a describe-first/sleep-after loop (20 s, then 10 s, then 10 s intervals), so an emulator that settles these states promptly finishes the whole body in seconds. Burning the full cap means the emulator keeps serving non-terminal states (or does not answer) where the lifecycle must settle, and none of the behaviors below is ever exercised.

AWS:      Smithy (dms) StopReplicationTask takes ReplicationTaskArn (required) and models InvalidResourceStateFault and ResourceNotFoundFault (both client errors, HTTP 400); StartReplicationTask takes ReplicationTaskArn and StartReplicationTaskType and models AccessDeniedFault, InvalidResourceStateFault and ResourceNotFoundFault. The behaviors this check grades are recorded behavior only: (a) CreateReplicationInstance is followed by DescribeReplicationInstances reporting 'available' within the service's own provisioning window, and CreateReplicationTask by DescribeReplicationTasks reporting 'ready'; (b) StopReplicationTask on a task that is not running — both a 'ready' task that was never started and a task that has already finished and is 'stopped' — is refused identically with HTTP 400, error code InvalidResourceStateFault and the message whose fixed text is `Replication Task: <arn> is currently not running.`, where <arn> is the ReplicationTaskArn from the request; (c) a started full-load task settles 'stopped' with StopReason the fixed text `Stop Reason FULL_LOAD_ONLY_FINISHED` and ReplicationTaskStats TablesLoaded 1 / TablesErrored 0, writing exactly one object under the target table prefix; (d) StartReplicationTask with StartReplicationTaskType 'reload-target' re-runs the full load, giving a FullLoadStartDate later than the first run's and rewriting that same single object with the source rows.
Emulator: the check completes no step within the cap — 'Error: Check timed out after 60.0s', with no assertion reached and no refusal observed. Because the poll loops only sleep when the state they read is not yet terminal, the emulator is serving 'creating'/non-'ready'/non-'stopped' states (or not answering) long enough to consume the whole budget; which of the three stages stalls is not distinguished by the output. Hypothesis: replication instances and/or replication tasks are created in a non-terminal state and never advanced, as the emulator's asynchronous DMS state is not driven forward.
Why:      a client that waits for a replication instance to become 'available' or a task to become 'ready' before using it hangs forever; nothing that depends on a DMS migration completing (the full-load output objects, the stats, the terminal StopReason) can be observed, and the InvalidResourceStateFault boundary that tells a caller its stop/start request was against the wrong task state is unreachable.
Fix:      the DMS replication-instance and replication-task lifecycle state (the create/describe handlers' state advancement for CreateReplicationInstance/DescribeReplicationInstances and CreateReplicationTask/StartReplicationTask/DescribeReplicationTasks), and then the StopReplicationTask handler's not-running refusal.
Note:     the open issue 20261117T133104Z-dms-task-reporting-omits-resolved-settings-and-per.md records neighbouring DMS task-reporting gaps (resolved settings and per-table load counters) under the 'dms' service; it does not carry this check's replay key and does not cover the lifecycle stall reported here.
Traces:   dms__ec2__iam__s3.stop-replication-task-rejected-for-a-ready-or-stopped-task.

## Evidence
Check dms__ec2__iam__s3.stop-replication-task-rejected-for-a-ready-or-stopped-task [mismatch]. Detail: 'Error: Check timed out after 60.0s' — no assertion in the check body was reached.

The check's own waits are describe-first loops (replication instance -> 'available', poll 20 s; replication task -> 'ready', poll 10 s; started task -> 'stopped', poll 10 s) plus instant setup calls (S3 buckets, IAM role, VPC/subnets/gateway endpoint, DMS subnet group, endpoints, task). With states that settle promptly the body finishes in a few seconds, so exhausting the 60 s cap is evidence that the polled DMS states do not settle.

Expected (AWS), none of which was observed:
- DescribeReplicationInstances -> ReplicationInstanceStatus 'available'; DescribeReplicationTasks -> Status 'ready'.
- StopReplicationTask on the 'ready' task -> HTTP 400, code 'InvalidResourceStateFault', message `Replication Task: <ReplicationTaskArn> is currently not running.` (fixed text as shown; the ARN is the request's own).
- After StartReplicationTask 'start-replication': Status 'stopped', StopReason `Stop Reason FULL_LOAD_ONLY_FINISHED`, ReplicationTaskStats TablesLoaded=1 / TablesErrored=0, exactly one object under the target table prefix.
- StopReplicationTask on that stopped task -> the identical InvalidResourceStateFault refusal.
- StartReplicationTask 'reload-target' -> a FullLoadStartDate later than the first run's, the same single object rewritten with the source rows.

## Steps to Reproduce
1. Create source and target S3 buckets, put a CSV at srcdata/hr/employee/LOAD001.csv, and create an IAM role trusting dms.amazonaws.com with read/write on both buckets (plus the fixed-name dms-vpc-role).
2. Create a VPC with two subnets in different AZs and an S3 gateway endpoint; CreateReplicationSubnetGroup over the two subnets.
3. CreateReplicationInstance (dms.c5.large, 5 GB, MultiAZ false) and poll DescribeReplicationInstances for ReplicationInstanceStatus 'available' — it does not settle.
4. CreateEndpoint source (EngineName s3, ExternalTableDefinition for hr.employee) and target (EngineName s3), then CreateReplicationTask MigrationType 'full-load' and poll DescribeReplicationTasks for Status 'ready'.
5. StopReplicationTask on the ready task -> expect 400 InvalidResourceStateFault `Replication Task: <arn> is currently not running.`; StartReplicationTask 'start-replication', wait for 'stopped' with StopReason `Stop Reason FULL_LOAD_ONLY_FINISHED`; stop it again for the identical refusal; then StartReplicationTask 'reload-target' and verify the single output object is rewritten. None of these steps is reached: the check is cut at the 60 s cap while polling the lifecycle.
