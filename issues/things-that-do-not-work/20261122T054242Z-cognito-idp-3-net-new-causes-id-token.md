# cognito-idp: 3 net-new causes — ID-token iss is the bare emulator endpoint, a non-numeric custom Number attribute is refused with a regex-constraint message, and AdminResetUserPassword refuses a verified-phone recovery

> _Note: this issue was identified against the code base at commit `fceda236fd74c050af49bdc92c31da84e151e4fd`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
AdminUpdateUserAttributes

## Description
Three net-new root causes in the cognito-idp token-issuance, attribute-validation and password-reset planes. All three are grounded in failing behavioral checks of this suite that no open issue carries the replay key for.

Cause 1 of 3: the iss claim of every token this service issues is the bare emulator listener address, not a cognito-idp.<region> issuer.
AWS: recorded behavior only (the JWT body is not Smithy-modelled). A Cognito user pool issues its ID/access tokens with iss = https://cognito-idp.<region>.<domain>/<userPoolId>. The requirement is the FORM: scheme https; a host whose first two labels are the literal 'cognito-idp' and the pool's region, followed by at least one further non-empty domain label; a path of exactly one segment equal to the pool id; no query and no fragment. The <domain> suffix, host and port are environment values and are not part of the requirement; the 'cognito-idp.<region>' prefix and the /<userPoolId> path are.
Emulator: iss is the endpoint the pool was created through, with the pool id as the path — e.g. 'https://127.0.0.1:<port>/us-west-2_<suffix>' — so the host carries no cognito-idp.<region> labels at all. The same value is served by the pool's OpenID discovery document (issuer) and is what the refreshed token repeats.
Why: every OIDC/JWT verifier performs the issuer check and derives the JWKS URI from iss, and multi-provider code tells identity providers apart by it. A client configured against AWS's documented issuer rejects every token the emulator mints, and two different providers served on one host become indistinguishable.
Fix: the cognito-idp per-pool issuer computation shared by the token-minting path and the OpenID discovery/JWKS documents (the stored issuer URL and its serializer); services/service-com-amazonaws-cognitoidentityprovider-awscognitoidentityproviderservice/src/state/user_pool.rs stores issuer_endpoint as the dialled host[:port] (see the field doc at UserPool::issuer_endpoint) and src/state/openid_discovery.rs publishes it. NOTE: Cause 1 of the OPEN issue 20261111T061507Z-cognito-idp-3-net-new-causes-the-id.md (and Cause 2 of 20261109T124858Z-cognito-idp-5-net-new-causes-tokens-are.md) describes this same defect, but neither carries the replay keys of the three checks below — they now fail at the _assert_issuer step of a different check each — so this cause is filed with those keys and should be folded into that work if it is still open.
Traces: cognito-idp.id-token-from-another-pool-rejected-by-this-pools-jwks, cognito-idp.openid-discovery-jwks-uri-serves-unique-unpadded-rs256-signing-keys, cognito-idp.refreshed-id-token-verifies-under-the-same-jwks-and-keeps-the-session-claims.

Cause 2 of 3: a value that is not a number at all, written to a custom Number attribute, is refused with the generic parameter-validation regex message instead of Cognito's attribute-constraint message.
AWS: Smithy: AdminUpdateUserAttributes declares InvalidParameterException (httpError 400). For a custom attribute declared AttributeDataType=Number, Cognito refuses an unparseable value with HTTP 400 InvalidParameterException and message 'user.custom:<name>: Unable to parse the number\n' — fixed text 'user.' + the attribute name as the request spelled it (including the 'custom:' prefix) + ': Unable to parse the number' and a trailing newline; the attribute name is the only variable part. The same message family carries the bound refusals the emulator already gets right ('user.custom:<name>: String must be no shorter than <MinLength> characters\n', 'user.custom:<name>: Number must be greater than <MinValue>\n').
Emulator: the call is refused InvalidParameterException with the generic framework validation message "1 validation error detected: Value at 'Custom.User.<name>' failed to satisfy constraint: Member must satisfy regular expression pattern: $|^[+-]?((\\p{Nd}+(\\.\\p{Nd}*)?)|(\\.\\p{Nd}+))([eE][+-]?\\p{Nd}+)?" — a different message, a different wording convention and a different member path ('Custom.User.<name>' instead of 'user.custom:<name>').
Why: clients and test suites branch on this message to tell 'the value is out of the declared range' from 'the value is not a number', and surface it to end users; the emulator's text leaks a regex and a member path AWS never emits, so message-matching client code and UI copy break while the three sibling refusals of the same operation are worded correctly.
Fix: the cognito-idp custom-attribute value validation reached by AdminUpdateUserAttributes (and the other attribute-write paths) — the number-parse branch in the pool-schema attribute validation (src/state/attributes.rs), which must produce the 'Unable to parse the number' sentence rather than letting the generic @pattern validator of the Number attribute refuse the request first.
Traces: cognito-idp.admin-update-custom-attribute-lower-bounds-rejected.

Cause 3 of 3: AdminResetUserPassword refuses a CONFIRMED user who holds a verified phone number in a pool whose AccountRecoverySetting is verified_phone_number.
AWS: Smithy: AdminResetUserPassword declares InvalidParameterException (400) and succeeds with an empty output (HTTP 200) when self-service recovery is configured; its doc states 'your user pool must have self-service account recovery configured' and RecoveryOptionType documents that a verified phone number is a recovery destination reached by SMS. Recorded behavior: for a pool whose AccountRecoverySetting is [{Priority:1,Name:'verified_phone_number'}] and a CONFIRMED user whose phone_number is set and phone_number_verified is true, the call SUCCEEDS and moves the user to RESET_REQUIRED.
Emulator: the same call is refused HTTP 400 InvalidParameterException (the NO_RECOVERY_DESTINATION_MESSAGE branch), so the operation's positive control never passes and nothing downstream of a reset can be exercised. Hypothesis: UserPool::recovery_destination (src/state/user_pool.rs, the delivers_sms()/SMS_RECOVERED_ATTRIBUTE filter) drops the verified_phone_number mechanism and returns RecoveryDestination::None — either because the user's verified phone is not accepted as a destination unless phone_number is auto-verified, or because the pool's SmsConfiguration no longer satisfies delivers_sms() after an UpdateUserPool call that did not restate it.
Why: a client whose pool recovers accounts over SMS can never start an administrative password reset; every reset-code flow (ConfirmForgotPassword, the RESET_REQUIRED sign-in challenge) is unreachable, and the refusal reports a bad parameter for a request whose parameters are valid.
Fix: UserPool::recovery_destination in services/service-com-amazonaws-cognitoidentityprovider-awscognitoidentityproviderservice/src/state/user_pool.rs and its caller AdminResetUserPassword::begin_reset in src/ops/admin_reset_user_password.rs (the RecoveryDestination::None arm).
Traces: cognito-idp.invalid-lambda-response-error.

(The host/port values themselves are per-environment; the missing cognito-idp.<region> labels are the defect.)

Cause 2 — AssertionError: "AdminUpdateUserAttributes custom:score='abc' answered {'Message': \"1 validation error detected: Value at 'Custom.User.score' failed to satisfy constraint: Member must satisfy regular expression pattern: $|^[+-]?((\\p{Nd}+(\\.\\p{Nd}*)?)|(\\.\\p{Nd}+))([eE][+-]?\\p{Nd}+)?\", 'Code': 'InvalidParameterException'}". Expected: ('InvalidParameterException', 'user.custom:score: Unable to parse the number\n'). The two preceding cases in the same check — custom:tier='a' under MinLength=2 and custom:score='0' under MinValue=1 — were refused with the correct AWS wording, so only the unparseable-number branch diverges.

Cause 3 — AssertionError: "AdminResetUserPassword (no trigger) positive control: expected success, got InvalidParameterException". Expected: HTTP 200, empty body. Actual: HTTP 400 InvalidParameterException.
