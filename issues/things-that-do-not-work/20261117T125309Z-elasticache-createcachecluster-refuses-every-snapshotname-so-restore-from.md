# ElastiCache: CreateCacheCluster refuses EVERY SnapshotName so restore-from-snapshot is impossible, and the RBAC user-group revocation flow still never converges (2 causes, 3 checks)

> _Note: this issue was identified against the code base at commit `b9fa193222dbbf8f6227ac7f16352f3415fbd68d`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
CreateCacheCluster

## Description
Two net-new root causes, grounded in the three failing elasticache checks of this replay that the report binds to no open issue and does not mark ALREADY FILED. Both snapshot-restore checks previously failed in the data plane and are listed in the Issue-Trace-Ids of the open issue 20261111T005655Z-elasticache-data-plane-still-unreachable-and-multi-wait.md, but that issue keys them to `_redis_cmd#16` / `_redis_cmd_with_retry#15` frames; in this replay neither check reaches the data plane at all — both now die earlier, on a control-plane REFUSAL from CreateCacheCluster — so neither key matches and the report lists both unowned. The revocation flow was claimed fixed by 20261112T074018Z-elasticache-lifecycle-flows-never-converge-inside-a-client (status fixed, Cause 2 of 2) and still does not converge in this replay; it is reported again below so the path is not closed unrun.

Cause 1 of 2 — CreateCacheCluster refuses ANY request that carries SnapshotName, so a cache cluster can never be seeded from a snapshot the emulator itself holds. Failing checks: elasticache.e2e-cluster-snapshot-restore-data-consistency, elasticache.e2e-cluster-snapshot-restore-data-persists.
AWS: Smithy (services/service-com-amazonaws-elasticache-amazonelasticachev9/smithy-model/com-amazonaws-elasticache-amazonelasticachev9.json) — CreateCacheClusterMessage$SnapshotName (String, optional) is documented "The name of a Valkey or Redis OSS snapshot from which to restore data into the new node group (shard). The snapshot status changes to `restoring` while the new node group (shard) is being created", valid when Engine is redis. CreateCacheCluster returns CacheCluster and models InvalidParameterValueException (awsQueryError code InvalidParameterValue, 400) among its errors — that refusal is for a SnapshotName that names NO snapshot, not for the parameter being present. Recorded behavior: after CreateSnapshot(CacheClusterId=<src>, SnapshotName=<snap>) and DescribeSnapshots(SnapshotName=<snap>) reporting SnapshotStatus 'available', CreateCacheCluster(CacheClusterId=<new>, SnapshotName=<snap>, CacheNodeType=..., CacheSubnetGroupName=..., SecurityGroupIds=[...]) is ACCEPTED with 200, returns a CacheCluster in a transient status that settles to 'available', and the restored cluster serves the keys captured in the snapshot byte-identically. Snapshot names, cluster ids and payloads are per-run values; the requirement is that an existing, available snapshot is a valid restore source.
Emulator: the handler refuses unconditionally, before any lookup, with HTTP 400, error code InvalidParameterValue and the message `Invalid value <SnapshotName> for SnapshotName: no such snapshot exists.` — observed as `botocore.errorfactory.InvalidParameterValueException: An error occurred (InvalidParameterValue) when calling the CreateCacheCluster operation: Invalid value <snapshot name> for SnapshotName: no such snapshot exists.` in both checks, where the only variable part is the snapshot name taken from the request and the fixed text `Invalid value ` / ` for SnapshotName: no such snapshot exists.` is the emulator's own prose. The refusal is reached even though the same emulator's CreateSnapshot accepted the snapshot and its DescribeSnapshots reported it 'available' seconds earlier: the check's `_wait_snapshot_available` returned before the CreateCacheCluster call was made. The handler's own comment states the obsolete premise for the blanket refusal — "A cluster can only be seeded from a snapshot that exists, and none can: `CreateSnapshot` / `CopySnapshot` are scaffolded 501s" — which is no longer true (the CreateSnapshot and CopySnapshot stub issues are both resolved).
Why: a client that backs a cache up and restores it cannot do so at all: the restore call is rejected with a message asserting the snapshot does not exist, which is false in the emulator's own state. A client cannot distinguish "I named the wrong snapshot" from "this service never restores", snapshot/restore disaster-recovery procedures validated against the emulator prove nothing, and no snapshot-restore data-persistence behaviour downstream of the create is observable.
Fix: the CreateCacheCluster handler's restore-source validation (services/service-com-amazonaws-elasticache-amazonelasticachev9/src/ops/create_cache_cluster.rs, the `input.snapshot_name` block at lines 450-463) — resolve the named snapshot in the service state, refuse with InvalidParameterValue only when no snapshot of that name exists, and otherwise seed the new cluster from it and let its status settle to available (with the restored node data carried by the cluster's data-plane state).
Traces: elasticache.e2e-cluster-snapshot-restore-data-consistency, elasticache.e2e-cluster-snapshot-restore-data-persists.

Cause 2 of 2 — the RBAC user-group revocation flow still never converges: the check is killed by the 60 s per-check budget inside a status poll with no assertion ever evaluated. Failing check: elasticache.e2e-user-group-access-revocation-flow.
AWS: Smithy — ModifyUserGroup takes UserIdsToAdd / UserIdsToRemove and returns UserGroup{UserGroupId, Status, UserIds, PendingChanges, ReplicationGroups}, modeling DefaultUserRequired (400), InvalidUserGroupStateFault (400 InvalidUserGroupState), UserGroupNotFoundFault (404 UserGroupNotFound) and UserNotFoundFault (404 UserNotFound); ReplicationGroup$Status is documented "creating, available, modifying, deleting, create-failed, snapshotting"; Endpoint$Address is "The DNS hostname of the cache node" and Endpoint$Port "The port number that the cache engine is listening on". Recorded behavior: ModifyUserGroup(UserIdsToRemove=[u]) moves the group to 'modifying' and back to 'active' without u in UserIds while the attached replication group returns to 'available'; a RESP session to NodeGroups[0].PrimaryEndpoint.{Address,Port} from inside the group's VPC then refuses that user's previously accepted AUTH with a reply whose fixed prefix is `-WRONGPASS` (or `-NOAUTH`), and after ModifyUserGroup(UserIdsToAdd=[u]) settles the identical AUTH is accepted again with `+OK`. The user id, group id, password and endpoint host/port are per-run values.
Emulator: the check ends with exactly `Error: Check timed out after 60.0s` — no traceback, no assertion text — so none of the three AUTH observations (positive control, refusal after removal, restore after re-add) was ever evaluated. The flow chains six status waits (replication group available after create at interval 20 s, available AND the group attached after ModifyReplicationGroup at 20 s, then group-active / replication-group-available pairs at 15 s after each ModifyUserGroup) plus three in-VPC RESP sessions. Mechanism in this checkout: services/service-com-amazonaws-elasticache-amazonelasticachev9/src/state.rs:428 `pub const CLUSTER_TRANSITION: Duration = Duration::from_millis(500);` (and :438 SNAPSHOT_TRANSITION) with the doc comment at :416-427 — "it is deliberately NOT zero ... The due instant is stored on the record and materialised by whichever later call reads it; a REPORT issued inside the span answers with the transient status, because nothing of this service sleeps for a transition it has scheduled" — so a client's first poll after each create/modify always observes the transient status and then sleeps its whole interval even though the emulator settled in half a second; six such waits exceed the 60 s budget on their own. Hypothesis: the three RESP sessions add the remainder, because the advertised PrimaryEndpoint accepts no TCP from inside the VPC (the sibling data-plane checks of this replay, owned by 20261111T005655Z-elasticache-data-plane-still-unreachable-and-multi-wait.md, report the emulator's own 'a Lambda function in this emulator has no host network to reach' on that connect) and the probe retries a failed connect for its whole window; the two contributions cannot be separated here because no assertion fired.
Why: RBAC is the only mechanism by which an ElastiCache client scopes access to a replication group. Against this emulator a client cannot confirm that removing a user from the attached user group actually stopped that user authenticating, nor that re-adding it restored access; a timed-out run is indistinguishable from a group that never settles and from an engine that authenticates everyone, and every wait costs a client written against AWS its full poll interval.
Fix: two components — (a) the status-settling path of the elasticache crate's state (services/service-com-amazonaws-elasticache-amazonelasticachev9/src/state.rs around CLUSTER_TRANSITION at :428), so a record whose transition instant has passed reads back SETTLED to the FIRST call that observes it while the create/modify RESPONSE keeps reporting the transient status other checks assert; and (b) the replication-group data plane, so the emulator serves RESP on the Address:Port its NodeGroups[].PrimaryEndpoint projection publishes and enforces the attached user group's membership there.
Traces: elasticache.e2e-user-group-access-revocation-flow.
