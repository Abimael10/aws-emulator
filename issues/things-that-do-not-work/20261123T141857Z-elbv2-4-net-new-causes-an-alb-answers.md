# elbv2: 4 net-new causes — an ALB answers 502 for registered instance targets, DNSName is published as a "host:port" authority, SetSecurityGroups misclassifies an unknown group, and four listener/rule checks reach no verdict

> _Note: this issue was identified against the code base at commit `94f7b27553b727586aac9de0add3c17de28dbaa9`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
DescribeLoadBalancers

## Description
Four independent net-new root causes in the Elastic Load Balancing v2 emulator, all grounded in failing behavioral checks of the `elbv2` suite that no open issue carries the replay key of. A fixer must close ALL FOUR before submitting; each cause below names its own failing check ids.

Cause 1 of 4: the ALB data plane answers HTTP 502 with an empty body for every request routed to a registered EC2 instance target, so no target-lifecycle behaviour of an `instance` target group is observable.
AWS: recorded behavior only. For a target group created with `TargetType="instance"`, `Protocol=HTTP` and an HTTP health check, an instance that serves the traffic port is forwarded to and the client receives the TARGET's own response (HTTP 200 and the target's body). A 502 is reserved for a target the load balancer could not get a well-formed response from. On top of that baseline the three checks observe three documented behaviours: `deregistration_delay.timeout_seconds` keeps serving an in-flight request while `DescribeTargetHealth` reports `State=draining`; `slow_start.duration_seconds` ramps a newly healthy target in; and a target whose response exceeds `idle_timeout.timeout_seconds` yields HTTP **504** (not 502) while the target itself stays `healthy`.
Emulator: every data-plane GET at the published load-balancer address answers `(502, '')` for the whole 300 s poll — `AssertionError: load balancer serving 'TARGET-A' at http://127.0.0.1:39155/ (observed: []) not met within 300s. Last result: (502, '')`; `AssertionError: http://127.0.0.1:42437/x answering 200 (observed: []) not met within 300s. Last result: 502`; `AssertionError: load balancer serving 'SIM2REAL-TARGET-BODY' at http://127.0.0.1:36263/?s=0 (observed: []) not met within 300s. Last result: (502, '')`. The body is empty in every case, so nothing of the target's own answer reaches the client and the draining / slow-start / idle-timeout assertions are never reached.
Why: a client cannot use the emulator for any ALB request path backed by EC2 instance targets — a healthy-looking target group serves a gateway error, so deployment, drain and timeout logic written against AWS (and any assertion distinguishing a 504 timer from a 502 target fault) behaves oppositely here.
Fix: the data-plane forward path for `instance`-type targets (target resolution to the instance's address/traffic port and the proxying of the target's response), and the listener's 502-vs-504 classification for a response that outlives `idle_timeout.timeout_seconds`.

Cause 2 of 4: `DNSName` is published as a bare `host:port` authority instead of a host name, so a client that composes an authority from it — `http://{DNSName}:{listener port}` — or that compares it with the request's host cannot address or verify the data plane.
AWS: `DescribeLoadBalancers`/`CreateLoadBalancer` model `LoadBalancer.DNSName` as "The public DNS name of the load balancer" — a HOST, with no port in it; the listener's port is appended by the client. For redirects the model is explicit about the related rule: `RedirectActionConfig` documents the reserved keywords `#{protocol}`, `#{host}`, `#{port}`, `#{path}` ("the leading \"/\" is removed") and `#{query}`, so `#{host}` expands to the HOST of the incoming request (the `Host` header the client sent, i.e. the load balancer's `DNSName`), and `#{port}` to the port the request arrived on.
Emulator: `DNSName` is the host:port of the socket the load balancer opened, so composing the documented URL yields a value that is not a URL at all: `simparity.target.EndpointRefused: endpoint 'http://127.0.0.1:37113:80' is not a http/https/ws/wss/rtmp/rtmps URL with a host` (and `'http://127.0.0.1:34289:80'` in the second check). The same defect surfaces in the redirect rule: with `RedirectConfig.Host="#{host}"`, `Port="8443"`, `Path="/moved#{path}"`, `Query="orig=#{path}&keep=#{query}"` the emulator emits `Location: https://127.0.0.1:8443/movedredir/deep/thing?orig=redir/deep/thing&keep=a=1&b=2`, whose host (`127.0.0.1`) is NOT the host the request was addressed to (the published `DNSName`, `127.0.0.1:<port>`) — `AssertionError: #{host} not substituted with the request host`. Only the port-bearing `DNSName` makes those two disagree; once `DNSName` is a bare host, `#{host}` must expand to exactly that value.
Why: every client that builds a URL from `DNSName` (SDK users, CloudFormation outputs, CloudFront/Route 53 origins, any `curl http://$DNS:$PORT/`) gets an unusable address, and a redirect `Location` built from `#{host}` points somewhere other than the name the request used.
Fix: the published-endpoint value in the load balancer's state/serializer (`DNSName` must be a resolvable host the emulator serves, with the listener's port supplied by the listener rather than baked into the name), and the `#{host}`/`#{port}` expansion in the listener's redirect-action handling.

Cause 3 of 4: `SetSecurityGroups` with a security-group id the account holds no group under is refused as `InvalidSecurityGroup` instead of `InvalidConfigurationRequest`.
AWS: Smithy models both errors on this operation — `InvalidConfigurationRequestException` (awsQueryError code `InvalidConfigurationRequest`, HTTP 400) and `InvalidSecurityGroupException` (code `InvalidSecurityGroup`, HTTP 400). The recording shows AWS classifies an id that resolves to no group as HTTP 400 `InvalidConfigurationRequest` with the message `One or more security groups are invalid` — that whole sentence is FIXED text, it interpolates no value from the request or from state (the offending id is not named). The rejected call also leaves the load balancer's applied security groups unchanged.
Emulator: HTTP 400 with error code `InvalidSecurityGroup` — `AssertionError: expected the unknown security group to be rejected with InvalidConfigurationRequest, got 'InvalidSecurityGroup'`. The handler routes `SecurityGroupRefusal::NotFound` to `InvalidSecurityGroupException` and reserves `InvalidConfigurationRequestException` + the `One or more security groups are invalid` text for the wrong-VPC case only.
Why: a client that branches on the error code (retry, surface a specific message, or distinguish "not my VPC" from "no such group") takes the wrong branch, and generated SDK error types differ, for the single most common mistake on this call.
Fix: the refusal mapping in the `SetSecurityGroups` handler — the not-found refusal must answer the modeled `InvalidConfigurationRequestException` with the fixed `One or more security groups are invalid` message (file/line: services/service-com-amazonaws-elasticloadbalancingv2-elasticloadbalancing-v10/src/ops/set_security_groups.rs:257-280).
Traces: elbv2.set-security-groups-invalid-sg-fails.

Cause 4 of 4: four listener/rule/TLS checks make no observable progress and are cut off at the 60 s harness cap with no response recorded at all.
AWS: recorded behavior only. Each of the four converges well inside its own budget on AWS: a CloudFormation ELBv2 stack updates a listener rule and replaces a target group under deletion protection; an `instance` target serves HTTP and stops being routed to once it turns unhealthy; an HTTPS listener's security policy bounds the negotiated TLS version and cipher; and with `routing.http2.enabled=true` a client offering ALPN `['h2','http/1.1']` negotiates `h2`.
Emulator: `Error: Check timed out after 60.0s` for all four — no status, no error code, nothing observable, so the emulator never reaches the state these checks wait on (the ALB never becomes serveable / the HTTPS listener never completes a usable handshake inside the cap).
Why: a client gets no answer at all on these paths, so none of the four behaviours can be relied on; and the absence of any recorded response also means these failures carry no diagnosis beyond the cut-off.
Fix: whatever blocks convergence of the ALB/HTTPS listener bring-up on these paths — the load-balancer/listener readiness and the TLS listener socket (ssl policy + ALPN selection) — plus the CloudFormation ELBv2 rule-update/target-group-replacement path for the first check. Start by making one of the four reach its first assertion, since all four stall before producing any output.
