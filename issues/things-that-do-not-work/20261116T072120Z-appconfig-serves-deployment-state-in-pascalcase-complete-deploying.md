# appconfig serves Deployment$State in PascalCase ('Complete'/'Deploying'/'RolledBack') on GetDeployment, StartDeployment and StopDeployment instead of the modeled DeploymentState enum value, so every deployment barrier in the behavioral suite hangs (3 causes)

> _Note: this issue was identified against the code base at commit `0cc1593284dc57d1fa665d25f671e4cff118eb06`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
GetDeployment

## Description
This issue bundles 3 net-new causes, all in appconfig, that share ONE root cause: the token the emulator puts on the wire for Deployment$State is a PascalCase rendering of its internal deployment-state name instead of the modeled com.amazonaws.appconfig#DeploymentState enum value AWS serves. The defect reaches every operation whose output shape is `Deployment`: the GetDeployment read path and the StartDeployment / StopDeployment write paths. Because a deployment that AWS reports as COMPLETE is reported as 'Complete', every check that waits for a deployment to settle before exercising its real subject never clears that barrier: 85 of the appconfig behavioral checks fail here, most of them only as 'Check timed out after 60.0s' with the poll still reading State 'Complete'. A fixer must close all THREE causes below, not just the first.

Related open issues that the replay reports as NOT owning these checks (the suite marked none of the 85 checks OWNED or ALREADY FILED): 20261116T014021Z-appconfig-serves-deployment-state-in-pascalcase-across-the.md and 20261112T075825Z-appconfig-stopdeployment-refuses-a-baking-deployment-so-the.md describe the same casing fault from the WIRE corpus (StartDeployment/StopDeployment/ListDeployments and GetDeployment respectively); 20261115T213820Z-appconfig-lambda-2-net-new-causes-getdeployment-serves.md, 20261115T214126Z-appconfig-appconfigdata-getdeployment-serves-deployment-state-in-pascalcase.md, 20261115T214126Z-appconfigdata-appconfig-serves-deployment-state-in-pascalcase-complete-instead.md, 20261115T232640Z-appconfig-cloudwatch-getdeployment-serves-deployment-state-as-complete.md and 20261116T022927Z-appconfig-sqs-appconfig-getdeployment-serves-deployment-state-as-pascalcase-complete.md carry the same cause for the appconfig__lambda / appconfig__appconfigdata / appconfig__cloudwatch / appconfig__sqs service tokens only. 20261110T191755Z-appconfig-getdeployment-getenvironment-serve-state-as-the-model.md asserts the OPPOSITE of what the recordings show for Deployment$State and must not be used as the fix direction: the recordings prove Deployment$State is SCREAMING_SNAKE while Environment$State is PascalCase (see Cause 1).

Cause 1 of 3: GetDeployment's 200 body reports State 'Complete' (and 'Deploying', 'RolledBack') instead of 'COMPLETE' ('DEPLOYING', 'ROLLED_BACK').
  AWS: Smithy: GetDeployment GET /applications/{ApplicationId}/environments/{EnvironmentId}/deployments/{DeploymentNumber}, http code 200, output shape Deployment; Deployment$State targets com.amazonaws.appconfig#DeploymentState, an enum whose only values are BAKING, VALIDATING, DEPLOYING, COMPLETE, ROLLING_BACK, ROLLED_BACK, REVERTED. The wire value of an enum member IS that value string, so a finished deployment serializes as 'COMPLETE', one rolling out as 'DEPLOYING', one aborted as 'ROLLED_BACK'. The recorded behaviour the checks encode agrees: deployment terminal sets are ('COMPLETE','ROLLED_BACK','REVERTED') and in-flight sets are ('BAKING','VALIDATING','DEPLOYING'). Note this is NOT a blanket casing rule for the service: the same recordings treat Environment$State as PascalCase ('Deploying', 'RollingBack', 'ReadyForDeployment'), which the emulator already gets right, so only the DeploymentState projection is wrong.
  Emulator: GetDeployment answers 200 (status matches) and every other member of the body agrees, but $.State is 'Complete' / 'Deploying' / 'RolledBack' — the internal state name converted to PascalCase, which is not a member of DeploymentState (and for the multi-word members the enum's underscore is dropped as well).
  Why: the standard AppConfig client idiom is start-then-poll-GetDeployment-until-State-is-terminal. A caller comparing against 'COMPLETE' (or deserializing into the generated DeploymentState enum, where the unmodeled token lands in the unknown-variant bucket) never sees the deployment finish, so it blocks until its own timeout and then reports a successful deployment as failed or stuck. Everything gated behind 'the configuration is live' — reading the deployed document, starting an experiment run, deleting leaf resources — is unreachable.
  Fix: the appconfig response projection/serializer for the Deployment shape (or the Display/Serialize impl of the internal deployment-state type it reuses) must emit each state as its modeled DeploymentState enum value, keeping the underscore for ROLLING_BACK / ROLLED_BACK, rather than reusing the internal variant name.
  Traces: appconfig.op-contract-getDeployment, appconfig.e2e-experiment-full-flow-create-run-observe-teardown (poll result shows 'State': 'Complete' at PercentageComplete 100.0), appconfig.start-deployment-full-lifecycle-to-complete ('deployment reaching a terminal state not met within 45s ... State: Complete'), appconfig.exponential-growth-type-advances-in-powers-of-the-growth-factor, appconfig.final-bake-time-window-holds-the-deployment-non-terminal, appconfig.linear-rollout-serves-both-versions-across-sessions, appconfig.next-poll-token-before-minimum-interval-rejected (all four: "did not reach COMPLETE within 240s; last state 'Complete'"), appconfig.update-experiment-run-invalid-state-transition-rejected (TimeoutError: the deployment reaching COMPLETE), plus the ~70 checks that time out at the same barrier (full list in trace_ids).

Cause 2 of 3: StartDeployment's 201 body reports State 'Deploying' instead of 'DEPLOYING'.
  AWS: Smithy: StartDeployment POST /applications/{ApplicationId}/environments/{EnvironmentId}/deployments, http code 201, output shape Deployment, State -> DeploymentState. A freshly accepted deployment is reported with one of the in-flight members, 'DEPLOYING' (or 'BAKING'/'VALIDATING' depending on the strategy phase).
  Emulator: answers 201 (status matches) with $.State 'Deploying'.
  Why: a client that branches on the value returned by StartDeployment itself — before any GetDeployment poll — cannot classify the deployment it just created; the in-flight check takes the default/unknown path. This is a distinct serialization site from Cause 1, so fixing only the read path leaves it broken.
  Fix: same DeploymentState wire mapping, applied to the StartDeployment response projection.
  Traces: appconfig.op-contract-startDeployment ('unexpected initial state: Deploying'), appconfig.stop-deployment-then-list-deployments-state ('expected an in-flight state (BAKING/VALIDATING/DEPLOYING) right after StartDeployment, got \'Deploying\'').

Cause 3 of 3: StopDeployment's 202 body reports State 'RolledBack' instead of 'ROLLED_BACK'.
  AWS: Smithy: StopDeployment DELETE /applications/{ApplicationId}/environments/{EnvironmentId}/deployments/{DeploymentNumber}, http code 202, output shape Deployment, State -> DeploymentState, whose terminal rollback member is ROLLED_BACK. A stopped deployment is reported 'ROLLED_BACK' (or 'REVERTED' under Allow-Revert).
  Emulator: answers 202 (status matches) with $.State 'RolledBack' — the PascalCase rendering also collapses the enum's underscore, so multi-word members are doubly unrecoverable.
  Why: 'ROLLED_BACK' is the value safe-rollback tooling waits for to confirm an abort took effect. Receiving 'RolledBack' means the confirmation never matches, so the operator-facing rollback reads as never having happened although the emulator performed it.
  Fix: same DeploymentState wire mapping, applied to the StopDeployment response projection; multi-word members must keep the underscore form.
  Traces: appconfig.op-contract-stopDeployment ('unexpected state: RolledBack'), appconfig.stop-deployment-transitions-and-rejects-second-stop ('unexpected post-stop state: RolledBack'), appconfig.start-deployment-conflict-while-in-progress ("unexpected post-stop state: 'RolledBack'"), appconfig.in-flight-deployment-does-not-block-leaf-deletion (expected the stopped orphan to come back ROLLED_BACK, got 'RolledBack').
