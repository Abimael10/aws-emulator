# ecr__eks__logs: 3 net-new root causes — asynchronous EKS effects never settle: no /aws/eks/<cluster>/cluster log group after enabling 'api' logging on a CFN-provisioned cluster, no Container Insights performance delivery, and a pod's private-ECR image pull never reports Pulled

> _Note: this issue was identified against the code base at commit `4bb76b5ad778511f4e613dac77ae9e1eefd9f644`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
UpdateClusterConfig

## Description
Three distinct asynchronous EKS effects are never produced by the emulator. Each failing check below polls for one of them with a multi-minute budget and is cut off by the suite's per-check budget with 'Check timed out after 60.0s' — the awaited effect had not appeared at any point the check observed it. Three net-new causes, numbered; each carries its own failing check ids.

NOTE on scope: these are reported as timeouts, so the grading window is bounded by the suite budget rather than by an emulator error response. They are filed because the emulator serves the asynchronous state machine the checks poll, and nothing it served ever advanced. A fixer should re-replay exactly the check ids in trace_ids. Related open issues that do NOT cover these checks (different checks / different replay keys), named here so a fixer can share a fix: 20261112T155926Z-ecr-eks-logs-the-eks-control-plane-logging.md (control-plane logging contrast on a non-CFN cluster), 20261114T130859Z-ecr-eks-logs-2-net-new-root-causes-b62cb4.md (core/v1 events collection answered 405, pod logs), 20261116T033949Z-eks-5-net-new-root-causes-admitted-pods.md (admitted pods never run their containers), 20261115T110546Z-ecr-eks-logs-eks-the-served-cluster-kubernetes-api-exposes-no.md (no OpenAPI discovery document).

Cause 1 of 3: enabling control-plane log type 'api' with UpdateClusterConfig on a CloudFormation-provisioned cluster never creates /aws/eks/<cluster>/cluster, and no kube-apiserver-* log stream ever appears.
AWS: Smithy (services/service-com-amazonaws-eks-awswesleyfrontend): UpdateClusterConfig POST /clusters/{name}/update-config -> {update: Update}; input member logging targets Logging{clusterLogging: list<LogSetup{types: list<LogType>, enabled: boolean}>}; LogType enum values are api, audit, authenticator, controllerManager, scheduler. LogSetup.enabled is documented 'If a log type is enabled, that log type exports its control plane logs to CloudWatch Logs'. DescribeUpdate GET /clusters/{name}/updates/{updateId} reports the update's status, which reaches Successful. AWS therefore (a) creates no control-plane log group while every log type is disabled (the template in this check declares no Logging block at all) and (b) after the update succeeds, creates the CloudWatch Logs group named /aws/eks/<clusterName>/cluster and begins writing streams whose names start with kube-apiserver-. The group name is a template: the fixed parts are '/aws/eks/' and '/cluster', the variable part is the cluster name from the request; the stream prefix 'kube-apiserver-' is fixed.
Emulator: the check deploys the cluster via CloudFormation, confirms the absence of the group, calls UpdateClusterConfig with clusterLogging [{types:[api], enabled:true}], then polls DescribeLogGroups for /aws/eks/<cluster>/cluster (300 s) and DescribeLogStreams with logStreamNamePrefix=kube-apiserver- (180 s). Neither the group nor the stream was ever observed; the check was cut off by the suite budget while still polling.
Why: a client that enables control-plane logging to drive audit/observability tooling sees DescribeLogGroups return no group and DescribeLogStreams return an empty logStreams list forever, so any consumer tailing control-plane logs (or any assertion that logging is now on) can never make progress against the emulator, while the same code works on AWS.
Fix: the eks UpdateClusterConfig handler's logging side-effect and the state it shares with cloudwatchlogs — the update must, on reaching Successful, materialise the /aws/eks/<cluster>/cluster log group in logs state and emit at least one kube-apiserver-<id> stream; the CloudFormation AWS::EKS::Cluster path must route to the same side-effect so a CFN-created cluster behaves like a CreateCluster one.
Traces: ecr__eks__logs.deploy-eks-cluster-without-logging-config-no-log-groups.

Cause 2 of 3: no Container Insights performance data is ever delivered — /aws/containerinsights/<cluster>/performance stays empty after the amazon-cloudwatch-observability add-on is active with a pod-identity role carrying CloudWatchAgentServerPolicy, and it also stays empty after the missing permission is attached in the negative-control check.
AWS: recorded behavior only (the EKS Smithy model describes CreateAddon/CreatePodIdentityAssociation but not the add-on's data-plane emissions). The recordings show that once the cluster, the managed nodegroup, the eks-pod-identity-agent add-on and the amazon-cloudwatch-observability add-on are all ACTIVE and a pod identity association maps namespace amazon-cloudwatch / serviceAccount cloudwatch-agent to a role with arn:aws:iam::aws:policy/CloudWatchAgentServerPolicy, CloudWatch Logs group /aws/containerinsights/<clusterName>/performance receives events whose message bodies are Embedded Metric Format records containing a CloudWatchMetrics key and ClusterName equal to the cluster's name. The group name is a template: '/aws/containerinsights/' and '/performance' are fixed, the cluster name comes from the request. The negative control shows the mirror image: with an agent role lacking CloudWatch write permission the group receives nothing, and after attaching the permission delivery starts.
Emulator: both checks poll GetLogEvents/FilterLogEvents on that group (360 s for the deny window, 900 s for the delivery window). No performance event was ever observed in either check, so the positive assertion ('performance log events parse as EMF records tagged with ClusterName=<cluster>') can never be satisfied and the negative control can never reach its post-attachment delivery half. Both checks were cut off by the suite budget while polling.
Why: a client validating Container Insights — a dashboard, an alarm on an EMF-derived metric, or a test that the agent's permissions are correct — observes an empty log group and cannot distinguish 'permission denied' from 'observability add-on produces nothing', which is exactly the distinction the negative control exists to make.
Fix: the eks add-on state machine's data-plane emission for amazon-cloudwatch-observability (and its pod-identity authorization check), writing EMF records into cloudwatchlogs state under /aws/containerinsights/<cluster>/performance, gated on the associated role's CloudWatch write permission.
Traces: ecr__eks__logs.eks-container-insights-metrics-logs-delivery, ecr__eks__logs.eks-container-insights-without-agent-permission-no-delivery.

Cause 3 of 3: a pod never reports an image-pull outcome for a private ECR image — no 'Pulled' event on a Fargate-profile pod whose pod execution role is authorized, and no pull-failure outcome on a pod whose role lacks ECR permission.
AWS: Smithy: CreateFargateProfile/DescribeFargateProfile return FargateProfile{podExecutionRoleArn, selectors, status: FargateProfileStatus}, documented as 'the Pod execution role to use for any Pod that matches the selectors in the Fargate profile'. Recorded behavior: with the profile ACTIVE and no nodegroup and no imagePullSecrets, a pod scheduled onto it pulls its private ECR image through that role (AmazonEKSFargatePodExecutionRolePolicy) and the cluster's Kubernetes API reports a core/v1 Event with reason 'Pulled' naming the image; when the role carries no ECR permission the pull is refused and the pod reports the pull failure instead (reason 'Failed' with an ECR authorization message) rather than silently never progressing. 'Pulled'/'Failed' are the fixed reason strings; the image reference and pod name come from the request.
Emulator: both checks stand the cluster (and for the Fargate case the private VPC and Fargate profile) up, create the pod, then poll the served cluster Kubernetes API for the pod's events for up to 900 s. No pull outcome — neither success nor refusal — was ever observed; both checks were cut off by the suite budget while polling.
Why: a client cannot tell an authorized pull from an unauthorized one: both look like a pod stuck with no events. Any workflow that gates on the pull result (waiting for a pod to run, or asserting that a missing ECR permission is what broke it) hangs instead of resolving, and the negative control that proves authorization is enforced cannot be expressed.
Fix: the served cluster Kubernetes API's pod admission/runtime path and the ECR authorization it consults — a pod must progress to an image-pull attempt and record the resulting core/v1 Event (reason 'Pulled' on success, a pull-failure Event when the pod execution / node role is not authorized for the repository).
Traces: ecr__eks__logs.eks-fargate-execution-role-pulls-ecr-image, ecr__eks__logs.eks-pod-image-pull-fails-without-ecr-permission-rejected.

## Steps to Reproduce
1. Boot the emulator and replay the ecr__eks__logs checks named in trace_ids.
2. Control-plane logging: create an EKS cluster via CloudFormation (AWS::EKS::Cluster with no Logging property), confirm /aws/eks/<cluster>/cluster does not exist, then call eks UpdateClusterConfig(name=<cluster>, logging={"clusterLogging":[{"types":["api"],"enabled":true}]}), poll DescribeUpdate until status Successful, then poll logs DescribeLogGroups(logGroupNamePrefix="/aws/eks/<cluster>/cluster") — the group never appears; DescribeLogStreams with logStreamNamePrefix="kube-apiserver-" never returns a stream.
3. Container Insights: create cluster + managed nodegroup, CreateAddon eks-pod-identity-agent, CreatePodIdentityAssociation(namespace=amazon-cloudwatch, serviceAccount=cloudwatch-agent, roleArn=<role with arn:aws:iam::aws:policy/CloudWatchAgentServerPolicy>), CreateAddon amazon-cloudwatch-observability, wait ACTIVE, then poll logs on /aws/containerinsights/<cluster>/performance — no events ever arrive. Repeat with an agent role lacking CloudWatch write permission, then attach it — delivery still never starts.
4. Pod image pull: push an image to a private ECR repository, create a cluster with private subnets and a Fargate profile whose podExecutionRoleArn carries AmazonEKSFargatePodExecutionRolePolicy, create a pod on that profile with no imagePullSecrets, and poll the cluster Kubernetes API for the pod's core/v1 events — no 'Pulled' event ever appears. Repeat with a role that has no ECR permission — no pull-failure event appears either.
