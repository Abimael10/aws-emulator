# appsync__dynamodb__events: an EventBridge rule's AppSync GraphQL-endpoint target is never invoked — no mutation is performed, nothing is dead-lettered, and no Invocations/FailedInvocations are counted

> _Note: this issue was identified against the code base at commit `6e2d7185f30747a2356e601c1d412ac8e0be11c4`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
PutTargets

## Description
Cause 1 of 1: a rule target that names an AppSync GraphQL endpoint (Target.Arn = arn:<partition>:appsync:<region>:<account>:endpoints/graphql-api/<host-label>, Target.AppSyncParameters.GraphQLOperation, Target.RoleArn, Target.InputTransformer, Target.DeadLetterConfig, Target.RetryPolicy) is accepted but never dispatched: a matched event neither performs the GraphQL operation nor produces a dead letter nor a delivery metric. Failing checks: appsync__dynamodb__events.xsvc-appsync-2-resolver-error-in-a-200-response-is-a-successful-delivery-not-dead-lettered, appsync__dynamodb__events.xsvc-appsync-2-role-without-graphql-denied-dead-letters-and-counts-failed-invocations, appsync__dynamodb__events.xsvc-appsync-2-near-miss-events-not-delivered-while-the-pipeline-is-live, appsync__dynamodb__events.xsvc-appsync-2-rule-input-transformer-mutation-writes-the-mapped-item.

AWS: Smithy (eventbridge) models the AppSync target explicitly — Target$AppSyncParameters targets AppSyncParameters{GraphQLOperation: @length min 1 max 1048576, @sensitive} documented as "Contains the GraphQL operation to be parsed and executed, if the event target is an AppSync API"; Target$RoleArn is "the IAM role to be used for this target when the rule is triggered"; Target$InputTransformer supplies the custom input; Target$DeadLetterConfig{Arn} is "the Amazon SQS queue for EventBridge to use as a dead-letter queue (DLQ)" for undeliverable events, with Target$RetryPolicy. Delivery behavior is recorded behavior only: for each event matching the rule's pattern, EventBridge assumes Target.RoleArn, renders InputTransformer's InputTemplate from InputPathsMap, and executes AppSyncParameters.GraphQLOperation against the API's GraphQL endpoint with those values as the operation's variables, so the mutation's side effect (here a DynamoDB PutItem through the field's resolver) happens; that attempt counts one AWS/Events Invocations datapoint for the rule. A response that is HTTP 200 carrying GraphQL resolver errors is a SUCCESSFUL delivery — no dead letter, no FailedInvocations. A target role that is trusted by events.amazonaws.com but holds no appsync:GraphQL grant on the field is a FAILED invocation: the event is written to DeadLetterConfig.Arn with message attributes RULE_ARN = the rule ARN, ERROR_CODE = NO_PERMISSIONS and ERROR_MESSAGE, and one FailedInvocations datapoint is published for that rule. A near-miss event (detail.kind or detail-type differing from the pattern only in case) matches nothing, so it is neither executed nor dead-lettered.

Emulator: both PutRule/PutTargets (FailedEntryCount 0) and PutEvents (FailedEntryCount 0) are accepted, and the same signed GraphQL mutation executed directly against the API's endpoint in the same check resolves and writes its item — but the rule's AppSync target leg does nothing at all. Over 5 rounds, each polled for 120 s, the healthy rule's item never appears in the table and the target's DLQ stays empty: the resolver-error check ends on AssertionError "the healthy rule wrote ok-<id> or something was dead-lettered not met within 120s. Last result: None", and the denied-role check on AssertionError "both rules resolved event '<id>' (item written or dead-lettered) not met within 120s. Last result: set()" — set() meaning NEITHER the granted role's rule wrote an item NOR the role-without-appsync:GraphQL rule produced a NO_PERMISSIONS dead letter. The two sibling checks that assert the same leg (input-transformer-mapped mutation; near-miss suppression while the positive path is live) report only "Check timed out after 60.0s", waiting on that same never-arriving delivery. Related open issues 20261114T043034Z-appsync-dynamodb-events-vtl-mapping-template-resolvers-are.md and 20261114T102203Z-appsync-dynamodb-events-a-vtl-resolver-backed-putitem.md cover the UPSTREAM cause (VTL mapping-template resolvers not executed); in this run the direct signed mutation and the deliberately broken resolver both answer as AWS does (HTTP 200, errors[0].errorType "DynamoDB:DynamoDbException" naming the refused dynamodb:PutItem), so the checks now progress past that point and this target-dispatch gap is a distinct, uncovered cause.

Why: a client that routes events to an AppSync API through an EventBridge rule sees its events accepted and silently discarded — the mutation's write never happens, and because nothing is dead-lettered and no Invocations/FailedInvocations datapoint is published, the loss is undetectable by every mechanism AWS provides for it. Authorization regressions are equally invisible: a target role missing appsync:GraphQL looks exactly like a correctly configured one, and the documented distinction between "a 200 with resolver errors is a success" and "a refused invocation is dead-lettered" cannot be observed at all.

Fix: the EventBridge target-dispatch component — add the AppSync endpoint target handler (recognise the endpoints/graphql-api/<host-label> target ARN, assume Target.RoleArn, render Target.InputTransformer, execute Target.AppSyncParameters.GraphQLOperation against that API's GraphQL endpoint under the assumed role) and wire it into the existing delivery-outcome path so a refusal becomes a DeadLetterConfig message carrying RULE_ARN/ERROR_CODE/ERROR_MESSAGE and the per-rule AWS/Events Invocations and FailedInvocations counters are published.

Traces: appsync__dynamodb__events.xsvc-appsync-2-resolver-error-in-a-200-response-is-a-successful-delivery-not-dead-lettered, appsync__dynamodb__events.xsvc-appsync-2-role-without-graphql-denied-dead-letters-and-counts-failed-invocations, appsync__dynamodb__events.xsvc-appsync-2-near-miss-events-not-delivered-while-the-pipeline-is-live, appsync__dynamodb__events.xsvc-appsync-2-rule-input-transformer-mutation-writes-the-mapped-item.

## Evidence
Expected (AWS): after PutEvents of an entry matching the rule's pattern (source "app.ingest", detail-type "ItemArrived", detail {id, kind}), the rule's AppSync target executes `mutation PutItem($id: ID!, $kind: String!) { putItem(id: $id, kind: $kind) { id kind } }` with the InputTransformer-rendered variables, so GetItem(ConsistentRead) on the table returns {"id": {"S": "<prefix><id>"}, "kind": {"S": "<kind>"}}; the DLQ stays empty for that round and AWS/Events Invocations for the rule increments by one. For the sibling rule whose target role holds only appsync:GetGraphqlApi (no appsync:GraphQL), the same event appears on DeadLetterConfig.Arn with MessageAttributes RULE_ARN = that rule's ARN and ERROR_CODE = "NO_PERMISSIONS", and FailedInvocations for it increments; no item is written for it. A rule whose target mutation hits a resolver error inside an HTTP 200 GraphQL response is still a successful invocation: no DLQ message, FailedInvocations unchanged.

Actual (emulator):
- xsvc-appsync-2-resolver-error-in-a-200-response-is-a-successful-delivery-not-dead-lettered: AssertionError "the healthy rule wrote ok-<id> or something was dead-lettered not met within 120s. Last result: None" — the probe returns the DynamoDB item for the healthy rule (None = absent) and the DLQ drain found nothing. The check had already verified, immediately before, that the endpoint itself behaves: the directly signed broken mutation answered HTTP 200 with exactly one errors[0].errorType "DynamoDB:DynamoDbException" naming dynamodb:PutItem and data {"putItemBroken": null}, and the healthy mutation resolved and wrote its warm-up item.
- xsvc-appsync-2-role-without-graphql-denied-dead-letters-and-counts-failed-invocations: AssertionError "both rules resolved event '<id>' (item written or dead-lettered) not met within 120s. Last result: set()" — the resolved-set is empty, i.e. neither rule wrote its item and neither produced a dead letter (the expected ERROR_CODE for the denied rule is NO_PERMISSIONS).
- xsvc-appsync-2-near-miss-events-not-delivered-while-the-pipeline-is-live and xsvc-appsync-2-rule-input-transformer-mutation-writes-the-mapped-item: "Check timed out after 60.0s" — both wait on the same positive AppSync-target delivery before they can grade near-miss suppression / the mapped item.

Per-run values (role, table, bus, rule and api names, event ids, host labels) are generated per check and are not part of the requirement; what diverges is that the target leg produces no invocation, no dead letter and no metric at all.

## Steps to Reproduce
1. iam CreateRole trusting appsync.amazonaws.com with dynamodb:PutItem (+GetItem) on the table; iam CreateRole trusting events.amazonaws.com with appsync:GraphQL on arn:<p>:appsync:<region>:<account>:apis/<apiId>/types/Mutation/fields/putItem; optionally a second events-trusted role granted only appsync:GetGraphqlApi on the api ARN.
2. dynamodb CreateTable (HASH id:S, PAY_PER_REQUEST), wait ACTIVE.
3. appsync CreateGraphqlApi (AWS_IAM) + StartSchemaCreation (`type Mutation { putItem(id: ID!, kind: String!): Item }`) + CreateDataSource (AMAZON_DYNAMODB, serviceRoleArn) + CreateResolver for Mutation.putItem (VTL PutItem request template, $util.toJson($ctx.result) response template).
4. Confirm the endpoint works directly: SigV4-sign and POST the mutation to uris.GRAPHQL — it answers 200 with data.putItem populated and the item is in the table.
5. events CreateEventBus; sqs CreateQueue as the DLQ with a policy allowing events.amazonaws.com sqs:SendMessage for arn:<p>:events:<region>:<account>:rule/<bus>/*.
6. events PutRule with EventPattern {"source": ["app.ingest"], "detail-type": ["ItemArrived"]} and PutTargets with Arn arn:<p>:appsync:<region>:<account>:endpoints/graphql-api/<host-label-of-uris.GRAPHQL>, RoleArn (the appsync:GraphQL role), AppSyncParameters.GraphQLOperation = the mutation, InputTransformer{InputPathsMap {id: $.detail.id, kind: $.detail.kind}, InputTemplate '{"id": "ok-<id>", "kind": <kind>}'}, RetryPolicy{MaximumRetryAttempts: 0, MaximumEventAgeInSeconds: 60}, DeadLetterConfig{Arn: <dlq arn>}. PutTargets reports FailedEntryCount 0.
7. events PutEvents one matching entry (FailedEntryCount 0). Poll the table for the "ok-<id>" item and drain the DLQ for up to 120 s.
Observed: the item never appears and the DLQ stays empty; no AWS/Events Invocations or FailedInvocations datapoint is published for the rule. Expected: the item is written (or, for a target role without appsync:GraphQL, one DLQ message with ERROR_CODE NO_PERMISSIONS plus one FailedInvocations).
