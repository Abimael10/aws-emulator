# cloudformation__docdb: 2 net-new causes — a CREATE_COMPLETE AWS::DocDB::DBInstance does not exist in DocDB, and an AWS::DocDB::DBCluster naming an EngineVersion DocDB does not offer is not refused or rolled back

> _Note: this issue was identified against the code base at commit `3d549b51f10ecf86bd29287e87008ba36d5f0d1d`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
CreateStack

## Description
Two net-new root causes in CloudFormation's AWS::DocDB::* resource providers and the DocDB validation behind them. Both are reported together because they share the cloudformation__docdb service; each is numbered and carries its own failing check ids.

---
Cause 1 of 2: a stack's AWS::DocDB::DBInstance reaches CREATE_COMPLETE without the instance ever existing in DocDB, so DescribeDBInstances refuses it by identifier.
Failing check: cloudformation__docdb.deploy-docdb-dbcluster-and-dbinstance-round-trip-and-delete

AWS: the AWS::DocDB::DBInstance resource provider provisions the instance through DocDB's own CreateDBInstance. Smithy (com.amazonaws.docdb#AmazonRDSv19, awsQuery, endpointPrefix rds): CreateDBInstance input requires {DBInstanceIdentifier, DBInstanceClass, Engine, DBClusterIdentifier} plus Tags and returns a DBInstance; DescribeDBInstances (paginated: inputToken/outputToken Marker, items DBInstances, pageSize MaxRecords) takes an optional DBInstanceIdentifier filter and models exactly one error, DBInstanceNotFoundFault (awsQueryError code DBInstanceNotFound, httpError 404). An instance CloudFormation reports CREATE_COMPLETE is therefore readable through DocDB: DescribeDBInstances(DBInstanceIdentifier=<id>) returns 200 with exactly one DBInstances entry for the templated identifier, carrying DBInstanceClass and DBClusterIdentifier from the template, Engine 'docdb', DBInstanceStatus 'available', and a DBInstanceArn whose ListTagsForResource carries the template's Tags plus the stack's propagated tags. The 404 DBInstanceNotFound refusal, whose message is the fixed sentence "DBInstance " + the requested identifier + " not found." (the identifier is the value from the request), is correct ONLY after the stack is deleted. Resource-type reference: https://docs.aws.amazon.com/AWSCloudFormation/latest/TemplateReference/aws-resource-docdb-dbinstance.html

Emulator: the stack (AWS::DocDB::DBSubnetGroup + AWS::DocDB::DBCluster + AWS::DocDB::DBInstance) reaches CREATE_COMPLETE and DescribeStacks returns Outputs in which Ref(Cluster) and Ref(Instance) both equal the templated identifiers — so CloudFormation claims the instance exists — but the very next read, DescribeDBInstances(DBInstanceIdentifier=<templated instance id>), is refused: DBInstanceNotFound / "DBInstance <instance-id> not found." (404). The instance is tracked by CloudFormation but never materialized in DocDB state, so nothing downstream of it (DBInstanceClass, DBClusterIdentifier, Engine, DBInstanceStatus 'available', the instance's tags on DBInstanceArn) is observable either. This is the same class of defect as Cause 1 of the open issue 20261109T120625Z-cloudformation-docdb-4-net-new-causes-a-create.md (a CREATE_COMPLETE AWS::DocDB::DBClusterParameterGroup does not exist in DocDB) but in a different resource provider and not covered by it; the open issues 20261112T142502Z-docdb-dbinstance-projection-omits-modeled-instance-attributes-and.md and 20261115T142542Z-docdb-dbinstance-endpoint-address-is-published-as-a.md concern the projection/endpoint of an instance that DOES exist and do not cover an instance that is absent.

Why: a client that deploys a DocumentDB cluster plus instance as IaC and then reads, monitors, tags or connects to the instance through DocDB's API gets a 404 for a resource the stack reports as successfully created. Ref returns the identifier, so the template looks healthy while the instance it was supposed to create does not exist — the worst failure mode for infrastructure-as-code. Any automation that waits on DBInstanceStatus 'available' never completes, and the check can never reach the post-delete assertions.

Fix: the CloudFormation AWS::DocDB::DBInstance resource provider must perform create/read/update/delete against DocDB's own state (CreateDBInstance with the template's DBInstanceIdentifier/DBInstanceClass/DBClusterIdentifier/Tags and Engine inherited from the cluster, DeleteDBInstance on stack delete), so the docdb state store and its describe handlers are the single source of truth; it must not report CREATE_COMPLETE for an instance that was not written.

Cause 2 of 2: an AWS::DocDB::DBCluster naming an EngineVersion DocDB does not offer is accepted, so the stack reaches CREATE_COMPLETE instead of failing the resource and rolling back.
Failing check: cloudformation__docdb.deploy-docdb-dbcluster-invalid-engine-version-rejected-and-rolled-back

AWS: DocDB's CreateDBCluster takes an optional EngineVersion (String) and validates it against the versions the engine actually offers — the same set DescribeDBEngineVersions(Engine='docdb') enumerates. A version outside that set is refused with HTTP 400 and the fixed message text "Cannot find version " + the requested version + " for " + the requested engine; the version and engine are values from the request. CreateDBCluster's modeled errors (DBClusterAlreadyExistsFault, DBSubnetGroupNotFoundFault, InvalidParameterCombination-class common errors, ...) carry no version-specific shape, so the refusal arrives as RDS's 400 parameter refusal — recorded behavior only for the exact code; Hypothesis: AWS serves it as the RDS/DocDB common error InvalidParameterCombination. A CloudFormation stack whose AWS::DocDB::DBCluster names such a version therefore fails that resource at provision time and rolls the stack back: the stack ends ROLLBACK_COMPLETE and the CREATE_FAILED StackEvent for the cluster carries a resource-handler ResourceStatusReason of the form 'Resource handler returned message: "Cannot find version <version> for <engine> (Service: Rds, Status Code: 400, Request ID: <id>) (SDK Attempt Count: <n>)" (RequestToken: <token>)' — the sentence and the "(Service: Rds, Status Code: 400, ...)" suffix are fixed text, the version and engine come from the request, and the request id, attempt count and request token are per-run values. After the rollback DocDB must have no cluster by that name: DescribeDBClusters(DBClusterIdentifier=<name>) answers DBClusterNotFoundFault / "DBCluster <name> not found."

Emulator: the stack declaring EngineVersion '99.9.9' on its AWS::DocDB::DBCluster reaches CREATE_COMPLETE — "AssertionError: rejected stack ended 'CREATE_COMPLETE'". DocDB's CreateDBCluster never checks the requested EngineVersion against its engine-version catalog, so no resource is refused, no CREATE_FAILED row with the version handler reason is emitted, and no rollback happens; the handler reason, the HandlerErrorCode and the post-rollback DocDB absence are all unobservable, and the check's positive control at the latest offered version is never reached. The open issues 20261117T135409Z-docdb-createdbcluster-defaults-engineversion-to-the-highest-minor.md (which EngineVersion is DEFAULTED when none is given) and 20261117T135409Z-docdb-reference-data-catalogs-are-incomplete-engine-versions.md (which versions the catalog lists) do not cover this: here an explicitly requested version that is in no catalog at all is accepted unvalidated.

Why: a client relying on CloudFormation and DocDB to reject a mis-specified or unavailable EngineVersion before a DocumentDB cluster is built gets a stack reporting success over a cluster pinned to a version that does not exist; the cluster then reads back at a version the engine never offered, and automation branching on ROLLBACK_COMPLETE or on the resource-handler reason never fires.

Fix: the docdb CreateDBCluster handler's validation must resolve the requested EngineVersion against the engine-version catalog DescribeDBEngineVersions serves and refuse an unknown version with the 400 parameter refusal and the message above; the CloudFormation AWS::DocDB::DBCluster resource provider must map that service refusal into a CREATE_FAILED resource event whose ResourceStatusReason is the resource-handler wrapper and drive the stack to ROLLBACK_COMPLETE, leaving no cluster in docdb state.
