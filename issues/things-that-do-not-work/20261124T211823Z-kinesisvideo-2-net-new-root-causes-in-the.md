=== Cause 1 of 2: cross-session fragment-timecode monotonicity is evaluated on the raw Cluster timecode, so every new PutMedia connection using FragmentTimecodeType RELATIVE is refused FRAGMENT_TIMECODE_LESSER_THAN_PREVIOUS (4004) instead of appending to the stream ===
AWS: recorded behavior only — PutMedia is in no Smithy model (Smithy: com.amazonaws.kinesisvideo#KinesisVideo_20170930 binds 32 operations, of which none is PutMedia; GetDataEndpoint's own documentation is what points a producer at the ingest host: "write to it (using the PutMedia operation)"). The recording shows: a producer opens POST /putMedia on the host GetDataEndpoint(APIName=PUT_MEDIA) minted for the stream, with x-amzn-fragment-timecode-type: RELATIVE and x-amzn-producer-start-timestamp: <session start>, and a Matroska body in which one Cluster is one fragment. With RELATIVE timecodes a Cluster's Timecode is an offset from THAT session's producer start timestamp, so a fresh connection legitimately restarts its Cluster timecodes at 0. Such a session is accepted: HTTP 200 whose body streams JSON Acknowledgements (EventType BUFFERING -> RECEIVED -> PERSISTED), one PERSISTED per accepted Cluster carrying a service-minted FragmentNumber, with NO ERROR acknowledgement; the fragment numbers minted by the later session are all strictly greater than those of the earlier session on the same stream, the archive (ListFragments over the PRODUCER_TIMESTAMP window spanning both sessions) then holds every fragment of both sessions, and a single GetMedia from EARLIEST serves the frames of both. AWS's ERROR acknowledgement {"EventType":"ERROR","ErrorCode":"FRAGMENT_TIMECODE_LESSER_THAN_PREVIOUS","ErrorId":4004,...} is for a fragment whose timecode regresses relative to the previous fragment of the stream once the timecode type has been applied — i.e. compared on the absolute producer timestamp (producer start + Cluster timecode for RELATIVE, the Cluster timecode itself for ABSOLUTE), which never regresses merely because a new connection restarted at 0. Fixed text here is the JSON member names and the EventType/ErrorCode tokens; the variable parts are the FragmentNumber and FragmentTimecode, which come from the request and the emulator's state.
Emulator: the first session is accepted correctly (two PERSISTED acks). A SECOND connection on the same stream, same timecode type RELATIVE, new x-amzn-producer-start-timestamp, Cluster timecodes 0 and 1000, is answered HTTP 200 but emits no PERSISTED acknowledgement at all: replay of putmedia-across-two-connections-appends-to-the-same-stream reports "AssertionError: second connection expected two PERSISTED fragments, got []", and the parallel second session in putmedia-block-on-undeclared-track-rejected shows what is emitted instead — a single ERROR acknowledgement [{'EventType': 'ERROR', 'FragmentTimecode': 0, 'FragmentNumber': '3', 'ErrorId': 4004, 'ErrorCode': 'FRAGMENT_TIMECODE_LESSER_THAN_PREVIOUS'}]. The emulator is comparing the new session's raw Cluster timecode (0) against the previously persisted fragment's timecode rather than against the producer-start-adjusted timestamp, so any new RELATIVE session is rejected. (The FragmentNumber '3' and FragmentTimecode 0 in that ack are per-run state values, not part of the requirement.)
Why: every real producer re-connects — the KVS C/Java producer SDK and GStreamer kvssink open a new PutMedia session on reconnect, network blip, or token refresh, and each session sends RELATIVE timecodes starting near 0. Against this emulator the first session works and every subsequent one silently archives nothing: the client sees a 200 with an in-band 4004 it cannot avoid, fragment numbers never advance past the first session, ListFragments reports only the first session's fragments, and GetMedia serves only its frames. A producer that treats a session as durable once PutMedia returns 200 loses all media after the first connection.
Fix: the /putMedia handler's fragment-timecode validation (and the fragment-timestamp derivation it shares with the stream's fragment log) — the monotonicity check must be made on the fragment's derived absolute producer timestamp (x-amzn-producer-start-timestamp + Cluster timecode for RELATIVE; the Cluster timecode as epoch milliseconds for ABSOLUTE), per session, not on the raw Cluster timecode carried over from a previous connection, and an accepted session must continue minting strictly increasing fragment numbers on the existing stream.
Traces: kinesisvideo.putmedia-across-two-connections-appends-to-the-same-stream, kinesisvideo.putmedia-block-on-undeclared-track-rejected (its second session shows the 4004 ack verbatim).

=== Cause 2 of 2: a SimpleBlock naming a track number the Tracks element never declared is not refused with TRACK_NUMBER_MISMATCH (4010) ===
AWS: recorded behavior only (PutMedia is unmodeled, see Cause 1). The recording shows a container whose Tracks element declares only TrackNumber 1 while its SimpleBlock names track 2 refused IN BAND: HTTP 200 (a container-level ingest fault is never an HTTP error on PutMedia) whose acknowledgement stream carries {"EventType":"ERROR","ErrorCode":"TRACK_NUMBER_MISMATCH","ErrorId":4010} and NO PERSISTED acknowledgement for that fragment; the archive afterwards still holds only the fragments of the preceding valid session. Fixed text is the member names and the token TRACK_NUMBER_MISMATCH with ErrorId 4010; the FragmentTimecode/FragmentNumber members, when present, are values from the request and the service's state.
Emulator: the undeclared-track container is answered HTTP 200 (correct) but the acknowledgement stream carries ErrorCode FRAGMENT_TIMECODE_LESSER_THAN_PREVIOUS with ErrorId 4004 — the Cause 1 fault — and never TRACK_NUMBER_MISMATCH/4010. Replay: "AssertionError: expected the ingest error ('TRACK_NUMBER_MISMATCH', 4010), got ('FRAGMENT_TIMECODE_LESSER_THAN_PREVIOUS', 4004)". Hypothesis: the ingest container validation does not cross-check each SimpleBlock's track number against the TrackNumbers declared in Tracks at all, so with Cause 1 fixed this session would be accepted and the undeclared-track fragment would persist; the recorded evidence establishes only that 4010 is never produced for this container.
Why: a producer with a muxer/track-mapping bug (a block written on a track that was never declared) is told nothing about it, or is told the wrong thing: TRACK_NUMBER_MISMATCH/4010 is the signal that makes a producer fix its container, and 4004 points it at timestamps instead. Worse, if the fragment is accepted, the archive holds a fragment whose block references a track no reader can resolve, and GetMedia/GetMediaForFragmentList serve media no decoder can play.
Fix: the /putMedia handler's container validation — parse the Tracks element, collect the declared TrackNumbers, and reject any Cluster whose SimpleBlock/BlockGroup names a track outside that set with an in-band ERROR acknowledgement TRACK_NUMBER_MISMATCH / ErrorId 4010 inside the 200 response, persisting nothing for that fragment.
Traces: kinesisvideo.putmedia-block-on-undeclared-track-rejected.
