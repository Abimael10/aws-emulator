# apigatewayv2: CreateApi publishes ApiEndpoint as an `<api-id>.execute-api.<region>.localhost:<port>` host the emulator does not answer on, so the AppConfig-GetConfiguration AWS_PROXY subtype is never graded (1 cause)

> _Note: this issue was identified against the code base at commit `ec22e48eafa5e4290d9bdfafda3d7e5b1d68564a`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
CreateApi

## Description
1 net-new root cause on the apigatewayv2 surface, grounded in the one failing behavioral check the suite marked neither ALREADY FILED nor OWNED. Note on service attribution: the suite lists this check under the composite heading `### apigatewayv2__appconfig__iam__sts`; the defect itself is in the apigatewayv2 control-plane response for CreateApi, and the appconfig/iam/sts legs of the check all succeeded before it.

Cause 1 of 1: the invoke address apigatewayv2 publishes for an HTTP API names a host the emulator does not serve, so every request a client builds from ApiEndpoint leaves the emulator and the API is unreachable through its own published address. Failing check id: apigatewayv2__appconfig__iam__sts.appconfig-getconfiguration-proxy-missing-parameter-mapping-refused-else-returns-configuration.

AWS: Smithy apigatewayv2 CreateApi — POST /v2/apis, success code 201; CreateApiResponse.ApiEndpoint (target __string, jsonName apiEndpoint) is returned next to ApiId (target Id, jsonName apiId); GetApi returns the same member. For an HTTP API with a `$default` stage AWS publishes it as `https://{ApiId}.execute-api.{region}.amazonaws.com` — a name the execute-api data plane actually answers on, so `{ApiEndpoint}/<path>` is a working invoke URL. The requirement is structural and twofold: the value is an address with no port and whose authority identifies the API, AND the emulator answers on exactly the address it publishes. The model documents nothing further about the string, so the serving requirement is recorded behavior only: `{ApiId}` and `{region}` are values taken from the request and from state, the `https://` scheme and the `.execute-api.<region>` structure are the fixed parts, and no single run's id, host or port is itself part of the requirement.

Emulator: CreateApi answers 201 and returns ApiEndpoint = `https://<api-id>.execute-api.<region>.localhost:<port>` (one run: `https://mp67t4dbd4.execute-api.us-west-2.localhost:44031` — the id `mp67t4dbd4`, the region, and the port `44031` are per-run values and are not the requirement). That authority is not one of the emulator's own hosts and not the port it is reached on (the emulator's listener in that run was `127.0.0.1:36893`), so the published address is dead: building the stage URL from it is refused before any request is sent — `simparity.published.PublishedUrlRejected: endpoint_url was given https://mp67t4dbd4.execute-api.us-west-2.localhost:44031 (published by the emulator or built by the check): its host is not one of the emulator's own hosts; a customer of the emulator needs http(s)://127.0.0.1:<port>/<resource path>, or http(s)://<own host>:<port>/<path> on a per-resource listener`. No status, error code or error message is involved: CreateApi succeeded and only the published address diverges. Because the whole data-plane leg hangs off that address, the positive half of this check — a `GET /config` route on an `AWS_PROXY` integration with IntegrationSubtype `AppConfig-GetConfiguration` and all four of Application/Environment/Configuration/ClientId mapped, which must answer 200 with exactly the deployed hosted configuration content and echo `Content-Type: application/json` — is never graded at all. The negative half of the same check (CreateIntegration refusing the subtype with `RequestParameters={}` with `BadRequestException` and the message `Operation: AppConfig-GetConfiguration requires enabling passthrough, or defining all of the following parameters in the parameter mapping: [Application, Environment, Configuration, ClientId]` — fixed text whose only variable part is the subtype name) passed in this run, so the divergence is isolated to the published invoke address.

Why: a client takes ApiEndpoint (or `Fn::GetAtt ApiEndpoint`) verbatim as the base of every invoke URL, and SigV4 host signing, the Host/SNI value and any DNS or custom-domain mapping all key off that authority. Published as a `.localhost:<port>` authority the emulator does not bind, every generated client, importer, curl and integration test built against the emulator's own answer fails to connect, so an API that was created successfully can never be invoked through the address the service told the client to use — and no behavior behind the data plane (here, an AppConfig-GetConfiguration subtype integration) can be exercised.

Fix: the apigatewayv2 control-plane serializer that computes ApiEndpoint for CreateApi/GetApi (and the `Fn::GetAtt ApiEndpoint` path that mirrors it) must derive the authority from the address the emulator actually serves this API on — the request's Host, or the configured data listener plus its execute-api route, or a per-API listener it really binds — rather than templating a synthetic `<api-id>.execute-api.<region>.localhost:<port>` name; alternatively the execute-api front door must bind and serve the host it announces, so announcement and service agree.
