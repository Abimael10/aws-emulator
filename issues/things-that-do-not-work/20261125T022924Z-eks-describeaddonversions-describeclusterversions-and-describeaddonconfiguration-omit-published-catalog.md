# eks DescribeAddonVersions, DescribeClusterVersions and DescribeAddonConfiguration omit published catalog rows (5 causes)

> _Note: this issue was identified against the code base at commit `e1a20d446b2578340370dda6b22d020378cd7235`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Description
FIVE net-new root causes in the eks service, all found by replaying the wire fixture corpus (trace set simparity-wire-aws-v1) against the emulator built from this checkout. All five divergence clusters are reported UNOWNED by the replay (owned_by empty, stub_path empty): no open issue carries their replay keys. They share one fault: EKS's three read-only catalog/discovery reads (DescribeAddonVersions, DescribeClusterVersions, DescribeAddonConfiguration) answer 200 with content the emulator synthesises rather than the catalog AWS publishes, so the published rows are absent at the indexes a client reads them from.

Adjacent open issues that do NOT cover these five causes (named so a fixer does not close them as duplicates): 20261124T092047Z-eks-describeaddonversions-serves-a-synthesised-add-on-release.md covers the per-release addonVersions history INSIDE a correctly selected record (key keys=$.addons[0].addonVersions[0],$.addons[0].addonVersions[1]); 20261121T151648Z-eks-describeaddonversions-catalog-record-selection-and-registercluster-invalid.md carries the RegisterCluster message key and is reported by this replay as owning only that cluster, NOT the DescribeAddonVersions clusters below; 20261117T115837Z-eks-iam-describeaddonconfiguration-s-podidentityconfiguration-recommends-the-wrong.md covers the recommendedManagedPolicies of the CloudWatch-agent and EBS-CSI add-ons (behavioral corpus), not the EFS-CSI schema/pod-identity payload in Causes 4 and 5. The resolved issue 20261123T162615Z-eks-read-only-catalog-and-schema-discovery-reads.md is in the resolved folder and therefore covers nothing: these clusters are a recurrence.

Cause 1 of 5: for a multi-add-on filtered DescribeAddonVersions query, the add-on record the catalog publishes at addons[0] is not served at all, across 82 steps.
  AWS: DescribeAddonVersions is GET /addons/supported-versions, HTTP 200, with kubernetesVersion, addonName, types, publishers, owners, maxResults and nextToken all bound @httpQuery, @paginated items=addons, errors InvalidParameterException 400 / ResourceNotFoundException 404 / ServerException 500 (Smithy: services/service-com-amazonaws-eks-awswesleyfrontend/smithy-model/com-amazonaws-eks-awswesleyfrontend.json). Each addons element is an AddonInfo (addonName, type, addonVersions : AddonVersionInfoList, publisher, owner, marketplaceInformation, defaultNamespace); the list is the published add-on catalog SELECTED by the request's filters and in the catalog's own order, so the record a client reads at a given index is the catalog's record for that filter set. No error class is at stake; the requirement is the payload's membership, order and content.
  Emulator: answers 200, but the catalog record the request selects is absent from the served list - for example an observability-type record (addonName/type/addonVersions/publisher/owner/defaultNamespace as the catalog publishes them) is expected at addons[0] and nothing matching it is served at that index. The replay clusters 82 steps of this one query family under this single key, so the defect is the served catalog's membership and ordering for filtered queries generally, not one row.
  Why: this listing is how a client discovers which add-ons exist and which versions may be installed on a given cluster version. With the selected records absent, an installer enumerating add-ons for a cluster never sees the ones AWS publishes, and CreateAddon/UpdateAddon naming a published add-on or version is refused as unknown.
  Fix: the add-on catalog data behind DescribeAddonVersions and that handler's filter selection/projection in the eks service crate - the response must be built by selecting rows from the published catalog by kubernetesVersion/addonName/types/publishers/owners, preserving the catalog's record set and order, rather than synthesising records.
  Traces: eks-catalog-describe-addon-versions-accuknox-kubearmor-eg-innovations-eg-universal-agent-operator#task#2 (representative; 82 affected steps in the cluster).

Cause 2 of 5: a storage-type filtered DescribeAddonVersions query serves neither the catalog's record at addons[0] nor that record's Marketplace productUrl.
  AWS: same operation and shapes as Cause 1. For a Marketplace-owned add-on, AddonInfo.marketplaceInformation is a MarketplaceInformation whose productId is documented as "The product ID from the Amazon Web Services Marketplace" and productUrl as "The product URL from the Amazon Web Services Marketplace" - i.e. the catalog's published URL for that product id, not a locally composed URL form.
  Emulator: answers 200 with a different record at addons[0] than the catalog's storage record for that filter (the published record, with its own type, publisher/owner, defaultNamespace and multi-release addonVersions whose compatibilities span the older cluster versions, is absent), and where a Marketplace record is served its marketplaceInformation.productUrl is a different URL form than the catalog publishes for the same productId.
  Why: an installer filtering by type/owner never sees the Marketplace add-ons AWS publishes, so it cannot install them; and a client following marketplaceInformation.productUrl for a subscription or licence check lands on a URL that does not identify the product.
  Fix: the same add-on catalog data and filter selection as Cause 1, plus the MarketplaceInformation projection - productUrl must be the catalog's published URL for the record's productId rather than a URL the handler composes.
  Traces: eks-catalog-describe-addon-versions-eks-node-monitoring-agent-vpc-cni#task#20 (representative; 1 affected step).

Cause 3 of 5: DescribeClusterVersions serves none of the catalog's cluster-version rows - every row of the first page diverges.
  AWS: DescribeClusterVersions is GET /cluster-versions, HTTP 200, with clusterType, maxResults (range 1..100), nextToken, defaultOnly, includeAll, clusterVersions and versionStatus (plus the deprecated status) bound @httpQuery, @paginated items=clusterVersions, errors InvalidParameterException 400 / InvalidRequestException 400 / ServerException 500 (same model file). Each element is a ClusterVersionInformation carrying clusterVersion, clusterType, defaultPlatformVersion, defaultVersion (Boolean @default false), releaseDate, endOfStandardSupportDate, endOfExtendedSupportDate, status, versionStatus, kubernetesPatchVersion, controlPlaneScalingTiers (ControlPlaneScalingTierList, @length 0..10) and controlPlaneComponentConfig - the service's published support calendar and control-plane sizing data for each Kubernetes release, one row per release.
  Emulator: answers 200, but the replay reports clusterVersions[0] through clusterVersions[6] - the entire first page - as missing: not one published row is served. The expected rows carry the full member set (a Kubernetes release with its clusterType, defaultPlatformVersion, defaultVersion flag, releaseDate / endOfStandardSupportDate / endOfExtendedSupportDate timestamps, versionStatus and the deprecated status mirroring it, kubernetesPatchVersion, and controlPlaneScalingTiers each with tierName, apiRequestConcurrency, podSchedulingRatePerSecond, clusterDatabaseSizeGb and controlPlaneComponentConfigOverrides); what is served at those indexes does not match the catalog.
  Why: this read is the canonical source for which Kubernetes versions a cluster may be created or upgraded to, which one is default, when each leaves standard support and which control-plane scaling tiers exist. With the rows absent, a client cannot resolve the default release (the documented first step for sizing or add-on resolution), cannot plan an upgrade against the support calendar, and sees no scaling tiers at all.
  Fix: the cluster-version catalog data behind DescribeClusterVersions and that handler's row projection/pagination in the eks service crate - rows must come from the published cluster-version catalog with every modeled member populated (including the deprecated status mirroring versionStatus and the controlPlaneScalingTiers / controlPlaneComponentConfig trees), filtered by clusterType/clusterVersions/defaultOnly/includeAll/versionStatus.
  Traces: eks-catalog-describe-cluster-versions#task#1 (representative; 1 affected step).

Cause 4 of 5: DescribeAddonConfiguration serves a configurationSchema that is not the add-on build's published JSON schema, and its podIdentityConfiguration omits/alters the second service-account entry.
  AWS: DescribeAddonConfiguration is GET /addons/configuration-schemas with addonName and addonVersion both @required @httpQuery, HTTP 200, errors InvalidParameterException 400 / ResourceNotFoundException 404 / ServerException 500 (same model file). Output members are addonName, addonVersion, configurationSchema - documented as "A JSON schema that's used to validate the configuration values you provide when an add-on is created or updated" - and podIdentityConfiguration : AddonPodIdentityConfigurationList, each AddonPodIdentityConfiguration being {serviceAccount, recommendedManagedPolicies}. The model does not enumerate the schema text, so: recorded behavior only - the schema is the exact JSON-schema document the requested add-on BUILD publishes, keyed by the (addonName, addonVersion) pair, and it differs between builds of the same add-on: for the EFS-CSI driver build in this step the driver's access-point cleanup property is declared INSIDE the controller object's properties alongside that object's logLevel/nodeSelector/podAnnotations/tolerations, with the FIPS switch at the document's top level; and the response names one AddonPodIdentityConfiguration per service account the add-on uses (the driver's controller and node service accounts), each with its own recommendedManagedPolicies.
  Emulator: answers 200 with a configurationSchema whose property placement differs from the published document for that build (the replay reports $.configurationSchema value_mismatch: the served document begins with the same $schema declaration but its property tree is not the build's), and additionally diverges at $.podIdentityConfiguration[1] - the second service-account entry the recorded response carries is not served as recorded.
  Why: a client validates its add-on configuration against this schema before calling CreateAddon/UpdateAddon. A schema that places a property at a different level than the build accepts makes a valid configuration fail client-side validation (or lets an invalid one through, to be refused by CreateAddon), and a missing or altered pod-identity entry means the IAM roles a client provisions from this response do not cover every service account the add-on runs under.
  Fix: the add-on configuration catalog behind DescribeAddonConfiguration in the eks service crate - the configurationSchema and podIdentityConfiguration must be looked up per (addonName, addonVersion) from the published per-build documents rather than composed from a single version-independent template.
  Traces: eks-efsfips-traj-catalog-and-schema-discovery#task#1 (representative; 1 affected step).

Cause 5 of 5: the same read serves the same schema for a DIFFERENT build of the add-on, so the per-build schema variant is lost.
  AWS: same operation, members and "recorded behavior only" basis as Cause 4. For this second build of the same add-on the published document places the access-point cleanup property at the document's TOP level (not inside the controller object, whose properties then carry only logLevel/nodeSelector/podAnnotations/tolerations), with the FIPS switch again at top level - i.e. addonVersion selects the schema, and two builds of one add-on legitimately publish different property trees.
  Emulator: answers 200 with a configurationSchema that does not match this build's published document either (replay reports $.configurationSchema value_mismatch with the served document again opening on the same $schema declaration), which is the signature of addonVersion not participating in the lookup: one schema is served whatever build is asked for, so at most one build can ever be right.
  Why: a client that pins an add-on version and validates its configuration against the schema for THAT version is validated against another version's rules, so a configuration the pinned build accepts is rejected locally and one it rejects is sent; version-aware upgrade tooling cannot tell that the configuration contract changed between builds.
  Fix: same component as Cause 4 - DescribeAddonConfiguration's handler must key its schema lookup on the required addonVersion as well as addonName, and the catalog must hold one document per published build.
  Traces: eks-efsfips-traj-catalog-and-schema-discovery#task#2 (representative; 2 affected steps, the other in eks-eks-catalog-read-only-discovery#task#3).
