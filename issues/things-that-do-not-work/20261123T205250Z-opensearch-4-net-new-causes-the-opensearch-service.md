# opensearch: 4 net-new causes — the OpenSearch service-linked-role principal es.amazonaws.com is refused 403 AccessDenied (blocks all nine VPC-endpoint checks), CreateDomain accepts a WarmCount below the warm-tier minimum and refuses the modeled t2.small.search on an OpenSearch release, and the unicode-analyzer CreateIndex check never reaches a verdict

## Operation
CreateServiceLinkedRole, CreateDomain, CreateIndex

## Description
Twelve behavioral checks listed under `### opensearch` fail for four distinct root causes. Every other failure in this replay is marked OWNED by an already-filed issue and is skipped. This issue carries FOUR causes; all four must be closed before submitting.

=== Cause 1 of 4: IAM refuses the OpenSearch service-linked-role principal `es.amazonaws.com`, so every VPC-endpoint check dies in setup (9 of the 12 grounded checks) ===
Failing checks: opensearch.concurrency-update-vpc-endpoint-optimistic-lock, opensearch.data-plane-vpc-endpoints-for-domain-listing-accuracy, opensearch.overly-permissive-vpc-endpoint-update-invalid-security-group-rejected, opensearch.update-vpc-endpoint-conflict-on-concurrent-modify-rejected, opensearch.update-vpc-endpoint-out-of-range-config-rejected, opensearch.vpc-endpoint-access-lifecycle, opensearch.vpc-endpoint-lifecycle, opensearch.vpc-endpoint-list-and-delete-lifecycle-observed, opensearch.vpc-endpoint-update-and-domain-listing.
AWS: an OpenSearch VPC-access domain needs the OpenSearch service-linked role, and AWS's own OpenSearch VPC documentation has a caller create it with `AWSServiceName=es.amazonaws.com`; AWS accepts that principal and answers HTTP 200 with `Role` describing a role whose `Path` is the reserved service-linked-role path for that principal (`/aws-service-role/es.amazonaws.com/`). Smithy (iam): CreateServiceLinkedRole input `AWSServiceName` (groupNameType, len 1..128, pattern ^[\w+=,.@-]+$) is the only required member, and the operation declares exactly four errors — InvalidInputException (400/InvalidInput), LimitExceededException (409), NoSuchEntityException (404), ServiceFailureException (500). `AccessDenied` is NOT a declared error of this operation at all. Beyond that the model says nothing about which principals publish a role, so which principals are accepted is recorded behavior only: each of the nine recordings calls CreateServiceLinkedRole with es.amazonaws.com and proceeds to CreateDomain/CreateVpcEndpoint, i.e. AWS accepted it (or reported it already existing) and never refused it.
Emulator: answers 403 `AccessDenied` with message `es.amazonaws.com is not a valid AWS service name (Service Principal)`. The fixed text of that message is the emulator's own prose; the variable part is the request's AWSServiceName. The cause is the registry of principals that publish a service-linked role: it carries the row ("opensearchservice.amazonaws.com", "AWSServiceRoleForAmazonOpenSearchService") but no row for the equally valid `es.amazonaws.com`, and the handler turns a missing row into 403 AccessDenied.
Why: a client that follows AWS's documented OpenSearch VPC setup cannot create the role at all, and botocore raises on a status/code the operation does not model. In this suite it means the whole service-managed VPC-endpoint surface (CreateVpcEndpoint, UpdateVpcEndpoint, DescribeVpcEndpoints, ListVpcEndpoints, ListVpcEndpointsForDomain, DeleteVpcEndpoint, the optimistic-lock ConflictException and the invalid-security-group/out-of-range refusals) is never exercised: nine checks error before their first OpenSearch call, so the emulator's answers for those operations are unverified.
Fix: the iam crate's published-service-linked-role registry — `crate::state::PUBLISHED_SERVICE_LINKED_ROLE_NAMES` / `published_service_linked_role_name` — and the role/policy tables keyed by the same principal, consumed by the CreateServiceLinkedRole handler. Hypothesis: add the `es.amazonaws.com` row (AWS publishes `AWSServiceRoleForAmazonElasticsearchService` for that principal, the legacy spelling of the OpenSearch VPC role; the fixer should confirm the exact published name) so the create mints a role under `/aws-service-role/es.amazonaws.com/` and returns 200. Note that no open issue covers this; the only CreateServiceLinkedRole-adjacent issue is 20261029T234938Z-iam-deleteservicelinkedrole-answers-404-nosuchentity-for-an-existing.md, which is about DeleteServiceLinkedRole on an existing role.
Traces: the nine check ids above. Code: services/service-com-amazonaws-iam-awsidentitymanagementv20100508/src/ops/create_service_linked_role.rs lines 200-216 (missing row -> Scaffolded::access_denied / not_a_valid_service_name); src/state.rs lines 1993-2206 (the registry) and 2147-2149 (the opensearchservice.amazonaws.com row, the only OpenSearch principal present).

=== Cause 2 of 4: CreateDomain accepts a WarmCount below the warm-tier minimum ===
Failing check: opensearch.overly-permissive-storage-tier-dependency-rules.
AWS: `ClusterConfig$WarmCount` ("the number of warm nodes in the cluster") carries NO modeled range, so this bound exists only in the service's own validation — recorded behavior: AWS refuses a CreateDomain whose cluster enables the warm tier with a warm node count outside the service bound, with HTTP 400 ValidationException and the message `Warm storage node count must be between 2 and 150.` (fixed text throughout; the two numbers are the service's published warm-node bounds, not values from the request), and creates nothing. The recording's sibling negatives on the same chain — ColdStorage without UltraWarm (BaseException, "To use cold storage, you must have UltraWarm enabled."), UltraWarm without dedicated masters, UltraWarm on an unsupported instance family — already pass, so only the count bound is missing.
Emulator: accepts the request and provisions the domain; CreateDomain answers 200 with a DomainStatus for a cluster carrying WarmEnabled=true and WarmCount=1, and the domain is subsequently readable by DescribeDomain. The emulator already knows the bound — `WARM_NODE_COUNT_RANGE = 2..=150` is what DescribeInstanceTypeLimits publishes for the ultrawarm role — but the create path never applies it.
Why: a client that mis-sizes its warm tier gets a cluster AWS would have refused, and a caller that depends on the refusal to fail fast (a template validator, an UltraWarm sizing wizard) sees a success and then diverges from AWS for the rest of the domain's life; the asserted effect-absence (DescribeDomain -> ResourceNotFoundException after the refusal) is also lost.
Fix: the CreateDomain handler's cluster-configuration refusal chain (and the matching UpdateDomainConfig path, so both judge alike), beside the existing warm-tier rules: apply the warm-node count bound already held in state next to `warm_instance_type_refusal`/`warm_storage_refusal`.
Traces: opensearch.overly-permissive-storage-tier-dependency-rules. Code: services/service-com-amazonaws-opensearch-amazonopensearchservice/src/ops/create_domain.rs lines 649-657 (the refusal list: access policies, warm_instance_type_refusal, security groups, EBS performance — no warm-count rule); src/state/instance_types.rs line 1104 (WARM_NODE_COUNT_RANGE = 2..=150) and lines 1356-1372 (where that range is only published, via role_limits).

=== Cause 3 of 4: CreateDomain refuses the modeled instance type t2.small.search on an OpenSearch release ===
Failing check: opensearch.start-migration-invalid-source-version-rejected.
AWS: `t2.small.search` is a declared value of `OpenSearchPartitionInstanceType` (the enum CreateDomain's ClusterConfig$InstanceType targets). The model states no engine-release restriction for it, so which releases offer it is recorded behavior only: the recording creates BOTH an `Elasticsearch_1.5` and an `OpenSearch_2.11` single-node domain with `ClusterConfig.InstanceType = t2.small.search` and gp2/10 GiB EBS, and both CreateDomain calls succeed (the check then goes on to assert StartMigration's ValidationException for each domain ARN).
Emulator: refuses with `InvalidTypeException` (modeled client error, HTTP 409) and message `Invalid instance type: t2.small.search` — fixed text `Invalid instance type: ` plus the instance type from the request. The refusal comes from the per-release instance-type catalog, which marks the whole t2 family `OfferedReleases::ElasticsearchOnly`, so no OpenSearch release offers t2.* at all and the `OpenSearch_2.11` create is rejected before anything is stored.
Why: a client whose domain runs a previous-generation burstable type AWS still offers cannot create it, and the refusal is a 409 on an operation the caller had every reason to expect 200 from. Here it also means the check's actual subject is never reached: StartMigration is never called with a managed-domain ARN, so the collection-ARN-pattern ValidationException and the empty ListMigrations are unverified. (StartMigration itself is an unimplemented scaffold stub already filed as 20261027T004336Z-opensearch-startmigration-stub.md; that issue does not cover this CreateDomain refusal, and this check cannot reach it until this cause is fixed.)
Fix: the per-release instance-type catalog the create path consults — the t2 family's `releases` classification, read through `offers_instance_type` / `cluster_instance_type_refusal`.
Traces: opensearch.start-migration-invalid-source-version-rejected. Code: services/service-com-amazonaws-opensearch-amazonopensearchservice/src/state/instance_types.rs lines 759-769 (the t2 CatalogFamily, OfferedReleases::ElasticsearchOnly), lines 835-842 (offers_instance_type), lines 1935-1939 (invalid_instance_type message) and lines 2171-2179 (cluster_instance_type_refusal); src/ops/create_domain.rs lines 516-523 (where CreateDomain applies it).

=== Cause 4 of 4: the unicode custom-analyzer CreateIndex check never reaches a verdict — a seventh chained-wait check lost to the wall-clock transient window ===
Failing check: opensearch.index-settings-unicode-analyzer-rejected (Error: Check timed out after 60.0s).
AWS: CreateIndex with a NON-ASCII custom-analyzer name in IndexSchema is refused with a sustained `DependencyFailureException` and message `The domain is not available now, please try again later.` (fixed text, no variable part), while the byte-identical schema with an ASCII analyzer name on the same domain is CREATED and round-trips through GetIndex/UpdateIndex/DeleteIndex (GetIndex not-found message `Resource index <index-name> does not exist`, the index name taken from the request). Recorded behavior: against AWS the check completes its domain wait and reaches those assertions.
Emulator: the check makes it through none of them inside the budget. The domain readiness wait polls DescribeDomain every 30 s until `Processing=false` with a published `Endpoint`; because a domain's provisioning status is held for a WALL-CLOCK span (`state::DOMAIN_WORK`) and only materialised to its terminal value once that span has elapsed, the client's first probe — issued immediately after CreateDomain — always reads Processing=true and it then sleeps a full 30 s of the 60 s budget before it can see the terminal value. That is exactly the root cause already filed as 20261121T121321Z-opensearch-wall-clock-transient-windows-cost-a-client.md, whose Issue-Trace-Ids list six check ids and does NOT include this one, so it is filed here rather than assumed covered. Hypothesis: with the transient status reachable on the NEXT read rather than after a fixed span, this check reaches its CreateIndex arms instead of spending half its budget in one sleep; the fixer should re-replay this id after that change, and if the check still does not reach a verdict, the remaining budget is spent in the check's own refusal-confirmation sleeps rather than in an emulator wait, which is worth reporting back rather than patching around.
Why: a client provisioning a domain pays one full poll interval per state change no matter how fast it polls, and here the entire unicode-analyzer-name refusal class plus the CreateIndex/GetIndex/UpdateIndex/DeleteIndex round trip on the same domain go unverified.
Fix: the lifecycle state the control plane materialises transient statuses from (`state::DOMAIN_WORK` and the `Domain::settle` path that consumes its due instant) — gate the transition on observation rather than on wall clock.
Traces: opensearch.index-settings-unicode-analyzer-rejected. Code: services/service-com-amazonaws-opensearch-amazonopensearchservice/src/state.rs (DOMAIN_WORK span) and src/state/domains.rs (Domain::settle), as cited in 20261121T121321Z-opensearch-wall-clock-transient-windows-cost-a-client.md.
