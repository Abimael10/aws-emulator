# scn data-integration plane serves hollow flow and event projections and keeps a deleted flow readable

> _Note: this issue was identified against the code base at commit `d33d509d5311768bd1282d02eb2794d638dad9b8`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
GetDataIntegrationFlow

## Description
FOUR (4) net-new divergence clusters on AWS Supply Chain (wire service token `scn`; sdkId `SupplyChain`, endpointPrefix/arnNamespace/sigv4Name `scn`, served by the bootstrapped crate `services/service-com-amazonaws-supplychain-galaxypublicapigateway`, so these are fidelity findings and not a bootstrap gap). They share ONE fault: the DATA-INTEGRATION plane answers 2xx from state that was never written or is only partly projected — the flow read hands back a flow stripped of its managed/trigger/dataset identity and of its SQL transformation, the event listing hands back an empty page for an instance that has been sent an event, and a flow that has been DELETED keeps answering 200 instead of the modeled 404. A fixer MUST close ALL FOUR causes before submitting; each is listed below with its own fixture#step, and all four bindings are carried on this issue so each one gets re-replayed.

Cause 1 of 4 — GetDataIntegrationFlow answers 200 for a flow that was deleted (fixture `supplychain-data-integration-flow-dataset-target`, step `task#9`; the same cluster also covers `supplychain-data-integration-flow-s3#task#13`). AWS: GetDataIntegrationFlow is GET /api/data-integration/instance/{instanceId}/data-integration-flows/{name}, @readonly, SUCCESS_STATUS 200, output {flow: DataIntegrationFlow @required}; it declares ResourceNotFoundException @httpError 404, documented "Request references a resource which does not exist" (Smithy: input {instanceId UUID @httpLabel @required @pattern ^[a-f0-9]{8}-...$, name DataIntegrationFlowName @httpLabel @required @pattern ^[A-Za-z0-9-]+$}; errors ResourceNotFoundException 404, AccessDeniedException 403, ValidationException 400, ConflictException 409, ServiceQuotaExceededException 402, ThrottlingException 429, InternalServerException 500). DeleteDataIntegrationFlow is DELETE on that same URI, @idempotent, 200 — after it the flow is no longer readable, and the recorded response for this read is HTTP 404 carrying the restJson1 `x-amzn-errortype` header and a `message` whose FIXED text is "Flow " + " does not exist in instance " and whose VARIABLE parts are exactly two: the flow name from the request's `name` @httpLabel and the instance id from the request's `instanceId` @httpLabel (no other value appears in it). Emulator: HTTP 200 with the full flow body, `$.message` absent, `$headers.x-amzn-errortype` absent. Note that the sentence the emulator WOULD emit on its 404 branch is also wrong: the read returns the fixed constant `crate::state::FLOW_NOT_FOUND_MESSAGE` = "Flow not found.", which echoes neither name nor instance — its own doc comment says it was guessed from the not-found family and must be re-verified against a recording, and this recording is that evidence. Why: a client cannot distinguish a deleted flow from a live one; delete appears to do nothing, "wait until gone" polls never terminate, re-create-after-delete is refused as a conflict against a ghost record, and the client is handed a pipeline definition for a resource the service has said is gone. Fix: DeleteDataIntegrationFlow's handler must mutate state (remove the (instanceId, name) entry from the store's `flows` map) so GetDataIntegrationFlow's existing lookup misses, and GetDataIntegrationFlow's not-found message must render AWS's name-and-instance template above instead of the fixed sentence in the state module. Hypothesis: the 200 appears because the preceding delete is still a scaffolded 501, so nothing is ever removed.

Cause 2 of 4 — ListDataIntegrationEvents answers 200 with an EMPTY events list for an instance that has been sent an event (fixture `supplychain-data-integration-events`, step `task#5`). AWS: ListDataIntegrationEvents is GET /api-data/data-integration/instance/{instanceId}/data-integration-events, @readonly, 200, output {events: DataIntegrationEventList @required, nextToken}, @paginated(items: events, pageSize: maxResults @range 1..20 @default 10) (Smithy). An event accepted by SendDataIntegrationEvent for that instance is thereafter listed: the recorded page's first element is a DataIntegrationEvent carrying `instanceId`, `eventId` (the id the send returned), `eventType` (the DataIntegrationEventType value sent, e.g. a `scn.data.*` enum member), `eventGroupId` (the group id sent), `eventTimestamp`, and — for an event that targets a data-lake dataset — `datasetTargetDetails` with `operationType` APPEND and `datasetLoadExecution.status` SUCCEEDED (Smithy: DataIntegrationEvent members instanceId/eventId/eventType/eventGroupId/eventTimestamp all @required, datasetTargetDetails optional; DataIntegrationEventDatasetTargetDetails requires datasetIdentifier, operationType, datasetLoadExecution). Emulator: HTTP 200 with `$.events` empty — `$.events[0]` is absent entirely. Why: the whole data-integration ingest loop is unobservable. A client that sends an event and then polls the listing (or GetDataIntegrationEvent) to confirm ingest and read `datasetLoadExecution.status` never sees its event, so it cannot tell acceptance from loss and retries forever or reports a false failure. Fix: belongs in SendDataIntegrationEvent's handler and the service state — the send must persist a `DataIntegrationEventRecord` under `data_integration_event_key(instanceId, eventId)` in the store's `events` map (the record type, the key helper, the per-instance capacity check `data_integration_events_at_capacity` and the `drop_instance_events` reclamation all already exist in the state module) and populate `dataset_target_details` for a dataset-targeted event; ListDataIntegrationEvents' paging already projects whatever records exist via `to_wire`. Hypothesis: the listing is empty because SendDataIntegrationEvent is still a scaffolded 501 and never inserts.

Cause 3 of 4 — GetDataIntegrationFlow's flow projection omits the flow's managed/trigger members and its dataset source/target identity (fixture `supplychain-data-integration-flow-dataset-target`, step `task#7`; the same cluster also covers `supplychain-data-integration-flow-s3#task#7`). AWS: recorded behavior only for these members — the on-disk model (version 2024-01-01) defines DataIntegrationFlow as {instanceId, name, sources, transformation, target, createdTime, lastModifiedTime} with no `managedBy` and no `triggerOptions`, and its DataIntegrationFlowDatasetSourceConfiguration / DataIntegrationFlowDatasetTargetConfiguration carry `datasetIdentifier` rather than `datasetId`/`datasetType`. The recording shows the live service returning a WIDER flow projection: `flow.managedBy` = CUSTOMER for a customer-created flow, `flow.triggerOptions` present with `triggerType` SOURCE_CHANGE (and scheduleConfiguration/scheduleState null when the trigger is source-change), and each dataset end described by `datasetSource`/`datasetTarget` objects carrying `datasetId` and `datasetType` CUSTOM for a dataset in a customer namespace. Emulator: every one of those members is absent from the 200 body (`$.flow.managedBy`, `$.flow.triggerOptions`, `$.flow.sources[0].datasetSource.datasetId`, `$.flow.sources[0].datasetSource.datasetType`, `$.flow.target.datasetTarget.datasetId`, `$.flow.target.datasetTarget.datasetType` all got None). Why: a client that reads a flow back to decide how it is triggered, whether it is customer- or service-managed, or which dataset it reads and writes gets null for all of it, so round-tripping a flow definition through the read is lossy and any client branching on managedBy/triggerType takes the wrong branch. Fix: the flow wire types and GetDataIntegrationFlow's projection (the record-to-wire mapping in the state module, which today copies only the stored sources/transformation/target/timestamps) must carry the managed-by and trigger-options members and the dataset end's id/type members.

Cause 4 of 4 — GetDataIntegrationFlow loses the flow's SQL transformation, reporting transformationType NONE (fixture `supplychain-data-integration-flow-s3`, step `task#10`). AWS: DataIntegrationFlowTransformation = {transformationType: DataIntegrationFlowTransformationType @required (enum SQL | NONE), sqlTransformation: DataIntegrationFlowSQLTransformationConfiguration} (Smithy). A flow whose transformation is SQL reads back with transformationType SQL and the `sqlTransformation` configuration holding the query the flow was defined with (the recording's query text is that fixture's value, not part of the requirement); the same read also omits the managedBy/triggerOptions/dataset-identity members described in cause 3. Emulator: `$.flow.transformation.transformationType` = NONE and `$.flow.transformation.sqlTransformation` absent, i.e. the SQL definition the flow carries is not reflected at all. Why: a client that reads a flow back sees an untransformed pass-through pipeline where a SQL transformation is configured, so it cannot verify or re-apply its own definition, and a config-drift check reports a difference that does not exist. Fix: the flow's transformation must survive the write path and the read projection — UpdateDataIntegrationFlow must apply the submitted `transformation` (and sources/target) to the stored record and bump lastModifiedTime, and GetDataIntegrationFlow's projection must emit transformationType plus the matching configuration member. Hypothesis: the NONE comes from the create-time value never being replaced, because UpdateDataIntegrationFlow is still a scaffolded 501 and mutates nothing.
