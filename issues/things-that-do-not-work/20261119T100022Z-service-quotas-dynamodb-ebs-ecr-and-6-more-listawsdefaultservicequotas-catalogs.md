# dynamodb, ebs, ecr and 6 more ListAWSDefaultServiceQuotas catalogs re-word Descriptions and misbind rows to the wrong QuotaCode

> _Note: this issue was identified against the code base at commit `e91c89e9d6482fa7ae1cb641524eb980150715bc`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
ListAWSDefaultServiceQuotas

## Description
9 net-new causes, one per ServiceCode. For all nine ServiceCodes the emulator DOES answer ListAWSDefaultServiceQuotas with HTTP 200 and a non-empty Quotas list, so this is a body-fidelity defect in the static default-quota catalog, not a missing operation. Two sub-defects recur: (a) the Description (and sometimes QuotaName) member is re-written in the emulator's own house style instead of carrying the text AWS publishes for that quota, and (b) whole rows are MISBOUND — the row is served under one QuotaCode while its QuotaName/Value/Adjustable/Unit/Period/UsageMetric payload belongs to a different quota, so the catalog is effectively shifted against its keys. Each ServiceCode's catalog is a distinct cause and must be closed separately.

AWS (common to all 9 causes): Smithy ListAWSDefaultServiceQuotas(ServiceCode required, @length 1..63, @pattern ^[a-zA-Z][a-zA-Z0-9-]{1,63}$; NextToken/MaxResults paginated on items Quotas) answers 200 with Quotas: list<ServiceQuota>. Smithy ServiceQuota members: ServiceCode, ServiceName, QuotaArn, QuotaCode (@length 1..128, @pattern ^[a-zA-Z][a-zA-Z0-9-]{1,128}$), QuotaName, Value (double @range 0..10000000000), Unit, Adjustable (boolean, default false, 'Indicates whether the quota value can be increased'), GlobalQuota (default false), UsageMetric (MetricInfo: MetricNamespace, MetricName, MetricDimensions, MetricStatisticRecommendation @pattern ^(Sum|Maximum)$), Period (QuotaPeriod: PeriodValue, PeriodUnit) and Description (@length 0..350, 'The quota description'). AWS returns one row per published default quota for the ServiceCode, and every member of a row — QuotaName, Value, Unit, Adjustable, Description, and Period/UsageMetric for rate quotas — belongs to the SAME QuotaCode. Which codes exist, their published Description text and their values are not stated by the model (recorded behavior only); the recordings are the reference. The requirement filed here is the BINDING between QuotaCode and the rest of the row, and that the published Description/QuotaName text is served verbatim rather than paraphrased — not any single recorded number from one run.

Emulator (common): HTTP 200 in every cluster (expected_status 200, actual_status 200 — body-only divergence), but rows report value_mismatch on Description/QuotaName/Value/Adjustable/Unit, Period and UsageMetric are `missing ... got None` on rate quotas that publish them, and on many codes the served QuotaName+Value+Adjustable triple is another quota's.

Why (common): a client that resolves a limit by QuotaCode reads another quota's name and value under the code it asked for, so it enforces, displays or reports the wrong limit while believing it read the right one. An inverted Adjustable tells the client a fixed quota can be raised (or that an adjustable one cannot), which is what decides whether RequestServiceQuotaIncrease is attempted at all. A missing Period/UsageMetric breaks usage-vs-quota dashboards that join the quota to its CloudWatch metric, and paraphrased Description/QuotaName text breaks consoles, reports and any assertion on the published wording.

Fix (common): the service-quotas crate's static default-quota catalog plus the ListAWSDefaultServiceQuotas row projection. Every row must be keyed by QuotaCode with QuotaName/Value/Unit/Adjustable/GlobalQuota/Description — and Period/UsageMetric where AWS publishes them — taken from the SAME catalog entry, and the published Description/QuotaName strings must be stored and serialized verbatim instead of being re-worded.
