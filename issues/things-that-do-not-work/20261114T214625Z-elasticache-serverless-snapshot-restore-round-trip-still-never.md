Cause 1 of 1: a serverless cache cannot be created, written to, snapshotted, deleted and restored inside a client's budget, so the persistence of data across a serverless snapshot/restore is never observable. Failing check: elasticache.e2e-serverless-snapshot-restore-flow.

Neither the first SET/GET pair on cache 1 (`assert replies == ['+OK', '$serverless-original-value']`) nor the restored GET on cache 2 (`assert restored_value == '$serverless-original-value'`) is reached. The flow chains four waits — cache 1 available (DescribeServerlessCaches, 2 s poll), snapshot available (DescribeServerlessCacheSnapshots, 2 s poll), cache 1 gone (15 s poll per probe expecting ServerlessCacheNotFoundFault), cache 2 available (2 s poll) — plus two in-VPC TLS RESP sessions whose `connect:` failures are retried for a 180 s window each. Mechanism still in this checkout: services/service-com-amazonaws-elasticache-amazonelasticachev9/src/state.rs:426 `pub const CLUSTER_TRANSITION: Duration = Duration::from_millis(500);` and :436 `pub const SNAPSHOT_TRANSITION: Duration = Duration::from_millis(500);`, with the doc comment at :414-425 stating the span "is deliberately NOT zero" and "The due instant is stored on the record and materialised by whichever later call reads it; a REPORT issued inside the span answers with the transient status, because nothing of this service sleeps for a transition it has scheduled" — so a client's first poll after each create/snapshot/delete observes the transient value and then sleeps its whole interval even though the emulator settled in 500 ms. Hypothesis: the two TLS sessions against an endpoint that accepts no TCP from inside the VPC (the sibling data-plane checks of this same replay report the emulator answering `connect: OSError: a Lambda function in this emulator has no host network to reach`) contribute the remainder of the wall clock; the two contributions cannot be separated from this output because no assertion fired, and whether CreateServerlessCache(SnapshotArnsToRestore=...) actually loads the snapshot's keyspace therefore remains unverified as well.

Why: snapshot-and-restore is the only way an ElastiCache Serverless client moves or recovers a dataset. Against this emulator a client cannot confirm that a serverless cache became available, that a snapshot completed, that the deleted cache really stopped resolving, or that the restored cache holds the pre-snapshot data. A run that dies at the budget is indistinguishable from a snapshot that never settles and from a restore that silently produces an empty cache, so a backup/restore runbook validated against the emulator proves nothing; SDK waiters and CI pipelines simply time out.

Fix: two components — (a) the status-settling path of the elasticache crate's state (the settle/materialise helpers around CLUSTER_TRANSITION / SNAPSHOT_TRANSITION), so DescribeServerlessCaches and DescribeServerlessCacheSnapshots report the settled status to the client's FIRST read once the transition instant has passed, and a deleted cache is absent (404 ServerlessCacheNotFoundFault) on the first poll after its deletion is due, while the create/snapshot/delete RESPONSE keeps reporting the transient status other checks assert; and (b) the CreateServerlessCache restore path (SnapshotArnsToRestore) together with the serverless data plane, so the emulator serves RESP on the Address:Port its ServerlessCache$Endpoint projection publishes and the restored cache really holds the snapshot's keyspace.
