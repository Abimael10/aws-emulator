# geo-maps GetSprites sprite index is generated from a synthetic uniform grid, so every icon box width/height/x/y diverges from the published sheet

> _Note: this issue was identified against the code base at commit `4ff3210f42e9a1596cde6d86bb6d66809acacb1e`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
GetSprites

## Description
GetSprites with FileName="sprites.json" must return the sprite-sheet INDEX that belongs to the requested published basemap sheet: a JSON object keyed by icon name, each value carrying that icon's real pixel box (width, height, x, y, pixelRatio) inside the companion sprites.png. The emulator instead synthesizes the index programmatically — it assigns every ordinary icon a single uniform box size and lays the icons out on its own fixed-pitch grid — so the whole index diverges from the sheet AWS publishes while still answering HTTP 200. This is 2 net-new divergence clusters sharing that one root cause; both are GetSprites, both at status 200->200, and they reproduce across different Style/ColorScheme/Variant combinations.

Cause 1 of 2: GetSprites sprites.json icon box DIMENSIONS are a constant instead of per-icon.
AWS: Smithy (services/service-com-amazonaws-geomaps-mapsservice) GetSprites — GET /v2/styles/{Style}/{ColorScheme}/{Variant}/sprites/{FileName}, FileName @pattern ^sprites(@2x)?\.(png|json)$, required httpLabel members Style (MapStyle enum), ColorScheme (ColorScheme enum), Variant (Variant enum); output is an httpPayload Blob plus Content-Type/Cache-Control/ETag headers, errors: []. The model does not describe the index's contents, so: recorded behavior only — the recording shows each icon's width/height is that icon's own size in the published sheet and therefore VARIES per icon (plain POI pins one size, the oneway arrow and the generic "other" glyph each a different, larger size, and each road-shield glyph its own size).
Emulator: every ordinary icon is emitted at one constant size and the specially sized glyphs are flattened to that same constant. In the recorded step the POI-pin family (marker, marker_arts_entertainment, marker_food_drink, marker_recreation, marker_stores_services, marker_transit) is expected 21x21 but served 24x32; oneway is expected 50x29 and served 21x21; other is expected 32x32 and served 21x21; and width/height diverge the same way for several hundred shield-* entries. The numbers quoted here are that one recording's values, not the requirement — the requirement is that each icon's box is the icon's OWN size in the sheet being served.
Why: a MapLibre/Mapbox-GL client reads sprites.json to cut each icon out of sprites.png. With a constant box size every icon is cropped to the wrong rectangle, so pins are stretched or clipped, the oneway arrow and the generic marker are truncated, and road shields render as fragments of neighbouring glyphs. The client cannot detect this — it gets a well-formed 200 index.
Fix: the GetSprites handler's sprites.json index construction (and the sprite-asset state it reads from) must carry the published sheet's per-icon geometry rather than deriving boxes from a constant.
Traces: geo-maps-sprites-style-color-variants#task#3.

Cause 2 of 2: GetSprites sprites.json icon PACKING OFFSETS (x/y) are generated by the emulator's own fixed-pitch layout, so they drift from the published sheet and the shield key set does not match it either.
AWS: same Smithy binding as Cause 1; recorded behavior only — the recording shows x/y are the icon's actual top-left position in the published sprites.png, which follows the sheet's real packing (non-uniform pitch, because the icons have different sizes), and the key set is exactly the icon names that sheet publishes.
Emulator: x (and for the shield entries y as well) is computed by stepping a constant pitch over the emulator's own icon ordering, so the offsets progressively drift away from the recorded ones across the alphabet — in the recorded step metro/money/monorail/museum/nature/nightclub x each run ahead of expected, then from other onward they run behind — and the drift propagates through every shield-* entry. The same step also shows whole-entry divergences where the emulator's name set differs from the sheet's (expected shield-AE, shield-BAB, shield-NL-ring are reported as whole-key mismatches, and the two fixtures disagree on shield-CA-TransCanada vs shield-CA:transcanada), i.e. the synthesized index invents its own icon-name list rather than serving the sheet's. Again, the specific offsets are the recording's values; the requirement is that x/y locate the icon in the sheet actually served and that the key set be the sheet's.
Why: offsets that drift mean each icon is sampled from a region of the PNG belonging to a different icon, so a renderer draws the wrong symbol — worse than a missing icon, because it looks plausible. Missing/renamed shield keys additionally make every route-shield lookup in the style descriptor fail, dropping highway shields from the map entirely.
Fix: same component — the GetSprites handler's sprites.json serializer and the sprite-asset state must emit the published sheet's own packing coordinates and icon names, keyed by the requested Style/ColorScheme/Variant, instead of a generated grid.
Traces: geo-maps-vector-basemap-style-workflow#task#3.

Relation to already-open work: the open issue "20261116T151333Z-maps-geo-synthesizes-published-basemap-assets-at-request" owns the GetGlyphs/GetSprites __wire_sha256__/__wire_length__ byte-level clusters (and the GetStyleDescriptor cluster), and the replay reports these two clusters as NOT owned by it. They are filed here because they are a distinct, independently verifiable defect: the JSON index's per-icon geometry and key set, which is wrong even where the index parses and the status matches.
