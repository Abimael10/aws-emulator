## Description

Cause 1 of 3: DeleteCapacityReservation's "not cancelled yet" refusal does not name the state it met.
  AWS: Smithy (services/service-com-amazonaws-athena-amazonathena/smithy-model/com-amazonaws-athena-amazonathena.json) — DeleteCapacityReservation.Name @required (target CapacityReservationName, @length 1..128, @pattern ^[a-zA-Z0-9._-]+$), @idempotent, empty output, errors InvalidRequestException (client, httpError 400) and InternalServerException (500); the operation doc states a reservation must be cancelled before it can be deleted. Recorded behavior: 400 InvalidRequestException with Message "Reservation state is <STATUS>. Reservation can only be deleted when state is CANCELLED". Fixed text: "Reservation state is " … ". Reservation can only be deleted when state is CANCELLED"; the ONE variable part is the reservation's current status read from service state (the check exercises ACTIVE, but PENDING / UPDATE_PENDING / CANCELLING must each report themselves). The refused delete must not take effect: the reservation stays readable and unchanged.
  Emulator: right status (400) and right code (InvalidRequestException), but Message "Reservation must be cancelled before it can be deleted" — a constant that borrows the operation's documentation sentence and names no state at all.
  Why: a client reading this refusal to decide its next step (wait out PENDING/CANCELLING, or issue CancelCapacityReservation first) cannot tell which state blocked the delete, and a cancel-then-delete teardown keyed on AWS's wording never matches, so it aborts on an unrecognized message.
  Fix: the DeleteCapacityReservation handler's not-cancelled refusal path and the shared message constructor it calls (the constructor takes no status argument today and therefore cannot render the state).
  NOTE for the fixer: the already-open issue 20261111T163757Z-athena-capacity-reservation-lifecycle-refusals-diverge-delete-state.md carries this same wording defect for three other check ids (Cause 1 of that issue), but NOT for the check id below — the suite did not attribute this check to it, so closing that issue alone would never re-replay this one. One fix can close both; re-replay the check listed here too.
  Traces: athena.capacity-reservation-lifecycle-create-get-update-cancel-delete.

Cause 2 of 3: the non-Spark-workgroup refusal on the notebook operations is reworded and interpolates a request value AWS's message does not contain.
  AWS: Smithy — CreateNotebook requires WorkGroup (WorkGroupName, @pattern ^[a-zA-Z0-9._-]{1,128}$) and Name (NotebookName, @length 1..255); ListNotebookMetadata requires WorkGroup with the same pattern; both model InvalidRequestException (client, httpError 400), TooManyRequestsException (400) and InternalServerException (500). Recorded behavior: against a workgroup whose engine is not Spark, BOTH operations are refused 400 InvalidRequestException with Message "Workgroup EngineVersion is not Spark." — entirely fixed text, with NO variable parts: AWS does not name the workgroup. Nothing is created, and the identical CreateNotebook against a Spark-enabled workgroup (Configuration.EngineVersion.SelectedEngineVersion "PySpark engine version 3" + ExecutionRole) succeeds and is readable back through GetNotebookMetadata.
  Emulator: status 400 and code InvalidRequestException are right, but the Message is the emulator-authored "WorkGroup <workGroupName> is not a Spark enabled workgroup." — different fixed wording, plus the WorkGroup value copied from the request, which AWS's template for this class does not contain at all.
  Why: InvalidRequestException covers many distinct causes on these operations, so the message is the only discriminator. A client branching on "wrong workgroup type" never matches AWS's sentence, and because the emulator's text varies with the request, even an assertion written against the emulator is unstable.
  Fix: the workgroup-engine validation / refusal construction shared by the notebook operations (CreateNotebook and ListNotebookMetadata handlers) — emit AWS's fixed non-Spark message with no request interpolation.
  NOTE for the fixer: the open WIRE issue 20261116T220502Z-athena-listcapacityreservations-token-and-createnotebook-non-spark-refusals.md carries this wording for CreateNotebook from a wire fixture step only (its Issue-Trace-Ids are fixture ids, not this check id), and 20261108T041854Z-athena-notebook-operations-refuse-without-athenaerrorcode-errorcode-and.md carries it for ImportNotebook/ExportNotebook. Neither carries the ListNotebookMetadata path or this check id.
  Traces: athena.create-notebook-on-sql-workgroup-rejected.

Cause 3 of 3: the Spark-session bring-up path never yields a session, so five notebook/session checks burn the whole per-check budget and reach no verdict.
  AWS: Smithy — StartSession input WorkGroup @required, EngineConfiguration @required, ExecutionRole (RoleArn, @length 20..2048), SessionIdleTimeoutInMinutes @range 1..480, NotebookVersion (@length 1..128); output SessionId (@length 1..256) and State from SessionState (CREATING | CREATED | IDLE | BUSY | DEGRADED | FAILED | TERMINATING | TERMINATED); errors InvalidRequestException, ResourceNotFoundException, SessionAlreadyExistsException, TooManyRequestsException (all 400) and InternalServerException (500). Recorded behavior: StartSession against a Spark-enabled workgroup answers 200 with a SessionId, the session advances CREATING→CREATED→IDLE and GetSessionStatus/GetSession report that State; once IDLE it accepts StartCalculationExecution, it is listed by ListSessions (and, when started with EngineConfiguration.AdditionalConfigs.NotebookId, by ListNotebookSessions for exactly that notebook and not for a sibling notebook); CreatePresignedNotebookUrl for a live session answers 200 with NotebookUrl, a non-empty AuthToken carried inside that URL, and AuthTokenExpirationTime = 600 (the token LIFETIME in seconds), a re-issue returning a different AuthToken with the same lifetime; after TerminateSession the session reaches TERMINATED and CreatePresignedNotebookUrl is refused 400 InvalidRequestException "Invalid Request", while an unknown SessionId is refused 400 InvalidRequestException "Not authorized to make this request."
  Emulator: StartSession is an unimplemented scaffold — services/service-com-amazonaws-athena-amazonathena/src/ops/start_session.rs still carries the `SCAFFOLDED, NOT IMPLEMENTED` marker (line 4) and answers HTTP 501 with code NotImplemented, "operation StartSession is scaffolded but not implemented in this emulator". Each of these five checks wraps the session start in a bounded retry loop (retrying on ClientError, because on real AWS a freshly created ExecutionRole can briefly be rejected), so the 501 is swallowed and retried until the harness kills the check: every one of the five reports only "Check timed out after 60.0s" and asserts nothing. (Hypothesis: the Spark workgroup create that precedes it is also retried on ClientError, so if CreateWorkGroup with an ExecutionRole + PySpark EngineVersion is refused, the same timeout appears; the StartSession stub is the confirmed blocker, this alternative needs checking while fixing.)
  Why: no client can open an Athena Spark session at all, and because the failure is a hang rather than a refusal, every downstream contract (session state machine, notebook-scoped session listing, presigned notebook URL and its 600-second token lifetime, calculation execution on an IDLE session) is unobservable instead of merely wrong — a consumer sees a request that never resolves.
  Fix: implement the StartSession handler (services/service-com-amazonaws-athena-amazonathena/src/ops/start_session.rs) over session state so a Spark workgroup yields a SessionId that advances to IDLE, and make the session reads/projections that depend on it (GetSessionStatus/GetSession, ListSessions, ListNotebookSessions scoped by EngineConfiguration.AdditionalConfigs.NotebookId, CreatePresignedNotebookUrl) answer from that state.
  NOTE for the fixer: 20261104T163600Z-athena-startsession-stub.md (bare "implement the stub") and 20261108T110422Z-athena-spark-sessions-2-net-new-causes-startsession.md name the same handler, but neither carries any of the five check ids below — they are swallowed-then-timed-out, so the suite could not attribute them. One implementation can close all of these; re-replay the five checks listed here.
  Traces: athena.create-presigned-notebook-url-requires-existing-notebook, athena.e2e-notebook-session-calculation-teardown, athena.notebook-sessions-list-scoped-to-notebook, athena.presigned-notebook-url-reports-ten-minute-token-lifetime, athena.session-lifecycle-start-get-status-endpoint-terminate.
