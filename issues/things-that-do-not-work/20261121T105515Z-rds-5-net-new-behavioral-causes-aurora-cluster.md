## Description
FIVE net-new root causes in the rds emulator, all surfaced by the behavioral suite. Each has its own handler/component and its own failing checks; a fix must close all five before submitting.

=== Cause 1 of 5: an Aurora DB cluster's writer/reader/custom endpoints are published on a host the emulator does not serve, so every cluster data-plane check is ungradeable (13 checks) ===
AWS: Smithy rds (com.amazonaws.rds#AmazonRDSv19) DBCluster$Endpoint is "The connection endpoint for the primary instance of the DB cluster", DBCluster$ReaderEndpoint is the reader (load-balancing) endpoint, and DBClusterEndpoint$Endpoint is a custom endpoint's connection endpoint; DBCluster$Port is "The port that the database engine is listening on" (aurora-mysql 3306, aurora-postgresql 5432 by default). In AWS each of those names RESOLVES and a native session can be opened on it, and the writer, the 'cluster-ro-' reader and each 'cluster-custom-' endpoint are distinct, reachable names.
Emulator: the cluster envelopes publish AWS-shaped DNS names in the .rds.localhost domain — '<cluster-id>.cluster-<resource-id>.<region>.rds.localhost', '<cluster-id>.cluster-ro-<resource-id>...', '<endpoint-id>.cluster-custom-<resource-id>...' — paired with the emulator's ephemeral listener port, and NOTHING answers on that host. The replay harness refuses the published target outright: 'endpoint_host was given <id>.cluster-<rid>.<region>.rds.localhost:<port> (published by the emulator or built by the check): its host is not one of the emulator's own hosts; a customer of the emulator needs an own host[:port]: the endpoint host, a documented own host or, for a loopback endpoint, a loopback address' (and for the https form: 'a customer of the emulator needs http(s)://127.0.0.1:<port>/<resource path>, or http(s)://<own host>:<port>/<path> on a per-resource listener'). The host name, the random cluster-resource-id segment and the port number are per-run values; the requirement is the shape — a name the emulator answers on, with the writer, reader and custom endpoints distinct.
Why: a client cannot open a single session against an Aurora cluster. Clone copy-on-write isolation, backtrack, failover, reader-endpoint read-only refusal, custom-endpoint static-member routing, Serverless v2 pause/resume and the Aurora engine-truth suites all go unmeasurable — the emulator announces an address it does not serve, which is strictly worse for a client than announcing a loopback one.
Fix: the DB-cluster state that mints endpoint hostnames plus the serializers that publish them (DescribeDBClusters / CreateDBCluster / DeleteDBCluster / DescribeDBClusterEndpoints and the cluster-endpoint handlers) in services/service-com-amazonaws-rds-amazonrdsv19 — a SERVED cluster must publish an address the emulator actually answers on (a per-resource listener host[:port] or a name resolved to one), with writer, reader and custom endpoints distinct. Related open issues that do NOT carry these checks' replay keys: 20261118T181500Z-rds-the-published-endpoint-of-a-served-engine-is-the-core-listeners.md (same family, but filed when the emulator published 127.0.0.1 and an OS-assigned port — the keys there are AssertionErrors on host/port equality, not this PublishedUrlRejected refusal), 20261121T073752Z-rds-db-cluster-envelopes-publish-the-emulator-s.md (the wire-side host_not_own/Port divergence), 20261118T210044Z-rds-2-net-new-causes-describedbclusters-publishes-an.md, 20261121T053640Z-logs-rds-an-available-aurora-postgresql-cluster-publishes.md and 20261121T075629Z-rds-s3-3-net-new-causes-an-available.md (other services' sweeps).

=== Cause 2 of 5: ModifyDBParameterGroup refuses the modifiable MySQL parameter `reserved_connections` as unknown ===
AWS: ModifyDBParameterGroup models only DBParameterGroupNotFoundFault (404, DBParameterGroupNotFound) and InvalidDBParameterGroupStateFault (400) — recorded behavior otherwise. RDS for MySQL 8.0 exposes `reserved_connections` as a modifiable dynamic parameter of the mysql8.0 family (it appears in DescribeEngineDefaultParameters / DescribeDBParameters for that family), so setting it alongside `max_connections` succeeds with 200 and the group then reports it.
Emulator: the call is refused 400 InvalidParameterValue with the message 'Could not find parameter with name: reserved_connections'. Fixed text of that error class is 'Could not find parameter with name: ' followed by the ParameterName from the request; here it is emitted for a parameter the family DOES define, i.e. the family's parameter catalog is incomplete rather than the request being bad.
Why: a client that provisions a connection-cap scenario (max_connections plus the reserved superuser slots) cannot apply its parameter group at all, so the overflow-session refusal the parameters exist to produce can never be exercised.
Fix: the mysql8.0 family parameter catalog behind crate::state::published_db_parameters and the validation in services/service-com-amazonaws-rds-amazonrdsv19/src/ops/modify_db_parameter_group.rs (unknown-parameter check).
Traces: rds.max-connections-cap-rejects-the-overflow-session.

=== Cause 3 of 5: ModifyDBParameterGroup rejects an uppercase enum value that AWS accepts case-insensitively ===
AWS: same operation/errors as cause 2 (recorded behavior for value validation). RDS accepts a parameter value whose casing differs from the documented allowed values — `binlog_row_image=FULL` on family mysql8.0 is accepted — and DescribeDBParameters echoes the value back exactly as submitted ('FULL'), it is not folded or refused.
Emulator: the call is refused 400 InvalidParameterValue with 'Invalid parameter value: FULL for: binlog_row_image allowed values are: full,minimal,noblob'. The fixed text of that class is 'Invalid parameter value: <value> for: <ParameterName> allowed values are: <list>'; the variable parts are the request's value/name and the family's allowed list — the defect is that the comparison is case-SENSITIVE, so a legal request is refused.
Why: Terraform/CloudFormation stacks and operators routinely write enum parameter values in upper case; every such apply fails against the emulator, and the casing a client stored cannot be read back.
Fix: value validation in services/service-com-amazonaws-rds-amazonrdsv19/src/ops/modify_db_parameter_group.rs — match allowed values case-insensitively while storing (and echoing) the submitted casing verbatim. Open issue 20261117T174147Z-cloudformation-rds-3-net-new-causes-an-invalid.md carries the same symptom for the cloudformation__rds check and does NOT carry this rds check's key.
Traces: rds.modify-db-parameter-group-binlog-row-image-casing-preserved.

=== Cause 4 of 5: the emulated PostgreSQL engine does not understand a typed `interval` literal ===
AWS: PostgreSQL (RDS for PostgreSQL / Aurora PostgreSQL) supports the standard typed-literal form `interval '1 month'`; `SELECT '2024-01-31 00:00:00+00'::timestamptz + interval '1 month'` returns 2024-02-29 00:00:00+00, and timestamptz − timestamptz yields an interval. Recorded behavior: the check grades these exact values over a native psycopg session.
Emulator: the statement is refused by the served engine with SQLSTATE 42703 UndefinedColumn, 'column "interval" does not exist' — the parser reads the keyword `interval` as a column reference instead of a type for the following string literal, so date/time arithmetic is unusable.
Why: interval arithmetic is everyday PostgreSQL (retention windows, 'now() - interval ...'); every such query fails with a nonsense UndefinedColumn, and a client cannot distinguish an emulator gap from a genuine schema error.
Fix: the SQL parser/expression evaluator of the emulated PostgreSQL dialect served by the rds crate's data plane (typed-literal `<type> '<string>'` form, and the interval type's arithmetic with timestamptz). Related open issue 20261112T105401Z-rds-4-net-new-causes-the-emulated-postgresql.md concerns the same engine but not this construct or this check.
Traces: rds.pg-dialect-numeric-timestamptz-jsonb-arrays-returning-recursive-cte.

=== Cause 5 of 5: the postgres CloudWatch log-export delivery flow never reaches a verdict ===
AWS: with log_statement=all in its parameter group and ModifyDBInstance EnableLogTypes=['postgresql'], an available postgres DB instance reports EnabledCloudwatchLogsExports=['postgresql'], RDS itself creates the log group /aws/rds/instance/<id>/postgresql and delivers the executed statement's log line into it; after DisableLogTypes no further event arrives and no stream takes a newer lastEventTimestamp; after re-enabling, delivery resumes.
Emulator: the check reaches no assertion at all — the replay reports only 'Check timed out after 60.0s'. The flow it is blocked in consists solely of provisioning the postgres instance with its custom parameter group and polling it to available, then opening a native session and polling the log group for the marker event. Hypothesis (not a finding): either the instance never settles to available inside the budget or no engine log line is ever exported to /aws/rds/instance/<id>/postgresql, so the enabled/disabled/re-enabled delivery boundary is unobservable.
Why: a client cannot verify that enabling a log export starts delivery and that disabling it stops delivery — the only observable behavior of the feature.
Fix: ModifyDBInstance's Cloudwatch-logs-export handling plus the engine-log export path in services/service-com-amazonaws-rds-amazonrdsv19 (creation of the /aws/rds/instance/<id>/<type> group and delivery of engine log lines while the type is enabled), and whichever step of the postgres provisioning flow the wait never clears.
Traces: rds.cloudwatch-logs-export-delivers-only-while-enabled.
