# cloudwatch__sns__sqs: an evaluation-driven metric alarm (no warm-up) on a continuously breaching custom series delivers no AlarmActions SNS notification to its subscribed SQS queue within 300 s, so the warm-up withholding contrast never reaches a verdict (1 cause)

> _Note: this issue was identified against the code base at commit `1b14ccf8bc557e9f3ed20a9ce1fb318436d9b18d`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
PutMetricAlarm

## Description
Cause 1 of 1: a metric alarm with NO WarmUpConfiguration, whose custom-namespace series is breaching continuously from before the alarm existed, never delivers its AlarmActions SNS notification to a queue subscribed to that topic — nothing at all arrives on the queue in a 300 s window while the series is re-published every 5 s. The alarm->SNS->SQS leg of an evaluation-driven (not SetAlarmState-forced) transition is inert, so the check's positive control barrier can never be crossed and the whole warm-up semantics it grades (a gated arm must withhold its transition and its action for the warm-up, then release both) is never reached.
Failing check id: cloudwatch__sns__sqs.deep-cloudwatch-1-cw-warmup-withholds-alarm-and-notification-until-expiry

AWS: Smithy (com.amazonaws.cloudwatch#GraniteServiceVersion20100801) models PutMetricAlarm with AlarmActions (ResourceList, @length 0..5), documented "The actions to execute when this alarm transitions to the ALARM state from any other state. Each action is specified as an Amazon Resource Name (ARN) ... SNS notification action: arn:aws:sns:<region>:<account-id>:<sns-topic-name>", and WarmUpConfiguration documented "During the warm-up period, the alarm stays in INSUFFICIENT_DATA and does not perform alarm actions." So for an alarm created with Statistic=Maximum, Period=60, EvaluationPeriods=1, DatapointsToAlarm=1, ComparisonOperator=GreaterThanThreshold, ActionsEnabled=true, AlarmActions=[<topic>] and NO WarmUpConfiguration, over a series PutMetricData keeps above the threshold, CloudWatch's own evaluation clock moves the alarm INSUFFICIENT_DATA -> ALARM within a few evaluation periods, executes the SNS action, and the subscribed SQS queue receives an SNS envelope with Type="Notification" whose Message is the alarm JSON carrying AlarmName=<the alarm from the request>, NewStateValue="ALARM" and OldStateValue="INSUFFICIENT_DATA"; DescribeAlarmHistory(HistoryItemType="Action") records a matching item whose HistoryData actionState is "Succeeded" and whose HistorySummary names the topic ARN. No status code or error code is in play here — every request in the check succeeds (HTTP 200); the divergence is the absent delivery. The alarm/topic/queue names, the namespace and the timestamps are per-run values from the request and state, not part of the requirement.

Emulator: no notification is ever delivered. The replay fails in the control barrier with `AssertionError: the no-warm-up control '<name>' delivered its ALARM notification through SNS -> SQS on a series that has been breaching since before it existed did not happen within 300s; last observation {}` — the collected {AlarmName: [payload...]} map is EMPTY, i.e. the queue received no SNS envelope at all over 300 s of 5-second ReceiveMessage polls while PutMetricData re-published Value=100.0 against Threshold=10.0 every iteration. Everything before the barrier passes, so this is specifically the action/delivery leg and not the configuration surface: the control reads back with no WarmUpConfiguration and no EvaluationState, and both warm-up arms read back their WarmUpConfiguration verbatim with EvaluationState "IN_WARM_UP" and StateValue INSUFFICIENT_DATA. The emulator's evaluator does build and queue a notification for a transition (services/service-com-amazonaws-cloudwatch-graniteserviceversion20100801/src/state/alarm_evaluation.rs: AlarmNotification::of_transition near line 1143, enqueue_notification near line 2081, queue_notification/take_pending_notifications near lines 2133-2157), so the queued record is either never produced for this evaluation-driven transition or never drained into an SNS Publish on the topic. Hypothesis (neither the model nor the recording states which): the alarm either never reaches ALARM on a 60 s-period sliding window under the lazy settle, or reaches it while the pending-notification queue is never delivered to SNS.

Why: a client that creates an ordinary metric alarm with an SNS AlarmAction and publishes breaching data sees no page: no SNS notification, no SQS message, no subscriber invocation. Every alarm-driven pipeline built on real metric data (paging, scaling, deployment gates, rollback) is silent, and any test of a withholding feature — warm-up, DisableAlarmActions, mute rules, actions suppressors — becomes vacuous, because an absence produced by the broken delivery path is indistinguishable from an absence the feature is supposed to cause.

Fix: the CloudWatch alarm action-dispatch path in the cloudwatch crate — the evaluation-driven transition in services/service-com-amazonaws-cloudwatch-graniteserviceversion20100801/src/state/alarm_evaluation.rs must queue an AlarmNotification for an alarm with ActionsEnabled and a non-empty AlarmActions, and the settle path that drains pending_notifications must actually publish to the named SNS topic (and record the Action history item) so the topic's subscribers receive it; the warm-up gate (warm_up_withholds_evaluation) must remain the ONLY thing that withholds it for a gated alarm.

## Steps to Reproduce
1. Build and boot the emulator from this checkout; point botocore cloudwatch/sns/sqs clients at it.
2. sns CreateTopic; sqs CreateQueue; sqs GetQueueAttributes(AttributeNames=[QueueArn]); sqs SetQueueAttributes(Policy allowing Principal {"Service":"sns.amazonaws.com"} sqs:SendMessage on the queue ARN); sns Subscribe(TopicArn, Protocol="sqs", Endpoint=<queue arn>, ReturnSubscriptionArn=True).
3. Pick a unique namespace NS and metric M. cloudwatch PutMetricData(Namespace=NS, MetricData=[{MetricName:M, Timestamp: now-60s, Value:100.0, Unit:"Count"}]) and again at Timestamp=now.
