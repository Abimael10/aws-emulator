Cause 1 of 1 — after StopConfigurationRecorder followed by StartConfigurationRecorder, the Config recording pass never captures anything again: a subsequent configuration CHANGE to an already-existing resource (sqs:SetQueueAttributes on a queue the stopped window missed) yields no AWS::SQS::Queue configuration item, while DescribeConfigurationRecorderStatus reports the recorder as recording=true with lastStatus pinned at 'Pending' and no error. Failing check: config__sqs.config-stopped-recorder-records-no-configuration-item-until-restarted.

AWS: recorded behavior only for the discovery/recording side effect itself — the Smithy model (com.amazonaws.configservice#StarlingDoveService) models the control and read paths, not the recording pass. Smithy: StartConfigurationRecorder takes required ConfigurationRecorderName (@length 1..256), returns an empty output (HTTP 200) and declares NoAvailableDeliveryChannelException / NoSuchConfigurationRecorderException / UnmodifiableEntityException (all client, HTTP 400). GetResourceConfigHistory takes required resourceType (enum ResourceType) and resourceId (@length 1..768) plus laterTime/earlierTime/chronologicalOrder/limit (@range 0..100)/nextToken, returns configurationItems (ConfigurationItemList) + nextToken, and declares ResourceNotDiscoveredException / NoAvailableConfigurationRecorderException / InvalidTimeRangeException / InvalidLimitException / InvalidNextTokenException / ValidationException (all client, HTTP 400). ConfigurationItem carries configurationItemCaptureTime, configurationItemStatus, resourceType, resourceId, resourceName, arn and the JSON-encoded `configuration` document. ConfigurationRecorderStatus.lastStatus targets the RecorderStatus enum (Pending | Success | Failure | NotApplicable) and is documented as 'the status of the latest recording event processed by the recorder', with lastStatusChangeTime alongside it. On AWS, once a stopped recorder is started again, recording resumes for the types its recordingGroup covers: a change to an existing SQS queue (SetQueueAttributes) causes Config to write a NEW configuration item for resourceType AWS::SQS::Queue whose `configuration` document reflects the CHANGED attribute value, whose resourceName is that queue's name and whose configurationItemCaptureTime is AFTER the restart — so GetResourceConfigHistory(resourceType='AWS::SQS::Queue', resourceId=<queue url>) answers HTTP 200 with a non-empty configurationItems list. Nothing is backfilled for the stopped window (no snapshot of the queue as it was created while the recorder was stopped), and lastStatus leaves 'Pending' for 'Success' once a recording event has been processed.

Emulator: StopConfigurationRecorder is honoured (the queue created during the stopped window is correctly undiscovered, and GetResourceConfigHistory for it answers 400 ResourceNotDiscoveredException with Config's exact message `Resource <resourceId> of resourceType:<resourceType> is unknown or has not been discovered` — fixed text `Resource `, ` of resourceType:` and ` is unknown or has not been discovered`, with resourceId/resourceType substituted from the request; that leg PASSES). What fails is the repair leg: after StartConfigurationRecorder succeeds and DescribeConfigurationRecorderStatus reports recording=true, a sqs:SetQueueAttributes change (VisibilityTimeout) on that same queue produces NO configuration item for it at all within 480 s — GetResourceConfigHistory keeps answering with nothing for that resourceId — and the emulator's own DescribeConfigurationRecorderStatus at the moment of failure is {'recording': True, 'lastStatus': 'Pending', 'lastErrorCode': None, 'lastErrorMessage': None}: a recorder that reports itself healthy and recording while recording nothing and never advancing out of 'Pending'. Hypothesis (neither the model nor the recording states which of the two it is, and this evidence cannot separate them): either the restart does not re-arm the recording pass at all, or the recording pass only ever captures resource CREATION and never a configuration change to an existing resource. Scope note: the queue URL, queue name, recorder name, account id, the VisibilityTimeout values and the 480 s window are per-run values and are not part of the requirement; the requirement is that a post-restart change is recorded, is not backfilled into the stopped window, and that lastStatus advances.

Why: a client that stops recording for a maintenance window and starts it again gets a recorder that is permanently dead — Config reports recording=true and reports no error, so nothing warns the caller, yet the account's inventory stops growing from that point on. Because nothing is recorded after the restart, ResourceNotDiscoveredException becomes the answer to every GetResourceConfigHistory call, and a caller cannot distinguish 'this resource never existed' from 'Config stopped recording when I restarted it'. Drift, audit and compliance tooling that waits for a resource's post-change snapshot blocks forever, and anything gating on lastStatus == 'Success' to confirm the recorder came back up waits on 'Pending' indefinitely.

Fix: the configuration-recorder recording pass in the configservice crate and the state it reads — StartConfigurationRecorder's handler must re-arm the recording pass for the recorder's recordingGroup after a stop (rather than leaving the recorder flagged recording while inert), the pass must capture configuration CHANGES to already-existing resources of other emulated services (here AWS::SQS::Queue attribute changes from the SQS crate) and not only creations, GetResourceConfigHistory's handler must project those items (reserving ResourceNotDiscoveredException for ids genuinely absent from that state) without backfilling items whose capture time falls inside the stopped window, and the recorder status machine behind DescribeConfigurationRecorderStatus must advance lastStatus/lastStatusChangeTime out of 'Pending' once a recording event is processed.
