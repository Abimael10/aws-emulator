# dynamodb: 9 net-new causes — vector-index projection leaks the vector attribute and does not float32-round it, SearchVectors capacity ignores the projected vector, a self-delete of a building index returns no index row, and four refusal texts/carriers diverge

> _Note: this issue was identified against the code base at commit `864dd26a02416cc990250070e65c7b703d06755e`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
SearchVectors, CreateTable, UpdateTable, BatchWriteItem, PutItem, DescribeTable

## Description
Nine net-new root causes in the dynamodb emulator. None of these replay keys is carried by an open issue. Where an open issue covers an adjacent area it is named under the cause.

=== Cause 1 of 9: a vector index's Projection does not withhold unprojected attributes — the vector attribute itself is always returned ===
AWS: Smithy: VectorIndex.Projection (target Projection) is required, exactly as for a GSI; VectorIndexDescription.Projection mirrors it; SearchVectors returns SearchResults whose items are drawn from the index. A KEYS_ONLY or INCLUDE projection returns only the table key attributes plus the named NonKeyAttributes. The vector attribute named by VectorIndex.VectorAttribute is not a key attribute and is only returned when the projection names it.
Emulator: SearchVectors on an INCLUDE[note] index returns the vector attribute too — attributes `['emb', 'note', 'pk', 'tier']` where only `pk, tier, note` are projected; and on a second index, `['cat', 'emb', 'extra', 'note', 'pk']` where only `pk, cat, note, extra` are projected. In both cases `emb` (the indexed vector) is an extra attribute the projection does not name.
Why: a client that sized its responses and its parsing on a KEYS_ONLY/INCLUDE projection receives an unexpected, large vector payload per result; code that treats the returned item as exactly the projected set (or that asserts the vector is withheld for privacy/bandwidth reasons) breaks, and read-size accounting is wrong.
Fix: the SearchVectors result projection — the component that builds each SearchResultItem from the index entry must filter to the index's Projection (ProjectionType plus NonKeyAttributes) before serializing.
Traces: dynamodb.deep-dynamodb-1-ddbvec-include-projection-hides-unprojected-attributes; dynamodb.deep-dynamodb-1-ddbvec-search-condition-filters-below-topk-with-projection

=== Cause 2 of 9: a projected vector attribute is returned verbatim instead of float32-rounded ===
AWS: recorded behavior only. Vector components in a DynamoDB vector index are stored as 32-bit floats, so a number written to the vector attribute that is not representable in float32 comes back rounded to the nearest float32 value when SearchVectors projects that attribute.
Emulator: a component written as the integer 16777217 (2^24+1, not representable in float32) is projected back as the string `'16777217'`; AWS returns the float32-rounded `'16777216.0'`.
Why: a client that compares a projected vector against the float32 values the service actually scores against sees a value no similarity computation used, so re-scoring client-side disagrees with the service's own ranking; and the response implies a precision DynamoDB does not store.
Fix: the vector-index write/read path for the vector attribute — the stored representation must be narrowed to float32 on write and the projected value serialized from that narrowed representation.
Traces: dynamodb.search-vectors-dot-product-score-rounds-integer-above-2-24-to-float32

=== Cause 3 of 9: SearchVectors ConsumedCapacity.VectorSearchRequestBytes does not grow when the vector attribute is projected ===
AWS: Smithy: SearchVectors.output.ConsumedCapacity targets VectorCapacity, whose member VectorSearchRequestBytes is documented as "the number of vector search request bytes consumed by a SearchVectors operation". Recorded behavior: that figure is floored at 1024, grows with TopK, and grows again when the projection returns the searched vector attribute itself rather than withholding it.
Emulator: with everything else held constant (same index, same SearchVector, TopK=1), ProjectionExpression='pk' and ProjectionExpression='pk, emb_big' both report VectorSearchRequestBytes = 1024.0 — the meter never leaves the floor when the (large) vector attribute is added to the projection.
Why: a client budgeting or alarming on vector search spend cannot distinguish a cheap key-only search from one that returns full vectors; capacity planning and cost attribution built on this number are wrong in exactly the case that costs most. (Likely a consequence of Cause 1 as well, but the meter must move independently of which attributes the serializer happens to emit.)
Fix: the SearchVectors capacity meter — VectorSearchRequestBytes must be computed from the bytes actually searched and returned, including the projected vector attribute, not pinned at the 1 KB minimum.
Traces: dynamodb.search-vectors-consumed-capacity-is-vector-bytes-only-floored-and-scales

=== Cause 4 of 9: UpdateTable deleting an index that is still CREATING returns a TableDescription with no row for that index ===
AWS: Smithy: UpdateTable.output.TableDescription; GlobalSecondaryIndexDescription.IndexStatus and VectorIndexDescription.IndexStatus are the IndexStatus enum CREATING|UPDATING|DELETING|ACTIVE, and GlobalSecondaryIndexDescription.Backfilling documents that "you can delete an index that is being created during the Backfilling phase when IndexStatus is set to CREATING". AWS accepts that self-delete and the returned TableDescription still lists the index, now with IndexStatus DELETING; it disappears only once the removal completes.
Emulator: the self-delete is accepted but the returned TableDescription lists no indexes at all — the index row is dropped immediately instead of being reported as DELETING. Observed for both index kinds: a GSI (`UpdateTable self-delete described indexes [], expected only idx-a`) and a vector index (`UpdateTable self-delete described indexes [], expected only vidx-a`).
Why: a client that polls the UpdateTable response (or the subsequent DescribeTable) to watch a deletion through DELETING -> gone sees the index vanish in one step, so "is the teardown finished?" cannot be answered; and code that reads IndexStatus from the UpdateTable response gets a KeyError/IndexError on an empty list.
Fix: the UpdateTable handler's index-update path and the TableDescription projection — a Delete of a CREATING index must transition that index to DELETING and keep projecting its description (GlobalSecondaryIndexes / VectorIndexes) until removal completes.
Traces: dynamodb.gsi-creating-blocks-other-index-but-accepts-self-delete; dynamodb.vector-index-creating-blocks-other-index-but-accepts-self-delete

=== Cause 5 of 9: CreateTable's refusal of a second HASH element in a vector index's SearchSchema uses the KeySchema message ===
AWS: Smithy: VectorIndex.SearchSchema is a SearchSchema list of SearchSchemaElement, each with SearchSchemaElementType HASH|INLINE_FILTER; the HASH element "partitions the vector index" and at most one is allowed. AWS refuses a second one with ValidationException and the constraint-shaped message `One or more parameter values were invalid: Value '2' at 'SearchSchema' failed to satisfy constraint: Member must have HASH count less than or equal to 1` — fixed text apart from the count (`'2'`, the number of HASH elements in the request) and the member path (`SearchSchema`).
Emulator: ValidationException with `One or more parameter values were invalid: The KeySchema exceeds the maximum allowed number of HASH key attributes` — AWS's message for a table KeySchema, naming the wrong member entirely and omitting the offending count.
Why: the refusal points the operator at the table's KeySchema rather than at the vector index's SearchSchema, so the actual malformed field is never identified; tooling that greps the message for the member path mis-attributes the error.
Fix: the CreateTable VectorIndexes validation (the SearchSchema HASH-count check) and its message template. Note the open issue 20261109T021218Z-dynamodb-3-net-new-vector-index-causes-createtable.md covers other CreateTable vector-index validations but not this one.
Traces: dynamodb.create-table-vector-index-two-hash-search-schema-elements-rejected

=== Cause 6 of 9: a BatchWriteItem body with no RequestItems is refused with the wrong error code carrier and the wrong message ===
AWS: Smithy: BatchWriteItem.input.RequestItems is required (BatchWriteItemRequestMap, length 1..25). For an entirely absent required member DynamoDB answers HTTP 400 with the awsJson1.0 body `__type` = `com.amazon.coral.validate#ValidationException` and message `The requestItems parameter is required for BatchWriteItem` — fixed text apart from the member name (`requestItems`) and the operation name (`BatchWriteItem`). The coral-namespaced `__type` is the only carrier botocore reads for awsJson, so the namespace is part of the contract.
Emulator: `{'__type': 'ValidationException', 'message': "1 validation error detected: Value at 'requestItems' failed to satisfy constraint: Member must have length greater than or equal to 1"}` — the `__type` carries no namespace at all, and the message is the length-constraint text AWS uses for a present-but-empty map, not the required-parameter text for an absent one.
Why: an unnamespaced `__type` is still matched by botocore on the bare code, but any consumer that keys on the full shape id (or that distinguishes `com.amazon.coral.validate#` service-framework validation from `com.amazonaws.dynamodb.v20120810#` modeled errors) mis-routes it; and the message tells the caller a length constraint failed when the parameter was never sent, so an "am I sending it at all?" bug reads as an "is my batch empty?" bug.
Fix: the BatchWriteItem request deserializer/validator — distinguish an absent required member from a present empty map, emit the required-parameter message, and have the awsJson error serializer write the fully namespaced `__type`. Adjacent open issues 20261111T170613Z-dynamodb-non-constraint-validationexception-messages-are-wrapped-in.md and 20261117T172826Z-dynamodb-control-plane-and-request-deserialization-10-net.md do not carry this replay key.
Traces: dynamodb.batchwriteitem-request-over-16mib-rejected-413-before-auth

=== Cause 7 of 9: the IncompleteSignature message omits the hashed-Authorization suffix ===
AWS: recorded behavior only. When the Authorization header is missing required SigV4 components, DynamoDB answers HTTP 400 and a message that lists each missing component — `Authorization header requires 'Credential' parameter. Authorization header requires 'Signature' parameter. Authorization header requires 'SignedHeaders' parameter. Authorization header requires existence of either a 'X-Amz-Date' or a 'Date' header.` — and then appends the fixed suffix ` (Hashed with SHA-256 and encoded with Base64) Authorization=<value>`, where `<value>` is derived from the Authorization header as received (a per-request base64 string, not a constant).
Emulator: the per-component sentences are produced correctly but the message stops there; the ` (Hashed with SHA-256 and encoded with Base64) Authorization=…` suffix is absent.
Why: that suffix is what lets a caller confirm the server saw the same Authorization bytes it sent; without it, debugging a signing mismatch loses the server-side echo, and any consumer matching AWS's full message text fails.
Fix: the SigV4 pre-auth validator's IncompleteSignature message builder. The open issue 20261117T172826Z-dynamodb-5-net-new-causes-malformed-sigv4-answers.md covers other malformed-SigV4 answers and does not carry this replay key.
Traces: dynamodb.incomplete-sigv4-signature-lists-missing-components

=== Cause 8 of 9: a number whose exponent parses as a Long but is out of range gets the "cannot be converted" message instead of the overflow message ===
AWS: recorded behavior only, and the two messages are distinct by design. For a numeric literal whose exponent still parses as a signed 64-bit integer (e.g. `1E9223372036854775807`) the magnitude is range-checked and refused with ValidationException `1 validation error detected: Number overflow. Attempting to store a number with magnitude larger than supported range`. Only an exponent that cannot be parsed as an integer at all (one past Long range) gets `1 validation error detected: The parameter cannot be converted to a numeric value: <literal>`, where `<literal>` is the rejected value from the request.
Emulator: PutItem with `{'N': '1E9223372036854775807'}` is refused ValidationException `1 validation error detected: The parameter cannot be converted to a numeric value: 1E9223372036854775807` — it reports a parse failure where AWS reports a magnitude overflow.
Why: the two messages mean different things to a caller: "overflow" says the number is well-formed but too large (clamp or rescale it), "cannot be converted" says the literal is not a number at all (fix the serializer). Conflating them sends the caller after the wrong bug, and a client discriminating on the message cannot classify the failure.
Fix: the attribute-value number parser/validator — parse the exponent as a 64-bit integer first and, when that succeeds, apply the magnitude range check and emit the overflow (or underflow) message; reserve the "cannot be converted" message for literals whose exponent does not parse.
Traces: dynamodb.zero-with-out-of-range-exponent-rejected

=== Cause 9 of 9: a Lambda-hosted AWS SDK for JavaScript v3 client addressed at an in-sandbox loopback endpoint is answered by the emulator with UnrecognizedClientException ===
AWS: recorded behavior only. In the recording, a Node 22 Lambda stands up a loopback HTTP server inside its own sandbox, points a DynamoDBClient at that endpoint, and the server returns a canned HTTP 400 awsJson1.0 error whose code is carried only in `x-amzn-errortype: ResourceNotFoundException:http://internal` with no `__type` in the body. JS v3 reads the header first and constructs its modeled `ResourceNotFoundException` (name `ResourceNotFoundException`), which is what makes the carrier divergence observable; botocore, reading only the body, falls back to the `'400'` status code (that half passed here).
Emulator: the JS client reports `UnrecognizedClientException` — an error neither the canned loopback server nor the local endpoint can produce, i.e. the request was not answered by the endpoint the client addressed. Hypothesis: the emulator's Lambda runtime overrides the SDK's endpoint/credential resolution for the sandbox, so the client's explicit loopback endpoint is ignored and the request reaches the emulator, which refuses the throwaway loopback credentials.
Why: a function that talks to anything on its own loopback interface (a sidecar, a local test double, an in-process proxy) has that traffic silently redirected and refused, so any in-function integration that is not the emulator's own endpoint is unreachable; and the error a handler sees is an auth error for a request it never addressed to AWS.
Fix: the Lambda runtime's environment/endpoint injection for the function sandbox — an explicitly configured client endpoint must not be rewritten, and loopback egress from the sandbox must reach the sandbox's own listener.
Traces: dynamodb.awsjson-error-code-carrier-is-body-only-rejected
