# cloudfront__cloudwatch__sns__sqs: the distribution's announced edge address refuses the connection, so the 4xxErrorRate alarm -> SNS -> SQS path is never exercised

## Description

Cause 1 of 1: a Deployed distribution announces an edge address on which nothing is listening — the viewer GET is refused at the transport — so no viewer request is ever served, AWS/CloudFront publishes no 4xxErrorRate datapoint for the distribution, and the entire alarm chain under test (metric -> CloudWatch alarm -> SNS topic -> SQS queue) is unobservable, as is the untouched control distribution that must stay OK. Failing check: cloudfront__cloudwatch__sns__sqs.obs-cloudfront-2-4xx-error-rate-alarm-notifies-sqs-untouched-control-stays-ok.
AWS:      recorded behavior only for the edge and the metric values; the control plane is modelled (Smithy: cloudfront GetDistribution returns Distribution.Status and DomainName, the host viewers address; cloudwatch PutMetricAlarm over namespace AWS/CloudFront with Dimensions DistributionId + Region='Global' and AlarmActions naming an SNS topic ARN; sns Publish to a subscribed sqs queue). On AWS a Deployed distribution serves viewer GETs at its published DomainName: 200 for a key the origin holds and 403/404 for a key it does not (with the managed CachingDisabled policy every request reaches the origin). Those requests are metered as AWS/CloudFront 4xxErrorRate (a percentage of all viewer requests in the minute) under DistributionId=<id> + Region='Global' in us-east-1, so a minute dominated by misses drives an alarm whose threshold is below that percentage to StateValue 'ALARM', its SNS alarm action publishes, and the subscribed SQS queue receives the alarm notification — while a distribution that received no error traffic keeps its twin alarm in 'OK'. The particular distribution ids, hosts, burst size and minute of one run are not requirements; the relation is.
Emulator: the viewer GET never succeeds. The check polls for a 200 for 300 s and aborts with its own data-plane marker: `AssertionError: DATAPLANE_UNIMPLEMENTED: timed out waiting for 200 from https://<announced-edge-address>/_aws/cloudfront/<distribution-id>/present.txt after 300.0s (last: ConnectionError(... Failed to establish a new connection: [Errno 111] Connection refused))`. The emulator therefore announced an edge address other than one it answers on: the HTTPS port of the announced authority refuses the connection outright. No 4xx burst can be issued, so no 4xxErrorRate datapoint, no alarm transition, no SNS publish and no SQS message occur, and the control-stays-OK half is equally unverified. Not a runner fault: the check carries a 15 s per-request timeout and marks a never-serving edge with DATAPLANE_UNIMPLEMENTED so it reads as a fidelity failure.
Why:      a client cannot serve any content through the distribution it created — the address CloudFront handed it refuses connections — and every operational control built on edge error rates silently fails closed: the 4xxErrorRate alarm stays in INSUFFICIENT_DATA instead of going to ALARM, so the SNS notification and anything consuming it from SQS (paging, rollback, cache purge) never run during a real error burst.
Fix:      the CloudFront edge data plane's listener/address publication — a Deployed distribution must be served on exactly the address GetDistribution publishes as DomainName — and the per-request outcome metering that publishes AWS/CloudFront 4xxErrorRate under DistributionId + Region='Global' in us-east-1, which the CloudWatch alarm evaluator then drives to ALARM and whose alarm action fans out through SNS to the subscribed queue.
Traces:   cloudfront__cloudwatch__sns__sqs.obs-cloudfront-2-4xx-error-rate-alarm-notifies-sqs-untouched-control-stays-ok.
