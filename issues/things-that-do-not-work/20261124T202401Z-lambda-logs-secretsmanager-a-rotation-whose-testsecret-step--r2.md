=== Cause 1 of 1: RotateSecret accepts the request but never executes the rotation function's four-step protocol, so a testSecret failure neither blocks promotion nor is distinguishable from a rotation that never started ===
AWS: Smithy: RotateSecret input SecretId (required, @length 1..2048), RotationLambdaARN (@length 0..2048), RotationRules, RotateImmediately (boolean); output ARN/Name/VersionId; modeled errors InvalidParameterException, InvalidRequestException, ResourceNotFoundException (400) and InternalServiceError (500). Recorded behavior for the step protocol: with RotateImmediately=true AWS invokes the secret's RotationLambdaARN once per step with an event {SecretId, ClientRequestToken, Step} for Step in createSecret, setSecret, testSecret, finishSecret. A candidate value is staged under AWSPENDING by createSecret, and AWSCURRENT moves to that version ONLY when finishSecret runs. When the function RAISES during testSecret, AWS stops the cycle there: finishSecret is never delivered, AWSCURRENT stays on the pre-rotation version id with its original plaintext, exactly one version carries AWSCURRENT, and the untested candidate keeps AWSPENDING only. An otherwise byte-identical function whose testSecret succeeds does reach finishSecret and does promote. Both outcomes are observable from the data plane alone: the function's own log stream shows which steps were delivered, and GetSecretValue/DescribeSecret show whether AWSCURRENT moved.
Emulator: the rotation function is never executed at all. RotateSecret is accepted, but no step event is ever delivered — the failing function's log stream never shows createSecret/setSecret/testSecret, DescribeSecret never grows an AWSPENDING version, and GetSecretValue keeps returning the original version forever. The check therefore blocks in its poll for the failing function to reach its testSecret step and is killed by the suite's cap: 'Check timed out after 60.0s'. Because nothing is ever invoked, the emulator also cannot serve the positive control in the same check (the identical function with FAIL_ON_TEST unset must promote and AWSCURRENT must hold the value that function generated).
Why: a client cannot tell a SAFE rotation from a broken one. The invariant this check exists to prove — an untested credential is never made current — is vacuously 'satisfied' only because no rotation ever happens; the emulator gives the same answer whether the rotation function approved the candidate, rejected it, or was never run. Any client that calls RotateSecret and then waits for AWSCURRENT to move (or that relies on a failing testSecret to abort the cycle and leave the working credential in place) hangs indefinitely instead of either rotating or reporting failure.
Fix: the RotateSecret handler's step driver in the secretsmanager service — it must invoke RotationLambdaARN once per step with {SecretId, ClientRequestToken, Step}, propagate a step invocation that raises by aborting the cycle without delivering finishSecret, and move AWSPENDING -> AWSCURRENT only on a successful finishSecret — together with the Lambda invocation runtime it depends on to actually execute a deployment package.

## Evidence
Failing check: [mismatch] lambda__logs__secretsmanager.rotation-with-a-failing-testsecret-step-rejected-and-awscurrent-never-moves — detail: 'Check timed out after 60.0s'.

Expected (AWS): after RotateSecret(SecretId, RotationLambdaARN=<failing fn>, RotationRules={AutomaticallyAfterDays:30}, RotateImmediately=True), the function's log stream contains exactly the step markers createSecret, setSecret, testSecret and never finishSecret; GetSecretValue(SecretId) keeps VersionId == the version id CreateSecret returned and SecretString == the original plaintext; DescribeSecret(SecretId).VersionIdsToStages maps that original version to ['AWSCURRENT'] and no AWSPENDING version carries AWSCURRENT, with exactly one AWSCURRENT holder. Then, with rotation cancelled and re-pointed at the byte-identical function whose only difference is the FAIL_ON_TEST environment variable, the cycle reaches finishSecret and GetSecretValue returns a NEW VersionId whose SecretString carries the prefix that control function generated.

Actual (emulator): no step marker is ever logged for either function, DescribeSecret never reports an AWSPENDING version, and GetSecretValue never leaves the original version — so the check's poll for the failing function to reach its testSecret step never resolves and the check is cut off at the 60 s cap. RotateSecret itself returns 200 with ARN/Name/VersionId; there is no error code or message to compare, the divergence is the absent effect.

Note on the per-run values above: the secret name, version ids and the generated secret plaintext differ on every run and are not part of the requirement; the requirement is that the version id GetSecretValue returns is unchanged across the failed cycle and changed after the control cycle, and that the control's plaintext is the value the control function wrote.

EXPECTED: VersionId still the step-1 version, SecretString still the original, VersionIdsToStages[<original>] == ['AWSCURRENT'], exactly one AWSCURRENT holder, and an AWSPENDING candidate present from createSecret. OBSERVED: the original version is returned but NO AWSPENDING version ever exists, because the cycle never started.
