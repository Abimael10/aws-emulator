# iam: 4 net-new causes — access-key ids are EMULATOR-prefixed, the AccessDenied authorization-details trailer is appended to a denial class that carries none, the AWS-managed policy catalog is missing AmazonDynamoDBReadOnlyAccess, and AttachUserPolicy accepts a nonexistent PolicyArn

> _Note: this issue was identified against the code base at commit `496f13e8c3207ef947f41f94a4f2c11ee1d8339b`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
CreateAccessKey

## Description
FOUR net-new root causes in the iam service, each grounded in its own failing behavioral check(s) from simparity-behavioral-aws-v1. ALL FOUR must be closed before this issue is submitted. None of the listed checks is reported blocked by an unimplemented scaffold stub, and the replay reports none of them owned by an open issue.

=== Cause 1 of 4: minted IAM access-key ids are not in AWS's access-key-id class — they are EMULATOR-prefixed ===
AWS: Smithy iam#CreateAccessKey -> output AccessKey (required); AccessKey.AccessKeyId targets accessKeyIdType (@length 16-128, @pattern ^[\w]+$). AWS's IAM unique-identifier prefixes are documented and load-bearing: a long-term IAM user access key id is 20 characters and begins with the literal prefix `AKIA` (a temporary STS credential begins `ASIA`). The requirement is the id FORM — `AKIA` followed by 16 further characters, 20 in total — never any one run's literal id, which is per-run state. ListAccessKeys must project the same form.
Emulator: CreateAccessKey answers HTTP 200 and the key is otherwise correct (UserName, Status 'Active', 40-character secret all asserted and passed), but AccessKeyId is `EMULATOR`-prefixed: it satisfies the Smithy pattern and the 20-character length yet is not in AWS's access-key-id class.
Why: a client relying on AWS's behavior classifies credentials by prefix — long-term vs temporary, secret scanners, policy linters, presign helpers and credential-provider chains all branch on `AKIA`/`ASIA`. Every key the emulator mints is misclassified, and a client that validates the documented prefix rejects it outright.
Fix: the access-key-id allocator behind the IAM user access-key state (reached by CreateAccessKey and projected by ListAccessKeys/GetAccessKeyLastUsed), not the serializer. Two open issues describe the same EMULATOR prefix for OTHER recorded units and carry neither of these replay keys: 20261116T105641Z-iam-7-net-new-causes-minted-access-key.md (wire, causes 1-2) and 20261118T021609Z-iam-4-net-new-causes-denials-append-an.md (behavioral, cause 3, grounded in iam.minted-identifier-prefixes-and-arn-paths). Closing this cause must make all of those pass together.
Traces: iam.iam-access-key-crud, iam.user-access-key-round-trips-status-and-never-used.

=== Cause 2 of 4: the AccessDenied authorization-details trailer is appended unconditionally, including to a denial class whose recording carries none ===
AWS: recorded behavior only (the Smithy model carries no message text; iam#ListRoles models only ServiceFailure, so the denial is the authorization layer's). AWS's denial message for this class is exactly the one sentence `User: <principal-arn> is not authorized to perform: <action> on resource: <resource> because no identity-based policy allows the <action> action` and nothing more. Fixed text: everything except `<principal-arn>`, `<action>` and `<resource>`, which come from the request and the emulator's state — here the principal is the calling IAM user's ARN, the action is `iam:ListRoles`, and the resource is `arn:aws:iam::<account>:role/`. Crucially the trailer is NOT unconditional in AWS: the same check records iam:ListAccountAliases (resource `*`) denied WITH the `. Go to https://...` trailer and iam:ListRoles denied WITHOUT it, and the ListAccountAliases leg passes while the ListRoles leg fails. HTTP 403 and Error.Code AccessDenied are correct in the emulator and are not at issue.
Emulator: the leading sentence is byte-for-byte correct, then a second sentence AWS did not send for this denial is appended: `. Go to https://us-east-1.console.aws.amazon.com/iam/home?region=us-east-1#/authorization-details/<authorization-id> for complete details, or call the GetRequestAuthorizationDetails API with the following authorization id: <authorization-id>` (the `<authorization-id>` inside it is per-run; the defect is the presence of the whole sentence, not its id). The trailer is emitted by the shared denial serializer for every denial rather than per denial class.
Why: a client that matches, logs or asserts on AWS's denial message sees text AWS never sent, so message-equality and regression assertions fail even though status and code match; operators are pointed at an authorization id that identifies nothing. This also makes the aws:RequestedRegion contract for the global IAM endpoint unverifiable: the check proves the decision is right and then fails on the message.
Fix: the IAM authorization denial message builder (the shared AccessDenied serializer the IAM operation handlers call) — the trailer must be emitted only for the denial classes whose recordings carry it. Two open issues bracket this from both sides and carry neither this replay key: 20261119T085411Z-iam-every-accessdenied-refusal-message-stops-at-action.md says the trailer was OMITTED where AWS sends it (26 checks), and 20261118T021609Z-iam-4-net-new-causes-denials-append-an.md (cause 1) says it is appended where AWS does not (7 checks). A blanket choice in either direction breaks the other family; the requirement is to reproduce the recorded message per denial class.
Traces: iam.requested-region-for-global-iam-is-us-east-1-other-region-denied.

=== Cause 3 of 4: the built-in AWS-managed policy catalog is missing AmazonDynamoDBReadOnlyAccess, so GetPolicy answers NoSuchEntity for a policy AWS always has ===
AWS: Smithy iam#GetPolicy -> input PolicyArn (required, arnType @length 20-2048); output Policy; errors InvalidInput(400), NoSuchEntity(404), ServiceFailure(500). `arn:<partition>:iam::aws:policy/AmazonDynamoDBReadOnlyAccess` is a partition-wide AWS-managed policy that exists in every account, so GetPolicy on it answers HTTP 200 with PolicyName = the name from the ARN, Arn = the requested ARN, Path `/`, IsAttachable true, a PolicyId matching `ANPA[A-Z0-9]{17}`, and a DefaultVersionId matching `v[1-9][0-9]*`; GetPolicyVersion on that DefaultVersionId then returns IsDefaultVersion true and a Document whose Version is `2012-10-17` with a non-empty Statement list. NoSuchEntity with the message `Policy <PolicyArn> was not found.` is correct only for a name the catalog does not contain (the check's own absent-name leg uses `Sim2realNoSuchManagedPolicy`).
Emulator: GetPolicy(`arn:aws:iam::aws:policy/AmazonDynamoDBReadOnlyAccess`) raises HTTP 404 NoSuchEntity with `Policy arn:aws:iam::aws:policy/AmazonDynamoDBReadOnlyAccess was not found.` — the error shape and message template are right, so the defect is the catalog content, not the handler's refusal path. GetPolicy on `ReadOnlyAccess` in the same loop succeeded, so the catalog exists but is incomplete.
Why: a client resolves an AWS-managed policy by ARN before attaching it; a policy AWS always has and the emulator does not makes the whole Attach*Policy / GetPolicyVersion path unreachable, so a role or user that AWS can build cannot be built here, and the client is told the policy does not exist when it does.
Fix: the IAM crate's built-in AWS-managed-policy catalog seed (the data GetPolicy, GetPolicyVersion, ListPolicies and the ListAttached*Policies projections all read) — it must contain every AWS-managed policy in the recorded set, each with its own fixed PolicyId/CreateDate/UpdateDate/DefaultVersionId and a default version document. The open issue 20261123T093939Z-iam-built-in-aws-reference-catalogs-diverge-from--r2.md describes the same catalog being incomplete on the ListPolicies `/service-role/` page (a different missing member, AWSLambdaRole) and carries no behavioral replay key; 20261115T063919Z-iam-listpolicies-aws-managed-policy-catalog-diverges-from.md covers other pages of the same fixture. Neither covers this check.
Traces: iam.get-aws-managed-policy-metadata-and-default-version.

=== Cause 4 of 4: AttachUserPolicy accepts a PolicyArn that names no policy, returning 200 instead of refusing it ===
AWS: Smithy iam#AttachUserPolicy -> input UserName (required, userNameType @length 1-64, @pattern ^[\w+=,.@-]+$) and PolicyArn (required, arnType @length 20-2048); output Unit; errors InvalidInput(400), LimitExceeded(409), NoSuchEntity (httpError 404, awsQueryError code NoSuchEntity), PolicyNotAttachable(400), ServiceFailure(500). An AttachUserPolicy whose PolicyArn resolves to no policy is refused HTTP 404 / Error.Code NoSuchEntity with the message `Policy <PolicyArn> does not exist or is not attachable.` — fixed text apart from `<PolicyArn>`, which is echoed from the request — and nothing is attached to the user.
Emulator: the call SUCCEEDS. For a well-formed but nonexistent AWS-scope ARN the response is HTTP 200 with an empty body (ResponseMetadata only, content-type text/xml), so the user's attached-policy list is mutated or the request is silently swallowed with no refusal. The happy-path leg of the same check (attaching `arn:aws:iam::aws:policy/AmazonEC2ReadOnlyAccess` and reading it back through ListAttachedUserPolicies) passed, so the handler reaches its state write without validating that the PolicyArn resolves.
Why: a client relying on AWS's behavior treats a 200 from AttachUserPolicy as proof the permission is now in force. Here a typo'd or deleted policy ARN is accepted, so the user is believed to hold a grant that exists nowhere — a privilege-management no-op reported as success — and the NoSuchEntity/PolicyNotAttachable branches a provisioning tool needs are never exercised.
Fix: the AttachUserPolicy handler's input validation — resolve PolicyArn against the customer-managed policy state and the built-in AWS-managed policy catalog before any attachment is recorded, and refuse an unresolvable ARN with NoSuchEntity carrying AWS's sentence (PolicyNotAttachable for a policy that exists but is not attachable). The same resolution belongs on the sibling AttachRolePolicy / AttachGroupPolicy paths that share it.
Traces: iam.op-contract-attach-user-policy.
