# REOPENS: AWS::SQS::Queue still has no in-place UPDATE path — a stack update re-creates the queue, so it is refused QueueAlreadyExists or silently replaced (4 causes)

> _Note: this issue was identified against the code base at commit `44d4304dbd56e0f97705f387ff3fc6793140eb84`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
UpdateStack

## Description
REOPENS 20261023T135552Z-cloudtrail-cloudformation-cloudformation-cannot-update-aws-sqs-queue-properties-in.md: its fix left the call refused. That issue's Cause 1 was exactly this — a stack update of an AWS::SQS::Queue property failing the stack. The NotImplemented prose it quoted is gone, but the update is still refused: the handler now answers 'Resource handler returned message: "A queue already exists with the same name and a different value for attribute <AttrName>" (HandlerErrorCode: InvalidRequest)' and the stack still rolls back, or (unnamed queues) the queue is replaced instead of updated. This is not a new defect, it is the same update path still not implemented.

There are 4 distinct causes in this issue; ALL FOUR must be closed before submitting. They are all faces of one missing component — the AWS::SQS::Queue resource provider's UPDATE hook — but each is separately observable and separately asserted, so each is listed with its own failing checks.

Placement note: these checks are listed by the suite under composite scenario headings (cloudformation__sqs, cloudformation__sns__sqs, cloudformation__s3__sqs, cloudformation__kms__sqs, cloudformation__iam__sqs, cloudformation__events__sqs, cloudformation__lambda__sqs, cloudformation__pipes__sqs, cloudformation__scheduler__sqs, cloudformation__cloudwatch__sqs, cloudformation__cloudwatch__s3__sns__sqs, cloudformation__sqs__ssm and sqs), so the per-service bootstrap gate cannot place them by exact equality against the bootstrapped token list; get_bootstrap_status reports an EMPTY pending set, so no constituent service (cloudformation, sqs, sns, kms, events, lambda, pipes, scheduler, cloudwatch, s3, ssm, iam) is un-bootstrapped and this is filed rather than deferred. The service token recorded here is the heading of the majority of the grounding checks.

Cause 1 of 4: an UpdateStack that changes a mutable attribute or the tags of an existing AWS::SQS::Queue is executed as a CreateQueue of the same name instead of SetQueueAttributes/TagQueue, so SQS refuses the conflict and the stack rolls back.
  AWS: an UpdateStack that changes a mutable AWS::SQS::Queue property (VisibilityTimeout, MessageRetentionPeriod, DelaySeconds, KmsMasterKeyId, Tags, ...) is an in-place update: the resource keeps its physical id, the stack reaches UPDATE_COMPLETE, and no resource failure is reported. Smithy (sqs): the mutable surface is SetQueueAttributes(QueueUrl, Attributes) and TagQueue/UntagQueue(QueueUrl, Tags) — neither is modeled with any already-exists error. CreateQueue is the only SQS operation that models QueueNameExists (httpError 400, awsQueryError code 'QueueAlreadyExists'), and AWS raises it only when a CreateQueue names an existing queue with DIFFERENT attribute values — which is precisely what the emulator is doing on an update. Recorded behavior for the refusal class: when SQS genuinely refuses a queue update, CloudFormation reports the resource row UPDATE_FAILED with 'Resource handler returned message: "<the SQS message>" (RequestToken: <id>, HandlerErrorCode: InvalidRequest)' — fixed text 'Resource handler returned message: "', '" (RequestToken: ', ', HandlerErrorCode: ', ')'; the token and code are from the request/state.
  Emulator: every such update fails the Queue resource with 'Resource handler returned message: "A queue already exists with the same name and a different value for attribute VisibilityTimeout" (RequestToken: <id>, HandlerErrorCode: InvalidRequest)' — the attribute name varies with the property changed (observed: VisibilityTimeout, KmsMasterKeyId) and the tag form is '"A queue already exists with the same name and a different value for tags "' (note AWS's trailing space inside that message is reproduced). The stack then settles UPDATE_ROLLBACK_COMPLETE with StackStatusReason 'The following resource(s) failed to update: [<LogicalId>]. '. The same refusal propagates through StackSets: the stack-set operation ends Status FAILED with StatusReason 'ResourceLogicalId:Queue, ResourceType:AWS::SQS::Queue, ResourceStatusReason:Resource handler returned message: "A queue already exists with the same name and a different value for attribute VisibilityTimeout" ...'. Because the update never lands, every differential leg built on it also fails: a control update that must succeed after a refused one (deploy-cfn-stack-update-to-unmapped-stage-rejected, cfn-update-out-of-range-visibility-timeout-rejected-rolls-back, cfn-stack-policy-protected-resource-replacement-rejected, cfn-rollback-trigger-alarm-reverts-update-and-restores-property, cfn-metric-breach-rolls-back-only-the-update-it-triggers), an executed change set (cfn-execute-obsolete-changeset-rejected), a parked UPDATE_FAILED stack whose effects a rollback must restore (cdk-rollback-restores-an-update-failed-stack-to-its-last-good-state reports the parked update's effects as ('30','v2','added') where the new VisibilityTimeout 60 was expected), and an attribute/encryption change that must take effect and keep earlier messages readable (sqs.deploy-cfn-attribute-update-takes-effect, sqs.deploy-cfn-encryption-update-keeps-earlier-messages-readable).
  Why: no infrastructure-as-code flow can ever evolve a queue. A client that changes a timeout, a retention period, a tag or an encryption key gets a terminal stack failure for a change AWS applies, must assume its template is wrong, and any rollback/alarm/stack-policy/change-set behavior that is only observable on top of a successful update is unreachable.
  Fix: the AWS::SQS::Queue resource provider's UPDATE hook in the CloudFormation service — it must diff the previous and desired properties and apply the mutable ones with SQS SetQueueAttributes plus TagQueue/UntagQueue against the EXISTING queue URL, never re-issue CreateQueue for a queue it already owns.
  Traces: cloudformation__sqs.cfn-sqs-queue-in-place-update-retained-replacement-then-not-found, cloudformation__sqs.cfn-update-out-of-range-visibility-timeout-rejected-rolls-back, cloudformation__sqs.cfn-stackset-instance-deployed-queue-is-functional-and-tracks-updates, cloudformation__sqs.stack-tag-removal-propagates-to-queue-without-replacement, cloudformation__sqs.cfn-execute-obsolete-changeset-rejected, cloudformation__sqs.cfn-stack-policy-protected-resource-replacement-rejected, cloudformation__iam__sqs.sqs-queue-handler-permission-update-denied-then-delete-denied-recovers, cloudformation__s3__sqs.deploy-cfn-stack-update-remaps-stage-in-place, cloudformation__s3__sqs.deploy-cfn-stack-update-to-unmapped-stage-rejected, cloudformation__s3__sqs.deploy-cloudformation-3-include-snippet-snapshotted-until-stack-update, cloudformation__cloudwatch__sqs.cfn-metric-breach-rolls-back-only-the-update-it-triggers, cloudformation__cloudwatch__s3__sns__sqs.cfn-rollback-trigger-alarm-reverts-update-and-restores-property, cloudformation__sqs__ssm.cdk-rollback-restores-an-update-failed-stack-to-its-last-good-state, sqs.deploy-cfn-attribute-update-takes-effect, sqs.deploy-cfn-encryption-update-keeps-earlier-messages-readable.

Cause 2 of 4: a queue whose name CloudFormation generated is REPLACED on a stack update (new physical id, new queue URL, the old queue deleted) instead of updated in place, so the queue URL the stack previously published stops existing.
  AWS: changing only a mutable property of an AWS::SQS::Queue never replaces it — the PhysicalResourceId (the queue URL) is unchanged, Ref/GetAtt keep resolving to the same queue, and messages already in the queue survive. A resource no part of whose template changed is not touched at all by an update. Replacement is reserved for create-only properties (QueueName, FifoQueue), and a replaced queue gets a NEW generated name.
  Emulator: an update that changes a single mutable attribute moves the queue's PhysicalResourceId by appending a fresh suffix to the generated name — observed 'https://<host>/<account>/sim2real-behav-cfnres-own-<id>-Queue-21DED5433872' becoming '...-Queue-21DED5433872-bb5547a42227' for a MessageRetentionPeriod-only change — and the previous queue is gone: the next SQS call on the URL the stack reported is refused 'An error occurred (AWS.SimpleQueueService.NonExistentQueue) when calling the ReceiveMessage operation: The specified queue does not exist.' (SendMessage likewise). Hypothesis: the same re-create-per-update path as Cause 1, taking the generated-name branch where no name collision is possible; it also fires in the six '...-in-place-update-retained-replacement-then-not-found' checks, whose queue resource is NOT changed by the update at all (only a sibling AWS::Events::EventBus description, AWS::SNS::Topic/Subscription property, AWS::Pipes::Pipe, AWS::Scheduler::Schedule or AWS::Lambda::EventSourceMapping is), yet whose next ReceiveMessage/SendMessage on the stack-reported queue URL answers NonExistentQueue.
  Why: worse than a failed deploy — it silently destroys a queue and every message in it, and the queue URL a client read from Ref/GetAtt/Outputs or from DescribeStackResources before the update becomes a 400 NonExistentQueue afterwards. Any consumer, event-source mapping, pipe, schedule or subscription pointed at the old URL/ARN is dead after an unrelated stack update.
  Fix: the AWS::SQS::Queue resource provider's UPDATE hook and its replacement classification in the CloudFormation service — only create-only properties may classify Replacement, a mutable-only diff must keep the physical id, and a resource whose properties did not change must not be re-created.

Cause 3 of 4: when a nested child stack's queue update fails, the PARENT's rollback itself fails — the parent settles UPDATE_ROLLBACK_FAILED.
  AWS: a failed update of a nested AWS::CloudFormation::Stack rolls the parent back to its last good state and the parent settles UPDATE_ROLLBACK_COMPLETE; UPDATE_ROLLBACK_FAILED is reserved for a rollback the service could not perform (and then ContinueUpdateRollback is the documented recovery). Rolling a child queue's attribute back to the value it already has can never fail.
  Emulator: the parent update ends 'UPDATE_ROLLBACK_FAILED'. So on top of the refused child update (Cause 1), the rollback path for nested stacks does not complete either, leaving the stack in a state that needs manual intervention.
  Why: a client cannot recover the stack with a plain update after a failed nested deploy; CI that deploys nested stacks is wedged on the first failure.
  Fix: the nested-stack (AWS::CloudFormation::Stack) rollback path in the CloudFormation service — a child rollback whose resources are restored to their recorded previous properties must reach UPDATE_ROLLBACK_COMPLETE.
  Traces: cloudformation__cloudwatch__s3__sns__sqs.cfn-changeset-include-nested-stacks-lists-child-resource-changes.

Cause 4 of 4: the queue encryption transitions (swapping KmsMasterKeyId, and moving from SSE-KMS to SqsManagedSseEnabled) fail the queue update and roll the stack back.
  AWS: the encryption attributes are mutable: create with KmsMasterKeyId + KmsDataKeyReusePeriodSeconds, update to a DIFFERENT key/period, then update with KmsMasterKeyId absent and SqsManagedSseEnabled=true — each stage is an in-place update reaching UPDATE_COMPLETE with the same QueueUrl/Arn, after which GetQueueAttributes no longer reports KmsMasterKeyId and reports SqsManagedSseEnabled='true', and the queue still round-trips a message. Smithy (sqs): these are SetQueueAttributes attributes; SetQueueAttributes models no already-exists error.
  Emulator: the key-swap update (the SECOND stage, which previously passed) now settles 'UPDATE_ROLLBACK_COMPLETE' with 'The following resource(s) failed to update: [Queue]. ', so the SSE-KMS -> SQS-managed stage is never reached.
  Note for the fixer: open issue 20261117T122437Z-cloudformation-kms-sqs-2-net-new-causes-a.md already describes the SSE-KMS -> SqsManagedSseEnabled stage of this check, but the failure has MOVED EARLIER (to the key swap) so that issue no longer carries this check's replay key and will not re-replay it; it is filed here so the regression is not lost.   Why: a stack cannot rotate a queue's customer managed key or migrate a queue to SQS-managed encryption at all — routine, supported changes that now fail the deploy and leave the queue on the old key.
  Fix: the AWS::SQS::Queue resource provider's UPDATE hook for the encryption attributes, and SQS SetQueueAttributes' handling of changing KmsMasterKeyId and of clearing it while enabling SqsManagedSseEnabled (queue-attribute state/validation).
  Traces: cloudformation__kms__sqs.cfn-sqs-queue-kms-sse-properties-update-in-place-round-trip.
