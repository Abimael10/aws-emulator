# artifact ListReports first page both omits published reports and misprojects ReportSummary members (2 causes)

> _Note: this issue was identified against the code base at commit `4e36bbfa0b5661aa2fd9826663b014bc119c6585`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
ListReports

## Description
GET /v1/report/list (ListReports) answers HTTP 200, and the 200 body diverges from the recorded AWS Artifact catalog in two independent ways in the same response: a large set of published report resources is absent from the page altogether, and the entries that ARE present carry member values belonging to a different report than the entry's own id/arn/version names. Both causes are observed on fixture artifact-catalog-list-reports, step task#1 (expected_status 200, actual_status 200, verdict mismatch, affected_count 1). This issue carries 2 causes; both must be closed before it is submitted.

Cause 1 of 2: the first page enumerates only a subset of the published report catalog, so most published report resources are missing entirely (fixture artifact-catalog-list-reports, step task#1).
AWS: Smithy (com.amazonaws.artifact#Artifact) models ListReports as GET /v1/report/list returning 200 with ListReportsResponse.reports: ReportsList of ReportSummary plus nextToken, @paginated{inputToken: nextToken, outputToken: nextToken, pageSize: maxResults, items: reports}; maxResults is MaxResultsAttribute @range min 1 max 300 and nextToken is NextTokenAttribute @length 1..2048. The model fixes the pagination contract but not the catalog contents, so for which reports exist this is recorded behavior only: AWS returns, for a page of the requested size, the published report resources of the account's Artifact catalog, and signals a continuation with nextToken rather than silently dropping entries. A client that walks the pages must see every PUBLISHED report exactly once.
Emulator: the response is missing whole ReportSummary entries. The cluster's divergence key lists several hundred member-less whole-entry paths, i.e. paths of the form $.reports[arn="arn:aws:artifact:<region>::report/report-<id>:<version>"] with no member suffix, meaning the recorded entry with that arn has no counterpart anywhere in the emulator's response (for example report-0nXRsThNM4eHtuyn:4, report-0rFcyFMKMKeV4r7E:1, report-0tuV14iFC4pwSHN8:1, report-1KaYpOBS1YqdkgLq:2, report-LIE0oFai46aosWjf:58, report-pMuIoxgVQUTXLcGa:30). The missing set is the dominant part of the divergence, not a tail.
Why: a client relying on AWS's behavior cannot find a report it knows exists. Compliance automation that enumerates the catalog and then calls GetTermForReport/GetReport for a specific report (by series, category or name) concludes the report is not published and silently skips it; an auditor's download job produces an incomplete evidence set with no error to detect, because the call returns 200 and a well-formed, merely shorter, list.
Fix: the artifact ListReports handler and the report-catalog state it pages over - the page must be cut from the full stored set of PUBLISHED report resources (ordered deterministically, honouring maxResults and emitting nextToken when more remain) rather than from a reduced in-memory seed subset.
Note: resolved issue 20261115T113946Z-artifact-listreports-serves-a-truncated-report-catalog-the.md described a truncated first page and is marked fixed; it does NOT cover this, because the replay of the current checkout still reports the recorded first-page entries as missing. A resolved issue never covers a live failure.

Cause 2 of 2: each returned ReportSummary is populated with synthesized/re-authored content and a coarser timestamp rendering instead of the stored metadata of the report its id/arn/version identifies (fixture artifact-catalog-list-reports, step task#1).
AWS: Smithy models ReportSummary.name/series/category/companyName/productName as ShortStringAttribute (@length 1..256, @pattern ^[a-zA-Z0-9_\-\s]*$), description as LongStringAttribute (@length 1..2048, @pattern ^[^<>]*$), id as ReportId (@pattern ^report-[a-zA-Z0-9]{16}$), version as VersionAttribute (long, @range min 1), acceptanceType as the enum AcceptanceType whose values are exactly PASSTHROUGH and EXPLICIT (PASSTHROUGH documented as 'Do not require explicit click-through acceptance of the Term associated with this Report', EXPLICIT as 'Require explicit click-through acceptance'), and periodStart/periodEnd as TimestampAttribute with @timestampFormat date-time. The model fixes the shape, not the values, so for the content this is recorded behavior only: every member of an entry is a property of the report resource that entry's id/arn/version names - its own published title, its own published description text, its own series, its own acceptance type, and the start/end instants of the period that report covers, serialized as a date-time that carries the millisecond component AWS emits (YYYY-MM-DDTHH:MM:SS.mmmZ). Which values an entry carries is determined by which catalog entry it is, never by its position in the list or by the service it happens to be about.
Emulator: for one and the same arn the emulator returns another report's metadata, re-worded prose, the opposite acceptance type and a different period, and renders the period timestamps without milliseconds. Verbatim from the replay detail: $.reports[arn="arn:aws:artifact:us-east-1::report/report-7g5j2DTVeNXWx7St:1"].name expected 'Accessibility Conformance Report (VPAT) - AWS Transfer Family', got 'Accessibility Conformance Report VPAT - AWS Management Console'; the same entry's .description expected the published one-paragraph ACR/VPAT boilerplate ('This document is an Accessibility Conformance Report (ACR) based on the ITI VPAT(R) and is intended to provide information on the accessibility of the relevant AWS product or service. The VPAT references accessibility standards for information and communications technology including: Section 508 (U.S.), EN 301 549 (EU), and W3C/WAI WCAG.'), got a multi-sentence re-authored narrative about the AWS Management Console; the same entry's .periodStart expected '2024-11-01T00:00:00.000Z', got '2024-01-01T00:00:00Z'; $.reports[arn="arn:aws:artifact:us-east-1::report/report-5eevElBv6MyRmQsD:7"].acceptanceType expected 'PASSTHROUGH', got 'EXPLICIT', with .description, .name, .periodStart and .periodEnd of that same entry also value_mismatch. The cluster's divergence key repeats the member set .name, .description, .series, .acceptanceType, .periodStart, .periodEnd across further arns (report-073F0fUCdVVNKJrF:3, report-0QjvdIs6Bsw4uPxb:2, report-0c1IXmudeXuTlHJJ:3), so this is the entry projection, not a single bad row. Fixed text vs variable parts: none of the quoted strings is a per-run value - the report name, description, series, acceptanceType and period instants are catalog content keyed by the report id/arn/version in the request's page, so the requirement is that each member equal the stored value for that id, and that periodStart/periodEnd be rendered as date-time including the millisecond component.
Why: a client relying on AWS's behavior reads the wrong compliance document. Report pickers and compliance automation that select by name/series/category get another product's report presented under the arn they asked for (a Transfer Family ACR served as a Management Console one); code that branches on acceptanceType to decide whether GetTermForReport click-through acceptance is required takes the opposite branch, because PASSTHROUGH and EXPLICIT mean opposite things; auditors filtering on periodStart/periodEnd select the wrong reporting period, and a date-time without milliseconds breaks exact comparison against real/recorded responses.
Fix: the artifact ListReports response serializer and the report-catalog state it projects from - each ReportSummary member must be read from the stored catalog entry identified by that id/arn/version (never templated or regenerated from a service name), and the timestamp serializer for TimestampAttribute must emit date-time with the millisecond component.
