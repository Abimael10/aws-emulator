# Elastic Beanstalk option catalog omits aws:autoscaling:launchconfiguration/DisableDefaultEC2SecurityGroup, so a CloudFormation AWS::ElasticBeanstalk::Environment that sets it is rejected as an unknown configuration setting and the stack rolls back (1 cause)

> _Note: this issue was identified against the code base at commit `d1b4a778e7e158b48ec61c845affa7d1f6ee20bd`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
CreateEnvironment

## Description
Cause 1 of 1: the Elastic Beanstalk configuration-option catalog does not publish `DisableDefaultEC2SecurityGroup` in the `aws:autoscaling:launchconfiguration` namespace, so every CreateEnvironment (and the AWS::ElasticBeanstalk::Environment resource that wraps it) that sets that option is refused as if the option did not exist, and the CloudFormation stack that contains the environment rolls back. Failing checks: cloudformation__elasticbeanstalk.cfn-elasticbeanstalk-environment-in-place-update-keeps-instance-then-terminated, cloudformation__elasticbeanstalk.cfn-elasticbeanstalk-environment-retained-replacement-keeps-old-running-then-terminated, cloudformation__elasticbeanstalk.deploy-elasticbeanstalk-environment-round-trip-and-delete.

AWS: `DisableDefaultEC2SecurityGroup` is a documented, generally-available option of the `aws:autoscaling:launchconfiguration` namespace (Elastic Beanstalk "General options for all environments" reference): a boolean Scalar, valid values `true`/`false`, default `false`, which when `true` keeps Elastic Beanstalk from attaching its default EC2 security group (the one that opens the instance port to the internet) to the environment's instances. Because it is a real option of a namespace every platform version defines, AWS accepts a CreateEnvironment / AWS::ElasticBeanstalk::Environment OptionSettings entry naming it: the environment reaches `Ready`, the stack reaches `CREATE_COMPLETE`, DescribeConfigurationOptions lists the option, and DescribeConfigurationSettings echoes the value the request set. Smithy: CreateEnvironment.OptionSettings -> ConfigurationOptionSettingsList (ConfigurationOptionSetting {Namespace, OptionName, Value}); DescribeConfigurationOptions publishes ConfigurationOptionDescriptionsList; CreateEnvironment models only InsufficientPrivilegesException and TooManyEnvironmentsException, so nothing in the model makes a valid option setting a refusal. The "Invalid option specification (Namespace: '<ns>', OptionName: '<name>'): Unknown configuration setting." sentence is AWS's wording for a specification that resolves to NO option — correct text, wrongly applied here.

Emulator: the catalog's `aws:autoscaling:launchconfiguration` entries are DisableIMDSv1, EC2KeyName, IamInstanceProfile, InstanceType, MonitoringInterval, RootVolumeSize, RootVolumeType, SecurityGroups (and siblings) — `DisableDefaultEC2SecurityGroup` is absent. The settings validation resolves `(Namespace, OptionName)` against that same catalog, finds no option of that name in the namespace, and emits an `error`-severity ValidationMessage "Invalid option specification (Namespace: 'aws:autoscaling:launchconfiguration', OptionName: 'DisableDefaultEC2SecurityGroup'): Unknown configuration setting." CreateEnvironment therefore refuses the call, and the CloudFormation resource reports `CREATE_FAILED` with `Resource handler returned message: "Configuration validation exception: Invalid option specification (Namespace: 'aws:autoscaling:launchconfiguration', OptionName: 'DisableDefaultEC2SecurityGroup'): Unknown configuration setting." (RequestToken: <token>, HandlerErrorCode: InvalidRequest)` and the stack ends `ROLLBACK_COMPLETE` ("The following resource(s) failed to create: [Environment]. "). In that message only the namespace and option name are echoed from the request and the RequestToken is per-run; the rest is fixed text — and the whole message should not be produced at all for this option.

Why: a client that provisions a hardened Elastic Beanstalk environment the documented way — its own VPC, its own security group, and `DisableDefaultEC2SecurityGroup=true` so Beanstalk does not re-open the instance port — cannot create that environment at all against the emulator. Any CloudFormation template or CDK/Terraform module carrying this option fails at CREATE and rolls back the whole stack, so none of the downstream behavior (Ref/GetAtt outputs, DescribeConfigurationSettings echo, in-place update, retained replacement, terminate tombstone) is reachable. Conversely, a user who typo'd an option name gets the same message as one who used a valid option, so the message no longer distinguishes the two.

Fix: add the option to the service-owned configuration-option catalog (the `aws:autoscaling:launchconfiguration` table in the Elastic Beanstalk state's configuration_option_catalog module) as a boolean Scalar with ValueOptions ["false","true"] and default "false", so DescribeConfigurationOptions publishes it and the shared settings validation resolves it instead of reporting it unknown; then make the environment launch honor it (do not attach the default EC2 security group when it is `true`) so DescribeConfigurationSettings echoes the caller's value. No change to the unknown-specification message itself is wanted — it is correct for genuinely unresolvable specifications.

Traces: see trace_ids. Code: services/service-com-amazonaws-elasticbeanstalk-awselasticbeanstalkservice/src/state/configuration_option_catalog.rs lines 286-347 (the launch-configuration entries, with no DisableDefaultEC2SecurityGroup); services/service-com-amazonaws-elasticbeanstalk-awselasticbeanstalkservice/src/state/configuration_setting_validation.rs lines 92-103 (`unknown_specification_message`) and lines 10-17 (the doc stating a name not in the catalog names no option).

1. eb = client('elasticbeanstalk'); pick a solution stack from ListAvailableSolutionStacks (e.g. one 'running Python').
2. The emulator refuses it with the configuration-validation message above; AWS accepts it.
3. Equivalently via CloudFormation: CreateStack with an AWS::ElasticBeanstalk::Application plus an AWS::ElasticBeanstalk::Environment whose OptionSettings include that namespace/option pair, then poll DescribeStacks. The Environment goes CREATE_FAILED and the stack ends ROLLBACK_COMPLETE; DescribeStackEvents shows the 'Unknown configuration setting.' reason.
4. Cross-check: DescribeConfigurationOptions(SolutionStackName=<stack>) — no ConfigurationOptionDescription with OptionName 'DisableDefaultEC2SecurityGroup' is published, which is the root of the refusal.
5. Re-replay the three checks listed in trace_ids to confirm a fix.
