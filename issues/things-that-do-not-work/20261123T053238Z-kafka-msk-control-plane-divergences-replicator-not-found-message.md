# MSK control-plane divergences: replicator not-found message, server-property refusal version list, CreateVpcConnection refusal class/resource, SCRAM secret-ARN validation order, and two lifecycles that never settle (7 causes)

> _Note: this issue was identified against the code base at commit `089d95727e98bbbdc8a21b7993743873cfe21178`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
CreateVpcConnection

## Description
SEVEN distinct net-new root causes in the kafka (MSK) service, each grounded in failing behavioral checks that the suite report marked neither ALREADY FILED nor OWNED by an open issue. Each cause below must be closed separately before this issue is submitted.

=== Cause 1 of 7: the replicator not-found refusal drops MSK's "Invalid parameter replicatorArn: " prefix. (Failing checks: kafka.delete-nonexistent-resources-should-fail, kafka.replicator-read-paths-report-clean-miss, kafka.update-replication-info-nonexistent-replicator-rejected.)
AWS: Smithy com.amazonaws.kafka#Kafka binds NotFoundException (httpError 404) to DeleteReplicator (DELETE /replication/v1/replicators/{ReplicatorArn}), DescribeReplicator (GET /replication/v1/replicators/{ReplicatorArn}) and UpdateReplicationInfo (PUT /replication/v1/replicators/{ReplicatorArn}/replication-info); in all three ReplicatorArn is the @required @httpLabel. Recorded behavior: for a replicator ARN that was never issued, MSK answers 404 NotFoundException with Message "Invalid parameter replicatorArn: The requested resource doesn’t exist." Message anatomy: the whole string is FIXED text except the parameter name "replicatorArn", which is the modeled wire (lower-camel) name of the offending input member; the apostrophe in "doesn’t" is U+2019, not ASCII. The replicator family is deliberately different from the other MSK resources: the same checks confirm DeleteCluster, DeleteTopic, DeleteChannel and DeleteVpcConnection answer the unprefixed "The requested resource doesn’t exist." and those assertions pass.
Emulator: answers 404 NotFoundException but with Message "The requested resource doesn’t exist." — i.e. the replicator-scoped paths reuse the generic not-found message and never prepend the "Invalid parameter <wire member>: " clause. Observed on DeleteReplicator (delete-nonexistent-resources-should-fail) and on DescribeReplicator reached both directly (replicator-read-paths-report-clean-miss) and after UpdateReplicationInfo (update-replication-info-nonexistent-replicator-rejected).
Why: a client or operator that matches on the refusal text to learn WHICH parameter was wrong gets no attribution; for UpdateReplicationInfo, whose request carries four other ARNs (source/target cluster ARNs and ids), the caller cannot tell from the message that it is the replicatorArn that does not resolve, and diff-based parity harnesses flag the message as a mismatch.
Fix: the not-found path of the replicator handlers (DeleteReplicator, DescribeReplicator, UpdateReplicationInfo, and the shared replicator-ARN resolution they call) in the kafka service crate — emit the replicator-ARN-attributed fixed message for this resource family instead of the generic one. Related open/fixed issues that do NOT cover this: 20261029T202809Z-kafka-msk-error-payloads-name-the-smithy-member-instead.md (invalidParameter member naming, not the message text) and fixed 20261114T072820Z-kafka-msk-deletereplicator-refusal-blames-currentversion-instead-of-the.md (which parameter the refusal blamed, for an INVALID — not absent — ARN).
Traces: kafka.delete-nonexistent-resources-should-fail, kafka.replicator-read-paths-report-clean-miss, kafka.update-replication-info-nonexistent-replicator-rejected.

=== Cause 2 of 7: CreateConfiguration's unsupported-server-property refusal names the whole historical version catalog in ascending order instead of the versions MSK checks the key against. (Failing checks: kafka.configuration-property-value-type-accepted, kafka.configuration-reserved-broker-property-rejected.)
AWS: Smithy models CreateConfiguration as POST /v1/configurations with ServerProperties (@required blob, jsonName serverProperties) and binds BadRequestException (httpError 400); the model says nothing about property-key validation, so the rest is recorded behavior only. MSK refuses a ServerProperties key it does not support — both an unknown key (nosuchkey.at.all) and a key MSK reserves for itself (broker.id) — with HTTP 400, error code BadRequestException, and a Message that is a pretty-printed JSON array of per-property objects:
[ {\n  "name" : "<key>",\n  "value" : "<value>",\n  "errorMessages" : [ "Key '<key>' is not supported by at least one Apache Kafka version. Key checked against versions: [<versions>]" ]\n} ]
Message anatomy: the envelope and the sentence are FIXED text; <key> and <value> are taken verbatim from the submitted ServerProperties line; <versions> is the service's own set of versions the key is checked against, rendered in MSK's own enumeration order and containing repeats — as recorded: 3.7.x.kraft, 4.1.x.kraft, 3.9.x, 3.6.0, 3.8.x.kraft, 3.9.x.kraft, 3.7.x, 3.8.x, 4.2.x, 3.8.x, 3.9.x, 4.0.x.kraft. The requirement is that this is the currently-checked (live) version set in service order, NOT the full published catalog sorted ascending; the recorded tokens are the example of that set, not a literal constant.
Emulator: serves the right status (400), the right code (BadRequestException) and the right envelope, but renders <versions> as its entire historical catalog in ascending order: [1.1.1, 2.1.0, 2.2.1, 2.3.1, 2.4.1, 2.4.1.1, 2.5.1, 2.6.0, 2.6.1, 2.6.2, 2.6.3, 2.7.0, 2.7.1, 2.7.2, 2.8.0, 2.8.1, 2.8.2.tiered, 3.1.1, 3.2.0, 3.3.1, 3.3.2, 3.4.0, 3.5.1, 3.6.0, 3.6.0.1, 3.7.x, 3.7.x.kraft, 3.8.x, 3.8.x.kraft, 3.9.x, 3.9.x.kraft, 4.0.x.kraft, 4.1.x.kraft, 4.2.x.kraft] — identical for the unknown key and for the reserved broker.id key.
Why: the refusal's only actionable content is which versions were consulted; a client (or a human) reading it is told the key was checked against long-retired versions the service no longer offers, so it cannot work out which Kafka version to target, and parity assertions on the message fail.
Fix: the version list rendered by CreateConfiguration's ServerProperties key validation in the kafka service crate — render the versions the validator actually checks against, in the service's publication order, not the sorted full catalog. Related: fixed 20261112T094430Z-kafka-4-net-new-causes-createconfiguration-s-per.md fixed the envelope's JSON formatting and request-scoping, and open 20261102T083811Z-kafka-createconfiguration-s-unsupported-kafkaversions-refusal-message-is-the.md covers the unsupported-KafkaVersions (not server-property) refusal; neither carries these checks' replay keys.
Traces: kafka.configuration-property-value-type-accepted, kafka.configuration-reserved-broker-property-rejected.

=== Cause 3 of 7: CreateVpcConnection answers NotFoundException — an error it does not even model — for a cluster ARN whose resource segment is malformed. (Failing check: kafka.create-vpc-connection-malformed-cluster-arn-rejected.)
AWS: Smithy models CreateVpcConnection as POST /v1/vpc-connection with TargetClusterArn @required (jsonName targetClusterArn), and its bound error set is BadRequestException 400, ForbiddenException 403, UnauthorizedException 401, TooManyRequestsException 429, InternalServerErrorException 500, ServiceUnavailableException 503 — NotFoundException is NOT bound to this operation. Recorded behavior: a TargetClusterArn with this account's correct kafka cluster ARN prefix but a structurally invalid trailing id segment is refused either by authorization (AccessDeniedException, message "User: <caller ARN> is not authorized to perform: kafka:CreateVpcConnection on resource: *" — fixed text with the caller's own principal ARN as its only variable) or by Kafka input validation (BadRequestException); never as not-found.
Emulator: answers error code NotFoundException. No VPC connection is created, so only the refusal class is wrong — but it is a class the operation's modeled error union cannot carry, so an SDK dispatching on modeled errors has no branch for it.
Why: a client distinguishing "I am not allowed to do this / my input is malformed" from "the target does not exist" takes the wrong branch, and retry/backoff policies keyed on modeled error shapes see an unmodeled type.
Fix: CreateVpcConnection's handler in the kafka service crate — validate/authorize the TargetClusterArn before resolving it as an existing resource, and refuse with the authorization denial or BadRequestException rather than mapping a failed cluster lookup to NotFoundException. Related: fixed 20261104T171616Z-kafka-createvpcconnection-skips-msk-s-cluster-state-and-sasl.md covered the cluster-state/SASL-IAM gates for this operation and does not carry this check's replay key.
Traces: kafka.create-vpc-connection-malformed-cluster-arn-rejected.

=== Cause 4 of 7: CreateVpcConnection's authorization denial names the submitted TargetClusterArn as the resource where MSK names "*". (Failing check: kafka.vpc-connection-malformed-target-cluster-rejected.)
AWS: recorded behavior only (the model binds no AccessDeniedException shape; the denial is the IAM-layer refusal). For a TargetClusterArn that is not an ARN at all, MSK answers AccessDeniedException whose Message is "User: <caller ARN> is not authorized to perform: kafka:CreateVpcConnection on resource: *". Message anatomy: "User: ", " is not authorized to perform: kafka:CreateVpcConnection on resource: " and the resource token "*" are FIXED; the only variable is the caller's principal ARN, taken from the request's credentials. Because the submitted value is not a parseable ARN, no resource can be attributed to it, so the denial is rendered against "*" — the request's raw input value is never echoed.
Emulator: answers the right code (AccessDeniedException) and the right principal, but renders the resource token as the raw request value, e.g. "... on resource: not-an-arn-at-all" instead of "... on resource: *".
Why: the denial message is what operators paste into policy work; naming an unparseable literal as the resource suggests a resource-scoped grant would fix it, when the action is denied at "*". It also reflects request input back into an authorization message, which is a divergence a client comparing denials cannot normalize away.
Fix: the authorization-denial rendering for CreateVpcConnection in the kafka service crate — when the target ARN does not parse, render "*" as the resource token rather than the submitted string. Related: fixed 20261118T122856Z-kafka-msk-cluster-arn-authorization-refusals-the-accessdenied-resource.md covered the resource token for cluster-ARN denials on other operations and carries no replay key for this check.
Traces: kafka.vpc-connection-malformed-target-cluster-rejected.

=== Cause 5 of 7: BatchAssociateScramSecret answers the cluster not-found 404 for a SecretArnList entry that is not a Secrets Manager ARN at all, instead of 400 BadRequestException. (Failing check: kafka.scram-associate-invalid-arn-rejected.)
AWS: Smithy models BatchAssociateScramSecret as POST /v1/clusters/{ClusterArn}/scram-secrets with ClusterArn @required @httpLabel and SecretArnList @required (jsonName secretArnList), binding both BadRequestException (400) and NotFoundException (404). Recorded behavior: a SecretArnList entry that is not an ARN ("not-a-secrets-manager-arn") is refused with BadRequestException, Message "The provided secret ARN is invalid." — entirely FIXED text, no variable part — even when the path cluster also does not exist; whereas a WELL-FORMED Secrets Manager ARN against a nonexistent cluster is refused with NotFoundException, Message "The requested resource doesn’t exist." (fixed text, U+2019 apostrophe). The second half of that contract passes; the first half does not.
Emulator: answers ('NotFoundException', 'The requested resource doesn’t exist.') for the syntactically invalid secret ARN — it resolves the path cluster first and never reaches the secret-ARN syntax check, so the two input classes collapse onto one refusal.
Why: a client that submits a bad secret ARN is told the cluster is missing; it retries cluster creation or treats the call as a transient not-found instead of correcting the obviously malformed secret, and 404-means-already-gone cleanup paths mis-fire.
Fix: BatchAssociateScramSecret's validation order in the kafka service crate — the SecretArnList syntax check (is each entry a Secrets Manager secret ARN) must run ahead of cluster resolution, while a well-formed secret against an absent cluster keeps the 404. NOTE the interaction: open issue 20261116T025242Z-kafka-msk-scram-batch-operations-validate-secretarnlist-before-cluster.md asks for cluster resolution to precede SecretArnList validation for its own recorded input; the emulator now does exactly that and this check fails. Hypothesis (neither the model nor these recordings state it): the distinguishing axis is SYNTAX vs EXISTENCE — an entry that is not a Secrets Manager ARN is a 400 before any lookup, while a well-formed-but-unknown secret defers to the cluster's 404. Whoever fixes this must reconcile the two orders rather than flipping the single gate back.
Traces: kafka.scram-associate-invalid-arn-rejected.

=== Cause 6 of 7: the channel lifecycle on an Express cluster never settles, so the unicode round-trip reaches no verdict. (Failing check: kafka.channel-update-unicode-fields-round-trip.)
AWS: Smithy models CreateChannel/DescribeChannel/UpdateChannel on /v1/clusters/{ClusterArn}/channels[/{ChannelArn}], with Status drawn from the ChannelStatus enum (CREATING, ACTIVE, UPDATING, DELETING, FAILED, SUSPENDING, SUSPENDED); CreateChannel echoes no terminal status, so DescribeChannel is the only observation path and a created channel must reach ACTIVE, and an UpdateChannel setting DataFreshnessInSeconds=600 must become observable there. Recorded behavior: the sequence CreateClusterV2(Express) -> cluster ACTIVE -> CreateTopic -> topic ACTIVE -> CreateChannel -> channel ACTIVE -> UpdateChannel -> DescribeChannel completes at AWS cadences well inside the check's budget.
Emulator: the check produces the bare detail 'Error: Check timed out after 60.0s' — no HTTP status, no error code, no traceback frame — so some state in that chain (Express cluster ACTIVE, topic ACTIVE, or the channel's CREATING -> ACTIVE) never reaches its terminal value and the first waiter consumes the whole wall-clock ceiling; no assertion on the unicode tag value, channel name or S3 output prefix is ever evaluated.
Why: a client creating an MSK data-delivery channel and waiting for it to be usable hangs on its own waiter, and because CreateChannel echoes no state it cannot distinguish 'still provisioning' from 'silently dropped'. The unicode representation guarantee (tag value, name and prefix returned unchanged across an update) is unverifiable.
Fix: the channel/Express-cluster/topic state machines in the kafka service's state layer plus the CreateChannel and DescribeChannel handlers — each created resource must settle to its terminal state within a probe or two at an AWS-sized cadence. This is a RECURRENCE of fixed 20261111T052401Z-kafka-msk-channel-sequence-on-an-express-cluster-reaches.md (same check, same 60 s timeout) and of fixed 20261104T202326Z-kafka-channel-unicode-round-trip-never-reaches-a-verdict.md; open 20261114T065925Z-kafka-msk-asynchronous-lifecycles-never-settle-channel-configuration-delete.md covers the sibling kafka.channel-list-pagination-and-filter-consistency check and does NOT carry this check's replay key.

=== Cause 7 of 7: the cross-cluster replicator end-to-end flow never settles, so topic sync and teardown reach no verdict. (Failing check: kafka.e2e-replicator-cross-cluster-topic-sync-teardown.)
AWS: Smithy models CreateReplicator/DescribeReplicator (/replication/v1/replicators[/{ReplicatorArn}]) with ReplicatorState, and ListTopics/DeleteTopic/DeleteReplicator for the observation and teardown legs. Recorded behavior: with two 3-broker clusters (NumberOfBrokerNodes a multiple of the client-subnet count), the replicator reaches RUNNING, a source topic created afterwards appears in the target cluster's ListTopics, and DeleteTopic and DeleteReplicator each end in independently observed absence — the latter refusing the gone ARN with NotFoundException "Invalid parameter replicatorArn: The requested resource doesn’t exist." Emulator: the check ends on the bare detail 'Error: Check timed out after 60.0s' — the bring-up chain (service-execution role -> source and target clusters ACTIVE -> replicator RUNNING) never settles, so the first waiter spends the whole ceiling and neither the topic-sync assertion nor the teardown-absence assertions are evaluated.
Why: a client that provisions an MSK Replicator and waits for RUNNING before producing never gets a usable cluster pair, and the replication guarantee this flow exists to prove is unobservable.
Fix: the cluster-provisioning and replicator state machines in the kafka service's state layer plus the CreateReplicator/DescribeReplicator handlers — both clusters must settle to ACTIVE and the replicator to RUNNING at AWS-sized cadences, and the replicated-topic projection must follow.
