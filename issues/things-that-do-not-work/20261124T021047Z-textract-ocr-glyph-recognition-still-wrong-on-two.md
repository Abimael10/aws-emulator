# Textract OCR glyph recognition still wrong on two un-owned paths: TABLES CELL word text (AnalyzeDocument TABLES+FORMS) and S3Object-sourced DetectDocumentText (glyphs substituted and word breaks lost)

> _Note: this issue was identified against the code base at commit `428a0a660ec8f21315f2c255010ca5b9d3af4eb5`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
AnalyzeDocument

## Description
This issue reports 2 root causes, grounded in 2 failing checks. Both are HTTP 200 responses whose structure validates while the recognised TEXT is not the text rasterised onto the page, so both are silent data-corruption paths.

Context on what is already filed. The open issue 20261119T223911Z-textract-ocr-still-misclassifies-glyphs-inside-recognised-words.md describes glyph misclassification but carries replay keys only for textract.analyze-document-forms-extracts-key-value-pairs and textract.analyze-expense-extracts-summary-fields; the replay marks those two OWNED and marks the two checks below as having NO owner, so they are not covered by it. The open 20261114T190633Z (QUERY_RESULT leading characters), 20261030T113700Z (corrupt-image positive control) and 20261109T200548Z (CloudFormation AWS::Textract::Adapter) issues own their own checks and were skipped; the open 20261115T094519Z-textract-synchronous-blocks-geometry-confidence-and-text-do.md is a WIRE issue on Blocks geometry/confidence and carries no behavioral key for either check below. The resolved 20261110T200812Z-textract-analyzedocument-tables-cell-blocks-carry-garbled-text.md and 20261113T235649Z-textract-raster-reading-is-wrong-end-to-end.md addressed the TABLES CELL structure and the raster read path; the CELL blocks and their CHILD WORD relationships are now produced correctly (that part of the check passes), so this is not a reopened refusal — neither failure is a refusal, both calls return 200.

Cause 1 of 2 — AnalyzeDocument with FeatureTypes=[TABLES, FORMS]: the WORD children of the TABLE's CELL blocks spell characters that were never drawn, including a token where two drawn glyphs collapse into one.
AWS: Smithy (services/service-com-amazonaws-textract-textract/smithy-model/com-amazonaws-textract-textract.json): AnalyzeDocument input {Document required, FeatureTypes required, HumanLoopConfig, QueriesConfig, AdaptersConfig} / output {DocumentMetadata, Blocks, HumanLoopActivationOutput, AnalyzeDocumentModelVersion}; BlockType enum includes TABLE, CELL, WORD, LINE, KEY_VALUE_SET; Block$Text is documented "The word or line of text that's recognized by Amazon Textract", and Block$BlockType documents WORD as "one or more ISO basic Latin script characters that aren't separated by spaces" and CELL/TABLE as the table structure of the page. The requirement is general and character-exact: for ANY ASCII text rasterised into a ruled grid, the CHILD WORD text of each CELL spells exactly the characters drawn in that grid cell, one WORD token per whitespace-separated drawn word. No error is involved; the call is a 200.
Emulator: the TABLE and its CELL blocks and CHILD WORD relationships are correct (the check's TABLE/cell-count assertions pass) but the cell text is misrecognised. For a 2x2 grid drawing the header row "Item", "Price" and the data row "Widget", "10.00", the four cell texts come back as ['IWM', 'PRICE', 'WIDQET', '10.00']: the drawn word "Item" is returned as 'IWM' (the 'T'+'E' pair collapsed into a single 'W', a character dropped outright), and "Widget" is returned as 'WIDQET' ('G' classified as 'Q'). 'PRICE' and '10.00' are recovered, so the defect is per-glyph classification/segmentation, not a missing read path. The strings quoted are one run's output filling the template above, not the requirement.
Why: a client calling AnalyzeDocument with TABLES to read a tabular document gets a 200 with a well-formed grid whose cell contents are wrong — a header lookup for 'Item' finds nothing and the row value is stored as 'WIDQET'. Nothing in the response signals that recognition failed, so downstream data is silently corrupted and column-matching logic silently false-negatives.
Fix: the per-glyph classification and glyph-segmentation/scoring in the OCR module of the textract crate (services/service-com-amazonaws-textract-textract/src/state/ocr.rs and the glyph/template matching it uses), reached from the page reader that feeds the TABLES CELL CHILD words; adjacent glyphs must not be merged into one character, and each rendered ASCII glyph must resolve to the drawn character before any WORD text is emitted. The TABLES CELL builder consumes that text and needs no change once it is correct.
Traces: textract.analyze-document-combined-features-tables-and-forms.

Cause 2 of 2 — DetectDocumentText with Document.S3Object: the OCR of the stored object's pixels substitutes glyphs and loses the inter-word space, collapsing a three-word line into a single mangled token.
AWS: Smithy (same model): DetectDocumentText input {Document required} / output {DocumentMetadata, Blocks, DetectDocumentTextModelVersion}; Document{Bytes, S3Object} is documented "The input document, either as bytes or as an S3 object" and "You pass images stored in an S3 bucket to an Amazon Textract API operation by using the S3Object property" — the S3-sourced path must read the same pixels and produce the same result class as the Bytes path. Block$BlockType documents LINE as "a string of space-delimited, contiguous words" and WORD as characters "that aren't separated by spaces". The requirement is general: a page drawing N whitespace-separated words yields one LINE whose Text is those words space-delimited and N WORD blocks, each spelling exactly the drawn characters. The call is a 200; no error code is involved.
Emulator: the S3Object reference is accepted and a 200 returns, but for a page drawing the single line "S3 SOURCED DOCUMENT" the response contains one LINE whose text is 'S3 $)UICEDIXXUMENT': the drawn word "SOURCED" is returned as '$)UICED' (leading 'S'->'$', 'O'->')'), "DOCUMENT" as 'IXXUMENT' ('D'->'I', 'OC'->'XX'), and the space drawn between the two words is dropped so they are concatenated into one token — meaning the page's three drawn words are not segmented into separate WORD blocks either (the check's ">= 2 WORD blocks" assertion is downstream of the same collapse).
Why: a client that uploads a document to S3 and calls DetectDocumentText on the object gets a 200 whose LINE/WORD text is neither the drawn characters nor correctly tokenised; text search, keyword extraction and any per-word geometry mapping all operate on fabricated strings, with no signal that recognition failed. Because the drawn space is lost, even a fuzzy consumer cannot recover the word boundaries.
Fix: the same shared OCR module in the textract crate (services/service-com-amazonaws-textract-textract/src/state/ocr.rs) plus the word-segmentation step that must break tokens on inter-word pixel gaps, on the S3-sourced read path of DetectDocumentText (the handler that resolves Document.S3Object into page pixels must hand the recogniser the same raster the Bytes path uses).
Traces: textract.detect-document-text-from-s3-object-source.
