=== Cause 1 of 2: SigningCertURL is announced at sns.<region>.amazonaws.com, which is not an authority this emulator serves, so a subscriber that follows AWS's documented verification procedure cannot fetch the certificate at all ===
Failing check ids for this cause: sns.notification-signature-verifies-against-the-signing-certificate, sns.signature-version-two-switches-the-delivered-digest-to-sha256.

AWS:      Smithy (com.amazonaws.sns#AmazonSimpleNotificationService) does not model the delivered JSON envelope — Publish's fan-out document is recorded behavior only; Subscribe (TopicArn required, Protocol required, Endpoint, Attributes, ReturnSubscriptionArn; errors AuthorizationError 403 / InvalidParameter 400 / NotFound 404 / InternalError 500) and ConfirmSubscription (TopicArn required, Token required, AuthenticateOnUnsubscribe) are the modelled halves of the handshake. The AWS Developer Guide section "Verifying the signatures of Amazon SNS messages" documents SigningCertURL as "The URL of the certificate that was used to sign the message" and instructs a subscriber to RETRIEVE that URL and extract the public key from the certificate. The recordings show the envelope carrying Type, MessageId, TopicArn, Message, Timestamp, SignatureVersion, Signature, SigningCertURL and UnsubscribeURL, with SigningCertURL's path of the form /SimpleNotificationService-<32 hex characters>.pem on the default https port with no port component. The requirement is twofold and both halves must hold at once: one envelope announces ONE authority for all of its URL members, and that authority is one the RECIPIENT of the envelope can actually reach the service at and be answered 200 with the PEM the Signature verifies under. The concrete host name, the 32-hex certificate id, the Timestamp and the Signature bytes are per-run/per-environment values and are not part of the requirement.

Emulator: state/notification_signature.rs now returns the regional endpoint form unconditionally — announced_authority(region) is `format!("sns.{region}.amazonaws.com")` with no reached-endpoint or served-endpoint branch left — so every delivered envelope reads SigningCertURL = https://sns.<region>.amazonaws.com/SimpleNotificationService-<32 hex>.pem. That host is not one the emulator is reached on and no listener of this process claims it. The replay states it directly: sns.notification-signature-verifies-against-the-signing-certificate fails its `assert not (p := ctx.published_url_mismatch(cert_url))` with "the emulator published https://sns.us-west-2.amazonaws.com/SimpleNotificationService-<32 hex>.pem: its host is not one of the emulator's own hosts; a customer of the emulator needs http(s)://127.0.0.1:<port>/<resource path>, or http(s)://<own host>:<port>/<path> on a per-resource listener"; sns.signature-version-two-switches-the-delivered-digest-to-sha256 raises simparity.published.PublishedUrlRejected from context.py endpoint_route/_published_target on the same member. Both checks take the envelope out of a plain SQS subscription — no http/https delivery is involved — so this cause is visible on the SQS-envelope path on its own, independent of Cause 2. Everything up to that member matched: SignatureVersion is the topic's declared value and the envelope is otherwise well formed.

Why:      a client doing exactly what AWS documents — read SigningCertURL, fetch it, verify the RSASSA-PKCS1-v1_5 Signature over SNS's canonical string — is handed an address it cannot reach, so the fetch fails and EVERY notification is unverifiable even though SignatureVersion and Signature are present and internally correct. The client cannot distinguish an authentic notification from a forged one, which is the entire purpose of the signing members; it also cannot exercise the SignatureVersion 1 -> 2 digest switch, because that is observable only through a certificate it can fetch. Announcing a third party's hostname is strictly worse than announcing a wrong port: the name resolves away from the emulator entirely.

Fix:      the SNS notification/confirmation envelope's signing members — state/notification_signature.rs `announced_authority` and the `certificate_url` / `Signer::of_topic` path it feeds, reached from the Publish fan-out — must announce the certificate under an authority this process actually serves and answers `GET /SimpleNotificationService-<32 hex>.pem` on (the authority the recipient reaches the emulator at, or a per-resource listener's own host:port), and the sibling SubscribeURL / UnsubscribeURL members built in ops/publish/endpoint_delivery.rs must be moved to that SAME authority so one document still names one origin. Satisfying the one-origin invariant by moving every member onto the real AWS hostname is not a fix: it trades a two-origin document for a single unreachable one.

Traces:   sns.notification-signature-verifies-against-the-signing-certificate, sns.signature-version-two-switches-the-delivered-digest-to-sha256. Code read in this checkout: services/service-com-amazonaws-sns-amazonsimplenotificationservice/src/state/notification_signature.rs lines 306-336 (`announced_authority`, and the doc comment at 322-332 asserting this host is "the one address a SUBSCRIBER OF THIS EMULATOR can really fetch these documents at"), 338-345 (`addresses_certificate`).

=== Cause 2 of 2: an http/https subscription's endpoint still captures nothing — neither SubscriptionConfirmation, Notification nor UnsubscribeConfirmation is ever admitted, so the whole URL-push surface reaches no verdict ===
Failing check ids for this cause: sns.authenticate-on-unsubscribe-refuses-the-anonymous-unsubscribe-url, sns.confirm-subscription-token-confirms-only-its-own-subscription-whatever-the-topic-arn, sns.confirm-subscription-token-is-reusable-until-unsubscribe-then-not-found, sns.https-endpoint-failing-with-500-is-retried-then-dead-lettered, sns.https-raw-message-delivery-posts-the-bare-body-with-the-rawdelivery-header, sns.https-subscription-receives-nothing-until-confirmed-then-gets-the-notification, sns.raw-message-delivery-drops-message-attributes-for-an-https-subscriber-but-keeps-them-for-sqs.

AWS:      Smithy: Subscribe with Protocol "https" creates the subscription PendingConfirmation, and its documentation states that for an HTTP/S endpoint the endpoint owner must run ConfirmSubscription with the token from the subscription message; ConfirmSubscription(TopicArn, Token) returns that subscription's ARN and GetSubscriptionAttributes then reports PendingConfirmation "false". The POSTs themselves are recorded behavior only, and the recordings show: one POST per Subscribe carrying headers x-amz-sns-message-type: SubscriptionConfirmation, x-amz-sns-topic-arn: <the topic> and x-amz-sns-message-id: <the envelope's MessageId>, whose body carries Type, MessageId, Token, TopicArn, Message, SubscribeURL (a ConfirmSubscription URL for exactly that topic and token), Timestamp, SignatureVersion, Signature and SigningCertURL; one POST per Publish once confirmed with x-amz-sns-message-type: Notification plus x-amz-sns-message-id: <that Publish's MessageId> and x-amz-sns-subscription-arn: <the subscription>, body carrying that MessageId, the TopicArn and an UnsubscribeURL whose query is Action=Unsubscribe&SubscriptionArn=<that subscription>; the bare published body plus header x-amz-sns-rawdelivery: true (and no message attributes) when RawMessageDelivery=true; and one UnsubscribeConfirmation POST for the anonymous unsubscribe flow. A message published while the subscription was pending is never delivered after confirmation. (no variable part); the unflagged twin answers 200 with an UnsubscribeResponse. A Token replayed after Unsubscribe is refused NotFound. Subscribe returns 200 with a SubscriptionArn and Publish reports success, so the loss is silent. Two links on this one delivery path can produce it and the fixer must confirm which (the replay output shows only the timeout). First, Cause 1 is sufficient on its own: the endpoint admits a POST only after verifying it as the Developer Guide documents, requiring SigningCertURL to be https on exactly the host it reaches SNS at with port in (none, 443) and a 200 answer from fetching it, and the announced sns.<region>.amazonaws.com satisfies neither, so each POST is answered 403 and never captured. Second, and independently: ops/publish/endpoint_delivery.rs lines 50-54 state every delivery POST "goes through the IN-PROCESS emulator transport and nothing else … no socket is opened and no name is resolved", and lines 56-62 state a URL nothing here serves is not retried but dead-lettered at once — these endpoints are Lambda function URLs, so if the in-process router does not claim a published function URL, the subscriber is unreachable and the queue stays empty for that reason even after Cause 1 is fixed. Hypothesis, since only the timeout is observable: the 403 link fires first because the POST is built and dispatched (the prior resolved issue's fix landed in ops/subscribe.rs and ops/publish/endpoint_delivery.rs), but both links must hold.

Why:      a client that subscribes an http/https endpoint receives nothing while Subscribe and Publish both report success — silent, total data loss on a first-class SNS push protocol. The subscription can never leave PendingConfirmation through the documented path, because the Token travels only in that unadmitted POST; so webhook and alerting integrations are not merely wrong but inert, and the behaviors layered on the handshake — pending-vs-confirmed delivery, the Notification envelope and its x-amz-sns-* headers, RawMessageDelivery's bare body and attribute dropping, DeliveryPolicy retry budgets with RedrivePolicy dead-lettering, token reuse-then-NotFound, cross-topic token semantics, and the AuthenticateOnUnsubscribe 403 — are all unobservable rather than merely divergent.

Fix:      the SNS http/https delivery worker's outbound path (ops/publish/endpoint_delivery.rs) together with the envelope signing members of Cause 1: make the dispatched POST actually reach a subscribed endpoint this emulator serves, including a published Lambda function URL, and address the envelope's certificate under an authority that subscriber can fetch; then the Subscribe handler's confirmation dispatch (ops/subscribe.rs), the per-subscription retry loop bounded by EffectiveDeliveryPolicy and its dead-letter hand-off, the raw-delivery body/header rules, and the anonymous-unsubscribe path that must emit UnsubscribeConfirmation and refuse an AuthenticateOnUnsubscribe subscription 403 AuthorizationError.
