Cause 1 of 6: a submitted calculation never reaches COMPLETED — it settles FAILED about 5 seconds after submission, so no calculation produces stdout, a result object or DPU time.
  AWS: Smithy (services/service-com-amazonaws-athena-amazonathena/smithy-model/com-amazonaws-athena-amazonathena.json) — StartCalculationExecution returns CalculationExecutionId + State (CalculationExecutionState: CREATING|CREATED|QUEUED|RUNNING|CANCELING|CANCELED|COMPLETED|FAILED, where COMPLETED is documented as "The calculation has completed without error" and FAILED as "The calculation failed and is no longer running"); GetCalculationExecution(Status) carries Status.SubmissionDateTime/CompletionDateTime/State/StateChangeReason, Statistics.DpuExecutionInMillis and Result.StdOutS3Uri/StdErrorS3Uri/ResultS3Uri. Recorded behavior: on a PySpark workgroup (Configuration.EngineVersion.SelectedEngineVersion "PySpark engine version 3" + ExecutionRole) a session reaching IDLE RUNS the submitted cell in a live PySpark environment in which the SparkSession is already bound as the global `spark` — a cell `spark.sql('SELECT 41 + 1').show()` and a cell `print('<marker>', spark.range(1, 101).groupBy().sum().collect()[0][0])` both reach the terminal State COMPLETED, GetCalculationExecution then reports Result.StdOutS3Uri inside the workgroup's own OutputLocation bucket whose object body holds the program's stdout (the marker followed by the computed sum, which is not a literal in the code), Statistics.DpuExecutionInMillis > 0, and GetCalculationExecutionCode returns the exact submitted CodeBlock.
  Emulator: the calculation is accepted (200, State CREATED) and walks CREATED→RUNNING, but every submission settles at the terminal State FAILED roughly 5 s after SubmissionDateTime (observed Status: SubmissionDateTime 20:25:12.715 → CompletionDateTime 20:25:17.887, State 'FAILED'; and 20:24:54.305 → 20:24:59.553, State 'FAILED' — the ~5 s span, not the instants, is the signal). services/service-com-amazonaws-athena-amazonathena/src/state/calculation_engine.rs runs the code block as a standalone submitted Spark program (`service_common::spark_runtime::submitted_program_handler`) under CALCULATION_RUN_CEILING = 5 s, and reports `failed: true` both for a run that raised and for one its own bound stopped. Hypothesis: a cell that uses the session-provided global `spark` has no SparkSession bound in that standalone-program environment, and/or the run is cut by the 5 s ceiling, so the calculation is reported FAILED instead of COMPLETED.
  Why: the whole notebook/Spark data plane is unobservable past submission. A client that submits a cell and polls for its outcome is told the cell FAILED, finds no Result.StdOutS3Uri object to read, and reads zero DPU time for work it is billed for; a notebook UI shows every cell as failed.
  Fix: the calculation run path — services/service-com-amazonaws-athena-amazonathena/src/state/calculation_engine.rs together with the submission handler services/service-com-amazonaws-athena-amazonathena/src/ops/start_calculation_execution.rs — must bind the session's SparkSession (`spark`, and `sc`) into the environment the cell runs in exactly as an Athena Spark session does, give a cell a run span a real cell fits in rather than a 5 s ceiling that reports a stopped run as the cell's own failure, and settle a cell that ran to its end as COMPLETED with its stdout/stderr/result objects written under the session's working directory and a non-zero Statistics.DpuExecutionInMillis.
  Traces: athena.e2e-notebook-session-calculation-teardown, athena.spark-calculation-returns-computed-stdout-result.

Cause 2 of 6: TerminateSession leaves an in-flight calculation to settle FAILED instead of forcing it to the terminal CANCELED.
  AWS: Smithy — CalculationExecutionState documents CANCELED as "The calculation is no longer running as the result of a cancel request", and CalculationStatus.StateChangeReason is documented as "The reason for the calculation state change (for example, the calculation was canceled because the session was terminated)". Recorded behavior: with a long-running cell (`import time`/`time.sleep(600)`) observed in State RUNNING, TerminateSession on its session drives that calculation to the terminal State CANCELED — never COMPLETED and never left RUNNING — observable through GetCalculationExecutionStatus. A cell that is still running is NOT a failure: AWS keeps it RUNNING until something cancels it.
  Emulator: the cell is observed RUNNING, TerminateSession is accepted, and the calculation then reports State 'FAILED' (assertion: "expected the forcefully-stopped calculation to be marked CANCELED …, got FAILED"). Nothing in the termination path touches the calculation registry; the state the calculation comes to rest in is whatever the run's own 5 s ceiling of Cause 1 produced.
  Why: a client that terminates a session to stop runaway work cannot account for that work: a FAILED calculation reads as the cell's own error (something to report to the user or retry) where AWS reports an operator-initiated cancellation with a session-terminated StateChangeReason.
  Fix: the session-termination path (services/service-com-amazonaws-athena-amazonathena/src/ops/terminate_session.rs and the session/calculation state it owns) — force every non-terminal calculation of the terminated session to CANCELED with the session-terminated StateChangeReason, and stop reporting a cell the emulator itself stopped as the cell's failure.
  Traces: athena.calculation-execution-exceeds-timeout-marked-timed-out.

Cause 3 of 6: a submission into a session that exists but is TERMINATED takes the unknown-id sentence instead of AWS's state-naming refusal.
  AWS: Smithy — StartCalculationExecution models InvalidRequestException (client, httpError 400, "Indicates that something is wrong with the input to the request"). Recorded behavior: after TerminateSession and GetSessionStatus reporting State 'TERMINATED', StartCalculationExecution(SessionId=<that session>, CodeBlock=…) is refused HTTP 400 InvalidRequestException with Message "Session is in the TERMINATED state; needs to be IDLE to accept Calculations." The fixed text is "Session is in the " … " state; needs to be IDLE to accept Calculations."; the one variable part is the session's CURRENT State read from service state (TERMINATED here). The session still exists, so this is NOT the unknown-id/not-authorized sentence, which AWS reserves for an id it will not act on.
  Emulator: HTTP 400 InvalidRequestException with Message 'Not authorized to make this request.' — services/service-com-amazonaws-athena-amazonathena/src/ops/start_calculation_execution.rs collapses the `if !session.is_active_at(now)` branch into `crate::state::session_not_authorized()`, deliberately reusing the unknown-session sentence.
  Why: a client cannot tell "this session is finished, start a new one" (recoverable by starting a session) from "this id is unknown or you are not permitted" (an IAM/ownership problem) — the emulator gives both the identical text.
  Fix: the StartCalculationExecution handler's session-state gate (services/service-com-amazonaws-athena-amazonathena/src/ops/start_calculation_execution.rs) — refuse a session that exists but is not accepting calculations with the state-naming message, interpolating the session's current State, and keep the unknown-session sentence only for ids the store does not hold.
  Traces: athena.start-calculation-execution-on-terminated-session-rejected.

Cause 4 of 6: GetResourceDashboard does not pattern-validate ResourceARN — a session ARN built the documented way from a raw StartSession SessionId is served a dashboard URL instead of AWS's ARN-constraint refusal.
  AWS: Smithy — GetResourceDashboard.ResourceARN is @required, target AmazonResourceName @length 1..1011, output Url @required, errors InvalidRequestException (client, 400) and ResourceNotFoundException (client, 400); the model carries no @pattern, so the constraint is recorded behavior only. Recorded behavior: the service applies an ARN pattern to resourceARN and refuses a violation with InvalidRequestException (400) and the framework validation message "1 validation error detected: Value at 'resourceARN' failed to satisfy constraint: Member must satisfy regular expression pattern: ^arn:(aws[a-zA-Z0-9-]*):athena:[a-zA-Z0-9-]+:\\d{12}:(workgroup|datacatalog|capacity-reservation|system-table)/[a-zA-Z0-9+=,.@_-]+(/session/s-[a-z0-9]+)?$". Everything in that message is fixed text except the member name ('resourceARN') and the quoted pattern, which come from the constraint violated; the rejected value is not interpolated. Because the optional session segment must match `s-[a-z0-9]+`, an ARN whose session segment is a raw StartSession SessionId (a hyphenated UUID) violates the pattern and is refused this way — deterministically, the identical call giving the identical code and message on retry — while an ARN whose session segment DOES match the pattern and resolves to a live session is answered 200 with an https Url (athena.get-resource-dashboard-returns-monitoring-url records that accepting side, so the fix must keep it).
  Emulator: the call SUCCEEDS — HTTP 200 with a Url — for `arn:aws:athena:<region>:<account>:workgroup/<wg>/session/<raw SessionId>`. services/service-com-amazonaws-athena-amazonathena/src/ops/get_resource_dashboard.rs goes straight from `crate::state::addressed_session(&input.resource_arn, &region)` to the stored session and signs a URL; no character/shape constraint is applied to the ARN at all, and the only refusal in the handler is the resolve miss (`crate::state::RESOURCE_ARN_NOT_FOUND`).
  Why: a negative class AWS enforces is unobservable. A client that builds the ARN as AWS's own documentation shows is refused by AWS with a validation error it must repair (and any client matching on the "N validation error(s) detected" prefix to repair an argument never sees it), but here it is handed a monitoring URL — so code written against the emulator breaks the first time it runs against AWS.
  Fix: GetResourceDashboard's input validation (services/service-com-amazonaws-athena-amazonathena/src/ops/get_resource_dashboard.rs, ahead of the state resolve) — apply the resourceARN pattern constraint and answer the framework validation message for a violation, keeping the 200 + Url answer for a pattern-conforming ARN that resolves to a live session and the resolve-miss sentence for one that does not.
  Traces: athena.e2e-query-lifecycle-dashboard-and-workgroup-teardown, athena.telemetry-resource-dashboard-emitted-for-workgroup, athena.telemetry-resource-dashboard-reflects-reservation-usage.

Cause 5 of 6: GetSessionEndpoint serves an endpoint and auth token to an IAM-role caller on a live API-started session, where AWS refuses the request.
  AWS: Smithy — GetSessionEndpoint input SessionId @required @length 1..256; output EndpointUrl, AuthToken, AuthTokenExpirationTime all @required; errors InvalidRequestException (client, 400) and ResourceNotFoundException (client, 400). Recorded behavior: for a caller authenticated as an IAM role against a session started through StartSession — including a notebook-bound session (EngineConfiguration.AdditionalConfigs.NotebookId, NotebookVersion "Athena notebook version 1") that is IDLE and has a calculation observed RUNNING — the call is refused HTTP 400 InvalidRequestException with Message "Not authorized to make this request." (entirely fixed text, no variable parts), and it is refused CONSISTENTLY: 3 of 3 and 5 of 5 consecutive attempts at 5 s intervals, so this is not a readiness race. The live endpoint is reached through Athena's console notebook flow, not by an IAM-role caller of this API.
  Emulator: HTTP 200 with the full body (EndpointUrl, AuthToken, AuthTokenExpirationTime) on the first attempt. services/service-com-amazonaws-athena-amazonathena/src/ops/get_session_endpoint.rs gates only on `session.is_ready_at(now)` and makes no authorization decision at all (its comment: "No IAM decision here … a session-addressed request names none"), so every ready session is served an endpoint and a token.
  Why: a client is handed an endpoint URL and a bearer token for a Spark session that AWS would never issue to this caller, so code (and any test of a least-privilege path) that must handle the refusal is never exercised, and an emulator-only connect path appears to work; the emulator is over-permissive on an authorization boundary.
  Fix: the GetSessionEndpoint handler (services/service-com-amazonaws-athena-amazonathena/src/ops/get_session_endpoint.rs) — refuse a session-endpoint request from an IAM-role caller of the API with InvalidRequestException and AWS's exact "Not authorized to make this request." text, keeping the existing not-ready refusal for a session whose resources are not up. Note the interaction with open issue 20261123T120959Z-athena-2-net-new-getsessionendpoint-causes-a-malformed.md: the malformed-SessionId validation message and the pre-IDLE state refusal it describes are separate work items and must keep working.
  Traces: athena.session-full-lifecycle, athena.session-lifecycle-start-get-status-endpoint-terminate.
