## Description
FOUR net-new causes, one per AWS-managed catalog page the corpus reads back through ListPolicies. They share a single root: the per-policy identity metadata the emulator publishes for AWS-managed policies is synthesized at seed time instead of being each policy's fixed, published value. All FOUR steps must pass before this issue is submitted, because each page carries its own catalog slice and a fix applied to one page's data leaves the others wrong.

=== Cause 1 of 4: the /aws-service-role/ page (iam-catalog-list-policies#task#1) ===
AWS: Smithy ListPolicies -> output Policies (policyListType), filtered by Scope / PathPrefix / PolicyUsageFilter / OnlyAttached; errors: ServiceFailure(500) only, so a 200 body is the whole contract. Each member is iam#Policy: PolicyName (policyNameType), PolicyId (idType, @length 16-128, @pattern ^[\w]+$, documented as "The stable and unique string identifying the policy"), Arn, Path, DefaultVersionId (policyVersionIdType, @pattern ^v[1-9][0-9]*(\.[A-Za-z0-9-]*)?$), AttachmentCount, IsAttachable, CreateDate, UpdateDate (dateType). For Scope=AWS these are not per-account values: an AWS-managed policy has ONE partition-wide PolicyId AWS minted for it, one CreateDate, and the UpdateDate/DefaultVersionId of its current default version, identical in every account. The requirement is therefore that each catalog member's PolicyId/CreateDate/UpdateDate/DefaultVersionId are per-policy CONSTANTS from AWS's published catalog; the literal values in any one recording are examples of those constants, not a per-run value.
Emulator: status 200 in both, only the body diverges. The served values are not the catalog's: aws-service-role/AWSElasticBeanstalkServiceRolePolicy.PolicyId is served 'ANPARY3ZQTMWJ7KVPNHLB' where the recording carries 'ANPAIID62QSI3OSIPQXTM'; aws-service-role/AWSEC2SpotServiceRolePolicy.PolicyId is served 'ANPAQX6MZJWKT5PVNHLRD' where the recording carries 'ANPAIZJJBQNXQYVKTEXGM', and its CreateDate is served '2017-09-18T18:51:04Z' against the recorded '2017-09-18T18:51:54Z'; AmazonRedshiftServiceLinkedRolePolicy.DefaultVersionId is served 'v5' against 'v15' and its UpdateDate '2023-04-12T17:33:26Z' against '2025-02-19T17:22:07Z'. The served ids all share a generated shape (ANPA + a random body ending in a common tail), i.e. they are minted at boot rather than being the policy's identity, and the dates/versions are a frozen older snapshot. The cluster's divergence key additionally lists whole members with no member suffix (e.g. aws-service-role/AWSAgentRegistryServiceRolePolicy, aws-service-role/AWSBCMDataExportsServiceRolePolicy), i.e. membership of this page differs as well, not only metadata.
Why: a client relying on AWS's behavior enumerates this catalog to resolve a managed policy before attaching it, and keys inventories, drift detection and policy pinning on PolicyId. A PolicyId that changes per seed makes every such key worthless and makes two runs of the same client disagree about the same policy; a stale UpdateDate/DefaultVersionId makes a consumer believe it already holds the policy's current version, so it never re-reads GetPolicyVersion; a member that is absent from the page makes the following AttachRolePolicy/GetPolicy on that ARN unresolvable, so a role AWS can build cannot be built here.
Fix: the IAM crate's built-in AWS-managed-policy catalog seed — the data ListPolicies, GetPolicy, GetPolicyVersion and the ListAttached*Policies projections all read — not the ListPolicies handler, its filters or its pagination (status, paging and the per-page Path/Scope filtering all match). Each entry needs fixed per-policy PolicyId/CreateDate/UpdateDate/DefaultVersionId and the page's membership must be the recorded set.
