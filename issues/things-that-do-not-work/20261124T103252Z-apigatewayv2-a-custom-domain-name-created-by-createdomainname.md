# apigatewayv2: a custom domain name created by CreateDomainName / AWS::ApiGatewayV2::DomainName is still not a host the emulator serves, so an ApiMapping has no observable effect (1 cause)

> _Note: this issue was identified against the code base at commit `9b3ec711581582504a687984a45cdda758f31515`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
CreateDomainName

## Description
REOPENS 20261114T123844Z-apigatewayv2-3-net-new-causes-the-cors-preflight.md: its fix left the call refused. That report's cause 3 carried this check's replay key and is now under issues/things-that-now-work/, but the request addressed to the custom domain is still refused before it is made, with the same PublishedUrlRejected and the same diagnosis — the custom domain is not one of the emulator's own hosts. This is not a new defect, it is the same call still being refused.

Cause 1 of 1: a custom domain name created through CreateDomainName (or the AWS::ApiGatewayV2::DomainName provisioner) is recorded in the control plane but is never registered as a host the emulator serves, so no request can be addressed to it and the ApiMapping on it can never route anything. Failing check: apigatewayv2.deploy-api-mapping-cfn-behaves.
AWS: Smithy (services/service-com-amazonaws-apigatewayv2-apigatewayv2/smithy-model/com-amazonaws-apigatewayv2-apigatewayv2.json): CreateDomainName POST /v2/domainnames, 201, member DomainNameConfigurations : DomainNameConfiguration — ApiGatewayDomainName (jsonName apiGatewayDomainName, 'A domain name for the API'), DomainNameStatus (enum, AVAILABLE), EndpointType, HostedZoneId, CertificateArn, SecurityPolicy; CreateApiMapping POST /v2/domainnames/{DomainName}/apimappings, 201, members ApiId/Stage/ApiMappingKey; GetApiMapping GET /v2/domainnames/{DomainName}/apimappings/{ApiMappingId}. The data plane is recorded behavior only: a customer CNAMEs the custom domain at DomainNameConfigurations[0].ApiGatewayDomainName, so a client connects to that address but sends the CUSTOM DOMAIN as the TLS SNI and as the Host header; API Gateway resolves (Host, base path) through the domain's API mappings to ApiId + Stage and serves that stage's integration — here an HTTP_PROXY target, answered HTTP 200 with the upstream's body. The control-plane legs are already right in the emulator: GetApiMapping returns the stack's ApiId and Stage '$default', and GetDomainName reaches DomainNameStatus 'AVAILABLE'.
Emulator: the domain host itself is unserved, and the request is refused before it leaves the client — simparity.published.PublishedUrlRejected at context.py:632 (_published_target, raised from ctx.endpoint_route('http://<custom domain>')): 'endpoint_url was given http://<custom domain> (published by the emulator or built by the check): its host is not one of the emulator\'s own hosts; a customer of the emulator needs http(s)://127.0.0.1:<port>/<resource path>, or http(s)://<own host>:<port>/<path> on a per-resource listener'. The connect leg to ApiGatewayDomainName:443 succeeds, so the surviving gap is specifically the custom domain the customer created: it is accepted by the control plane and then announced as an address the emulator does not answer on. The particular domain name in the recording is a per-run generated value and is not itself a requirement; what is required is that a domain a customer creates becomes reachable on the emulator.
Why: the entire point of a custom domain plus an ApiMapping is that clients address the api by that domain. A client can drive the control plane to completion and then never send that domain a single request, so base-path mapping, multiple mappings on one domain, mapping keys, $default-stage mapping and domain-level TLS are all untestable, and an estate that fronts its HTTP apis with custom domains cannot be run end to end against the emulator. Because the address is announced but unserved, callers get a connection/addressing failure rather than any status they can branch on.
Fix: CreateDomainName/UpdateDomainName in the apigatewayv2 crate and the AWS::ApiGatewayV2::DomainName CloudFormation provisioner must register the created domain as a served host of the emulator (a host alias / per-resource listener), and the execute-api front door's request resolution must accept an incoming Host/SNI naming a custom domain and resolve it through that domain's API mappings (base path -> ApiId + Stage) to the mapped stage's route and integration.
Traces: apigatewayv2.deploy-api-mapping-cfn-behaves. Related but not covering: open issues 20261027T053233Z-apigatewayv2-9-net-new-root-causes-api-mapping.md and 20261101T041930Z-apigatewayv2-3-net-new-root-causes-the-http.md own other custom-domain/API-mapping checks (custom-domain-mapping-key-routes-to-stage-routes, e2e-custom-domain-mapping-invoke-flow) but not this check's replay key, and the suite did not attribute this failure to either.
