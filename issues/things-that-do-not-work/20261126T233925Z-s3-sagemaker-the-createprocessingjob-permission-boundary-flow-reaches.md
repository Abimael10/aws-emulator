# s3__sagemaker: the CreateProcessingJob permission-boundary flow reaches no verdict inside a client budget — a role without s3:ListBucket on its S3Prefix input is never synchronously refused and the positive-control job never settles, so the check exhausts its whole 60 s budget

> _Note: this issue was identified against the code base at commit `f5d264f55dca24e5e6d27fac712858d2ae9d9b34`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
CreateProcessingJob

## Description
Cause 1 of 1: the SageMaker Processing permission-boundary flow over S3 produces no outcome at all within a client's budget — the failing check is ended by its 60.0 s timeout rather than by any response from the emulator, so neither the required synchronous refusal nor the positive control's terminal job status is ever observed.

AWS: Smithy (sagemaker): CreateProcessingJob takes the required RoleArn (pattern ^arn:aws[a-z\\-]*:iam::\\d{12}:role/?[a-zA-Z_0-9+=,.@\\-_/]+$) and AppSpecification, with ProcessingInputs[].S3Input.S3DataType = S3Prefix; DescribeProcessingJob returns the required ProcessingJobStatus enum plus optional FailureReason/ExitMessage. The modeled errors on CreateProcessingJob are ResourceInUse, ResourceLimitExceeded and ResourceNotFound; the input-enumeration refusal below is recorded behavior only (ValidationException, HTTP 400) and is what the recording shows. Recorded AWS: SageMaker enumerates the S3Prefix input channel with the execution role at CreateProcessingJob time, so a role that holds s3:GetObject but NOT s3:ListBucket on the input bucket makes the control-plane call itself fail synchronously with code ValidationException and the message whose FIXED text is: 'No S3 objects found under S3 URL "<s3-uri>" given in input data source. Please ensure that the bucket exists in the selected region (<region>), that objects exist under that S3 prefix, and that the role "<role-arn>" has "s3:ListBucket" permissions on bucket "<bucket>". Error message from S3: User: <assumed-role-arn> is not authorized to perform: s3:ListBucket on resource: "arn:aws:s3:::<bucket>" because no identity-based policy allows the s3:ListBucket action' — the variable parts are the request's S3Uri, the caller's region, the RoleArn from the request, the input bucket name, and the assumed-role ARN derived from that role; none of the concrete names in any one run are part of the requirement. An otherwise identical role that DOES hold s3:ListBucket is accepted and that job reaches ProcessingJobStatus 'Completed', with the declared EndOfJob S3Output carrying the input bytes byte-for-byte, while the refused job's output prefix stays empty.

Emulator: the whole exchange yields no verdict — the check is killed by its 60.0 s budget with 'Check timed out after 60.0s', meaning the emulator neither returned the synchronous ValidationException for the role lacking s3:ListBucket nor settled the accepted positive-control job to a terminal ProcessingJobStatus within the budget. Hypothesis: CreateProcessingJob is answered with a ValidationException whose message contains 'is not authorized' / 'Could not assume role' for a role AWS accepts (the positive-control role holds every needed permission and trusts sagemaker.amazonaws.com), which keeps a client in its role-propagation retry loop until the budget is gone; the alternative stall point is an accepted job whose status never leaves InProgress. The replay output records only the timeout, so the exact stall point is not stated by it.

Why: a client cannot use this operation's permission boundary at all. Code that relies on CreateProcessingJob refusing an under-privileged role up front (and on an adequately privileged role being accepted and the job settling) gets no answer in bounded time instead of either outcome: an authorization defect in the caller's own IAM policy is indistinguishable from a service that simply never answers, and any wait-for-terminal loop built on DescribeProcessingJob hangs. Neither branch of the safety property — refuse the role that cannot enumerate its input, run the one that can — is observable.

Fix: the CreateProcessingJob handler's input-channel validation (enumerate ProcessingInputs[].S3Input with the RoleArn's effective S3 permissions at create time and refuse with the ValidationException above, without leaving the client in a retryable 'is not authorized'/'Could not assume role' state for a role that is in fact authorized and trusted) and the processing-job state machine that must drive an accepted job to a terminal ProcessingJobStatus that DescribeProcessingJob reads back.

Not covered by the open issues 20261126T213548Z-s3-sagemaker-2-net-new-causes-a-bin.md (two entrypoint forms that DO settle, ending Failed with 'AlgorithmError: , exit code: 127' or with no ExitMessage — here no status is ever reached), 20261122T072036Z-s3-sagemaker-a-processing-job-whose-execution-role.md (a KMS-starved job that settles Completed), or 20261024T160943Z-sagemaker-runs-no-job-work-processing-pipeline-step.md (jobs that run no work but do reach a terminal status); the failure point here is that no response or terminal state arrives inside the budget.
