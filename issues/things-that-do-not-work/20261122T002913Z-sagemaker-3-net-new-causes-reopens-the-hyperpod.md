# sagemaker: 3 net-new causes — REOPENS the HyperPod cluster-lifecycle fix (DeleteCluster leaves the cluster immediately un-describable instead of Deleting), every Studio Domain/UserProfile/App transition still costs a polling client a whole interval, and CreatePresignedDomainUrl answers 501 NotImplemented so the Pending-domain refusal is unobservable

> _Note: this issue was identified against the code base at commit `d9b28bb7c9b1d2f4efcddff69d51730c9e04bf9c`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
DescribeCluster, DescribeDomain, DescribeApp, CreatePresignedDomainUrl

## Description
REOPENS 20261110T204514Z-sagemaker-hyperpod-cluster-lifecycle-transitions-are-each-deferred-behind.md: its fix left the call refused. That issue's fix removed the cluster lifecycle's wall-clock spans (crate::state::transition_owed_at is now the identity function), and with it the window in which a deleted HyperPod cluster is still readable: the DescribeCluster that immediately follows DeleteCluster is now refused 400 ResourceNotFound instead of answering 200 with ClusterStatus=Deleting. That is Cause 1 below; it is not a new defect but the same cluster-lifecycle work item coming back on the opposite side.

THREE root causes, all grounded in failing checks the suite report lists under `### sagemaker`, none of which the report marked ALREADY FILED or OWNED by an open issue. They are numbered and each carries its own failing check ids; all three must be closed before this issue is submitted.

=== Cause 1 of 3: DeleteCluster makes the cluster un-describable on the very next call, so ClusterStatus=Deleting is never observable and a mid-teardown read is refused ===
AWS: Smithy — DescribeCluster output member ClusterStatus is **required** and targets the ClusterStatus enum whose members are `Creating | Deleting | Failed | InService | RollingBack | SystemUpdating | Updating`; `Deleting` exists precisely because a cluster whose teardown has been asked for is still a cluster a reader answers for. DeleteCluster answers 200 with the ClusterArn and models ConflictException / ResourceNotFound (both HTTP 400); its teardown of a HyperPod cluster takes minutes on AWS. Recorded behavior: DescribeCluster called straight after an accepted DeleteCluster answers 200 with ClusterStatus `Deleting` and the cluster's InstanceGroups still projected, and only once the teardown completes does it answer 400 ResourceNotFound with `Cluster with name <identifier> not found` (`Cluster with name` / `not found` fixed text, `<identifier>` the ClusterNameOrArn the request carried). While Deleting, a node-scaling call against the cluster is refused 400 ValidationException `Cluster <cluster arn> is in a termination state that cannot be modified.` — a refusal that can only be produced by a cluster that is still there in that state.
Emulator: DeleteCluster parks the record in Deleting but makes the removal due at the same instant it answers — services/service-com-amazonaws-sagemaker-sagemaker/src/ops/delete_cluster.rs:190-194 calls `cluster.begin_deletion(now)`, whose due instant comes from `crate::state::transition_owed_at(now)`, which is now the IDENTITY (state/cluster.rs, documented as deliberately returning `now`). `Cluster::is_released(now)` is therefore true immediately, `ComAmazonawsSagemakerSagemakerState::cluster_key` filters the record out, and the next DescribeCluster is refused 400 ResourceNotFound `Cluster with name <name> not found`. The Deleting status the record was given is unreachable: no sequence of requests can read it, and neither can the termination-state ValidationException that depends on it.
Why: a client that does the documented thing — DeleteCluster, then poll DescribeCluster until the cluster is gone — gets an exception on its FIRST poll where AWS gives it a 200/Deleting, so it cannot distinguish "teardown in progress" from "never existed" and cannot confirm its own delete. Any code that reads the cluster between delete and disappearance (to log the status, to assert nothing else mutated it, to refuse a second operation) breaks, and the whole Deleting branch of the cluster state machine — including the termination-state refusal of BatchAddClusterNodes/BatchDeleteClusterNodes — is untestable against the emulator.
Fix: the HyperPod cluster slice's teardown clock and the readers that materialise it — `Cluster::begin_deletion` / `Cluster::is_released` and the removal instant they share with `crate::state::transition_owed_at` (services/service-com-amazonaws-sagemaker-sagemaker/src/state/cluster.rs and src/state.rs), plus src/ops/delete_cluster.rs and src/ops/describe_cluster.rs. A deleted cluster must stay describable in Deleting for at least the read that follows the delete, and reach "gone" without charging a polling client a full interval (that is the constraint the reopened issue imposed) — e.g. settle the removal on the read AFTER the one that observed Deleting, rather than at the instant the delete answered.
Traces: sagemaker.batch-add-cluster-nodes-wrong-state-rejected.

=== Cause 2 of 3: every clock-owed Studio transition (Domain 3 s, UserProfile 3 s, App 300 ms) is due only after the read that follows the create, so a polling client pays one whole poll interval per transition and five Studio scenarios reach no verdict ===
AWS: recorded behavior only for the timing; the model states the lifecycle these checks walk — DescribeDomain.Status -> DomainStatus, DescribeUserProfile.Status -> UserProfileStatus, DescribeApp.Status -> AppStatus (`Pending | InService | Deleting | Deleted | Failed`). A Studio domain, its user profile and its app are all driven by the documented poll-until-settled pattern, and every status in the chain has to be reachable by a client polling at a realistic interval.
Emulator: every call is answered — no refusal is recorded — but each transition is deferred behind a stored wall-clock instant that the first read after the mutation always misses: `DOMAIN_IN_SERVICE_AFTER = Duration::from_secs(3)` and `DOMAIN_RELEASED_AFTER` (services/service-com-amazonaws-sagemaker-sagemaker/src/state/domain.rs:40-56), `USER_PROFILE_IN_SERVICE_AFTER = DOMAIN_IN_SERVICE_AFTER` (src/state/user_profile.rs:61-68), and `APP_IN_SERVICE_AFTER` / `APP_DELETED_AFTER` = `ENDPOINT_IN_SERVICE_AFTER` = 300 ms (src/state/app.rs:19-34). The settle happens on whichever read first runs at or after that instant, so a client that probes immediately after each create reads the transient status and then sleeps its own full interval. Hypothesis for the arithmetic: the chained waits alone exceed the 60 s replay budget — sagemaker.app-lifecycle-in-service-to-deleted waits Domain(20 s) + UserProfile(10 s) + App(15 s) + App-delete(15 s) = 60 s of pure sleeping; sagemaker.app-lifecycle-state-transitions waits 20 + 15 + 15 + 15; sagemaker.domain-user-profile-app-teardown-cascade waits 20 + 10 + profile-gone(10) + domain-gone(20); sagemaker.domain-delete-with-active-user-profile-rejected waits 20 + 10 before its DeleteDomain assertion; sagemaker.create-app-already-running-resource-in-use waits 15 + 10 + 10 + an app wait. All five are cut off with `Check timed out after 60.0s` with no verdict. Note the same root cause is already filed for OTHER resource families and other checks and does not cover these five: open issue 20261113T002132Z-sagemaker-3-net-new-causes-invokeendpoint-scores-a.md (Cause 3, the training-job/endpoint/recommender chain) and fixed issue 20261110T204514Z (the HyperPod cluster chain, whose fix is Cause 1 above); the Studio domain/profile/app spans were left as they were. Five of these six checks also carry the trace ids of the FIXED issue 20261118T212957Z-sagemaker-7-net-new-causes-a-deleted-app.md: that fix made the Studio lifecycle statuses correct, and they are now unreachable inside a replay budget for the timing reason described here, which is a different cause and not a refusal.
Why: a client (or `aws sagemaker wait`) that polls at a realistic interval sees the transient status on the describe that follows each create and pays its whole interval for every transition; a scenario chaining domain -> profile -> app -> teardown pays it four times, so a multi-resource Studio flow is unobservably slow even though the emulator holds the settled state a few seconds later. Everything past the second wait — the app's Deleted retention, the KernelGateway refusal, the DeleteDomain ResourceInUse, the ResourceInUse of a duplicate CreateApp — cannot be verified at all.
Fix: the clock-owed spans of the Studio slices and the readers that materialise them — `DOMAIN_IN_SERVICE_AFTER`/`DOMAIN_RELEASED_AFTER` and `Domain::settle_status`/`Domain::is_released` (src/state/domain.rs), `USER_PROFILE_IN_SERVICE_AFTER` and `UserProfile::settle_status` (src/state/user_profile.rs), `APP_IN_SERVICE_AFTER`/`APP_DELETED_AFTER` and `App::settle_status` (src/state/app.rs), with src/ops/describe_domain.rs, describe_user_profile.rs and describe_app.rs. The transient status must stay observable to the read that immediately follows the mutation WITHOUT costing a polling caller a full interval — settle on the first read after the one that observed the transient value, rather than on a read that happens to fall after a fixed wall-clock instant.
Traces: sagemaker.app-lifecycle-in-service-to-deleted, sagemaker.app-lifecycle-state-transitions, sagemaker.create-app-already-running-resource-in-use, sagemaker.domain-delete-with-active-user-profile-rejected, sagemaker.domain-user-profile-app-teardown-cascade.

=== Cause 3 of 3: CreatePresignedDomainUrl against a Pending Domain answers NotImplemented instead of the state refusal that names the Pending state ===
AWS: Smithy — CreatePresignedDomainUrl takes DomainId and UserProfileName (both required) and models exactly one error, ResourceNotFound (HTTP 400), so a lifecycle-state refusal travels as the service-common ValidationException. Recorded behavior: while the domain's DomainStatus is still `Pending`, the call is refused HTTP 400 with Error.Code `ValidationException` and the message `Domain must be in either InService or Update_Failed state and not in: Pending` — `Domain must be in either InService or Update_Failed state and not in: ` is fixed text for this error class and the trailing token is the domain's CURRENT status read from state; once the domain is InService the same call mints an AuthorizedUrl. The sibling calls in the same window are refused their own sentences (`Unable to create UserProfile [<user-profile arn>] because Domain [<domain arn>] is not in InService.` / `Unable to create Space [<space arn>] because Domain [<domain arn>] is not in InService.`), which the emulator already answers correctly — this cause is the presigned-URL call alone.
Emulator: the call is refused with Error.Code `NotImplemented`, because CreatePresignedDomainUrl is still an unimplemented scaffold stub (services/service-com-amazonaws-sagemaker-sagemaker/src/ops/create_presigned_domain_url.rs). The check reaches the assertion with code `'NotImplemented'`, so the Pending-state gate this operation owes cannot be observed at all. Open issue 20261118T212957Z-sagemaker-createpresigneddomainurl-stub.md covers implementing that stub and the suite report marks a DIFFERENT check (sagemaker.presigned-domain-url-expires-after-ttl) as already filed against it; it does not carry this check's replay key and says nothing about the not-InService gate or its wording, which is the requirement recorded here.
Why: a client that mints a Studio sign-in URL right after CreateDomain gets a 501-class `NotImplemented` where AWS gives it a retryable, self-explaining 400 ValidationException naming the state to wait for, so the retry-until-InService loop every real Studio integration needs is never exercised, and a caller cannot tell "not ready yet" from "this API does not exist".
Fix: implement the CreatePresignedDomainUrl handler (services/service-com-amazonaws-sagemaker-sagemaker/src/ops/create_presigned_domain_url.rs) including the domain-status precondition: resolve the DomainId (and the UserProfileName/SpaceName owner) against the Studio domain slice, settle the domain's clock-owed status first, and refuse with ValidationException/400 carrying the sentence above whenever the resolved status is not InService (or Update_Failed), minting the AuthorizedUrl otherwise.
Traces: sagemaker.domain-pending-refuses-user-profile-space-and-presigned-url.
