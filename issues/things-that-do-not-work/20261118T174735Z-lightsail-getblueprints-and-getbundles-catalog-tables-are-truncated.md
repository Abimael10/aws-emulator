# Lightsail GetBlueprints and GetBundles catalog tables are truncated and row-misaligned

> _Note: this issue was identified against the code base at commit `73fc9d83704180bc6fc0934371242895ca7d1faa`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
GetBlueprints

## Description
Two net-new root causes, both in the static read-only catalog tables behind Lightsail's instance-catalog reads. Both operations answer 200 with a correctly shaped envelope, so a client cannot detect either divergence from the status or the member set: the fault is entirely in which ROWS the tables hold and which row sits at which position. Both causes must be closed before submitting.

Cause 1 of 2: GetBlueprints serves a short blueprint table whose rows do not line up with AWS's catalog, so at nearly every asserted position the row's description prose and product/licence URLs belong to a different image, and the tail of the catalog is absent.
AWS: Smithy com.amazonaws.lightsail#GetBlueprints is an awsJson RPC operation (POST /ls/api/2016-11-28/GetBlueprints, success 200) whose output member `blueprints` is a BlueprintList of com.amazonaws.lightsail#Blueprint. Smithy documents the members it must carry - blueprintId, name, group, type (BlueprintType os|app), `description` ("The description of the blueprint"), isActive, minPower, `version` ("The version number of the operating system, application, or stack"), versionCode, `productUrl` ("The product URL to learn more about the image or blueprint"), `licenseUrl` ("The end-user license agreement URL for the image or blueprint"), platform (InstancePlatform) - but fixes no row set and no values, so the table's contents and order are recorded behavior only. The recording shows AWS serving a complete catalog of 39 blueprint rows in a fixed order (the Windows Server OS block, then the Windows SQL Server app blueprints, then the Linux/Unix OS and app blocks), each row carrying that image's own AWS marketplace description paragraph, a productUrl under aws.amazon.com/marketplace/pp/<prodview-id>, and a licenseUrl that is either the AWS EULA host (d7umqicpi7263.cloudfront.net/eula/product/<id>/<id>.txt) or that row's marketplace page with the '#pdp-usage' fragment - consistently per row, never crossed between rows. The specific prodview ids, EULA paths, catalog date and paragraph text in the recording are that catalog generation filling the template; the requirement is that each row carries ITS OWN AWS text and ITS OWN AWS links, and that the whole row set is served.
Emulator: the table is both short and misaligned. Replay reports positions $.blueprints[1] through $.blueprints[38] as divergent as whole entries, and productUrl/licenseUrl as verdict host_not_own on rows 5 and 7-32. At $.blueprints[1] ('windows_server_2022') AWS's description is the Microsoft-Web-Platform paragraph ending '... Learn more about Windows Server 2022 on the AWS Marketplace.' while the emulator serves the generic 'Amazon Lightsail helps you build, deploy, scale, and manage Microsoft applications ... running any other application requiring Windows software.' paragraph that belongs to a different Windows row - i.e. the prose is attached to the wrong blueprint. The same crossing shows in the links: at $.blueprints[7] AWS serves productUrl 'https://aws.amazon.com/marketplace/pp/prodview-s4zvkzmlirbga' and licenseUrl that page plus '#pdp-usage', while the emulator serves productUrl 'https://aws.amazon.com/amazon-linux-2' and a licenseUrl under the d7umqicpi7263.cloudfront.net EULA host - the licence style of a different row. Positions 33-38 are absent entirely, so the emulator's list is shorter than AWS's 39 rows.
Why: a client that renders a blueprint's description, presents its licence terms, or follows its product link gets another image's text and another image's URL under a blueprintId that looks right, so the error is invisible at the API and surfaces only in what a user is shown or asked to accept. A blueprint that is not listed at all cannot be selected, so the workflows that start from the omitted tail rows cannot be driven against the emulator, and any client reading the catalog by position gets a different image than AWS serves at that index.
Fix: the static instance-blueprint catalog table behind the GetBlueprints handler in the lightsail crate - its row set (add the missing rows, in AWS's order) and the per-row description/productUrl/licenseUrl columns, so each row's text and links are its own. Not handler, validation or serializer logic: the status, member set and envelope are already correct.
Traces: lightsail-catalog-get-blueprints#task#1.

Cause 2 of 2: GetBundles serves only the first 20 bundles, so the large Windows bundles and the entire IPv6-only bundle family are absent from the catalog.
AWS: Smithy com.amazonaws.lightsail#GetBundles is an awsJson RPC operation (POST /ls/api/2016-11-28/GetBundles, success 200) whose output member `bundles` is a BundleList of com.amazonaws.lightsail#Bundle (bundleId, name, instanceType, power, price, cpuCount, ramSizeInGb, diskSizeInGb, transferPerMonthInGb, publicIpv4AddressCount, isActive, supportedPlatforms). Smithy documents `power` as the value a client pairs with a blueprint's minPower to decide whether that blueprint will run on the bundle, and `publicIpv4AddressCount` as 0 or 1, but fixes no row set, so the catalog contents are recorded behavior only. The recording shows AWS serving the full bundle catalog - well past 100 entries - including the large Windows tiers ('12xlarge_win_3_0', instanceType '12xlarge', power 7500, supportedPlatforms ['WINDOWS'], publicIpv4AddressCount 1; '16xlarge_win_3_0', instanceType '16xlarge', power 8000) and the IPv6-only Linux family ('nano_ipv6_3_0', 'micro_ipv6_3_0', 'small_ipv6_3_0', 'medium_ipv6_3_0', 'large_ipv6_3_0', ... - each with publicIpv4AddressCount 0).
Emulator: the list stops after 20 rows. Replay reports every asserted position from $.bundles[20] to $.bundles[99] as missing with actual value None, status 200 -> 200. The IPv6-only family (publicIpv4AddressCount 0) and the large Windows tiers are therefore not present in the catalog at all.
Why: a bundle that is not listed cannot be chosen, so no client can create an instance on an IPv6-only bundle or on a large Windows tier against the emulator, and a client that validates a bundleId against GetBundles before calling CreateInstances will reject a bundle AWS accepts. Because the operation answers 200 with a well-formed list, the client sees a plausible-looking but silently truncated catalog rather than an error. This is a separate cause from cause 1: it is a different operation and a different table, and completing the blueprint table does not add a single bundle row.
Fix: the static bundle catalog table behind the GetBundles handler in the lightsail crate - add the omitted rows (the large Windows tiers and the whole IPv6-only family) with their bundleId/instanceType/power/price/cpuCount/ramSizeInGb/diskSizeInGb/transferPerMonthInGb/publicIpv4AddressCount/supportedPlatforms values, in AWS's order.
Traces: lightsail-catalog-get-bundles#task#1.
