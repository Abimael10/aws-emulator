# cloudwatch: 2 net-new causes — a child forced by SetAlarmState is reclaimed before any composite alarm can observe it, so no composite rule ever reaches ALARM, and DescribeAlarmsForMetric reports the pre-force state seconds after the force

> _Note: this issue was identified against the code base at commit `73ee5db70c54544c27a351cd5968d4682ba0e095`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
SetAlarmState

## Description
TWO independent net-new causes in the cloudwatch alarm-state engine. None of the failing checks below was marked ALREADY FILED or OWNED by the replay report. TWO causes must be closed before submitting.

Prior work that does NOT carry these failures: 20261108T001650Z-cloudwatch-3-net-new-causes-a-composite-alarmrule.md (its Cause 1) owns only the two AND-combinator checks (cloudwatch.composite-alarm-and-rule-requires-all-children, cloudwatch.composite-alarm-boolean-and-logic) and explicitly records that at that time a SINGLE-term ALARM("child") rule DID reach ALARM; the nine composite checks listed here are single-term, OR-term and lifecycle checks it does not list, and they now fail as timeouts because no rule shape at all becomes observably ALARM. 20261111T170129Z-cloudwatch-a-setalarmstate-transition-delivers-no-notification-to.md covers the NOTIFICATION a forced transition owes, not how long the forced state stands. 20261029T182452Z-cloudwatch-request-validation-and-error-envelope-divergences-10.md owns cloudwatch.op-contract-set-alarm-state (request validation), not the duration of a forced state.

=== Cause 1 of 2: a composite alarm never observably transitions to ALARM when a child its AlarmRule references is forced into ALARM ===
Failing check ids: cloudwatch.composite-alarm-evaluates-child-alarm-state, cloudwatch.composite-alarm-or-logic, cloudwatch.composite-alarm-reflects-child-alarm-state, cloudwatch.composite-alarm-reflects-child-alarm-transition, cloudwatch.composite-alarm-state-derived-from-child-alarm, cloudwatch.composite-alarm-state-derived-from-children, cloudwatch.e2e-composite-alarm-cascade-lifecycle, cloudwatch.e2e-composite-alarm-drives-downstream-action-and-cleanup, cloudwatch.op-contract-put-composite-alarm.
AWS: Smithy (services/service-com-amazonaws-cloudwatch-graniteserviceversion20100801/smithy-model/com-amazonaws-cloudwatch-graniteserviceversion20100801.json) — PutCompositeAlarm input AlarmRule is @required, @length 1..10240, "an expression that specifies which other alarms are to be evaluated to determine this composite alarm's state", and the operation documents "When this operation creates an alarm, the alarm state is immediately set to INSUFFICIENT_DATA. The alarm is then evaluated and its state is set appropriately. Any actions associated with the new state are then executed." SetAlarmState documents "Temporarily sets the state of an alarm for testing purposes. When the updated state differs from the previous value, the action configured for the appropriate state is invoked. [...] Metric alarms returns to their actual state quickly, often within seconds. [...] If you use SetAlarmState on a composite alarm, the composite alarm is not guaranteed to return to its actual state. It returns to its actual state only once any of its children alarms change state." DescribeAlarms returns composite alarms in CompositeAlarms and only when AlarmTypes names CompositeAlarm. Recorded behavior: a metric child driven to ALARM by SetAlarmState holds ALARM long enough for every composite whose rule reads it to be re-derived and transition to ALARM — the recordings observe that transition by polling DescribeAlarms every 3-5 s — and the composite then STAYS in ALARM (its state is owned by the rule over the children's current states, and the child's forced state is the child's current state) until a child changes state again.
Emulator: the composite is created and is visible via DescribeAlarms(AlarmTypes=['CompositeAlarm']) with a non-ALARM baseline (those legs pass), but after SetAlarmState(child, 'ALARM') no poll ever reads the composite in ALARM; all nine checks exhaust their budget (reported as `Check timed out after 60.0s`, the harness cap on polling windows of 90-150 s). This holds for the single-term rule ALARM("child"), for an OR rule with one child forced, and for the AND rule of cloudwatch.op-contract-put-composite-alarm. Hypothesis, grounded in the checkout: services/service-com-amazonaws-cloudwatch-graniteserviceversion20100801/src/state/alarm_evaluation.rs:357 sets FORCED_STATE_SECS = 3.0 and forced_state_span_secs() (same file, ~line 921) clamps the forced span to AT MOST 3 s whatever the alarm's Period, while the parent composite's evaluation is only owed COMPOSITE_EVALUATION_DELAY_SECS later (src/state.rs:2942, make_parents_due at src/state.rs:3238) and the metric-alarm reclaim is materialised in the same settle pass; so by the time a composite evaluation is materialised the child has already been taken back out of ALARM and the rule is evaluated against the reclaimed state. The forced child state is therefore never an input any composite evaluation can see.
Why: composite alarms exist to combine conditions into one page, and SetAlarmState is the documented way to drive a child's state in a test. A composite that can never be observed in ALARM never runs its AlarmActions, so a client testing an alarm topology against the emulator sees "nothing is wrong" where the real topology would have paged, and cannot distinguish a correctly derived composite from one whose rule is never evaluated.
Fix: the forced-state span and the settle ordering in the alarm state engine (the SetAlarmState handler plus the metric/composite evaluation passes it drives): a state forced on a metric alarm must stand until that alarm's own next evaluation — one of its Periods away, not a fixed few seconds — and the composite pass owed by that child's transition must evaluate the rule against the forced state rather than against a reclaim materialised first in the same pass.
Traces: cloudwatch.composite-alarm-evaluates-child-alarm-state, cloudwatch.composite-alarm-reflects-child-alarm-state, cloudwatch.composite-alarm-reflects-child-alarm-transition, cloudwatch.composite-alarm-state-derived-from-child-alarm, cloudwatch.composite-alarm-state-derived-from-children (single-term ALARM("child") rules), cloudwatch.composite-alarm-or-logic (OR rule, one child forced), cloudwatch.op-contract-put-composite-alarm (AND rule; the malformed-AlarmRule leg of that check is never reached), cloudwatch.e2e-composite-alarm-cascade-lifecycle and cloudwatch.e2e-composite-alarm-drives-downstream-action-and-cleanup (lifecycle checks blocked at the same transition). Code cited above: src/state/alarm_evaluation.rs:357 and ~921, src/state.rs:2942 and 3238.

=== Cause 2 of 2: a metric alarm's forced state is already reclaimed a few seconds after SetAlarmState, so DescribeAlarmsForMetric reports the pre-force state inside one client session ===
Failing check id: cloudwatch.cli-alarms-for-metric-query-matches-the-sdk.
AWS: Smithy (same model) — DescribeAlarmsForMetric takes Namespace and MetricName (@required) plus Dimensions/Statistic/Period/Unit and returns MetricAlarms; it models no errors, so the StateValue it reports is the whole observable. SetAlarmState documents the forced state as standing until the alarm returns to its actual state, which for a metric alarm is its next evaluation ("Metric alarms returns to their actual state quickly, often within seconds"). Recorded behavior: after SetAlarmState(alarm, 'ALARM') on an alarm configured with Period=300 over a metric with no datapoints at all, both the CLI (`aws cloudwatch describe-alarms-for-metric --dimensions Name=...,Value=... --query 'MetricAlarms[0].StateValue'`) and the SDK still report StateValue 'ALARM' after the four intervening lookups the check makes, while the sibling alarm that was never forced still reports 'INSUFFICIENT_DATA'.
Emulator: the CLI and SDK agree with each other (that leg passes, for both the one- and two-dimension alarm), but the final read of the forced alarm reports a StateValue other than 'ALARM' — `AssertionError: the cluster-wide alarm should read ALARM`. The forced state has already been taken back by an evaluation a few seconds after the write, because the span it stands for is capped at 3 s (src/state/alarm_evaluation.rs:357, forced_state_span_secs ~line 921) instead of being derived from the alarm's Period (300 s here).
Why: SetAlarmState is the only way a client can drive an alarm into a state without waiting for real data, and every test of alarm-triggered behavior reads the state back afterwards. An emulator that reclaims the forced state within a couple of seconds makes SetAlarmState unusable: the read that follows it reports the state the caller was trying to replace, and the caller cannot tell a forced transition that happened from one that was refused.
Fix: forced_state_span_secs in the alarm evaluation state (src/state/alarm_evaluation.rs) — the span a forced metric-alarm state stands for must be the alarm's own next evaluation, i.e. derived from its Period, not a fixed 3-second ceiling.
Traces: cloudwatch.cli-alarms-for-metric-query-matches-the-sdk.
