Cause 1 of 2: GetTraceSummaries returns a NextToken on a response that is the complete answer to the requested window.
AWS: Smithy (services/service-com-amazonaws-xray-awsxray/smithy-model/com-amazonaws-xray-awsxray.json) models GetTraceSummaries as POST /TraceSummaries (success 200) with @paginated {inputToken: NextToken, outputToken: NextToken, items: TraceSummaries}; GetTraceSummariesResult$NextToken is String, unconstrained, documented "If the requested time frame contained more than one page of results, you can use this token to retrieve the next page. The first page contains the most recent results, closest to the end of the time frame" — i.e. whether a token is due is keyed on how many RESULTS the requested time frame holds, not on how many hour boundaries that frame happens to cross. For the sub-hour window this is recorded behavior only: the recording queries a window of a few minutes that holds exactly the one trace just accepted by PutTraceSegments, and AWS answers 200 with that single summary and NO NextToken member at all (the fixture asserts NextToken is absent/null).
Emulator: the same request answers 200 with a NextToken present. The emulator cuts the requested window into one-hour slices of the ABSOLUTE epoch hour grid and serves only the slice the window's EndTime falls in, then emits a token whenever the requested window still reaches into an earlier slice — explicitly "whether or not the slice just served held anything". A window of a few minutes that straddles the top of an hour therefore always pages, so the token's presence is decided by the clock rather than by the result set.
Why: a client that paginates GetTraceSummaries (every SDK paginator, and any "fetch until NextToken is absent" loop) is told there is a further page of results for a window whose answer it has already received in full, so it issues at least one additional round trip per query and cannot use "no NextToken" as the termination signal AWS defines. Worse, the signal is not reproducible: the identical logical query made a minute later, on the other side of an hour boundary, answers with no token, so a client cannot tell "more results exist" from "my window happened to cross the top of an hour".
Fix: the next_token composition in the GetTraceSummaries handler together with the window/page derivation it reads — services/service-com-amazonaws-xray-awsxray/src/ops/get_trace_summaries.rs (the `next_token` match over `resume_at` / `page.earlier`, and TRACE_SUMMARIES_PAGE_SIZE) and services/service-com-amazonaws-xray-awsxray/src/state/trace_pages.rs (TRACE_PAGE_SECONDS, the hour-grid boundary walk and WindowPage.earlier). A token must be due only while the query has RESULTS left to serve: derive the pages from the requested window and the number of selected summaries, so a window shorter than one page is one page and answers with the NextToken member absent, while a genuinely multi-page result set keeps carrying one.
Traces: xray-put-segment-is-found-by-trace-summaries-and-batch-get#task#2.

Cause 2 of 2: ApproximateTime is the absolute hour-grid boundary the served slice is cut on, not the start of this page of results.
AWS: Smithy GetTraceSummariesResult$ApproximateTime targets Timestamp and is documented "The start time of this page of results." With StartTime/EndTime required on the input and the whole window answered in one page (Cause 1), the start time of that page IS the start of the requested window; the recording shows AWS reporting an instant equal to the window's requested StartTime — a value derived from the REQUEST, with no alignment to any hour. The literal epoch second in the recording is a per-run value and is not the requirement; the requirement is the anchoring rule: ApproximateTime is where the served page's results begin within the requested window.
Emulator: ApproximateTime is set from the served slice's grid boundary — `page.start`, documented in trace_pages.rs as "the top of the hour that begins it" — so for a window that starts inside an earlier hour the response reports the hour boundary rather than the requested window start. In this step the value returned is exactly divisible by 3600 (the top of the hour), while the recorded value is not hour-aligned, which is what identifies this as grid snapping rather than clock skew.
Why: a client uses ApproximateTime to label the page it just read and to position the next request ("results from this instant onward"). Snapping it forward to the next hour boundary makes the response claim its page begins after traces it actually had to cover, so a client that windows or dedupes on that instant drops the part of its own requested window between StartTime and the hour boundary, and any UI that renders "results since <ApproximateTime>" mislabels the page by up to one hour. Because the reported instant depends on where the request's window sits relative to the grid, two queries over the same results report different page starts.
Fix: the ApproximateTime assembly in services/service-com-amazonaws-xray-awsxray/src/ops/get_trace_summaries.rs (`approximate_time: timestamp_of(page.start)`) and the WindowPage.start definition in services/service-com-amazonaws-xray-awsxray/src/state/trace_pages.rs — report where the page's results actually begin inside the requested window (the requested StartTime for the first/only page of a window shorter than a page), not the hour the internal slice is cut on. This is the same page-derivation decision as Cause 1 and should move with it.
Traces: xray-put-segment-is-found-by-trace-summaries-and-batch-get#task#2.
