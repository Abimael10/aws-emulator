# logs: StartLiveTail opens a session but never streams a LiveTailSessionUpdate frame, so every live-tail consumer blocks forever

> _Note: this issue was identified against the code base at commit `fa5a827558c7852c4bea0e628f9a7809957676ef`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
StartLiveTail

## Description
Cause count: 1 — one root cause must be closed before submitting.

Cause 1 of 1: a StartLiveTail session reports sessionStart and then delivers no data frame and no terminal frame.

AWS: Smithy (com.amazonaws.cloudwatchlogs#Logs_20140328) StartLiveTail takes logGroupIdentifiers (required, @length min 1 max 10) plus the optional scope members logStreamNames and logStreamNamePrefixes (@length min 1 max 100) and logEventFilterPattern (FilterPattern, @length 0..1024); its output member responseStream targets the @streaming union StartLiveTailResponseStream, and the operation carries the endpoint hostPrefix "stream-". That union models exactly four frames: sessionStart (LiveTailSessionStart: requestId, sessionId, and the resolved logGroupIdentifiers / logStreamNames / logStreamNamePrefixes / logEventFilterPattern echoed back), sessionUpdate (LiveTailSessionUpdate: sessionMetadata plus sessionResults, documented as "as many as 500 log events" per frame, sampled down above 500/s with sessionMetadata.sampled reporting that), SessionTimeoutException (documented: "returned in the stream when the Live Tail session times out. Live Tail sessions time out after three hours") and SessionStreamingException. Each LiveTailSessionLogEvent in sessionResults carries logStreamName, logGroupIdentifier, message, timestamp and ingestionTime. So AWS emits one sessionStart, then one sessionUpdate per batch of NEWLY ingested matching events — only events ingested after the session opened, narrowed by the session's logStreamNames / logStreamNamePrefixes / logEventFilterPattern scope — and ends the stream with a modelled terminal frame, never silence.

Emulator: the session opens and sessionStart IS delivered (each check's bounded wait for sessionStart, 15 s or 30 s, completes — otherwise the check would have failed with its own "StartLiveTail never delivered a sessionStart event" assertion rather than running out the clock), but no sessionUpdate frame ever follows. Events written with PutLogEvents into the tailed group and stream AFTER the session opened never appear on the response stream, and no SessionTimeoutException / SessionStreamingException frame is sent either, so the stream neither yields nor ends. Every check that drains the stream for a sessionUpdate blocks until the harness kills it: `Error: Check timed out after 60.0s` on all five check ids below. Because nothing is ever delivered, the scope semantics on top of it are unobservable too: a session scoped to logStreamNames=[A] cannot be shown to echo its scope in sessionStart and to carry only A's lines, a session with logEventFilterPattern cannot be shown to drop non-matching lines, and the rule that an already-stored event matching the filter is NOT delivered cannot be exercised at all.

Why: a client that live-tails a log group gets neither its events nor an error — it hangs indefinitely on the stream instead of either receiving data or failing. `aws logs tail --follow`, the console Live Tail view and any SDK consumer of StartLiveTail silently produce no output forever, and a caller cannot distinguish "no new matching events" from "the session is broken", because AWS's idle session still eventually reports SessionTimeoutException while this one reports nothing.

Fix: the StartLiveTail handler's streaming response in the logs service — the live-tail session registry must be fed off the log-group ingest path (PutLogEvents) and publish LiveTailSessionUpdate frames to every session subscribed to that log group, filtered by that session's logStreamNames / logStreamNamePrefixes / logEventFilterPattern scope and excluding events ingested before the session opened, with each sessionResults entry populating logStreamName, logGroupIdentifier, message, timestamp and ingestionTime, and sessionMetadata.sampled set; the session must also be terminated with the modelled SessionTimeoutException frame at the three-hour session limit rather than left silent.

Related already-filed work, named so it is not re-filed: open issue 20261107T035448Z-logs-startlivetail-refuses-a-valid-logeventfilterpattern-rejecting-any.md covers a DIFFERENT defect (StartLiveTail refusing a hyphenated unquoted filter term before any stream exists) and does not cover this missing-frame gap — the five checks here all use a quoted filter term or logStreamNames and are accepted. Resolved issue 20261110T172047Z-logs-startlivetail-never-streams-livetailsessionupdate-frames-two-refusal.md recorded this same gap as its Cause 1 against commit f23784b0aff92740251c6928f623341ae96cfe61 and is marked fixed, but the behaviour is unchanged on this replay: the identical five check ids still time out at 60 s with no sessionUpdate frame. StartLiveTail itself is not refused (it still answers with an open stream and a sessionStart frame), so this is filed as the persisting missing-frame defect rather than a refusal regression.

Traces (check ids): logs.start-live-tail-streams-new-events, logs.start-live-tail-streams-matching-events, logs.live-tail-excludes-pre-subscription-events-and-honours-the-filter, logs.log-cwl-plumbing-live-tail-stream-names-scope-delivers-only-the-named-stream, logs.log-cwl-plumbing-live-tail-stream-scope-rejected-across-two-log-groups.

## Evidence
All five live-tail checks fail with the same detail: `Error: Check timed out after 60.0s`.

Expected (AWS): after CreateLogGroup G / CreateLogStream S and StartLiveTail(logGroupIdentifiers=[<G's ARN with a trailing ':*' stripped>], logEventFilterPattern='"<marker>"'), the response stream yields one sessionStart frame echoing the requested logGroupIdentifiers (and logStreamNames when supplied) with a sessionId and requestId, and then, for each PutLogEvents batch written after the session opened, a sessionUpdate frame whose sessionResults contain the matching messages with logStreamName == S, logGroupIdentifier == '<account>:<G>', timestamp equal to the timestamp submitted in the put, an integer ingestionTime not before that timestamp, and sessionMetadata.sampled == false for an unsampled session. Non-matching lines, lines from a stream outside the session's logStreamNames scope, and lines ingested before the session opened are absent from the stream while remaining readable via FilterLogEvents.

Actual (emulator): sessionStart arrives, then nothing. logs.start-live-tail-streams-matching-events re-sends a noise line plus a matching 'hello <marker> world (attempt N)' line every 5 s for up to 60 s and then a '<marker> barrier' line, draining the stream throughout; no sessionUpdate is ever observed, so the check is killed by the suite's 60 s cap before reaching `assert matched`. logs.log-cwl-plumbing-live-tail-stream-names-scope-delivers-only-the-named-stream loops writing a numbered pair to streams A and B every 4 s waiting for an A line to be pushed and is likewise killed at 60 s, so its assertions on sessionStart's echoed logStreamNames and on each result's logStreamName / logGroupIdentifier / timestamp / ingestionTime are never reached. logs.live-tail-excludes-pre-subscription-events-and-honours-the-filter stores a pre-session event that deliberately matches the filter and then writes post-session matching and noise events for up to 90 s; it times out at 60 s with nothing delivered. No SessionTimeoutException or SessionStreamingException frame is delivered in any of them. The 60 s value is the harness budget and the marker/account/group names are per-run values, not requirements; the requirement is that a sessionUpdate frame carrying the newly ingested matching events is delivered at all.

## Steps to Reproduce
1. logs.create_log_group(logGroupName=G); logs.create_log_stream(logGroupName=G, logStreamName=S).
2. Read G's ARN from logs.describe_log_groups(logGroupNamePrefix=G) and strip the trailing ':*' (StartLiveTail rejects the wildcard suffix).
3. resp = logs.start_live_tail(logGroupIdentifiers=[<arn>]); consume resp['responseStream'] on a background thread. A sessionStart frame arrives — note its sessionId/requestId and the echoed logGroupIdentifiers.
4. logs.put_log_events(logGroupName=G, logStreamName=S, logEvents=[{'timestamp': <now ms>, 'message': 'probe <marker>'}]) and keep draining the stream. AWS delivers a sessionUpdate whose sessionResults contain 'probe <marker>' with logStreamName=S, logGroupIdentifier='<account>:<G>', the submitted timestamp and an ingestionTime; the emulator delivers no further frame at all.
5. Repeat with logStreamNames=[S] and confirm sessionStart echoes logStreamNames and that only S's post-session lines (never a second stream B's) are pushed.
6. Repeat with logEventFilterPattern='"<marker>"' and confirm non-matching lines written after the session opened are not pushed, while an event stored BEFORE the session opened that matches the filter is also never pushed — and that all of them remain readable via logs.filter_log_events(logGroupName=G).
7. Leave the session idle and confirm it is eventually terminated with the modelled SessionTimeoutException frame instead of staying silent.
