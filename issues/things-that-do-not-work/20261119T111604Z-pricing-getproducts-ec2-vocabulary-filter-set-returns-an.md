The same response's NextToken continues exactly THAT filtered population. Status 200, no error code and no error message — the requirement being violated is the response body, not the status. In the recorded run the template is filled with sku 'K7ERD2Q28HHU97DT', instanceType 't3.nano', memory '0.5 GiB', rate '0.0052000000' and description '$0.0052 per On Demand Linux t3.nano Instance Hour'; those are that run's VALUES, not the requirement — the fixed text is '$<rate> per On Demand <os> <instanceType> Instance Hour' and the variable parts come from the matched product and its published rate.

Emulator: the step also answers 200, but the replay reports `$.PriceList[0]: value_mismatch` AND names `$.NextToken` as diverging (divergence_key `service=pricing|GetProducts|status=200->200|keys=$.NextToken,$.PriceList[0]`). The pricing catalog is synthesised at seed time rather than published: services/service-com-amazonaws-pricing-awspricelistservice/src/state.rs builds an immutable process-wide catalog (`seeded_catalog` / `SEEDED_CATALOG` / `build_seeded_catalog`, around lines 1273-1299) whose offer documents are RENDERED from ProductDrafts (`offer_document`, `product_from_draft`), whose SKUs are derived by concatenating identifying parts (`fn sku`, lines 1252-1263) instead of being the published opaque catalog SKUs, whose product.attributes map is only whatever keys the draft carries (`fn attributes`, lines 1266-1271), and whose Reserved terms are computed by scaling the draft's single on-demand rate by a hard-coded `rate_percent`/`upfront_percent` per `RESERVED_TERMS` entry (lines 1120-1185, with `fn scale` at 1248). Consequently the filtered selection for this vocabulary filter set starts at a different product than AWS publishes, the served document's attribute set and terms are the seed's rather than the catalog's, and the emitted continuation token describes a different remaining population.

Why: a client prices a workload from PriceList[0] and then walks the rest of the filtered set with NextToken. A different first offer means a different price AND a different product identity for the same filter set, and a token describing a different remainder means the rest of the walk enumerates different products — so a cost estimate assembled by paging GetProducts is wrong both in the figure it reports and in the inventory it covers. A client that keys a cache, a budget or a purchase off product.sku keys it off an identifier AWS never published, and because the status is 200 with a structurally valid body nothing signals that the figures are not AWS's.

Fix: the GetProducts handler's filtered selection, result ordering and NextToken encoding, together with the pricing service's catalog seed and offer-document builders in its state (`build_seeded_catalog`, `product_from_draft`, `offer_document`, `on_demand_term`, `reserved_terms` in services/service-com-amazonaws-pricing-awspricelistservice/src/state.rs). The catalog must publish offer documents — published SKU, full published attribute set, published OnDemand and Reserved dimensions — rather than documents derived from draft fields and rate-scaling percentages, and the continuation token must describe the remaining members of the same filtered set.
