# s3: the static-website data plane is unreachable — no website endpoint is published or served, so index/error documents, the unconfigured-bucket refusal, routing rules, bare-folder redirects and RedirectAllRequestsTo cannot be observed

> _Note: this issue was identified against the code base at commit `8cfbdd66d98adcc9174c78d846b863b5ea52b9a5`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
GetObject

## Description
This issue bundles 2 net-new root causes of the s3 service, both in the static-website data plane. Neither of the 7 failing checks below is marked ALREADY FILED or OWNED by an open issue in this replay, so neither cause is covered: open issue `20261118T010000Z-s3-the-rest-endpoint-serves-no-plaintext-http-and-no-website-endpoint.md` carries only the two replay keys `s3.s3-ssec-and-endpoint-enforcement-ssec-request-over-plain-http-rejected` and `s3.s3-ssec-and-endpoint-enforcement-website-endpoint-serving-an-ssec-object-rejected`, and the website-endpoint reports `20261113T120806Z-s3-the-emulator-publishes-no-s3-website-endpoint.md`, `20261117T213222Z-s3-4-net-new-causes-no-static-website.md`, `20261109T220008Z-s3-7-net-new-causes-cors-preflight-answers.md` and `20261107T185637Z-s3-4-net-new-causes-anonymous-and-website-endpoint.md` are all RESOLVED and therefore cover nothing live. The whole static-website surface is still unobservable from a client.

Cause 1 of 2: the emulator announces no S3 website endpoint at all, so every website-hosting behaviour is unreachable. Failing checks: s3.e2e-website-deployment, s3.website-endpoint-serves-index-and-error-documents-and-refuses-writes, s3.s3-website-hosting-get-rejected-for-a-bucket-never-configured, s3.s3-ssec-and-endpoint-enforcement-website-routing-rule-on-404-redirects-missing-keys.
AWS: recorded behavior only — the Smithy model describes the CONFIGURATION operations but not the serving endpoint (com.amazonaws.s3#PutBucketWebsite PUT /{Bucket}?website with a required WebsiteConfiguration payload, com.amazonaws.s3#GetBucketWebsite GET /{Bucket}?website returning RedirectAllRequestsTo / IndexDocument / ErrorDocument / RoutingRules; both model an empty `errors` list). What the recordings show is a SECOND, anonymous, plaintext-HTTP endpoint per bucket, distinct from the REST endpoint, that: serves the configured IndexDocument's bytes for `/` and for any prefix ending in `/`; serves the configured ErrorDocument with HTTP 404 for a key that does not exist; answers a write (PUT/DELETE) with HTTP 405 and the error code `MethodNotAllowed` because the website endpoint supports only GET and HEAD; answers HTTP 404 for a bucket that was never given a website configuration, with an HTML error page whose `<li>Name: value</li>` fields carry Code `NoSuchWebsiteConfiguration` and the message AWS words for that class (the fixed text is that sentence; the variable parts are the bucket name and the per-request ids); and applies RoutingRules — a rule with `Condition.HttpErrorCodeReturnedEquals: 404` answers the configured 3xx with a `Location` built from `ReplaceKeyPrefixWith`/`ReplaceKeyWith` and the rule's HostName, instead of the error document. The REST endpoint's own answers for the same keys are unchanged (GetObject of a missing key is still 404 `NoSuchKey`, message "The specified key does not exist.").
Emulator: there is no such endpoint and no address for one. The harness aborts before any request is sent with `simparity.behavioral.context.CapabilityNotOffered: the emulator offers no S3 website endpoint (the run names no website endpoint template: s3_website_url=, SIMPARITY_S3_WEBSITE_URL)`. PutBucketWebsite/GetBucketWebsite themselves succeed and store the configuration, so the configuration is accepted and then serves nothing.
Why: a client that deploys a static site gets a successful PutBucketWebsite and a bucket that no browser can reach. Nothing in the website contract can be relied on: the index document, the error document, the 405 on writes, the `NoSuchWebsiteConfiguration` refusal for an unconfigured bucket and every routing rule are all absent, and any tool that chains on the website endpoint (CloudFront S3-website origins, Route 53 website aliases, `aws s3 website`) has no origin to talk to.
Fix: the s3 crate's website data plane — `services/service-com-amazonaws-s3-amazons3/src/service/website_endpoint.rs` already answers a `<bucket>.s3-website-<region>` Host and `src/service.rs` routes such a request to it, so what is missing is (a) an ADDRESS the emulator publishes and answers on for that surface, so the run names a website endpoint template, and (b) the serving semantics above (index/error document selection, 405 on non-GET/HEAD, `NoSuchWebsiteConfiguration` for an unconfigured bucket, RoutingRules evaluation).
Traces: s3.e2e-website-deployment; s3.website-endpoint-serves-index-and-error-documents-and-refuses-writes; s3.s3-website-hosting-get-rejected-for-a-bucket-never-configured; s3.s3-ssec-and-endpoint-enforcement-website-routing-rule-on-404-redirects-missing-keys.

Cause 2 of 2: the documented website hostname shapes resolve to nothing the emulator answers on, so a client that dials `<bucket>.s3-website-<region>` style hosts is refused before the request leaves. Failing checks: s3.s3-website-hosting-bare-folder-path-redirects-to-trailing-slash, s3.s3-website-hosting-missing-key-with-no-error-document-is-rejected-with-the-default-error-page, s3.s3-website-hosting-redirect-all-requests-to-answers-301-to-the-target-host.
AWS: recorded behavior only. A website-hosting bucket is reachable at both documented hostname shapes — the dash form `<bucket>.s3-website-<region>.amazonaws.com` and the dot form `<bucket>.s3-website.<region>.amazonaws.com` — over plain HTTP, and on that host: a GET of a bare folder path (a prefix that is not itself an object, e.g. `/folder`) answers HTTP 302 with `Location: /folder/` and no body bytes of the folder's index, while the REST twin GetObject of key `folder` answers 404 `NoSuchKey` "The specified key does not exist."; a GET of a missing key on a bucket with an IndexDocument but NO ErrorDocument answers HTTP 404 with S3's own default HTML error page whose `<li>Name: value</li>` fields name Code `NoSuchKey` and its message, plus the bucket name and request ids; and a bucket configured with `RedirectAllRequestsTo` answers HTTP 301 for every path with a `Location` naming the configured HostName (and Protocol when set). The fixed text in each case is the status, the code and AWS's sentence for that class; the host, bucket, key and ids are values from the request and state.
Emulator: the emulator announces no website host, so these hostnames belong to nobody it serves. The harness refuses the target with `simparity.published.PublishedUrlRejected: endpoint_url was given http://<bucket>.s3-website-<region>.amazonaws.com/ (published by the emulator or built by the check): its host is not one of the emulator's own hosts; a customer of the emulator needs http(s)://<own host>:<port>/<path> on a per-resource listener`. No HTTP exchange happens, so neither the 302-to-trailing-slash, the default error page, nor the 301 of RedirectAllRequestsTo can be produced.
Why: the website endpoint is identified by its HOST, not by a path, so a client of this emulator has no way to address a bucket's website at all — every documented website hostname is unroutable. Code and templates that encode the documented `s3-website` host shape (CDK/CloudFormation website URLs, CloudFront custom origins, Route 53 alias targets) cannot be pointed at this emulator.
Fix: publish a per-resource website listener on one of the emulator's own hosts and route the documented `<bucket>.s3-website-<region>` / `<bucket>.s3-website.<region>` Host shapes to `src/service/website_endpoint.rs`, then implement the three serving rules above (bare-folder 302 to the trailing-slash path, the default HTML error page when no ErrorDocument is configured, and the 301 for RedirectAllRequestsTo).
Traces: s3.s3-website-hosting-bare-folder-path-redirects-to-trailing-slash; s3.s3-website-hosting-missing-key-with-no-error-document-is-rejected-with-the-default-error-page; s3.s3-website-hosting-redirect-all-requests-to-answers-301-to-the-target-host.

2. PutBucketWebsite with WebsiteConfiguration={"IndexDocument":{"Suffix":"index.html"}} — succeeds.
3. Ask the emulator for the bucket's website endpoint. Expected: a published website URL that answers. Observed: CapabilityNotOffered — the run names no website endpoint template (Cause 1).
4. Dial the documented hostnames directly: GET http://<bucket>.s3-website-<region>.amazonaws.com/folder and GET http://<bucket>.s3-website.<region>.amazonaws.com/folder. Expected: HTTP 302 with Location /folder/. Observed: PublishedUrlRejected — the host is not one of the emulator's own hosts (Cause 2).
5. Repeat step 4 for (a) a missing key on a bucket with an IndexDocument and no ErrorDocument — expect HTTP 404 with the default HTML error page naming Code NoSuchKey; (b) a bucket whose WebsiteConfiguration is RedirectAllRequestsTo={"HostName":<target>} — expect HTTP 301 with Location naming <target>; (c) a bucket that was never given a website configuration — expect HTTP 404 with Code NoSuchWebsiteConfiguration; (d) a PUT to the website endpoint — expect HTTP 405 MethodNotAllowed; (e) a bucket with a RoutingRule on HttpErrorCodeReturnedEquals 404 — expect the configured 3xx with the rewritten Location.
6. Confirm the REST endpoint is unaffected: GetObject of the missing key still answers 404 NoSuchKey "The specified key does not exist."
