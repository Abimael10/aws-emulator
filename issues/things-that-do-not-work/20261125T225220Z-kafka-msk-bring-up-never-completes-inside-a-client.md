# MSK bring-up never completes inside a client-sized budget, so four data-plane contracts reach no verdict at all: the SASL/IAM produce/consume round trip, broker-enforced max.message.bytes, Configuration-supplied topic defaults and the end-to-end SCRAM cluster/topic lifecycle (4 causes)

## Operation
DescribeClusterV2

## Description
FOUR net-new root causes on the emulated kafka (MSK) surface. Each is grounded in a failing behavioral check the suite lists under `### kafka` that the report marks neither ALREADY FILED nor OWNED by an open issue, and each leaves a DIFFERENT contract unobservable. Every one of the four is killed on the harness's bare per-check ceiling (`Error: Check timed out after 60.0s`) with no HTTP status, no AWS error code and not one assertion evaluated — the emulator owns the lifecycle transitions and the endpoints these checks wait on, so the stall is the emulator's and not the runner's. Related open issues name the same family for OTHER check ids and carry none of these four replay keys: 20261124T075919Z-kafka-msk-end-to-end-cluster-topic-produce-consume.md (its recorded key is this e2e check's `_produce_and_consume#25` frame; this run is killed on the bare ceiling with no frame, so that key is not this failure's), 20261120T044901Z-kafka-msk-native-data-plane-the-sasl-iam-and.md, 20261116T234316Z-kafka-msk-native-data-plane-the-concurrent-producer-check.md, 20261118T164608Z-kafka-msk-native-data-plane-the-transactional-abort-isolation.md, 20261124T060000Z-kafka-msk-asynchronous-spans-outlast-a-client-sized-poll-scram-consume-and-the-cluster-replicator-guards.md and 20261114T065925Z-kafka-msk-asynchronous-lifecycles-never-settle-channel-configuration-delete.md. None of them covers the four contracts below.

=== Cause 1 of 4: the SASL/IAM native produce/consume round trip reaches no verdict — the IAM bring-up barrier never clears ===
AWS: Smithy kafka CreateClusterV2 (POST /api/v2/clusters, output member State -> ClusterState) answers CREATING, and DescribeClusterV2 (GET /api/v2/clusters/{ClusterArn}, output ClusterInfo -> Cluster) reports ACTIVE within a poll or two of an AWS-sized interval; GetBootstrapBrokers (GET /v1/clusters/{ClusterArn}/bootstrap-brokers) then publishes BootstrapBrokerStringSaslIam (jsonName bootstrapBrokerStringSaslIam), and an in-VPC client completes SASL_SSL / AWS_MSK_IAM on tcp/9098 and is served ApiVersions, SaslHandshake, Metadata, CreateTopics, Produce and Fetch. The round trip itself is recorded behavior plus the Apache Kafka protocol: a produced record's value, key, partition and offset as reported to the producer are exactly what a consumer reads back, binary-exact including NUL (0x00) and 0xff bytes, and the topic holds exactly that one record.
Emulator: `Error: Check timed out after 60.0s`, nothing asserted. The shared `_bring_up` leg (create -> DescribeClusterV2 ACTIVE -> an advertised SASL/IAM endpoint that accepts TCP and completes the AWS_MSK_IAM handshake) does not finish inside the budget, so neither the produce nor the consume leg runs.
Why: the canonical MSK bring-up — create a cluster, poll for ACTIVE, connect an IAM-authenticated producer — hangs against the emulator instead of returning a record or an error. Binary payload fidelity and offset/partition reporting cannot be validated at all, so an SDK integration developed here is validated against nothing.
Fix: the cluster-lifecycle timing in the kafka crate's state layer (services/service-com-amazonaws-kafka-kafka) — the CREATING -> ACTIVE span must be consumable by a first or second AWS-sized poll rather than outlasting a client's whole budget — plus the native broker plane behind every address GetBootstrapBrokers advertises, which must accept on the SASL/IAM listener, complete the handshake and serve Produce/Fetch.
Traces: kafka.kafka-iam-auth-produce-consume-round-trip-over-the-native-protocol.

=== Cause 2 of 4: broker-enforced max.message.bytes is unobservable — the same IAM bring-up plus topic-config path never reaches the produce legs ===
AWS: a topic created over the native AdminClient with the topic config `max.message.bytes` set reads that value back from the broker's DescribeConfigs (api key 32) unchanged, and the limit is enforced ON THE PRODUCE PATH BY THE BROKER: a record above the topic's max.message.bytes is refused (Kafka MESSAGE_TOO_LARGE, protocol error 10 — a protocol constant, not an account-varying value) and never appears in the log, while a record just under the limit is appended and round-trips byte-exactly. This is recorded behavior plus the Apache Kafka protocol; the AWS control plane cannot observe it (the Smithy model has no member for it).
Emulator: `Error: Check timed out after 60.0s`, nothing asserted — the run dies in the same pre-data-plane bring-up, so neither the config read-back, nor the refusal, nor the just-under round trip is exercised.
Why: an over-permissive broker that accepts an oversized record, or one that silently drops the topic config, is indistinguishable from a correct one here. A client that relies on the broker to bound record size (and on MESSAGE_TOO_LARGE to signal it) gets no signal at all.
Fix: the same bring-up path as Cause 1, and in the native broker plane the per-topic config store and the produce-path size check that must honour `max.message.bytes` and answer MESSAGE_TOO_LARGE without appending.
Traces: kafka.kafka-record-above-max-message-bytes-rejected-and-a-just-under-record-round-trips.

=== Cause 3 of 4: a cluster Configuration's num.partitions / default.replication.factor defaults are unobservable — the PLAINTEXT bring-up never reaches the broker legs ===
AWS: CreateConfiguration (Smithy: POST /v1/configurations, required members Name and ServerProperties -> __blob, KafkaVersions -> __listOf__string, output State -> ConfigurationState) publishes server properties; a cluster created with that ConfigurationInfo runs brokers that SUBSTITUTE those values for a CreateTopics (api key 19) asking for the defaults — num_partitions=-1 and replication_factor=-1 get the Configuration's `num.partitions` and `default.replication.factor`, the brokers' own DescribeConfigs (api key 32) reports those same values, an explicit-count topic in the same run still gets exactly what it asked for, and a never-created topic stays UNKNOWN_TOPIC_OR_PARTITION (Kafka error 3) because `auto.create.topics.enable` is false. Recorded behavior plus the Apache Kafka protocol; the Smithy model carries only the Configuration control plane.
Emulator: `Error: Check timed out after 60.0s`, nothing asserted. This check's listener is PLAINTEXT on tcp/9092 and unauthenticated — no TLS or SASL is involved — so the stall is in the create/Configuration/ACTIVE/endpoint-publication chain itself, not in any handshake.
Why: a client that centralises topic defaults in an MSK Configuration cannot tell whether the emulator honours them, drops them, or applies Apache defaults instead. Partition counts and replication factors are capacity and durability decisions; getting them silently wrong in a validation environment is worse than failing.
Fix: the cluster-lifecycle and configuration-association timing in the kafka crate's state layer, and the native broker plane's CreateTopics default substitution plus DescribeConfigs for the broker-level properties a Configuration supplies.
Traces: kafka.msk-cluster-configuration-num-partitions-default-is-applied-by-the-broker.

=== Cause 4 of 4: the end-to-end SCRAM cluster/topic lifecycle (create -> serve -> delete -> NotFoundException) reaches no verdict ===
AWS: the full sequence is observable within a client-sized polling budget — CreateClusterV2 provisioned (Sasl.Scram + Sasl.Iam, EncryptionInTransit.ClientBroker=TLS, an ACL-enforced Configuration) -> DescribeClusterV2 CREATING then ACTIVE -> BatchAssociateScramSecret -> CreateTopic (POST /v1/clusters/{ClusterArn}/topics, Status -> TopicState) CREATING then ACTIVE -> GetBootstrapBrokers.BootstrapBrokerStringSaslScram -> a SCRAM-SHA-512 SASL_SSL producer's record consumed back from the earliest offset -> DeleteTopic, after which DescribeTopic answers 404 with Error.Code NotFoundException, and DeleteCluster, after which DescribeClusterV2 answers 404 with Error.Code NotFoundException.
Emulator: `Error: Check timed out after 60.0s`. The budget is spent in the waiters that precede the data-plane leg; no record is produced and neither post-delete NotFoundException assertion is reached.
Why: the service's primary happy path plus its deleted-resource refusal contract are both unreachable, so teardown correctness (does a deleted topic/cluster really stop resolving?) is unverifiable.
Fix: the same cluster/topic lifecycle timing in the kafka crate's state layer (the cluster create span, the topic activation span, and whatever gates the bootstrap-broker strings and the SCRAM listener behind cluster ACTIVE) and the SCRAM listener behind the advertised string. Open issue 20261124T075919Z-kafka-msk-end-to-end-cluster-topic-produce-consume.md describes this same check's family but carries a different replay key (a timeout inside `_produce_and_consume#25`, i.e. a run that had already reached the data plane); this run never reaches it, so the failure is filed here.
Traces: kafka.e2e-cluster-topic-lifecycle-produce-consume-teardown.

Note on what is NOT claimed: the 60.0 s figure is this runner's per-check ceiling and the checks' 2/5/15/30 s sleeps are their own poll intervals. No particular literal duration is a requirement — the requirement is that each CREATING -> ACTIVE transition and each advertised endpoint's readiness be observable to a client polling at an AWS-sized interval, as they are on real MSK.
