# cognito-idp hosted-UI read paths serve incomplete server-managed state: managed-login branding defaults truncated and DomainDescription empty (3 causes)

> _Note: this issue was identified against the code base at commit `9a6c9844b7b2b3cba2945c38dfe9b6ac305cdb4c`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
DescribeManagedLoginBranding

## Description
Three independent causes, all cognito-idp, all 200 responses whose body reports less hosted-UI/managed-login state than AWS does. In each case the emulator answers 200 but the server-managed payload it projects (the Cognito-provided branding style, or the user pool domain record) is materially incomplete, so a client reading it back cannot reconstruct the resource AWS would have described.

Cause 1 of 3: DescribeManagedLoginBranding returns a truncated Cognito-provided default asset set and wrong default style values.
AWS: DescribeManagedLoginBranding answers 200 with ManagedLoginBranding populated from the style stored for the branding id. For a style created with UseCognitoProvidedValues=true, Cognito materializes its complete default branding style, and the describe path returns that whole style: Assets as the full list of default image assets (one AssetType per Category/ColorMode/Extension combination Cognito ships, each with its Bytes blob), and Settings as the full default settings document. Smithy: DescribeManagedLoginBranding output ManagedLoginBranding -> ManagedLoginBrandingType; ManagedLoginBrandingType.Assets -> AssetListType @length min 0 max 40 of AssetType (Category @required, ColorMode @required, Extension @required, Bytes blob @length 0..1000000, ResourceId); ManagedLoginBrandingType.Settings -> Document; ManagedLoginBrandingType.UseCognitoProvidedValues doc: "When true, applies the default branding style options. This option reverts to default style options that are managed by Amazon Cognito." The exact byte content and colour literals of Cognito's default style are recorded behavior only; what is required is that the default style the emulator materializes is the SAME, COMPLETE default style on every read, not a prefix of it.
Emulator: answers 200 but Assets stops short of the recorded default list - the recorded entries at positions 30 through 37 are absent entirely (Assets[30]..Assets[37] all read None), i.e. the emulator's built-in default asset table holds only the first 30 of the default assets. In the same response, these Settings paths carry values other than the recorded Cognito defaults: componentClasses.dropDown.darkMode.match.itemTextColor; componentClasses.statusIndicator.darkMode.pending.indicatorColor; componentClasses.statusIndicator.lightMode.pending.indicatorColor; components.idpButton.standard.darkMode.defaults.borderColor; components.idpButton.standard.darkMode.defaults.textColor; components.idpButton.standard.lightMode.defaults.borderColor; components.idpButton.standard.lightMode.defaults.textColor; components.pageFooter.darkMode.background.color; components.pageFooter.lightMode.borderColor; components.pageHeader.darkMode.background.color; components.pageHeader.lightMode.borderColor; components.primaryButton.darkMode.disabled.backgroundColor; components.primaryButton.darkMode.disabled.borderColor; components.primaryButton.lightMode.disabled.backgroundColor; components.primaryButton.lightMode.disabled.borderColor. Hypothesis: the default style is a hand-transcribed constant in the emulator that was copied partially and with substituted colour tokens, rather than the default style Cognito serves.
Why: a client that reads a Cognito-provided style to seed its own branding editor, or that diffs a describe against the style it intends to PUT, sees a style missing eight assets and with different disabled/pending/header/footer/idp-button colours. It will either render a managed-login page with missing images, or compute a spurious diff and overwrite Cognito's defaults on the next UpdateManagedLoginBranding - and a round-trip (describe then update with the describe result) silently drops the eight absent assets.
Fix: the managed-login branding state that CreateManagedLoginBranding writes when UseCognitoProvidedValues=true (the stored default asset list and default Settings document must be the complete default style), and DescribeManagedLoginBranding's projection of it. Not the error paths - the branding refusal wording is owned by the open issue 20261030T233240Z-cognito-idp-branding-and-user-pool-not-found.md, which does not carry this step.
Traces: cognito-idp-managed-login-branding-crud#task#6.

Cause 2 of 3: DescribeManagedLoginBrandingByClient has the same truncated/altered default style on the by-client read path.
AWS: DescribeManagedLoginBrandingByClient resolves the style assigned to the given app client and answers 200 with the identical ManagedLoginBranding payload the by-id read would return for that style - same Assets list, same Settings document. Smithy: DescribeManagedLoginBrandingByClient input UserPoolId @required, ClientId @required (@sensitive), ReturnMergedResources default false; output ManagedLoginBranding -> ManagedLoginBrandingType (the same shape as DescribeManagedLoginBranding).
Emulator: answers 200 with the same defect as Cause 1 on this operation - recorded Assets[30]..Assets[37] absent, and the same componentClasses.dropDown/statusIndicator, components.idpButton/pageFooter/pageHeader/primaryButton Settings paths carrying non-default values. It is listed separately because it is a separate handler/read path: a fix to the by-id serializer alone leaves this one diverging, and vice versa; whichever component is corrected, both read paths must return the same complete style.
Why: a managed-login client (the hosted UI itself, or an app resolving branding for its client id) is the main consumer of this operation, so the incomplete style is what actually gets rendered: eight default assets never load and the dark/light mode colours differ from AWS's.
Fix: the shared default-style source the branding state holds, plus DescribeManagedLoginBrandingByClient's handler/serializer (client -> style resolution must project the whole stored style).
Traces: cognito-idp-managed-login-branding-lifecycle#task#6.

Cause 3 of 3: DescribeUserPoolDomain answers 200 with an entirely empty DomainDescription for a domain that exists.
AWS: after CreateUserPoolDomain succeeds, DescribeUserPoolDomain answers 200 with DomainDescription populated: UserPoolId naming the attached pool, AWSAccountId, Domain echoing the created prefix, S3Bucket, CloudFrontDistribution, Version, Status (ACTIVE once provisioned) and ManagedLoginVersion as configured. Smithy: DescribeUserPoolDomain input Domain @required (@length 1..63, pattern ^[a-z0-9](?:[a-z0-9\-]{0,61}[a-z0-9])?$); output DomainDescription -> DomainDescriptionType with members UserPoolId, AWSAccountId, Domain, S3Bucket, CloudFrontDistribution, Version, Status (DomainStatusType enum), CustomDomainConfig, ManagedLoginVersion, Routing. The S3 asset bucket name and the CloudFront hostname are server-generated per environment and the Version is a generated stamp, so their literal values are not the requirement - presence and internal consistency are (Domain equal to the created prefix, UserPoolId equal to the pool it was created against, Status ACTIVE, ManagedLoginVersion equal to the value supplied at create).
Emulator: answers 200 with a DomainDescription in which every one of those members reads None - UserPoolId, AWSAccountId, Domain, S3Bucket, CloudFrontDistribution, Version, Status and ManagedLoginVersion are all absent. An empty DomainDescription is AWS's answer for a domain that does NOT exist, so the emulator reports a freshly created, attached domain as non-existent.
Why: a client resolving a pool's hosted-UI / managed-login endpoint, or polling for Status to become ACTIVE after CreateUserPoolDomain, gets no endpoint and no status at all: the poll never terminates and the sign-in URL cannot be constructed. Diagnostic flows that read a domain back to confirm which pool owns a prefix conclude the prefix is free. Note: the open issue 20261102T111936Z-cognito-idp-response-payloads-diverge-read-paths-omit.md describes this same read path and names this fixture and step, but the replay harness reports this cluster as unowned (its current key set additionally covers $.DomainDescription.S3Bucket, .CloudFrontDistribution, .Status and .Version), so it is filed here to keep the replay key bound to a live issue; a fixer closing that issue should re-replay this step too.
Fix: DescribeUserPoolDomain's handler/serializer plus the domain record CreateUserPoolDomain writes - the server-generated asset bucket, distribution hostname, version and status must be materialized at create time and projected on the read.
Traces: cognito-idp-osc-dashboards-client-callback-diagnosis#task#7.
