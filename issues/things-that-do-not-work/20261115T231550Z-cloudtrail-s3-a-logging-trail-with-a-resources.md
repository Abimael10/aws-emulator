# cloudtrail__s3: a logging trail with a resources.ARN StartsWith/NotStartsWith advanced selector delivers no S3 object data-event log file, so prefix-exclusion semantics are never observable

> _Note: this issue was identified against the code base at commit `7b55baed730004102687694205eddf9ed2138a54`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
PutEventSelectors

## Description
ONE net-new root cause in this issue (Cause 1 of 1).

Cause 1 of 1 — while a trail is logging with an advanced event selector scoped to eventCategory Data / resources.type AWS::S3::Object and a resources.ARN StartsWith (plus, on one trail, NotStartsWith) condition, no object data-event log file is ever delivered to the trail's S3 bucket, so neither the included nor the excluded side of a prefix exclusion can be observed. Failing check: cloudtrail__s3.obs-s3-2-arn-prefix-exclusion-withholds-object-data-events.

AWS: Smithy (services/service-com-amazonaws-cloudtrail-cloudtrail-20131101/smithy-model/com-amazonaws-cloudtrail-cloudtrail-20131101.json) models exactly the configuration this check installs: PutEventSelectors.AdvancedEventSelectors, AdvancedEventSelector.FieldSelectors (required, @length min 1) of AdvancedFieldSelector, whose Field is required and whose operator members include Equals, StartsWith and NotStartsWith — NotStartsWith is documented as "An operator that excludes events that match the first few characters of the event record field specified as the value of Field", and the Field doc states selectors support no wildcards so StartsWith/NotStartsWith are the sanctioned way to match a prefix. GetEventSelectors echoes the stored selectors and GetTrailStatus.IsLogging reports the logging state. The delivery itself is recorded behavior only (as measured by this check against real AWS): while such a trail is logging, every S3 object-level call whose object ARN matches the selector is delivered as a record inside a gzipped JSON object under the trail's configured S3 key prefix, path <S3KeyPrefix>/AWSLogs/<account-id>/CloudTrail/<region>/YYYY/MM/DD/, with eventSource "s3.amazonaws.com", eventCategory "Data", requestParameters.bucketName and requestParameters.key taken from the request, and exactly one resources[] entry of type AWS::S3::Object whose ARN is arn:aws:s3:::<bucket>/<key>. A selector carrying NotStartsWith [arn:aws:s3:::<bucket>/<excluded-prefix>/] must deliver the calls on keys outside that prefix and withhold every call on keys under it, while an otherwise identical selector without the NotStartsWith (the check's control trail, delivered under its own S3KeyPrefix in the same bucket) must deliver both sides. All bucket names, key names and account ids above are values from the request and state, not fixed text.

Emulator: nothing is delivered on either trail. The check creates the log bucket (with the cloudtrail.amazonaws.com delivery policy for both key prefixes), creates the data bucket, creates two trails, calls PutEventSelectors, asserts GetEventSelectors reads the advanced selectors back as submitted, calls StartLogging and asserts GetTrailStatus().IsLogging is True — so the emulator claims both trails are logging. It then issues rounds of PutObject/GetObject on an included/ key, PutObject/GetObject on an excluded/ key and a barrier PutObject (all of which return successfully from S3, with the GetObject bodies asserted equal to the payload) and polls ListObjectsV2 + GetObject over <prefix>/AWSLogs/ in the log bucket for the records of any one round. Its own delivery budget is 600 s (2 s poll interval, up to 20 rounds, DATAPLANE_MARKER = 'DATAPLANE_UNIMPLEMENTED' for exactly this absence), so the poll never exits and the harness ends the check: verdict 'mismatch', detail 'Check timed out after 60.0s'. ListObjectsV2 under either key prefix returns no *.json.gz object at all.

Why: a client that consumes a trail's S3 prefix (Athena/Glue over the CloudTrail log layout, SIEM ingestion, incident reconstruction) sees a permanently empty prefix and cannot tell "no one touched the data" from "nothing was recorded". Specifically for this configuration, the exclusion cannot be validated at all: a cost- or privacy-motivated NotStartsWith exclusion appears to work only because nothing is ever delivered, so a client cannot distinguish a correctly applied exclusion from a trail that records nothing, and would ship a selector it has never actually exercised.

Fix: S3 object data-event capture plus trail log-file delivery, and advanced-selector evaluation in the trail's logging path — S3's object operations must feed the shared event-recording seam as eventCategory Data records carrying the AWS::S3::Object resource ARN and the request parameters; the logging trail must evaluate its stored AdvancedEventSelectors (including the negative operators NotStartsWith/NotEndsWith/NotEquals, which must exclude a matching record even when a positive StartsWith in the same field selector matches) against those records and write the matching ones as gzipped objects under the trail's configured S3KeyPrefix in the documented key layout.
