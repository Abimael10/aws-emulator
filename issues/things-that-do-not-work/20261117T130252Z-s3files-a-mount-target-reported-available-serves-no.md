# s3files: a mount target reported `available` serves no NFS data plane — the in-guest mount/write/read-back script ends SSM Status 'Failed' with no output

> _Note: this issue was identified against the code base at commit `cea05121548b3a16dc11942b4ef340d67b81162b`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
CreateMountTarget

## Description
One net-new root cause in the s3files native (NFS) data plane, grounded in the single failing check the suite lists under '### s3files' that the replay report marks neither ALREADY FILED nor OWNED (the other three s3files failures and all five cloudformation__s3files failures are marked OWNED and are skipped here).

Related open issues, none of which covers this check (the report reports no owner for it): 20261022T204614Z-s3files-six-control-plane-fidelity-defects-missing-nested.md is control-plane validation only; 20261110T025853Z-s3-getobject-404-nosuchkey-for-an-object-written.md and 20261116T083428Z-s3-getobject-still-answers-404-nosuchkey-for-a.md are filed under service 's3' and cover only the LATER leg of this flow (the S3 GetObject of the written key), which this check never reaches because the mount itself fails first; 20261117T112858Z-efs-the-native-nfsv4-data-plane-still-does.md is the same failure mode in the efs service, not s3files, and a fixer should close the two together if one backing listener/data-plane gap explains both. The ssm Run Command issues (20261114T235914Z-ssm-run-command-responses-diverge-sendcommand-and-getcommandinvocation.md, 20261115T010213Z-ssm-getcommandinvocation-an-in-guest-dns-probe-invocation.md) describe in-guest execution and response-member gaps on other flows and do not carry this check's key either.

Cause 1 of 1: a mount target whose control-plane status the service reports as `available` does not serve the s3files NFS protocol at the ipv4Address it reports, so the in-guest script that installs the mount helper, mounts the file system, writes a file through the mount and cats it back never succeeds — the AWS-RunShellScript invocation reaches terminal Status 'Failed' and carries no StandardErrorContent at all, so the client cannot even tell which step failed. The check's own marker classifies this as DATAPLANE_UNIMPLEMENTED and explicitly rules out network reachability: the instance is launched into the mount target's own subnet with a security group that allows TCP 2049 from itself, the file system has a resource policy granting the account s3files:* and the instance role carries s3files:ClientMount/ClientWrite/ClientRootAccess. Failing check: s3files.native-nfs-mount-round-trip.

AWS: Smithy com.amazonaws.s3files (services/service-com-amazonaws-s3files-s3files/smithy-model/com-amazonaws-s3files-s3files.json): CreateMountTarget (PUT /mount-targets, success 200) takes fileSystemId (required, ^(arn:aws[-a-z]*:s3files:...:file-system/fs-[0-9a-f]{17,40}|fs-[0-9a-f]{17,40})$), subnetId (required, ^subnet-[0-9a-f]{8,40}$) and securityGroups, and returns MountTargetId (required, ^fsmt-[0-9a-f]{17,40}$), subnetId, ipv4Address (^[0-9]{1,3}(\.[0-9]{1,3}){3}$), networkInterfaceId, vpcId, securityGroups and status (LifeCycleState); GetMountTarget (GET /mount-targets/{mountTargetId}, 200) is the documented read-back of status and ipv4Address. Its modelled refusals (ConflictException 409, ResourceNotFoundException 404, ServiceQuotaExceededException 402, ValidationException 400, ThrottlingException 429, InternalServerException 500) say nothing about what status `available` promises; that promise is recorded behavior only. Recorded behavior: once GetMountTarget reports status `available`, the s3files NFS endpoint answers at that ipv4Address from inside the VPC, `mount -t s3files <fileSystemId>:/ <dir>` via amazon-efs-utils (>= 3.0) succeeds using the instance role over TLS, a file written through the mount is read back byte-for-byte on the same mount, the AWS-RunShellScript invocation ends Status 'Success' with the payload on StandardOutputContent, and the write is afterwards exported to the backing S3 bucket as an object at that key. Recorded behavior for SSM additionally: a FAILED AWS-RunShellScript invocation still returns the script's captured StandardErrorContent (here the mount helper's own error text), so a terminal 'Failed' with both output members empty is itself a divergence.

Emulator: the check provisions a versioned bucket, an s3files role, a file system that reaches status `available`, a file-system policy granting the account, a security group opening TCP 2049 to itself, and a mount target that GetMountTarget reports with status `available` and an ipv4Address in the chosen subnet; it then launches an instance in that same subnet, waits for SSM PingStatus 'Online' and sends the mount/write/read script. The invocation reaches terminal Status 'Failed' and StandardErrorContent is empty ('DATAPLANE_UNIMPLEMENTED: NFS mount/write/read script against mount target <fsmt-id> (<ipv4Address>) failed:' with nothing after the colon), so the payload is never echoed back and the downstream S3 read of the written key is never even attempted. The control plane answers CreateMountTarget/GetMountTarget and reports `available`, but nothing behind the reported address completes a mount. The mount target id and address in the message (fsmt-759fddd1d14e395ee, 172.31.0.4) are per-run values and are not part of the requirement; the requirement is that whatever address an `available` mount target reports serves the protocol.

Why: the whole premise of s3files is a file system clients mount. A client that follows the documented sequence — CreateFileSystem, wait `available`, PutFileSystemPolicy, CreateMountTarget, wait `available`, read ipv4Address, mount from an instance in the VPC — gets no usable file system, and `available` cannot be trusted as a usability signal. Every workload layered on the mount (write/read round-trip, POSIX semantics, and the export of mount writes into the backing S3 bucket that the two open 's3' GetObject issues are about) is unreachable, and because the failing invocation returns empty stdout and stderr the client has no diagnostic to distinguish a missing mount helper, a refused mount, a failed write or a failed read.

Fix: the s3files native data plane — the NFS/mount listener that a mount target's reported ipv4Address must answer on, the binding from the mount-target record in the s3files service crate's state to that listener, and the mount-target lifecycle transition that may report status `available` only once that listener answers (plus the IAM/file-system-policy authorization of the mount session the control plane already accepts). Secondarily the ssm Run Command invocation path, which must return the script's captured StandardOutputContent/StandardErrorContent on a 'Failed' invocation rather than empty strings.

Traces: s3files.native-nfs-mount-round-trip.
