# Elastic Beanstalk environment CNAME is published as host:port/path instead of a DNS name, and the RetrieveEnvironmentInfo tail is a synthesized event list rather than the instance's logs (2 causes)

Cause 1 of 2: an environment's published CNAME is not a DNS name — it is a '<host>:<port>/_aws/elasticbeanstalk/<region>/<name>' string, so its first dot-label is not the environment's CNAME prefix and no client can recover the prefix, build a DNS record, or set a Host header from it.
AWS: Smithy: DescribeEnvironments -> EnvironmentDescriptionsMessage/EnvironmentDescription member CNAME, target DNSCname (string, @length 1..255), documented 'The URL to the CNAME for this environment'; CheckDNSAvailability input CNAMEPrefix targets DNSCnamePrefix @length 4..63 and its output FullyQualifiedCNAME is documented as 'The fully qualified CNAME to reserve when CreateEnvironment is called with the provided prefix'. Recorded behavior: a launched environment's CNAME is the fully qualified name its prefix minted — a dot-separated name whose FIRST label is exactly the CNAMEPrefix the environment was created with and whose second label is the region, followed by the service's own domain; it carries neither ':' nor '/', and the prefix can therefore always be recovered as CNAME.split('.')[0] and fed straight back to CheckDNSAvailability.
Emulator: DescribeEnvironments reports CNAME as '<host>:<port>/_aws/elasticbeanstalk/<region>/<cname-prefix>' — the prefix is the LAST path segment, the region is a path segment, and the value contains a port separator and path separators a DNS name cannot hold. The CNAME-prefix check fails outright ("environment CNAME '...' does not start with its own prefix '<prefix>'"), and a client that takes the documented first dot-label gets the first octet of the host literal ('127', 3 characters), so the derived CheckDNSAvailability call is not even well-formed: botocore.exceptions.ParamValidationError 'Invalid length for parameter CNAMEPrefix, value: 3, valid min length: 4' against the modelled @length min 4. The host, port and generated names are per-run values; the requirement is the dot-separated '<prefix>.<region>.<service domain>' form with the port and path kept OUT of the CNAME value.
Why: the CNAME is the environment's public identity. A client that points a DNS alias at the environment, re-checks its prefix's availability after SwapEnvironmentCNAMEs, configures a health check, or simply asserts that the environment got the prefix it asked for has only this string to work from. In this shape it is not a name, is not parseable, and the SDK refuses the follow-up API call derived from it, so every CNAME/DNS workflow breaks at its first step.
Fix: the environment CNAME the CreateEnvironment / UpdateEnvironment / SwapEnvironmentCNAMEs handlers record and the EnvironmentDescription serializer emits, plus the shared environment-address helper it is built from, must mint a dot-separated name whose first label is the request's CNAMEPrefix and whose second label is the region, on a domain the emulator itself answers on (keeping any port/path out of the published CNAME value and resolving them at the listener). Belongs in the elasticbeanstalk operation handlers and the service's environment state module.
Traces: elasticbeanstalk.deploy-environment-via-cloudformation-then-active-and-reachable (CNAME does not start with its prefix), elasticbeanstalk.e2e-swap-cname-then-verify-dns-and-traffic-consequence (prefix recovered from the CNAME is '127', SDK refuses CheckDNSAvailability).

Cause 2 of 2: the tail RetrieveEnvironmentInfo publishes contains only emulator-synthesized control-plane event lines — the running application's stdout and the on-instance log paths are absent.
AWS: Smithy: RequestEnvironmentInfo(EnvironmentName/EnvironmentId, InfoType required, enum EnvironmentInfoType values tail|bundle|analyze) -> Unit; RetrieveEnvironmentInfo(same input) -> RetrieveEnvironmentInfoResultMessage/EnvironmentInfoDescription{InfoType, Ec2InstanceId 'The Amazon EC2 Instance ID for this information', SampleTimestamp, Message 'The retrieved information. Currently contains a presigned Amazon S3 URL. The files are deleted after 15 minutes.'}; no modelled operation errors. Recorded behavior: InfoType='tail' returns the last 100 lines of the instance's own logs — a concatenation of the on-instance log files, each section introduced by a header naming its '/var/log/...' path — so a line the deployed application printed to its stdout (which the platform redirects into the instance's web/application log) appears verbatim in the fetched bytes.
Emulator: the request is accepted and the published URL is now fetchable (HTTP 200), but the body is a short synthesized control-plane transcript — two Elastic Beanstalk lifecycle event lines of the form '<timestamp> INFO createEnvironment is starting.' and '<timestamp> INFO Successfully launched environment: <env-name>' — totalling ~166 bytes. The line the application confirmed it wrote to its own stdout ('SIM2REAL-LOG-LINE <nonce>', echoed back 200 by the app over its published address in the same check) is nowhere in it, and no '/var/log/' section header appears at all. The timestamps, nonce, byte count and environment name are per-run values; the requirement is that the tail is the instance's real multi-file log tail, carrying the application process's stdout and naming the on-instance paths it concatenates.
Why: the tail is the only way a client can read what its application printed. A deploy pipeline that calls RequestEnvironmentInfo/RetrieveEnvironmentInfo to diagnose a failing deployment, grep for an application error, or confirm a startup line gets an event transcript it already has from DescribeEvents, and concludes its application logged nothing — the exact opposite of the truth. Clients that split the tail on its '/var/log/...' headers to separate web, application and eb-engine logs find no sections to split on.
Fix: the tail payload assembled behind RequestEnvironmentInfo / RetrieveEnvironmentInfo must be sourced from the environment instance's actual process output (the stdout/stderr of the deployed application version's process, plus the platform's own on-instance logs) with per-file '/var/log/...' section headers, instead of being rendered from the environment's event list. Belongs in the RequestEnvironmentInfo and RetrieveEnvironmentInfo handlers and the environment/instance log state they read, in the elasticbeanstalk service.
Traces: elasticbeanstalk.eb-retrieved-environment-info-carries-the-applications-own-log-line.
