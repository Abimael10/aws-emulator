# cloudformation: an UpdateStack that changes an AWS::SQS::Queue's VisibilityTimeout in place fails the Queue resource and rolls the stack back, so no stack-update behaviour layered on a successful queue update is reachable

> _Note: this issue was identified against the code base at commit `a3841edc9a1ab0db1665cc08dab76ccb227286ad`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Description
There is 1 net-new root cause in this issue (Cause 1 of 1); it must be closed before submitting. All three grounding checks are listed by the suite under the `cloudformation` heading and none of them is marked ALREADY FILED or OWNED by the replay report, so none of the already-open issues carries their replay keys.

Placement note: get_bootstrap_status() reports an EMPTY pending set, so no constituent service is un-bootstrapped and this is filed rather than deferred; the service token is the suite heading `cloudformation`.

Cause 1 of 1: an UpdateStack whose only change to an AWS::SQS::Queue is a mutable attribute (VisibilityTimeout) does not update the existing queue — the Queue resource row goes UPDATE_FAILED and the stack settles UPDATE_ROLLBACK_COMPLETE.
  Failing check ids for this cause: cloudformation.update-stack-replaces-a-renamed-queue-and-updates-visibility-in-place, cloudformation.termination-protection-enabled-after-update-blocks-delete-by-stack-id, cloudformation.deep-cloudformation-1-cfn-enforce-continue-update-rollback-requires-resource-skip.
  AWS: changing a mutable AWS::SQS::Queue property is an in-place update. The resource row reaches UPDATE_COMPLETE, the PhysicalResourceId (the queue URL) is unchanged, Ref/GetAtt keep resolving to the same queue, and the stack reaches UPDATE_COMPLETE; only create-only properties (QueueName, FifoQueue) classify Replacement. Smithy (sqs): the mutable surface is SetQueueAttributes(QueueUrl required, Attributes required) and TagQueue/UntagQueue(QueueUrl, Tags) — neither models any already-exists error (their modelled errors are InvalidAddress 404, InvalidAttributeName 400, InvalidAttributeValue 400, InvalidSecurity 403, OverLimit 403, QueueDoesNotExist 400 AWS.SimpleQueueService.NonExistentQueue, RequestThrottled 403, UnsupportedOperation 400). CreateQueue is the ONLY SQS operation that models QueueNameExists (httpError 400, awsQueryError code 'QueueAlreadyExists'), and AWS raises it only for a CreateQueue naming an existing queue with different attribute values — i.e. it can never be reached by a correct update path.
  Emulator: the update is refused at the resource. The stack leaves UPDATE_IN_PROGRESS through UPDATE_ROLLBACK_IN_PROGRESS to UPDATE_ROLLBACK_COMPLETE, the queue's resource row is UPDATE_FAILED, and the stack carries StackStatusReason exactly "The following resource(s) failed to update: [<LogicalId>]. " — fixed text 'The following resource(s) failed to update: [', then the failing logical ids, then ']. ' (the trailing space is AWS's); the logical id is from the template (observed 'Queue', and 'Q' in the ContinueUpdateRollback check). Observed verbatim in cloudformation__cloudtrail.obs-cloudformation-1-...: "stack <stack-arn> reached 'UPDATE_ROLLBACK_COMPLETE' instead of 'UPDATE_COMPLETE': 'The following resource(s) failed to update: [Queue]. '". Per check: update-stack-replaces-a-renamed-queue-and-updates-visibility-in-place changes VisibilityTimeout 31 -> 97 on a named queue and gets 'update ended UPDATE_ROLLBACK_COMPLETE, expected UPDATE_COMPLETE'; termination-protection-enabled-after-update-blocks-delete-by-stack-id changes 30 -> 75 and never reaches UPDATE_COMPLETE; deep-cloudformation-1-cfn-enforce-continue-update-rollback-requires-resource-skip changes 30 -> 60 (while adding a never-signalled WaitCondition) and its event stream is [('Q','UPDATE_IN_PROGRESS'), ('Q','UPDATE_FAILED'), stack UPDATE_ROLLBACK_* ] where ('Q','UPDATE_COMPLETE') is required. Open issue 20261123T065749Z-cloudformation-sqs-reopens-aws-sqs-queue-still-has-no-in.md records the handler message behind this rollback for its own (cloudformation__sqs...) checks — 'Resource handler returned message: "A queue already exists with the same name and a different value for attribute VisibilityTimeout" (RequestToken: <id>, HandlerErrorCode: InvalidRequest)' — i.e. the UPDATE is executed as a CreateQueue of the same name; that issue does NOT list any of the three check ids above, so it will not re-replay them.
  Why: no infrastructure-as-code flow can evolve a queue: a client that raises a visibility timeout gets a terminal stack failure for a change AWS applies in place. Worse, every behaviour that is only observable ON TOP of one successful queue update becomes unreachable and reads as a second, phantom defect: the rename-replacement contract (a QueueName change must replace the queue, the old one must be deleted) is never exercised; termination protection switched on after an update cannot be tested, so DeleteStack-by-StackId refusal on a protected stack is unverified; and the UPDATE_ROLLBACK_FAILED / ContinueUpdateRollback(ResourcesToSkip=['Q']) recovery path is never entered, because the stack rolls back cleanly before the denial that is meant to wedge it is installed.
  Fix: the AWS::SQS::Queue resource provider's UPDATE hook in the CloudFormation service — it must diff previous vs desired properties, apply the mutable ones against the EXISTING queue URL with SQS SetQueueAttributes (plus TagQueue/UntagQueue for tags), keep the physical id, and never re-issue CreateQueue for a queue the stack already owns; replacement classification must be limited to the create-only properties.
  Traces: cloudformation.update-stack-replaces-a-renamed-queue-and-updates-visibility-in-place, cloudformation.termination-protection-enabled-after-update-blocks-delete-by-stack-id, cloudformation.deep-cloudformation-1-cfn-enforce-continue-update-rollback-requires-resource-skip.
