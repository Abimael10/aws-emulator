# rds: 3 net-new behavioral causes — the custom DB-cluster-endpoint lifecycle, the DB-snapshot / DB-cluster-snapshot copy round trip, and the postgres snapshot-restore data read all fail to converge (every one of the four checks is killed at the per-check budget with no observation)

> _Note: this issue was identified against the code base at commit `9d0591483a26da063c45639c4a10cbe50c5f123c`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
CopyDBSnapshot

## Description
Three net-new root causes on the rds surface, found by replaying the behavioral suite (simparity-behavioral-aws-v1) against the emulator built from this checkout. Each is independent and must be closed on its own. All three present the same way in the replay output — the check spends its whole per-check budget without the state it waits for ever becoming observable, so the suite reports only 'Check timed out after 60.0s' — but they sit in three different parts of the service and each has to be fixed separately. None of the four checks below was reported ALREADY FILED or OWNED by an open issue.

Cause 1 of 3: the custom DB-cluster-endpoint lifecycle never walks its status progression, so a caller waiting on a custom endpoint never proceeds.
AWS: CreateDBClusterEndpoint stores a custom endpoint that reports Status 'creating' and then 'available'; ModifyDBClusterEndpoint (Smithy: ModifyDBClusterEndpoint, required DBClusterEndpointIdentifier, optional EndpointType/StaticMembers/ExcludedMembers, output DBClusterEndpoint carrying Status, EndpointType, CustomEndpointType, Endpoint, DBClusterEndpointArn; errors DBClusterEndpointNotFoundFault 400, InvalidDBClusterEndpointStateFault 400) moves it to 'modifying' and back to 'available' with CustomEndpointType switched to the requested type; DeleteDBClusterEndpoint moves it to 'deleting', after which DescribeDBClusterEndpoints for that identifier is refused DBClusterEndpointNotFoundFault. DBClusterEndpoint$Status publishes exactly that value list ('creating, available, deleting, inactive, modifying'). Every step of the progression must be reachable by polling DescribeDBClusterEndpoints.
Emulator: starting from an Aurora (aurora-mysql) cluster that itself has to reach 'available' first, the create → available → modify(EndpointType=ANY) → available → delete → not-found walk never completes inside the check's budget; the replay carries no refusal, no wrong field and no status value, only the budget expiring. The emulator's own state does model the progression (services/service-com-amazonaws-rds-amazonrdsv19/src/state/cluster_endpoints.rs declares creating/available/modifying/deleting and src/state.rs settle_due_transitions walks db_cluster_endpoints), so what diverges is that the walk is not observable end to end in the time AWS's own clients allow for an emulated service.
Why: every client that creates a custom reader endpoint — CDK and CloudFormation deploys, connection-string handoffs, any script that waits for Status=='available' before dialing — blocks forever instead of getting a usable endpoint, and the delete half never confirms the endpoint is gone.
Fix: the custom-cluster-endpoint state machine — the CreateDBClusterEndpoint / ModifyDBClusterEndpoint / DeleteDBClusterEndpoint handlers and the stored endpoint's pending-status transitions in state/cluster_endpoints.rs — together with the cluster-availability path the endpoint hangs off, so each step is reported promptly on the next describe. NOTE: open issue 20261117T083457Z-rds-6-net-new-behavioral-causes-custom-db.md describes this same non-convergence as its cause 3, but it carries a DIFFERENT replay key for this check (_wait_endpoint_gone#21) and the replay therefore did not treat this failure as owned; the two should be closed together and this check re-replayed when that fix lands.
Traces: rds.cluster-endpoint-lifecycle.

Cause 2 of 3: the snapshot COPY round trip never converges — neither a copied DB snapshot nor a copied DB cluster snapshot is observed reaching 'available', and the source-deleted/copy-survives half is never reached.
AWS: CopyDBSnapshot (Smithy: required SourceDBSnapshotIdentifier + TargetDBSnapshotIdentifier, output DBSnapshot; errors DBSnapshotAlreadyExistsFault 400, DBSnapshotNotFoundFault 404, InvalidDBSnapshotStateFault 400, KMSKeyNotAccessibleFault 400, SnapshotQuotaExceededFault 400, CustomAvailabilityZoneNotFoundFault 404) and CopyDBClusterSnapshot (Smithy: required SourceDBClusterSnapshotIdentifier + TargetDBClusterSnapshotIdentifier, output DBClusterSnapshot; errors DBClusterSnapshotAlreadyExistsFault 400, DBClusterSnapshotNotFoundFault 404, InvalidDBClusterSnapshotStateFault 400, InvalidDBClusterStateFault 400, KMSKeyNotAccessibleFault 400, SnapshotQuotaExceededFault 400) both answer with the copy in 'copying' and the copy then becomes 'available' on its own; the documentation for the copy's source states it 'must be in the available state'. The copy is an INDEPENDENT resource: DescribeDBSnapshots / DescribeDBClusterSnapshots report it under its own identifier and ARN with the source's Engine, and deleting the SOURCE leaves the copy 'available'.
Emulator: the full round trip — create cluster/instance, wait available, CreateDB(Cluster)Snapshot, wait available, Copy, wait the copy available, delete the source, confirm the copy still available — never gets as far as reading the copy back; both checks end at the per-check budget with no verdict, so neither the copy's status nor its identifier/ARN/Engine independence nor the source-deletion step is ever observed. The handlers do write the copy as 'copying' with a pending transition to 'available' (src/ops/copy_db_snapshot.rs and src/ops/copy_db_cluster_snapshot.rs), so the defect is in the chain of transitions a copy depends on (the instance/cluster reaching available, the source snapshot reaching available, the copy settling) not being observable in sequence. Hypothesis: each stage of that chain stays transient past the first poll a client makes, so the stages cost a client a full poll interval each and the round trip cannot finish.
Why: a client that copies a snapshot — cross-account/cross-region backup copies, pre-upgrade safety copies, retention jobs — never sees the copy become restorable and cannot safely delete the source, because the only signal AWS gives that the copy holds the data is the copy's Status going 'copying' → 'available'.
Fix: the snapshot and cluster-snapshot status progression in the RDS crate's state (PendingStatus/settle_due_transitions in src/state.rs and the snapshot records it settles) plus the create/copy handlers that queue those transitions, so a copy and the resources it hangs off report their terminal status to the next describe rather than only after a long wait.
Traces: rds.copy-db-snapshot-round-trip, rds.copy-db-cluster-snapshot-round-trip.

Cause 3 of 3: a postgres snapshot restore is never readable over SQL — the snapshot-as-point-in-time-image contract is unobservable.
AWS: RestoreDBInstanceFromDBSnapshot (Smithy: required DBInstanceIdentifier, DBSnapshotIdentifier, output DBInstance; errors include DBSnapshotNotFoundFault 404, InvalidDBSnapshotStateFault 400, InvalidRestoreFault 400) creates a new DB instance whose database holds exactly what was committed before the snapshot was taken and nothing written after it. The restored instance reaches DBInstanceStatus 'available' and publishes an Endpoint (Address + an integer Port in 1..65535) a client connects to with the master credentials of the source, and a SELECT over that session returns the pre-snapshot rows and not the post-snapshot row.
Emulator: the check creates a postgres instance, waits for 'available', seeds rows, snapshots, writes one more row, restores and tries to read the restored database over a native PostgreSQL session — and ends at the per-check budget with no observation; nothing about the restored rows, the published port or the restored endpoint is ever asserted. Recorded behavior only: the replay output is 'Check timed out after 60.0s'.
Why: restore-and-verify is the whole point of a snapshot; a client that restores to recover data gets no readable database, so a backup/restore runbook cannot be validated at all against this emulator.
Fix: the RestoreDBInstanceFromDBSnapshot handler and the data-plane engine endpoint it stands up for the restored instance — the restored instance must reach 'available' and serve the snapshot's contents at the Endpoint it publishes. NOTE: open issues 20261118T181500Z-rds-the-published-endpoint-of-a-served-engine-is-the-core-listeners.md and 20261121T105515Z-rds-5-net-new-behavioral-causes-aurora-cluster.md report unserved published endpoint hosts for other checks and may share the data-plane half of this cause; neither carries this check's replay key, so this check must be re-replayed on its own.
Traces: rds.snapshot-restore-data-query-round-trip.

## Evidence
Behavioral suite replayed against the emulator built from this checkout: 476/709 checks passed (67.1%), 199 mismatched, 34 errored. Per-service: rds 293/411 (71%), 118 failed. Every failure below was reported neither ALREADY FILED (blocked by an unimplemented scaffold stub) nor OWNED by an open issue.

Cause 1 — rds.cluster-endpoint-lifecycle [mismatch]: 'Error: Check timed out after 60.0s'. The check creates a DB subnet group, CreateDBCluster(Engine=aurora-mysql) and waits for Status=='available', then CreateDBClusterEndpoint(EndpointType='READER'), waits for the endpoint Status=='available' and asserts CustomEndpointType=='READER', then ModifyDBClusterEndpoint(EndpointType='ANY'), waits for 'available' again and asserts CustomEndpointType=='ANY', then DeleteDBClusterEndpoint and waits for DescribeDBClusterEndpoints to answer DBClusterEndpointNotFoundFault. No assertion was ever reached: the budget expired first, so no status value, no refusal and no field divergence is recorded — the progression itself is what is missing.

Cause 2 — rds.copy-db-snapshot-round-trip [mismatch]: 'Error: Check timed out after 60.0s'. Sequence: CreateDBSubnetGroup; CreateDBInstance(Engine=mysql, DBInstanceClass=db.t3.micro, AllocatedStorage=20, BackupRetentionPeriod=1); poll DescribeDBInstances for DBInstanceStatus=='available'; CreateDBSnapshot; poll DescribeDBSnapshots for Status=='available'; CopyDBSnapshot(Source=<src>, Target=<copy>); poll DescribeDBSnapshots for the copy's Status=='available'; then DeleteDBSnapshot(source) and assert the copy is still 'available'. The run ends in the poll chain with no verdict.
Cause 2 — rds.copy-db-cluster-snapshot-round-trip [mismatch]: 'Error: Check timed out after 60.0s'. Same shape for Aurora: CreateDBCluster(Engine=aurora-mysql, StorageEncrypted=True, BackupRetentionPeriod=1) + a cluster member instance; poll DescribeDBClusters for Status=='available'; CreateDBClusterSnapshot; poll for Status=='available'; CopyDBClusterSnapshot; poll the copy for Status=='available'; then assert copy identifier != source identifier, copy DBClusterSnapshotArn != source ARN, both Engine=='aurora-mysql', delete the source, and assert the copy remains 'available'. None of those assertions is reached.
Expected per AWS: the copy is answered in 'copying' and becomes 'available' without further calls, is reported by Describe* under its own identifier/ARN with the source's Engine, and survives deletion of the source.

Cause 3 — rds.snapshot-restore-data-query-round-trip [mismatch]: 'Error: Check timed out after 60.0s'. Sequence: open a security group for 5432; CreateDBInstance(Engine=postgres, DBName=<db>, MasterUsername/MasterUserPassword, BackupRetentionPeriod=0, PubliclyAccessible=False, VpcSecurityGroupIds=[sg]); wait DBInstanceStatus=='available'; assert the published Endpoint.Port is an integer in 1..65535; seed rows over a native PostgreSQL session; CreateDBSnapshot; write one more row; RestoreDBInstanceFromDBSnapshot; read the restored database and assert it holds exactly the pre-snapshot rows. The budget expires before any of that is observed.

Note on per-run values: the identifiers, ports, hosts and the 60 s budget above are this environment's; the requirement is the status progressions and the restored contents, not any literal value from one run.

## Steps to Reproduce
1. Build and boot the emulator from this checkout.
2. Replay the behavioral suite (simparity-behavioral-aws-v1), service rds.
3. Cause 1: run rds.cluster-endpoint-lifecycle — create an aurora-mysql cluster in a DB subnet group, wait for 'available', CreateDBClusterEndpoint(EndpointType='READER'), poll DescribeDBClusterEndpoints for Status=='available' (CustomEndpointType must be 'READER'), ModifyDBClusterEndpoint(EndpointType='ANY') and poll back to 'available' (CustomEndpointType must be 'ANY'), DeleteDBClusterEndpoint and poll until DescribeDBClusterEndpoints answers DBClusterEndpointNotFoundFault. Observe that the walk does not complete and the check is killed at the per-check budget.
4. Cause 2: run rds.copy-db-snapshot-round-trip — CreateDBInstance(mysql) → available, CreateDBSnapshot → available, CopyDBSnapshot to a new identifier, poll the copy to 'available', DeleteDBSnapshot on the source, re-describe the copy. Then run rds.copy-db-cluster-snapshot-round-trip for the Aurora cluster equivalent. Both end in the status polls with no verdict.
5. Cause 3: run rds.snapshot-restore-data-query-round-trip — CreateDBInstance(postgres) → available, seed rows over the published endpoint, CreateDBSnapshot, insert one more row, RestoreDBInstanceFromDBSnapshot, then connect to the restored instance and SELECT: the restored rows are never read before the budget ends.
