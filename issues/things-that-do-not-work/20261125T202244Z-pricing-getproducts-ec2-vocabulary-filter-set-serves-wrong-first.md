# GetProducts EC2 vocabulary filter set serves wrong first offer document and wrong NextToken

> _Note: this issue was identified against the code base at commit `e0dd7a4e9d8aa683c383dd9c3df969fda9922d23`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Description
ONE cause, on service `pricing`, operation GetProducts. This cluster carries NO stub_path and NO owned_by in this replay, so it is reported unowned and is filed here.

Cause 1 of 1: GetProducts over the EC2 attribute-vocabulary TERM_MATCH filter set answers 200 but both the first PriceList entry and the continuation token diverge, so the filtered price query identifies a different product at a different price and then pages a different remaining population.

AWS: Smithy (services/service-com-amazonaws-pricing-awspricelistservice/smithy-model/com-amazonaws-pricing-awspricelistservice.json) — GetProducts input {ServiceCode required, Filters @length 0..50, FormatVersion @length 1..32, NextToken, MaxResults @range 1..100}; output {FormatVersion @length 1..32, PriceList (PriceListJsonItems), NextToken}; @paginated{inputToken NextToken, outputToken NextToken, items PriceList, pageSize MaxResults}; modelled errors InvalidParameterException / NotFoundException / InvalidNextTokenException / ExpiredNextTokenException (httpError 400), AccessDeniedException (401), ThrottlingException (429), InternalErrorException (500, retryable). The model does not describe the CONTENT of a PriceList item, so for the document itself this is recorded behavior only. Status for this step is 200 with no error code and no error message; the requirement is the BODY. The recording's first PriceList entry is the published aws_v1 offer document for the matched EC2 offer: product.productFamily "Compute Instance", product.sku the catalog's published SKU for that offer, product.attributes the FULL published EC2 attribute set for the offer (instanceType, instanceFamily, instanceFamilyCategory, operatingSystem, tenancy, capacitystatus, licenseModel, preInstalledSw, operation, usagetype, marketoption, memory, vcpu, storage, normalizationSizeFactor, clockSpeed, ecu, physicalProcessor, processorArchitecture, processorFeatures, networkPerformance, dedicatedEbsThroughput, dedicatedEbsThroughputDescription, enhancedNetworkingSupported, intelAvxAvailable, intelAvx2Available, intelTurboAvailable, classicnetworkingsupport, vpcnetworkingsupport, gpuMemory, availabilityzone, regionCode, location, locationType, servicecode, servicename), serviceCode "AmazonEC2", and terms carrying BOTH an OnDemand block whose usage dimension is worded "$<rate> per On Demand <operatingSystem> <instanceType> Instance Hour" with unit "Hrs", beginRange "0", endRange "Inf", and a Reserved block whose usage dimension is worded "<platform>, <instanceType> reserved instance applied". The fixed text of those dimension descriptions is the template above; <rate>, <operatingSystem>, <instanceType> and <platform> are values taken from the product and its published rate, and the SKU, rate codes, offer term codes, effectiveDate and the specific instance size in the recording are that run's catalog values filling the template, not requirements. The same response's NextToken must continue THAT filtered set.

Emulator: the step also answers 200, but the replay reports `$.PriceList[0]: value_mismatch` and the divergence key names NextToken as diverging too — divergence_key "service=pricing|GetProducts|status=200->200|keys=$.NextToken,$.PriceList[0]". The emulator serves an offer document derived from its seeded product drafts rather than a published catalog document, so its product.sku and term/rate codes are derived identifiers, its product.attributes contain only the keys the seed carries, and its OnDemand/Reserved terms are formulaic. Its filtered selection also orders a different product first, and the continuation token it emits does not describe the same remaining population for the filter set.

Why: a client prices a workload off PriceList[0] and then walks the rest of the filtered set with NextToken. A different first document means a different price and a different product identity for the same filter set, and a token describing a different remainder means the rest of the walk covers different products — so a cost estimate assembled by paging GetProducts is wrong both in the figure it reports and in the inventory it covers, and a client keying a cache, a quote or an order off product.sku keys it off an identifier AWS never published. Because the status is 200 and the shape is valid, nothing signals the figures are not AWS's.

Fix: the pricing service's GetProducts handler — its filter matching, result ordering and NextToken encoding/decoding — together with the service's catalog state and offer-document/terms builders, which must publish the catalog's published offer documents (full attribute set, published per-term dimensions) instead of documents rendered from seeded drafts.
