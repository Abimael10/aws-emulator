# docdb: 3 net-new causes — DescribeDBEngineVersions serves none of the recorded engine versions, DescribeOrderableDBInstanceOptions omits the db.r6gd instance family, and DescribeDBInstances publishes the emulator's internal socket port as Endpoint.Port

> _Note: this issue was identified against the code base at commit `48ea639b2644fe3267d5fb5c94b4b1fdebe2ae92`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
DescribeDBEngineVersions, DescribeOrderableDBInstanceOptions, DescribeDBInstances

## Description
Three net-new wire divergences in the DocumentDB (docdb) control plane, all in the reference/endpoint data a client reads BEFORE it can provision or connect: two published catalogs that do not match the catalogs AWS serves, and an instance endpoint whose port is the emulator's internal socket port instead of the port the engine is documented to listen on. All three must be closed before this issue is submitted.

=== Cause 1 of 3: DescribeDBEngineVersions returns no entry that matches AWS's published engine-version catalog (fixture docdb-catalog-describe-db-engine-versions, step task#1) ===

AWS: Smithy (com.amazonaws.docdb#AmazonRDSv19) DescribeDBEngineVersions -> DBEngineVersionMessage{Marker, DBEngineVersions: DBEngineVersionList}, serialized by the awsQuery protocol at DescribeDBEngineVersionsResponse/DescribeDBEngineVersionsResult/DBEngineVersions/DBEngineVersion[i]. The operation is documented "Returns a list of the available engines" and the shape DBEngineVersion is "Detailed information about an engine version", with Engine, EngineVersion, MajorEngineVersion, MinorEngineVersion, DBParameterGroupFamily, DBEngineVersionDescription, SupportedCACertificateIdentifiers, SupportsCertificateRotationWithoutRestart, the Supports* capability flags and ValidUpgradeTarget. The recorded AWS response for an unfiltered DescribeDBEngineVersions(Engine=docdb) carries EIGHT DBEngineVersion entries; the first is the complete record for the 3.6 line — Engine=docdb, EngineVersion=3.6.0, MajorEngineVersion=3.6, MinorEngineVersion=0, DBParameterGroupFamily=docdb3.6, DBEngineVersionDescription='Amazon DocumentDB (with MongoDB compatibility)', SupportedCACertificateIdentifiers=[rds-ca-rsa4096-g1, rds-ca-rsa2048-g1], SupportsCertificateRotationWithoutRestart=true, SupportsBabelfish/SupportsRDSProxy/SupportsGlobalDatabases/SupportsParallelQuery/SupportsDataGroups/SupportsReadReplica/SupportsCluster/SupportsLimitlessDatabase=false, and ValidUpgradeTarget naming the 5.0.x and 8.0.x releases as major upgrade targets (Description='Amazon DocumentDB (with MongoDB compatibility)', AutoUpgrade=false, IsMajorVersionUpgrade=true). Status 200, no error.

Emulator: status is 200, but replay reports EVERY index of the served list — DBEngineVersion[0] through DBEngineVersion[7] — as divergent, and the first as `missing`: the response presents no entry at the recorded path for any of AWS's eight published versions. This is not a gap in the underlying table (services/common/src/docdb_engine_catalog.rs:141-150 does list 3.6.0 through 8.0.1), so the defect is in the DescribeDBEngineVersions response path: the selection/pagination in the handler drops the catalog for this request, or the list is serialized somewhere other than DBEngineVersions/DBEngineVersion. A fixer must diff one served entry against the recorded one element by element; the requirement is that an unfiltered call publishes one DBEngineVersion per release AWS publishes, oldest first, each with the members above derived from that release (version, major/minor components, docdb<major>.<minor> parameter-group family, the engine's own description, the shared CA identifier list, and the upgrade targets of its line).

Why: every provisioning client that validates an EngineVersion before CreateDBCluster, or enumerates upgrade targets to plan an in-place upgrade (CDK/CloudFormation, the console flow, `aws docdb describe-db-engine-versions`), reads this list. An empty-or-unmatched catalog makes every version look unavailable and every upgrade path invisible, so a correct create is refused by client-side validation and no upgrade can be planned.

Fix: the DescribeDBEngineVersions handler and its serializer — services/service-com-amazonaws-docdb-amazonrdsv19/src/ops/describe_db_engine_versions.rs (the filter/DefaultOnly/paginate_catalog path at lines 184-239) and the projection crate::state::engine_version_to_shape it calls.

=== Cause 2 of 3: DescribeOrderableDBInstanceOptions omits the db.r6gd instance family, so the published option list diverges from index 30 onward (fixture docdb-catalog-describe-orderable-db-instance-options, step task#1) ===

AWS: Smithy DescribeOrderableDBInstanceOptions -> OrderableDBInstanceOptionsMessage{OrderableDBInstanceOptions, Marker}; OrderableDBInstanceOption is "The options that are available for an instance" with DBInstanceClass "The instance class for an instance", Engine, EngineVersion, LicenseModel, AvailabilityZones, Vpc, StorageType and the Supports*/Capable capability flags. The recorded AWS response for Engine=docdb publishes the NVMe-backed memory-optimised family db.r6gd alongside t3/t4g/r5/r6g/r7g: index 30 of the recorded list is Engine=docdb, EngineVersion=5.0.0, DBInstanceClass=db.r6gd.12xlarge, LicenseModel=na, StorageType=standard, Vpc=true, SupportsClusters=true, SupportsGlobalDatabases=true, SupportsStorageEncryption=true, SupportsPerformanceInsights=true, SupportedEngineModes=[provisioned], SupportedNetworkTypes=[IPV4, DUAL], and the remaining flags false. Status 200, no error.

Emulator: status 200, but the served list carries db.r7g.12xlarge at the index where AWS carries db.r6gd.12xlarge, and replay reports indexes 30 through 65 — 36 consecutive options — as divergent. The cause is the shared family table: services/common/src/docdb_engine_catalog.rs:476-482 publishes only (t3, t4g, r5, r6g, r7g), so the whole db.r6gd family is absent and the generated cross-product (version x class x storage type) is both short by that family and shifted out of AWS's ordering from the first r6gd option onward. The requirement is that the option list offers every DBInstanceClass AWS offers for this engine, in AWS's published order, each crossed with the engine versions and storage types it is orderable with.

Why: a client that enumerates orderable options to pick a valid class before CreateDBInstance (the console flow, CDK's instance-class validation, any capacity planner) never sees the r6gd classes, so ordering a db.r6gd.* instance looks impossible; and because the list is also mis-ordered from that point, any client that pages or indexes into it reads option metadata for the wrong instance class.

Fix: the shared DocumentDB instance-family catalog (INSTANCE_FAMILIES in services/common/src/docdb_engine_catalog.rs, read by crate::state::instance_classes) that services/service-com-amazonaws-docdb-amazonrdsv19/src/ops/describe_orderable_db_instance_options.rs projects.

=== Cause 3 of 3: DescribeDBInstances reports the emulator's internal socket port as DBInstance.Endpoint.Port instead of the port the engine listens on (fixture docdb-cluster-and-instance-endpoint-discovery, step task#9) ===

AWS: Smithy models DBInstance.Endpoint as Endpoint — "Network information for accessing a cluster or instance. Client programs must specify a valid endpoint to access these Amazon DocumentDB resources." — whose Port member is documented "Specifies the port that the database engine is listening on." For DocumentDB that is the PORT THE CLUSTER WAS CREATED WITH, 27017 when CreateDBCluster$Port is absent (the engine's default port; the emulator itself records this as DEFAULT_PORT = 27017, services/service-com-amazonaws-docdb-amazonrdsv19/src/state.rs:69-71). The recorded response reports Endpoint.Port = 27017, the same value DescribeDBClusters reports for the owning cluster's Port. Status 200, no error.

Emulator: status 200, but DBInstance.Endpoint.Port is the core-assigned socket port of the emulator's own listener (replay: expected '27017', got '45751' — the number itself is a per-run allocation; the defect is that an internal socket port is reported at all). crate::state::DBInstanceRecord::endpoint_port (state.rs:654-664) returns served.port whenever the instance has a served endpoint and only falls back to the cluster's Port otherwise, and that value is projected into Endpoint.Port at state.rs:1819-1823. The result also contradicts the same emulator's own cluster record: DescribeDBClusters reports the cluster Port 27017 while DescribeDBInstances reports a different port for that cluster's member, so the two reports disagree about one fact.

Why: a client builds its MongoDB connection string from the cluster's Port and the instance Endpoint, and DocumentDB tooling pins 27017; an instance that advertises an arbitrary high port makes the advertised endpoint disagree with the cluster's configured Port, breaks security-group/driver configuration derived from it, and makes the reported port unusable as a stable value across runs.

Relation to already-filed issues (neither carries this failure's replay key, so this failure is not covered by them): open issue 20261115T142542Z-docdb-dbinstance-endpoint-address-is-published-as-a.md is about Endpoint.ADDRESS being an unreachable *.docdb.amazonaws.com name and asks for an emulator-served host; open issue 20261112T142502Z-docdb-cluster-endpoint-and-reader-endpoint-are-published.md covers DBCluster.Endpoint/ReaderEndpoint (and already owns the two endpoint clusters this replay reported). Neither covers the instance Endpoint.Port value. Serving the data plane on a host the emulator owns does not license publishing an internal port: the advertised port must stay the cluster's configured Port (27017 by default), with the listener bound to or mapped onto that port.

Fix: crate::state::DBInstanceRecord::endpoint_port and the DBInstance Endpoint projection in services/service-com-amazonaws-docdb-amazonrdsv19/src/state.rs, which the DescribeDBInstances/CreateDBInstance handlers serialize.

Traces: docdb-catalog-describe-db-engine-versions#task#1 (cause 1); docdb-catalog-describe-orderable-db-instance-options#task#1 (cause 2); docdb-cluster-and-instance-endpoint-discovery#task#9 (cause 3).
