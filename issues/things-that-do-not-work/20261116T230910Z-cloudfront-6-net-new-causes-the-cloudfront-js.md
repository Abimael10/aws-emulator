# cloudfront: 6 net-new causes — the cloudfront-js-2.0 runtime rejects ES-module function code, edge cache entries never expire, a CFN AutoPublish toggle answers InvalidAction, CachePolicy handler reasons drop AWS's envelope, CachePolicy drift is never detected, and the KVS data-plane host is unserved

## Description
Six distinct root causes in the CloudFront surface, all grounded in failing behavioral checks the suite reports under `### cloudfront` and none of them marked ALREADY FILED or OWNED. Each must be closed before submitting.

=== Cause 1 of 6: the cloudfront-js-2.0 function runtime cannot parse ES-module code and provides no built-in `cloudfront` module ===
Failing checks: cloudfront.deploy-cloudfront-2-function-kvs-rename-replaces-code-update-in-place, cloudfront.deploy-cloudfront-2-function-second-kvs-association-rejected
AWS: Smithy — FunctionConfig.Runtime is the enum FunctionRuntime with values `cloudfront-js-1.0` and `cloudfront-js-2.0`, and FunctionConfig.KeyValueStoreAssociations carries the function's KeyValueStoreAssociation (KeyValueStoreARN, pattern ^arn:aws:cloudfront::[0-9]{12}:key-value-store\/[0-9a-fA-F-]{36}$). The cloudfront-js-2.0 runtime runs the function code as an ES module and exposes the built-in `cloudfront` module, so code of the form `import cf from 'cloudfront'; const kvs = cf.kvs(); async function handler(event) {...}` loads, and `cf.kvs()` binds to the function's single KeyValueStoreAssociation (the store ARN never appears in the code). TestFunction then answers 200 with TestResult.FunctionOutput set and TestResult.FunctionErrorMessage absent — Smithy documents FunctionErrorMessage as "If the result of testing the function was an error, this field contains the error message."
Emulator: for exactly that code at both the DEVELOPMENT and the published stage, TestFunction returns a TestResult whose FunctionErrorMessage is the parse error `Unexpected identifier 'cf'` with FunctionExecutionLogs empty — i.e. the code is evaluated as a classic script with no module loader and no `cloudfront` module registered, so the `import` statement never parses and the handler is never entered.
Why: every cloudfront-js-2.0 function that reads a key value store is dead. A client cannot test, publish or run any KVS-backed edge function, and the KeyValueStoreAssociations feature is unobservable even though the control plane accepts the association.
Fix: the CloudFront Functions evaluator used by TestFunction (and by the edge invocation path) in the cloudfront service's function-execution component — it must parse cloudfront-js-2.0 code as an ES module and provide the built-in `cloudfront` module whose `kvs()` resolves the function's single KeyValueStoreAssociation. Not the control-plane CreateFunction/UpdateFunction handlers, which accepted the code and the association. Related open issue 20261112T142015Z-cloudfront-5-net-new-cloudfront-functions-causes-testresult-drops.md reports other TestFunction/TestResult divergences; it does not carry either of these checks' keys, and neither does 20261112T130455Z-cloudfront-testfunction-result-and-failure-reporting-diverge-from.md.

=== Cause 2 of 6: an edge cache entry never expires, so the distribution serves a stale object forever ===
Failing check: cloudfront.deploy-cache-policy-cfn-ttl-enforced
AWS: Smithy — CachePolicyConfig.MinTTL is "The minimum amount of time, in seconds, that you want objects to stay in the CloudFront cache before CloudFront sends another request to the origin to see if the object has been updated", MaxTTL/DefaultTTL bound the TTL CloudFront derives from the origin's Cache-Control/Expires. With a cache policy whose MinTTL is above the origin's own max-age, the edge must hold the cached bytes for at least MinTTL and then, once that floor has elapsed and the origin's max-age is expired, go back to the origin and serve the updated object.
Emulator: the MinTTL floor is honoured (immediately after the origin object is replaced, the edge correctly still serves the old bytes with 200), but the entry never becomes stale: for MinTTL + 90 s of repeated GETs at 3 s intervals the edge keeps answering 200 with the pre-update body and never serves the updated object.
Why: any content update behind a distribution is permanently invisible — a client that relies on TTL-based expiry (the default content-freshness mechanism) can only ever refresh by creating an invalidation.
Fix: TTL/expiry and origin revalidation in the CloudFront edge cache (the data-plane cache state must compute an expiry from the attached cache policy's MinTTL/MaxTTL/DefaultTTL plus the origin's Cache-Control and re-fetch once it passes). The cache-policy control plane is correct here: GetCachePolicyConfig read back MinTTL/DefaultTTL/MaxTTL as declared and the distribution's DefaultCacheBehavior.CachePolicyId referenced it.

=== Cause 3 of 6: a CloudFormation update that toggles AWS::CloudFront::Function AutoPublish fails with the message "InvalidAction" and rolls the stack back ===
Failing check: cloudfront.deploy-cloudfront-2-function-autopublish-toggle-publishes-live
AWS: a stack-deployed AWS::CloudFront::Function with AutoPublish false exists only at the DEVELOPMENT stage; updating the same template with AutoPublish true publishes the existing function in place — same physical resource id and same FunctionARN, Fn::GetAtt "Stage" becomes LIVE, DescribeFunction(Stage=LIVE) reports Status UNASSOCIATED, and the stack reaches UPDATE_COMPLETE. Smithy: the publish path is PublishFunction, whose modeled errors are InvalidArgument, InvalidIfMatchVersion, NoSuchFunctionExists, PreconditionFailed and UnsupportedOperation — there is no `InvalidAction` error in the CloudFront model for this path, so no correct run can produce that message.
Emulator: the update leaves the resource UPDATE_FAILED and the stack UPDATE_ROLLBACK_COMPLETE, with the resource status reason `Resource handler returned message: "InvalidAction" (RequestToken: <uuid>, HandlerErrorCode: InvalidRequest)`. In that reason `Resource handler returned message: "`, `" (RequestToken: `, `, HandlerErrorCode: `, `)` are the fixed CloudFormation envelope and the uuid is a per-run value; the defect is the message payload `InvalidAction`, which names an action the emulator's CloudFront router did not recognise.
Why: AutoPublish cannot be flipped by a stack update at all. The function stays unpublished, no LIVE stage ever appears, and the stack rolls back instead of converging — the documented way to promote a CFN-managed edge function is unusable.
Fix: the CloudFormation AWS::CloudFront::Function update handler's publish path and the CloudFront operation it dispatches to (PublishFunction / UpdateFunction routing) — one of the two is issuing or dispatching an action the service does not route, and the resulting error is surfaced as `InvalidAction`.

=== Cause 4 of 6: an AWS::CloudFront::CachePolicy UPDATE_FAILED reason drops AWS's "Invalid request provided: <ResourceType>: " prefix and SDK error envelope ===
Failing check: cloudfront.deploy-cloudfront-1-cache-policy-invalid-ttl-order-update-rejected-rolls-back
AWS: when a stack update sets a CachePolicyConfig that violates MinTTL <= DefaultTTL <= MaxTTL, CloudFront refuses the UpdateCachePolicy call with InvalidArgument (Smithy: UpdateCachePolicy declares InvalidArgument, client, httpError 400) and CloudFormation records the resource's UPDATE_FAILED reason as `Resource handler returned message: "<relayed SDK error>" (RequestToken: <uuid>, HandlerErrorCode: InvalidRequest)`, where the relayed SDK error is the fixed text `Invalid request provided: ` + the resource type (`AWS::CloudFront::CachePolicy`) + `: ` + the service's own message (recorded behavior only: `MinTTL, MaxTTL and DefaultTTL should follow order MinTTL less than or equal to DefaultTTL less than or equal to MaxTTL`) + the fixed envelope ` (Service: CloudFront, Status Code: 400, Request ID: <request id>) (SDK Attempt Count: <n>)`. Fixed text: `Invalid request provided: `, `: `, `(Service: CloudFront, Status Code: 400, Request ID: `, `) (SDK Attempt Count: `, `)`. Variable: the resource type from the template, the service message from the refusing operation, and the per-run request id / attempt count (present, never compared literally).
Emulator: the reason carries only the bare CloudFront message — `Resource handler returned message: "MinTTL, MaxTTL and DefaultTTL should follow order MinTTL less than or equal to DefaultTTL less than or equal to MaxTTL" (RequestToken: <uuid>, HandlerErrorCode: InvalidRequest)` — with no `Invalid request provided: AWS::CloudFront::CachePolicy: ` prefix and no `(Service: ..., Status Code: ..., Request ID: ...) (SDK Attempt Count: ...)` suffix. HandlerErrorCode (`InvalidRequest`) and the rollback itself are already right; the TTL rule is enforced.
Why: a client that parses the handler reason to recover the originating service, HTTP status and request id — the documented shape of a CloudFormation resource-handler failure — gets none of them, so a failed update cannot be attributed to CloudFront or correlated with a request id.
Fix: the CloudFormation resource-provider error relay that formats a downstream SDK error into the handler message, on the UPDATE path as well as CREATE. Related open issues report the same envelope drop on other paths and do not carry this check's key: 20261116T174247Z-cloudformation-cloudfront-3-net-new-causes-handler-reason.md (Cause 1, the CREATE path of the same CachePolicy rule, filed under service cloudformation__cloudfront) and 20261111T095650Z-cloudformation-cloudfront-ec2-elbv2-a-cloudformation-resource-handler.md.

=== Cause 5 of 6: DetectStackDrift reports IN_SYNC after an out-of-band UpdateCachePolicy ===
Failing check: cloudfront.deploy-cloudfront-1-cache-policy-out-of-band-ttl-drift-detected-then-updated-in-place
AWS: DetectStackDrift compares each resource's live properties with the template's. After an out-of-band UpdateCachePolicy changes MinTTL from the template's value to a different one (ETag-guarded, and the emulator does apply it — GetCachePolicyConfig reads the new MinTTL back), DescribeStackDriftDetectionStatus must report StackDriftStatus DRIFTED with DriftedStackResourceCount 1, and DescribeStackResourceDrifts must report the CachePolicy resource MODIFIED with its PhysicalResourceId, exactly one PropertyDifferences entry at PropertyPath `/CachePolicyConfig/MinTTL` with DifferenceType NOT_EQUAL, ExpectedValue the template's MinTTL and ActualValue the live one, and ExpectedProperties/ActualProperties carrying those two values.
Emulator: the fresh-stack baseline is correctly IN_SYNC, but after the out-of-band edit DescribeStackDriftDetectionStatus still returns StackDriftStatus `IN_SYNC`, DetectionStatus `DETECTION_COMPLETE`, DriftedStackResourceCount 0 — no resource drift is reported at all, so no PropertyDifferences exist to inspect.
Why: drift detection silently claims a stack matches its template when it does not. A client using drift as the guardrail against out-of-band edits gets a false all-clear for every CloudFront resource.
Fix: drift detection for the AWS::CloudFront::* resource handlers — the live-state reader the drift comparator calls must return the resource's current properties so the comparator can emit MODIFIED plus PropertyDifferences. Related open issues report the same never-detected drift for other resource families and carry none of this check's keys: 20261114T035529Z-cloudformation-2-net-new-causes-an-out-of.md, 20261114T035529Z-cloudformation-dynamodb-detectstackdrift-reports-in-sync-after-a.md, 20261029T171940Z-cloudformation-drift-reporting-returns-live-resource-attributes-and.md.

=== Cause 6 of 6: the cloudfront-keyvaluestore data plane must be reached at an account-id-prefixed host the emulator serves no address for ===
Failing check: cloudfront.cf-keyvaluestore-put-key-visible-to-function-at-edge
AWS: the KVS data plane (DescribeKeyValueStore/PutKey/GetKey/DeleteKey, all keyed by KvsARN) is addressed at a host derived from the KvsARN — the SDK's endpoint resolution prepends the ARN's 12-digit account id as a leading DNS label to the service endpoint host. Recorded behavior only for the exact host form; what is required is that the data-plane endpoint derived from the ARN the control plane returned is answerable.
Emulator: CreateKeyValueStore succeeds and returns a KeyValueStore.ARN, but the data-plane endpoint resolved from that ARN is `<account-id>.<endpoint host>` — observed as `000000000000.127.0.0.1` — and the emulator announces/serves no address there, so the very first cloudfront-keyvaluestore call is refused before any request is sent: `CapabilityNotOffered: the target serves no address for 000000000000.127.0.0.1` / `egress refused: '000000000000.127.0.0.1' is not the endpoint under test`. The check aborts before PutKey, so nothing downstream (KVS -> function propagation) is exercised. The account id and the endpoint host are per-environment values; the requirement is that the account-id-prefixed data-plane host form resolves to the endpoint the emulator answers on.
Why: the whole key-value-store data plane is unusable — a client can create a store through CloudFront and then has no reachable endpoint to write or read a single key, so no edge function can ever observe data in it.
Fix: endpoint/host handling for the cloudfront-keyvaluestore data plane — the emulator must answer on the account-id-prefixed host derived from the KvsARN it hands out (accept the `<account-id>.` label on the served endpoint), or hand out an ARN whose endpoint resolution lands on the host it is reached on. Related open issues describe earlier failure modes of the same data plane and carry neither this check's key: 20261024T174507Z-cloudfront-keyvaluestore-data-plane-is-unreachable-every-describekeyvaluestore.md (404 UnknownService) and 20261026T232858Z-cloudfront-keyvaluestore-data-plane-is-refused-at-auth.md (403 AccessDenied).
