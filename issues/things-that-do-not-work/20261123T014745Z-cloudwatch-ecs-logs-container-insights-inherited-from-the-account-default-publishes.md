# Container Insights inherited from the account default publishes nothing: the account-default insights check never completes

> _Note: this issue was identified against the code base at commit `fda9c10fdfacd5c8a2bec05c9c210d2748ab313c`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
PutMetricData

## Description
Cause 1 of 1: a cluster that inherits containerInsights=enabled from the ECS account default never publishes any ECS/ContainerInsights telemetry, so the account-default inheritance / explicit-disabled differential check exhausts its whole budget instead of grading. Failing check: cloudwatch__ecs__logs.obs-ecs-2-account-default-insights-inherited-explicit-disabled-publishes-nothing.

AWS: ECS account settings are modelled — PutAccountSettingDefault(name: SettingName (enum, required), value: String (required)) -> {setting} and UpdateClusterSettings(cluster (required), settings: ClusterSettings (required)) -> {cluster}; the containerInsights setting itself is prose-only in the model, so for its telemetry effect this is recorded behavior only. The recording shows: with the account default containerInsights=enabled, a cluster created with NO settings block inherits enabled (captured at creation time, unchanged by a later change of the default), publishes the ECS/ContainerInsights namespace for its cluster dimension — in particular TaskCount with Maximum == the number of RUNNING tasks and Unit == "Count", resolvable through CloudWatch GetMetricStatistics(Namespace=ECS/ContainerInsights, MetricName=TaskCount, Dimensions=[ClusterName], Period=60) and listable through ListMetrics — and gets a performance log group named /aws/ecs/containerinsights/<clusterName>/performance created on the account's behalf. A sibling cluster created with an explicit containerInsights=disabled setting publishes no datapoints, lists no ECS/ContainerInsights metrics and gets no performance log group, until UpdateClusterSettings sets it to enabled, after which it publishes TaskCount in Count like the other cluster. All calls in the recording succeed (HTTP 200, no error code); the divergence is in emitted telemetry, not in a refusal.

Emulator: the check produces no assertion at all — it is killed by the harness with 'Check timed out after 600.0s'. The only unbounded-by-assertion waits it can be sitting in are the ones that poll for the inheriting cluster's ECS/ContainerInsights TaskCount datapoints (600 s), the later-minute TaskCount datapoint, and the appearance of /aws/ecs/containerinsights/<cluster>/performance (600 s) — i.e. the emulator serves GetMetricStatistics/ListMetrics for ECS/ContainerInsights as permanently empty and never creates the performance log group for a cluster whose containerInsights came from the account default. Hypothesis: the same missing Container Insights publisher reported in the open issue 20261109T143515Z-cloudwatch-ecs-logs-container-insights-publishes-no-cluster-metrics-and-no.md, which is grounded in two different checks (container-insights-publishes-cluster-metrics-and-performance-logs and obs-ecs-2-fargate-service-metrics-dimensioned-per-service-not-per-cluster) and whose replay keys do not carry this check; that issue does not cover the account-default inheritance path exercised here, so this check is filed separately and should be re-replayed even if that issue is closed.

Why: a client cannot tell enabled-by-account-default Container Insights from disabled Container Insights. Every dashboard, alarm and autoscaling decision built on ECS/ContainerInsights TaskCount sees no data while DescribeClusters reports containerInsights=enabled, and anything that waits for /aws/ecs/containerinsights/<cluster>/performance to appear (log subscriptions, insight queries, teardown that deletes it) waits forever. Because the negative half of the differential also reads empty, a client gets a false confirmation that an explicitly disabled cluster is correctly silent.

Fix: the ECS Container Insights telemetry publisher — the component that resolves a cluster's effective containerInsights value (cluster setting, else the account default captured at CreateCluster time) and, when it is enabled, emits the ECS/ContainerInsights metric series for the cluster dimension into CloudWatch metric state and creates the /aws/ecs/containerinsights/<cluster>/performance log group in the logs state. It must also start publishing for a cluster switched to enabled by UpdateClusterSettings, and must remain silent for an explicitly disabled cluster.

Traces: cloudwatch__ecs__logs.obs-ecs-2-account-default-insights-inherited-explicit-disabled-publishes-nothing.

## Evidence
Suite report, ### cloudwatch__ecs__logs: '[mismatch] cloudwatch__ecs__logs.obs-ecs-2-account-default-insights-inherited-explicit-disabled-publishes-nothing — Error: Check timed out after 600.0s'. The check's own failure texts that would have been raised had the budget allowed are 'no TaskCount datapoint for the inheriting cluster <cluster> within 600 s of its task running -- the inherited containerInsights=enabled published nothing' and 'Container Insights performance log group /aws/ecs/containerinsights/<cluster>/performance not met within 600s. Last result: []'. Fixed text in those messages is the wording above; the variable parts are the generated cluster name and the task ARN, which differ per run and are not requirements. Expected: GetMetricStatistics(Namespace=ECS/ContainerInsights, MetricName=TaskCount, Dimensions=[{ClusterName: <inheriting cluster>}], Period=60) returns at least one datapoint with Maximum=1.0 and Unit=Count while one task is RUNNING, DescribeLogGroups(logGroupNamePrefix=/aws/ecs/containerinsights/<cluster>/performance) lists that exact group, and the same reads for the explicitly disabled sibling stay empty until UpdateClusterSettings enables it. Actual: the insights reads never become non-empty, so the check never reaches a verdict.

## Steps to Reproduce
Replay cloudwatch__ecs__logs.obs-ecs-2-account-default-insights-inherited-explicit-disabled-publishes-nothing. In short: PutAccountSettingDefault(name=containerInsights, value=enabled); CreateCluster with no settings (inheriting) and CreateCluster with settings=[{name: containerInsights, value: disabled}] (control); RegisterTaskDefinition (FARGATE/awsvpc, 256/512) and RunTask one task in each cluster; wait for both RUNNING; then poll CloudWatch GetMetricStatistics(Namespace=ECS/ContainerInsights, MetricName=TaskCount, Dimensions=[{Name: ClusterName, Value: <inheriting cluster>}], Period=60, Statistics=[Maximum, SampleCount]) and logs DescribeLogGroups(logGroupNamePrefix=/aws/ecs/containerinsights/<inheriting cluster>/performance). Both stay empty for the full 600 s window; finally UpdateClusterSettings(cluster=<control>, settings=[{name: containerInsights, value: enabled}]) and RunTask again in the control — its TaskCount never appears either.
