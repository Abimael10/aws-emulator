# dynamodb: 3 net-new causes — SearchVectors withholds the vector attribute even when ProjectionExpression names it, VectorSearchRequestBytes is pinned at the 1 KB floor across TopK, and a TransactWriteItems Update over the 400 KB item limit is refused with a top-level ValidationException instead of TransactionCanceledException

> _Note: this issue was identified against the code base at commit `47e808590d465f96c3f3c8da194aaffba935d68f`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
SearchVectors, TransactWriteItems

## Description
Three net-new root causes in the dynamodb emulator. None of these replay keys is carried by an open issue; where an open issue covers an adjacent area it is named under the cause.

=== Cause 1 of 3: SearchVectors omits the vector attribute from every result item even when ProjectionExpression explicitly names it ===
AWS: Smithy: SearchVectorsInput.ProjectionExpression is documented as "A string that identifies one or more attributes to retrieve from the index. Separate attribute names with commas. If not specified, the operation returns all attributes projected into the vector index. Only attributes projected into the vector index can be retrieved." The vector attribute named by VectorIndex.VectorAttribute IS projected into an index whose Projection is ProjectionType ALL, so naming it in ProjectionExpression retrieves it; recorded behavior is that it is withheld from the DEFAULT projection but returned, as an L of N components, as soon as ProjectionExpression names it.
Emulator: the vector attribute is never present in SearchResults items, whatever ProjectionExpression says. On a COSINE index whose Projection is ALL, `SearchVectors(..., ProjectionExpression='emb, pk')` returns an item carrying only `['pk']`; on two DOT_PRODUCT indexes with Projection ALL, `ProjectionExpression='pk, emb'` returns items with no `emb` key at all (the checks die with `KeyError: 'emb'` when reading it). The default-projection half is correct (`{pk, tier}` without the vector) and ranking/score values are correct — only the explicitly named vector attribute is dropped. Note this is the inverse of the behavior described in the open issue 20261119T104646Z-dynamodb-9-net-new-causes-vector-index-projection.md (Cause 1: the vector attribute leaked into an INCLUDE projection that did not name it) and of the fixed 20261027T001720Z-dynamodb-10-net-new-root-causes-searchvectors-ignores.md: the projection filter now withholds the vector attribute unconditionally instead of honouring the request's ProjectionExpression.
Why: the whole point of a vector search for a client that re-ranks or re-scores locally, or that renders the embedding, is to get the embedding back; with no way to retrieve it, SearchVectors can only ever return non-vector attributes and a client must issue a second GetItem per hit (which returns the unrounded base-table value, not the index's float32 copy, so client-side re-scoring then disagrees with the service's own ranking). Code that reads `item['emb']` raises KeyError rather than mis-ranking, so this fails loudly in every such client.
Fix: the SearchVectors result projection — the component that builds each SearchResultItem from the index entry must evaluate the request's ProjectionExpression (with ExpressionAttributeNames) against the attributes projected into the index and include the vector attribute when the expression names it, rather than stripping it unconditionally.

=== Cause 2 of 3: SearchVectors ConsumedCapacity.VectorSearchRequestBytes never leaves the 1024-byte floor — it does not grow with TopK ===
AWS: Smithy: SearchVectors.output.ConsumedCapacity targets VectorCapacity, whose member VectorSearchRequestBytes is documented as "The number of vector search request bytes consumed by a SearchVectors operation". Recorded behavior: that figure is the only key reported for SearchVectors (no CapacityUnits/TableName/Table, same flat shape for ReturnConsumedCapacity TOTAL and INDEXES), is floored at 1024.0, and GROWS with the work done — a larger TopK on the same index with the same SearchVector scores more candidate vectors and reports strictly more bytes than TopK=1.
Emulator: on a 128-dimension index holding 25 items, TopK=1 and TopK=25 with an identical SearchVector both report `VectorSearchRequestBytes: 1024.0`. The floor itself and the key shape are correct; the meter simply never moves off the minimum. (The open issue 20261119T104646Z-dynamodb-9-net-new-causes-vector-index-projection.md Cause 3 reports the same meter not moving when the vector attribute is projected in; it does not carry this replay key, and the TopK dimension is a separate input to the same computation.)
Why: a client budgeting, alarming on, or attributing cost to vector search cannot distinguish a cheap single-nearest-neighbour lookup from a 25-way top-K scan over 128-dimension vectors — every search bills the 1 KB minimum, so capacity planning and cost attribution built on this number are wrong exactly where the spend is.
Fix: the SearchVectors capacity meter — VectorSearchRequestBytes must be computed from the bytes actually searched (candidate vectors scored, their dimensionality, and the attributes returned) with 1024.0 as a floor, not returned as a constant.
Traces: dynamodb.search-vectors-consumed-capacity-is-vector-bytes-only-floored-and-scales

=== Cause 3 of 3: a TransactWriteItems Update that would push an item past 409600 bytes is refused with a top-level ValidationException instead of TransactionCanceledException ===
AWS: Smithy: TransactWriteItems declares TransactionCanceledException among its errors (client error, HTTP 400); the documented item-size quota is 400 KB = 409600 bytes counting attribute names and values, key included (https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/ServiceQuotas.html#limits-items). Recorded behavior: a per-item failure inside a transaction — including an Update whose result would exceed the item-size limit — is reported as a CANCELLATION, not as request validation: HTTP 400, error code `TransactionCanceledException`, message `Transaction cancelled, please refer cancellation reasons for specific reasons [ValidationError]` (fixed text; the bracketed list carries one reason Code per entry in TransactItems, in request order, `ValidationError` for the offending entry and `None` for entries that did not fail), with the corresponding CancellationReasons entry naming the failure; the stored item is left unchanged. A Put of an item at exactly 409600 bytes, and an Update that grows an item to exactly 409600 bytes, are both ACCEPTED (those legs pass).
Emulator: the same Update, one byte past the limit, is refused with code `ValidationException` and message `Item size to update has exceeded the maximum allowed size` — AWS's wording for a bare UpdateItem, raised as a top-level request validation error, so no TransactionCanceledException and no CancellationReasons are produced at all.
Why: a client wraps TransactWriteItems in a `catch (TransactionCanceledException e)` handler and reads `e.CancellationReasons` to learn WHICH of its up-to-100 entries failed and why; a ValidationException escapes that handler entirely (it is the "my request is malformed, do not retry this shape" class), and the caller is given no per-entry attribution, so a 100-entry transaction reports only that something somewhere was too big. Adjacent open issues 20261120T124018Z-dynamodb-6-net-new-causes-transactwriteitems-cancellation-reason.md and 20261120T093536Z-dynamodb-3-net-new-causes-the-transactitems-100.md cover other cancellation-reason and TransactItems-cap divergences and do not carry this replay key.
Fix: the TransactWriteItems handler's per-item validation — an item-size overflow computed while applying an Update (or Put) entry must be raised as a cancellation of that entry (CancellationReasons Code `ValidationError`) and serialized as TransactionCanceledException with AWS's cancellation message, not as a top-level ValidationException from the item-size validator.
Traces: dynamodb.transact-write-items-put-and-update-accept-flat-409600-byte-item

## Evidence
Cause 1 — expected: `SearchVectors(TableName=…, IndexName='idx', TopK=5, SearchVector=…, ProjectionExpression='emb, pk')` returns each item with exactly the attribute set {pk, emb}, `emb` being the written vector as an L of N components. Actual: `AssertionError: ProjectionExpression naming the vector attribute did not return it: ['pk']`. On the two DOT_PRODUCT checks the same omission surfaces as `KeyError: 'emb'` while reading `by_pk['d']['emb']['L'][0]['N']` / `by_pk['unrepresentable']['Item']['emb']['L'][0]['N']` from results fetched with `ProjectionExpression='pk, emb'`. The default projection (no ProjectionExpression) correctly returns {pk, tier} without the vector, and the scores/ordering asserted before these lines passed.

Cause 2 — expected: on one 128-dimension COSINE index with an identical SearchVector, VectorSearchRequestBytes for TopK=25 is strictly greater than for TopK=1 (both at or above the 1024.0 floor). Actual: `AssertionError: TopK=25 reported 1024.0 bytes, not more than TopK=1's 1024.0`. The preceding assertions — ConsumedCapacity carries only VectorSearchRequestBytes, equal to 1024.0 at the floor, with the same flat shape under ReturnConsumedCapacity=INDEXES — passed.

Cause 3 — expected: HTTP 400, code `TransactionCanceledException`, message `Transaction cancelled, please refer cancellation reasons for specific reasons [ValidationError]` (the bracketed reason list is derived from the request's entries; the rest of the sentence is fixed), and the stored item unchanged. Actual: `AssertionError: a TransactWriteItems Update growing an item one byte past 409600 bytes must be TransactionCanceledException, got 'ValidationException': 'Item size to update has exceeded the maximum allowed size'`. The two accept legs (a TransactWriteItems Put of an exactly-409600-byte item, and an Update growing an item to exactly 409600 bytes) both passed and read back whole.
