# ListPurchaseOptions answers 200 with an empty purchase-option list where the recorded flow returns one

> _Note: this issue was identified against the code base at commit `348061a84c3b2478701b3a4c5bc85ef0cc515a9a`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
ListPurchaseOptions

## Description
This issue bundles 2 causes, both in marketplace-discovery, both on ListPurchaseOptions, and both the same symptom: the operation answers 200 but selects NO purchase option where the recording returns one. Each cause is one replay cluster and each needs its own re-replay before it is closed.

Cause 1 of 2: a ListPurchaseOptions call whose filters name a product and that product's seller of record matches nothing, so `purchaseOptions` comes back empty.
AWS: Smithy ListPurchaseOptions (POST /2026-02-05/listPurchaseOptions, success 200; input `filters` PurchaseOptionFilterList @length 1..10, `maxResults` MaxResults @range 1..100 default 25, `nextToken` NextToken @length 0..8192 @pattern ^[a-zA-Z0-9+/=]+$, `locale` Locale; output `purchaseOptions` PurchaseOptionSummaryList @length ..100 and `nextToken`; errors ValidationException 400 / AccessDeniedException 403 / ThrottlingException 429 / InternalServerException 500; @paginated items=purchaseOptions). The operation's own documentation states "Returns the purchase options (offers and offer sets) available to the buyer. You can filter results by product, seller, purchase option type, visibility scope, and availability status", and PurchaseOptionFilter$filterValues documents that `PRODUCT_ID` takes "One or more product identifiers to filter by" and `SELLER_OF_RECORD_PROFILE_ID` "One or more seller profile identifiers to filter by", with "Multiple filters ... combined with AND logic. Multiple values within the same filter are combined with OR logic". So the requirement is a selection rule, not a particular row: a purchase option whose associated product is one of the PRODUCT_ID values AND whose sellerOfRecord.sellerProfileId is one of the SELLER_OF_RECORD_PROFILE_ID values MUST be returned, as a PurchaseOptionSummary carrying purchaseOptionId, catalog, purchaseOptionType (OFFER | OFFERSET), sellerOfRecord, badges and associatedEntities (all @required except badges/purchaseOptionName/times). For the row itself this is recorded behavior only: the recording answers 200 with exactly one element, purchaseOptionType `OFFER`, one badge (badgeType `AUTO_RENEW`, displayName `Auto-renew`), catalog `AWSMarketplace`, and one associatedEntities entry naming the filtered product and the offer, with sellerOfRecord equal to the seller profile id the filter asked for — and that seller profile id in the recorded body is the fixture's captured `{{po_seller_id}}` variable, i.e. a value taken from an EARLIER step of the same flow rather than a literal, so the request filtered on an id this emulator itself had just published.
Emulator: 200 with the list EMPTY — the replay reports `$.purchaseOptions[0]: missing (expected {...purchaseOptionType 'OFFER', badges [AUTO_RENEW], associatedEntities [{offer, product}]...}, got None)`. Nothing matched, so no summary was serialized at all. The same cluster covers the offer drill-down fixture's first ListPurchaseOptions call (marketplace-discovery-purchase-options-offer-drilldown#task#1), which is empty the same way. Hypothesis for the mechanism: the filter evaluation in services/service-com-amazonaws-marketplacediscovery-awsmarketplacediscovery/src/ops/list_purchase_options.rs (matches_every_filter, lines 234-276) ANDs `PRODUCT_ID` against `entry.product_ids` and `SELLER_OF_RECORD_PROFILE_ID` against `entry.seller_profile_id`, and the seeded catalog never satisfies both at once for a product the flow's earlier steps published — either because the offer's stored sellerOfRecord is not the publisher/manufacturer profile id the earlier step handed the fixture, or because the catalog holds no offer at all for that product; a `VISIBILITY_SCOPE` filter would likewise never select a breadth-seeded row, since every seeded offer and offer set is stored `VISIBILITY_PUBLIC` (src/state.rs:4838 and :4887).
Why: an empty list is not an error, so a client cannot tell "no purchase option exists" from "the emulator failed to select one". A buyer-side client that asks which offers it may transact on for a product it just discovered concludes the product cannot be purchased and stops: the discover-then-purchase path dead-ends, and because `nextToken` is absent there is nothing to continue from either. Any client that cross-checks the seller it filtered on against the seller the product's listing published also sees the two halves of the same catalog disagree.
Fix: the purchase-option selection path of this operation — matches_every_filter / the entry projection it reads (ComAmazonawsMarketplacediscoveryAwsmarketplacediscoveryState::purchase_options, src/state.rs:1133-1202) and the seeded offers/offer sets those entries are built from, whose sellerOfRecord and product_ids must agree with the publisher/manufacturer and product ids the same catalog's SearchListings/GetListing/GetProduct publish, so a PRODUCT_ID + SELLER_OF_RECORD_PROFILE_ID conjunction taken from this emulator's own earlier response selects that product's offer.
Traces: marketplace-discovery-purchase-options-filter-by-product-and-seller#task#1 (expected 200 / got 200, key $.purchaseOptions[0]); same cluster also marketplace-discovery-purchase-options-offer-drilldown#task#1.

Cause 2 of 2: the offer-set drill-down's ListPurchaseOptions call also selects nothing, so the drill-down has no purchase option to drill into.
AWS: same operation and same modelled shapes as cause 1. Recorded behavior: the second step of the offer-set drill-down answers 200 with a one-element `purchaseOptions` list — purchaseOptionType `OFFER`, catalog `AWSMarketplace`, one `AUTO_RENEW` badge, sellerOfRecord naming the seller, and one associatedEntities entry pairing the product with the offer and its seller of record. The requirement is again the selection rule, not the literal ids: the filters that follow an offer-set drill-down must still select the offers that offer set covers.
Emulator: 200 with `$.purchaseOptions: value_mismatch (expected [ {...one OFFER summary...} ], got [])` — the whole list is empty where one element is expected. Hypothesis: the offer-set projection (src/state.rs:1162-1194) builds an `OFFERSET` entry's product_ids only from offers that resolve inside `self.offers` and skips any that do not, and the seeded offer-set rows exist only for rows flagged `offer_set` (src/state.rs:4816, 4876-4889) — so a drill-down filter derived from an offer set can end up matching no entry at all.
Why: the fixture's whole point is to drill from an offer set to the purchase options under it. With an empty list the client is told the offer set has nothing purchasable under it, which is a false negative that silently truncates the flow rather than failing it.
Fix: same component as cause 1 — the purchase-option entry projection and the filter evaluation, so that offers reachable through a seeded offer set are selected by the filters the drill-down issues.
Traces: marketplace-discovery-purchase-options-offerset-drilldown#task#2 (expected 200 / got 200, key $.purchaseOptions).

Explicitly NOT claimed as requirements anywhere in this issue: the recorded literal purchaseOptionId / productId / sellerProfileId values, the recorded display names, and any clock-derived availableFromTime or expirationTime. Those differ per environment and per run. The defect is that the documented filter conjunctions select NOTHING, so a required, non-empty result set is served as an empty list.
