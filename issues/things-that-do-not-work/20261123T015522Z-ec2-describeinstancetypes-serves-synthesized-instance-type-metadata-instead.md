# ec2 DescribeInstanceTypes serves synthesized instance-type metadata instead of the published per-type values

> _Note: this issue was identified against the code base at commit `6c5e437ac482b043e6839b0d94a89be6f95b8112`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
DescribeInstanceTypes

## Description
DescribeInstanceTypes answers 200 with a row for every requested instance type, but the per-type metadata in each row is derived/synthesized by the emulator (computed from family+size heuristics) rather than taken from AWS's published instance-type catalog. The replay clusters 110 net-new divergence clusters on this one operation, all of them `status=200->200` value/missing mismatches inside `$.DescribeInstanceTypesResponse.instanceTypeSet.item[...]`, spread over the `ec2-catalog-describe-instance-types-*` fixture family. Three of those clusters are named below and in the replay pointer as the representatives of the single root cause; a fixer MUST re-replay the whole `ec2-catalog-describe-instance-types-*` family (every step of it), not only the three named fixtures, because the remaining 107 clusters are the same defect on other instance-type families.

Cause 1 of 3 — EBS-optimized performance, EBS attachment and network-card numbers are computed, not catalogued (fixture ec2-catalog-describe-instance-types-a1-c9g, step task#28; c8i.* rows).
AWS: Smithy (services/service-com-amazonaws-ec2-amazonec2/smithy-model): InstanceTypeInfo.ebsInfo -> EbsInfo{attachmentLimitType, maximumEbsAttachments, ebsOptimizedInfo}; EbsOptimizedInfo{baselineBandwidthInMbps(int), baselineIops(int), baselineThroughputInMBps(double), maximumBandwidthInMbps(int), maximumIops(int), maximumThroughputInMBps(double)}; NetworkCardInfo{networkPerformance, baselineBandwidthInGbps, peakBandwidthInGbps, defaultEnaQueueCountPerInterface, maximumEnaQueueCount, maximumEnaQueueCountPerInterface, additionalFlexibleNetworkInterfaces, maximumNetworkInterfaces, interfaceTypeSet}. The model constrains the shape only; the per-type VALUES are a published AWS catalog, so the recording is authoritative for them (recorded behavior for the values).
Emulator: for the same type it emits different, internally-derived numbers and omits members it has no source for: e.g. c8i.metal-96xl ebsInfo.ebsOptimizedInfo.baselineBandwidthInMbps 81600 instead of 80000, baselineIops 360000 instead of 480000, baselineThroughputInMBps 10200.0 instead of 10000.0, maximumIops 360000 instead of 480000, ebsInfo.maximumEbsAttachments 27 instead of 79, ebsInfo.attachmentLimitType 'shared' instead of 'dedicated', autoRecoverySupported false instead of true, networkInfo.connectionTrackingConfiguration.defaultTcpEstablishedTimeout 432000 instead of 350, and networkInfo.bandwidthWeightings missing entirely where AWS returns {item:[default, ebs-1, vpc-1]}.
Why: callers use these numbers to choose instance types and to size EBS/network expectations (capacity planners, Compute-Optimizer-style tooling, CDK/Terraform validation). A client that trusts the emulator reads attachment limits, EBS baselines and ENA queue counts that no real instance type has, and code that branches on an absent optional member (bandwidthWeightings, defaultEnaQueueCountPerInterface) takes the 'unsupported' path against AWS where the member is always present.
Fix: the DescribeInstanceTypes handler's backing catalog/state — the instance-type metadata table the operation reads — must carry the published per-type record (and the serializer must emit every member the record has) instead of computing values from the type name.
Traces: ec2-catalog-describe-instance-types-a1-c9g#task#28.

Cause 2 of 3 — network-card/network-info and capability flags are wrong for older families (fixture ec2-catalog-describe-instance-types-c9gd-m6gd, step task#41; m5zn.* rows).
AWS: same shapes as above plus InstanceTypeInfo.hibernationSupported(boolean), networkInfo.networkPerformance, networkInfo.networkCards.item.networkPerformance/baselineBandwidthInGbps/peakBandwidthInGbps/defaultEnaQueueCountPerInterface; values are the published catalog (recorded behavior only).
Emulator: for m5zn.large it returns ebsOptimizedInfo.baselineBandwidthInMbps 575 instead of 800, baselineIops 3000 instead of 3333, baselineThroughputInMBps 71.875 instead of 100.0, maximumBandwidthInMbps 4750 instead of 3170, maximumIops 18750 instead of 13333, hibernationSupported true instead of false, networkCards.item.networkPerformance 'Up to 10 Gigabit' instead of 'Up to 25 Gigabit', peakBandwidthInGbps 10.0 instead of 25.0, baselineBandwidthInGbps 4.16 instead of 3.0, and omits networkCards.item.defaultEnaQueueCountPerInterface (AWS: 8). Other rows in the same response diverge on networkInfo.efaSupported/efaInfo, maximumNetworkInterfaces, ipv4/ipv6AddressesPerInterface, processorInfo.sustainedClockSpeedInGhz, supportedBootModes and vCpuInfo.validCores.
Why: the derived numbers are monotone in instance size, so they contradict AWS exactly for the types that break the pattern (z-series clock-boosted, *-flex, metal). Clients that gate on hibernationSupported or efaSupported get the opposite answer from AWS.
Fix: same component as Cause 1 — the per-type catalog record behind the DescribeInstanceTypes handler; validCores/processorInfo/bootModes must come from the record too.
Traces: ec2-catalog-describe-instance-types-c9gd-m6gd#task#41.

Cause 3 of 3 — flex/newest families diverge on host, placement and nitro members as well (fixture ec2-catalog-describe-instance-types-r5-r8in, step task#26; r8i-flex.* rows).
AWS: InstanceTypeInfo.dedicatedHostsSupported(boolean), nitroEnclavesSupport(enum), placementGroupInfo.supportedStrategies(list), processorInfo.supportedFeatures, networkInfo.enaSrdSupported/secondaryNetworkSupported/trafficMirroringSupport — again shape from the Smithy model, values from the published catalog (recorded behavior only).
Emulator: r8i-flex.2xlarge dedicatedHostsSupported true instead of false, ebsInfo.attachmentLimitType 'shared' instead of 'dedicated', ebsOptimizedInfo.baselineBandwidthInMbps 2300 instead of 1250, baselineIops 12000 instead of 6000, maximumBandwidthInMbps 4750 instead of 10000, maximumIops 18750 instead of 40000, maximumEbsAttachments 27 instead of 32, networkInfo.bandwidthWeightings missing, connectionTrackingConfiguration.defaultTcpEstablishedTimeout 432000 instead of 350; placementGroupInfo.supportedStrategies and nitroEnclavesSupport also diverge across the flex rows.
Why: flex types are precisely the ones a right-sizing client is asked to compare, and the emulator reports them as dedicated-host-capable and EBS-weaker/stronger than they are, so the client's selection differs from what AWS would allow.
Fix: same component — the instance-type catalog the handler reads; no per-cause code path differs.
Traces: ec2-catalog-describe-instance-types-r5-r8in#task#26.
