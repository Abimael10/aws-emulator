# cloudformation__efs: 2 net-new causes — an AWS::EFS::FileSystem with LifecyclePolicies is never created in EFS (Ref is a synthesized physical id), and a lockout FileSystemPolicy stack reaches CREATE_COMPLETE instead of rolling back

> _Note: this issue was identified against the code base at commit `384e9c06f8b850c3e6c1129231f41c38ae5339ba`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
CreateStack

## Description
Two distinct net-new causes, both reached through CloudFormation templates declaring AWS::EFS::FileSystem. Both are grounded in failing checks the suite lists under '### cloudformation__efs' that the replay report does NOT mark ALREADY FILED or OWNED.

Related open issue, which does not cover either check as the report scores them: 20261109T132032Z-cloudformation-efs-3-net-new-causes-aws-efs.md (its Issue-Trace-Ids are deploy-cfn-efs-file-system-resource-lifecycle, deploy-cfn-efs-file-system-provisioned-throughput-missing-rejected, deploy-cfn-efs-access-point-and-mount-target-round-trip-and-delete, deploy-cfn-efs-mount-target-second-in-same-az-rejected — neither check filed here is among them, and neither is marked owned). Cause 1 below is the same family as that issue's Cause 1 reached through a different template (LifecyclePolicies) and additionally covers the LifecyclePolicies property itself; a fixer should close them together if they share one backing gap. Cause 2 is a refusal path no open issue describes.

Cause 1 of 2: an AWS::EFS::FileSystem declaring LifecyclePolicies reaches CREATE_COMPLETE but is never created in EFS, and !Ref resolves to a CloudFormation-synthesized '<stack>-<LogicalId>-<hex>' name rather than the EFS FileSystemId, so no EFS read of the deployed file system is possible and the template's LifecyclePolicies can never be read back. Failing check: cloudformation__efs.deploy-cfn-efs-lifecycle-policies-round-trip-and-delete.
AWS: CloudFormation provisions AWS::EFS::FileSystem by calling elasticfilesystem:CreateFileSystem and, for LifecyclePolicies, PutLifecycleConfiguration; the resource's PhysicalResourceId — and therefore !Ref — IS the EFS FileSystemId, 'fs-' plus 8..40 hex digits. Smithy (efs): DescribeLifecycleConfiguration is GET /2015-02-01/file-systems/{FileSystemId}/lifecycle-configuration, 200, output LifecycleConfigurationDescription.LifecyclePolicies (list, max 3); its input member FileSystemId is @required, @httpLabel, length 0..128, pattern ^(arn:aws[-a-z]*:elasticfilesystem:[0-9a-z-:]+:file-system/fs-[0-9a-f]{8,40}|fs-[0-9a-f]{8,40})$; modelled errors BadRequest 400, FileSystemNotFound 404, InternalServerError 500. A stack whose LifecyclePolicies are [{TransitionToIA: AFTER_30_DAYS}, {TransitionToPrimaryStorageClass: AFTER_1_ACCESS}] is read back by DescribeLifecycleConfiguration exactly, in template order, and after the stack is deleted the same read is refused 404 FileSystemNotFound with message "File system '<FileSystemId>' does not exist." (fixed text "File system '" ... "' does not exist." with the requested id as its only variable part).
Emulator: the stack reaches CREATE_COMPLETE and its Outputs resolve FileSystemIdRef to a name of the form '<stack-name>-<LogicalId>-<hex>' (one run produced 'sim2real-behav-stack-2159aee6042e-Fs-38F4FB67EB6E'; the stack name, logical id and hex suffix are per-run values — the '<stack>-<logical-id>-<suffix>' template is the defect). Passing it to DescribeLifecycleConfiguration is refused 400 ValidationException: "1 validation error detected: Value '<that id>' at 'fileSystemId' failed to satisfy constraint: Member must satisfy regular expression pattern: ^(arn:aws[-a-z]*:elasticfilesystem:[0-9a-z-:]+:file-system/fs-[0-9a-f]{8,40}|fs-[0-9a-f]{8,40})$" (fixed text is AWS's standard validation wording; the variable parts are the rejected value from the request, the member name 'fileSystemId' and the modelled pattern). Hypothesis: the AWS::EFS::FileSystem handler mints a physical id without calling EFS, so neither the file system nor its lifecycle configuration exists.
Why: a client that deploys EFS lifecycle policies through CloudFormation cannot read back, verify or use what it deployed — every !Ref/!GetAtt it hands to EFS or to another service is rejected as a malformed FileSystemId, and deleting the stack removes nothing from EFS, so the post-delete FileSystemNotFound contract is unreachable too.
Fix: the CloudFormation AWS::EFS::FileSystem resource handler (create/read/delete) — it must call elasticfilesystem:CreateFileSystem, apply the template's LifecyclePolicies via PutLifecycleConfiguration, and record the returned FileSystemId as the resource's PhysicalResourceId so Ref/GetAtt resolve to it.
Traces: cloudformation__efs.deploy-cfn-efs-lifecycle-policies-round-trip-and-delete.

Cause 2 of 2: a FileSystemPolicy that denies everyone elasticfilesystem:PutFileSystemPolicy is accepted, so the stack reaches CREATE_COMPLETE where AWS fails the resource and rolls the stack back — the EFS policy-lockout safety check is not enforced. Failing check: cloudformation__efs.deploy-cfn-efs-file-system-policy-lockout-rejected.
AWS: Smithy (efs): PutFileSystemPolicy is PUT /2015-02-01/file-systems/{FileSystemId}/policy, 200, with input members FileSystemId (@required, @httpLabel), Policy (@required, length 1..20000) and BypassPolicyLockoutSafetyCheck (boolean, @default false); modelled errors BadRequest 400, FileSystemNotFound 404, IncorrectFileSystemLifeCycleState 409, InternalServerError 500, InvalidPolicyException 400. InvalidPolicyException is documented as "Returned if the FileSystemPolicy is malformed or contains an error such as a parameter value that is not valid or a missing required parameter. Returned in the case of a policy lockout safety check error." So a policy whose only statement is {Effect: Deny, Principal: {AWS: "*"}, Action: "elasticfilesystem:PutFileSystemPolicy"} must be refused 400 with the lockout message unless BypassPolicyLockoutSafetyCheck is set. Through CloudFormation that refusal surfaces as a single CREATE_FAILED event on the AWS::EFS::FileSystem resource whose ResourceStatusReason is the resource-handler wrapping 'Resource handler returned message: "This policy would prevent future FileSystemPolicy updates. Retry the request with the BypassPolicyLockoutSafetyCheck parameter to apply this policy. (Service: Efs, Status Code: 400, Request ID: <id>) (SDK Attempt Count: <n>)" (RequestToken: <token>, HandlerErrorCode: InvalidRequest)' — the quoted sentence, 'Service: Efs', 'Status Code: 400' and HandlerErrorCode InvalidRequest are the fixed requirement; the request id, request token and SDK attempt count are per-run values — and the stack ends ROLLBACK_COMPLETE with no file system left carrying the template's Name tag.
Emulator: the stack with the lockout policy reaches CREATE_COMPLETE. No CREATE_FAILED event and no lockout refusal are produced for the Fs resource, and the file system (plus its locking policy) is left behind rather than rolled back.
Why: a client relying on the lockout safety check to stop it from writing a policy that would make the file system's policy permanently unmanageable is told the deployment succeeded. The guard rail AWS documents is absent, the InvalidRequest/rollback failure path can never be exercised, and the only distinguishing signal between a safe and an unsafe policy deployment is gone.
Fix: EFS PutFileSystemPolicy validation (the lockout safety check over the submitted policy document, honouring BypassPolicyLockoutSafetyCheck and raising InvalidPolicyException 400 with AWS's lockout sentence), plus the CloudFormation AWS::EFS::FileSystem create handler, which must route the template's FileSystemPolicy through that validation and map the refusal to a CREATE_FAILED resource event with HandlerErrorCode InvalidRequest so the stack rolls back.
Traces: cloudformation__efs.deploy-cfn-efs-file-system-policy-lockout-rejected.
