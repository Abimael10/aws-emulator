# Listing, product and fulfillment detail views answer from a substituted catalog record

> _Note: this issue was identified against the code base at commit `348061a84c3b2478701b3a4c5bc85ef0cc515a9a`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
GetListing

## Description
This issue bundles 3 causes, all in marketplace-discovery, all in the same drill-down flow (SearchListings -> GetListing -> GetProduct -> ListFulfillmentOptions). Each cause is one replay cluster and each needs its own re-replay to be confirmed closed.

NOTE ON OVERLAP — read before closing. Two open issues describe this flow and name these same steps: 20261109T122558Z-marketplace-discovery-getlisting-and-getproduct-detail-responses-restate-a-seeded.md (task#2/task#3) and 20261119T070657Z-marketplace-discovery-listfulfillmentoptions-announces-a-saas-fulfillmenturl-on-an-address.md (task#4). The current replay nonetheless reports all three clusters as UNOWNED (`owned_by` empty — no filed issue carries their replay key), and the emulator's behaviour has MOVED since those were written: the slug-shaped `categoryId` values ('machine-learning', 'structured-data-ml') and the generated 'Fulfilled as <...>' highlight sentences those issues quote are gone — categoryId is now UUID-shaped and highlights are real feature sentences — yet every content member still describes a different record from the one the requested id names. Neither of those issues is a substitute for closing the causes below; treat this issue as the one carrying the replay keys for these three steps.

This service is READ-ONLY: every operation is @readonly and the model declares no create/put operation, so a client has no way to put data into the catalog it reads. The emulator therefore OWNS the catalog it answers from (its own src/state.rs says exactly this), which makes the content of that catalog part of what this emulator has to get right — a detail view that answers from a different record than the id names is a defect, not an environment difference.

Cause 1 of 3: GetListing answers 200 for the requested listingId, but every content member describes a different record than that id names.
AWS: Smithy GetListing (POST /2026-02-05/getListing, success 200; input listingId ListingId @required @length 1..255 @pattern ^[\w\-]+$, locale Locale) returns associatedEntities (@required @length ..100, ListingAssociatedEntity pairs of product + offer information), badges (@required @length ..20), catalog (@required), categories (@required @length ..30, Category{categoryId @required, displayName @required}), fulfillmentOptionSummaries (@required @length ..20), highlights (@required @length ..10), listingId/listingName (@required), logoThumbnailUrl (URL @required @length 1..2048 @pattern ^https?://.*$), longDescription (@required @length ..32768), pricingModels/pricingUnits/promotionalMedia/publisher/resources/sellerEngagements/shortDescription/useCases (all @required), reviewSummary (optional); errors ResourceNotFoundException 404 / AccessDeniedException 403 / ValidationException 400 / ThrottlingException 429 / InternalServerException 500. The model fixes the SHAPE, not the content, so for content this is recorded behavior only: the response restates the stored listing the requested id names — its own listingName, short and long description, its publisher, its categories with their taxonomy identifiers in the listing's stored order, its own highlight sentences, its own resources and seller engagements, and an associatedEntities entry naming the real product AND the real offer for that listing with their real seller of record. ($.purchaseIndicators appears in the recorded response but is not declared on GetListingOutput in the on-disk model — recorded behavior only.)
Emulator: 200, and 30+ keys diverge whole-element. For the SAME listing the drill-down arrived at, `$.associatedEntities[0]` resolves the same productId to a different product and a different offer with a different seller of record (expected product 'Data' by 'Smeup LAB s.r.l.' with offer 'Offer created on <timestamp>'; got 'Borealis Structured Data Service' by 'Borealis Data' with offer 'Borealis Structured Data Service — Contract'). `$.categories[0..3].displayName` are the generated row's classification ('Structured Data', 'Machine Learning', 'Retail', 'Industries') rather than the record's ('Data Integration', 'Data Analytics', 'Infrastructure Software', 'Data Preparation'); `$.highlights[0..2]` are the generated row's feature sentences ('Trains gradient-boosted models over tabular columns', 'Feature importance is reported beside every prediction', 'Model drift is flagged against a held-out sample') rather than the record's; and `$.listingName`, `$.shortDescription`, `$.longDescription`, `$.logoThumbnailUrl`, `$.promotionalMedia[0]`, `$.publisher.displayName`/`.sellerProfileId`, `$.purchaseIndicators`, `$.resources[0..3]` (contentType, displayName, resourceType, value), `$.sellerEngagements[0..1]` and `$.useCases[0]` all come from that generated row too.
Why: GetListing is the detail view the whole discovery flow funnels into. A client that looked a listing up by id renders a different seller's record under that id — wrong publisher, wrong description, wrong support resources, wrong contact engagement — and because the substituted record is internally self-consistent, cross-checking the listing against the product cannot detect it. The identifiers are load-bearing: a categoryId fed back as a CATEGORY search filter, or a sellerProfileId fed to ListPurchaseOptions, addresses a different entity than the one the client meant.
Fix: the seeded catalog and the projections GetListing restates it through, in the service crate's state (services/service-com-amazonaws-marketplacediscovery-awsmarketplacediscovery/src/state.rs — the per-row seeder seed_rows at 4675-4891 and the listing projection the handler reads). The handler must restate the stored record for the requested listingId, and the record the flow's ids resolve to must be the record the corpus says those ids name.
Traces: marketplace-discovery-search-listings-and-drill-into-listing#task#2 (GetListing, expected 200 / got 200; 30 diverging keys).

Cause 2 of 3: GetProduct repeats the substitution for the product resolved from that listing.
AWS: Smithy GetProduct (POST /2026-02-05/getProduct, success 200; input productId ProductId @required @length 1..255 @pattern ^[\w\-]+$) returns productId, catalog, productName, manufacturer (SellerInformation), deployedOnAws (DeployedOnAwsStatus enum), shortDescription, longDescription, logoThumbnailUrl (URL @pattern ^https?://.*$), fulfillmentOptionSummaries, categories, highlights (@length ..10), promotionalMedia, resources, sellerEngagements and listingId — all @required; same five modelled errors. Recorded behavior for content: the product restates its own stored record — its categories as taxonomy-identifier/displayName pairs in stored order, its own highlight sentences, its own manufacturer, productName, descriptions, logo URL, resources and seller engagements.
Emulator: 200 with the same substitution as cause 1. `$.categories[0..3]` diverge as WHOLE elements — both categoryId and displayName (expected {'f42ec728-09b3-46d2-956a-8a0cde3f8ee6','Data Integration'}, got {'645edc21-2120-59fd-a2c4-451dfca0161e','Structured Data'}, and likewise for the other three) — so a client cannot rely on either half; `$.highlights[0..2]`, `$.longDescription`, `$.shortDescription`, `$.productName`, `$.manufacturer.displayName`/`.sellerProfileId`, `$.logoThumbnailUrl`, `$.resources[0..3]`, `$.sellerEngagements[0..1]` and `$.purchaseIndicators` all come from the generated row.
Why: a client that drills product detail after a listing gets a second, independently substituted copy of the same record, so the two views agree with each other and with nothing else. A persisted categoryId or manufacturer sellerProfileId read from here names a different entity than the product the client asked about.
Fix: same component as cause 1 — the seeder and the category / highlight / text projections GetProduct shares with GetListing in that crate's state; the handler must restate the stored product the requested productId names.
Traces: marketplace-discovery-search-listings-and-drill-into-listing#task#3 (GetProduct, expected 200 / got 200; 27 diverging keys).

Cause 3 of 3: ListFulfillmentOptions announces the SaaS `fulfillmentUrl` on an authority the request did not reach the emulator on, so the published address dereferences to nothing.
AWS: Smithy ListFulfillmentOptions (POST /2026-02-05/listFulfillmentOptions, success 200; input productId ProductId @required, maxResults @range 1..50 default 25, nextToken @pattern ^[a-zA-Z0-9+/=]+$) returns `fulfillmentOptions` (FulfillmentOptionsList, @required). Its SaaS union member SaasFulfillmentOption declares fulfillmentOptionId / fulfillmentOptionType / fulfillmentOptionDisplayName / quickLaunch (@required), `fulfillmentUrl` (String, documented "The URL of the seller's software registration landing page"), usageInstructions, availableFromTime, and `launchUrl` (URL @length 1..2048 @pattern ^https?://.*$, documented "distinct from fulfillmentUrl, which is the seller's software registration landing page"). The model does not fix the host and on AWS these pages live on the seller's own hosts, so the requirement is not a particular host: it is that `fulfillmentUrl` names a page the buyer can actually dereference. Recorded behavior only for the host itself (the recording's value is a seller-hosted page).
Emulator: 200, and `fulfillmentUrl` is announced as an emulator-local URL of the form `https://<authority>/_aws/marketplace-discovery-saas-fulfillment/<fulfillmentOptionId>/register` whose authority is NOT the one the replayed request reached the emulator at — in this replay the announced authority is a loopback port other than the data listener that accepted the request, and the replay checker classifies the member `resource_not_identified`: the published address identifies no resource. The emulator's own design states this is wrong: src/state.rs documents that every address this service publishes for a client to FETCH is "announced on the address this process answers requests at" (announced_page_base). The defect is that the announced authority drifts from the serving one, not that it is local. Hypothesis: announced_page_base falls back past the request's reached-endpoint parts to an authority/scheme this process is not serving the data plane on.
Why: `fulfillmentUrl` is the one member a buyer-facing client turns into a link or a redirect after subscribing. A client that follows the announced registration page gets a refused connection or a resource that does not exist, so the subscribe-then-register path cannot be exercised end to end even though the emulator does serve that page at its real front door.
Fix: the announced-address resolution this operation's projection uses — announced_page_base in src/state/announced_address.rs and the SaaS page addressing in src/state/saas_fulfillment.rs — must yield the scheme and authority the answering request actually arrived on before it is stamped into fulfillmentUrl/launchUrl.
Traces: marketplace-discovery-search-listings-and-drill-into-listing#task#4 (ListFulfillmentOptions, expected 200 / got 200; keys $.fulfillmentOptions[0] and $.fulfillmentOptions[0].saasFulfillmentOption.fulfillmentUrl, the latter verdict `resource_not_identified`).

Explicitly NOT claimed as requirements anywhere in this issue: the recorded literal ids and hostnames (listing / product / offer / fulfillment-option ids, sellerProfileId values, the CloudFront media host and review-list paths, the seller-hosted fulfillment host), and any clock-derived timestamp such as `availableFromTime` (the recorded 1719446400 vs the emulator's 1793105745 is a per-run clock value). Those differ per environment and per run. The defects are that the detail views answer from a different record than the requested id names — including the identifier/displayName pairs, the associated product+offer resolution and the record's own prose and support resources — and that a published fetchable URL is announced on an authority the emulator is not reached on.
