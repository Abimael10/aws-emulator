# bedrock-agentcore: 2 net-new causes — InvokeHarness streams a fixed "no language model runs" notice instead of the harness turn's answer, and the data-plane authorizer never publishes bedrock-agentcore:namespace so a namespace-conditioned Allow refuses even the namespace it allows

> _Note: this issue was identified against the code base at commit `95ac6b97296b25f638775ef6173e027be717227c`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
InvokeHarness

## Description
Two independent net-new root causes on the bedrock-agentcore data plane in this sweep. Each is numbered below with its own failing check ids; BOTH must be closed before this work item is submitted.

=== Cause 1 of 2: InvokeHarness serves a fixed notice as the assistant turn, so a harness invocation never answers the conversation it was given ===
AWS: Smithy models InvokeHarness as POST /harnesses/invoke with required `harnessArn` (query), `runtimeSessionId` (header X-Amzn-Bedrock-AgentCore-Runtime-Session-Id) and `messages`, optional `model`/`systemPrompt`/`tools`/`skills`/`allowedTools`/`maxIterations`/`maxTokens`, and an output that is the required streaming `stream` member of InvokeHarnessStreamOutput (source: smithy_query query="operation" operation="InvokeHarness" on com-amazonaws-bedrockagentcore-amazonbedrockagentcore.json). The model says nothing about the CONTENT of the assistant text, so for that this is recorded behavior only: a harness configured with a Bedrock model (the recording used the us.amazon.nova-micro-v1:0 cross-region inference profile) runs a server-managed agent loop and the streamed assistant text ANSWERS the prompt — asked to add two operands chosen at request time and reply with only the digits, the streamed text contains the correct sum. The call is HTTP 200 with no stream-level error event in both AWS and the emulator; the divergence is purely the text the emulator serves.
Emulator: the stream is well-formed (messageStart/contentBlockDelta/contentBlockStop/messageStop/metadata, role `assistant`, counted tokens, measured latency) but the single text block is a fixed notice whose template is `No language model runs in this emulator. <modelId> generated no text for this request. The request carried <n> message(s) and <m> input token(s).` — its only variable parts are the configured model id and the two counts; nothing in it derives from the conversation. No inference, no tool use and no iteration of the agent loop happens, so arithmetic (or any other) content asked for in `messages` is never produced. (The model id, message count and token count in a single run are per-run values, not part of the requirement.) Related but NOT covering this: fixed issue 20261029T215145Z-bedrock-agentcore-agentcore-data-plane-invocation-unserved-invokecodeinterpreter-and-invokeharness.md made InvokeHarness reachable at all (it previously answered UnknownService); the call now succeeds, so this is not a refusal left behind by that fix but a new divergence in what the served stream carries.
Why: the whole point of a harness is that the service runs the agent loop and the client consumes the answer. A client that invokes a harness and parses its reply (an answer, a number, a JSON object, a tool result) gets a constant English notice from the emulator, so every agent-orchestration path a client builds on InvokeHarness is untestable against the emulator, and a test that asserts on the content passes only because it asserts nothing.
Fix: the harness invocation's turn composition — the text served must be derived from the request's conversation (the in-process generation/tool-execution path the emulator already owns for its Bedrock inference surface, with the harness's tools/skills/maxIterations applied), not the fixed inference-floor notice; the surrounding frames, counts and stop reason are already correct and need no change.
Traces: bedrock-agentcore.invoke-harness-managed-orchestration-result (assertion: `expected the server-computed sum '<n>' to appear in the model's reply, got 'No language model runs in this emulator. …'`). File/line pointers for the fixer: services/service-com-amazonaws-bedrockagentcore-amazonbedrockagentcore/src/ops/invoke_harness.rs:251-258 (prompt + turn composition) and src/state/harness_invocation.rs:293-327 (`harness_turn`, which delegates to the bedrock-runtime plane's `emulated_completion`).

=== Cause 2 of 2: the data-plane authorizer evaluates every policy with an EMPTY request context, so a bedrock-agentcore:namespace-conditioned Allow grants nothing — ListMemoryRecords refuses even the namespace the policy names ===
AWS: Smithy models ListMemoryRecords as POST /memories/{memoryId}/memoryRecords with optional `namespace` and `namespacePath` (Namespace, @length 1..1024) and models AccessDeniedException (httpError 403) among its errors (source: smithy_query query="operation" operation="ListMemoryRecords"). Recorded behavior: a principal whose only Allow for bedrock-agentcore:ListMemoryRecords on the memory's ARN is conditioned on StringEquals of the service condition key `bedrock-agentcore:namespace` to one namespace CAN list that namespace (HTTP 200, exactly that namespace's records) and is refused 403 AccessDeniedException on a sibling namespace of the same memory, with the fixed sentence `User: <caller principal ARN> is not authorized to perform this operation` (the principal ARN is the request's signing identity — for an assumed role, arn:aws:sts::<account>:assumed-role/<role-name>/<session-name>; nothing else in it varies). Broadening the same condition to StringLike on the parent prefix makes the identical sibling call succeed. So the decision is a function of the request's `namespace` argument: the allowed namespace must be ALLOWED and only the others refused.
Emulator: the authorizer builds its IAM request from the action and the resource alone and passes an empty condition context (services/service-com-amazonaws-bedrockagentcore-amazonbedrockagentcore/src/state/authorization.rs:113 `iam::Request::new(&action, resource, &caller.principals)`; the module docs at lines 73-76 state conditions are not modelled), and the shared evaluator's documented fail-closed rule is that a clause it cannot decide — including a key the request context does not carry — leaves the statement UNDECIDED and an undecided Allow never grants (services/common/src/iam_authorization.rs:57-71). The conditioned Allow therefore grants nothing at all: the restricted principal's read of the namespace its own policy explicitly allows is refused 403 AccessDeniedException too, so the check's positive control never becomes effective, its bounded wait for a non-AccessDenied outcome never satisfies, and the check is killed at the harness wall clock (`Error: Check timed out after 60.0s`) with the later beats (the sibling denial, the independent read, the StringLike restore) unreachable. The failure is now OVER-refusal, the opposite direction from what open issue 20261121T033538Z-bedrock-agentcore-3-net-new-causes-listmemoryrecords-ignores.md recorded for the same check (there the sibling read returned HTTP 200 with the forbidden record); that issue is still open and describes the ignore-the-condition direction, so it does not cover this refusal of the permitted call — and the fix for both is the same missing piece, publishing the key.
Why: namespace scoping is how AgentCore memories are multi-tenanted, and it is now broken in both directions. A client whose production policy scopes bedrock-agentcore:namespace to one actor/session prefix cannot read its OWN namespace against the emulator — every memory-record read under such a role is 403 — so the scoped-credential path is unusable, while a client that drops the condition gets a blanket grant over every namespace of the memory.
Fix: the data-plane authorization gate for the memory-record operations (ListMemoryRecords, and the same key on GetMemoryRecord/RetrieveMemoryRecords/DeleteMemoryRecord) must extract the request's namespace argument into the IAM request context under the key `bedrock-agentcore:namespace` (and declare the key as published so absence is decidable), so StringEquals/StringLike clauses on it are evaluated: allow when a matching Allow exists, refuse 403 AccessDeniedException with AWS's fixed sentence above when none does.
Traces: bedrock-agentcore.namespace-condition-key-blocks-cross-namespace-memory-read. Note for the fixer: the check's bounded propagation polls need more wall clock than the 60s replay budget, so also drive the sequence directly (CreateMemory → BatchCreateMemoryRecords into two sibling namespaces → PutRolePolicy with the StringEquals condition → AssumeRole → ListMemoryRecords on the allowed namespace, then on the sibling).

## Steps to Reproduce
Cause 1 (InvokeHarness turn text):
1. Boot the emulator. Create an IAM execution role, CreateHarness configured with a Bedrock model (e.g. us.amazon.nova-micro-v1:0), wait for the harness to be READY.
2. InvokeHarness(harnessArn=<arn>, runtimeSessionId=<33-100 char id>, messages=[{"role":"user","content":[{"text":"Compute 1234 + 5678. Reply with ONLY the resulting integer digits, no words."}]}]).
3. Drain the event stream: the contentBlockDelta text is the fixed `No language model runs in this emulator. <modelId> generated no text for this request. The request carried N message(s) and M input token(s).` notice instead of a reply containing 6912.

Cause 2 (namespace condition key):
1. CreateMemory, wait for ACTIVE; note its ARN and id.
2. BatchCreateMemoryRecords two records: one with namespaces=['/t/<tenant>/actor/alpha/facts/'], one with namespaces=['/t/<tenant>/actor/beta/facts/']. Confirm an unrestricted ListMemoryRecords(namespacePath='/t/<tenant>/actor/') sees both.
3. CreateRole (trusted by the account root) + PutRolePolicy with a single Allow on bedrock-agentcore:ListMemoryRecords for the memory ARN, Condition {"StringEquals": {"bedrock-agentcore:namespace": "/t/<tenant>/actor/alpha/facts/"}}; AssumeRole and build a bedrock-agentcore client from the temporary credentials.
4. ListMemoryRecords(memoryId, namespace='/t/<tenant>/actor/alpha/facts/') as that principal — observe 403 AccessDeniedException instead of HTTP 200 with alpha's record. The grant never becomes effective, however long you retry.
5. Replace the condition with {"StringLike": {"bedrock-agentcore:namespace": "/t/<tenant>/actor/*"}} and repeat: still refused, confirming no condition clause on this key is ever evaluated and no such Allow ever grants.
