# Listed custom detection rule associations advertise a re-minted identity that no Get resolves

> _Note: this issue was identified against the code base at commit `96b6253dc6ea8319b5f1ad39858d0c023680de77`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Description
This issue bundles 4 distinct net-new replay clusters, all in the guardduty crate and all on ListCustomDetectionRuleAssociations. Fix ALL 4 causes and re-replay every fixture#step named in Traces (and in trace_ids) before submitting. None of the 4 clusters is marked owned by an open issue (owned_by []) and none is blocked by a stub (stub_path "").

The shared fault: the identity an AssociationSummary advertises for an association is not the identity that association is established under, so the id a caller lifts out of a listing is not interchangeable with the id named by the trailing /association/<id> segment of that same summary's own arn nor with the id a following Get/Update/Delete accepts as its AssociationId path label. The id digits, the region, the account and the ruleId in the ARN are per-run values and are NOT the requirement; the requirement is that one association has ONE identity and that every projection of it (create detail, read detail, list summary, ARN suffix) serializes that same identity byte for byte.

Hypothesis for the fixer, because the replay's rendering is ambiguous: the report prints the expected and the actual associationId with the SAME visible hex digits on all four clusters, so the compared difference does not lie in the digits a human reads. Two mechanisms can produce that, and both must be ruled out: (a) the listed identity is a value the create minted afresh rather than the association identity the scenario established, and the list selector (which is resolved from the emulator's own ARN) therefore renders both sides alike while the asserted identity is the recording's; or (b) the summary member is serialized in a form that is not byte-identical to the ARN suffix in the same payload (JSON type, case, or leading/trailing whitespace). Compare the RAW serialized member against the ARN's trailing segment, and against the id the fixture's earlier create reported, rather than by eye.

Several OPEN guardduty issues describe this same fault family but do NOT cover these clusters: the replay reports all four with an empty owner, because the owning issues' replay keys embed a per-run ARN (hence a per-run minted id) and this run minted different ids, so the keys do not join. Treat these clusters as still-open behaviour. The non-covering issues are 20261107T064647Z-guardduty-custom-detection-rule-association-identity-is-not-stable.md (its causes 4-7 name these same four fixture#steps but key on ARNs containing other ids; its causes 1-3 own this run's create/get clusters), 20261107T151807Z-guardduty-listcustomdetectionruleassociations-summaries-report-an-associationid-that-does-not.md, 20261107T235238Z-guardduty-listcustomdetectionruleassociations-summary-reports-an-associationid-that-is-not.md, 20261108T181442Z-guardduty-associationsummary-associationid-is-serialized-in-a-form-that.md, 20261112T052523Z-guardduty-custom-detection-rule-associations-are-listed-under-a.md, 20261112T075616Z-guardduty-listcustomdetectionruleassociations-summaries-report-an-associationid-that-does-not-e1ac75.md and 20261114T175626Z-guardduty-associationsummary-associationid-diverges-byte-for-byte-from-its.md. A fix that makes a listed summary id byte-identical to its own ARN suffix AND equal to the identity the association was created under (so it is accepted verbatim as a Get path label) closes this bundle and that family together.
