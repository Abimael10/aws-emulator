# appsync__dynamodb: 3 net-new causes — a VERSIONED DynamoDB data source never refuses a stale _version (no ConflictUnhandled), AUTOMERGE accepts a stale DeleteItem and writes a tombstone, and concurrent AUTOMERGE merges are not serialized (all stamped the same _version)

> _Note: this issue was identified against the code base at commit `ea39dba1da951c7945754830175526ec44cfb5ae`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
Mutation over an AMAZON_DYNAMODB data source with SyncConfig conflictDetection=VERSION (PutItem/UpdateItem/DeleteItem)

## Description
Three distinct net-new root causes in the AppSync GraphQL data plane's versioned (conflict-detecting) AMAZON_DYNAMODB data-source resolver, all reached through the emulator's own GraphQL endpoint with a data source whose resolver carries syncConfig {conflictDetection: VERSION, conflictHandler: OPTIMISTIC_CONCURRENCY | AUTOMERGE}.

These are net-new relative to the open issue 20261119T104646Z-appsync-dynamodb-3-net-new-causes-a-versioned.md. That issue's Cause 1 was that _version/_lastChangedAt were never stamped at all (every write returned _version: null), and it carries replay keys at the `_version == 1` assertions. The emulator now DOES stamp and increment _version/_lastChangedAt (the failures below report concrete versions 2 and 3), so these three checks now fail strictly further on, at the conflict-handling step, which that issue's keys do not cover. The remaining causes of that issue (the Sync operation, the forged nextToken) are untouched here.

=== Cause 1 of 3: a version mismatch under OPTIMISTIC_CONCURRENCY is not detected — the stale write is applied and no GraphQL error is returned ===
AWS: Smithy: SyncConfig.conflictHandler (ConflictHandlerType, values OPTIMISTIC_CONCURRENCY|LAMBDA|AUTOMERGE|NONE) documents OPTIMISTIC_CONCURRENCY as "Resolve conflicts by rejecting mutations when versions don't match the latest version at the server", with SyncConfig.conflictDetection = VERSION meaning "Detect conflicts based on object versions". Recorded behavior for the wire shape: the refusal is reported INSIDE an HTTP 200 GraphQL response, as exactly one entry in `errors` whose `errorType` is `ConflictUnhandled`, whose `path` is the single refused field (the mutation field name from the query), whose `data` is the CURRENT server item read from live state (so it carries that item's `_version` and its current attribute values), and with `data.<field>` null. The stored row is left untouched. The fixed text here is the errorType token `ConflictUnhandled`; everything else (field name, item attributes, the version integer) is taken from the request and from the emulator's stored item — a particular run's ids/titles/versions are not part of the requirement.
Emulator: the mutation carrying a `_version` that no longer matches the stored item is executed as an ordinary write: HTTP 200 with an EMPTY `errors` array (`AssertionError: expected exactly one GraphQL error, got []`), so no `ConflictUnhandled` entry, no `path`, and no `data` object carrying the live server item. The conflict handler configured on the resolver is never invoked on the version-mismatch path.
Why: a client built on AppSync's conflict-detection/DataStore model treats a `ConflictUnhandled` error, and the server item in `error.data`, as its signal to rebase and retry. Here the stale mutation silently overwrites the server's newer value, so concurrent writers lose data last-writer-wins where AWS refuses the write, and every `if (err.errorType === 'ConflictUnhandled')` retry branch is dead code.
Fix: the AMAZON_DYNAMODB data-source resolver's versioned-write path — the component that applies a resolver's PutItem/UpdateItem request against the table must compare the request document's `_version` against the stored item's `_version` and, on a mismatch, route the write through the resolver's syncConfig.conflictHandler instead of applying it, and the GraphQL error serializer must emit that refusal as a single `ConflictUnhandled` field error carrying the live item in `data`.

=== Cause 2 of 3: AUTOMERGE accepts a stale DeleteItem, soft-deletes the row and writes a tombstone, instead of refusing it ===
AWS: recorded behavior only for the delete path. On a versioned data source with conflictHandler AUTOMERGE, a DeleteItem request whose `_version` is older than the stored item's version CANNOT be merged (a delete has nothing to merge) and is refused: HTTP 200 with exactly one `errors` entry, `errorType` `ConflictUnhandled`, `path` naming the delete field, `data.<field>` null, and the error's `data` holding the live server item (its current `_version` and attribute values). No tombstone is written: the row keeps its pre-delete version and `_deleted` is not set.
Emulator: the stale delete SUCCEEDS. The response is HTTP 200 with no `errors` at all and a populated payload for the delete field — the item comes back soft-deleted with `_deleted: true`, `_lastChangedAt` set and `_version` incremented past the server's version (observed: the item stood at _version 2 and a delete carrying `_version` 1 returned `_version` 3 with `_deleted` true). So a tombstone is written on a request AWS rejects.
Why: an offline/DataStore client that replays a queued delete made against a since-updated item destroys the newer server state instead of being told to reconcile; the row is tombstoned and subsequent delta syncs propagate that deletion to every other client. The absent refusal also means the client never learns the item moved on.
Fix: the AMAZON_DYNAMODB data-source resolver's DeleteItem path under conflict detection — a version mismatch must be handed to the conflict handler (AUTOMERGE refuses it) and must abort the write before the soft-delete/tombstone is applied, with the same single `ConflictUnhandled` field error as Cause 1.
Traces: appsync__dynamodb.deep-appsync-1-appsync-conflict-automerge-stale-delete-rejected-and-no-tombstone-written

=== Cause 3 of 3: concurrent AUTOMERGE merges are not serialized — every merged write is stamped the same _version and each writer's response shows a different partial merge ===
AWS: recorded behavior only. Under AUTOMERGE, several concurrent writers each holding the same stale `_version` all succeed, but each merge is applied against the item as it stands at that moment and each accepted write increments `_version` exactly once, so N merged writes after version V hand out versions V+1 … V+N, each to exactly one writer, and the stored row ends at V+N holding every merged attribute plus the server's existing ones.
Emulator: all three concurrent merged writes report the SAME version — `three merged writes after v2 must be stamped 3, 4 and 5 -- each exactly once; got [3, 3, 3]` — and each writer's response reflects a different, partial view of the item (one response carries all three merged attributes, another only its own and one sibling's, with the remaining attributes null). Each merge is computed from the same base snapshot and stamped V+1 rather than being serialized against the current item, so the version sequence collapses and responses disagree about the item's contents.
Why: a client uses `_version` as the item's identity for its next write and for conflict detection. When concurrent merges all return the same version, two clients hold the same "latest" version for different item contents: the next write from either is accepted against a version that does not describe what is stored, so conflict detection is defeated and merged attributes can be dropped. The divergent per-writer payloads also mean the mutation response is not a readback of committed state.
Fix: the versioned AMAZON_DYNAMODB data-source resolver's AUTOMERGE path — the read-merge-write of an item must be serialized per item (compare-and-set on the stored `_version`) so each accepted merge increments `_version` once and returns the item as committed.

## Evidence
Cause 1 — appsync__dynamodb.appsync-optimistic-concurrency-conflict-returns-server-version-and-data.
Expected: HTTP 200 whose `errors` array holds exactly one entry with `errorType == "ConflictUnhandled"`, `path == [<mutation field>]` and a `data` object that is the live server item (its `_version` equal to the version actually stored, its attributes equal to the stored ones), while the stored row is unchanged. A second refusal after a successful intervening update must report the NEW live version and title, i.e. the payload is read from live state, not a constant.
Actual: `AssertionError: expected exactly one GraphQL error, got []` — the response carried no errors at all, so the stale mutation was applied. The assertions on errorType/path/data were never reached.

Cause 2 — appsync__dynamodb.deep-appsync-1-appsync-conflict-automerge-stale-delete-rejected-and-no-tombstone-written.
Expected: HTTP 200 with exactly one error, `errorType == "ConflictUnhandled"`, `path == ["deletePost"]`, `data.deletePost` null, and the error's `data` carrying the live item at its current version/title; no tombstone written.
Actual: `AssertionError: expected exactly one GraphQL error, got {'data': {'deletePost': {'id': 'post-ac51dfdcce18', 'title': 'v2-1d1bcc1e634d', '_version': 3, '_deleted': True, '_lastChangedAt': 1795333843441}}}` — no errors, the delete committed and tombstoned the row. (The id, title, version number and timestamp are per-run values; the requirement is that the stale delete is refused with a single ConflictUnhandled error and that `_deleted` is not set.)

Cause 3 — appsync__dynamodb.deep-appsync-1-appsync-conflict-automerge-concurrent-stale-writers-all-merge-with-distinct-versions.
Expected: the three concurrent merged writes carry versions 3, 4 and 5, each exactly once (base version 2 + three accepted merges), and the stored row ends at `_version` 5 with all three merged attributes and the server's v2 title.
Actual: `AssertionError: three merged writes after v2 must be stamped 3, 4 and 5 -- each exactly once; got [3, 3, 3] from {'alpha': {..., 'alpha': 'alpha-…', 'beta': 'beta-…', 'gamma': 'gamma-…', '_version': 3}, 'beta': {..., 'alpha': None, 'beta': 'beta-…', 'gamma': None, '_version': 3}, 'gamma': {..., 'alpha': None, 'beta': 'beta-…', 'gamma': 'gamma-…', '_version': 3}}` — one shared version and three disagreeing payloads. (The attribute values shown are per-run; the requirement is one distinct, monotonically increasing version per accepted merge.)

## Steps to Reproduce
1. Create a DynamoDB table with a single STRING hash key `id`, and an AppSync GraphQL API whose AMAZON_DYNAMODB data source points at it through a role allowing the table's writes.
2. Attach unit resolvers whose request mapping templates are version "2018-05-29" documents carrying a top-level `_version` taken from a mutation argument, and whose response template re-raises `$ctx.error` via `$util.error($ctx.error.message, $ctx.error.type, $ctx.result)`. Set syncConfig on them.
3. Cause 1 (syncConfig conflictHandler OPTIMISTIC_CONCURRENCY, conflictDetection VERSION): run a create mutation (PutItem with `_version` 1) so the item exists at version 1, then run the SAME mutation again with `expectedVersion` 1 over the now-existing item. AWS answers HTTP 200 with one `ConflictUnhandled` error whose `data` is the live item; the emulator answers 200 with an empty `errors` array and applies the write.
4. Cause 2 (conflictHandler AUTOMERGE): create the item (version 1), update it with the current version so it reaches version 2, then run the delete mutation passing the STALE version 1. AWS refuses with one `ConflictUnhandled` error on the `deletePost` path and leaves the row un-tombstoned; the emulator returns no errors and comes back with `_deleted: true` and the version bumped.
5. Cause 3 (conflictHandler AUTOMERGE): create the item, move it to version 2 with a current-version write, then fire three concurrent mutations that each set a DIFFERENT attribute while all passing the stale version 1. AWS stamps the three accepted merges 3, 4 and 5 (one each) and the stored row ends at 5 with all three attributes; the emulator stamps all three 3 and each response shows a different partial merge.
6. Re-replay the three checks named in trace_ids to confirm the fix.
