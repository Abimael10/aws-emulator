# An UpdatePolicy AutoScalingRollingUpdate is performed as one atomic swap: the batch pacing MaxBatchSize/MinInstancesInService guarantees is never observable, so no reader ever sees the group dip below its desired capacity during the update

> _Note: this issue was identified against the code base at commit `5b0e08c6133f12b05f514bb54271d0b79fd97b96`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
UpdateStack

## Description
One net-new root cause, grounded in the one failing autoscaling__cloudformation__ec2 check of this run that the replay report marks neither ALREADY FILED nor OWNED (the other entry for this service, deploy-autoscaling-1-replacing-update-swaps-group-failed-signal-replacement-rejected, is OWNED by 20261117T062252Z and was skipped).

Cause 1 of 1: an UpdateStack that changes the LaunchTemplate property of an AWS::AutoScaling::AutoScalingGroup carrying `UpdatePolicy: AutoScalingRollingUpdate` with MaxBatchSize=1, MinInstancesInService=1, MinSuccessfulInstancesPercent=100 and WaitOnResourceSignals over a 3-instance group settles in UPDATE_COMPLETE after what is effectively one atomic swap: a client reading the group throughout the update never observes an intermediate state, so the batch-at-a-time contract the policy exists to provide — at most MaxBatchSize instances out of service at once, never fewer than MinInstancesInService in service, each batch terminated BEFORE its replacement is launched, and each batch gated on its replacements' resource signals — is not observable and therefore not honoured as pacing. Failing check id: autoscaling__cloudformation__ec2.cfn-rolling-update-honours-max-batch-size-then-rolls-back-on-a-failed-signal.

AWS: Smithy (services/service-com-amazonaws-cloudformation-cloudformation-*/smithy-model) models UpdateStack, DescribeStacks/StackStatus (UPDATE_IN_PROGRESS, UPDATE_COMPLETE, UPDATE_ROLLBACK_COMPLETE, …) and SignalResource (StackName, LogicalResourceId, UniqueId @length 1..64, Status in {SUCCESS, FAILURE}); UpdatePolicy is a template attribute and is not in the model, so for the policy's semantics this is recorded behavior only. What AWS does: with AutoScalingRollingUpdate, CloudFormation replaces the group's instances in batches of at most MaxBatchSize, keeping at least MinInstancesInService in service, and for each batch it takes the old instances OUT of service first and then launches the replacements — so the group's InService count DIPS to (DesiredCapacity - MaxBatchSize) for the span of each batch and never surges above DesiredCapacity (this policy, unlike an instance refresh, does not launch before terminating). With WaitOnResourceSignals and MinSuccessfulInstancesPercent=100 the stack holds each batch until its replacements signal, so a 3-instance / MaxBatchSize=1 update is three observable, separately-gated steps. On the modeled surface nothing is refused in this cause: there is no status code or error code to compare, the divergence is in the sequence of states an observer can read from DescribeAutoScalingGroups while the stack reports UPDATE_IN_PROGRESS.

Emulator: the stack reaches UPDATE_COMPLETE and the replacement is really performed, but the whole 3-batch update completes inside roughly one sampling interval. The check samples the group's InService instance ids every 10 s for as long as the stack reports UPDATE_IN_PROGRESS and collected only 2 samples across a 3-batch update — 'AssertionError: only 2 samples were taken across a 3-batch rolling update; at least 9 are needed before the observed minimum in-service count means anything. The update finished faster than expected -- widen the sampling, do not trust this run.' No sample can therefore witness the held dip to DesiredCapacity - MaxBatchSize = 2, and the assertions that follow (observed_floor >= MinInstancesInService, observed_floor == 2, observed_ceiling <= DesiredCapacity) are never evaluated. The emulator does not sequence the batches into states a reader can see: the per-batch terminate-then-launch ordering, the MinInstancesInService floor and the per-batch signal gate are all collapsed into the update's own transaction.

Why: a client relying on AWS's behavior uses AutoScalingRollingUpdate precisely because the replacement is PACED — a load balancer keeps serving from the MinInstancesInService instances it holds back, and a failing revision is caught at the first batch instead of after the whole fleet is gone. Against this emulator the group is swapped wholesale: a client (or a canary, a health check, a deployment gate) that watches the group during the update sees desired capacity before and desired capacity after and nothing in between, so it can neither verify nor rely on the floor the policy promises, and a bad revision takes out the entire fleet in one step with no observable batch boundary at which it could have been stopped. Every behavior that can only be shown by COMPLETING a paced update goes unexercised, including the negative leg of this check (replacements that signal FAILURE under MinSuccessfulInstancesPercent=100 must cancel the update, drive the stack to UPDATE_ROLLBACK_COMPLETE and restore the group to the previous launch template version with its SUCCESS-signalling UserData).

Fix: the UpdatePolicy.AutoScalingRollingUpdate path of the AWS::AutoScaling::AutoScalingGroup resource handler in the CloudFormation provisioner, together with the group-instance replacement pacing it drives in the autoscaling crate (services/service-com-amazonaws-autoscaling-autoscaling-2011-01-01/src/state.rs — replace_group_instance and the due-instant/materialize_due machinery, whose replacement span INSTANCE_REFRESH_REPLACEMENT is the existing precedent for a paced, reader-visible replacement). The update must advance one batch at a time with each batch's intermediate state readable while the stack reports UPDATE_IN_PROGRESS: at most MaxBatchSize instances taken out of service at once, the old instances removed before their replacements are launched (so the InService count dips to DesiredCapacity - MaxBatchSize and never exceeds DesiredCapacity), never fewer than MinInstancesInService in service, and the next batch started only once the current batch's replacements have satisfied MinSuccessfulInstancesPercent via SignalResource. Having made the pacing observable, the fixer must also confirm the tail this check has never reached: UPDATE_COMPLETE with every generation-1 instance replaced and the group pinned to the new launch template version, every post-update instance 'running' at EC2, and the FAILURE-signal leg ending in UPDATE_ROLLBACK_COMPLETE with the group restored to the prior launch template version.

## Steps to Reproduce

1. CreateStack a template whose AWS::AutoScaling::AutoScalingGroup has DesiredCapacity=3, a launch template whose UserData calls `aws cloudformation signal-resource --stack-name <stack> --logical-resource-id AutoScalingGroup --unique-id <instance-id> --status SUCCESS`, a CreationPolicy.ResourceSignal requiring 3 signals, and `UpdatePolicy: AutoScalingRollingUpdate: {MaxBatchSize: 1, MinInstancesInService: 1, MinSuccessfulInstancesPercent: 100, WaitOnResourceSignals: true}`. Wait for CREATE_COMPLETE and record the group's 3 InService instance ids and its LaunchTemplate version.
2. UpdateStack with a parameter change that rewrites the launch template's UserData (a new launch template version, so the group's LaunchTemplate property changes).
3. While the stack reports UPDATE_IN_PROGRESS, poll autoscaling:DescribeAutoScalingGroups(AutoScalingGroupNames=[<group>]) every 10 s and record the number of instances at LifecycleState 'InService'.
   Observed: the update is terminal after about one interval (2 samples for a 3-batch update); no sample reports fewer than 3 InService instances, so no batch boundary is observable.
   Expected: the update spans three separately-gated batches, each observable — the InService count dips to exactly DesiredCapacity - MaxBatchSize = 2 while a batch is held, never falls below MinInstancesInService = 1, and never exceeds DesiredCapacity = 3; each batch advances only after its replacement signals SUCCESS.
4. Confirm the update did the work regardless: the group must end with 3 InService instances, none of them from the pre-update set, pinned to the new launch template version, each 'running' at EC2.
5. UpdateStack once more with UserData that signals FAILURE. Expected: the update is cancelled and the stack ends in UPDATE_ROLLBACK_COMPLETE with the group restored to the previous launch template version (whose UserData is the SUCCESS-signalling one); UPDATE_COMPLETE here means the FAILURE signal was ignored.
6. Re-replay the check in trace_ids.
