The model fixes NO rate value, no row membership and no row order, so for the card's content this is RECORDED BEHAVIOR ONLY. The recording answers HTTP 200 with a 32-row card for one plan in which (a) the card prices MORE THAN ONE usage type per instance type — rows carry usageType 'UnusedBox:<instanceType>' alongside 'BoxUsage:<instanceType>' (the unused-capacity line item of the same instance type); (b) the platform rows cover usage-operation codes in forms the crate does not hold at all, including a ':box'-suffixed code and the HA + database-edition combinations (recorded rows at indices 3, 4, 5 carry operation 'RunInstances:1014' with productDescription 'Red Hat Enterprise Linux with HA and SQL Server Standard', operation 'RunInstances:0102:box' with 'Windows with SQL Server Enterprise', and operation 'RunInstances:0010' with a Red Hat Enterprise platform); (c) the rows arrive in the CATALOG's own order, which is not a function of the platform's licence price. The requirement is the general one: the card is SERVED from a stored per-combination rate catalog — each row's usageType, operation, productDescription, rate and the row's POSITION all taken from the stored entry — so the row at index N is the catalog's Nth entry and a caller paging or joining positionally lands on the line item the catalog put there. The particular codes, platform names, rates and instance type in the recording are catalog values filling that template, not the requirement itself.

Emulator: HTTP 200 (status matches, so nothing signals the shift) but 29 of the 32 compared positions diverge — replay reports $.searchResults[3] through $.searchResults[31] all 'missing'. At index 3 the recording has usageType 'UnusedBox:m5.large' / operation 'RunInstances:1014' / productDescription 'Red Hat Enterprise Linux with HA and SQL Server Standard' / rate '0.61'; the emulator answers usageType 'BoxUsage:m5.large' / operation 'RunInstances:0100' / 'Linux with SQL Server Enterprise' / rate '1.991'. At index 4 the recording has operation 'RunInstances:0102:box' / 'Windows with SQL Server Enterprise' / rate '0.066'; the emulator answers operation 'RunInstances:0006' / 'Windows with SQL Server Standard' / rate '0.638'. Two structural departures explain the whole tail: the catalog mints exactly ONE usage type per instance type — src/state.rs build_rate_line_items pushes format!("BoxUsage:{instance_type}") and nothing else, so no 'UnusedBox:*' row exists anywhere in the card — and the platform rows are reordered at request time by price: src/state.rs ec2_platforms_in_card_order() takes EC2_PLATFORMS (19 rows, each a (productDescription, operation, licence-uplift) triple whose licence column is COMPOSED from per-vCPU uplift constants) and sorts it by Reverse(licence), i.e. dearest platform first, while the operation codes themselves are limited to the forms that table spells. src/ops/describe_savings_plan_rates.rs handle() then walks crate::state::rate_line_items() in that generated order through page_window and projects each row with project(). Hypothesis: because both the row membership and the row order are derived (one usage type per instance type, platforms sorted by a computed licence), no index past the first few can line up with the stored card AWS serves, independent of whether any individual row's rate is right.

Why: DescribeSavingsPlanRates IS the price lookup for a purchased commitment. A client that walks the card — or pages it and joins row N to a usage line item from its bill — lines up against a different platform, and against a different USAGE TYPE: it reads a 'BoxUsage' price where AWS reports the 'UnusedBox' line item, so unused-capacity usage is priced as running capacity. Whole classes of line item ('UnusedBox:*', the HA and ':box' platform codes) can never be found at all, including via the operation/usageType filters, which match against the same generated rows; and because the answer is 200 with a plausibly shaped 32-row body, nothing tells the client the card is not the service's.

Fix: the DescribeSavingsPlanRates handler's catalog source (services/service-com-amazonaws-savingsplans-awssavingsplan/src/ops/describe_savings_plan_rates.rs handle/project) and the rate catalog it projects from in src/state.rs (build_rate_line_items, EC2_PLATFORMS, ec2_platforms_in_card_order). Rows must come from a STORED per-combination catalog keyed by serviceCode/usageType/operation/productDescription/region/tenancy/instanceType — covering every usage type the card prices for an instance type, not 'BoxUsage' alone, and every usage-operation code the platform catalog carries — emitted in that catalog's own stored order rather than in an order computed from a licence column.
