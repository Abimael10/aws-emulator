# codedeploy: the minimumHealthyHosts concurrency check still cannot start — a running EC2 instance never becomes an Online SSM managed node, so no Server-platform deployment is ever paced (1 cause)

> _Note: this issue was identified against the code base at commit `f6d8f01946911e76d57d5db06ea3a96a4efb6135`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
CreateDeployment

## Description
Cause 1 of 1: codedeploy.minimum-healthy-hosts-bounds-observed-concurrent-unavailability — the only behavioral check that measures a custom deployment config's minimumHealthyHosts bound as OBSERVABLE concurrency over a real Server-platform (EC2) fleet — makes no progress at all and is cut off by the harness cap ("Error: Check timed out after 60.0s", no assertion diagnostic). The check launches a 2-host tagged t3.micro fleet with an SSM-capable instance profile, then blocks in its fleet-readiness gate (`_wait_fleet_ready`), which polls ssm:DescribeInstanceInformation(Filters=[{Key:'InstanceIds',Values:[<ids>]}]) for PingStatus 'Online' on a 600 s budget and then runs `systemctl is-active codedeploy-agent` via ssm:SendCommand/GetCommandInvocation on each host. Because the readiness list stays empty, the gate spins rather than failing fast, and nothing downstream is ever reached: CreateDeploymentConfig, the two CreateDeployment legs, ListDeploymentTargets/BatchGetDeploymentTargets sampling, GetDeployment's deploymentOverview and the createTime→completeTime comparison are all ungraded.

AWS: a running EC2 instance whose instance profile grants SSM managed-node permissions registers itself as a Systems Manager managed node within a minute or two, after which DescribeInstanceInformation returns one InstanceInformation entry for that instance id (ssm Smithy: InstanceInformation.InstanceId pattern ^(^i-(\w{8}|\w{17})$)|(^mi-\w{17}$)$, InstanceInformation.PingStatus enum, documented "Connection status of SSM Agent") with PingStatus 'Online', and SendCommand/GetCommandInvocation can then run in-guest commands on that node (an invocation leaves Pending/InProgress and reaches Success with StandardOutputContent). On such a host, CodeDeploy's Server compute platform honours the deployment config: codedeploy Smithy MinimumHealthyHosts.type = HOST_COUNT | FLEET_PERCENT with MinimumHealthyHosts.value, documented as "HOST_COUNT: The minimum number of healthy instances as an absolute value" and, in the model's own example, "In an example of nine instances, if a HOST_COUNT of six is specified, deploy to up to three instances at a time" — i.e. at most (fleet size − value) instances are out of service at any one instant. So an in-place rolling deployment shows an InProgress window bounded by that arithmetic in ListDeploymentTargets/BatchGetDeploymentTargets, a GetDeployment deploymentOverview whose Pending+InProgress+Succeeded+Failed+Skipped (codedeploy Smithy DeploymentOverview, all InstanceCount) partitions the fleet at every instant, and a createTime→completeTime span strictly longer than the same revision deployed through CodeDeployDefault.AllAtOnce over the same hosts.

Emulator: the launched instances are never cross-registered as SSM managed nodes — DescribeInstanceInformation's InstanceInformationList never reports the ids, so no PingStatus is ever produced and no in-guest command plane exists for them. The check is cut off inside that poll at the 60 s cap, having issued no codedeploy operation under test. Hypothesis: a RunInstances-created instance is modelled only in EC2 state and never projected into the SSM managed-node inventory that backs DescribeInstanceInformation/SendCommand, so the Server-platform deployment path has no host to drive and minimumHealthyHosts pacing is unreachable.

Why: a client cannot observe minimumHealthyHosts at all on this emulator. The entire purpose of a custom deployment config — bounding how many instances a rolling in-place deployment takes out of service at once — is unobservable, and the blocking symptom is a silently empty list rather than an error, so a client's own readiness poll hangs to its own deadline instead of failing with a diagnosable response.

Related open issues that do NOT cover this check (the replay report did not mark it owned by any of them, so its replay key is not carried): 20261110T134745Z-codedeploy-the-minimumhealthyhosts-concurrency-check-cannot-start-the.md names this same check but its recorded Issue-Key (`_wait_fleet_ready#12|Timeout|time.sleep(5)`) no longer matches the current failure, which now arrives as a bare 60 s cutoff with no frame; 20261107T094623Z-codedeploy-no-server-platform-ec2-agent-deployment-check.md, 20261114T130417Z, 20261114T164802Z, 20261114T202732Z, 20261115T031454Z and 20261115T085328Z report the same family of host-readiness failures for OTHER Server-platform checks. This check must be re-replayed on its own to confirm a fix.

Fix: the EC2 instance lifecycle must cross-register a running instance into the SSM managed-node state behind DescribeInstanceInformation (an entry with PingStatus 'Online' shortly after the instance reaches 'running'), and the SSM in-guest command plane (SendCommand/GetCommandInvocation) must act on that node instead of leaving invocations Pending. On the CodeDeploy side, the Server-platform deployment execution path — the instance-target lifecycle driver — must then pace instance targets according to the deployment group's deployment config minimumHealthyHosts and report the per-instant buckets in GetDeployment's deploymentOverview, with createTime/completeTime reflecting the paced wall time.

Traces: codedeploy.minimum-healthy-hosts-bounds-observed-concurrent-unavailability (timed out inside `_wait_fleet_ready`, before CreateDeploymentConfig/CreateDeployment are graded).

## Evidence
Expected (AWS): after ec2:RunInstances of two tagged t3.micro hosts with an SSM-capable instance profile, ssm:DescribeInstanceInformation(Filters=[{Key:'InstanceIds',Values:[<the two ids>]}]) returns one InstanceInformation per instance with PingStatus 'Online'; ssm:SendCommand(AWS-RunShellScript, 'systemctl is-active codedeploy-agent') yields an invocation that leaves Pending/InProgress with Status 'Success' and StandardOutputContent 'active'. Then a Server-platform CreateDeployment through a group using a HOST_COUNT=1 config over the 2-host fleet shows at most (2 − 1) = 1 instance InProgress at any sampled instant in BatchGetDeploymentTargets, a deploymentOverview whose Pending+InProgress+Succeeded+Failed+Skipped equals 2 at every sample, a terminal status 'Succeeded', and completeTime − createTime strictly greater than the same revision deployed with CodeDeployDefault.AllAtOnce over the same hosts (which in turn must show both hosts InProgress at once).

Actual (emulator): 'Error: Check timed out after 60.0s' with no assertion diagnostic — the run is cut off inside the fleet-readiness gate. InstanceInformationList never contains the launched instance ids, so PingStatus is never reported, the subsequent `systemctl is-active codedeploy-agent` leg is never reached, and no CodeDeploy operation under test (CreateDeploymentConfig / CreateDeployment / ListDeploymentTargets / BatchGetDeploymentTargets / GetDeployment) is ever issued; the minimumHealthyHosts bound is therefore never exercised. Instance ids, host names, bucket names and per-run timings are per-run values and are not part of the requirement; the requirement is that a running instance becomes an Online managed node at all, that in-guest commands complete on it, and that a HOST_COUNT config bounds concurrently out-of-service instances to (fleet size − value).

## Steps to Reproduce
1. Create a VPC with a public subnet and an internet gateway; create an IAM role with SSM managed-node permissions (AmazonSSMManagedInstanceCore) plus s3:GetObject/ListBucket on a revision bucket, and an instance profile holding it.
2. Upload a zip revision to S3 whose appspec.yml installs payload.txt to /opt/sim2real and whose BeforeInstall hook sleeps ~45 s.
3. ec2:RunInstances two t3.micro instances in that subnet with the instance profile and a tag the deployment group will filter on (KEY_AND_VALUE); wait for state 'running'.
4. Poll ssm:DescribeInstanceInformation(Filters=[{Key:'InstanceIds',Values:[<both ids>]}]) — observe InstanceInformationList stays empty indefinitely, so no PingStatus 'Online' is ever reported and the readiness gate never returns (the check is cut off at the 60 s harness cap).
5. (Blocked by step 4, and what the check grades) codedeploy:CreateDeploymentConfig(computePlatform='Server', minimumHealthyHosts={type:'HOST_COUNT', value:1}); create one deployment group using it and one using CodeDeployDefault.AllAtOnce over the same ec2TagFilters; CreateDeployment the same revision through each with fileExistsBehavior='OVERWRITE'; sample BatchGetDeploymentTargets every 3 s plus GetDeployment's deploymentOverview, and compare completeTime − createTime across the two legs.
