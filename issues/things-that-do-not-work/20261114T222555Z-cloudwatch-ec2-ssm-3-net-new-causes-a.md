# cloudwatch__ec2__ssm: 3 net-new causes — a managed node's guest has no CloudWatch agent package, an attached EBS volume never appears as a block device in it, and IMDS answers nothing

> _Note: this issue was identified against the code base at commit `fa5a827558c7852c4bea0e628f9a7809957676ef`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
SendCommand

## Description
These seven checks use an SSM managed node as their observation point: each one sends AWS-RunShellScript to the instance and reads markers the guest echoes. The instance now DOES become a managed node and the invocation now DOES run and is reported Status='Success' with ResponseCode 0 (Smithy: ssm GetCommandInvocation -> Status, ResponseCode default 0, StandardOutputContent), so each check reaches its own in-guest assertion and fails there. Three distinct capabilities the guest must have are missing. Related open issues describe the same family for a DIFFERENT service heading and different programs and do not cover these: 20261115T000000Z-ec2-ssm-a-managed-nodes-guest-has-no-network-programs.md (ping/tracepath/listener/rpm under `ec2__ssm`), 20261107T064927Z-cloudwatch-ec2-ssm-the-ssm-installed-cloudwatch-agent.md and 20261110T160612Z-cloudwatch-ec2-ssm-the-ssm-installed-cloudwatch-agent-8d3e9c.md (both filed when these checks timed out at the agent-online/metric poll rather than failing on the markers below), and 20261109T142303Z-cloudwatch-ec2-ssm-an-ec2-instance-launched-with-the-amazonssmmanagedinstancecore-profile.md (the managed-node gate, now closed).

Cause 1 of 3: the guest has no package database and no amazon-cloudwatch-agent, so the SSM-installed CloudWatch agent does not exist and publishes nothing.
AWS:      recorded/documented behavior only — the CloudWatch agent is not a Smithy shape. On a managed AL2023 node, an AWS-RunShellScript invocation that installs the agent makes `rpm -q amazon-cloudwatch-agent` print `amazon-cloudwatch-agent-<version>.<arch>`, leaves `/opt/aws/amazon-cloudwatch-agent/bin/amazon-cloudwatch-agent-ctl` on disk and a systemd unit that reports its state, and once started with the fetched config the agent opens the configured StatsD UDP listener (observable in /proc/net/udp) and publishes exactly the configured series — the StatsD counter it receives, mem_used_percent, disk_used_percent — into the configured namespace with the configured dimensions (InstanceId resolved from ${aws:InstanceId}); a measurement NOT named in the config never appears, and nothing is published while the agent is stopped.
Emulator: the invocation is reported Success, but every agent marker the guest echoes is EMPTY — `CWAGENT-RPM `, `CWAGENT-INSTALL-TAIL `, `CWAGENT-FETCH-TAIL `, `CWAGENT-SYSTEMD `, `CWAGENT-CTL `, `CWAGENT-GUEST-MEM `, `CWAGENT-DF-BEFORE `, `CWAGENT-AVAIL-MB ` — and the guest has no /proc/net/udp at all (`cat: /proc/net/udp: No such file or directory`, likewise udp6), so the listener probe is blind. The checks fail at `assert rpm is not None and rpm.startswith("amazon-cloudwatch-agent-")` with 'the guest must report the installed agent package, got \'\''. Consequently no custom-namespace datapoint is ever published either.
Why:      guest-sourced telemetry (memory, disk, application StatsD counters) has no API that can derive it; with none of it arriving, every CloudWatch-agent deployment against the emulator is silently inert and alarms over mem_used_percent/disk_used_percent/custom counters stay INSUFFICIENT_DATA forever, while the install itself reports success.
Fix:      the guest-session environment the SSM Run Command executes in (the posix shell session's EnvironmentPrograms and the image's package database) must provide a queryable package database and an installable amazon-cloudwatch-agent whose ctl/unit, StatsD listener and configured-series publication into the cloudwatch metric store are real, rather than per-check synthesized output.
Traces:   cloudwatch__ec2__ssm.dcwagent-custom-statsd-value-and-guest-only-memory-metric-reach-cloudwatch, cloudwatch__ec2__ssm.dcwagent-disk-used-percent-tracks-bytes-written-in-guest-while-an-unconfigured-metric-never-appears, cloudwatch__ec2__ssm.dcwagent-statsd-value-blocked-while-the-agent-is-not-running-then-arrives-once-started.

Cause 2 of 3: a volume the control plane reports attached never appears as a block device inside the guest, so no byte can be written to it and no AWS/EBS series can follow it.
AWS:      Smithy: ec2 AttachVolume(Device, InstanceId, VolumeId required) -> VolumeAttachment{VolumeId, InstanceId, Device, State, AttachTime}. AWS documents that on Nitro instances an attached EBS volume is exposed as an NVMe device whose serial is the volume id with its hyphens removed, reachable through the stable symlink /dev/disk/by-id/nvme-Amazon_Elastic_Block_Store_<volume id without hyphens>; `readlink -f` on it names the real device and `lsblk -dno SERIAL` on that device prints that serial, so a guest can address exactly the intended volume. Writes through it land on the volume (a read-back of the written range equals the payload) and drive the AWS/EBS series — VolumeWriteBytes/VolumeWriteOps, VolumeReadBytes/VolumeReadOps, VolumeConsumedReadWriteOps for io1/io2 only — under exactly the {VolumeId} dimension, for the attached volume only, and the series follows the volume when it is detached and re-attached to another instance.
Emulator: AttachVolume succeeds and DescribeVolumes reports Attachments[0].InstanceId == the instance, but in the guest the device never materializes: the script's 60-second `[ -e /dev/disk/by-id/nvme-Amazon_Elastic_Block_Store_<serial> ]` wait expires and both `EBS-DEV ` (readlink -f) and `EBS-SERIAL ` (lsblk -dno SERIAL) come back empty, while the invocation is still reported Success with ResponseCode 0. The checks fail at `assert _marker(out, "EBS-SERIAL") == serial` — "the guest device behind /dev/disk/by-id/nvme-Amazon_Elastic_Block_Store_<serial> reports serial '', not '<serial>' -- the bytes would land on some other volume".
Why:      a client cannot do guest I/O against an attached volume at all, so nothing can verify which volume bytes landed on, no AWS/EBS telemetry can be grounded in real traffic, and the attach/detach boundary (series only while attached, series following the volume across a move) is unobservable. A success-reported attach that the guest cannot see is worse than a refusal: scripts proceed and silently write nowhere.
Fix:      the EC2 attachment state must surface in the guest session as a block device — the /dev/disk/by-id/nvme-Amazon_Elastic_Block_Store_<serial> node and its backing device with the volume id as its NVMe serial — and guest writes/reads through it must mutate that volume's content and feed the AWS/EBS metric series in the cloudwatch metric store.
Traces:   cloudwatch__ec2__ssm.obs-ec2-2-ebs-consumed-iops-published-for-io2-and-withheld-from-a-gp3-written-in-the-same-instant, cloudwatch__ec2__ssm.obs-ec2-2-ebs-reads-and-writes-land-on-separate-series-under-exactly-the-volume-id-dimension, cloudwatch__ec2__ssm.obs-ec2-2-ebs-write-telemetry-published-only-while-attached.

Cause 3 of 3: the instance metadata service is not served inside the guest, so the guest cannot learn its own instance id.
AWS:      recorded/documented behavior only. IMDSv2 inside an instance: `PUT http://169.254.169.254/latest/api/token` with header X-aws-ec2-metadata-token-ttl-seconds returns a session token, and `GET http://169.254.169.254/latest/meta-data/instance-id` with X-aws-ec2-metadata-token returns that instance's own id (i-...). This is how a guest, an agent or an in-guest SDK identifies the host it runs on.
Emulator: both calls return nothing — the token request and the instance-id request yield empty output, so `EBS-IID ` is empty (and `CWAGENT-IID ` is empty in the agent checks above), while the invocation is reported Success. The check fails at `assert _marker(out, "EBS-IID") == instance_id` — "the guest that ran the write is '', not '<the instance id>'".
Why:      nothing running in the guest can identify its host, so the CloudWatch agent's ${aws:InstanceId} dimension, in-guest SDK region/credential resolution and any per-host tagging break, and a check cannot even confirm which instance performed an action.
Fix:      the guest session must serve the link-local IMDS endpoint (169.254.169.254) for the instance it belongs to — the IMDSv2 token exchange and at minimum the identity paths (instance-id, and the rest of /latest/meta-data derived from that instance's EC2 state).
Traces:   cloudwatch__ec2__ssm.obs-ec2-2-ebs-write-series-follows-the-volume-across-a-move-to-a-second-instance (and the empty CWAGENT-IID marker in all three dcwagent checks).

## Evidence
Cause 1 — expected: `rpm -q amazon-cloudwatch-agent` prints `amazon-cloudwatch-agent-<version>.<arch>` after the SSM install, the ctl binary and systemd unit report state, /proc/net/udp shows the StatsD listener, and the configured namespace receives the StatsD counter, mem_used_percent and disk_used_percent (and nothing not configured).
Actual: `AssertionError: the guest must report the installed agent package, got ''; stdout was '...\nCWAGENT-RPM \nCWAGENT-INSTALL-TAIL \nCWAGENT-FETCH-TAIL \nCWAGENT-SYSTEMD \nCWAGENT-CTL \ncat: /proc/net/udp: No such file or directory\ncat: /proc/net/udp6: No such file or directory\nCWAGENT-LISTEN \nCWAGENT-IID \nCWAGENT-SENT 3625\nCWAGENT-GUEST-MEM \n'` — only the markers the shell itself can produce (the base64 config echo, the bytes the StatsD send wrote) are non-empty.

Cause 2 — expected: within 60 s of AttachVolume the guest holds /dev/disk/by-id/nvme-Amazon_Elastic_Block_Store_<vol id without hyphens>, `readlink -f` names the device and `lsblk -dno SERIAL` prints that serial, and dd with oflag=direct conv=fsync writes the payload (read-back sha256 equals payload sha256).
Actual: `AssertionError: the guest device behind /dev/disk/by-id/nvme-Amazon_Elastic_Block_Store_vol000000000000000ac reports serial '', not 'vol000000000000000ac' -- the bytes would land on some other volume; stdout='EBS-DEV \nEBS-SERIAL \nEBS-T0 \nEBS-DD \nEBS-T1 \nEBS-READBACK \nEBS-PAYLOAD \n'` (and the same assertion from the two sibling checks), with the invocation still Status='Success'.

Cause 3 — expected: the IMDSv2 token PUT returns a token and the instance-id GET returns the i-... id of the instance that ran the command.
Actual: `AssertionError: the guest that ran the write is '', not 'i-...'` — EBS-IID is empty; CWAGENT-IID is likewise empty in all three agent checks.

## Steps to Reproduce
Common setup: create an IAM role/instance profile carrying arn:aws:iam::aws:policy/AmazonSSMManagedInstanceCore (plus arn:aws:iam::aws:policy/CloudWatchAgentServerPolicy for cause 1), RunInstances a t3.micro from the AL2023 AMI named by SSM parameter /aws/service/ami-amazon-linux-latest/al2023-ami-kernel-default-x86_64, and poll ssm DescribeInstanceInformation until PingStatus == 'Online' (this now settles).

Cause 1: ssm SendCommand AWS-RunShellScript with commands that install the agent, write a config declaring a statsd input and the mem/disk measurements, fetch it with /opt/aws/amazon-cloudwatch-agent/bin/amazon-cloudwatch-agent-ctl, then `echo "CWAGENT-RPM $(rpm -q amazon-cloudwatch-agent)"`, `systemctl is-active amazon-cloudwatch-agent`, and `cat /proc/net/udp`. Read GetCommandInvocation: Status is 'Success' but every marker is empty and /proc/net/udp does not exist; GetMetricStatistics over the configured namespace returns no datapoint.

Cause 2: ec2 CreateVolume + AttachVolume to the instance, confirm DescribeVolumes reports the attachment, then SendCommand a script that waits up to 60 s for /dev/disk/by-id/nvme-Amazon_Elastic_Block_Store_<volume id without hyphens>, echoes `readlink -f` of it and `lsblk -dno SERIAL`, and dd's a few MiB to it with oflag=direct conv=fsync. The wait expires, both markers are empty, and the invocation is still Success.

Cause 3: SendCommand a script that does `TOK=$(curl -s -m 10 -X PUT http://169.254.169.254/latest/api/token -H 'X-aws-ec2-metadata-token-ttl-seconds: 300')` then `curl -s -m 10 -H "X-aws-ec2-metadata-token: $TOK" http://169.254.169.254/latest/meta-data/instance-id`. Expected: the instance's own i-... id. Actual: empty output.
