# batch: a DISABLED compute environment's withholding and its release on re-ENABLE are unobservable — the scenario reaches no verdict because jobs are never placed or run (1 cause)

> _Note: this issue was identified against the code base at commit `56ffd506de18ea98615974ecd6d480d9043186a0`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
UpdateComputeEnvironment

## Description
One net-new root cause in the AWS Batch scheduler/job data plane, grounded in the single batch check the suite left unowned on this replay.

Related open issues that do NOT cover this check (neither carries its replay key; the suite reports it as unowned): 20261107T210820Z-batch-the-job-data-plane-never-executes-a.md, 20261104T041055Z-batch-array-jobs-unimplemented-managed-ces-have-no.md, 20261121T005755Z-batch-2-net-new-causes-getjobqueuesnapshot-reports-no.md, 20261119T015949Z-batch-2-net-new-causes-timeout-attemptdurationseconds-is.md. They are named here only so a fixer can see the adjacency; this check's behaviour — the state-gated placement differential and the release of an already-submitted job on re-ENABLE — is filed by this issue.

Cause 1 of 1: the compute environment's `state` does not gate placement and a submitted job is never placed or run, so neither the withheld leg (a job whose only compute environment is DISABLED staying in RUNNABLE with no attempt) nor the released leg (that same job, without resubmission, being placed and reaching SUCCEEDED after UpdateComputeEnvironment moves the environment back to ENABLED) can be observed at all. Failing check id: batch.compute-environment-disabled-withholds-placement-until-reenabled.
AWS: Smithy (com.amazonaws.batch): CEState enumerates ENABLED | DISABLED; ComputeEnvironmentDetail.state is documented "If the state is ENABLED, then the Batch scheduler can attempt to place jobs from an associated job queue on the compute resources within the environment... If the state is DISABLED, then the Batch scheduler doesn't attempt to place jobs within the environment. Jobs in a STARTING or RUNNING state continue to progress normally." `state` and `status` are independent members: a DISABLED compute environment still reports status VALID. JobStatus enumerates SUBMITTED, PENDING, RUNNABLE, STARTING, RUNNING, SUCCEEDED, FAILED; AttemptDetail.startedAt is "the Unix timestamp (in milliseconds) for when the attempt was started (when the attempt transitioned from the STARTING state to the RUNNING state)" and stoppedAt the transition "from the RUNNING state to a terminal state". SubmitJob is POST /v1/submitjob (200, jobId/jobArn/jobName) and UpdateComputeEnvironment is POST /v1/updatecomputeenvironment (200, computeEnvironmentName/computeEnvironmentArn), each with ClientException (400) / ServerException (500). So on AWS: a job submitted to an ENABLED, VALID queue whose only compute environment is DISABLED sits in RUNNABLE indefinitely — `attempts` stays empty and JobDetail has no `startedAt` — while the identical job on an identical ENABLED twin is placed (DescribeJobs reports STARTING/RUNNING with container.taskArn naming a real ECS task) and reaches SUCCEEDED; the moment UpdateComputeEnvironment(state="ENABLED") is applied to the first environment, the already-submitted job is released with no resubmission, records exactly one attempt whose container names its ECS task, gains a startedAt no earlier than the control's stoppedAt, and ends SUCCEEDED. Recorded behavior additionally shows CreateComputeEnvironment refusing state="DISABLED" at create ("Compute Environment must be created in ENABLED state."), which is why the DISABLED environment is created ENABLED and then updated.
Emulator: the check reaches no verdict. The suite reports "Error: Check timed out after 60.0s" with no assertion having been evaluated — the scenario is still blocked in its data-plane phase (the positive control's placement observation, i.e. DescribeJobs reporting STARTING/RUNNING with container.taskArn, followed by the calibrated absence window over the withheld job and the post-re-ENABLE terminal poll). None of the three observables of the withheld leg (status RUNNABLE, empty `attempts`, absent `startedAt`), the control leg (taskArn at placement, SUCCEEDED terminal), or the release leg (exactly one attempt, a taskArn, a startedAt >= the control's stoppedAt, SUCCEEDED) is ever produced, even though the check's own deadlines are generous (compute environment 300 s, job 900 s).
Why: a client cannot use the compute environment's state as a scheduling control on this emulator. Draining an environment by disabling it, and then resuming the queued work by re-enabling it, is the standard Batch operational lever; here the state member round-trips as data but has no scheduling effect that is ever observable, and because jobs are never placed or run the "released" job never becomes SUCCEEDED and never records the attempt a client reads taskArn, startedAt and stoppedAt from. Any workflow that submits work against a disabled environment and waits for it after re-enabling blocks forever or reads a status that never changes.
Fix: the Batch scheduler/placement component — the dispatcher that moves a RUNNABLE job onto its queue's associated compute environments must consult each environment's `state` and place only on ENABLED ones, must re-evaluate already-queued RUNNABLE jobs when UpdateComputeEnvironment flips a referenced environment from DISABLED to ENABLED, and the job data-plane runner must then actually execute the container and record the attempt (container.taskArn, startedAt, stoppedAt) and the SUCCEEDED/FAILED terminal status; UpdateComputeEnvironment's handler must persist the state change and keep `status` VALID independently of `state`.
Traces: batch.compute-environment-disabled-withholds-placement-until-reenabled.

## Evidence
Expected (AWS): two identical MANAGED/FARGATE compute environments, one ENABLED and one DISABLED (both status VALID), each behind its own ENABLED VALID job queue, with the same FARGATE container job definition.
  (a) SubmitJob on the DISABLED environment's queue -> DescribeJobs repeatedly returns status 'RUNNABLE', `attempts` empty, no `startedAt` member, for the whole observation window; DescribeComputeEnvironments still reports that environment state 'DISABLED', status 'VALID'.
  (b) SubmitJob on the ENABLED twin's queue -> DescribeJobs reaches STARTING/RUNNING with container.taskArn naming a real ECS task, then SUCCEEDED with a stoppedAt.
  (c) UpdateComputeEnvironment(computeEnvironment=<withholding env>, state='ENABLED') returns 200 and the environment settles state 'ENABLED'/status 'VALID'; the job submitted in (a) is then placed WITHOUT resubmission and reaches SUCCEEDED with exactly 1 attempt, attempts[0].container.taskArn set, an integer `startedAt` >= the control job's `stoppedAt`.

Actual (emulator): no verdict at all. The runner kills the check — "Error: Check timed out after 60.0s" — before any of (a)-(c) is observed; the scenario never gets past its data-plane observations. The 60 s figure is the runner's budget and the generated environment/queue/job names and ids are per-run values; the requirements are the state-gated placement differential, the three withheld-job observables (RUNNABLE / no attempts / no startedAt), the single attempt with a taskArn and a startedAt after the control's stoppedAt on release, and the SUCCEEDED terminal status on both the control and the released job.

## Steps to Reproduce
1. Create an ECS task execution role (trust ecs-tasks.amazonaws.com, AmazonECSTaskExecutionRolePolicy) and the Batch service-linked role; create a VPC with one public subnet and use its default security group.
2. CreateComputeEnvironment twice (type MANAGED, computeResources.type FARGATE, maxvCpus 4, those subnets/security group, state ENABLED); poll DescribeComputeEnvironments until each reports status VALID.
3. UpdateComputeEnvironment(computeEnvironment=<second env>, state='DISABLED') and poll until it reports state 'DISABLED' with status 'VALID' (AWS refuses state='DISABLED' at create).
4. CreateJobQueue over each compute environment (state ENABLED, priority 10); poll each to status VALID.
5. RegisterJobDefinition (type container, platformCapabilities ['FARGATE'], image public.ecr.aws/docker/library/busybox:1.36, command ['/bin/sh','-c','exit 0'], the execution role, VCPU 0.25 / MEMORY 512, assignPublicIp ENABLED).
6. SubmitJob to the DISABLED environment's queue (the withheld job), then SubmitJob to the ENABLED environment's queue (the control).
7. Poll DescribeJobs on the control until STARTING/RUNNING/SUCCEEDED and assert container.taskArn is set; then sample DescribeJobs on the withheld job repeatedly and assert status 'RUNNABLE', no `attempts`, no `startedAt`.
8. Wait for the control to reach SUCCEEDED, then UpdateComputeEnvironment(computeEnvironment=<withholding env>, state='ENABLED'), poll it to ENABLED/VALID, and poll DescribeJobs on the withheld job for SUCCEEDED with exactly 1 attempt, attempts[0].container.taskArn set and startedAt >= the control's stoppedAt. On the emulator the run never gets this far: it is killed at the runner budget with none of these observations made.
