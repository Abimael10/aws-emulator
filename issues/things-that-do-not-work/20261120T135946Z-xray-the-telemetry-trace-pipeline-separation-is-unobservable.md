Cause 1 of 1: a service X-Ray has just accepted a segment for is not reachable as a GetServiceGraph node within the window spanning that segment, so the contrast this check measures — trace ingest draws a node, telemetry ingest does not — never becomes observable and the check runs out the harness ceiling.
AWS: Smithy (services/service-com-amazonaws-xray-awsxray/smithy-model/com-amazonaws-xray-awsxray.json) models GetServiceGraph as POST /ServiceGraph, success 200, required StartTime and EndTime, paginated {inputToken: NextToken, outputToken: NextToken, items: Services}, items of ServiceList -> Service{Name, Names, Type, State, Edges, SummaryStatistics}; its only modeled errors are InvalidRequestException (400, client) and ThrottledException (429). PutTraceSegments is POST /TraceSegments, 200, output UnprocessedTraceSegments. PutTelemetryRecords is POST /TelemetryRecords, 200, with an EMPTY output shape and no reader anywhere in the API. The documented purpose of GetServiceGraph is to "describe services that process incoming requests, and downstream services that they call as a result". The timing of the projection is recorded behavior only: the recording shows that a segment document accepted by PutTraceSegments (UnprocessedTraceSegments == []) makes that document's `name` appear, for a window spanning the segment's start_time, as some node's `Name` or as an entry of some node's `Names` alias list on a fully paginated walk, and that a host which only called PutTelemetryRecords never becomes a node of that graph — the telemetry and trace pipelines are separate aggregates.
Emulator: PutTraceSegments accepts the segment (the check asserts UnprocessedTraceSegments == [] before anything else, and that assertion does not fire) and PutTelemetryRecords answers 200 (also asserted, and it does not fire), but the check never reaches a verdict: it is cut off at the harness ceiling with `Check timed out after 60.0s` while reading GetServiceGraph in a loop over the window [segment_time-600s, now+300s]. Nothing after the two ingest asserts is ever evaluated, so the emulator never demonstrates either half of the contract: the traced service is not shown to become a node, and the telemetry-only host is never shown to stay out of the graph. The time can only be spent in the two GetServiceGraph read loops the check runs (the pin of the account trace-segment destination cannot be the sink: this emulator's default destination is already `XRay` (state.rs DEFAULT_TRACE_SEGMENT_DESTINATION) and its PENDING->ACTIVE span is 500 ms (DESTINATION_ACTIVATION_SPAN), so the pin returns immediately).
Why: the service map is X-Ray's primary aggregate read. A client that submits segments and then reads GetServiceGraph to discover topology, latency and fault statistics must see its own services there, and must NOT see hosts that only uploaded daemon telemetry (which would invent topology real X-Ray does not draw). As long as the positive half is not observable through a bounded read, a caller cannot distinguish "no traffic in this window" from "the graph is not derived", and the telemetry/trace separation is unverified in either direction.
Fix: the GetServiceGraph handler and the segment/graph derivation it reads (services/service-com-amazonaws-xray-awsxray/src/ops/get_service_graph.rs, services/service-com-amazonaws-xray-awsxray/src/state/graphs.rs::service_graph and the trace/segment store in services/service-com-amazonaws-xray-awsxray/src/state.rs) must make an accepted segment's `name` reachable as a node for any window that contains the segment's start_time, on the FIRST read after acceptance and on every subsequent read of the same window, while nothing stored by PutTelemetryRecords (the telemetry map, keyed by reporter identity) contributes a node or an alias. A fixer must confirm this by direct probe rather than by the check alone, because this check's grading cannot be reached from a timeout: put one segment, then page GetServiceGraph over [start-600s, now+300s] once, and assert the segment's name is present and the telemetry hostname is absent. If that direct probe already holds on the current build, then what remains is that the same read must keep holding for repeated reads over the SAME window across the check's absence-grace window (it re-pages the graph every 2 s and requires the traced name to stay present and the telemetry host to stay absent each time) — a node that is derived once and then falls out of, or is added to, the same window on a later read is the same defect seen from the other side.
