# appstream DescribeImages serves a base-image catalog whose published data diverges from AWS (synthesized timestamps, derived recipe revisions, wrong GRID driver) and omits the Windows Server 2016 families entirely, refusing them with HTTP 400

> _Note: this issue was identified against the code base at commit `4196477f4b88a7f6bfc2e255c57de6071ef2afb9`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
DescribeImages

## Description
Five net-new root causes, all in the ONE component that answers DescribeImages for AWS-published base images: the seeded image catalog in services/service-com-amazonaws-appstream-photonadminproxyservice/src/state/images.rs (PUBLISHED_OPERATING_SYSTEMS / PUBLISHED_RELEASE_BATCHES / PublishedImage::record / PublishedImage::recipe) which DescribeImages renders through ImageRecord::to_image. Four causes are published data the catalog DERIVES from a row's batch date instead of carrying it, and the fifth is a whole platform family the catalog does not ship at all, which turns a 200 catalog read into a 400 refusal. No open issue covers any of them: the open appstream wire/behavioral issues (20261102T120557Z-appstream-ec2-7-net-new-appstream-root-causes.md and the CreateStack/UpdateStack + Stack-projection issues it names) are all on the stack/access-endpoint write and read paths, and 20261122T035842Z-appstream-associateapplicationtoentitlement-stub.md is an unrelated stub; none touches the image catalog.

Cause 1 of 5: every published base image's CreatedTime is synthesized as midnight UTC of the date in its name, so a whole release batch reports one identical whole-second instant.
AWS: Smithy: Image$CreatedTime -> Timestamp, doc "The time the image was created"; Image$PublicBaseImageReleasedDate -> Timestamp, doc "The release date of the public base image". Recorded behavior only for the values: each published base image carries its OWN publish instant at millisecond precision, distinct per image, and that instant is NOT midnight of the MM-DD-YYYY date in the image's name — it falls hours to days after it. In the recording the two members of one image also differ from each other by milliseconds (a WinServer2016 image shows CreatedTime 1739564019.612 beside PublicBaseImageReleasedDate 1739564019.466), so they are two recorded instants, not one value used twice; another image of the 2026-02-18 batch reports CreatedTime 1771549107.058 where that batch's date is 1771372800. Those numbers are examples of the shape of the value (per-image, sub-second, later than the name's date), not the requirement.
Emulator: PublishedImage::record builds `let released = instant("<batch.released>T00:00:00Z")` and assigns it to BOTH `created_time` and `public_base_image_released_date`, so every image of a batch reports the same whole-second midnight (got 1771372800 for the 2026-02-18 batch, 1748563200 for 2025-05-30, 1762732800 for 2025-11-10, 1776297600 for 2026-04-16, 1788134400 for 2026-08-31).
Why: a client that sorts or selects base images by CreatedTime gets a total tie across an entire batch rather than an order, any age/staleness computation is off by up to days, and the emulator asserts an invariant AWS does not have (CreatedTime == PublicBaseImageReleasedDate, to the second). Image-pinning logic that records a timestamp against an image and later re-resolves it cannot match.
Fix: the catalog table in src/state/images.rs — carry each published image's own publish instant (and its own released date) per row, rather than deriving both from the batch's date in PublishedImage::record.
Traces: appstream-catalog-describe-images#task#1, #task#2, #task#3, #task#4.

Cause 2 of 5: appStreamRecipeReleaseTimestamp is set to the image's own release date, so it is a duplicate of CreatedTime instead of the recipe revision's release date.
AWS: recorded behavior only — the on-disk Smithy model's Image shape declares no appStreamRecipe* members (query=shape Image lists Name/Arn/.../ImageSoftwareMetadata and nothing else), so these are undocumented wire members the recording establishes. The recording shows the recipe release timestamp LAGS the image's own release by a whole publication batch and is shared by every image built from that recipe revision: images of the 2026-02-18 batch report 1762819200 (2025-11-11 00:00Z, the previous batch's date) and images of the 2026-04-16 batch report 1771372800 (2026-02-18). The requirement is that the member reports the recipe revision's release instant, which is independent of — and earlier than — the image's own CreatedTime.
Emulator: PublishedImage::record sets `appstream_recipe_released: Some(released)` using the same `released` instant it gave created_time, so the member always equals the image's own release date (got 1771372800 where 1762819200 is published, 1776297600 where 1771372800 is published, 1762732800 where 1762819200 is published).
Why: the member exists so a client can tell which recipe build an image came out of. Reported as the image's own release date it carries no information at all, and a client that groups images by recipe-revision release — or that detects "this image was rebuilt from a newer recipe" — sees every image as its own revision and never sees two images sharing one.
Fix: same catalog table — carry the recipe revision's release instant per row (per recipe line and batch), decoupled from the image's released date.
Traces: appstream-catalog-describe-images#task#1, #task#2, #task#3, #task#4.

Cause 3 of 5: the revision segment of appStreamRecipeArn is computed as a linear count from a constant base plus the batch index, which is not the revision AWS publishes.
AWS: recorded behavior only (undocumented wire member, as in cause 2). The recipe ARN has the form arn:aws:amifarm:<region>:<account>:recipe/<RecipeName>/<revision>, and <revision> is the published revision of that recipe line for that image's build. It does NOT advance one-per-publication-batch: on the Graphics-G4 RHEL8 line the recording shows revision 4 for the 05-30-2025 image and revision 14 for the 08-31-2026 image — six batches apart in the emulator's batch list but ten revisions apart in reality. The same spread appears on the RockyLinux8 Graphics-G4 line. The requirement is that the revision is carried per published image, not derived.
Emulator: PublishedImage::recipe returns `GRAPHICS_FIRST_RECIPE_REVISION + self.batch_index` for an accelerated image and `GENERAL_FIRST_RECIPE_REVISION + self.batch_index` for a general-purpose one (GENERAL_FIRST_RECIPE_REVISION = 6), so the revision is a one-per-batch counter from a fixed base: it emits .../AppStreamRHEL8GraphicsG4Recipe/6 where AWS publishes /4, and .../14 is emitted as /12.
Why: the ARN names a build artifact. A client that records or resolves the recipe ARN of a running fleet's image gets an ARN pointing at a revision that is not the one the image was built from, so provenance tracking, drift detection and "is my fleet on the current recipe" checks all compare the wrong identity.
Fix: PublishedImage::recipe plus the catalog table — carry the published revision per (recipe line, batch) row instead of computing it from batch_index.
Traces: appstream-catalog-describe-images#task#1, #task#3.

Cause 4 of 5: the NVIDIA GRID driver version shipped for the newest accelerated batch is wrong.
AWS: Smithy: ImageSoftwareMetadata$nvidiaGridDriverVersion -> NvidiaGridDriverVersion, @length min 1 max 32, @pattern ^[0-9]+(\.[0-9]+){1,2}$, doc "The version of the NVIDIA GRID driver installed on the image. This field is empty if no NVIDIA GRID driver is installed." The value is published data per release batch; the recording reports 595.91.07 for the accelerated images of the 2026-08-31 batch, across every operating system and accelerator in that batch.
Emulator: PUBLISHED_RELEASE_BATCHES carries `PublishedBatch { released: "2026-08-31", nvidia_grid_driver: Some("580.82.07") }`, so every accelerated image of that batch reports 580.82.07.
Why: GRID driver version is exactly the field a client gates image selection on (an application requiring a minimum driver). A stale value makes the emulator reject images a client would accept on AWS, or accept ones it would skip, and the error only surfaces on real hardware.
Fix: the nvidia_grid_driver entry of the affected batch in PUBLISHED_RELEASE_BATCHES.
Traces: appstream-catalog-describe-images#task#1, #task#3.

Cause 5 of 5: the catalog ships no WINDOWS_SERVER_2016 (nor WINDOWS) base images at all, so a DescribeImages read that addresses them is refused HTTP 400 with no Images member instead of answering 200 with the image records.
AWS: Smithy: DescribeImages -> DescribeImagesResult{Images: ImageList, NextToken}; Image$Platform -> PlatformType, whose values include WINDOWS and WINDOWS_SERVER_2016 alongside the Linux and newer Windows Server platforms; DescribeImages' modeled errors are only InvalidParameterCombinationException (400) and ResourceNotFoundException (404). AWS's public catalog still publishes Windows Server 2016 base images — general-purpose and one per graphics accelerator, under AWS's base-image naming AppStream[-Graphics-<accelerator>]-WinServer2016-<MM-DD-YYYY> — including release dates the emulator's batch list does not contain (the recording carries a 02-11-2025 batch beside the 04-16-2026 one). A DescribeImages that addresses them answers HTTP 200 with those Image records, each carrying Platform WINDOWS_SERVER_2016, Visibility PUBLIC, State AVAILABLE, ImageBuilderSupported true and the batch's published metadata.
Emulator: PUBLISHED_OPERATING_SYSTEMS omits WINDOWS_SERVER_2016 and WINDOWS outright (its own comment: "WINDOWS and WINDOWS_SERVER_2016 are the platforms of images published before this snapshot and carry no current base image"), so no such ImageRecord is ever seeded and the four Windows pages of the fixture come back HTTP 400 with the whole Images member absent (replay detail: "status: expected 200, got 400" and "$.Images: missing"). Hypothesis: the refusal is the ResourceNotFoundException raised by DescribeImages' name/ARN selection in src/ops/describe_images.rs when the store holds no matching image — this service serves every refusal on HTTP 400 rather than the shape's @httpError 404 (crate::state::modelled_error_status), which matches the observed 400; the replay detail does not carry the error body, so the code is not confirmed.
Why: a client pinned to Windows Server 2016 — still a supported AppStream platform — cannot enumerate a single launchable image, and instead of an empty-but-valid answer it gets a hard client error that aborts the call. Nothing downstream of image selection (CreateFleet, CreateImageBuilder, image copy/update on that platform) can be exercised against the emulator at all.
Fix: the seeded catalog's PUBLISHED_OPERATING_SYSTEMS and PUBLISHED_RELEASE_BATCHES tables in src/state/images.rs — ship the Windows Server 2016 families (general-purpose and per-accelerator) and the release batches they are published under, so the read is satisfied from the catalog rather than refused.
Traces: appstream-catalog-describe-images#task#5 (cluster also covers #task#6, #task#7, #task#8).
