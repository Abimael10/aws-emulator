# elb: 2 net-new causes — a registered Classic ELB instance never reaches InService, and the published DNSName/listener socket is not the endpoint the emulator is reached on, so all six Classic data-plane scenarios reach no verdict

> _Note: this issue was identified against the code base at commit `dd0dfa661ba492304c3b4ddf1bd869b805afe51f`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
DescribeInstanceHealth

## Description
2 net-new causes, both in the ELB Classic (elasticloadbalancing) emulator. None of the six failing checks below is marked ALREADY FILED or OWNED in this replay report, so none is gated by an existing issue; the open issues that report the same faults from other recorded keys are named per cause. Every one of the six checks follows the same shape — build a public VPC estate (two usable AZs), launch one or two EC2 HTTP backends via user data, CreateLoadBalancer(Scheme=internet-facing, HTTP:80 -> HTTP:80), ConfigureHealthCheck(Target='HTTP:80/<path>', Interval=5, Timeout=2, HealthyThreshold=2, UnhealthyThreshold=2), RegisterInstancesWithLoadBalancer, poll DescribeInstanceHealth for State='InService', then make real unsigned HTTP GETs through the address the load balancer published — and every one of the six ends as '[mismatch] ... Error: Check timed out after 60.0s' with no assertion value whatsoever, i.e. each was still inside a BOUNDED poll (the checks' own deadlines are 300-480 s, far beyond the 60 s replay cap) when the wrapper ended it. The two causes below are the two reasons those polls can never be satisfied.

Cause 1 of 2 — DescribeInstanceHealth never reports a registered, serving backend as InService, so no Classic data-plane leg is ever entered. Failing checks: elb.registered-instance-serves-real-http-through-elb-dns-name, elb.instance-health-decides-whether-real-http-reaches-the-backend, elb.out-of-service-instance-blocked-from-receiving-traffic, elb.lb-cookie-stickiness-pins-a-client-to-one-registered-instance, elb.lb-cookie-stickiness-pins-client-to-one-instance, elb.cross-zone-load-balancing-spreads-requests-beyond-the-node-zone.
AWS: Smithy (com.amazonaws.elasticloadbalancing#ElasticLoadBalancing_v7): DescribeInstanceHealth input DescribeEndPointStateInput {LoadBalancerName required, Instances}, output DescribeEndPointStateOutput {InstanceStates: list<InstanceState>}; InstanceState {InstanceId, State 'InService|OutOfService|Unknown', ReasonCode 'ELB|Instance|N/A', Description}; modeled errors AccessPointNotFoundException -> LoadBalancerNotFound (400) and InvalidEndPointException -> InvalidInstance (400). ConfigureHealthCheck input {LoadBalancerName required, HealthCheck required} with HealthCheck {Target required, Interval required range 5-300, Timeout required range 2-60 and strictly less than Interval, UnhealthyThreshold required range 2-10, HealthyThreshold required range 2-10}. State is the OUTCOME of the load balancer probing each registered instance on the stored Target: once a backend answers HealthyThreshold consecutive probes the member reads State='InService' with ReasonCode='N/A' and Description='N/A' (the model enumerates 'N/A' for both, alongside the fixed sentences 'Instance has not passed the configured HealthyThreshold number of health checks consecutively.' and 'Instance has failed at least the UnhealthyThreshold number of health checks consecutively.' for the pre-/post-threshold states) — those strings are AWS's fixed text; only InstanceId comes from the request. An InService instance then RECEIVES traffic: a GET of the load balancer's published address is forwarded to it and the client is handed the BACKEND's own status and bytes, including a 404 the backend itself chose; an instance driven below UnhealthyThreshold is reported OutOfService (ReasonCode 'Instance') and stops receiving requests while a healthy sibling keeps serving.
Emulator: all six checks report only 'Check timed out after 60.0s'; no leg of any scenario produced a value. The emulator cannot satisfy the InService predicate at all: the crate's own data-plane documentation states that the only two statuses this plane answers itself are 'having no instance to send the request to' (NO_IN_SERVICE_INSTANCE_STATUS) and 'having selected one whose connection cannot be established' (INSTANCE_UNREACHABLE_STATUS) because nothing of this emulator listens on the port the listener forwards to — the same unreachable backend fails every health probe, so a registered instance never passes HealthyThreshold and never emits the InService/'N/A'/'N/A' triple. Hypothesis: with health pinned below InService, the downstream legs (listener forwarding, the withdrawal of an unhealthy instance, AWSELB cookie minting and pinning, cross-zone spreading) are never reached, so whether they are implemented is not observable from these checks.
Why: a client cannot tell a healthy backend from a failed one. Every deploy, registration or canary gate that waits for InService before sending traffic blocks until its own timeout, and everything behind that gate — a request actually served through a Classic load balancer, an unhealthy instance being taken out of rotation, the AWSELB stickiness contract — is unreachable. A Classic load balancer that never has an InService instance never serves traffic at all.
Fix: the health-check evaluation that feeds the per-load-balancer instance-health state read by the DescribeInstanceHealth handler, and the data plane's connection to the selected instance — a registered backend must be able to pass its probes and report InService/'N/A'/'N/A', and a request to the load balancer must reach the backend the instance id names so that backend's own status and body are relayed. That requires the EC2 half of the emulator to let a launched instance serve on a port (its user data is not run as a networked guest today), which is the platform side of this cause.

Cause 2 of 2 — the address a Classic load balancer publishes is a socket of the emulator's own choosing rather than the endpoint the emulator is reached on, so a client given DNSName cannot reach the data plane even once health settles. Failing checks: elb.cross-zone-load-balancing-spreads-requests-beyond-the-node-zone, elb.registered-instance-serves-real-http-through-elb-dns-name, elb.lb-cookie-stickiness-pins-a-client-to-one-registered-instance, elb.lb-cookie-stickiness-pins-client-to-one-instance, elb.out-of-service-instance-blocked-from-receiving-traffic.
AWS: Smithy: CreateLoadBalancer input CreateAccessPointInput {LoadBalancerName required, Listeners required, AvailabilityZones/Subnets/SecurityGroups/Scheme/Tags}, output CreateAccessPointOutput {DNSName}; DescribeLoadBalancers reports the same DNSName on LoadBalancerDescription, and it is the ONLY address a Classic client is given. Its contract is that it is a resolvable HOST name (no embedded port) which a client resolves and connects to on the listener's LoadBalancerPort (80 here); the load balancer accepts that connection and forwards it to its registered InService instances, spreading beyond one node's own zone once ModifyLoadBalancerAttributes sets CrossZoneLoadBalancing.Enabled=true. The generated name is a per-run value and is not a requirement; what IS required is that the published address is one the emulator answers on at the endpoint it is reached on.
Emulator: the crate publishes, as DNSName, a per-load-balancer socket of its own (src/state/load_balancer_endpoint.rs / src/service/listener_socket.rs) and its data-plane module docs state this outright: 'the address a load balancer publishes is a socket of this emulator's own ... and this module is what answers on it'. That address is not the endpoint under test, so a client that resolves the published name and connects to port 80 — exactly what these checks do, including the cross-zone check which pins the node addresses the name resolves to via getaddrinfo — gets no answer from the endpoint it reached the API on; a prior replay of the same cross-zone check recorded the refusal verbatim as "egress refused: '<host>:<port>' is not the endpoint under test" (the host and port digits are per-run values; publishing a second address instead of the endpoint's own is the defect). In this replay the same scenarios simply exhaust the 60 s cap with no verdict.
Why: a client that uses DNSName as AWS documents it — an HTTP client, a health probe, a Route 53 alias target, an integration test — is pointed at an address that is neither a resolvable host nor the endpoint it reached the API on, and a value with a port embedded in it fails on the string itself in any Host header or DNS record. The entire Classic data plane (listener forwarding, cross-zone spreading, AWSELB stickiness) stays unreachable through the only address AWS gives a client.
Fix: the published-address construction in the CreateLoadBalancer handler and the identical projection in DescribeLoadBalancers / the load balancer's stored endpoint, together with the socket that address names — the published DNSName must be a resolvable host served AT the endpoint the emulator is reached on (routed by Host header on the endpoint's own port), not an extra loopback port and not a value carrying a port.
