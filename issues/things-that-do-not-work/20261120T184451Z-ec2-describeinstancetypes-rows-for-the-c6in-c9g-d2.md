# ec2 DescribeInstanceTypes rows for the c6in, c9g, d2 and d3 families carry name-derived attributes instead of AWS's published catalog

> _Note: this issue was identified against the code base at commit `e62e0ae23225a1c6c2c24fb08c0dcaf4852934da`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
DescribeInstanceTypes

## Description
SHARED FAULT: every member of an InstanceTypeInfo row is COMPUTED from the instance type's name (family / generation / capability letters / size) instead of being read from AWS's published per-type catalog, so the EBS, network-card, storage, vCPU and feature members of a described type differ from what AWS reports, and modelled members AWS always emits are absent. The emulator states this design in its own handler doc: "every member is derived by crate::state::instance_type_info from the type's name ... read against the per-family ratios the EC2 User Guide publishes" (services/service-com-amazonaws-ec2-amazonec2/src/ops/describe_instance_types.rs lines 10-16). The corpus replay reports 4 unowned divergence clusters named below, and roughly 120 further unowned DescribeInstanceTypes clusters across the ec2-catalog-describe-instance-types-* fixtures that have the same root cause; fixing the catalog source closes all of them, but only the clusters named here plus the representative are bound to this issue's replay pointer. Two open issues describe the same family of fault for OTHER instance-type rows and do NOT carry these replay keys: 20261117T164306Z-ec2-describeinstancetypes-serves-formula-derived-instance-type-rows.md and 20261120T081949Z-ec2-instance-type-and-fpga-image-catalog-reads.md.

Cause 1 of 4 — c6in rows (fixture ec2-catalog-describe-instance-types-a1-c9g, step task#16).
AWS: recorded behavior only for the attribute VALUES (the Smithy model constrains shape, not catalog content). Smithy: DescribeInstanceTypes -> InstanceTypeInfo.networkInfo -> NetworkInfo.networkCards -> NetworkCardInfo, which models networkPerformance, maximumNetworkInterfaces, baselineBandwidthInGbps, peakBandwidthInGbps, defaultEnaQueueCountPerInterface, maximumEnaQueueCount, maximumEnaQueueCountPerInterface and interfaceTypeSet; EbsInfo models attachmentLimitType, ebsOptimizedInfo and maximumEbsAttachments. The recording shows AWS returning, for the network-dense c6in types, the real per-type figures (for the two-card metal row: 8 interfaces per card and 16 for the type, 200.0 Gbps baseline and peak, an ENA default queue count per interface, an interfaceTypeSet that includes the efa-only entry, and a networkPerformance string of the "Up to N Gigabit"/"N Gigabit" form matching the type's real bandwidth).
Emulator: serves ratio-derived figures instead — fewer interfaces than AWS reports per card and per type, a baseline and peak bandwidth unrelated to the type's real bandwidth, no defaultEnaQueueCountPerInterface member at all, a short interfaceTypeSet missing the efa-only entry, and a networkPerformance string derived from its own computed bandwidth.
Why: a client that sizes a deployment from DescribeInstanceTypes (max ENIs per card, EFA availability, ENA queue budget, EBS attachment limit, baseline vs peak bandwidth) plans against numbers AWS never reports, and code that reads networkCards[*].defaultEnaQueueCountPerInterface finds the member missing where AWS always emits it.
Fix: the instance-type catalog the DescribeInstanceTypes handler reads — crate::state::instance_type_info in the ec2 crate's state, which must serve stored per-type catalog rows rather than deriving members from the type name; the handler itself only projects what the catalog holds.
Traces: ec2-catalog-describe-instance-types-a1-c9g#task#16.

Cause 2 of 4 — c9g rows (fixture ec2-catalog-describe-instance-types-a1-c9g, step task#34).
AWS: recorded behavior only. The recording shows the c9g sizes with a dedicated EBS attachmentLimitType, real ebsOptimizedInfo figures (baseline bandwidth, baseline IOPS, baseline throughput, maximum bandwidth, maximum IOPS, maximum throughput), a maximumEbsAttachments of the published limit, a networkInfo.bandwidthWeightings list (default, ebs-1, vpc-1), the published connectionTrackingConfiguration timeouts, enaSrdSupported false for the small sizes, and per-size ipv4/ipv6 addresses-per-interface, maximumNetworkInterfaces, validCores, sustainedClockSpeedInGhz, trafficMirroringSupport and secondaryNetworkSupported values.
Emulator: answers shared instead of dedicated for attachmentLimitType, EBS-optimized bandwidth/IOPS/throughput and maximumEbsAttachments computed from size ratios, omits networkInfo.bandwidthWeightings entirely, substitutes a generic 432000-second TCP-established timeout for the per-type connection-tracking default, and reports enaSrdSupported true where AWS reports false.
Why: EBS and network provisioning decisions (attachment limits, EBS-optimized ceilings, bandwidth weighting support, connection-tracking timeouts, ENA Express availability) are read straight off this call, so every one of them is wrong for a whole modern family, and a client switching on the presence of bandwidthWeightings concludes the feature is unsupported.
Fix: same component — the per-type catalog rows behind crate::state::instance_type_info, including the EBS and network sub-structures and the members the emulator currently never populates.
Traces: ec2-catalog-describe-instance-types-a1-c9g#task#34.

Cause 3 of 4 — d2 rows (fixture ec2-catalog-describe-instance-types-c9gd-m6gd, step task#2).
AWS: recorded behavior only. For the previous-generation, storage-dense d2 sizes the recording shows currentGeneration false, a shared EBS attachmentLimitType, ebsOptimizedSupport default with a populated ebsOptimizedInfo, the published maximumEbsAttachments, instanceStorageInfo giving the real disk count, per-disk sizeInGB and totalSizeInGB, networkInfo.enaSupport unsupported, and the published network-card baseline bandwidth, ENA default queue count and networkPerformance string, plus supportedRootDeviceTypes as AWS lists them.
Emulator: reports currentGeneration true, a dedicated attachmentLimitType, ebsOptimizedSupport unsupported with ebsOptimizedInfo missing altogether, a lower maximumEbsAttachments, a different disk count and per-disk size (and therefore a different total instance-store size), enaSupport supported, and derived network figures.
Why: a client cannot tell a previous-generation type from a current one, is told the type cannot be EBS-optimized when AWS says it is EBS-optimized by default, and sizes instance-store capacity from a disk layout the type does not have.
Fix: same component — the catalog rows behind crate::state::instance_type_info must carry the recorded generation, EBS-optimized, instance-store and ENA facts per type instead of deriving them.
Traces: ec2-catalog-describe-instance-types-c9gd-m6gd#task#2.

Cause 4 of 4 — d3 rows (fixture ec2-catalog-describe-instance-types-c9gd-m6gd, step task#3).
AWS: recorded behavior only. For the d3 sizes the recording shows dedicatedHostsSupported false, the published EBS-optimized baseline/maximum bandwidth and throughput, a maximumEbsAttachments of the published limit, the real instance-store disk count / per-disk size / total size, ipv4AddressesPerInterface and ipv6AddressesPerInterface equal to the published per-type figure, the published maximumNetworkInterfaces, and the published rebootMigrationSupport and sustainedClockSpeedInGhz.
Emulator: reports dedicatedHostsSupported true, higher derived EBS-optimized bandwidth and throughput, a far smaller maximumEbsAttachments, a different disk count/size/total, more addresses per interface than AWS reports, more network interfaces than AWS reports, and derived reboot-migration and clock-speed values.
Why: placement planning (Dedicated Hosts eligibility), ENI/IP budgeting and storage sizing all come back wrong for the family, and a client that validates its own capacity math against this call gets consistent-looking but fabricated numbers.
Fix: same component — the catalog rows behind crate::state::instance_type_info.
Traces: ec2-catalog-describe-instance-types-c9gd-m6gd#task#3.
