# athena__glue__s3: the Glue-job FAILED → 'Glue Job State Change' → EventBridge/SQS target-policy differential still reaches no verdict — the whole per-check budget is consumed with no assertion graded

> _Note: this issue was identified against the code base at commit `34b956776d59299fbb546444fafe35aa6ddbd93a`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
StartJobRun

## Description
Cause 1 of 1: the chain "pythonshell job run settles FAILED → Glue publishes a 'Glue Job State Change' event → an EventBridge rule matching it delivers to the SQS target whose queue policy grants events.amazonaws.com, and silently drops the sibling target that has none" makes no progress, so the check that grades EventBridge's SELECTIVE delivery is cut off at the harness budget before any assertion runs. Failing check: athena__glue__s3.glue-job-failed-event-missing-target-permission-negative.

Note on prior work: this exact check id was filed before as 20261121T042913Z-athena-glue-s3-the-glue-job-failed-negative.md, which is now listed as FIXED, yet the replay observation is byte-for-byte the same (`Error: Check timed out after 60.0s`, no assertion reached). The failure here is a non-converging wait, not a refusal, so this is reported as the same defect still present rather than as a newly refused call; whatever that fix changed, this path still produces no event and no verdict.

AWS: Smithy com.amazonaws.glue#StartJobRun returns StartJobRunResponse{JobRunId} for an existing job, and com.amazonaws.glue#GetJobRun returns JobRun{JobRunState, ErrorMessage, ...} where com.amazonaws.glue#JobRunState enumerates STARTING, RUNNING, STOPPING, STOPPED, SUCCEEDED, FAILED, TIMEOUT, ERROR, WAITING, EXPIRED. The event emission is recorded behavior only (the Glue model says nothing about EventBridge): a pythonshell job whose script is `import sys\nsys.exit(1)` progresses STARTING → RUNNING → terminal FAILED (its ErrorMessage is the script failure, NOT an "assume role permissions" message); on that terminal transition Glue publishes an event on the default bus with source `aws.glue`, detail-type `Glue Job State Change` and a detail carrying at least jobName (the job definition's name) and state (the terminal JobRunState). A rule whose pattern narrows on that source/detail-type plus detail.jobName/detail.state delivers exactly one message to the SQS target whose queue policy allows Principal {Service: events.amazonaws.com} Action sqs:SendMessage on that queue ARN (Condition ArnEquals aws:SourceArn = the rule ARN), and delivers NOTHING to the sibling target queue that carries no resource policy — PutTargets succeeds for both and no error is surfaced anywhere; the unpermitted queue simply stays empty. The requirement is that pair of observations; the job name, run id, queue names, bucket name and timestamps are per-run values.
Emulator: no part of the chain completes inside the budget. Replay detail: `Error: Check timed out after 60.0s` — no assertion in the check body was reached. The check's only unbounded waits before its first assertion are _run_job_to_terminal_state() (StartJobRun, then GetJobRun polled every 10 s until JobRunState ∈ {SUCCEEDED, FAILED, TIMEOUT, STOPPED, ERROR}, restarting the run while the terminal run's ErrorMessage contains "assume role permissions") and then _wait_for_matching_message() long-polling ReceiveMessage on the permitted queue for a body whose detail.jobName equals the job. Either the run never settles in a terminal JobRunState the client accepts, or it settles and no 'Glue Job State Change' message is ever published to the permitted target; both legs are consumed with no verdict, and the negative 45 s drain on the unpermitted queue is never entered.
Why: post-failure wiring is silently dead. A client that routes Glue job FAILED events to an alerting/retry/DLQ queue never receives them, and because PutRule/PutTargets answer 200 it gets no signal that the notification was lost; a consumer blocked on that queue blocks forever instead of failing. The negative half is worse than silent: a reviewer cannot distinguish "EventBridge correctly refused the target with no queue policy" from "no event was published to any target", so a missing queue policy looks exactly like a correctly enforced deny.
Fix: the Glue job-run executor and run-state machine behind StartJobRun/GetJobRun in the Glue service crate (services/service-com-amazonaws-glue-awsglue), which must execute the referenced pythonshell script and settle a non-zero exit in terminal JobRunState FAILED with AWS's ErrorMessage semantics; and the terminal-transition publication of the 'Glue Job State Change' envelope into the EventBridge default bus, handed to the events crate for pattern matching and per-target delivery, where the target queue's resource policy for events.amazonaws.com must be evaluated so an unpermitted target is dropped silently rather than erroring or skipping delivery wholesale.
