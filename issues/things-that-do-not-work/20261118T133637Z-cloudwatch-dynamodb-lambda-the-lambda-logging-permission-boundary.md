# cloudwatch__dynamodb__lambda: the Lambda logging-permission-boundary scenario never completes — it hangs to the 60 s cap, so printed handler output never becomes visible via FilterLogEvents

> _Note: this issue was identified against the code base at commit `505e225be56e8a8dc67d417f965dd4a20cae2870`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
FilterLogEvents

## Description
One net-new root cause (Cause 1 of 1).

Cause 1 of 1: a Lambda invocation's stdout never becomes retrievable through CloudWatch Logs FilterLogEvents within the scenario's window, so the logging-permission-boundary scenario never terminates — it is killed at the harness cap instead of reaching any assertion.
Failing check id: cloudwatch__dynamodb__lambda.lambda-missing-logs-permission-negative

AWS: On AWS this scenario is a two-arm permission boundary. A function whose execution role carries logs:CreateLogGroup/CreateLogStream/PutLogEvents (the managed policy arn:aws:iam::aws:policy/service-role/AWSLambdaBasicExecutionRole) has every line its handler writes to stdout delivered by the Lambda service to the log group /aws/lambda/<function-name>, and that line is then returned by logs:FilterLogEvents as a member of `events` whose `message` contains the printed text; a quoted filterPattern term (e.g. "marker-pos-xxxx") matches any event whose message contains that literal substring. A function whose role carries no logs permission at all still invokes successfully (Invoke answers 200 with the handler's return payload and no FunctionError header — the missing permission is not an invocation error), but no log group, no log stream and no log events are ever created for it, so FilterLogEvents on /aws/lambda/<function-name> answers ResourceNotFoundException (or an empty `events`) forever. Both arms are observable within seconds. Smithy: FilterLogEvents input logGroupName @length 1..512 @pattern ^[\.\-_/#A-Za-z0-9]+$, filterPattern @length 0..1024; output `events` (FilteredLogEvents) + `searchedLogStreams` + `nextToken`; modeled errors InvalidParameterException (400), ResourceNotFoundException (400), ServiceUnavailableException (500). The delivery rule itself is recorded behavior only — the model does not describe which principal's permissions gate log delivery — and the recording shows the positive arm's printed line becoming visible promptly and the negative arm staying empty.

Emulator: the scenario never reaches either assertion. The replay verdict is the bare timeout `Check timed out after 60.0s` with no traceback and no AWS error response, i.e. the emulator was still being polled when the cap fired. The only waits in the scenario that can consume that window are the CreateFunction retry loop (bounded at 60 s, and exhausting it would surface the modeled InvalidParameterValueException rather than a timeout), the function_active_v2 waiter, and the positive-control poll of FilterLogEvents for the handler's printed MARKER line (bounded at 90 s, i.e. longer than the 60 s cap, so this is the one wait that can swallow the cap without producing an exception). Hypothesis: the positive arm's predicate is never satisfied — either the handler's stdout is never turned into log events under /aws/lambda/<function-name>, or those events exist but a quoted-literal filterPattern never matches them — so the poll runs until the harness kills it and the negative arm (the actual boundary being tested) is never evaluated at all.

Why: a client relying on AWS's behavior gets two things wrong. First, it can never read its own function's output: code that invokes a function and then tails /aws/lambda/<fn> with FilterLogEvents (every log-tailing CLI, every `sam logs`-style flow, every CI assertion on a handler's printed diagnostics) blocks until its own timeout and then reports the function as silent, even though the invocation succeeded. Second, and worse for correctness testing, the IAM boundary is silently unverifiable: because the positive arm never produces evidence, nothing in the emulator distinguishes a role that may write logs from one that may not, so a caller cannot tell whether the emulator enforces logs:CreateLogStream/PutLogEvents on the execution role or ignores it entirely. A hang is also strictly worse than a wrong answer — the caller gets no status, no error code and no message to branch on.

Fix: the Lambda invocation path's log-delivery component (the step that creates /aws/lambda/<function-name>, opens a log stream and appends the invocation's stdout/stderr plus the START/END/REPORT lines as log events) together with CloudWatch Logs' FilterLogEvents handler and its filterPattern matcher, which must return those events and honour a quoted-literal term as a substring match over `message`. The same path must gate delivery on the execution role's logs:CreateLogGroup/CreateLogStream/PutLogEvents so that the no-policy arm creates no group, no stream and no events while Invoke still answers 200 with no FunctionError.

Traces: cloudwatch__dynamodb__lambda.lambda-missing-logs-permission-negative (group permission-boundary; [mismatch], Error: `Check timed out after 60.0s`). This is the only failing check in the replay that is not already owned by an open issue. No open issue covers it: 20261024T043741Z-apigateway-cloudwatch-dynamodb-lambda-lo-...-the-sam.md is a different hang-to-60 s scenario in the apigateway__cloudwatch__dynamodb__lambda__logs__sqs group (a SAM order-service deploy), and the cloudwatch__dynamodb__lambda permission-boundary issues on file (20261114T085344Z-cloudwatch-dynamodb-lambda-a-lambda-whose-execution-role-omits-cloudwatch-putmetricdata.md, 20261109T074412Z-cloudwatch-dynamodb-lambda-putmetricdata-is-never-authorized-against.md) are about cloudwatch:PutMetricData, not about log-event delivery or FilterLogEvents.

## Evidence
Expected (AWS): (1) Invoke of the no-logs-permission function -> 200, no FunctionError, payload {"ok": true}; (2) Invoke of the control function (role with AWSLambdaBasicExecutionRole) -> 200, no FunctionError, payload {"ok": true}; (3) FilterLogEvents(logGroupName="/aws/lambda/<control-fn>", filterPattern='"<marker>"') -> `events` contains at least one FilteredLogEvent whose `message` contains the printed marker, within seconds; (4) FilterLogEvents(logGroupName="/aws/lambda/<no-logs-fn>", filterPattern='"<marker>"') -> ResourceNotFoundException (400) or `events`: [] for the whole window, because no log group/stream is ever created for a role without logs permission.

Actual (emulator): the scenario produces no AWS response to compare at all — the replay verdict is the bare timeout `Check timed out after 60.0s`, with no traceback, no HTTP status, no error code and no error message. The positive-control poll of FilterLogEvents (its own bound is 90 s, longer than the 60 s cap) is the only wait that can absorb the cap without raising, so step (3) above never becomes true and step (4) — the boundary assertion `expected no log events without logs permission` — is never evaluated.

Note on values: the function names, role names and MARKER strings are per-run generated values (ctx.unique_name) and are not part of the requirement; the requirement is the log group name template /aws/lambda/<function-name>, the substring match of a quoted filterPattern term against FilteredLogEvent.message, and the ResourceNotFoundException/empty-events outcome for a function whose role lacks logs permission.

## Steps to Reproduce
1. Clone the repo and run the behavioral suite; the failure is the check cloudwatch__dynamodb__lambda.lambda-missing-logs-permission-negative (the only failing check in the report not marked OWNED).
2. Manually: iam.CreateRole with a trust policy allowing lambda.amazonaws.com to sts:AssumeRole and NO attached or inline policies -> role A. iam.CreateRole with the same trust policy and attach_role_policy PolicyArn=arn:aws:iam::aws:policy/service-role/AWSLambdaBasicExecutionRole -> role B.
3. lambda.CreateFunction twice (Runtime=python3.12, Handler=lambda_function.handler, Publish=true, Environment.Variables.MARKER set to a distinct value per function) with a handler whose body is `print(f"MARKER::{os.environ['MARKER']}"); return {"ok": True}` — one function on role A, one on role B — and wait for function_active_v2.
4. lambda.Invoke each function with Payload={}. Both must answer 200 with no FunctionError and payload {"ok": true}.
5. logs.FilterLogEvents(logGroupName="/aws/lambda/<function-on-role-B>", filterPattern='"<MARKER value for B>"'): AWS returns a non-empty `events` list within seconds. Observe the emulator never returning a matching event, so a poll of this call does not terminate.
6. logs.FilterLogEvents(logGroupName="/aws/lambda/<function-on-role-A>", filterPattern='"<MARKER value for A>"'): AWS returns ResourceNotFoundException / empty `events` indefinitely, because the role has no logs permission. This assertion is currently unreachable because step 5 never completes.
