# ram ListResourceTypes serves an emulator-authored shareable-resource-type catalog: wrong type spellings, absent published types and GLOBAL scope on the IPAM types

> _Note: this issue was identified against the code base at commit `31c031c895c00bd085183e943b31dd8a7e8d67a9`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Description
One net-new cause (Cause 1 of 1), in ram, grounded in a wire divergence the replay reported as neither stub-blocked (stub_path empty) nor owned by any open issue (owned_by empty). The response is a well-formed HTTP 200 whose body diverges: the catalog of shareable resource types that ListResourceTypes publishes is served from the emulator's own static table, and that table is not AWS's.

Cause 1 of 1 — the resourceTypes catalog diverges from the published one at 27 of its ~92 entry positions: several resource types are served under a spelling AWS does not publish (so the type AWS publishes is absent and an emulator-authored one appears in its place), and the two IP Address Manager types are published with resourceRegionScope GLOBAL where AWS publishes REGIONAL. Shape ServiceNameAndResourceType members {resourceType: String — "The type of the resource. The model enumerates no catalog CONTENT, so WHICH types the service publishes, how each type's name is spelled, and which scope each one carries is recorded behavior only. The recording shows the published catalog carries (among the 27 diverging positions) servicecatalog:Applications and servicecatalog:AttributeGroups (plural), events:EventBusv2 as a type of its own, s3:AccessGrants, and ec2:IpamPool and ec2:IpamResourceDiscovery each with resourceRegionScope REGIONAL and restrictToServiceLinkedShares false.
  Emulator: HTTP 200 (expected 200) whose resourceTypes list diverges as a whole entry at 27 index positions (9, 11, 19, 20, 21, 23, 32, 35, 37, 48, 50, 51, 52, 66-71, 74-77, 79, 80, 88, 91). Where AWS publishes servicecatalog:AttributeGroups the emulator's table carries no such entry (it has the singular servicecatalog:AttributeGroup); likewise servicecatalog:Applications (it has servicecatalog:Application), events:EventBusv2 (it has only events:EventBus) and s3:AccessGrants (it has s3:AccessGrantsInstance). ec2:IpamPool and ec2:IpamResourceDiscovery are not served with resourceRegionScope REGIONAL, because the emulator classifies the IPAM types as GLOBAL-scope types. No status or error diverges; the catalog's CONTENT does.
  Why: this catalog is a discovery API — a client calls it to learn which resource types it may share and which scope filter to use, and in this emulator the same table also decides which resource ARNs a share may carry and which resource types a customer-managed permission may be created for. So the divergence is not cosmetic: a client that reads the published type string and then shares that type (events:EventBusv2, s3:AccessGrants, servicecatalog:Applications, servicecatalog:AttributeGroups) names a type this catalog does not know, and its CreateResourceShare / AssociateResourceSharePermission / CreatePermission is refused InvalidParameterException for a type AWS shares. Conversely a client that filters resourceRegionScope=REGIONAL loses ec2:IpamPool and ec2:IpamResourceDiscovery, which AWS publishes as REGIONAL, and one that filters GLOBAL is handed them wrongly — so an inventory built from the filtered read is wrong in both directions. The read is consistent and consistently wrong, so no retry recovers it.
  Fix: the static shareable-resource-type catalog table the read is projected from, and the per-type scope table beside it — the membership and the spelling of each published type, and each type's resourceRegionScope. The ListResourceTypes handler itself only pages and projects what those tables hold, so it needs changing only where it derives a field instead of reading it from the entry.
