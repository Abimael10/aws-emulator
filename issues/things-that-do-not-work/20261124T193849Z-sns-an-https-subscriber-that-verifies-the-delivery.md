# sns: an https subscriber that verifies the delivery it is POSTed admits none — the signed envelope announces SigningCertURL at the reached loopback authority (host:port) instead of the SNS endpoint host its sibling SubscribeURL/UnsubscribeURL name, so no Token ever reaches the endpoint

> _Note: this issue was identified against the code base at commit `d50969a6e6efc58b2521aa7f9ba160b669c146a6`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
Subscribe

## Description
Cause 1 of 1: SNS's http/https delivery path now BUILDS and dispatches the SubscriptionConfirmation / Notification / UnsubscribeConfirmation POSTs (unlike when the earlier issue was filed), but no delivery is ever ADMITTED by a subscriber that performs AWS's documented signature verification, because the envelope announces its signing certificate at an address that is neither AWS's form nor the sibling URL members' host. All seven surviving `sns`-heading checks subscribe one https endpoint that admits only messages whose signature verifies against a certificate fetched from the SNS host it reaches, and each is killed at the 60 s cap having captured nothing — so the confirmation Token never arrives and every behavior layered on it (confirmation-token semantics, pending-vs-confirmed delivery, the notification envelope and its x-amz-sns-* headers, RawMessageDelivery, DeliveryPolicy retries + dead-lettering, the AuthenticateOnUnsubscribe 403 on the anonymous UnsubscribeURL) stays ungraded. Failing check ids for this cause: sns.authenticate-on-unsubscribe-refuses-the-anonymous-unsubscribe-url, sns.confirm-subscription-token-confirms-only-its-own-subscription-whatever-the-topic-arn, sns.confirm-subscription-token-is-reusable-until-unsubscribe-then-not-found, sns.https-endpoint-failing-with-500-is-retried-then-dead-lettered, sns.https-raw-message-delivery-posts-the-bare-body-with-the-rawdelivery-header, sns.https-subscription-receives-nothing-until-confirmed-then-gets-the-notification, sns.raw-message-delivery-drops-message-attributes-for-an-https-subscriber-but-keeps-them-for-sqs.

Its fix landed — ops/subscribe.rs now mints a confirmation and ops/publish/endpoint_delivery.rs performs the POST — yet all seven checks still fail at the same wait, one layer deeper: the POST is made but refused by the verifying subscriber, so this is NOT a re-report of "no POST is made" and the fixer must not close it by re-confirming that a POST is emitted. The SAME addressing defect is already filed, for the SQS-envelope surface only, as OPEN issue 20261120T082601Z-sqs-the-sns-notification-delivered-into-a-subscribed.md (service token `sqs`, grounded in a wire ReceiveMessage step); it does not carry any of these seven behavioral check ids and so does not cover them. Also related and NOT covering these: OPEN 20261124T020517Z-sns-a-numretries-0-https-subscription-s-one.md (the eighth sns https check) and OPEN 20261121T105340Z-iam-lambda-sns-sqs-an-sns-https-subscription.md (the iam__lambda__sns__sqs heading).

AWS:      Smithy (com.amazonaws.sns#AmazonSimpleNotificationService): `Subscribe` (TopicArn, Protocol, Endpoint, Attributes, ReturnSubscriptionArn; errors AuthorizationError/InvalidParameter/NotFound/...) creates an http/https subscription PendingConfirmation, and its doc states "If the endpoint type is HTTP/S ... the endpoint owner must run the ConfirmSubscription action ... You call the ConfirmSubscription action with the token from the subscription response"; `ConfirmSubscription` (TopicArn, Token) returns that subscription's ARN. The POSTed document is recorded behavior only; the AWS Developer Guide section "Verifying the signatures of Amazon SNS messages" states the requirement at issue: `SigningCertURL` is "The URL of the certificate that was used to sign the message", and the subscriber must RETRIEVE it and extract the public key. What AWS emits, as recorded: one POST per subscribe with `x-amz-sns-message-type: SubscriptionConfirmation` whose JSON body carries Type, MessageId, Token, TopicArn, Message, SubscribeURL, Timestamp, SignatureVersion, Signature and SigningCertURL, and one POST per Publish once confirmed with `x-amz-sns-message-type: Notification`. The addressing rule: SigningCertURL names the SNS endpoint host of the message's Region — `https://sns.<region>.amazonaws.com/SimpleNotificationService-<32 hex characters>.pem`, i.e. the DEFAULT https port, no port component — which is the SAME host the same envelope's SubscribeURL / UnsubscribeURL name, and a GET of it answers 200 with the PEM the Signature verifies against. The host name, the 32-hex certificate id, the Timestamp, the Token and the Signature bytes are per-run/per-environment values; the requirement is that ONE envelope announces ONE reachable host for all of its URL members, on the default https port, with the certificate actually served there.

Emulator: the confirmation and notification documents are signed and dispatched, but their two URL families are addressed by two different rules, so the certificate is announced at a host:port a subscriber cannot accept or fetch. state/notification_signature.rs `certificate_url(ctx, region)` takes `data_plane_addressing::reached_emulator_endpoint_of_parts(ctx.parts())`, falling back to `served_endpoint_authority(ctx.endpoint())`, and uses `sns.{region}.amazonaws.com` only as a last resort — so SigningCertURL reads `https://<loopback-authority-with-its-ephemeral-port>/SimpleNotificationService-<id>.pem`, while ops/publish/endpoint_delivery.rs `subscribe_url()` (and the sibling `unsubscribe_url`) format `https://sns.{region}.amazonaws.com/?Action=ConfirmSubscription&...` unconditionally. One delivered document therefore names two different origins, and the certificate's is a non-default port. Observed effect in replay: every one of the seven checks reaches no verdict at all — `Error: Check timed out after 60.0s`, with no assertion from the check body evaluated, because its endpoint captured nothing. Hypothesis (the replay output shows only the timeout, so the fixer must confirm which link breaks): the subscriber refuses each POST with 403 before capturing it, since it requires the envelope's SigningCertURL to be https on exactly the SNS host it reaches with port in (default, 443) and the fetch of that URL to answer 200 — the announced ephemeral-port loopback authority satisfies neither; a second candidate on the same path is that the POST never reaches the subscriber's endpoint at all, since ops/publish/endpoint_delivery.rs routes every delivery through the in-process emulator transport only (`EmbeddedEmulator::http_connector`, "no socket is opened and no name is resolved"), and these endpoints are Lambda function URLs, so a function URL the in-process router does not claim is silently an unreachable subscriber.

Why:      a client that subscribes an https endpoint and does what AWS documents — verify the signature before trusting the message — rejects every message SNS hands it, so the webhook fan-out is inert while Subscribe and Publish both report success: silent, total data loss on a first-class SNS push protocol. The subscription can never leave PendingConfirmation through the documented path, because the Token travels only in that refused POST. A client that instead merely compares the envelope's own members sees one document claiming two origins, and any assertion that SigningCertURL shares the host of SubscribeURL/UnsubscribeURL (the AWS invariant) fails. Downstream, retry budgets, dead-lettering, raw delivery and the anonymous-unsubscribe 403 cannot be exercised at all.

Fix:      the SNS notification/confirmation envelope's signing members and the http/https delivery worker's outbound path — announce the certificate under the SAME authority the envelope's SubscribeURL/UnsubscribeURL members use for the message's Region, with no non-default port, and keep the certificate served at that authority's `/SimpleNotificationService-<32 hex>.pem` so the subscriber's fetch is answered; then make the delivery worker's outbound POST actually reach a subscribed Lambda function URL. ## Steps to Reproduce
1. Build and boot the emulator from this checkout.
2. Stand up an https endpoint that admits a request ONLY after verifying it the way the AWS Developer Guide documents, and records what it admits — e.g. a Lambda function URL (AuthType=NONE) whose handler parses the body, reads `SigningCertURL`, requires it to be https on the same host the client reaches SNS at with no port other than 443, path `/SimpleNotificationService-<hex>.pem`, GETs it, and verifies the RSASSA-PKCS1-v1_5 Signature over SNS's canonical string with that certificate's public key, writing admitted requests to an SQS capture queue and answering 403 otherwise.

4. sns Subscribe --topic-arn <t> --protocol https --notification-endpoint <that function URL> --return-subscription-arn.
5. Drain the capture queue for a body with Type == "SubscriptionConfirmation" and TopicArn == <t>. Against AWS it is there within seconds and its Token confirms the subscription. Against the emulator nothing is ever captured, so no Token exists and the documented confirmation path is unusable — this is where all seven checks block until the 60 s cap.
6. Inspect the envelope the emulator actually sends (log it in the endpoint before the 403, or use the simpler SQS path: Subscribe a queue with default envelope delivery, Publish, and read Messages[0].Body). 7. GET the announced SigningCertURL as the subscriber would: against AWS it answers 200 with the PEM; against the emulator the announced host/port is not one the subscriber is served at, so the fetch does not reach the certificate and the Signature cannot be verified.
8.
