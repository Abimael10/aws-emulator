## Description
Eight distinct root causes in the EventBridge Scheduler control plane, each grounded in a failing check of simparity-behavioral-aws-v1 replayed against the emulator. All eight must be closed before this issue is submitted. None is marked ALREADY FILED or OWNED by the replay report. Two open issues are adjacent and are named explicitly below where they touch the same component but carry neither these checks nor these conditions: 20261030T010351Z-scheduler-wire-responses-drop-validationexception-messages-modeled-getschedule.md (its Cause 1 is the GetSchedule defaults on CREATE; its Cause 8 is ListTagsForResource against a never-created group) and 20261109T161036Z-scheduler-2-net-new-behavioral-causes-an-enddate.md (StartDate/EndDate window wording).

Cause 1 of 8: a cron() expression that states BOTH the day-of-month and the day-of-week field is accepted instead of refused.
AWS: ScheduleExpression's cron form has six fields (minutes hours day-of-month month day-of-week year) and one of the two day fields must be '?' ("no specific value"); an expression that gives a value in both — e.g. 'L' in day-of-month beside '3#2' in day-of-week — states instants cron() never allows and is refused with HTTP 400 ValidationException whose message is the expression class: fixed text `Invalid Schedule Expression ` + the ScheduleExpression the request carried + `.` (Smithy: CreateSchedule.ScheduleExpression, @length 1..256, error ValidationException httpError 400; recorded behavior for the cross-field rule). The same expressions one at a time ('cron(0 12 L * ? *)', 'cron(0 12 ? * L *)', 'cron(0 12 3W * ? *)', 'cron(0 12 ? * 3#2 *)') are accepted and round-trip through GetSchedule unchanged — the emulator gets those right.
Emulator: answers HTTP 200 and returns a ScheduleArn for the both-day-fields expression, creating the schedule. Cause: in services/service-com-amazonaws-scheduler-awschronosservice/src/state/schedule_definition.rs, cron_expression_states_its_instants() sets `service_dialect` when ANY field contains one of the service wildcards (L/W/#) and then short-circuits the whole-expression parse (`service_dialect || normalised_cron(...).parse()`), so no cross-field rule is ever applied to a dialect expression.
Why: the caller is handed a ScheduleArn for a schedule whose expression AWS would never have stored, so the typo surfaces only as non-delivery at runtime, and a test that asserts the refusal passes on AWS and fails on the emulator in the opposite direction (200 where a 400 is required).
Fix: the cron validation in src/state/schedule_definition.rs — the service-dialect path must still enforce that exactly one of the two day fields is '?' instead of bypassing all whole-expression checks.
Traces: scheduler.create-schedule-cron-last-weekday-and-nth-weekday-wildcards-accepted.

Cause 2 of 8: a cron() whose Year puts every occurrence beyond the feasible lookahead is refused with the wrong message class.
AWS: when an expression is well-formed but can never fire inside Scheduler's feasible lookahead from the schedule's window, the refusal is the NEVER-FIRES class, not the malformed-expression class: HTTP 400 ValidationException whose message is fixed text `The schedule expression ` + the ScheduleExpression from the request + `, with StartDate ` + the StartDate as the service echoes it (UTC, no zone suffix, minute resolution when seconds are zero) + ` and EndDate ` + the EndDate the same way or the literal `null` when none was given + `, is invalid because it will never schedule an invocation.` (recorded behavior; Smithy states only ValidationException httpError 400). A cron with a nearby reachable Year and the same StartDate is accepted.
Emulator: refuses with the right code but the malformed-expression message, `Invalid Schedule Expression ` + the expression + `.`, so the two very different conditions are indistinguishable.
Why: a client that branches on the message (or surfaces it to a user) reports a syntax error for an expression whose syntax is fine; it never learns the schedule was rejected because its window and expression have no common instant, so it retries the same expression with a different StartDate forever.
Fix: src/state/schedule_definition.rs — schedule_expression_violation()/schedule_window_violation() must distinguish an unreadable expression from a readable one with no reachable occurrence, and the never-fires branch must build its own message from the expression, StartDate and EndDate (the 'null' literal when EndDate is absent).
Traces: scheduler.create-schedule-cron-year-beyond-feasible-horizon-rejected.

Cause 3 of 8: the pattern echoed in the Target.DeadLetterConfig.Arn constraint message is the SDK model's regex, not the one the service reports.
AWS: a FIFO queue ARN (ending '.fifo') as Target.DeadLetterConfig.Arn is refused with HTTP 400 ValidationException in the standard constraint form: fixed text `1 validation error detected: Value '` + the submitted ARN + `' at 'target.deadLetterConfig.arn' failed to satisfy constraint: Member must satisfy regular expression pattern: ` + the pattern AS THE SERVICE PRINTS IT, `arn:aws[a-z-]*:sqs:[a-z0-9\-]+:\d{12}:[a-zA-Z0-9\-_]+` — unanchored, with the partition written `aws[a-z-]*`. The on-disk Smithy model spells the same constraint differently (Smithy: DeadLetterConfig.Arn @pattern ^arn:aws(-[a-z]+)?:sqs:[a-z0-9\-]+:\d{12}:[a-zA-Z0-9\-_]+$), and the service does NOT echo that spelling; it echoes its own. The service's other ARN members echo the same `arn:aws[a-z-]*` style (see Cause 5 of 20261030T010351Z... for resourceArn).
Emulator: status, code, value and member path are all right, but the echoed pattern is the model's: `...Member must satisfy regular expression pattern: arn:aws(-[a-z]+)?:sqs:[a-z0-9\-]+:\d{12}:[a-zA-Z0-9\-_]+`.
Why: the echoed pattern is the only machine-readable part of the message; tooling that lifts it to validate candidate ARNs locally, and golden-output tests that compare the refusal text, both diverge from AWS on a request AWS and the emulator agree to refuse.
Fix: the pattern-violation message builder in the scheduler constraint validator (the shared `1 validation error detected: ...` formatter reached from src/ops/types.rs) must emit the service's printed form of the pattern for ARN members rather than the raw @pattern string from the model (strip anchors and use the `aws[a-z-]*` partition form).
Traces: scheduler.create-schedule-dead-letter-config-fifo-queue-rejected.

Cause 4 of 8: an ECS target with AssignPublicIp ENABLED and LaunchType EC2 is accepted instead of refused.
AWS: AssignPublicIp may be ENABLED only for Fargate (Smithy: AwsVpcConfiguration.AssignPublicIp — "You can specify ENABLED only when LaunchType in EcsParameters is set to FARGATE"), so CreateSchedule with EcsParameters.LaunchType='EC2' and NetworkConfiguration.awsvpcConfiguration.AssignPublicIp='ENABLED' is refused with HTTP 400 ValidationException whose message is entirely fixed text: `Parameter AssignPublicIp for the target is not supported when launch type is EC2`, and no schedule is created (a following GetSchedule answers ResourceNotFoundException `Schedule ` + the name + ` does not exist.`). The same target with AssignPublicIp='DISABLED' is accepted and the EcsParameters block round-trips.
Emulator: answers HTTP 200 with a ScheduleArn and stores the schedule; the cross-member rule is not implemented anywhere on the create path.
Why: the invalid network configuration is accepted at deploy time and only fails when the occurrence tries to RunTask, so the caller gets a schedule that can never deliver instead of an immediate, actionable refusal.
Fix: ECS-target validation on the write path — add an EcsParameters cross-member check beside the other request-validation calls in src/ops/create_schedule.rs handle() (the `.or_else(...)` chain around the schedule_expression/universal_target/event_bridge_target violations) with the rule itself in src/state (next to event_bridge_target.rs), so UpdateSchedule gets it too.
Traces: scheduler.create-schedule-ecs-target-assign-public-ip-with-ec2-launch-type-rejected.

Cause 5 of 8: a full-replace UpdateSchedule that omits Target.RetryPolicy leaves GetSchedule with no RetryPolicy at all instead of the service default.
AWS: UpdateSchedule replaces the whole schedule, and Scheduler then supplies its own defaults for what the request omitted; GetSchedule always reports an effective Target.RetryPolicy, defaulted to MaximumEventAgeInSeconds 86400 and MaximumRetryAttempts 185 — the maxima of the modeled ranges (Smithy: RetryPolicy.MaximumEventAgeInSeconds @range 60..86400, RetryPolicy.MaximumRetryAttempts @range 0..185). Explicit values at both bounds (60/0 and 86400/185) and a mid-range 3600/5 do round-trip on the emulator; only the revert-to-default after an omitting update diverges.
Emulator: after update_schedule() without Target.RetryPolicy, GetSchedule's Target carries NO RetryPolicy key, so the client-side lookup raises KeyError: 'RetryPolicy' (the check errors rather than mismatching).
Why: a reconciler reading the schedule back sees no retry policy where AWS always has one, computes a spurious diff against its desired state and rewrites the schedule forever; code reading Target.RetryPolicy.MaximumRetryAttempts gets a null dereference. Note: 20261030T010351Z-scheduler-wire-responses-drop-validationexception-messages-modeled-getschedule.md Cause 1 reports the same missing default for a schedule that was CREATED without a RetryPolicy and carries none of these checks; this cause is the UPDATE path and must be closed for it too.
Fix: the schedule record's defaulting on write and/or the response projection — src/ops/update_schedule.rs plus the shared record construction in src/state.rs (ScheduleRecord) and src/ops/get_schedule.rs: the RetryPolicy default must be persisted or projected on every write path, not only on create.
Traces: scheduler.create-schedule-retry-policy-bounds-and-refusals.

Cause 6 of 8: a universal (aws-sdk) target naming a READ-ONLY API is accepted instead of refused.
AWS: a universal target's operation must be one Scheduler will invoke; a read-only API is not supported as a schedule target, so Target.Arn='arn:aws:scheduler:::aws-sdk:sqs:getQueueUrl' is refused by CreateSchedule with HTTP 400 ValidationException whose message is fixed text `Invalid RequestJson provided. Reason ` + the operation name from the ARN's last field, in the SDK's lowerCamelCase spelling + ` API is not supported.` (recorded behavior; the Smithy model constrains only Target.Arn's length/pattern). A mutating operation in the same namespace ('arn:aws:scheduler:::aws-sdk:sqs:sendMessage') is accepted and round-trips.
Emulator: answers HTTP 200 and creates the schedule — the universal-target validator in src/state/universal_target.rs checks only the ARN's grammar (service id spelling, lowerCamelCase operation), never whether the named API is supported as a target.
Why: the caller is handed a schedule whose every occurrence will fail, and tests that assert the refusal invert on the emulator (200 where a 400 is required).
Fix: universal_target_violation() in src/state/universal_target.rs (reached from the request-validation chain of src/ops/create_schedule.rs and the same chain in update_schedule.rs) must refuse an operation Scheduler does not support as a target, with the `Invalid RequestJson provided. Reason <operation> API is not supported.` message.
Traces: scheduler.create-schedule-universal-target-read-only-action-rejected.

Cause 7 of 8: the CreateScheduleGroup name-conflict message does not depend on whether the request carries Tags.
AWS: CreateScheduleGroup for a Name a group already holds is refused with HTTP 409 ConflictException (Smithy: ConflictException, httpError 409, Message required), and the message has TWO forms: a request with NO Tags gets fixed text `Schedule group ` + the Name from the request + ` already exists.`, while a request that DOES carry Tags gets fixed text `Schedule group ` + the held group's ARN + ` was modified concurrently.` (recorded behavior — the tagging path takes the conflict as a concurrent modification of the existing group). Neither refusal changes the held group's Arn, CreationDate, LastModificationDate or Tags.
Emulator: emits the untagged form for both — the tagged conflicting create is refused `Schedule group ` + the name + ` already exists.` src/ops/create_schedule_group.rs line 207-214 builds one message from input.name with no regard for input.tags.
Why: a client that distinguishes a durable name collision (do not retry) from a concurrent-modification conflict (retry) reads the wrong class, and the ARN AWS puts in the tagged form — the identity of the group it collided with — is lost.
Fix: the conflict branch of src/ops/create_schedule_group.rs: when the request carries Tags, build the ConflictException message from the existing group's ARN in the `was modified concurrently.` form; keep the `already exists.` form for an untagged request.
Traces: scheduler.schedule-group-name-conflict-message-depends-on-tags.

Cause 8 of 8: the tagging operations report a deleted schedule group with a generic message no Scheduler API produces.
AWS: once DeleteScheduleGroup has finished (GetScheduleGroup answers ResourceNotFoundException), TagResource, ListTagsForResource and UntagResource against that group's ARN each answer HTTP 404 ResourceNotFoundException with the group form of the message: fixed text `Schedule group ` + the group NAME parsed out of the request's ResourceArn + ` does not exist.` — the same wording the service's own helper produces (src/state.rs group_does_not_exist(), line 467). A sibling group's tags are untouched.
Emulator: answers 404 ResourceNotFoundException with `Resource not found: ` + the full ARN — a message shape this service never produces. src/ops/tag_resource.rs line 192-199 formats that string locally instead of calling crate::state::group_does_not_exist(); the untag and list-tags handlers do the same.
Why: callers and tooling that match the documented not-found text to tell 'group absent' from other 404s read the emulator's message as a different condition, and the message is not even in the service's vocabulary. Note: 20261030T010351Z-...-modeled-getschedule.md Cause 8 reports this for ListTagsForResource against a group that was NEVER created and carries none of these checks; the failing check here is TagResource against a DELETED group, and ListTagsForResource/UntagResource are asserted on the same path, so all three handlers must use the shared helper.
Fix: the not-found branches of src/ops/tag_resource.rs, src/ops/untag_resource.rs and src/ops/list_tags_for_resource.rs must use crate::state::group_does_not_exist(<group name from the ARN>) rather than a local generic string.
Traces: scheduler.tag-untag-list-tags-on-deleted-schedule-group-not-found.
