# s3: 3 net-new browser-edge refusal causes — a correctly signed query-string (presigned) GET/PUT is refused 403 SignatureDoesNotMatch, a presigned DELETE carrying an allowed Origin is refused with an invented cross-site message, and a POST Object form upload is refused 403 AccessDenied

> _Note: this issue was identified against the code base at commit `d86755c0f73584fec4314e4e117b5b920040171c`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
GetObject

## Description
REOPENS 20261029T211510Z-s3-browser-edge-surface-presigned-get-refused-403.md: its fix left the call refused. That issue's Cause 1 (a valid presigned GET is refused 403) and Cause 2 (POST Object is not routed) were closed, and the refusals have only changed shape: the query-string credential is now parsed (the request no longer answers 'AccessDenied'/'Sign the request with the emulator credentials' and POST Object no longer answers 501 NotImplemented), but every presigned read/write is still refused 403, now as SignatureDoesNotMatch, and the form POST is still refused 403. Three distinct root causes on the browser-facing S3 edge; a fixer must close all three.

Cause 1 of 3: a correctly signed query-string (presigned) GET/PUT/HEAD is refused 403 SignatureDoesNotMatch.
AWS: a SigV4 query-string presigned URL (X-Amz-Algorithm=AWS4-HMAC-SHA256, X-Amz-Credential, X-Amz-Date, X-Amz-Expires, X-Amz-SignedHeaders=host, X-Amz-Signature) is authenticated exactly like the header-signed request and, inside its expiry window, is served: GetObject answers 200 with the object's exact bytes (404 NoSuchKey for a key that does not exist), PutObject answers 200 and stores the bytes. The signature covers only the signed headers (host), so an extra request header the browser adds — Origin — is not part of the string-to-sign and never changes the verdict. Smithy (s3): GetObject/PutObject/HeadObject are the ordinary REST-XML object operations; the sigv4 auth scheme is the service-level authScheme, with no separate query-string variant.
Emulator: every such URL answers HTTP 403 with <Error><Code>SignatureDoesNotMatch</Code><Message>The request signature we calculated does not match the signature you provided. Check your key and signing method.</Message> plus AWSAccessKeyId and StringToSign elements. The message sentence is AWS's fixed text for that code; the AWSAccessKeyId and StringToSign values are per-request. The emulator computes a different signature than botocore does for the same presigned URL, so a URL that AWS honours is rejected. One of the bundled checks (s3.cors-max-age-absent-from-the-rule-is-not-invented-on-the-preflight) reports the same refusal as 'the GET answered 403 with Allow-Origin None'. The CORS preflight itself now succeeds (OPTIONS answers 200 with the rule's headers), so the failure has moved onto the signed request.
Why: presigned URLs are the standard way browsers and third parties read and write S3 objects. Every time-limited download/upload link is dead, no CORS response-header contract can be observed on the real request, and a client sees a signing error it cannot fix because its signing is correct.
Fix: the query-string (presigned) SigV4 verification in the S3 authentication path — the canonical request and string-to-sign it rebuilds for a query-signed request (canonical URI/query, the host-only SignedHeaders set, and the UNSIGNED-PAYLOAD hash) must match the SDK's.

Cause 2 of 3: a request is refused because it carries an Origin header — even one the bucket's CORS rule allows — with a message AWS never returns.
AWS: CORS on S3 is advisory and browser-enforced: S3 never refuses a request because it carries an Origin header. A presigned DELETE whose Origin and method match a CORSRule (AllowedOrigins naming that site, AllowedMethods containing DELETE) answers HTTP 204 with an empty body, Access-Control-Allow-Origin set to that origin and Access-Control-Allow-Methods: DELETE, and the addressed object is gone afterwards (a later GetObject is refused ('NoSuchKey', 'The specified key does not exist.')). Smithy (s3): PutBucketCors/GetBucketCors model CORSConfiguration.CORSRules (AllowedOrigins, AllowedMethods, AllowedHeaders, ExposeHeaders, MaxAgeSeconds); DeleteObject's success is HTTP 204 with no body.
Emulator: the DELETE answers HTTP 403 with <Error><Code>AccessDenied</Code><Message>Requests a browser sends from another site are refused</Message>. That sentence is not an AWS message for any code — it is invented — and the refusal happens although the very same origin/method pair was just granted by the emulator's own preflight (the check asserts the preflight answered Access-Control-Allow-Methods: DELETE before spending the delete). The emulator is enforcing CORS server-side, as a deny, instead of using it to decorate the response.
Why: a client that does everything right — configures the rule, gets a clean preflight, sends the signed request — is still denied, and the error text gives it no AWS code/message to branch on. Server-side Origin gating also makes any cross-origin workload fail closed, the exact opposite of AWS, where the rule is advisory.
Fix: the object DELETE/GET/PUT authorization path — remove the Origin-based refusal; CORS evaluation belongs only in the preflight answer and in the Access-Control-* response headers of an otherwise authorized request.
Traces: s3.cors-presigned-delete-with-origin-removes-the-object-and-grants-the-rule

Cause 3 of 3: a browser form POST Object that satisfies its presigned policy is refused 403 AccessDenied.
AWS: a multipart/form-data POST to the bucket URL whose fields carry the policy, x-amz-credential, x-amz-algorithm, x-amz-date and x-amz-signature produced by a presigned POST, and whose file satisfies every policy condition, stores the object and answers HTTP 204 with an empty body (201 with a PostResponse document when success_action_status=201); with an Origin a POST rule allows, the answer also carries Access-Control-Allow-Origin for that origin and Access-Control-Allow-Methods: POST, and the bucket afterwards holds exactly the signed key.
Emulator: the POST answers HTTP 403 with <Error><Code>AccessDenied</Code><Message>Access Denied</Message> and stores nothing. The route now exists (it no longer answers 501 NotImplemented), so the refusal is in the policy/signature verification of the form fields. Hypothesis: the form's signature is verified with the same code path as Cause 1 and fails for the same reason.
Why: browser direct-to-S3 uploads — the standard pattern for user uploads without proxying bytes through an application — cannot work, and the bare 'Access Denied' names no condition the caller could have violated.
Fix: POST Object's policy-document and signature verification in the S3 bucket-level POST handler, and the CORS decoration of its response.
Traces: s3.cors-browser-form-post-upload-with-origin-stores-the-bytes-and-grants-the-rule
