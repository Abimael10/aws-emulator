# eks DescribeAddonVersions marketplaceInformation.productUrl is minted locally instead of the Marketplace product URL

> _Note: this issue was identified against the code base at commit `15f808f6512aed05afde1caaa5d6c2b7e80884c0`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
DescribeAddonVersions

## Description
THREE net-new root causes share one fault: the add-on catalog projected by DescribeAddonVersions does not carry the real AWS Marketplace linkage for a Marketplace-owned add-on. Instead of the product URL AWS publishes for that listing, the emulator mints a productUrl on its own data listener (an /_aws/eks-addon-marketplace-listings/<id> path on the host:port the emulator happens to be reached on), and it fabricates one even for add-ons AWS reports with no productUrl at all. All three clusters answer HTTP 200 and the envelope/shape are correct — only the catalog content diverges, so no status or error wording is at stake. Each cause below must be closed before this issue is resubmitted.

Cause 1 of 3: a kubernetesVersion/name-filtered read of a Marketplace-owned add-on returns a synthesised AddonInfo whose version rows are not the published ones AND whose marketplaceInformation.productUrl is in the emulator's own URL form.
  AWS: Smithy (services/service-com-amazonaws-eks-awswesleyfrontend/smithy-model/com-amazonaws-eks-awswesleyfrontend.json): DescribeAddonVersions GET /addons/supported-versions -> addons : Addons of AddonInfo, with httpQuery filters addonName/types/publishers/owners/kubernetesVersion; AddonInfo members addonName, type, addonVersions, publisher, owner, marketplaceInformation, defaultNamespace; MarketplaceInformation members productId ("The product ID from the Amazon Web Services Marketplace") and productUrl ("The product URL from the Amazon Web Services Marketplace"). The rule: for an add-on whose owner is 'aws-marketplace', marketplaceInformation.productId and productUrl are that listing's identifiers in the AWS Marketplace catalog — a URL on the AWS Marketplace site that resolves to the product (the recordings show both published forms, a .../marketplace/pp/prodview-<id> listing URL and a .../marketplace/pp?sku=<sku> form) — and the returned addonVersions are the releases published for that add-on that are compatible with the requested kubernetesVersion, each with its own architecture, computeTypes, compatibilities (clusterVersion / platformVersions / defaultVersion) and requiresConfiguration / requiresIamPermissions.
  Emulator: serves a record for the requested add-on name whose addonVersions are a single fabricated newest release (compatibilities listing only recent minors, not the minors the request's filter selects), and whose marketplaceInformation.productUrl is not the published product URL for that listing.
  Why: a client that must accept the seller's terms before installing a Marketplace add-on follows marketplaceInformation.productUrl; a URL that is not an AWS Marketplace product URL cannot identify the product, so the subscription step that gates the install can never be completed. The same read is how the client picks an installable addonVersion, so it also pins or upgrades to a release AWS does not publish for its cluster version.
  Fix: the add-on catalog seed data behind DescribeAddonVersions' handler in the eks service crate (the per-add-on release history and the marketplaceInformation it carries) and that handler's kubernetesVersion/addonName filter path. Not the serializer: status, envelope and field names are already right.
  Traces: eks-catalog-describe-addon-versions-accuknox-kubearmor-eg-innovations-eg-universal-agent-operator#task#1 — 19 affected steps across that fixture and eks-catalog-describe-addon-versions-eks-node-monitoring-agent-vpc-cni.

Cause 2 of 3: in a full (unfiltered) catalog listing, productUrl is fabricated for add-ons AWS reports WITHOUT one, and is the emulator-local form for the one that does have one.
  AWS: same operation and shapes. marketplaceInformation.productUrl is populated only where the catalog publishes a Marketplace product URL for that add-on; for the other catalogued add-ons the member is absent from the response (recorded behavior: the recording shows no productUrl on those entries at all, and the AWS Marketplace product URL on the entry that has one).
  Emulator: returns a productUrl on every entry — including the entries AWS returns none for — each pointing at the emulator's own listing path (verdict resource_not_identified: it announces a URL on the address it is served from rather than the Marketplace product).
  Why: the presence of marketplaceInformation.productUrl is what a client uses to decide whether an add-on is a Marketplace listing needing a subscription at all; fabricating one makes non-Marketplace add-ons look like paid listings, and sends the genuine one to an address that identifies no product.
  Fix: the add-on catalog seed data and the DescribeAddonVersions serializer's handling of marketplaceInformation — the member must be omitted when the catalog has no Marketplace URL, never synthesised from the request's host.
  Traces: eks-efsfips-traj-catalog-and-schema-discovery#task#8 (keys $.addons[3]/[4]/[5].marketplaceInformation.productUrl).

Cause 3 of 3: the same local-URL substitution on a single name-filtered Marketplace read, where the published URL is the ?sku=<sku> form.
  AWS: same operation and shapes; the add-on's marketplaceInformation.productUrl is the AWS Marketplace product URL for that SKU (recorded form: https://aws.amazon.com/marketplace/pp?sku=<sku>, the sku being the product's catalog identifier, not a per-run value).
  Emulator: answers 200 with marketplaceInformation.productUrl pointing at its own data listener's /_aws/eks-addon-marketplace-listings/<id> path.
  Why: as in cause 1 — a subscriber or a compliance check that resolves the product URL reaches the emulator instead of the Marketplace listing, so neither the EULA acceptance nor the product identification can succeed.
  Fix: the add-on catalog seed data behind DescribeAddonVersions' handler: carry the catalog's own product URL, do not derive it from the serving endpoint.
  Traces: eks-efsfips-traj-marketplace-fips-addon-detour#task#6.

Note on values: the concrete add-on names, versions, product ids and SKUs quoted below are the recordings' examples of the requirement. The requirement is that productUrl be the AWS Marketplace product URL held in the catalog for that listing (and absent where the catalog has none); the emulator's host and port are never the requirement, and are cited only to show the URL is derived from the serving endpoint.
