# AWS-managed security requirement descriptions are paraphrases of published pack text

> _Note: this issue was identified against the code base at commit `ec2ef26d41329427f76ddd397b9730fbe7244eae`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
ListSecurityRequirements

## Description
Four net-new root causes, one per AWS-managed security requirement pack. They share ONE fault: the seeded catalog content now has the right requirement NAMES, the right count, the right packId and the right fixed createdAt/updatedAt, but every entry's `description` carries a SHORTENED, RE-WORDED restatement of the requirement instead of the requirement's own published statement. The shape of the response is correct in every case; only the rule text diverges. Each pack is seeded from its own table, so each pack's text is its own cause and must be corrected separately — fixing one pack's wording leaves the other three paraphrased.

Note on an adjacent open issue: 20261108T133019Z-securityagent-aws-managed-security-requirement-packs-return-no-requirements reports these same four fixture steps when the packs answered with an EMPTY securityRequirementSummaries list. The packs are no longer empty — they are populated with the wrong description text — so that issue does not cover these four causes, and the replay reports owned_by empty for all four. This issue is what binds the remaining wording divergence to the wire corpus.

Cause 1 of 4 — pack srp-am-base (fixture securityagent-catalog-list-security-requirements, step task#1).
AWS: Smithy: ListSecurityRequirements (POST /ListSecurityRequirements, 200, @readonly, @paginated items=securityRequirementSummaries) returns securityRequirementSummaries (SecurityRequirementSummaryList, @required); SecurityRequirementSummary.description targets String and is @required, documented "A description of the security requirement." The model does not enumerate what AWS ships in a managed pack, so for the CONTENT this is recorded behavior only: the recording shows each entry's description is the requirement's full published statement for that framework area, a fixed catalog string that is identical on every call and in every environment (it carries no value from the request, no id and no clock reading). Eight of the base pack's requirements diverge: authorization-best-practices, information-protection-best-practices, log-protection-best-practices, privileged-access-best-practices, secret-protection-best-practices, secure-by-default-best-practices, tenant-isolation-best-practices, trusted-cryptography-best-practices.
Emulator: HTTP 200 with the correct entries but a re-worded description on each of those eight, e.g. for authorization-best-practices it serves 'Ensure users can only perform the actions they are permitted to.' where the published statement is 'Ensure systems follow authorization best practices.'; for secure-by-default-best-practices it serves 'Ensure the system is secure by default.' where the published statement is "Ensure the system's default configuration is secure." The whole string is the requirement here — it is fixed text with no variable parts — so any difference in wording is a difference in the rule.
Why: a client reads `description` AS the rule. It renders it to a reviewer, matches it against its own control catalog, or hashes the pack's content to detect catalog drift. A paraphrase makes the base pack look like a different (and in several cases narrower) rule set than the one AWS publishes: a reviewer is shown the wrong requirement text, a catalog-mapping step fails to match, and a content hash of srp-am-base never agrees with the real service.
Fix: the service's seeded state — the base pack's shipped-content table, whose `description` field must hold each requirement's published statement verbatim rather than a condensed restatement. The ListSecurityRequirements handler is correct and merely projects the table.
Traces: securityagent-catalog-list-security-requirements#task#1.

Cause 2 of 4 — pack srp-am-nist-csf (fixture securityagent-catalog-list-security-requirements, step task#2).
AWS: same modeled contract as Cause 1; recorded behavior only for the content. The recording shows all 37 NIST Cybersecurity Framework requirements of this pack carrying their full published multi-sentence statements.
Emulator: HTTP 200, 37 entries, and ALL 37 descriptions diverge from the published statement. The divergence is systematic compression and re-wording, e.g. for adverse-event-analysis-and-threat-intelligence-integration the published statement ends with the design ensuring "...that adverse event information flows to authorized personnel and automated response tooling in a timely manner, enabling accurate impact and scope estimation", while the emulator serves a shorter variant that instead ends with "...recording the characterization each event received, and establishing defined criteria for escalating adverse events to formal incident declarations." — dropping a clause the published text states and adding one it does not. ai-component-risk-assessment-and-security-integration and the remaining 35 diverge the same way.
Why: as Cause 1, and worse at this scale — a client that maps this pack onto NIST CSF functions, or that diffs the pack against the framework it tracks, sees 37 of 37 rules whose text does not match the framework statement, so every mapping and every drift check on srp-am-nist-csf is wrong.
Fix: the nist_csf shipped-content table in the service's seeded state; each entry's `description` must be the framework requirement's published statement verbatim.
Traces: securityagent-catalog-list-security-requirements#task#2.

Cause 3 of 4 — pack srp-am-pci-dss (fixture securityagent-catalog-list-security-requirements, step task#3).
AWS: same modeled contract; recorded behavior only for the content. The recording shows all 50 PCI DSS v4.0.1 requirements of this pack carrying their full published statements, phrased as what the WORKLOAD and its architecture must demonstrate.
Emulator: HTTP 200, 50 entries, and all 50 descriptions diverge. Beyond compression the emulator also changes the voice of the rule: for account-data-classification-and-retention-controls the published statement begins 'Workloads that store, process, or transmit payment account data should clearly identify and classify cardholder data (CHD) elements...' while the emulator serves 'All stored account data must be identified and classified into cardholder data (CHD) and sensitive authentication data (SAD) elements...' — a restatement of the control rather than the pack's own workload-scoped statement. anti-malware-protection-for-workload-components and the remaining 48 diverge the same way.
Why: as Cause 1. A PCI DSS consumer uses this text as assessment evidence; serving a restatement means the emulator cannot be used to exercise any flow that renders, exports or attests to the pack's requirement text, and a scope/applicability decision made from the emulator's wording (e.g. 'All stored account data must...' vs the published workload-scoped phrasing) differs from the decision real AWS's text produces.
Fix: the pci_dss shipped-content table in the service's seeded state; each entry's `description` must be the published statement verbatim, including its workload-scoped phrasing.
Traces: securityagent-catalog-list-security-requirements#task#3.

Cause 4 of 4 — pack srp-am-well-architected (fixture securityagent-catalog-list-security-requirements, step task#4).
AWS: same modeled contract; recorded behavior only for the content. The recording shows all 32 Well-Architected Security Pillar requirements carrying their full published statements, phrased as what the ARCHITECTURE DOCUMENTS must define ('Architecture documents must define...').
Emulator: HTTP 200, 32 entries, and all 32 descriptions diverge. The emulator drops the 'Architecture documents must define...' framing and serves a shorter workload-scoped rule instead: for authenticated-network-communication-architecture the published statement is 'Architecture documents must define how network communications are authenticated to verify the identity of communicating parties...' including the explicit mechanism list (TLS with certificate validation, mutual TLS, IPsec, AWS SigV4) and the requirement that services verify caller identity even inside one network boundary, where the emulator serves 'Network communication within and into the workload must be authenticated rather than trusted on the basis of its origin...'. automated-certificate-management-architecture and the remaining 30 diverge the same way.
Why: as Cause 1. These requirements are consumed as design-review criteria; the published text states WHAT THE DESIGN DOCUMENT must contain, and the emulator's text states what the workload must do. A client that drives a document review from the pack asks for the wrong artifact, and the named mechanisms a reviewer is told to look for are absent.
Fix: the well_architected shipped-content table in the service's seeded state; each entry's `description` must be the published statement verbatim, preserving its architecture-document framing and its enumerated mechanisms.
Traces: securityagent-catalog-list-security-requirements#task#4.
