# s3: 4 net-new causes — no static-website endpoint is served (and the AWS website host is announced instead), CopyObject accepts a specific ETag in If-None-Match, HeadObject omits the stored SSE-KMS encryption context, and aws-chunked trailer checksums/names are never validated

> _Note: this issue was identified against the code base at commit `d86755c0f73584fec4314e4e117b5b920040171c`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
GetBucketWebsite

## Description
Four distinct root causes in the S3 website surface, the conditional-copy path, the SSE-KMS metadata it returns and its aws-chunked upload validation; a fixer must close all four.

Cause 1 of 4: the emulator serves no S3 static-website endpoint, and where one is needed it names the real AWS website host instead of an address it answers on.
AWS: a bucket with a website configuration is served on its own website endpoint host (<bucket>.s3-website-<region>.amazonaws.com / <bucket>.s3-website.<region>.amazonaws.com), which is a different surface from the REST endpoint: GET / returns the IndexDocument's bytes with its Content-Type; a bare folder path (no trailing slash) answers a 301/302 redirect to the same path with a trailing slash in Location; a missing key answers 404 with the ErrorDocument, or — when none is configured — S3's own default error page naming the NoSuchKey condition; RedirectAllRequestsTo answers 301 with Location pointing at the configured host/protocol; a RoutingRule whose condition is HttpErrorCodeReturnedEquals 404 answers its redirect for missing keys; and a write (PUT/POST/DELETE) on the website endpoint is refused 405 MethodNotAllowed. A bucket that was never configured for website hosting answers 404 NoSuchWebsiteConfiguration on that host. Smithy (s3) models PutBucketWebsite/GetBucketWebsite/DeleteBucketWebsite and WebsiteConfiguration (IndexDocument, ErrorDocument, RedirectAllRequestsTo, RoutingRules), but the endpoint host itself is not an API operation — recorded behavior only.
Emulator: no website endpoint exists or is published. Four checks stop at the harness with CapabilityNotOffered: 'the emulator offers no S3 website endpoint (the run names no website endpoint template: s3_website_url=, SIMPARITY_S3_WEBSITE_URL)'. Three more, which fall back to the AWS website host, are refused as egress: 'endpoint_url was given http://<bucket>.s3-website-<region>.amazonaws.com/ (published by the emulator or built by the check): its host is not one of the emulator's own hosts' — i.e. the only website address available is one the emulator does not answer on.
Why: static-website hosting is one of S3's two serving surfaces; with no endpoint, index/error-document serving, folder redirects, RedirectAllRequestsTo and routing rules are all unusable and untestable, and a client that follows the announced amazonaws.com host leaves the emulator entirely.
Fix: a website listener/endpoint for the S3 service that the emulator publishes on its own host, plus the website-endpoint request handler (index/error document, trailing-slash redirect, RedirectAllRequestsTo, RoutingRules, 405 on writes, NoSuchWebsiteConfiguration for an unconfigured bucket). The open issue 20261113T120806Z-s3-the-emulator-publishes-no-s3-website-endpoint.md records the same absence for the stored-WebsiteRedirectLocation check but does not carry these replay keys.
Traces: s3.e2e-website-deployment, s3.website-endpoint-serves-index-and-error-documents-and-refuses-writes, s3.s3-website-hosting-bare-folder-path-redirects-to-trailing-slash, s3.s3-website-hosting-get-rejected-for-a-bucket-never-configured, s3.s3-website-hosting-missing-key-with-no-error-document-is-rejected-with-the-default-error-page, s3.s3-website-hosting-redirect-all-requests-to-answers-301-to-the-target-host, s3.s3-ssec-and-endpoint-enforcement-website-routing-rule-on-404-redirects-missing-keys

Cause 2 of 4: CopyObject accepts a specific ETag value in If-None-Match and performs the copy.
AWS: Smithy (s3) models CopyObject's IfNoneMatch on the If-None-Match header. S3 implements only the wildcard form for a conditional copy: If-None-Match: * creates the destination when it is absent and is refused ('PreconditionFailed', 'At least one of the pre-conditions you specified did not hold') when it exists. A specific ETag value is a header whose functionality CopyObject does not implement: the request is refused with code 'NotImplemented' and the fixed message 'A header you provided implies functionality that is not implemented' (HTTP 501), and no destination object is created.
Emulator: the copy succeeds — HTTP 200 with a CopyObjectResult (ETag, LastModified, ChecksumType FULL_OBJECT, ChecksumCRC32) — and the destination key is created. The earlier parts of the same scenario (the resource-policy deny on the destination write, and If-None-Match: * both ways) behave correctly, so only the specific-ETag branch diverges.
Why: a client using an ETag-conditional copy believes S3 honoured its precondition when nothing was checked, so a copy that must only happen when the destination's content differs runs unconditionally and overwrites.
Fix: CopyObject's If-None-Match validation in the copy handler — only '*' is supported; any other value must raise the NotImplemented refusal before any destination write.
Traces: s3.copy-object-under-if-none-match-policy

Cause 3 of 4: HeadObject does not return the stored SSE-KMS encryption context.
AWS: an object written with ServerSideEncryption aws:kms and x-amz-server-side-encryption-context stores that context augmented with S3's own entry 'aws:s3:arn': 'arn:aws:s3:::<bucket>/<key>', and HeadObject returns it on the x-amz-server-side-encryption-context header as Base64-encoded JSON, alongside x-amz-server-side-encryption-aws-kms-key-id holding the key's full ARN. Smithy (s3): PutObjectOutput and CopyObjectOutput model SSEKMSEncryptionContext on that header; HeadObjectOutput models no such member, so the header on HEAD is recorded behavior only.
Emulator: PutObject echoes the augmented context correctly, but HeadObject returns no x-amz-server-side-encryption-context header at all (the check reads None where it expects the stored map).
Why: a client cannot read back the KMS encryption context of a stored object, so it cannot verify which context its data was wrapped under (a compliance and key-rotation requirement) or even tell that the context it sent was retained. The same check's later assertions — a malformed context header must be refused ('InvalidArgument', "The header 'x-amz-server-side-encryption-context' shall be Base64-encoded UTF-8 string holding JSON which represents a string-string map") with ArgumentName x-amz-server-side-encryption-context and ArgumentValue echoing the bad value — stay unreachable until HEAD answers.
Fix: the HeadObject response serializer and the object's stored encryption metadata — the SSE-KMS encryption context recorded at write time must be emitted on x-amz-server-side-encryption-context.
Traces: s3.put-object-sse-kms-encryption-context-round-trips-then-malformed-rejected

Cause 4 of 4: an aws-chunked upload's trailer is never validated — neither its checksum value nor its header name.
AWS: for a PUT with Content-Encoding: aws-chunked, x-amz-content-sha256: STREAMING-UNSIGNED-PAYLOAD-TRAILER and x-amz-trailer naming a checksum header, S3 recomputes the declared checksum over the received bytes and compares it with the trailer chunk's value: a value that does not match is refused HTTP 400 with ('BadDigest', 'The CRC32 you specified did not match the calculated checksum.') — fixed text whose algorithm name comes from the declared x-amz-trailer — and a trailer chunk whose header name differs from the declared one is refused HTTP 400 with ('MalformedTrailerError', 'The request contained trailing data that was not well-formed or did not conform to our published schema.'). Neither rejected request stores an object: a following GetObject is refused ('NoSuchKey', 'The specified key does not exist.'). The identical request with a correct, matching trailer answers 200 and the object's ChecksumCRC32 is the trailer's value.
Emulator: both malformed uploads answer HTTP 200 with an empty body and the object is stored, so a corrupted payload and a malformed trailer are both accepted silently.
Why: the trailing-checksum form is how SDKs stream large uploads with end-to-end integrity; accepting a mismatched checksum destroys the only corruption signal the protocol has, and a client that relies on BadDigest to retry stores bad bytes instead.
Fix: the aws-chunked/trailer decoding in the PutObject data-plane path — verify the trailer chunk's header name against x-amz-trailer and its value against the checksum computed over the decoded payload, and refuse with the two errors above before the object is written.
Traces: s3.s3-chunked-upload-trailer-checksum-mismatch-rejected-object-absent, s3.s3-chunked-upload-trailer-name-mismatch-rejected-object-absent
