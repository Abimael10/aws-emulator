# No product reachable from a default SearchListings scan has more than one fulfillment option, so ListFulfillmentOptions' maxResults truncation and nextToken are unreachable

> _Note: this issue was identified against the code base at commit `cd40bf0ce0c339e7c23b4535749b1d315534bb0d`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
ListFulfillmentOptions

## Description
This issue carries 1 cause, in marketplace-discovery.

Cause 1 of 1: the catalog a client actually sees on the first page of SearchListings exposes exactly ONE fulfillment option per product, so ListFulfillmentOptions never returns a list it could truncate and its paging path is unreachable. Failing checks: marketplace-discovery.list-fulfillment-options-maxresults-respected, marketplace-discovery.list-fulfillment-options-pagination-respects-max-results.

AWS: Smithy (services/service-com-amazonaws-marketplacediscovery-awsmarketplacediscovery/smithy-model/com-amazonaws-marketplacediscovery-awsmarketplacediscovery.json): ListFulfillmentOptions output member fulfillmentOptions targets FulfillmentOptionsList, a list of the 12-member FulfillmentOption union (FulfillmentOptionType = AMAZON_MACHINE_IMAGE, API, CLOUDFORMATION_TEMPLATE, CONTAINER, HELM, EKS_ADD_ON, EC2_IMAGE_BUILDER_COMPONENT, DATA_EXCHANGE, PROFESSIONAL_SERVICES, SAAS, SAGEMAKER_ALGORITHM, SAGEMAKER_MODEL), and the operation is @paginated {inputToken: nextToken, outputToken: nextToken, pageSize: maxResults, items: fulfillmentOptions} with maxResults @range(min 1, max 50) default 25 and nextToken documented as "If nextToken is returned, there are more results available". The model therefore pins a one-to-many relation between a product and its fulfillment options and a continuation path over them; the listing and product views restate that same multiplicity through fulfillmentOptionSummaries (a list). What the catalog CONTAINS is not modelled, so for the content this is recorded behavior only: a real AWS Marketplace product is commonly offered through several routes (an AMI plus the Image Builder component that bakes it, a SaaS subscription plus its API, a container image plus its Helm chart), so a client that scans the first page of an unfiltered SearchListings reaches products with 2+ fulfillment options, and asking for them with maxResults=1 returns exactly one option plus a nextToken.

Emulator: every ListFulfillmentOptions call made over the products of the first 20 listing summaries of a default SearchListings (no searchText, no filters, maxResults=20) answers 200 with a fulfillmentOptions list of length <= 1, for every scanned product, so no truncation and no nextToken is ever produced. The seeded catalog does hold multi-option products (an AMI + EC2_IMAGE_BUILDER_COMPONENT row, a SAAS + API row, a CONTAINER + HELM row, and the hand-written SAAS + API product), but none of them is reachable in that scan: the per-category tier gives each of its products exactly one fulfillment option (fulfillment: vec![fulfillment_for_kind(kind)], one FulfillmentOptionType per row), that tier's ids are seeded in the highest id block, and SearchListings with an empty searchText scores every match 0.0 and tie-breaks on listing id, which the modelled default sortOrder=DESCENDING reverses — so the whole first page is single-option per-category rows and the multi-option rows sort last. The result is that the emulator's maxResults truncation and nextToken behaviour for this operation cannot be exercised by any client that discovers products the documented way (search, then drill into an associated product).

Why: a client that branches on the number of deployment routes a product offers (rendering a "choose how to deploy" step, or looping on nextToken until it has collected every option) sees a catalog in which every product has exactly one route and the loop never runs a second iteration. Code written against the emulator therefore never exercises its own pagination path, and any defect in the emulator's own ListFulfillmentOptions page cutting or token minting stays invisible; a consumer that caches "one option per product" diverges from AWS the moment it meets a real multi-route product.

Fix: the seeded catalog and the first-page ordering it is read through — the per-category row builder that assigns a single FulfillmentOptionType per product, and/or the empty-query ordering in the SearchListings handler that pushes every multi-option row behind the single-option block. At least one product reachable within the first page of a default, unfiltered SearchListings must offer 2+ fulfillment options, with its full list returned under maxResults=50 with no nextToken and exactly one option plus a nextToken under maxResults=1. ListFulfillmentOptions' own handler needs no change: it already pages whatever the product record holds.

Traces: checks marketplace-discovery.list-fulfillment-options-maxresults-respected and marketplace-discovery.list-fulfillment-options-pagination-respects-max-results. Not covered by the open issue "GetListing, GetProduct and ListFulfillmentOptions serve synthesized placeholder records instead of the catalog's stored content" (20261029T201942Z): that one is about the CONTENT of an individual option (quickLaunch, launchUrl, template URLs); this one is about how many options a reachable product has and about the paging path that multiplicity unlocks. Also distinct from "ListFulfillmentOptions SaaS option serves a placeholder example.com fulfillmentUrl" (20261116T021400Z).

Explicitly NOT claimed as requirements: any particular productId, listingId or fulfillmentOptionId literal, any particular option type on any particular product, and the exact relevance score of an empty query. The requirement is that a product with 2+ fulfillment options is reachable on the first page of a default search and that maxResults/nextToken then behave as the @paginated trait describes.

## Evidence
Behavioral suite replay against the emulator built from this checkout: 76/78 passed, both failures in marketplace-discovery and both on the same precondition.

1) marketplace-discovery.list-fulfillment-options-maxresults-respected — AssertionError: "no scanned product (across up to 20 listing summaries) exposes 2+ fulfillment options; maxResults truncation cannot be meaningfully exercised". The check calls SearchListings(maxResults=20), then for each distinct product in listingSummaries[*].associatedEntities[*].product calls ListFulfillmentOptions(productId=..., maxResults=50) and looks for a response with len(fulfillmentOptions) >= 2. Every call returned 200 (no ResourceNotFoundException, so every scanned productId resolved) with 0 or 1 options, so the assertion on maxResults=1 -> exactly 1 option + a nextToken was never reached.

2) marketplace-discovery.list-fulfillment-options-pagination-respects-max-results — AssertionError: "no scanned product (across up to 20 listing summaries) exposes 2+ fulfillment options; pagination cannot be meaningfully exercised", from the same scan (it additionally requires the unbounded maxResults=50 page to carry no nextToken).

Expected (AWS): the scan reaches at least one product whose ListFulfillmentOptions response lists 2+ options; ListFulfillmentOptions(productId=that, maxResults=1) then returns exactly 1 option and a non-empty nextToken, and paging with that token reassembles the same set of options as the unbounded call.
Actual (emulator): no scanned product lists more than one option, so no page is ever truncated and no nextToken is ever minted for this operation.

Seed/ordering evidence from the checkout: src/state/taxonomy_rows.rs builds one CatalogRow per taxonomy subcategory with fulfillment: vec![fulfillment_for_kind(kind)] (exactly one type) and sequence SEQUENCE_BLOCK + index, the highest id block in the catalog; src/ops/search_listings.rs gives every match relevance 0.0 when searchText is absent and tie-breaks on listing id, reversed for the modelled default sortOrder=DESCENDING, so that highest-id single-option block is exactly what the first page of a default search returns. The multi-option records (src/state.rs BREADTH_ROWS entries with fulfillment &["AMAZON_MACHINE_IMAGE", "EC2_IMAGE_BUILDER_COMPONENT"], &["SAAS", "API"], &["CONTAINER", "HELM"], and the hand-written SAAS + API product) all sit in lower id blocks and are never reached within 20 summaries.
