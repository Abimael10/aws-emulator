# resiliencehubv2 test surface diverges: CreateTest refuses every template on a blanket multi-AZ RTO precondition, refusal wordings wrong, UpdateTest validation and assertion service-event descriptions missing (7 causes)

> _Note: this issue was identified against the code base at commit `bb8ef245653a926b9aee7b2453a52ccc9360968a`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
CreateTest

## Description
Behavioral replay of the resiliencehubv2 suite leaves the whole test (`/v2/*-test`) surface unusable, plus one unrelated service-event representation defect. This bundle contains 7 causes; ALL SEVEN must be closed before submitting.

Relation to already-open issues: the open issue 20261125T185751Z-resiliencehubv2-createtest-refuses-with-a-blanket-multi-az.md (wire corpus, fixture resiliencehubv2-test-configuration-errors) describes the same blanket-refusal family from the wire side and overlaps Cause 1 and Cause 3 below; it does NOT carry any of the behavioral check ids listed here, and it does not state the correct multi-AZ-RTO refusal wording (Cause 2), the multi-Region precondition (Cause 4), UpdateTest's stop-condition and parameter validation (Causes 5 and 6), or the assertion service events (Cause 7). The other open resiliencehubv2 issues (TagResource/UntagResource Content-Length, effectivePolicyValues, user-journey/system responses, the DeleteUserJourney stub) are unrelated.

--- Cause 1 of 7: CreateTest applies the multi-AZ-RTO policy precondition to EVERY test template, so no test can ever be created. ---
AWS: Smithy: CreateTest is POST /v2/create-test, success code 200, output CreateTestResponse with REQUIRED member `test` (shape Test); input `serviceArn` and `testTemplateArn` required, `parameters` a TestParameters map (max 20), plus `roleName`, `stopConditions`, `loggingConfiguration`. A test template (shape TestTemplate) declares its own `parameters` and `actions`; nothing in the model ties an arbitrary template to a resilience-policy multi-AZ RTO target. Recorded behavior: CreateTest for the AWS-owned `aws-dependency-validation:<id>` template, on a service with NO resilience policy at all, succeeds with 200 and the minted Test (name `Test-<testId>`, the submitted parameters, roleName, serviceArn, testTemplateArn, successfulTestRuns 0, totalTestRuns 0, generated testId/creationTime). Only templates that actually exercise multi-AZ recovery (the AZ-recovery template) carry the policy precondition.
Emulator: every CreateTest call is answered 400 ValidationException with the message "Cannot create test for service '<serviceArn>'. Ensure the resilience policy associated with the service defines a multi-AZ RTO." — fixed text with the request's serviceArn interpolated — regardless of which template is named and regardless of whether the service has a policy. Five behavioral checks die on their FIRST CreateTest call for the dependency-validation template; test-creation-requires-multi-az-rto-on-services-policy is additionally refused with the same message after UpdatePolicy has observably added multiAz.rtoInMinutes=15 to the service's policy, so the precondition is not even re-evaluated against current policy state.
Why: the operation can never succeed, so every downstream flow a client builds on it — ListTests, GetTest, UpdateTest, DeleteTest, test runs — is unreachable and the emulator holds no test state at all. A client is also told to change its resilience policy for inputs that have nothing to do with policy.
Fix: the CreateTest handler and its state — scope the multi-AZ-RTO precondition to the templates that declare that requirement, evaluate it against the service's CURRENT policy, and otherwise mint and persist the Test from the named template and return 200 with the required `test` member. Note the downstream requirements the same checks assert once unblocked: a created test is named `Test-<testId>`; a second CreateTest for the same (serviceArn, testTemplateArn) pair must be refused 409 ConflictException with "A test already exists for this test template on this service. Only one test can be created per template on a service. Update the existing test, delete it, or use a different template." (fixed text, no interpolation); after DeleteTest, GetTest for that id must answer ResourceNotFoundException with "No test was found for the provided test ID and service ARN. Verify that the test ID and service ARN belong to the same service, then try again." (fixed text); a re-created test carries a NEW testId and ListTests shows only it.
Traces: resiliencehubv2.one-test-per-template-per-service, resiliencehubv2.update-test-replaces-the-parameter-map, resiliencehubv2.test-parameters-rejected-when-they-break-the-template-contract, resiliencehubv2.stop-condition-with-source-none-rejects-a-value, resiliencehubv2.multi-region-template-rejected-for-a-single-region-service, resiliencehubv2.test-creation-requires-multi-az-rto-on-services-policy.

--- Cause 2 of 7: the multi-AZ-RTO refusal, where it IS correct, carries the wrong message. ---
AWS: Smithy: CreateTest declares ValidationException (httpError 400, members message/reason/fieldList). Recorded behavior: when the AZ-recovery test template is created against a service whose resilience policy defines no multi-AZ RTO target, AWS answers 400 ValidationException with "The test template requires a policy with Multi-AZ RTO configured. Configure Multi-AZ RTO on the service's policy and try again." That sentence is entirely FIXED text for this error class — it interpolates no serviceArn, policy name, template id or value.
Emulator: answers 400 ValidationException (status and code correct) with "Cannot create test for service '<serviceArn>'. Ensure the resilience policy associated with the service defines a multi-AZ RTO." — different fixed text, and it interpolates the request's serviceArn, which AWS's message does not contain at all.
Why: the message is a contract surface for this error class. A client or operator matching the documented sentence, or surfacing it as remediation copy, sees a foreign string; the emulator's variable serviceArn also makes the message unstable across requests where AWS's is constant.
Fix: the CreateTest handler's policy-precondition refusal path — emit AWS's fixed sentence for this error class instead of the internal "Cannot create test for service '<arn>'..." formatter.
Traces: resiliencehubv2.test-creation-requires-multi-az-rto-on-services-policy.

--- Cause 3 of 7: CreateTest's unknown-test-template refusal carries the wrong message. ---
AWS: Smithy: CreateTest.testTemplateArn is a required ServiceOwnedArn and CreateTest declares ResourceNotFoundException (httpError 404). Recorded behavior: naming a test template that does not exist is refused ResourceNotFoundException with "The specified test template does not exist. Verify the test template ARN and try again." — wholly fixed text; it does NOT interpolate the supplied ARN or template identifier. (GetTestTemplate for the same ARN uses a different, shorter form — "Test template not found: <template-name>", where only the template name is variable — so the two operations are not interchangeable.)
Emulator: answers ResourceNotFoundException with "TestTemplate not found: <template-id>" — an internal "<Type> not found: <id>" formatter that substitutes the request's template identifier.
Why: a client matching the documented sentence, or distinguishing CreateTest's refusal from GetTestTemplate's, cannot; user-facing copy diverges from AWS.
Fix: the CreateTest handler's test-template lookup/refusal path — emit the fixed AWS sentence rather than the generic internal not-found formatter. (Overlaps Cause 1 of the open wire issue named above; that issue does not carry this check id.)
Traces: resiliencehubv2.create-test-rejects-unknown-template.

--- Cause 4 of 7: CreateTest does not enforce the multi-Region-resources precondition of the multi-Region isolation template. ---
AWS: Smithy: CreateTest declares ValidationException (400). Recorded behavior: CreateTest for the AWS-owned `aws-multi-region-isolation:<id>` template on a service whose resources live in a single Region is refused 400 ValidationException with "The test template requires the service to have resources configured in multiple Regions. Add resources in the required Regions and try again." — fixed text, no interpolation — and no test is created (ListTests stays empty), while the dependency-validation template on the SAME service creates a test.
Emulator: refuses the call, but with the blanket multi-AZ-RTO ValidationException message of Cause 1, i.e. this precondition is not modelled at all; after Cause 1 is fixed the call would instead succeed, which is also wrong.
Why: a client is given the wrong remediation (change the policy, not the Regions), and once the blanket refusal is removed a multi-Region test would be accepted for a single-Region service, so the emulator would mint test state AWS refuses.
Fix: the CreateTest handler's per-template precondition validation — add the multi-Region-resources precondition for the multi-Region isolation template, keyed on the service's configured Regions, and raise ValidationException with AWS's fixed sentence, creating nothing.
Traces: resiliencehubv2.multi-region-template-rejected-for-a-single-region-service.

--- Cause 5 of 7: UpdateTest does not validate stopConditions — source 'none' carrying a value must be refused. ---
AWS: Smithy: StopCondition has REQUIRED members `source` (enum StopConditionSource) and `value` (String); UpdateTest is POST /v2/update-test and declares ValidationException (400). Recorded behavior: a stop condition whose `source` is `none` must carry an EMPTY `value`; UpdateTest with `{"source": "none", "value": "<anything non-empty>"}` is refused 400 ValidationException with "Stop condition with source 'none' must not have a value." — fixed text, with the source name as its only variable part — and the test keeps the stop conditions it already had. The same source with `value` "" is accepted and stored verbatim; a `aws:cloudwatch:alarm` source with an alarm ARN round-trips through GetTest unchanged.
Emulator: unobservable, because the check's setup CreateTest is refused by Cause 1, so the stop-condition path is never reached and no stop-condition validation exists on the UpdateTest path. Fixing Cause 1 alone leaves this check failing.
Why: a client can store a self-contradictory stop condition (source none with a value) that AWS rejects, so a test configuration that the emulator accepts cannot be applied against real AWS, and a refused update must not partially mutate stored stop conditions.
Fix: UpdateTest's (and CreateTest's) stopConditions validation, plus the test state's stop-condition storage so a refused update leaves prior stop conditions intact.
Traces: resiliencehubv2.stop-condition-with-source-none-rejects-a-value.

--- Cause 6 of 7: UpdateTest does not validate the parameter map against the template's parameter contract, and must replace rather than merge it. ---
AWS: Smithy: UpdateTest.parameters is a TestParameters map (max 20 entries, values StringList); the named TestTemplate declares the parameter set (`parameters`, each with a name and a required flag). Recorded behavior, each with its own fixed-text ValidationException (400) message whose variable parts come from the request and the template's parameter schema: a non-integer value for an integer parameter -> "Parameter '<parameterName>' must be a valid integer."; a parameter the template does not declare -> "Unknown parameter provided. Valid parameters for this template: <comma-separated, alphabetically sorted template parameter names>."; more values than a single-valued parameter allows -> "Parameter '<parameterName>' exceeds maximum of <max> values."; a required parameter omitted -> "The '<parameterName>' parameter is required.". Each refused UpdateTest leaves the stored parameter map exactly as it was. A successful UpdateTest carrying `parameters` REPLACES the whole map (a key omitted from the request is removed, not retained), while an UpdateTest that omits `parameters` entirely keeps the map and applies only the other members (e.g. roleName).
Emulator: unobservable, because the setup CreateTest is refused by Cause 1; no UpdateTest parameter validation or replace-semantics behavior is exercised. Fixing Cause 1 alone leaves these two checks failing.
Why: a client that submits an unknown, mistyped, over-filled or missing template parameter gets no refusal (or the wrong one), so invalid test configurations are accepted and the wrong member is blamed; and merge-instead-of-replace semantics silently retain parameters the client intended to drop, so the test runs with parameters the client never asked for.
Fix: UpdateTest's input validation against the resolved test template's parameter schema (one message per class above, nothing mutated on refusal) and UpdateTest's state update so a present `parameters` member replaces the map wholesale while an absent one leaves it untouched.
Traces: resiliencehubv2.test-parameters-rejected-when-they-break-the-template-contract, resiliencehubv2.update-test-replaces-the-parameter-map.

--- Cause 7 of 7: assertion service events carry a generated description instead of the assertion's text. ---
AWS: Smithy: ListServiceEvents (GET /v2/list-service-events) returns ServiceEvent items whose `eventDetails` is a ServiceEventDetails with REQUIRED `title` and `description` plus the `eventMetadata` union (which declares `assertionCreated`, `assertionUpdated`, `assertionDeleted`). Recorded behavior: CreateAssertion, UpdateAssertion and DeleteAssertion each append exactly one event (ASSERTION_CREATED / ASSERTION_UPDATED / ASSERTION_DELETED) naming the service, with `eventMetadata` = {<assertionCreated|assertionUpdated|assertionDeleted>: {assertionId: <id>}} and a `description` that is the assertion's TEXT AS IT STOOD AT THAT MOMENT for the created and updated events (i.e. the text passed to CreateAssertion, then the text passed to UpdateAssertion), and the fixed string "Assertion deleted" for the deleted event. The description is therefore request-derived state, not a generated sentence.
Emulator: ASSERTION_CREATED carries the description "Assertion <assertionId> was created." — a generated sentence interpolating the assertion id — instead of the assertion's text; the assertion's own text appears nowhere in the event.
Why: the service-event log is the audit surface for assertion changes. A client reading ListServiceEvents to show what an assertion said when it was created or edited gets an id-echo instead of the text, so audit/history views lose the only information the event exists to carry, and the same defect shape applies to the updated event.
Fix: the assertion-event recording in the CreateAssertion/UpdateAssertion/DeleteAssertion handlers (or the shared service-event writer) — set ServiceEventDetails.description from the assertion's text at the time of the event, and to the fixed "Assertion deleted" on delete, rather than formatting a sentence from the assertion id.
Traces: resiliencehubv2.assertion-lifecycle-is-recorded-in-service-events.
