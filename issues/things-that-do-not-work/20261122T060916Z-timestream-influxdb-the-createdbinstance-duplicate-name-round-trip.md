# timestream-influxdb: the CreateDbInstance duplicate-name round trip STILL never converges — each DB-instance settle is owed TRANSITION_SPAN (3 s) from the announcing call, so a polling client pays a full probe interval per transition and create → AVAILABLE → delete → re-create → AVAILABLE cannot finish

## Operation
CreateDbInstance

## Description
One net-new root cause in the timestream-influxdb emulator, grounded in the only failing check of this service that is neither ALREADY FILED nor OWNED by an open issue (the other two timestream-influxdb failures are OWNED by 20261116T094729Z-timestream-influxdb-an-available-instance-s-influxdb-v2.md and 20261121T231652Z-timestream-influxdb-the-restorefromdbbackup-round-trip-still-never.md, and both cloudformation__timestream-influxdb failures are OWNED by 20261109T183400Z-cloudformation-timestream-influxdb-aws-timestream-influxdbinstance-is-not.md).

Recurrence note (not a refusal, so not a REOPENS: every call in the sequence answers 2xx and no assertion fails): the resolved issue 20261113T092956Z-timestream-influxdb-the-createdbinstance-duplicate-name-restore-round.md was filed from this exact check and claimed this exact workflow fixed. Its visible effect in the checkout is only that TRANSITION_SPAN was moved (now `pub const TRANSITION_SPAN: Duration = Duration::from_secs(3);`), which is still well above a loopback round trip, so the check it was filed from fails identically with `Check timed out after 60.0s`. A resolved issue does not cover a still-failing check, so it is re-filed here. The ConflictException message cause of open issue 20261109T183400Z-timestream-influxdb-2-net-new-causes-createdbinstance-duplicate.md is no longer what this check fails on — `state.rs::name_already_exists` now renders AWS's template — and that issue's replay keys (the Message AssertionError and the published-endpoint rejection) do not carry this timeout signature, so it does not cover this cause either.

Cause 1 of 1: the DB-instance lifecycle this service announces is not REACHABLE by a client that polls GetDbInstance, because every owed settle is dated TRANSITION_SPAN after the call that announced the transition rather than being due by the poller's next read. The create → AVAILABLE → delete (name freed) → identical re-create → AVAILABLE round trip therefore cannot complete: each of the two CREATING→AVAILABLE transitions costs the client one whole probe interval, and the check that walks exactly that sequence is cut off as `Check timed out after 60.0s` before the restored instance's terminal status is ever observed.

AWS: Smithy (services/service-com-amazonaws-timestreaminfluxdb-amazontimestreaminfluxdb/smithy-model/...json) — CreateDbInstance (idempotent) requires `name` (DbInstanceName, @length 3..40, @pattern ^[a-zA-Z][a-zA-Z0-9]*(-[a-zA-Z0-9]+)*$), `password`, `dbInstanceType`, `vpcSubnetIds`, `vpcSecurityGroupIds`, `allocatedStorage`, and returns required `id`/`name`/`arn` plus `status` (enum Status) and models ConflictException (client, httpError 409); GetDbInstance is @readonly, returns the same record and models ResourceNotFoundException (404); DeleteDbInstance returns the record and models ConflictException (409) + ResourceNotFoundException (404). The TRANSITION TIMING itself is recorded behavior only (a real instance takes minutes): what the recording establishes as the requirement is that each transient status actually settles and is observable through a polled read — CreateDbInstance's record leaves CREATING for AVAILABLE, DeleteDbInstance frees the name and the id stops resolving, and the identical CreateDbInstance is then accepted and returns a NEW `id` with status CREATING which in turn reaches AVAILABLE — so a client's wait loop terminates. The name conflict is a STATE (a live instance owns the name), not an always-invalid input.

Emulator: the sequence does not converge inside any budget proportional to an emulator's speed. Verdict [mismatch], detail `Check timed out after 60.0s`; no error code, no non-2xx and no AssertionError, so the whole budget was spent inside the check's poll loops. The timing is the emulator's own choice: src/state.rs declares `TRANSITION_SPAN: Duration = Duration::from_secs(3)` with a doc comment stating it is deliberately "WELL ABOVE the round trip a client needs to issue its next request"; `DbInstance::begin_transition` sets `settles_at = Some(now + TRANSITION_SPAN)` and `DbInstance::settle` flips to AVAILABLE only once `now >= settles_at`, materialised lazily on a reporting read. A polling client's FIRST read after CreateDbInstance therefore still observes CREATING and it then sleeps a whole probe interval; this scenario chains two such transitions (the original instance and the re-created one) at a 30 s probe interval each — 60 s of pure client sleeping against a 60 s budget — so the final AVAILABLE can never be observed. (DeleteDbInstance, src/ops/delete_db_instance.rs, removes the record and releases the name index immediately and reports DELETING, so the delete leg costs the poller nothing; the two create legs are where the budget goes.) Single-transition checks of this service still fit, which is why 16 of 19 pass.

Why: a client cannot use the ordinary create-if-absent / re-provision pattern against this emulator. It creates an instance, correctly gets the 409 for the duplicate name, and then hangs on readiness: the conflict reads as permanent rather than as the transient state AWS makes it, and nothing distinguishes "still provisioning" from "never going to settle". This is the failure mode SDK waiters, `aws ... wait`-style loops and infrastructure tools consume asynchronous lifecycles with — no error to handle, just a workflow that runs until the caller's own deadline while the emulator reports no failure at all.

Fix: the DB-instance lifecycle-settle timing in this service's state — `TRANSITION_SPAN`, `DbInstance::begin_transition` and `DbInstance::settle` in the service crate's src/state.rs, as consumed by the CreateDbInstance handler and by the reporting reads (GetDbInstance / ListDbInstances). The owed transition must already be DUE by the time a polling client's NEXT read arrives, while the transient status stays observable in the announcing call's own response — e.g. settle on the first reporting read that FOLLOWS the announcing call (count reads rather than wall-clock seconds) so a chained create → delete → re-create workflow costs no probe interval per transition. Moving a wall-clock span alone cannot satisfy both halves, which is why the previous attempt did not converge. The same timing is what open issue 20261121T231652Z reports for the backup/restore chain; fixing the span in one place must cover both, but that issue's replay key does not carry this check.

## Steps to Reproduce
1. Boot the emulator and create the networking prerequisites via EC2 (a VPC with at least two subnets and a security group).
2. CreateDbInstance(name=<N>, password=<8-64 chars matching ^[a-zA-Z0-9]+$>, dbInstanceType="db.influx.medium", vpcSubnetIds=[<subnet-a>,<subnet-b>], vpcSecurityGroupIds=[<sg>], allocatedStorage=20, dbStorageType="InfluxIOIncludedT1", deploymentType="SINGLE_AZ", tags={...}); keep the returned `id`. Expect status CREATING.
3. CreateDbInstance again with the identical `name` and a different password; expect 409 ConflictException, Message "The DbInstance with id [<the first id>], name [<N>], customer [<account id>] already exists".
4. ListDbInstances and confirm exactly one instance owns <N>, the original id.
5. Poll GetDbInstance(identifier=<id>) every 30 s until `status` is AVAILABLE or FAILED. Note the FIRST read, issued immediately after step 2, still reports CREATING (the settle is owed 3 s after the announcing call), so the loop sleeps a full 30 s.
6. DeleteDbInstance(identifier=<id>) and poll GetDbInstance until the id no longer resolves (ResourceNotFoundException) or reports DELETED.
7. CreateDbInstance with the identical name <N>; expect success with a NEW id and status CREATING, then poll GetDbInstance every 30 s until AVAILABLE.
   EXPECTED: the whole sequence converges — exactly one instance owns the freed name, its id differs from the original, and it reports AVAILABLE.
   ACTUAL: each CREATING→AVAILABLE transition costs the poller a full probe interval (30 s + 30 s = 60 s of sleeping), so the sequence cannot finish inside the suite's 60 s per-check budget; the run ends as `Check timed out after 60.0s` with no error and no failed assertion, and the re-created instance's terminal status is never observed.
