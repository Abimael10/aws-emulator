# s3__sagemaker: 2 net-new causes — a Completed processing job never uploads its S3Output LocalPath to S3, and a training job whose ContainerEntrypoint is python3 never runs

> _Note: this issue was identified against the code base at commit `76dad09634cc65ae9776af758f347397530b73a6`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
CreateProcessingJob

## Description
Two net-new root causes on the SageMaker-job-over-S3 surface; a fixer must close both. The emulator's job executor has clearly moved on since the earlier job-execution issues were written (the 'no container runtime' FailureReason is gone and a /bin/sh job now reaches Completed), so neither of these is covered by the open issue 20261029T211510Z-s3-sagemaker-sagemaker-jobs-never-execute-and-are-never-validated.md nor by the fixed issues 20261029T203709Z-sagemaker-an-accepted-createtrainingjob-is-never-executed-the.md / 20261102T115206Z-sagemaker-endpoint-lifecycle-check-blocked-an-accepted-createtrainingjob.md: those describe neighbouring symptoms but do not carry the replay keys listed here, and the failing assertions below are at different points in the checks than the keys they hold.

Cause 1 of 2: a processing job that reaches ProcessingJobStatus=Completed uploads nothing from its ProcessingOutputConfig output LocalPath to the declared S3Uri.
AWS: for a ProcessingOutput with S3Output (AppManaged absent/false), SageMaker itself performs the output upload. Smithy: ProcessingOutput.AppManaged — "When False (default), output operations are managed by Amazon SageMaker"; ProcessingS3Output.LocalPath — "The local path of a directory where you want Amazon SageMaker to upload its contents to Amazon S3 ... This directory will be created by the platform and exist when your container's entrypoint is invoked"; ProcessingS3Output.S3UploadMode (ProcessingS3UploadMode) = EndOfJob means every file the container wrote under LocalPath is uploaded under S3Uri when the job finishes. So after a job whose entrypoint writes /opt/ml/processing/output/file_1.txt .. file_3.txt reaches Completed, ListObjectsV2 under the output prefix returns exactly one key per file written, each GetObject returning the bytes the container wrote. Key names and bodies are whatever the container wrote — the requirement is "one object per file under LocalPath, at S3Uri + the file's relative path, with identical content", not the particular names in any one recording.
Emulator: the job settles Completed (the status assertion passes), but the output prefix is empty. s3__sagemaker.sagemaker-processing-job-writes-s3-output-positive: `assert keys == ["output/file_1.txt", "output/file_2.txt", "output/file_3.txt"]` fails with `AssertionError: []`. s3__sagemaker.sagemaker-processing-job-s3-output-bucket-policy-blocks-write-negative gets past `desc_ok["ProcessingJobStatus"] == "Completed"` and then GetObject of the single declared output object raises `botocore.errorfactory.NoSuchKey: An error occurred (NoSuchKey) when calling the GetObject operation: The specified key does not exist.` Because no upload is ever attempted, the bucket-policy negative in that same check can never reach its verdict either: there is no PutObject for the explicit Deny on s3:PutObject to refuse, so the denied job cannot end Failed with an AccessDenied FailureReason and is indistinguishable from the allowed one.
Why: a client that waits for ProcessingJobStatus=Completed and then reads the declared S3Uri gets NoSuchKey / an empty listing for data AWS guarantees is there — the most common SageMaker Processing contract (write to LocalPath, read from S3) silently produces nothing, and any downstream step (a pipeline, a training job consuming the processed data) blocks or fails on absent input. A Completed status that is not backed by the output upload is worse than a Failed job: it reports success for work that did not happen.
Fix: the CreateProcessingJob execution path — the end-of-job output stage that must walk each ProcessingOutputConfig.Outputs[].S3Output.LocalPath and upload its contents to S3Uri (honouring S3UploadMode and the job's output KMS key), and the authorization of those writes under the job's RoleArn plus the destination bucket policy, so that a denied write ends the job Failed with an AccessDenied FailureReason instead of being skipped.
Traces: s3__sagemaker.sagemaker-processing-job-writes-s3-output-positive, s3__sagemaker.sagemaker-processing-job-s3-output-bucket-policy-blocks-write-negative

Cause 2 of 2: a training job whose AlgorithmSpecification.ContainerEntrypoint names `python3` is never executed — the emulator's in-process program executor knows no such program, so the job leaves InProgress without doing any work.
AWS: Smithy: AlgorithmSpecification.ContainerEntrypoint — "The entrypoint script for a Docker container used to run a training job. This script takes precedence over the default train processing..." with ContainerArguments supplying its arguments. The SageMaker built-in XGBoost image (<account>.dkr.ecr.<region>.amazonaws.com/sagemaker-xgboost:<version>) is a standard Python environment, so ContainerEntrypoint ["python3"] + ContainerArguments ["-c", <script>] runs that script inside the container; the script reads the channel data mounted at /opt/ml/input/data/<ChannelName>/ and writes to /opt/ml/model. The job then reaches TrainingJobStatus=Completed and DescribeTrainingJob.ModelArtifacts.S3ModelArtifacts names the archive of /opt/ml/model under OutputDataConfig.S3OutputPath (Smithy ModelArtifacts: "A SageMaker container stores your trained model artifacts in the /opt/ml/model directory. After training has completed, by default, these artifacts are uploaded to your Amazon S3 bucket as compressed files").
Emulator: the job does not complete. DescribeTrainingJob returns a non-Completed status with FailureReason "This emulator performs a job's declared container program itself and provides no program named \"python3\", so the container's program was never started and the job performed no work." (fixed text; the quoted program name is taken from the request's ContainerEntrypoint). The check's assertion `result_good["TrainingJobStatus"] == "Completed"` fails with that reason. The same check's synchronous-rejection half now passes, so this is the only remaining divergence in it: the emulator executes a declared container program only when it recognises the program name (a /bin/sh entrypoint completes, see Cause 1), and every entrypoint it does not recognise — python3 first among them, since that is what both the built-in algorithm images and every bring-your-own-script training job use — is dropped instead of run.
Why: a client that submits the standard "override the entrypoint with python3 -c / python3 train.py" training job never gets Completed and never gets a model artifact, and the FailureReason it is handed describes the emulator's own executor rather than anything about the job, so the failure is not actionable and cannot be distinguished from a genuine algorithm error.
Fix: the CreateTrainingJob execution path — the in-process container-program executor behind AlgorithmSpecification.ContainerEntrypoint/ContainerArguments (it must support the python3 interpreter the built-in images provide, with the channel data materialised under /opt/ml/input/data/<ChannelName>/ and /opt/ml/model collected afterwards), the terminal status it sets, and the FailureReason it reports.
Traces: s3__sagemaker.cli-sagemaker-invalid-s3-input-uri-negative

## Evidence
Cause 1:
- s3__sagemaker.sagemaker-processing-job-writes-s3-output-positive — expected: after the processing job reaches Completed, ListObjectsV2(Bucket=<out>, Prefix="output/") returns one key per file the container wrote under /opt/ml/processing/output (three, here "output/file_1.txt", "output/file_2.txt", "output/file_3.txt"), each body equal to what the container wrote. Actual: `AssertionError: []` — the prefix is empty although ProcessingJobStatus == "Completed".
- s3__sagemaker.sagemaker-processing-job-s3-output-bucket-policy-blocks-write-negative — expected: the allowed role's job Completed and its one declared output object readable, then the Denied role's job Failed with "AccessDenied" in FailureReason and nothing under its prefix. Actual: the allowed job reports Completed, then `botocore.errorfactory.NoSuchKey: An error occurred (NoSuchKey) when calling the GetObject operation: The specified key does not exist.` on the declared output object — no upload was attempted at all, so the Deny-on-PutObject verdict is never reached.

Cause 2:
- s3__sagemaker.cli-sagemaker-invalid-s3-input-uri-negative — expected: the positive-control CreateTrainingJob (built-in XGBoost image, ContainerEntrypoint ["python3"], ContainerArguments ["-c", <script that counts lines of /opt/ml/input/data/train/* and writes /opt/ml/model/artifact.txt>]) reaches TrainingJobStatus "Completed" and ModelArtifacts.S3ModelArtifacts points at a model archive containing artifact.txt. Actual: `AssertionError: positive control did not complete: This emulator performs a job's declared container program itself and provides no program named "python3", so the container's program was never started and the job performed no work.`

## Steps to Reproduce
Replay the behavioral suite and run the three checks in trace_ids.

Cause 1: create an S3 bucket and an IAM role trusted by sagemaker.amazonaws.com with s3:PutObject/s3:ListBucket on it. Call CreateProcessingJob with AppSpecification.ContainerEntrypoint ["/bin/sh","-c"] and a ContainerArguments command that writes files under /opt/ml/processing/output, and ProcessingOutputConfig.Outputs = [{OutputName, S3Output:{S3Uri: s3://<bucket>/output/, LocalPath: /opt/ml/processing/output, S3UploadMode: EndOfJob}}]. Poll DescribeProcessingJob to Completed, then ListObjectsV2 under "output/" and GetObject each file — observe an empty listing / NoSuchKey. Repeat with a bucket policy that explicitly Denies s3:PutObject to the job role's ARN and observe the job still does not end Failed with an AccessDenied FailureReason.

Cause 2: upload a CSV to s3://<bucket>/train/valid.csv, then CreateTrainingJob with AlgorithmSpecification = {TrainingImage: the region's built-in sagemaker-xgboost ECR image, TrainingInputMode: "File", ContainerEntrypoint: ["python3"], ContainerArguments: ["-c", "<script reading /opt/ml/input/data/train/* and writing /opt/ml/model/artifact.txt>"]}, one S3Prefix input channel named "train", and OutputDataConfig.S3OutputPath. Poll DescribeTrainingJob to a terminal status — observe it is not Completed and FailureReason reports that the emulator provides no program named "python3".
