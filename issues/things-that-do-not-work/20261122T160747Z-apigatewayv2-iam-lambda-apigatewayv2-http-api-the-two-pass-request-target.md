Cause 1 of 1: an HTTP API with an AutoDeploy `$default` stage, six explicit route keys and a Lambda AWS_PROXY (payload format 2.0) integration never answers the routed literal `GET /items` with the integration's own document, so the two-pass percent-decode / dot-segment-normalisation-before-route-selection contract cannot be observed at all; the check exhausts the harness budget with no verdict. Failing check id: apigatewayv2__iam__lambda.http-api-request-target-decoded-twice-and-normalised-before-route-selection.

AWS: the control plane here is modelled — Smithy (services/service-com-amazonaws-apigatewayv2-apigatewayv2/smithy-model/com-amazonaws-apigatewayv2-apigatewayv2.json): `CreateRoute` http {method: POST, uri: "/v2/apis/{ApiId}/routes", code: 201} with `RouteKey` (SelectionKey, @required) and `Target`; `CreateStage` http {method: POST, uri: "/v2/apis/{ApiId}/stages", code: 201} with `AutoDeploy` (__boolean, jsonName autoDeploy) and `StageName` (@required); `GetRoutes` http {method: GET, uri: "/v2/apis/{ApiId}/routes", code: 200}. Errors modelled on all three: BadRequestException 400, NotFoundException 404, TooManyRequestsException 429 (CreateRoute/CreateStage additionally ConflictException 409). The execute-api DATA plane is NOT in the model, so for it this is recorded behavior only: a `$default` stage created with AutoDeploy=true serves its routes immediately, and a declared literal route key (`GET /items`) is answered 200 by the integration — the response carries the integration's own body and headers, not a gateway envelope. On that same data plane AWS decodes the request target exactly TWICE before route selection and then matches: `/items/a%41b` selects `GET /items/{id}` with rawPath `/items/aAb` and pathParameters `{"id":"aAb"}`; `/items/a%2541b` reaches the same decoded form on the second pass; `/items/a%252541b` stops at rawPath `/items/a%41b`. A target that decodes to a MALFORMED escape on the second pass (`/items/a%25b`) is refused 400 with the gateway's own envelope body `{"message":"Bad Request"}` (that whole body is fixed text — it has no variable parts), content-type `application/json`, a `content-length` equal to those 23 bytes, an `apigw-requestid` header, and no header from the integration; `/items/a%2525b` is served 200. `%2F` does not separate path segments, a trailing slash is significant, and dot/empty segments are removed before matching. An unrouted target on an API with no `$default` and no root greedy route is refused 404 with the gateway envelope `{"message":"Not Found"}` (fixed text) under the same header rules.

Emulator: the replay detail for this check is only `Error: Check timed out after 60.0s` — no status, no body, no error code is ever produced. The check's very first data-plane step is a warm-up/leg-4 poll that holds until `GET /items` answers 200 twice in a row carrying the backend's stamped document (its own internal budget is 180 s, far beyond the 60 s harness cap), and every subsequent leg polls the same stage. Because nothing on that stage ever answers with the integration's stamped 200, the poll loop retries until the run budget ends and the whole decode/normalise contract — the two decode passes, the 400 `{"message":"Bad Request"}` refusal on a malformed second pass, `%2F` not splitting segments, trailing-slash significance, dot-segment normalisation, and the rawPath / requestContext.http.path / pathParameters / rawQueryString mirroring — is never exercised. Hypothesis: the auto-deployed `$default` stage of an HTTP API either is not reachable on the address the control plane publishes for it, or serves a gateway refusal rather than dispatching to the AWS_PROXY integration; this is consistent with the sibling check in the same group failing on the published invoke host (`AssertionError: the invoke host '127.0.0.1' must be this API's own hostname, whose first label is the API id`). The control-plane legs that precede it pass: GetRoutes reports exactly the six created route keys.

Why: a client relying on AWS's behavior gets two wrong answers. First, a deployed HTTP API route that AWS answers 200 from its Lambda proxy returns nothing at all here, so any application fronted by an HTTP API is unserviceable and hangs rather than failing fast. Second, because the scenario never terminates, the entire request-target contract is silently unverifiable: a handler that reads `rawPath`, `requestContext.http.path` or `pathParameters` cannot be shown to receive the decoded, normalised target AWS produces, route selection for encoded targets is untested, and the request AWS refuses with 400 `{"message":"Bad Request"}` is indistinguishable from a stage that simply never answers. A real regression in decoding or in route matching would look identical to this timeout.

Fix: the execute-api front door for HTTP APIs and its route-selection path — the stage dispatcher must serve an AutoDeploy `$default` stage on the address the control plane publishes for the API and hand a matched route to its AWS_PROXY integration; the target handling in that path must percent-decode the request target in exactly two passes (refusing a malformed escape on either pass with the gateway's own 400 `{"message":"Bad Request"}` envelope, `application/json`, matching content-length, an `apigw-requestid` header and no integration header), remove dot and empty segments before matching route keys, keep `%2F` from splitting segments and the trailing slash significant, and build `rawPath`, `requestContext.http.path` and `pathParameters` from the decoded normalised target while leaving `rawQueryString` encoded. The unrouted case must be the gateway's 404 `{"message":"Not Found"}` envelope.
