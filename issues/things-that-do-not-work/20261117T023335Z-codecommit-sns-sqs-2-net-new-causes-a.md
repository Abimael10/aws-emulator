# codecommit__sns__sqs: 2 net-new causes — a real ref update fires no repository trigger (nothing reaches the subscribed queue), and the TestRepositoryTriggers record's eventName is 'ReferenceChanges' instead of 'TriggerEventTest'

> _Note: this issue was identified against the code base at commit `da1bdaf0970a5b39397b846da655b4a2fa6e7dc9`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
PutRepositoryTriggers

## Description
TWO net-new root causes behind the two codecommit__sns__sqs trigger checks, both in the codecommit crate's trigger-notification path. A fixer must close BOTH before submitting.

=== Cause 1 of 2: a configured repository trigger produces no notification when a reference actually changes ===
AWS: Smithy com-amazonaws-codecommit-codecommit-20150413 — `RepositoryTrigger$events` (`RepositoryTriggerEventEnum`: `all`, `updateReference`, `createReference`, `deleteReference`), `RepositoryTrigger$branches` ("if you specify an empty array, the trigger applies to all branches") and `RepositoryTrigger$destinationArn` ("The ARN of the resource that is the target for a trigger (for example, the ARN of a topic in Amazon SNS)"). A write that moves a reference a stored trigger is in scope for publishes one record to that destination; a write on a branch the trigger does not list publishes nothing. Recorded behavior for the record: one `Records` entry with `eventSource` `aws:codecommit`, `eventName` `ReferenceChanges`, `eventSourceARN` = the repository ARN, `eventTriggerName` = the trigger's `name`, `eventTriggerConfigId` = the `configurationId` `PutRepositoryTriggers` returned, and `codecommit.references[0]` = {`ref`: `refs/heads/<branch>` (fully qualified, not the short branch name), `commit`: the exact commit id the write created}. One run's commit ids/names/config id fill that template and are not part of it.
Emulator: nothing is published for a real reference change. The only producer of a trigger record in the crate is `crate::state::trigger_notifications::test_notifications`, called only from the `TestRepositoryTriggers` handler. `PutFile` writes the commit, calls `repository.set_branch_tip(..)` and then only `crate::state::pull_request_events::publish_all_detached(..)`; it never reads `repository.trigger_configuration`, so no SNS `Publish` happens. `CreateCommit`, `CreateBranch`, `DeleteBranch`, `DeleteFile`, the merge handlers and the git push path are the same.
Why: a client using the standard CodeCommit→SNS→SQS notification wiring receives nothing for any real commit, while both `GetRepositoryTriggers` and `TestRepositoryTriggers` report a healthy trigger — so the failure is invisible from the API. Negative expectations are equally unobservable: it is impossible to distinguish "the unlisted branch correctly published nothing" or "the queue policy correctly suppressed delivery" from "nothing is ever published", which is what these two checks exist to tell apart.
Fix: the reference-moving write path of the codecommit service. The one place a branch tip moves (`crate::state::Repository::set_branch_tip`, used by `PutFile`, `CreateCommit`, `CreateBranch`, `DeleteBranch`, `DeleteFile`, the merge handlers and `crate::service::git_http`) must, with the store guard released, select the stored configuration's triggers matching the moved branch (listed, or an empty `branches`) and the event class (`all` plus the matching `createReference`/`updateReference`/`deleteReference`), render the record `crate::state::trigger_notifications` already renders — with the STORED `configurationId` — and send it through the existing `TriggerNotification::send` seam. Delivery must then follow the destination topic's own subscriptions and each subscriber's resource policy, so a queue whose policy does not allow the publishing topic receives nothing while its correctly scoped twin receives every record.
Traces: codecommit__sns__sqs.repository-trigger-fires-on-a-real-ref-update, codecommit__sns__sqs.trigger-notification-blocked-when-the-queue-policy-denies-the-topic.

=== Cause 2 of 2: the record TestRepositoryTriggers sends carries eventName 'ReferenceChanges', so it is indistinguishable from a record about a reference that really changed ===
AWS: Smithy documents `TestRepositoryTriggers` as "Tests the functionality of repository triggers by sending information to the trigger target. If real data is available in the repository, the test sends data from the last commit. If no data is available, sample data is generated." Recorded behavior: that synthetic record is labelled as a TEST — its `Records[0].eventName` is `TriggerEventTest`, not `ReferenceChanges` — which is exactly how a consumer tells a test probe apart from a real reference change (every other member keeps its normal meaning: `eventSource` `aws:codecommit`, the repository ARN, the trigger name, and a reference/commit pair that may be generated sample data).
Emulator: `crate::state::trigger_notifications` has a single `TRIGGER_EVENT_NAME = "ReferenceChanges"` constant and `record(..)` stamps it on every record, including the one `test_notifications` builds, so a `TestRepositoryTriggers` probe arrives at the destination claiming a reference changed.
Why: a consumer that filters on `eventName` (the documented way to ignore test probes) processes a test as a real event — building, notifying or deploying for a commit id that exists in no repository when the probe is sample data — and a consumer waiting for the test probe never sees one. It also destroys the test's use as a reachability barrier: a client cannot confirm the SNS→SQS leg works without risking counting the probe as a real delivery.
Fix: the record rendering in the codecommit service's trigger-notification state module — the test path must stamp `TriggerEventTest` as the record's `eventName` while the reference-change path (cause 1) stamps `ReferenceChanges`; the constant must stop being shared by both.
Traces: codecommit__sns__sqs.repository-trigger-fires-on-a-real-ref-update.
