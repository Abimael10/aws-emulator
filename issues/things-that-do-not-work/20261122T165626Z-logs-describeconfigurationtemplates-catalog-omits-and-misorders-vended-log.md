# logs DescribeConfigurationTemplates catalog omits and misorders vended-log templates (10 causes)

> _Note: this issue was identified against the code base at commit `53ca3190ddccd906197b0d4d5e8474d7add13c5d`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
DescribeConfigurationTemplates

## Description
Ten independent net-new divergence clusters in CloudWatch Logs DescribeConfigurationTemplates. They share one fault: the emulator serves an emulator-authored vended-logs configuration-template catalog instead of the catalog AWS publishes — whole services are absent, entries are present that AWS does not publish, per-service logType sets and list order differ, and the per-template metadata (allowedFields and their mandatory flags, allowedOutputFormats, defaultDeliveryConfigValues.recordFields, allowedSuffixPathFields, s3TablesIntegration) is generic placeholder data rather than the service's real schema. All ten were replayed on HTTP 200 vs 200, so only the body content diverges.

General requirement (applies to every cause below). AWS: Smithy DescribeConfigurationTemplates takes optional service/logTypes/resourceTypes/deliveryDestinationTypes/nextToken/limit and returns configurationTemplates: list<ConfigurationTemplate> (+nextToken); ConfigurationTemplate members are service, logType, resourceType, deliveryDestinationType (enum S3|CWL|FH|XRAY), defaultDeliveryConfigValues, allowedFields, allowedOutputFormats, allowedActionForAllowVendedLogsDeliveryForResource, allowedFieldDelimiters, allowedSuffixPathFields, deliverySourceConfiguration and s3TablesIntegration. The list is AWS's own published catalog of which (service, resourceType, logType, deliveryDestinationType) combinations are deliverable and of what each one allows; its contents and element order are the behaviour, and the model itself does not enumerate them, so the recorded responses are the reference (recorded behavior only for the per-entry values). Fix for every cause: the seeded static catalog behind the DescribeConfigurationTemplates handler, plus the handler's filter/ordering logic that selects entries from it — not the fixtures' particular service names.

Cause 1 of 10: the catalog contains a template AWS does not publish. AWS: for the filtered request this step issues, the response carries exactly the entries AWS publishes — there is no bedrock / TRACES / agent-alias / XRAY entry in it (expected element at index 24 is absent, i.e. the list is shorter). Emulator: returns an extra element at configurationTemplates[24] = {service: bedrock, logType: TRACES, resourceType: agent-alias, deliveryDestinationType: XRAY, allowedOutputFormats: ['json'], ...}. Why: a client that enumerates deliverable log types to build a delivery (CreateDelivery/UpdateDeliveryConfiguration) is offered a destination/logType pair AWS would refuse, so capability discovery is wrong in the permissive direction. Traces: logs-b2-delivery-source-destination-pipeline#task#2.

Cause 2 of 10: whole services are missing from the catalog. AWS: the response for this filter carries six templates, the first being service 'aidevops' with allowedActionForAllowVendedLogsDeliveryForResource 'aidevops:AllowVendedLogDeliveryForResource', allowedOutputFormats ['plain','json','w3c','parquet'], allowedFieldDelimiters ['\t',' ',','], allowedSuffixPathFields ['accountid','region','resource_id','yyyy','MM','dd','HH'] and its own 22-member allowedFields list. Emulator: elements [0]..[5] are all reported missing — the emulator's catalog has no entry at all for these services. Why: DescribeConfigurationTemplates is how a caller learns a service supports vended-log delivery; with the service absent the caller concludes delivery is impossible. Traces (cluster of 6 steps): logs-catalog-describe-configuration-templates#task#1 (also task#6, task#13, task#17, task#21, task#24).

Cause 3 of 10: allowedOutputFormats is narrowed. AWS: the apigateway / stages / EXECUTION_LOGS / FH template publishes allowedOutputFormats ['plain','json','raw']. Emulator: the same template publishes ['plain','json'] — 'raw' is dropped (reported as a missing+extra pair at index 2). Why: a caller that picks the Raw output format AWS allows is told it is unsupported. Traces: logs-catalog-describe-configuration-templates#task#2.

Cause 4 of 10: for this service filter the emulator's 21-element list diverges element-for-element from AWS's. AWS: index 0 is the autoloop / subscription / ERROR_LOGS / S3 template with allowedOutputFormats ['plain','json','w3c','parquet'], allowedSuffixPathFields ['accountid','region','yyyy','MM','dd','HH'] and defaultDeliveryConfigValues.s3DeliveryConfiguration {suffixPath '{region}/{yyyy}/{MM}/{dd}/{HH}/', enableHiveCompatiblePath false}. Emulator: every index [0]..[20] is flagged — the entries it serves are not AWS's entries at those positions (content and/or ordering of the catalog slice differ). Why: any client indexing or diffing the catalog sees a different capability set than AWS's. Traces (cluster of 2 steps): logs-catalog-describe-configuration-templates#task#3 (also task#22).

Cause 5 of 10: the per-service logType set/order is wrong for bedrock. AWS: index 0 for this filter is service bedrock / resourceType agent-alias / logType EVENT_LOGS / S3. Emulator: index 0 is bedrock / agent-alias / APPLICATION_LOGS / S3, and all 17 indices of the slice are flagged. Why: a caller enumerating a resource's deliverable log types gets a different (and differently ordered) set, so EVENT_LOGS appears unavailable. Traces: logs-catalog-describe-configuration-templates#task#4.

Cause 6 of 10: the bedrock-agentcore slice diverges across all 48 elements. AWS: index 0 is bedrock-agentcore / workload-identity / APPLICATION_LOGS / S3 with its 23-member allowedFields list, allowedSuffixPathFields ['accountid','region','workload_identity_id','yyyy','MM','dd','HH'] and its own 21-field default recordFields. Emulator: every index [0]..[47] is flagged — the served slice is not AWS's. Why: as above; nothing a caller reads about this service's delivery capabilities is accurate. Traces: logs-catalog-describe-configuration-templates#task#5.

Cause 7 of 10: allowedFields / recordFields are a generic placeholder set rather than the service's schema. AWS: the codewhisperer / customization / EVENT_LOGS / S3 template publishes allowedFields [timestamp(optional), event_timestamp(mandatory), resource_id(mandatory), customization_id(optional), log_level(mandatory), event_message(mandatory)], defaultDeliveryConfigValues.recordFields ['event_timestamp','resource_id','log_level','event_message'] and allowedOutputFormats ['plain','json','w3c']. Emulator: it publishes allowedFields [timestamp, resource_arn, resource_id, event_timestamp, log_level, operation, request_id, message(mandatory)], recordFields ['resource_arn','event_timestamp','log_level','operation','request_id','message'] and allowedOutputFormats including 'parquet' — a generic resource_arn/operation/request_id/message skeleton instead of the service's real fields, with the mandatory flags on the wrong members. Why: CreateDelivery validates recordFields against this list, so a caller building a delivery from the published template selects field names the real service does not emit (and is refused fields AWS marks mandatory). Traces (cluster of 10 steps): logs-catalog-describe-configuration-templates#task#7 (also task#8, task#9, task#12, task#15, task#16, task#23, task#25, task#28, task#29).

Cause 8 of 10: EKS log types are wrong. AWS: index 0 for this filter is eks / cluster / AUTO_MODE_LOAD_BALANCING_LOGS / S3. Emulator: index 0 is eks / cluster / AUTO_MODE_BLOCK_STORAGE_LOGS / S3 and all 33 indices of the slice are flagged, so at least one AWS log type is unpublished and the set/order differs. Why: EKS Auto Mode load-balancing log delivery cannot be discovered. Traces: logs-catalog-describe-configuration-templates#task#10.

Cause 9 of 10: the ELB slice omits ALB_CONNECTION_LOGS and never populates s3TablesIntegration. AWS: index 0 is elasticloadbalancing / loadbalancer / ALB_CONNECTION_LOGS / S3, carrying s3TablesIntegration {datasourceName 'aws_alb', datasourceType 'connection'} and the 15-field connection-log schema. Emulator: index 0 is ALB_ACCESS_LOGS with the access-log schema and no s3TablesIntegration member at all; all 12 indices of the slice are flagged. Why: connection-log delivery and the S3 Tables datasource binding are invisible to a caller. Traces (cluster of 2 steps): logs-catalog-describe-configuration-templates#task#11 (also task#20).

Cause 10 of 10: allowedFields carries members AWS does not list. AWS: the events / subscriber / ERROR_LOGS / S3 template's allowedFields are exactly [timestamp, resource_arn, message_timestamp_ms, subscriber_name, request_id, event_id, invocation_id, message_type, log_level, details, error] (all optional). Emulator: it inserts a resource_id member into that list. Why: the published allowedFields set is the contract CreateDelivery's recordFields are validated against, so a caller is offered a field the service never emits. Traces: logs-catalog-describe-configuration-templates#task#14.
