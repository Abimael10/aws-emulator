# AWS managed security-requirement catalog descriptions are paraphrased, not the service text

> _Note: this issue was identified against the code base at commit `d26390c9b72db2589fa327994590745892c0adba`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
ListSecurityRequirements

## Description
Three net-new root causes, one per AWS managed security-requirement pack whose seeded catalog content the emulator serves. In each case ListSecurityRequirements answers HTTP 200 with the right pack, the right requirement NAMES, the right page size and the right pagination behaviour — every divergence is confined to the `description` member of the SecurityRequirementSummary entries, which carries a rewritten paraphrase of the requirement instead of the text the service publishes for that requirement. The shared fault is that the seeded AWS-managed requirement bodies were re-authored rather than reproduced, so the catalog is structurally right and textually wrong across every managed pack.

General form of the defect: `description` is a @required String member of SecurityRequirementSummary documented only as "A description of the security requirement" — the model constrains neither its length nor its content, so the recorded responses are the authority for it. These are AWS-MANAGED packs: their requirement names and bodies are service-published catalog content, identical in every account and region and not derived from the request, from generated ids or from a clock. That makes each description a fixed string the emulator must reproduce verbatim, exactly like a fixed error message: nothing in the response varies per run, so there is no template to fill and no per-run value to excuse the difference. The emulator instead serves its own summary of each requirement — same topic, different sentences: it compresses the enumerated specifics (the examples, the named mechanisms, the clauses that say what the design must demonstrate), swaps the pack's house phrasing ("Workloads should be designed to ...", "Workloads that ... should ...", "Architecture documents must define ...") for a different voice, and in places adds clauses the published text does not contain.

Cause 1 of 3 (fixture securityagent-catalog-list-security-requirements, step task#2, ListSecurityRequirements): the workload-cybersecurity / NIST-CSF-style managed pack. Every requirement on the page diverges on `description` — 37 names, from "adverse-event-analysis-and-threat-intelligence-integration" through "workload-third-party-dependency-risk-management".
AWS: recorded behavior only (Smithy: ListSecurityRequirements POST /ListSecurityRequirements -> 200; output securityRequirementSummaries: SecurityRequirementSummaryList @required; SecurityRequirementSummary.description: String @required, "A description of the security requirement"). For "adverse-event-analysis-and-threat-intelligence-integration" the published description is 'Workloads should be designed to support the detection and analysis of anomalies, indicators of compromise (IoCs), and other potentially adverse events. This includes emitting sufficient telemetry from all workload components to enable multi-source correlation, integrating cyber threat intelligence (CTI) to contextualize observed anomalies against known tactics, techniques, and procedures (TTPs), and establishing defined criteria for escalating adverse events to formal incident declarations. The design should ensure that adverse event information flows to authorized personnel and automated response tooling in a timely manner, enabling accurate impact and scope estimation.' This whole string is fixed text: it has no variable part, because the requirement is catalog content, not a per-request value.
Emulator: HTTP 200, same name, but description is 'Workloads should be designed to support the detection and analysis of anomalies, indicators of compromise (IoCs), and other potentially adverse events. This includes emitting telemetry sufficient for correlation across multiple sources, integrating cyber threat intelligence to contextualize anomalies against known adversary tactics, techniques and procedures (TTPs), recording the characterization each event received, and establishing defined criteria for escalating adverse events to formal incident declarations.' — the middle clauses are reworded, 'recording the characterization each event received' is added, and the entire final sentence about adverse-event information flowing to authorized personnel and automated response tooling for impact and scope estimation is dropped. The same kind of rewrite is reported for the other 36 names on the page (for example "ai-component-risk-assessment-and-security-integration").

Cause 2 of 3 (fixture securityagent-catalog-list-security-requirements, step task#3, ListSecurityRequirements): the PCI-DSS managed pack. Every requirement on the page diverges on `description` — 50 names, from "account-data-classification-and-retention-controls" through "vulnerability-identification-and-patch-management".
AWS: recorded behavior only, same model citation. The published text for this pack is written as workload-design guidance — for "account-data-classification-and-retention-controls": 'Workloads that store, process, or transmit payment account data should clearly identify and classify cardholder data (CHD) elements—including PAN, cardholder name, expiration date, and service code—and sensitive authentication data (SAD) elements—including full track data, card verification codes, and PINs/PIN blocks. The architecture should enforce that SAD is never retained after transaction authorization, even in encrypted form. PAN, if stored post-authorization, should be rendered unreadable through cryptographic means or equivalent protection. Third-party services handling account data on behalf of the workload should be subject to documented accountability for data protection.' Fixed text throughout, including the em-dash-delimited enumerations of the CHD and SAD elements.
Emulator: HTTP 200 with 'All stored account data must be identified and classified into cardholder data (CHD) and sensitive authentication data (SAD) elements, and kept only for as long as a documented business need requires. Sensitive authentication data must not be retained after authorization completes, even when it is encrypted, and a stored primary account number must be rendered unreadable wherever it is held. The retention period for each element, the data it covers and the process that deletes or renders unrecoverable the data no longer needed must be documented and enforced.' — restated as PCI control language ("All stored account data must ...") rather than the catalog's workload-scoped guidance, dropping the enumerated CHD/SAD element lists and the third-party accountability clause and adding retention-documentation clauses the published text does not carry. The same rewrite is reported for the other 49 names on the page (for example "anti-malware-protection-for-workload-components").

Cause 3 of 3 (fixture securityagent-catalog-list-security-requirements, step task#4, ListSecurityRequirements): the architecture-review managed pack. Every requirement on the page diverges on `description` — 32 names, from "authenticated-network-communication-architecture" through "traffic-inspection-architecture".
AWS: recorded behavior only, same model citation. Every description in this pack is phrased as a statement about the architecture document — for "authenticated-network-communication-architecture": 'Architecture documents must define how network communications are authenticated to verify the identity of communicating parties. The design must specify authentication mechanisms for service-to-service communications (east-west traffic) and external communications (north-south traffic), rejecting the principle that network boundaries alone provide sufficient trust. The architecture must demonstrate authentication through cryptographic protocols (TLS with certificate validation, mutual TLS, IPsec) or identity-based authentication mechanisms (AWS SigV4, IAM role-based authentication). The design must show that services verify caller identity before allowing communications, even when services are within the same network boundary.' Fixed text, including the parenthesised mechanism lists.
Emulator: HTTP 200 with 'Network communication within and into the workload must be authenticated rather than trusted on the basis of its origin. The design must show how east-west traffic between workload components and north-south traffic from clients establishes a verified identity — mutual TLS (mTLS), IPsec, or request signing with a service identity such as SigV4 — how the certificates or credentials behind that identity are issued and rotated, and how a connection that presents no verified identity is rejected rather than served.' — the pack's "Architecture documents must define ..." opening is gone, the TLS-with-certificate-validation / IAM-role-based-authentication mechanisms are replaced by a shorter list, and issuance/rotation clauses absent from the published text are added. The same rewrite is reported for the other 31 names on the page (for example "automated-certificate-management-architecture").

Why: these packs are the service's published compliance catalog, and clients consume the description as content, not as decoration. A client that renders a requirement to a reviewer, diffs the managed catalog against its own copy to detect catalog updates, hashes or fingerprints requirement bodies for change detection, feeds the description to a model or rules engine that must decide whether a workload satisfies the requirement, or greps it for the specifics it enumerates (the CHD/SAD element lists, "TLS with certificate validation", "AWS SigV4, IAM role-based authentication", the adverse-event information-flow sentence) gets different text against the emulator than against AWS: it reports spurious catalog drift on every requirement, and the clauses it keys on are missing. Because the paraphrase is plausible and the names, ordering and pagination are all correct, nothing signals that the content is wrong — the client simply reaches wrong conclusions quietly, on all three managed packs at once.

Fix: the seeded AWS-managed requirement catalog, not the handler. crate::state's `aws_managed_requirements` module (re-exported from state.rs, which the ListSecurityRequirements handler reads through `security_requirements_from` / `SecurityRequirement::summary`) holds the per-requirement `description` bodies for each managed pack; each one must reproduce the service's published description verbatim rather than a re-authored summary of it. The handler's paging, cursor codec and ResourceNotFoundException/ValidationException behaviour all replay clean and need no change.
