# ecs__iam__sns__sqs: a STOPPED Fargate task reports no container exitCode and stoppedReason 'Essential container in task exited' — the container's command never runs, so the sns:Publish denial and its repair are never observable

> _Note: this issue was identified against the code base at commit `bf5f1b716fd44070c371033dd9201606434af162`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
DescribeTasks

## Description
Cause 1 of 1: a Fargate task created by RunTask settles to lastStatus 'STOPPED' almost immediately, but the essential container in the DescribeTasks response carries NO exitCode at all and the task's stoppedReason is 'Essential container in task exited' — i.e. the container's entryPoint/command was never executed and no outcome of the run is readable. Failing check: ecs__iam__sns__sqs.fargate-task-role-without-sns-publish-is-denied-until-granted.

NOTE for the fixer: two open issues describe the same scenario but were NOT reported as owning this check by the replay (their recorded key is a 60s harness timeout, whereas this run fails on an assertion against a task that DID settle to STOPPED without an exitCode), so this surviving failure is filed here and those issues are named to deduplicate against: 20261117T181448Z-ecs-iam-sns-sqs-a-fargate-task-never.md and 20261117T135333Z-ecs-iam-sns-sqs-a-fargate-task-whose-role-lacks-sns-publish.md. The generic exitCode defect is also described by 20261116T034914Z-ecs-2-net-new-causes-describetaskdefinition-derives-a.md; none of them covers this check's replay key.

AWS: Smithy (ECS, com.amazonaws.ecs) models Task$lastStatus, Task$stopCode (TaskStopCode), Task$stoppedReason and Task$containers -> Container, whose member Container$exitCode (BoxedInteger) is documented as "The exit code returned from the container." Recorded behavior for the runtime: a FARGATE task registered with awsvpc networkMode runs its container's entryPoint ["bash","-c"] command; when that command exits 0 the task reaches lastStatus 'STOPPED' with the essential container's exitCode set to the process's exit status (0 here, because the script ends with `exit 0`), stopCode 'EssentialContainerExited' and stoppedReason 'Essential container in task exited' only AFTER the container actually ran. The awslogs driver creates the stream <awslogs-stream-prefix>/<container-name>/<task-id> in the configured log group and the lines the container printed (here a single 'OUTCOME=OK ...' or 'OUTCOME=DENIED ... DETAIL=...' line) are returned by CloudWatch Logs GetLogEvents. In the denied run the in-container AWS CLI Publish call is refused with error code 'AuthorizationError' and a message whose FIXED text is "User: " + " is not authorized to perform: SNS:Publish on resource: " + " because no identity-based policy allows the SNS:Publish action"; its VARIABLE parts are the caller ARN arn:aws:sts::<account>:assumed-role/<task-role-name>/<task-id> (account, the task role from the task definition, the task id of the running task) and the topic ARN from the request. After the one missing sns:Publish statement is granted to the SAME role, the next task's publish succeeds and the SNS envelope whose Message equals the published body arrives in the subscribed SQS queue.

Emulator: DescribeTasks reports the task lastStatus 'STOPPED' with stoppedReason 'Essential container in task exited' and the 'Publisher' container object carrying exitCode absent (the check reads None). The replay assertion is: AssertionError: task '00000000000000000000000000000001' container exited None: 'Essential container in task exited'. The task is reported stopped-because-the-container-exited for a container that never ran, so no exit status, no awslogs output and therefore neither the AuthorizationError refusal nor the post-grant SNS->SQS delivery is ever produced.

Why: a client that launches a one-shot Fargate task and reads DescribeTasks to learn whether it succeeded gets a STOPPED task with no exitCode — it cannot distinguish success from failure, and the stoppedReason actively claims an essential container exited when none was executed. Every diagnose-then-repair workflow built on 'run a task, read its exit code and its logs' (here: prove a task role without sns:Publish is denied with AuthorizationError, grant the one missing statement, re-run and see the message delivered) is unrunnable; automation that gates on `exitCode == 0` either crashes on the missing field or treats a never-run task as a pass.

Fix: the ECS task runtime/lifecycle state that executes a RunTask-created Fargate task's container command and records the essential container's exit status on the Container record DescribeTasks serializes (and must not report stopCode/stoppedReason 'Essential container in task exited' for a container that was never started), plus the awslogs log-driver delivery that must create the task's log stream and append the container's stdout; once the container's calls are actually issued, the SNS Publish authorization path must refuse the un-granted task role with AuthorizationError and allow it after the grant.

Traces: ecs__iam__sns__sqs.fargate-task-role-without-sns-publish-is-denied-until-granted (assertion in _await_stopped on the granted task).

## Evidence
Expected (AWS): DescribeTasks on the granted task reports lastStatus 'STOPPED' with containers[name='Publisher'].exitCode == 0 (the script's `exit 0`); GetLogEvents on granted/Publisher/<task-id> returns 'OUTCOME=OK BODY=<body>' and the subscribed SQS queue carries the SNS envelope whose Message is that body. For the un-granted role the log line is 'OUTCOME=DENIED BODY=<body> DETAIL=An error occurred (AuthorizationError) when calling the Publish operation: User: arn:aws:sts::<account>:assumed-role/<denied-role-name>/<task-id> is not authorized to perform: SNS:Publish on resource: <topic-arn> because no identity-based policy allows the SNS:Publish action' and nothing reaches the queue; after put_role_policy grants sns:Publish on that topic to the same role, the next task logs 'OUTCOME=OK' and its body arrives.

Actual (emulator): the task reaches STOPPED but the container record has no exitCode member and the task's stoppedReason is 'Essential container in task exited'. Replay detail: AssertionError: task '00000000000000000000000000000001' container exited None: 'Essential container in task exited' (check_ecs__iam__sns__sqs_fargate_task_role_without_sns_publish_is_denied_until_granted.py line 294, in _await_stopped, `assert publisher.get("exitCode") == 0`). No container output and no SNS/SQS delivery follow, so no error code or message was produced to compare.

## Steps to Reproduce
1. Create an SQS queue; create an SNS topic, set the queue's Policy to allow sns.amazonaws.com sqs:SendMessage from that topic, and Subscribe the queue (Protocol 'sqs').
2. Create three IAM roles trusting ecs-tasks.amazonaws.com: an execution role with AmazonECSTaskExecutionRolePolicy attached, one task role with an inline Allow of sns:Publish on the topic ('granted'), and one task role with no inline policy ('denied').
3. Create a CloudWatch Logs log group and an ECS cluster.
4. RegisterTaskDefinition (requiresCompatibilities FARGATE, networkMode awsvpc, cpu '256', memory '512', the execution role and one task role) with one essential container 'Publisher' whose entryPoint is ["bash","-c"] and whose command runs `aws sns publish --topic-arn $TOPIC_ARN --message $BODY`, prints 'OUTCOME=OK ...' or 'OUTCOME=DENIED ... DETAIL=<last CLI line>' and ends with `exit 0`; logConfiguration logDriver 'awslogs' into that log group with an awslogs-stream-prefix.
5. RunTask with launchType FARGATE, count 1 and an awsvpcConfiguration (one subnet, one security group, assignPublicIp ENABLED).
6. Poll DescribeTasks until lastStatus == 'STOPPED' and read containers[].exitCode.
Observed: the task is STOPPED with stoppedReason 'Essential container in task exited' and the container carries NO exitCode (None); GetLogEvents finds no OUTCOME= line and no message reaches the subscriber queue. Expected: exitCode 0 for the granted run with 'OUTCOME=OK' in the log stream and the SNS envelope in the queue; exitCode 0 with the 'OUTCOME=DENIED ... (AuthorizationError) ... is not authorized to perform: SNS:Publish on resource: <topic-arn> because no identity-based policy allows the SNS:Publish action' line and no queue message for the un-granted role; delivery again after the grant is added to that same role.
