# cloudformation__sqs__ssm: DeleteChangeSet refuses the change set a previous deploy executed or failed to execute, so the redeploy of a CREATE_FAILED stack never runs and a failing `--no-rollback` update leaves the stack in its pre-update status

> _Note: this issue was identified against the code base at commit `d480a9c819aca039333e6ccd75fa51254e2ac722`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
DeleteChangeSet

## Description
Cause 1 of 1: DeleteChangeSet refuses a change set in a terminal ExecutionStatus (EXECUTE_FAILED, EXECUTE_COMPLETE) instead of deleting it, which aborts the second deploy of a stack before any plan is created — so neither the fixed redeploy of a CREATE_FAILED stack nor the failing update that should park a stack UPDATE_FAILED ever happens (failing checks: cloudformation__sqs__ssm.cdk-deploy-no-rollback-keeps-create-failed-then-fixed-redeploy-completes, cloudformation__sqs__ssm.cdk-rollback-restores-an-update-failed-stack-to-its-last-good-state).
AWS: Smithy (cloudformation): DeleteChangeSet input {ChangeSetName (required), StackName}; empty output; the only modeled error is InvalidChangeSetStatusException (client, httpError 400, awsQueryError InvalidChangeSetStatus), documented "The specified change set can't be used to update the stack. For example, the change set status might be CREATE_IN_PROGRESS, or the stack status might be UPDATE_IN_PROGRESS." — a refusal for a plan still being computed or still being applied. A change set in a terminal execution status (EXECUTE_COMPLETE after a successful execution, EXECUTE_FAILED after one whose stack operation failed) is deletable: AWS answers HTTP 200 with an empty body. The CDK CLI relies on that, deleting any pre-existing change set of its fixed name before creating the next one; after a first deploy — successful or failed — that change set is always in a terminal status. Downstream of that, AWS's own stack-status contract for these two flows is: a `--no-rollback` deploy whose resource fails leaves the stack CREATE_FAILED (DisableRollback true) and the fixed redeploy of the same stack id reaches UPDATE_COMPLETE; and a `--no-rollback` UPDATE whose resource fails parks the stack at UPDATE_FAILED with the already-applied changes in place, so `cdk rollback` can then drive it to UPDATE_ROLLBACK_COMPLETE.
Emulator: HTTP 400 InvalidChangeSetStatusException with the message "Cannot delete ChangeSet in execution status EXECUTE_FAILED" (and "... EXECUTE_COMPLETE"). Both the refusal and that sentence are the emulator's own — AWS emits neither for a terminal change set. The handler refuses on every ExecutionStatus past the two a plan waits in, rather than only the in-progress ones the modeled error names. Consequence observed in the second check: after a first deploy that reached CREATE_COMPLETE, the failing `--no-rollback` update exits 1 and DescribeStacks still reports StackStatus 'CREATE_COMPLETE' — not 'UPDATE_FAILED' — because the update was never planned or executed at all. Hypothesis: that stack-status symptom is downstream of this same refusal (the deploy dies at the DeleteChangeSet step after synthesis, as it does in the first check where the message is quoted verbatim); if the check still reports a wrong StackStatus once DeleteChangeSet accepts a terminal change set, the residual is a separate defect in the failing-update state machine (a failing update with DisableRollback must leave UPDATE_FAILED) and must be filed as such.
Why: a client cannot redeploy any stack twice through a named change set. The first check's recovery path — deploy fails with `--no-rollback`, the operator fixes the template and redeploys — is the standard way out of a CREATE_FAILED stack, and it exits 1 with an emulator-authored sentence while the half-built stack stays CREATE_FAILED forever. The second check cannot even reach the UPDATE_FAILED state that `cdk rollback` exists to repair, so the whole park-then-rollback workflow is unreachable and a caller reading StackStatus is told the stack is healthy ('CREATE_COMPLETE') after a deploy that failed.
Fix: the DeleteChangeSet handler's precondition on execution status — refuse InvalidChangeSetStatusException only while the change set's creation has not concluded or its execution is in progress; delete a terminal-status change set (with its nested hierarchy) and answer 200. The same root cause is filed for other service headings as 20261120T150300Z-cloudformation-deletechangeset-refuses-an-executed-change-set-so.md, 20261120T150929Z-cloudformation-s3-deletechangeset-refuses-a-change-set-in.md, 20261120T150929Z-cloudformation-iam-lambda-s3-deletechangeset-refuses-the-change.md and 20261120T162942Z-cloudformation-lambda-deletechangeset-refuses-an-executed-change-set.md, and under this project's cloudformation__ssm heading in the companion issue filed in this same sweep; none of those carries these two checks' replay keys.

## Evidence
cloudformation__sqs__ssm.cdk-deploy-no-rollback-keeps-create-failed-then-fixed-redeploy-completes: the `--no-rollback` deploy correctly parks the stack ('CREATE_FAILED', 'The following resource(s) failed to create: [Bad]. ', DisableRollback True) and keeps the good queue and parameter; the FIXED redeploy then fails — `AssertionError: the fixed redeploy exited 1; output tail '\n✨  Synthesis time: 1.8s\n\nCannot delete ChangeSet in execution status EXECUTE_FAILED\n'`. Expected: DeleteChangeSet answers 200 for that change set, the redeploy exits 0, and the SAME stack id reaches UPDATE_COMPLETE without re-creating the queue.

cloudformation__sqs__ssm.cdk-rollback-restores-an-update-failed-stack-to-its-last-good-state: after a successful first deploy, the failing `--no-rollback` update exits 1 as expected but `AssertionError: the --no-rollback update left the stack 'CREATE_COMPLETE'` — expected StackStatus 'UPDATE_FAILED' with the queue VisibilityTimeout at 60, the kept parameter at 'v2' and the added parameter present, so that `cdk rollback` can restore 30/'v1'/ParameterNotFound and reach UPDATE_ROLLBACK_COMPLETE.

The refused call is HTTP 400 InvalidChangeSetStatusException, message "Cannot delete ChangeSet in execution status EXECUTE_FAILED" — fixed text "Cannot delete ChangeSet in execution status " plus the change set's ExecutionStatus; AWS answers 200 with an empty DeleteChangeSetResult.

## Steps to Reproduce
1. Clone the repo and boot the emulator built from it.
2. CreateChangeSet(StackName=<new stack>, ChangeSetName='cdk-deploy-change-set', ChangeSetType='CREATE', TemplateBody=<template whose second resource cannot be created>), ExecuteChangeSet with DisableRollback=true, and wait: the stack reaches CREATE_FAILED and the change set reports ExecutionStatus EXECUTE_FAILED.
3. DeleteChangeSet(StackName=<stack>, ChangeSetName='cdk-deploy-change-set') — observe HTTP 400 InvalidChangeSetStatusException "Cannot delete ChangeSet in execution status EXECUTE_FAILED" instead of 200.
4. End to end (needs `cdk` and `node`): `cdk deploy <stack> --require-approval never --no-rollback` with the broken resource, then the same command with the resource fixed — the second run exits 1 with that sentence and the stack stays CREATE_FAILED.
5. For the second check: `cdk deploy <stack>` (good variant), then `cdk deploy <stack> --no-rollback` (variant whose last resource collides) — DescribeStacks still reports 'CREATE_COMPLETE' instead of 'UPDATE_FAILED'.
