# apigatewayv2__lambda: the execute-api front door refuses an Origin-bearing request 403 'cross-site origin', ignoring the API's CorsConfiguration (1 cause)

> _Note: this issue was identified against the code base at commit `c1cdd983ca2491984ece40896171481518806128`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
CreateApi

## Description
One net-new root cause in the apigatewayv2 HTTP API execute-api data plane. It must be closed before submitting.

Cause 1 of 1: a SigV4-signed GET that carries an Origin header is refused by the emulator's front door with HTTP 403 and the plain-text body 'cross-site origin' before the route's AWS_IAM authorization or its AWS_PROXY integration is reached — even though that exact origin is listed in the API's CorsConfiguration.AllowOrigins. The gate is evidently a same-origin comparison against the host the request was reached on (a loopback host:port), not a check against the API's configuration: the recorded Origin is identical to the single entry of AllowOrigins, so no correct allowlist evaluation could refuse it. Failing check: apigatewayv2__lambda.http-api-cors-signed-iam-get-granted-unsigned-get-refused.
AWS: Smithy (services/service-com-amazonaws-apigatewayv2-apigatewayv2/smithy-model/com-amazonaws-apigatewayv2-apigatewayv2.json): CreateApi member CorsConfiguration : Cors — members AllowOrigins (CorsOriginList, jsonName allowOrigins), AllowMethods, AllowHeaders, ExposeHeaders (jsonName exposeHeaders), AllowCredentials, MaxAge @range -1..86400, all documented 'Supported only for HTTP APIs', shape doc linking https://docs.aws.amazon.com/apigateway/latest/developerguide/http-api-cors.html; CreateRoute members RouteKey and AuthorizationType (AWS_IAM); CreateIntegration IntegrationType AWS_PROXY with PayloadFormatVersion 2.0. The model does not describe the data plane, so the dispatch rule is the documented CORS rule plus recorded behavior: CORS is a BROWSER mechanism, and API Gateway never refuses a request because of its Origin. An HTTP API serves the request on its merits and only stamps response headers: (a) a signed GET on an AWS_IAM route whose Origin is in AllowOrigins is served HTTP 200 with the integration's body, the handler seeing the caller's Origin in event.headers.origin, and exactly two CORS headers on the response — access-control-allow-origin equal to the request's Origin and access-control-expose-headers equal to the configured ExposeHeaders; (b) the same signed GET from an origin NOT in AllowOrigins is STILL served 200 with the integration's body, but with no access-control-* header at all; (c) the same GET unsigned is refused by the route's AWS_IAM authorization with HTTP 403 and body {"message":"Forbidden"} ('Forbidden' is the fixed text; there are no variable parts), the integration not invoked, and that refusal still carries the CorsConfiguration grant headers. In every case the status, the body and the header names are the fixed part; the origin string, the exposed header name and the handler's own marker are values taken from the request and from the API's own CorsConfiguration.
Emulator: the first, positive leg never reaches 200. Every attempt inside the poll window is answered HTTP 403 with content-type 'text/plain; charset=utf-8' and the 17-byte body 'cross-site origin' — 'AssertionError: signed GET <stage-url>/items from <allowed origin> not answered 200 within 42.8s; last (403, {...\'content-type\': \'text/plain; charset=utf-8\', \'content-length\': \'17\'...}, \'cross-site origin\')'. Neither the status, the error code nor the body is anything AWS produces: AWS's 403 on this surface is the JSON {"message":"Forbidden"}, and here the refusal is not an authorization refusal at all (the request was correctly signed). Because the positive control never passes, the foreign-origin leg (b) and the unsigned-refusal leg (c) are never exercised.
Why: a client relying on AWS's behavior gets the opposite of the contract in two ways. First, the very requests CORS exists to permit are the ones destroyed: any browser page — or any SDK/fetch wrapper that forwards an Origin header — is refused 403 by an API whose allowlist explicitly names its origin, so a correctly configured single-page application cannot call its own API at all. Second, server-side Origin enforcement is not a CORS mechanism: code written against the emulator will assume an Origin header is an access control, whereas in AWS the request is served regardless and only the response headers differ, so an application that believes it is protected by AllowOrigins is in fact open in AWS. The invented plain-text body also breaks any client parsing API Gateway's JSON {"message":...} error shape.
Fix: the execute-api HTTP data-plane front door for apigatewayv2 — delete the server-side Origin/same-site gate that answers 403 'cross-site origin' and let the request proceed to route matching, the route's authorizer (AWS_IAM) and its integration; CORS must only shape the RESPONSE, emitting access-control-allow-origin + access-control-expose-headers from the API's CorsConfiguration when the request's Origin is in AllowOrigins and omitting them otherwise, on both the 200 and the 403 {"message":"Forbidden"} branch.

## Evidence
Cause 1 — Expected (AWS): on an HTTP API created with CorsConfiguration {AllowOrigins:[<allowed origin>], AllowMethods:['GET'], AllowHeaders:['authorization','x-amz-date'], ExposeHeaders:['x-app-marker']}, an AWS_PROXY integration (PayloadFormatVersion '2.0') to a Lambda, route 'GET /items' with AuthorizationType='AWS_IAM', a '$default' AutoDeploy stage and the apigateway invoke permission: (a) a SigV4-signed (service 'execute-api') GET <stage-url>/items carrying Origin: <allowed origin> -> HTTP 200, body {"marker":<handler marker>,"seen":{"origin":"<allowed origin>"}}, and exactly {access-control-allow-origin: <allowed origin>, access-control-expose-headers: x-app-marker}; (b) the same signed GET with Origin: <an origin not in AllowOrigins> -> HTTP 200, the handler still seeing that origin, and NO access-control-* header; (c) the same GET unsigned -> HTTP 403 with body {"message":"Forbidden"}, no x-app-marker header (the handler was not reached) and the CorsConfiguration grant headers still present. Actual (emulator): leg (a) never answers 200 — every poll attempt returns HTTP 403, content-type 'text/plain; charset=utf-8', content-length 17, body 'cross-site origin'. Replay assertion: 'AssertionError: signed GET https://<emulator-host:port>/_aws/execute-api/<api-id>/items from <allowed origin> not answered 200 within 42.76s; last (403, {...}, \'cross-site origin\')'. Legs (b) and (c) are consequently never reached. The host:port, api id, marker string and the specific origin name are per-run values, not requirements; the requirement is that an Origin-bearing signed request is served 200 and that the only Origin-dependent difference is the presence of the two response headers.
