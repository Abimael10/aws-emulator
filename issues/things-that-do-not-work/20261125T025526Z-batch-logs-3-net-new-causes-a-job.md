=== Cause 1 of 3: timeout.attemptDurationSeconds is never enforced — a job that outlives its attempt timeout is reported SUCCEEDED with exitCode 0 ===
AWS: Smithy (com.amazonaws.batch): JobTimeout.attemptDurationSeconds — "The job timeout time (in seconds) that's measured from the job attempt's startedAt timestamp. After this time passes, Batch terminates your jobs if they aren't finished. The minimum value for the timeout is 60 seconds. For array jobs, the timeout applies to the child jobs, not to the parent array job." JobStatus is the enum [SUBMITTED, PENDING, RUNNABLE, STARTING, RUNNING, SUCCEEDED, FAILED]. A job whose attempt passes that deadline is terminated by Batch: the job reaches FAILED, the container never reaches its completion marker (so the marker line never appears in the awslogs stream named by container.logStreamName), and the attempt's statusReason reports the attempt timeout rather than a clean container exit (https://docs.aws.amazon.com/batch/latest/userguide/job_timeouts.html). The variable parts of that reason are the job's own values; the requirement graded here is the terminal status and the absent completion marker. Hypothesis: AWS words the attempt's statusReason for this class "Job attempt duration exceeded timeout".
Emulator: the victim job — submitted with timeout={"attemptDurationSeconds": 60} over a container that sleeps far past it and only writes its DONE marker if the sleep RETURNED — is reported by DescribeJobs with status 'SUCCEEDED' and container.exitCode 0. The check's assertion reads "a job past attemptDurationSeconds must be FAILED, got 'SUCCEEDED' (exitCode=0)". The timeout is accepted on SubmitJob and then never evaluated. The identical control job (long timeout, short sleep) is also SUCCEEDED, so the two legs are indistinguishable and the timeout has no observable effect in either direction.
Why: a client that uses attemptDurationSeconds as its only bound on a runaway job is told the job completed successfully. Alerting and retry logic keyed on FAILED never fires, and a job AWS would have killed mid-run is reported the same as one that finished its work — including a reported exitCode 0 for a command that never ran to completion.
Fix: the job attempt lifecycle in the Batch job data-plane runner — the attempt must carry its startedAt + attemptDurationSeconds deadline and be terminated into FAILED when it elapses, with the timeout recorded in the attempt's statusReason and the container's completion output absent.
Traces: batch__logs.batch-attempt-timeout-kills-container-before-completion-marker.

=== Cause 2 of 3: an attempt has zero duration — a job is already terminal on the caller's first read, so it is never observable in RUNNING and TerminateJob of a running job is unreachable ===
AWS: Smithy: JobStatus enumerates SUBMITTED, PENDING, RUNNABLE, STARTING, RUNNING, SUCCEEDED, FAILED; AttemptDetail.startedAt is "The Unix timestamp (in milliseconds) for when the attempt was started (when the attempt transitioned from the STARTING state to the RUNNING state)" and AttemptDetail.stoppedAt the transition "from the RUNNING state to a terminal state, such as SUCCEEDED or FAILED". TerminateJob(jobId required, reason required) is POST /v1/terminatejob returning 200 with an empty body (errors ClientException 400 / ServerException 500). On AWS a job whose container is still executing is observable as RUNNING for the whole duration of that execution; TerminateJob against it stops the container, the job becomes FAILED with the caller's reason reported verbatim in statusReason, the completion marker never reaches the log stream, and stoppedAt-startedAt is shorter than the command's own duration.
Emulator: the victim job, whose container command sleeps for minutes before writing its marker, is already 'SUCCEEDED' on the first DescribeJobs read — the check fails with "the victim must be observed RUNNING before TerminateJob, not already 'SUCCEEDED' -- a job terminated while still RUNNABLE never executed and the absence assertion would be vacuous". The SUBMITTED→STARTING→RUNNING window collapses to zero because the terminal status (with exitCode 0) is written at placement time instead of at container exit, so TerminateJob can only ever be aimed at a job that has already finished and none of its documented effects (FAILED, verbatim statusReason, truncated startedAt/stoppedAt interval, absent completion marker) is reachable.
Why: a client cannot observe, poll on, or cancel work on this emulator: progress reporting keyed on RUNNING never advances, and cancellation is unimplementable because every job is terminal before the first poll. Worse, a job reported SUCCEEDED/exitCode 0 did not run its command to completion, so success is not evidence the work happened.
Fix: the Batch job state machine's status transitions in the data-plane runner — RUNNING must be entered when the container starts and held until the container exits, with the attempt's startedAt/stoppedAt bracketing that real interval; and TerminateJob's handler must stop the RUNNING container and record the caller's reason in JobDetail.statusReason.
Traces: batch__logs.batch-terminate-running-job-stops-container-before-completion-marker.

=== Cause 3 of 3: a SEQUENTIAL array job's children are never executed and write no log events, so the array never settles and index-ordered serialisation is unobservable ===
AWS: Smithy: ArrayJobDependency is the enum [N_TO_N, SEQUENTIAL], used as JobDependency.type on SubmitJob; ArrayPropertiesDetail.index is the child's index within the array. With a SEQUENTIAL array dependency the children of one array submission run strictly one after another in ascending index order even on capacity that could run them all at once (here maxvCpus=4 against 3 × 0.25-vCPU children), each child runs its own container with AWS_BATCH_JOB_ARRAY_INDEX expanded, each writes its own awslogs stream (one event per stdout line, in the stream DescribeJobs names in container.logStreamName), the parent ends SUCCEEDED with arrayProperties.statusSummary accounting for all children as SUCCEEDED, and child i's first log event is no earlier than child i-1's last.
Emulator: the check reaches no verdict at all — it is killed by the runner with "Error: Check timed out after 60.0s" while blocked waiting on the children's execution and on their END= log lines. Nothing the children were supposed to produce materialises: no per-child stream content, hence no timestamps to compare and no serialisation or index ordering to grade. (Sibling checks in this run show the emulator does mark jobs SUCCEEDED instantly, so the stall is on the child execution / awslogs delivery path, not on the job reaching a status.)
Why: a client that expresses an ordered pipeline over array indices with a SEQUENTIAL array dependency gets neither execution nor ordering: stage i+1 can never be known to follow stage i, and any consumer reading a child's output from the stream Batch names blocks forever or silently processes nothing.
Fix: the array-job child scheduling and execution in the SubmitJob/array path plus the awslogs delivery path — a SEQUENTIAL dependency must gate each child on the preceding index's termination and release them in ascending index order, each child must actually run its container with its index injected, and each child's stdout must be delivered line-by-line to the log stream it reports.
Traces: batch__logs.batch-sequential-array-children-run-one-at-a-time-in-index-order.

## Evidence
Suite: 250/295 passed; service `batch__logs` 4/10 (40%), 6 failed. Three of those six were marked neither ALREADY FILED nor OWNED and are the three causes above.

Cause 1 — batch__logs.batch-attempt-timeout-kills-container-before-completion-marker
  Expected (AWS): a job with timeout.attemptDurationSeconds=60 whose container sleeps far longer is terminated by Batch → DescribeJobs status 'FAILED', the attempt's statusReason reporting the attempt timeout, and the container's completion marker never present in its awslogs stream; the identical long-timeout control job SUCCEEDS and does deliver both markers.
  Actual (emulator): AssertionError "a job past attemptDurationSeconds must be FAILED, got 'SUCCEEDED' (exitCode=0)" — HTTP 200 on every call; the timeout is stored and never evaluated.

Cause 2 — batch__logs.batch-terminate-running-job-stops-container-before-completion-marker
  Expected (AWS): at least one DescribeJobs read returns status 'RUNNING' (with container.logStreamName set and the container's START line readable) while the long-sleeping container executes; TerminateJob(jobId, reason) then returns 200 and DescribeJobs reports 'FAILED' with statusReason equal to the caller's reason verbatim, no completion marker in the stream, and stoppedAt-startedAt shorter than the command's sleep.
  Actual (emulator): AssertionError "the victim must be observed RUNNING before TerminateJob, not already 'SUCCEEDED' -- a job terminated while still RUNNABLE never executed and the absence assertion would be vacuous". The job is terminal on the first read, so TerminateJob's behaviour is never exercised.

Cause 3 — batch__logs.batch-sequential-array-children-run-one-at-a-time-in-index-order
  Expected (AWS): a size-3 array job submitted with dependsOn type SEQUENTIAL on 4 vCPUs of capacity ends SUCCEEDED with statusSummary.SUCCEEDED=3; each child <arrayJobId>:i is listed, reports arrayProperties.index=i and exitCode 0, owns a distinct log stream holding exactly its own BEGIN=i / END=i lines, and child i's BEGIN is no earlier than child i-1's END.
  Actual (emulator): no verdict — "Error: Check timed out after 60.0s" while waiting on the children's execution and their END= lines; no child output exists to order.

The 60 s figure is this run's runner budget, and the sleep lengths, job ids, task ARNs, stream names and timestamps in these checks are per-run values, not requirements. The requirements are: FAILED on attempt-timeout expiry, an observable RUNNING window held for the container's real duration with TerminateJob's verbatim reason, and SEQUENTIAL array children actually executing in ascending index order with their own log streams.

## Steps to Reproduce
Preconditions for all three: a Fargate task execution role, a fresh CloudWatch Logs group, a MANAGED/FARGATE compute environment polled to VALID and an ENABLED job queue polled to VALID, and a FARGATE job definition (image public.ecr.aws/docker/library/busybox:1.36, resourceRequirements VCPU 0.25 / MEMORY 512) whose logConfiguration uses the awslogs driver pointed at that group.

Cause 1: RegisterJobDefinition with command ["sh","-c","echo START; sleep 300 && echo DONE"]. SubmitJob a control with containerOverrides command ["sh","-c","echo START; sleep 5 && echo DONE"] and timeout={"attemptDurationSeconds":3600}; SubmitJob the victim unmodified with timeout={"attemptDurationSeconds":60}. Poll DescribeJobs on the victim: it reports SUCCEEDED with container.exitCode 0 instead of FAILED, and its stream carries no evidence it was killed.

Cause 2: With the same definition (sleep 240 && echo DONE), SubmitJob a short-sleeping control and the long-sleeping victim together, then poll DescribeJobs on the victim immediately — the first read already reports 'SUCCEEDED', so TerminateJob(jobId=victim, reason="<caller reason>") can never be issued against a RUNNING job and the FAILED/verbatim-statusReason/startedAt-stoppedAt assertions are unreachable.

Cause 3: RegisterJobDefinition with command ["sh","-c","echo BEGIN=$AWS_BATCH_JOB_ARRAY_INDEX; sleep 15; echo END=$AWS_BATCH_JOB_ARRAY_INDEX"]. SubmitJob with arrayProperties={"size":3} and dependsOn=[{"type":"SEQUENTIAL"}] on a compute environment with maxvCpus=4. Poll DescribeJobs on the parent and ListJobs with arrayJobId over every status, then GetLogEvents/FilterLogEvents on each child's reported logStreamName: the children never execute and no BEGIN=/END= event is ever delivered, so the ascending-index serialisation cannot be observed and the scenario never completes.
