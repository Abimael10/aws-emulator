# artifact ListReports report summaries carry re-authored catalog content instead of the published report metadata

> _Note: this issue was identified against the code base at commit `2eb3e162f2b8ae792971ae16f8b17dcde772ffd5`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
ListReports

## Description
GET /v1/report/list (ListReports) answers 200 with a reports list whose ReportSummary members are populated with emulator-authored content rather than the metadata of the report resource the entry's id/arn identifies. For the report entries the emulator does serve, the fields name, description, series, acceptanceType, periodStart and periodEnd all disagree with the published catalog, and the period timestamps are additionally serialized at a coarser precision than the service uses.

Cause 1 of 1 - ReportSummary fields are synthesized per entry instead of being read from the report catalog (fixture artifact-catalog-list-reports, step task#1).

AWS: Smithy (com.amazonaws.artifact#Artifact) models ListReports as GET /v1/report/list -> ListReportsResponse.reports: ReportsList of ReportSummary, paginated (inputToken/outputToken nextToken, pageSize maxResults, items reports). Each ReportSummary carries id (pattern ^report-[a-zA-Z0-9]{16}$), arn, version (long, min 1), name, description, series, category, companyName, productName, state, uploadState, statusMessage and acceptanceType (enum AcceptanceType with exactly the values PASSTHROUGH and EXPLICIT), plus periodStart and periodEnd (TimestampAttribute, @timestampFormat date-time). The model fixes the shape but not the catalog contents, so for the values this is recorded behavior only: AWS Artifact returns the metadata of the actual published report named by that id/arn/version - the report's own title, its own published description text, its own series, its own acceptance type, and the start/end instants of the period that report covers, rendered as date-time with millisecond precision (e.g. a periodStart of the form YYYY-MM-DDTHH:MM:SS.mmmZ). Which report a given id names, and therefore every one of those values, is a property of the catalog entry, not of the position in the list.

Emulator: for one and the same report arn/id the emulator returns a different report's metadata, re-worded prose, a different acceptance type and a different period. Verbatim from the replay of fixture artifact-catalog-list-reports step task#1 (status 200 expected, 200 actual, verdict mismatch):
  - $.reports[arn="arn:aws:artifact:us-east-1::report/report-7g5j2DTVeNXWx7St:1"].name: expected 'Accessibility Conformance Report (VPAT) - AWS Transfer Family', got 'Accessibility Conformance Report VPAT - AWS Management Console' (a different product, and the parenthesised VPAT token dropped).
  - the same entry's .description: expected the published one-paragraph ACR/VPAT boilerplate ('This document is an Accessibility Conformance Report (ACR) based on the ITI VPAT(R) and is intended to provide information on the accessibility of the relevant AWS product or service. The VPAT references accessibility standards for information and communications technology including: Section 508 (U.S.), EN 301 549 (EU), and W3C/WAI WCAG.'), got a multi-sentence re-authored narrative about the AWS Management Console ('The Accessibility Conformance Report for the AWS Management Console records how the console's user interfaces meet the accessibility criteria ...').
  - the same entry's .periodStart: expected '2024-11-01T00:00:00.000Z', got '2024-01-01T00:00:00Z' - both a wrong instant and a date-time rendering that drops the millisecond component AWS emits.
  - $.reports[arn="arn:aws:artifact:us-east-1::report/report-5eevElBv6MyRmQsD:7"].acceptanceType: expected 'PASSTHROUGH', got 'EXPLICIT'; the same entry's .description expected the one-line UAE IAR assessment text ('Independent compliance assessment against the United Arab Emirates (UAE) Information Assurance Regulation (IAR).') and its .name, .periodStart and .periodEnd likewise diverge.
  The cluster's divergence key lists this same field set (.name, .description, .series, .acceptanceType, .periodStart, .periodEnd) across many report arns, alongside a large set of whole-entry keys for reports absent from the response.

Why: a client cannot use the catalog it is given. Report pickers and compliance-automation that select a report by name, series or category get the wrong product's report (a Transfer Family ACR presented as a Management Console one); code that keys on acceptanceType to decide whether a click-through term must be accepted before GetReport/GetTermForReport takes the wrong branch, because PASSTHROUGH and EXPLICIT mean opposite things; auditors filtering by periodStart/periodEnd select the wrong reporting period, and a date-time without the millisecond component breaks exact-string comparison against recorded/real responses and round-trips to a different instant than the one the catalog publishes.

Fix: the artifact ListReports handler and the report-catalog state it serializes from - each ReportSummary must be projected from the stored catalog entry identified by that id/arn/version (name, description, series, category, companyName, productName, acceptanceType taken from the entry, never regenerated or templated from the service name), and the summary serializer must render periodStart/periodEnd as date-time with the millisecond component AWS emits.

Related (does NOT cover this): open issue 20261107T124604Z-artifact-listreports-catalog-enumeration-omits-nearly-every-published.md reports that ListReports omits most published reports from its first page; it is about which entries are enumerated. This issue is about the content of the entries that ARE returned being wrong, which a fix to enumeration alone leaves diverging. Open issue 20261111T084526Z-artifact-listcomplianceinquiryqueries-omits-the-inquiry-s-query-record.md owns a separate ListComplianceInquiryQueries divergence.
