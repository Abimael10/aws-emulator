# Lightsail GetBlueprints catalog rows carry locally authored description text and crossed product/licence links, and the row tail is absent

> _Note: this issue was identified against the code base at commit `549411669247f115f7ed02366cae7caee2095e03`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
GetBlueprints

## Description
Two net-new root causes, both in the static read-only instance-blueprint catalog table behind Lightsail GetBlueprints. In both the operation answers 200 with a well-formed GetBlueprintsResult whose member set is correct, so no client can detect the divergence from the status or the envelope: the fault is entirely in which rows the table holds and what the per-row columns contain. BOTH causes must be closed before submitting.

Cause 1 of 2 (fixture lightsail-catalog-get-blueprints, step task#1): the blueprint rows carry a locally authored description paragraph in place of the paragraph AWS publishes for that image, and the tail of the row set is not served at all.
AWS: Smithy com.amazonaws.lightsail#GetBlueprints is an awsJson RPC operation (POST /ls/api/2016-11-28/GetBlueprints, success 200; errors AccessDeniedException 403, AccountSetupInProgressException 428, InvalidInputException 400, NotFoundException 404, OperationFailureException 400, RegionSetupInProgressException 428, ServiceException 500, UnauthenticatedException 401). Its output member `blueprints` is a BlueprintList of com.amazonaws.lightsail#Blueprint, whose members Smithy documents as blueprintId, name, group, type (BlueprintType os|app), `description` ("The description of the blueprint"), isActive, minPower, `version` ("The version number of the operating system, application, or stack"), versionCode, `productUrl` ("The product URL to learn more about the image or blueprint"), `licenseUrl` ("The end-user license agreement URL for the image or blueprint"), platform (InstancePlatform) and appCategory. The model fixes no row set and no column values, so the table's contents and order are recorded behavior only. The recording shows AWS serving a complete catalog of 39 rows in a fixed order (the Windows Server OS block, then the Windows SQL Server app rows, then the Linux/Unix OS and app rows), each row carrying the description paragraph AWS publishes for THAT image on its own listing. The requirement is that each row's `description` is AWS's published copy for that image and that the whole row set is served; the particular paragraph wording, catalog date and ids in the recording are that catalog generation filling the template.
Emulator: replay reports $.blueprints[1] .. $.blueprints[38] as divergent whole entries, status 200 -> 200. At $.blueprints[1] ('windows_server_2022') blueprintId, name, group, type, platform, minPower, version, versionCode, productUrl and licenseUrl all agree, but the description's body differs: AWS's paragraph is "Windows Server is an environment for deploying applications using the Microsoft Web Platform. This blueprint allows you to run compatible solutions that are based on Windows on Amazon Web Services (AWS), providing high-performance, reliable, and cost-effective cloud computing. Learn more about Windows Server 2022 on the AWS Marketplace.", while the emulator keeps AWS's first and last sentences and substitutes a locally written middle sentence ("The image carries the Internet Information Services web server, ASP.NET and the .NET Framework, so a Windows application, its services and its management tooling run on a Lightsail instance as they do on a server of your own."). $.blueprints[2] ('windows_server_2019') diverges the same way against AWS's "Amazon Lightsail helps you build, deploy, scale, and manage Microsoft applications quickly, easily, and cost effectively with Windows Server 2019. For business IT applications, Lightsail runs Windows-based solutions in a secure, easily managed ..." paragraph. Positions $.blueprints[33] .. $.blueprints[38] are absent entirely, so the emulator's list ends before AWS's 39th row.
Why: a client that renders a blueprint's description to a user, or matches/searches on it, is shown text AWS does not publish for that image under a blueprintId that looks correct, so the error is invisible at the API and surfaces only in the product surface. A blueprint that is not listed at all cannot be selected, so the workflows that start from the omitted tail rows cannot be driven against the emulator, and a client that reads the catalog by position gets a different image than AWS serves at that index.
Fix: the static instance-blueprint catalog table behind the GetBlueprints handler in the lightsail crate (its state/data, not handler, validation or serializer logic): the `description` column of the rows it serves, and the row set itself - add the omitted tail rows in AWS's order.
Traces: lightsail-catalog-get-blueprints#task#1.

Cause 2 of 2 (fixture lightsail-catalog-and-operations-lifecycle, step task#4): on the rows the catalog does serve, `productUrl` names a Marketplace listing that is not that row's listing, and `licenseUrl` uses the other row's licence style - the Marketplace '#pdp-usage' form where AWS serves the EULA document, and the EULA document where AWS serves '#pdp-usage'.
AWS: recorded behavior only for the values (Smithy documents only that `productUrl` is "The product URL to learn more about the image or blueprint" and `licenseUrl` is "The end-user license agreement URL for the image or blueprint"; neither has a modelled constraint). The recording shows every row carrying its OWN listing - a productUrl under aws.amazon.com/marketplace/pp/<prodview-id> - and a licenseUrl that is, per row, either that same listing page plus the '#pdp-usage' fragment or that image's agreement document on the AWS EULA host (d7umqicpi7263.cloudfront.net/eula/product/<id>/<id>.txt). The two links agree with each other and with the row; AWS never crosses one row's listing or licence style onto another row. The requirement is that pairing, not the literal prodview ids and EULA paths, which are this catalog generation's values.
Emulator: replay reports verdict host_not_own on $.blueprints[5].licenseUrl and on the productUrl AND licenseUrl of rows 8, 9, 10, 11 and on through row 32, status 200 -> 200. Examples: $.blueprints[5].licenseUrl expected the EULA-host document 'https://d7umqicpi7263.cloudfront.net/eula/product/5c071384-.../1402cd01-....txt' but served a Marketplace '…/marketplace/pp/prodview-xbikutlmywslu#pdp-usage' URL; $.blueprints[8].productUrl expected the row's listing 'https://aws.amazon.com/marketplace/pp/prodview-f2if34z3a4e3i' but served a different listing ('…/prodview-2jmwz6bqxkd4t'), and its licenseUrl expected that listing plus '#pdp-usage' but served an EULA-host document instead; rows 9, 10 and 11 show the same inversion (expected '…/prodview-<id>' + '#pdp-usage', served an unrelated prodview id and a cloudfront EULA path). So both the identifier and the licence style are taken from somewhere other than the row.
Why: a client that follows a blueprint's product link, or presents its end-user licence agreement for acceptance before launching an instance, sends the user to another image's Marketplace listing and shows another image's terms - a licence-presentation fault that cannot be detected from the response, since the fields are present, well formed and on AWS-owned hosts. This is a distinct cause from cause 1: it is a different column pair, reported through a different fixture path, and correcting the description prose and adding the tail rows does not re-pair a single link.
Fix: the same static instance-blueprint catalog table in the lightsail crate - the per-row `productUrl`/`licenseUrl` columns, so each row carries its own listing id and the licence form AWS serves for that row.
Traces: lightsail-catalog-and-operations-lifecycle#task#4.
