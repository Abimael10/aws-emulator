Cause 1 of 3: GetServiceGraph never reports a service-graph node for a service whose segment PutTraceSegments has just accepted.
AWS: Smithy (services/service-com-amazonaws-xray-awsxray/smithy-model/com-amazonaws-xray-awsxray.json) models GetServiceGraph as POST /ServiceGraph (success 200), required StartTime/EndTime, paginated on NextToken with items Services -> ServiceList of Service{Name, Names, Type, State, Edges, SummaryStatistics}; its only errors are InvalidRequestException (400) and ThrottledException (429). PutTelemetryRecords is POST /TelemetryRecords with an empty output. The derivation itself is recorded behavior only: the recording shows that a segment accepted by PutTraceSegments makes its document's `name` appear, within a window spanning the segment, as some node's `Name` or as an entry of some node's `Names` alias list, while a host that only called PutTelemetryRecords never becomes a node — the telemetry and trace pipelines are separate.
Emulator: PutTraceSegments accepts the segment (UnprocessedTraceSegments == [], asserted before the poll) and PutTelemetryRecords answers 200, but a fully paginated GetServiceGraph walk over the window [segment_time-600s, now+300s] never contains the submitted segment's service name. The check is cut off inside that poll (its own budget is 900 s, probing every 15 s) at the harness's 60 s ceiling, reported as `Check timed out after 60.0s`. Because the positive half never lands, the absence-side assertion (the telemetry-only hostname must never be a node) is never even evaluated.
Why: the service map is X-Ray's primary aggregate read. A client that submits segments and then reads GetServiceGraph to discover topology, latency and fault statistics sees a graph that never contains its own services, so dependency discovery, console-style service maps and anything alarming off the map are blind — and the caller cannot distinguish 'no traffic in this window' from 'the graph is not derived at all'.
Fix: derive the service-graph projection (nodes keyed by the segment document's `name`, with Names/Type/State/Edges/SummaryStatistics) from the stored segment documents, in the GetServiceGraph handler and the segment/service index it reads (services/service-com-amazonaws-xray-awsxray/src/ops/get_service_graph.rs plus the trace/segment state).
Traces: xray.telemetry-only-host-absent-from-service-graph.

Cause 2 of 3: CreateSamplingRule's duplicate-RuleName rejection carries the state layer's internal resource-collision message, including a per-run internal id, instead of AWS's constant message.
AWS: Smithy models CreateSamplingRule as POST /CreateSamplingRule (success 200), input SamplingRule (required) + Tags, errors InvalidRequestException (client, 400), RuleLimitExceededException (400), ThrottledException (429). The model does not spell out the duplicate-name message, so for the message this is recorded behavior only: re-creating a sampling rule whose RuleName is already in use answers HTTP 400 with error code InvalidRequestException and message exactly `Sampling rule already exists`. That message is entirely FIXED text — it interpolates nothing from the request or from service state (no rule name, no ARN, no id).
Emulator: same HTTP 400 and same error code InvalidRequestException, but the message is the emulator's generic registry collision text, of the form `A resource with the same resourceName but a different internalId already exists: <internal-id>` (this run: `...already exists: cbfdcbb6cb239fdd`). The fixed text is wrong, and a volatile internally generated id — not part of any AWS message template, quoted here only as the recorded instance — has been injected into a message AWS defines as constant.
Why: InvalidRequestException is shared by every malformed-request rejection on this operation, so the message is the only discriminator for a create-or-reuse / retry path. Clients branching on the duplicate-name message never take that branch, and because the emulator's text embeds a fresh internal id each run no client or test can match it at all; it also leaks emulator implementation detail that no AWS response contains.
Fix: the CreateSamplingRule handler's name-conflict check must itself raise the modeled InvalidRequestException with the constant message `Sampling rule already exists`, rather than letting the shared resource-registry collision error of the state layer become the response surface (services/service-com-amazonaws-xray-awsxray/src/ops/create_sampling_rule.rs and the sampling-rule state).
Traces: xray.create-sampling-rule-duplicate-name-fails.

Cause 3 of 3: when an AWS::XRay::Group resource is refused by X-Ray, the CloudFormation CREATE_FAILED event's ResourceStatusReason omits the upstream-service context, so the failure is indistinguishable from CFN-side template validation.
AWS: recorded behavior only (Smithy models CreateGroup as POST /CreateGroup, GroupName required @length 1-32, FilterExpression, errors InvalidRequestException 400 and ThrottledException 429 — it says nothing about CFN event text). The recording shows that a stack whose AWS::XRay::Group carries an invalid FilterExpression rolls back to ROLLBACK_COMPLETE, the stack-level ROLLBACK_IN_PROGRESS reason is `The following resource(s) failed to create: [TraceGroup]. Rollback requested by user.`, and the resource's own CREATE_FAILED reason wraps the upstream X-Ray refusal with the calling-service context, i.e. the fixed fragments `Service: XRay` and `Status Code: 400` appear in it alongside the service's own message. Fixed text in that reason: `Resource handler returned message:`, `Service: XRay`, `Status Code: 400`, `HandlerErrorCode: InvalidRequest`; variable parts: the logical resource id, the X-Ray message for the specific invalid expression, the X-Ray Request ID and the CFN RequestToken.
Emulator: the rollback and the stack-level reason are right, and the group is correctly never created, but the TraceGroup CREATE_FAILED reason is `Resource handler returned message: "Error Location: line 1, position 27 : Invalid input symbol: '(annotation.scenario = \"x\"'" (RequestToken: <token>, HandlerErrorCode: InvalidRequest)` — it carries neither `Service: XRay` nor `Status Code: 400` nor a Request ID, so the only machine-readable signal that the refusal came from the X-Ray API with a 400 is missing.
Why: a client (or a deploy pipeline) reads the resource event reason to attribute a rollback — upstream API rejection versus CFN template/handler validation, and which upstream status it was. With the service and status stripped, every such attribution is wrong or impossible, and retry logic keyed on an upstream 4xx cannot fire.
Why this is the emulator's: the check's own positive control (an identically shaped stack with a valid FilterExpression) is what the assertion precedes, and the refusal itself is produced by the emulator's X-Ray group validation, so only the reason-string composition diverges.
Fix: when a resource provisioner's underlying service call is refused, compose the CREATE_FAILED ResourceStatusReason with the upstream context block (`(Service: <sdkId>, Status Code: <http status>, Request ID: <id>)`) around the service's message before appending `(RequestToken: ..., HandlerErrorCode: ...)` — in the CloudFormation resource-handler error mapping used by the AWS::XRay::Group provisioner and the stack-event writer.
Traces: xray.deploy-group-via-cloudformation-invalid-filter-expression-rejected.
