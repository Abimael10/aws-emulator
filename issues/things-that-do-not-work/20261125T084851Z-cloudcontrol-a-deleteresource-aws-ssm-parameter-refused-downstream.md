# cloudcontrol: a DeleteResource(AWS::SSM::Parameter) refused downstream under RoleArn reports ErrorCode AccessDenied with the raw IAM denial prose instead of the delete path's GeneralServiceException / "Error occurred during operation 'DeleteParameter'."

> _Note: this issue was identified against the code base at commit `6651c87027da78b467298e3a28f696cadd44fc38`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
DeleteResource

## Description
ONE net-new root cause in the cloudcontrol (Cloud Control API) service. Model citations are from services/service-com-amazonaws-cloudcontrol-cloudapiservice/smithy-model/com-amazonaws-cloudcontrol-cloudapiservice.json.

Cause 1 of 1: when a Cloud Control DELETE of an AWS::SSM::Parameter is refused by the downstream service (here because the request's RoleArn carries an explicit Deny on ssm:DeleteParameter for that parameter), the terminal ProgressEvent carries HandlerErrorCode 'AccessDenied' and the downstream authorization exception's own prose as StatusMessage, instead of the AWS::SSM::Parameter delete path's catch-all 'GeneralServiceException' with the generic placeholder StatusMessage that names the downstream operation. Failing check: cloudcontrol.role-arn-service-role-policy-governs-the-downstream-delete.

AWS: Smithy models ProgressEvent.ErrorCode -> HandlerErrorCode, documented "For requests with a status of FAILED, the associated error code" and pointing at the CloudFormation CLI handler error codes. HandlerErrorCode is a closed enum that carries BOTH values at issue — AccessDenied and GeneralServiceException — so which one a given handler PATH emits for a given downstream exception is part of the resource handler contract, not a cosmetic choice. ProgressEvent.StatusMessage is modelled as "Any message explaining the current status" (@length 0-2048). The model does not fix which member a downstream authorization refusal gets, so the concrete requirement is recorded behavior only: DeleteResource(TypeName="AWS::SSM::Parameter", Identifier=<parameter name>, RoleArn=<a role that may create but is explicitly denied ssm:DeleteParameter on that parameter>) is accepted synchronously (200), the role IS honoured (the parameter is NOT deleted), and the request reaches OperationStatus FAILED with ErrorCode "GeneralServiceException" and StatusMessage exactly "Error occurred during operation 'DeleteParameter'.". In that message the fixed text is "Error occurred during operation '" ... "'." and the only variable part is the name of the downstream API call the handler's delete path made (DeleteParameter for this resource type) — it carries no account id, role name, arn or request id. The AWS::SSM::Parameter handler's Delete path does not map a downstream AccessDeniedException to a specific HandlerErrorCode and falls back to this documented catch-all, UNLIKE its Create path, which maps the same underlying AccessDeniedException to HandlerErrorCode AccessDenied; the recording shows both halves of that asymmetry (the same role's create succeeded, and the suite's create-path propagation handling expects AccessDenied there).

Emulator: OperationStatus FAILED is correct and the RoleArn is correctly honoured (the parameter survives), but GetResourceRequestStatus reports ErrorCode 'AccessDenied' and surfaces the downstream authorization exception verbatim as the StatusMessage, of the form "User: arn:aws:sts::<account-id>:assumed-role/<role-name>/AWSCloudControlAPI is not authorized to perform: ssm:DeleteParameter on resource: <parameter arn> with an explicit deny in an identity-based policy". The account id, role name and parameter arn in that text are per-run values from the request and the emulator's IAM state; the divergence being filed is that the delete path emits the downstream exception's code and prose at all, where AWS emits its own catch-all code and a generic message that names only the downstream operation.

Why: HandlerErrorCode is how a client classifies a failed Cloud Control request without parsing prose, and the CloudFormation-CLI handler contract makes the per-path mapping testable. A client (or a resource-type contract test, or IaC error handling) that distinguishes "this handler path could not classify the downstream fault" (GeneralServiceException) from "the handler itself determined the caller is not authorized" (AccessDenied) is told the wrong thing here, so assertions on the documented delete-path behavior never match. Separately, the StatusMessage contract is inverted: AWS's delete path deliberately emits a short generic message naming the downstream operation, while the emulator leaks the full IAM/STS denial sentence, so a client parsing StatusMessage for the operation name finds no "Error occurred during operation '...'" form at all.

Fix: the error-classification step of the Cloud Control AWS::SSM::Parameter DELETE handler in the cloudcontrol service — the code that turns a downstream refusal into the terminal ProgressEvent's ErrorCode and StatusMessage. The delete path must not reuse the create path's downstream-exception-to-HandlerErrorCode mapping or pass the downstream message through: it must record GeneralServiceException with "Error occurred during operation '<downstream operation>'.". Note related open issue 20261121T195413Z-cloudcontrol-3-net-new-causes-downstream-handler-input.md, which files the OPPOSITE direction (create paths emitting GeneralServiceException where AWS emits InvalidRequest) for the SQS and DynamoDB handlers; it carries only those checks' replay keys and does not cover this delete-path cause, but a single shared classifier may back both and both should be re-replayed after either fix.

Traces: cloudcontrol.role-arn-service-role-policy-governs-the-downstream-delete — the preceding steps all pass (the service role can CREATE the parameter; SSM reports the created Value; the denied DeleteResource terminates FAILED), and it asserts on ErrorCode. The StatusMessage assertion and the subsequent steps (the parameter survives untouched at Version 1, and the identical DeleteResource WITHOUT RoleArn succeeds under the caller's own session, after which SSM answers ParameterNotFound with an empty message) are never reached and must also pass once this is fixed.

## Steps to Reproduce
Boot the emulator and point botocore at it: cc = client("cloudcontrol"), iam = client("iam"), ssm = client("ssm"), sts = client("sts").

1. Create a service role trusted by cloudformation.amazonaws.com and attach an inline policy with two statements: Allow Action "ssm:*" on Resource "*", and Deny Action "ssm:DeleteParameter" on Resource "arn:<partition>:ssm:<region>:<account>:parameter/<name>" (account/partition from sts.get_caller_identity()).
2. Positive control: cc.create_resource(TypeName="AWS::SSM::Parameter", DesiredState=json.dumps({"Name": <name>, "Type": "String", "Value": "created-by-the-service-role"}), RoleArn=<role arn>, ClientToken=str(uuid4())); poll cc.get_resource_request_status to SUCCESS; ssm.get_parameter(Name=<name>) must report that Value. (This passes today.)
3. cc.delete_resource(TypeName="AWS::SSM::Parameter", Identifier=<name>, RoleArn=<role arn>, ClientToken=str(uuid4())); poll cc.get_resource_request_status(RequestToken=...) until OperationStatus is terminal.
   Expected: OperationStatus FAILED, ErrorCode "GeneralServiceException", StatusMessage "Error occurred during operation 'DeleteParameter'.".
   Observed: OperationStatus FAILED (correct), ErrorCode "AccessDenied", StatusMessage the full "User: ... is not authorized to perform: ssm:DeleteParameter on resource: ... with an explicit deny in an identity-based policy" sentence.
4. Then confirm the rest of the check, which the assertion in step 3 prevents from running: ssm.get_parameter(Name=<name>) still reports Value "created-by-the-service-role" and Version 1; the identical cc.delete_resource WITHOUT RoleArn (caller's own session) reaches SUCCESS; ssm.get_parameter(Name=<name>) then raises ParameterNotFound with an empty message.
