# rds: DescribeDBProxyEndpoints misreports a custom DB proxy endpoint — EndpointType omitted, and a deleted endpoint is still served 200 (2 causes)

> _Note: this issue was identified against the code base at commit `3782a478df79733166a479e9eeeb36883992dea2`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
DescribeDBProxyEndpoints

## Description
Two net-new divergence clusters on the rds service, both on DescribeDBProxyEndpoints in the DB-proxy-endpoint lifecycle fixture. The replay reported no owning issue and no blocking stub for either (owned_by empty, stub_path empty). They share one fault: the DB-proxy-endpoint read path does not report the endpoint record AWS reports — it omits a member AWS always emits, and it keeps reporting an endpoint whose lifecycle has ended.

Cause 1 of 2: DescribeDBProxyEndpoints reports a custom DB proxy endpoint with no EndpointType member.
AWS: recorded behavior only — the on-disk Smithy model (services/service-com-amazonaws-rds-amazonrdsv19/smithy-model/com-amazonaws-rds-amazonrdsv19.json) shape com.amazonaws.rds#DBProxyEndpoint models DBProxyEndpointName, DBProxyEndpointArn, DBProxyName, Status (DBProxyEndpointStatus: available|modifying|incompatible-network|insufficient-resource-limits|creating|deleting), VpcId, VpcSecurityGroupIds, VpcSubnetIds, Endpoint, CreatedDate, TargetRole (READ_WRITE|READ_ONLY), IsDefault and EndpointNetworkType, and models NO EndpointType member; the recording nevertheless shows AWS emitting an EndpointType member in each DBProxyEndpoints.member of the DescribeDBProxyEndpointsResponse, with the value CUSTOM for an endpoint that CreateDBProxyEndpoint created (the same member that carries IsDefault false). The requirement is therefore the recorded wire shape: the report of a caller-created endpoint carries EndpointType = CUSTOM alongside IsDefault = false. Hypothesis: AWS reports the RDS-created default endpoint (IsDefault true) with the complementary value, but the recording does not show that case, so only the CUSTOM case is asserted here.
Emulator: the step is answered HTTP 200 with the DescribeDBProxyEndpointsResponse/DescribeDBProxyEndpointsResult/DBProxyEndpoints envelope and the endpoint's other members, but $.DescribeDBProxyEndpointsResponse.DescribeDBProxyEndpointsResult.DBProxyEndpoints.member.EndpointType is absent (replay: "missing (expected 'CUSTOM', got None)"). The emulator cannot emit it today: the generated wire type has no such field, because the member is absent from this model revision.
Why: a client that distinguishes a proxy's default endpoint from the custom read/write and read-only endpoints it created — the documented way to pick the endpoint to connect through, and what the CLI/SDK surface as EndpointType — reads a null/absent attribute for every endpoint. Code that branches on EndpointType == 'CUSTOM' (or asserts the field is present) treats a created custom endpoint as untyped and either skips it or fails deserialization on a required-by-the-client field.
Fix: the DescribeDBProxyEndpoints projection/serializer for the DBProxyEndpoint wire shape — the endpoint record must project an EndpointType of CUSTOM for an endpoint written by CreateDBProxyEndpoint (IsDefault false) and the complementary value for the synthesized default endpoint, and the serializer must emit that member even though this model revision omits it.
Traces: rds-db-proxy-lifecycle#task#8 (cluster of 1). Projection sites: services/service-com-amazonaws-rds-amazonrdsv19/src/ops/describe_db_proxy_endpoints.rs lines 210-219 (`crate::state::default_proxy_endpoint(proxy)` for the default endpoint and `added.to_wire(Some(proxy))` for each stored custom endpoint); the wire type that has no field to carry it is `DBProxyEndpoint` at services/service-com-amazonaws-rds-amazonrdsv19/src/ops/types/shared_types.rs lines 1399-1414.

Cause 2 of 2: after the fixture deletes the custom proxy endpoint, DescribeDBProxyEndpoints keeps answering HTTP 200 with that endpoint in state 'available' instead of the modeled 404 not-found fault, so the delete waiter never settles.
AWS: Smithy DeleteDBProxyEndpoint input DBProxyEndpointName (required, len 1..63, pattern ^[a-zA-Z](?:-?[a-zA-Z0-9]+)*$) returns the endpoint and removes it; Status passes through 'deleting' (DBProxyEndpointStatus) and the endpoint then stops existing. DescribeDBProxyEndpoints models DBProxyEndpointNotFoundFault (errorKind client, httpError 404, awsQueryError code DBProxyEndpointNotFoundFault / httpResponseCode 404, doc "The DB proxy endpoint doesn't exist"), so a report narrowed by DBProxyEndpointName to a deleted endpoint is refused HTTP 404 with an awsQuery ErrorResponse envelope: Error.Type Sender, Error.Code DBProxyEndpointNotFoundFault, Error.Message of the fixed form "DBProxyEndpoint '<name>' not found." — the quoted name is the DBProxyEndpointName from the request, the rest of the message is the fixed text, and the envelope's RequestId is per-run.
Emulator: for 19 polling attempts over the fixture's 180 s cap the request is still answered HTTP 200 with DescribeDBProxyEndpointsResponse.DescribeDBProxyEndpointsResult.DBProxyEndpoints.member for the deleted endpoint, Status 'available'; no ErrorResponse is produced and the observed error code is None (replay: "status: expected 404, got 200"; "poll: error code None not in ['DBProxyEndpointNotFoundFault'] after 19 attempt(s)"). Nothing ever removes the endpoint record, because DeleteDBProxyEndpoint is still an unimplemented scaffold that answers 501 (services/service-com-amazonaws-rds-amazonrdsv19/src/ops/delete_db_proxy_endpoint.rs line 158, `Scaffolded::not_implemented`), and the describe read path projects every stored custom endpoint unconditionally with no deleting/deleted lifecycle.
Why: the delete half of the custom-proxy-endpoint lifecycle is unobservable. A client that deletes an endpoint and waits for it to disappear (the documented completion signal, and what the SDK waiters poll for) waits forever and then times out, while a client that re-reads the endpoint is told it is 'available' and may keep routing connections to an endpoint it deleted; a caller that recreates the endpoint under the same name also hits a stale record instead of a clean create.
Fix: the DeleteDBProxyEndpoint handler plus the rds proxy-endpoint state it must mutate, and the DescribeDBProxyEndpoints read path over it — delete must transition the stored endpoint through 'deleting' and remove it, and the describe narrowing must then raise the modeled DBProxyEndpointNotFoundFault (HTTP 404, awsQuery code DBProxyEndpointNotFoundFault, message "DBProxyEndpoint '<name>' not found.") for a name that no longer resolves. No open stub issue carries this step's replay key; the related open issue 20261122T063107Z-rds-describedbproxyendpoints-reports-only-a-synthesized-default-endpoint.md covers the earlier 200->404 read-back failure at task#8 (the custom endpoint being invisible) and does NOT cover either cause here — the read path now serves the endpoint, but without EndpointType and without ever ceasing to serve it.
