# elasticache: 2 net-new snapshot causes — the single-node CreateSnapshot→CopySnapshot→DeleteSnapshot round trip and the create→write→snapshot→delete→restore round trip never converge, so neither reaches any verdict

## Description
Two net-new root causes in the elasticache emulator, grounded in the only two failing checks of this replay that the suite report binds to NO open issue and does not mark ALREADY FILED. Each cause is independent and must be closed on its own; re-replay the check id listed under each cause's Traces before submitting.

=== Cause 1 of 2: the snapshot copy-and-delete round trip of a single-node cache cluster never reaches a verdict ===
Failing check: elasticache.snapshot-of-a-single-node-cluster-copies-and-deletes, whose whole detail is `Error: Check timed out after 60.0s` — no assertion fired, no error code, no non-2xx: every control-plane call was answered while the flow never got through its six sequential state waits.
AWS: Smithy (services/service-com-amazonaws-elasticache-amazonelasticachev9/smithy-model/com-amazonaws-elasticache-amazonelasticachev9.json): CreateSnapshot{ReplicationGroupId, CacheClusterId, SnapshotName(required), KmsKeyId, Tags} -> Snapshot, errors CacheClusterNotFoundFault (404, awsQueryError CacheClusterNotFound), InvalidCacheClusterStateFault (400, InvalidCacheClusterState), SnapshotAlreadyExistsFault (400); Snapshot$SnapshotStatus is documented "Valid values: creating | available | restoring | copying | deleting"; CopySnapshot{SourceSnapshotName(required), TargetSnapshotName(required), TargetBucket, KmsKeyId, Tags} -> an independent second Snapshot, errors InvalidSnapshotStateFault (400, InvalidSnapshotState), SnapshotAlreadyExistsFault (400), SnapshotNotFoundFault (404, SnapshotNotFoundFault); DescribeSnapshots{SnapshotName} -> Snapshots with SnapshotNotFoundFault (404); DeleteSnapshot -> the snapshot being removed; DeleteCacheCluster removes the cluster so DescribeCacheClusters answers 404 CacheClusterNotFound. The model states NO timing. Recorded behavior only: each stage settles so that a polling client converges — the cluster reaches CacheClusterStatus 'available', the manual snapshot reaches SnapshotStatus 'available' carrying exactly ONE NodeSnapshot for a single-node cluster, the copy reaches 'available' recording the ORIGINAL source cluster's CacheClusterId with one NodeSnapshot, the copy survives deleting its source and stays 'available', both snapshots then stop resolving, and finally the cluster stops resolving. Names, ids and timestamps are per-run values; the requirement is that a client polling each stage converges and can observe those properties.
Emulator: the check is killed at the per-check budget (`Error: Check timed out after 60.0s`) with NO assertion reached, so none of its own verdicts (`expected exactly 1 NodeSnapshot for a single-node cluster, got <n>`, `expected the copy to record the original source cluster <id>`, `expected both snapshots to coexist`, `expected the copy <name> to survive deleting its source`, `expected <name> to be gone after delete`) was ever produced. The flow has SIX sequential state waits (cluster->available, source snapshot->available, copy->available, source snapshot->gone, copy->gone, cluster->gone) polled at a 15 s cadence, and every transient phase is held for a deliberately non-zero span that the FIRST read issued after the starting call still observes, so a waiting client pays one whole poll interval per stage: 6 x 15 s = 90 s against a 60 s budget. The flow therefore cannot finish no matter what the emulator would have answered, and CopySnapshot's semantics (independence from the source, the source cluster it records, its single NodeSnapshot) are left entirely unverified.
Why: a client that snapshots a cache, copies the snapshot, deletes the original and tears the cluster down gets no verdict at all — every call returns 200 while the sequence never completes, so the caller cannot distinguish 'still applying' from 'never applied', and SDK waiters and CI pipelines block. A snapshot copy is the ElastiCache backup-retention story: a client cannot confirm its copy is independent of the snapshot it was taken from.
Fix: the elasticache crate — (a) the status-settling path of its state (the `pending_status`/`pending_removal` due-instant clock and its `settled_cluster_mut` / `settled_snapshot_mut` / snapshot-purge readers), so a record whose transition is already due reads back SETTLED to the first Describe that observes it and a multi-stage flow converges in a bounded number of polls instead of one full client poll interval per stage, while the create/copy/delete RESPONSE keeps reporting the transient status other checks assert; and (b) the CreateSnapshot / CopySnapshot / DeleteSnapshot / DeleteCacheCluster handlers' use of that clock. Related open issue 20261124T135051Z-elasticache-the-snapshot-copy-and-delete-round-trip.md describes this same family and names this check in its Issue-Trace-Ids, but the suite report does NOT mark this failure OWNED by it (its replay key is pinned to a frame the current failure no longer takes), so it is filed here rather than left closed-unrun.
Traces: elasticache.snapshot-of-a-single-node-cluster-copies-and-deletes.

=== Cause 2 of 2: the create -> write -> snapshot -> delete -> restore round trip of a cache cluster never reaches a verdict, so snapshot data persistence is unverified ===
Failing check: elasticache.e2e-cluster-snapshot-restore-data-persists, whose whole detail is `Error: Check timed out after 60.0s` — no assertion fired.
AWS: Smithy (same model): CreateCacheCluster accepts SnapshotName ("seed the new cluster from an existing snapshot") alongside CacheClusterId(required), Engine, CacheNodeType, NumCacheNodes, CacheSubnetGroupName, SecurityGroupIds and returns CacheCluster$CacheClusterStatus; CacheNode$Endpoint / Endpoint{Address "The DNS hostname of the cache node", Port} is what "client programs" connect to; CreateSnapshot -> Snapshot with SnapshotStatus "creating | available | restoring | copying | deleting"; DescribeSnapshots{SnapshotName} reports that snapshot and answers SnapshotNotFoundFault (404) once gone; DeleteCacheCluster removes the cluster so DescribeCacheClusters answers 404 CacheClusterNotFound (awsQueryError CacheClusterNotFound). The model states NO timing. Recorded behavior only: each stage settles so that a polling client converges — the source cluster reaches 'available', its published CacheNodes[0].Endpoint speaks RESP from inside the cluster's VPC (`SET <key> <value>` -> `+OK`), the snapshot reaches 'available', the deleted cluster stops resolving, and a cluster created with SnapshotName=<that snapshot> reaches 'available' and answers `GET <key>` with the bulk string `$<value>`. Ids, keys and values are per-run; the requirement is convergence plus the restored keyspace holding what the snapshot captured.
Emulator: the check is killed at the 60 s per-check budget with NO assertion reached, so neither of its verdicts (`expected snapshot <name> to be available, got <status>`, `restored cluster data mismatch: <read> != <value>`) was ever produced. The flow has FOUR sequential waits (cluster->available, snapshot->available, cluster->gone, restored cluster->available) polled at a 20 s cadence, and the same settling clock as Cause 1 leaves every transient phase observable to the first read after its starting call, so the client's sleeps alone (4 x 20 s) exceed the budget. Snapshot/restore data persistence is therefore wholly unexercised.
Why: snapshot-and-restore is the ElastiCache durability story. A client that snapshots a cache, tears it down and restores hangs instead of succeeding or failing diagnosably and can never verify a backup; because every control-plane call answers 200 while nothing converges, the caller cannot tell 'still applying' from 'never applied' and SDK waiters/CI pipelines block.
Fix: the elasticache crate — the same settling clock as Cause 1, plus the CreateSnapshot / DeleteCacheCluster / CreateCacheCluster(SnapshotName=...) handlers and the restored keyspace they seed, so the restored cluster's published node endpoint serves the keys the snapshot captured. Related open issue 20261125T064538Z-elasticache-3-net-new-causes-a-3-shard.md lists this check id in its Issue-Trace-Ids, but the suite report does NOT mark this failure OWNED by it (that issue currently owns only the cluster-mode-routing and user-group-revocation checks of this replay), so it is filed here rather than left closed-unrun.
Traces: elasticache.e2e-cluster-snapshot-restore-data-persists.
