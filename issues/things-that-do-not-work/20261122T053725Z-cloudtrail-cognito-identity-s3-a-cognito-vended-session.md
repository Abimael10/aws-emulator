# cloudtrail__cognito-identity__s3: a Cognito-vended session's audit record carries no userIdentity.sessionContext.webIdFederationData, so web-identity federation is unauditable

> _Note: this issue was identified against the code base at commit `fceda236fd74c050af49bdc92c31da84e151e4fd`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
LookupEvents

## Description
Cause 1 of 1: every CloudTrail record of a call made with credentials vended by cognito-identity GetCredentialsForIdentity omits the userIdentity.sessionContext.webIdFederationData block entirely, so the record cannot be told apart from a plain sts:AssumeRole session's record and says nothing about the web identity the session was federated from.

AWS: CloudTrail's record-contents reference documents, for a session obtained through sts:AssumeRoleWithWebIdentity, a userIdentity.sessionContext.webIdFederationData object beside sessionIssuer and attributes, with two members: federatedProvider — the issuer of the web identity token, which for a session Amazon Cognito vended on an identity's behalf is the fixed string 'cognito-identity.amazonaws.com' — and attributes, the map of federation claims the token was exchanged under. For a Cognito identity-pool session those attributes are keyed by the provider name: '<provider>:aud' = the identity pool id the credentials were vended for, '<provider>:sub' = the IdentityId, and '<provider>:amr' = the authentication-method reference of the session ('unauthenticated' for a guest GetId identity; containing 'authenticated', and naming the login provider, for an authenticated/developer identity). A session minted by plain sts:AssumeRole involves no web identity and so carries NO webIdFederationData at all — presence of the member is exactly what separates the two in event history. The fixed text here is the member names and the literal provider 'cognito-identity.amazonaws.com' and the ':aud'/':sub'/':amr' key suffixes; the variable parts (pool id, identity id, amr values, provider name) come from the request and the emulator's identity-pool state. The Smithy model carries the record only as an opaque string, so the contents are a documented-behavior requirement, not a model constraint (Smithy: com.amazonaws.cloudtrail#Event member CloudTrailEvent — "A JSON string that contains a representation of the event returned"; member AccessKeyId — the access key id of the temporary credentials the request was signed with).

Emulator: the record for the vended session is otherwise well-formed — userIdentity.type = 'AssumedRole', userIdentity.arn = arn:aws:sts::<account>:assumed-role/<pool-role>/CognitoIdentityCredentials, accessKeyId = the vended key, and sessionContext.sessionIssuer naming the identity pool's mapped role all match — but sessionContext has no webIdFederationData key whatsoever, so the checks read webIdFederationData=None (and {} after their `or {}` fallback) where federatedProvider was required. The shared recorder has no place to hold the facts: services/common/src/management_events.rs RecordedSession (lines ~908-935) declares principal_type / principal_id / arn / account_id / user_name / issuer / source_identity / created_at / expires_at and no web-identity federation member, and ManagementEvent::to_cloudtrail_event_json() (lines ~1221-1254) builds sessionContext from exactly sessionIssuer + attributes.creationDate + sourceIdentity. Correspondingly, cognito-identity's GetCredentialsForIdentity, which mints the session and is the only component that knows the pool id, the IdentityId and the AMR, remembers nothing of them in the SessionAuditDirectory.

Why: a client cannot audit web-identity federation at all. The questions CloudTrail exists to answer for an identity pool — which end user (sub) under which pool (aud) performed an action, and whether the session was a guest or an authenticated one (amr) — have no answer in the record, and because the member is absent rather than empty, a Cognito-federated session is byte-for-byte indistinguishable from a plain AssumeRole session of the same role, so a reader cannot even classify the call's provenance. Least-privilege review, per-end-user incident response and guest-vs-authenticated reporting over identity-pool traffic are all unexercisable.

Fix: two seams, one defect. The shared session audit state — services/common/src/management_events.rs RecordedSession / SessionAuditDirectory — must carry the web-identity federation facts of a session, and ManagementEvent::to_cloudtrail_event_json() must emit sessionContext.webIdFederationData{federatedProvider, attributes} when the session has them (and continue to omit the member for a session that does not); the cognito-identity GetCredentialsForIdentity handler, where the session is minted, must populate them with provider 'cognito-identity.amazonaws.com' and the aud/sub/amr attributes of the identity it vended for.

Traces: cloudtrail__cognito-identity__s3.xsvc-cognito-identity-1-vended-session-list-buckets-audited-as-cognito-federation (the authenticated developer identity: webIdFederationData=None); cloudtrail__cognito-identity__s3.xsvc-cognito-identity-1-guest-and-authenticated-sessions-audited-with-own-amr-and-role (both the guest and the authenticated session: got {}). Neither check was marked ALREADY FILED or OWNED by the replay report. The open issues 20261031T171713Z-cloudtrail-audit-records-are-attributed-to-the-ambient.md (missing sessionContext/sourceIPAddress on assumed-role records) and 20261114T025704Z-cloudtrail-cognito-identity-s3-getcredentialsforidentity-re-serves-the.md (one AccessKeyId re-served per identity) read as adjacent but neither carries this replay key or mentions webIdFederationData; they are named only so a fixer can see the neighbourhood. Code citations: services/common/src/management_events.rs:908-935 (RecordedSession), :1221-1254 (sessionContext assembly).

## Steps to Reproduce
1. Create a cognito-identity identity pool (AllowUnauthenticatedIdentities=true) with a developer provider; create two IAM roles trusting cognito-identity.amazonaws.com via sts:AssumeRoleWithWebIdentity (one for amr 'authenticated', one for 'unauthenticated'), each granting s3:ListAllMyBuckets, and attach them with SetIdentityPoolRoles.
2. Mint an authenticated identity with GetOpenIdTokenForDeveloperIdentity and a guest identity with GetId.
3. For each identity call GetCredentialsForIdentity and use the returned temporary credentials to call s3:ListBuckets.
4. Call cloudtrail:LookupEvents with LookupAttributes=[{AttributeKey: 'AccessKeyId', AttributeValue: <that session's AccessKeyId>}] and json.loads the matching record's CloudTrailEvent.
5. Read userIdentity.sessionContext. Observe sessionIssuer and attributes.creationDate are present but webIdFederationData is absent entirely; AWS returns webIdFederationData with federatedProvider 'cognito-identity.amazonaws.com' and attributes carrying '<provider>:aud' = the pool id, '<provider>:sub' = the IdentityId and '<provider>:amr' = the session's authentication-method reference.
