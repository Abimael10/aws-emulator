# opensearch: 3 net-new causes — UpdateIndex refuses an unavailable cluster with a 400 schema ValidationException instead of a 424 DependencyFailureException, and the 3 s wall-clock domain-work window makes a config change unobservable in flight and costs a provisioning poll a full interval

> _Note: this issue was identified against the code base at commit `7af2f9baaab69289469a980a729eadc620ae14df`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
UpdateIndex

## Description
Three net-new root causes in the opensearch control plane, each grounded in its own failing behavioral check. All three concern the same crate (services/service-com-amazonaws-opensearch-amazonopensearchservice) but are independent defects and must each be closed before this issue is submitted.

Cause 1 of 3: UpdateIndex validates the submitted IndexSchema BEFORE it checks that the domain's cluster is available, so a call that AWS refuses as a dependency failure is refused as a schema validation error. Failing check: opensearch.dependency-failure-on-update-index.
AWS: Smithy: UpdateIndex (PUT /2021-01-01/opensearch/domain/{DomainName}/index/{IndexName}) models both ValidationException (client, httpError 400) and DependencyFailureException (client, httpError 424 — "An exception for when a failure in one of the dependencies results in the service being unable to fetch details about the resource"). The model says nothing about the order the two preconditions are applied in, so for the order this is recorded behavior only: the recording shows that on a domain whose EngineVersion does NOT support Automatic Semantic Enrichment the call is refused with ValidationException and the fixed text "Automatic Semantic Enrichment feature is not supported on this software version." (the emulator already matches this arm), while on a domain running a version that DOES support the feature but whose cluster has not finished provisioning the identical call is refused with DependencyFailureException, HTTP 424, message "The domain is not available now, please try again later." — that message is entirely fixed text with no variable part. The index-schema rule AWS applies only once the cluster is reachable ("Updates to index settings is not supported.") is therefore never what an unavailable domain answers.
Emulator: for the same UpdateIndex call (IndexSchema = {"settings": {"index": {"number_of_shards": 1}}}) against a just-created domain on the newest version ListVersions offers, it answers ValidationException / HTTP 400 with message 'Updates to index settings is not supported.' — the schema rule, with no cluster-availability precondition in front of it.
Why: a client cannot tell "not ready yet, retry" from "your request is invalid, never retry". Every AWS SDK/retry wrapper keyed on DependencyFailureException (424) — including the recorded suite's own retry helpers — treats a 400 ValidationException as terminal and abandons an index operation that would have succeeded moments later; conversely a caller is told its schema is unsupported when the schema was never examined.
Fix: the UpdateIndex handler's precondition order — the cluster-availability (dependency) check belongs in front of the index-schema validation, and must raise DependencyFailureException with AWS's fixed message, so the version gate, the dependency gate and the schema rule are evaluated in AWS's order (version gate, then availability, then schema).

Cause 2 of 3: a cluster-configuration change completes 3 s after UpdateDomainConfig, so DescribeDomainChangeProgress can never be observed in flight by more than a single poll and stage progression is unobservable. Failing check: opensearch.osx-deep-opensearch-3-blue-green-scale-out-data-continuity.
AWS: Smithy: ChangeProgressStatusDetails carries Status (OverallChangeStatus), TotalNumberOfStages and ChangeProgressStages (a list of ChangeProgressStage{Name,Status,Description,LastUpdated}); DescribeDomainChangeProgress exists precisely so a client can watch a blue/green deployment advance stage by stage. The model does not state a duration, so the duration is recorded behavior only: the recording shows an InstanceCount 2 -> 3 scale-out staying non-COMPLETED across several consecutive polls taken 4 s apart, with the count of COMPLETED stages strictly increasing between the first in-flight poll and the final one, and the data plane serving the same documents throughout.
Emulator: the change is owed its outcome DOMAIN_WORK = 3 s after the call, so a client polling every 4 s sees the change in flight at most ONCE and reads COMPLETED on its next poll. The check observed exactly 1 in-flight poll ("only 1 continuity probe(s) ran while the change was in flight") where AWS yields two or more, and the stage series it needs to show advancement (series[-1] > series[0]) cannot be collected.
Why: a client or orchestrator that reports deployment progress to a user, or that verifies read continuity while the topology changes, has nothing to observe — the whole staged-progress surface is reachable only by a caller that happens to poll within 3 s of its own write, and no number of stages is ever seen advancing.
Fix: the domain configuration-change lifecycle and its stage materialisation — the ConfigChange record's settle/to_details path (consumed by Domain::settle and reported through Domain::latest_change()->to_details) and the span that governs it. The right shape is progress driven by OBSERVATION rather than by wall clock: successive DescribeDomainChangeProgress reads should walk the stage list (PENDING -> stages completing one by one -> COMPLETED) regardless of how fast the client polls, which also resolves the tension with Cause 3 and with the already-open issue named below.

Cause 3 of 3: the domain provisioning transition is gated on wall clock, so the FIRST DescribeDomain after CreateDomain always reports Processing=true and a polling client loses one full poll interval; a wait that requires two quiescent polls at 30 s therefore burns the entire 60 s check budget before the operation under test is ever called. Failing check: opensearch.upgrade-domain-server-managed-progress-tracking.
AWS: Smithy: DomainStatus$Processing / $DomainProcessingStatus (DomainProcessingStatusType: Creating, Active, Modifying, ...). AWS does pass through Creating/Processing=true and reaches Active asynchronously, and the model states no duration, so this is recorded behavior only: what the recording shows is that the check completes its domain wait and goes on to call UpgradeDomain and poll GetUpgradeStatus to a terminal UPGRADE step with StepStatus SUCCEEDED, then GetUpgradeHistory and DescribeDomain (EngineVersion == TargetVersion).
Emulator: processing_until is set DOMAIN_WORK = 3 s ahead and the terminal state is materialised only by a read taken after that instant, so the first probe (issued immediately after CreateDomain) necessarily reads Processing=true; the client sleeps 30 s, reads Processing=false (consecutive=1), sleeps another 30 s for its second quiescent poll — and the suite kills the check at 60 s ("Check timed out after 60.0s") before UpgradeDomain, GetUpgradeStatus, GetUpgradeHistory are exercised at all.
Why: any caller whose deadline is in the tens of seconds pays one of ITS OWN poll intervals per transition no matter how quickly it polls, because the transition is gated on elapsed wall clock rather than on progress; here it means the whole server-managed engine-upgrade surface is never exercised and its answers are unverified.
Fix: the domain lifecycle state that materialises Processing/DomainProcessingStatus (the DOMAIN_WORK span and Domain::settle) — gate the transition on observation (first read still reports the transient status, the NEXT read reports Active) instead of on a fixed wall-clock span. NOTE: the open issue 20261121T121321Z-opensearch-wall-clock-transient-windows-cost-a-client.md describes this same root cause for six OTHER checks, but it does not carry opensearch.upgrade-domain-server-managed-progress-tracking in its replay key set, so that check is not covered by it and is filed here; a fixer closing that issue should re-replay this check too.

Traces: opensearch.dependency-failure-on-update-index (Cause 1), opensearch.osx-deep-opensearch-3-blue-green-scale-out-data-continuity (Cause 2), opensearch.upgrade-domain-server-managed-progress-tracking (Cause 3). Code: services/service-com-amazonaws-opensearch-amazonopensearchservice/src/state.rs line 786 (DOMAIN_WORK = 3 s); src/state/domains.rs lines 746-795 (Domain::settle, processing_until materialisation) and line 1293 (change_progress_details from latest_change()->to_details).
