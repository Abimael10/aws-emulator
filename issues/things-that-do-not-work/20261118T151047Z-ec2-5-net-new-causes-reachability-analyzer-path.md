# ec2: 5 net-new causes — Reachability Analyzer path components omit the ACL hop, wrong ExplanationCode, an ENI→IGW analysis still ends `failed`, CreateVpcEndpoint accepts a policy on a full-access-only service, and CreateIpamRoutingPolicyRegistration answers 501

> _Note: this issue was identified against the code base at commit `4f65c0b98ba8534c1e9a66f38e6904bfd7dc41bb`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
StartNetworkInsightsAnalysis

## Description
Five net-new root causes in the ec2 service, bundled because they share that service token. Each is a separate defect with its own failing checks; all five must be closed before the listed checks pass.

Related open issue, named for context and NOT a duplicate: 20261106T015719Z-ec2-reachability-analyzer-analyses-always-end-failed-with.md lists the three `asgssh-reachability-*` check ids under an earlier symptom (every analysis ended Status `failed`). The emulator has moved on: an ENI→ENI analysis now reaches Status `succeeded` with a NetworkPathFound verdict, so those checks now fail at LATER assertions — the ones described in Causes 1 and 2 — which that issue's replay keys do not carry. Cause 3 is the residue of that earlier symptom on a path shape that still is not traced.

Cause 1 of 5: on a reachable path, ForwardPathComponents carries no component for the network ACL the path crosses, so the matching ACL rule is invisible.
AWS: Smithy (services/service-com-amazonaws-ec2-amazonec2/smithy-model/com-amazonaws-ec2-amazonec2.json) — StartNetworkInsightsAnalysis → NetworkInsightsAnalysis; NetworkInsightsAnalysis.ForwardPathComponents is a PathComponentList, and PathComponent carries `Component` (AnalysisComponent, with Id) together with `AclRule` (AnalysisAclRule: Cidr, Egress, PortRange, Protocol, RuleAction, RuleNumber — "The network ACL rule"). Recorded behavior: a succeeded analysis of an ENI→ENI tcp/22 path whose destination subnet is associated with a network ACL emits exactly one ForwardPathComponents entry whose Component.Id is that ACL id and whose AclRule is the FIRST matching ingress entry — the lowest matching rule number wins, so an allow at 100 ahead of a deny at 150 yields (RuleNumber 100, RuleAction "allow"), and a deny at 50 covering ports 23-1024 is skipped for tcp/22 so the same (100, "allow") hop is reported.
Emulator: Status and NetworkPathFound are right (the preceding assertions pass), but ForwardPathComponents contains no entry at all that carries an AclRule — filtering the forward path for components with an AclRule whose Component.Id is the ACL yields the empty list.
Why: Reachability Analyzer is the API a client uses to learn WHICH rule admitted or closed a path. With no ACL hop in the forward path, a client cannot tell which NACL entry matched, cannot verify NACL rule-number ordering, and any diagnosis tool that walks ForwardPathComponents to attribute a hop to a rule reports "no ACL on this path" for a path that crosses one.
Fix: the StartNetworkInsightsAnalysis / DescribeNetworkInsightsAnalyses path-evaluation and its serializer — the forward-path builder must emit a PathComponent for each network ACL the path traverses, populated from the stored NACL entries evaluated in ascending rule-number order, with Component.Id set to the ACL id and AclRule set to the first matching entry.
Traces: ec2.asgssh-reachability-allow-all-ordered-before-deny-finds-path, ec2.asgssh-reachability-deny-on-neighbouring-ports-does-not-block-22.

Cause 2 of 5: the Explanation for a path blocked by a network ACL carries the wrong ExplanationCode.
AWS: Smithy — Explanation.ExplanationCode is a String documented as "The explanation code", and the Explanation shape's own documentation points at the published Reachability Analyzer explanation-code list ("Describes an explanation code for an unreachable path. For more information, see Reachability Analyzer explanation codes"); the model does not enumerate the values, so this is recorded behavior only for the value itself. Recorded behavior: a path blocked by an ingress deny on the destination subnet's ACL answers Status "succeeded", NetworkPathFound false and exactly one Explanations entry whose ExplanationCode is the fixed token `SUBNET_ACL_RESTRICTION`, with Acl.Id, AclRule.RuleNumber / AclRule.RuleAction, Direction "ingress" and Subnet.Id taken from the request's resources and the emulator's own state.
Emulator: every other field of that Explanation is correct — the ACL id, rule number, RuleAction "deny", Direction "ingress" and the destination subnet id all match — but ExplanationCode is the token `ACL_RULE`, which AWS does not emit for this class. (Observed tuple: ('ACL_RULE', <acl-id>, 50, 'deny', 'ingress', <subnet-id>); AWS: ('SUBNET_ACL_RESTRICTION', <acl-id>, 50, 'deny', 'ingress', <subnet-id>) — only the first element diverges, and the ids/rule number shown are per-run values filling the template, not part of it.)
Why: the explanation code is the machine-readable reason a client branches on. A client that switches on SUBNET_ACL_RESTRICTION to point an operator at the blocking NACL falls through to its unknown-code branch and reports no cause, even though the analysis did identify the ACL.
Fix: the Explanation serialization in the Reachability Analyzer result builder — the code emitted for a subnet-ACL block must be the published explanation-code token, not an internal name.
Traces: ec2.asgssh-reachability-path-blocked-by-nacl-deny-22-until-replaced.

Cause 3 of 5: an analysis of a network-interface → internet-gateway path still terminates Status `failed` with an emulator-authored StatusMessage and no verdict.
AWS: Smithy — AnalysisStatus = running | succeeded | failed; NetworkInsightsAnalysis.StatusMessage is documented as "The status message, if the status is failed", and NetworkPathFound as "Indicates whether the destination is reachable from the source". CreateNetworkInsightsPath accepts a network interface as Source and an internet gateway as Destination. Recorded behavior: that path's analysis reaches Status "succeeded" and carries a NetworkPathFound verdict (so DeleteNetworkInsightsAnalysis can then remove a completed analysis); `failed` is reserved for an analysis AWS could not run, and no AWS StatusMessage announces an emulator.
Emulator: the analysis settles at Status "failed" with no NetworkPathFound, no ForwardPathComponents and no Explanations, and StatusMessage set to the fixed emulator text "This emulator does not perform Reachability Analyzer path tracing, so no reachability result was produced for this path." — text AWS never emits. So the ENI→ENI case now traces (see Causes 1 and 2) while this path shape does not, and the downstream DeleteNetworkInsightsAnalysis contract is never reached.
Why: a client waiting for a terminal analysis gets an AWS-side failure signal rather than a verdict, so retry logic loops or an operator is told the analysis broke rather than whether the path is open; and the emulator's own name leaks into a modeled response field.
Fix: the StartNetworkInsightsAnalysis / DescribeNetworkInsightsAnalyses handlers and their path evaluation over stored VPC state — gateway endpoints of a path (internet gateway, and the other Source/Destination component types CreateNetworkInsightsPath accepts) must be traced to a succeeded verdict instead of falling back to a `failed` status, and the emulator-authored StatusMessage must go away.
Traces: ec2.op-contract-delete-network-insights-analysis.

Cause 4 of 5: CreateVpcEndpoint accepts a PolicyDocument for an endpoint service that supports only the full-access endpoint policy.
AWS: Smithy — CreateVpcEndpoint input carries ServiceName and PolicyDocument and declares no error shapes (ec2Query), so the refusal code and message are the contract; DescribeVpcEndpointServices' ServiceDetail.VpcEndpointPolicySupported states whether the service accepts a custom endpoint policy. Recorded behavior: for a service whose catalogue entry reports VpcEndpointPolicySupported=false (the AppStream streaming service, com.amazonaws.<region>.appstream.streaming), CreateVpcEndpoint with ANY PolicyDocument — including an allow-all one — is refused with code `InvalidParameter` and the message "Service <ServiceName> only supports the full-access endpoint policy.": that fixed text with the service name taken verbatim from the request's ServiceName. Nothing is created: a tag-filtered DescribeVpcEndpoints finds no endpoint, and the same request without PolicyDocument is the control that succeeds.
Emulator: the call SUCCEEDS — no error is raised, so there is no code or message at all, and the endpoint is created with the caller's narrowing policy.
Why: a client can install an endpoint policy real AWS rejects, so an estate that builds cleanly here fails on AWS, and the emulator's stored endpoint diverges from what AWS would hold. The catalogue already reports VpcEndpointPolicySupported=false (that assertion passes), so the flag is present and simply not consulted.
Fix: CreateVpcEndpoint's validation — gate PolicyDocument on the target service's VpcEndpointPolicySupported flag in the endpoint-service catalogue and refuse before anything is created. The open issue 20261114T033033Z-ec2-8-net-new-causes-vpc-endpoint-not.md carries the sibling gap on ModifyVpcEndpoint for com.amazonaws.<region>.iot.data; it does not carry this check id and does not cover the create path.
Traces: ec2.asvpce-streaming-vpce-custom-policy-rejected.

Cause 5 of 5: CreateIpamRoutingPolicyRegistration answers HTTP 501 NotImplemented instead of the IncorrectState refusal for an internet-registry association that is not enable-complete.
AWS: Smithy — CreateIpamRoutingPolicyRegistration(IpamInternetRegistryAssociationId required, Cidr required, Asns required, PermitMoreSpecificAnnouncements, MaxLength 0..48, Description, Force, ClientToken, DryRun) → IpamRoutingPolicyRegistrationDelta; the operation "Creates a routing policy registration and publishes Route Origin Authorizations (ROAs) to the RPKI", and the model declares no error shapes, so code and message are the contract. Recorded behavior: the registration requires the association in state `enable-complete` (an RIR BPKI handshake), so on a freshly created association it is refused with a 400 whose code is `IncorrectState` and whose message is "The specified action is not valid. The Internet Registry association <IpamInternetRegistryAssociationId> is in an invalid state <State>." — that fixed text, with the association id taken from the request and <State> taken from the association's current state in the emulator's own store (the check reads it back through DescribeIpamInternetRegistryAssociations first).
Emulator: the call answers code `NotImplemented` (HTTP 501). The handler is still a scaffold stub — services/service-com-amazonaws-ec2-amazonec2/src/ops/create_ipam_routing_policy_registration.rs returns `Scaffolded::not_implemented("CreateIpamRoutingPolicyRegistration")` and still carries the `//! SCAFFOLDED, NOT IMPLEMENTED` marker — and the replay report did NOT mark this check as blocked by an unimplemented operation, so no auto-filed issue covers it.
Why: a 501 is a server fault, not a client refusal. A client that creates an association and immediately registers a routing policy cannot tell "this association is not activated yet" from "the service is broken", so backoff/retry logic retries a permanent state error, and the whole registration round trip (create → refuse → delete) is unobservable.
Fix: implement the CreateIpamRoutingPolicyRegistration handler in that file — read the referenced association from the IPAM state, refuse a non-enable-complete association with the IncorrectState code and the message template above, and return the IpamRoutingPolicyRegistrationDelta on the success path; delete the SCAFFOLDED marker. The open issues 20261022T235108Z-ec2-ipam-byoasn-routing-policy-registration-and-prefix.md and 20261114T091241Z-ec2-ipam-9-net-new-causes-internet-registry.md record the same 501-instead-of-refusal class for neighbouring IPAM internet-registry operations; neither carries this check id or this operation's state refusal.
Traces: ec2.ipam-routing-policy-registration-round-trip.
