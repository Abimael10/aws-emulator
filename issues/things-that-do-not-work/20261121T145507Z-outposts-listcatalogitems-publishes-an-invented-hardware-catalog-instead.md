# outposts ListCatalogItems publishes an invented hardware catalog instead of the one AWS reports

> _Note: this issue was identified against the code base at commit `b61d91764c5b64113b88eda248364bbad90afe06`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
ListCatalogItems

## Description
2 net-new root causes, one shared fault: the catalog of orderable hardware configurations this emulator PUBLISHES is a locally synthesised table rather than the catalog AWS answers ListCatalogItems with, so a read of the catalog reports the wrong NUMBER of items and the wrong facts about each one. Both causes land on the same reference data (services/service-com-amazonaws-outposts-outpostsolafservice/src/state/catalog.rs, CATALOG_ITEMS / catalog_item_catalog) but they are separate replay units and must each be re-replayed: one is a filtered/short read that over-reports, the other is the whole catalog read that disagrees item for item.

Cause 1 of 2: ListCatalogItems reports one catalog item MORE than AWS does for the same request.
AWS: 200 ListCatalogItemsOutput whose CatalogItems list ENDS after the third item for this request (Smithy: ListCatalogItems GET /catalog/items, output CatalogItems -> CatalogItemListDefinition, NextToken; filters ItemClassFilter / SupportedStorageFilter / EC2FamilyFilter and page size MaxResults 1..1000 are the only things that may add or remove an element). AWS publishes the catalog itself: which configurations exist, and for each one its ItemClass, Dimensions, RackUnitHeight, PowerKva, WeightLbs, SupportedStorage, SupportedUplinkGbps/SupportedUplinkGiB, ItemStatus and EC2Capacities. Which rows exist is service-owned reference data, so for the contents the recording is the authority (recorded behavior only for the individual values).
Emulator: 200 with a FOURTH element at $.CatalogItems[3] where AWS's list has none - a SERVER configuration (ItemClass SERVER, Dimensions OUTPOST_SERVER_2U, RackUnitHeight HEIGHT_2U, CurrentType AC, PowerKva 1.0, WeightLbs 70, SupportedStorage [EBS], SupportedUplinkGbps/GiB [1,10], ItemStatus AVAILABLE, EC2Capacities for families c6gd and c6id). The extra element comes from a row of the emulator's own CATALOG_ITEMS table that AWS's catalog does not contain.
Why: a client that enumerates the catalog to pick hardware to quote or order is offered a configuration AWS will not price or order, and any count- or index-based assertion over a catalog page ("the browse page has N configurations", "items[3] is the one I wanted") silently shifts. Paging is affected too: an element the real catalog does not hold moves every later item's position, and NextToken is a position in that order.
Fix: the published reference data in services/service-com-amazonaws-outposts-outpostsolafservice/src/state/catalog.rs - the CATALOG_ITEMS table and the catalog_item_catalog() projection that seeds state.catalog_items. The ListCatalogItems handler's filter/page logic (src/ops/list_catalog_items.rs) applies the modelled rules correctly; it is the table it reads that holds configurations AWS does not publish.
Traces: outposts-catalog-and-instance-types-browsing#task#1.

Cause 2 of 2: an unfiltered ListCatalogItems answers a different catalog entirely - far too few items, and each item's published facts disagree.
AWS: 200 with a catalog of 37 items for this request, each a narrowly specified configuration: e.g. the first reported item is a RACK, Dimensions OUTPOST_RACK, RackUnitHeight HEIGHT_42U, CurrentType AC, PowerKva 6.39, WeightLbs 1328, RackScalingType MULTI_RACK, SupportedStorage [EBS, S3], SupportedUplinkGbps/GiB [10, 40, 100], ItemStatus AVAILABLE, and EC2Capacities naming a SINGLE family with a small whole-host Quantity (family c5, MaxSize 24xlarge, Quantity 1); the second likewise names two families with Quantity 2 and 5. The structural rule the recording shows is that a published item is ONE hardware configuration carrying a specific, small quantity of one or two families' whole hosts - not every family the generation runs. (Smithy: CatalogItem members CurrentType, Dimensions, ItemClass, RackUnitHeight, SupportedUplinkGiB, CatalogItemId (SkuCode ^OR-[A-Z0-9]{7}$), ItemStatus, EC2Capacities, PowerKva, WeightLbs, SupportedUplinkGbps, SupportedStorage, RackScalingType; EC2Capacity members Family/MaxSize/Quantity. The per-row values are recorded behavior only - AWS does not model the catalog's contents.)
Emulator: 200 with a catalog built from 8 hand-written rows, so most of AWS's items are absent ($.CatalogItems[0] through $.CatalogItems[36] all diverge; from the 9th position on the emulator reports nothing at all), and the items it does report are different hardware: the first is PowerKva 15.0, WeightLbs 1800, with EC2Capacities for SEVEN families (c5, c5d, i3en, m5, m5d, r5, r5d) each at Quantity 15 - a quantity computed as capacity_vcpus / vCPUs-of-largest-size rather than a published per-configuration figure - and the second is published with ItemStatus DISCONTINUED and SupportedUplinkGiB [1, 10].
Why: the catalog is the entry point to the whole order/quote flow. A client cannot find the configuration it is written against, sizing logic reading EC2Capacities.Quantity gets an invented figure (15 hosts of each of seven families on one rack), a filtered browse (ItemClassFilter / EC2FamilyFilter / SupportedStorageFilter) selects from the wrong population, and pagination over the catalog never reaches AWS's item count. Note that the per-item CatalogItemId values are published reference data, not per-run generated ids - the emulator derives them with SHA-256 over its own row facts (sku_code / CatalogConfiguration::sku_seed) - but the divergence being filed is the item SET and the published facts of each item, not the id strings themselves.
Fix: the same published reference data - CATALOG_ITEMS and catalog_item_catalog() in src/state/catalog.rs, plus ec2_capacities(), which derives each item's per-family Quantity from a total vCPU figure instead of publishing the configuration's own capacity. The seeded catalog must be the one the corpus records: the same number of items, in the same stable order, each with its own PowerKva / WeightLbs / ItemStatus / SupportedUplink* / SupportedStorage / RackScalingType and its own EC2Capacities (family, MaxSize, Quantity) entries.
Traces: outposts-catalog-list-catalog-items#task#1.
