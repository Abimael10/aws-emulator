=== Cause 1 of 3: the legacy target-group attachment list and the traffic-source attachment list are two independent stores, so each attachment is visible in only one pair of views. ===
Failing checks: autoscaling__ec2__elbv2.asgdx-reattaching-an-attached-target-group-through-either-api-keeps-one-attachment, autoscaling__ec2__elbv2.asghc-target-groups-attached-through-both-apis-appear-in-both-views
AWS: Smithy (services/service-com-amazonaws-autoscaling-autoscaling-2011-01-01/smithy-model/com-amazonaws-autoscaling-autoscaling-2011-01-01.json): AttachTrafficSources input {AutoScalingGroupName required XmlStringMaxLen255 length 1-255, TrafficSources required list of TrafficSourceIdentifier, SkipZonalShiftValidation}, empty output; AttachLoadBalancerTargetGroups input {AutoScalingGroupName required, TargetGroupARNs required list}, empty output; DescribeTrafficSources output {TrafficSources: TrafficSourceStates, NextToken}; DescribeLoadBalancerTargetGroups output {LoadBalancerTargetGroups: LoadBalancerTargetGroupStates, NextToken}; DescribeAutoScalingGroups projects both AutoScalingGroups[].TargetGroupARNs and AutoScalingGroups[].TrafficSources. AttachTrafficSources' own documentation states the ELBv2 attachment surface is one surface: "Attaches one or more traffic sources to the specified Auto Scaling group. You can use any of the following as traffic sources ... Application Load Balancer ... Network Load Balancer ... This operation is additive and does not detach existing traffic sources from the Auto Scaling group. After the operation completes, use the DescribeTrafficSources API to return details about the state of the attachments between traffic sources and your Auto Scaling group." On AWS the two APIs are two VIEWS of ONE attachment set: a target group attached at CreateAutoScalingGroup time via TargetGroupARNs, or later via AttachLoadBalancerTargetGroups, is reported by DescribeAutoScalingGroups.TargetGroupARNs, by DescribeAutoScalingGroups.TrafficSources as {Identifier: <that target-group ARN>, Type: 'elbv2'}, by DescribeLoadBalancerTargetGroups as a LoadBalancerTargetGroupState with LoadBalancerTargetGroupARN = that ARN, AND by DescribeTrafficSources(TrafficSourceType='elbv2') as a TrafficSourceState with Identifier = that ARN; a target group attached via AttachTrafficSources with Type 'elbv2' appears in all four the same way. Attachment is a SET, so re-attaching an already-attached target group through either API is accepted and still leaves exactly one attachment, and one detach through either API removes it from all four views. (The set/idempotency and cross-view equivalence are recorded behavior only — the model declares the members but not the invariant; the recordings show all four views agreeing.)
Emulator: the two stores are disjoint. (a) A target group passed as CreateAutoScalingGroup TargetGroupARNs reads back in TargetGroupARNs and in DescribeLoadBalancerTargetGroups, but DescribeTrafficSources(TrafficSourceType='elbv2') returns an EMPTY TrafficSources list for the same group — replay: {'arns': [<tg>], 'lbtg': [<tg>], 'dts': []} where all three were expected to hold <tg>. (b) After AttachLoadBalancerTargetGroups(tg1) and AttachTrafficSources({Identifier: tg2, Type: 'elbv2'}) on one group, the four views split cleanly down the middle — replay: {'arns': [tg1], 'ts': [(tg2, 'elbv2')], 'lbtg': [tg1], 'dts': [tg2]} where every view was expected to hold both tg1 and tg2. tg1 is invisible to DescribeTrafficSources and to DescribeAutoScalingGroups.TrafficSources; tg2 is invisible to DescribeAutoScalingGroups.TargetGroupARNs and to DescribeLoadBalancerTargetGroups.
Why: a client cannot learn what a group is attached to. Code written against the modern traffic-source API (and CloudFormation/CDK drift detection, which reads TrafficSources) sees no attachment for a group configured the legacy way — including every group created with CreateAutoScalingGroup TargetGroupARNs, the most common shape — and concludes the group feeds no load balancer. Code written against the legacy API sees nothing for a group attached as a traffic source. Detaching through the other API then silently no-ops, and a retried attach can be made to double-count, because the emulator's notion of "already attached" is per-store rather than per-group.
Fix: the autoscaling service's group attachment state — hold ONE attachment set per group keyed by {Identifier, Type}, written by CreateAutoScalingGroup's TargetGroupARNs, AttachLoadBalancerTargetGroups and AttachTrafficSources alike (set semantics, so a redundant attach is accepted and does not duplicate), removed by DetachLoadBalancerTargetGroups and DetachTrafficSources alike, and projected by all four readers: DescribeTrafficSources, DescribeLoadBalancerTargetGroups, and the DescribeAutoScalingGroups serializer's TargetGroupARNs (the Type='elbv2' entries) and TrafficSources members.
Traces: autoscaling__ec2__elbv2.asgdx-reattaching-an-attached-target-group-through-either-api-keeps-one-attachment (asserts views() == {arns:[tg], lbtg:[tg], dts:[tg]} right after create), autoscaling__ec2__elbv2.asghc-target-groups-attached-through-both-apis-appear-in-both-views (asserts all four views hold both target groups after attaching one through each API).

=== Cause 2 of 3: attaching a target group from a different VPC to an Auto Scaling group never produces the Failed scaling activity that records the rejected registration, so the negative control never reaches a verdict. ===
Failing check: autoscaling__ec2__elbv2.asg-registration-fails-with-mismatched-target-group-vpc
AWS: recorded behavior only (the model declares DescribeScalingActivities -> Activities[].{StatusCode, StatusMessage, Description} but not this rule). AttachLoadBalancerTargetGroups ACCEPTS a target group that lives in a VPC other than the one the group's instances are in — the request is answered 200 — and the failure surfaces asynchronously: Auto Scaling tries to register its in-service instance into that target group, ELBv2 refuses the registration because the instance is not in the target group's VPC, and Auto Scaling records a scaling activity with StatusCode 'Failed' whose StatusMessage carries ELBv2's VPC-mismatch refusal text. The fixed text is ELBv2's own target-not-in-VPC sentence as surfaced by Auto Scaling's activity log; the variable parts are the instance id, the target-group ARN and the VPC id, all taken from the request and from the emulator's state. A target group in the SAME VPC is registered normally and records no Failed activity.
Emulator: no Failed activity with any VPC wording ever appears. The check polls DescribeScalingActivities for an activity with StatusCode=='Failed' and 'vpc' in its StatusMessage/Description and finds none; the check is killed by the harness with `Check timed out after 60.0s`, so neither the negative leg nor the same-VPC positive leg that follows it is ever evaluated.
Why: the cross-VPC misconfiguration is the single most common reason an ASG silently serves no traffic, and on AWS the scaling-activity log is the ONLY place it is reported (the attach call itself succeeds). A client or runbook that diagnoses "why is my target group empty" by reading DescribeScalingActivities gets a clean log from the emulator and concludes the wiring is correct; a negative test that asserts the refusal is recorded can never pass.
Fix: the autoscaling registration path that reconciles a group's attachments against ELBv2 (the component that calls RegisterTargets on behalf of the group) plus the scaling-activity recorder — resolve the target group's VpcId, compare it with the instance's VPC, and on mismatch record an activity with StatusCode 'Failed' carrying ELBv2's VPC-mismatch message instead of leaving the attachment silently inert. Related existing filing for the autoscaling__ecs__elbv2 heading: 20261111T010150Z-autoscaling-ecs-elbv2-asg-launch-into-a-target-group-in-a.md.
Traces: autoscaling__ec2__elbv2.asg-registration-fails-with-mismatched-target-group-vpc.

=== Cause 3 of 3: the full ASG → target-group → ALB → ELB-health round trip never reaches an observable step, so the happy path is cut off with no verdict. ===
Failing check: autoscaling__ec2__elbv2.asg-target-group-registration-serves-http-and-feeds-back-health
AWS: recorded behavior only for the end-to-end timing; the members are modeled (DescribeAutoScalingGroups -> AutoScalingGroups[].Instances[].{LifecycleState, HealthStatus}, elbv2 DescribeTargetHealth -> TargetHealthDescriptions[].TargetHealth.State). An Auto Scaling group created with TargetGroupARNs=[tg] and HealthCheckType='ELB' launches its instance, registers that instance as an 'instance' target of tg, the target reaches TargetHealth.State 'healthy' once the instance answers the configured health check, a request to the load balancer's DNS name is answered HTTP 200 with the instance's own body, and the load balancer's verdict is fed BACK into Auto Scaling so the group's instance reads LifecycleState 'InService' and HealthStatus 'Healthy' with DesiredCapacity 1.
Emulator: nothing in that chain becomes observable. The check is killed by the harness with `Check timed out after 60.0s` while still inside its convergence polls (instance appears, target registered, target healthy, HTTP 200 through the load balancer, instance InService/Healthy), so the whole happy path is unverifiable.
Why: this is the reference happy path for load-balanced capacity. A client cannot confirm that a group it created is actually serving, cannot read a target's health, and cannot rely on HealthCheckType='ELB' feeding the load balancer's verdict back into HealthStatus — the backward edge Auto Scaling uses to replace an unhealthy instance. Everything built on it (deployments gated on healthy targets, ELB-driven instance replacement) is unreachable.
Fix: the autoscaling group-convergence path and its ELBv2 integration — register a launched instance into every attached target group, run the target group's health check against the instance and publish the resulting TargetHealth.State, serve the load balancer's data plane on the DNSName it publishes, and project the ELB verdict into Instances[].HealthStatus for HealthCheckType='ELB' groups, all within the emulator's normal response budget rather than never.
