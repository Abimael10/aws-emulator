# elbv2: 2 net-new causes — the ALB data plane never answers at the published DNSName, so neither the desync_mitigation_mode=strictest refusal nor the source-ip listener-rule contract reaches a verdict (both checks killed at the 60 s ceiling)

> _Note: this issue was identified against the code base at commit `bdb545ca849f9697d9c5980364556461a4c64e99`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
ModifyLoadBalancerAttributes

## Description
Two net-new root causes behind the two elbv2 failures the replay report leaves unmarked (every other elbv2 failure in this run is marked OWNED or ALREADY FILED). Both are ALB data-plane scenarios that produce no observable behavior at all: the suite reports only `Error: Check timed out after 60.0s`, i.e. the emulator never answered the request the check was polling for, so none of the behavior under test was ever exercised.

Related open filings that do NOT carry these replay keys, named here so a fixer can correlate rather than re-discover: 20261105T151413Z-elbv2-routing-http-desync-mitigation-mode-is-inert.md and 20261105T093535Z-elbv2-4-net-new-data-plane-causes-desync.md (desync family), 20261107T183213Z-elbv2-a-lambda-target-s-in-handler-sqs.md (the Lambda side-channel step of the desync check), 20261111T195612Z-elbv2-the-source-ip-listener-rule-check-reaches.md (the source-ip check), 20261112T140934Z-elbv2-7-net-new-causes-loadbalancer-dnsname-is.md and 20261109T153103Z-elbv2-4-net-new-causes-the-published-dnsname.md (the unserved DNSName family). The fixed filing 20261111T030957Z-elbv2-2-net-new-causes-routing-http-desync.md claimed routing.http.desync_mitigation_mode=strictest; after it, the check no longer gets a wrong answer — it gets no answer at all, so the behavior it claimed is still unverified. Neither failure is a refusal (no error code, no non-2xx was returned), so this is reported as a no-response defect rather than as a reopened refusal.

Cause 1 of 2: routing.http.desync_mitigation_mode=strictest is never observable — the ambiguously framed request is never answered, so the ALB neither refuses it with 400 nor demonstrably withholds it from the target. Failing check id: elbv2.desync-mitigation-strictest-blocks-ambiguous-framing-before-the-target.
AWS: Smithy (elasticloadbalancingv2, elasticloadbalancing-v10) LoadBalancerAttribute.Key documents, for Application Load Balancers only, `routing.http.desync_mitigation_mode` — "Determines how the load balancer handles requests that might pose a security risk to your application. The possible values are monitor, defensive, and strictest. The default is defensive." Recorded behavior for the wire effect: with the attribute set to `strictest`, a POST carrying two mutually exclusive framing headers (`Content-Length: 8` together with `Transfer-Encoding: chunked`) is answered by the load balancer itself with the status line `HTTP/1.1 400 Bad Request` and the registered target is NOT invoked (zero invocations on the target's own side channel, held for a window calibrated from the latency a compliant POST needed on the same wiring); a compliant POST over the same listener in the same instant is still forwarded and returns 200 with the target's own body; with the attribute set back to `monitor`, the identical ambiguous bytes are forwarded and return the target's body again. ModifyLoadBalancerAttributes/DescribeLoadBalancerAttributes must round-trip the key/value in the modeled shape before any of this.
Emulator: the check never reaches any of those assertions. The replay detail is the bare `Check timed out after 60.0s`; every step before the first data-plane poll is a control-plane call that would surface its own ClientError instead of hanging (CreateQueue, VPC/SG, IAM role, CreateFunction, Invoke + side-channel collect, CreateLoadBalancer + wait-active, CreateTargetGroup(TargetType=lambda), AddPermission, RegisterTargets, CreateListener, ModifyLoadBalancerAttributes + DescribeLoadBalancerAttributes), so the emulator is sitting in a raw-socket poll against the published DNSName that never produces a 200 for a compliant POST, or in the Lambda side-channel collect that follows it. Nothing is returned for the ambiguous request either, so the 400 refusal and the "target not invoked" effect-absent leg are both unverifiable.
Why: a client that sets desync_mitigation_mode=strictest is buying protection against HTTP request smuggling. On the emulator the setting has no observable consequence whatsoever: a request AWS answers 400 and never forwards produces no response at all, so code and tests that depend on ambiguous framing being rejected before the target cannot distinguish "protected" from "silently forwarded", and an application validated against the emulator can ship with a smuggling path open.
Fix: the ALB data-plane request path — the raw HTTP listener that must accept a connection on the published DNSName, parse request framing, and apply the load balancer's stored `routing.http.desync_mitigation_mode` before forwarding (answering 400 Bad Request itself under `strictest` and forwarding under `monitor`) — together with the lambda-target forwarding path that must invoke the registered function and return its response body.
Traces: elbv2.desync-mitigation-strictest-blocks-ambiguous-framing-before-the-target (mismatch, `Check timed out after 60.0s`).

Cause 2 of 2: a `source-ip` listener-rule condition is never exercised — the ALB never answers the priority-5 forward rule into its lambda target group, so neither the source-ip match, nor the X-Forwarded-For non-spoofability, nor the forbidden-CIDR refusal is reached. Failing check id: elbv2.source-ip-condition-uses-the-layer3-address-not-x-forwarded-for.
AWS: Smithy SourceIpConditionConfig documents "You can use this condition to route based on the IP address of the source that connects to the load balancer. If a client is behind a proxy, this is the IP address of the proxy not the IP address of the client" and "For Application Load Balancers, use Values to specify CIDR ranges" (ListOfString, wildcards unsupported) — i.e. the match is on the connection's layer-3 peer address and a client-supplied X-Forwarded-For header can never satisfy it. Recorded behavior for the sequence: (a) a GET through a priority-5 path-pattern rule forwarding to a TargetType=lambda group returns 200 with the function's JSON echo of the headers the ALB attached, including the ALB-added `x-forwarded-for` whose first entry is the client address; (b) a priority-20 rule whose conditions are path-pattern + source-ip `<client-ip>/32` wins over a priority-30 path-only fall-through and serves its fixed response; (c) pointed at an unroutable CIDR (RFC 5737 TEST-NET-1 192.0.2.0/24) the same request falls through to priority 30, and still falls through when the client sends `X-Forwarded-For: 192.0.2.7` or its own address; (d) restoring the /32 makes priority 20 win again; (e) DescribeRules echoes SourceIpConfig.Values unchanged; (f) ModifyRule with the forbidden CIDR is refused with HTTP 400, error code `ValidationError`, message `The specified value '255.255.255.255/32' is not a valid CIDR block` — fixed text "The specified value '" + the rejected CIDR taken verbatim from the request + "' is not a valid CIDR block"; the CIDR is the only variable part, and the stored condition is left unchanged.
Emulator: the check produces no verdict — the replay detail is the bare `Check timed out after 60.0s`. The only blocking step at that point is the first data-plane poll (`http://<DNSName>/<slug>/echo`, interval 10 s, budget 420 s) waiting for the lambda target to echo back a body containing `x-forwarded-for`; all preceding calls are control-plane and would raise their own ClientError. So the published ALB endpoint never answers 200 with the target's body, and legs (b)-(f) — the source-ip match, the X-Forwarded-For discriminator, the DescribeRules SourceIpConfig round trip, and the 255.255.255.255/32 ValidationError refusal — are never exercised.
Why: a client that gates access with a source-ip listener rule gets no usable signal. It cannot confirm that its CIDR allow-list routes at all, and — the part that matters for security — it cannot confirm that the condition is matched against the layer-3 peer address and is NOT satisfiable by a client-supplied X-Forwarded-For header, so an allow-list real AWS enforces may be silently spoofable (or silently dead) against the emulator; likewise CreateRule/ModifyRule may accept a CIDR AWS refuses with ValidationError.
Fix: the ALB data-plane request path (listener/rule evaluation and the lambda-target invocation that answers a request arriving on the published DNSName, including the X-Forwarded-For header the ALB attaches before invoking the target), source-ip condition evaluation against the connection's layer-3 peer address (never X-Forwarded-For) in the rule matcher, and CIDR validation in the CreateRule/ModifyRule condition validation.
Traces: elbv2.source-ip-condition-uses-the-layer3-address-not-x-forwarded-for (mismatch, `Check timed out after 60.0s`).

## Steps to Reproduce
Cause 1 (desync mitigation):
1. Create an SQS queue, a VPC with a public subnet, a security group open on TCP 80, an IAM role allowing sqs:SendMessage, and a Python Lambda whose handler sends {"path": event["path"], "request_id": context.aws_request_id} to the queue and returns {"statusCode": 200, "body": "TARGET-REACHED"}.
2. CreateLoadBalancer (Scheme=internet-facing, that subnet, that SG); wait for State=active. CreateTargetGroup(TargetType="lambda"); lambda AddPermission for elasticloadbalancing.amazonaws.com with SourceArn=<tg arn>; RegisterTargets(Targets=[{"Id": <fn arn>}]); CreateListener(Port=80, Protocol=HTTP, DefaultActions=[forward -> tg]).
3. ModifyLoadBalancerAttributes(routing.http.desync_mitigation_mode=monitor) and confirm DescribeLoadBalancerAttributes echoes it. On a raw socket to <DNSName>:80 send a compliant POST (Content-Length + body) — expect a status line ending `200 OK` with body `TARGET-REACHED` — then the ambiguous POST (`Content-Length: 8` plus `Transfer-Encoding: chunked`, body `0\r\n\r\n`) — expect the same 200/`TARGET-REACHED` plus one side-channel message.
4. ModifyLoadBalancerAttributes(routing.http.desync_mitigation_mode=strictest). Send the identical ambiguous POST: expect exactly `HTTP/1.1 400 Bad Request` and ZERO messages on the queue; send a compliant POST in the same instant: expect 200/`TARGET-REACHED` and exactly one message.
5. Restore `monitor` and resend the ambiguous POST: expect 200/`TARGET-REACHED`. Observed on the emulator: no response at any step; the check is killed at the 60 s ceiling.
6. Re-replay elbv2.desync-mitigation-strictest-blocks-ambiguous-framing-before-the-target.

Cause 2 (source-ip rule):
1. Create a VPC with public subnets, a security group open on TCP 80, an IAM role for Lambda, and a Lambda returning {"statusCode": 200, "headers": {"Content-Type": "application/json"}, "body": json.dumps(event["headers"])}.
2. CreateLoadBalancer (internet-facing) and wait active; CreateTargetGroup(TargetType="lambda"); AddPermission for elasticloadbalancing.amazonaws.com with SourceArn=<tg arn>; RegisterTargets(Targets=[{"Id": <fn arn>}]); CreateListener(Port=80, Protocol=HTTP, DefaultActions=fixed-response "DEFAULT-RULE"); CreateRule(Priority=5, Conditions=[path-pattern /<slug>/echo], Actions=[forward -> tg]).
3. GET http://<DNSName>/<slug>/echo — expect 200 with a JSON body containing `x-forwarded-for`. Observed: never returns 200; the check dies at the 60 s ceiling.
4. (Blocked by step 3) CreateRule(Priority=20, Conditions=[path-pattern /<slug>/src, source-ip <client-ip>/32], Actions=fixed-response "BY-SOURCE-IP") and CreateRule(Priority=30, Conditions=[path-pattern /<slug>/src], Actions=fixed-response "FELL-THROUGH"); GET /<slug>/src with and without an X-Forwarded-For header; ModifyRule the priority-20 rule to SourceIpConfig.Values=["192.0.2.0/24"] and then to ["255.255.255.255/32"].
5. Re-replay elbv2.source-ip-condition-uses-the-layer3-address-not-x-forwarded-for.
