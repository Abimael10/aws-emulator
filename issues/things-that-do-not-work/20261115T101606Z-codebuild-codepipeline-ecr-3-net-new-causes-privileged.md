# codebuild__codepipeline__ecr: 3 net-new causes — privileged builds have no docker daemon (dockerd exits 127), a build that pulls a private ECR base image FAILS, and the repository-policy Deny/restore pull differential never converges

> _Note: this issue was identified against the code base at commit `e4ca4939f46b803ca65adff0207938919af7628e`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
StartBuild

## Description
Three independent root causes in the CodeBuild->ECR container path, all surfacing through builds that are started (directly or by a CodePipeline Build action) against a project with environment.privilegedMode=true and image aws/codebuild/standard:7.0. Each must be closed before this issue is submitted.

Cause 1 of 3 — a privilegedMode build environment provides no docker daemon, so the buildspec's docker bootstrap command exits 127 and the build fails for the wrong reason (failing check: codebuild__codepipeline__ecr.cli-pipeline-execution-fails-when-codebuild-role-lacks-ecr-permissions).
AWS: on AWS, a project with environment.privilegedMode=true runs its phase commands in a container where the docker daemon can be started (the standard images ship dockerd), so `nohup dockerd --storage-driver=overlay2 > /tmp/dockerd-log.txt 2>&1 &` returns exit status 0 and the build proceeds into pre_build. The build then calls ecr:GetAuthorizationToken with the project's service-role credentials; because the role's identity policy omits that action, ECR refuses it and the CLI writes the service's own text into the build log: "An error occurred (AccessDeniedException) when calling the GetAuthorizationToken operation: User: arn:aws:sts::<account>:assumed-role/<roleName>/AWSCodeBuild-<buildUuid> is not authorized to perform: ecr:GetAuthorizationToken on resource: * because no identity-based policy allows the ecr:GetAuthorizationToken action". Fixed text of that message is everything outside the angle-bracketed slots; <account> is the caller's account, <roleName> the project's serviceRole name, <buildUuid> the id suffix of THIS build, and the action/resource clauses are the denied action (ecr:GetAuthorizationToken) and its resource (*) from the request — never the literal ids of one recording. Smithy: ECR GetAuthorizationToken models only InvalidParameterException/ServerException, so the AccessDenied refusal is the IAM authorization layer, not a modeled error; the build-log text is recorded behavior of the AWS CLI reporting that refusal.
Emulator: the build fails, but the only error line in its CloudWatch Logs stream is "Phase context status code: COMMAND_EXECUTION_ERROR Message: Error while executing command: nohup dockerd --storage-driver=overlay2 > /tmp/dockerd-log.txt 2>&1 &. Reason: exit status 127" — exit 127 is "command not found", i.e. there is no dockerd in the build runtime. No AccessDeniedException line is ever written, because the build never reaches the ECR login; the permission boundary under test is never exercised at all.
Why: a client that uses CodeBuild logs to diagnose a permissions problem is told the wrong thing — every container build fails identically with a docker bootstrap error regardless of its IAM grants, so an under-permissioned role and a correctly permissioned role are indistinguishable, and IAM-boundary regression tests pass/fail for the wrong reason.
Fix: the CodeBuild build-execution runtime (the buildspec phase runner / build container provisioning for privilegedMode projects) in the codebuild service crate, plus the ECR authorization check that must refuse GetAuthorizationToken for a role whose identity policy does not allow it and surface AWS's AccessDeniedException text to the build's log stream.

Cause 2 of 3 — a build that pulls a base image out of the emulator's own private ECR repository FAILS, although the build that pushed that image SUCCEEDED (failing check: codebuild__codepipeline__ecr.codebuild-pulls-base-image-from-ecr-private-registry).
AWS: a build whose service role holds ecr:GetAuthorizationToken, ecr:BatchGetImage and ecr:GetDownloadUrlForLayer can `docker login` to the account registry, `docker pull <repoUri>:base`, build an image FROM it and `docker push <repoUri>:derived`; BatchGetBuilds then reports buildStatus SUCCEEDED (Smithy: StatusType = SUCCEEDED|FAILED|FAULT|TIMED_OUT|IN_PROGRESS|STOPPED) and ECR DescribeImages(imageIds=[{imageTag:'derived'}]) returns exactly one imageDetails entry whose imageTags contain 'derived'.
Emulator: the preceding push build on the same project and role reports SUCCEEDED, but the pull-and-build build reports buildStatus FAILED with currentPhase COMPLETED after its SUBMITTED/QUEUED/PROVISIONING/DOWNLOAD_SOURCE/PRE_BUILD phases all report SUCCEEDED — so the failure is in the BUILD phase, where `docker pull` of the just-pushed private base tag runs. No image tagged 'derived' is delivered.
Why: the whole "build FROM a private base image" pattern is unusable — a client cannot verify a layered image pipeline, and the asymmetry (push works, pull does not) makes the emulator report success for half of a round trip whose second half can never work.
Fix: the CodeBuild build-execution runtime's image/registry integration — the pull path against the ECR registry the emulator itself serves (the same component that already serves the push path) — in the codebuild service crate, together with the ECR registry data-plane endpoint it resolves. Related but not covering: open issue 20261109T141609Z-codebuild-ecr-ecs-elbv2-logs-the-ecr-repository.md (repositoryUri announced on an unserved dkr.ecr host) is about a different service token and a different check.

Cause 3 of 3 — the ECR repository-policy Deny / DeleteRepositoryPolicy restore differential for a CodeBuild pull never converges: the check reaches no verdict inside its 60 s budget (failing check: codebuild__codepipeline__ecr.ecr-repository-policy-denies-codebuild-role-blocks-pull).
AWS: with an identity policy allowing full ECR push/pull, SetRepositoryPolicy with an explicit Deny of ecr:BatchGetImage and ecr:GetDownloadUrlForLayer for the build's role ARN blocks that role's pull, so the pull-and-verify build ends buildStatus FAILED and DescribeImages for imageTag 'pull-verified' is refused ImageNotFoundException (Smithy: DescribeImages errors ImageNotFoundException, 400) with message "The image with imageId {imageDigest:'null', imageTag:'<tag>'} does not exist within the repository with name '<repositoryName>' in the registry with id '<registryId>'" — fixed text outside the slots, with <tag>, <repositoryName> from the request and <registryId> the caller's account. After DeleteRepositoryPolicy the identical build SUCCEEDS and the 'pull-verified' tag appears; a control repository that never carried the Deny succeeds throughout.
Emulator: the scenario never settles — the check is cut off ("Check timed out after 60.0s") before any of the three legs (deny-blocked FAILED, restored SUCCEEDED, control SUCCEEDED) can be observed, so the repository-policy Deny is never shown to be enforced and the restore is never shown to re-enable the pull. This sits on top of Cause 2: with the private-registry pull path broken, no leg of the differential can reach its expected state.
Why: a client cannot rely on ECR repository policies to constrain who may pull an image from a build, and cannot distinguish "deny enforced" from "pull broken for everyone"; a deny/restore lifecycle silently never converges instead of failing loudly.
Fix: ECR repository-policy evaluation for the pull actions (BatchGetImage/GetDownloadUrlForLayer) against the build role's principal, in the ecr service crate's authorization path, plus the build-side pull path from Cause 2 so the restored and control legs can succeed. Related but not covering: open issue 20261113T121947Z-cloudwatch-ecr-ecs-2-net-new-causes-an.md (repository-policy explicit Deny not enforced) is filed under a different service token and a different check.

Traces: the three failing behavioral checks listed in trace_ids, one per cause.

## Steps to Reproduce
1. Create an ECR repository (CreateRepository) and an IAM role trusted by codebuild.amazonaws.com with logs:* and the ECR push/pull actions (for cause 1, omit ecr:GetAuthorizationToken and the push actions).
2. CreateProject with source {type: NO_SOURCE, buildspec: <inline>}, artifacts {type: NO_ARTIFACTS}, environment {type: LINUX_CONTAINER, image: aws/codebuild/standard:7.0, computeType: BUILD_GENERAL1_SMALL, privilegedMode: true}, serviceRole = that role.
3. Cause 1: run the project (directly or as a CodePipeline Build action) with a buildspec whose install phase runs `nohup dockerd --storage-driver=overlay2 > /tmp/dockerd-log.txt 2>&1 &` and whose pre_build runs `aws ecr get-login-password | docker login ...`. StartBuild/StartPipelineExecution, wait for the terminal build, then read its log stream via BatchGetBuilds(...).builds[0].logs and logs:GetLogEvents — observe the dockerd exit-127 COMMAND_EXECUTION_ERROR and no AccessDeniedException line.
4. Cause 2: StartBuild with a buildspec that pushes busybox-derived `<repoUri>:base`, wait for SUCCEEDED; then StartBuild again with buildspecOverride that logs in, `docker pull $BASE_URI:base`, builds `FROM $BASE_URI:base` and pushes `$FINAL_URI:derived` — observe buildStatus FAILED after PRE_BUILD SUCCEEDED and no 'derived' tag in DescribeImages.
5. Cause 3: seed two repositories with a `:base` tag, SetRepositoryPolicy on one with an explicit Deny of ecr:BatchGetImage/ecr:GetDownloadUrlForLayer for the role ARN, then run the pull-and-verify buildspec against the denied repo, DeleteRepositoryPolicy and re-run it, and run it against the untouched control repo — observe that the scenario never settles within the check's budget.
