# cloudformation__s3vectors: 2 net-new causes — an AWS::S3Vectors::Index create-only property change is refused NotImplemented instead of replacing the index, and an out-of-range Dimension rollback emits no stack-level CREATE_FAILED event

> _Note: this issue was identified against the code base at commit `7dc215237948fb0f525a17841803e21ef74f8c7d`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
UpdateStack

## Description
Two independent root causes behind the CloudFormation / S3 Vectors index-lifecycle checks. Related but NOT covering: open issue 20261111T111216Z-cloudformation-s3vectors-2-net-new-causes-queryvectors-returns-placeholder-distances.md carries the same NotImplemented wording for AWS::S3Vectors::VectorBucket's IN-PLACE update; Cause 1 here is a different resource type (Index) and a different update behaviour (REPLACEMENT of a create-only property), and its replay keys are not in that issue.

Cause 1 of 2: a create-only property change on AWS::S3Vectors::Index is refused with an emulator-authored NotImplemented reason instead of replacing the index.
AWS: Dimension, DataType, DistanceMetric and VectorBucketName are create-only properties of AWS::S3Vectors::Index (the S3 Vectors API has no mutator for them — Smithy: CreateIndex input dimension @range min 1 max 4096, dataType/distanceMetric are required enums, and there is no UpdateIndex operation in the model). A template change to such a property is therefore handled by CloudFormation's standard create-only/replacement update behaviour: when IndexName is omitted CloudFormation mints a fresh physical name, so the resource is replaced — the resource records UPDATE_IN_PROGRESS with reason 'Requested update requires the creation of a new physical resource; hence creating one.', then UPDATE_COMPLETE against the NEW index ARN, and with no UpdateReplacePolicy the old physical resource is deleted (DELETE_IN_PROGRESS then DELETE_COMPLETE against the OLD ARN). Ref and Fn::GetAtt IndexArn, and DescribeStackResources' PhysicalResourceId, then resolve to the new ARN, GetIndex on the old ARN answers 404 NotFoundException 'The specified index could not be found', and the stack ends UPDATE_COMPLETE. (When the template DOES fix IndexName, the same change is instead refused by CloudFormation's custom-named-replacement guard, reason 'CloudFormation cannot update a stack when a custom-named resource requires replacing. Rename <index ARN> and update the stack again.' — fixed text as quoted, the ARN taken from the resource — and the stack ends UPDATE_ROLLBACK_COMPLETE with the original index untouched. That branch is never reached today because the unnamed branch fails first.)
Emulator: the Index resource goes UPDATE_FAILED with ResourceStatusReason 'NotImplemented: this emulator does not change the properties of an existing AWS::S3Vectors::Index in place; the resource was left as it is.' (fixed text 'NotImplemented: this emulator does not change the properties of an existing ' ... ' in place; the resource was left as it is.'; the variable part is the resource type) and the stack ends UPDATE_ROLLBACK_COMPLETE with StackStatusReason 'The following resource(s) failed to update: [Index]. '. Both a Dimension change (2 -> 3) and a DistanceMetric change (cosine -> euclidean) take this path. AWS has no NotImplemented error here, and the handler never considers replacement at all.
Why: a CloudFormation-managed S3 Vectors index can never be re-dimensioned or re-metriced — every such deploy rolls back, so the stack and the template permanently disagree; and because the unnamed-index replacement path is dead, the named-index rename refusal (a deliberate CloudFormation guard clients rely on to detect the 'rename it' remediation) is never exercised either.
Fix: the AWS::S3Vectors::Index resource handler's update path in the CloudFormation provisioner — classify create-only properties as requiring replacement, run create-new/delete-old with the matching resource events and physical ids, and apply the custom-named-resource replacement guard when IndexName is set in the template.
Failing checks: cloudformation__s3vectors.cfn-s3vectors-index-dimension-change-without-indexname-replaces-and-deletes-original, cloudformation__s3vectors.cfn-s3vectors-index-createonly-change-replaces-unnamed-conflicts-named.

Cause 2 of 2: a stack rejected for an out-of-range AWS::S3Vectors::Index Dimension rolls back without any stack-level CREATE_FAILED event.
AWS: Dimension is bounded 1..4096 (Smithy: CreateIndex.dimension @range min 1 max 4096; the AWS::S3Vectors::Index template reference documents the same ceiling). A template declaring Dimension 4097 is caught by property validation before any resource is provisioned: CloudFormation records a STACK-level CREATE_FAILED event (LogicalResourceId equal to the stack name) whose ResourceStatusReason is 'Validation failed with 1 error(s). Call DescribeEvents to retrieve the full list of issues with resource and property details, resolve each error, then retry the operation.' — fixed text exactly as quoted, with the error count taken from the number of property violations found — and the stack settles ROLLBACK_COMPLETE with NO events at all for the Index logical id.
Emulator: the stack does settle ROLLBACK_COMPLETE, but DescribeStackEvents contains no stack-level CREATE_FAILED row at all (the check's filter over stack-level CREATE_FAILED events returns []), so the validation reason is nowhere in the event stream.
Why: a client or deploy tool that reads the stack-level CREATE_FAILED reason to tell WHY a create was rejected (and to distinguish a pre-provisioning validation rejection from a downstream resource failure) gets no reason at all and cannot surface or classify the failure; CI gates keyed on that reason see a silent rollback.
Fix: the CloudFormation provisioner's create-stack validation/rollback path — emit the stack-level CREATE_FAILED event carrying the 'Validation failed with N error(s). ...' reason when template property validation rejects a stack before provisioning. Same shape as open issues 20261117T111420Z-cloudformation-codepipeline-iam-s3-a-pattern-violating-aws.md and 20261114T222509Z-cloudformation-events-a-stack-rejected-by-pre-provisioning.md, which are filed for other services' checks and do not carry this check's key.
Failing check: cloudformation__s3vectors.cfn-s3vectors-index-dimension-above-maximum-create-rejected-sibling-stack-unaffected.
