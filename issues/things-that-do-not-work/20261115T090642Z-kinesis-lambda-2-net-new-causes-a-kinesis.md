# kinesis__lambda: 2 net-new causes — a Kinesis ESM ignores MaximumBatchingWindowInSeconds (one record per invoke) and ignores TumblingWindowInSeconds (no window/state/isFinalInvokeForWindow in the event, no closing invocation)

> _Note: this issue was identified against the code base at commit `48ab13f61564abe631f24038b106fee51cab80bf`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
CreateEventSourceMapping

## Description
Two net-new root causes in the Kinesis event-source-mapping poller. Records DO now reach the function (so this is not the delivery gap open issue 20261109T210043Z-kinesis-lambda-a-kinesis-event-source-mapping-never-delivers-stream.md describes, and neither of the checks below is carried by it); what diverges is how the poller batches and windows them. Both causes are in the same service, so they are bundled here; a fixer must close BOTH before submitting.

Cause 1 of 2: MaximumBatchingWindowInSeconds has no effect on a Kinesis mapping — the poller invokes as soon as any record is available, whatever the window.
AWS: Smithy: CreateEventSourceMapping.MaximumBatchingWindowInSeconds targets MaximumBatchingWindowInSeconds, @range min 0 max 300, and is echoed on EventSourceMappingConfiguration.MaximumBatchingWindowInSeconds. Beyond the range the model states nothing about buffering, so: recorded behavior only — for a stream source Lambda buffers records until either BatchSize records are gathered or MaximumBatchingWindowInSeconds elapses, whichever comes first, and a value of 0 means invoke as soon as records are available (https://docs.aws.amazon.com/lambda/latest/dg/invocation-eventsourcemapping.html#invocation-eventsourcemapping-batching, https://docs.aws.amazon.com/lambda/latest/dg/with-kinesis.html#kinesis-polling-and-batching). The consequence a client relies on is ordinal, not numeric: fed the identical trickle of arrivals with BatchSize held equal, a mapping with a non-zero window must gather strictly more records per invocation, and so use strictly fewer invocations, than one with the window at 0.
Emulator: the create response echoes the configured window correctly (the check's assertion on the echoed value passes), but the poller behaves identically for both arms. Two mappings over two streams, BatchSize equal and the same arrival trickle (records put alternately, one per source, spaced ~1.2 s, ten per arm), produced one invocation per record on BOTH arms: the windowed mean batch size equalled the immediate mean (1.0 over ten batches of size 1 each, versus 1.0 over ten batches of size 1 each), and the windowed arm never once batched more than a single record. No HTTP refusal is involved — every call succeeds; the buffering simply does not happen.
Why: a client that sets a batching window to trade latency for fewer, larger invocations gets neither on the emulator: it is billed/invoked once per record, its handler never sees a multi-record Records array it must be correct for, and any assertion about batch sizes or invocation counts that holds on AWS fails here. Code tuned against the emulator will be mis-tuned on AWS.
Fix: the Kinesis poller of the Lambda event-source-mapping data plane — the buffering step that assembles a batch before invoking (it must hold records until BatchSize or the mapping's MaximumBatchingWindowInSeconds, whichever first), not CreateEventSourceMapping's validation or its serializer, both of which already round-trip the value.

Cause 2 of 2: TumblingWindowInSeconds is inert — the event carries no tumbling-window fields and no window is ever opened, threaded or closed.
AWS: Smithy: CreateEventSourceMapping.TumblingWindowInSeconds, @range min 0 max 900, documented as "(Kinesis and DynamoDB Streams only) The duration in seconds of a processing window for DynamoDB and Kinesis Streams event sources. A value of 0 seconds indicates no tumbling window." For a non-zero value: recorded behavior only (https://docs.aws.amazon.com/lambda/latest/dg/services-kinesis-windows.html) — each invocation's event carries, per shard, a `window` object with `start` and `end` whose span is exactly TumblingWindowInSeconds, a `shardId`, a `state` object (empty for the first invocation of a window, and otherwise exactly the `state` the previous invocation in that window returned), `isFinalInvokeForWindow` and `isWindowTerminatedEarly`; each window closes with exactly one final invocation that carries an empty Records list and isFinalInvokeForWindow true, whose incoming state is the state accumulated over that window; and every record is delivered once, in the window containing its approximate arrival time.
Emulator: with TumblingWindowInSeconds=10 and BatchSize=2 echoed correctly by the create response, the events the handler receives carry none of it: `window` is absent (null), `state` is absent so every invocation opens with an empty state and the returned state is dropped rather than threaded into the next invocation, `shardId` is absent, and `isFinalInvokeForWindow`/`isWindowTerminatedEarly` are both absent. No record-less closing invocation is ever delivered, so no window is ever closed. Records themselves arrive (two per invocation, as BatchSize asks), which is why this reads as a windowing gap and not a delivery gap.
Why: tumbling-window aggregation is the documented way to compute per-window rollups in a stream consumer. On the emulator such a handler silently computes nothing: it cannot tell which window it is in, its accumulated state is discarded between invocations, and the final flush that emits the window's result never fires. A client gets no error — just永 missing aggregates — which is worse than a refusal because nothing signals the feature is absent.
Fix: the Kinesis poller of the Lambda event-source-mapping data plane — the tumbling-window accumulator (per-shard window bookkeeping, state carried across invocations in a window, and the final record-less invoke that closes it) plus the invoke-event builder that must add window/state/shardId/isFinalInvokeForWindow/isWindowTerminatedEarly to the event. CreateEventSourceMapping's validation and serializer already accept and echo TumblingWindowInSeconds.
