# autoscaling lifecycle-hook scenarios never converge inside a client's budget: every instance transition is withheld for a fixed wall-clock span, so a multi-wait hook/retention scenario reaches no verdict

> _Note: this issue was identified against the code base at commit `c119c6290af0aef232d88082a679964269a74639`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
CompleteLifecycleAction

## Description
One net-new root cause, grounded in the only two failing autoscaling behavioral checks of this run that the replay report does not mark ALREADY FILED or OWNED (every other autoscaling failure in the report is marked and was skipped). Both fail identically — verdict mismatch, detail 'Check timed out after 60.0s' — with no ClientError, no AssertionError and no stub on their path: the emulator refuses nothing and asserts nothing wrong, the scenarios simply never reach a verdict.

Cause 1 of 1: an Auto Scaling instance's lifecycle transition is made observable only after a fixed span of WALL-CLOCK time has elapsed since the call that decided it, and is materialised only by a request that arrives after that instant — so a client that polls DescribeAutoScalingGroups at AWS-sized intervals pays one full interval for EVERY transition, and a scenario that chains a lifecycle hold, a completion, a retention decision, a replacement launch and a teardown cannot complete. Failing check ids: autoscaling.deep-autoscaling-2-asg-enforce-terminate-hook-abandon-retain-keeps-instance-outside-desired, autoscaling.complete-lifecycle-action-reused-on-a-consumed-action-rejected-and-the-instance-stays-waiting.

AWS: the Smithy model (services/service-com-amazonaws-autoscaling-autoscaling-2011-01-01/smithy-model/com-amazonaws-autoscaling-autoscaling-2011-01-01.json) declares the whole state chain these two scenarios walk: LifecycleState enumerates Pending, 'Pending:Wait', 'Pending:Proceed', InService, Terminating, 'Terminating:Wait', 'Terminating:Proceed', 'Terminating:Retained', Terminated; CompleteLifecycleAction takes a required LifecycleActionResult ('You can specify either CONTINUE or ABANDON') addressed either by LifecycleActionToken (@length 36..36) or by InstanceId; RetentionTriggers$TerminateHookAbandon documents the retention contract verbatim — 'Specifies the action when a termination lifecycle hook is abandoned due to failure, timeout, or explicit abandonment (calling CompleteLifecycleAction). Set to retain to move instances to a retained state. Set to terminate for default termination behavior. Retained instances don't count toward desired capacity and remain until you call TerminateInstanceInAutoScalingGroup.' The model states no timing at all, so for the timing itself this is recorded behavior only: on AWS the delay between 'Pending' and 'InService', or between 'Terminating:Proceed' and the instance leaving the group, IS real provisioning work, and a client sizes its poll interval against that work. What is NOT part of AWS's contract is a service that has already DECIDED the outcome synchronously and then withholds it from the next read for a span of its own choosing. Each individual answer these scenarios wait on is already determined the moment its call returns.

Emulator: every instance transition is stored as a due instant computed from the wall clock — services/service-com-amazonaws-autoscaling-autoscaling-2011-01-01/src/state.rs declares `pub const LIFECYCLE_TRANSITION: Duration = Duration::from_millis(500)` ('this emulator picks a short, fixed span (chosen, not documented) and never sleeps for it'), and AutoScalingState::materialize_due, called at the top of every handler including the read-only ones, materialises only transitions whose due instant has already passed. src/state/lifecycle_actions.rs::end_lifecycle_wait sets `due = now + LIFECYCLE_TRANSITION` for everything except an admitted launch, so the DescribeAutoScalingGroups a client issues milliseconds after CompleteLifecycleAction still reports the pre-transition state; the client's poll loop probes first and sleeps on a miss, so it burns an entire interval per transition. For autoscaling.deep-autoscaling-2-... the waits are: control InService (interval 10 s), subject InService (10 s), control 'Terminating:Wait' (5 s), subject 'Terminating:Wait' (5 s), subject 'Terminating:Retained' (5 s), control gone from the group (10 s), control terminated at EC2 (10 s), a replacement InService alongside the retained instance (10 s), the retained instance back at 'Terminating:Wait' (5 s), it gone from the group (10 s) and terminated at EC2 (10 s) — well above the 60 s per-check budget, so the check is killed mid-scenario and the retention semantics it exists to verify are never observed. The same mechanism kills autoscaling.complete-lifecycle-action-reused-... on its chain of waits ('Pending:Wait' under two launching hooks, then InService after hook B's own completion).

Why: a client written against AWS polls at AWS-sized intervals because that is the only sane choice against the real service. Against this emulator the same client spends tens of seconds watching transitions the emulator had ready in half a millisecond, so any workflow that chains more than two or three Auto Scaling lifecycle steps — a deploy script that waits for a hook, a drain-and-replace loop, a teardown routine, an integration suite — runs orders of magnitude slower than the work being done and trips its own deadlines. Worse, every behavior that can only be demonstrated by COMPLETING such a chain goes untested in every environment: that an ABANDONed termination under InstanceLifecyclePolicy.RetentionTriggers.TerminateHookAbandon='retain' parks the instance in 'Terminating:Retained' while an unretained twin in an identical group terminates; that a retained instance counts toward no capacity (DesiredCapacity stays 1 while a replacement launches alongside it) and keeps running at EC2; that only TerminateInstanceInAutoScalingGroup clears it, running the terminating hook again; and that an instance held by two launching hooks stays at 'Pending:Wait' when one of them is completed, that re-completing that consumed action is refused with ValidationError and the message 'No active Lifecycle Action found with instance ID <instance-id> and HookName <hook-name>' (fixed text 'No active Lifecycle Action found with instance ID ' + ' and HookName ', the two variable parts taken from the request — the emulator already formats exactly this in src/state/lifecycle_actions.rs::no_active_action_under_hook_message, but no replay ever reaches it), and that the refused call does not release the instance.

Fix: the instance lifecycle clock of this crate — LIFECYCLE_TRANSITION and the due-instant/materialize_due path in services/service-com-amazonaws-autoscaling-autoscaling-2011-01-01/src/state.rs, together with the hold-release path in src/state/lifecycle_actions.rs (end_lifecycle_wait, move_held_instance, retain_held_instance). A transition whose outcome is already decided must be settled by the time the NEXT request observes the group rather than after a wall-clock span (advance pending changes on request arrival/sequence instead of on SystemTime::now()), while keeping the transient state in the response of the call that started it: a scale-out still reports Pending, a scale-in still reports Terminating, a held instance still reports 'Pending:Wait'/'Terminating:Wait' until its action is resolved. Having made the chains convergent, the fixer must also confirm the functional tail of each scenario actually holds (retained instance excluded from desired capacity with a replacement launched, EC2 state 'running', the second TerminateInstanceInAutoScalingGroup re-running the hook, and the consumed-action refusal above), since no replay has ever reached it. CAVEAT for the fixer on the second check: autoscaling.complete-lifecycle-action-reused-... contains one deliberately fixed 120 s hold (a _holds_for that proves the refused completion did NOT release the instance), so under a 60 s per-check budget that check can still be cut off by the harness after the timing fix; verify it by driving its sequence directly and confirming each wait converges on the first read that follows the call.

## Steps to Reproduce
Boot the emulator and point a botocore autoscaling client (Query protocol, sigv4) at it, with EC2 and SSM available for the launch-template prerequisites.

1. ec2:CreateLaunchTemplate(LaunchTemplateName=lt, LaunchTemplateData={ImageId: <AL2023 AMI from ssm:GetParameter>, InstanceType: t3.micro}).
2. autoscaling:CreateAutoScalingGroup(AutoScalingGroupName=G1, LaunchTemplate={LaunchTemplateName: lt}, MinSize=0, MaxSize=2, DesiredCapacity=1, VPCZoneIdentifier=<subnet>, HealthCheckGracePeriod=0, LifecycleHookSpecificationList=[{LifecycleHookName: h, LifecycleTransition: 'autoscaling:EC2_INSTANCE_TERMINATING', DefaultResult: 'ABANDON', HeartbeatTimeout: 900}]); and G2 identically plus InstanceLifecyclePolicy={RetentionTriggers:{TerminateHookAbandon:'retain'}}.
3. Observe the timing mechanism directly: immediately after CreateAutoScalingGroup, call DescribeAutoScalingGroups(AutoScalingGroupNames=[G1]) — the instance reports 'Pending'. Sleep 0.5 s and repeat: now 'InService'. The outcome was decided by the create; only wall-clock time made it visible.
4. autoscaling:TerminateInstanceInAutoScalingGroup(InstanceId=<G1 member>, ShouldDecrementDesiredCapacity=False), then DescribeAutoScalingGroups a few milliseconds later: the instance is not yet 'Terminating:Wait'. Sleep 0.5 s: it is. Repeat the same next-request observation for CompleteLifecycleAction(h, G2, InstanceId=<G2 member>, LifecycleActionResult='ABANDON') -> 'Terminating:Retained', and for the control group's ABANDON -> instance gone from the group / 'terminated' at EC2.
5. Now drive the whole scenario as a client written against AWS does — probe first, sleep an AWS-sized interval (5-10 s) on a miss. Expect it to finish as soon as the emulator has each answer (sub-millisecond). Observe it instead spend >= 90 s asleep and exceed the 60 s per-check budget, so the scenario's tail is never reached.
6. After the timing fix, the tail must be reachable AND must hold: G2's abandoned instance reports 'Terminating:Retained' and 'running' at EC2 while G1's twin leaves the group and reaches 'terminated'; G2 holds the retained instance plus a newly launched InService replacement with DesiredCapacity still 1; TerminateInstanceInAutoScalingGroup on the retained instance puts it back at 'Terminating:Wait' (the hook runs again) and a CONTINUE completion removes it from the group and terminates it at EC2, leaving exactly one InService instance.
