## Description

=== Cause 1 of 2: DeleteRule accepts a bare, non-ARN ruleIdentifier and answers 204 success where AWS refuses it with 400 ValidationException ===
AWS: Smithy model DeleteRule — DELETE /rules/{ruleIdentifier}, success @http code 204, @idempotent, output Unit; input member ruleIdentifier is @httpLabel + @required targeting RuleIdentifier (@length 1..1010) and is documented "The identifier of the rule. This is the rule's Amazon Resource Name (ARN)." The identifier is therefore required to BE an ARN (the rule's ARN member carries @pattern ^arn(:[a-z0-9]+([.-][a-z0-9]+)*){2}(:([a-z0-9]+([.-][a-z0-9]+)*)?){2}:(.+)$), so a value that is not an ARN is a field-validation failure, not an absent-resource no-op. DeleteRule models ValidationException (@error client, @httpError 400) with @required message, reason (ValidationExceptionReason = ACCOUNT_NOT_ONBOARDED | FIELD_VALIDATION_FAILED | OTHER) and fieldList. For a ruleIdentifier that is a bare rule id rather than an ARN the recorded response is HTTP 400 with an x-amzn-errortype response header naming the error shape, reason "FIELD_VALIDATION_FAILED" and Error.Message "ruleIdentifier must be the resource's ARN." — that message is entirely fixed text for this error class, naming the offending input member; no part of it is taken from the request or from state. A content-length header accompanies the error body. The @idempotent no-op path (204 for an identifier that names no rule) applies only to a WELL-FORMED identifier; a malformed one never reaches the lookup.
Emulator: answers HTTP 204 with an empty body for the same request — no message, no reason, no x-amzn-errortype and no content-length header (replay: "status: expected 400, got 204", "$: empty_body", "$headers.x-amzn-errortype: missing", "$headers.content-length: missing"). The handler resolves any string as a candidate key (store.resolve_rule_id(&input.rule_identifier)) and, on a miss, returns Ok(DeleteRuleOutput) as the @idempotent success, so the ARN-form check never runs. This is the DeleteRule half of the shared ruleIdentifier resolver defect; the GetRule half (same fixture, step task#2, where the miss surfaces as 404 ResourceNotFoundException) is owned by open issue 20261118T031240Z-network-security-manager-rule-read-path-and-response.md Cause 2, which carries only the GetRule replay key and says nothing about the delete path — the delete path fails differently (a false SUCCESS, not a wrong error class), so it is recorded here.
Why: the emulator reports SUCCESS for a request AWS rejects. A client that passes a rule id where an ARN is required is told the rule was deleted when nothing was deleted: teardown loops and reconciliation code mark the resource gone, the rule is leaked in state, and code branching on ValidationException.reason == FIELD_VALIDATION_FAILED to correct the argument never fires. A false 204 is strictly worse than the wrong error class, because there is no error for the caller to inspect at all.
Fix: DeleteRule's input validation (the ruleIdentifier ARN-form check must run BEFORE the state lookup and before the @idempotent no-op path) plus the ValidationException serializer for this operation, which must emit message, reason and the x-amzn-errortype header. Because the same identifier resolver is shared by the other rule operations, the check belongs where ruleIdentifier is resolved.
Traces: network-security-manager-rule-identifier-validation#task#3.

=== Cause 2 of 2: a teardown DeleteRule is refused with 409 ConflictException instead of succeeding with 204, because the reference check counts associations held by resources that are already supposed to be gone ===
AWS: Smithy model DeleteRule — DELETE /rules/{ruleIdentifier}, success @http code 204 with an empty body, @idempotent; modeled errors AccessDeniedException (403), ConflictException (@httpError 409), InternalServerException (500), ThrottlingException (429), ValidationException (400). ConflictException is documented "The request conflicts with the current state of the resource. For example, the resource was modified concurrently, or it is in a state that does not allow the requested operation" and carries @required message plus optional resourceId/resourceType. AWS refuses a rule delete with 409 only while a LIVE resource still associates the rule; once the associating template/policy has itself been deleted (or was never created), the identical DeleteRule call succeeds with 204 and an empty body. The recorded responses at the end of both lifecycles are 204.
Emulator: answers HTTP 409 for that delete (replay: "status: expected 204, got 409"), i.e. the modeled ConflictException with the in-use message, so the rule is never removed and the fixture's cleanup cannot complete. The refusal comes from delete_rule.rs (store.is_referenced(&rule.rule_arn, &rule.rule_id) at lines 189-200) consulting crate::state::references (src/state/references.rs is_referenced), which walks every stored policy's associatedTemplateAndRuleList, every stored template's associatedRuleList and every stored deployment's associations. Hypothesis: the references outliving the delete are held by entities the lifecycle already asked to remove — DeleteTemplate is still an unimplemented scaffold in this checkout (src/ops/delete_template.rs line 4 "SCAFFOLDED, NOT IMPLEMENTED", handler returns Scaffolded::not_implemented, so a template delete answers 501 and the template record is never dropped), which leaves its associatedRuleList pinning the rule forever. Whatever removes the holder, the requirement filed here is DeleteRule's own: a rule with no live associating resource must be deletable and must answer 204 with an empty body, and the in-use refusal must be driven by live references only (a reference belonging to a removed or unreadable holder is not a live reference).
Why: the rule can never be deleted. Every cleanup/teardown path leaks rules, repeated runs accumulate entities and hit the store's create ceilings, and a client that correctly orders its deletes (holder first, then rule) gets a permanent 409 that no retry clears — the opposite failure from AWS, where the ordered delete succeeds. Because a 409 is a client-fault conflict, callers conclude their own ordering is wrong and give up rather than retrying.
Fix: DeleteRule's reference check and the state reference graph it reads (src/ops/delete_rule.rs's is_referenced call and src/state/references.rs), so the refusal is computed from live holders only; and the holder-removal path that must drop those associations when the holder is deleted (DeleteTemplate's handler and the template store), so a deleted template stops pinning its associated rules.
Traces: network-security-manager-scope-and-template-crud#teardown#10 (cluster also covers network-security-manager-scope-and-template-tag-lifecycle#teardown#15).
