# cloudfront__elbv2: a distribution over an ALB custom origin still never serves at the edge, so both ALB-origin enforcement checks are cut off at the 60 s budget with no verdict

> _Note: this issue was identified against the code base at commit `78227bf8b82e2b43db17fd6c8dc7d3251947433d`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
CreateDistribution

## Description
Cause 1 of 1 — a CloudFront distribution whose Origins[].DomainName is an Application Load Balancer DNS name (CustomOriginConfig) never produces a served response at the distribution's edge domain, and the convergence points the checks wait on (the ALB reaching State.Code 'active', the distribution reaching Status 'Deployed', then a first 200 through the edge) are never all reached, so both checks in the cloudfront__elbv2 group burn their whole budget on the positive control and are killed with no assertion ever evaluated. Failing checks: cloudfront__elbv2.xsvc-cloudfront-2-alb-origin-protocol-policy-mismatch-rejected, cloudfront__elbv2.xsvc-cloudfront-2-alb-origin-secret-header-direct-request-forbidden (the group's only two checks; 0/2 passed). NOTE: the resolved issue 20261115T163206Z-cloudfront-elbv2-a-cloudfront-distribution-over-an-alb.md claimed this exact pair; both still fail identically (same timeout, no edge answer), so its fix did not land for the ALB-origin combination. This is not a refusal — nothing is answered at all — so it is re-filed rather than described as a refusal regression.

AWS: CreateDistribution accepts a custom (non-S3) origin and CloudFront then proxies viewer requests to it. Smithy (com.amazonaws.cloudfront): Origin.CustomOriginConfig -> CustomOriginConfig with required HTTPPort, required HTTPSPort and required OriginProtocolPolicy; OriginProtocolPolicy is an enum with values http-only | match-viewer | https-only, documented as 'http-only – CloudFront always uses HTTP to connect to the origin', 'match-viewer – CloudFront connects to the origin using the same protocol that the viewer used to connect to CloudFront', 'https-only – CloudFront always uses HTTPS to connect to the origin'. Smithy: Origin.CustomHeaders -> CustomHeaders/OriginCustomHeader with required HeaderName and required (sensitive) HeaderValue — 'the name of a header that you want CloudFront to send to your origin' — i.e. CloudFront injects it into every origin request. CustomOriginConfig also models OriginReadTimeout/OriginKeepaliveTimeout, and Origin models ConnectionAttempts/ConnectionTimeout, which bound how fast an unopenable origin port fails. For the data plane the model says nothing, so recorded behavior only: once Status is 'Deployed' and the ALB is 'active', a GET at the distribution domain on a behavior bound to an http-only ALB origin returns HTTP 200 carrying the ALB listener's fixed-response body; a behavior bound to an https-only origin whose ALB security group admits tcp/80 only fails at the edge with HTTP 504 and must NOT carry the origin body; the same match-viewer origin returns 200 over an HTTP viewer and 504 over an HTTPS viewer. With Origin.CustomHeaders carrying a secret header, the edge request matches the ALB listener's http-header rule and gets 200 with that rule's body, while a direct GET at the ALB DNS name with no header or a wrong value gets the listener default's 403 and its body, and one with the correct value gets 200 with the rule's body. (The distribution domain, ALB DNS name, secret value and body markers are per-run values; the statuses, the port each OriginProtocolPolicy dials, and which body is served are the requirements.)

Emulator: both checks end with 'Error: Check timed out after 60.0s' and no assertion is reached. Each check's own bounded polls — elbv2 DescribeLoadBalancers until State.Code == 'active' (600 s), cloudfront GetDistribution until Status == 'Deployed' (900 s), then the distribution domain until a 200 (300 s at 20 s per request) — never converge inside the harness cap, so the ALB-origin data path produces no status, no body and no observable origin request at all. Neither subject the checks exist to verify is exercised: (a) which origin port OriginProtocolPolicy makes the edge dial and the 504 it must answer when that port cannot be opened, and (b) that Origin.CustomHeaders are injected into the origin request so the ALB's header rule — not CloudFront's network position — is the gate.

Why: a client that fronts an ALB with CloudFront can verify none of it against the emulator. An origin-protocol misconfiguration that AWS surfaces as a fast 504 at the edge yields nothing, and the standard secret-header origin lock (which stops viewers bypassing the distribution) can neither be shown to admit the edge nor to refuse a direct caller. Any client or suite that waits on a CloudFront-over-ALB response hangs instead of failing with a diagnosis.

Fix: the CloudFront edge data plane's origin-fetch path for CustomOriginConfig origins — origin host resolution for an ELBv2-published DNSName, the port choice driven by OriginProtocolPolicy (including match-viewer following the viewer scheme), injection of Origin.CustomHeaders into the origin request, and the edge's 504 when the chosen origin port cannot be opened (honouring ConnectionAttempts/ConnectionTimeout) — together with whatever leaves the distribution short of 'Deployed' or the load balancer short of 'active' in this combination. Related but non-covering OPEN issues: 20261122T170634Z-cloudfront-ec2-elbv2-a-distribution-s-domainname-is.md (a distribution's DomainName announced as a bare host:port the emulator does not serve) and 20261117T143723Z-cloudfront-s3-6-net-new-causes-a-distribution.md (a distribution never leaving InProgress); neither carries a cloudfront__elbv2 check id, so the ALB-origin combination is unowned.

Traces: cloudfront__elbv2.xsvc-cloudfront-2-alb-origin-protocol-policy-mismatch-rejected and cloudfront__elbv2.xsvc-cloudfront-2-alb-origin-secret-header-direct-request-forbidden. Both must clear their positive control (a 200 with the ALB listener's body through the http-only origin) before the 504 and secret-header assertions can be judged.

## Evidence
Expected (AWS): after CreateDistribution over an ALB custom origin reaches Status 'Deployed' and the ALB reaches State.Code 'active' — GET https://<distribution-domain>/<path on an http-only behavior> -> HTTP 200 with the ALB listener's fixed-response body; GET on the https-only behavior against an ALB with no reachable 443 -> HTTP 504 with the origin body absent; GET http://<domain>/<match-viewer path> -> 200 with the body and GET https://<domain>/<the same match-viewer path> -> 504 without it. With Origin.CustomHeaders = {<secret-header>: <secret>}: GET through the edge -> 200 with the header-matched rule's body; direct GET at the ALB DNS name with no header or a wrong value -> 403 with the listener default's body; direct GET with the correct value -> 200 with the rule's body.

Actual (emulator): both checks terminate with 'Error: Check timed out after 60.0s'. No status line, body or origin-request header is ever observed; the checks' convergence polls (ALB 'active' 600 s, distribution 'Deployed' 900 s, first 200 at the edge 300 s) all exceed the harness cap without an answer. Per-service rate in this run: cloudfront__elbv2 0/2 (0%), 2 failed. The identical pair was reported and marked fixed as 20261115T163206Z-cloudfront-elbv2-a-cloudfront-distribution-over-an-alb.md; the behavior is unchanged.

## Steps to Reproduce
1. Create a VPC with two public subnets (two distinct AZs) and a security group admitting tcp/80 only from the com.amazonaws.global.cloudfront.origin-facing managed prefix list; create an internet-facing ipv4 Application Load Balancer in it.
2. Check A: add an HTTP:80 listener whose default action is fixed-response 200 with a known body marker. CreateDistribution with Enabled=true and three CustomOriginConfig origins over the ALB's DNSName (HTTPPort 80, HTTPSPort 443, ConnectionAttempts 1, ConnectionTimeout 2), one per OriginProtocolPolicy (http-only, https-only, match-viewer), cache behaviors routing /tls/* to the https-only origin and /mv/* to the match-viewer origin, the managed CachingDisabled cache policy, and CustomErrorResponses for 504 with ErrorCachingMinTTL 0.
3. Poll elbv2 DescribeLoadBalancers until State.Code == 'active' and cloudfront GetDistribution until Status == 'Deployed'.
4. GET https://<distribution-domain>/plain/a — expect 200 with the marker; the emulator never answers and the check is cut at 60 s. Then GET /tls/a (expect 504, no marker), http://<domain>/mv/a (expect 200 + marker), https://<domain>/mv/a (expect 504, no marker).
5. Check B: same VPC/ALB, but the HTTP:80 listener default is fixed-response 403 with a denial body plus a priority-1 rule matching http-header <secret-header> == <secret> returning 200 with a marker; CreateDistribution with a single ALB origin carrying Origin.CustomHeaders = {<secret-header>: <secret>} and a 403 CustomErrorResponses entry with ErrorCachingMinTTL 0. After 'Deployed', GET through the edge (expect 200 + marker), then GET the ALB DNS name directly with no header and with a wrong value (expect 403 + denial body) and with the right value (expect 200 + marker).
