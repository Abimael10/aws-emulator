Cause 1 of 3: an AccessDenied produced for an STS session credential by an implicit identity-based deny carries a trailing authorization-details sentence that these recordings do not carry.
AWS: recorded behavior only (no Smithy trait governs error message text; Smithy sts#AssumeRole mints the Credentials whose principal appears in the message). For this denial class AWS's Error.Message is exactly one sentence and nothing else: `User: <assumed-role session ARN> is not authorized to perform: <service:Action> on resource: <resource ARN> because no identity-based policy allows the <service:Action> action`. Fixed text: everything except the variable parts, which come from the request and the emulator's state — the session principal ARN (`arn:aws:sts::<account>:assumed-role/<role name>/<session name>`), the action, and the resource ARN (e.g. `arn:aws:iam::<account>:user/`, `arn:aws:iam::<account>:role/`). HTTP status 403 and Error.Code `AccessDenied` are already correct in the emulator and are not at issue; only the message body is.
Emulator: the leading sentence is correct, then a second sentence AWS did not send is appended: `. Go to https://<region>.console.aws.amazon.com/iam/home?region=<region>#/authorization-details/<authorization-id> for complete details, or call the GetRequestAuthorizationDetails API with the following authorization id: <authorization-id>`. It appears for both grounding checks (iam:ListUsers denied because the session policy's `*` cannot exceed the role's identity policy; iam:ListRoles denied because an aws:PrincipalTag condition is unsatisfied), i.e. it is appended unconditionally rather than per denial class. The authorization id inside the trailer is per-run state; the defect is the presence of the whole sentence, not its value.
Why: a client that matches, logs or asserts on AWS's denial text sees text AWS never sent, so message-equality and regression assertions fail even though the authorization decision, status and code are right; operators are pointed at an authorization id that identifies nothing.
Fix: the shared AccessDenied message formatter on the request-authorization path (the component that renders the denial for a request signed with an STS session credential) — emit the trailer only for the denial classes whose recordings carry it (the "no session policy allows" family), not for the identity-based-deny family. The policy evaluator is correct and must not be touched.
Traces: sts.assume-role-session-policy-cannot-exceed-role-permissions-denied, sts.assume-role-session-tags-unicode-value-round-trip.

Cause 2 of 3: the UnauthorizedOperation refusal of a session-policy-denied ec2:RunInstances DryRun carries no `Encoded authorization failure message:` trailer, so no encoded blob is ever minted and sts:DecodeAuthorizationMessage has nothing genuine to decode.
AWS: Smithy com.amazonaws.ec2#RunInstancesRequest$DryRun — "Checks whether you have the required permissions for the operation, without actually making the request, and provides an error response. If you have the required permissions, the error response is DryRunOperation. Otherwise, it is UnauthorizedOperation." Recorded behavior for the sentence: HTTP 403, code `UnauthorizedOperation`, message `You are not authorized to perform this operation. User: <assumed-role session ARN> is not authorized to perform: ec2:RunInstances on resource: <resource ARN> with an explicit deny in a session policy. Encoded authorization failure message: <blob>` — the fixed text is `You are not authorized to perform this operation. User: `, ` is not authorized to perform: `, ` on resource: `, the deny-classification clause ` with an explicit deny in a session policy.` and the trailer ` Encoded authorization failure message: `; the variable parts are the session ARN, the action, the resource ARN and the per-failure blob. Smithy com.amazonaws.sts#DecodeAuthorizationMessage then decodes that blob (input EncodedMessage @required, @length min 1 max 10240; output DecodedMessage; error InvalidAuthorizationMessageException, errorKind client, httpError 400, awsQueryError code InvalidAuthorizationMessageException/400) to allowed=false, explicitDeny=true, context.principal.arn/id = the session ARN and the AssumedRoleId AssumeRole returned, context.action = the BARE operation name `RunInstances`, context.resource = the instance ARN, context.conditions carrying the keys EC2 derived from the request (`ec2:InstanceType` = the type the request asked for) and exactly one matchedStatements item with effect `DENY` naming the service-qualified action and this session's principal id. A malformed EncodedMessage must be refused HTTP 400 / `InvalidAuthorizationMessageException` with `Message is not valid: [<the base64url decode of the submitted input as signed decimal bytes, comma-separated>]` — fixed text `Message is not valid: [` ... `]`, the byte list determined entirely by the submitted input.
Emulator: the refusal is now reached and correctly classified (403 / UnauthorizedOperation, with the explicit-deny-in-a-session-policy clause), but its message ENDS at that clause — the ` Encoded authorization failure message: <blob>` trailer is absent, so no blob exists. Both grounding checks fail at `assert "Encoded authorization failure message:" in message`, and consequently the genuine decode (the positive control) and the InvalidAuthorizationMessageException leg that must follow it are never reached.
Why: the whole authorization-diagnostics loop is dead. A client that captures the encoded blob from a 403 and calls sts:DecodeAuthorizationMessage to learn WHICH statement denied it gets nothing to decode, troubleshooting tooling built on that loop cannot be exercised, and an implementation that rejected every decode request would be indistinguishable from a correct one.
Fix: the shared request-authorization gate must mint the encoded blob from the decision it already made (principal ARN + AssumedRoleId, bare action name, request-derived resource ARN, the request's condition keys, and the matched statement with its effect/actions/principals), EC2's RunInstances refusal serializer must append the trailer to the UnauthorizedOperation message, and the STS DecodeAuthorizationMessage handler must decode a genuine blob to that content while keeping its invalid-input path refusing 400 / InvalidAuthorizationMessageException with the `Message is not valid: [...]` sentence.
Traces: sts.encoded-authorization-failure-message-decodes-to-the-denied-principal-and-action, sts.decode-authorization-message-invalid-rejected.

Cause 3 of 3: the same UnauthorizedOperation message names the request's SUBNET ARN as the denied resource instead of the instance ARN the launch would have created.
AWS: recorded behavior only for the resource rendering (the model fixes only the code/clause semantics, see Cause 2). For a denied RunInstances the resource in both the message and the decoded context is `arn:aws:ec2:<region>:<account>:instance/*` — fixed text apart from the request's region and the caller's account id; the subnet the request named is a request parameter, not the authorized resource.
Emulator: the message reads `... is not authorized to perform: ec2:RunInstances on resource: arn:aws:ec2:<region>:<account>:subnet/<subnet-id> with an explicit deny in a session policy.` — the resource is the request's SubnetId ARN. (The subnet id in any one run is per-run state; the defect is the ARN's resource TYPE, `subnet/<id>` instead of `instance/*`.)
Why: a client or operator reading the denial is told the wrong resource was denied, so least-privilege work keyed on the resource ARN scopes the wrong thing; the same wrong value would propagate into the decoded context.resource once Cause 2 is fixed.
Fix: the resource-ARN derivation RunInstances passes to the authorization gate and its denial serializer (the request-to-resource mapping for RunInstances), not the policy evaluator.
Traces: sts.encoded-authorization-failure-message-decodes-to-the-denied-principal-and-action.
