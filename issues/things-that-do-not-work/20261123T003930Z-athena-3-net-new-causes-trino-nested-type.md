## Description
3 net-new root causes in the Athena service, all reached through the behavioral suite and none of them marked OWNED or ALREADY FILED by the replay. Related OPEN issues that do NOT carry these checks' replay keys: 20261121T213708Z-athena-2-net-new-causes-an-integer-varchar.md (its Cause 1 is an integer+varchar arithmetic expression in a plain SELECT, not parameter binding of an EXECUTE, and it lists neither check below), 20261111T090701Z-athena-s-sql-engine-refuses-trino-hive-statements.md (its 10 causes are CTAS WITH, UNLOAD, SHOW PARTITIONS, MSCK REPAIR and similar statement forms — none is nested-type projection or a scalar array function), 20261116T142606Z-athena-metadata-lookup-refusals-omit-the-wrapped-amazondatacatalog.md (GetTableMetadata for an absent TABLE and ListTableMetadata for an absent DATABASE; the envelope it asks for is now present, and the GetTableMetadata absent-DATABASE branch below is a different branch of a different condition) and the FIXED 20261114T133324Z-athena-cloudformation-glue-gettablemetadata-s-metadataexception-for-an.md (same note: its fix supplied the envelope, which this cause no longer disputes).

Cause 1 of 3: a SELECT that projects INSIDE the nested types of a JSON-SerDe table fails because the engine never implements Trino's array/struct/map functions — the scalar `cardinality()` reaches the backing SQLite engine untranslated.
AWS: Athena's Trino engine deserialises a table declared `ROW FORMAT SERDE 'org.openx.data.jsonserde.JsonSerDe'` over newline-delimited JSON and evaluates nested-type projections over it: `tags[1]` (1-based array indexing) yields the first element, `cardinality(tags)` yields the array length as bigint, `meta.k`/`meta.v` read struct members keeping the declared `int` type (including a negative value), and `kv['a']` subscripts a `map<string,int>` by key. Such a statement settles in the terminal state SUCCEEDED (Smithy: GetQueryExecution -> QueryExecution.Status.State; StartQueryExecution accepts QueryString @length 1-262144 and models only InternalServerException/InvalidRequestException/TooManyRequestsException, so a refusal of a valid statement is not modelled), GetQueryResults returns one row per source record, ResultSetMetadata.ColumnInfo types the projected values with the engine's own types (cardinality() -> bigint, a struct `int` member -> integer, a varchar element -> varchar), a whole array column is rendered as its bracketed comma-joined elements and typed `array`, a predicate on a map value filters server-side, and Statistics.DataScannedInBytes equals the bytes actually read. The model states no message text for the failure path, so for the failure text this is recorded behavior only.
Emulator: the execution settles FAILED and GetQueryExecution reports Status.StateChangeReason of the form `no such function: <function> in <the rewritten statement> at offset <n>` — fixed text `no such function: `, then the function name, then ` in `, then the statement the emulator rewrote, then ` at offset ` and an offset; the function name, statement and offset are the variable parts. The rewritten statement shows the translation layer mapping `tags[1]` to `json_extract(tags, '$[0]')`, `meta.k` to `json_extract(meta, '$."k"')` and `kv['a']` to `json_extract(kv, '$."a"')`, while `cardinality(tags)` is passed through verbatim to SQLite, which has no such function. The same rewritten text also collapses the submitted two-part quoted name `FROM "<db>"."<tbl>"` into one identifier `FROM "<db>.<tbl>"`, so the name would resolve against a table literally called `<db>.<tbl>`. No rows, no column types and no scan statistics are ever produced.
Why: the JSON SerDe is the documented way to query nested JSON in Athena, so a client's query over its own data is refused with a diagnostic that names no mistake in SQL that AWS accepts. Because the failure is a missing-function error rather than a type or name error, a client cannot tell an unsupported engine from a bad query, and every downstream consumer (a BI tool reading ColumnInfo, a job reading the result CSV) gets nothing at all.
Fix: the SQL translation/execution layer of the Athena query engine in services/service-com-amazonaws-athena-amazonathena (the component StartQueryExecution hands the statement to): Trino's collection functions and nested-type operators must be implemented or translated rather than leaked to the backing engine, and qualified-name handling must preserve a two-part quoted identifier.
Traces: athena.json-serde-nested-array-struct-and-map-project-exact-values.

Cause 2 of 3: an EXECUTE whose ExecutionParameters value cannot bind to the placeholder's type SUCCEEDS instead of failing analysis.
AWS: a prepared statement created with `CreatePreparedStatement(QueryStatement='SELECT id, name FROM "<db>"."<tbl>" WHERE id = ?')` binds ExecutionParameters as VALUES, never as SQL text. A submission of `EXECUTE <stmt>` with ExecutionParameters=['<non-integer text>'] is ACCEPTED by StartQueryExecution (Smithy: ExecutionParameters, list @length min 1) and the execution then FAILS during analysis: GetQueryExecution reports Status.State 'FAILED' with Status.StateChangeReason in Trino's type-mismatch form — fixed text `TYPE_MISMATCH: line <line>:<col>: Logical expression term must evaluate to a boolean (actual: <type>)`, where the line/column, and the actual type, come from the submitted statement and the placeholder's catalog type (the recorded run's `line 1:48` and `integer` are values, not part of the requirement). GetQueryResults on that execution is then refused with InvalidRequestException / message `Query did not finish successfully. Final query state: FAILED`. Recorded behavior only for the exact reason wording; the binding-as-a-value rule is Athena's documented parameterized-query behavior.
Emulator: the execution settles SUCCEEDED. With ExecutionParameters=['2 OR 1=1'] against the integer placeholder, GetQueryExecution reports Status.State 'SUCCEEDED', no StateChangeReason and no AthenaError, so the invalid binding is never detected. The positive legs of the same check pass (ExecutionParameters=['2'] selects exactly the id=2 row, Query is recorded verbatim as `EXECUTE <stmt>`, SubstatementType is EXECUTE and ExecutionParameters is not echoed), so only the type analysis of the bound parameter is missing.
Why: a client that submits a parameter AWS refuses receives a SUCCEEDED query and reads whatever the coercing backing engine returned as if it were a real result; there is no state, no reason and no AthenaError to inspect. Worse, for the injection-shaped value this is exactly the case where AWS's value-binding guarantee is what a client depends on, so a silently SUCCEEDED execution hides whether the parameter was bound as a value or spliced into the SQL.
Fix: parameter binding and expression type analysis in the Athena query engine's SQL front end, plus the failure path that sets Status.State=FAILED and populates Status.StateChangeReason/Status.AthenaError, and the GetQueryResults refusal for a non-SUCCEEDED execution.
Traces: athena.prepared-statement-execute-with-parameters.

Cause 3 of 3: GetTableMetadata for a table in a database the catalog does not hold relays the emulator's own `Database <db> not found.` clause where AWS relays the catalog's `Entity Not Found`.
AWS: GetTableMetadata (Smithy: required CatalogName @length 1-256, required DatabaseName and TableName @length 1-128, optional WorkGroup; errors InternalServerException HTTP 500, InvalidRequestException HTTP 400, MetadataException HTTP 400) refuses a lookup whose DatabaseName does not exist in AwsDataCatalog with HTTP 400 / MetadataException. The model states no message text, so recorded behavior only for the text: the message is the relayed AmazonDataCatalog exception, of the fixed form `Entity Not Found (Service: AmazonDataCatalog; Status Code: 400; Error Code: EntityNotFoundException; Request ID: <request id>; Proxy: null)`. Everything there is fixed text for this error class except <request id>, which is per-run. Athena does NOT distinguish the absent database from the absent table on this operation: both relay the catalog's `Entity Not Found` clause, so the requested database name appears nowhere in the message. The sibling reads in the same check now agree with AWS (GetDatabase and ListTableMetadata for the same absent database both produce the relayed envelope and pass), which is what isolates this one branch.
Emulator: answers HTTP 400 / MetadataException with Message `Database <DatabaseName> not found. (Service: AmazonDataCatalog; Status Code: 400; Error Code: EntityNotFoundException; Request ID: <request id>; Proxy: null)` — the envelope is right, but the relayed clause is the emulator's own sentence (`Database ` + the request's DatabaseName + ` not found.`) instead of the catalog's `Entity Not Found`.
Why: a client that string-matches AWS's message for this error class, or that treats the leading clause as the upstream catalog's own text, never matches, so create-if-missing and fallback logic keyed on the relayed entity-not-found sentence does not fire; and the emulator leaks a distinction (database vs. table) AWS does not make on this operation, so a client written against the emulator parses a clause AWS never sends.
Fix: the database-not-found branch of the GetTableMetadata handler (services/service-com-amazonaws-athena-amazonathena/src/ops/get_table_metadata.rs, the `catalog.database(...)` miss at lines 232-236, which calls `crate::state::database_not_found(&input.database_name)`): relay the same entity-not-found clause the table-miss branch below it uses (`crate::state::table_not_found()`), through the shared `crate::state::relayed_catalog_entity_not_found` renderer.
Traces: athena.metadata-reads-reject-unknown-database.
