# cloudformation__efs: a FileSystemPolicy statement that omits Resource is stored verbatim instead of being normalized to the file system's own ARN, so DescribeFileSystemPolicy never reads back the Resource AWS fills in

> _Note: this issue was identified against the code base at commit `5b88798ccff0ec7f765809a75ef2c7dfb1d7aad0`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
PutFileSystemPolicy

## Description
One net-new root cause, reached by both failing checks the suite lists under '### cloudformation__efs' that the replay report does NOT mark ALREADY FILED or OWNED. Both checks deploy an AWS::EFS::FileSystem whose FileSystemPolicy statement has no Resource element, then read the stored policy back with DescribeFileSystemPolicy; both fail on the same readback assertion, and they differ only in the statement they deploy (Allow ClientMount+ClientWrite with a Condition, vs the lockout check's positive control Deny ClientMount).

Related open issue, which does not cover this cause as the report scores it: 20261117T112858Z-cloudformation-efs-2-net-new-causes-an-aws.md. That issue's Cause 2 is the lockout refusal in the SAME check (deploy-cfn-efs-file-system-policy-lockout-rejected) but keyed to its earlier `assert status == "ROLLBACK_COMPLETE"` divergence; that stage now passes and the check proceeds to its positive control, where it fails on the policy readback described here. The two should be closed independently.

Cause 1 of 1: EFS stores a FileSystemPolicy statement exactly as submitted and does not apply AWS's resource-scoping normalization, so a statement submitted without a Resource element is read back without one.
AWS: Smithy (efs, magnolioapiservice-v20150201): PutFileSystemPolicy is PUT /2015-02-01/file-systems/{FileSystemId}/policy -> 200, input FileSystemId (@required, @httpLabel, pattern ^(arn:aws[-a-z]*:elasticfilesystem:[0-9a-z-:]+:file-system/fs-[0-9a-f]{8,40}|fs-[0-9a-f]{8,40})$), Policy (@required, @length 1..20000), BypassPolicyLockoutSafetyCheck (boolean, @default false); errors BadRequest 400, FileSystemNotFound 404, IncorrectFileSystemLifeCycleState 409, InternalServerError 500, InvalidPolicyException 400. DescribeFileSystemPolicy is GET on the same URI -> 200 FileSystemPolicyDescription{FileSystemId, Policy}; errors BadRequest 400, FileSystemNotFound 404, InternalServerError 500, PolicyNotFound 404. The model does not state how the stored document is canonicalized, so this part is recorded behavior only: when a FileSystemPolicy statement omits Resource, EFS scopes that statement to the file system the policy is attached to and persists it with Resource set to that file system's own ARN — the value DescribeFileSystems reports as FileSystemArn, of the form arn:aws:elasticfilesystem:<region>:<account-id>:file-system/<FileSystemId>. Every other element of the submitted statement (Version, Effect, Principal, Action in its submitted form including a list, Condition) is persisted and read back unchanged, and the Resource element is inserted into each statement that lacked one. This holds whether the policy is written through PutFileSystemPolicy directly or through a CloudFormation AWS::EFS::FileSystem FileSystemPolicy property, which CloudFormation provisions by calling PutFileSystemPolicy.
Emulator: the statement is read back byte-for-byte as submitted, with no Resource key at all. For the Allow statement the emulator returns {'Version': '2012-10-17', 'Statement': [{'Effect': 'Allow', 'Principal': {'AWS': '<role-arn>'}, 'Action': ['elasticfilesystem:ClientMount', 'elasticfilesystem:ClientWrite'], 'Condition': {'Bool': {'elasticfilesystem:AccessedViaMountTarget': 'true'}}}]} where AWS returns the same statement plus 'Resource': '<the file system's own FileSystemArn>'; for the Deny control it returns {'Version': '2012-10-17', 'Statement': [{'Effect': 'Deny', 'Principal': {'AWS': '*'}, 'Action': 'elasticfilesystem:ClientMount'}]} where AWS returns the same statement plus that same 'Resource'. The call succeeds with 200 in both directions — the divergence is purely the missing Resource element in the stored/served document, not a status or error-code divergence. Hypothesis: the policy document is treated as an opaque string and persisted unparsed, so no per-statement resource scoping is applied on write.
Why: a client that reads its own resource policy back cannot tell which resource the stored statements are scoped to, and any client that round-trips the document — reads it, edits one statement, and PutFileSystemPolicy's it back — loses the scoping AWS added, or diffs the policy it deployed against the policy AWS reports and sees a spurious difference. Policy-drift detection, CloudFormation/IaC drift comparisons and any authorization reasoning performed client side on the served document are all driven off a document that is not the one AWS would serve.
Fix: EFS PutFileSystemPolicy's policy handling — the write path must parse the submitted document and, for each statement with no Resource element, insert the attached file system's own ARN before persisting, so DescribeFileSystemPolicy (which serves the persisted document) reads it back with Resource filled in. The CloudFormation AWS::EFS::FileSystem create handler needs no separate change provided it routes the template's FileSystemPolicy through that same EFS write path.
Traces: cloudformation__efs.deploy-cfn-efs-file-system-policy-round-trip-and-delete, cloudformation__efs.deploy-cfn-efs-file-system-policy-lockout-rejected.
