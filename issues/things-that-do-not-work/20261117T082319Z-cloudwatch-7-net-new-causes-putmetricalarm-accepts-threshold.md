# cloudwatch: 7 net-new causes — PutMetricAlarm accepts Threshold together with ThresholdMetricId, and six refusal messages are emulator-authored (anomaly-detector conflict order, GetDashboard single-violation, GetMetricStatistics Period, DescribeAnomalyDetectors InvalidNextToken, PutInsightRule rule body, LimitExceeded quota text)

> _Note: this issue was identified against the code base at commit `4656e0c05364d93352205f500cecb8d1e125c90a`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
PutMetricAlarm

## Description
This issue bundles 7 net-new root causes, all in the cloudwatch (monitoring, 2010-08-01) emulator. Each is numbered below with its own failing check ids. All seven must be closed before submitting.

Cause 1 of 7: PutMetricAlarm accepts Threshold and ThresholdMetricId together instead of refusing the ambiguous alarm definition.
AWS: Smithy (cloudwatch 2010-08-01) models PutMetricAlarm with both Threshold (double) and ThresholdMetricId (target MetricId, @length min 1 max 255) as optional members; ThresholdMetricId's documentation is "If this is an alarm based on an anomaly detection model, make this value match the ID of the ANOMALY_DETECTION_BAND function", so an alarm is either a static-threshold alarm or an anomaly-band alarm, never both. The model declares only LimitExceededFault for PutMetricAlarm, so this refusal is recorded behavior only: AWS rejects the request with HTTP 400, Error.Code ValidationError and the fixed message "Threshold and ThresholdMetricId cannot both be set" (the whole sentence is fixed text; it has no variable part), and creates no alarm.
Emulator: the call SUCCEEDS — HTTP 200, content-type application/x-amz-json-1.0, empty JSON body — so an alarm carrying both a static Threshold and a band ThresholdMetricId is admitted. Because the check stops at this first rejection, the two sibling refusals in the same validation block are never exercised and are presumed broken the same way: a range ComparisonOperator (GreaterThanUpperThreshold) with a static Threshold and no ThresholdMetricId must be refused ValidationError "ComparisonOperators for ranges require ThresholdMetricId to be set", and a ThresholdMetricId naming an id absent from the alarm's own Metrics array must be refused ValidationError "Metrics list must contain exactly one metric matching the ThresholdMetricId parameter".
Why: a client that relies on AWS rejecting the ambiguous definition instead stores an alarm whose threshold source is undefined. The alarm then evaluates against whichever source the emulator happens to prefer, and the caller has no error to correct; configuration bugs that AWS catches at write time become silent, wrong alarm behavior at evaluation time.
Fix: PutMetricAlarm's input validation (the threshold/ThresholdMetricId mutual-exclusion and band-operator checks), not its state writer — the request must be refused before any alarm is created.
Traces: cloudwatch.anomaly-detection-band-alarm-threshold-metric-id.

Cause 2 of 7: the anomaly-detector conflicting-identification message enumerates the conflicting sources in the reverse of AWS's order.
AWS: PutAnomalyDetector and DeleteAnomalyDetector both model InvalidParameterCombinationException (errorKind client, httpError 400, awsQueryError code InvalidParameterCombination / 400), documented "Parameters were used together that cannot be used together." Both operations accept three mutually exclusive ways to identify a detector: the deprecated top-level single metric attributes (Namespace/MetricName/Dimensions/Stat, each carrying @deprecated "Use SingleMetricAnomalyDetector."), SingleMetricAnomalyDetector, and MetricMathAnomalyDetector. When more than one is supplied the refusal message is the template "Either single metric attributes, SingleMetricAnomalyDetector or MetricMathAnomalyDetector can be set, found <sources>." — the leading clause and the trailing period are fixed text; <sources> is the comma-separated list of the sources actually present in the request, enumerated in the same order the sentence lists the alternatives (single metric attributes, then SingleMetricAnomalyDetector, then MetricMathAnomalyDetector). For a request carrying the deprecated top-level attributes together with SingleMetricAnomalyDetector, the message therefore ends "found single metric attributes, SingleMetricAnomalyDetector."
Emulator: status and Error.Code are correct, but the list is built in discovery order rather than declaration order, yielding "Either single metric attributes, SingleMetricAnomalyDetector or MetricMathAnomalyDetector can be set, found SingleMetricAnomalyDetector, single metric attributes." on both PutAnomalyDetector and DeleteAnomalyDetector.
Why: the message is a requirement of the error class. A client that matches CloudWatch's wording to decide which parameter to drop, and anyone reading the text, sees a sentence AWS never emits; the reversed list also mis-states which identification source AWS considers primary.
Fix: the shared anomaly-detector identification validation used by both handlers (the construction of the <sources> list in the InvalidParameterCombination message) — enumerate the detected sources in the model's declaration order.
Traces: cloudwatch.delete-anomaly-detector-invalid-parameter-combination-rejected, cloudwatch.invalid-parameter-combination-family, cloudwatch.op-contract-putAnomalyDetector, cloudwatch.put-anomaly-detector-conflicting-identification-params.

Cause 3 of 7: GetDashboard's malformed-DashboardName refusal reports only the first failing constraint instead of every one.
AWS: GetDashboard models InvalidParameterValueException (client, httpError 400, awsQueryError InvalidParameterValue / 400), documented "The value of an input parameter is bad or out-of-range." A valid dashboard name contains only alphanumerics, dash and underscore and is at most 255 characters; the model puts no pattern or length constraint on GetDashboardInput$DashboardName, so a malformed name reaches the service. AWS accumulates EVERY field violation into one message, each sentence terminated by a newline. For a name that violates both the character set and the length bound the message is "The value for field DashboardName contains invalid characters. It can only contain alphanumerics, dash (-) and underscore (_).\nThe value for field DashboardName is too long. It must have length less than or equal to 255.\n". Both sentences and their trailing newlines are fixed text; the variable parts are the field name (DashboardName) and the length bound (255).
Emulator: it emits only the first sentence — "The value for field DashboardName contains invalid characters. It can only contain alphanumerics, dash (-) and underscore (_).\n" — and stops validating.
Why: a client that fixes the reported problem is rejected again for a violation AWS already reported in the same response. Validation becomes an iterative guessing game instead of one complete answer, and any client asserting on the full message text fails.
Fix: GetDashboard's DashboardName validation / its InvalidParameterValue message construction — collect all violations for the field and concatenate their sentences, rather than returning on the first failure.
Traces: cloudwatch.get-dashboard-invalid-parameter-value-rejected.

Cause 4 of 7: GetMetricStatistics rejects a sub-60, non-high-resolution Period with the wrong message.
AWS: GetMetricStatistics models Period as required (target Period, range min 1) and declares InvalidParameterValueException (client, 400, awsQueryError InvalidParameterValue / 400). A Period that is neither one of the high-resolution values nor a multiple of 60 (e.g. 45) is refused with HTTP 400, Error.Code InvalidParameterValue and the fixed message "The parameter Period must be a value in the set [1, 5, 10, 20, 30]." — the sentence, including the bracketed set, is fixed text with no variable part; AWS answers with the legal high-resolution set rather than restating the multiple-of-60 rule.
Emulator: the status and Error.Code are correct, but the message is "The parameter Period must be a multiple of 60." — an emulator-authored sentence that names a different rule and omits the set of legal values.
Why: the message is the only thing telling the caller which Periods are acceptable. A client told "must be a multiple of 60" will not discover that 1/5/10/20/30 are valid, and any client matching CloudWatch's wording breaks. This is a different operation and a different sentence from the PutMetricAlarm Period message already filed as Cause 5 of the open issue 20261109T183935Z-cloudwatch-6-net-new-causes-in-the-control.md; that issue does not carry these checks' replay keys, so this cause is net-new.
Fix: GetMetricStatistics' Period validation message construction (the branch that handles Period < 60 / non-multiple-of-60 values).
Traces: cloudwatch.get-metric-statistics-conflicting-statistics-rejected, cloudwatch.invalid-parameter-value-family, cloudwatch.period-rollup-query-alignment.

Cause 5 of 7: DescribeAnomalyDetectors' InvalidNextToken message is an emulator-authored sentence that drops both of AWS's variable parts.
AWS: DescribeAnomalyDetectors is @paginated (inputToken/outputToken NextToken) and models InvalidNextToken (client, httpError 400, awsQueryError InvalidNextToken / 400), documented "The next token specified is invalid." Its message template is "nextToken = <token>, accountId = <account>." — the fixed text is "nextToken = ", ", accountId = " and the terminal period; the variable parts are the rejected NextToken value taken from the request and the caller's 12-digit account id. CloudWatch's other paginated operations each have their OWN fixed text for the same error class, which the same check also exercises and which the emulator answers correctly: DescribeAlarmHistory and DescribeAlarmContributors use "Invalid NextToken : <token>", DescribeInsightRules and ListManagedInsightRules use "INVALID_TOKEN: Invalid token.", ListMetricStreams uses "Invalid NextToken", GetMetricData uses an empty message, and DescribeAlarms / ListAlarmMuteRules do not validate the token at all.
Emulator: DescribeAnomalyDetectors answers Error.Code InvalidNextToken with the message "NextToken is not a token this service issued" — a single emulator-authored clause, with neither the rejected token nor the account id, and no terminal period.
Why: the message is a requirement of the error class, and AWS's variable parts are what make it actionable — the caller cannot see which token was rejected or under which account it was evaluated. Clients that log or match the refusal text diverge from AWS on this one operation while agreeing on its six siblings.
Fix: DescribeAnomalyDetectors' pagination-token validation (its InvalidNextToken message construction) — emit AWS's per-operation template with the request's token and the caller's account id interpolated.
Traces: cloudwatch.invalid-next-token-family.

Cause 6 of 7: PutInsightRule's refusal of an unparsable RuleDefinition reports a missing key instead of the parse failure.
AWS: PutInsightRule models RuleDefinition as required (target InsightRuleDefinition, @length min 1 max 8192, pattern ^[\x00-\x7F]+$) and declares InvalidParameterValueException (client, 400, awsQueryError InvalidParameterValue / 400). A RuleDefinition of "{}" — syntactically valid JSON but not a Contributor Insights rule body — is refused with HTTP 400, Error.Code InvalidParameterValue and the fixed message "INVALID_RULE_BODY: The RuleBody could not be parsed." The whole sentence, including the INVALID_RULE_BODY prefix, is fixed text with no variable part.
Emulator: it answers the right status and code but the message "INVALID_RULE_BODY: MissingKey encountered at Schema in the RuleBody." — the same prefix followed by an emulator-authored detail that names a specific absent key (Schema) where AWS reports the body as unparsable.
Why: the message is a requirement of the error class. A client matching CloudWatch's wording fails, and the substituted detail mis-describes the failure: it implies the body parsed and one key was missing, inviting the caller to add that key rather than supply a rule body.
Fix: PutInsightRule's RuleDefinition validation message construction — a body that is not a parseable rule definition must produce AWS's fixed INVALID_RULE_BODY sentence, not a per-key diagnostic.
Traces: cloudwatch.missing-required-parameter-family.

Cause 7 of 7: PutMetricAlarm's LimitExceeded refusal uses the Smithy error shape's documentation string as its wire message instead of AWS's quota message.
AWS: PutMetricAlarm declares LimitExceededFault (errorKind client, httpError 400, awsQueryError code LimitExceeded / 400). The shape's documentation sentence is "The quota for alarms for this customer has already been reached." — that is the model's prose description of the error shape, not the message AWS puts on the wire. When a PutMetricAlarm creating a Metrics Insights query alarm (a Metrics entry whose Expression is a SELECT ... query) would exceed the account's fixed, non-adjustable quota of Metrics Insights alarms per account per Region, AWS refuses with HTTP 400, Error.Code LimitExceeded and the message "The maximum limit of <quota> metrics insights alarms would be exceeded." — fixed text whose only variable part is the quota value (200 for this quota) — and creates no alarm.
Emulator: the quota IS enforced and the code is correct (LimitExceeded), but the Message is "The quota for alarms for this customer has already been reached.", i.e. the LimitExceededFault shape's documentation reused verbatim as the runtime message. It names no quota, no quota value and not the quota class that was hit.
Why: the message is a requirement of the error class, and here it is also the only thing identifying WHICH quota was exhausted — CloudWatch has a 5,000 metric+composite alarm quota and a separate 200 Metrics Insights alarm quota that share this error code. A client cannot tell which limit to raise or which alarm class to prune, and any client matching AWS's wording breaks. Reusing a shape's doc string as a message will reproduce this divergence for every error shape serialized the same way.
Fix: PutMetricAlarm's Metrics-Insights-alarm quota enforcement / its LimitExceeded message construction — emit AWS's sentence with the account's quota interpolated, and never fall back to the modelled shape's documentation as the message.
Traces: cloudwatch.put-metric-alarm-limit-exceeded-enforced.
