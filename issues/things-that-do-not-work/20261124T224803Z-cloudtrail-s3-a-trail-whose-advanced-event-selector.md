# cloudtrail__s3: a trail whose advanced event selector scopes S3 object data events with resources.ARN StartsWith/NotStartsWith delivers no data-event log file at all, so neither the included nor the excluded prefix is observable

> _Note: this issue was identified against the code base at commit `2529a01341a5048631af6b5932130400389c11d0`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
PutEventSelectors

## Description
ONE net-new root cause in this issue; it must be closed before submitting.

Cause 1 of 1: a trail that accepts and echoes an advanced event selector for the S3 object data-event class (eventCategory=Data / resources.type=AWS::S3::Object / resources.ARN with StartsWith=[arn:aws:s3:::<bucket>/] and NotStartsWith=[arn:aws:s3:::<bucket>/<excluded-prefix>/]) and is then started with StartLogging never writes a single gzipped log file into its configured S3 bucket under its S3KeyPrefix, so no PutObject/GetObject data event is ever delivered for either the included or the excluded key prefix. The scoping semantics the selector exists to express — deliver object data events outside the excluded ARN prefix, withhold every one under it — are therefore not observable at all, and neither is the control trail's (StartsWith only) full capture of the same calls. Failing check: cloudtrail__s3.obs-s3-2-arn-prefix-exclusion-withholds-object-data-events.

AWS: PutEventSelectors takes TrailName (required) plus EventSelectors / AdvancedEventSelectors and echoes TrailARN + the stored selectors (Smithy, cloudtrail: PutEventSelectors input TrailName (required) / EventSelectors / AdvancedEventSelectors, output TrailARN / EventSelectors / AdvancedEventSelectors; errors InvalidEventSelectorsException 400, InvalidTrailNameException 400, TrailNotFoundException 404, UnsupportedOperationException 400, ConflictException 409). Smithy: AdvancedEventSelector.FieldSelectors is required, and AdvancedFieldSelector carries Field (required) plus the operator lists Equals / StartsWith / EndsWith / NotEquals / NotStartsWith / NotEndsWith — its own documentation states selectors do not support wildcards and that StartsWith / EndsWith / NotStartsWith / NotEndsWith are the way to match the beginning or end of an event field, so NotStartsWith on resources.ARN is a modelled exclusion operator, not a no-op. StartLogging has an empty output (Smithy: StartLogging input Name required, output {}), and GetTrailStatus then reports IsLogging plus LatestDeliveryTime / LatestDeliveryError / LatestDeliveryAttemptTime / LatestDeliveryAttemptSucceeded, i.e. the members that describe log-file delivery (Smithy: GetTrailStatus output). What the selector then CAUSES is recorded behavior only, as the check's reference states (https://docs.aws.amazon.com/awscloudtrail/latest/userguide/filtering-data-events.html): a logging trail writes gzipped objects named *.json.gz under <S3KeyPrefix>/AWSLogs/<account-id>/CloudTrail/<region>/YYYY/MM/DD/, whose body is a JSON object with a Records list; each S3 object-level call matching the selector appears there as one record with eventSource "s3.amazonaws.com", eventName "PutObject" or "GetObject", eventCategory "Data", requestParameters.bucketName == the data bucket and requestParameters.key == the object key, and a resources entry {type: "AWS::S3::Object", ARN: "arn:aws:s3:::<bucket>/<key>"}. On the trail whose resources.ARN selector carries NotStartsWith, NO record is delivered for any key under the excluded prefix, while records for keys outside it (including one written after them) ARE delivered; on a control trail with StartsWith only and no NotStartsWith, records for BOTH prefixes are delivered. Those literals (the event source, the event names, "Data", the resource type "AWS::S3::Object", the arn:aws:s3:::<bucket>/<key> object-ARN form and the <prefix>/AWSLogs/<account-id>/CloudTrail/<region>/YYYY/MM/DD/ key layout) are the requirement; the per-run bucket names, object keys, account id, region, event ids and timestamps that fill them are not.

Emulator: the whole setup leg is accepted — two buckets with the CloudTrail bucket policy, CreateTrail for the excluding trail (S3KeyPrefix "excl") and the control trail (S3KeyPrefix "ctrl"), PutEventSelectors for each, GetEventSelectors echoing the submitted FieldSelectors unchanged (that per-field comparison runs before any wait and did not fire), StartLogging, and GetTrailStatus reporting IsLogging true (that assertion also did not fire). The S3 data-plane calls then genuinely succeed: every PutObject is accepted and every GetObject returns the exact payload (those byte-comparison assertions precede the delivery loop and did not fire). After that nothing is ever written: the check re-issues a fresh round of PutObject included/, GetObject included/, PutObject excluded/, GetObject excluded/ and a later barrier PutObject every 30 s and re-lists <prefix>/AWSLogs/ after every 2 s poll, and it is still inside that delivery loop when the harness cap ends the run — verdict 'mismatch' with "Check timed out after 60.0s". No record-shape assertion, no control-trail object-ARN assertion and no excluded/-withheld assertion is ever reached. Hypothesis (stated by neither the model nor the replay): the emulator has no trail log-file delivery writer and no advanced-event-selector evaluator, so the gap is not specific to the S3 object data class or to the NotStartsWith operator.

Why: a client that configures the advanced event selector AWS publishes for scoping S3 object data events gets a trail that looks completely healthy — the selector is echoed back field-for-field and GetTrailStatus says IsLogging true — and an S3 log prefix that stays permanently empty. Every detective control built on object-level data events reads nothing: SIEM/Athena ingestion of the log prefix, incident reconstruction of who read or wrote which object, and above all the cost/compliance control that the NotStartsWith exclusion is bought for. Because nothing is delivered, a client cannot distinguish "the exclusion is working" from "no data events are recorded at all", so a wrongly scoped selector that leaks sensitive-prefix reads in real AWS passes silently against the emulator, and a correctly scoped one cannot be proved.

Fix: CloudTrail's trail log-file delivery path and its advanced-event-selector evaluator (the trail logging state machine plus the S3 writer it feeds), together with the S3 object handlers' hook into that seam: a logging trail must evaluate its stored AdvancedEventSelectors against each served call — the Data category matched on eventCategory, resources.type and resources.ARN, with the StartsWith / NotStartsWith operators applied to the object ARN — and write the matching records as gzipped JSON objects into the configured bucket under <S3KeyPrefix>/AWSLogs/<account-id>/CloudTrail/<region>/YYYY/MM/DD/, each populated with eventSource, eventName, eventCategory "Data", requestParameters.bucketName / requestParameters.key and the AWS::S3::Object resources entry; GetTrailStatus's LatestDelivery* members must then reflect that delivery. Neighbouring OPEN issues, named because they do not carry this failure's replay key and do not cover it: 20261107T051039Z-cloudtrail-lambda-s3-a-trail-whose-advanced-event.md (the Lambda AWS::Lambda::Function data class), 20261124T165729Z-cloudtrail-cognito-identity-an-advanced-event-selector-naming.md (the AWS::Cognito::IdentityPool data class), 20261029T173328Z-cloudtrail-records-and-delivers-no-audit-record-for.md and 20261031T171713Z-cloudtrail-audit-records-are-attributed-to-the-ambient.md (management-event recording and attribution).
