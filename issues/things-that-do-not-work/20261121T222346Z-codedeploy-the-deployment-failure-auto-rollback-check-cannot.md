# CodeDeploy: the DEPLOYMENT_FAILURE auto-rollback check cannot start — a running EC2 instance never becomes an Online SSM managed node, so no Server-platform rollback is ever exercised (1 cause)

> _Note: this issue was identified against the code base at commit `02547b2f84faa16ea751ab52ba7acd12fdf2e9dd`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
CreateDeployment

## Description
Cause 1 of 1: codedeploy.auto-rollback-on-deployment-failure-reinstalls-the-prior-artifact — the only behavioral check that grades an automatic DEPLOYMENT_FAILURE rollback as an OBSERVABLE effect on a Server-platform (EC2) host — makes no progress and is cut off by the harness cap ("Error: Check timed out after 60.0s", no assertion diagnostic, no frame). The check creates a VPC/public subnet, an SSM-capable instance profile with read on a revision bucket, uploads two S3 zip revisions (A validating, B failing ValidateService), launches one tagged t3.micro with user-data that installs the codedeploy-agent, and then blocks in its fleet-readiness gate `_wait_fleet_ready`: it polls ssm:DescribeInstanceInformation(Filters=[{Key:'InstanceIds',Values:[<id>]}]) for PingStatus 'Online' on a 600 s budget, then runs `systemctl is-active codedeploy-agent` through ssm:SendCommand/GetCommandInvocation. Because the readiness list stays empty, the gate spins instead of failing fast, and everything the check actually grades is never reached: CreateApplication/CreateDeploymentGroup with autoRollbackConfiguration, the revision-A positive control, the failing revision-B deployment, GetDeployment's rollbackInfo, the rollback deployment's creator and status, and the bytes on the host.

AWS: a running EC2 instance whose instance profile grants SSM managed-node permissions (AmazonSSMManagedInstanceCore) registers as a Systems Manager managed node within a minute or two; ssm:DescribeInstanceInformation then returns one InstanceInformation entry for that instance id with PingStatus 'Online' (documented as the "Connection status of SSM Agent"), and SendCommand/GetCommandInvocation run in-guest commands on it — an invocation leaves Pending/InProgress and reaches Status 'Success' with StandardOutputContent. On such a host CodeDeploy's Server compute platform then behaves as modelled (codedeploy Smithy): a deployment group may carry AutoRollbackConfiguration{enabled, events} with AutoRollbackEvent 'DEPLOYMENT_FAILURE' ("The event type or types that trigger a rollback"); when a deployment fails its ValidateService hook the service creates a SEPARATE rollback deployment, GetDeployment on the failed deployment reports RollbackInfo.rollbackDeploymentId ("The ID of the deployment rollback") pointing at it, GetDeployment on the rollback reports RollbackInfo.rollbackTriggeringDeploymentId ("The deployment ID of the deployment that was underway and triggered a rollback deployment because it failed or was stopped") pointing back at the failed deployment, and the rollback's DeploymentInfo.creator is DeploymentCreator 'codeDeployRollback' (not 'user'), its revision the last revision that succeeded, its status 'Succeeded', and its instance target's Install lifecycle event 'Succeeded' — i.e. the prior artifact's bytes are back in the deployed file on the host.

Emulator: the launched instance is never cross-registered as an SSM managed node — DescribeInstanceInformation's InstanceInformationList never contains the id, so no PingStatus is ever reported and no in-guest command plane exists for that host. The check is cut off inside that poll at the 60 s cap having issued no CodeDeploy operation under test, so the auto-rollback behaviour is entirely ungraded. Hypothesis: a RunInstances-created instance is modelled only in EC2 state and never projected into the SSM managed-node inventory backing DescribeInstanceInformation/SendCommand, so the Server-platform deployment path has no reachable host and the rollback's host-visible effect is unreachable.

Related open issues that do NOT cover this check (the replay report did not mark it owned by any of them, so its replay key is not carried by any): 20261114T202732Z-codedeploy-the-alarm-gating-check-on-the-server.md, 20261115T031454Z-codedeploy-the-server-platform-host-readiness-gate-still.md, 20261115T085328Z-codedeploy-the-server-platform-appspec-hook-check-cannot.md and 20261116T030341Z-codedeploy-the-minimumhealthyhosts-concurrency-check-still-cannot-start.md report the same family of host-readiness failures for OTHER Server-platform checks; 20261120T163729Z-codedeploy-server-platform-deployments-never-resolve-ec2tagfilters-to.md covers tag-filter target resolution, not the rollback record or the restored artifact. This check must be re-replayed on its own to confirm a fix.

Why: a client cannot observe automatic rollback at all on this emulator. The whole point of autoRollbackConfiguration with DEPLOYMENT_FAILURE is that a failed deployment is followed by a service-created rollback that puts the last good revision back on the host; here neither the rollback record nor its host effect can be reached, and the blocking symptom is a silently empty readiness list rather than an error, so a client's own readiness poll hangs to its own deadline instead of failing with a diagnosable response.

Fix: the EC2 instance lifecycle must cross-register a running instance into the SSM managed-node state behind DescribeInstanceInformation (an entry with PingStatus 'Online' shortly after the instance reaches 'running'), and the SSM in-guest command plane (SendCommand/GetCommandInvocation) must drive invocations on that node to a terminal Status instead of leaving them Pending. On the CodeDeploy side, the Server-platform deployment execution path — the instance-target lifecycle driver and the auto-rollback trigger in the deployment state — must, on a hook failure in a group whose autoRollbackConfiguration names DEPLOYMENT_FAILURE, create a distinct rollback deployment with creator 'codeDeployRollback', cross-link it through rollbackInfo on both deployments, re-deploy the last successful revision and report its Install lifecycle event.

Traces: codedeploy.auto-rollback-on-deployment-failure-reinstalls-the-prior-artifact (timed out inside `_wait_fleet_ready`, before any CodeDeploy operation under test is graded).

## Evidence
Expected (AWS): after ec2:RunInstances of one tagged t3.micro with an SSM-capable instance profile, ssm:DescribeInstanceInformation(Filters=[{Key:'InstanceIds',Values:[<the id>]}]) returns an InstanceInformation for it with PingStatus 'Online', and ssm:SendCommand(AWS-RunShellScript, 'systemctl is-active codedeploy-agent') yields an invocation that reaches Status 'Success' with StandardOutputContent 'active'. Then: revision A deploys 'Succeeded' and /opt/sim2real/payload.txt holds A's marker; revision B (ValidateService exits 1) installs — Install 'Succeeded', B's marker on disk — and the deployment ends 'Failed' with ValidateService 'Failed'; GetDeployment(B).deploymentInfo.rollbackInfo.rollbackDeploymentId names a DISTINCT deployment; that rollback deployment reports creator 'codeDeployRollback', rollbackInfo.rollbackTriggeringDeploymentId == B, status 'Succeeded', revision.s3Location.eTag equal to revision A's, Install 'Succeeded', and the file on the host reads A's marker again.

Actual (emulator): 'Error: Check timed out after 60.0s' with no assertion diagnostic — the run is cut off inside the fleet-readiness gate. InstanceInformationList never contains the launched instance id, so PingStatus is never reported, the `systemctl is-active codedeploy-agent` leg is never reached, and no CodeDeploy operation under test (CreateDeploymentGroup/CreateDeployment/GetDeployment/ListDeploymentTargets/GetDeploymentTarget) is ever issued; rollbackInfo, the rollback's creator and the restored artifact are never produced. Instance ids, bucket names, marker strings and per-run timings are per-run values and are not part of the requirement; the requirement is that a running instance becomes an Online managed node at all, that in-guest commands complete on it, and that a DEPLOYMENT_FAILURE auto-rollback creates a distinct 'codeDeployRollback' deployment that re-installs the last successful revision on the host.

## Steps to Reproduce
1. Create a VPC with a public subnet, internet gateway and route; create an IAM role with AmazonSSMManagedInstanceCore plus s3:GetObject/ListBucket on a revision bucket, and an instance profile holding it.
2. Upload two zip revisions to S3: A whose appspec.yml installs payload.txt to /opt/sim2real with a ValidateService hook exiting 0, and B identical except its ValidateService script exits 1 after waiting for a release file.
3. ec2:RunInstances one t3.micro in that subnet with the instance profile, user-data installing the codedeploy-agent, and a tag the deployment group filters on (KEY_AND_VALUE); wait for state 'running'.
4. Poll ssm:DescribeInstanceInformation(Filters=[{Key:'InstanceIds',Values:[<the id>]}]) — observe InstanceInformationList stays empty indefinitely, so PingStatus 'Online' is never reported and the readiness gate never returns (the check is cut off at the 60 s harness cap).
5. (Blocked by step 4, and what the check grades) codedeploy:CreateApplication(computePlatform='Server'); CreateDeploymentGroup with ec2TagFilters for the tag, deploymentConfigName='CodeDeployDefault.AllAtOnce' and autoRollbackConfiguration={enabled:true, events:['DEPLOYMENT_FAILURE']}; CreateDeployment revision A and wait 'Succeeded'; CreateDeployment revision B, release its hold, and wait for 'Failed'; then GetDeployment(B) for rollbackInfo.rollbackDeploymentId, GetDeployment(<rollback>) for creator 'codeDeployRollback', rollbackTriggeringDeploymentId == B, status 'Succeeded' and revision A's eTag, GetDeploymentTarget for the rollback's Install event, and read /opt/sim2real/payload.txt back through SSM expecting revision A's marker.
