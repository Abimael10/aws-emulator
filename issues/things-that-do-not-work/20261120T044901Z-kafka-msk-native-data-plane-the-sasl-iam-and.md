# MSK native data plane: the SASL/IAM and public SASL/SCRAM bring-up never completes in a client-sized budget, and the broker's ApiVersions omits AddPartitionsToTxn so no transaction can be committed (3 causes)

> _Note: this issue was identified against the code base at commit `affa1bfa12dd63e88a970dbf7c95dba619b96dc2`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

GetBootstrapBrokers

## Description
THREE net-new root causes on the emulated kafka (MSK) surface, each grounded in a failing behavioral check the suite lists under `### kafka` that is marked neither ALREADY FILED nor OWNED by an open issue. Related open issues name the same family for OTHER check ids and carry none of these replay keys: 20261116T210722Z-kafka-msk-native-data-plane-sasl-iam-bring-up.md, 20261117T031317Z-kafka-msk-native-sasl-iam-data-plane-five-more.md, 20261118T164608Z-kafka-msk-native-data-plane-the-transactional-abort-isolation.md, 20261116T122712Z-kafka-msk-end-to-end-cluster-topic-scram-produce.md and 20261114T205343Z-kafka-msk-data-plane-and-lifecycle-bootstrap-string-carries.md (whose data-plane cause is the missing CreateTopics api key 19, a different Kafka api key from the one in Cause 3 here).

=== Cause 1 of 3: the SASL/IAM native bring-up barrier does not complete, so consumer-group behavior over the Kafka protocol is unmeasurable ===
AWS: CreateClusterV2 (Smithy: POST /api/v2/clusters, input member Provisioned -> ProvisionedRequest / Serverless -> ServerlessRequest, output member State -> ClusterState) answers State CREATING and the cluster settles to ACTIVE, observable through DescribeClusterV2 (Smithy: GET /api/v2/clusters/{ClusterArn}, output ClusterInfo -> Cluster). GetBootstrapBrokers (Smithy: GET /v1/clusters/{ClusterArn}/bootstrap-brokers, output member BootstrapBrokerStringSaslIam, jsonName bootstrapBrokerStringSaslIam, target __string) then publishes a comma-separated host:port list, and a client inside the cluster's VPC completes a SASL_SSL / AWS_MSK_IAM handshake on tcp/9098 and is served ApiVersions, Metadata, FindCoordinator, JoinGroup, SyncGroup, Heartbeat, OffsetCommit, OffsetFetch, Produce and Fetch. The Kafka wire protocol itself is not in the Smithy model, so the data-plane half is recorded behavior plus the Apache Kafka group protocol: committed offsets survive a rebalance and no already-committed record is redelivered to the group, and the group resource's IAM actions are enforced per group name (kafka-cluster:DescribeGroup governs FindCoordinator/OffsetFetch, kafka-cluster:AlterGroup governs JoinGroup/SyncGroup/Heartbeat, a denied join is refused with GROUP_AUTHORIZATION_FAILED, Kafka error 30, while an assign()-only read of an authorized topic succeeds).
Emulator: both checks produce the verdict `mismatch` with the single detail `Error: Check timed out after 60.0s`. No HTTP status, no Kafka protocol error, no stack frame and not one assertion evaluated — the shared bring-up path the emulator owns (cluster CREATING -> ACTIVE on DescribeClusterV2, then an endpoint announced by GetBootstrapBrokers that both accepts TCP and completes the AWS_MSK_IAM handshake) does not finish inside the budget. Because the emulator owns those lifecycle transitions and announces those endpoints, the stall is the emulator's, not the runner's.
Why: a client that provisions an MSK cluster and connects an AWS_MSK_IAM consumer group blocks until its own timeout instead of receiving a rebalance, an offset or an error. Exactly-once-ish consumer code (offset durability across a rebalance) and every IAM group-scope authorization decision are unverifiable against the emulator, so applications validated here are validated against nothing.
Fix: the kafka crate's cluster-lifecycle state machine (CreateClusterV2/DescribeClusterV2 must settle to ACTIVE promptly so a first poll after the create observes the terminal state) and the native broker plane reached through every address GetBootstrapBrokers advertises — it must accept connections, complete the SASL/IAM handshake, and implement the group coordinator (FindCoordinator, JoinGroup, SyncGroup, Heartbeat, OffsetCommit/OffsetFetch) with per-group IAM authorization that answers GROUP_AUTHORIZATION_FAILED (30) rather than leaving the client hanging.
Traces: kafka.kafka-consumer-group-offsets-survive-a-rebalance-and-no-record-is-redelivered, kafka.msk-iam-group-scope-denies-a-consumer-group-join-while-an-assigned-read-succeeds.

=== Cause 2 of 3: the public SASL/SCRAM provisioned bring-up does not complete, so per-partition FIFO ordering is unmeasurable ===
AWS: a provisioned cluster created with ClientAuthentication.Sasl.Scram enabled reaches ACTIVE, UpdateConnectivity with PublicAccess.Type SERVICE_PROVIDED_EIPS returns the cluster to ACTIVE, GetBootstrapBrokers then publishes BootstrapBrokerStringPublicSaslScram (jsonName bootstrapBrokerStringPublicSaslScram), and CreateTopic (Smithy: POST /v1/clusters/{ClusterArn}/topics, required members TopicName, PartitionCount -> __integerMin1, ReplicationFactor -> __integerMin1; output Status -> TopicState) reaches ACTIVE via DescribeTopic. A SASL_SSL/SCRAM-SHA-512 producer then appends N records to a single-partition topic and a consumer reads them back in exactly the produced order — the per-partition FIFO guarantee of the Kafka protocol (recorded behavior; the protocol is outside the Smithy model).
Emulator: verdict `mismatch`, single detail `Error: Check timed out after 60.0s`. Nothing is asserted: the chain CreateClusterV2 -> ACTIVE -> AssociateScramSecret -> UpdateConnectivity -> ACTIVE -> CreateTopic -> ACTIVE -> a public SASL/SCRAM endpoint that accepts and serves metadata never completes in the budget.
Why: a client doing a plain ordered produce/consume over SASL/SCRAM against the emulator hangs, so the most basic data-plane guarantee it depends on (FIFO per partition) cannot be observed at all.
Fix: the kafka crate's provisioned-cluster lifecycle (create/UpdateConnectivity/topic-create transitions must settle promptly on the write path) and the SASL/SCRAM listener behind the public bootstrap string the emulator advertises, which must accept and serve Produce/Fetch in per-partition offset order.
Traces: kafka.topic-partition-message-ordering-preserved.

=== Cause 3 of 3: the emulated broker advertises no AddPartitionsToTxn (Kafka api key 24), so a transactional producer cannot commit or abort ===
AWS: an MSK broker running the requested KafkaVersion (here 3.9.x) answers ApiVersions with the full set of api keys that version supports, including InitProducerId (22), AddPartitionsToTxn (24), AddOffsetsToTxn (25), EndTxn (26) and WriteTxnMarkers, so a kafka-python/Java producer with transactional_id set can run init_transactions -> begin_transaction -> send -> commit_transaction / abort_transaction. Committed records are visible to a read_committed consumer, aborted ones are not, and each commit or abort control batch physically occupies one offset (recorded behavior plus the Apache Kafka transaction protocol; the wire protocol is outside the Smithy model, which models only the control plane).
Emulator: verdict `error`. The transactional producer fails inside kafka-python's transaction manager with, verbatim: `kafka.errors.KafkaError: KafkaError: Cannot execute transactional method because we are in an error state: [Error 35] IncompatibleBrokerVersion: Kafka broker does not support the 'AddPartitionsToTxnRequest' Kafka protocol.` (frames: transaction_manager.py begin_commit -> _maybe_fail_with_error). The fixed text here is the client's own classification of a missing api key; the requirement is that the broker's ApiVersions response ADVERTISE AddPartitionsToTxn (api key 24) and the rest of the transaction api keys, and implement them. Note this check cleared SASL/IAM bring-up, codecs/headers/timestamps, offsets_for_times, seeks, OFFSET_OUT_OF_RANGE, the idempotent producer and CreatePartitions growth, so the only divergence it reached is the transaction surface.
Why: a client doing exactly-once processing (transactional producer, read_committed consumer) is refused by its own client library before a single request is sent, with an IncompatibleBrokerVersion error that misleads the developer into thinking their cluster is on an older Kafka version than the one they asked MSK for. All transactional and read_committed/read_uncommitted isolation behavior is unreachable.
Fix: the native broker plane in the kafka crate — its ApiVersions handler's advertised api-key/version ranges, and the transaction coordinator behind them (InitProducerId, AddPartitionsToTxn, AddOffsetsToTxn, EndTxn with COMMIT/ABORT control batches that occupy an offset, and isolation-level-aware Fetch/ListOffsets).
Traces: kafka.kafka-native-codecs-headers-timestamps-partition-growth-transactions-and-seeks.
