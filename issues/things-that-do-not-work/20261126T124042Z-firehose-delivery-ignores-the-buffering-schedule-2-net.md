# firehose: delivery ignores the buffering schedule — 2 net-new causes: BufferingHints.IntervalInSeconds is not honoured for S3 destinations (records land on PutRecord), and a destination's default buffer interval is skipped before the first delivery attempt so failed-event S3 backups appear immediately

> _Note: this issue was identified against the code base at commit `f7078ec9d24b4839050651ec5b14c25693a01eca`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
PutRecord

## Description
The emulator's Firehose delivery engine writes buffered data to the destination synchronously with (or within a couple of seconds of) PutRecord, instead of holding it for the stream's buffering window. Two distinct causes, both in the delivery/flush scheduler rather than in any single API handler.

Cause 1 of 2: BufferingHints.IntervalInSeconds is not honoured for an S3 (ExtendedS3) destination.
AWS: Smithy: firehose#BufferingHints has SizeInMBs @range min 1 max 128 (default 5) and IntervalInSeconds @range min 0 max 900 (default 300); the shape doc says data is buffered 'for the specified period of time, in seconds, before delivering it to the destination'. Delivery is therefore triggered by whichever of the two thresholds is crossed FIRST. With SizeInMBs pinned at or near its maximum (64/128 MiB) and a payload of a few bytes, the size threshold can never be crossed, so the interval timer is the only trigger available and no object may exist in the destination bucket before roughly IntervalInSeconds after the put. The hints are explicitly hints as to the exact flush instant (the model says Firehose 'might choose to use different values when it is optimal'), but a flush at a small fraction of the configured interval — with a single tiny record and no size pressure — is not an optimisation of the hint, it is the absence of a buffer. There is no flush/commit API in the Firehose model, so the service's own schedule is the only thing that can produce the object.
Emulator: the record is visible in S3 within seconds of PutRecord, long before the interval elapses. Observed: with IntervalInSeconds=60/SizeInMBs=128 an object appears at t≈0–20 s (checks buffering-hint-interval-delays-delivery, buffering-hints-delay-controls-delivery-timing at t=20.0 s, s3-delivery-triggered-by-buffer-interval-timeout); with IntervalInSeconds=120/SizeInMBs=128 an object appears at t=18 s (buffering-hints-delay-delivery-to-s3); with IntervalInSeconds=60/SizeInMBs=1 all ten tiny records are readable in S3 inside the first 40 s (server-side-managed-flush-without-explicit-trigger). The delivered CONTENT is correct in each case — only the timing diverges — so the defect is the scheduler, not the writer or the key layout. The object key's embedded timestamp matches the put time, confirming the write happens at ingest rather than at a scheduled flush.
Why: a client cannot distinguish a buffered delivery stream from a synchronous per-record writer. Code and tests that assert the documented buffering contract — 'no object before the interval', object counts/sizes implied by aggregation over the window, one object per buffer rather than one per record, and any downstream consumer tuned for the aggregate object granularity — all behave differently against the emulator than against AWS. Cost and partition-count reasoning built on buffering is also invalidated, and a consumer that reads each delivered object expecting many aggregated records sees single-record objects.
Fix: the delivery-stream flush scheduler for the S3/ExtendedS3 destination: PutRecord/PutRecordBatch must append to a per-stream in-memory buffer and the destination write must be driven by a timer at the destination's effective IntervalInSeconds (configured value, else the modeled default of 300) OR by accumulated bytes crossing the effective SizeInMBs (configured value, else 5), whichever comes first, aggregating all records buffered in that window into one object. It must not write on the ingest path.
Traces: firehose.buffering-hint-interval-delays-delivery, firehose.buffering-hints-delay-controls-delivery-timing, firehose.buffering-hints-delay-delivery-to-s3, firehose.s3-delivery-triggered-by-buffer-interval-timeout, firehose.server-side-managed-flush-without-explicit-trigger.

Cause 2 of 2: a destination's default buffer interval is skipped before the FIRST delivery attempt, so a failed-event S3 backup is written almost immediately.
AWS: Smithy: SplunkDestinationConfiguration carries RetryOptions (firehose#SplunkRetryOptions.DurationInSeconds @range min 0 max 7200, documented as the time spent on retries, which 'starts after the initial attempt to send data to Splunk fails'), HECAcknowledgmentTimeoutInSeconds and S3BackupMode FailedEventsOnly. Buffering precedes the delivery attempt: a Splunk stream created with no BufferingHints uses the destination's default buffer interval (60 s per the Firehose buffering-hints documentation) before the first attempt to the HEC endpoint is made at all. Only after that attempt fails, and after the retry duration (here 0 s, i.e. no retries) is exhausted, is the event written to the S3 backup prefix. Nothing can therefore exist in the backup bucket within the first ~30 s of the put. The backup record itself is correct in shape and the recorded errorCode class is Splunk.* — those parts are already right here; only the instant of the write diverges.
Emulator: the failed record is already present under the backup prefix within 30 s of PutRecord (key 'splunk-failed/<yyyy/mm/dd/hh>/<stream>-1-<timestamp>-<uuid>', 252 bytes), i.e. the buffer window and the attempt/retry timeline are collapsed into the ingest call. The DescribeDeliveryStream assertions on RetryOptions.DurationInSeconds, HECAcknowledgmentTimeoutInSeconds and S3BackupMode all passed, so the configuration is stored correctly and only the delivery schedule is wrong.
Why: a client that measures time-to-backup, or that relies on the retry/acknowledgment timeline to decide whether an event is still in flight versus finally failed, gets a result the real service cannot produce; an unreachable destination looks like an instant hard failure rather than one that occurs only after buffering, the first attempt and the configured retry duration.
Fix: the same delivery-stream flush scheduler, in its non-S3 destination path: buffer to the destination's effective interval (default 60 s when no BufferingHints are given) before the first attempt, then apply RetryOptions.DurationInSeconds and HECAcknowledgmentTimeoutInSeconds before routing the event to the S3 backup prefix under FailedEventsOnly.
Traces: firehose.destination-retry-duration-respected.

No open issue covers either cause: the open firehose entries concern HttpEndpointDestination requests, exception messages, GZIP ContentType, Iceberg/KFI validation, OpenSearch backup errorCode and a reserved 'aws:' tag key — all content/validation defects, none the flush schedule.

## Evidence
Cause 1 — expected: with BufferingHints {SizeInMBs: 128, IntervalInSeconds: 60} and one ~14-byte record, ListObjectsV2 on the destination bucket returns no Contents throughout the first 40 s after PutRecord, and the object appears only after the interval. Actual: 'AssertionError: record delivered before buffer interval elapsed: [{Key: 2026/11/26/12/<stream>-1-<timestamp>-<uuid>, Size: 14, ...}]' on the first probe. Same with {SizeInMBs: 64, IntervalInSeconds: 60}: 'record appeared in S3 before the 60s buffering interval elapsed (at t=20.0s)'. Same with {SizeInMBs: 128, IntervalInSeconds: 120}: 'record delivered to S3 before the 120s buffering interval elapsed (at t=18s)'. Same with {SizeInMBs: 1, IntervalInSeconds: 60} and ten tiny records: all ten markers ('auto-flush-0' .. 'auto-flush-9') readable inside 40 s — 'data delivered before the buffer interval elapsed, with no explicit trigger'. The fixed text of each assertion is the check's own; the variable parts (stream name, key date path, uuid, t= value, size) come from the request and emulator state and are not part of the requirement. Delivered bytes matched the put payload in every case, so only timing diverged.

Cause 2 — expected: for a Splunk destination with an unroutable HEC endpoint (203.0.113.7:8088, RFC 5737 TEST-NET-3), no BufferingHints, RetryOptions.DurationInSeconds=0, HECAcknowledgmentTimeoutInSeconds=180, S3BackupMode=FailedEventsOnly: ListObjectsV2 on the backup bucket returns no Contents 30 s after PutRecord; the backup object with the base64 'rawData' marker and an errorCode starting 'Splunk.' materialises later. Actual: 'AssertionError: failed record was backed up to S3 implausibly early: [{Key: splunk-failed/2026/11/26/12/<stream>-1-<timestamp>-<uuid>, Size: 252, ...}]' — present at t<30 s. DescribeDeliveryStream returned the configured RetryOptions.DurationInSeconds, HECAcknowledgmentTimeoutInSeconds and S3BackupMode correctly.

No status code or error code diverges in either cause: every API call returned 200 and the correct body; the divergence is entirely in when the destination write happens.

## Steps to Reproduce
Cause 1: (1) create an S3 bucket and a Firehose delivery role; (2) CreateDeliveryStream with an ExtendedS3/S3 destination and BufferingHints {SizeInMBs: 128, IntervalInSeconds: 60}; (3) wait for ACTIVE; (4) PutRecord with a ~15-byte payload; (5) poll ListObjectsV2 on the bucket every 5 s for the first 40 s. AWS: empty throughout. Emulator: an object with the record is already listed on the first poll. Repeat with IntervalInSeconds=120/SizeInMBs=128 (one record) and with IntervalInSeconds=60/SizeInMBs=1 (ten tiny records) for the same result.

Cause 2: (1) create an S3 bucket and a Firehose delivery role; (2) CreateDeliveryStream with a SplunkDestinationConfiguration whose HECEndpoint is https://203.0.113.7:8088/services/collector/event, no BufferingHints, RetryOptions {DurationInSeconds: 0}, HECAcknowledgmentTimeoutInSeconds 180, S3BackupMode FailedEventsOnly; (3) wait for ACTIVE; (4) PutRecord with a marker payload; (5) 30 s later call ListObjectsV2 on the backup bucket. AWS: no Contents yet. Emulator: the failed-event backup object is already there.
