# geo-routes: CalculateIsolines "at least one of" ValidationException message drops the single quotes AWS puts around field names, and CalculateRoutes falls back to the bare tag "en" instead of "en-us"

## Description
This issue bundles 2 net-new root causes in the geo-routes data plane (both under service heading `### geo-routes` in the simparity-behavioral-aws-v1 replay). A fixer must close BOTH causes before submitting.

Related already-open issues, none of which covers either cause: 20261110T072828Z-geo-routes-optimizewaypoints-validation-message-quotes-field-names.md and 20261109T081037Z-geo-routes-optimizewaypoints-validationexception-message-quotes-the-member-names-diverging.md carry the OPPOSITE direction for a DIFFERENT operation (for OptimizeWaypoints the recorded AWS message has BARE member names, so the emulator must stop quoting there); 20261114T030203Z (CalculateIsolines SnappedOrigin), 20261114T131205Z / 20261116T014451Z (CalculateRouteMatrix and OptimizeWaypoints metrics) and 20261116T014451Z (synthesized positions / SnapToRoads geometry) are about response geometry and metrics, not about either cause here. Cause 1 of 2: the CalculateIsolines "at least one of the following fields must be set" ValidationException message is emitted with UNQUOTED field names.
NOT a new defect — a previously resolved issue, 20261105T025127Z-geo-routes-calculateisolines-inapplicable-threshold-member-emitted-as-0-instead.md, named this exact message (its Cause 2 of 3) and claimed to fix it; the divergence is still present at the current commit, so that fix did not land for this message (plausibly because a shared message helper was later made to emit bare names for OptimizeWaypoints, where AWS really does emit them bare). The two operations need separate message templates, not one shared convention.
AWS: Smithy (com.amazonaws.georoutes#CalculateIsolines, POST /v2/isolines): CalculateIsolinesRequest marks only Thresholds @required; Origin and Destination are both optional members targeting Position (@length 2..2, @sensitive), so the "at least one of" rule is not expressible in the model — recorded behavior only. A CalculateIsolines request carrying neither Origin nor Destination is refused with HTTP 400 and error code ValidationException (modeled error ValidationException, errorKind client, httpError 400) and the message "At least one of the following fields must be set: 'Origin', 'Destination'." Fixed text of this message class: the literal prefix "At least one of the following fields must be set: ", each field name wrapped in ASCII single quotes, names joined by ", ", terminated by a single ".". Variable part: the list of field names, which comes from the operation's own set of mutually-alternative input members — for CalculateIsolines that set is Origin, Destination. (The names are a property of the operation's shape, not of one recording.)
Emulator: returns the correct HTTP 400 and the correct code ValidationException, but the message is "At least one of the following fields must be set: Origin, Destination." — the single quotes around each field name are missing. The check's positive control (the same request plus Origin returning exactly one isoline) was never reached because the message assertion failed first, so nothing is claimed here about the success path.
Why: the error message is part of the API contract. Clients, SDK error handling, log-based alerting and parity harnesses that match or display the exact AWS text see a string AWS never emits, so a caller cannot distinguish "you omitted a required combination of fields" from other 400s by its documented wording, and code written against real AWS text silently stops matching against the emulator.
Fix: the CalculateIsolines request-validation component in the geo-routes service crate — the template that renders the missing-alternative-members ValidationException must quote each field name for this operation (keep it independent of OptimizeWaypoints' bare-name wording rather than sharing one formatter).
Traces: geo-routes.calculate-isolines-missing-origin-and-destination-rejected.

Cause 2 of 2: when CalculateRoutes is asked for a language it does not support, the leg reports the bare language subtag "en" instead of the region-qualified fallback tag "en-us".
AWS: Smithy: CalculateRoutesRequest.Languages targets LanguageTagList (@length max 10); RouteLeg.Language targets LanguageTag (string, @length 2..35); RouteResponseNoticeCode includes MainLanguageNotFound and RouteResponseNotice defines only Code and Impact. The model does not state what tag the service falls back to, so: recorded behavior only. For a route request whose Languages list holds only the reserved/undetermined tag "qqq", real AWS still routes (Routes is non-empty), never echoes the reserved tag back, and each returned leg's Language is the service's default locale written as a region-qualified tag, "en-us" (case-insensitively), with plain-ASCII English step instructions. The requested-and-supported case is already correct in the emulator: Languages=["es-ES"] comes back with leg Language es-ES, accented Spanish instructions and no MainLanguageNotFound notice — those assertions passed.
Emulator: for Languages=["qqq"] it does route and does not echo "qqq", but the leg's Language is "en" — the bare subtag, with the region subtag dropped — where AWS reports "en-us". The replayed assertion reads: AssertionError: expected the undetermined-language tag to fall back to en-us, got 'en'. Because the run stopped there, the later assertions of that check (fallback instruction text is plain-ASCII and differs from the Spanish one, and every notice carries only Code/Impact keys) were not reached and nothing is claimed about them; they must also hold after the fix.
Why: Language is how a client learns which locale the instructions it received are actually in. A client that compares the leg's tag to the locale it wants (or uses it to pick instruction formatting, text-to-speech voice or measurement presentation) does an exact or BCP-47 region-aware comparison against the tag AWS emits; "en" is a different tag from "en-us", so the comparison fails or selects a region-neutral configuration AWS never returns, and a client cannot tell that it got the US-English fallback.
Fix: the CalculateRoutes handler's language-resolution step in the geo-routes service crate — when no requested language tag is supported, resolve to the service's region-qualified default locale tag and populate RouteLeg.Language (on every leg) with that resolved tag, rather than with a truncated primary subtag.
Traces: geo-routes.calculate-routes-unsupported-language-triggers-fallback-notice.
