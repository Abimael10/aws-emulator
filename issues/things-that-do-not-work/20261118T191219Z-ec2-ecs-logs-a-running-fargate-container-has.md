# ec2__ecs__logs: a running Fargate container has no procfs — /proc/mounts and /proc/partitions do not exist in the guest, so no filesystem or block-device state is observable from inside the task

## Description
One net-new root cause, grounded in the failing check listed under `### ec2__ecs__logs` that no ALREADY FILED / OWNED marker claims. Cause count: 1 — it must be closed before this issue is submitted.

RELATED OPEN ISSUES (neither carries this check's current replay key, so neither covers it): 20261118T053334Z-ec2-ecs-logs-2-net-new-causes-a-7de377.md names this same check and describes the symptom as "the mount section is empty: grep ' <containerPath> ' /proc/mounts yields nothing". Fixing only the volume-to-container binding described there cannot satisfy this check, because there is no /proc/mounts for the binding to appear in. 20261115T105104Z-ec2-ecs-logs-a-fargate-task-s-container.md (empty process table for `ps`) and 20261116T034914Z-ec2-ecs-logs-a-stopped-fargate-task-s.md (containers never run / no exitCode) are also distinct: here the container genuinely RUNS and its stdout reaches CloudWatch Logs — every marker the probe prints (BEGIN-MOUNT/END-MOUNT, BEGIN-PART, BEGIN-DF, READY) is delivered — so this is not a non-running container, it is a running container with no procfs.

=== Cause 1 of 1: the emulated container guest exposes no /proc, so /proc/mounts and /proc/partitions cannot be read ===
AWS: a Fargate LINUX task's container runs on a Linux kernel with procfs mounted at /proc. Reading /proc/mounts lists the container's mount table, including one row per `mountPoints[].containerPath` the task definition declares (Smithy: ecs#MountPoint.containerPath "The path on the container to mount the host volume at", ecs#MountPoint.sourceVolume), and for a RunTask-supplied managed EBS volume (Smithy: ecs#TaskManagedEBSVolumeConfiguration with required roleArn plus sizeInGiB, volumeType, filesystemType — "The Linux filesystem type for the volume … ext3, ext4, and xfs") that row's filesystem type is the requested filesystemType. /proc/partitions lists the backing block device at the requested size, and df reports just under it. Recorded behavior only for the in-guest view itself (the model describes no guest filesystem state): the guest prints a single /proc/mounts row for the containerPath with fstype ext4, the device appears in /proc/partitions at 4194304 KiB for a 4 GiB volume, and a write-then-read-back of a file under the containerPath succeeds.
Emulator: the control plane is correct — the task reaches lastStatus RUNNING, DescribeVolumes shows exactly one volume for the run's tag at the requested size and volumeType with State `in-use` and one `attached` attachment — and the container's command really executes and its output really reaches the awslogs stream. But the command's `grep ' /data ' /proc/mounts` emits `grep: /proc/mounts: No such file or directory`: /proc/mounts does not exist in the guest. The same absence applies to the sibling reads of /proc/partitions, so nothing about the guest's filesystems or block devices is observable from inside the task.
Why: a procfs is part of the Linux runtime contract every containerised workload assumes. Software that reads /proc to discover its own mounts, its block devices, its cgroup/memory limits or its process tree fails outright or mis-detects its environment against the emulator — and specifically, no client can verify that a managed EBS volume, an EFS volume, a bind mount or a readOnly mountPoint actually took effect, because the control plane reports the volume as attached while the guest cannot be asked whether it is mounted. Failures surface as a missing-file error from unrelated tooling instead of as a storage problem.
Fix: the container-guest runtime in the ECS RunTask execution path — it must present a procfs to the container (at minimum /proc/mounts reflecting the container's real mount table, including each declared mountPoints[].containerPath with the volume's filesystemType, and /proc/partitions listing the attached block devices at their real sizes) rather than a filesystem with no /proc at all. The volume-to-mount binding tracked by 20261118T053334Z-ec2-ecs-logs-2-net-new-causes-a-7de377.md is only observable once this exists.
Traces: ec2__ecs__logs.deep-ecs-1-guestdepth-ebs-volume-configured-at-launch.

The guest command is `echo BEGIN-MOUNT; grep ' /data ' /proc/mounts; echo END-MOUNT; echo BEGIN-PART; cat /proc/partitions; echo END-PART; echo BEGIN-DF; df -k /data; echo END-DF; echo <probe> > /data/probe.txt && echo WROTE=$(cat /data/probe.txt); echo READY; sleep 900`. The single line captured between BEGIN-MOUNT and END-MOUNT is grep's own error text, which is how the absence of /proc/mounts is visible: the emulator delivered the container's output to the awslogs stream (the markers and READY are all present), so the container ran and logging works — it simply has no /proc.

Assertions that passed first, which bound the divergence to the guest filesystem view: RegisterTaskDefinition retained volumes[0].configuredAtLaunch == true; RunTask with volumeConfigurations[].managedEBSVolume succeeded and DescribeTasks reached lastStatus RUNNING; DescribeVolumes filtered on the run tag returned exactly one volume with Size 4, VolumeType gp3, State 'in-use' and exactly one attachment in state 'attached'; the awslogs stream `ecs/app/<taskId>` existed and carried the guest's markers including READY.

Expected (AWS): the lines between BEGIN-MOUNT and END-MOUNT are exactly one /proc/mounts row whose second field is the request's containerPath and whose third field is the request's filesystemType; /proc/partitions names the backing device at the requested size in KiB; `df -k <containerPath>` reports just under that size; and `WROTE=<probe>` appears, proving the mount is writable. Actual (emulator): `grep: /proc/mounts: No such file or directory`, and consequently nothing parseable from /proc/partitions or df either.

`/data`, `ebs`, `ext4`, `gp3` and 4 GiB are values this request supplied; the cluster/task/volume ids, the probe token and the stream name are per-run values. The requirement is that a running LINUX container exposes /proc with a mount table and partition list describing its own filesystems.
