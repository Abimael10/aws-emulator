# ram ListPermissions catalog entries carry wrong per-entry published metadata: version, resourceType, isResourceTypeDefault and membership

> _Note: this issue was identified against the code base at commit `b98f9d0d84764ef6d14adb426ab1818e6d6e9d0e`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
ListPermissions

## Description
One net-new cause (Cause 1 of 1), in ram, grounded in a wire divergence the replay reported as neither stub-blocked (stub_path empty) nor owned by an open issue (owned_by empty). The response is a well-formed HTTP 200 whose body diverges: the AWS-managed permission library ListPermissions publishes is served from the emulator's own table, and that table's per-entry published metadata is wrong.

Cause 1 of 1 — ListPermissions reports the wrong published version, the wrong resourceType and the wrong isResourceTypeDefault flag for entries of RAM's AWS-managed permission library, and the library's membership still diverges at several permission names. Fixture ram-catalog-list-permissions, step task#1.
  AWS: ListPermissions "retrieves a list of available RAM permissions that you can use for the supported resource types" and is the only enumeration API for managed permissions (GetPermission's own doc points callers at it to find a permission ARN). Smithy (com.amazonaws.ram): ListPermissions input {resourceType, nextToken, maxResults @range 1..500, permissionType: PermissionTypeFilter}, output {permissions: ResourceSharePermissionList, nextToken}, http POST /listpermissions 200, paginated {inputToken nextToken, outputToken nextToken, pageSize maxResults}; errors InvalidNextTokenException 400, InvalidParameterException 400, OperationNotPermittedException 400, ServerInternalException 500, ServiceUnavailableException 503. Shape ResourceSharePermissionSummary members {arn, name, version (String — "The version of the permission associated with this resource share"), defaultVersion (Boolean), resourceType (String, "<service-code>:<resource-code>, case-insensitive"), status (String; PermissionStatus enumerates ATTACHABLE|UNATTACHABLE|DELETING|DELETED), creationTime, lastUpdatedTime, isResourceTypeDefault (Boolean — "whether the managed permission ... is the default managed permission for all resources of this resource type"), permissionType: PermissionType AWS_MANAGED|CUSTOMER_MANAGED, featureSet, tags}. The model enumerates no catalog CONTENT, so which permissions the library publishes, at which version, for which resource type, and which of them is its resource type's default is recorded behavior only. The recording shows that the library (a) publishes individual permissions at REVISED versions rather than all at version 1 (e.g. an AmazonDataZone domain default permission at version '10', the Network Firewall stateful-rule-group and security-group default permissions at '2', the IPAM-pool default permission at '4', several AccessGrants/SageMaker/Glue/DataZone/VpcLattice/SSM-document permissions at versions above 1); (b) spells each permission's resourceType as the owning service publishes it, which for the EventBridge v2 family is 'events:EventBusv2' (not 'events:EventBus'), for the S3 Access Grants family 's3:AccessGrants' (not 's3:AccessGrantsInstance'), and for the server-manageability permission 'ec2:DedicatedHost' (not 'ssm:ManagedInstance'); (c) marks exactly one permission per resource type as that type's default, so e.g. AWSRAMEventBridgeEventBusV2FullAccess is isResourceTypeDefault false while AWSRAMEventBridgeEventBusV2SubscribeOnly is true; and (d) publishes entries under names the emulator's table does not carry (the matcher reports a whole-entry divergence, not a member divergence, at ten ARNs including AWSRAMDefaultPermissionIpamPool, AWSRAMDefaultPermissionNetworkFirewallFirewallPolicy, AWSRAMDefaultPermissionOutpost, AWSRAMDefaultPermissionSite, AWSRAMDefaultPermissionStatefulRuleGroup, AWSRAMDefaultPermissionVpcLatticeServiceNetwork and the three AWSRAMSubordinateCACertificatePathLen{1,2,3}IssuanceCertificateAuthority entries).
  Emulator: HTTP 200 (expected 200) whose permissions list diverges on about seventy entries. Every revised permission is reported at version '1' (the table's default) — expected '10', got '1'; expected '2', got '1'; expected '4', got '1'. resourceType is reported with the emulator's own spelling — 'events:EventBus' for all four EventBridge v2 permissions, 's3:AccessGrantsInstance' for the Access Grants family, 'ssm:ManagedInstance' for the server-manageability permission, and likewise for the Mlflow and SageMaker catalog-search entries. isResourceTypeDefault is inverted on several entries (AWSRAMEventBridgeEventBusV2FullAccess expected false, got true; AWSRAMEventBridgeEventBusV2SubscribeOnly expected true, got false; the same on the AccessGrants, SageMaker-hub and ServiceCatalog AppRegistry application/attribute-group entries). At the ten ARNs above the entry itself diverges rather than one of its members.
  Why: a client enumerating the library to pick a permission ARN to hand to CreateResourceShare/AssociateResourceSharePermission reads wrong facts about every such permission. It attaches version '1' of a permission AWS publishes at version 10 or 4 (so the share is governed by a policy that does not exist), it filters by resourceType and misses or wrongly matches whole families because the type string differs from the one ListResourceTypes and the resource ARNs use ('events:EventBusv2' vs 'events:EventBus', 's3:AccessGrants' vs 's3:AccessGrantsInstance'), and code that relies on isResourceTypeDefault to learn which permission RAM attaches when a share names none picks the wrong one — on the inverted entries it picks a non-default permission believing it is the default. None of this is recoverable by retry: the read is consistent and consistently wrong.
  Fix: the AWS-managed permission catalog table the read is projected from, and the per-entry fields that table records — each entry's published version, its resource type spelled as the resource-type catalog publishes it, and its is-resource-type-default flag (exactly one true per resource type) — plus the table's membership at the names reported as whole-entry divergences. The ListPermissions handler itself only pages what the table holds, so the handler's projection needs changing only where it defaults a member instead of reading it from the entry. File and line citations are under Traces.
  Traces: wire fixture ram-catalog-list-permissions, step task#1 (ListPermissions).
