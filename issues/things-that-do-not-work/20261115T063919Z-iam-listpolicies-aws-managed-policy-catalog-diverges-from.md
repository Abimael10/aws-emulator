# iam ListPolicies AWS-managed policy catalog diverges from AWS: entries missing and per-policy metadata wrong (4 causes)

> _Note: this issue was identified against the code base at commit `051d1ca879f4768e0cde48b6e9d78ea8677353f9`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
ListPolicies

## Description
ListPolicies with Scope=AWS answers HTTP 200, but the AWS-managed policy catalog it projects is not AWS's: whole policies are absent from the list, and the ones that are present carry per-policy metadata that does not match AWS's published values. Four causes, one per replayed path prefix / page.

AWS (all four causes): Smithy ListPolicies returns ListPoliciesResponse.Policies -> policyListType of iam#ManagedPolicyDetail, whose members include PolicyId (@pattern ^[\w]+$, @length 16-128, documented as "the stable and unique string identifying the policy"), Arn, Path, DefaultVersionId (@pattern ^v[1-9][0-9]*(\.[A-Za-z0-9-]*)?$, "the identifier for the version of the policy that is set as the default (operative) version"), CreateDate and UpdateDate (ISO 8601 dateType). For an AWS-managed policy (Path under /service-role/, /aws-service-role/, /job-function/, /root-task/) these are facts of the AWS partition, identical in every account: the set of policies AWS publishes at a path, each policy's stable ANPA... PolicyId, its current DefaultVersionId, and its create/update timestamps. The recordings carry those published values. ListPolicies models no client error, so the only requirement is the content of the 200.

Cause 1 of 4: the /aws-service-role/ page. Emulator: a number of policies AWS publishes are absent from Policies entirely (the comparison reports member[Arn="..."] with no sub-key, e.g. AWSAgentRegistryServiceRolePolicy, AWSAppFabricServiceRolePolicy, AWSArtifactServiceRolePolicy, AWSBCMDataExportsServiceRolePolicy and many more), and for the policies that are present PolicyId, DefaultVersionId, CreateDate and UpdateDate differ from AWS's (e.g. AmazonElasticsearchServiceRolePolicy PolicyId expected 'ANPAJFEWZPHXKLCVHEUIC', got 'ANPABK4QJZMWT3KVPNHLY'; AWSEC2SpotServiceRolePolicy DefaultVersionId expected 'v4', got 'v3').
Traces: iam-catalog-list-policies#task#1.

Cause 2 of 4: the /job-function/ page. Emulator: the job-function policies are present but their metadata is stale or synthetic - ViewOnlyAccess DefaultVersionId expected 'v46', got 'v22'; ViewOnlyAccess PolicyId expected 'ANPAID22R6XPJATWOFDK6', got 'ANPAXG3ZQTJWK7PVNHLYD'; SupportUser DefaultVersionId expected 'v11', got 'v9'; SystemAdministrator DefaultVersionId expected 'v12', got 'v7'; CreateDate/UpdateDate differ for AWSManagementConsoleAdministratorAccess, the AmazonODB* set, Billing, DataScientist, DatabaseAdministrator, NetworkAdministrator.
Traces: iam-catalog-list-policies#task#2.

Cause 3 of 4: the /root-task/ page. Emulator: CreateDate and UpdateDate for every root-task policy are a single seeded instant rather than each policy's own timestamps (S3UnlockBucketPolicy, IAMAuditRootUserCredentials, IAMCreateRootUserPassword, IAMDeleteRootUserCredentials all answer with timestamps a few minutes apart in one window), and two PolicyIds differ (IAMCreateRootUserPassword expected 'ANPAZKAPJZG4OEGTN7YT5', got 'ANPAZKAPJZG4KXMTQDLWR'; IAMDeleteRootUserCredentials expected 'ANPAZKAPJZG4CX73XKORQ', got 'ANPAZKAPJZG4VSNEUHYCT').

Why (all four): the AWS-managed policy catalog is the thing callers enumerate to discover and then attach a policy by ARN. A policy that is absent from ListPolicies cannot be discovered at all, so a client that lists the catalog and then attaches (for example AWSLambdaRole) finds no candidate where AWS has one, and any inventory/compliance walk under-reports the partition. PolicyId is documented as the policy's stable identifier, so a client that caches or asserts policy ids resolves the wrong identity, and DefaultVersionId feeding a GetPolicyVersion call names a version that is not AWS's operative one.
Fix: the AWS-managed policy catalog seed data behind the iam service's policy state - the per-policy records it is loaded from - must carry AWS's full membership for each managed path prefix and each policy's published PolicyId, DefaultVersionId, CreateDate and UpdateDate rather than generated ids and a seeding timestamp. Note that CreateDate/UpdateDate/DefaultVersionId drift as AWS revises its managed policies, so the durable requirements are complete membership per path prefix and AWS's stable PolicyId; the timestamps and version ids should track the catalog snapshot the corpus was recorded against.
