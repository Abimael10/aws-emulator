# controlcatalog ListDomains and ListObjectives serve an emulator-minted taxonomy instead of the published catalog (2 causes)

> _Note: this issue was identified against the code base at commit `7490275b5e4f9b52d1ecbf091bb2849bce1b0cbf`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
ListDomains

## Description
ListDomains and ListObjectives both answer 200 with a correctly shaped response, but the taxonomy rows they serve are not the published ControlCatalog taxonomy: a large fraction of the entries are served under locally minted hex-shaped ARNs that AWS never published, the catalogued ARNs for those records are absent, and some surviving records carry a shortened Description. Two divergence clusters (one per operation) share one root cause - the seeded domain/objective taxonomy table - so they are bundled here as 2 causes.

SHARED STATEMENT OF THE FAULT
AWS: Smithy (controlcatalog): ListDomains -> POST /domains, 200, paginated (items Domains, ListDomainsResponse$Domains : list<DomainSummary>, @required); ListObjectives -> POST /objectives, 200, paginated (items Objectives, ListObjectivesResponse$Objectives : list<ObjectiveSummary>, @required). DomainSummary requires Arn (DomainArn, @length 33..2048, @pattern ^arn:(aws(?:[-a-z]*)?):controlcatalog:::domain/[0-9a-z]+$), Name ('The name of the domain'), Description ('The description of the domain'), CreateTime, LastUpdateTime. ObjectiveSummary requires Arn (ObjectiveArn, @length 36..2048, @pattern ^arn:(aws(?:[-a-z]*)?):controlcatalog:::objective/[0-9a-z]+$), Name, Description, Domain (AssociatedDomainSummary), CreateTime, LastUpdateTime. These are AWS-owned, read-only catalog content (both operations are @readonly and take no resource identifier): the SET of ARNs a listing returns is the published catalog's membership, and each record's Name/Description is the published string for that ARN, byte for byte. Nothing here is caller-supplied or server-synthesizable. Recorded behavior is the authority for the individual ARNs, names and descriptions; the model is the authority for these being AWS-owned catalog content.
Emulator: it answers 200 but serves a different membership. For each of the two listings a block of entries exists only on the emulator side under 25-hex-character identifiers (domain/01d780d3ff2c8fd25185836de, objective/03e1b5972efd4eeaae13002f7 and the like), while the catalogued slug-shaped identifiers the recording contains are missing entirely from the response. Of the records that do appear under their published ARN, some carry a Description that is a truncated form of the published text.
Why: callers treat the ControlCatalog taxonomy as stable published AWS content. Compliance tooling, control-objective mapping, evidence export, console/portal navigation and catalog-diffing all enumerate ListDomains/ListObjectives and then pin, cache or join on the returned ARNs, and render Name/Description as the authoritative statement of what a domain or objective covers. Against this emulator such a client indexes domain and objective ARNs that do not exist in AWS (so every later GetControl/ListControlMappings/filter call keyed on them resolves to nothing against the real service), silently loses the catalogued domains and objectives it needs (incident management, legal, network security, business continuity, disaster recovery, crisis and emergency management, ...), and reports a shortened description as the published one.
Fix: the seeded taxonomy data behind the ListDomains and ListObjectives handlers in the controlcatalog service crate (its catalog state/seed data, not the serializer): the domain table and the objective table must hold exactly the published ARN sets with their published Name/Description text verbatim, so the handlers pass them through unchanged. The identifiers must be seeded from the catalog rather than minted locally. Status (200) and wire shape are already correct; this is a state/data-fidelity defect.
