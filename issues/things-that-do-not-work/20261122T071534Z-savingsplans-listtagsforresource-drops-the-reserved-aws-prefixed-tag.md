# savingsplans ListTagsForResource drops the reserved aws: prefixed tag key written on the plan

> _Note: this issue was identified against the code base at commit `d7b4052c712fff8a25ca6c0c18e5294a64b31920`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
ListTagsForResource

## Description
Replay of the savingsplans wire corpus (simparity-wire-aws-v1, 6 fixtures / 27 steps, 23 passed, 4 mismatched, score 85.2%) reports ONE net-new cause in the savingsplans crate (services/service-com-amazonaws-savingsplans-awssavingsplan): a tag whose KEY carries the reserved 'aws:' prefix is accepted by the write path with a success response and is then absent from every later read of the resource's tag set.

=== Cause 1 of 1: ListTagsForResource reports a tag set that is missing the reserved-prefix key the plan was tagged with — fixture savingsplans-queued-plan-delete-lifecycle, step task#5 (cluster also covers task#7) ===

AWS: Smithy (com.amazonaws.savingsplans#ListTagsForResource, POST /ListTagsForResource, http code 200): input resourceArn (SavingsPlanArn, @required, @pattern '^arn:aws([-a-z]*)?:[a-z]+:([a-z]{2}-[a-z]+-\d{1}|):(\d{12}):savingsplan\/([0-9a-f]{8}-[0-9a-f]{4}-[1-5][0-9a-f]{3}-[89ab][0-9a-f]{3}-[0-9a-f]{12})$'); output tags -> TagMap, a map of TagKey (string, NO @length and NO @pattern) to TagValue (string, NO @length and NO @pattern); modeled errors ValidationException (400), ResourceNotFoundException (404), InternalServerException (500). The companion write, TagResource (POST /TagResource, 200), takes tags (TagMap, @required) and models ValidationException (400), ResourceNotFoundException (404), ServiceQuotaExceededException (402), InternalServerException (500). Because the model places no constraint whatever on tag-key spelling, the prefix behavior is RECORDED BEHAVIOR ONLY: the recording shows AWS accepting a tag whose key begins with the reserved 'aws:' prefix (key form 'aws:tag:<name>' mapped to its value) on the Savings Plan, answering the write with success, and then answering ListTagsForResource HTTP 200 with that key present, spelled byte-for-byte as supplied, mapped to the value supplied. The requirement is the general one: ListTagsForResource projects the resource's STORED tag map verbatim — every key that a successful write put on the plan, including a reserved-prefix key, with its stored value — and a tag the service will not keep must be REFUSED at write time with the write's modeled ValidationException (400), never accepted and then discarded. The particular key and value in the recording ('aws:tag:domain' -> 'prod') are request values filling that template, not part of it.

Emulator: HTTP 200 (status matches, so nothing signals the loss) but the returned tags map does not contain the reserved-prefix key at all. Replay reports '$.tags.aws:tag:domain: missing (expected 'prod', got None)' at step task#5 and again at task#7 — two separate reads of the same plan, both after a tag write that itself replayed as PASSING (steps_errored=0, so the write answered exactly as recorded). The key is therefore accepted on the write and then not present on the read. The crate's own tag code does NOT do this filtering: state.rs check_tags validates only tag COUNT and key/value character length, SavingsPlanRecord::merge_tags stores the merged map as-is, remove_tags removes only the named keys, state.rs purchase() copies the supplied tag map onto the record unchanged, and the four tag-touching handlers (ops/tag_resource.rs, ops/untag_resource.rs, ops/list_tags_for_resource.rs which returns plan.tags.clone(), ops/create_savings_plan.rs which passes input.tags straight into purchase()) contain no prefix test. Hypothesis: the reserved-prefix key is dropped UPSTREAM of the handler — in the request-side TagMap ingestion/validation layer or the shared engine tag plumbing — so the handler never sees it and every read of the plan (ListTagsForResource here, and DescribeSavingsPlans in the related issue below) reports the truncated set.

Why: ListTagsForResource is how a client reads back what it tagged. A client that writes a reserved-prefix tag, gets a success response, and then reads the resource sees the tag silently gone — so tag-driven cost allocation, inventory and tag-based authorization all evaluate against a tag set smaller than the one the account actually asked for, and because both the write and the read answered 200 nothing tells the client state was discarded. A caller cannot even detect the loss by checking status codes; it must diff the map it sent against the map it reads, which no AWS client does.

Fix: the tag INGESTION path for this service — the request-side TagMap handling ahead of ops/tag_resource.rs and ops/create_savings_plan.rs (the crate's handlers and state.rs already store and project the map unfiltered), plus the ListTagsForResource projection if the filtering turns out to sit on the read side. Keys must be stored and projected verbatim, reserved 'aws:'-prefixed keys included; if such a key is to be rejected at all, reject it at write time with the write operation's modeled ValidationException (400) rather than accepting it and discarding it.

Related but NOT covering: open issue 20261120T210104Z-savingsplans-describe-bodies-still-diverge-from-the-recorded.md carries, as its Cause 2, the SAME tag loss seen through DescribeSavingsPlans (step task#11) bundled with that operation's null-member projection defect, and the replay reports that cluster as owned by it. This ListTagsForResource cluster (task#5/task#7) is reported with owned_by EMPTY — no open issue carries its replay key — so it is filed here with its own fixture/step linkage. The older savingsplans tag issue that the earlier report named as owning this cluster is no longer an open issue, which is why the cluster now replays unowned.
