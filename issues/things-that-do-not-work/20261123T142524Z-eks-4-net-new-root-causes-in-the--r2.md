# eks: 4 net-new root causes in the served cluster Kubernetes API — the bearer token's cluster binding is not checked, Service creation is 405, no kube-system add-on DaemonSets exist, and selfsubjectrulesreviews is 404

> _Note: this issue was identified against the code base at commit `94f7b27553b727586aac9de0add3c17de28dbaa9`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
DescribeCluster

## Description
FOUR separate net-new root causes in the Kubernetes API the EKS emulator serves at the address DescribeCluster publishes as cluster.endpoint. The Smithy model (services/service-com-amazonaws-eks-awswesleyfrontend/smithy-model/com-amazonaws-eks-awswesleyfrontend.json) types only DescribeCluster -> Cluster.endpoint / Cluster.certificateAuthority.data; the apiserver surface reached through them is recorded behavior only. Each cause below is a SEPARATE defect and must be closed separately; each carries its own failing check ids.

Cause 1 of 4: the aws-iam-authenticator bearer token's cluster binding is not verified — a token minted for a DIFFERENT cluster name is ACCEPTED.
AWS:      recorded behavior only. An EKS bearer token is a presigned STS GetCallerIdentity URL whose signed header x-k8s-aws-id names the cluster it may be used on; the cluster's authenticator rejects a token whose x-k8s-aws-id is any other cluster name. The refusal is HTTP 401 (403 is the only other value a real apiserver gives for an unusable credential) with a Kubernetes Status object: kind "Status", apiVersion "v1", status "Failure", reason "Unauthorized", message "Unauthorized", code 401, and no data (no "items") in the body. The reason/message/code tokens are fixed text; nothing in the body is per-run.
Emulator: on an ACTIVE cluster created with accessConfig.authenticationMode=API and bootstrapClusterCreatorAdminPermissions=true, a token signed by the same principal but minted for cluster name `<name>-not-this-cluster` is accepted on GET <endpoint>/version: HTTP 200 with the version document ({"major":"1","minor":"36","gitVersion":"v1.36.0-eks-...",...}) instead of 401/403 with a Status Failure. (The same check shows anonymous requests ARE refused on this cluster, so the defect is specifically the missing cluster-name check, not authentication in general; the open issue 20261123T045518Z-eks-iam-sts-the-served-cluster-kubernetes-api-89ba98.md covers the separate anonymous-200 defect and does not cover this one.)
Why:      a token is replayable across every cluster in the account. A client that relies on EKS's per-cluster token scoping — the reason x-k8s-aws-id is signed at all — gets no isolation: a credential scoped to a dev cluster authenticates against a production cluster, and any test that asserts cross-cluster token rejection passes against AWS and fails to detect the hole here.
Fix:      the authentication path of the served cluster Kubernetes API (the EKS cluster data-plane handler that validates the Authorization bearer token): resolve the presigned token's signed x-k8s-aws-id and refuse with 401 and a Status Failure when it is not this cluster's name.
Traces:   eks.cluster-kubernetes-api-server-serves-advertised-version.

Cause 2 of 4: the core/v1 `services` collection accepts no POST — Service objects cannot be created at all.
AWS:      recorded behavior only. A real apiserver answers POST /api/v1/namespaces/<ns>/services with a well-formed Service manifest with HTTP 201 and the created Service object, including spec.clusterIP allocated out of the cluster's service CIDR and metadata.uid/resourceVersion. A rejection, when the manifest is bad, is 422 Invalid — never a method-level refusal, because POST on a collection is the create verb every Kubernetes resource routes.
Emulator: HTTP 405 with {"kind":"Status","apiVersion":"v1","metadata":{},"status":"Failure","message":"the server does not allow POST on /api/v1/namespaces/<namespace>/services","reason":"MethodNotAllowed","details":null,"code":405}. The fixed text is "the server does not allow POST on " + the request path; the namespace in the two observed messages (sim2real-dns-…, sim2real-dp-…) is a per-run value. Nothing a client sends changes the outcome.
Why:      no ClusterIP service can exist, so nothing in the cluster is addressable by name or by VIP: in-cluster DNS resolution of <svc>.<ns>.svc.cluster.local, Service-based load balancing across pods, and every workload that talks to another workload through a Service are unreachable. Related open issues record 405 MethodNotAllowed for OTHER verbs/resources of this same surface — 20261122T113249Z-eks-3-net-new-root-causes-in-the.md (DELETE) and 20261114T130859Z-ecr-eks-logs-2-net-new-root-causes-b62cb4.md (the core/v1 events collection) — neither routes or covers POST on `services`, and these two checks reproduce at this commit.
Fix:      the request routing of the served cluster Kubernetes API (the EKS cluster data-plane handler's verb/resource table for core/v1 services) plus the ClusterIP allocator that must assign spec.clusterIP from the cluster's serviceIpv4Cidr and return 201 with the stored object.
Traces:   eks.eks-coredns-resolves-a-service-to-the-clusterip-the-api-reports, eks.eks-deployment-pod-is-reachable-through-a-cluster-service.

Cause 3 of 4: an ACTIVE cluster ships none of its default add-on workloads — kube-system has no kube-proxy DaemonSet.
AWS:      recorded behavior only. Every EKS cluster is created with its self-managed networking add-ons already running in kube-system, so GET /apis/apps/v1/namespaces/kube-system/daemonsets/kube-proxy answers 200 with the DaemonSet, whose spec.template.spec.containers[] holds a container named kube-proxy with an image whose tag is the add-on version, and whose status reports desiredNumberScheduled/numberReady/updatedNumberScheduled over the cluster's nodes. (coredns ships as a Deployment and aws-node as a DaemonSet, the same way.) CreateAddon (modeled: POST /clusters/{clusterName}/addons, pinning addonVersion) then changes that DaemonSet's image tag to the pinned version. The container name and the resource names are fixed text; the version tag and node counts come from the request and cluster state.
Emulator: 404 with {"kind":"Status","apiVersion":"v1","metadata":{},"status":"Failure","message":"daemonsets \"kube-proxy\" not found","reason":"NotFound","details":{"name":"kube-proxy","kind":"daemonsets"},"code":404}, read BEFORE any CreateAddon call — the pre-existing in-cluster add-on workload simply does not exist, so there is no image to observe and no rollout to converge.
Why:      an add-on is only real if it runs in the cluster. A client cannot read the running version of kube-proxy/coredns/vpc-cni, cannot verify that pinning an add-on version changed what runs, and cannot patch or roll back the DaemonSet that DeleteAddon(preserve=true) is documented to leave behind; every add-on management flow becomes control-plane bookkeeping with no data-plane effect. The open issue 20261104T105252Z-eks-2-net-new-root-causes-the-metrics.md concerns the metrics-server configuration SCHEMA, not the absent in-cluster workloads, and does not cover this check.
Fix:      the cluster bootstrap/state of the served cluster Kubernetes API (the EKS cluster data-plane handler's seeded kube-system objects) and the add-on handler's projection onto them: an ACTIVE cluster must expose the default add-on DaemonSets/Deployments, and CreateAddon must set their container image tag to the resolved addonVersion.
Traces:   eks.eks-pinned-addon-version-is-the-image-running-in-the-cluster.

Cause 4 of 4: the authorization.k8s.io/v1 `selfsubjectrulesreviews` resource is not served — POST is answered 404.
AWS:      recorded behavior only. A real apiserver routes POST /apis/authorization.k8s.io/v1/selfsubjectrulesreviews with a SelfSubjectRulesReview whose spec.namespace names the namespace to enumerate, and answers 200/201 with the object, status filled in. On an EKS cluster whose access is enforced by the access-entries webhook authorizer the status comes back status.incomplete=true with status.evaluationError="webhook authorizer does not support user rule resolution" — fixed text, identical in every namespace, because that authorizer cannot enumerate rules. The sibling resource selfsubjectaccessreviews on the same API group IS routed by the emulator and answers, so the group is reachable; only this resource is missing.
Emulator: HTTP 404 with {"kind":"Status","apiVersion":"v1","metadata":{},"status":"Failure","message":"the server could not find the requested resource: /apis/authorization.k8s.io/v1/selfsubjectrulesreviews","reason":"NotFound","details":null,"code":404}. The fixed text is "the server could not find the requested resource: " + the request path.
Why:      `kubectl auth can-i --list`, every UI that renders "what can I do in this namespace", and any client that probes its own effective permissions before acting get a hard 404 instead of the review; with EKS access entries this also hides the one signal AWS gives that rule enumeration is delegated to the webhook authorizer (incomplete=true plus that evaluationError), so a client cannot tell "no rules" from "not enumerable".
Fix:      the request routing of the served cluster Kubernetes API (the EKS cluster data-plane handler's authorization.k8s.io/v1 resource table) — route selfsubjectrulesreviews next to selfsubjectaccessreviews and answer 201 with status.incomplete=true and the webhook authorizer's evaluationError.
Traces:   eks.namespace-scoped-access-policy-confines-reads-to-its-namespace.
