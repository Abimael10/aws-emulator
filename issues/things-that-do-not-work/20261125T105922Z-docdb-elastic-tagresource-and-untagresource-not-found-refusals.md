# DocDB Elastic TagResource and UntagResource not-found refusals stamp a Coral-namespace x-amzn-errortype that fails the recorded header shape

> _Note: this issue was identified against the code base at commit `352f4536081af191daff3bc92f8d9fe5d775df3a`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
TagResource

## Description
The DocDB Elastic restJson1 error-response serializer appends an Amazon-internal Coral namespace URL to the x-amzn-errortype value it stamps on not-found refusals of the tag-write operations. The HTTP status, the error class and the response body of these refusals are correct; only the error-type header diverges, and it diverges identically on both operations, which is why they are bundled as one serializer fault. This bundle contains 2 causes; BOTH must be closed before submitting.

Cause 1 of 2: TagResource against an ARN that no DocDB Elastic resource carries (fixture docdb-elastic-tag-resource-ops-missing-cluster-not-found, step task#1).
AWS: HTTP 404 with error code ResourceNotFoundException. Smithy (services/service-com-amazonaws-docdbelastic-chimeradblionfishservicelambda/smithy-model/com-amazonaws-docdbelastic-chimeradblionfishservicelambda.json): service ChimeraDbLionfishServiceLambda, sdkId "DocDB Elastic", version 2022-11-28, protocols [restJson1], sigv4Name/arnNamespace docdb-elastic; TagResource is POST /tags/{resourceArn} with resourceArn @required @httpLabel @length 1-1011 and tags @required, errors ResourceNotFoundException (client, httpError 404), ValidationException (400), ThrottlingException (429), InternalServerException (500). For the x-amzn-errortype header itself the model states no value - it only @cors-exposes x-amzn-errortype alongside x-amzn-requestid and x-amzn-trace-id - so this part is recorded behavior only: the corpus asserts the header by SHAPE, not by literal, and the stable requirement that shape carries is that the value's leading token is the error code of the modeled error being served, here exactly the fixed text 'ResourceNotFoundException' taken from the error shape name, with nothing in it drawn from the request or from emulator state. Everything after that leading code is environment-dependent and is not itself a requirement; what the recording does establish is that the qualifier AWS serves is not an Amazon-internal Coral namespace URL, which is not part of the public wire contract. Hypothesis: AWS qualifies the code with a reference to the modeled error shape, so only the leading code is stable across runs.
Emulator: status 404 (correct) and error class ResourceNotFoundException (correct), but x-amzn-errortype is served as 'ResourceNotFoundException:http://internal.amazon.com/coral/com.amazonaws.docdbelastic/' - the error code followed by an internal Coral namespace URL - which does not satisfy the recorded header shape. Replay: '$headers.x-amzn-errortype: shape_mismatch (expected <shaped-not-asserted>, got ResourceNotFoundException:http://internal.amazon.com/coral/com.amazonaws.docdbelastic/)'; expected_status 404, actual_status 404; divergence_key service=docdb-elastic|TagResource|status=404->404|keys=$headers.x-amzn-errortype.
Why: x-amzn-errortype is the header SDKs, proxies and log pipelines read to classify a failure before parsing the body, and several SDK error parsers split it at ':' or '#' and reject values whose qualifier is not a shape reference. A client relying on AWS's behavior sees a value AWS never serves, fails to map the refusal onto ResourceNotFoundException, and falls into a generic-failure branch - so retry policy and 'create it if it is missing' provisioning logic takes a different path against the emulator than against AWS, for a refusal that is otherwise byte-correct.
Fix: the DocDB Elastic crate's shared restJson1 error-response serializer - the single place x-amzn-errortype is written for this service's modeled errors - not the TagResource handler, whose status, error selection and body are already correct.
