# Neptune catalog reads serve an RDS-derived inventory: the engine-version catalog and the orderable-instance catalog do not match the engine's published releases and instance classes

> _Note: this issue was identified against the code base at commit `7ea62d1f718eb0ddea36ce5991d6f153f8f96be6`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
DescribeDBEngineVersions

## Description
Neptune's two unfiltered catalog read paths — DescribeDBEngineVersions with no Engine/EngineVersion filter and DescribeOrderableDBInstanceOptions for the graph engine — answer HTTP 200 with a body whose element LIST is not the engine's published inventory. Both paths are assembled from a catalog the emulator synthesizes (an RDS-wide / serverless-flavoured one) rather than from the graph engine's release and instance-class inventory, so the collections a client enumerates before it creates anything are a different set from the service's. THIS ISSUE HAS 2 CAUSES — both must be closed before submitting.

Cause 1 of 2: the unfiltered DescribeDBEngineVersions catalog does not contain the engine's published releases.
AWS: Smithy (com.amazonaws.neptune#AmazonRDSv19) DescribeDBEngineVersions errors=[], input DescribeDBEngineVersionsMessage {Engine, EngineVersion, DBParameterGroupFamily, Filters, MaxRecords, Marker, DefaultOnly, ListSupportedCharacterSets, ListSupportedTimezones}, output DBEngineVersionMessage {Marker, DBEngineVersions: DBEngineVersionList}, paginated (inputToken Marker / outputToken Marker / items DBEngineVersions / pageSize MaxRecords); the element shape com.amazonaws.neptune#DBEngineVersion models Engine, EngineVersion, DBParameterGroupFamily, DBEngineDescription, DBEngineVersionDescription, ValidUpgradeTarget (ValidUpgradeTargetList — 'A list of engine versions that this database engine version can be upgraded to'), ExportableLogTypes, SupportsLogExportsToCloudwatchLogs, SupportsReadReplica, SupportsGlobalDatabases. The model does not enumerate which releases exist, so recorded behavior only for the inventory: an unfiltered call returns the engine's whole published release history as a MULTI-element DBEngineVersions list — the recording carries 29 DBEngineVersion elements, one per published release (the recorded run spans the 1.1.x/1.2.x/1.3.x/1.4.x families, e.g. an element with Engine 'neptune', EngineVersion '1.1.1.0', DBParameterGroupFamily 'neptune1', DBEngineVersionDescription 'Neptune <version>.R<n>'), each carrying its own ValidUpgradeTarget chain of UpgradeTarget entries (EngineVersion / MajorEngineVersion / MinorEngineVersion / AutoUpgrade / IsMajorVersionUpgrade / Description / SupportsGlobalDatabases ...) and the RDS-shared capability flags. The requirement is that the list enumerate every release the engine publishes, with each element's upgrade targets naming the releases it can be upgraded to; the specific version strings in the recording are that run's catalog filling the template.
Emulator: the 200 body does not carry those elements at all — replay reports EVERY recorded position $...DBEngineVersions.DBEngineVersion[0] through [28] as 'missing', i.e. the emulator's DBEngineVersions collection does not present the release history as an indexable multi-element list (consistent with it serving a single synthesized release element, the shape already reported for the FILTERED read).
Why: this is the discovery call a client makes before CreateDBCluster/CreateDBInstance and the one an upgrade planner reads. With the release history absent, a client cannot choose a version, cannot compute an upgrade path (no ValidUpgradeTarget chains to walk), and pagination over DBEngineVersions returns a collection of the wrong cardinality — so version pinning, upgrade-path planning and catalog caches all operate on an inventory the service never served.
Fix: the engine-version reference catalog behind the DescribeDBEngineVersions handler, and that handler's projection of DBEngineVersionMessage.DBEngineVersions for the unfiltered read — the list must be built from the graph engine's published releases (each with its ValidUpgradeTarget chain) instead of a single synthesized element.
Traces: neptune-catalog-describe-db-engine-versions#task#1.

Cause 2 of 2: the orderable-DB-instance-option catalog serves a different instance-class inventory from the engine's.
AWS: Smithy DescribeOrderableDBInstanceOptions errors=[], input DescribeOrderableDBInstanceOptionsMessage {Engine (required), EngineVersion, DBInstanceClass, LicenseModel, Vpc, Filters, MaxRecords, Marker}, output OrderableDBInstanceOptionsMessage {OrderableDBInstanceOptions: OrderableDBInstanceOptionsList, Marker}, paginated over OrderableDBInstanceOptions; the element shape com.amazonaws.neptune#OrderableDBInstanceOption models Engine, EngineVersion, DBInstanceClass, LicenseModel, AvailabilityZones, MultiAZCapable, ReadReplicaCapable, Vpc, SupportsStorageEncryption, StorageType, SupportsIops, SupportsEnhancedMonitoring, SupportsIAMDatabaseAuthentication, SupportsPerformanceInsights, SupportsGlobalDatabases, SupportedNetworkTypes and the storage/IOPS bounds. The model does not enumerate the orderable classes, so recorded behavior only: for the graph engine the service returns one option per (release, DB instance class, license model) combination it will actually accept at CreateDBInstance — the recording's list enumerates the provisioned instance families (e.g. an element with Engine 'neptune', EngineVersion '1.4.8.0', DBInstanceClass 'db.r7i.12xlarge', LicenseModel 'amazon-license', SupportsClusters true, SupportsGlobalDatabases true, SupportedNetworkTypes ['DUAL','IPV4'], Vpc true) in the service's order.
Emulator: from recorded position [78] onward the lists disagree — at [78] the recording has DBInstanceClass 'db.r7i.12xlarge' while the emulator serves 'db.serverless' for the same release, and the remaining recorded positions (through [119]) are reported mismatched or missing. So the emulator's option set for the engine is a different, shorter inventory (serverless-weighted, missing provisioned classes) rather than the engine's orderable-class catalog.
Why: this is the call a client uses to pick a DB instance class, and a provisioning tool or console picker driven by it is offered classes the service does not list and never offered the ones it does — so a later CreateDBInstance names a class the catalog said was orderable (or omits one that is), and any paginated enumeration or cached picker is built on an inventory that disagrees with the service.
Fix: the orderable-instance reference catalog behind the DescribeOrderableDBInstanceOptions handler and that handler's projection of OrderableDBInstanceOptionsList — the option set (instance classes per release, and their per-element capability flags) must come from the graph engine's orderable inventory, not an RDS-wide/serverless-derived one.
Traces: neptune-catalog-describe-orderable-db-instance-options#task#1.
