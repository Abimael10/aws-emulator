# cloudfront__s3: 3 net-new causes — the edge-generated 403 error page is not CloudFront's, the large-object Miss→Hit pair never settles, and the continuous-deployment staging promotion reaches no verdict

> _Note: this issue was identified against the code base at commit `c8aff5e88329c10bb52bfa1e75179b846109ef58`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
CloudFront distribution edge data plane (viewer GET) / UpdateDistribution / UpdateDistributionWithStagingConfig

## Description
Three net-new root causes in the CloudFront edge data plane and distribution propagation, all grounded in failing checks of the cloudfront__s3 suite group. They are NOT the already-filed "the edge serves nothing / the published DomainName is an unserved <id>.cloudfront.net host" family (e.g. 20261125T174119Z-cloudfront-s3-the-s3-origin-edge-is-unreachable--r2.md): in this run the edge DOES answer — one check reads a real edge-generated 403 page and another reads 200s from the edge — so these are finer-grained divergences behind that, and none of the open issues listed below covers them.

=== Cause 1 of 3: the edge-generated 403 "The request could not be satisfied" page body is not CloudFront's ===
Failing check: cloudfront__s3.cf-viewer-get-with-body-rejected

AWS: recorded behavior only — the edge error page is not in the CloudFront Smithy model (it is a data-plane response, not a modeled operation shape). A viewer GET that carries a request body is refused by the edge with HTTP 403 and the header `X-Cache: Error from cloudfront`, and the body is CloudFront's own generated error page. That page is FIXED text except for the Request ID the edge mints per request; the recording shows the fixed text as:
  `<!DOCTYPE HTML PUBLIC "-//W3C//DTD HTML 4.01 Transitional//EN" "http://www.w3.org/TR/html4/loose.dtd">`\n`<HTML><HEAD><META HTTP-EQUIV="Content-Type" CONTENT="text/html; charset=iso-8859-1">`\n`<TITLE>ERROR: The request could not be satisfied</TITLE>`\n`</HEAD><BODY>`\n`<H1>403 ERROR</H1>`\n`<H2>The request could not be satisfied.</H2>`\n`<HR noshade size="1px">`\n`Bad request.`\n`We can't connect to the server for this app or website at this time. There might be too much traffic or a configuration error. Try again later, or contact the app or website owner.`\n`<BR clear="all">`\n`If you provide content to customers through CloudFront, you can find steps to troubleshoot and help prevent this error by reviewing the CloudFront documentation.`\n`<BR clear="all">`\n`<HR noshade size="1px">`\n`<PRE>`\n`Generated by cloudfront (CloudFront)`\n`Request ID: <per-request id>`\n`</PRE>`\n`<ADDRESS>`\n`</ADDRESS>`\n`</BODY></HTML>`
The ONLY variable part is the Request ID; everything else is the requirement.

Emulator: the 403 status and `X-Cache: Error from cloudfront` are right, but the page body diverges in four places — (a) the sentence "We can't connect to the server for this app or website at this time. There might be too much traffic or a configuration error. Try again later, or contact the app or website owner." is missing entirely; (b) the sentence "If you provide content to customers through CloudFront, you can find steps to troubleshoot and help prevent this error by reviewing the CloudFront documentation." and the second `<BR clear="all">` that precedes it are missing; (c) it emits `<PRE>Generated by cloudfront (CloudFront)` — no newline after `<PRE>`, where AWS writes `<PRE>` then a newline; (d) it emits `<ADDRESS></ADDRESS>` where AWS writes `<ADDRESS>` then a newline then `</ADDRESS>`.

Why: a browser user sees a CloudFront refusal page stripped of the explanation and troubleshooting pointer AWS always includes, and any client, log scraper or operator script that recognises an edge-generated refusal by matching CloudFront's page (prefix/suffix match around the Request ID, as this check does) fails to recognise the emulator's page at all and misattributes the 403 to the origin.

Fix: the CloudFront edge data plane's generated-error-page writer — the component that produces the body alongside `X-Cache: Error from cloudfront`. It must emit the full fixed page, with the Request ID the only substituted value.

=== Cause 2 of 3: a several-megabyte S3-origin object never produces the Miss-then-Hit pair, so the check is cut off with no verdict ===
Failing check: cloudfront__s3.cf-s3-large-object-first-fetch-miss-second-fetch-hit

AWS: recorded behavior only — a 3 MiB S3-origin object served under the managed CachingOptimized cache policy (id 658327ea-f89d-4fab-a63d-7e88639e58f6) answers the first viewer fetch from the origin with `X-Cache: Miss from cloudfront` and the second from the edge with `X-Cache: Hit from cloudfront`, both HTTP 200 and both with byte-identical bodies.

Emulator: the check never reaches either assertion — it is cut off with `Check timed out after 60.0s`. Its two poll loops (200 + `X-Cache: Miss from cloudfront` at a 10 s interval, then 200 + `X-Cache: Hit from cloudfront` at a 10 s interval) do not both settle inside the budget. Hypothesis: the multi-megabyte body is either not served through the edge or is re-fetched from the origin rather than answered from the edge cache, so the Hit poll never satisfies; the recording states only the timeout.

Why: a client cannot distinguish an edge-cache answer from an origin fetch for large objects — `X-Cache` is the only signal CloudFront gives — so cache effectiveness, origin-offload and the "same bytes on hit and miss" guarantee are all unobservable for the object sizes real distributions mostly serve.

Fix: the CloudFront edge data plane's cache lookup/store path for an S3 origin, and the `X-Cache` header it stamps (Miss vs Hit). Related but NOT the same cause: 20261116T230910Z-cloudfront-6-net-new-causes-the-cloudfront-js.md reports edge cache entries never EXPIRING; this one is about a large object never being served from cache at all.

=== Cause 3 of 3: the continuous-deployment staging-promotion scenario reaches no verdict — the staging distribution is still InProgress when the budget runs out ===
Failing check: cloudfront__s3.continuous-deployment-staging-origin-path-promotion-serves-staging-bytes

AWS: Smithy `Distribution.Status` — "The distribution's status. When the status is Deployed, the distribution's information is fully propagated to all CloudFront edge locations." The model publishes no propagation deadline, so the timing is recorded behavior only: a caller mutates a distribution (CopyDistribution with Staging=true, UpdateDistribution to repoint OriginPath, UpdateDistribution to attach the ContinuousDeploymentPolicyId, then UpdateDistributionWithStagingConfig to promote) and polls GetDistribution until Status == Deployed before using the edge.

Emulator: the scenario never reaches its assertions. The body fails inside the wait-for-Deployed poll with `AssertionError: timed out waiting for distribution <distribution-id> to reach Deployed after 14.7s (last: 'InProgress')` — the budget-bounded poll got exactly one probe, which answered InProgress, and the check's remaining time was gone before the next probe. Every mutating distribution call re-enters an emulator-invented propagation window (services/service-com-amazonaws-cloudfront-cloudfront2020-05-31/src/state.rs:213, `PROPAGATION_DELAY: Duration = Duration::from_millis(500)`, materialised by `settle()` on read), so a caller that polls on an interval chosen for real AWS pays a whole poll interval of sleep per mutation, and the scenario's four mutations plus the emulator's own call latency exhaust the check's budget before the first edge fetch is even attempted. Nothing in the run shows the SingleHeader routing, the promotion or the post-promotion bytes being wrong — they are never reached.

Why: a client following the documented wait-until-Deployed pattern cannot drive a continuous-deployment workflow to completion against the emulator: each of CopyDistribution, UpdateDistribution and UpdateDistributionWithStagingConfig leaves the distribution reporting InProgress for a window the emulator chose, and a multi-step workflow is spent entirely in propagation waits for propagation that has in fact already finished. The whole SingleHeader staging-traffic/promotion surface is therefore unverifiable.

Fix: the distribution propagation deadline and `settle()` in services/service-com-amazonaws-cloudfront-cloudfront2020-05-31/src/state.rs, together with the write paths that re-enter it (ops/update_distribution.rs, ops/copy_distribution.rs, ops/update_distribution_with_staging_config.rs:591 `store.apply_config(...)`). A distribution whose configuration is already applied must not be reported InProgress for longer than the instant of the call that applied it, so that the first GetDistribution a caller makes after a mutation can observe the terminal status and a multi-mutation workflow is not charged a poll interval per step.

## Steps to Reproduce
Replay the three failing behavioral checks listed in trace_ids against the emulator:

1. cf-viewer-get-with-body-rejected: create a bucket and put an object; create an OAC (s3/always/sigv4); create an enabled distribution whose single origin is the bucket's regional S3 domain with that OAC and the managed CachingOptimized cache policy; grant cloudfront.amazonaws.com s3:GetObject on the bucket conditioned on AWS:SourceArn = the distribution ARN; wait for Status=Deployed. GET the object through the distribution's edge with NO body (expect 200 and the object's bytes), then issue the identical GET carrying a request body. Observe: HTTP 403 with X-Cache: Error from cloudfront (correct) but a body missing the two explanatory sentences and the second <BR clear="all">, with <PRE> not followed by a newline and <ADDRESS></ADDRESS> collapsed onto one line.

2. cf-s3-large-object-first-fetch-miss-second-fetch-hit: same setup with a 3 MiB random object; after Status=Deployed, GET the object through the edge twice and read the X-Cache header each time. Observe: the pair 'Miss from cloudfront' then 'Hit from cloudfront' is never both reached — the check is cut off at its 60 s cap.

3. continuous-deployment-staging-origin-path-promotion-serves-staging-bytes: put primary/obj.txt and staging/obj.txt in a bucket; create a primary distribution with OriginPath=/primary under the managed CachingDisabled policy; wait Deployed; CopyDistribution(PrimaryDistributionId, Staging=true, Enabled=true); UpdateDistribution on the copy to set OriginPath=/staging and poll GetDistribution for Deployed. Observe: the probe immediately after the update answers Status='InProgress' (the emulator's 500 ms propagation window), the caller's poll interval is then spent sleeping, and the scenario — SingleHeader routing, UpdateDistributionWithStagingConfig promotion, post-promotion bytes — is never reached within the check's budget.
