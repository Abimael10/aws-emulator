# ec2 DescribeInstanceTypes serves formula-derived instance-type rows instead of the recorded catalog

> _Note: this issue was identified against the code base at commit `81e21ca007588719de802b4dd67d83498ccb7823`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
DescribeInstanceTypes

## Description
3 causes, one shared fault: DescribeInstanceTypes does not serve AWS's instance-type catalog - it computes each row from the instance size, so whole blocks of hardware facts are wrong and several members AWS always emits are absent. The same cause recurs on every catalog page of the corpus; the three below are the clusters named here, and each must be re-replayed.

Cause 1 of 3: the c6i family page
AWS: Smithy: DescribeInstanceTypes returns InstanceTypeInfo per type; NetworkInfo.NetworkCards items carry BaselineBandwidthInGbps, PeakBandwidthInGbps, DefaultEnaQueueCountPerInterface, MaximumEnaQueueCount, MaximumEnaQueueCountPerInterface and AdditionalFlexibleNetworkInterfaces - these are per-instance-type facts of the AWS catalog, not derived quantities. Recorded response for this page (HTTP 200) gives, e.g., c6i.16xlarge networkCards baselineBandwidthInGbps 25.0 / peakBandwidthInGbps 25.0, defaultEnaQueueCountPerInterface 8, maximumEnaQueueCount 120, maximumEnaQueueCountPerInterface 32, additionalFlexibleNetworkInterfaces 0, and a third interfaceTypeSet entry on the .32xlarge and .metal rows.
Emulator: HTTP 200, but baseline/peak bandwidth are halved or otherwise scaled from the size (c6i.16xlarge 12.5/12.5 instead of 25.0/25.0; c6i.4xlarge 3.12 instead of 6.25), and defaultEnaQueueCountPerInterface, maximumEnaQueueCount, maximumEnaQueueCountPerInterface and additionalFlexibleNetworkInterfaces are absent on every row.
Why: capacity planners, placement logic and ENA-queue sizing read these members to pick an instance type; derived values make the emulator recommend the wrong type, and the absent members make code that reads them fail outright rather than read a wrong number.
Fix: the DescribeInstanceTypes handler's instance-type catalog data in the EC2 crate - serve the catalog rows verbatim instead of computing network-card facts from the size, and emit the ENA queue-count and flexible-interface members.
Traces: ec2-catalog-describe-instance-types-a1-c9g#task#14

Cause 2 of 3: the c6id family page
AWS: same modeled members; recorded response (HTTP 200) gives, e.g., c6id.8xlarge networkCards baselineBandwidthInGbps 12.5 / peakBandwidthInGbps 12.5, defaultEnaQueueCountPerInterface 8, maximumEnaQueueCount 64, maximumEnaQueueCountPerInterface 32, additionalFlexibleNetworkInterfaces 0; c6id.2xlarge baseline 3.125.
Emulator: HTTP 200 with the same derivation error (c6id.8xlarge 6.25/10.0; c6id.2xlarge 1.56) and the same missing members on every row of the page.
Why: as cause 1.
Fix: as cause 1 (catalog data for the c6id rows).
Traces: ec2-catalog-describe-instance-types-a1-c9g#task#15

Cause 3 of 3: the c9gd family page - the derivation also corrupts EBS, connection-tracking, address-per-interface and vCPU facts
AWS: Smithy: InstanceTypeInfo.EbsInfo (AttachmentLimitType, EbsOptimizedInfo baseline/maximum bandwidth-IOPS-throughput, MaximumEbsAttachments), NetworkInfo.ConnectionTrackingConfiguration.TcpEstablishedTimeout, NetworkInfo.EnaSrdSupported / FlexibleEnaQueuesSupport / Ipv4AddressesPerInterface / Ipv6AddressesPerInterface / Ipv4AddressesPerSecondaryInterface / MaximumNetworkInterfaces, ProcessorInfo.SustainedClockSpeedInGhz, RebootMigrationSupport and VCpuInfo.ValidCores. Recorded response (HTTP 200) gives, e.g., c9gd.metal-48xl ebsInfo.attachmentLimitType 'shared', connectionTrackingConfiguration.defaultTcpEstablishedTimeout 350, enaSrdSupported true, flexibleEnaQueuesSupport 'supported', ipv4AddressesPerInterface 64, ipv6AddressesPerInterface 64, ipv4AddressesPerSecondaryInterface 0, maximumNetworkInterfaces 24, networkCards baselineBandwidthInGbps 100.0, defaultEnaQueueCountPerInterface 32.
Emulator: HTTP 200 with attachmentLimitType 'dedicated', defaultTcpEstablishedTimeout 432000, enaSrdSupported false, flexibleEnaQueuesSupport 'unsupported', ipv4/ipv6AddressesPerInterface 50, maximumNetworkInterfaces 15, networkCards baselineBandwidthInGbps 25.0, ipv4AddressesPerSecondaryInterface and the ENA queue-count members absent, plus formula-derived ebsOptimizedInfo/instanceStorageInfo/validCores/sustainedClockSpeedInGhz/rebootMigrationSupport values across the whole page.
Why: every one of these is a hard constraint a client plans against (ENI and IP-per-ENI limits, EBS attachment limits and throughput, idle-connection timeout, valid core counts). A synthesized row makes the emulator agree with no real instance type.
Fix: as cause 1 - the instance-type catalog the DescribeInstanceTypes handler reads, covering ebsInfo, networkInfo, processorInfo, vCpuInfo and rebootMigrationSupport, not just networkCards.
Traces: ec2-catalog-describe-instance-types-c9gd-m6gd#task#1
