# ec2__resourcegroupstaggingapi: 3 causes — GetResources never discovers EC2-tagged resources, TagResources/UntagResources never reach EC2's native tags, and absent EC2 ARNs get no FailedResourcesMap entry

> _Note: this issue was identified against the code base at commit `464916eef2b3c982c1baee9561b862edbea1b318`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
GetResources

## Description
Three net-new root causes in the Resource Groups Tagging API's handling of EC2 resources, all grounded in the behavioral suite's ec2__resourcegroupstaggingapi checks (8 failing checks). Related OPEN issue 20261114T013533Z-resourcegroupstaggingapi-getresources-never-returns-tagged-ec2-resources-1.md describes the same EC2 discovery gap from the WIRE corpus but does not carry these behavioral check ids, and the open issue 20261106T224449Z-resourcegroupstaggingapi-tagresources-omits-the-per-resource-failedresourcesmap-entry-for.md covers only an absent SNS topic ARN, not EC2. Operations affected: GetResources, TagResources, UntagResources.

Cause 1 of 3: GetResources never returns an EC2 resource that carries tags written through EC2's own tag plane (CreateTags, or TagSpecifications at create time), so tag-based discovery of EC2 is empty and ResourceTypeFilters scoping over EC2 types cannot be exercised at all.
AWS: Smithy (services/service-com-amazonaws-resourcegroupstaggingapi-resourcegroupstaggingapi-20170126/smithy-model/...json): GetResources (awsJson1_1, POST /GetResources, HTTP 200) takes TagFilters / ResourceTypeFilters / ResourceARNList and answers ResourceTagMappingList, each entry carrying ResourceARN and Tags; GetResourcesInput.ResourceTypeFilters is documented 'The format of each resource type is service[:resourceType] ... All tagged resources, whether the tagging used the Resource Groups Tagging API or not, are returned by the Get* operation.' So a VPC, security group or internet gateway tagged natively must appear in a TagFilters query for that key/value under its own ARN (arn:aws:ec2:<region>:<account>:vpc/<vpc-id>, .../security-group/<sg-id>, .../internet-gateway/<igw-id>), and a ResourceTypeFilters of ec2:vpc / ec2:security-group must return only the resources of that type while a filter naming neither type (ec2:subnet) returns an empty list.
Emulator: the TagFilters query answers 200 with an empty ResourceTagMappingList and keeps answering empty for the whole poll window, so the checks exhaust their deadline (reported as 'Check timed out after 60.0s') on the very first discovery poll. Because that positive control never passes, the type-filter partitioning assertions below it are never reached.
Why: tag-based discovery is how clients enumerate what they own — cost allocation, reaper/cleanup jobs, ops consoles. Against this emulator every such client concludes the account owns no tagged EC2 resources, and a reaper that deletes 'untagged' resources does the opposite of what the tags say.
Fix: the cross-service resource/tag index the GetResources handler reads, plus the EC2 publisher into it (EC2 CreateTags and create-with-TagSpecifications must register the resource ARN and its tags), and the TagFilters/ResourceTypeFilters evaluation in the GetResources handler.
Traces: ec2__resourcegroupstaggingapi.internet-gateway-tags-visible-through-get-resources-both-directions, ec2__resourcegroupstaggingapi.vpc-tags-visible-through-get-resources-both-directions, ec2__resourcegroupstaggingapi.vpc-and-security-group-tags-visible-and-type-filtered-through-get-resources, ec2__resourcegroupstaggingapi.resource-type-filter-scopes-ec2-tag-discovery-by-type.

Cause 2 of 3: a tag written by tagging-API TagResources on an EC2 ARN never becomes an EC2 tag — EC2's own DescribeTags does not report it (and the matching UntagResources removal is therefore unobservable natively).
AWS: recorded behavior only for the cross-plane coupling (the Smithy model states only that TagResources takes ResourceARNList (1..20) + Tags (1..50) and answers 200 with FailedResourcesMap). AWS's tagging API is a facade over the owning service's tag plane: after TagResources(ResourceARNList=[arn:aws:ec2:<region>:<account>:vpc/<vpc-id>], Tags={<key>:<value>}) returns 200 with an empty FailedResourcesMap, ec2:DescribeTags filtered on resource-id=<vpc-id> reports that key/value alongside any tag EC2's own CreateTags already set, and UntagResources(TagKeys=[<key>]) removes exactly that key and leaves the natively-written one.
Emulator: TagResources answers 200 with an empty FailedResourcesMap, but DescribeTags for the VPC keeps reporting only the natively-created tag; the key written through the tagging API never appears, so the check exhausts its deadline polling DescribeTags ('Check timed out after 60.0s').
Why: a client that tags through the tagging API and reads back through the owning service (console views, IaC drift detection, EC2 tag-based IAM conditions and tag-filtered Describe* calls) sees the tag silently missing — the write is acknowledged and then lost.
Fix: the TagResources/UntagResources handlers' per-ARN dispatch into the owning service's tag store for EC2 ARNs (vpc, security-group, internet-gateway, subnet, instance), not a tagging-API-private side table.
Traces: ec2__resourcegroupstaggingapi.tag-resources-and-untag-resources-round-trip-through-ec2-native-tags.

Cause 3 of 3: TagResources and UntagResources silently accept a well-formed EC2 ARN whose resource does not exist — FailedResourcesMap comes back empty instead of naming that ARN with EC2's own error.
AWS: Smithy: TagResources/UntagResources answer HTTP 200 with FailedResourcesMap, a map from the ARN that failed to a FailureInfo carrying StatusCode, ErrorCode and ErrorMessage; a batch mixing a live and an absent resource is a partial success, not a whole-batch error. The per-resource failure is the owning service's own error: for an absent VPC, ErrorCode 'InvalidVpcID.NotFound', StatusCode 400 and ErrorMessage "The vpc ID '<vpc-id>' does not exist" — fixed text "The vpc ID '" + "' does not exist" with the requested VPC id taken from the request's ARN; the equivalent holds for an absent internet gateway. The live resource in the same batch must still be tagged and must not appear in the map.
Emulator: FailedResourcesMap is {} for a batch containing an ARN for a VPC/internet gateway that was created and then deleted, i.e. the absent resource is reported as successfully tagged. Observed: "TagResources FailedResourcesMap named [], expected exactly the absent vpc 'arn:aws:ec2:<region>:<account>:vpc/<vpc-id>'" and "FailedResourcesMap named [], expected exactly the absent gateway 'arn:aws:ec2:<region>:<account>:internet-gateway/<igw-id>'". Note the same emulator DOES populate FailedResourcesMap correctly for an absent DynamoDB table, so this is EC2-specific existence checking, not a missing map. (The resolved issue 20261022T081518Z-resource-groups-tagging-api-tagresources-is-over-permissive.md claimed over-permissive absent-ARN handling; it is resolved and does not cover these still-failing checks.)
Why: a caller cannot tell a typo'd or stale ARN from a successful tag. Tagging scripts and compliance tooling that read FailedResourcesMap to decide what to retry or report treat a never-tagged resource as tagged, and the absent ARN must also never enter the tagging index.
Fix: the per-ARN existence resolution in the TagResources/UntagResources handlers (resolve each EC2 ARN against EC2's resource state and emit a FailureInfo with EC2's own error code/message/400 when it does not resolve), plus the guarantee that a failed ARN is not indexed.
Traces: ec2__resourcegroupstaggingapi.tag-resources-nonexistent-vpc-rejected-per-resource, ec2__resourcegroupstaggingapi.tag-and-untag-resources-nonexistent-vpc-rejected-per-resource, ec2__resourcegroupstaggingapi.tag-resources-live-internet-gateway-and-nonexistent-one-partial-rejected.
