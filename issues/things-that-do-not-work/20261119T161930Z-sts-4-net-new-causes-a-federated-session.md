=== Cause 1 of 4: a GetFederationToken session calling IAM is refused AccessDenied instead of being rejected at AUTHENTICATION with InvalidClientTokenId ===
AWS: federated-user credentials are a credential TYPE IAM does not accept at all, so the refusal happens before policy evaluation and is independent of what the session policy or the user's identity policy allows: IAM answers HTTP 403, error code `InvalidClientTokenId`, message `The security token included in the request is invalid` — entirely FIXED text, no request or state values. The same session remains usable elsewhere (e.g. s3:ListAllMyBuckets succeeds when the user policy and the session Policy both allow it) and GetCallerIdentity reports the FederatedUser Arn. Smithy: com.amazonaws.sts#GetFederationToken -> Name (required, @length 2..32, @pattern ^[\w+=,.@-]*$), Policy -> sessionPolicyDocumentType @length 1..2048, output FederatedUser + Credentials; the credential-type refusal itself is recorded behavior only (no modeled STS/IAM error carries it).
Emulator: the IAM call IS refused, but with code `AccessDenied` — a policy verdict — so the federated credential type is being resolved to a principal and then judged on permissions. Replayed assertions: "GetFederationToken sessions must never be able to call IAM APIs, got code='AccessDenied'" and `assert denied_code == "InvalidClientTokenId", f"unexpected code: {denied_code}"` -> "unexpected code: AccessDenied".
Why: the two codes drive opposite client behavior. `InvalidClientTokenId` is terminal and tells an SDK credential provider the credential cannot be used with this service at all; `AccessDenied` reads as a missing grant on a valid credential, so callers (and operators) try to widen the federation policy to call IAM — something AWS can never permit — and the hard guardrail that federated sessions are locked out of IAM is silently not enforced in kind. The second check cannot proceed to its Expiration and minimum-duration legs at all.
Fix: the request-authentication stage for federated-user session credentials in the IAM handler's credential resolution (before authorization): a credential minted by GetFederationToken must fail IAM authentication and serialize HTTP 403 / `InvalidClientTokenId` / the fixed sentence above, while remaining valid for the services that do accept it. Related but distinct open issues that do NOT carry these ids: 20261113T073604Z-sts-a-getfederationtoken-session-policy-refusal-is-attributed.md and 20261115T230737Z-sts-a-getfederationtoken-inline-session-policy-s-allow-be3b4e.md (both about the federated session's authorization messages/grants, not about the credential type being refused by IAM).
Traces: sts.get-federation-token-cannot-call-iam-denied, sts.e2e-federation-token-policy-restricts-then-expires.

=== Cause 2 of 4: GetCallerIdentity signed with credentials STS itself minted is refused SignatureDoesNotMatch ===
AWS: GetCallerIdentity requires no permissions and declares no modeled errors (Smithy: com.amazonaws.sts#GetCallerIdentity -> empty input, output UserId/Account/Arn, errors []). A session minted by AssumeRole — including a chained session, a session of a role under a nested Path, and a session whose role has since been deleted — signs the call successfully and gets HTTP 200 with Arn `arn:aws:sts::<account>:assumed-role/<roleName>/<sessionName>` (role name WITHOUT its path), UserId `<RoleId>:<sessionName>` and the caller's Account; the fixed parts are the ARN/UserId templates, the variable parts are the account, role name, RoleId and session name from the request and state. A signature error is reserved for a request whose computed signature genuinely differs (status 403, code `SignatureDoesNotMatch`, message `The request signature we calculated does not match the signature you provided. Check your AWS Secret Access Key and signing method. Consult the service documentation for details.`).
Emulator: GetCallerIdentity signed with the SecretAccessKey/SessionToken the emulator's own AssumeRole returned raises `botocore.exceptions.ClientError: An error occurred (SignatureDoesNotMatch) when calling the GetCallerIdentity operation: The request signature we calculated does not match the signature you provided...`, aborting all three checks as errors. All three use the identical pattern: mint a session with AssumeRole (pathed role / role chain / plain role), use it, delete the role, and re-read the session's identity. Hypothesis (the recorded fact is the SignatureDoesNotMatch response; the mechanism is inferred): the emulator stops being able to recompute the signing key for such a session — most plausibly because the session's secret is dropped from the session directory when its role is deleted (two of the three checks fail only after a delete) — and the auth layer then reports a signature mismatch rather than a credential decision. Note that even the credential-decision answer would be wrong here: AWS serves this call.
Why: a signature error is the one failure a client must never retry or re-sign around — SDKs surface it as a clock/secret/signing-method bug in the caller, so an operator debugs their own signer instead of the emulator, and any flow that re-reads `GetCallerIdentity` to confirm which identity it is running as (every assume-use-verify journey) dies with a misleading diagnosis instead of the identity it asked for.
Fix: the sigv4 verification path's lookup of a temporary session's signing secret, and the lifetime of that record in the shared session store — verification must resolve the secret for every session STS minted for as long as the credential has not expired, and a session whose principal is no longer resolvable must be answered with the credential-resolution refusal, never with SignatureDoesNotMatch. Related open issue that does NOT carry these ids: 20261110T040626Z-sts-2-net-new-behavioral-root-causes-a-4313eb.md (a TAMPERED session token is answered SignatureDoesNotMatch instead of InvalidClientTokenId); here the token is untampered and AWS answers 200.
Traces: sts.assumed-role-arn-omits-the-role-path-and-honours-a-raised-max-session-duration, sts.chained-session-carries-the-second-role-identity-and-its-deletion-refuses-the-first-session, sts.e2e-role-lifecycle-assume-use-delete-revokes-future-assumption.

=== Cause 3 of 4: a chained AssumeRole gated on the calling session's tags never reaches either verdict ===
AWS: session tags passed to AssumeRole (Smithy: AssumeRoleRequest.Tags -> tagListType @length 0..50, with the trust policy granting sts:TagSession) populate the request context key `aws:PrincipalTag/<key>` for that session, so role A's inline Allow of sts:AssumeRole on role B under `StringEquals {aws:PrincipalTag/department: engineering}` lets an identically tagged session chain into role B (the chained session then reports `:assumed-role/<roleB>/...` from GetCallerIdentity), and replacing that statement with an explicit Deny of sts:AssumeRole on role B refuses a freshly assumed session with HTTP 403, code `AccessDenied`, message `User: arn:aws:sts::<account>:assumed-role/<roleA>/<sessionName> is not authorized to perform: sts:AssumeRole on resource: <roleB ARN>` — fixed text `User: `, ` is not authorized to perform: sts:AssumeRole on resource: `, with the caller session ARN and the target role ARN taken from the request and state. Restoring the Allow re-enables the identical chain. Condition-key semantics are recorded behavior only (the model declares no condition keys).
Emulator: the check never reaches a verdict — reported detail, verbatim and in full: "Error: Check timed out after 60.0s". Every poll in it is bounded and each is preceded by a positive control, so a deadline miss is the verdict. Hypothesis: either the tag-gated Allow never permits the chain (the `_retry_until_success` on the chained AssumeRole, 90 s cap) because `aws:PrincipalTag/<key>` is not published for a tagged session, or the explicit Deny never refuses it (the `_retry_until` for a non-success outcome, 10 s interval) because the chained AssumeRole stays allowed; in both shapes the emulator never produces the transition AWS produces immediately.
Why: tag-gated role chaining is the core ABAC pattern for delegating assumption, and an explicit Deny that never takes effect is an over-permissive authorization decision — a caller that has revoked a chain still gets credentials. Worse, no response ever arrives for the expected outcome, so the divergence is indistinguishable from an outage.
Fix: the request-context construction for session credentials in the shared authorization evaluator (publish `aws:PrincipalTag/<key>` for every tag carried by an AssumeRole session) and the AssumeRole handler's identity-policy evaluation for a session principal (a matched explicit Deny must refuse with the message above). Related OPEN issue that does NOT carry this id: 20261027T130805Z-sts-5-net-new-behavioral-root-causes-temporary.md ("session tags never reach aws:PrincipalTag") — it describes the same family but the report did not bind this check to it, so this check is recorded here and must be re-replayed.

=== Cause 4 of 4: an AssumeRole carrying BOTH PolicyArns and an inline Policy never produces the documented session-policy set algebra ===
AWS: multiple session policy documents on one AssumeRole UNION their Allows, and that union intersects the role's identity policy (Smithy: AssumeRoleRequest.PolicyArns -> policyDescriptorListType, AssumeRoleRequest.Policy -> unrestrictedSessionPolicyDocumentType @length min 1; AssumeRoleResponse.PackedPolicySize -> nonNegativeIntegerType, which AWS reports as a 1..100 percentage). So, for a role allowing ListBucket/GetObject/PutObject, a managed document allowing ListBucket/GetBucketTagging/GetObject and an inline document allowing GetBucketTagging/GetObject: GetObject succeeds; ListBucket (only the PolicyArns document) succeeds; GetBucketTagging (both session documents, NOT the role) is refused HTTP 403 `AccessDenied` with `User: <session ARN> is not authorized to perform: s3:GetBucketTagging on resource: "<bucket ARN>" because no identity-based policy allows the s3:GetBucketTagging action`; PutObject (the role only, neither session document) is refused `AccessDenied` with the session-policy diagnosis `... because no session policy allows the s3:PutObject action` — in both messages `User: `, ` is not authorized to perform: `, ` on resource: `, the quotes and the trailing clause are fixed text, while the session ARN, action and resource ARN come from the request. Controls: the same role with NO session policy may write, and widening the role to include GetBucketTagging makes the previously denied read succeed.
Emulator: the check never reaches a verdict — reported detail, verbatim and in full: "Error: Check timed out after 60.0s". Its polls only wait on error CODES (a wrong MESSAGE would fail fast instead), so a code transition never arrived. Hypothesis: either the union leg stalls (ListBucket, allowed only by the PolicyArns document, stays refused because the two session documents are intersected with each other rather than unioned, so the 240 s `_poll_allowed` never clears) or a cap leg stalls (GetBucketTagging / PutObject stay ALLOWED because the session-policy set does not cap the role, so the 180 s `_poll_denied` for `AccessDenied` never clears). Either shape is a defect in session-policy-set evaluation.
Why: this is how scoped-down credentials are issued in practice (a managed policy ARN plus a per-request inline document). If the union is not taken, legitimately granted actions are refused; if the cap is not applied, a session keeps permissions the caller deliberately removed — a privilege-escalation-shaped divergence — and either way the client gets no verdict inside its budget.
Fix: the AssumeRole handler's session-policy assembly (union the Allows of PolicyArns documents and the inline Policy into ONE session-policy set, and report PackedPolicySize as a 1..100 percentage that grows with the documents supplied) and the data-plane authorization gate that intersects that set with the role's identity policy, including the `because no session policy allows the <action> action` diagnosis for an action only the session set withholds. Already-resolved issue on the same mechanism, which does NOT cover this failure: 20261029T061503Z-sts-a-managed-session-policy-passed-by-assumerole.md; the OPEN issue 20261117T190411Z-sts-4-net-new-causes-session-policy-accessdenied.md owns other session-policy checks but not this id.
Traces: sts.managed-policy-arn-and-inline-session-policy-intersect-to-the-narrower-of-the-two.
