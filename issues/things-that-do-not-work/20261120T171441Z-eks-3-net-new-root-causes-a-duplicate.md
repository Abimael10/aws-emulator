# eks: 3 net-new root causes — a duplicate CreateFargateProfile is InvalidRequestException not ResourceInUseException, a pod execution role without the eks-fargate-pods trust is accepted, and a cluster vanishes the instant DeleteCluster is accepted instead of reading DELETING

> _Note: this issue was identified against the code base at commit `3fc1bb2776bd84c02126163be463ba1779e82c7d`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
CreateFargateProfile

## Description
Three net-new root causes surviving under the `eks` heading of the behavioral suite after every ALREADY-FILED and OWNED failure is accounted for. All cluster names, profile names, role ARNs and subnet ids quoted below are template slots filled from the request or from the emulator's own state — never literal requirements.

Cause 1 of 3: CreateFargateProfile under a name the cluster already holds is refused with the wrong error class AND the wrong message.
  AWS: Smithy: CreateFargateProfile (POST /clusters/{clusterName}/fargate-profiles) — the model's error list for this operation is ClientException/InvalidParameterException/InvalidRequestException/ResourceLimitExceededException/UnsupportedAvailabilityZoneException (400) and ServerException (500); it does NOT list the conflict error, so this is recorded behavior only. Recorded behavior: a second CreateFargateProfile naming a profile that already exists on the same cluster is refused with error code `ResourceInUseException` (the shape this same model carries at @httpError 409, as DeleteCluster's error list shows) and the message "A Fargate Profile already exists with this name in this cluster." — that whole sentence is fixed text, with NO variable part: it names neither the profile nor the cluster.
  Emulator: the refusal carries code `InvalidRequestException` (400) with the emulator-authored message "Fargate Profile already exists with name: <fargateProfileName> and cluster name: <clusterName>" (see services/service-com-amazonaws-eks-awswesleyfrontend/src/ops/create_fargate_profile.rs, the duplicate-name branch around the `state.fargate_profiles.get(...)` lookup, whose comment states "This operation models no conflict error" and deliberately picks InvalidRequestException).
  Why: ResourceInUseException is the signal a client uses to recognise "this profile is already there" — it is the retry/idempotency discriminator for CDK, Terraform and controllers that re-drive a create after a timeout. Against the emulator the same situation looks like a malformed/invalid request (InvalidRequestException), which those clients treat as a permanent template error and surface as a deploy failure instead of adopting the existing profile; code-based matching and the message-based matching in runbooks both fail.
  Fix: CreateFargateProfile's handler (the duplicate-name branch in create_fargate_profile.rs) — refuse the name conflict with ResourceInUseException and EKS's fixed sentence.
  Traces: eks.fargate-profile-full-lifecycle.

Cause 2 of 3: CreateFargateProfile accepts a podExecutionRoleArn whose trust policy does not trust eks-fargate-pods.amazonaws.com.
  AWS: Smithy: CreateFargateProfile.podExecutionRoleArn is required and documented as "the Pod execution role ... allows Fargate infrastructure to register with your cluster as a node"; the operation models InvalidParameterException (400). Recorded behavior: when the named role's trust policy does not carry the eks-fargate-pods.amazonaws.com service principal, the create is refused 400 InvalidParameterException with the message "Misconfigured PodExecutionRole Trust Policy; Please add the eks-fargate-pods.amazonaws.com Service Principal" — the entire sentence is fixed text, with no variable part — and no profile is left behind (DescribeFargateProfile is ResourceNotFoundException "The requested resource does not exist." and ListFargateProfiles does not list the name). The check isolates this to the trust rule by passing genuinely PRIVATE subnets (the public-subnet refusal, which runs first in the same check, now passes).
  Emulator: the create SUCCEEDS with a role whose trust policy names only ec2.amazonaws.com (the node role) — "expected the call to fail, but it succeeded". The handler's only check on this member is the pass-role authorization (`state::pass_role_refusal(&input.pod_execution_role_arn)`), which judges the ARN alone; nothing resolves the role in IAM and inspects its AssumeRolePolicyDocument.
  Why: a Fargate profile AWS would never create is recorded as ACTIVE, so the misconfiguration is not discovered at create time; on real AWS the same template fails immediately, while against the emulator it deploys and the pods it selects can never register as nodes. A client validating its pod execution role by attempting the create gets a false pass.
  Fix: CreateFargateProfile's validation in create_fargate_profile.rs — after the pass-role check and the cluster resolution, resolve podExecutionRoleArn in IAM and refuse with InvalidParameterException and EKS's fixed sentence unless its trust policy allows sts:AssumeRole for eks-fargate-pods.amazonaws.com.
  Traces: eks.fargate-profile-public-subnet-rejected.

Cause 3 of 3: an accepted DeleteCluster removes the cluster synchronously, so an independent DescribeCluster right after it answers 404 instead of reporting DELETING.
  AWS: Smithy: DeleteCluster (DELETE /clusters/{name}) returns the Cluster and models ResourceNotFoundException (404); DescribeCluster (GET /clusters/{name}) returns the Cluster and models ResourceNotFoundException (404). AWS accepts DeleteCluster with 200 and cluster.status DELETING, and the cluster REMAINS describable for the whole (multi-minute) deletion: an independent DescribeCluster on the same name returns 200 with cluster.status DELETING and the same ARN, and only once the deletion finishes does the name answer 404 ResourceNotFoundException ("No cluster found for name: <name>." — fixed text "No cluster found for name: " plus the requested name and the trailing period).
  Emulator: DeleteCluster's own response does report DELETING, but the very next DescribeCluster for that name raises ResourceNotFoundException "No cluster found for name: <name>." — the handler (services/service-com-amazonaws-eks-awswesleyfrontend/src/ops/delete_cluster.rs) removes the record from `clusters` and the ARN index inside the same lock and then calls `finish_cluster_deletion` before answering, so the cluster is gone the moment the call returns and the DELETING state it just reported is unobservable to any reader.
  Why: every client that drives an EKS teardown polls DescribeCluster until it 404s (that is the documented wait pattern, and what the CLI/CDK/Terraform waiters do). Against the emulator the resource is absent at once, so a DELETING phase never exists: waiters that require seeing DELETING before "gone" never see it, and any code that distinguishes "deleting" from "never existed"/"already deleted" — including re-creating the name — gets the wrong answer, with a different status class (404 vs 200) at the same instant. Open issue 20261111T132907Z-eks-5-net-new-root-causes-a-losing.md is the nearest neighbour: its Cause 1 covers a LOSING concurrent DeleteCluster being answered 404 instead of 409, and its Issue-Trace-Ids list this check under the (now-passing) public-subnet key; it does not cover DescribeCluster on a cluster whose deletion was accepted, which is what this cause names. Both share the synchronous-removal root and should be closed together.
  Fix: DeleteCluster's state transition in delete_cluster.rs plus the cluster state machine — keep the cluster record in the store with status DELETING when the delete is accepted, release what it owns in the background, and only then remove it so DescribeCluster/ListClusters report DELETING for the deletion window and 404 afterwards.
  Traces: eks.delete-cluster-blocked-by-nodegroup-dependency.
