# sagemaker: 7 net-new causes — a deleted App is purged instead of staying Deleted for 24h, DeleteDomain ignores UserProfiles, a Pending Domain accepts CreateUserProfile, KernelGateway is accepted, and three refusal messages diverge

> _Note: this issue was identified against the code base at commit `6970f21b7283988b5371627e3c9438f5aa65b548`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
DeleteApp

## Description
SEVEN net-new root causes in the SageMaker AI Studio App / UserProfile / Domain control-plane surface. All seven must be closed before this issue is submitted.

Cause 1 of 7: DeleteApp purges the App record, so the Deleting/Deleted statuses are never observable and a re-delete answers ResourceNotFound.
AWS: an App's lifecycle runs Pending -> InService -> (DeleteApp) -> Deleting -> Deleted, and the record is RETAINED after deletion — DescribeApp and ListApps keep answering for it for 24 hours, reporting Status=Deleted (Smithy: DescribeApp output Status -> AppStatus enum, values Deleted | Deleting | Failed | InService | Pending; DescribeApp models only ResourceNotFound). While the App is still Deleting, a second DeleteApp is refused with HTTP 400, error code ValidationException, message `App [<AppName>] is already being deleted. Wait until the app is deleted.`; once it has settled on Deleted, the refusal is HTTP 400 ValidationException `App [<AppName>] has already been deleted. For tracking purposes, apps are available in the ListApps API results for only 24 hours after deletion.` In both messages the only variable part is the request's AppName; the rest is fixed text for that error class. (The 24h retention and the two sentences are recorded behavior: the model declares only ResourceInUse/ResourceNotFound for DeleteApp, so these refusals travel as the service-common ValidationException.)
Emulator: DeleteApp removes the record from the store outright, so every later read of that key is HTTP 400 ResourceNotFound with message `App [<app ARN>] does not exist.` — the lifecycle never shows Deleting or Deleted, ListApps drops the app immediately, and a second DeleteApp is ResourceNotFound instead of ValidationException. The handler's own module doc states this deliberately ("The record is RELEASED here rather than parked in AppStatus's Deleting and then Deleted").
Why: a client that polls DescribeApp after DeleteApp to watch the teardown settle (the documented pattern) gets an exception instead of Status=Deleted and cannot distinguish "deleted" from "never existed"; idempotent/retrying teardown code that treats ValidationException-"already deleted" as success takes the ResourceNotFound branch instead, and any audit flow that lists recently-deleted apps within the 24h window sees nothing.
Fix: DeleteApp's handler plus the App record in the sagemaker crate's state — park the record in Deleting, let the clock settle it to Deleted, retain it for the retention window, have DescribeApp/ListApps report it, and raise the two ValidationException sentences above from DeleteApp for the Deleting and Deleted states (reserve ResourceNotFound for a key nothing ever created).
Traces: sagemaker.app-create-delete-lifecycle, sagemaker.app-lifecycle-in-service-to-deleted, sagemaker.app-lifecycle-state-transitions, sagemaker.create-app-lifecycle-transitions, sagemaker.delete-app-already-deleted-wrong-state-rejected, sagemaker.delete-app-double-delete-rejected.

Cause 2 of 7: CreateApp's duplicate-app refusal carries an "already exists" message instead of AWS's status-based wording.
AWS: CreateApp for a DomainId/UserProfileName/AppType/AppName tuple that is already running is refused with HTTP 400 and the modeled ResourceInUse (Smithy: CreateApp errors ResourceInUse, ResourceLimitExceeded; ResourceInUse.Message -> FailureReason @length 0..1024). The message names the app's ARN and the status it is currently in: fixed text `App [` ... `] is currently in [` ... `] status. To restart the App, wait until it is in Deleted or Failed status.`, with the app ARN (built from region, account, DomainId, owner, AppType, AppName) and the app's CURRENT AppStatus as the only variable parts.
Emulator: answers ResourceInUse/400 but with the message `App [<app ARN>] already exists.` — the status clause and the remediation sentence are absent, and the message is the same regardless of what state the existing app is in.
Why: the code is right but the message is the only place AWS reports WHY the create was refused and what the caller must wait for; a client (or a human reading a log) that branches on, or surfaces, the current-status clause gets nothing to act on, and the refusal cannot be told apart from a name collision with an already-terminated app.
Fix: CreateApp's duplicate-key refusal in the sagemaker crate — word the ResourceInUse message from the stored app's current status using the sentence above.
Traces: sagemaker.create-app-already-running-resource-in-use.

Cause 3 of 7: CreateApp accepts the deprecated AppType KernelGateway.
AWS: KernelGateway is still a member of the AppType enum (Smithy: AppType values JupyterServer | KernelGateway | DetailedProfiler | TensorBoard | CodeEditor | JupyterLab | RStudioServerPro | RSessionGateway | Canvas), but the service has withdrawn it and refuses every CreateApp naming it, before any app is created. Recorded behavior: HTTP 400, error code ValidationException, message `Invalid AppType [KernelGateway]. This AppType has been deprecated.` — fixed text `Invalid AppType [` ... `]. This AppType has been deprecated.` with the request's AppType as the only variable part. (Recorded behavior only: the model marks nothing deprecated, so the refusal travels as the service-common ValidationException.)
Emulator: answers HTTP 200 with a CreateAppResponse and an AppArn, and the app then appears in ListApps, so a KernelGateway app is created and billed-looking state accumulates for an app type AWS will never run.
Why: a client relying on AWS's refusal to drive users off the deprecated app type gets a "successful" app that behaves nothing like AWS; migration checks that assert the refusal pass against AWS and fail here, and the error-handling branch for a withdrawn app type is never exercised.
Fix: CreateApp's input validation in the sagemaker crate — refuse AppType=KernelGateway with ValidationException/400 and the sentence above, ahead of any state write.
Traces: sagemaker.domain-user-profile-app-teardown-cascade.

Cause 4 of 7: CreateUserProfile's duplicate-name refusal message is ARN-shaped instead of naming the profile name and its domain.
AWS: a second CreateUserProfile for a UserProfileName already present in the domain is refused with HTTP 400 and the modeled ResourceInUse (Smithy: CreateUserProfile errors ResourceInUse, ResourceLimitExceeded). The message is fixed text `A UserProfile with name '` ... `' already exists in Domain ` ... `.` with the request's UserProfileName and the DomainId (the bare `d-…` id, not an ARN) as its variable parts.
Emulator: answers ResourceInUse/400 with `UserProfile [<user-profile ARN>] already exists.` — a different sentence built from the profile ARN, produced by the crate's shared `user_profile_already_exists(&arn)` helper (services/service-com-amazonaws-sagemaker-sagemaker/src/ops/create_user_profile.rs:248-253).
Why: the message is a requirement of the error class; tooling and users that parse or display AWS's wording (quoted name, domain id) see neither, and the emulator's sentence is indistinguishable from the App-level collision message, so a generic handler cannot tell which resource collided.
Fix: CreateUserProfile's duplicate-key refusal and the shared message helper in the sagemaker crate — word the ResourceInUse message as above from the request's UserProfileName and DomainId.
Traces: sagemaker.create-user-profile-duplicate-name-denied, sagemaker.create-user-profile-duplicate-name-rejected.

Cause 5 of 7: CreateUserProfile's unknown-domain refusal names the domain by ARN (with a trailing period) instead of the DomainId the request supplied.
AWS: CreateUserProfile against a DomainId this account holds no domain under is refused with HTTP 400 ValidationException (the model declares no not-found error for the operation, so the service-common error carries it) and the message is fixed text `Domain [` ... `] does not exist` with the request's DomainId — the bare `d-…` value — as its only variable part, and no trailing period. AWS words the same fact differently per reader: DescribeDomain's ResourceNotFound uses the domain ARN and a trailing period (`Domain [arn:aws:sagemaker:<region>:<account>:domain/<DomainId>] does not exist.`), which is why one shared sentence cannot serve both.
Emulator: refuses with ValidationException but the message is `Domain [arn:aws:sagemaker:<region>:<account>:domain/<DomainId>] does not exist.` — the ARN form plus a period, because the handler calls the crate's single `crate::state::domain_not_found(&region, &input.domain_id)` helper (create_user_profile.rs:191-198) that the describe/delete readers also use.
Why: a client that echoes or matches the refusal text sees an ARN where AWS put the id it passed, and the existence check cannot be told from the not-found wording of the other readers; message-equality assertions on this error class fail.
Fix: CreateUserProfile's unknown-domain refusal in the sagemaker crate — give this error class its own message worded from the request's DomainId, rather than reusing the ARN-shaped domain-not-found helper.
Traces: sagemaker.create-user-profile-missing-domain-rejected.

Cause 6 of 7: DeleteDomain succeeds while the domain still has UserProfiles.
AWS: DeleteDomain requires the domain to be empty — "All of the members of the domain must be deleted first" — and a domain that still holds a UserProfile is refused with HTTP 400 and the modeled ResourceInUse (Smithy: DeleteDomain errors ResourceInUse, ResourceNotFound), message fixed text `Unable to delete Domain [` ... `] because UserProfile(s) are associated with it.` with the domain's ARN as its only variable part. Nothing is deleted: the domain and the profile are both still InService afterwards. The positive control is that deleting the profile first and then the domain succeeds.
Emulator: answers HTTP 200 (empty DeleteDomainResponse) and begins the domain teardown while the profile is still there. The handler only asks `store.domain_holds_apps(&input.domain_id)` (services/service-com-amazonaws-sagemaker-sagemaker/src/ops/delete_domain.rs:168-212) and has no equivalent user-profile precondition.
Why: this is a destructive overly-permissive path — a client whose delete AWS would have refused loses the domain, and every UserProfile record left hanging off it addresses a domain no reader resolves. Cleanup code that relies on the refusal to order its teardown (profiles, then domain) never runs, and the modeled ResourceInUse branch is unreachable.
Fix: DeleteDomain's preconditions in the sagemaker crate — extend the in-use check beside the existing apps check to refuse while the domain holds any UserProfile, with ResourceInUse/400 and the sentence above, leaving domain and profile untouched. (Distinct from the open issue '20261113T100553Z-sagemaker-deletedomain-never-removes-the-studio-domain-describedomain.md', which is about a domain that is NOT removed after an accepted delete; this cause is the delete being accepted at all.)
Traces: sagemaker.domain-delete-with-active-user-profile-rejected.

Cause 7 of 7: CreateUserProfile is accepted while the Domain is still Pending.
AWS: a UserProfile can only be created in a settled domain; while the domain's Status is Pending the call is refused with HTTP 400 ValidationException and the message fixed text `Unable to create UserProfile [` ... `] because Domain [` ... `] is not in InService.`, whose variable parts are the would-be profile's ARN (region, account, DomainId, UserProfileName) and the domain's ARN. Once the domain reaches InService the identical CreateUserProfile is accepted (positive control). (Recorded behavior: CreateUserProfile models only ResourceInUse/ResourceLimitExceeded, so the state refusal travels as the service-common ValidationException.)
Emulator: accepts the call with HTTP 200 and a UserProfileArn while DescribeDomain still reports Status=Pending. The handler resolves the DomainId and the domain's AuthMode but weighs no domain status at all (create_user_profile.rs:182-198 explicitly leaves the domain's lifecycle state out of the preconditions).
Why: a client that creates profiles immediately after CreateDomain sees a success here and a ValidationException on AWS, so the retry-until-InService loop every real integration needs is never exercised; profiles are attached to a domain whose networking/EFS provisioning has not resolved.
Fix: CreateUserProfile's preconditions in the sagemaker crate — gate the create on the resolved domain status (after the clock settles it) and raise ValidationException/400 with the sentence above while the domain is not InService.
Traces: sagemaker.domain-pending-refuses-user-profile-space-and-presigned-url.
