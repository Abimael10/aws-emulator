## Description
This issue bundles 2 distinct net-new root causes on the RDS DBInstance role-association (s3Import) surface, both reached through CloudFormation. A fixer must close BOTH before submitting. Neither check is marked ALREADY FILED or OWNED in the replay report. Related open issues that do NOT carry these two checks' replay keys and therefore do not cover them: 20261114T102206Z-rds-s3-4-net-new-causes-aws-rds.md (that one is about an AWS::RDS::DBCluster s3Import FeatureName on aurora-mysql, StartExportTask's S3 action name, cluster endpoint hosts and non-settling long-running states), 20261114T214055Z-rds-s3-the-mixed-trust-aurora-role-association.md (a DB *cluster* association that never reaches a verdict) and 20261113T114936Z-cloudformation-sagemaker-a-resource-handler-s-failure-reason.md (a SageMaker handler reason that drops the whole SDK service/status/request-id suffix, not the SDK-attempt-count segment described in Cause 2).

Smithy consulted (services/service-com-amazonaws-rds-amazonrdsv19/smithy-model/com-amazonaws-rds-amazonrdsv19.json): AddRoleToDBInstance input DBInstanceIdentifier/RoleArn/FeatureName all required, empty output; its modelled errors are DBInstanceNotFoundFault (404, awsQueryError DBInstanceNotFound), DBInstanceRoleAlreadyExistsFault (400), DBInstanceRoleQuotaExceededFault (400) and InvalidDBInstanceStateFault (400) — none of them covers a role ARN that does not exist, so AWS answers that condition with the query protocol's service-common client refusal at HTTP 400. DescribeDBInstances models DBInstanceNotFoundFault (404, awsQueryError code DBInstanceNotFound).

---
Cause 1 of 2: a CloudFormation stack whose AWS::RDS::DBInstance carries AssociatedRoles [{FeatureName: "s3Import", RoleArn: <an ARN of a role that was never created>}] reaches CREATE_COMPLETE instead of failing the resource and rolling the stack back.
AWS: the AWS::RDS::DBInstance handler associates each AssociatedRoles entry through RDS (AddRoleToDBInstance / the create's role-integration step). RDS validates the role before persisting anything: an ARN that names no existing role is refused with HTTP 400 and the message "IAM role ARN value is invalid or does not include the required permissions for: AWS_ROLE_INTEGRATION" (the model has no dedicated fault for it — see the Smithy note above — so this is the service-common 400 client refusal). CloudFormation therefore records a CREATE_FAILED event on the DBInstance resource whose ResourceStatusReason is 'Resource handler returned message: "IAM role ARN value is invalid or does not include the required permissions for: AWS_ROLE_INTEGRATION (Service: Rds, Status Code: 400, Request ID: <rds request id>) (SDK Attempt Count: <n>)" (RequestToken: <cfn request token>, HandlerErrorCode: InvalidRequest)' and the stack settles in ROLLBACK_COMPLETE. Because the refusal happens before RDS persists a DBInstance record, DescribeDBInstances on that identifier then answers Error.Code DBInstanceNotFound with the message "DBInstance <identifier> not found." (fixed text "DBInstance " and " not found."; the identifier comes from the request). That the emulator itself emits exactly that AWS_ROLE_INTEGRATION sentence on the sibling check in Cause 2 confirms the wording and the HandlerErrorCode are already known to this code base — they are simply not applied when the role is merely absent.
Emulator: the stack reaches CREATE_COMPLETE. The check fails with `AssertionError: expected stack <stack> to be rejected (nonexistent role ARN) but it reached CREATE_COMPLETE -- the target accepted an IAM role ARN that does not exist`, so the DBInstance is created and the bogus association is accepted. No CREATE_FAILED event on the DBInstance resource is produced at all.
Why: an over-permissiveness defect. A template that AWS refuses deploys clean against the emulator, so a stack that cannot exist in production passes pre-production validation and the caller never learns that the role it named does not exist. Worse, the caller is handed a DB instance whose s3Import association can never work, and a later AWS deploy of the same template fails where the emulator said it succeeded.
Fix: existence (and trust/permission) validation of the role named in an AssociatedRoles entry, in the RDS role-association handler behind AWS::RDS::DBInstance (AddRoleToDBInstance and the DBInstance create path that applies AssociatedRoles), plus the CloudFormation resource provider's propagation of that refusal into a CREATE_FAILED event with HandlerErrorCode: InvalidRequest and a stack rollback that leaves no DBInstance record.

---
Cause 2 of 2: when the emulator DOES refuse the association (a role trusted by s3.amazonaws.com instead of rds.amazonaws.com for s3Import), the CloudFormation resource-failure reason it records omits the "(SDK Attempt Count: N)" segment that AWS places inside the quoted handler message.
AWS: the reason recorded on the failed resource is a fixed template with three per-request values. Fixed text, in order: 'Resource handler returned message: "IAM role ARN value is invalid or does not include the required permissions for: AWS_ROLE_INTEGRATION (Service: Rds, Status Code: 400, Request ID: ', then ') (SDK Attempt Count: ', then ')" (RequestToken: ', then ', HandlerErrorCode: InvalidRequest)'. The variable parts are the RDS request id, the SDK attempt count (an integer, at least 1) and the CloudFormation request token — all per-run values, none of them part of the requirement. The stack settles in ROLLBACK_COMPLETE/CREATE_FAILED and no DB instance exists afterwards (DescribeDBInstances -> DBInstanceNotFound, "DBInstance <identifier> not found.").
Emulator: everything matches except that the ' (SDK Attempt Count: <n>)' segment between the Request ID parenthetical and the closing quote is absent. Recorded reason: 'Resource handler returned message: "IAM role ARN value is invalid or does not include the required permissions for: AWS_ROLE_INTEGRATION (Service: Rds, Status Code: 400, Request ID: 026af4b4-a29b-76d2-0a6f-03cf48eac0ee)" (RequestToken: f6c5a675-b5d9-d299-0226-c6a87c9cf21e, HandlerErrorCode: InvalidRequest)' — the request id and token shown are that run's values, the missing fixed text is ' (SDK Attempt Count: ' ... ')'. The status assertion and the HandlerErrorCode assertion both pass; only the reason text diverges.
Why: the resource-status reason is the only machine-readable account a client gets of why a stack rolled back. Tooling and operators that parse or match AWS's handler-reason template (the SDK-attempt-count segment is how callers tell a first-attempt refusal from one that was retried) do not recognise the emulator's shortened reason, so a validation rejection cannot be distinguished from a throttled or retried failure.
Fix: the CloudFormation resource-handler failure-reason formatter for RDS role-integration refusals — the component that wraps an RDS SDK error into the 'Resource handler returned message: "..." (RequestToken: ..., HandlerErrorCode: ...)' reason must emit the SDK attempt count alongside Service/Status Code/Request ID.
