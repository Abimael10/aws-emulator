# rds: 2 net-new causes — a custom DB cluster endpoint never becomes observably 'available', and a READER custom endpoint with StaticMembers never pins a session to that member

> _Note: this issue was identified against the code base at commit `74429669c22f4248895c195473d5b207144eaced`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
CreateDBClusterEndpoint

## Description
Two net-new root causes on the rds surface, found by replaying the behavioral suite (simparity-behavioral-aws-v1) against the emulator built from this checkout. Each is independent and must be closed on its own before this issue is submitted. Both present in the replay as the per-check budget expiring with no assertion reached ('Check timed out after 60.0s'), because each sits behind a status progression the client must observe before it can assert anything. Neither of the two checks below was reported ALREADY FILED (blocked by an unimplemented scaffold stub) nor OWNED by an open issue.

Cause 1 of 2: a custom DB cluster endpoint's status progression is not observable to a polling client, so the duplicate-identifier contract of CreateDBClusterEndpoint is never reachable.
AWS: Smithy (services/service-com-amazonaws-rds-amazonrdsv19/smithy-model/com-amazonaws-rds-amazonrdsv19.json) models CreateDBClusterEndpoint with required DBClusterIdentifier, DBClusterEndpointIdentifier and EndpointType plus optional StaticMembers/ExcludedMembers/Tags, output DBClusterEndpoint carrying Status, EndpointType, CustomEndpointType, Endpoint and DBClusterEndpointArn, and errors DBClusterEndpointAlreadyExistsFault (HTTP 400), DBClusterEndpointQuotaExceededFault (403), DBClusterNotFoundFault (404), DBInstanceNotFoundFault (404), InvalidDBClusterStateFault (400), InvalidDBInstanceStateFault (400). The endpoint is answered in Status 'creating' and becomes 'available' on its own, reported by DescribeDBClusterEndpoints under its identifier. A second CreateDBClusterEndpoint naming an identifier already in use is refused DBClusterEndpointAlreadyExistsFault, HTTP 400, with the message whose fixed text is "An endpoint with the identifier " ... " already exists: " and whose variable parts are the requested DBClusterEndpointIdentifier and the existing endpoint's Endpoint (DNS address) taken from state — i.e. "An endpoint with the identifier <DBClusterEndpointIdentifier> already exists: <Endpoint>". The refusal must leave exactly ONE endpoint object under that identifier, and the name must be released by DeleteDBClusterEndpoint so the identical create then succeeds.
Emulator: starting from a CreateDBCluster(Engine=aurora-postgresql, ServerlessV2ScalingConfiguration) that must itself reach Status 'available', the walk create → DescribeDBClusterEndpoints Status=='available' → duplicate create refused → describe shows one endpoint → delete → describe shows none → identical create succeeds → a second new identifier succeeds never completes inside the per-check budget. The replay carries no refusal, no wrong code and no status value, only the budget expiring, so the duplicate-name refusal, its message and the name-release behaviour are all unverifiable here. Hypothesis: each stage (cluster to 'available', endpoint to 'available', endpoint to gone) stays transient past the first poll a client makes, costing a full poll interval each (the check polls the cluster every 20 s and the endpoint every 10 s), so the chain cannot finish.
Why: a client that creates a custom endpoint — CloudFormation/CDK deploys, connection-string handoffs, any script that waits for Status=='available' before dialing — blocks instead of getting a usable endpoint, and a client that re-runs a create (idempotent deploy retry, name collision) never sees the DBClusterEndpointAlreadyExistsFault it must handle.
Fix: the custom-cluster-endpoint state machine — the CreateDBClusterEndpoint / DeleteDBClusterEndpoint handlers, their duplicate-identifier validation and the stored endpoint's pending-status transitions in the rds crate's cluster-endpoint state — plus the cluster-availability path the endpoint hangs off, so each step is reported to the next DescribeDBClusterEndpoints.
NOTE: open issue 20261121T224824Z-rds-3-net-new-behavioral-causes-the-custom.md reports the same non-convergence for rds.cluster-endpoint-lifecycle (its cause 1); it does not carry this check's replay key, so this check was not treated as owned and must be re-replayed on its own.
Traces: rds.cluster-endpoint-duplicate-name-rejected.

Cause 2 of 2: a custom READER endpoint with one StaticMembers entry never serves a session pinned to that member, so the static-member routing contract is unobservable.
AWS: CreateDBClusterEndpoint(EndpointType='READER', StaticMembers=[<reader instance id>]) stores a custom endpoint that reports CustomEndpointType 'READER' and keeps exactly the declared StaticMembers list; DescribeDBClusterEndpoints publishes its Endpoint (a DNS address) and the cluster's port. Every connection opened through that endpoint lands on a member of StaticMembers — on Aurora MySQL, SELECT @@aurora_server_id over the session returns that member's DB instance identifier — and that member, being a reader, reports @@innodb_read_only = 1.
Emulator: the check creates an aurora-mysql cluster with a writer and a reader member (PromotionTier=15), polls both members to DBInstanceStatus 'available', creates the custom READER endpoint with StaticMembers=[reader] and then opens native MySQL sessions through the published endpoint — and ends at the per-check budget with no assertion reached: neither StaticMembers, nor CustomEndpointType, nor @@aurora_server_id, nor @@innodb_read_only is ever observed. Recorded behavior only: the replay output is 'Check timed out after 60.0s'.
Why: read-scaling clients point their read traffic at a custom READER endpoint precisely to pin reads to chosen members; against this emulator such a client never gets a reachable, correctly pinned read session, so a read/write split cannot be validated at all.
Fix: the custom-endpoint data plane — the endpoint address CreateDBClusterEndpoint publishes for a custom READER endpoint and the session routing behind it (which cluster member a connection through that endpoint is served by, and that member's read-only session identity), in the rds crate's cluster-endpoint handlers and the Aurora member session it serves.
Traces: rds.aurora-mysql-custom-reader-endpoint-routes-to-static-member.

## Evidence
Behavioral suite replayed against the emulator built from this checkout: 556/709 checks passed (78.4%); service rds 311/411 (76%), 100 failed. Both failures below were reported neither ALREADY FILED nor OWNED.

Cause 1 — rds.cluster-endpoint-duplicate-name-rejected [mismatch]: 'Error: Check timed out after 60.0s'. The check runs: CreateDBSubnetGroup; CreateDBCluster(Engine=aurora-postgresql, MasterUsername, ServerlessV2ScalingConfiguration={MinCapacity:0.5,MaxCapacity:1}, DeletionProtection=False); poll DescribeDBClusters every 20 s for Status=='available'; CreateDBClusterEndpoint(EndpointType='ANY'); poll DescribeDBClusterEndpoints every 10 s for Status=='available'; repeat the identical CreateDBClusterEndpoint and assert Error.Code=='DBClusterEndpointAlreadyExistsFault' and Error.Message=='An endpoint with the identifier <endpoint-id> already exists: <existing Endpoint>'; assert DescribeDBClusterEndpoints returns exactly 1 endpoint under that identifier; DeleteDBClusterEndpoint and poll until it is gone; re-create under the SAME identifier and poll to 'available'; create a second, new identifier and poll to 'available'. No assertion was reached — the budget expired first, so no error code, no message and no status value is recorded; the progression itself is what is missing.

Cause 2 — rds.aurora-mysql-custom-reader-endpoint-routes-to-static-member [mismatch]: 'Error: Check timed out after 60.0s'. The check runs: create a security group for 3306 and a DB subnet group; CreateDBCluster(Engine=aurora-mysql, EngineVersion=<default>, DatabaseName, BackupRetentionPeriod=1); CreateDBInstance writer and CreateDBInstance reader (PromotionTier=15) in that cluster; poll both to DBInstanceStatus=='available'; CreateDBClusterEndpoint(EndpointType='READER', StaticMembers=[<reader id>]); poll DescribeDBClusterEndpoints for Status=='available' and assert StaticMembers==[<reader id>] and CustomEndpointType=='READER'; then open repeated fresh MySQL sessions to the published Endpoint and assert SELECT @@aurora_server_id == <reader id> and SELECT @@innodb_read_only == 1 on five consecutive connections. The budget expires before the first of those assertions.

Note on per-run values: the identifiers, ports, hosts and the 60 s budget are this environment's; the requirements are the endpoint status progression, the DBClusterEndpointAlreadyExistsFault refusal with AWS's message template, and static-member pinning — not any literal value from one run.
