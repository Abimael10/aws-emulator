# ds: 2 net-new causes — the two-way-trust end-to-end flow and the Managed Microsoft AD create→Active→delete lifecycle each reach no verdict, because every clock-owed ds transition settles only AFTER the probe that follows the call that started it

> _Note: this issue was identified against the code base at commit `a11c67ddfc7199c8950e9df279eea2cbb1f1bbbc`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
DescribeDirectories

## Description
Two more ds behavioral checks reach NO verdict in this replay: each is killed with "Check timed out after 60.0s" while asleep inside a poll loop. The emulator answers every request it is asked; what diverges is WHEN a clock-owed state transition becomes observable. Each ds transition the emulator owns (directory Requested/Creating -> Active, Deleting -> gone, trust Creating -> Created, Verifying -> Verified, Deleting -> gone) comes due only AFTER the probe that immediately follows the call that started it, so a client that calls, probes once, then sleeps its poll interval pays one FULL interval per transition. Two to seven such legs exceed the suite's 60 s per-check ceiling before any assertion runs, so none of the contracts these two scenarios exist to pin is exercised at all.

Related open issue that the replay report did NOT mark as owning either of these two checks, and which therefore does not cover them: 20261113T164150Z-ds-3-net-new-causes-the-msad-stage.md (plus its siblings 20261111T120514Z-ds-the-directory-data-access-disable-re-enable-c3f4bd.md, 20261110T232837Z-ds-the-directory-data-access-disable-re-enable.md, 20261107T061500Z-ds-data-access-cycle-check-cannot-fit-its-sixty-second-budget.md, 20261111T085740Z-ds-the-ldaps-enable-disable-and-directory-data.md). Those carry OTHER check ids (ds.directory-data-access-server-enforced-toggle, ds.remove-primary-region-denied, ds.state-machine-trust-create-verify-delete-404, the LDAPS and ds-data toggles) for the same mechanism. The two causes below extend it to the END-TO-END trust flow and to the FULL single-directory lifecycle, which no filed issue names; all of them should be resolved as one work item, but these two check ids must be re-replayed to close this issue.

--- Cause 1 of 2: the end-to-end two-way trust create/verify/delete flow never reaches its assertions (failing check id: ds.e2e-trust-create-verify-delete-flow).
AWS: the walk is modelled. Smithy (services/service-com-amazonaws-directoryservice-directoryservice-20150416/smithy-model/com-amazonaws-directoryservice-directoryservice-20150416.json): TrustState = [Creating, Created, Verifying, VerifyFailed, Verified, Updating, UpdateFailed, Updated, Deleting, Deleted, Failed]; CreateTrust input {DirectoryId @required ^d-[0-9a-f]{10}$, RemoteDomainName @required, TrustPassword @required @sensitive, TrustDirection @required} / output {TrustId ^t-[0-9a-f]{10}$}, errors ClientException(400), EntityAlreadyExistsException(400), EntityDoesNotExistException(400), InvalidParameterException(400), ServiceException(500), UnsupportedOperationException(400); VerifyTrust input {TrustId @required} / output {TrustId}; DeleteTrust input {TrustId @required, DeleteAssociatedConditionalForwarder default false} / output {TrustId}, errors incl. EntityDoesNotExistException; DescribeTrusts input {DirectoryId, TrustIds, NextToken, Limit} / output {Trusts, NextToken}; EntityDoesNotExistException is a client error, httpError 400, members {Message, RequestId}. DirectoryStage = [Requested, Creating, Created, Active, Inoperable, Impaired, Restoring, RestoreFailed, Deleting, Deleted, Failed, Updating], and CreateMicrosoftAD answers with just a DirectoryId — i.e. AWS answers each call BEFORE the transition settles and exposes the walk through DescribeDirectories/DescribeTrusts. For the wall clock there is recorded behavior only: on real AWS a Managed Microsoft AD takes tens of minutes to reach Active, so the 60 s per-check ceiling is this environment's, not AWS's.
Emulator: no status, error-code, message or shape divergence is reported for this check — the only output is "Check timed out after 60.0s". The scenario owes SEVEN clock-owed legs and probes each immediately after the call that starts it: create_microsoft_ad x2 then poll describe_directories for Stage 'Active' at interval 20 s each (40 s owed); create_trust x2 then poll describe_trusts for TrustState in {Created, Verified} at 15 s each (30 s); verify_trust then poll for 'Verified' at 15 s (15 s); delete_trust x2 then poll describe_trusts until the trust is gone/Deleted at 15 s each (30 s) — about 115 s of sleeping owed inside a 60 s ceiling, so the check dies in the second directory wait.
Why: a client gets no verdict on the entire inter-directory trust contract. Unverified are: that both directories report non-empty DnsIpAddrs once Active; that CreateTrust on each side mints a TrustId matching ^t-[0-9a-f]{10}$ and the trust leaves Creating for 'Created'; that VerifyTrust drives the trust to 'Verified' (and never 'VerifyFailed'); that after DeleteTrust the trust stops being served by DescribeTrusts(DirectoryId, TrustIds=[id]); that a SECOND, identical DeleteTrust on the gone id is refused rather than succeeding idempotently, with HTTP 400, Error.Code 'EntityDoesNotExistException' and AWS's wording for that class — fixed text 'Trust: ' + ' does not exist : RequestId: ', with the trust id taken from the request and the RequestId from the response (no single run's literal id or RequestId is part of the requirement); and that the deleted trust is absent from the unfiltered describe_trusts(DirectoryId=...) inventory. A trust that never changed state, or a deleted trust that kept reading back, or an idempotent second delete, would all pass today.

--- Cause 2 of 2: the Managed Microsoft AD Standard create -> Active -> delete -> gone lifecycle never reaches its assertions (failing check id: ds.simple-ad-small-lifecycle-to-active-then-deleted).
AWS: modelled. For the create/delete durations there is recorded behavior only (the check records ~24 minutes to Active on real AWS).
Emulator: again no response divergence is reported for this check, only "Check timed out after 60.0s". Two clock-owed legs at 30 s each — create_microsoft_ad then poll describe_directories until Stage is terminal at interval 30 s, and delete_directory then poll until DescribeDirectories no longer serves the directory at interval 30 s — are exactly the 60 s ceiling, so the check is killed in the second sleep, before the delete-side assertions.
Why: a client gets no verdict on the single most load-bearing ds scenario. Unverified are: that a Standard MicrosoftAD reaches Stage 'Active' and passes only through Requested/Creating/Created on the way; that the DirectoryDescription is fully populated and echoes the request (Type 'MicrosoftAD', Edition 'Standard', derived Size 'Small', Name, ShortName, SsoEnabled false, Alias == DirectoryId, AccessUrl leading with the DirectoryId, LaunchTime and StageLastUpdatedDateTime set with StageLastUpdatedDateTime >= LaunchTime, DesiredNumberOfDomainControllers 2, OsVersion present, RegionsInfo.PrimaryRegion == the caller's Region with no AdditionalRegions, NetworkType 'IPv4' with no DnsIpv6Addrs, and no password echoed back); that DnsIpAddrs are exactly the two private addresses of the directory's own two ENIs, one per subnet, inside the VPC CIDR, in the directory's own security group named '<directoryId>_controllers' with every ingress rule scoped to the VPC CIDR; and the whole delete side — that DeleteDirectory drives the directory to gone, that DescribeDirectories then SUCCEEDS with an EMPTY DirectoryDescriptions list for the deleted id while a well-formed but never-issued id is still REFUSED with HTTP 400 / 'EntityDoesNotExistException' worded as the invalid-id sentence (fixed text 'Invalid directory ID(s): ' + '. : RequestId: ', the id from the request and the RequestId from the response), that a second DeleteDirectory and a GetSnapshotLimits on the deleted id are refused with HTTP 400 / 'EntityDoesNotExistException' worded as the does-not-exist sentence (fixed text "Directory: '" + "' does not exist. : RequestId: ", again id from the request and RequestId from the response), and that deletion releases the directory's ENIs. None of that is exercised today, so a regression in any of it passes unnoticed.

Fix: neither cause is an operation-handler response defect — no ds handler is reported answering wrongly in either check. The owner is the ds state machine's clock-owed-transition contract where it meets the suite's per-check ceiling: either shorten/settle the transition spans ds state applies to the directory-stage chain (Requested/Creating -> Active, Deleting -> gone) and the trust state machine (Creating -> Created, Verifying -> Verified, Deleting -> gone) so a settled value is observable on the client's FIRST probe after the call — accepting that the transient stages/states and the refusals that depend on them (DirectoryUnavailableException and friends) stop being observable, and loosening any in-tree suite that pins them — or the harness's per-check budget and poll intervals for these scenarios.

Traces: ds.e2e-trust-create-verify-delete-flow and ds.simple-ad-small-lifecycle-to-active-then-deleted (both verdict 'mismatch', both with detail "Check timed out after 60.0s", both killed inside a poll helper's time.sleep(interval_s)). Neither is marked ALREADY FILED or OWNED in this replay.
