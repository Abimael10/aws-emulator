# acm__apigateway__s3: a REGIONAL custom domain with mutualTlsAuthentication never enforces (or completes) client-certificate TLS — the mTLS check reaches no verdict and is killed at the 60 s cap

> _Note: this issue was identified against the code base at commit `bcdc3f99d3414a3a6a231e6e8e09ef9d25ae993a`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Description
1 net-new root cause for the acm__apigateway__s3 trio. The replay report marked this failure neither ALREADY FILED nor OWNED, so no open issue carries its replay key. Two open issues describe the neighbouring, non-mTLS legs of the same front door and do NOT cover this one: issues/things-that-do-not-work/20261116T020413Z-acm-apigateway-the-regional-custom-domain-still-reaches.md (service acm__apigateway — plain TLS presentation of the domain's ACM leaf) and issues/things-that-do-not-work/20261117T134237Z-acm-apigateway-apigatewayv2-iam-lambda-r-api-gateway-custom-domains-never-serve-a-mapped.md (a signed GET on a custom domain never answers). This filing records the mutual-TLS contract specifically: the client-certificate half of the handshake and the truststore that decides it, which neither of those issues names. The failure is a HANG, not a refusal, so it is not a reopened refusal.

Cause 1 of 1: a REGIONAL custom domain created with mutualTlsAuthentication produces no observable two-way-TLS behaviour at all. The check is killed with 'Error: Check timed out after 60.0s' having graded none of its four beats, against a trajectory whose own waits are far longer (certificate -> ISSUED 300 s, domainNameStatus -> AVAILABLE 300 s, first trusted-certificate request -> 200 300 s, re-serve after refusals 120 s), so the whole budget was consumed inside one blocking readiness/handshake loop rather than by a wrong field value.

AWS: a REGIONAL custom domain carrying mutualTlsAuthentication is a TLS terminator that REQUESTS and VERIFIES a client certificate against an S3-hosted truststore, and the three outcomes are distinct. Smithy (com.amazonaws.apigateway): CreateDomainName -> POST /domainnames, success 201, errors BadRequestException (400), ConflictException (409), LimitExceededException (429), TooManyRequestsException (429), UnauthorizedException (401). MutualTlsAuthenticationInput$truststoreUri — 'An Amazon S3 URL that specifies the truststore for mutual TLS authentication, for example s3://bucket-name/key-name. The truststore can contain certificates from public or private certificate authorities. To update the truststore, upload a new version to S3, and then update your custom domain name to use the new version. To update the truststore, you must have permissions to access the S3 object.' MutualTlsAuthenticationInput$truststoreVersion — 'The version of the S3 object that contains your truststore. To specify a version, you must have versioning enabled for the S3 bucket.' MutualTlsAuthentication (output) adds truststoreWarnings — 'A list of warnings that API Gateway returns while processing your truststore. Invalid certificates produce warnings. Mutual TLS is still enabled, but some clients might not be able to…'. The structure's own doc states the behaviour: 'If specified, API Gateway performs two-way authentication between the client and the server. Clients must present a trusted certificate to access your API.' Beyond the model, recorded behavior only (reference: https://docs.aws.amazon.com/apigateway/latest/developerguide/rest-api-mutual-tls.html): (a) a SigV4-signed GET to the published regionalDomainName on port 443 with ClientHello SNI = the custom domain, presenting a leaf signed by a CA present in the truststore object, is served by the mapped stage — here HTTP 200 with the MOCK integration's response body; (b) the same request presenting NO client certificate is refused AT THE TLS LAYER and never gets an HTTP response — the server resets the connection, tears it down without an alert, closes it with no response, or sends a certificate-required alert (TLS 1.3 certificate_required / TLS 1.2 handshake_failure); (c) a request presenting a leaf signed by a CA that is NOT in the truststore completes the handshake and is then refused by the HTTP layer with status 403, body exactly {"message":"Forbidden"} and response header x-amzn-ErrorType: ForbiddenException. In (c) the whole message is fixed text — the envelope carries no domain name, no certificate subject and no member name, which is what keeps it distinct from an authorization failure of the method's AWS_IAM authorizer; (d) after (b) and (c) the trusted path still serves 200, i.e. the refusals do not wedge the domain.

Emulator: nothing on the far side of the control plane is observable, and the mTLS configuration is inert by construction. No completed handshake, no TLS alert, no connection reset, no HTTP status line, no Forbidden envelope and no x-amzn-ErrorType header is ever produced — the check is killed at the harness ceiling with none of the four beats graded. CreateDomainName accepts mutualTlsAuthentication, length-bounds truststoreUri/truststoreVersion and stores them verbatim on the DomainName record, then reports them back; the handler states in its own comment that 'The truststore is an S3 object this emulator does not fetch, so nothing read one and there is nothing to warn about' and hard-codes truststoreWarnings to None. Nothing ever reads the S3 object, so no trust anchor set exists; and the custom-domain front door terminates TLS with one static process certificate and no per-connection resolver and never requests a client certificate, so the three outcomes above collapse into one: a connection that neither completes nor is refused. Hypothesis: the dial to port 443 on the resolved/published gateway host is refused or hangs and the check's _poll_request retry loop spins until the cap; the alternative — a handshake that completed and served the wrong status — would have failed on the 200/403/body assertions rather than timing out, which it did not.

Why: a client relying on AWS's behavior gets no mutual-TLS enforcement and cannot tell that it has none. mutualTlsAuthentication becomes write-only config: it round-trips through CreateDomainName/GetDomainName so a deployment's assertions on the stored value pass, while the data plane admits (or rather, answers nothing to) every client regardless of its certificate. The two security-relevant negatives are both lost — a caller with no client certificate is not refused at the TLS layer, and a caller holding a certificate from an untrusted CA is not refused 403 ForbiddenException — so a test suite or a production guardrail that proves 'only certificates from our CA reach this API' proves nothing here. Because the failure mode is a HANG rather than a refusal, nothing distinguishes 'not ready yet' from 'will never enforce', and any client or CI job probing the domain blocks instead of passing or failing. truststoreWarnings being permanently absent additionally hides the one signal AWS gives about an unreadable truststore.

Fix: the apigateway REGIONAL custom-domain data plane and its mutual-TLS seam, plus the core listener/TLS plumbing it depends on. The front door published as regionalDomainName must be reachable on port 443, must select and present the leaf named by regionalCertificateArn by ClientHello SNI, and when the DomainName record carries mutualTlsAuthentication it must (1) resolve truststoreUri/truststoreVersion to the S3 object through the emulator's own S3 state and parse the PEM bundle into a trust anchor set, reporting unparsable entries in truststoreWarnings, (2) request a client certificate on every connection and refuse a connection presenting none at the TLS layer, and (3) complete the handshake for a presented certificate that chains to no anchor and have the HTTP layer answer 403 with the {"message":"Forbidden"} envelope and the x-amzn-ErrorType: ForbiddenException header, without wedging subsequent trusted requests. The control-plane record already carries every field needed; only the enforcement and the listener reachability are missing. File and line citations are under Traces.

Traces: acm__apigateway__s3.regional-custom-domain-mutual-tls-enforces-trusted-client-certificates (mismatch, 'Error: Check timed out after 60.0s'). Component files: services/service-com-amazonaws-apigateway-backplanecontrolservice/src/ops/create_domain_name.rs — lines 242-252 length-bound mutualTlsAuthentication.truststoreUri/truststoreVersion and nothing else validates or resolves them; lines 644-654 store the requested truststore URI/version and hard-code truststore_warnings: None with the comment that the S3 object is never fetched; line 364 echoes the stored record back on read. services/service-com-amazonaws-apigateway-backplanecontrolservice/src/service/custom_domain_socket.rs (942 lines) — the custom-domain front door, with no client-certificate request, no truststore verification and no SNI-driven certificate resolver.

## Evidence
Expected (AWS): the account's DNS-baseline public hosted zone yields an apex; a versioned S3 bucket holds truststore.pem containing a private root CA's certificate; acm:RequestCertificate(DomainName=<label>.<apex>, ValidationMethod=DNS) plus the published DomainValidationOptions[0].ResourceRecord written into that zone reaches Status=ISSUED; a REGIONAL REST API with disableExecuteApiEndpoint=true exposes GET / with authorizationType=AWS_IAM over a MOCK integration returning a fixed JSON body, deployed to stage 'prod'; apigateway:CreateDomainName(domainName=<domain>, endpointConfiguration={types:[REGIONAL]}, regionalCertificateArn=<issued>, securityPolicy=TLS_1_2, mutualTlsAuthentication={truststoreUri: s3://<bucket>/truststore.pem, truststoreVersion: <object version>}) answers 201; a base path mapping binds the API's prod stage; GetDomainName reaches domainNameStatus=AVAILABLE with a non-empty regionalDomainName. Then, dialling that host on port 443 with SNI/Host = <domain>: (1) presenting a leaf signed by the truststore's CA and SigV4-signed for execute-api is answered HTTP 200 with the integration's exact body; (2) presenting NO client certificate gets NO HTTP response — the connection is reset, closed with no bytes, or failed with a certificate-required alert (ssl reason in {TLSV13_ALERT_CERTIFICATE_REQUIRED, SSLV3_ALERT_HANDSHAKE_FAILURE}); (3) presenting a leaf signed by a DIFFERENT, untrusted CA completes the handshake and is answered HTTP 403 with body exactly {"message":"Forbidden"} and header x-amzn-ErrorType: ForbiddenException; (4) the trusted request is served 200 again afterwards.

Actual (emulator): no terminal assertion is reached. Replay verdict: mismatch, 'Error: Check timed out after 60.0s'. None of beats (1)-(4) is graded: no 200 with the integration body, no TLS-layer refusal for the certificate-less request, no 403 / {"message":"Forbidden"} / x-amzn-ErrorType: ForbiddenException for the untrusted-CA request, and no re-serve. The 60 s figure is the harness ceiling, not an AWS requirement — the check's own waits are 300 s/300 s/300 s/120 s, so the budget was consumed inside one blocking handshake/readiness loop. Corroborating the inertness independently of the hang: create_domain_name.rs stores truststoreUri/truststoreVersion verbatim and sets truststore_warnings: None with the comment 'The truststore is an S3 object this emulator does not fetch, so nothing read one and there is nothing to warn about', so no trust anchor set is ever constructed and no client certificate can be verified even if the handshake did complete.
