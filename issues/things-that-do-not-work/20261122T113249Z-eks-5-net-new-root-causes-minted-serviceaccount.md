# eks: 5 net-new root causes — minted ServiceAccount tokens name a real-AWS OIDC issuer the cluster does not advertise, a deleted CloudFormation stack leaves its cluster describable, and nodegroup, CA/add-on and pod-level flows never converge

> _Note: this issue was identified against the code base at commit `ce4ee9e56b2f664f3ccf49966acace7716de13e8`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
DeleteCluster

## Description
FIVE separate net-new root causes in the eks service, each grounded in failing behavioral checks that no open issue carries the replay key for. Each cause is a SEPARATE defect and must be closed separately; its own failing check ids are listed with it.

Cause 1 of 5: the ServiceAccount token the cluster mints carries an `iss` claim on a real AWS host, not the OIDC issuer the same cluster advertises and the IAM OIDC provider is registered for.
AWS:      Smithy: DescribeCluster returns Cluster.identity.oidc.issuer (shape OIDC.issuer, "The issuer URL for the OIDC identity provider"). On AWS that URL is https://oidc.eks.<region>.amazonaws.com/id/<oidc-id>, and it is the SAME string that appears as the `iss` claim of every projected ServiceAccount token the cluster's apiserver signs — that identity is what AssumeRoleWithWebIdentity and the registered IAM OIDC provider match on. The requirement is the equality between the advertised issuer and the minted token's `iss`; an emulator must advertise and sign with an address it is itself reached on (the host/port and oidc-id are per-run values).
Emulator: DescribeCluster advertises an issuer on the emulator's own address (path shape https://<host>:<port>/id/<OIDC-ID>, which the test registers with IAM), but the token the cluster mints names `iss` = https://oidc.eks.<region>.amazonaws.com/id/<A-DIFFERENT-OIDC-ID> — a real-AWS hostname and an unrelated id. Advertised issuer and signed issuer disagree, so no IRSA trust relationship can ever match.
Why:      every IRSA flow breaks and breaks silently in the wrong place: a client registers the advertised issuer with IAM, projects a token into a pod, and AssumeRoleWithWebIdentity sees a token from an issuer no provider is registered for. Neither the positive path nor the intended negative contrasts (a cross-namespace `sub` condition denial, a deregistered provider) can be exercised, because both fail for the wrong reason. (The open issue 20261111T111216Z-cloudformation-eks-eks-publishes-an-oidc-issuer-url-on-a.md records the DescribeCluster side of this for a cloudformation__eks check; it does not cover the token-signing path, which is the half that still names the AWS host here.)
Fix:      the token-minting seam of the served cluster Kubernetes API (the code that signs projected ServiceAccount tokens for an EKS cluster): the `iss` claim must be the cluster's stored/advertised identity.oidc.issuer, from the same source DescribeCluster reads, instead of a synthesised oidc.eks.<region>.amazonaws.com URL.
Traces:   eks.irsa-cross-namespace-serviceaccount-token-rejected, eks.irsa-web-identity-rejected-when-the-oidc-provider-is-deregistered.

Cause 2 of 5: deleting the CloudFormation stack that created an AWS::EKS::Cluster does not delete the cluster — DescribeCluster still answers 200 after the stack is gone.
AWS:      Smithy: DescribeCluster's modeled errors include ResourceNotFoundException (HTTP 404) with the service's not-found sentence "No cluster found for name: <name>." (the cluster name comes from the request). On AWS, once the stack that owns an AWS::EKS::Cluster reaches DELETE_COMPLETE the cluster no longer exists, so DescribeCluster on that name is refused 404 ResourceNotFoundException.
Emulator: after the stack's deletion completes, DescribeCluster on the stack-created cluster name still SUCCEEDS (HTTP 200 with a cluster object) instead of being refused ResourceNotFoundException.
Why:      a client that tears down by stack cannot tell whether its resources are gone: names stay taken, quota and dependency checks see phantom clusters, and a redeploy of the same template can collide with a cluster the client believes it deleted.
Fix:      the AWS::EKS::Cluster resource handler's delete path in the CloudFormation integration (the seam that must call through to the EKS state slice's cluster deletion and remove the record), plus the EKS state slice's deletion so the name becomes not-found.
Note:     the open issue 20261122T043035Z-cloudformation-eks-a-delete-complete-stack-leaves-its.md describes a neighbouring symptom (cluster left stuck in 'DELETING') for a cloudformation__eks check and carries only that check's replay key; here the cluster is left fully describable and the check below is not owned by it.
Traces:   eks.deploy-cluster-via-cloudformation-active.

Cause 3 of 5: the managed-nodegroup lifecycle and the cluster teardown that depends on it never converge — a caller polling the modeled states never observes a terminal one inside its budget.
AWS:      Smithy: NodegroupStatus = CREATING | ACTIVE | UPDATING | DELETING | CREATE_FAILED | DELETE_FAILED | DEGRADED; ClusterStatus = CREATING | ACTIVE | DELETING | FAILED | UPDATING | PENDING. DeleteNodegroup (DELETE /clusters/{clusterName}/node-groups/{nodegroupName}) moves the nodegroup to DELETING and then out of existence, after which DescribeNodegroup is refused 404 ResourceNotFoundException with "The requested resource does not exist." (fixed text in its entirety). DeleteCluster models ResourceInUseException (HTTP 409) for a cluster that still has dependents. Every one of those transitions is observable to a poller within one polling interval.
Emulator: all of these checks are cut off with "Check timed out after 60.0s" while polling DescribeNodegroup/DescribeCluster for a terminal status (CREATING -> ACTIVE, the ACTIVE -> UPDATING -> ACTIVE edge of UpdateNodegroupConfig, DELETING -> 404, and the cluster's own delete), so the ResourceInUseException refusals, the deletion-protection refusal-then-success contrast and the post-delete not-found reads are never reached at all. No status is ever seen to settle.
Hypothesis: each transition is owed only after a stored due instant and is materialised lazily on the next read, so a caller pays a full polling interval per step and a chained create/update/delete sequence cannot settle inside a client budget.
Why:      a client cannot drive a nodegroup through its documented state machine or tear a cluster down: waiters hang instead of resolving or failing diagnosably, and dependency refusals (409 ResourceInUseException) and deletion protection can never be observed.
Fix:      the asynchronous lifecycle clock of the EKS state slice for nodegroups and clusters (the due-instant/materialisation seam behind CreateNodegroup, UpdateNodegroupConfig, DeleteNodegroup and DeleteCluster), so each modeled transition becomes observable promptly rather than only after a chain of lazily-materialised delays.
Note:     the open issue 20261121T142446Z-eks-4-net-new-root-causes-admitted-pods.md states a related node-registration cause and lists eks.eks-delete-cluster-with-a-live-node-is-rejected among its trace ids, but carries only the eks.eks-managed-nodegroup-node-joins-and-runs-a-targeted-pod replay key; that check is not owned by it and times out identically here.
Traces:   eks.delete-cluster-with-active-nodegroup-rejected, eks.e2e-cluster-delete-blocked-by-active-nodegroup-rejected, eks.e2e-cluster-nodegroup-pod-identity-teardown, eks.e2e-cluster-nodegroup-podidentity-teardown-flow, eks.e2e-cluster-nodegroup-workload-scale-teardown, eks.nodegroup-full-lifecycle-transitions, eks.ekscc-delete-cluster-with-deletion-protection-rejected-until-disabled, eks.eks-delete-cluster-with-a-live-node-is-rejected.

Cause 4 of 5: certificate-authority rotation and add-on version updates never settle — neither the CA chain nor an add-on upgrade reaches a verdict.
AWS:      Smithy: CreateCertificateAuthority returns the appended CA with signingStatus NOT_USED and a distributionStatus from CertificateAuthorityDistributionStatus (IN_PROGRESS | COMPLETE | FAILED | DELETING) plus the Update tracking trust distribution; a successor cannot be activated until its distributionStatus is COMPLETE. ActivateCertificateAuthority makes the successor IN_USE and retires the predecessor to NOT_USED; DeleteCertificateAuthority refuses the signing CA 409 ResourceInUseException with "Cannot delete the active certificate authority. Activate a different CA first." UpdateAddon's Update likewise reaches a terminal status (Successful/Failed/Cancelled) observable through DescribeUpdate. Each step is observable within one polling interval.
Emulator: all three checks end with "Check timed out after 60.0s" while polling DescribeCertificateAuthority for distributionStatus in (COMPLETE, FAILED), DescribeUpdate for a terminal update status, signingStatus NOT_USED -> IN_USE, and the deleted CA leaving ListCertificateAuthorities / the upgraded add-on reaching ACTIVE. No transition converges, so neither the activation path, the protected-signer refusal, nor the add-on upgrade consequence is ever exercised.
Hypothesis: same lazily-materialised due-instant model as cause 3, chained across cluster activation, CA distribution, the activation update and retirement.
Why:      a client cannot complete the documented CA rotation or an add-on version upgrade at all: it never sees distributionStatus COMPLETE or an update settle, so the workflow hangs rather than failing with a diagnosable status.
Fix:      the certificate-authority and add-on update lifecycle clocks in the EKS state slice (the due-instant/materialisation seam for CA distribution, the activation update, the retirement of the outgoing CA, and UpdateAddon's update record).
Note:     the open issue 20261121T142446Z-eks-4-net-new-root-causes-admitted-pods.md states the CA half as its Cause 2 and lists both CA checks, but its recorded replay keys are the inner _poll_until frames, not these outer budget exhaustions, so neither check is marked owned; both reproduce at this commit.
Traces:   eks.e2e-certificate-authority-activation-to-teardown, eks.e2e-certificate-authority-issue-activate-disable-delete, eks.e2e-addon-version-upgrade-consequence-flow.

Cause 5 of 5: pod-level identity and networking flows never converge — a pod never carries usable IRSA/pod-identity credentials nor a VPC-backed address.
AWS:      recorded behavior only for the cluster data plane; Smithy models the control-plane records these flows depend on (CreatePodIdentityAssociation/DescribePodIdentityAssociation echo clusterName/namespace/serviceAccount/roleArn; DescribeCluster publishes identity.oidc.issuer). On a real cluster: a projected ServiceAccount token mounted in a pod is accepted by STS AssumeRoleWithWebIdentity for a role whose trust policy names the cluster's issuer and the `sub` system:serviceaccount:<ns>:<sa> (and is denied when the condition does not match); with the eks-pod-identity-agent add-on and a matching association the mutating webhook injects AWS_CONTAINER_CREDENTIALS_FULL_URI = http://169.254.170.23/v1/credentials and AWS_CONTAINER_AUTHORIZATION_TOKEN_FILE plus a projected eks-pod-identity-token volume with audience pods.eks.amazonaws.com; and a running pod's status.podIP is one of the VPC ENI's secondary private addresses, visible through EC2 DescribeNetworkInterfaces for the node.
Emulator: all three checks are cut off with "Check timed out after 60.0s" while polling for the pod to become usable — the credential environment/projected token never appears, the in-pod assume never resolves, and no pod ever reports an address matching a secondary private IP of a real VPC ENI. The control-plane calls themselves answered; it is the pod-side convergence that never happens.
Why:      a client cannot obtain credentials inside a workload (no IRSA, no pod identity) and cannot verify VPC-CNI addressing, so both the allowed path and the intended denials (an unallowed bucket, a non-matching `sub`) are unobservable and a misconfiguration is indistinguishable from a working setup.
Fix:      the pod admission/mutation and addressing seams of the served cluster Kubernetes API (the pod-identity webhook injection, the projected-token mount, and the VPC-CNI address assignment that must allocate the pod's address as a secondary private IP on the node's EC2 ENI).
Note:     the open issue 20261121T142446Z-eks-4-net-new-root-causes-admitted-pods.md states the pod-identity-webhook half as its Cause 4 and lists eks.eks-pod-identity-credentials-are-scoped-and-an-unallowed-bucket-is-denied, but carries a different replay key for it; the check is not owned and reproduces here.
Traces:   eks.eks-irsa-projected-token-assumed-inside-the-pod-and-sub-condition-denied, eks.eks-pod-identity-credentials-are-scoped-and-an-unallowed-bucket-is-denied, eks.eks-pod-ip-is-a-secondary-address-on-a-real-vpc-eni.

## Evidence
Cause 1: AssertionError "the token the cluster minted names issuer 'https://oidc.eks.<region>.amazonaws.com/id/<ID-A>', not the 'https://<emulator-host>:<port>/id/<ID-B>' DescribeCluster advertises and the IAM provider is registered for" (both checks, at the `claims["iss"] == issuer` assertion). Expected (AWS): the minted token's `iss` is byte-identical to DescribeCluster's cluster.identity.oidc.issuer. Hosts, ports and OIDC ids are per-run values; the requirement is the equality.

Cause 2: AssertionError "expected DescribeCluster to fail with ResourceNotFoundException for '<cluster>' after stack deletion, but it still succeeded" (eks.deploy-cluster-via-cloudformation-active, line 112). Expected (AWS): 404 ResourceNotFoundException, message "No cluster found for name: <cluster>." with the name taken from the request. Actual: HTTP 200 with a cluster object.

Cause 3: all eight checks end "Check timed out after 60.0s" with no assertion reached, while polling DescribeNodegroup for status in (ACTIVE, CREATE_FAILED) then (ACTIVE, UPDATE_FAILED) then out of existence (the checks allow 900 s at 15 s intervals), and DescribeCluster through its delete. The expected follow-ons never run: DeleteCluster -> 409 ResourceInUseException, DescribeNodegroup after delete -> 404 ResourceNotFoundException with "The requested resource does not exist.", and the deletion-protection refuse-then-succeed contrast.

Cause 4: "Check timed out after 60.0s" for both CA checks while polling DescribeCertificateAuthority for distributionStatus in (COMPLETE, FAILED) (480 s budget, 15 s interval), DescribeUpdate for Successful, signingStatus -> IN_USE and ListCertificateAuthorities for the deleted CA; and for the add-on check while polling the add-on update to a terminal status. The protected-signer refusal (409 ResourceInUseException, "Cannot delete the active certificate authority. Activate a different CA first.") is never reached.

Cause 5: "Check timed out after 60.0s" for all three pod-level checks: the in-pod IRSA assume with a `sub`-conditioned role, the pod-identity credential scoping (expected injected AWS_CONTAINER_CREDENTIALS_FULL_URI = http://169.254.170.23/v1/credentials, AWS_CONTAINER_AUTHORIZATION_TOKEN_FILE and a projected eks-pod-identity-token volume with audience pods.eks.amazonaws.com), and the pod address check (expected status.podIP to equal a secondary private address of the node's EC2 network interface).
