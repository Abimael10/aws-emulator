# ec2__sts: an AWS-RunShellScript probe reports Success but its output carries no values — the commands list is performed element-by-element so shell state does not persist and no `aws` CLI runs in the guest, making an instance-profile session's aws:userid unobservable

> _Note: this issue was identified against the code base at commit `d33d509d5311768bd1282d02eb2794d638dad9b8`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
SendCommand

## Description
1 net-new root cause on the `ec2__sts` heading, grounded in the single failing check under it, which is neither ALREADY FILED nor OWNED. The scenario's only observation point is inside the launched instance: it asks the guest, via `AWS-RunShellScript`, what `aws:userid` its instance-profile session presents and what two prefix-scoped PutObject calls do under a policy conditioned on that composite. Nothing it grades is observable unless the shipped script runs as a script.

Cause 1 of 1: the resolved `commands` of an aws:runShellScript step are performed as independent shell commands rather than as one script, so command substitutions assigned on one element are gone on the next, and the guest has no `aws` program to produce them in the first place; the invocation nevertheless settles Status=Success and serves a stdout line with empty substitutions.
  AWS: the SSM agent writes the resolved `commands` list of an `aws:runShellScript` step into ONE script file and runs that file with the guest's shell. Variables therefore persist across elements: `UID_=$(aws sts get-caller-identity --query UserId --output text)` on one line is readable as `"$UID_"` on a later `printf` line, and `ARC=$?` captures the preceding command's exit status. On the AMI this check launches (the image named by the public parameter /aws/service/ami-amazon-linux-latest/al2023-ami-kernel-default-x86_64) the `aws` CLI is present and signs with the instance-profile credentials IMDS serves, so GetCommandInvocation reports Status=`Success`, ResponseCode=0 and a StandardOutputContent whose last line is the probe's single JSON object with every field populated: `userid` = `<role-id>:<instance-id>` (AWS documents the instance-profile session's aws:userid as the role's unique id and the instance id joined by a colon — https://docs.aws.amazon.com/IAM/latest/UserGuide/reference_policies_variables.html), `allowed_rc` 0, and `decoy_rc` non-zero with an S3 AccessDenied on the captured stderr. Smithy (services/service-com-amazonaws-ssm-amazonssm): GetCommandInvocation output members `Status` (CommandInvocationStatus), `StatusDetails`, `ResponseCode`, `StandardOutputContent` (@length 0..24000), `StandardErrorContent` (@length 0..8000); whether a script succeeds is the guest's outcome, not an API refusal, so no modelled error is involved and the exact stdout bytes are recorded behavior only.
  Emulator: SendCommand is accepted, the invocation reaches a terminal status, and GetCommandInvocation reports Status=`Success` (the check's Status assertion passes), but the last non-blank line of StandardOutputContent is not the JSON object the probe printed: json.loads fails with `JSONDecodeError: Expecting value: line 1 column 27 (char 26)`. Hypothesis: the stdout line is the probe's own printf template with empty substitutions — `{"userid":"","allowed_rc":,"allowed_err":"","decoy_rc":,"decoy_err":""}`, whose first missing value sits at exactly column 27 — because each `commands` element ran in its own shell (so `UID_`, `ARC` and `DRC` were unset when `printf` ran) and because the guest provides no `aws` program for the substitutions to call. This is the same guest-execution seam named by open issues 20261114T203825Z-ec2-iam-an-aws-runshellscript-imds-probe-never.md (element-by-element execution in ec2 `run_in_instance_guest`; no curl/python3/aws in the session) and 20261114T200121Z-ec2-elbv2-ssm-getcommandinvocation-reports-status-success-with.md (Success with empty StandardOutputContent); neither carries this check's id and neither is grounded in this heading, so a fix to either closes nothing here. It also adds an outcome neither describes: a Success/ResponseCode-0 invocation whose stdout is a half-filled template, which is strictly worse than a Failed one because a client cannot tell the script did not really run.
  Why: every behavior that exists only inside an instance becomes unobservable or, worse, silently wrong. A client driving an instance by shipping it a program gets a Success invocation and corrupt output instead of its program's results, and the contract under test — that an instance-profile session's `aws:userid` is `<role-id>:<instance-id>`, that a policy conditioned on that composite authorizes the write, that the twin statement naming another instance id refuses it with the documented `User: arn:aws:sts::<account>:assumed-role/<role>/<instance-id> is not authorized to perform: s3:PutObject on resource: ... because no identity-based policy allows the s3:PutObject action` message, and that the refusal inverts once the condition is rewritten — can never be exercised, however faithful IAM, EC2 and S3 are on the API surface.
  Fix: SSM's guest-execution script assembly and the EC2 guest session it runs in — the resolved `commands` must be performed as ONE script by ONE shell so variables, redirections and `$?` persist across elements, the session must provide an `aws` CLI that signs with the instance profile's credentials against the emulator's endpoints, and an invocation whose script did not actually run must not be projected as Status=Success/ResponseCode=0 (its stderr must reach StandardErrorContent).
  Traces: ec2__sts.instance-profile-session-userid-is-the-role-id-and-instance-id-composite.
