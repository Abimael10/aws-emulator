# sagemaker: 2 net-new causes — CreatePresignedDomainUrl's not-InService refusal is worded with an emulator-authored sentence naming the domain ARN, and every Studio Domain/UserProfile/App transition still costs a polling client a full interval so the duplicate-CreateApp ResourceInUse scenario reaches no verdict

> _Note: this issue was identified against the code base at commit `00e6ece75f29fc3dbb59d9bb8e588a23bd31cb1e`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
CreatePresignedDomainUrl, CreateApp, DescribeDomain, DescribeUserProfile, DescribeApp

## Description
TWO root causes, both grounded in failing checks the suite report lists under `### sagemaker`, neither of which the report marked ALREADY FILED or OWNED by an open issue. They are numbered and each carries its own failing check ids; BOTH must be closed before this issue is submitted.

=== Cause 1 of 2: CreatePresignedDomainUrl against a Pending Domain is refused with the right code but an emulator-authored message ===
AWS: Smithy (services/service-com-amazonaws-sagemaker-sagemaker/smithy-model/com-amazonaws-sagemaker-sagemaker.json) — CreatePresignedDomainUrl takes DomainId and UserProfileName (both required) and models exactly ONE error, ResourceNotFound (HTTP 400), so a lifecycle-state refusal travels as the service-common ValidationException. Recorded behavior: while the domain's DomainStatus is still `Pending`, the call is refused HTTP 400, Error.Code `ValidationException`, Error.Message `Domain must be in either InService or Update_Failed state and not in: Pending`. In that sentence `Domain must be in either InService or Update_Failed state and not in: ` is the FIXED text of this error class and the trailing token is the domain's CURRENT status read from state (`Pending` here, `Failed`/`Deleting` for a domain in those states); the message names no ARN, no region and no account. Once the domain is InService the identical call mints an AuthorizedUrl. The sibling creates refused in the same window carry their own sentences (`Unable to create UserProfile [<user-profile arn>] because Domain [<domain arn>] is not in InService.` / `Unable to create Space [<space arn>] because Domain [<domain arn>] is not in InService.`), which the emulator already answers correctly — this cause is the presigned-URL call alone.
Emulator: the call is refused 400 ValidationException with the emulator's own sentence `Unable to create a presigned domain URL for Domain [<domain arn>] because it is in Pending status instead of InService.` — a different template (fixed text `Unable to create a presigned domain URL for Domain [` / `] because it is in ` / ` status instead of InService.`), carrying the domain ARN the recording never mentions and omitting Update_Failed as an accepted state. Emitted at services/service-com-amazonaws-sagemaker-sagemaker/src/ops/create_presigned_domain_url.rs:234-238 from the Studio domain slice helper `crate::state::domain_url_needs_domain_in_service(&domain_arn, &domain_status)`.
Why: a client that polls CreateDomain -> CreatePresignedDomainUrl until the domain is ready matches on, logs and surfaces that sentence; against the emulator it gets prose AWS never emits, so message-matching retry logic, user-facing error text and test fixtures written against AWS all diverge, and the emulator's wording asserts InService is the only usable state when AWS also admits Update_Failed.
Fix: the refusal sentence owned by the Studio domain slice (`crate::state::domain_url_needs_domain_in_service`) and its use in the CreatePresignedDomainUrl handler's not-InService gate (src/ops/create_presigned_domain_url.rs:234-238) — word it as AWS does, with the domain's current status as the only variable part. Open issue 20261122T002913Z-sagemaker-3-net-new-causes-reopens-the-hyperpod.md (Cause 3) covered the PREVIOUS state of this call, where it answered `NotImplemented`; the operation is now implemented and refuses with the modelled class, so what is left is the wording recorded here, and that issue does not carry this check's replay key.
Traces: sagemaker.domain-pending-refuses-user-profile-space-and-presigned-url.

=== Cause 2 of 2: every clock-owed Studio transition is due only after the read that follows the mutation, so a polling client pays one whole poll interval per transition and the duplicate-CreateApp ResourceInUse scenario never reaches its assertion ===
AWS: recorded behavior only for the timing; the model states the lifecycle the check walks — DescribeDomain.Status -> DomainStatus, DescribeUserProfile.Status -> UserProfileStatus, DescribeApp.Status -> AppStatus (`Pending | InService | Deleting | Deleted | Failed`), and CreateApp models ResourceInUse (HTTP 400) and ResourceLimitExceeded (HTTP 400). A second CreateApp for a DomainId/UserProfileName/AppType/AppName tuple that is already running is refused 400 ResourceInUse with `App [<app arn>] is currently in [<status>] status. To restart the App, wait until it is in Deleted or Failed status.` — `App [` / `] is currently in [` / `] status. To restart the App, wait until it is in Deleted or Failed status.` is the fixed text, the ARN is the app the request resolves to and the bracketed status is read from state — while the same AppType/AppName under a DIFFERENT user profile of the same domain succeeds. Every status in the domain -> profile -> app chain has to be reachable by a client polling at a realistic interval.
Emulator: every call is answered — no refusal is recorded anywhere in the run — but each transition is deferred behind a stored wall-clock instant that the first read after the mutation always misses: `DOMAIN_IN_SERVICE_AFTER: Duration = Duration::from_secs(3)` (src/state/domain.rs:46, materialised only by `Domain::settle_status`, src/state/domain.rs:270-285), `USER_PROFILE_IN_SERVICE_AFTER = DOMAIN_IN_SERVICE_AFTER` (src/state/user_profile.rs) and `APP_IN_SERVICE_AFTER = ENDPOINT_IN_SERVICE_AFTER = Duration::from_millis(300)` (src/state/app.rs, src/state.rs:254). The settle happens on whichever read first runs at or after that instant, so a client that probes immediately after each create reads the transient status and then sleeps its own full interval. Hypothesis for the arithmetic: the chained waits alone exhaust the replay budget — this check waits DescribeDomain at interval 15 s, DescribeUserProfile at interval 10 s for each of TWO profiles, then DescribeApp at interval 15 s (15+10+10+15 = 50 s of pure sleeping on top of role/domain setup), and the replay is cut off with `Check timed out after 60.0s` with no verdict, so the duplicate-CreateApp ResourceInUse refusal, its exact sentence, the "still exactly one app" effect-absent read and the different-profile positive control are never exercised.
Why: a client (or `aws sagemaker wait`) polling at a realistic interval sees the transient status on the describe that immediately follows each create and pays its whole interval for every transition; a scenario chaining domain -> profile -> profile -> app pays it four times, so a multi-resource Studio flow is unobservably slow even though the emulator holds the settled state a few seconds later, and everything past the last wait cannot be verified at all.
Fix: the clock-owed spans of the Studio slices and the readers that materialise them — `DOMAIN_IN_SERVICE_AFTER` / `Domain::settle_status` (src/state/domain.rs), `USER_PROFILE_IN_SERVICE_AFTER` / `UserProfile::settle_status` (src/state/user_profile.rs), `APP_IN_SERVICE_AFTER` / `App::settle_status` (src/state/app.rs) with src/ops/describe_domain.rs, describe_user_profile.rs and describe_app.rs. The transient status must stay observable to the read that immediately follows the mutation WITHOUT costing a polling caller a full interval — settle on the first read AFTER the one that observed the transient value, rather than on a read that happens to fall after a fixed wall-clock instant. Open issue 20261122T002913Z-sagemaker-3-net-new-causes-reopens-the-hyperpod.md (Cause 2) describes the same mechanism for other Studio checks and names this check in its prose, but the suite report did not mark this failure as OWNED by it (its recorded replay key names a different stack frame), so it is filed here and should be closed together with it.
Traces: sagemaker.create-app-already-running-resource-in-use.
