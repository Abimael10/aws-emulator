# ec2__events__kms__sqs: a RunInstances whose root volume is under a disabled CMK reaches no verdict — no 'EC2 Instance State-change Notification' is ever delivered and the launch is never settled as Client.InvalidKMSKey.InvalidState (check times out)

> _Note: this issue was identified against the code base at commit `2d48989723ffc52951945f21d9774f4aa78dfaff`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
RunInstances

## Description
Cause 1 of 1: the disabled-CMK RunInstances scenario makes no observable progress in the emulator — the whole asynchronous KMS-refusal path for an instance launch (terminal state + state reason + the EC2 instance state-change events that report it) never materialises, so the check is killed by the harness budget before any of its assertions can be graded. Failing check: ec2__events__kms__sqs.xsvc-ec2-2-run-instances-under-disabled-key-terminates-with-client-kms-reason-rejected.

AWS: the EC2 Smithy model declares no errors for RunInstances (smithy_query operation=RunInstances on services/service-com-amazonaws-ec2-amazonec2/smithy-model/com-amazonaws-ec2-amazonec2.json reports `errors: []`), and it models the state reason only structurally — com.amazonaws.ec2#StateReason with members Code (xmlName 'code') and Message (xmlName 'message'), whose documentation enumerates the launch/termination classes ('Client.InternalError: A client error caused the instance to terminate during launch.', etc.). The event schema is not modelled at all, so the eventing half is recorded behavior only. What the recording shows: RunInstances with BlockDeviceMappings[].Ebs {Encrypted=true, KmsKeyId=<key whose KeyState is Disabled>} is ACCEPTED synchronously and returns an instance whose State.Name is 'pending' (the KMS refusal is asynchronous, never a synchronous error). EC2 then terminates that instance: DescribeInstances settles it at State.Name 'terminated' with StateReason.Code exactly 'Client.InvalidKMSKey.InvalidState' and StateReason.Message exactly 'Client.InvalidKMSKey.InvalidState: The KMS key provided is in an incorrect state' — the entire message is fixed text for this error class (the code, a colon, and that sentence); it contains no request- or state-derived parts, no key id and no timestamp. In parallel, EC2 publishes 'EC2 Instance State-change Notification' envelopes onto the EventBridge default bus with source 'aws.ec2', `account` = the caller's account id, `region` = the request region and `resources` = exactly ["arn:aws:ec2:<region>:<account>:instance/<instance-id>"] (the instance ARN alone), carrying detail.instance-id = that instance and detail.state. For the KMS-blocked instance the delivered states include 'shutting-down' and 'terminated' and NEVER 'running'; for an identical launch under an ENABLED key (the positive control) the instance reaches State.Name 'running' and its delivered states are 'pending' and 'running' only, with no 'shutting-down'/'terminated'. Deliveries are unordered.

Emulator: the check reaches none of these verdicts — the replay reports only `Error: Check timed out after 60.0s`, i.e. the scenario is still blocked in a polling barrier when the harness kills it, after the keys, VPC/subnet, AMI lookup, queue, default-bus rule (EventPattern {"source":["aws.ec2"],"detail-type":["EC2 Instance State-change Notification"]}, State ENABLED, PutTargets FailedEntryCount 0) and both launches have been set up. Nothing in the run ever satisfies either barrier the scenario depends on: the instance never settles into a terminal state carrying the KMS class, and no state-change envelope is ever delivered to the rule's SQS target. Hypothesis (the two barriers the check blocks on, each independently corroborated by already-filed causes elsewhere in this emulator): EC2 publishes no instance state-change notifications onto the EventBridge bus at all (the same shape of gap as the already-filed sibling cause for EBS volume notifications, 20261116T003513Z-ec2-events-kms-sqs-a-createvolume-under-a.md, and as 20261118T173313Z-autoscaling-ec2-events-sqs-no-ec2-instance-launch.md), and a launch blocked by a non-enabled CMK is not settled with the KMS state reason (the open wire issue 20261120T135008Z-ec2-describeinstances-reports-a-kms-key-blocked-launch.md records the emulator answering 'Client.UserInitiatedShutdown' / 'Client.UserInitiatedShutdown: User initiated shutdown' with reason 'User initiated (<timestamp> GMT)' for the Auto Scaling variant of this same termination). Neither of those issues was marked by the replay as owning this check: this one is the direct RunInstances path plus the instance state-change event stream, which they do not carry.

Why: a client that launches an instance on an encrypted root volume and watches EC2 instance state-change events to learn the outcome is told nothing. RunInstances returns 'pending' and then the instance neither reaches 'running' nor is reported as terminated-for-a-KMS-reason, and no 'shutting-down'/'terminated' notification arrives, so an operator cannot distinguish 'still booting', 'launch killed because the CMK is disabled' and 'eventing is not wired'. Remediation keyed on Client.InvalidKMSKey.InvalidState (re-enable the key, swap the encryption key in the block-device mapping) never fires, event-driven capacity trackers never see the instance leave 'pending', and the negative requirement that a KMS-failed instance never emits 'running' cannot be relied upon.

Fix: EC2's asynchronous launch-settlement path for encrypted block-device mappings (the RunInstances handler's post-accept settlement in the service crate's state — it must check the KMS key state for each encrypted EBS mapping and terminate the instance recording StateReason.Code 'Client.InvalidKMSKey.InvalidState' with the fixed message above) and EC2's instance-lifecycle event publisher into the EventBridge default bus (the 'EC2 Instance State-change Notification' emission for pending/running/shutting-down/terminated, with source 'aws.ec2', the account/region envelope fields and the instance ARN as the sole `resources` entry).

Traces: ec2__events__kms__sqs.xsvc-ec2-2-run-instances-under-disabled-key-terminates-with-client-kms-reason-rejected.
