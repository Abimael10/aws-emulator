# rds__s3: 2 net-new causes — AddRoleToDBCluster answers the IAM-role-validation sentence instead of AWS's "feature name ... is not valid for the engine" refusal, and a snapshot export's export_tables_info manifest reports an empty database with a flat skipReason instead of warningMessage.skippedDatabase

## Operation
AddRoleToDBCluster

## Description
Two net-new root causes in the rds__s3 surface. Both must be closed before submitting; each is numbered below with its own failing check ids.

=== Cause 1 of 2: AddRoleToDBCluster rejects an unsupported/unrecognized FeatureName with AWS's role-validation sentence instead of the feature-name sentence ===
AWS: AddRoleToDBCluster refuses a FeatureName the target cluster's engine does not support with HTTP 400, error code InvalidParameterValue, and the message "The feature name <FeatureName> is not valid for the engine <engine>." The fixed text is "The feature name " ... " is not valid for the engine " ... "."; the variable parts are the FeatureName copied from the request and the engine as RDS names it for the resolved cluster (recorded: "Aurora MySQL" for an aurora-mysql cluster, "Aurora (PostgreSQL)" for an aurora-postgresql one). This refusal is independent of the role: it is returned for a feature name the engine does not support (s3Import on aurora-mysql) and for a feature name that is not a feature at all (an arbitrary string on aurora-postgresql). It is distinct from the role-visibility/permission refusal, "IAM role ARN value is invalid or does not include the required permissions for: AWS_ROLE_INTEGRATION", which AWS returns — under the same InvalidParameterValue code — while a freshly created role is not yet resolvable by RDS; callers poll that sentence out and then read the real verdict. Smithy (com.amazonaws.rds#AmazonRDSv19, awsQuery): AddRoleToDBCluster input DBClusterIdentifier (required), RoleArn (required, IAMRoleArn, @length 20..2048, @pattern ^arn:aws[a-z-]*:iam::[0-9]*:role/.*$) and FeatureName, a plain String with no enum; modeled errors are DBClusterNotFoundFault(404), DBClusterRoleAlreadyExistsFault(400), DBClusterRoleQuotaExceededFault(400) and InvalidDBClusterStateFault(400). The model therefore says nothing about which feature names an engine supports, and InvalidParameterValue is a service-common error — the code and both message texts are recorded behavior only.
Emulator: the code is right (InvalidParameterValue) but the message is always the role sentence: "IAM role ARN value is invalid or does not include the required permissions for: AWS_ROLE_INTEGRATION". It is returned for FeatureName=s3Import on an aurora-mysql cluster where AWS says "The feature name s3Import is not valid for the engine Aurora MySQL.", and for an unrecognized FeatureName on an aurora-postgresql cluster where AWS says "The feature name <name> is not valid for the engine Aurora (PostgreSQL)." Through CloudFormation the same sentence is what the AWS::RDS::DBCluster handler reports as the UPDATE_FAILED/rollback reason ("Resource handler returned message: \"IAM role ARN value is invalid or does not include the required permissions for: AWS_ROLE_INTEGRATION ...\""), where AWS's reason names the rejected feature and says it is not valid.
Why: the two sentences carry opposite instructions to a client under one error code. The role sentence means "transient — the role is not visible or not permissive yet, wait and retry"; the feature sentence means "terminal — this engine has no such feature, change the request". A caller that implements AWS's documented retry (loop while the answer is the role sentence) never exits against the emulator, because the terminal rejection wears the retryable wording: both negative checks here burn their entire budget and reach no verdict instead of grading a refusal, and the positive control that follows (the same role with a feature name the engine DOES support reaching ACTIVE) is never attempted. A CloudFormation user reading the rollback reason is told their role ARN or its permissions are wrong when the template's feature name is what was rejected.
Fix: the FeatureName validation in the AddRoleToDBCluster handler — resolve the cluster, validate the requested FeatureName against that cluster's engine, and raise InvalidParameterValue with AWS's feature-name sentence (feature name from the request, engine from cluster state) rather than falling through to the role-validation refusal; keep the role sentence for the case it describes, a role RDS cannot yet resolve or that lacks the required permissions.
Traces: rds__s3.rds-load-from-s3-missing-role-negative (aurora-mysql, FeatureName=s3Import, message asserted verbatim), rds__s3.rds-associate-role-wrong-feature-name-negative (aurora-postgresql, unrecognized FeatureName, times out in the role-sentence retry loop), rds__s3.cfn-stack-update-rds-cluster-add-s3-role-positive (the same sentence surfaces as the AWS::RDS::DBCluster rollback reason instead of one naming the rejected s3Export feature).

=== Cause 2 of 2: a COMPLETE snapshot export's export_tables_info manifest reports an empty source database with a flat status/skipReason pair instead of warningMessage.skippedDatabase[].reason ===
AWS: a COMPLETE StartExportTask writes, alongside <export_id>/export_info_<export_id>.json, a companion export_tables_info_<...>.json whose perTableStatus list describes what was extracted. For a source database with no user tables AWS does not write an empty value: the entry is {"target": <database>, "warningMessage": {"skippedDatabase": [{"reason": "DATABASE_IS_EMPTY"}]}} — the skip reason lives in a nested warningMessage.skippedDatabase list of {"reason": ...} objects, and DATABASE_IS_EMPTY is the fixed reason token for that condition. Recorded behavior only: the Smithy model (com.amazonaws.rds#AmazonRDSv19) describes StartExportTask's API envelope (ExportTask with ExportTaskIdentifier, SourceArn, S3Bucket, S3Prefix, IamRoleArn, KmsKeyId, Status, PercentProgress, TotalExtractedDataInGB, FailureCause, WarningMessage, SourceType, and errors DBSnapshotNotFoundFault(404), InvalidS3BucketFault(400), IamRoleMissingPermissionsFault(400), IamRoleNotFoundFault(404), KMSKeyNotAccessibleFault(400), ExportTaskAlreadyExistsFault(400), InvalidExportOnlyFault(400), InvalidExportSourceStateFault(400), DBClusterSnapshotNotFoundFault(404), DBClusterNotFoundFault(404)); the S3 manifest objects the task writes are not modeled at all, so their layout is fixed only by what AWS writes.
Emulator: the perTableStatus entry is a different, flat record — {"target": "postgres", "database": "postgres", "status": "SKIPPED", "skipReason": "DATABASE_IS_EMPTY", "sizeGB": 0, "files": []}. The reason token itself is right, but it is reported under a scalar "skipReason" member beside an invented "status"/"database"/"sizeGB"/"files" quadruple, and there is no warningMessage member and no skippedDatabase list at all.
Why: a client parsing AWS's manifest reads entry["warningMessage"]["skippedDatabase"][*]["reason"]; against the emulator that path is absent, so the export looks as though it skipped nothing and reported no reason, even though the task is COMPLETE and the reason is sitting in a member the client does not read. Tooling that branches on DATABASE_IS_EMPTY (to distinguish "nothing to export" from "extraction failed") takes the wrong branch, and a schema-validating consumer rejects the document for carrying members AWS never emits.
Fix: the export-manifest serializer that writes export_tables_info_<...>.json in the snapshot-export worker/state behind StartExportTask — emit the skip as the nested warningMessage.skippedDatabase list of {"reason": <token>} objects on the per-target entry, and drop the flat status/skipReason/sizeGB/files members for a skipped database.
Traces: rds__s3.rds-export-manifest-file-format-positive.
