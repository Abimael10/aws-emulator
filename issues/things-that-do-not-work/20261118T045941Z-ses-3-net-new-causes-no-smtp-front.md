# ses: 3 net-new causes — no SMTP front door is served at all (TCP refused on 465 and 587), and two v1 configuration-set refusals carry the wrong error code and an emulator-authored message

> _Note: this issue was identified against the code base at commit `2b493b29800d7a854b42f905b4db8bab42375d7a`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
CreateConfigurationSet

## Description
Three net-new behavioral root causes on the SES v1 surface. None of the eight failing checks below was marked ALREADY FILED or OWNED by the replay report.

Cause 1 of 3: the SES SMTP front door is never served — every TCP connect to the SMTP endpoint is refused, so the whole SMTP interface (EHLO capability set, STARTTLS upgrade, SigV4-derived credential AUTH, and the DATA-stage sender gate) is unreachable.
AWS: recorded behavior only — the SES Smithy model (com.amazonaws.ses#SimpleEmailService) models only the HTTPS awsQuery API and says nothing about SMTP. SES additionally serves an SMTP endpoint for the Region (email-smtp.<region>.amazonaws.com) on the documented SMTP ports: 587 as a plaintext session that advertises STARTTLS, AUTH PLAIN LOGIN and 8BITMIME in its EHLO reply and, after a TLS 1.2+ upgrade, advertises the same capability set with STARTTLS withdrawn; and 465 as an implicit-TLS (RFC 8314 "smtps") session carrying the identical credential algebra. On that listener AUTH succeeds for a password derived by the documented SMTP-credential formula (https://docs.aws.amazon.com/ses/latest/dg/smtp-credentials.html — version byte 0x04 prepended to an HMAC-SHA256 SigV4 chain keyed on "AWS4"+secret over the fixed date 11111111, then region, "ses", "aws4_request", "SendRawEmail", base64-encoded) and is refused for a password derived for the wrong region or tampered with; AUTH attempted before STARTTLS on 587 is refused; and a MAIL FROM/DATA submission from an unverified sender is refused at the DATA stage with the same not-verified refusal the API answers (fixed text "Message rejected: Email address is not verified." plus the per-request identity detail), while the account-level sending pause outranks that identity gate on both the API and the SMTP front door.
Emulator: nothing is listening. Every one of these checks dies in socket.create_connection with `ConnectionRefusedError: [Errno 111] Connection refused` before a single SMTP verb is exchanged — on port 465 and on port 587 alike. The ports are the service's documented ones, not per-environment values; the emulator announces an SES SMTP endpoint for the Region but serves no listener on the address it is reached on.
Why: a client that sends mail through SES over SMTP (every MTA, every application using an SMTP library instead of the SDK, every appliance configured with SES SMTP credentials) cannot connect at all. The SMTP credential derivation, the STARTTLS negotiation, the authentication-failure classification and the SMTP-side sender/account gating are all untestable and unusable, and a connection refusal is indistinguishable to the caller from a networking fault rather than a missing feature.
Fix: an SMTP listener belongs in the ses crate alongside its HTTP front door (services/service-com-amazonaws-ses-simpleemailservice) — it must accept on the documented SMTP ports, advertise and perform the STARTTLS upgrade on the plaintext port, implement implicit TLS on the smtps port, authenticate the SigV4-derived SMTP password against the account's credentials, and run the submission through the same identity-verification and account-sending gates the API path uses (the account flag written at services/service-com-amazonaws-ses-simpleemailservice/src/ops/update_account_sending_enabled.rs line 163, `state.lock().account.sending_enabled`).
Traces: ses.smtp-accepts-both-advertised-auth-mechanisms, ses.smtp-auth-before-starttls-is-rejected, ses.smtp-derived-credential-authenticates-and-a-wrong-region-derivation-is-rejected, ses.smtp-listener-advertises-starttls-then-withdraws-it-after-upgrade, ses.smtp-rejects-a-tampered-sigv4-derived-password, ses.smtp-send-from-unverified-sender-rejected-at-the-data-stage, ses.account-sending-pause-outranks-the-identity-gate-on-both-front-doors.

Cause 2 of 3: v1 CreateConfigurationSet refuses an out-of-charset configuration-set name with the wrong error code and a message copied from the model's documentation prose.
AWS: Smithy (com.amazonaws.ses#CreateConfigurationSet) takes ConfigurationSet (required) and models ConfigurationSetAlreadyExistsException (awsQuery code ConfigurationSetAlreadyExists, 400), InvalidConfigurationSetException (awsQuery code InvalidConfigurationSet, 400) and LimitExceededException (400); ConfigurationSet.Name is documented as "Contain only letters (a-z, A-Z), numbers (0-9), underscores (_), or dashes (-)" and "Contain 64 characters or fewer". Recorded behavior for a name holding a character outside [A-Za-z0-9_-] is HTTP 400 with code `InvalidParameterValue` and the message "Invalid configuration set name <NAME>: only alphanumeric ASCII characters, '_', and '-' are allowed." — fixed text "Invalid configuration set name <", then the submitted name copied verbatim from the request, then ">: only alphanumeric ASCII characters, '_', and '-' are allowed." Nothing is created for the refused name, and a name mixing '_' and '-' is accepted.
Emulator: HTTP 400 with code `InvalidConfigurationSet` and message "The configuration set name must contain only letters (a-z, A-Z), numbers (0-9), underscores (_), or dashes (-), and 64 characters or fewer." — the model's ConfigurationSet.Name documentation prose rewritten as a sentence, naming neither the submitted name nor the offending character.
Why: a client branching on the awsQuery error code sees InvalidConfigurationSet (a code AWS reserves for other invalid-configuration-set conditions) where AWS answers InvalidParameterValue, so its error handling takes the wrong branch; and the diagnosis loses the name that was rejected, which is what a caller validating user-supplied names needs to report.
Fix: the name validation in the v1 handler at services/service-com-amazonaws-ses-simpleemailservice/src/ops/create_configuration_set.rs — raise the awsQuery InvalidParameterValue error with AWS's sentence, interpolating the request's name between the angle brackets.
Traces: ses.v1-configuration-set-name-charset.

Cause 3 of 3: v1 UpdateConfigurationSetReputationMetricsEnabled on a configuration set that does not exist answers the not-found class instead of AWS's update-conflict refusal.
AWS: Smithy (com.amazonaws.ses#UpdateConfigurationSetReputationMetricsEnabled) takes {ConfigurationSetName required, Enabled required} and models only ConfigurationSetDoesNotExistException (awsQuery code ConfigurationSetDoesNotExist, 400), but the modeled error is NOT what the service answers for an unknown set: recorded behavior is HTTP 400 with code `Throttling` and the message "Update conflict when updating configuration set <NAME>." — fixed text "Update conflict when updating configuration set <", the requested configuration-set name copied from the request, then ">." (the same account's v1 DescribeConfigurationSet for that name does answer ConfigurationSetDoesNotExist "Configuration set <NAME> does not exist.", so the two operations deliberately differ).
Emulator: HTTP 400 with code `ConfigurationSetDoesNotExist` and message "Configuration set <NAME> does not exist." — the describe-path refusal reused for the update path.
Why: Throttling is a retryable class and ConfigurationSetDoesNotExist is terminal, so a client that retries on Throttling (as AWS's own SDK retry policy does for that code) and gives up on not-found behaves the opposite way against the emulator; the happy-path half of the same operation (the toggle read back through both v1 DescribeConfigurationSet and SESv2 GetConfigurationSet) passes, so only the unknown-set refusal diverges.
Fix: the unknown-set branch of the handler at services/service-com-amazonaws-ses-simpleemailservice/src/ops/update_configuration_set_reputation_metrics_enabled.rs — answer the awsQuery Throttling error with AWS's update-conflict sentence naming the requested set, leaving the describe path's ConfigurationSetDoesNotExist untouched.
Traces: ses.v1-reputation-metrics-crossapi-and-unknown-set-refused.
