# pricing GetProducts serves derived offer documents and page tokens instead of the published Price List catalog (2 causes)

> _Note: this issue was identified against the code base at commit `a0d31926d54e568c2ffb39ccb2c80a5db565f5fd`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
GetProducts

## Description
The Price List API's GetProducts is answered out of a synthetically derived, seeded catalog: each product's aws_v1 offer document is RENDERED from a ProductDraft at seed time (services/service-com-amazonaws-pricing-awspricelistservice/src/state.rs: offer_document / product_from_draft / build_seeded_catalog), so the SKU, the product.attributes map and the terms blocks are whatever the seed happens to carry rather than what the Price List API publishes. Two distinct divergence clusters in this replay are the result: for two different EC2 filter sets the emulator answers 200 with a first PriceList entry that is not the published offer, and in one of them the continuation token for the same filtered set also diverges. TWO net-new causes, both on service `pricing`, both GetProducts, neither carrying a stub_path and neither carrying an owned_by in this replay.

Related open issues that do NOT cover these clusters (none carries their replay keys): 20261108T161655Z-pricing-catalog-metadata-diverges-from-the-published-price.md (its Cause 3 discusses the same EC2 filter-set cluster in prose but its registered replay keys are pricing|GetProducts|2xx->2xx|$.NextToken and the GetAttributeValues/DescribeServices keys, so this cluster's key keys=$.NextToken,$.PriceList[0] is not owned by it and is reported unowned here), 20261103T043017Z-pricing-getproducts-5-net-new-root-causes-ec2.md, 20261108T114447Z-ec2-pricing-pricing-getproducts-publishes-no-windows-sku-for-the.md and 20261103T021956Z-ec2-pricing-pricing-getproducts-matches-no-sku-for-the-standard.md (all about which SKUs the EC2 catalog matches, none about the offer-document CONTENT of the first page entry plus the page token for these two fixtures).

Cause 1 of 2: GetProducts over the EC2 vocabulary filter set returns a different first offer document AND a different continuation token, so a filtered price query returns a different result set than AWS.
AWS: Smithy — GetProducts(ServiceCode required, Filters @length 0..50, FormatVersion @length 1..32, NextToken, MaxResults @range 1..100) -> {FormatVersion, PriceList: PriceListJsonItems, NextToken}, @paginated{inputToken: NextToken, outputToken: NextToken, items: PriceList, pageSize: MaxResults}; modelled errors InvalidParameterException / NotFoundException / InvalidNextTokenException / ExpiredNextTokenException (httpError 400), AccessDeniedException (401), ThrottlingException (429), InternalErrorException (500). The model does not describe the CONTENT of a PriceList item, so for the document this is recorded behavior only: for this filter set the recording's first PriceList entry is the published 'Compute Instance' offer for a Linux, shared-tenancy, current-generation t3-class instance in US East (N. Virginia) — a document whose product.sku is the catalog's published SKU for that offer, whose product.attributes carry the FULL published EC2 attribute set (clockSpeed, ecu, networkPerformance, processorArchitecture, processorFeatures, dedicatedEbsThroughput and dedicatedEbsThroughputDescription, enhancedNetworkingSupported, intelAvxAvailable, intelAvx2Available, intelTurboAvailable, classicnetworkingsupport, vpcnetworkingsupport, instanceFamily, instanceFamilyCategory, gpuMemory, marketoption, availabilityzone, storage, tenancy, capacitystatus, normalizationSizeFactor, regionCode, servicename, servicecode, location, locationType, licenseModel, preInstalledSw, operation, usagetype, memory, vcpu, operatingSystem, instanceType), and whose terms carry BOTH an OnDemand block (its usage dimension described as '$<rate> per On Demand <operatingSystem> <instanceType> Instance Hour', unit 'Hrs', beginRange '0', endRange 'Inf') and a Reserved block; and the same response carries a NextToken that continues THAT filtered set. HTTP status 200, no error code, no error message — the divergence is purely in the body.
Emulator: the same step also answers 200, but the replay reports $.PriceList[0]: value_mismatch and the divergence key names $.NextToken as diverging too (divergence_key 'service=pricing|GetProducts|status=200->200|keys=$.NextToken,$.PriceList[0]'). The served document is the seed-rendered one (offer_document, state.rs:1189-1216, writes product.attributes straight from the draft's attribute map and derives the SKU and term/rate codes from the draft), so its attribute set is only the keys the seed carries and its terms are the formulaic OnDemand/Reserved terms built by on_demand_term (state.rs:1220-1241) and reserved_terms (state.rs:1250-1290); the emulator's filtered selection also starts at a different product and its continuation token does not describe the same remaining population.
Why: a client prices a workload off PriceList[0] and then pages the rest with NextToken. A different first offer means a different price and a different product identity for the same filter set, and a continuation token describing a different remaining set means the rest of the walk covers different products — so a cost estimate assembled by paging GetProducts is wrong both in the figure it reports and in the inventory it covers, and a client that keys a cache or an order off product.sku keys it off an identifier AWS never published.
Fix: the GetProducts handler's filtered selection, result ordering and NextToken encoding, together with the EC2 product seed and the offer-document builder in the pricing service's state (the catalog must publish the published offer documents, not documents derived from the seed's draft fields).
Traces: pricing-ecc-traj-ec2-vocabulary-in-price-filters#task#4 (representative); also affected: pricing-ecc-traj-get-products-request-mistakes#task#7, pricing-ecc-traj-upstream-lookup-page-token-and-os-split#task#1, pricing-ecc-traj-upstream-lookup-page-token-and-os-split#task#4.

Cause 2 of 2: GetProducts for the upstream OS-split lookup returns a first offer document that is not the published one — in particular its Reserved terms do not carry the published lease dimensions.
AWS: Smithy — same GetProducts signature and errors as above; document content is recorded behavior only. For this lookup the recording's first PriceList entry is the published 'Compute Instance' offer for the next size up in the same Linux shared-tenancy t3 family in US East (N. Virginia): product.sku the published catalog SKU, the same full published EC2 attribute set, terms.OnDemand with the '$<rate> per On Demand <operatingSystem> <instanceType> Instance Hour' dimension (unit 'Hrs'), and terms.Reserved containing BOTH the hourly usage dimension (described as '<platform>, <instanceType> reserved instance applied') and a one-off 'Upfront Fee' dimension stated with unit 'Quantity' for every partial/all-upfront purchase option. Status 200.
Emulator: 200, but $.PriceList[0] is value_mismatch (divergence_key 'service=pricing|GetProducts|status=200->200|keys=$.PriceList[0]'); the first entry of the page is the seed-derived document for a different product/rate rather than the published offer. The Reserved block is computed arithmetically from the draft's single rate (reserved_terms scales the draft rate by a hard-coded percentage per RESERVED_TERMS entry and only then synthesises an upfront dimension, state.rs:1250-1290), so the published per-term rates and dimensions cannot be reproduced.
Why: a client comparing on-demand against reserved pricing for the same product reads terms.Reserved; when the document is not the published one, the lease rates and the upfront fee it reports are fabricated, so a reservation break-even calculation and the resulting purchase decision are both wrong. Because the status is 200 and the shape is valid, nothing signals to the client that the figures are not AWS's.
Fix: the pricing service's EC2 product seed plus the offer-document/terms builders in its state (offer_document, on_demand_term, reserved_terms) — a product's published offer document, including each published Reserved term's dimensions, must come from the catalog rather than from a rate-scaling formula; and the GetProducts handler's selection/ordering must put the published offer first for this filter set.
Traces: pricing-ecc-traj-upstream-lookup-page-token-and-os-split#task#3.
