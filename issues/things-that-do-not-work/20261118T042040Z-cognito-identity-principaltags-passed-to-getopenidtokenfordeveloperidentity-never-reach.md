# cognito-identity: PrincipalTags passed to GetOpenIdTokenForDeveloperIdentity never reach the STS session, so an ABAC role policy keyed on aws:PrincipalTag denies a read it authorizes

> _Note: this issue was identified against the code base at commit `0ec2fb94436bf840a0bf63ae99f3da1459d90f3e`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
GetOpenIdTokenForDeveloperIdentity

## Description
One cause (Cause 1 of 1): a developer-authenticated OIDC token minted by GetOpenIdTokenForDeveloperIdentity with an explicit PrincipalTags argument does not carry those tags into the STS session produced by sts:AssumeRoleWithWebIdentity for that token, so aws:PrincipalTag/<key> resolves to nothing in the assumed role's policies and every request gated on it is refused — including the request the role's own inline policy explicitly allows.
Failing check ids for this cause: cognito-identity.e2e-principal-tags-federation-to-sts-session-tags.

AWS: GetOpenIdTokenForDeveloperIdentity accepts a PrincipalTags map and configures the principal tags for the token it returns (Smithy, com.amazonaws.cognitoidentity#AWSCognitoIdentityService: GetOpenIdTokenForDeveloperIdentity input IdentityPoolId @required @length{1,55} @pattern ^[\w-]+:[0-9a-f-]+$, IdentityId @length{1,55} same pattern, Logins @required map @length{0,10}, PrincipalTags map @length{0,50} documented "Use this operation to configure attribute mappings for custom providers.", TokenDuration @range{1,86400}; output IdentityId + Token (@sensitive); errors DeveloperUserAlreadyRegisteredException 400, InvalidParameterException 400, NotAuthorizedException 403, ResourceConflictException 409, ResourceNotFoundException 404, TooManyRequestsException 429, InternalErrorException 500). When that token is exchanged through the basic (classic) flow — sts:AssumeRoleWithWebIdentity against a role whose trust policy permits sts:AssumeRoleWithWebIdentity and sts:TagSession for the federated principal cognito-identity.amazonaws.com — the configured principal tags become SESSION TAGS on the resulting session, and are what aws:PrincipalTag/<key> resolves to during authorization. Consequently a role whose inline policy allows s3:GetObject on arn:aws:s3:::<bucket>/<key> under Condition StringEquals {"s3:ExistingObjectTag/department": "${aws:PrincipalTag/department}"} must be authorized to read an object tagged department=<value> when the token was minted with PrincipalTags={"department": "<value>"} — the condition key resolves to the session tag and the two sides match, so the call is served 200 with the stored bytes. The model does not describe the Cognito→STS session-tag join itself (recorded behavior only for that linkage); the recording shows it, because the recorded run reads the ABAC-gated object successfully with exactly this setup.
Emulator: the whole control plane of this flow is accepted. CreateIdentityPool (AllowUnauthenticatedIdentities=true, DeveloperProviderName, SupportedLoginProviders), SetIdentityPoolRoles for both authenticated and unauthenticated roles, and SetPrincipalTagAttributeMap(IdentityProviderName=<social provider>, UseDefaults=false, PrincipalTags={"department": "department"}) all succeed, and SetPrincipalTagAttributeMap echoes PrincipalTags == {"department": "department"}; GetCredentialsForIdentity for an unauthenticated identity vends an AccessKeyId; GetOpenIdTokenForDeveloperIdentity(Logins={<developer provider>: <dev user id>}, PrincipalTags={"department": "engineering"}) returns an IdentityId distinct from the unauthenticated one plus a Token; and AssumeRoleWithWebIdentity on that Token against the authenticated role returns credentials. The session those credentials name is not tagged: the very next call, GetObject on the object tagged department=engineering that the role's inline policy allows for exactly that tag value, is refused HTTP 403 AccessDenied with the message 'User: arn:aws:sts::<account id>:assumed-role/<role name>/<role session name> is not authorized to perform: s3:GetObject on resource: "arn:aws:s3:::<bucket>/<object key>" because no identity-based policy allows the s3:GetObject action'. In that message the fixed text is everything outside the angle brackets; the account id, role name, role session name, bucket and object key are values taken from the request and from emulator state, and a single run's values (e.g. the recorded 000000000000 / sim2real-behav-role-f88a1acfabc2 / sess-4284cd714434) are not part of the requirement. The status, code and wording of the refusal match what AWS emits for an implicit deny, so the refusal's SHAPE is not the defect — the defect is that it is emitted at all for an authorized request. Hypothesis (neither the model nor the recording states the mechanism): either the PrincipalTags argument is dropped when the developer-identity token is minted, or the token's tags are not translated into session tags by the AssumeRoleWithWebIdentity leg, or s3:ExistingObjectTag is not populated from the object tagging written by PutObject(Tagging="department=engineering") — in all three the ABAC condition evaluates false and the allow statement never matches.
Why: a client that uses principal tags to carry a tenant/department attribute from a developer-authenticated Cognito identity into IAM — the documented way to do ABAC over federated Cognito sessions — gets an authorization boundary that fails CLOSED and silently. Every request the role legitimately allows is denied with a message that says no policy allows the action, even though one does, so the operator sees no indication that the tag is missing and has no way to distinguish a missing session tag from a genuinely absent permission. Multi-tenant designs built on ${aws:PrincipalTag/...} in Resource or Condition elements are unusable against the emulator, and tests of them pass only when the policy happens not to depend on a tag.
Fix: the cognito-identity token-minting path for GetOpenIdTokenForDeveloperIdentity, together with the session-tag handoff it feeds — the PrincipalTags supplied on the request (and, where UseDefaults/attribute-map state applies, the map resolved at mint time) must be recorded on the issued OIDC token and materialized as session tags on the session that AssumeRoleWithWebIdentity creates from it, so that aws:PrincipalTag/<key> resolves during policy evaluation. The authorization evaluator must also resolve s3:ExistingObjectTag/<key> from the object's stored tag set so a StringEquals between the two can match.
Related but NOT covering this check: open issue 20261114T155215Z-cognito-identity-an-in-place-update-of-the.md covers an UPDATED principal-tag attribute map not reaching the GetCredentialsForIdentity (enhanced-flow) vending path, and 20261113T003009Z-cognito-identity-a-create-complete-aws-cognito-identitypoolprincipaltag.md covers the CloudFormation provider writing no map at all. This check never depends on either: it passes PrincipalTags directly on the GetOpenIdTokenForDeveloperIdentity request and exchanges the token through the BASIC flow (AssumeRoleWithWebIdentity), so the defect is in that mint-and-exchange path.
Traces: cognito-identity.e2e-principal-tags-federation-to-sts-session-tags — the run ends at the first ABAC-gated GetObject, so the legs after it (GetCallerIdentity confirming the assumed-role ARN ends in the chosen RoleSessionName, DeleteIdentityPool, and the two post-deletion ResourceNotFoundException assertions on DescribeIdentityPool and GetOpenIdTokenForDeveloperIdentity with message "IdentityPool '<pool id>' not found.") were never exercised and must be re-checked after the fix.
