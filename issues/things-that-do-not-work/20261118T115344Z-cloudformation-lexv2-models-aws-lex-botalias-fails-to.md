# cloudformation__lexv2-models: AWS::Lex::BotAlias fails to create, rolling every Lex bot/version/alias stack back to ROLLBACK_COMPLETE

> _Note: this issue was identified against the code base at commit `dbfb69aefee0710bac7557ee12bd6d5cddfc5418`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
CreateStack

## Description
One net-new root cause (1 of 1).

NOTE on existing issues: 20261109T170659Z-cloudformation-lexv2-models-2-net-new-causes-aws.md (Cause 2) and 20261117T134552Z-cloudformation-lexv2-models-a-create-complete-aws-lex.md both describe a *CREATE_COMPLETE* Lex stack whose DescribeStacks Outputs carry an OutputKey but no OutputValue. Neither covers what the suite now reports: the stack no longer reaches CREATE_COMPLETE at all — AWS::Lex::Bot and AWS::Lex::BotVersion now provision, and AWS::Lex::BotAlias is the resource that fails, so the whole stack rolls back and the output path is never reached. The suite marked neither of the two checks below OWNED (their replay keys moved from `stack_outputs#9/#12|KeyError` to `run#...|AssertionError expected CREATE_COMPLETE`), i.e. this is a distinct cause that needs its own gate.

Cause 1 of 1: the AWS::Lex::BotAlias resource provider's create path fails for a well-formed alias declaration, so CloudFormation fails the resource and rolls the stack back.
Failing checks: cloudformation__lexv2-models.cfn-lex-bot-version-alias-description-and-sentiment-analysis-read-back, cloudformation__lexv2-models.cfn-lex-bot-version-and-alias-read-back-then-resource-not-found-after-delete.
AWS: an AWS::Lex::BotAlias declaring {BotId: {Ref: <AWS::Lex::Bot>}, BotAliasName: <name>, BotVersion: {Fn::GetAtt: [<AWS::Lex::BotVersion>, BotVersion]}} (optionally SentimentAnalysisSettings {DetectSentiment: true}) is created by calling lexmodelsv2 CreateBotAlias and reaches CREATE_COMPLETE; the stack then reaches CREATE_COMPLETE. Smithy (lexmodelsv2): CreateBotAlias is PUT /bots/{botId}/botaliases, success code 202, required input members botId -> Id (@length min 10 max 10, @pattern ^[0-9a-zA-Z]+$) and botAliasName -> Name (@length 1-100, @pattern ^([0-9a-zA-Z][_-]?){1,100}$); optional botVersion -> NumericalBotVersion (@length 1-5, @pattern ^[0-9]+$) and sentimentAnalysisSettings -> SentimentAnalysisSettings; modeled errors ConflictException (409), PreconditionFailedException (412), ServiceQuotaExceededException (402), ThrottlingException (429), ValidationException (400), InternalServerException (500). The provider's Ref is the composite "<botAliasId>|<botId>" and GetAtt Arn is arn:<partition>:lex:<region>:<account>:bot-alias/<botId>/<botAliasId>; DescribeBotAlias (GET /bots/{botId}/botaliases/{botAliasId}, 200) must then report botAliasName, botVersion, botAliasStatus "Available" and the declared sentimentAnalysisSettings.
Emulator: in both checks the stack's resource events are Role CREATE_COMPLETE, Bot CREATE_COMPLETE, BotVersion CREATE_COMPLETE, **BotAlias CREATE_FAILED**, then BotVersion/Bot/Role DELETE_COMPLETE and the stack ROLLBACK_COMPLETE. The replay fails at `assert created == "CREATE_COMPLETE"` with `AssertionError: expected CREATE_COMPLETE, got 'ROLLBACK_COMPLETE': [('Role','CREATE_COMPLETE'),('Bot','CREATE_COMPLETE'),('BotVersion','CREATE_COMPLETE'),('BotAlias','CREATE_FAILED'),('BotVersion','DELETE_COMPLETE'),('Bot','DELETE_COMPLETE'),('Role','DELETE_COMPLETE'),(<stack name>,'ROLLBACK_COMPLETE')]` (the stack-name element is one run's generated value, not part of the requirement). The same alias declaration fails with and without SentimentAnalysisSettings, so the sentiment member is not the trigger. Hypothesis: the alias provider receives an empty/unresolved value for its BotVersion property from Fn::GetAtt [BotVersion, BotVersion] — the very attribute the two existing issues above report as unresolvable — and CreateBotAlias is then refused for a botVersion that cannot satisfy NumericalBotVersion's ^[0-9]+$/@length 1-5, or the provider has no working create path at all. The suite output carries only the resource statuses, not the resource-level ResourceStatusReason, so the refusal's status/code/message is not observable from the replay; a fixer should read the BotAlias event's ResourceStatusReason, which must carry Lex's own message and the provider's HandlerErrorCode.
Why: a client cannot deploy a Lex bot alias (and therefore a usable, aliased bot) with CloudFormation at all. The whole stack rolls back, so the bot, its version, its locale and the IAM role are deleted too and nothing of the deployment survives; every downstream consumer — DescribeBotAlias, ListBotAliases, and any lexv2-runtime conversation addressed by botAliasId — has nothing to talk to. This is strictly worse than the previously filed value-less-Output behavior, which at least left the resources standing.
Fix: the AWS::Lex::BotAlias resource provider in the CloudFormation crate's resource-type registry, together with the stack engine's Fn::GetAtt resolution against AWS::Lex::BotVersion's BotVersion attribute: the provider's create path must resolve its BotId/BotVersion property values, call the lexmodelsv2 CreateBotAlias handler, store "<botAliasId>|<botId>" as the physical id, expose Arn via GetAtt, and surface any Lex refusal as the resource's ResourceStatusReason with Lex's own error code and message rather than failing opaquely.
Traces: cloudformation__lexv2-models.cfn-lex-bot-version-alias-description-and-sentiment-analysis-read-back, cloudformation__lexv2-models.cfn-lex-bot-version-and-alias-read-back-then-resource-not-found-after-delete.

1. CreateStack with Capabilities=[CAPABILITY_IAM] and a template containing:
   - AWS::IAM::Role with AssumeRolePolicyDocument trusting lexv2.amazonaws.com;
   - AWS::Lex::Bot {Name: <unique>, RoleArn: {Fn::GetAtt: [Role, Arn]}, DataPrivacy: {ChildDirected: false}, IdleSessionTTLInSeconds: 300, AutoBuildBotLocales: true, BotLocales: [{LocaleId: "en_US", NluConfidenceThreshold: 0.40, Intents: [{Name: "OrderPizza", SampleUtterances: [{Utterance: "I want to order a pizza"}]}, {Name: "FallbackIntent", ParentIntentSignature: "AMAZON.FallbackIntent"}]}]};
   - AWS::Lex::BotVersion {BotId: {Ref: Bot}, BotVersionLocaleSpecification: [{LocaleId: "en_US", BotVersionLocaleDetails: {SourceBotVersion: "DRAFT"}}]};
   - AWS::Lex::BotAlias {BotId: {Ref: Bot}, BotAliasName: "live", BotVersion: {Fn::GetAtt: [BotVersion, BotVersion]}};
   - Outputs {BotId: {Value: {Ref: Bot}}, BotVersionNumber: {Value: {Fn::GetAtt: [BotVersion, BotVersion]}}, BotAliasId: {Value: {Ref: BotAlias}}, BotAliasArn: {Value: {Fn::GetAtt: [BotAlias, Arn]}}}.
2. Poll DescribeStacks(StackName=<StackId>) until a terminal status. The stack ends ROLLBACK_COMPLETE, not CREATE_COMPLETE.
3. DescribeStackEvents(StackName=<StackId>): Role, Bot and BotVersion each reach CREATE_COMPLETE, then the BotAlias resource reaches CREATE_FAILED and the stack rolls back, deleting BotVersion, Bot and Role. Read that BotAlias event's ResourceStatusReason to see the provider's refusal.
4. Repeat with SentimentAnalysisSettings: {DetectSentiment: true} added to the BotAlias Properties — same CREATE_FAILED/ROLLBACK_COMPLETE.
5. Expected instead: CREATE_COMPLETE; DescribeStackResources PhysicalResourceId for logical id "BotAlias" equals "<botAliasId>|<botId>"; Outputs carry that composite and the bot-alias ARN; lexv2-models DescribeBotAlias(botId, botAliasId) returns botAliasName "live", botVersion equal to the GetAtt version number and botAliasStatus "Available".
