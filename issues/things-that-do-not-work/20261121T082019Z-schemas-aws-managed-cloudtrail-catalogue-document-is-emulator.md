# schemas AWS-managed CloudTrail catalogue document is emulator-authored on both read paths (DescribeSchema Content, ExportSchema Content)

> _Note: this issue was identified against the code base at commit `73055cfbc4a89939a7bb60fef53ea3ae4e5e2120`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
DescribeSchema

## Description
ONE shared fault, 2 numbered causes below: reading an AWS-managed (service-owned, discovered) schema out of the `aws.events` catalogue answers 200 with a `Content` document that is NOT the document AWS publishes for that catalogue entry. The two causes are the two read paths — the describe path serves the seeded document, the export path serves the draft-04 translation OF that same seeded document — and they are two separate replay units, so a fixer MUST close both (each has its own fixture#step below) before submitting. Correcting the seed and re-replaying only the describe step leaves the export step diverging.

SHARED SHAPE
AWS: Smithy (services/service-com-amazonaws-schemas-schemas/smithy-model/com-amazonaws-schemas-schemas.json) — `DescribeSchema` GET /v1/registries/name/{RegistryName}/schemas/name/{SchemaName}, code 200, output member `Content` targets `__string` (errors BadRequestException 400, UnauthorizedException 401, ForbiddenException 403, NotFoundException 404, InternalServerErrorException 500, ServiceUnavailableException 503); `ExportSchema` GET /v1/registries/name/{RegistryName}/schemas/name/{SchemaName}/export with required @httpQuery("type") member `Type`, code 200, output `Content` targets `__string`. WHAT the document SAYS is recorded behavior only — the model constrains `Content` only to be a string. The recording shows that for an AWS-managed CloudTrail-delivered catalogue entry the describe path returns the OpenAPI 3.0.0 document AWS publishes for that entry and the export path returns its JSON-Schema draft-04 rendering, and the replay key compares the WHOLE `Content` string, so the published document's member set, member spelling, member typing and member ORDER are all part of the requirement.
Emulator: both paths answer 200 but the string differs over the whole `$.Content` value, because the document is rendered from a seed the emulator authored itself (one CloudTrail components template fanned out over the entire CloudTrail event family and every event source) rather than being the published document for the requested entry.
Why: `Content` is the entire purpose of these two operations. A client validates delivered events against it, generates language bindings from it, caches it, diffs it between versions, or hashes it. A document that declares the record differently from AWS's — any member missing, extra, differently typed, or written in another order — makes those bindings and validators disagree with ones built against AWS, and makes any cached copy or digest of the schema text differ from the published one.
Fix: the AWS-managed catalogue SEED in the schemas service's state module, which both read paths reach through the stored schema row — not the handlers and not the serializers. The describe path's envelope rendering and the export path's OpenApi3 -> JSONSchemaDraft4 conversion already reproduce the recorded shape conventions (see Traces for file/line citations); what is wrong is the source document they publish. The fixer must diff the SERVED document against the recorded one end to end rather than spot-checking a subtree: three earlier reports of these same two steps were each closed after correcting one visible subtree and the steps still diverge.

NOT already covered: both clusters come back from this replay with an EMPTY `owned_by` and an EMPTY `stub_path`, so no open issue carries their replay key. The open issue 20261110T235024Z-schemas-listschemas-omits-aws-managed-schemas-from-the.md owns the other 56 clusters of this run (which entries ListSchemas enumerates and what LastModified they report) and does NOT cover the document a schema READ returns. Three prior reports of these exact two steps are in the RESOLVED folder (20261101T214917Z-schemas-aws-managed-schema-content-remains-a-seeded-document.md and its predecessors 20261030T170146Z / 20261029T203553Z / 20261023T194150Z); a resolved issue covers nothing, and the last of them closes with a caveat recording that both steps still report `$.Content: value_mismatch` after its change.

AWS: `DescribeSchema` 200 with `Content` = the published OpenAPI 3.0.0 document for the entry, of the form {"openapi":"3.0.0","info":{"title":"<detail type> published by <source>","version":"1.0.0"},"paths":{},"components":{"schemas":{"<EventName>":{"type":"object","properties":{...}}}}} — the detail type and the publishing source in the title come from the requested registry/schema name, not from any recording. The portion of the recorded document the replay detail exposes (the openapi/info/paths/components envelope and the record's members from `addendum` through `userIdentity.onBehalfOf.{identityStoreArn,userId}`) agrees member-for-member and order-for-order with the template, so the residual difference lies in the region the detail clips — at or after `components.schemas.<EventName>.properties.userIdentity.properties.sessionContext` — and the replay withholds the actual value, so it must be obtained by issuing the call and diffing.
