=== Cause 1 of 2: an Aurora DBCluster created through CloudFormation publishes DBCluster.Endpoint as the listener's bind literal instead of the cluster's own DNS name ===
AWS: Smithy DBCluster$Endpoint is documented "The connection endpoint for the primary instance of the DB cluster" — one DNS name per cluster, derived from the cluster's own identifier: <cluster-id>.cluster-<suffix>.<region>.rds.amazonaws.com, with ReaderEndpoint the same name carrying the cluster-ro- prefix and the IDENTICAL suffix. The writer endpoint therefore always begins with the DBClusterIdentifier the request supplied (the comparison is case-insensitive, since RDS lowercases identifiers).
Emulator: after a stack containing AWS::RDS::DBCluster (Engine=aurora-mysql) + AWS::RDS::DBInstance reaches CREATE_COMPLETE, DescribeDBClusters answers Endpoint='127.0.0.1' — the core listener's bind host, carrying no cluster identity at all. The reader side of the same envelope is built as a per-resource DNS name, so the two sides of one envelope are produced by different code.
Why: a client cannot tell two clusters apart, cannot derive the writer name from the reader name (or the reverse) as every read/write-split driver does, and cannot verify that a stack update replaced the cluster. Any config generated from the stack's outputs points at a loopback literal rather than at the cluster.
Fix: the DB-cluster envelope serializer / the state field that records a cluster's published endpoint — the writer address must be built from the cluster identifier by the same code path that already builds the cluster-ro- reader name, and the CloudFormation AWS::RDS::DBCluster provisioning path must go through it.
Traces: rds.deploy-db-cluster-cfn-behaves (AssertionError: 127.0.0.1, on `assert endpoint.lower().startswith(cluster_id.lower())`).

=== Cause 2 of 2: the automated-backup lifecycle of a live DB instance never settles, so DescribeDBInstanceAutomatedBackups reaches no verdict ===
AWS: a running DB instance with BackupRetentionPeriod greater than 0 has exactly one automated-backup record describable by DBInstanceIdentifier whose Status is 'active' (Smithy DBInstanceAutomatedBackup$Status: "active - Automated backups for current instances / retained - Automated backups for deleted instances / creating - Automated backups that are waiting for the first automated snapshot to be available"). After DeleteDBInstance with the default DeleteAutomatedBackups=true, that record goes away and the operation refuses the identifier with DBInstanceAutomatedBackupNotFoundFault (HTTP 404), message "DBInstanceAutomatedBackup for DBInstance <identifier> not found." — the fixed text is everything but <identifier>, which is the value the request carried.
Emulator: the check creates a mysql instance (BackupRetentionPeriod=1, StorageType=gp2), waits for 'available', then polls DescribeDBInstanceAutomatedBackups for a non-empty DBInstanceAutomatedBackups list, then deletes the instance and polls for the record to disappear. No poll in the check sleeps unconditionally, so a settled lifecycle finishes in seconds; instead the check is killed by the harness: 'Check timed out after 60.0s'. One of the polled conditions is therefore never reached — the active record is never projected for a live instance (empty list), or the record is never withdrawn once the instance is deleted. Hypothesis: the instance's automated-backup projection (has_automated_backup / instance_automated_backup_to_wire) or the retained-record handling on delete does not settle for a plain mysql instance; the report shows only the budget exhaustion, not which of the two polls stalled.
Why: a client polling for its instance's backup record — the documented way to confirm continuous backups are in place before a restore or a PITR — never gets one, and backup-governance tooling sees a region with no automated backups at all.
Fix: the DescribeDBInstanceAutomatedBackups handler's projection of live instances plus the DeleteDBInstance path that converts (or removes) that record — services/service-com-amazonaws-rds-amazonrdsv19/src/ops/describe_db_instance_automated_backups.rs and the automated-backup records in the service's state; the 'active' record must exist for every live instance with a non-zero retention period and must disappear with the instance under the default DeleteAutomatedBackups.
Traces: rds.describe-instance-automated-backups (Error: Check timed out after 60.0s).

## Evidence
Cause 1: AssertionError: 127.0.0.1 — raised by `assert endpoint.lower().startswith(cluster_id.lower()), endpoint` in check_rds_deploy_db_cluster_cfn_behaves.py line 64, after a CloudFormation stack with AWS::RDS::DBCluster (Engine=aurora-mysql, BackupRetentionPeriod=1) + AWS::RDS::DBInstance (db.t3.medium) reached CREATE_COMPLETE and DescribeDBClusters reported Status=available with the single writer member. Expected: Endpoint is a DNS name beginning with the DBClusterIdentifier (AWS form <cluster-id>.cluster-<suffix>.<region>.rds.amazonaws.com); actual: the bare literal 127.0.0.1. The loopback literal and the per-run cluster id are environment values; the requirement is that the published writer endpoint is a per-cluster DNS name rooted on the cluster identifier, sharing its suffix with ReaderEndpoint.

Cause 2: Error: Check timed out after 60.0s for rds.describe-instance-automated-backups. The check's own waits are condition-polls (instance 'available' at 10 s intervals, automated-backup record non-empty at 5 s intervals, instance gone at 10 s intervals, record gone at 5 s intervals) with an immediate first probe each, so a settled emulator completes in seconds and no fixed sleep can consume the budget. Expected on AWS: DescribeDBInstanceAutomatedBackups(DBInstanceIdentifier=<id>) returns one record with DBInstanceIdentifier=<id> and Status='active' while the instance lives, and after DeleteDBInstance(SkipFinalSnapshot=true) it refuses with 404 DBInstanceAutomatedBackupNotFoundFault, message "DBInstanceAutomatedBackup for DBInstance <id> not found." Actual: no verdict — one of those two transitions never occurs inside the budget.
