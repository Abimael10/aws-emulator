# QConnect message-template attachment reads diverge: epoch uploadedTime/urlExpiry and a deleted attachment still rendered

> _Note: this issue was identified against the code base at commit `a7bef14f25237d595eccda8ae7c58763b2cfbcfb`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
CreateMessageTemplateAttachment

## Description
Three net-new causes on the Amazon Q in Connect message-template ATTACHMENT path, all in the same service (service token `wisdom`, Smithy service com.amazonaws.qconnect#WisdomService). Causes 1 and 2 are the same fault — the modelled `date-time` timestamp members of `MessageTemplateAttachment` are serialized as bare epoch numbers — surfacing on the two operations that project an attachment; cause 3 is the attachment lifecycle: a deleted attachment is still reported by a later render. All three must be closed before this issue is done.

Cause 1 of 3: CreateMessageTemplateAttachment answers 200 but with `attachment.uploadedTime` and `attachment.urlExpiry` as epoch-second NUMBERS instead of the modelled date-time strings.
AWS: Smithy (services/service-com-amazonaws-qconnect-wisdomservice/smithy-model/com-amazonaws-qconnect-wisdomservice.json) — CreateMessageTemplateAttachment, POST /knowledgeBases/{knowledgeBaseId}/messageTemplates/{messageTemplateId}/attachments, success 200, output shape CreateMessageTemplateAttachmentResponse with member `attachment` -> MessageTemplateAttachment. On that shape BOTH timestamp members carry an explicit format: `uploadedTime` (target Timestamp, timestampFormat `date-time`, @required, doc "The timestamp when the attachment file was uploaded.") and `urlExpiry` (target Timestamp, timestampFormat `date-time`, @required, doc "The expiration time of the pre-signed Amazon S3 URL."). `date-time` is RFC3339/ISO-8601, i.e. a JSON STRING such as the sibling recorded value shape '2026-09-06T19:23:22.468Z' — not the restJson1 default epoch-seconds. The recording asserts these two members only on shape (they are per-run values), and the recorded shape is the date-time string.
Emulator: HTTP 200 with the two members emitted as JSON numbers — replay detail "$.attachment.uploadedTime: value_mismatch (expected '<shaped-not-asserted>', got 1794969357.279359)" and "$.attachment.urlExpiry: value_mismatch (expected '<shaped-not-asserted>', got 1794971157.279359)". The handler itself holds the right type (services/service-com-amazonaws-qconnect-wisdomservice/src/state/message_template_attachments.rs:134-143, `MessageTemplateAttachmentFile::to_attachment` builds `aws_smithy_types::DateTime` values), so the format is lost on the way out, not in state.
Why: a client deserializing with any AWS SDK expects a date-time string for these members because the model pins the format there; a number either fails deserialization outright or is read as a wall-clock instant in the wrong unit. A caller that uses `urlExpiry` to decide whether to refresh the pre-signed download URL therefore cannot compare it to a clock at all, and any code formatting `uploadedTime` for display or for a condition gets a type error instead of a timestamp.
Fix: the output serialization of this service — the MessageTemplateAttachment timestamp members must be written in the modelled `date-time` (ISO-8601, Z-suffixed) form rather than epoch seconds, in the serializer/schema the operation's output walk uses, so every operation projecting an attachment is fixed at once. Related already-open issues report the same epoch-vs-date-time fault on the message-template record's own createdTime/lastModifiedTime (20261111T121353Z-wisdom-qconnect-message-template-responses-omit-modeled-members-emit.md and 20261111T125533Z-wisdom-qconnect-message-template-write-and-version-paths-omit.md); neither carries this fixture step's replay key and neither covers the attachment members, so this cause is net-new.
Traces: qconnect-message-template-attachment-render#task#4 (CreateMessageTemplateAttachment, 200 vs 200, keys $.attachment.uploadedTime,$.attachment.urlExpiry).

Cause 2 of 3: RenderMessageTemplate projects the same attachment with the same epoch-number timestamps.
AWS: Smithy — RenderMessageTemplate, POST /knowledgeBases/{knowledgeBaseId}/messageTemplates/{messageTemplateId}/render, success 200, output member `attachments` -> MessageTemplateAttachmentList (uniqueItems) of MessageTemplateAttachment. Every element carries the same @required members, so each rendered attachment's `uploadedTime` and `urlExpiry` are date-time strings, exactly as on the upload response.
Emulator: HTTP 200 whose attachments element carries numbers — replay detail "$.attachments[0].uploadedTime: value_mismatch (expected '<shaped-not-asserted>', got 1794969357.279359)" and "$.attachments[0].urlExpiry: value_mismatch (expected '<shaped-not-asserted>', got 1794971157.279359)". Projection site: services/service-com-amazonaws-qconnect-wisdomservice/src/ops/render_message_template.rs:263 via `MessageTemplate::attachments_out` (src/state/message_template_attachments.rs:240-247), which reuses the same `to_attachment` projection as cause 1.
Why: the render path is how a client discovers the attachments of a message it is about to send, including each attachment's download URL and that URL's expiry. With numbers there, SDK deserialization of the render response fails or yields unusable timestamps, so the attachment list cannot be consumed even though the attachment is present.
Fix: same component as cause 1 — the date-time serialization of MessageTemplateAttachment's timestamp members, which is shared by the render projection; no change to the render logic itself is needed once the format is right. The open issue 20261115T171229Z-wisdom-qconnect-rendermessagetemplate-omits-the-attachments-member-for-a.md covers the member being ABSENT (it is now present, so that issue does not cover this), not its timestamp encoding.
Traces: qconnect-message-template-attachment-render#task#5 (RenderMessageTemplate, 200 vs 200, keys $.attachments[0].uploadedTime,$.attachments[0].urlExpiry).

Cause 3 of 3: after the attachment is deleted, RenderMessageTemplate still reports it — the render of the working copy keeps an attachment the account no longer holds.
AWS: Smithy — DeleteMessageTemplateAttachment, DELETE /knowledgeBases/{knowledgeBaseId}/messageTemplates/{messageTemplateId}/attachments/{attachmentId}, success 204, documented as "Deletes the attachment file from the Amazon Q in Connect message template that is referenced by $LATEST qualifier. Attachments on available message template versions will remain unchanged." So on AWS a successful delete removes that attachment from the template's WORKING COPY, and every later read or render of the $LATEST template reports the remaining attachments only — the deleted attachmentId appears in no subsequent RenderMessageTemplate response. The recording asserts exactly that: after the delete step, the render's attachments must contain NO element whose attachmentId is the deleted one.
Emulator: HTTP 200 whose attachments list still carries the deleted attachment in full — replay detail "$.attachments[0]: unexpected_present (expected {'attachmentId': '<the deleted id>'}, got {'contentDisposition': 'ATTACHMENT', 'name': '<uploaded file>.txt', 'uploadedTime': ..., 'url': 'https://<host>/knowledgeBases/<kb>/messageTemplates/<mt>/attachments/<id>/file', 'urlExpiry': ..., 'attachmentId': '<the deleted id>'})". Root cause: DeleteMessageTemplateAttachment is still a 501 scaffold stub (services/service-com-amazonaws-qconnect-wisdomservice/src/ops/delete_message_template_attachment.rs:4 SCAFFOLDED marker, :170 returns `Scaffolded::not_implemented`), so nothing ever removes the record from `MessageTemplate::attachments`. The stub itself is already filed as 20261117T164534Z-qconnect-deletemessagetemplateattachment-stub.md under the `qconnect` token; that issue does NOT carry this fixture step's replay key and its replay never exercises the render, so this wire-visible consequence on RenderMessageTemplate is net-new and must be re-replayed here.
Why: a client that deletes an attachment (because it was wrong, or carried data that must go) and then renders the template still gets that attachment back, with a live download URL for bytes the emulator still serves. The delete is reported as impossible (501) and the state is unchanged, so an attachment can never be withdrawn from a template — a correctness and data-retention divergence, not a cosmetic one.
Fix: the message-template attachment lifecycle in this service — DeleteMessageTemplateAttachment must remove the addressed attachment from the working copy's attachment list (404 ResourceNotFoundException for a knowledge base, template or attachmentId this account does not hold; the published versions' snapshots deliberately unchanged) and answer its modelled 204, after which the shared `attachments_out` projection already drops it from GetMessageTemplate and RenderMessageTemplate.
Traces: qconnect-message-template-attachment-render#task#7 (RenderMessageTemplate after the delete, 200 vs 200, key $.attachments[0]).
