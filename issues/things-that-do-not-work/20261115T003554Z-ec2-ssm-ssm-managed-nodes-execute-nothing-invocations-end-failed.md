# SSM managed nodes execute nothing (invocations end Failed with rc=127 and empty stdout), IMDS is unserved inside the node, and transit-gateway route-table associations are not recorded

> _Note: this issue was identified against the code base at commit `a49cdab94fc41177458b6e53730040285f53d8d6`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
SendCommand

## Description
Three net-new root causes.

Cause 1 of 3: AWS-RunShellScript invocations against a registered managed node never execute — they terminate in status 'Failed' with ResponseCode 127 (or 1) and empty StandardOutputContent/StandardErrorContent, so nothing the script computes or observes is ever reported.
AWS: Smithy (ssm) models SendCommand -> Command and GetCommandInvocation -> GetCommandInvocationResult with Status (CommandInvocationStatus), ResponseCode and StandardOutputContent/StandardErrorContent. For a reachable managed node and a valid shell document AWS drives the invocation to Status 'Success' with ResponseCode 0 and StandardOutputContent equal to the script's stdout; a script that exits non-zero yields Status 'Failed' WITH that script's output and a non-zero ResponseCode. ResponseCode 127 with empty output means the command was never found/run, which AWS does not produce for a well-formed document on a healthy node (guest execution itself is recorded behavior only).
Emulator: every in-node probe reports "status='Failed' rc=127 stderr=''" or "the guest reported no stdout: 'Failed' stderr=''"; an arithmetic probe over 1..100 returned '' instead of '5050'; a probe reading an SSM parameter through the instance profile returned '2' instead of the computed '207'; the AL2 identity probe returned '-'; a listener probe returned SIM2REAL_NOT_LISTENING; and one user-data check never terminated at all (Check timed out after 60.0s). The expected literals ('5050', '207') are the checks' own computed values; the requirement is that the invocation reaches 'Success' and reports the script's real stdout.
Why: Run Command is the primary way clients inspect and configure fleets. A terminal 'Failed' with no output and rc=127 is indistinguishable from "node unreachable", "document wrong" and "script exited non-zero", so automation cannot branch; and because the node is simultaneously reported Online by DescribeInstanceInformation, an operator is told the fleet is healthy while nothing runs. Open issues 20261114T143448Z-ec2-ssm-guest-execution-never-terminates-describeinstanceinformation-reports.md and 20261115T000000Z-ec2-ssm-a-managed-nodes-guest-has-no-network-programs.md describe the same family but do not carry these checks' replay keys.
Fix: the SSM command-invocation execution path — document delivery to the managed node and collection of its exit status and output streams.
Traces: ec2__ssm.ssm-run-command-executes-on-a-real-managed-instance-and-returns-its-stdout; ec2__ssm.guest-user-data-output-read-back-through-run-command; ec2__ssm.guest-user-data-does-not-rerun-after-a-stop-start-cycle; ec2__ssm.nacls-are-stateless-but-security-groups-are-stateful; ec2__ssm.run-command-shows-sshd-listening-while-no-group-allows-port-22-from-the-internet; ec2__ssm.sg-resolution-prefix-list-and-reachability-analyzer; ec2__ssm.vscan-deprecated-ami-guest-has-more-pending-security-updates-than-the-current-ami.

Cause 2 of 3: the instance metadata service is not served inside a managed node — both the IMDSv1 GET and the IMDSv2 token PUT come back with an empty HTTP status and an empty body.
AWS: with MetadataOptions.HttpTokens=optional an unauthenticated GET of http://169.254.169.254/latest/meta-data/instance-id is served with HTTP 200 and the instance id; with HttpTokens=required it is refused with HTTP 401 and only a token-bearing read succeeds. A PUT to /latest/api/token with X-aws-ec2-metadata-token-ttl-seconds=21600 (the documented maximum) is served with HTTP 200 and a token, and a TTL above 21600 is refused with HTTP 400 (recorded behavior only; EC2's model carries the HttpTokens/HttpPutResponseHopLimit members but not the endpoint's status codes).
Emulator: the guest sees no status at all for either arm — "with HttpTokens=optional an unauthenticated IMDS read must be served; the guest saw status ''" with probe output 'GUEST-V1-STATUS \nwc: : No such file or directory\nGUEST-V1-BYTES \nGUEST-V1-HAS-IID no\nGUEST-TOKEN-BYTES \nGUEST-V2-STATUS \ncat: : No such file or directory\nGUEST-V2-BODY ', and "a token PUT with TTL 21600 (the documented maximum) must be served with 200; the guest saw ''". So neither the 200/401 enforcement boundary nor the TTL bound is observable.
Why: IMDSv2 enforcement is a security control customers audit; an endpoint that answers nothing makes both the enforced and the optional posture look identical, and every in-node credential provider and agent that depends on IMDS has no identity or credentials.
Fix: the guest-facing IMDS endpoint — its HttpTokens enforcement, its token PUT handling and TTL validation, and the per-instance metadata state behind it.
Traces: ec2__ssm.guest-imdsv1-read-rejected-once-http-tokens-is-required; ec2__ssm.imds-token-ttl-above-21600-seconds-rejected-while-the-maximum-is-served.

Cause 3 of 3: transit-gateway route-table associations are accepted but not recorded — reading the associations of the route table returns an empty set after both VPC attachments were associated with it.
AWS: Smithy (ec2) models AssociateTransitGatewayRouteTable and GetTransitGatewayRouteTableAssociations; after a successful association the attachment appears in that route table's associations with State 'associated', and the table's routes govern forwarding between the attached VPCs (a blackhole route stops traffic). The association read-back is recorded behavior only for its exact shape.
Emulator: after associating both attachments the association lookup for the route table reports {} — "both attachments must be associated with '<tgw-rtb-id>' so their lookups use the table this check writes; the table reports {}" (the route-table id is a per-run value).
Why: a client that associates attachments with a purpose-built route table and then writes routes into it is operating on a table nothing is attached to: forwarding does not follow the table it wrote, and a blackhole route it adds to stop traffic has no effect. The resulting network behaviour is the opposite of what the control plane reports.
Fix: the transit-gateway route-table association state and the association read paths (GetTransitGatewayRouteTableAssociations / DescribeTransitGatewayAttachments' association view) that forwarding is derived from.
Traces: ec2__ssm.dtgw-transit-gateway-forwards-packets-between-two-vpcs-and-a-blackholed-route-stops-them.

## Steps to Reproduce
Cause 1: launch an EC2 instance with an instance profile carrying AmazonSSMManagedInstanceCore, wait for ssm.DescribeInstanceInformation to report it, then ssm.SendCommand(DocumentName='AWS-RunShellScript', InstanceIds=[<id>], Parameters={'commands': ['seq 1 100 | paste -sd+ | bc']}) and poll ssm.GetCommandInvocation. AWS reaches Status 'Success' with StandardOutputContent '5050'; the emulator reaches Status 'Failed' with ResponseCode 127 and empty output.

Cause 2: launch with MetadataOptions={'HttpTokens': 'optional'} and from inside the node curl -s -o /dev/null -w '%{http_code}' http://169.254.169.254/latest/meta-data/instance-id (expect 200); relaunch with HttpTokens='required' and repeat without a token (expect 401) and with a token from PUT /latest/api/token (expect 200). Also PUT /latest/api/token with X-aws-ec2-metadata-token-ttl-seconds: 21600 (expect 200) and with 21601 (expect 400). The emulator returns an empty status for every arm.

Cause 3: create a transit gateway and two VPC attachments, create a transit-gateway route table, call ec2.AssociateTransitGatewayRouteTable for both attachments, then ec2.GetTransitGatewayRouteTableAssociations(TransitGatewayRouteTableId=<id>). AWS lists both attachments as 'associated'; the emulator lists none. Then write a route and a blackhole route into that table and confirm forwarding between the two VPCs follows it.
