# savingsplans Describe responses return synthesized values instead of stored plan and rate catalog

> _Note: this issue was identified against the code base at commit `e91c89e9d6482fa7ae1cb641524eb980150715bc`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
DescribeSavingsPlanRates

## Description
Replay of the savingsplans wire corpus (simparity-wire-aws-v1, 6 fixtures / 27 steps, score 85.2%) shows TWO net-new causes in the savingsplans service crate. BOTH must be closed before this issue is submitted. They share one fault: the response projections for the Describe* operations emit values the emulator synthesizes on the fly rather than the catalog row / stored plan record the operation is defined to return, so the body is shaped correctly but its contents are not the service's data.

=== Cause 1 of 2: DescribeSavingsPlanRates returns one constant rate for every row and malformed/mis-paired operation codes (fixture savingsplans-queued-plan-delete-lifecycle, step task#8) ===

AWS: Smithy: DescribeSavingsPlanRates (POST /DescribeSavingsPlanRates, http code 200), input savingsPlanId (SavingsPlanId, @required) + filters (SavingsPlanRateFilterList) + maxResults (range 1..1000); output searchResults -> SavingsPlanRateList of com.amazonaws.savingsplans#SavingsPlanRate with members rate (Amount), currency (CurrencyCode enum), unit (SavingsPlanRateUnit enum), productType (SavingsPlanProductType enum), serviceCode (SavingsPlanRateServiceCode enum), usageType (SavingsPlanRateUsageType, @length 0..255, pattern '^[a-zA-Z0-9_ /.:-]+$'), operation (SavingsPlanRateOperation, @length 0..255, pattern '^[a-zA-Z0-9_ /.:-]*$') and properties (SavingsPlanRatePropertyList of SavingsPlanRateProperty{name: SavingsPlanRatePropertyKey enum [region|instanceType|instanceFamily|productDescription|tenancy], value}); modeled errors ValidationException (400), ResourceNotFoundException (404), InternalServerException (500). The per-row rate value itself is not modeled, so for the rate content this is recorded behavior only: the recording shows AWS returning, on HTTP 200, one row PER PRICED COMBINATION of the rate dimensions, where each row's `rate` is the rate of THAT combination and each row's `operation` is the AWS usage-operation code that identifies it. In the recording the rows for one instanceType/region/tenancy differ from one another exactly as their productDescription differs: the bare 'RunInstances' code carries productDescription 'Linux/UNIX' at rate '0.066', 'RunInstances:0006' carries 'Windows with SQL Server Standard' at rate '0.638', 'RunInstances:0200' carries 'Linux with SQL Server Web' at rate '0.133', and so on across all 32 returned rows. The requirements here are the general ones: (a) a row's rate is the rate for that row's dimension tuple, so distinct product descriptions must not share one rate; (b) a row's `operation` is a real usage-operation code -- the bare operation name, or that name suffixed ':' plus the hex operation suffix AWS assigns to the product description; (c) the code and the productDescription property in the same row must name the same product. The particular numbers and codes in the recording ('0.066', ':0006', ':0200') are catalog values filling that template, not part of it.

Emulator: HTTP 200 (status matches) but EVERY row in searchResults carries the identical rate string '0.06696960' regardless of productDescription -- the Windows-with-SQL-Server row, the Linux-with-SQL-Server-Web row and the Linux/UNIX row all come back at the same price -- and the operation codes are not real codes: the row whose productDescription is 'Red Hat BYOL Linux' reports operation 'RunInstances:00g0', whose suffix '00g0' is not hexadecimal and corresponds to no AWS usage operation, and its pairing with that product description matches no recorded row. All 32 result entries diverge ($.searchResults[0] .. $.searchResults[31] are each reported missing, i.e. no expected row is reproduced). Hypothesis: the handler generates rows by iterating the rate-dimension enums and formatting one computed hourly amount (a commitment-derived figure printed to 8 decimal places) for all of them, and derives the operation suffix arithmetically from the product-description index instead of looking up a stored catalog row.

Why: DescribeSavingsPlanRates IS the price lookup. A client that uses it to compute coverage, to pick a commitment, or to compare a Windows/SQL Server rate against a Linux rate gets a single flat price for every product and therefore a wrong answer, with no error to signal it. Clients that key off `operation` to join these rows against Cost-and-Usage-Report line items find no matching usage-operation code at all, because codes like 'RunInstances:00g0' do not exist in any billing record.

Fix: the DescribeSavingsPlanRates handler and the rate catalog it projects from -- rows must be served from a stored per-combination catalog (rate keyed by serviceCode/usageType/operation/productDescription/region/tenancy/instanceType), with the usage-operation code taken from that catalog entry rather than computed, and the amount formatted as the catalog holds it instead of a single derived value reused for all rows.

=== Cause 2 of 2: DescribeSavingsPlans projects an empty tag map and omits the plan's null-valued members (fixture savingsplans-queued-plan-delete-lifecycle, step task#11) ===

AWS: Smithy: DescribeSavingsPlans (POST /DescribeSavingsPlans, http code 200), output savingsPlans -> SavingsPlanList of com.amazonaws.savingsplans#SavingsPlan, whose members include tags (TagMap: TagKey -> TagValue, no key/value constraints), region (Region), ec2InstanceFamily (EC2InstanceFamily), state (SavingsPlanState enum), start/end/returnableUntil (String), commitment/upfrontPaymentAmount/recurringPaymentAmount (Amount), termDurationInSeconds (long, default 0); modeled errors ValidationException (400), InternalServerException (500). Tag-key spelling is unconstrained by the model, so for the tag behavior this is recorded behavior only: the recording shows AWS returning the plan record with its tag set as written on the plan, including a key carrying the reserved 'aws:' prefix ('aws:tag:<name>' -> its value), and returning the dimension members that do not apply to a Compute plan (region, ec2InstanceFamily) as explicit nulls in the body rather than dropping them. Requirement: the described plan's tags map is the stored tag set projected verbatim (every key as supplied, mapped to its supplied value), and a member that has no value for this plan type is still present in the serialized plan.

Emulator: HTTP 200 (status matches) but the described plan comes back with tags = {} -- the reserved-prefix entry that was written earlier in the same fixture and acknowledged with a success response is absent -- and the serialized plan OMITS the region and ec2InstanceFamily keys entirely where the recorded answer carries them as null. Everything else about the record (savingsPlanId, savingsPlanArn, offeringId, description, state 'queued-deleted', savingsPlanType, paymentOption, productTypes, currency, commitment, upfront/recurring amounts, termDurationInSeconds, and the start/end/returnableUntil relationships) matches; the absolute timestamps differ only because they are per-run clock values and are NOT part of this finding.

Why: a client that tags a Savings Plan and then reads it back through DescribeSavingsPlans sees a tag it successfully wrote simply gone, so tag-driven cost allocation, inventory filtering and tag-based authorization all evaluate against a truncated set, and because both the write and the read answered 200 there is no signal that state was dropped. The missing null members break clients and SDK-adjacent code that read a fixed set of keys off the plan object instead of probing for presence.

Fix: the DescribeSavingsPlans handler's plan-to-wire projection and the tag ingestion into the plan record in the service state -- the projection must emit the stored tag map unfiltered (including reserved-prefix keys) and must serialize the plan's unset dimension members as null instead of skipping them; if a reserved-prefix key is to be refused it must be refused at write time with the modeled ValidationException (400), not accepted and silently discarded.
