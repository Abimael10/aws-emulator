# cloudformation__network-security-manager: 2 net-new causes — an AWS::NetworkSecurityManager::Scope never creates (stack rolls back), and a stack holding an ::Template can never roll back (Template DELETE_FAILED -> ROLLBACK_FAILED, NSM resources leaked)

> _Note: this issue was identified against the code base at commit `81c8b967db5bad2d27b5d567dc6b4b0ded0abe26`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
CreateStack

## Description
Two distinct root causes observed replaying the simparity-behavioral-aws-v1 behavioral suite against the emulator built from this checkout. Both appear when CloudFormation provisions Network Security Manager resource types (AWS::NetworkSecurityManager::Rule/Template/Policy/Scope) through the CFN resource-handler path; neither failing check was marked ALREADY FILED or OWNED by the replay report, so both are recorded here, and the related open Network Security Manager issues are named inside each cause.

=== Cause 1 of 2: a CloudFormation stack that must roll back a stack containing an AWS::NetworkSecurityManager::Template ends ROLLBACK_FAILED instead of ROLLBACK_COMPLETE, and leaves the NSM resources behind ===
AWS: a CREATE whose resource fails is rolled back by deleting every resource CloudFormation already created, in reverse dependency order; when each delete succeeds the stack reaches the terminal status ROLLBACK_COMPLETE and every created resource is gone from the owning service. The delete CloudFormation issues for AWS::NetworkSecurityManager::Template is NSM DeleteTemplate (Smithy: DeleteTemplate, DELETE /templates/{templateIdentifier}, templateIdentifier @httpLabel @required length 1..1010, output Unit, success @http code 204, @idempotent; modeled errors AccessDeniedException 403, ConflictException 409, InternalServerException 500, ThrottlingException 429, ValidationException 400 — no 501/NotImplemented outcome exists). A rollback only reaches ROLLBACK_FAILED when a resource delete genuinely fails, and only that resource's row carries DELETE_FAILED; a template whose associated rule is still present is deleted first and the rule after it, so both deletes succeed. In the recorded rejection flow the stack's terminal status is ROLLBACK_COMPLETE and ListPolicies/ListTemplates/ListRules no longer list the rolled-back names.
Emulator: NSM DeleteTemplate is an unimplemented scaffold that answers HTTP 501 with error code NotImplemented and a message of the form "operation DELETE /templates/{templateIdentifier} is not implemented in this emulator" (fixed text plus the operation's method and URI; no part of it comes from the request). CloudFormation relays that failure as a Template DELETE_FAILED stack event and the stack settles in ROLLBACK_FAILED. Both failing checks observe it: the waf-stack check's decisive event rows are [('Rule','CREATE_COMPLETE'), ('Scope','CREATE_FAILED'), ('Template','CREATE_COMPLETE'), ('Policy','CREATE_COMPLETE'), ('Scope','DELETE_COMPLETE'), ('Policy','DELETE_COMPLETE'), ('Template','DELETE_FAILED'), (<stack>,'ROLLBACK_FAILED')], and the ambiguous-reference check asserts the rejected stack ends ROLLBACK_COMPLETE and gets 'ROLLBACK_FAILED'. Because the Template delete never completes, the Rule behind it is never deleted either, so the rule and template remain listed in NSM after the rollback.
Why: a client that relies on AWS's rollback contract is left with a stack in a terminal failure state that only manual resource deletion can clear, and with NSM rules/templates still live (and still billable/limit-consuming) after a create it believes was fully undone. Automation that treats ROLLBACK_COMPLETE as "the create was cleanly undone and the names are free again" either loops or re-creates onto names that still exist; the subsequent stack delete fails the same way.
Fix: implement the NSM DeleteTemplate handler and its state (remove the template entity, release its name, refuse with 409 ConflictException only while something still references it) in services/service-com-amazonaws-networksecuritymanager-piccolocustomerapiservice/src/ops/delete_template.rs (today its handle() returns Scaffolded::not_implemented("DeleteTemplate")), so the CloudFormation AWS::NetworkSecurityManager::Template resource handler's DELETE succeeds and the rollback reaches ROLLBACK_COMPLETE with the rule deleted behind it. Related open issues: the Network Security Manager stub issues cover other operations (DeleteRule, ListRules, CreateTemplate, CreateScope, UpdateRule, Create*Snapshot) — none of them names DeleteTemplate, and none carries these two CloudFormation checks' replay keys.
Traces: cloudformation__network-security-manager.deploy-network-security-manager-waf-stack-reads-back-then-removed, cloudformation__network-security-manager.deploy-network-security-manager-policy-ambiguous-reference-rejected.

=== Cause 2 of 2: AWS::NetworkSecurityManager::Scope goes CREATE_FAILED, so a valid Rule+Template+Policy+Scope stack never reaches CREATE_COMPLETE ===
AWS: AWS::NetworkSecurityManager::Scope is created through NSM CreateScope (Smithy: POST /scopes, success @http code 201, @idempotent; required input scopeName (length 1..128, pattern ^[a-zA-Z0-9][a-zA-Z0-9 _.:/=+\-@]*$) and scopeConfiguration, optional clientToken/scopeDescription/isPublished (default true)/tags; CreateScopeOutput requires scopeId (^[a-z0-9]{1,64}$), scopeArn, scopeName, status, version (^[1-9][0-9]*$) and also carries scopeConfiguration, updateToken, isSnapshot, hasPublishedVersion, updatedAt (@timestampFormat date-time); modeled errors 403/409/500/402/503/400/429/400 — 501 is not among them). A valid declaration therefore reaches CREATE_COMPLETE, Ref and Fn::GetAtt ScopeArn resolve to the scopeArn ListScopes returns for that scopeName, GetAtt ScopeId/Status resolve to the scopeId and ACTIVE, and the whole four-resource stack reaches CREATE_COMPLETE.
Emulator: the Scope resource's create fails — the check records a Scope CREATE_FAILED row — because NSM CreateScope is an unimplemented scaffold answering HTTP 501 NotImplemented ("operation POST /scopes is not implemented in this emulator"). CloudFormation then rolls the whole stack back, so no Ref/GetAtt output, no NSM read-back and no stack-delete assertion in the check is reachable.
Why: no CloudFormation template that declares a Network Security Manager scope can be deployed at all, and the 501 is outside the service's modeled exception set, so neither CloudFormation's resource handler nor an SDK caller can classify it as a retryable or a client failure; a scope is the accounts-and-resources selection a policy deployment needs, so the policy estate cannot be expressed in CFN.
Fix: implement the NSM CreateScope handler and its scope entity state (scopeId/scopeArn generation, version and updateToken issuance, DRAFT vs ACTIVE from isPublished, updatedAt, tag storage) in services/service-com-amazonaws-networksecuritymanager-piccolocustomerapiservice/src/ops/create_scope.rs with its 201 serializer, and make the created scope visible to ListScopes/GetScope so CloudFormation's AWS::NetworkSecurityManager::Scope handler can stabilize and publish its physical id and attributes. Related open issue: 20261118T171232Z-network-security-manager-unimplemented-operations-break-lifecycle-checks.md describes the same CreateScope 501 as its Cause 2, and 20261109T164319Z-network-security-manager-create-entity-operations-diverge-3.md describes it as its Cause 3; neither carries this CloudFormation check's replay key, so a fixer closing them must re-replay the check named below as well.
Traces: cloudformation__network-security-manager.deploy-network-security-manager-waf-stack-reads-back-then-removed.

## Steps to Reproduce
Boot the emulator from this checkout and replay the two behavioral checks, or drive CloudFormation directly:

Cause 1: CreateStack with a template whose Resources are an AWS::NetworkSecurityManager::Rule (RuleName=<valid name>, FirewallType=WAF, RuleType=CONFIGURATION, Configuration={"DefaultAction":{"Allow":{}}}), an AWS::NetworkSecurityManager::Template (TemplateName=<valid name>, FirewallType=WAF, AssociatedRuleList=[{"RuleArn": {"Fn::GetAtt": ["Rule","RuleArn"]}}]) and one resource that is guaranteed to fail its create (e.g. an AWS::NetworkSecurityManager::Policy whose AssociatedTemplateAndRuleList entry names BOTH TemplateArn and RuleArn, which NSM must refuse). Poll DescribeStacks(StackName=<StackId>) to a terminal status. Expect ROLLBACK_COMPLETE with the rule and template gone from ListRules/ListTemplates. Observe ROLLBACK_FAILED with a Template DELETE_FAILED event row and the rule/template still listed; calling DeleteTemplate(templateIdentifier=<template ARN>) directly against NSM answers 501 NotImplemented.
