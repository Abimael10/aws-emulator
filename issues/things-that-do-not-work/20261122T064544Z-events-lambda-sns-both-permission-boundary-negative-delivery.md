Cause 1 of 2: the EventBridge→SNS target permission boundary produces no distinguishable outcome — neither the grantless publish nor the granted one is observable, so the topic resource policy is ungraded as a control.
AWS: recorded behavior only for the rule leg (the EventBridge envelope is not modeled); Smithy (sns, com-amazonaws-sns-amazonsimplenotificationservice): Publish declares AuthorizationErrorException with httpError 403 and awsQueryError code 'AuthorizationError'. EventBridge calls SNS Publish on an SNS target as the service principal events.amazonaws.com; a topic whose resource policy carries no Allow statement for that principal refuses the call, which is invisible to the PutEvents caller and surfaces as no delivery to any subscriber plus a FailedInvocation / dead-letter on the rule. After SetTopicAttributes(AttributeName=Policy) adds Effect Allow, Principal {"Service":"events.amazonaws.com"}, Action "SNS:Publish", Resource <topic arn> (optionally Condition ArnEquals aws:SourceArn=<rule arn>), the identical rule and target must deliver the event envelope to the topic's subscribers. The three facts AWS keeps distinguishable are: (a) a direct Publish by the topic owner is delivered; (b) the rule-triggered publish with no grant is delivered to nobody; (c) after the grant, the same rule-triggered publish is delivered. Topic/queue/rule ARNs, MessageIds and markers are per-run values; the requirement is the three-way distinction.
Emulator: the check reaches none of its graded assertions and ends '[mismatch] ... Error: Check timed out after 60.0s'; (b) and (c) are indistinguishable on this build, so the boundary is ungraded. The behaviour previously recorded on this same path (open 20261029T182228Z, Cause 1) was the opposite failure — the subscriber received the notification with the full EventBridge envelope as Message although the topic policy granted events.amazonaws.com nothing, i.e. the resource policy was not consulted at all. Hypothesis, to be measured rather than assumed: with the grantless publish now correctly withheld, the check's budget is consumed by its own withheld-delivery window, and the step that must now settle fast is (c) — the granted rule-triggered publish reaching the subscriber promptly after SetTopicAttributes.
Why: a client cannot use the topic policy as a control. Either the emulator fabricates a publish AWS refuses (a least-privilege rollout that breaks fan-out in AWS passes locally), or granting the statement never visibly unblocks delivery; in both shapes a real authorization regression is invisible.
Fix: resource-policy authorization in the EventBridge SNS-target invoker and in the SNS Publish path it calls, plus the SNS-target delivery itself, so a grantless publish is refused (and counted as a failed invocation) while a granted one is delivered promptly, with the grant taking effect on the next matching event.

Cause 2 of 2: the fan-out both-targets-denied boundary is ungraded because its observation channels never converge — an asynchronous Invoke's handler output is not promptly readable in /aws/lambda/<fn>, and/or the control publish is not promptly readable on the subscribed queue.
AWS: Smithy (lambda, com-amazonaws-lambda-awsgirapiservice): Invoke POST /2015-03-31/functions/{FunctionName}/invocations with InvocationType carried in the X-Amz-Invocation-Type header; InvocationType=Event is accepted 202 with an empty payload and the function runs asynchronously. Recorded behavior: the run's log lands in /aws/lambda/<function-name> (group and per-environment stream created on first use when the execution role allows logs:CreateLogGroup/CreateLogStream/PutLogEvents — the check attaches the managed AWSLambdaBasicExecutionRole) and contributes 'START RequestId: <id> Version: <version>', every line the handler printed, 'END RequestId: <id>' and 'REPORT RequestId: <id>\tDuration: ... ms\tBilled Duration: ... ms\tMemory Size: ... MB\tMax Memory Used: ... MB'. The fixed text is the START/END/REPORT RequestId prefixes and the Duration / Billed Duration / Memory Size / Max Memory Used field names; the request id, durations and sizes are per-invocation values. FilterLogEvents on that group with a filterPattern quoting a string the handler printed therefore returns at least one event within seconds. Separately, a Publish by the topic owner to a topic with an SQS subscription is received by the queue within seconds, and a matching rule whose Lambda target has no lambda:InvokeFunction grant for events.amazonaws.com and whose SNS target has no topic-policy grant invokes/publishes nothing.
Emulator: the check reaches none of its graded assertions ('lambda was invoked despite missing resource policy', 'sns received a publish despite missing topic policy') and ends '[mismatch] ... Error: Check timed out after 60.0s'; its first blocking convergence is the asynchronous-invoke log-marker positive control, which resolved issue 20261107T143733Z recorded as returning no events for the whole window (group absent or empty). Nothing is refused; the determinable fact is that neither observation channel produces the control evidence in time, so 'EventBridge correctly refused to invoke the un-permitted targets' cannot be told apart from 'nothing is ever recorded'.
Why: asynchronous invocations are unobservable — `aws logs tail /aws/lambda/<fn>`, metric filters over handler output, log-driven alarms and every invoke-then-read-the-log diagnosis loop see nothing — and for permission-boundary scenarios the log group is the only evidence a target was NOT invoked, so negative-delivery conclusions drawn against this emulator are unsound.
Fix: the Lambda Invoke execution path's log emission on the asynchronous (Event) branch — each run's captured stdout framed by the START/END/REPORT lines written through to the CloudWatch Logs state store under /aws/lambda/<function-name>, creating group and stream on first use — together with the EventBridge Lambda- and SNS-target invokers' resource-policy checks so the denied fan-out is refused rather than silent.
