# bedrock-agent: 2 net-new causes in the delete plane — DeleteFlowVersion 404 for a version the flow should hold, and a deleted document's NOT_FOUND is never listed

> _Note: this issue was identified against the code base at commit `39ac78f4c744f316ef870f9b4f7492229bfc440d`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
DeleteFlowVersion

## Description
2 causes. Both sit on the bedrock-agent DELETE path: the teardown delete of a flow version is refused as missing, and the terminal state of an accepted document deletion is never reportable through the data source's document listing. Neither of these two fixture steps' replay keys is carried by any open issue, so neither is covered today.

Cause 1 of 2: DeleteFlowVersion on version '1' of a flow that was prepared and versioned answers 404 ResourceNotFoundException instead of 200 with {id, version} (fixture bedrock-agent-flow-alias-lifecycle, step teardown#11).
AWS: Smithy (services/service-com-amazonaws-bedrockagent-amazonbedrockagentbuildtimelambda/smithy-model/com-amazonaws-bedrockagent-amazonbedrockagentbuildtimelambda.json) models DeleteFlowVersion as DELETE /flows/{flowIdentifier}/versions/{flowVersion}/ with success status 200 and output requiring id (Id @pattern ^[0-9a-zA-Z]{10}$) and version (NumericalVersion @pattern ^[0-9]{1,5}$); its errors are ResourceNotFoundException (404), ConflictException (409), ValidationException (400), AccessDeniedException (403), ThrottlingException (429), InternalServerException (500), and input carries skipResourceInUseCheck (httpQuery, default false). Recorded behavior: in this fixture the flow was created, prepared and versioned (CreateFlowVersion answered 201 and cut version 1), and the teardown delete of that numbered version answered 200 reporting the flow's own id and the version number that was removed. The requirement: a numbered version the flow holds, with no alias routing to it, is deleted and reported back with id = the addressed flow's id and version = the version number that was removed (the recording's concrete flow id and version token are per-run values, not part of the contract).
Emulator: replay observed HTTP 404 where 200 was required, with no DeleteFlowVersionResponse body. The handler (services/.../src/ops/delete_flow_version.rs lines 203-213) resolves state.flow_version_of(flow, version) and, finding nothing, refuses with flow_version_not_found_message — whose fixed text is "Couldn't perform <operation> operation. Failed to retrieve resource type <resourceType> because it doesn't exist. Check the resource ID and retry your request.", its only variable parts being the invoked operation name (DeleteFlowVersion) and the resource type that failed to resolve (FlowVersion); no identifier appears in it. Hypothesis: the handler itself is correct for a store that holds the version — the store never holds one, because CreateFlowVersion in this same fixture refuses a just-prepared flow with 409 ConflictException (that earlier step is owned by open issue 20261108T082251Z-bedrock-agent-flow-deployment-plane-a-prepared-flow.md, which carries setup#4/task#5/task#8 but NOT this teardown step's replay key, so nothing re-runs this delete today).
Why: a client that versions a flow and later retires that version is told the version does not exist, so the whole version lifecycle has no observable end: cleanup code cannot tell "already gone" from "never created", retries loop on a resource AWS considers deletable, and an orchestrator that deletes versions before deleting the flow aborts its teardown.
Fix: the flow versioning plane that must make version 1 exist for a prepared flow (the preparation state machine and the CreateFlowVersion pre-condition in the flow slice of services/.../src/state.rs and services/.../src/ops/create_flow_version.rs), then re-verify the DeleteFlowVersion handler's not-found/in-use path in services/.../src/ops/delete_flow_version.rs so a held version is removed and answered 200 with {id, version}.
Traces: bedrock-agent-flow-alias-lifecycle#teardown#11.

Cause 2 of 2: after an accepted DeleteKnowledgeBaseDocuments, ListKnowledgeBaseDocuments never reports the document's terminal NOT_FOUND status — the document simply vanishes from the listing, which reports an empty documentDetails forever (fixture bedrock-agent-knowledge-base-documents-delete-workflow, step task#8).
AWS: Smithy models ListKnowledgeBaseDocuments as POST /knowledgebases/{knowledgeBaseId}/datasources/{dataSourceId}/documents with success 200, output requiring documentDetails (KnowledgeBaseDocumentDetails, paginated on nextToken/maxResults 1..1000), and KnowledgeBaseDocumentDetail requiring knowledgeBaseId, dataSourceId, identifier and status (DocumentStatus = INDEXED | PARTIALLY_INDEXED | PENDING | FAILED | METADATA_PARTIALLY_INDEXED | METADATA_UPDATE_FAILED | IGNORED | NOT_FOUND | STARTING | IN_PROGRESS | DELETING | DELETE_IN_PROGRESS), whose own documentation states "NOT_FOUND – The document wasn't found", "DELETING – You submitted the delete job containing the document" and "DELETE_IN_PROGRESS – The document is being deleted"; DeleteKnowledgeBaseDocuments is POST .../documents/deleteDocuments with success 202. Recorded behavior: after the delete of a CUSTOM document is accepted, the listing for that (knowledgeBaseId, dataSourceId) pair keeps carrying exactly one detail for that document — identifier {custom: {id: <the id that was deleted>}}, dataSourceType CUSTOM, the addressed knowledgeBaseId/dataSourceId, an updatedAt timestamp — and its status settles at NOT_FOUND. The requirement is that the deletion's terminal state is observable through the listing: a poller watching documentDetails[0].status reaches NOT_FOUND. The recording's concrete ids and timestamp are per-run values.
Emulator: replay observed HTTP 200 but {"documentDetails": []} — $.documentDetails[0] missing, and the poll on $.documentDetails[0].status gave up after 61 attempts / the 180s cap because the member never appears, let alone reaches NOT_FOUND. This is deliberate in the store: DocumentStatus::NotFound in services/.../src/state.rs (around lines 2327-2333) documents that "a record that reaches it is retired from the store by the same pass that applies it: the status is the answer a targeted read gives for an identifier nothing is held for, not a document the data source still enumerates", and page_of_documents (services/.../src/state.rs around lines 3391-3417) enumerates only records the data source still holds, so once the DELETING -> DELETE_IN_PROGRESS -> NOT_FOUND chain completes in materialise_due_transitions the listing is empty. The handler (services/.../src/ops/list_knowledge_base_documents.rs lines 253-265) faithfully pages whatever the store holds.
Why: the listing is how a client confirms a delete landed on the right document. A client that deletes documents and polls ListKnowledgeBaseDocuments for the modelled NOT_FOUND terminal status never observes it and spins until its own timeout; worse, an empty listing is indistinguishable from "this data source never held the document", so the client cannot confirm WHICH document was removed (the identifier is only carried by the detail entry) and cannot distinguish a completed deletion from a deletion that was never accepted.
Fix: the document slice of the bedrock-agent store — the terminal step of the deletion chain in materialise_due_transitions and the enumeration in page_of_documents (services/.../src/state.rs), so a document whose accepted deletion has run to completion keeps a reportable detail with status NOT_FOUND for the listing instead of being retired from the store; the ListKnowledgeBaseDocuments handler itself needs no change. Related open issue 20261105T115813Z-bedrock-agent-deleteknowledgebasedocuments-stub.md asks for DeleteKnowledgeBaseDocuments to be implemented (it now is, and it answers 202 and starts the deletion chain) and carries no wire replay key, so it does not cover this listing divergence.
Traces: bedrock-agent-knowledge-base-documents-delete-workflow#task#8.
