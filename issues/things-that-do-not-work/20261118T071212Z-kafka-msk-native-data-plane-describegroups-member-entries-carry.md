# MSK native data plane: DescribeGroups member entries carry an empty client_id so per-member assignments collapse, and the PLAINTEXT provisioned bring-up for the cluster-Configuration check no longer clears (2 causes)

> _Note: this issue was identified against the code base at commit `3711ad27c0bcb075eca07005071efebbd0f057fa`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
DescribeGroups

## Description
TWO net-new root causes in the emulated MSK (kafka) service, both grounded in failing behavioral checks listed under `### kafka` in the behavioral suite report. The open issue 20261116T210722Z-kafka-msk-native-data-plane-sasl-iam-bring-up.md lists both of these check ids, but it does NOT carry either replay key below: its key for the consumer-group check is `_invoke#2|Timeout|_out, err = proc.communicate(...)` (the check never got past bring-up) and its key for the configuration check is `run#12|AssertionError|assert entry.get("n_partitions") == partitions`. Both checks now fail at different points, so neither cause is covered by it.

=== Cause 1 of 2: the group coordinator's DescribeGroups response leaves the member's client_id empty, so a client cannot attribute a stored SyncGroup assignment to a member. ===
AWS: recorded behavior only (this is the Apache Kafka wire protocol an MSK broker serves, not a Smithy-modeled operation; the control-plane model offers nothing here). Against real MSK, after two consumers with distinct client_ids (one per member) join one group that proposes only RangePartitionAssignor and the coordinator reports the group Stable with 2 members and protocol "range", DescribeGroups (api key 15) returns one member entry per live member, and each entry carries that member's own `client_id` — the value the member sent in its JoinGroup/connection setup — alongside its `member_assignment`. The recording shows the coordinator's stored assignments read back as the two contiguous RangeAssignor halves of a 4-partition topic, one per DISTINCT client_id: [0,1] and [2,3]. The client_id is per-member request data; the partition split is a function of the partition count and the live member count, not of any recorded literal.
Emulator: DescribeGroups reports `members` = 2 and state Stable (those assertions pass), but every member entry's client_id is the empty string, so the two entries collapse onto one key and only one assignment remains observable: 'AssertionError: DescribeGroups reports the coordinator's own per-member assignment as {'': [2, 3]}; the SyncGroup assignment it distributed and stored must be the contiguous RangeAssignor split [0,1] and [2,3]'. The dict has a single key '' while the response declares two members, which can only happen if BOTH member entries carry an empty client_id. (The surviving value [2,3] and the member names in the recording are this run's values and are not the requirement; the requirement is that each member entry carries the client_id that member supplied.)
Why: a client or operator tool that reads group membership over the admin protocol — kafka-python's describe_groups, kafka-consumer-groups.sh, any lag/ownership dashboard — cannot tell which consumer owns which partitions. Two distinct members appear as one unnamed member, per-member assignment attribution is lost, and tooling that keys its state by client_id silently overwrites one member with the other. Rebalance and ownership diagnosis against the emulator is impossible even though the split itself may be right.
Fix: the emulated broker's group-coordinator state and its DescribeGroups response serializer in the kafka service — record the client_id each member presents at JoinGroup and emit it in each DescribeGroups member entry (together with that member's stored member_assignment), instead of an empty string.
Traces: kafka.msk-consumer-group-two-member-range-split-then-session-timeout-expiry-reassigns (assertion at the two-member describe, before the session-timeout eviction legs).

=== Cause 2 of 2: the PLAINTEXT provisioned-cluster bring-up for the cluster-Configuration check never clears, so the check reaches no verdict. ===
AWS: CreateConfiguration stores ServerProperties (the check's independent DescribeConfigurationRevision read of num.partitions=N is part of the same sequence); CreateCluster (Smithy: POST /v1/clusters, required members brokerNodeGroupInfo, clusterName, kafkaVersion, numberOfBrokerNodes @range 1..15, optional configurationInfo; output member state -> ClusterState) answers CREATING and the cluster settles to ACTIVE; GetBootstrapBrokers (Smithy: GET /v1/clusters/{ClusterArn}/bootstrap-brokers, output member BootstrapBrokerString, jsonName bootstrapBrokerString) then publishes host:port brokers that accept a TCP connection inside the cluster's VPC and answer a hand-framed ApiVersions request with error_code 0 advertising api keys 0 (Produce), 3 (Metadata), 19 (CreateTopics) and 32 (DescribeConfigs). Recorded behavior: the whole bring-up completes and the check goes on to assert that a CreateTopics with num_partitions=-1/replication_factor=-1 resolves to the attached Configuration's num.partitions and default.replication.factor.
Emulator: the check is killed by the harness — 'Error: Check timed out after 60.0s' — and no response is asserted on at all. It previously failed at the n_partitions assertion (see the open issue named above), so the bring-up barrier it used to clear no longer does. The sequence being held is CreateConfiguration -> DescribeConfigurationRevision -> CreateCluster(provisioned, 2 brokers, ConfigurationInfo) -> poll DescribeClusterV2 until State in (ACTIVE, FAILED) -> GetBootstrapBrokers -> TCP accept on the advertised PLAINTEXT endpoint -> a Kafka Metadata/DescribeCluster the broker must answer -> ApiVersions. Hypothesis: either the provisioned-cluster lifecycle does not reach ACTIVE promptly, or nothing accepts and answers the Kafka protocol on the PLAINTEXT host:port the emulator advertises in bootstrapBrokerString; the recording and the model do not state which, and no stage output survived the kill.
Why: a client that creates a provisioned MSK cluster with a ConfigurationInfo and then connects a PLAINTEXT Kafka client to bootstrapBrokerString hangs instead of being served or refused. Every downstream guarantee of that path — the Configuration's num.partitions/default.replication.factor defaults, auto.create.topics.enable=false enforcement, and the brokers' own describe_configs view — is unobservable, and a test suite built on MSK blocks rather than getting records or an error.
Fix: the kafka service's cluster-lifecycle state (the CreateCluster/DescribeClusterV2 state machine must reach ACTIVE promptly) and the emulated native broker listener that bootstrapBrokerString advertises — it must accept on the host:port it publishes and serve the Kafka protocol (at minimum ApiVersions, Metadata, CreateTopics, DescribeConfigs, Produce) over PLAINTEXT.
Traces: kafka.msk-cluster-configuration-num-partitions-default-is-applied-by-the-broker.

## Evidence
Cause 1 — kafka.msk-consumer-group-two-member-range-split-then-session-timeout-expiry-reassigns:
  Expected: DescribeGroups on a Stable 4-partition/2-member group returns two member entries, each carrying the client_id that member supplied and that member's stored SyncGroup assignment, so the per-member view is {<member-A client_id>: [0,1], <member-B client_id>: [2,3]} (the contiguous RangeAssignor split).
  Actual: AssertionError: DescribeGroups reports the coordinator's own per-member assignment as {'': [2, 3]}; the SyncGroup assignment it distributed and stored must be the contiguous RangeAssignor split [0,1] and [2,3]
  Note: the same response reported members = 2, state 'Stable' and protocol 'range' (those assertions passed), so both member entries carried an empty client_id and collapsed onto one key.

Cause 2 — kafka.msk-cluster-configuration-num-partitions-default-is-applied-by-the-broker:
  Expected: CreateConfiguration -> CreateCluster(provisioned, ConfigurationInfo) -> DescribeClusterV2 ACTIVE -> GetBootstrapBrokers -> the advertised PLAINTEXT endpoint accepts TCP and answers ApiVersions with error_code 0 and api keys {0,3,19,32}; the check then grades the -1 CreateTopics.
  Actual: Error: Check timed out after 60.0s — the check is killed inside bring-up; zero responses asserted on. (Previously this check reached the n_partitions assertion, so this is a new failure point for the same check.)

Observe that every member entry's client_id is the empty string, so the two members are indistinguishable and only one assignment is recoverable.
