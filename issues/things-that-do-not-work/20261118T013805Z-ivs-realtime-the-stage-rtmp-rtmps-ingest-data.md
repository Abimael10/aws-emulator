# ivs-realtime: the stage RTMP/RTMPS ingest data plane is never served, so a live publish never makes an IngestConfiguration ACTIVE and no StageSession/Participant is ever created

> _Note: this issue was identified against the code base at commit `775d8b7a5dc0233a720d935fa0de7ffef061d5f2`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
GetIngestConfiguration

## Description
Cause 1 of 1: a real RTMP/RTMPS publisher dialing the endpoint a stage announces is never ingested, so every state an IVS real-time publish is supposed to produce stays absent forever.

Failing checks for this cause: ivs-realtime.delete-active-ingest-configuration-without-force-rejected, ivs-realtime.list-ingest-configurations-filter-by-state, ivs-realtime.rtmp-publish-full-participant-lifecycle, ivs-realtime.rtmp-publish-lifecycle-and-disconnect, ivs-realtime.stage-active-session-absent-until-participant.

AWS: the IVS real-time data plane is what drives these reads. Smithy (services/service-com-amazonaws-ivsrealtime-amazoninteractivevideoservicerealtime/smithy-model/com-amazonaws-ivsrealtime-amazoninteractivevideoservicerealtime.json): IngestConfiguration$state targets IngestConfigurationState with values [ACTIVE, INACTIVE] and is documented "State of the ingest configuration. It is ACTIVE if a publisher currently is publishing to the stage associated with the ingest configuration." Stage$activeSessionId (StageSessionId, @length 16..16, pattern ^st-[a-zA-Z0-9]+$) is "ID of the active session within the stage"; Participant$state is "Whether the participant is connected to or disconnected from the stage", Participant$published is "Whether the participant ever published to the stage session", and Participant$protocol is "Type of ingest protocol that the participant employs for broadcasting" (RTMP|RTMPS). StageEndpoints$rtmp/$rtmps are the addresses an encoder dials to contribute. So on AWS: an encoder that completes an RTMP(S) handshake against the stage's advertised ingest endpoint with an ingest configuration's streamKey causes (a) GetIngestConfiguration/ListIngestConfigurations to report that configuration state=ACTIVE (and ListIngestConfigurations(filterByState=ACTIVE) to list it, while filterByState=INACTIVE does not), (b) GetStage to report a non-empty activeSessionId and ListStageSessions to list that sessionId, (c) GetParticipant for that participantId to report state=CONNECTED, published=true, protocol=RTMP/RTMPS, and ListParticipantEvents to carry JOINED (and LEFT once it goes away), and (d) DeleteIngestConfiguration without force=true to be refused 409 ConflictException while that publisher is live. Those last two refusal messages are templates: the conflict message's fixed text is "Unable to mutate resource " + the request's ingest-configuration ARN + " while participant is actively publishing", and the post-delete not-found message's fixed text is "Resource: " + that ARN + " not found" (the ARN is the only variable part in each; the ARNs in the replay output are one run's values, not part of the template).

Emulator: nothing ever becomes ACTIVE. Every one of the five checks starts a real ffmpeg publish (ffmpeg was present — the suite reports 0 skipped, so require_tools("ffmpeg") passed) against both candidate URLs built from the endpoint the emulator itself announced (stage.endpoints.rtmp / rtmps), and then polls GetIngestConfiguration. The poll always returns HTTP 200 with state="INACTIVE" until it times out, e.g. {'name': 'sim2real-ingest-...', 'ingestProtocol': 'RTMP', 'stageArn': 'arn:aws:ivs:...:stage/...', 'participantId': '000003e01229', 'state': 'INACTIVE', ...} — note the configuration already carries a minted participantId while reporting INACTIVE. ivs-realtime.rtmp-publish-full-participant-lifecycle simply runs out its 60 s budget on the same poll. Because the first leg never completes, every downstream fact is unreachable too: GetStage keeps reporting the empty activeSessionId, ListStageSessions stays [], GetParticipant has no participant to report, ListParticipantEvents has no JOINED/LEFT, and the ConflictException leg of DeleteIngestConfiguration is never exercised. The code says this outright: src/state.rs (the "Stage sessions and the participants in them" section) states "A participant reaches a stage through the stage's DATA plane ... No operation of this control plane makes a participant join", and src/state/stage_endpoints.rs composes rtmp://<host:port>/app/ and rtmps://<host:port>/app/ from the emulator's own HTTP authority (announced_authority) while the crate mounts no RTMP listener at all (src/lib.rs declares only ops, scaffolded, service, state). So the advertised ingest address answers HTTP, not RTMP, and the publish handshake can never succeed; GetIngestConfiguration itself is faithful — it computes state from ingest_configuration_publishers, which no publisher ever enters.

Why: a client that uses IVS real-time the way AWS documents it — create a stage, create an ingest configuration, point an encoder at the advertised RTMP(S) endpoint, then watch state/activeSessionId/participant to know the broadcast is live — sees a broadcast that never starts. Readiness waits never finish, contribution monitoring reports a permanently idle stage, and the safety rail that stops a live ingest configuration from being deleted without force can never fire, so destructive code paths look safe against this emulator and are not safe against AWS.

Fix: the stage data plane is missing end-to-end and belongs with the service's data plane and the session/participant state it writes: (1) serve the RTMP and RTMPS contribution endpoints the service advertises (an RTMP listener reachable at the authority and /app/ path stage_endpoints.rs announces, authenticating the publish by the stream key the ingest configuration minted); (2) on an accepted publish, write the records the reads already derive from — start a stage session on the configuration's stage (filling Stage.active_session_id with an ^st-[a-zA-Z0-9]+$ 16-char id), add the configuration's participant to it as CONNECTED/published with protocol RTMP or RTMPS and a JOINED event, and unwind it (DISCONNECTED, LEFT, session endTime, configuration back to INACTIVE) when the publisher stops or DisconnectParticipant/forced delete removes it; (3) with a live publisher present, DeleteIngestConfiguration without force must take the modeled ConflictException (409) path with the message template above. Related but not covering this: the resolved issue 20261028T212209Z-ivs-realtime-getingestconfiguration-wrong-behavior.md tightened ACTIVE so it requires a publishing participant — the remaining gap is that no publishing participant can ever exist, because the publish is never ingested.

Traces: the five failing checks listed above; the delete-without-force conflict and post-force-delete not-found legs are blocked behind the same first assertion.

## Evidence
Expected (AWS): after ffmpeg completes an RTMP(S) handshake to stage.endpoints.rtmp/rtmps with the ingest configuration's streamKey — GetIngestConfiguration -> ingestConfiguration.state == "ACTIVE"; ListIngestConfigurations(filterByState="ACTIVE") contains that arn and filterByState="INACTIVE" does not; GetStage -> non-empty activeSessionId matching ^st-[a-zA-Z0-9]+$ and ListStageSessions lists it; GetParticipant -> state == "CONNECTED", published == true, protocol in {RTMP, RTMPS}; ListParticipantEvents -> JOINED (then LEFT); DeleteIngestConfiguration without force -> HTTP 409 ConflictException, message "Unable to mutate resource <ingest-configuration ARN from the request> while participant is actively publishing", and the configuration still ACTIVE afterwards; after force=true delete, GetIngestConfiguration -> HTTP 404 ResourceNotFoundException, message "Resource: <that ARN> not found".

Actual (emulator): the publish is never ingested. GetIngestConfiguration answers HTTP 200 with state="INACTIVE" for the whole poll window, e.g.
  AssertionError: {'name': 'sim2real-ingest-23188734302d', 'arn': 'arn:aws:ivs:us-west-2:000000000000:ingest-configuration/000002e01208', 'ingestProtocol': 'RTMP', 'streamKey': 'rt_000000000000_us-west-2_000003e01229_...', 'stageArn': 'arn:aws:ivs:us-west-2:000000000000:stage/000001dfaed8', 'participantId': '000003e01229', 'state': 'INACTIVE', 'userId': '', 'redundantIngest': False, 'tags': {'team': 'sim2real'}}
  AssertionError: timed out waiting for predicate; last observed {... 'state': 'INACTIVE' ...}  (list-ingest-configurations-filter-by-state)
  AssertionError: condition not met within 20.0s; last value={... 'state': 'INACTIVE' ...}  (stage-active-session-absent-until-participant)
  Check timed out after 60.0s  (rtmp-publish-full-participant-lifecycle, polling the same ACTIVE predicate)
All downstream assertions (activeSessionId, ListStageSessions, GetParticipant CONNECTED/published, JOINED/LEFT events, ConflictException on delete-without-force) are therefore never reached.

Code evidence in the checkout: services/service-com-amazonaws-ivsrealtime-amazoninteractivevideoservicerealtime/src/state/stage_endpoints.rs:49-58 composes rtmp://<announced_authority>/app/ and rtmps://<announced_authority>/app/ from the emulator's HTTP authority; src/lib.rs:10-13 mounts only ops/scaffolded/service/state (no RTMP listener); src/state.rs ("Stage sessions and the participants in them") records "No operation of this control plane makes a participant join"; src/ops/get_ingest_configuration.rs:144-168 reports the stored/derived state faithfully, so the gap is upstream of the handler.

## Steps to Reproduce
1. CreateStage(name=<unique>) and read stage.endpoints.rtmp / endpoints.rtmps (or GetStage).
2. CreateIngestConfiguration(name=<unique>, stageArn=<stage arn>, ingestProtocol="RTMP", insecureIngest=true) and keep arn + streamKey. GetIngestConfiguration reports state=INACTIVE (correct at this point).
3. Publish a live stream to the advertised endpoint with the stream key, e.g.
   ffmpeg -re -f lavfi -i testsrc=size=640x360:rate=30 -f lavfi -i sine=frequency=1000 -pix_fmt yuv420p -c:v libx264 -b:v 800k -c:a aac -t 60 -f flv "<endpoints.rtmp>/app/<streamKey>"  (also try "<endpoints.rtmp>/<streamKey>").
4. Poll GetIngestConfiguration(arn=<ingest arn>) for up to 60 s: it stays state="INACTIVE" (AWS reports ACTIVE within seconds). ListIngestConfigurations(filterByState="ACTIVE") never lists it.
5. Poll GetStage(arn=<stage arn>): activeSessionId stays empty and ListStageSessions(stageArn=...) stays []. No GetParticipant/ListParticipantEvents record exists for the configuration's participantId.
6. Call DeleteIngestConfiguration(arn=<ingest arn>) with no force while the publisher is still running: it is accepted instead of being refused with 409 ConflictException "Unable to mutate resource <arn> while participant is actively publishing".
