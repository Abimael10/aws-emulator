=== Cause 1 of 3: ModifyDBSnapshot is an unimplemented scaffold, so an invalid engine-version target is answered HTTP 501 NotImplemented instead of the modelled refusal ===
AWS: Smithy ModifyDBSnapshot(DBSnapshotIdentifier required, EngineVersion, OptionGroupName) -> DBSnapshot; modelled errors DBSnapshotNotFoundFault (404), InvalidDBSnapshotStateFault (400), KMSKeyNotAccessibleFault (400); the operation doc states it "Updates a manual DB snapshot with a new engine version". Only an UPGRADE target is supported, so asking to move a snapshot to an OLDER engine version is refused with the query-protocol common error code InvalidParameterCombination at HTTP 400 and the message "You can't upgrade the DB snapshot from the engine version <current> to <target>." — fixed text "You can't upgrade the DB snapshot from the engine version ", then the snapshot's CURRENT EngineVersion as read from state, " to ", the request's EngineVersion value, and a terminating ".". Neither version number is part of the template: both come from state and from the request. A refused ModifyDBSnapshot must leave the snapshot's EngineVersion and its Status ('available') untouched.
Emulator: the handler returns the scaffold's 501 NotImplemented for every call, so the error code observed is 'NotImplemented' where InvalidParameterCombination is required, and no snapshot engine-version upgrade or downgrade refusal can be exercised at all.
Why: a client that downgrades-by-mistake gets a 501 it must treat as an emulator/service outage rather than the 400 InvalidParameterCombination it is written to catch; retry and error-classification logic takes the wrong branch, and no client can upgrade a snapshot's engine version either.
Fix: the ModifyDBSnapshot handler (services/service-com-amazonaws-rds-amazonrdsv19/src/ops/modify_db_snapshot.rs — the handle body still returns crate::scaffolded::Scaffolded::not_implemented("ModifyDBSnapshot") and the file still carries the SCAFFOLDED marker), plus its validation of EngineVersion against the snapshot's recorded engine version, and the DB-snapshot state it must leave unchanged on refusal.
Traces: rds.snapshot-attribute-share-restore-then-invalid-engine-upgrade-rejected ("AssertionError: unexpected error code: 'NotImplemented'" at the assert code == "InvalidParameterCombination"). The same check's earlier assertions on DescribeDBSnapshotAttributes / ModifyDBSnapshotAttribute 'restore' round-tripping passed, so only the ModifyDBSnapshot step diverges.

=== Cause 2 of 3: a postgres DB instance created with an explicit Port publishes the OS-assigned listener port as Endpoint.Port ===
AWS: Smithy Endpoint$Port is "Specifies the port that the database engine is listening on" and Endpoint$Address "the DNS address of the DB instance". CreateDBInstance$Port is echoed verbatim when supplied (any value in the documented 1150-65535 range), and defaults to the engine family's port otherwise (postgres 5432). The published port is therefore ALSO the port the engine accepts sessions on — the same number must be both reported and listening.
Emulator: the requested Port is discarded and the ephemeral port the host OS assigned that resource's listener is published instead, e.g. a postgres instance created with Port=5439 reports a high ephemeral port. That number is per-run, so it is neither predictable nor configurable by a client. (The requested-port value and the ephemeral number differ in every environment and are not part of the requirement; the requirement is that Endpoint.Port equals the requested port, and that the engine listens there.)
Why: a client that hardens a database onto a non-default port connects to the wrong port, and anything asserting "this instance serves the port I asked for" is wrong on every resource.
Fix: the CreateDBInstance handler and the DB-instance state field that records the port, plus the DBInstance envelope serializer that reads it — record and publish the requested (or engine-default) port, and bind/announce the data-plane listener for that port rather than publishing the listener's OS-assigned port.
Traces: rds.postgres-custom-port-is-the-published-and-listening-port ("AssertionError: Endpoint.Port must be the requested 5439; got <OS-assigned ephemeral port>").

=== Cause 3 of 3: the native postgres COPY ... FROM STDIN bulk-load path never settles, so the whole bulk-load behaviour is unobservable ===
AWS: recorded behavior only (this is engine-level PostgreSQL behaviour an RDS postgres instance serves, not Smithy-modelled). A COPY <table> FROM STDIN WITH (FORMAT text) of 50,000 rows loads exactly those rows byte-exact (verified by an engine-side md5 over the stored values), NUMERIC(12,4) round-trips as an exact decimal, the text-format \N sentinel is stored as SQL NULL, pg_relation_size is non-zero, and a COPY ... TO STDOUT WITH (FORMAT binary) emits the PGCOPY signature and re-imports losslessly. One malformed datum ('not-a-number' in a NUMERIC column) anywhere in the stream aborts the ENTIRE statement: SQLSTATE 22P02 (invalid_text_representation) with ErrorResponse context "COPY <table>, line <N>, column <column>: \"<datum>\"" — fixed text "COPY ", the table name, ", line ", the 1-based line of the offending row in the stream, ", column ", the column name, ": " and the quoted offending datum, all taken from the request's stream — and the table is left with ZERO rows (no valid prefix committed). The identical payload with that row repaired then loads all rows.
Emulator: the check never reaches a verdict — it is cut off by its replay window ("Check timed out after 60.0s") while exercising this path, so none of the above is answered. The emulator either does not complete the COPY FROM STDIN / COPY TO STDOUT stream or completes it so slowly that the bulk-load path is effectively hung; no COPY result, no 22P02 refusal and no zero-row assertion can be observed.
Why: bulk load is the standard way data is put into a postgres database. A client's loader either hangs (no response on the copy-in stream) or, if it eventually returns, has had no refusal path verified — the partial-load failure mode (committing the valid prefix of a rejected COPY) is exactly the silent-corruption bug this check exists to rule out.
Fix: the postgres data-plane engine's COPY protocol support — the CopyInResponse/CopyData/CopyDone and CopyOutResponse handling on the served session, its per-datum parse of the text and binary formats, and the statement-scoped abort that must roll the whole copy back and raise 22P02 with the line/column context.
Traces: rds.copy-from-stdin-bulk-load-rejects-a-malformed-row ("Error: Check timed out after 60.0s").
