# A launching lifecycle hook created with PutLifecycleHook after the group never catches the group's in-flight launches: no instance ever reaches Pending:Wait, so HeartbeatTimeout/DefaultResult=ABANDON and RecordLifecycleActionHeartbeat are unreachable

> _Note: this issue was identified against the code base at commit `5b0e08c6133f12b05f514bb54271d0b79fd97b96`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
PutLifecycleHook

## Description
One net-new root cause, grounded in the single failing autoscaling behavioral check of this run that the replay report marks neither ALREADY FILED nor OWNED (every other autoscaling-service failure in the report is marked and was skipped; the one remaining autoscaling entry, autoscaling.suspended-launch-process-blocks-launch, is a bare 'Check timed out after 60.0s' on a check whose own body contains a fixed 60 s suppression window, so it cannot fit the per-check budget however the emulator behaves and no divergence was observed — it is reported, not filed).

Cause 1 of 1: an instance an Auto Scaling group launches is admitted to service essentially instantaneously, and a group's LAUNCHING lifecycle hooks are consulted only against instances the group still reports 'Pending' at the instant the hook is stored — so a hook created by a PutLifecycleHook that follows CreateAutoScalingGroup (or any capacity change) holds nothing, the group's launches never park at 'Pending:Wait', and every behavior that only a held launch can show (the wait state itself, HeartbeatTimeout expiry to DefaultResult=ABANDON, and RecordLifecycleActionHeartbeat restarting that window) is unobservable. Failing check id: autoscaling.lifecycle-hook-heartbeat-extends-timeout.

AWS: the Smithy model (services/service-com-amazonaws-autoscaling-autoscaling-2011-01-01/smithy-model/com-amazonaws-autoscaling-autoscaling-2011-01-01.json) declares the whole contract this check walks. PutLifecycleHook$LifecycleTransition: 'To create a lifecycle hook for scale-out events, specify autoscaling:EC2_INSTANCE_LAUNCHING'; PutLifecycleHook$HeartbeatTimeout: 'The maximum time, in seconds, that can elapse before the lifecycle hook times out. The range is from 30 to 7200 seconds. The default value is 3600 seconds'; PutLifecycleHook$DefaultResult: 'The action the Auto Scaling group takes when the lifecycle hook timeout elapses or if an unexpected failure occurs. The default value is ABANDON. Valid values: CONTINUE | ABANDON'; the operation's own documentation states the hold and its extension verbatim — 'Create a launch template or launch configuration with a user data script that runs while an instance is in a wait state due to a lifecycle hook. … If you need more time, record the lifecycle action heartbeat to keep the instance in a wait state using the RecordLifecycleActionHeartbeat API call. If you finish before the timeout period ends, send a callback by using the CompleteLifecycleAction API call.' RecordLifecycleActionHeartbeat takes LifecycleHookName and AutoScalingGroupName (both required) addressed by LifecycleActionToken (@length 36..36) or InstanceId, and models no client error at all (only ResourceContentionFault, HTTP 500). LifecycleState enumerates the states involved: Pending, 'Pending:Wait', 'Pending:Proceed', InService, Terminating, 'Terminating:Wait', 'Terminating:Proceed', Terminated. The model states no timing, so the timing itself is recorded behavior only: on AWS an EC2 instance a group launches spends tens of seconds reported 'Pending' (real provisioning work), so a launching hook stored seconds after the capacity change is still in front of those launches and parks each of them at 'Pending:Wait'; the hook's HeartbeatTimeout then elapses from the start of the hold or from the last heartbeat, and the un-heartbeated instance resolves to the hook's DefaultResult (ABANDON -> the instance leaves through 'Terminating'/'Terminating:Wait' and the capacity is relaunched) while a heartbeated one stays at 'Pending:Wait' past the ORIGINAL deadline. No refusal is involved anywhere in this cause: there is no status code or error code to compare, the divergence is entirely in the LifecycleState the group reports.

Emulator: the group's launches are admitted to service after a 2-millisecond span — services/service-com-amazonaws-autoscaling-autoscaling-2011-01-01/src/state.rs declares `pub const LAUNCH_TRANSITION: Duration = Duration::from_millis(2)` ('How long an instance a group LAUNCHED spends Pending before it is in service … Chosen, not documented, and never slept for'), stamped as the launched instance's `transition_due` and materialised by AutoScalingState::materialize_due, which every handler calls at its top. src/ops/put_lifecycle_hook.rs calls `state.materialize_due(&*self.engine, now)` with `now = SystemTime::now()` before it stores the hook, and then calls state.hold_launches_in_flight(...), which (src/state/lifecycle_actions.rs) collects only instances whose `lifecycle_state == LIFECYCLE_PENDING` and returns false when that set is empty. A client's next HTTP request cannot reliably arrive within 2 ms of the previous one, so by the time PutLifecycleHook runs the launches have already been materialised to InService and the hold set is empty: no 'Pending:Wait' instance is ever created, no lifecycle-action event is queued, and no action token exists. The check observes exactly that — 'AssertionError: timed out waiting for two instances to reach \'Pending:Wait\' (last seen matching: [])' after polling DescribeAutoScalingGroups every 5 s — so the heartbeat leg it exists to prove is never reached, and whether this emulator enforces HeartbeatTimeout/DefaultResult=ABANDON at all, and whether RecordLifecycleActionHeartbeat extends the window, remain unverified in every environment.

Why: a client relying on AWS's behavior writes the documented lifecycle-hook sequence in exactly this order — create the group (or scale it out), then add the launching hook, then do the custom work while the instance sits in the wait state. Against this emulator that client's hook silently applies to nothing: instances it expected to find at 'Pending:Wait' are already InService, DescribeAutoScalingGroups never reports a wait state, the 'EC2 Instance-launch Lifecycle Action' event carrying the LifecycleActionToken is never published, so CompleteLifecycleAction has no token to be given and RecordLifecycleActionHeartbeat has no action to extend. Bootstrap/userdata work that AWS guarantees runs before an instance takes traffic is skipped, and a deploy script that blocks waiting for its hook to fire hangs until its own deadline. The same 2 ms window makes the catch a race no client can win, so the behavior is not merely slow — it is unreachable.

Fix: the launch-admission path of this crate — LAUNCH_TRANSITION and the due-instant/materialize_due machinery in services/service-com-amazonaws-autoscaling-autoscaling-2011-01-01/src/state.rs, together with AutoScalingState::hold_launches_in_flight / hold_lifecycle_transition in src/state/lifecycle_actions.rs and the call site in src/ops/put_lifecycle_hook.rs. Admission of a launched instance to InService must be gated on the LAUNCHING hooks the group holds AT THE MOMENT that admission is materialised (and on the hooks stored since the launch), rather than only on hooks that happen to be stored inside a 2 ms window: materialize_due must not promote a Pending instance of a group that now holds a launching hook, and must instead take it into the wait state, queue its lifecycle-action event and mint its token. Having made the hold reachable, the fixer must also confirm the tail of this scenario, which no replay has ever reached: the held instance reports 'Pending:Wait'; the un-heartbeated sibling resolves to the hook's DefaultResult ABANDON at about HeartbeatTimeout after the hold began and leaves the group; RecordLifecycleActionHeartbeat on the other instance restarts that window so it is still 'Pending:Wait' past the original deadline; and CompleteLifecycleAction with LifecycleActionResult=CONTINUE then admits that SAME instance id to InService.

Traces: autoscaling.lifecycle-hook-heartbeat-extends-timeout.

Related but non-covering open issue: 20261120T045442Z-autoscaling-lifecycle-hook-scenarios-never-converge-inside-a.md carries the two other lifecycle-hook check ids and the opposite mechanism (a decided transition WITHHELD from the next read for a wall-clock span); this cause is a hold that is never TAKEN because the launch span is shorter than one request round trip, and that issue does not carry this check id (the replay report does not mark this check owned).

1. ssm:GetParameter(Name='/aws/service/ami-amazon-linux-latest/al2023-ami-kernel-default-x86_64'); ec2:CreateLaunchTemplate(LaunchTemplateName=lt, LaunchTemplateData={ImageId: <that AMI>, InstanceType: t3.micro}).

3. As the very next call, autoscaling:PutLifecycleHook(AutoScalingGroupName=G, LifecycleHookName=h, LifecycleTransition='autoscaling:EC2_INSTANCE_LAUNCHING', HeartbeatTimeout=30, DefaultResult='ABANDON').
4. autoscaling:DescribeAutoScalingGroups(AutoScalingGroupNames=[G]).
   Observed: both instances report LifecycleState 'InService'; no instance is at 'Pending:Wait', no 'EC2 Instance-launch Lifecycle Action' event is published and no LifecycleActionToken exists.
   Expected: both instances report 'Pending:Wait' and stay there, exactly as they would had the hook been supplied in CreateAutoScalingGroup's LifecycleHookSpecificationList.
5. Show the window directly: repeat steps 2-3 but sleep 1 s between them. The behavior is identical (no hold), which is the point — the catch window is LAUNCH_TRANSITION = 2 ms, shorter than any client's request round trip, so the hold is unreachable rather than merely racy.
