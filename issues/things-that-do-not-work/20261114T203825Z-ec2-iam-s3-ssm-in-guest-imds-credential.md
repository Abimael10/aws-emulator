# ec2__iam__s3__ssm: in-guest IMDS credential probes produce no verdict — Run Command performs the commands list line-by-line so here-documents never form, the guest has no curl/python3/aws and no IMDS, and failures carry no stderr

> _Note: this issue was identified against the code base at commit `1428e63d4058e13a4521886f9248923e22581e2a`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
SendCommand

## Description
3 net-new root causes in SSM Run Command's guest-execution seam, grounded in both failing checks under the `ec2__iam__s3__ssm` heading that are neither ALREADY FILED nor OWNED. Both scenarios grade a property that exists only inside the instance — what IMDSv2 serves a guest, and what a request signed with those credentials may do — by shipping a shell script to the managed node with `AWS-RunShellScript`, so nothing they grade is observable unless that script runs.

Nearest open issues, none of which carries either check's replay key: 20261114T143448Z-ec2-iam-s3-ssm-imds-role-credential-probes-never-complete-the-ssm.md names these two check ids but its cause (and its replay keys) is that the invocation NEVER reaches a terminal status — that is no longer what happens: SendCommand is accepted and GetCommandInvocation now settles ('Failed' for one, 'Success'-with-no-output for the other), so the residue below is different; 20261114T172248Z-ec2-s3-sqs-ssm-aws-runshellscript-invocations-that.md and 20261114T161545Z-ec2-route53-route53resolver-ssm-an-aws-runshellscript-script.md cover the same seam from other services' checks but neither names the line-by-line script assembly; 20261107T081213Z-ec2-iam-s3-ssm-an-instance-launched-with.md says the instance never becomes an Online managed node, which it now does. A fix to any of those closes none of the causes below.

Cause 1 of 3: the document's `commands` input is performed one list element per shell command instead of as ONE script, so a here-document never forms, a redirection in a line that did not run leaves no file, and the run's status is whatever the LAST element happened to answer.
  AWS: the SSM agent writes the resolved `commands` of an `aws:runShellScript` step into a single script file and runs it with the guest's shell. The list is therefore one script: a line may open a here-document (`python3 - > /tmp/exports.sh <<'PYEXP'`), the following lines are its body, a line equal to the terminator closes it, and the redirection creates the file; variables and files persist to later lines, so `. /tmp/exports.sh` then sources what the interpreter wrote. GetCommandInvocation reports Status=`Success`, ResponseCode=0 and the script's stdout. Smithy: GetCommandInvocation output members `Status` (CommandInvocationStatus), `StatusDetails` (@length 0..100), `ResponseCode` (integer, default 0), `StandardOutputContent` (@length 0..24000), `StandardErrorContent` (@length 0..8000); a script's success is the GUEST's outcome, not an API refusal, so no modelled error is involved and the per-shell wording of a shell diagnostic is recorded behavior only.
  Emulator: services/service-com-amazonaws-ssm-amazonssm/src/state/guest_execution.rs hands the step's `commands` vector to `perform_in_guest`, and `ComAmazonawsEc2Amazonec2State::run_in_instance_guest` (services/service-com-amazonaws-ec2-amazonec2/src/state/guest_commands.rs) loops `for command in commands { status = session.run(command) }`, one shell command per element. The heredoc opener runs alone and produces no `/tmp/exports.sh`, its Python body lines run as shell commands, the bare terminator word runs as a command the session has no program for, and the run's status is the last element's: a script whose last line is `rm -f /tmp/doc.json` is reported `Success` although everything before it failed, while one whose last line is the bare terminator `PYSUM` is reported `Failed`. Both failing checks show exactly this split. (Hypothesis: the loop is additionally bounded by `MAX_GUEST_RUN_COMMANDS` = 64 in that file, so probe scripts longer than 64 lines are abandoned part-way.)
  Why: a client that drives an in-VPC node by shipping it a program gets no program output and no side effects, and — worse — can be told `Success` for a script that did nothing, because the status reported is an unrelated trailing line's. The security properties under test (IMDS credentials being scoped to the role's policy; an explicit bucket-policy Deny refusing the permitted write; credentials disappearing after DisassociateIamInstanceProfile) can never be observed.
  Fix: the script-assembly step of SSM's guest execution and the session seam it runs in — services/service-com-amazonaws-ssm-amazonssm/src/state/guest_execution.rs (`perform_in_guest`) and services/service-com-amazonaws-ec2-amazonec2/src/state/guest_commands.rs (`run_in_instance_guest`): perform the resolved `commands` as ONE script in ONE shell (here-document redirection, multi-line constructs, persisted variables and files) and report that script's exit status.
  Traces: ec2__iam__s3__ssm.xsvc-ec2-3-imds-credentials-put-object-outside-role-policy-denied — AssertionError: "the probe printed no JSON; stdout='.: /tmp/exports.sh: No such file or directory\n'" with Status='Success'; ec2__iam__s3__ssm.xsvc-ec2-3-imds-credentials-withdrawn-after-disassociate-iam-instance-profile — AssertionError: "the probe must run to completion; SSM reports 'Failed' stderr=''", whose script's last element is the bare terminator `PYSUM`.

Cause 2 of 3: the guest session provides no HTTP client, no interpreter and no AWS CLI, and reaches no network, so an in-guest IMDSv2 read and an in-guest AWS CLI call can never run.
  AWS: on the AMI these checks launch (the image named by the public parameter /aws/service/ami-amazon-linux-latest/al2023-ami-kernel-default-x86_64) the guest ships `curl`, `python3` and the `aws` CLI, and the link-local Instance Metadata Service answers inside the instance: `PUT http://169.254.169.254/latest/api/token` returns a token; `GET /latest/meta-data/iam/security-credentials/` answers 200 with the instance profile's role name while a profile is associated, and 404 once it is disassociated; `GET /latest/meta-data/iam/security-credentials/<role>` returns `{"Code":"Success","AccessKeyId":"ASIA…","SecretAccessKey":…,"Token":…}`; `GET /latest/meta-data/iam/info` returns the `InstanceProfileArn` (404 after disassociation). A call signed with those credentials is identified by sts:GetCallerIdentity as `arn:aws:sts::<account>:assumed-role/<role>/<instance-id>`, and a PutObject the role does not allow is refused `AccessDenied` with the message `User: arn:aws:sts::<account>:assumed-role/<role>/<instance-id> is not authorized to perform: s3:PutObject on resource: "arn:aws:s3:::<bucket>/<key>" because no identity-based policy allows the s3:PutObject action` — fixed text whose variable parts are the session ARN, bucket and key from the request and state; with an explicit bucket-policy Deny the same code carries AWS's resource-policy wording instead.
  Emulator: services/service-com-amazonaws-ec2-amazonec2/src/state/guest_commands.rs states of the session that "there is no process, no socket and no host path in it" and that "every command the session provides no program for … runs nothing and answers the status a shell answers for a utility it could not find". So `curl`, `python3` and `aws` are not provided and 169.254.169.254 is unreachable from the guest: no token, no role listing, no credential document, no CLI call, and therefore no HTTP status, no caller ARN and no AccessDenied message to grade.
  Why: the entire instance-credentials contract — that a guest receives the role's credentials from IMDS, that they carry exactly the role's authority, and that they are withdrawn when the profile is disassociated — is unobservable from inside an instance, which is the only place it exists; and any client workload relying on the EC2 instance-profile credential chain (every AWS SDK default chain on EC2) cannot run.
  Fix: the guest program environment and link-local metadata service of the in-process session — services/service-com-amazonaws-ec2-amazonec2/src/state/guest_commands.rs together with the session's program set in service_common's posix_shell_session: an HTTP client able to reach the instance's own IMDS (whose role listing and iam/info must follow the instance-profile association), a `python3` able to run a shipped script, and an `aws` CLI that signs with what IMDS served against the emulator's endpoints.
  Traces: both check ids in trace_ids; their probes begin with `curl -sS -X PUT "$IMDS/latest/api/token"` and continue with `curl -o /tmp/list.txt -w "%{http_code}" …/iam/security-credentials/`, `aws sts get-caller-identity` and `aws s3api put-object`.

Cause 3 of 3: a Failed invocation reports an empty StandardErrorContent, so the failure carries no diagnostic at all.
  AWS: when a RunShellScript invocation ends non-zero, GetCommandInvocation reports the script's own stderr in `StandardErrorContent` beside the non-zero `ResponseCode` and `StatusDetails`=`Failed`; for a line naming a program the shell cannot find, that stderr is the shell's own diagnostic — fixed text of the form `<program>: command not found` whose only variable part is the program name taken from the failing script line (recorded behavior only for the exact per-shell wording; the requirement is that a non-empty diagnostic accompanies a Failed status).
  Emulator: `GuestRun` (services/service-com-amazonaws-ec2-amazonec2/src/state/guest_commands.rs) carries only `output` and `status` — there is no stderr stream in the seam at all — so a failed invocation answers `StandardErrorContent` `''`.
  Why: a client cannot distinguish a missing interpreter from a syntax error, a denied call or a killed probe; all look like an empty `Failed`, and automation that classifies or retries on `StandardErrorContent` has nothing to read. These checks' own diagnostics degrade to `stderr=''`.
  Fix: SSM's invocation-result projection and the GetCommandInvocation serializer — carry the session's stderr into `StandardErrorContent`, consistently with `StatusDetails` and `ResponseCode`.
  Traces: ec2__iam__s3__ssm.xsvc-ec2-3-imds-credentials-withdrawn-after-disassociate-iam-instance-profile (assertion ends in `stderr=''`); the sibling check reaches its stdout assertion first and reports an empty JSON line set.
