# IVS native RTMPS live path still never goes LIVE: an out-of-process ffmpeg publish to the announced ingestEndpoint leaves GetStream refusing with 404 ChannelNotBroadcasting

> _Note: this issue was identified against the code base at commit `828474cb0b88792fe721eac89f3b3c78ba0887f9`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
GetStream

## Description
REOPENS 20261125T072712Z-ivs-createchannel-announces-an-ingestendpoint-no-out-of.md: its fix left the call refused. That issue was filed for this very check (its Issue-Trace-Ids is exactly ivs.native-rtmps-live-stream-lifecycle) and is marked fixed; the announced contribute authority is now accepted by the harness (no PublishedUrlRejected this run), but the live path it was supposed to open is still not served: through the whole publish, GetStream keeps refusing with 404 ChannelNotBroadcasting where AWS answers 200 with a LIVE stream, so the check now exhausts its budget instead of being rejected up front. This is not a new defect, it is the same cause one layer further in. Related: the FIXED 20261122T024053Z-ivs-the-channel-rtmps-ingest-data-plane-is.md (same cause, earlier fix), and the OPEN 20261124T065254Z-ivs-reopens-ivs-channel-rtmps-ingest-remains-undialable-createchannel.md and 20261023T004057Z-ivs-7-behavioural-divergences-error-messages-dropped-on.md (Cause 7) — neither carries this check on its replay key (they carry ivs.rtmps-ingest-live-stream-lifecycle and ivs.rtmps-ingest-native-protocol-round-trip), so this check would otherwise be closed unrun. The OPEN 20261125T153458Z-ivs-5-net-new-causes-announced-channel-addresses.md constrains only the FORM of the announced members, not whether a publish to them brings a channel live.

Cause 1 of 1: an RTMPS publish from a process OUTSIDE the emulator to rtmps://<channel.ingestEndpoint>/app/<streamKey.value> never brings the channel live, so no read ever observes a LIVE stream and the entire live leg of the service is unobservable.

AWS: Smithy (com.amazonaws.ivs, restJson1) — CreateChannel POST /CreateChannel 200 -> {channel: Channel, streamKey: StreamKey}; Channel$ingestEndpoint targets IngestEndpoint, a plain string with no @length/@pattern, documented "Channel ingest endpoint, part of the definition of an ingest server, used when you set up streaming software"; StreamKey$value is @sensitive and is the secret the encoder authenticates the publish with. GetStream(channelArn required, @length 1..128, @pattern ^arn:aws:ivs:[a-z0-9-]+:[0-9]+:channel/[a-zA-Z0-9-]+$) -> {stream: Stream} with Stream$state targeting StreamState (values LIVE, OFFLINE) and Stream$streamId @length 26..26 @pattern ^st-[a-zA-Z0-9]+$; errors ChannelNotBroadcasting @httpError 404 (doc "The stream is offline for the given channel ARN"), ResourceNotFoundException 404, ValidationException 400. PutMetadata POST /PutMetadata, success code 204. StopStream POST /StopStream 200. GetStreamSession -> {streamSession}. Recorded behavior: once an encoder completes the RTMPS handshake and publishes with the channel's stream key, GetStream answers 200 with stream.state == "LIVE" and a streamId within seconds; PutMetadata on that channel is accepted (204); StopStream is accepted (200) and GetStream afterwards answers 404 ChannelNotBroadcasting whose message is the fixed text "Channel: " + the request's channelArn + " is not currently online" (the ARN is the only variable part, taken from the request); the stream session for that streamId then reports both startTime and endTime.

Emulator: CreateChannel answers 200 and announces an ingestEndpoint the harness now accepts, and the crate does open a contribute plane (services/service-com-amazonaws-ivs-amazoninteractivevideoservice/src/state/ingest_plane.rs opens one TCP socket per deployment, negotiates in-band TLS for rtmps:// and serves the RTMP wire in src/state/ingest_plane/ingest_plane/rtmp_wire.rs) — but a genuine out-of-process ffmpeg FLV publish to rtmps://<ingestEndpoint>/app/<streamKey.value> never results in a LIVE stream: every GetStream poll keeps answering 404 ChannelNotBroadcasting, state.start_stream/accept_publish is evidently never reached for that publish, and the check consumes its whole budget in the LIVE poll ("Check timed out after 60.0s"; the check polls GetStream every 3 s for up to 90 s and asserts stream.state == "LIVE"). Because the LIVE state never arrives, every later leg is unreached: PutMetadata while live (expected 204), StopStream (expected 200), the revert to 404 ChannelNotBroadcasting with the offline message, and the ad-configuration ValidationException while LIVE. Hypothesis (not stated by the model or the recording): either the rtmps:// TLS negotiation on the contribute socket is not completed for an ffmpeg publisher, or the handshake/connect/publish exchange of the wire does not reach PublishStreamRequested, so accept_publish never runs.

Why: a client that uses IVS the way AWS documents it — CreateChannel, read channel.ingestEndpoint and streamKey.value, point an encoder at rtmps://<ingestEndpoint>:443/app/<streamKey>, poll GetStream until LIVE, PutMetadata, StopStream — cannot get a channel live against this emulator. The LIVE stream state, metadata insertion while live, the StopStream unwind, the stream session's start/end times and the whole live-path error semantics are unobservable, so broadcaster and player code that works against AWS fails here at the contribution step.

Fix: the contribute plane and the state it drives — the RTMP/RTMPS wire of the ingest plane (its in-band TLS negotiation, the server handshake and the connect/releaseStream/publish command exchange) must admit an out-of-process encoder's publish authenticated by the channel's stream key and write the LIVE Stream and its session that the GetStream/GetStreamSession handlers already read, and unwind it on StopStream, publisher exit or channel delete.
