# lambda__s3: a presigned S3 GET the emulator itself minted is refused 403 InvalidAccessKeyId, so no in-function HTTP client (python http.client, node https.get, node global fetch) ever reads the object

> _Note: this issue was identified against the code base at commit `95874034a8b8f8d63ab74cd551a8e6e28bd2f3c9`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
GetObject

## Description
REOPENS 20261115T013003Z-lambda-s3-a-presigned-s3-url-the-emulator.md: its fix left the call refused. That report's cause (the in-function egress router not attributing a path-style presigned URL on the emulator's own endpoint to s3, failing ENOTFOUND) is genuinely gone — the request now leaves the sandbox and reaches S3 — but the call it unblocked is answered HTTP 403 InvalidAccessKeyId instead of 200 with the object's bytes, for every in-function HTTP client, so none of these checks passes.

One net-new root cause, grounded in four failing behavioral checks the replay report left unmarked (no ALREADY FILED marker, no OWNED-by marker). Related open issues that do NOT carry these checks' replay keys and so do not cover them, named here for the fixer: 20261027T190000Z-s3-legacy-query-credential-presigned-get.md (service s3, grounded in s3.multipart-upload-and-presigned-get-round-trip) describes the framework-level refusal of the legacy query-credential form and records the core change it needs; 20261124T120026Z-lambda-s3-the-presigned-s3-get-minted-against.md is scoped to the earlier failure point of one of these checks (the tamper step aborting because the minted URL carried no SigV4 signature to alter) and not to the refusal the control leg now gets; 20261121T130631Z-lambda-s3-a-nodejs22-x-handler-s-global.md is scoped to the in-handler 'TypeError: fetch failed' egress fault, which no longer occurs; 20261109T220008Z-smoke-query-string-presigned-sigv4-requests-are-refused.md owns the same refusal only under the _smoke heading.

Cause 1 of 1: a presigned GetObject URL that this emulator's own presigner minted, fetched unmodified and unexpired by credential-less code, is refused HTTP 403 with <Code>InvalidAccessKeyId</Code> instead of being served 200 with the object's bytes. The refusal is independent of the client: it reproduces from a python3.12 handler using http.client.HTTPSConnection, from a nodejs22.x handler using node:https get, and from a nodejs22.x handler using global fetch. Failing check ids: lambda__s3.function-handler-http-client-fetches-a-presigned-url, lambda__s3.nodejs-handler-https-get-fetches-a-presigned-url, lambda__s3.nodejs22-global-fetch-reads-presigned-object, lambda__s3.nodejs22-global-fetch-tampered-presigned-url-rejected.

  AWS:      Smithy (com.amazonaws.s3#AmazonS3): GetObject is GET /{Bucket}/{Key+} with http code 200 and models exactly two errors — InvalidObjectState (403) and NoSuchKey (404). InvalidAccessKeyId is not a modeled outcome of GetObject at all, and nothing in the model distinguishes a query-string (presigned) credential from a header credential: the signing location is a protocol concern. Recorded/documented behavior for the presigned form: AWS accepts the credential in the query string in either presentation — the SigV4 form (X-Amz-Algorithm/X-Amz-Credential/X-Amz-Date/X-Amz-Expires/X-Amz-SignedHeaders/X-Amz-Signature) or the legacy form (AWSAccessKeyId/Signature/Expires, AWS General Reference, 'Authenticating requests: using query parameters') — and serves an unexpired, correctly signed presigned GET of an existing key with HTTP 200 and the object's exact bytes, with the stored Content-Type (https://docs.aws.amazon.com/AmazonS3/latest/userguide/ShareObjectPreSignedURL.html). The only presigned refusals AWS words this way are: a credential naming a key the account does not know -> 403 Code InvalidAccessKeyId, Message 'The AWS Access Key Id you provided does not exist in our records.'; a signature that does not verify -> 403 Code SignatureDoesNotMatch, Message 'The request signature we calculated does not match the signature you provided. Check your key and signing method.' (both messages are fixed text, interpolating nothing from the request). The key in these URLs is the emulator's own credential — the same access key that authorizes the header-signed PutObject earlier in each check — so InvalidAccessKeyId is factually wrong here.
  Emulator: every one of the four fetches is answered HTTP 403 with body <Error><Code>InvalidAccessKeyId</Code><Message>The AWS Access Key Id you provided does not exist in our records.</Message><RequestId>…</RequestId><HostId>…</HostId></Error> (the RequestId/HostId are per-run values and no part of the requirement; the Code and the Message text are). Nothing in that message is derived from the request, i.e. the signature carried in the URL is never verified against the key the emulator itself issued. Hypothesis (neither the model nor the recording states it): the authentication layer recognises only one query-credential presentation, so a URL minted in the other presentation resolves no known key and is refused before the GetObject handler runs — consistent with the evidence in 20261124T120026Z that the presigner mints the legacy AWSAccessKeyId/Signature/Expires trio against this emulator. The refusal also makes the tamper check's negative leg unreachable: with the control leg refused 403 InvalidAccessKeyId, the emulator never produces the SignatureDoesNotMatch code and message AWS gives for an altered signature.
  Why:      Handing a presigned URL to code that holds no credentials of its own is the documented way to give a Lambda handler (or a browser, or a CDN origin fetch) object access. Against this emulator that pattern never works from inside a function: the handler gets 403 rather than the bytes, and the error it is given says the access key does not exist — pointing the operator at credentials the request is deliberately not supposed to carry — so a client cannot tell this apart from a genuinely unknown key, and cannot reach S3's real presigned refusals (SignatureDoesNotMatch for a tampered or re-signed URL, NoSuchKey for a missing object). Error handling written against AWS's codes and messages is never exercised and breaks in production.
  Fix:      the S3 request-authentication / signature-verification layer that runs ahead of the GetObject handler (the presigned-credential recognition and verification path), together with whatever mints the URL, so that the presentation the emulator's presigner emits is the presentation its authenticator verifies. A presigned GET of an existing key whose signature verifies and whose expiry has not passed must be served 200 with the object's bytes and its stored Content-Type; 403 InvalidAccessKeyId must be reserved for a credential naming a key the emulator does not know, and a non-verifying signature must be refused 403 with Code SignatureDoesNotMatch and the fixed message AWS words for it. The in-function egress routing half is already fixed and must stay fixed (the requests do now reach S3).
  Traces:   lambda__s3.function-handler-http-client-fetches-a-presigned-url (python3.12 http.client.HTTPSConnection GET); lambda__s3.nodejs-handler-https-get-fetches-a-presigned-url (node:https get); lambda__s3.nodejs22-global-fetch-reads-presigned-object (nodejs22.x global fetch); lambda__s3.nodejs22-global-fetch-tampered-presigned-url-rejected (control leg, the untouched URL).

## Evidence
Four failing checks, all [mismatch], same emulator answer.

1) lambda__s3.function-handler-http-client-fetches-a-presigned-url
Expected (AWS): the handler's http.client.HTTPSConnection GET of the presigned URL answers status 200 and exactly the bytes PutObject wrote.
Actual: 'AssertionError: http.client.HTTPSConnection GET answered status 403, expected 200: {\'status\': 403, \'bodyB64\': ...}' — the decoded body is <Error><Code>InvalidAccessKeyId</Code><Message>The AWS Access Key Id you provided does not exist in our records.</Message><RequestId>…</RequestId><HostId>…</HostId></Error>.

2) lambda__s3.nodejs-handler-https-get-fetches-a-presigned-url
Expected (AWS): https.get answers 200 with the object's bytes.
Actual: 'AssertionError: https.get answered status 403, expected 200: {\'status\': 403, \'bodyB64\': ...}' — same InvalidAccessKeyId body. Note the ENOTFOUND 'addresses no service this emulator serves' fault reported for this check in 20261115T013003Z is gone; the request now reaches S3 and is refused.

3) lambda__s3.nodejs22-global-fetch-reads-presigned-object
Expected (AWS): typeof fetch == 'function' (it is), and fetch(url) -> status 200, ok true, body == the text PutObject wrote, content-type 'text/plain'.
Actual: 'AssertionError: fetch of the presigned GetObject URL: status 403, ok False; body \'<Error><Code>InvalidAccessKeyId</Code><Message>The AWS Access Key Id you provided does not exist in our records.</Message>…</Error>\''.

4) lambda__s3.nodejs22-global-fetch-tampered-presigned-url-rejected
Expected (AWS): the untouched presigned URL answers 200 with the stored body (control), and only the altered URL is refused 403 with Code 'SignatureDoesNotMatch' and Message 'The request signature we calculated does not match the signature you provided. Check your key and signing method.'
Actual: 'AssertionError: control: the untouched presigned URL answered 403 with body \'<Error><Code>InvalidAccessKeyId</Code>…\', expected 200 and the stored body' — the control leg is refused, so the SignatureDoesNotMatch path is never reached.

In all four, the access key in the URL is the emulator's own credential: the header-signed CreateBucket/PutObject calls earlier in the same check are authorized with it and succeed, so 'does not exist in our records' contradicts the emulator's own state. Fixed text of the diverging message is 'The AWS Access Key Id you provided does not exist in our records.'; RequestId and HostId are per-run values and are not part of the requirement.

## Steps to Reproduce
1. git_clone() the project and boot the emulator built from the checkout.
2. s3:CreateBucket <bucket> (with CreateBucketConfiguration.LocationConstraint when region != us-east-1); s3:PutObject(Bucket=<bucket>, Key='fetch/object.txt', Body=<some text>, ContentType='text/plain'). Both are header-signed with the emulator credentials and succeed.
3. Generate a presigned GetObject URL for that object against the emulator (ExpiresIn=300..600), signed for the object's own S3 URL on the emulator's endpoint.
4. Fetch that URL unmodified, with no credentials of their own, from each of: a python3.12 handler using http.client.HTTPSConnection/HTTPConnection; a nodejs22.x handler using node:https get; a nodejs22.x handler using global fetch. In every case Invoke answers StatusCode 200 with no FunctionError, and the handler reports status 403 with body <Error><Code>InvalidAccessKeyId</Code><Message>The AWS Access Key Id you provided does not exist in our records.</Message>… — AWS answers 200 with the object's exact bytes and Content-Type 'text/plain'.
5. Alter one character of that URL's signature and fetch it again: AWS answers 403 with Code SignatureDoesNotMatch and Message 'The request signature we calculated does not match the signature you provided. Check your key and signing method.'; the emulator cannot reach that path because it already refuses the untouched URL.
